# 既存のテストを見直す（消す・まとめる）

番号は CLAUDE.md「原則」の番号。「3問」「1問目」等は、[testing.md](testing.md)「そのテストは要るか（3問を順に）」の問いを指す。

## 消す・まとめる前に、残す側が落ちるかを見る

- テストか表の行を消す・まとめるときは、どの経路で消すものでも、前の版にあって後の版に無いもの1本ごとに、それが落ちる実装の
  壊れ方（比べ方を1つ変える・境界を1つずらす・値を定数へ変える）を1つ書く。その壊れ方で、前の版の消すテストが落ち、残す側
  （まとめた先の表・含むとした広い方・移した先・低い方）が次のどちらかになることを見てから消す。壊れ方を当てて戻すのは、
  共通の道具で行う（例: `scripts/break_tests.py`。使い方はその先頭）。（原則8・11）
  - (a) 残す側が落ちる。
  - (b) その壊れ方は作れない: 型・制約・宣言の検査（tsc・mypy・DBの制約・構造のテスト）が止める。止める検査を壊した版で回し、
    落ちることを見る。型の計算を自前で書いたもの（パスの文字列から引数の型を導く等）は、崩してもtscが通るので(b)に数えない。
- 前の版の消すテストがその壊れ方で落ちないなら、壊れ方が当たっていないので書き直す。前の版で落ちて(a)(b)のどちらにも
  ならなければ、残す側を直す（表の補助が見る値を足す・行を足す）か、消さずに残す。（原則11）
- 壊れ方が書けないものは、確かめずに消す。当たるのは、何も見ていないもの（1問目の恒真式）・宣言の書き写し（宣言の値を変える
  ことを壊れ方に数えない）・約束ごと消したテスト（見ていた約束が Pull Request の課題の「消した約束」か「変えた約束」の前の側に
  当たり、見ていた実装を同じ差分で消したもの）である。並び・値が利用者に見える振る舞いを決める宣言は書き写しではないので、
  並びを入れ替える・値を変える壊れ方を当てる。約束だけを変えて実装が後の版に残るテストは、残った実装に壊れ方を書く。（原則8）
- 同じ側の行（通る書かれた比べ方のどれでも、残す側の入力と同じ側にある行。「同じ側の値を足さない」で消す・まとめる行と、
  3問目の「狭い方を消す」で消す行のうち入力が広い方と同じ側にあるもの）には、書かれた比べ方の片側をまるごと変える壊れ方
  （向きを反対にする・境界を1つずらす・比べ方を外して常に片側の結果にする・値を残す行の答えと違う定数へ変える）だけを当てる。
  同じ側の中で答えを分ける壊れ方（別の比べ方へ置き換える（`in`を`==`へ）・書かれていない比べ方を足す（`if a:`を
  `if a and not b:`へ）・書かれた値の並び（`IN (…)`）から1つ外す・書かれていない既定値を足す（`?? 0`）・定数を残す行の答えに
  合わせる）は当てない。（原則11）
- Pull Request の本文の検証に、消した・まとめたテスト1本につき1行の表で、壊れ方と結果（(a) 落ちたテストの名前・(b) 止めた検査と
  その出力・壊れ方が書けない理由（恒真式・宣言の書き写し・約束ごと消した））を書く。（原則2・11）
  - 1本は、前の版にあって後の版に無いテスト（関数・`it`）と、表から消した行である。表の行を持つテストを丸ごと消したときは、
    中の行ごとに1本と数える（テストの実行が数える本数と同じ）。
  - 同じ側の行は、どの書かれた比べ方（実装のファイルとその比べ方）の同じ側かも書く。
  - 約束ごと消した行は、当たる課題の約束の行と、消した実装を書き、変えた約束なら新しい約束を見るテストの名前も書く。消した実装は、
    名前を持つもの（関数・定数・印）を丸ごと消したならその名前を、持ち主（関数・部品・ハンドラ）が残って中の一部だけを消したなら、
    持ち主（ファイルと、名前か画面の位置）と、消した一部が使っていた名前を書く（例: `UsageGuide.tsx`の✕のボタンの`onClick`から
    消した`onEndRef.current()`の呼び出し）。
- 消す・まとめる・題名を変えるテストを名指す設計書の行は、同じ差分で直す。手を入れたテストのファイル名を`docs/`で grep し
  （例: `grep -rn 'legends.test' docs/modules`）、そのテストが確かめる・固定すると書いた行があれば、保証の今の置き場（残す側の
  テストとその題名・型・源泉の宣言）に合わせて書き直す。（原則3・4）
- 対象モジュールの行を1つも実行していないテスト（`backend/scripts/audit_test_rewrite.py`が出す）は、それだけで要らないと決めず、
  3問へ通す。定数・型宣言（SQL文字列の定数・規則表・Pydanticの`Field`制約・`Protocol`）を見るテストは、import時に評価されるので
  対象の行を実行しない。（原則10）

## テストを変異テストで見直す（効き・重なり・隔離・書き方）

- 変異テストの測りから、足す（効き）・直す（隔離・書き方）・消す（重なり）を同じ測りで出し、消す側だけを見ない。（原則5・8）
- 測りが見ない所を確かめるテストは、変異を見つけないことを理由に消さない。見ない所は、関数の外（モジュールの直下の表・定数・
  既定値）・変異を作らない所（`backend/scripts/mutation/setup.cfg`が外すファイルと、ログと警告の行）・部分どうしのつなぎの
  食い違い・本番のデータで初めて出る問題・テストの名前と例が振る舞いを言葉で説明する役である。（原則10）

### 効き: 変えた所の生き残りにテストを足す

- `backend/app`を変えた Pull Request で、変えた行に出た生き残り（どのテストも見つけない変異）には2問目を当てる。壊れるものが
  言えるなら、その壊れ方で落ちるテストを足す。言えない（振る舞いが変わらない・丸めの桁のように外へ効かない）なら足さず、
  本文の検証にその理由を1行で書く。（原則5・11）

### 重なり: 2回続けてほかと重なったテストを消す

- 重なりで消すのは、前の測りと今の測りの両方で候補になったテスト関数だけにし、1回の測りでは消さない。測りのあとに実装や
  テストが変わると重なりも変わり、1回で消すと、あとから効くはずだったテストを失う。（原則10）
- 消したあとに落ちたテストが、消したテストの残す状態に頼っていたなら、落ちた側が自分で用意する形に直してから消す。消した
  テストを戻して通すだけで終えない。（原則9）
- 本文の表（上の「消す・まとめる前に、残す側が落ちるかを見る」）は、確かめに使った変異と結果で書く。（原則2）

### 隔離: 並びで落ちるテストは、汚した側を探して直す

- 並びを変えた回にだけ落ちるテスト（汚される側）は、その前に同じプロセスで走って状態を残したテスト（汚す側）を探し、状態を
  残さない形に直す（片付け方は testing-scaffold.md「テストの足場で、本来のNGを覆わない」の片付けの箇条）。直すまで、汚す側と
  汚される側のどちらも重なりの候補にしない。（原則9）

### 書き方: 測りから出た形を、型として足す

- 測りから出た書き方の候補（`review.json`の`writing`）は1本ずつ3問へ通す。見直して出た形のうち機械で見分けられるものは、
  下の「消すべきテストの型」へ行を足し、ソースを読む検査にも足す（置き場は testing-structure.md「ソースを読む検査は、専用
  ディレクトリへ置く」）。（原則9）

## 消すべきテストの型

- 次の型に当たるテストは書かず、見つけたら消す。（原則8）

| 型 | 見分け方 |
|---|---|
| **正しく直すと落ちるテスト** | 実行せずに、SQL文字列やパスへ特定の名前が含まれることをアサートする |
| **空振りの検知器** | 「Xが作る形を検証する」と書きながらXを呼ばず、期待値を手で書いている |
| **宣言の書き写し** | 定数・モデルの既定値・レジストリの中身をテスト側へ再掲して突き合わせる。ただし宣言の並び・値が利用者に見える振る舞い（地図に描く順・既定で選ばれる項目）を決めているなら、書き写しではなく振る舞いの確かめである。宣言に対して書いてよいのは、型・導出で保証できないときの、**導出した母集団すべてに対する不変条件**（要素が1つ増えたときに発火するもの。testing.md「そのテストは要るか（3問を順に）」の「本番のデータそのものに対する不変条件」）だけで、手で名指しした数件に対する検査は書かない（設計原則 構造仕様12） |
| **恒真式** | `set(versions) == set(TILE_SHAPES)`（同じ内包表記の結果を同じ定数と比べる） |
| **効いていない除外リスト** | ガードに付けた除外の一覧（効いているかを測っていない一覧には、存在しないファイル名や、先行条件で既に弾かれるものが残る） |
| **消したものを見張るアサーション** | `assert not cleared`のように、実装から消した機構が呼ばれないことを確かめる |
| **等価テスト** | 新旧2実装の出力一致。代わりに、**入力に対するあるべき値**を書いた期待値テストを**生きている1本の実装へ当てる**。移行が終わったら等価テストは消す |
| **カバレッジの水増し** | 「落ちるとき何が壊れるか」に答えられない。`MIN <= MAX`・`isinstance(x, int)`・定数への等値 |
| **実装の規則の再実装** | 実装が「名称に『特別警報』を含むか」で決めているのを、テストも同じ規則で期待値を作る |
| **型が保証していることの検査** | 戻り値が3値の`Literal`なのに「3値のいずれかへ落ちる」を確かめる |
| **本番に生えたテスト専用の口の検査** | テスト専用の初期化関数（`reset_*_for_testing()`の類）が状態を空にすることを確かめる |
| **宣言から作った足場へ宣言を当てる** | 宣言された全クラスについて`em.lc_{key}`が読めることを、`lc_{key}`という列を自分で用意して確かめる。宣言された語彙の全件が`= ANY(:語彙)`で真になることを確かめる。**振る舞いがidごとに違わないなら、性質ごとに1件で足りる**。「宣言した列・値が実在するか」は実テーブル・実カタログへ通して確かめる |
| **テストのフィクスチャに対する不変条件** | `AXIS_DEFINITIONS`の全軸が排他チェックを通ることを確かめる（テスト中の中身は注入したフィクスチャ）。**その宣言がテスト中に差し替わるなら、全件の不変条件は書かない**。足場そのものを対象と名乗る足場のテスト（testing-scaffold.md パターン5）はこれに当たらない |

## 黙って縮退する分岐は、取り除いて実験する

- 例外を送出せずに縮退した結果を返す分岐（空を返す`return`・`.get(`・`x or y`・`except: pass`）が要るかは、コードを読んで、
  またはコメントの語（「通常は到達しない」「念のため」「防御的」）をgrepして決めない。ASTで母集団を出し、1件ずつ縮退の道を
  外して（`x or y`→`x`・`d.get(k)`→`d[k]`・`except: pass`→`except: raise`・空の`return`→`raise`）テストを流して決める
  （外して戻すのは`scripts/break_tests.py`）。（原則10）
- 流した結果ごとに次のとおりにする。（原則8・10）
  - 落ちる → その縮退はテストが見ている。仕分けを終える。
  - 通り、その道を通る入力が本番で作れない（testing-backend.md「パターン8」）→ 到達できない分岐として消す。
  - 通り、作れる → 2問目を当て、言えるならその縮退で落ちるテストを足す。残すか消すかが設計書・コード・テストの主張から1つに
    決まらないときだけ、要確認にする。
- 要確認を群にまとめるときは、その縮退が起きる実データ上の条件を1つ挙げてからまとめ、挙げられないものは別の群にする。（原則2）

### 要確認の出し方

- テストの欠陥と判定する前に、対比先（宣言の隣のコメント・docstring が対で読めと指す関数）が本当に何を言っているかを読む。（原則10）
- 設計書・コード・テストの主張が食い違ったら、食い違いを生んだ判断をタスクの issue から探し、新しい判断に従って古い側を同じ
  差分で直す。それでも1つに決まらないときだけ問う（問いの形と届け方は[ask/SKILL.md](../skills/ask/SKILL.md)「問い」）。（原則1・4）
- テストの欠陥の問いは、判断材料に、利用者への約束と場面の次に、設計書・コード・テストがそれぞれ何を主張しているかを、
  同じ粒度で、実装の語を使わずに（「コードはこう実装されている」でなく「コードはこう主張している」）3行の表で置く。（原則2）
- 案は消すか残すかの2つにし、案ごとに、消したとき外で何が起きるかと、その道を通る呼び出し元の件数を書く。（原則2・10）

## テストと実装のずれを疑う印

- テストを見直すときは、次の印を探す。（原則8）
  - テストにだけ残った語彙: 実装から消えた機構の名前がフィクスチャ名・テスト名に残っている。
  - テストのために本番コードへ生えた宣言: 読み手が`backend/tests/`だけの公開名のうち、testing.md「確かめる高さ」の (a)〜(c) に
    当たらないもの。
