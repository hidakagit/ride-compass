# コードコメントの方針

コードのコメント・docstringを書く・見直すときと、コードを撤去するときの決まり。

## ルール

- **書くのは、実装を読んでも分からず、消すと今後の変更を誤らせる制約・理由だけで、現在形の一文にする**。実装を読めば
  分かることは、理由があっても書かない（原則6・8）。
- **経緯（いつ・誰の指摘で・どのタスクで・以前は〜だった・実測で〜だったため）は書かず、タスクの issue に書く**
  （[documentation.md](documentation.md)「用語集」）（原則4）。

## 判定基準（新しくコメントを書く/既存コメントを見直す/コードを撤去するとき）

- **コードを撤去するときは、消す文を1件ずつ下の2問へ通してから消す**。関数・ファイルと、そこにある文を、同じスクリプト・
  同じ一括置換で一度に消さない（原則8）。
- **経緯の言い回しは落とし、中身を残すかは、実装と対象の`docs/modules/*.md`を読んで次の2問で決める**。読んでも罠（下の
  行き先の(a)）かどうかが決まらないものは残す（原則8・10）。
  1. **消すと、今後の変更を誤らせる、実装から読めない制約・理由か。** いいえなら消す。
  2. **同じ中身が、コメントの外（`docs/modules/*.md`・型・assert・テスト）にもう在るか。** 在るなら消す。`docs/records/`にしか
     無いものは、まだ無いものとして数える。無ければ、モジュールを越えて効く知識は`docs/modules/*.md`へ今の事実として移してから
     消し、この1か所だけの制約は現在形の一文で残す（原則3）。
- **2問目で残す制約を型・assertで表せるなら、コメントでなくそちらにする**。テストへ置き換えるかは[testing.md](testing.md)
  「そのテストは要るか（3問を順に）」で決める（原則6）。

## 残すと決めたものの行き先

判定木で残すと決めたものは、中身の性質で置き場を決める。(e)を先に分ける（原則1・3）。

| 中身の性質 | 行き先 |
|---|---|
| **(e) 要件として採るかの判断が要るもの** | **タスクとして提案する**（[file-issue](../skills/file-issue/SKILL.md)「起票する」） |
| **(a) 罠（その機構が消えても再発する落とし穴）** | **コードのコメント**。その罠を置けるコードが1行も残っていないなら設計書へ |
| **(b) 実測値・値を選んだ根拠のデータ** | **設計書**。コメントには、値が満たすべき制約か合わせる先だけを1行で書く |
| **(c) 今の記述から落ちた含み**（否定形の知見（「◯◯では解決しない」）・弊害の形・条件・「安全側ではない」等の自己申告） | **コードのコメント** |
| **(d) 一般則・規約になりうるもの** | CLAUDE.md「ドキュメント階層」の表で決めた置き場 |

(b)(d)を文書へ移したら、同じ中身をコードに残さない。根拠を読む先を示すなら、文書と節の名前を書く（原則3）。

## 他所を写さない・代弁しない（docstringも同じ）

- **[documentation.md](documentation.md)「判定基準: その文書だけを読んで、正しさを検証できるか」の型（数え上げ・代弁・撤去済みの
  名指し・写し）を、コメントとdocstringにも当てる**。コメントとdocstringには、ほかに次の型が出る（原則3・10）。

  | 型 | 当たる形 | 代わりに書く |
  |---|---|---|
  | **無いものの説明** | そのファイルに無いものについて、なぜ無いかを書く | 書かない。足すと壊れるなら、罠（(a)）として残す |
  | **中身の無いポインタ** | 読む節を名指さない参照（「詳細は`◯◯.py`のdocstring参照」） | 要る事実をその場に1行で書くか、読む文書と節を名指すか、消す |
  | **定数の値の復唱** | `# TTL 900秒` の隣に `_TTL_SECONDS = 15 * 60` | その値でなければならない理由 |
  | **ほかの側の数値の書き写し** | frontend等の定数の値を写す | 数値を写さず、制約（「ポーリングの最大待機以上であること」）だけ |
  | **責務の自己申告** | 「ここは組み立てだけを持つ」 | 書かない |
  | **「次の1回」だけの指示** | 「3つ目の軸を追加する際は、このdictへ1エントリ足すだけでよい」 | 個数を言わずに足し方だけ |

- **backendのコメントは、frontendの実装（ファイル・関数・state）を名指さない**。書くのは境界の契約（APIのフィールド名・
  生成物の名前・受け取る側に任せること）だけにする（原則3）。
- 自分のモジュールの中で閉じた説明（引数の意味・不変条件・並行性の前提）は、ここで言う代弁・写しに当たらず、書いてよい（原則3）。

## テストのdocstringも対象（判定基準）

- **テストのdocstringには、対象の実装（そのテストがimportしているapp配下のモジュール全部）が書いていないことだけを書く**。
  書いてよいのは次の3つで、どれにも落ちない文は書かない（原則3・5）。
  - 落ちたとき、利用者の側で何が起きるか（例:「0点で塗ると、最良の色になってしまう」）
  - このファイルが見ない範囲と、どのファイルが持つか（例:「取得・キャッシュは`test_wbgt_service.py`が持つ」）
  - その確かめ方を選んだ理由（例:「刻みが0.1mなので、0.1m単位へ丸めてから比べる」）
- **モジュールdocstringの「対象は何か」と「ここでは見ないもの・どのファイルが持つか」は、実装と重なってよい**
  （[testing.md](testing.md)「ファイルの冒頭で責務を宣言する」）（原則3）。
- **実装のコメントの裏返し（実装の「XはYのため」を「Yでないと Xが壊れる」と書く）・アサーションの言い換え・外部仕様の典拠の
  再掲を書かない**（原則3）。

## 実例

経緯だけの記述を消し、今も成り立つ制約だけを残す。

```ts
// Before
// ユーザー要望（2026-08-31、…）: 既存の重み配分バー（帯グラフ、以前は表示専用）を、隣り合う2要素の
// 境界をドラッグして配分し直せるようにする...（AskUserQuestionでユーザーが選択）。

// After
// 境界を1つ動かすと、その両隣の2軸間でだけ重みが移動する（他の軸・合計自体は変わらない）。
```
