# コードコメントの方針

コードコメントを書く・見直す・撤去するときに読む。

## ルール

**書いてよいコメント**: 今のコードを安全に変更するために必要な、非自明な制約・理由を**現在形の一文**で書いたもの
（例は下の「実例」②）。実装を読めば分かることは書かない。

**書いてはいけないコメント**: 経緯——「いつ・誰の指摘で・改善計画Txxxで・以前は〜だった・実機/実測で〜だったため」という
時系列の記述。経緯はタスクの issue に書く（[documentation.md](documentation.md)用語集の「経緯」）。

## 判定基準（新しくコメントを書く/既存コメントを見直す/コードを撤去するとき）

**撤去のときは、コードと文を別の工程で判定する。** 関数・ファイルを丸ごと消す作業を1つの操作（同じスクリプト・
同じ一括置換）で済ませない。消す対象の文は、下の判定木へ1件ずつ通してから消すこと。

**既定は削除**。経緯の言い回し（「以前は」「改善計画Txxxで」「ユーザー要望…」「実機で…」等）に一致したコメントは、
以下の**両方**を満たすと確認できた場合に限り、経緯の言い回しだけを落として残してよい。どちらか一方でも満たさなければ
削除する——推測では残さない。

1. **そのコメントを消したら、今後の安全な変更が妨げられる非自明な制約・理由か？**
   （実装を読むだけでは分からないことか。実装を読めば分かることは、理由があっても書かない）
   - No → 削除（経緯自体を残したいなら該当タスクの issue へ——新規に書き足すのではなく、既にそこにある背景と
     重複していないか先に確認する）。
   - Yes → 2へ。
2. **その制約・理由は、コード内コメント以外の場所にまだ存在しないか？**
   （`docs/modules/*.md`に同じ内容がある、型・assert・テストで既に強制されている、のいずれにも該当しないか）
   **`docs/records/`は数えない。** **`docs/records/`にしか無いなら、それはまだ書かれていないのと同じ**として扱い、
   下の行き先表へ進む。
   - 該当する（docs/modulesに既にある、または強制されている） → 削除する
     （`docs/modules/README.md`索引で対象モジュールを確認できる）。
   - 該当しない、かつモジュール横断で再利用される知識なら → `docs/modules/*.md`側へ「現在の事実」として昇格してから削除する。
   - 該当しない、かつこの1箇所だけの局所的な制約なら → 経緯の言い回しだけ落として現在形の一文で残す（実例②参照）。

2の判断時に、コメントを型・assert・テストへ置き換えられないかも検討する。可能な場合は、自己強制できる形を優先する。

## 残すと決めたものの行き先

判定木を通って「残す」側になったら、**中身の性質で置き場を決める**（1件ずつ考え直さない）。(e)を先に分ける（残りの4つは採ると決まっているもの）。

| 中身の性質 | 行き先 |
|---|---|
| **(e) 要件として採るかの判断が要るもの** | **タスクとして提案する**（要望として起こすと保留で入り、起こした者が問う。既存のタスクに属するならその issue へ書く。[flow.md](../../docs/conventions/flow.md)） |
| **(a) 罠（その機構が消えても再発する落とし穴）** | **コードのコメント**。**迷ったら残す側（安全側）へ倒す**。ただしその罠を置けるコードが1行も残っていないなら設計書へ |
| **(b) 根拠・実測値（なぜこの値なのか）** | **設計書**。コメントへ実測値を書かない |
| **(c) 現行の記述から落ちた含み**（否定形の知見（「◯◯では解決しない」）・弊害の形・条件・「安全側ではない」等の自己申告） | **コードのコメント（残す）** |
| **(d) 一般則・規約になりうるもの** | **設計書**（`docs/conventions/*.md`・`docs/modules/*.md`） |

(b)(d)を設計書へ置いたら、**コード側には残さない**。値の近くに何か要るなら、「どの文書のどの節を読むか」を名指しした
1行だけにする——節の名前を書かないポインタは、下の「中身の無いポインタ」に当たる。

## 他所を写さない・代弁しない（docstringも同じ）

**判定基準は[documentation.md](documentation.md)と同じ——そのコメントを読むだけで正しいか誤りか判定できるか**。

数え上げ・代弁・撤去済みの名指し・写しは、
[documentation.md](documentation.md)「判定基準: その文書だけを読んで、正しさを検証できるか」の表の型がそのまま当たる。
コメントとdocstringには、ほかに次の型が出る。

| 型 | 当たる形 | 代わりに書く |
|---|---|---|
| **存在しないものの説明** | そのファイルに無いものについて、なぜ無いかを書く | 書かない |
| **中身の無いポインタ** | 「詳細は`◯◯.py`のdocstring参照」「上のモジュールdocstring『△△』節を参照」 | 要る事実をその場に1行で書くか、消す |
| **定数の値の復唱** | `# TTL 900秒` の隣に `_TTL_SECONDS = 15 * 60` | 値ではなく、その値でなければならない理由を書く |
| **外部の数値の書き写し** | 他の側（frontend等）の定数の値を写す | 数値を写さず制約（「ポーリングの最大待機以上であること」）だけ書く |
| **責務の自己申告** | 「ここは組み立てだけを持つ」「DBに依存しない」 | 書かない |
| **「次の1回」しか想定しない指示文** | 「3つ目の軸を追加する際は、このdictへ1エントリ足すだけでよい」 | 個数を言わずに足し方だけ書く |

**backendのコメントはfrontendの実装（ファイル・関数・state）を名指さない。** 書くのは境界の契約——APIのフィールド名・
生成物の名前・受け取る側に任せること——だけにする。同じファイルの外の定義を名指すときは「パス: 名前」の形で書く
（[documentation.md](documentation.md)「他のファイルの名前は「パス: 名前」で指す」）。

**「〜と同じ」は写経の自白**。書きたくなったら、コメントではなく実装を1本へ寄せる。

**同じ説明が1ファイル内で二重・三重になる**とき（モジュールdocstring・定数コメント・関数docstringに同じ制約が載っていたら）、
1箇所へ寄せる。

**インフラ・スキーマの移行は、説明の塊を丸ごと殺す**。移行のタスクでは、移行前を前提にした説明（接続方式・テーブル名・
配置先）を同じコミットで消す。

自分のモジュールの中で閉じた説明——引数の意味・不変条件・並行性の前提——は対象外で、これらは書いてよい。

## テストのdocstringも対象（判定基準）

**この方針はテストコードにも適用される。** 上の判定基準2は、**実装のコメント・docstringとテストのdocstringの間でも
成り立つ**——実装が既に言っていることをテスト側へ書き写さない。

**判定は1問**——その文は、対象の実装を読んでも書かれていないことか。**「対象の実装」はそのテストがimportしている
app配下のモジュール全部**で、責務のモジュール1本ではない。

答えがYesのものは次の3つのどれかに落ちる。落ちないなら、Yesの判定を疑う。

| 型 | 中身 |
|---|---|
| **落ちたとき、利用者の側で何が起きるか** | 表示・経路・所要時間がどう壊れるか（例:「0点で塗ると、最良の色になってしまう」） |
| **このファイルが見ない範囲と、どのファイルが持つか** | テストの分担（例:「取得・キャッシュは`test_wbgt_service.py`、地点の解決は`test_geo.py`（最寄りの点）が持つ」） |
| **テストの手法そのもの** | その確かめ方を選んだ理由（例:「刻みが0.1mなので、0.1m単位へ丸めてから比べる」） |

**モジュールdocstringの宣言部分は重なってよい。** 「対象は何か」と「ここでは見ないもの・どのファイルが持つか」は
宣言として要る（[testing-backend.md](testing-backend.md)「テストは、テストだけで成立させる」）。重なってよいのはこの2つだけで、本文は対象外。

書いてはいけない形:

- **実装のコメントの裏返し**——実装が「XはYのため」と書いているのを、テストが「Yでないと Xが壊れる」と書く
- **アサーションの言い換え**——`assert x is None`の上に「Noneを返す」
- **典拠の再掲**——外部仕様・公開値の出どころは実装が持つ。テストは突き合わせる値だけを持つ

**文面の類似は、読む順序にしか使えない。** docstringと実装の散文を文字列として比べて重なりの大きい順に読むのはよいが、
**しきい値で捨てる判断をしてはならない**。1文ずつ判定する。

## 実例（`RouteSettingsPanel.tsx`のコメントより）

**① 設計書と重複 → 削除**: 軸をカテゴリで分けて表示していた経緯を書いたコメント。
`docs/modules/frontend/route-settings-and-results.md`に同じ内容（カテゴリによるグルーピング表示は行わない）が現在形で
書かれているので、コード側は削除する（手がかりを残すなら、文書を名指した1行に圧縮する）。

**② 非自明な理由 → 経緯の言い回しだけ落として残す**（この例は経緯の言い回しを含まないので、そのまま）

```ts
// 下限は0ではなくWEIGHT_STEPにする——0まで下げるとその軸がチェックOFF相当（weight>0判定）に
// 化け、ドラッグ中に帯の区間数が変わってしまうため、ドラッグでは「チェックを外す」操作を
// 兼ねさせない（0まで下げたい場合は詳細ポップオーバーかチェックボックス自体を使う）。
```

「経緯を書かない」は「理由を書かない」ことではない。

**③ 日記的記述のみ → 削除**（技術的判断だけを残し、いつ・どう頼まれたかは削る）

```ts
// Before
// ユーザー要望（2026-08-31、…）: 既存の重み配分バー（帯グラフ、以前は表示専用）を、隣り合う2要素の
// 境界をドラッグして配分し直せるようにする...（AskUserQuestionでユーザーが選択）。

// After
// 境界を1つ動かすと、その両隣の2軸間でだけ重みが移動する（他の軸・合計自体は変わらない）。
```

## 適用範囲・実行タイミング

- **新規に書く/変更するコメントは、すぐにこのルールに従う**（既存コードの一掃を待たない）。
- **既存コードに残る経緯コメントの一掃**は一括では行わず、モジュール単位の個別タスクで計画的に実施する
  （着手するモジュールごとにタスクの issue へ起こす）。
- 判定基準2前半（設計書との重複確認）を行うときは（新しく書く・見直す・撤去する・一掃する）、必ず対象ファイルが属するモジュールの
  `docs/modules/*.md`を先に読んでから、人が読み比べる（[docs/modules/README.md](../../docs/modules/README.md)「着手の前に読む」）。

## 守り方

**この方針を機械的に強制する仕組みは持たない**（禁止語の一覧でコメント行を走査する検知器を作らない）。

守るのは書く人と、周期レビュー（`/review`）の「整合性」の観点である。例外は他のファイル・APIの名指しで、「パス: 名前」の
形の名前と、テストのファイル名・最上位のディレクトリから書いたパス・APIのパスが実在するかを
`backend/tests/structure/test_named_references.py`が見る（読む範囲は[documentation.md](documentation.md)「他のファイルの名前は
「パス: 名前」で指す」）。
