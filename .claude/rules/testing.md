# テスト方針

どのテストを書く・直す・消すときにも当てる決まり。書く場所と作業に固有の決まりは、同じディレクトリの`testing-*.md`が持つ。
番号は CLAUDE.md「原則」の番号。

## 確かめる高さ

- 振る舞いは、モジュールの公開の入口で確かめる。途中の手順（内部の関数の呼ばれ方・中間の値・呼ぶ順番）は確かめない。（原則5）
- テストから内部名（`_`で始まる名前）へ入らない。計算を直接確かめたい・入口から条件を作りにくいときは、その計算を公開名にする
  （`_`を外すか、公開の小さな部品へ切り出す）。途中を差し替えて済ませない。（原則5・8）
- テストが読むことだけを理由に公開してよいのは、次の3つだけにする。（原則8）
  - (a) 入力を値で受けて判断を持つ計算（モジュールの状態を読み書きしない関数・クラス）
  - (b) テストが本物の値から境界の入力を組み立てる定数（`count = ID_CHUNK_SIZE + 1` 等）
  - (c) テストが差し替えるプロセス境界の置き場（ディスクのパス・OSのファイル。`infrastructure/road_network_store.py: ROOT`・
    `infrastructure/container_memory.py: CGROUP_MEMORY_MAX`等）。本番がいつも同じ置き場を渡すだけなら、置き場を引数や設定から
    受ける形にしない
- 可変の状態（キャッシュ・接続・スケジューラ・時刻や世代の記録・集計）は、テストのために公開しない。テストが空にしたい・
  差し替えたい状態は、次の上から当たるもので直す。（原則3・8）
  1. 大域に持たず、持ち主のオブジェクトへ寄せて依存として注入する（例: `api/dependencies.py: get_gsi_tile_client`）
  2. 本番の寿命の口（閉じる・作り直す等、本番が呼ぶもの）を使う。無ければ本番が要る口として作り、足場もそれを使う
  3. どちらもできないものだけ、理由を定義の隣に書いた例外にする
- プロセス境界（網・ディスク・時計・Redis・ログ）は、必ず差し替える（backend には、テストから実の網へ出る要求を止める仕組みが無い）。
  差し替えてよいのは、プロセス境界（網・ディスク・時計・外部サービス）・契約の狭い層の境目（依存として注入されるService等。
  自分のDB（Repository）は除く）・本番の正本を持つ宣言のデータ（testing-backend.md「テストは、テストだけで成立させる」）だけに
  する。自分のdomainの関数と定数は、差し替えずに本物を通す。（原則5）
- 差し替えた相手への呼び出しを確かめるのは、状態を変える呼び出し（送る・書く）と、回数そのものが相手との約束（回数制限・
  利用の上限・課金）に効く外部サービスへの問い合わせだけにする。読むだけの相手は応答を差し替えるだけにし、呼ばれたか・何回・
  どの引数か、を確かめない。確かめる引数は、そのテストの関心事に絞る。（原則5）
- 呼ばれたかを記録するために自分の関数を包まない（本物へ委ねる記録用の包みも同じ）。順序の約束（「作る前に断る」等）は、
  入口の結果に現れる形（断ったときに外部サービスへ問い合わせない等）があればそれで確かめ、無ければテストにせず、理由を
  実装の隣のコメントに書く。（原則5）

## ループで実I/Oを繰り返さない

- N回の繰り返しを確かめるテストは、境界の直前までを実I/O（HTTPの要求・新しいDB接続）無しで埋め、境界の1〜2回だけを
  実際に実行する。（原則8・11）

## 単体で確かめるかを、コードの種類で先に決める

- テストを書く前・見直す前に、対象のコードを、判断（計算・業務の判断。込み入っているか、外れると利用者への約束が崩れるもの）を
  持つかと、つなぐ相手（呼ぶ他のモジュール・外部）が多いかで分け、次の表で確かめ方を決める。（原則5・8）

| 種類 | 例 | 確かめ方 |
|---|---|---|
| 判断を持ち、相手が少ない | domainの計算・分類・検証 | 単体で確かめる。下の3問と起こし直しは主にここへ当てる |
| 判断が無く、相手も少ない | 受け取った値を詰め替えて渡すだけの関数 | 確かめない。使う側のテストが通す（3問の1問目の「1行の委譲」） |
| 判断が無く、相手が多い（つなぎ役） | 相手を順に呼ぶだけのServiceやフック・子を並べるだけの部品・ルーター | 単体では書かない。上の入口（APIの経路・ページ）のテストで受け渡しを少し通す（3問の3問目の「別の高さで同じ判断を見ている」） |
| 判断を持ち、相手も多い | 判断と結線が1つの関数・部品に混ざったもの | テストの前に実装を分け、判断を相手の少ない部品へ出す（testing-rewrite.md「書きたくなったテストが、実装の歪みを教える」） |

## そのテストは要るか（3問を順に）

- テストを新しく書くとき・既存を見直すときは、次の3問を順に当て、先に決まった所で終える。（原則8）
  1. **構造が守っているか。**
     - 既に守られている → 書かない・消す。恒真式・1行の委譲（受け取ったprops・属性・参照をそのまま中へ渡す、呼び出し側の
       ハンドラを同じ名前の受け口へそのまま渡す（`onFocus`を中の`onFocus`へ）、値に単位を付けてstyleへ渡す
       （`` `${height}px` ``））・宣言の書き写し・型が保証していること（Pydanticの`Field`制約・`Literal`）・フレームワークの
       設定や結線・宣言から作った足場へ同じ宣言を当てる形・テストの足場に対する不変条件（見分け方はtesting-review.md
       「消すべきテストの型」）。自前の要素にハンドラを結ぶ形（✕を押すと`onClose`）は委譲ではなく、知らせ1つにつき1本残す。
     - 守れるが守っていない → 実装を直してから消す。型で通らなくする（`Field(min_length=1)`・`allow_inf_nan=False`）・片方を
       もう片方から導く・並びそのもので順序を表す（直し方はtesting-rewrite.md「書きたくなったテストが、実装の歪みを教える」）。
     - 守れない → 構造で表せない理由を1行で言えるときだけ2問目へ進む。言えないなら「守れる」側として扱う。
  2. **落ちるとき、モジュールの外の何が壊れるかを言えるか。** 外とは、利用者の画面・他モジュール・配信される値・保存される
     データ・運用するユーザーに見える振る舞いである。言えない → 書かない・消す。（原則5）
  3. **ほかに同じことを見ているものがあるか。**（原則3）
     - 別のモジュールの責務（テスト対象がファイル名の指すモジュールでない）→ そのモジュールのテストへ移す。移した先で同じことを
       見ているなら、移さず消す。
     - 同じファイルの別のテストが、同じ実装要素を広い入力か、狭い方を含む操作で見ている → 狭い方を書かない・消す（どのテストも
       メニューを押して開いてから確かめるなら、「押すまでメニューを出さない」は別に書かない）。
     - 別の高さで同じ判断を見ている → 判断は低い方（domainのテスト）に残し、経路のテストは受け渡し（判断の結果が応答のどこへ
       出るか）だけを見る。ただし経路ごとに受け渡しを1本は残す。E2Eとvitestの分担はtesting-e2e.md パターン4「何を対象にするか」。
     - どれも無い → 残す。ほかのテストと似ていても残す。
- 残すと決めたものも、同じ判断の入力違い（検証が断る形の1つずつ・分類の1つずつ・境界の両側）は、1つのテストの表の行にする。
  行には判断が分かれる入力だけを置き（境界は両側の2つ）、同じ側の値を足さない。（原則8）
  - 両側は、書かれた比べ方の両側である。`!== 0`なら「0」と「0でない」の2行で、負の値の行は、本番で負が来て扱いが違うときだけ
    足す。
  - 既定を持つ読み出しも比べ方に数える。`.get(k)`・`?.`は「キーが無い」と「ある」、`??`は「null・undefined」と「それ以外」、
    `or`は偽と真を両側に持つ。既定を持たない読み出し（`entry["k"]`・`obj.k`）は比べ方に数えない。1つの行が、いくつもの
    比べ方の片側を兼ねてよい。
  - 最小・最大で寄せる所には、境界ちょうどの行を書かない。
  - 同じ判断の関数を何か所で呼ぶときは、判断の両側はその関数のテストに置き、呼ぶ所ごとには寄せていることを示す1行だけにする。
- 本番のデータそのものに対する不変条件（「全材料が説明文を持つ」「参考点の値が有限」）も1問目を通し、型でも導出でも保証
  できないものだけを、そのデータを宣言しているモジュールのテストに、差し替えない節として分けて残す。（原則8）

## ファイルの冒頭で責務を宣言する

- テストのファイルの冒頭（backendはモジュールdocstring）に、対象と、ここでは見ないもの・それを持つファイルを書く。書けない
  ときは、書く前に責務を決める。「ここでは見ない」と書いた先は、そのファイルで確かめない。（原則3）

## 挙動を変えるなら、テストを先に書く

- 挙動を変える作業では、テストを先に足すか直してから、実装を変える。（原則11）

## 警告は既定でエラー

- 警告を許すのは、直せない・直すべきでないもの（依存ライブラリが自分の内部で出すもの等）だけにし、1件ずつメッセージまで
  名指して、許す理由と外せる条件を添える。（原則4・9）
- 警告を出すこと自体を確かめるテスト（ログの口のテスト等）は、出力を止めて（`vi.spyOn(console, ...)`に`mockImplementation`を
  付ける）中身を確かめ、全体の許可の一覧へ足さない。（原則9）

## テストが落ちたときの直し方

- 既存のテストを直してよいのは、振る舞いを変えたとき（誤った振る舞いを固定していたテストが落ちたバグ直しを含む）だけにする。
  新しい機能で既存のテストが落ちたら、既存の振る舞いを変えていないかを問い、変えていたなら振る舞いの変更に数える。（原則11）
- 作り替え（利用者から見た振る舞いを変えない変更）で落ちたテストは、落ちた箇所を直して済ませない。入口より下（内部の関数・
  途中の形）を見ていたものは入口の高さで起こし直し（testing-rewrite.md「既存テストを直さず、実装から起こし直す」）、入口の
  高さで見ていたものは、次の箇条のとおり結びつきを断つ。（原則9）
- 落ちたテストを、何に敏感だったか（口（呼び方・引数の形）の変更・準備や確かめに使った他の振る舞いの変更・共有のデータ
  （足場・フィクスチャの中身）の変更・時計や外部の変化）で分け、共通するものを1回で断つ（組み立ての関数へ寄せる・前提を
  引数で宣言させる・時計を固定する等）。1本ずつ直さない。（原則9）
- 小さな実装の変更でテストに大きな変更が要ったら、テストが多すぎるか実装に結びつきすぎている印として扱い、どちらかを直す案を
  出す。（原則9）
- 2周直しても同じ失敗が残るときは、何を見落としたかをタスクの issue に書いてから3周目に入る。（原則4）

## パターン10: 期待値が実行環境（OS）で変わる入力を使わない

- テストの入力に、OSによって解釈が変わる綴り（パスの区切り等）を使わない。パスは実行中の環境の区切りで組み
  （`str(Path("venv") / "Scripts" / "uvicorn.exe")`）、確かめたい性質（「拡張子つきでも読める」等）だけを入力に持たせる。（原則5）
- テストを通すために、実装に両方の区切りを読む分岐を足さない。（原則11）
