# 既存のテストを起こし直す

「3問」「1問目」等は、[testing.md](testing.md)「そのテストは要るか（3問を順に）」の問いを指す。

## 既存テストを直さず、実装から起こし直す

**作り替え・構造の変更で落ちたときは、落ちた箇所を直して済ませない。** 1ファイルずつ、**毎回一から書く**
（ファイルごと置き換える。部分編集しない）。振る舞いを変えたときは、その振る舞いを見ている該当のテストを
直す（どちらに当たるかは「テストが落ちたときの直し方」の②で決める）。
既存のテストを1本ずつ[3問](testing.md#そのテストは要るか3問を順に)へ通して消す・表の行へまとめる見直しは、起こし直しではなく
部分の直しとして行ってよい（消す・まとめる前の確かめは[testing-review.md](testing-review.md)「消す・まとめる前に、残す側が落ちるかを見る」が持つ）。

**始める前に、そのファイルが単体で確かめる種類かを決める**（[単体で確かめるかを、コードの種類で先に決める](testing.md#単体で確かめるかをコードの種類で先に決める)）。
つなぎ役なら起こし直さない——そのテストのファイルを消し、受け渡しは上の入口のテストへ寄せる（上の入口のテストが
既に通しているなら足さない）。判断と結線が混ざったものなら、先に実装を分ける（テストの起こし直しとは別の作業）。

1. **既存テストを開かずに**、**公開の入口から見える振る舞い**を箇条書きで列挙する（どの入力の組で何が返り、
   何が外へ出るか。エラー経路・表示文言・disabled条件を落とさない）。**期待値の出どころは仕様**
   （`docs/modules/*.md`・APIの契約・画面の約束）で、先にそこから列挙する。仕様が書いていない振る舞いは、実装から入口の言葉へ言い直して
   列挙する。**仕様と実装が食い違ったら、期待値をどちらかへ黙って合わせない。** 食い違いを生んだ判断をタスクの issue から探し、
   新しい判断に従って古い側を同じ差分で直す。1つに決まらないときだけ問いに回す（testing-review.md「要確認の出し方」）。
   **列挙の単位は分岐ではなく振る舞いである**（[確かめる高さ](testing.md#確かめる高さ)）。
   実装は、振る舞いの見落としを探す手がかりとして読む: `if`の両側、同じ判断を2度実装して
   いる経路（スカラーと配列・PythonとSQL）、モジュールが持つデータの不変条件、比較（`<`・`>=`）の
   境界ちょうどの値、画面部品が子の部品へ何を渡すか。**`if`にも分岐カバレッジにも現れない判断も
   手がかりにする**——`and`/`or`の各項・numpyのベクトル化された条件（`np.where`・`np.clip`等）・
   SQL文字列の中の条件・`dict.get`の既定値・剰余や`min`/`max`での寄せ・`Field(ge=…)`の宣言した
   範囲・ルーターの宣言（認証・`response_model`）等。それぞれが入口からどう見えるかへ言い直して
   列挙し、入口から見えないものは列挙しない。
2. 列挙した振る舞いを1つずつ[3問](testing.md#そのテストは要るか3問を順に)へ通し、残ったものだけを
   **新しいファイルとして**書き起こす（同じ判断の入力違いは表の行にまとめる）。**他のモジュールの実装を読まないと分からないことは
   書かない。**
3. **カバレッジで見落としを探す**（1ファイル分を書き終えてから当てる。書きながら測らない）。対象モジュールへ分岐カバレッジを当て、
   届いていない行・分岐を出す。**母集団は「同名のテストファイル」ではない**——先に
   `grep -rln --include='*.py' '<モジュール名>' tests` で母集団を出す。旧版の中身を読むのは手順4からで、手順1〜3では開かない。
   **frontendは手で組み立てず**、`frontend/scripts/audit-test-rewrite.mjs <実装>`で測る
   （出すもの・母集団の集め方・使い方はスクリプトの先頭）。
   **grepの母集団は間接的な消費者を落とす**——1行だけ孤立して見えたら、`--cov-context=test`でどのテストが通しているかを引いてから
   「無検査」と判断する。

   **分岐カバレッジは「どこを見ていないか」の検出器であって、母集団ではない。** 未到達を
   埋める前に3問を通す。**埋めなかった未到達は、なぜ埋めないかを1行ずつ残す。**

   **埋める前に、その入力が本番で作れるかを確かめる**（testing-backend.md「パターン8」）。**対象ファイルが作る値**
   （`_bin_count`が`[1, MAX_TIME_BINS]`しか返さない等）は実装を読んで必ず確かめ、
   **境界の向こうから来る値**（他モジュールの戻り値・DBの行）は、確かめるなら向こうの契約を
   1関数だけ読み、何を何のために読んだかを残す。
   **作れない組を使っていたら、テストを消すのではなく作れる組へ置き換える。**
   **作れない組でしか通らない分岐は実装の到達不可コードである。** 入力を作れる組へ直すと支えが外れ、撤去できる。
4. 既存テストのテスト名を並べ、新旧を突き合わせる。**旧版を開いてよい目的は「今のソース
   からは導けない過去の事情」だけ**である——回帰（過去のバグを刺したもの）と、実データ由来の
   事情。**構造を写すために開かない。**

   **旧版を物差しにしない。**
   - 2つのファイルを diff しない
   - 「新版は◯◯を落とした」と言わない
   - 旧版にあったからという理由で足さない
   - 一致率で新版の出来を語らない
   - **「今あるものから無駄を省く」形にしない**
5. 両方向を判定する。
   - **新版にしか無い**: そのまま残す。
   - **旧版にしか無い**: 下の4分類を通す。
6. **埋め残しを作らない。** 旧版にあって新版に無いものは必ずどれかへ振り分ける。

**起こし直しの成果は、判定の件数で報告する。** 4分類それぞれの件数を書き、とくに
**「列挙漏れ」の件数**と、**「責務外」「重複」で消した件数**を実測値として扱う。あわせてテスト本数・
行数（母集団のテストのファイルの`git diff --numstat`の増減。起こし直しの物差しはこれ1つにする。
変更全体の実装・テスト・文書の増減は別の数で、Pull Request の本文の「増減:」（`.github/pull_request_template.md`）に書く）を**前後の値つき**で書く。前の本数は、`origin/master` との合流点の版のテストを`pytest --collect-only -q`（frontend は `vitest list`）で数える。

**起こし直したあとのテストの行数は、前の行数を超えない。** 数えるのは手順3の母集団のテストのファイルの行で、
起こし直しのコミットの`git diff --numstat`の足した行から消した行を引いた値が0以下であることを、完了の条件にする。
超えたら、増えた分のテストごとに守るもの（落ちたら何が壊れるか）を1行ずつ書き、確かめる担当がそれで判断する。
見落としを無くすことと量を抑えることは両方を完了の条件にする。
行数を減らすために、補助の関数・ループ・共有の準備へ畳まない——減らすのは本数と確かめる対象で、
テストを読みやすくするなら少しの重複は残してよい。

**旧版にしか無いものは、次のどれかへ振り分ける。**

| 判定 | 見分け方 | すること |
|---|---|---|
| **重複** | 同じ実装要素を、別の入力・別の言い方で見ているだけ（分岐の同じ側・同じ早期return） | 足さない。「対比のため」「代表を変えて」も重複に数える |
| **責務外** | 実在のid・実データ・他モジュールの宣言に依っている | 足さない。持ち主のファイルへ移すか、消す |
| **列挙漏れ** | 実装の別要素なのに新版に無い（`if`の反対側・2つ目の経路・型でも導出でも保証できないデータそのものの不変条件） | **列挙をやり直す**。1件を足して済ませず、同じ数え方をした他の要素の漏れも探す。データの不変条件の漏れは、テストを足す前に型で通らなくできないかを見る |
| **上のどれとも言い切れない** | 同じ要素の別の入力に見えるが、重複と断じる根拠が無い（過去のバグを刺した回帰がここへ来る） | 3問を通す |

**旧版にしか無いものを「残す」と決めたら、なぜ自分の導出から漏れたのかを、次に導出する
人が読む場所へ1行足す。** 実装から導けるはずだったなら実装のdocstringへ、仕様に書かれていなかったなら
`docs/modules/*.md`へ書く。

**回帰と重複を一律のルール（印を付ける取り決め・消すたびにgit履歴を引く義務）で分けようとしない。** 表の「言い切れない」は3問へ送る。

**3問を当ててよいのは、起こし直し版に元からある検査と、表で「言い切れない」へ落ちたもの
だけである。** **旧版から取り込むのは、「言い切れない」から3問を通ったものと、下の「残すべきテストの型」だけ**で、
列挙漏れは旧版から戻さず、**列挙をやり直し、実装から自分で導く**。逐語で同じになったかどうかは関係がない。

**「残す」「移す」と決めた場でテストを書き換えない。** 移すなら移すだけ、残すならそのまま残す。
書き直したくなったら、起こし直しの側（列挙）で行う。

判定と理由は、Pull Request の本文の検証の表（[testing-review.md](testing-review.md)「消す・まとめる前に、残す側が落ちるかを見る」の4）に
テストごとに添える。**「重複だから消した」で止めず、3問のどこで決まったかを書く。**

**旧版の構造をそのまま引き受けない。** 「旧版の形のほうが強い」と思ったときは、その強さが
何に由来するかを言う。実在のid・実データに由来するなら、それは責務外である。

**テストが落ちたら、まず自分の前提を疑う。** 実装の欠陥だと決める前に、書いた性質が本当に成り立つかを確かめる。

## 残すべきテストの型（起こし直しで取り込む）

これは**旧版から取り込むかどうか**の判定で、3問とは別の問いである
（3問を通った検査のうち、**仕様と実装を読んで復元できないもの**だけが取り込む対象になる）。
仕様と実装から復元できるものは取り込まない。

| 型 | 見分け方 |
|---|---|
| **外部の権威との突き合わせ** | 期待値の出どころが公開値・配布物・実測で、コードのどこにも無い |
| **過去のバグを刺した回帰** | 「この入力で落ちた」という事実。由来（経緯）はタスクの issue が持つ（テストのdocstringへ経緯は書かない）。消すかどうかは3問で決める |

**「意図的に外した値」は残す理由にならない。** 除外を、値を名指しして「入っていない」と確かめるテストは書かない。
除外の理由は設計書（`docs/modules/*.md`）が持ち（実測値は[comments.md](comments.md)「残すと決めたものの行き先」の
(b) で設計書へ置く。宣言の隣に要るなら、その節を名指す1行だけ）、テストは書かない。残すのは**期待値の出どころが
テストの中にある**ものだけである。

## 書き終えたら、テストが触る外のシンボルを数える

テストが対象モジュール経由で触るシンボル（`engine.X`の`X`）をASTで集め、**対象ファイルの
定義**か**他モジュールからのimport**かに分ける。import側は1件ずつ「差し替えのseamか、
責務外か」を言う。

**テストファイルから直接importしてよい`app.*`は、対象モジュールと、対象の公開シグネチャが
要求する型だけ。** それ以外——他モジュールの**関数・サービス・例外・定数**——は触らない。
例外は、本番の状態を本番の口で作るもの（回数制限の上限まで埋める`infrastructure/rate_limiter.py: check_rate_limit`。testing-backend.md パターン1）で、
経路のテストが境界の直前までを実I/O無しで埋めるために、その口だけを読む。
入力を組み立てるのに要る値は、対象が受け取る形の値として書くか、対象の名前空間から読む。
**差し替えが要るのは[確かめる高さ](testing.md#確かめる高さ)が許すもの（プロセス境界・契約の狭い層の境目・
宣言のデータ）だけ**で、そのときは対象の名前空間で差し替える。

**対象が引数に取る型の中身の型（ノード・辺等）を真似た偽の型を作らない。** 実物が作るコストの無い型（frozen dataclass等）は
実物で作る（設計原則 構造仕様16「境界は、破られたときに落ちる形で表現する」）。

**この数え上げは手で組み立てない。** 起こし直しの監査は`backend/scripts/audit_test_rewrite.py`で出す（テストは手順3の母集団を並べて渡す。
出すものは道具の先頭）。**自分で書いたものにも当てる。**`njit`を通る対象は`--no-jit`を付ける。
出力は候補であって判定ではない。

## 書きたくなったテストが、実装の歪みを教える

**「この検査を書かないと守れない」と思ったら、まず実装が構造で保証できないかを問う。**
できるなら実装を直し、検査は消す。

| 書きたくなった検査 | 何が歪んでいるか | 直し方 |
|---|---|---|
| 2つの独立した宣言の関係（「Aの全要素がBにある」） | 片方がもう片方から導かれていない | **導く** |
| 戻り値だけでは2つの意味を区別できない（0が「宣言が0」か「未知」か分からない） | 既定値へ倒す設計が、正常と異常を同じ値にしている | 宣言の側を見る検査でしのがず、**呼び出し側が区別できる形**にできないかを問う |
| どんな入力でも通らない分岐がある | 起こり得ない状態への防御が残っている | **消す** |
| 常に空のフィールドを「空であること」で確かめたくなる | 公開契約に、配信されない値が乗っている | フィールドごと外す |
| 条件を作るのに他モジュールの実装へ寄りかかる（実在の材料を選んでrampにする等） | そのモジュールが他の判断へ強く結びついている | **差し替えて与える**。差し替えられないなら、依存の向きを疑う |
| 同じ偽の世界をテストごとに建て直す | 実装が大域から読んでいる | 大域に持たず、持ち主のオブジェクトへ寄せて注入する（直す順はtesting.md「確かめる高さ」の可変の状態の箇条） |

**100%にならない行が残ったら、まずそれが到達できる状態かを
問う**——到達できないなら、埋めるのではなく消す。
