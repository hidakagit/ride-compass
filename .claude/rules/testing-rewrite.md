# 既存のテストを起こし直す

番号は CLAUDE.md「原則」の番号。「3問」「1問目」等は、[testing.md](testing.md)「そのテストは要るか（3問を順に）」の問いを指す。

## 既存テストを直さず、実装から起こし直す

- 作り替え・構造の変更で、入口より下を見ていたテストが落ちたら、落ちた箇所を直して済ませず、1ファイルずつ毎回一から書いて
  ファイルごと置き換える（部分編集しない）。どの落ちたテストをここへ回すかは testing.md「テストが落ちたときの直し方」が決める。（原則9）
- 既存のテストを1本ずつ3問へ通して消す・表の行へまとめる見直しは、起こし直しにせず、部分の直しとして行ってよい（消す・まとめる
  前の確かめは testing-review.md「消す・まとめる前に、残す側が落ちるかを見る」）。（原則8）
- 起こし直す前に、そのファイルの対象が単体で確かめる種類かを決める（testing.md「単体で確かめるかを、コードの種類で先に決める」）。
  つなぎ役なら起こし直さず、テストのファイルを消して、受け渡しは上の入口のテストへ寄せる（上の入口のテストが既に通しているなら
  足さない）。判断と結線が混ざったものは、起こし直しとは別の作業として先に実装を分ける。（原則8）

### 振る舞いを列挙する

- 既存のテストを開く前に、公開の入口から見える振る舞い（どの入力の組で何が返り、何が外へ出るか。エラー経路・表示文言・
  disabledの条件を落とさない）を箇条書きで列挙する。期待値の出どころは仕様（`docs/modules/*.md`・APIの契約・画面の約束）で、
  先にそこから列挙し、仕様が書いていない振る舞いは、実装から入口の言葉へ言い直して列挙する。（原則10）
- 仕様と実装が食い違ったら、期待値をどちらかへ黙って合わせず、testing-review.md「要確認の出し方」で決める。（原則1・11）
- 列挙の単位は分岐でなく振る舞いにし、実装は見落としを探す手がかりとして読む。`if`の両側・同じ判断を2度実装している経路
  （スカラーと配列・PythonとSQL）・モジュールが持つデータの不変条件・比較（`<`・`>=`）の境界ちょうどの値・画面部品が子の部品へ
  渡すものに加え、`if`にも分岐カバレッジにも現れない判断（`and`/`or`の各項・numpyのベクトル化された条件（`np.where`・`np.clip`等）・
  SQL文字列の中の条件・`dict.get`の既定値・剰余や`min`/`max`での寄せ・`Field(ge=…)`の宣言した範囲・ルーターの宣言（認証・
  `response_model`）等）も手がかりにして、入口からどう見えるかへ言い直して列挙する。入口から見えないものは列挙しない。（原則5・10）
- 列挙した振る舞いを1つずつ3問へ通し、残ったものだけを新しいファイルとして書く（同じ判断の入力違いは表の行にまとめる）。
  他のモジュールの実装を読まないと分からないことは書かない。（原則3・8）

### カバレッジで見落としを探す

- カバレッジは1ファイル分を書き終えてから当て、書きながら測らない。対象モジュールへ分岐カバレッジを当て、母集団は同名の
  テストファイルでなく、対象を名指すテスト全部にする。測るのは監査の道具（backendは`backend/scripts/audit_test_rewrite.py`、
  frontendは`frontend/scripts/audit-test-rewrite.mjs`）で行う。（原則6・10）
- 届いていない行・分岐は見落としの候補で、母集団ではない。埋める前に3問を通し、埋めなかった未到達は、なぜ埋めないかを
  Pull Request の本文の検証に1行ずつ書く。（原則2・10）
- 未到達を埋める前に、その入力が本番で作れるかを確かめる（testing-backend.md「パターン8」）。対象ファイルが作る値（`_bin_count`が
  `[1, MAX_TIME_BINS]`しか返さない等）は実装を読んで必ず確かめ、境界の向こうから来る値（他モジュールの戻り値・DBの行）は、
  確かめるなら向こうの契約を1関数だけ読み、何を何のために読んだかを残す。（原則4・5）
- 作れない組を使っていたテストは、消さずに作れる組へ置き換える。作れない組でしか通らない分岐は、到達不可のコードとして撤去する。（原則5・8）

### 旧版と突き合わせる

- 旧版のテストを開くのは、振る舞いの列挙とカバレッジでの見落とし探しを終えてからにし、目的は今のソースからは導けない過去の
  事情（下の「残すべきテストの型」）を探すことだけにする。構造を写すために開かない。（原則10）
- 旧版を物差しにしない: 2つのファイルをdiffしない・「新版は◯◯を落とした」と言わない・旧版にあったからという理由で足さない・
  一致率で新版の出来を語らない・「今あるものから無駄を省く」形にしない。「旧版の形のほうが強い」と思ったら、その強さが何に
  由来するかを言い、実在のid・本番のデータに依る入力に由来するなら責務外として扱う。（原則10）
- テスト名を並べて新旧を両方向に突き合わせ、新版にしか無いものはそのまま残し、旧版にしか無いものは全部、次の表のどれかへ振り分けて
  埋め残しを作らない。（原則11）

| 判定 | 見分け方 | すること |
|---|---|---|
| **重複** | 同じ実装要素を、別の入力・別の言い方で見ているだけ（分岐の同じ側・同じ早期return） | 足さない。「対比のため」「代表を変えて」も重複に数える |
| **責務外** | 入力が実在のid・本番のデータ・他モジュールの宣言に依っている（期待値の出どころが外部の権威・実測なのは、下の「残すべきテストの型」） | 足さない。持ち主のファイルへ移すか、消す |
| **列挙漏れ** | 実装の別要素なのに新版に無い（`if`の反対側・2つ目の経路・型でも導出でも保証できないデータそのものの不変条件） | **列挙をやり直す**。1件を足して済ませず、同じ数え方をした他の要素の漏れも探す。データの不変条件の漏れは、テストを足す前に型で通らなくできないかを見る |
| **上のどれとも言い切れない** | 同じ要素の別の入力に見えるが、重複と断じる根拠が無い（過去のバグを刺した回帰がここへ来る） | 3問を通す |

- 3問を当ててよいのは、起こし直し版に元からある検査と、表で「言い切れない」へ落ちたものだけにする。旧版から取り込むのは、
  「言い切れない」から3問を通り、下の「残すべきテストの型」に当たる（仕様と実装から復元できない）ものだけにし、復元できるものと
  列挙漏れは旧版から戻さず、列挙をやり直して実装から自分で導く。逐語で同じになったかどうかは問わない。（原則10）
- 旧版にしか無いものを「残す」と決めたら、なぜ自分の導出から漏れたのかを、次に導出する人が読む所へ1行足す。書くのは実装を
  読んでも導けなかった前提だけで、実装のdocstring（実装の暗黙の前提）か`docs/modules/*.md`へ書く。（原則4）
- 「残す」「移す」と決めたテストは、その場で書き換えない。移すなら移すだけ、残すならそのまま残し、書き直したくなったら
  列挙の側で行う。（原則3）
- 判定と理由は、Pull Request の本文の検証の表（testing-review.md「消す・まとめる前に、残す側が落ちるかを見る」）にテストごとに添え、
  「重複だから消した」で止めず、3問のどこで決まったかまで書く。（原則2）
- 起こし直しの報告には、4分類それぞれの件数（とくに「列挙漏れ」の件数と、「責務外」「重複」で消した件数）と、テストの本数・
  行数（母集団のテストのファイルの`git diff --numstat`の増減。前の値は`origin/master`との合流点の版のテストで数える）・seams数
  （`backend/scripts/audit_test_rewrite.py`が出す）を、前後の値つきで証拠として書く。（原則2・11）
- **テストが落ちたら、まず自分の前提を疑う。** 実装の欠陥だと決める前に、書いた性質が本当に成り立つかを確かめる。（原則11）

## 残すべきテストの型（起こし直しで取り込む）

- 旧版から取り込むのは、次の型に当たるものだけにする。これは旧版から取り込むかの判定で、3問とは別の問いである（当てる順は上の
  「3問を当ててよいのは」の箇条）。（原則10）

| 型 | 見分け方 |
|---|---|
| **外部の権威との突き合わせ** | 期待値の出どころが公開値・配布物・実測で、コードのどこにも無い |
| **過去のバグを刺した回帰** | 「この入力で落ちた」という事実。由来（経緯）はタスクの issue が持つ（テストのdocstringへ経緯は書かない）。消すかどうかは3問で決める |

- 「意図的に外した値」は残す理由にしない。除外を、値を名指しして「入っていない」と確かめるテストは書かず、除外の理由は設計書
  （`docs/modules/*.md`）に置く（宣言の隣に要るなら、その節を名指す1行だけ）。残すのは、期待値の出どころがテストの中にあるもの
  だけにする。（原則3）

## 書き終えたら、テストが触る外のシンボルを数える

- 書き終えたら、自分で書いたテストにも、監査の道具（`backend/scripts/audit_test_rewrite.py`）でテストが触るシンボルを出し、対象
  モジュール経由で触るもの（`engine.X`の`X`）のうち他モジュールからのimportを、1件ずつ「差し替えのseamか、責務外か」を言う。（原則6・10）
- テストのファイルから直接importしてよい`app.*`は、対象モジュールと、対象の公開シグネチャが要求する型だけにし、他モジュールの
  関数・サービス・例外・定数は触らない。例外は、本番の状態を本番の口で作るもの（回数制限の上限まで埋める
  `infrastructure/rate_limiter.py: check_rate_limit`）で、経路のテストが境界の直前までを実I/O無しで埋めるために、その口だけを読む
  （testing.md「ループで実I/Oを繰り返さない」）。入力を組み立てるのに要る値は、対象が受け取る形の値として書くか、対象の名前空間から
  読む。差し替えは testing.md「確かめる高さ」が許すものだけを、対象の名前空間で行う。（原則3）
- 対象が引数に取る型の中身の型（ノード・辺等）を真似た偽の型を作らない。作るコストの無い型（frozen dataclass等）は実物で作る
  （設計原則 構造仕様16「境界は、破られたときに落ちる形で表現する」）。（原則5）

## 書きたくなったテストが、実装の歪みを教える

- 「この検査を書かないと守れない」と思ったら、書く前に、実装が構造で保証できないかを問い、できるなら実装を直して検査は書かない。
  歪みと直し方は次の表で決める。（原則8・9）

| 書きたくなった検査 | 何が歪んでいるか | 直し方 |
|---|---|---|
| 2つの独立した宣言の関係（「Aの全要素がBにある」） | 片方がもう片方から導かれていない | **導く** |
| 戻り値だけでは2つの意味を区別できない（0が「宣言が0」か「未知」か分からない） | 既定値へ倒す設計が、正常と異常を同じ値にしている | 宣言の側を見る検査でしのがず、**呼び出し側が区別できる形**にできないかを問う |
| どんな入力でも通らない分岐がある | 起こり得ない状態への防御が残っている | **消す** |
| 常に空のフィールドを「空であること」で確かめたくなる | 公開契約に、配信されない値が乗っている | フィールドごと外す |
| 条件を作るのに他モジュールの実装へ寄りかかる（実在の材料を選んでrampにする等） | そのモジュールが他の判断へ強く結びついている | **差し替えて与える**。差し替えられないなら、依存の向きを疑う |
| 同じ偽の世界をテストごとに建て直す | 実装が大域から読んでいる | 大域に持たず、持ち主のオブジェクトへ寄せて注入する（直す順は testing.md「確かめる高さ」の可変の状態の箇条） |
