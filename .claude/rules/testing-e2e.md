# E2Eのテストの書き方

番号は CLAUDE.md「原則」の番号。

## パターン4: フロントエンドのE2E（Playwright）→ 実機でしか出ないものだけを見る

### 何を対象にするか

- E2Eでは、実ブラウザ・本番ビルドでしか出ず、機械で判定できる次の3つの観点だけを確かめる。（原則5・8）

| 観点 | 例 | 何で判定するか |
|---|---|---|
| 1. 収まる・押せる | ヘッダーが幅からはみ出す、凡例の行がセルからはみ出す、下部のバーの下に潜り込んで押せない | `scrollWidth`/`clientWidth`・`boundingBox()`の実寸 |
| 2. ブラウザ・ランタイムの実挙動 | ブラウザ既定の動作（暗黙のフォーム送信・タッチ操作の割り当て）、実イベントが地図を通って届くか、MapLibreのWorker・描画・スタイル検証・`idle` | 実イベントを起こした結果・画素・コンソール |
| 3. カスケードの勝ち負け | `@layer`の外に置いたリセットがTailwindのユーティリティを潰す、モジュールCSSの詳細度が部品の既定サイズを踏む | `getComputedStyle`の計算後の値 |

- 決まった基準の無い見え方（配色が凡例と合っているか・縁取りが見えるか）はE2Eにせず、画面を撮って見る
  （[frontend-design-system.md](../../docs/modules/frontend/frontend-design-system.md)「実機確認の方法」）。DOMの状態・ロジックだけの
  主張（押すと何が出るか・候補が何件並ぶか・`aria-pressed`が反転するか）はvitestで確かめる。（原則3）
- 各テストの冒頭のコメントに、どの観点を見ているかを書く。書けないテストは置かない。（原則3）

### 共通フィクスチャに置くもの

- `e2e/fixtures.ts`には、目的の画面まで進める導線（アプリが起動するためのAPIモックの既定応答と、`openMobileApp`・`openMobileSheet`・
  `generateRoutes`・`seedStoredState`のような段取りのヘルパー）だけを置く。判定対象になる値（幅を測るための長いラベル・段階の
  細かい軸・描けたかを見る塗り色等）は、各テストが自分で用意する。（原則3）
- 見たい画面まで進める段取りは、`e2e/fixtures.ts`のヘルパーを使い、テストごとに書き直さない。保存される画面状態（レイヤーの
  ON/OFF等）は、クリックで作らず`seedStoredState`で与える。（原則3・8）

### 走査する画面の状態は、画面から辿る

- 観点1〜3を当てる画面の状態は、テストごとに手で選ばず、`e2e/all-states.spec.ts`の走査（`e2e/states.ts`が辿る画面の状態へ、
  `e2e/scans.ts`の検査を当てる）に任せる。（原則9）

### 書き方

- ロケータは当て推量で書かず、実際の名前を、落ちたテストのその時点の画面構造で確かめる。（原則10）
- 地図が描けたかは画素で見て、その確認は`e2e/map-runtime.spec.ts`の1本だけに置く。ほかのテストへ同じ確認を足さない。（原則3）
