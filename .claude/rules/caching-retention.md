# キャッシュ方針（何を持ち、いつ捨てるか）

Redisへ置くもの・TTL・判断のキャッシュ・無効化の決まり。「決まり」の節と保持層の選び方は[caching.md](caching.md)が持つ。

## Redisへ置くもの・置かないもの

**基準は「外部への負荷を肩代わりしているかどうか」。**

- **Redisへ置く**: 失うと**自分では制御できない相手**（気象庁等の外部サービス）へ取りに行くことになるもの
- **プロセス内で持つ**: 失っても**自前の正本**（PostGIS）から復元できるもの

例（全件ではない）:

| データ | 失うと誰に取りに行くか | 置き場所 |
|---|---|---|
| JMAタイル本体（`jma:tile`） | **気象庁** | Redis |
| 在否インデックス（`jma:tile-index`） | 同上（プリウォームが作る共有知識） | Redis |
| アメダス観測値（`jma:amedas`） | **気象庁** | Redis |
| アメダスの1時間雨量の履歴（`jma:amedas:rain-history`、正時ごと×観測所） | **気象庁** | Redis（読む側は求めた材料の値をプロセス内に短く持つ、`jma_amedas_service.py: _RAIN_MATERIALS_CACHE_TTL_SECONDS`） |
| 取込範囲全体の道路網の配列（`road_network_store`） | 自前のPostGIS | ディスク（メモリマップで読む） |
| way_id別の動的値（勾配） | 自前で再計算 | ディスク |
| タイルのフィーチャーごとの材料（地図の配信が評価する） | 自前のPostGIS | ディスク |

### キャッシュしないという選択

**キャッシュが節約する時間を測ってから置き場所を決める。** 節約が小さいなら、置き場所を選ぶ前にキャッシュ自体をやめる。

## Redisへ持つときは`redis_json_cache`を使う

Redisは骨格（`backend/app/infrastructure/redis_json_cache.py`）を通す。**呼び出し元が持つのはキー設計・TTL・値の意味づけだけ**にする。
値がバイナリなら、base64にしてJSONへ包まず、生のバイト列の口を使う。

**自前で骨格を書いてよい例外**は置かない。骨格に無い操作（`mget`で1リクエストに数百キーを引く・TTLの付与以外で
キーの生存期間を操作する等）が要るときは、呼び出し元で骨格を書かず、骨格へ口を足す（`get_hash`/`set_hashes`と同じ形）。

## TTLの決め方

**数字を書くときは、必ず「何に合わせた値か」をコメントへ書く。** 決め方は次のいずれかに揃える。

| 類型 | 決め方 | 現在の例 |
|---|---|---|
| 上流の更新間隔に合わせる | 上流の更新周期 ＋ 取り込みの余裕 | アメダス観測（`jma_amedas_store.py: _OBSERVATION_TTL_SECONDS`、取得のバッチの間隔＋余裕） |
| 内容が変わらない期間に合わせる | 内容が確定して以後変化しないなら、その識別子が有効な間 | JMAタイル本体（`jma_tile_redis_cache.py: TTL_SECONDS`。`basetime`が変わればキーも変わる） |
| ほぼ不変なマスタ | 1日 | 地域マスタ・WBGT地点マスタ（`wbgt_client.py: _POINT_MASTER_CACHE_TTL_SECONDS`）・観測所一覧・地点の検索をブラウザが持つ時間（`api/cache_policy.py: MASTER_LOOKUP`） |
| 共有率で決める | 短くしすぎるとヒットせず、長くすると鮮度を失う中間 | `targetTimes`（`jma_tile_client.py: _TARGET_TIMES_TTL_SECONDS`） |
| 再計算コストで決める | 失っても計算し直すだけなら長め | 道ごとの勾配の値（`dynamic_way_value_cache.py: _TTL_SECONDS`） |

## 判断をキャッシュしてよい条件

「データ」（正本の行の写し）ではなく「判断」（真偽値・鮮度）をキャッシュするときは、次の3つを**すべて**満たすこと。
1つでも欠けるならキャッシュしない。

1. **入力がすべてキーに入っている**（＝純関数のメモ化になっている）
2. **判断が一方向に単調で、保持するのが安全側**であること（「一度真なら覆らない」判断の真だけを保持する。
   「最新である」等の危険側を保持しない）
3. **TTLが「誤ってよい窓」から導かれている**こと。その時間だけ誤った判断を返しても許容できる、と説明できること

**別プロセス（バッチ等）から無効化を送りつける形は、上記1が満たせないときの代償行為である。** まず1〜3を満たせないか、
それが無理ならキャッシュしないかを先に検討する。

### 版をキーに入れるなら、版の照会が十分に安いこと

上記1を満たす標準的な手段は、入力の版（世代番号・更新時刻）をキーへ含めることである。ただし**版を読むコストが、
キャッシュが節約するコストと同じ桁なら、その設計は成立しない**。

## 「取っても得るものが無い」ことの覚え方

疎なデータ（気象庁の動的タイル・整備区域外のDEM等）では、空振りを覚える。

## 無効化（キャッシュを捨てる）

**既定は世代番号**。キー自体に世代を埋め、変わった瞬間から新旧が別物になる方式にする。

**世代は手で書かず、`app/infrastructure/cache_identity.py`で組み立てる**。鍵は「手で書くリビジョン」と「形の署名」の合成で、
形——MVTへ焼き込むSQL、そこへ**あらかじめ束ねた値**（分類タグ集合等）、pickleするdataclassの列構成——は機械的に署名する。
**署名に入らないものを増やさないこと**（`str()`に現れない材料（バインドパラメータの値等）は、焼き込む値だけが変わって鍵が動かない）。
手で上げるのは、「形は変わらないが意味が変わった」のに、形の署名にも下のDBの世代にも表れないときだけ（値を作る式を変えた・
土地被覆の画素が変わった等。例: `gradient_way_service.py: GRADIENT_VALUE_SHAPE`の先頭・`cache_identity.py: LANDCOVER_REVISION`。
下の「値を作る関数のソースまではハッシュしない」）。

**ただし、デプロイを伴わずに起きる変化は手で書くリビジョンでは表せない。** この種の変化は**DBを正にする**——書いた側が
単調カウンタを進め、読み手はディスクへ最後に書いた時点の記録と突き合わせて、違えば捨てる。**鍵に入れる世代は、
キャッシュする値が読む表のすべてを覆う**。読み手はTTL付きで読み直し、**読み直しは、そのキャッシュを
実際に読む経路の入口へ置く**。

**値を作る関数のソースまではハッシュしない**。過剰な無効化のコストが実害を上回る場合は手動に留める
（docs/architecture/design-principles.md構造仕様12の例外条項）。

**派生物の世代は元データの世代に従属させる**。派生物の鍵には元データの世代も署名の材料として含め、元データの世代を上げれば
派生物側も機械的に無効化されるようにする。独立した2つの文字列にしない。

**ただし世代番号は"古い実体が消える"ことを意味しない。** TTLのある層（Redis・TTLCache）は古い世代が自然に失効するが、
**ディスクは残り続ける**（消す手段とそれをどこで呼ぶかは[caching.md](caching.md)「ディスクを選ぶときの責任」の2）。
どの関数をいつ呼ぶかは、そのモジュールの`docs/modules/*.md`が持つ。

世代を定期に変える案を出すときは、焼くかを次の値と並べてユーザーに問う（焼くかは
かける量の決定。CLAUDE.md「原則」の1）:

- 世代が変わった直後のタイルを今は事前に焼かないことと、比べる実測値・枚数の桁は
  [静的道路属性](../../docs/modules/backend/static-road-attributes.md)「RegionService（路面・点のタイル、区間インスペクタ）」の
  「タイル世代」が持つ。

**全消し（`tile_cache.clear_all()`）は例外**。他レイヤーのキャッシュまで巻き添えにするため、運用操作としてのみ残す。
新しいキャッシュへ全消し手段を足さない。

**「元データの世代」には、どの元データを開いていたかも含む。**

焼き込み値（MVTのCASE式・材料タグ）を変えたときに同じコミットで揃える生成物は、[deployment-sync.md](deployment-sync.md)
「コミットと同時に揃えるもの」が持つ。
