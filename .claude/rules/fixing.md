# 修正の決まり

指摘・不具合を直すとき（直すタスクに着手してから閉じるまで）の決まり。括弧の番号は、導く CLAUDE.md「原則」。

## 直し方

- **範囲は性質から導く**: 直す範囲は、次の4つの欄をこの順に issue の背景かやることへ書いて決める。起票で欠けた欄は
  着手したときに書き、今の版で当て直す。（原則9・10）
  1. **性質**: 欠陥を成立させている性質を1文で。道具の名前・綴り・場所を含めない。
  2. **道具**: 列挙に使う道具（grep・AST・検査等）と、その対象（ファイル・層・範囲）。
  3. **拾わない形**: 性質に当たりうるのに道具が見ない形（関数の中・別の綴りや言い換え・別の層・走査の届かない所等）と、
     それを誰がどう見るか（別の grep・読んで確かめる・このタスクの範囲の外とする理由）。
  4. **検算**: 性質に当たる既知の例のうち、道具の綴り・形と違うものを1つ以上（過去の回で漏れた実例を先に使う）。
     道具が拾わなければ、道具を広げるか 3 に書き足し、そのことを経緯に書く。
- **機械の出した一覧は候補として扱い、処置の根拠にしない**: grep・AST・参照の数が出した一覧を削除・改名・撤去へ移す前に、
  その機械が見ていない読み手を1件ずつ確かめる。フレームワークが規約として読む口（`app/**/route.ts`の`GET`/`POST`、
  `layout.tsx`の`metadata`/`viewport`）は、名前の除外リストでなく、規約として読まれる場所にあるかで見分ける。文字列やパスで
  解決される参照と、走査範囲の外にあるもの（`frontend/e2e/`等）も見る。（原則10）
- **本番で人が見つけた不具合は、拾えなかった層も直す**: 直す Pull Request で、issue の不具合の節に書いた拾えなかった層の
  少なくとも1つに、同じ形を落とす確かめを足す。どの層にも足せなければ、拾える層と確かめを名指した issue を起こし、
  その番号を直すタスクの issue の経緯に書く。（原則9・5）
- **検証は別の入力で行う**: 直ったことは、直す根拠にした入力とは別の入力で確かめる。母集団で範囲を決めたタスクの完了の
  条件には、母集団を決めた道具の0件のほかに、性質を表す門（構造テスト・型）が検算の例の形を壊した入力で落ちることか、
  道具の外から選んだ例（「範囲は性質から導く」の検算の例・拾わない形の例）が直っていることを確かめる行を1つ以上置く。
  検査の側を緩めたときは、緩める前に検知できていた既知の1件が今も検知されることを示し、検知0件を直った証拠にしない。（原則11）
- **足した検知器・ガード・表示は、わざと壊した入力を1件通して、落ちる・出ることを見てから完了にする。**（原則11）
- **ゆるめは、外す件数を測ってから入れる**: 除外・許可リスト・判定条件のゆるめを足すときは、それが検査対象から外す件数と
  母集団に対する割合を実測し、タスクの issue へ書く（検知器には足さない。下の「検知器を足す条件は厳しい」）。（原則10）
- **移行・置き換えの差を測る前に、基準を書く**: 「旧と何%違うか」を測る前に、基準（仕様・材料の式・制約の宣言）と、
  測る単位が新旧で同じものを数えていることを1行で書く。置き換えられる側（旧実装・旧DB）を基準にしない。書けないなら測らない。（原則10・11）
- **性能は本番で測る**: 性能の計測・前後の比較を開発DBでしない。性能を変える直しは、変えた処理を通る経路のすべてを、
  出す前と本番へ出したあとに本番で同じ測り方で測り、前後の値をタスクの issue に書く。（原則5・10）

## 消す・残す

- **置き換えではなく削除を既定にする**: XをYへ置き換えるなら、「Xをただ消せない理由」を先に言えること。言えないなら消す
  （消して利用者かユーザーにできなくなることが出るなら、CLAUDE.md「原則」の1のとおりユーザーが決める）。
- **変更で使われなくなったものは、同じ変更で次の母集団から探して消す・締める**（消した名前の grep では出ない）。（原則8・9）
  - 呼び手を消したら、消した呼び手が頼っていた既定値・任意の欄・引数を残る呼び手と1項目ずつ突き合わせ、誰も渡さなくなった
    既定値・残る呼び手の全員が同じ値を渡す引数・読み手の無くなった欄を消す。
  - 口（画面の部品・API の欄等の、値が利用者に届く所）を閉じたら、閉じた口が読んでいた項目を口から DB の列まで1項目ずつたどり、
    その口のためだけに値を作る・運ぶ・設定させる経路（DB の列・API の欄・管理画面の欄・入力の検査）を消すか、残る読み手に合う
    意味を名前と説明に付け直す。
  - 口を閉じたら、閉じた口の綴り（保存の鍵・応答の欄名・型の欄名・画面の名前）をリポジトリ全体（`docs/records/` を除く）で grep し、
    型にも import にも CI にも結ばれない読み手・作り手（e2e-live・撮影の脚本・`frontend/scripts/`・`backend/scripts/`等）まで直す。
    推論で型へ流れ着くリテラル（`.map` の戻り値等）には余分な欄の検査が効かないので、消した欄の名前をオブジェクトの鍵として探す。
    綴りを組み立てて読む所（テンプレートで名前を作る等）は読んで確かめる。
  - 応答のモデルの既定値つきの欄は、本番の作り手の引数と1項目ずつ突き合わせる。作り手が渡さず、後段の上書きでしか埋まらない欄は、
    組み立て途中の型と応答の型を分けて、応答の型で必須にする。
  - 契約（HTTP の要求・応答の欄・関数の引数）を必須へ締めるときは、相手側（生成物の型・呼び手の宣言）も同じ差分で締める。
- **1本化・置き換えで置き換えられた側（旧実装・フォールバック・既定値）は、同じ作業の中で消す**。「回帰テストのオラクルにする」
  「既存を壊さないため」「後で消す」を残す理由にしない。（原則8）
- **コードから要件を推定しない**: 参照の数・読み手と書き手の有無・テストやカバレッジの有無は消す候補を出すだけで、
  要るかどうかの根拠にしない。要るかどうかが怪しいものは自分で分類せず、全件ユーザーへ問う（消しても利用者かユーザーに
  できなくなることが出ないと導けるものは、CLAUDE.md「原則」の1のとおり Claude が消す）。

## 共有の形を変える・廃止する

フィールド・パターン・データや文書の書式・契約のように、複数の読み手が使う形を変える・廃止するとき。（原則9・3・8）

- 変更前の綴りをリポジトリ全体（`docs/records/` を除く）で grep し、取り残された読み手が無いことと、残る読み手が変更後の契約と
  両立すること（その契約が無いことを前提に、外から別の値を与えていた所）の両方を確かめる。
- 前の形の実物（DB の行・ファイル）が残るなら、実物を今の形へ一度で直し、読む側に前の形を読む口を残さない（本番の行を移す
  順は [deployment-sync.md](deployment-sync.md)「コミットと同時に揃えるもの」）。直す対象は、紛れの無い1つの規則（許す形を列挙し、
  それ以外を形に合わないとする）で読めないもの、として機械的に導き、別の見分け方を持たない。直し方は推測で書かず、その形を
  作った・受け付けた側のコードの規則を使う。対象の全件で、前の読み方と直した結果が一致すること・直した結果が新しい規則で
  読めること・直した後に前の形が新しく作られないことを確かめる。

## 直すタスクを閉じる

- タスクを completed で閉じる前に、issue に未実施の段階・派生が残っていないかを読む。「見送り」（今後もやらない確定の判断）
  以外が残るなら、閉じずに、残りを完了の条件の行か段階（sub-issue）に置く。別の issue へ切り出すのは、残りが元のタスクと
  別の時機で進むと分かっているときだけにする。（原則4）

## 検知器を足す条件は厳しい

検知器（`scripts/review_checks.py docs`）はCIで一律に実行され、実行の時機も走査範囲も選べない。足すのは、どの文脈でも
正しいと言えるものだけにし、次のどれかに当たるものは足さない。思いつきは検知器にしない。（原則8・6）

- **走査範囲を絞る仕組みが要る**: 不変条件なら全件でも差分でも同じ答えになる。「新しく入った分だけを咎める」必要があるなら、
  不変条件ではない。
- **許可リストが要る**: 許可リストは誤検知を認めた印で、「この綴りは外部の語彙だから除く」が要る検査は事実を見ていない。
- **母集団を手で書く**: 対象のファイルを人が列挙すると、実装が動いたときに静かにずれる。対象は、その検査が読むもの
  （マークダウン全件）から決まるものに限る。
- **実装そのものを検査対象にする**（コードの書き方・import の規則・型・レイヤーの不変条件）: 実装側の道具（lint・型検査・テスト）が
  持つ。検知器が実装の姿を知ろうとすると写しを抱え、実装が変わったときに黙って効かなくなる。
- **保存した過去の値と比べる**: それは検査でなく報告である。要る過去の値は`periodic-review/NNN`タグが指すコミットから導く。
