# 修正の原則

指摘・不具合を直すときは、症状ではなく欠陥を直す。

## 直し方

- **範囲は性質から導く**: 直す対象を「症状が出た場所」で決めず、「その欠陥を成立させている性質」で決め、その性質に
  当てはまる箇所を機械的に列挙してから直す（[design-principles.md](../../docs/architecture/design-principles.md)構造仕様12）。
  母集団は道具の取りやすさで決めない。次の4つの欄をこの順に、起票のときに issue の背景かやることへ書く。着手したら今の版で
  当て直し（欠けた欄は自分で書く）、検算の例を道具が拾わなければ道具を広げるか拾わない形に足して、経緯に書く。
  完了の条件は下の「検証は別の入力で行う」。
  1. **性質**: 欠陥を成立させている性質を1文で。道具の名前・綴り・場所を含めない。
  2. **道具**: 列挙に使う道具（grep・AST・検査等）と、その対象（ファイル・層・範囲）。
  3. **拾わない形**: 性質に当たりうるのに道具が見ない形（関数の中・別の綴りや言い換え・別の層・走査の届かない所等）と、
     それを誰がどう読むか（別の grep・読んで確かめる・このタスクの範囲の外とする理由）。
  4. **検算**: 性質に当たる既知の例のうち、道具の綴り・形と違うものを1つ以上挙げ、道具が拾うことを示す（過去の回で
     漏れた実例を先に使う）。拾わなければ、道具を広げるか拾わない形に書く。
- **本番で人が見つけた不具合は、拾えなかった層も直す**: 直す Pull Request で、issue の不具合の節に書いた拾えなかった層
  （.claude/skills/file-issue/SKILL.md「issue の形」）のうち少なくとも1つに、同じ形を落とす確かめを足す。どの層にも足せなければ、
  拾える層と確かめを名指した対策の issue を起こし、その番号を直すタスクの issue の経緯に書く。
- **機械の出力をそのまま処置へ繋げない**: grep・AST・参照カウントが出した一覧は**候補**として扱い、処置（削除・改名・撤去）へ
  移す前に、**その機械が見ていないもの**を1つずつ確かめる。「参照0だから消してよい」としない——フレームワークが規約として
  読む口（`app/**/route.ts`の`GET`/`POST`、`layout.tsx`の`metadata`/`viewport`）、文字列やパスで解決される参照、走査範囲の
  外にあるもの（`frontend/e2e/`等）を確かめる。**名前の除外リストで逃げない**——「規約として読まれる場所にあるか」という
  位置で判定する。
- **検証は別の入力で行う**: 修正を書く根拠にした入力とは別の入力で確かめる。**検査の側を緩めて「検知0件になった」ことを、
  その検査が直った証拠にしない**——緩める前に検知できていた既知の1件が今も検知されることを、別途示す。
  母集団で範囲を決めたタスクの完了の条件は、母集団を決めた道具の0件だけで書かない。性質を表す門（構造テスト・型）が
  検算の例の形を壊した入力で落ちることか、道具の外から選んだ実例（「範囲は性質から導く」の4つの欄の検算の例・拾わない形の
  例）が直っていることを確かめる行を、少なくとも1つ置く。
- **比べる前に基準を決める**: 移行・置き換えの検証で「旧と何%違うか」を測る前に、基準（仕様・材料の式・制約の
  宣言）と、測る単位が新旧で同じものを数えていることを1行で書く。置き換えられる側（旧実装・旧DB）を基準にしない。
  書けないなら測らない。
- **緩和は影響を測ってから入れる**: 除外・許可リスト・判定条件のゆるめを足すときは、それが検査対象から外す件数と
  母集団に対する割合を実測し、タスクの issue へ書く。
- **「実装した」ではなく「効いている」を確認して完了にする**: 新設した検知器・ガード・表示は、わざと壊した入力を1件
  通して落ちる/出ることを見てから完了扱いにする。**手順・規約を新設したときも同じで、それに従って作った成果物を1件
  読んでから確定する。**
- **見積もりとずれたら、全体の結論より先にずれを報告する**: 実測が見積もりと違ったら、結論の補足へ回さない。反する内訳を
  落として全体を「改善」とまとめない。
- **性能は利用者から見た単位で測る**: 部品の計測（関数1本・木1本）は原因の切り分けにだけ使い、それで全体を判断しない。
  利用者が通る経路が複数あるなら、都合の良い側だけを測って結論にしない。
- **性能は本番で測る**: 性能の計測・前後の比較は開発DBで行わない。性能を変える直しは、記録として、修正が波及する範囲（変えた処理を通る経路のすべて）を、
  出す前と本番へ出したあとに本番で同じ測り方で測り、前後の値をタスクの issue に書く。

## 消す・残す

- **置き換えではなく削除を既定にする**: XをYへ置き換えるなら、「Xをただ消せない理由」を先に言えること。言えないなら消す。
- **変更のたびに「これで何が死んだか」を測り、同じコミットで消す**: 参照が0になったフィールド・関数・分岐・テストを
  次のタスクへ回さない。
  - **呼び手を消したら、消した呼び手が頼っていた既定値・任意の欄・引数を、残る呼び手と1項目ずつ突き合わせる**
    （誰も渡さなくなった既定値・残る呼び手の全員が同じ値を渡す引数・読み手の無くなった欄。消した名前の grep では出ない）。
  - **口（画面の部品・API の欄等の、値が利用者に届く所）を閉じたら、その口のためだけに値を作る・運ぶ・設定させる経路**
    **（DB の列・API の欄・管理画面の欄・入力の検査）も同じ変更で消すか、残る読み手に合う意味を名前と説明に付け直す**:
    母集団は、閉じた口が読んでいた項目を、口から逆に DB の列まで1項目ずつたどって数える。
  - **契約（HTTP の要求・応答の欄・関数の引数）を必須へ締めるときは、相手側（生成物の型・呼び手の宣言）も同じ差分で締める。**
- **いま消したものを見張るテスト・アサーションを足さない**（[testing.md](testing.md)「消すべきテストの型」の
  「消したものを見張るアサーション」）。守りを足すのは、消していないものに対してだけ。
- **本番から外れたものを「残す」判断を自分でしない**: 1本化・置き換えの改修で、置き換えられた側（旧実装・
  フォールバック・既定値）を残す理由として「回帰テストのオラクルにする」「既存を壊さないため」「後で消す」を挙げない。
  **残したいと思ったら、残す理由と、いつ通るのかを添えてユーザーへ問う**——こちらで決めてコメントに書いて流さない。
  **置き換えた側が本番から呼ばれなくなったら、そのテストも同時に消す。**
- **コードから要件を推定しない**: 参照の数・読み手と書き手の有無・テストやカバレッジの有無を、要るかどうかの根拠にしない。
  要るかどうかが怪しいものは自分で分類せず、全件ユーザーへ問う。

## 書かないテスト

書かないテストの型は [testing.md](testing.md)「消すべきテストの型」が持つ。

## 報告と段取り

- **完了報告の実装の増減**は、Pull Request の本文の「増減:」（`.github/pull_request_template.md`）に書く。
- **「意図的に」は比べて選んだときだけ使う**: 残した・見送った理由を書くとき、比べて選んだなら比べた軸を書く。
  範囲外だった・手が回らなかった・忘れていたなら、そのとおり書く。
- **新しい種類の成果物は、置き場と命名を先に決める**: 既存の慣習が無い所へ1本目を置くとき、書き始める前に決めて合意する。
  分ける軸は「何を守るか」ではなく**それが何を読むか・何に属するか**
  （例: テストは [testing.md](testing.md)「ソースを読む検査は、専用ディレクトリへ置く」）。
- **段階を別タスクへ切り出すときは、切り出す先の中身を具体化してから切り出す**: 「あとは〜するだけ」と見えている状態で
  切り出さない。

## 検知器を足す条件は厳しい

検知器（`scripts/review_checks.py docs`）はCIで一律に自動実行され、実行タイミングも走査範囲も選べないので、
**どの文脈でも絶対に正しいと保証できるものだけ**を足す。次のどれかに当たるものは足さない:

- **走査範囲を絞る仕組みが要る**——不変条件なら全件でも差分でも同じ答えになる。「新しく入った分だけを咎める」必要が
  あるなら、それは不変条件ではない
- **許可リストが要る**——許可リストは誤検知を認めた印である。「この綴りは外部の語彙だから除外する」が必要なら、その検査は
  事実を見ていない
- **母集団を手で書く**——「どのファイルが対象か」を人が列挙すると、実装が動いたときに静かにずれる。対象は、その検査が
  読む対象そのもの（マークダウン全件）から決まるものに限る
- **実装そのものを検査対象にする**（コードの書き方・import規則・型・レイヤーの不変条件）——実装側の道具（lint・型検査・
  テスト）が持つ。検知器が実装の姿を知ろうとすると写し（スナップショット・定数表）を抱え、実装が変わった瞬間に黙って死ぬ
- **保存した過去の値と比べる**——それは検査ではなく報告である。要る過去の値は`periodic-review/NNN`タグが指すコミットから導く

**担当に課す手順の決まり（確かめる担当が Pull Request を閉じる条件など）も同じ基準で足す**: 形が目的と同じで、見逃すと
気づかれないまま壊れるものだけを、閉じる・断る条件にする。それ以外は決まりにしない。

**思いつきは issue に起こして人が採否を決める**ことにし、検知器にはしない。自己申告のチェックを文章のルールとして足すことも
しない。その場合も**実行したコマンドと観測値をコミットメッセージへ書く**（「確認した」とだけ書かない）。

## 人が見るしかないもの

次のものは検査器にできず人が見る。どれも実行したgrepと観測値をコミットメッセージへ残す。

1. **共有フィールド・パターン・形（データや文書の書式・契約）を変更/廃止したとき**: 変更前のフィールド・パターンを
   リポジトリ全体でgrepし、①取り残された消費者がいないか、②**残る消費者が変更後の契約と両立するか**（従来その契約が
   無いことを前提に外側から別の値を与えていた箇所）の両方を確認する。③**前の形の実物が残るなら、読む側に前の形を残さず、
   実物を今の形へ一度で直す**（設計原則 構造仕様8）。
   正本の規則は1つで紛れが無いもの（許す行を列挙し、それ以外は形に合わないとする）にし、直す対象はその規則から機械的に
   導く（新しい規則で読めない実物＝対象。別の見分け方を持たない）。直し方は推測で書かない——その形を作った・受け付けた側の
   コードの規則をそのまま使い、対象の全件を前の読み方と直した結果に通して一致を確かめ、直した結果が新しい規則で読めることも
   確かめる。直した後に前の形が新しく作られないことも確かめる。直す道具は、流した後に消すタスクを紐づける。
2. **タスクを閉じる（completed で閉じる）とき、issue に未実施の段階・派生が残っていないか**: 「見送り」
   （今後もやらない確定判断）以外が残るなら、**元タスクを閉じずに**段階（sub-issue）にするか、保留へ動かして
   残りと再開の条件を書く。別の issue へ切り出すのは、残りが元タスクと別の時機で進むと分かっているときだけにする。
   **範囲外で見つけたものも同じときに見る**（扱い方は .claude/skills/task-work/SKILL.md「範囲の外の気づき」）。
