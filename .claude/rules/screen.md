# 画面の作法

利用者に見える画面（置き方・見せ方・操作の形・語）を足す・変えるときの決まり。案と見本にも当てる。地図アプリで、
いちばん厳しい利用者の条件は、ロードバイクで走りながら見るスマホの幅である。部品の作り方は
[デザイン基盤](../../docs/modules/frontend/frontend-design-system.md)が持つ。

## 置き方と見せ方

- **地図の視界を削って情報を足さない**: パネル・ポップアップ・凡例へ足すものは、地図の見える範囲を狭めない形にする。新しい表示は
  「走行中に見るか」で分け、見ないものは折りたたみの奥に置く（原則5・8）。
- **ヘッダーへ操作を足すときは、既存のメニューへ項目として足す**。ヘッダーはスマホでも常に出て、単独のボタンは1つずつ横幅を取る。
  単独のボタンにする案は、メニューへ足せない理由を添えて出す（原則7・8）。
- **画面に出る文言の括弧は半角の`[]`にし、共通語の重なった言い方を削る**。読み上げにだけ使う文言（`aria-label`等）と、
  地図を持たない管理画面は外す（原則5）。
- **設定の置き場所は反映の時で分ける**: 生成ボタンを押して初めて効く設定はルート設定パネル、すぐ地図へ効く設定は
  地図の見え方パネルに置き、生成の結果はルート結果パネルで読むだけにする（原則7）。
- **1つの状態は1つの場所でだけ操作する**: レンズ・走行方位・出発時刻・想定速度のような状態は入口を1つにし、ほかの場所には
  表示だけの値か、その入口への近道だけを置く。同じ調整を2通りの操作で用意しない——どちらが正しいか読み手が迷う（原則3・8）。
- **数値は3層で見せる**: 地図は色だけ、パネルの一覧は段階ラベルと0〜100の難易度まで、物理量（生値・材料値）は押して開く詳細に
  置く。ルートの区間の詳細は評価軸ごとの難易度までにし、区間の材料値の一覧は出さない。一覧に物理量を並べると、単位の分だけ幅と
  段を取り、評価軸が増えるほど読めなくなる（原則5・7）。
- **消さずに薄くする**: 評価に使っていない評価軸・値が無い区間は隠さず、「未使用」「データなし」として薄さと操作の可否で示す
  （レンズの一覧は未使用の評価軸も選べる形で並べ、重み配分は重み0の評価軸もチップとして残す）。チップの形は画面の間で共有する。
  **例外: ルート結果の評価軸の内訳は、その評価に効いた評価軸だけに絞る**——候補ごとに縦へ伸び、狭い幅では何が効いたかが
  読めなくなる（原則5・7）。
- **内部名を画面に出さない**: このアプリが付けた識別子（軸id・材料id・一次属性id・分類器が付ける種別・0次フィルタの名前等）は
  どの画面にも出さない。表示名は、その語彙を宣言する所が識別子と同じ行に持ち、生成物・APIで一緒に届ける——名前だけを別の表に
  持つと、語彙を足したときに名前の無い識別子ができる。名前を引けないときは識別子で埋めず、その項目を出さない（件数だけ示す）か
  「不明」にする。OSMタグの生値のような外部のデータ値は、対訳が無ければ生値を見せてよい。管理画面（軸スタジオ）は外す（原則3・5）。
- **冗長なものは削る**: 操作して1回で分かることを文で説明しない。説明は画面へベタ書きせず、情報アイコン（ⓘ）の奥へ入れる——
  読むのは1度なのに、場所は取り続ける（原則8）。
- **利用者が自分で選んだ値（高さ・モード・入力値等）は、次に開いたときも保つ**。自動の調整は、利用者が決めていない間だけ働かせる。
  行くたびに変わる場所（目的地・経由地のピン）は保たない——古い値が残ると、気づかないまま実行してしまう（原則5）。

## 操作ボタンの形

- **パネル（ルート設定・ルート結果・編集面）の操作は、どの幅でもアイコンだけの形にそろえ、名前は`aria-label`で渡す**。名前を
  並べるとパネルの幅に収まらず、縦に積むと下部シートの高さを取る。消す・戻す・再試行のような小さな操作も、同じ操作をパネルの外
  （常設のヘッダーの印の中等）に置くときも同じ形にする——形が混ざると、どれが同じ種類の操作かを形で読めない。外すのは、✕（閉じる・
  選択の解除）と、画面の値を名前に含む操作（「「◯」に切り替える」）と、窓の中の確かめるボタン（「保存」「消す」等）だけ（原則7）。
- **押して切り替える操作も同じ形にし、押している間はアクセント色で塗る**。押している間・押せない間の名前も`aria-label`で伝える（原則5・7）。
- **案内の文（初回の案内・空の案内・使い方の説明・失敗の文等）でアイコンだけの操作を指すときは、文の中にそのボタンと同じ見た目の
  アイコンを置き、文には`aria-label`の名前をかぎ括弧で書く**（例: 「ルート生成」を押すと…）。名前の文字だけでは、どのアイコンを
  押すのかが結びつかない（原則5）。
- **置き場は効く範囲で決める**: 候補すべてに効く操作は見出しの行、候補1本に効く操作はその候補のタブの中に置く（原則7）。

## 状態の伝え方

- **色だけで伝えている状態は、同じ事実を`aria-label`か`title`の文字にも持たせる**。色を見分けられない利用者に届かない（原則5）。
- **同じ行に並ぶ操作の`aria-label`は、互いに違う文言にする**。同じだと、読み上げでも`getByRole(name)`でも区別できない（原則5・11）。
- **利用者がした操作が何に反映されたか（呼び出した設定・選んだ地点がどの地点として置かれたか）を、画面で見せる**。見えないと、
  利用者は確かめ直すか、違うまま進む（原則5）。
- **新しいシート・パネルを足すときは、開閉する部品に`aria-expanded`（または`role="tab"`）を付ける**。E2Eの全状態の走査は、これを
  持つ部品だけを押して画面の状態を辿る（[testing-e2e.md](testing-e2e.md)「走査する画面の状態は、画面から辿る」）（原則5・11）。

## 画面の語

**利用者に見せる概念は、下の表の語1つで呼ぶ**——同じものを画面ごとに別の語で呼ぶと、利用者は別のものだと読む。frontendの文言
（管理画面を除く）と、backendが配る文（`domain/map_display.py`の説明の文・画面に出るエラーの`detail`）のどちらにも当てる。表に無い
概念を画面に足すときは、行を足してから書く。表に無い開発用語（「フォールバック」「キャッシュ」等）も画面に出さず、初めて見る
利用者が意味を取れる言い方にする（原則5・7）。

| 概念 | 画面の語 | 使わない語 |
|---|---|---|
| 道の走りにくさを測る観点の1つ（勾配・舗装質等。重みを配る単位） | 評価軸 | 評価・軸 |
| 評価軸で道・ルートを測ること、その結果 | 評価（「評価する」「道の評価」） | 評価軸の意味では使わない |
| 0〜100の走りにくさ（評価軸ごとの値も、重みで合わせた値も） | 難易度（評価軸ごとは「この評価軸の難易度」） | 合成・スコア・コスト |
| 候補の区間をほかの候補の道へ乗り換えて作ったルート | 合成ルート（作る操作は「ルートを合成」） | 難易度の意味では「合成」を使わない |
| 地図に点で出す場所（停止要因・補給・事故） | スポット | POI |
| 利用者が変えていないときに使う値 | 既定（既定の配分・既定値） | デフォルト・サーバー既定 |
| ルートを作り、データを配る側 | アプリ（主語に要るときだけ） | サーバー・ジョブ |
