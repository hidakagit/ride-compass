# 画面の作法

利用者に見える画面（置き方・見せ方・操作の形・語）の決まり。地図アプリで、主な利用場面がロードバイク走行中の
スマホであることに由来する。部品の作り方（`components/ui/`・
トークン）は[デザイン基盤](../../docs/modules/frontend/frontend-design-system.md)が持つ。

## 置き方と見せ方

- **ヘッダーへ操作を足すときは、既存のメニューへ項目として足す**: ヘッダーはモバイルでも常に出る領域で、個別の
  ボタンを並べるたびに横幅を取る。単独のボタンを足す案は、メニューへ足せない理由があるときだけ出す。
- 地図アプリとして地図表示エリアを最大限確保する構造を優先する。UI文言は表示幅を
  圧迫しない（全角括弧でなく半角角括弧`[]`、共通語の重複表現を割愛）。括弧の決まりは
  画面に出る文言が対象で、読み上げにだけ使う文言（`aria-label`等。表示幅を取らない）と、
  地図を持たない管理画面は外す。パネル・
  ポップアップ・凡例のいずれも地図そのものの視界を削ってまで情報量を増やさない。
- **設定の置き場所は反映タイミングで分ける**: 生成ボタンを押して初めて効く設定は
  ルート設定パネル、即座に地図へ反映される設定は地図の見え方パネル、生成結果は
  ルート結果パネルで読むだけにする。
- **1つの状態は1つの場所でだけ操作する**: レンズ（地図の色分け）・走行方位・出発時刻・
  想定速度はそれぞれ入口を1つに絞り、他の場所には表示専用の値かその入口へのショート
  カットだけを置く。
- **数値は3層で見せる**: 地図そのものは色だけで示し、パネルは段階ラベルと0〜100の
  難易度で示し、元の物理量は押して開く詳細に置く。**パネルが一覧として並べる
  数値は0〜100の得点までで、物理量（生値・材料値）は押して開く詳細に置く**
  ——一覧に物理量を並べると、単位の文字数ぶん幅と段を取り、公開軸が増えるほど一覧そのものが
  読めなくなる。軸単体で経路を判断するには生値が要る（[設計原則](../../docs/architecture/design-principles.md)の構造仕様11）が、
  それは1クリック奥で足りる。**ルートの区間の詳細は軸ごとの寄与（得点）までで、
  区間の材料値の一覧は出さない**——区間の詳細は走行中に見る画面で、軸の数だけ
  行が増えると縦に伸びる（下記「走行中に見るか」）。
- **消さずに薄くする**: 評価に使っていない軸・値が無い区間は非表示にせず、「未使用」
  「データなし」として存在ごと示す。**使っていないことは、消すのではなく薄さと
  操作の可否で示す**——レンズの一覧は未使用の軸も選べる形で並べ、ルート設定の重み配分は
  重み0の軸もチップとして残す。同じ軸がどの画面でも違う形に見えないよう、チップの形自体は
  共有する。
  **例外: ルート結果の軸内訳は、その評価に効いた軸だけに絞る。** 内訳は候補ごとに縦へ
  伸びるため、使っていない軸まで並べると狭い幅では「このルートで何が効いたか」が読めなく
  なる。軸の全体像は設定側（重み配分）が持ち、結果側は絞った一覧を出す。
- **一覧は単一の情報源から機械的に生成する**: 軸カタログの並び順・色・名前をそのまま
  使い、手で並べた一覧を別途持たない。
- **内部名を画面に出さない**: このアプリが付けた識別子（軸id・材料id・一次属性id・
  分類器が付ける種別・0次フィルタの名前等。例: `wind`）は、どの画面にも出さない。
  **表示名は、その語彙を持つ宣言（軸定義・材料カタログ・一次属性・フィルタの宣言）が
  識別子と同じ行に持ち、生成物・APIで一緒に届く**——名前だけを別の表に持つと、語彙を
  1つ足したときに名前の無い識別子ができる。名前を引けないとき（非公開になった軸・カタログを
  取れていない間）は**識別子で埋めない**: その項目を出さない（件数だけ示す）か「不明」にする。
  **OSMタグの生値のような外部のデータ値は内部名ではない**——語彙を外部が決め、対訳表で
  閉じられないため、対訳が無ければ生値を見せる。管理画面（軸スタジオ）は物理名を見せるのが
  目的なので、この規則の外にある。
- **冗長なものは削る**: 操作して1回で分かることを文章で説明しない。**説明文をベタ書きで
  画面へ置かず、情報アイコン（ⓘ）の奥へ入れる**——ただでさえ地図に割く幅が無く、説明は
  読むのが1度きりなのに場所は常に取り続ける。同じ調整を2通りの操作で用意することもしない
  （どちらが正しいか読み手が迷い、片方の実装だけが古くなる）。
- **利用者が意図して決めた値は覚える**: 高さ・モード・入力値など、利用者が自分で選んだ
  ものは次に開いたときも保つ（localStorage）。**自動調整は利用者が決めていない間だけ働く**
  ——決めた値を「中身に合わせて」戻すと、決め直す手間が毎回かかる。
  場所（目的地・経由地のピン）のように、行くたびに変わり、古い値が残ると気づかないまま
  実行してしまうものは対象にしない。
- **走行中に見るかを基準に情報量を絞る**: 主な利用場面はロードバイク走行中のスマホ
  操作であるため、1画面の情報量を増やさない。新しい表示を足すときは「走行中に見るか」を
  基準に判定し、見ないものは折りたたみの奥に置く。

## 操作ボタンの形

- **パネル（ルート設定・ルート結果・編集面）の操作は、どの幅でもアイコンだけの形にそろえる**
  （`Button`の`size="panelIcon"`）。名前は`aria-label`で渡し、マウスを重ねた吹き出し（`title`）にも同じ名前が出る。
  名前を並べると、操作が増える見出しの行（区間の乗り換えの見出しと4つの操作）が
  パネルの幅に収まらないため。縦に積まないのは、下部シートの高さを取らないため（地図のチップは縦に積むが、パネルの操作は
  シートの中で候補一覧と高さを取り合う）。消す・戻す・再試行のような小さな操作も同じ形にする——同じパネルに文字のボタンと
  アイコンのボタンが混ざると、どれが同じ種類の操作かを形で読めない。パネルと同じ操作をパネルの外（常設ヘッダーの印の中の
  再試行等）に置くときも同じ形にする。この形にしないのは、✕（閉じる・選択の解除）と、画面の値を名前に含む操作
  （「「◯」に切り替える」）、窓の中の確かめるボタン（「保存」「消す」等）だけ。
- **押して切り替える操作（地点を地図で置く等）も同じ形**で、押している間はボタンをアクセント色で塗る。押している間・押せない間の
  名前（「◯の指定をやめる」「上限まで置いてあります」）も`aria-label`と吹き出しで伝える。
- **案内の文（初回の案内・空の案内・使い方の説明・失敗の文等）でアイコンだけの操作を指すときは、文の中にそのボタンと同じ見た目の
  アイコンを置く**。名前の文字では、画面のどのアイコンを押すのかが結びつかないため。文は`aria-label`の名前をかぎ括弧で書く
  （例: 「ルート生成」を押すと…）。新しい操作を案内で指すときは`GuideText`に足す。
- **置き場は効く範囲で決める**: 候補すべてに効く操作は見出しの行、候補1本に効く操作はその候補のタブの中。

## 状態の伝え方

- **色だけで伝えている状態は、`aria-label`/`title`にも載せる。** 現在地マーカーの色で
  「GPSで取れた／既定値に倒れた」を示すような表現は、色を見分けられない利用者に届かない。
  見た目は色のままでよいので、同じ事実を必ず文字でも持たせる。
- **同じ行に並ぶ操作は、`aria-label`の文言を互いに変える。** 同名だとアクセシビリティ
  ツリー上でも`getByRole(name)`でも区別できず、テストは「どちらかに当たった」状態で通る。
- **UIの文言に開発用語を出さない。** 「デフォルト」「フォールバック」「キャッシュ」などは、
  初見の利用者が意味を取れる表現へ置き換える。
- **利用者がした操作が何に反映されたかを、画面で見せる。** 呼び出した設定が反映されたか、選んだ地点がどの地点として
  置かれたかが見えないと、利用者は確かめ直すか、違うまま進む。
- **新しいシート・パネルは、開閉する部品に`aria-expanded`（または`role="tab"`）を付けて
  走査の母集団に入れる。** E2Eの全状態の走査は、これを持つ部品だけを押して画面の状態を辿る
  （[testing-e2e.md](testing-e2e.md)パターン4「走査する画面の状態は、画面から辿る」）。窓（`Dialog/Dialog.tsx`）を開くボタンも、
  `aria-haspopup="dialog"`と開いている間`true`の`aria-expanded`を付けて入れる。

## 画面の語

**利用者に見せる概念は、下の表の語1つで呼ぶ。** 同じものを画面ごとに別の語で呼ぶと、利用者は別のものだと読む。
frontendの文言（管理画面を除く）と、backendが配る文（`domain/map_display.py`の説明の文・画面に出るエラーの`detail`）の
どちらにも効く。表に無い概念を画面に足すときは、行を足してから書く。

| 概念 | 画面の語 | 使わない語 |
|---|---|---|
| 道の走りにくさを測る観点の1つ（勾配・舗装質等。重みを配る単位） | 評価軸 | 評価・軸 |
| 評価軸で道・ルートを測ること、その結果 | 評価（「評価する」「道の評価」） | 評価軸の意味では使わない |
| 0〜100の走りにくさ（評価軸ごとの値も、重みで合わせた値も） | 難易度（評価軸ごとは「この評価軸の難易度」） | 合成・スコア・コスト |
| 候補の区間をほかの候補の道へ乗り換えて作ったルート | 合成ルート（作る操作は「ルートを合成」） | 難易度の意味では「合成」を使わない |
| 地図に点で出す場所（停止要因・補給・事故） | スポット | POI |
| 利用者が変えていないときに使う値 | 既定（既定の配分・既定値） | デフォルト・サーバー既定 |
| ルートを作り、データを配る側 | アプリ（主語に要るときだけ） | サーバー・ジョブ |
