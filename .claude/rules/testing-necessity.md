# テスト方針（そのテストは要るか）

書く前・見直すときに、そのテストを持つか・消すか・旧版から取り込むかを決める判定。土台の決まりは[testing.md](testing.md)が持つ。節の名前とパターンの番号で指す先は、この文書か`testing*.md`のどれかにある（名前は重ならない）。

## そのテストは要るか（3問を順に）

**新しく書くとき・既存を見直すときは、この3問を使う。** 先に出た問いで決まったらそこで
終わりで、「念のため残す」はしない。起こし直しで**旧版にしか無い**ものが出たときは、先に
[マージの4分類](testing-rewrite.md#既存テストを直さず実装から起こし直す)を通してからここへ来る。

1. **構造が守っているか。守っているなら書かない。**
   - **既に守られている → 消す。** 恒真式・1行の委譲（受け取った props・属性・参照をそのまま中へ渡す、
     呼び出し側のハンドラを同じ名前の受け口へそのまま渡す（`onFocus`を中の`onFocus`へ）、値に単位を付けて
     styleへ渡す（`` `${height}px` ``））・宣言の書き写し・型が保証している
     こと（Pydanticの`Field`制約・`Literal`）・フレームワークの設定や結線・宣言から作った
     足場へ同じ宣言を当てる形・テストの足場に対する不変条件（見分け方は「消すべきテストの型」が持つ）。
     自前の要素にハンドラを結ぶ形（✕を押すと`onClose`）は委譲ではない——知らせ1つにつき1本残す。
   - **守れるが守っていない → 実装を直してから消す。** 型で通らなくする
     （`Field(min_length=1)`・`allow_inf_nan=False`）、片方をもう片方から導く、並びそのもので
     順序を表す（直し方は[書きたくなったテストが、実装の歪みを教える](testing-writing.md#書きたくなったテストが実装の歪みを教える)の表）。
   - **守れない → 2問目へ。** ただし**構造で表せない理由を1行で言えること**。言えないなら
     まだ「守れる」側である。
   **「構造が守っている」と判断したら、消してからカバレッジで確かめる。** 未到達の行が
   出たら、守っていたのは構造ではなく**コード**である。
2. **外部影響があるか。判定は「落ちるとき、何が壊れるか言えるか」。** その答えは
   モジュールの外——利用者の画面・他モジュール・配信される値・保存されるデータ——に
   ついてでなければならない。
   - **言えない → 消す。**
   - **答えを実装のコメントが既に持っているなら、docstringへ書き写さない**（判定基準は[comments.md](comments.md)
     「テストのdocstringも対象（判定基準）」）。
3. **他に同じことを見ているものがあるか。**
   - **別のモジュールの責務 → 移す。** テスト対象がファイル名の指すモジュールでないなら、それだけで移す
     理由になる。移した先で同じことを見ているなら、移さず消す。
   - **同じファイルの別のテストが同じ実装要素を見ている → 狭い方を消す。** 広い入力で
     見ているテストがあるなら、その部分集合は書かない。広い方が別の操作で狭い方を含むときも同じ
     （どのテストもメニューを押して開いてから確かめるなら、「押すまでメニューを出さない」は別に書かない）。
   - **別の高さで同じ判断を見ている → 低い方に残す。** 判断はdomainのテストに残し、経路のテストは受け渡し（判断の結果が応答の
     どこへ出るか）だけを見る。ただし**経路ごとに受け渡しを1本は残す**。
     E2Eとvitestの分担はパターン4の「何を対象にするか」が持つ。
   - **どれも無い → 残す。** 他のテストと似ていても残す。

**残すと決めたものも、同じ判断の入力違いは1つのテストの表の行にする。** 検証が断る形の1つずつ・
分類の1つずつ・境界の両側を、別のテストにしない。表の行は判断の違う入力だけを置き（境界は両側の2つ）、
同じ側の値を足さない。

- **両側は、書かれた比べ方の両側である。** `!== 0`なら「0」と「0でない」の2行。負の値の行は、本番で負が
  来て、扱いが違うときだけ足す。
- **既定を持つ読み出しも、書かれた比べ方である。** `.get(k)`・`?.`は「キーが無い」と「ある」、`??`は「null・undefined」と
  「それ以外」、`or`は偽と真を両側に持つ。1つの行が、通る比べ方の片側をいくつも兼ねてよい。既定を持たない読み出し
  （`entry["k"]`・`obj.k`）は比べ方ではない。
- **最小・最大で寄せる所には、境界ちょうどの行を書かない。**
- **同じ判断の関数を何か所で呼ぶときは、判断の両側は関数のテストに置く。** 呼ぶ所ごとには、寄せていることを
  示す1行だけにする。

**消す・まとめる前に、消すテストが落ちる実装の壊れ方を1つ書き、残す側がそれで落ちるかを見る。** どの経路で消す・
まとめるテストにも当てる（1問目の既に守られている・2問目の言えない・3問目の移した先が見ている・狭い方を消す・低い方に残す・
表の行へまとめる）。下の2・3は手で組み立てず、`scripts/break_tests.py`で流す（frontend も backend も同じ一覧で、`--ref`で前の版のテストも並べて回す。
一覧の形と使い方は道具の先頭）。

1. 消す・まとめるテスト1本ごとに、それが落ちる実装の壊れ方を1つ書く（比べ方を1つ変える・境界を1つずらす・値を定数へ変える）。
   書けないなら、そのテストは何も見ていない（1問目の恒真式）ので、確かめずに消す。
   宣言の書き写しは、宣言の値を変えることを壊れ方に数えず、書けないものとして確かめずに消す。並び・値が利用者に見える振る舞いを決める宣言は書き写しではない
   （「消すべきテストの型」）ので、並びを入れ替える・値を変える壊れ方を当てる。
   約束ごと消したテスト——見ていた約束が Pull Request の課題の「消した約束」か「変えた約束」の前の側に当たり、見ていた実装を
   同じ差分で消したもの——も、書けないものとして確かめずに消す。実装が後の版に残る
   （約束だけを変えた）テストはこれに当たらず、残った実装に壊れ方を書く。
   同じ側の行——通る書かれた比べ方のどれでも、残す側の入力と同じ側にある行（「同じ側の値を足さない」で消す・まとめる行と、
   3問目の「狭い方を消す」で消す行のうち入力が広い方と同じ側にあるもの）——には、書かれた比べ方の片側をまるごと変える壊れ方だけを
   当てる: 向きを反対にする・境界を1つずらす・比べ方を外して常に片側の結果にする・値を残す行の答えと違う定数へ変える。
   同じ側の中で答えを分ける壊れ方——別の比べ方へ置き換える（`in`を`==`へ・`Number.isFinite`を`Number.isNaN`へ）・
   書かれていない比べ方を足す（`if a:`を`if a and not b:`へ）・
   書かれた値の並びから1つ外す（`IN (…)`の値。並びの値ごとの行は宣言の書き写しで、値で結果が分かれるなら分類で同じ側ではない）・
   書かれていない既定値を足す（`?? 0`）・定数を残す行の答えに合わせる——は当てない。
2. 実装のその行を一時に変え、残す側（まとめた先の表・含むとした広い方・移した先・低い方）のテストのファイルだけを回して、
   次のどれかになることを見る。
   - (a) 残す側が落ちる。
   - (b) その壊れ方は作れない: 型・制約・宣言の検査（tsc・mypy・DB の制約・構造のテスト）が止める。止める検査を壊した版で
     回し、落ちることを見る（テストのファイルなら残す側に並べる。tsc・mypy は壊した版で打ち、3 と同じく戻す）。
     `break_tests.py` が「テストの前に止まった（(b)）」と止まり方の1行（例外の行）を出した件は、その行を 4 の出力として書く。
     型の計算を自前で書いたもの（パスの文字列から引数の型を導く等）は、その計算を崩しても tsc が通るので (b) に数えない。
   - (c) 前の版の消すテストも、その壊れ方で落ちない（`--ref`で並べて回す）: 消すテストは何も見ていなかった。

   どれにもならなければ、残す側を直す（表の補助が見る値を足す・行を足す）か、消さずに残す。
3. 変えた行を編集で戻し、`git diff --exit-code -- <実装のファイル>` で戻ったことを見てから次へ進む。
4. Pull Request の本文の検証に、消した・まとめたテスト1本につき1行の表で、壊れ方と結果（(a) 落ちたテストの名前・(b) 止めた
   検査とその出力・(c) 前の版でも落ちなかったこと・壊れ方が書けない理由（恒真式・宣言の書き写し・約束ごと消した））を書く。
   約束ごと消した行は、当たる課題の約束の行と、消した実装を書き、変えた約束なら新しい約束を見るテストの名前も書く。消した実装は、名前を持つもの（関数・定数・印）を丸ごと
   消したならその名前を書く。持ち主（関数・部品・ハンドラ）が残り、その中の一部（呼び出し・分岐・行）だけを消したなら、持ち主
   （ファイルと、名前か画面の位置）と、消した一部が使っていた名前を書く（例: `UsageGuide.tsx` の ✕ のボタンの `onClick` から
   消した `onEndRef.current()` の呼び出し）。1本は、前の版に
   あって後の版に無いテスト（関数・`it`）と、表から消した行で、表の行を持つテストを丸ごと消したときは中の表の行ごとに1本と
   数える（テストの実行が数える本数と同じ）。行の数はその数と同じにする。
   同じ側の行は、どの書かれた比べ方（実装のファイルとその比べ方）の同じ側かも書く。

**消す・まとめる・題名を変えるテストを名指す設計書の行は、同じ差分で直す。** 手を入れたテストの
ファイル名を `docs/` で grep し（例: `grep -rn 'legends.test' docs/modules`）、そのテストが確かめる・固定すると書いた行があれば、
保証の今の置き場（残す側のテストとその題名・型・源泉の宣言）に合わせて書き直す。

**「対象へ届いているか」は測れる。** `pytest --cov=app --cov-context=test`でテスト単位の
文脈を取り、対象モジュールの行を1つも実行していないテストを機械的に出す。ただし
**定数・型宣言を見るテストは対象の行を実行しない**（SQL文字列の定数・規則表・Pydanticの
`Field`制約・`Protocol`の宣言はimport時に評価される）ので、この信号だけでは判定しない。
出たものを3問へ通す。

**本番のデータそのものに対する不変条件**（「全材料が説明文を持つ」「参考点の値が有限」）も
1問目を通す——型で通らなくすれば検査は不要になる。型でも導出でも
保証できないものだけが、そのデータを宣言しているモジュールのテストへ残る（その場合は
差し替えない節を分け、ファイル冒頭の宣言にそう書く）。

## 消すべきテストの型

| 型 | 見分け方 |
|---|---|
| **正しく直すと落ちるテスト** | 実行せずに、SQL文字列やパスへ特定の名前が含まれることをアサートする |
| **空振りの検知器** | 「Xが作る形を検証する」と書きながらXを呼ばず、期待値を手で書いている |
| **宣言の書き写し** | 定数・モデルの既定値・レジストリの中身をテスト側へ再掲して突き合わせる。ただし宣言の並び・値が利用者に見える振る舞い（地図に描く順・既定で選ばれる項目）を決めているなら、書き写しではなく振る舞いの確かめである。宣言に対して書いてよいのは、型・導出で保証できないときの、**導出した母集団すべてに対する不変条件**（要素が1つ増えたときに発火するもの。「そのテストは要るか（3問を順に）」の「本番のデータそのものに対する不変条件」）だけで、手で名指しした数件に対する検査は書かない（設計原則 構造仕様12） |
| **恒真式** | `set(versions) == set(TILE_SHAPES)`（同じ内包表記の結果を同じ定数と比べる） |
| **効いていない除外リスト** | ガードに付けた除外の一覧（効いているかを測っていない一覧には、存在しないファイル名や、先行条件で既に弾かれるものが残る） |
| **消したものを見張るアサーション** | `assert not cleared`のように、呼ばれないことを確かめる |
| **等価テスト** | 新旧2実装の出力一致。代わりに、**入力に対するあるべき値**を書いた期待値テストを**生きている1本の実装へ当てる**。移行が終わったら等価テストは消す |
| **カバレッジの水増し** | 「落ちるとき何が壊れるか」に答えられない。`MIN <= MAX`・`isinstance(x, int)`・定数への等値 |
| **実装の規則の再実装** | 実装が「名称に『特別警報』を含むか」で決めているのを、テストも同じ規則で期待値を作る |
| **型が保証していることの検査** | 戻り値が3値の`Literal`なのに「3値のいずれかへ落ちる」を確かめる |
| **本番に生えたテスト専用の口の検査** | テスト専用の初期化関数（`reset_*_for_testing()`の類）が状態を空にすることを確かめる |
| **宣言から作った足場へ宣言を当てる** | 宣言された全クラスについて`em.lc_{key}`が読めることを、`lc_{key}`という列を自分で用意して確かめる。宣言された語彙の全件が`= ANY(:語彙)`で真になることを確かめる。**振る舞いがidごとに違わないなら、性質ごとに1件で足りる**。「宣言した列・値が実在するか」は実テーブル・実カタログへ通して確かめる |
| **テストのフィクスチャに対する不変条件** | `AXIS_DEFINITIONS`の全軸が排他チェックを通ることを確かめる（テスト中の中身は注入したフィクスチャ）。**その宣言がテスト中に差し替わるなら、全件の不変条件は書かない**。足場そのものを対象と名乗る足場のテスト（パターン5）はこれに当たらない |

## 残すべきテストの型（起こし直しで取り込む）

これは**旧版から取り込むかどうか**の判定で、「そのテストは要るか」の3問とは別の問いである
（3問を通った検査のうち、**仕様と実装を読んで復元できないもの**だけが取り込む対象になる）。
仕様と実装から復元できるものは取り込まない。

| 型 | 見分け方 |
|---|---|
| **外部の権威との突き合わせ** | 期待値の出どころが公開値・配布物・実測で、コードのどこにも無い |
| **過去のバグを刺した回帰** | 「この入力で落ちた」という事実。由来（経緯）はタスクの issue が持つ（テストのdocstringへ経緯は書かない）。消すかどうかは「そのテストは要るか」の3問で決める |

**「意図的に外した値」は残す理由にならない。** 除外を、値を名指しして「入っていない」と確かめるテストは書かない。
除外の理由は設計書（`docs/modules/*.md`）が持ち（実測値は[comments.md](comments.md)「残すと決めたものの行き先」の
(b) で設計書へ置く。宣言の隣に要るなら、その節を名指す1行だけ）、テストは書かない。残すのは**期待値の出どころが
テストの中にある**ものだけである。
