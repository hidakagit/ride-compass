# テストの足場とフェイク

番号は CLAUDE.md「原則」の番号。「3問」「1問目」等は、[testing.md](testing.md)「そのテストは要るか（3問を順に）」の問いを指す。

## テストの足場で、本来のNGを覆わない

- テストは要るものを自分で宣言し、無ければ落ちる形にする。足場（共通のフィクスチャ・セットアップ・共通のフェイク）で既定を
  配ったり失敗を吸ったりしない。覆う形は、次の「代わりに」の形で書く。（原則9・11）

| 覆う形 | 代わりに |
|---|---|
| 既定を自動で入れる足場（autouseのフィクスチャ・vitestの`setupFiles`） | 要るテストが引数（`usefixtures`）で取る。autouseで配ってよいのは、何も与えないものだけ |
| 例外を握りつぶす`try`/`catch` | 失敗してよい操作だけを囲み、それ以外の失敗は失敗として記録する |
| 環境が無いときのスキップ（`pytest.skip`・`skipif`・`test.skip`） | 落とす。外すかどうかは実行する側がマーカーで選ぶ（`-m "not postgis"`） |
| 落ちたテストを再試行する設定（Playwrightの`retries`） | 再試行しない（`retries: 0`）。不安定に落ちたら、落ちた原因を直す |
| 警告を無視する設定 | testing.md「警告は既定でエラー」の条件を満たすものだけ |
| 呼び出しの内容を見ずに値を返すフェイク（`lambda *a: 値`・任意の属性を受ける器） | 本物の署名に当てる形にする（例: `tests/bound_fake.py: bound`）。組み立てて返す型は本物を使う |

- 次は覆いに当たらないので、足場に置いてよい: 並行実行のための隔離（作業ツリーごとのDB・一時ディレクトリ）・時刻の固定・
  テスト環境が作れない本番の規則を本番と同じに置くもの（`vitest.setup.ts`の`pointer-events-auto`の規則）・呼ばれないことを
  確かめるフェイクと例外を投げるだけのフェイク（どんな引数でも同じ結果を狙う）・`await`されないPromiseの未処理扱いを避ける
  `catch`（後で同じPromiseを検査する）・E2Eの共通応答のうち画面まで進める導線（testing-e2e.md パターン4「共通フィクスチャに
  置くもの」）。（原則9）
- 前提の宣言は、覆いを外して落ちたテストだけでなく、外しても通るが主張がその前提に立つテストにもさせる。（原則11）
- 覆いを外して落ちたら、どちらの欠陥かを分ける。前提を宣言していなかっただけならテストに宣言させ、本物の型が拒む入力を足場が
  通していた等は、実装の判断が問われるものとして要確認にする（testing-review.md「要確認の出し方」）。（原則1・11）
- 片付けは、本番のコードが既に持つ操作（持ち主のオブジェクトをテストごとに作り直して注入する・本番の寿命の口（閉じる・作り直す）を
  呼ぶ等）だけで書く。片付けのためにappへ口（テスト専用の初期化関数・引数）を足さず、可変の状態を公開名にもしない（設計原則
  構造仕様15）。本番の操作だけで片付けられない大域状態は、testing.md「確かめる高さ」の可変の状態の箇条の順で、実装の側を直す。（原則3・8）

## フェイクの数は、実装の外向き参照の写し

- 自分のDB（Repository）は差し替えず、SQLは実DBで確かめる（testing-backend.md パターン2）。Repositoryを差し替えてよいのは、
  その上の層に固有の判断を確かめるときだけで、そのときもRepositoryへの呼び出しは確かめない（読むだけの相手）。（原則5）
- 実物は組み立ての関数で作り、組み立ての関数は、そのテストが関心を持つ値だけを引数に取って、ほかを妥当な既定値で埋める。
  判定に効く値は必ず引数で渡す。（原則3・11）
- 2つ目以降のフェイクを書きたくなったら、対象の外向き参照（実装がimportする`app.*`のモジュール数）を数え、4本以上なら、
  テストの書き方より先に、そのモジュールが何を読んでいるかを問う。層の境目（Service・Engine）の差し替え先が5メソッド10引数の
  ように広いなら、契約の狭い層ではなく癒着として、実装の側を直す案を出す。（原則9）
- **共有フェイクへ出すのは3箇所目から**にし、寄せる前に、その外部が本当に3つから読まれるべきかを1度問う。（原則8・9）
- 起こし直しのあとで共有フェイクを見直すときは、その共有物が無ければ書かれなかったテストが混ざっていないかも一緒に見る。（原則8）

## パターン5: 外部クライアントのフェイクは共有モジュールから取る

- 複数のテストで同じ形になるフェイク・足場は、共有の置き場（例: backendは`backend/tests/`直下の、`test_`で始まらないモジュール
  （`conftest.py`を除く）、frontendは`frontend/src/testing/`）に置き、用途を先頭のdocstring・コメントに書く。共有の組み立ての関数があるものは、
  それを全部の場所が使う（`frontend/src/testing/routeFixtures.ts: makeRouteCandidate`は`e2e/fixtures.ts`も使う）。（原則3）
- 共有の足場とフェイクが自分のテストを持つかは、3問で決める。本物の口を真似て、ずれうる振る舞いを自分で持つフェイクは持ち、
  同じ公開の口に対するテストを本物とフェイクの両方へ流してずれを止める（本物の側は、HTTPならrespx、DBなら実DB、テスト環境で
  作れない`maplibre-gl`は実ブラウザのE2Eで流す。例: `frontend/src/testing/mapTrace/recordingMap.contract.ts`）。組み立ての足場は、
  崩れても頼るテストが緑のまま通る約束だけを確かめる。値を並べるだけ・1行の委譲の足場（1問目）と、約束が崩れると頼るテストが
  赤になる足場（3問目）は、自分のテストを持たない。（原則8・11）
- フィクスチャ同士に順序が要るなら、先に動くべきものを引数に取る依存で書き、宣言順に頼らない。（原則3）
