# ログ方針（実運用調査のためのログレベル・粒度）

本番のbackendコンテナのログだけで、障害の調査を終えられるようにするための決まり。

## 決まり

1. エラーと警告は、`debug_mode`に関わらず常に出す。`debug_mode`は DEBUG の詳細を増やすためだけに使い、ERROR・WARNING を出すかどうかを切り替えない。（原則4）
2. 常に出す INFO は、1リクエストにつき集約した1行にし、あとで数え直さずに読める形にする。イベントごとの詳細は DEBUG に出す。（原則4・8）
3. リクエストIDはフォーマッタが全部の行に付けるので、個々のログの文にIDを書き込まない。（原則3）
4. **常時出るログ(INFO以上)の座標は小数2桁(≈1km)へ丸める。** 道路のノードのOSMのid（`osm-node-…`）と、OSMの道のidを
   含む区間の鍵（`way-…`）も座標に数え、常時出るログとそこへ載る例外の文には書かない。ノードは小数2桁の地点で、
   区間は件数で書く（ノードと区間の id はユーザーの決定。tasks#558・tasks#561）。DEBUGはそのまま出してよい。APIキー・認証ヘッダは
   どのレベルでも出さない。（原則5）

## レベルの使い分け

ログのレベルは次の表で選ぶ。（原則4）

| レベル | 出す条件 | 出すもの |
|---|---|---|
| ERROR | 常に | 未処理例外（スタックトレース付き）、想定外の内部エラー |
| WARNING | 常に | 利用者に影響する準異常（外部APIの失敗・429拒否・候補0件等）。同じ種類の警告は`debug_log.py: log_throttled_warning`でカテゴリごとに抑える |
| INFO | 常に | 1リクエスト1行のアクセスの要約、ルート生成の段の要約、起動時の構成 |
| DEBUG | `debug_mode`のときだけ | 外部API・キャッシュのイベントごとの記録、方位ごとの trace の失敗理由、距離の絞り込みで落とした詳細 |

## 使う仕組み

新しく書くコードは、次の仕組みでログを出す。

### 外部API・キャッシュアクセス

- 外部APIとキャッシュを読む所は`debug_log.py: log_external_call`で囲む。（原則4）
- 取れないのが正常な場合（GSIの整備区域外の404等）は、`fields["result"]`を`"error"`にせず、理由を別の欄（`fields["status"]=404`等）に残す。WARNING でログを埋めると本当の失敗が見えなくなるため。実例は`gsi_tile_client.py: GsiTileClient.get`の404の分岐。（原則4・7）
- 例外を捕まえて既定値（空・None）へ倒すときは、`debug_log.py: mark_failed`で失敗を記録し、自前の WARNING を書き足さない。対象を示す値（タイル・ID等）は`log_external_call`へ渡す`fields`に入れる。（原則3・4）
- タイル1枚ごとに通る口（とそこから呼ばれるキャッシュ等の下の層）で、呼び出しの失敗ではない劣化（入力の時刻が予報の範囲外・キャッシュを読めず取り直す・補間できない等）を知らせる警告は、`debug_log.py: log_throttled_warning`で出し、`logger.warning`を直接書かない。タイルでない口でも、利用者の要求ごとに通り、要求の中身に依らない原因（配信元の配色・コード・配信の止まり、置き場のファイル、プロキシの設定等）を知らせる警告は同じにする。1回の操作で1度しか通らない口（ルート生成・定期の同期・起動時の確認等）は、この限りでない。（原則4）
- キャッシュの hit/miss は、値を使う側の`log_external_call`の1か所で数える。その下のキャッシュの層（ディスクの`tile_cache.py`・`tile_persistent_cache.py`等）は`log_external_call`で囲まず、失敗を`debug_log.py: log_throttled_warning`で出す。失敗しないプロセス内メモリだけの層（`infrastructure/detour_ratio_cache.py`等）はどちらも出さない。（原則3）

### 429拒否

- レート制限・同時実行の制限で429を返す所では、`debug_log.py: record_rate_limit_rejection`を呼んで拒否を記録する。（原則4）

### リクエストID

- frontend から backend を呼ぶ新しい呼び出しは、`lib/apiClient.ts: requestApi`を通す。（原則3・7）
- リクエストIDは DebugConsole の detail に出し、利用者に見せる失敗の文言には混ぜない。（原則5）

### 処理ステージのサマリ

- 複数の段からなる重い処理（ルート生成等）は、段ごとの所要時間と、中間結果の減り方（折返し点の候補→trace の成功→距離の絞り込みの通過→上位n件）を1行の INFO にまとめる（実例は`route_generator.py`）。利用者に何も返せない結果（候補0件等）は WARNING にし、どの段で減ったかを同じ行に入れる。（原則4）
- CPUの重い処理（グラフの構築・MVTのエンコード等）を足すときは、所要時間を測る。要求ごとに通る口（タイル1枚の生成等）なら`log_external_call`で囲み、複数の段からなる処理の1段なら、その段の所要時間を上の1行に足す。（原則4・10）

### 外部データの読み飛ばし

- 外部から配られるデータ（CSV・JSONの配列等）を読むパーサが、形の合わない記録を飛ばして続けるときは、1件でも飛ばしたら、飛ばした件数と総件数を取得1回につき1行の WARNING で出す。行ごとには出さない。配布元が宣言した除外（運用終了済みの地点等）と空行は、飛ばした件数に数えない（実例は`infrastructure/wbgt_client.py: _parse_point_master`）。（原則4）
