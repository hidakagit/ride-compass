## 流れの摩擦を記録する

導く原則: 6・3。

担当と開発機の対話のセッションは、流れそのもの（`docs/conventions/flow.md` と流れのスキルの手順・`tools/flow-gate` の道具・
担当のワークフロー・検査）で困ったことに当たっても、そのために起票しない・その場だけを直さない。直すのは周期レビューで、
前の回からの摩擦を集めて原則から全体で見て決める（`.claude/commands/review.md`「流れの摩擦を集める」）。

- **書くもの**: この回に実際に起きたことだけ。例: 手順どおりに打った道具が断った・失敗した、手順に無い場面や手順どうしが
  食い違う場面で自分で決めた、同じ長いコマンドを手で組み立て直した、待ち（鍵・CI・重い処理の順番）が作業より長かった。
  観測の無い思いつきは書かない。
- **書き方**: 作業中のタスクの issue の報告（担当は終え方の要約。後始末が終わりのコメントへ写す）に、行の頭を「流れの摩擦:」に
  した行を1件1行で書く。手順のどこで・打ったコマンドと出た値を書き、元の作業を続ける。

## 起票する

導く原則: 3・4。

製品（コード・文書・テスト）の、今のタスクの範囲の外の気づき（.claude/skills/task-work/SKILL.md「範囲の外の気づき」）を起こすときの決まり。

- **今の差分で直せるものは直す**: 今のタスクの範囲で片付く直しは、起票せずに今の差分へ入れる（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。
- **直す場所を書く**: 探す前に、変える所（ファイル・関数・設定の項目・文書の節）を1行で書く。症状ではなく、どこを変えれば
  消えるかで書く。
- **重ねない**: まず `git fetch origin` のあと、直す場所を今の master の版（`git show origin/master:<パス>`）で読み直し、既に直って
  いれば起こさない。直っていなければ、直す場所が同じ開いた issue を探す（探し方は「前後関係と組」の「探す」）。直す場所が同じ issue があれば、症状が違っても新しく起こさず、
  起きたこと（日時・作業中の issue の番号・打ったコマンドと出た値）と、同じ直す場所に当たる別の症状であることをその issue へ
  コメントで足すだけにする。寄せた先が前提待ち・保留でも寄せる（そこが直れば消える）。寄せた症状まで直すかは、寄せた先の作る担当が
  [fixing.md](../../rules/fixing.md)「直し方」の「範囲は性質から導く」で決める。
- **書き方**: 「issue の形」のとおりに本文をファイルへ書き、hidakagit-bot の名義で起こす
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --type <種類> --title <題名> --body-file <ファイル>`）。
  背景の節に、どの issue の作業中に・何を打って・何が出たか（観測値）を書き、やることで直す場所を名指す。規模と優先度は
  `field.js` で入れる（「ラベルと種類と欄」の「規模の札」「優先度の見積もり」）。ほかの開いた issue との前後関係と組も探して張る（「前後関係と組」）。
- 入口は種類で決まる（`docs/conventions/flow.md`「ステータスと割り当て」の「入口」）: 保守・調査・不具合は未着手で入り、そのまま
  進む。要望（種類なしも）は保留で入るので、同じ回に、`field.js` で欄を入れたあと（Project に入って保留になってから）
  .claude/skills/ask/SKILL.md「問い」の形で `ask.js` で問う（入る前に打つと、ステータスが無いので断られる）。起こした・コメントを足した issue の番号は、
  自分のタスクの issue への報告に書き添える。

## issue の形

導く原則: 4・3。

**題名**は、何をするか（または何が困るか）だけを30字前後で書く。数値・経緯・やり方・括弧書きの補足は本文へ。

**本文**は次の節をこの順に並べ、1 以外は `<details><summary>節の名前</summary>` で畳む。節ごとに「答える問い」が1つだけあり、
それに当たらないものはその節に書かない。

| 順 | 節 | 答える問い | 書くもの | 書かないもの |
|---|---|---|---|---|
| 1 | 要約（畳まない） | 開いて2行で何が分かるか | 何が起きていて、何をするか（1〜2文） | 経緯・数値の詳細 |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | なぜやるのか | 事実（誰がどの場面で何に困るか。不具合なら再現の手順と、期待する動き・実際の動き）。保留中は最後に「再開の条件」 | 案・やり方 |
| 3 | やること（調査は: 調べ方） | どうやるのか | 案と手段。番号付き。段階があれば段階ごと | なぜやるかの事実 |
| 4 | 決めること | まだ決まっていないことは何か | 決まっていないことを1行ずつ（問うのは1度に1つ。問うているものは本文の先頭にある） | 決まったこと（→ 6）。無ければ節ごと省く |
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる形のチェック（`- [ ]`。本文のチェックはここにだけ使う。チェックの無いものが残るとゲートは閉じない）。マージの時点で確かめられることだけを書く（ユーザーの確認は `- [ ] ユーザーが確かめる: …` の行）。Actions の担当が確かめられる形で書く: 開発機にしか無いもの（`docs/conventions/flow.md`「担当」の「開発機が要る」）で確かめる条件は、同じことをテスト DB・CI で確かめる形（前後の SQL 文の比べ・テストの期待値等）で書き、書けなければ起票のときにラベル「開発機が要る」を付ける（マージのあとの残りにだけ要るなら付けない。.claude/skills/task-work/SKILL.md「確かめる担当」の3）。マージの前に済ませる本番への書き込み（コードが新しく読む表を作る等。.claude/rules/deployment-sync.md「コミットと同時に揃えるもの」）が要ると起票の時点で分かれば、それを本番で済ませたことを条件の1行に書く（ラベルは付けない。作る担当がコードを作ってから返す。`docs/conventions/flow.md`「担当」の「自動で進めないもの」）。本番での前後の比べは、何をどう測るかを書いたマージのあとの残りの1行にし、前の値を取る行を別に書かない（前の値はマージの前に確かめる担当が取る。.claude/skills/task-work/SKILL.md「確かめる担当」の5） | 手段。マージのあとにしかできない作業（本番での操作・公開・長い観測）は、自動にするか別の issue にして blocked by でつなぐ（待つ日時があれば、その issue に着手可能日時を入れる） |
| 6 | 経緯 | いつ何が決まり、何が変わったか | 日付つきで1行ずつ、新しいものを上に。無ければ省く | 問いと答えの全文（答えのコメントにある） |
| 7 | 規模と優先度の根拠 | 規模の札と優先度の見積もりの根拠 | 札と値と、それぞれの根拠1行（「ラベルと種類と欄」の「規模の札」「優先度の見積もり」） | ― |

- **本番で人が見つけた不具合**（CI・デプロイの確かめ・見張りではなく、利用者やユーザーが本番で見つけたもの）は、2 の不具合の節に
  拾えなかった層と理由を、層（CI のテスト・e2e・e2e-live・デプロイの確かめ等）ごとに1行書く（その層が何を見ていて、なぜこの形を見なかったか）。
- 節の中では、並べるものは箇条書きにし、長い段落を作らない。複数の案や観点を比べるときは表にする。
- `<details>` の中は、`<summary>` の行のあとに空行を1つ入れてから書く。
- 問いに答えが出たら、Claude は 4 からその行を消し、6 へ1行足す。
- **誰がやっても同じ品質になるように書く**。会話でしか共有していない判断基準・母集団の決め方・完了の条件も issue に書き、
  そのタスクを実行する人が、対象をどう列挙し、何を満たせば完了で、
  何を根拠に残す/消すを決めるのかを、issue だけ読んで再現できる状態にする。「実測して判断する」と書いたなら、何をどう測るかまで書く。
- **1つの Pull Request に収まらない・方針を選ぶタスクは、着手したら最初に背景・方針を issue に書く**。
- hidakagit が GitHub の画面で種類のテンプレート（置き場の `.github/ISSUE_TEMPLATE/`）から作った issue は、節が
  見出し（`###`）で並ぶ。Claude は着手するときに、この形（畳む節）へ整える。

## ラベルと種類と欄

導く原則: 3・1・4。

- 種類は Issue types（不具合・要望・保守・調査）で、1つのタスクにちょうど1つ。
- 1つのタスクに1つの値を持つもの（Status・規模・優先度）は、Project の単一選択の欄に置く（組織の issue fields は使わない）。優先度は仕事としての重さの見積もりで、
  入っている値は誰かが決めた値（ユーザーが付けた・Claude が起票で下の「優先度の見積もり」のとおり入れた・段階が入口で親から継いだ）だけで、
  誰も決めていない欄は空のまま見せる。`field.js` は入っている
  値の書き換えを断る（変えるならユーザーに問う）。振り出しはその選択肢の順に並べ、空は `flow.config.json: project.unsetPriority` の位置に置く。
  `field.js` は、起票の直後でまだ Project に入っていない issue なら、入るまで待ってから書く。今の値は値を渡さない
  `field.js <番号>` で読む（書かずに、Status を含む全部の欄を出す。`gh issue view --json projectItems` は Status しか出さない）。
  欄は機械が決めるものなので、回答フォームには出さない（ユーザーが直すときはボードで）。選択肢を足せば並べ順はそのまま効く。
- 着手可能日時（`flow.config.json: project.startField`。Project の文字の欄）は、その時刻より前には振り出さない日本時間の日時で、
  `YYYY-MM-DD HH:MM`（時刻を省いた `YYYY-MM-DD` は 00:00）で書く。誰が入れてもよい（ユーザーはボード・スマホで、Claude は
  `field.js` で。`field.js` は形の合わない値を断り、`YYYY-MM-DD HH:MM` にそろえて書く）。ステータスは変えず、未着手のまま待つ。
  時間を待つ残り・外部の公開待ち・取得制限が解ける時刻・決まった日の作業など、「この時刻以降にやる」を表す。今との比べは日本時間の分で行い、
  ボードで書いた値の形が合わなければ、振り出さずに待つ理由として出す（`tools/flow-gate/src/rules.js: waitsFor`）。
- ステータスは Project の Status だけが持ち、ラベルに写さない。動かすのは回答フォーム・ボードの移動・Pull Request の出来事・Claude の道具（`move.js`・`ask.js`）・閉じる操作で、どれもゲートが遷移の表で照らす。
- ラベルはユーザーが付ける札（例: 急ぎ）。状態・操作待ちのように、ステータスと問いで表せるものはラベルにしない。「急ぎ」はユーザーの「急いで」の依頼で、振り出しは優先度の欄より先に並べる。「開発機が要る」は担当かユーザーが付け、振り出しはそのタスクを飛ばす（`docs/conventions/flow.md`「担当」）。回答フォームは、置き場に定義されたラベルを
  名前を持たずに全部出す。前提は blocked by で付ける（「前後関係と組」）。
- **規模の札**（Project の欄「規模」）: 実装＋テストの変更行（追加＋削除。生成物・文書・設定を除く。分け方は
  `scripts/review_checks.py: change_kind`）が200以下ならS・1000以下ならM・超えればL。本番DBへ書くタスクは行数によらずL。
  Claude は起票のときに見込みの札を `field.js <番号> 規模 <S|M|L>` で入れ、規模と優先度の根拠の節に根拠を1行書く。
  見込みは次の順で決める: ①調べないと分からない部分は先に調べる段階として切り、その段階はS ②本番DBへ書く予定ならL
  ③ファイルを置き換える作業は、置き換えるファイルの今の行数×2を、1本ずつ見て減らす作業は、対象のファイルの今の行数の4分の1を
  変更行の見込みとして上の閾値で決める ④それ以外は、変わると見込むファイル数（テストを含み文書を除く。契約を変えるなら読む側も数える）が
  7以下ならS・20以下ならM・超えればL。欄は見込みのまま残し、作り終えたあとの札（`python scripts/review_checks.py change` の
  「規模:」の行）で付け直さない。
- **優先度の見積もり**: Claude が起票するときは、Project の欄「優先度」を仕事としての重さで見積もり（`field.js <番号> 優先度 <高|中|低>`）、
  規模と優先度の根拠の節に理由を1行添える。高は利用者に届いている不具合・データの誤り・止まっている流れ、低は調べ・整理・見た目の小さな直し、
  それ以外は中。ユーザーの「急いで」はラベル「急ぎ」で、見積もりとは別に振り出しが先に並べる。
- 状態を動かしただけのコメントは書かない。本文と判断材料の詳細は `<details>` に入れる。

## 前後関係と組

導く原則: 3・4。

別々に起きたタスクどうしの関係は、GitHub の標準の依存関係（blocked by・blocking）だけで持つ。前提が開いている未着手は、見回りが飛ばす（`dispatch.js --dry-run` で見られる。ゲートは前提を見ない。`docs/conventions/flow.md`「ステータスと割り当て」）。

- **前後関係**（後の作業が先の中身に依る: 先の結果しだいで後の成果が要らなくなる・作り直しになる・後の判断の材料が狂う）:
  後の issue に先を blocked by で張る
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue edit <後> -R ridecompass/ride-compass-tasks --add-blocked-by <先>`。起こすときは `GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --blocked-by <先>`）。
  張ったら、張った理由（重なった直す場所の名前と、後が先のどの中身に依るか）を後の issue に1行書く（起こすときは本文のやることの
  最後、あとから張るときはコメント。段階の「前提を張った理由」と同じ）。
  - **中身に依らない重なりは張らない**: 直す場所が重なっても、後の作業が先の中身に依らないなら前提にせず並べて進め、後から
    マージされる側が.claude/skills/task-work/SKILL.md「競合を解く」のとおりに合わせる。中身に依らない重なりの例（これに限らず、
    後の作業が先の中身に依らない重なりはどれも張らない）:
    - 生成物（`frontend/src/types/generated/`・`openapi.json` 等）: master を取り込んでから作り直せば揃う。
    - 同じ文書・同じファイルの、別の行・別の節。
    - 先が既にマージした所: 重なりは master にあり、後はそれを取り込んで作る。
  - **向き**: 片方の結果しだいで他方の成果が要らなくなる・作り直しになるなら、要らなくする側を先（前提）にする。同じ所を触るので
    ぶつからない順に並べたくなる場面でも、この向きを優先する。どちらの結果も
    相手の作業に効かないなら、前提にしない（上の「中身に依らない重なり」）。
- **組**（同じ本番の作り直し・同じ変更の範囲に触り、別々に進めると作り直しや確かめが2回になる・先の確かめが後の変更で崩れる）:
  - 合わせて1つの Pull Request に収まるなら、1つの issue にまとめる。片方を閉じることになるので、残す側の issue で問い、
    未着手の答えなら残す側の本文へもう片方のやること・完了の条件を移し、もう片方は移した先を書いて見送りで閉じる。
  - 収まらないなら、先にやるほうを後の前提（blocked by）にする。本番の作り直しと本番での確かめは後の issue で1回だけ行い、
    先の issue の完了の条件には入れない（後の issue の本文に「#<先> の分も含める」と書く）。
  - 親子（段階）にはしない。段階は1つのタスクを分けたもので、組のそれぞれは自分の採否と完了の条件を持つ。
- **申し送り**（ほかのタスクに、その範囲で決めてほしい・済ませてほしいこと）: 相手の issue へコメントで書き、相手の本文（完了の
  条件）は書き換えない（本文はそのタスクを進める担当が書き直す。.claude/skills/task-work/SKILL.md「作る担当」の6・「確かめる担当」の3）。相手の作る担当が着手する前なら着手のときに読まれ、着手より後に届いたものは確かめる担当が完了の条件へ足す
  （.claude/skills/task-work/SKILL.md「確かめる担当」の3）。
- **探す**: 起票するとき・作る担当が着手するとき・段階に分けるときに、自分の**直す場所**（変える所。
  ファイル・道具の関数・設定の項目・手順の節。同じ派生の段・同じモジュール・同じ本番の作り直しもその例）を1行で書き、その名前
  （パス・道具名・節の名前）と題名の語で開いた issue を探す。
  当たったものは題名と本文を読んで判じ、同じ直す場所に触るものがあれば前後関係（後が先の中身に依るときだけ）か組を張り、
  張った関係と理由を起票の本文か自分のタスクの issue への報告に書く。重なっても中身に依らないので張らなかったものも、その理由を
  同じ所に1行書く。何も無かったときも、探した鍵
  （直す場所と検索した語）を報告に1行書く。
  - **打ち方**: 語（パスは最後の名前）1つにつき1回、`GH_TOKEN=$FLOW_BOT_TOKEN gh issue list -R ridecompass/ride-compass-tasks --state open --limit 1000 --search '"<語>" in:title,body'`
    を Bash で打つ。
  - 着手したタスクに、まだ閉じていない前提が見つかったら、張ったうえで問う（未着手の答えなら、前提が閉じるまで待つ）。
    答えが前提を張って待つことを求めた（張るのが答えのあと）なら、答えで未着手になった時点では前提が無いので、見回りがすぐ作る
    担当へ振り出す。その担当は前提を張り、Pull Request も問いも出さずに終える（後始末が未着手へ戻し、見回りが前提が閉じるまで振り出さない。`docs/conventions/flow.md`「担当」の
    「担当のワークフローの1回」の4）。
    自分のタスクがほかの issue の先に当たるなら、張るだけで続ける。
  - 着手のあとでほかの担当が自分のタスクに前提を張ったら、上の「向き」と同じ基準で決める。前提の結果しだいで自分の作業が
    要らなくなる・作り直しになるなら、自分で見つけた前提と同じに扱って問う。同じ文書の行が重なるだけ（前提の中身に依らない）なら
    問わずに、前提が変える行を避けて進める（重なった行は、後からマージされる側が.claude/skills/task-work/SKILL.md「競合を解く」のとおりに合わせる）。そう判じた
    理由（何が重なり、なぜ中身に依らないか）を自分のタスクの issue の経緯に書く。

## 段階に分ける

導く原則: 4・1。

1つの Pull Request に収まらないタスクは、段階ごとに親と同じ形（「issue の形」）の issue を作り、普通のタスクとして進める。

    node tools/flow-gate/bin/stage.js <親の番号> <題名> <本文のファイル> [前の段階の番号...]

- 道具は段階を親を付けたまま作り、前の段階を blocked by にする（前の段階が閉じるまで見回りが振り出さない）。Project へは「Auto-add sub-issues to project」が
  入れ、ゲートが入口で未着手・Claude にし、優先度の欄が空なら親の値を入れる（`docs/conventions/flow.md`「ステータスと割り当て」の「入口」）。
  規模は `field.js` で入れる（「ラベルと種類と欄」の「規模の札」）。
  種類（Issue types）は、道具が作るときに親と同じものを付ける（親に種類が無ければ付けない）。
- 段階を作るときは、兄弟の段階どうしの直す場所（「前後関係と組」の「探す」）を照らし、重なるなら後が先の中身に依るかを見て、
  依るものだけを前後関係の向きで先の段階を後の段階の前提にする（`stage.js` の「前の段階の番号」で渡す）。
  前提を張るのは、後の段階が前の段階の中身に依る（前の段階の結果しだいで後の段階の書き換えが変わる・前の段階の成果が後の段階の
  材料になる。「前後関係と組」の前後関係）ときだけにする。直す場所が重なっても中身に依らない重なり（生成物・同じファイルの
  別の行や別の節など。「前後関係と組」の「中身に依らない重なりは張らない」）は前提を張らずに並べる。「念のため」「層の順に」は張る理由にしない。
  - 段階の本文のやることの最後に、前提を張った理由（重なった直す場所の名前と後が前のどの中身に依るか、または成果を材料にする
    前の段階）か「前提なし」（重なりがあれば、中身に依らない理由も）を1行書く。
- 道具は親にもその段階を blocked by で張り、親が進行中なら未着手へ戻す。親は段階が全部閉じるまで、前提待ちとして振り出されない。
  sub-issue（親子の印）はボードで進み具合を見せるためだけのもので、流れは blocked by だけで決まる。
- 親の本文の「やること」に段階の番号を並べる。
- 親の作業ブランチ（`orch/tasks-<親の番号>`）に push 済みの変更があれば（分ける前の回が作り始めていた）、段階の1つへ渡す。
  渡す先は、その変更を含める段階のうち前の段階を
  持たないもの（ふつうは最初の段階）にする。段階を作ったあと、親の作業ブランチに今の master を取り込み（`git merge origin/master`）、
  `git push origin HEAD:refs/heads/orch/tasks-<段階の番号>` でその段階の作業ブランチとして置き、段階の本文のやることに載せた
  コミットの ID を書く（`stage.js` のあと本文を `gh issue edit` で書き直す）。段階の作る担当は、
  .claude/skills/task-work/SKILL.md「作る担当」の1の、作業ブランチが GitHub にあるときの手順で続ける。
- 段階は1件ずつ、自分の作業ブランチ（`orch/tasks-<段階の番号>`）と Pull Request で進む。段階が全部閉じると親の前提が閉じ、
  見回りが親を作る担当へ渡す。作る担当は、段階で確かめていない親の完了の条件を確かめて閉じる（.claude/skills/task-work/SKILL.md「作る担当」）。
