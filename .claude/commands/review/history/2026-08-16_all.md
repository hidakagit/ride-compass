## Phase 6: 矛盾と判断（相互確認）

### 対立1: T59バックグラウンド構築のDI工場迂回（overall） vs 実装の正当化（complexity）
- 競合: overall観点では region_service.py が GraphService を直接構築し
  モジュールレベル可変状態3つ＋専用semaphoreを持つのはDI工場迂回・責務逸脱の疑い。
  complexity観点では「リクエスト寿命を超えるタスクにFastAPI Dependsは使えない」
  「rate_limiter前例のプロセス内状態」という根拠コメントが十分。
- **判断: 許容（KEEP追加候補）**。根拠: (1)構築形は dependencies.py:
  get_graph_service と同形で乖離がない (2)T59緊急修正の実障害（プール枯渇502）を
  踏まえた設計で、config.py に定量根拠（6+6/15枠）が明記されている (3)代替案
  （タスクキュー導入）は現フェーズ（個人開発・低利用規模）では複雑度の対価に合わない。

### 対立2: domain/accident.py の `_density_per_km` 薄い複製（設計原則2 vs 依存最小化）
- 競合: 「同じ集約ロジックが traffic.py と accident.py の2箇所」は原則2
  （2箇所書き禁止）に見える。一方 overall観点では accident→traffic の import は
  意味的に不要な依存。
- **判断: 複製維持（KEEP）**。根拠: 変更理由が異なる（事故密度のみ収録年数正規化を
  含む別式であり、「同じ理由で変更されるか」基準＝設計原則6で共通化対象外）。
  docstring に根拠明記済み。3箇所目の同型が現れたら共通化を再検討（トリガー付き）。

### 対立3: ComparisonPanel の METRIC_ROWS 追記（カタログ集約原則8 vs 過剰抽象化回避）
- 競合: 比較パネルへ4行（交通ストレス・自転車インフラ率・交差点密度・事故密度）を
  コンポーネント内テーブルへ直接追加しており、UI語彙のカタログ集約（原則8）違反に
  見える。一方これは単一コンポーネントが1回だけ使う表示定義で、evaluationAxes.ts の
  重み軸名（「事故」）と METRIC_ROWS の指標名（「事故密度 件/(km・年)」）は概念が別。
- **判断: ローカルテーブル維持（KEEP）**。原則8が禁じるのは「同じ語彙の対訳表の
  2箇所目」であり、単一利用のローカル宣言テーブルは対象外。単位・書式つき指標行を
  3箇所目が必要になったらカタログ化を検討（トリガー付きDEFER）。

### 対立4: MapView 1,299行の閾値超過（分割すべき？ vs KEEP契約「それ以上の分割はしない」）
- 競合: R-6 の閾値（1,200行 or 静的レイヤー+2種）は**両方成立済み**。overall的には
  分割検討に見えるが、KEEP契約は「決めてある2点のみ実施し、それ以上の分割はしない」。
