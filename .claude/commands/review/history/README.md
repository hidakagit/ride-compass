# レビュー履歴

各レビューコマンドの実行結果をこのディレクトリへ蓄積する。
レビューを毎回ゼロから行わず、「過去 → 現在 → 改善」の変化を追跡するための記録。

## ファイル命名

```
YYYY-MM-DD_<review-type>.md
```

- review-type: `overall` / `complexity` / `consistency` / `ui` / `all` / `improve` /
  `codereview` / `codereview-self`（2026-08-30追加、README.md「定期的なレビュー」節参照）。
  `codereview`はユーザーがターミナルで起動した本物の`/code-review`（`ultra`含む、複数
  エージェント・クラウド実行）の結果。`codereview-self`はセッション自身が`ReportFindings`
  ツールで行った簡易な自己レビューの結果——**品質・カバレッジが本物より劣ることを
  history内でも明記すること**、2つを混同しない
- 例: `2026-08-16_overall.md`、`2026-08-16_all.md`
- 同日に同種を複数回実行した場合は `_2` 等の連番を付ける

## 本基盤構築以前のレビュー

2026-08-15〜16 に実施したレビューは docs/ 直下にある（context.md に一覧あり）。
これらもレビュー履歴の一部として、再発チェック・比較の参照元に含めること。
docs/ から history/ への移動はしない（improvement-plan.md 等からのリンクを維持するため）。

## スコア推移（トレンド追跡）

`scores.md`が種別ごとの経時トレンドを1ファイルにまとめた追記専用テーブル
（[principles.md](../principles.md)「スコアサマリ」節参照）。個別レビュー実施時は、
そのレビューの`history/YYYY-MM-DD_<type>.md`本体に加えて、`scores.md`の対応する
種別テーブルへも1行追記すること。

## 各履歴ファイルに最低限含める項目

principles.md の標準フォーマットに従っていれば自然に満たされるが、以下は必須:

- **実施日**・**対象**（範囲・対象コミット/ブランチ。`git rev-parse HEAD` の値を書く）
- **レビュー種別**
- **重要な指摘**（P0/P1）と**優先度**
- **対応状況**（起票済みT番号 / 起票案のまま / ユーザー棄却。
  後日タスク対応が進んだら追記してよい——履歴ファイルの「対応状況」欄の更新のみ許可）
- **前回からの改善**（前回指摘のうち解消されたもの）
- **新たに発生した問題**（前回時点では存在しなかった指摘）

## 運用ルール

- 履歴ファイルは追記型。過去の判断を書き換えない（誤りだった場合は削除せず
  「訂正」節を追記する。docs/ui-review-2026-08-16.md の訂正1・2が先例）
- レビュー実行時は、直近の同種レビュー1〜2件を必ず読み、
  Regression / Previous Findings セクションで対応関係を明示する
- **2026-08-27、トリガー成立**: `history/`が24ファイル・約6,900行に達し、
  `/review:improve`自体の実施に複数サブエージェントへの分割委任を要するようになった。
  同種レビューの各`all`実施結果に完全に包含される個別レビュー
  （例: `_all.md`と同日・同範囲の`_overall.md`等、重複が明らかなもの）や、
  3世代以上前の`all`は、`docs/improvement-plan-archive/`と同じ発想で
  日付範囲ごとの要約ファイルへ圧縮することを検討する。直近2〜3世代の`all`と
  各観点の最新1件はフルテキストのまま残す（Regression追跡に必要なため）。
  実施は本提案がユーザー承認された後、別タスクとして着手する（改善提案自体は
  コードを書かないため、要約作業は`/review:improve`の範囲外の実装タスクとする）。
