# 設計・実装・テスト整合性レビュー

「設計 → 実装 → テスト」の3つが一致しているかを確認する。
特に「実装を変更したのに、テストや設計書が古いまま」と
「テストは通るが、設計上の意図を検証できていない」を重点的に探す。

[principles.md](principles.md) と [context.md](context.md) を先に読むこと。
設計書（docs/）を無条件に正とみなさない。実装を一次情報として突き合わせ、
乖離があれば「どちらが正か」を判断材料つきで示す。
$ARGUMENTS があればそれを対象範囲とする。無指定なら前回同種レビュー以降の
コミット（git log）で変更されたコード・docs・テストを対象の中心にする。

対象範囲の確定・精読の手順（ベースラインブランチ→分割要否判定→Agent委任）は
[principles.md](principles.md)「共通実行手順」4（全レンズ共通の機械的手順）に従う。
本ファイルは、その手順でAgentへ渡す「このレンズ固有の確認観点」（下記）を定義する。

## 確認観点

### 設計 ↔ 実装
- docs/architecture.md（現状文書。同一コミット更新ルール）と実装の乖離。
  変更されたコードに対応する記述が現状化されているか（**差分だけでなく、対象範囲でチェック済み/
  完了マークが付いたimprovement-plan.mdのタスクを1つずつ列挙し、各タスクの主要な変更
  （新設ファイル・新設テーブル・新設APIエンドポイント・新設ドメイン概念）がarchitecture.mdの
  どこかに反映されているかを確認する。「更新されているが古い」だけでなく「対応するセクション
  自体が存在しない」を積極的に検出すること。過去にこの検出漏れが実際に発生した実績がある——
  docs/complexity-review-2026-08-16.mdは「乖離は検出されなかった」としたが、実際には静的道路属性
  P0/P1が丸ごと未文書化のまま残っていた（history/2026-08-16_all.md F-1参照）**）
- API仕様と実装の乖離: openapi.json / `types/generated/api.d.ts` が最新か
  （生成→`git diff --exit-code` 相当の確認。CIのapi-contractジョブと同じ観点）。
  **同型のドリフトが3回以上再発した実績がある**（T180・T185・T218→CLAUDE.mdへ
  ルール昇格→昇格の翌日に4回目が発生、history/2026-08-24_overall.md F-1）。
  書かれた手順・CLAUDE.mdへの格上げだけでは再発を防げなかった一方、その後の
  機械的検知の強化で収束した（history/2026-08-25_overall.md）。**同種の手動同期
  ペア（生成→diff確認という定型作業を要するもの）で2回以上の再発が観測された
  場合は、Recommendationとして「手順の再徹底」ではなく「機械的検知の追加
  （pre-commit/CI/テストでの強制）」を既定の第一候補にする。**
- データモデルとDBの乖離: `road_graph_models.py` 等のモデル定義と
  `backend/migrations/` の番号付きSQLの整合。migration未起票のスキーマ差分はないか
- ドメインルールと実装の乖離: 正準定義（domain/road.py の路面語彙、highway 3スコープ表、
  RouteSegmentDetail の符号定義等）と、SQL・フロント・docsの記述が一致しているか。
  SQLのCASE式と domain 純関数の突き合わせテストが新属性にも追従しているか
- docs/improvement-plan.md のチェック状態と実態の乖離
  （完了マーク済みタスクの完了条件が実際に成立しているか、抜き取りで確認）
- docs/logging.md のログ方針と実装の乖離（新規コードがエラー常時WARNING・
  log_external_call・1行INFOサマリの方針に従っているか）
- タイル世代の対上げ: MVT焼き込み値（CASE式・材料タグ・domain純関数）を変更した
  コミットが、対応するタイル世代定数（`ROAD_SURFACE_TILE_VERSION`等）と生成物
  （region-tile-config.json）を同一コミットで上げているか（T70・T93で対上げ漏れが
  2回発生。プロパティ削除を伴う変更はv9と同じ非互換のため、frontend先行デプロイの
  注意書きの有無も確認する）
- **分割元タスクの未起票フォローアップ**: 対象範囲に「T400のように複数のTxxxへ分割する
  親タスク」が含まれ、それが完了マーク済みの場合、分割した子タスクのdocs/tasks/Txxx.md
  すべてを「未起票」「別タスク」「スコープ外」等の語で機械的に検索し、該当箇所を洗い出す。
  各該当箇所は、①起票済みタスク番号にリンクされているか、②起票しないと決めた理由が
  明記されているか、のいずれかである状態になっているか確認する（2026-08-30、T405が
  「環境グループの風[時刻＋方向指定→gridFill面表示]はT400.md記載の別タスク・未起票・
  スコープ外」と正しくフラグを立てていたにもかかわらず、T400自体を完了扱いにする際に
  このフラグが実際に起票されたか確認されず見過ごされた実績を受けてルール化。
  バックグラウンド実行のタスクはユーザーが逐次内容を確認できないため、この種の見落としに
  気づく機会がユーザー側に無く実質的に握りつぶした判断になってしまう——このチェックは
  バックグラウンド実行の完了報告を受けたときこそ重要）
- **共有フィールド・パターンの全消費者チェック**: 対象範囲に「既存の共有フィールド・
  パターンの変更/廃止」（例: `RouteCandidate`の個別スコアフィールドを`axis_difficulties`
  ベースへ置き換える等）が含まれる場合、そのタスクが直接触ったファイルだけでなく、
  変更前のフィールド・パターンをリポジトリ全体でgrepし、他に取り残された消費者が
  いないか確認する（2026-08-30、T401がRouteScorerの候補順位付け計算を`overall_difficulty`
  ベースへ統一した際、`RouteList.tsx`・`ComparisonPanel.tsx`が旧フィールド
  [`elevation_gain_m`・`wind_score`・`road_score`等]を直接べた書きしたまま取り残されて
  いるのを、ユーザーが実機で気づくまで4回以上のタスクが検出できなかった実績を受けて
  ルール化）
- **削除・統合された事実を語る周辺表現の残存**: 対象範囲に「N個の◯◯」「両方の△△」の
  ように個数・組み合わせを主張する記述が変わる変更（例: エンジンが2つ→1つ、選択肢が
  N個→N-1個、設定が2系統→1系統）が含まれる場合、削除した具体的シンボル名（関数名・
  設定名等）の逆引きgrepだけでは不十分——それらのシンボルを直接名指ししない、より緩やかな
  周辺表現（「両方」「どちらか」「2つの」に限らず、「従来は」「以前は」「〜と使い分ける」
  「〜によって異なる」等、複数の選択肢・状態の存在を前提にした言い回し全般）が、コードの
  コメント/docstringとdocs/modules/\*.mdの両方に残っていないか確認する。固定のキーワード
  リストに頼らず、変更箇所の前後を実際に読んで「この記述はまだ成立する事実か」を都度
  判断すること（経緯は[_history.md](_history.md)参照）。
- **docs/modules/\*.mdのフォーマット準拠**: `docs/modules/README.md`「記載粒度」節が
  禁止する経緯記述（「以前は…」「改善計画Txxxで…に変更した」「実機/実測で…だったため」
  等）・Txxxへの違反リンクが紛れ込んでいないか、変更されたファイルだけでなく全15ファイルを
  周期的に走査して確認する（経緯は[_history.md](_history.md)参照）。
- **docs/modules/\*.mdの記載漏れ・死んだ参照**: CLAUDE.md「毎タスク完了時の即時チェック」
  4（新規ファイル追加時、そのファイル名がdocs/modules/\*.mdに出現するか）は個別タスク
  完了時の自己申告に依存するため、実施漏れそのものは個別タスクの中では検知できない
  （2026-09-01、T517完了コミットがこのチェックを踏まずにマージされ、新設した
  `BackendLogsPanel.tsx`が`developer-research-tools.md`の対象ファイル表に一切
  出現しないまま残っていた実績を受けて追加。あわせて同日の調査で、`dynamic-way-values.md`
  が`wind_service.py`[T462で削除済み]を対象ファイル表に残したままの死んだ参照も
  発見・是正した——**「新規追加の記載漏れ」と「削除済みファイルへの死んだ参照」は
  どちらも同じ根本原因（コードを触った箇所からの追跡だけで済ませ、docs/modules全体との
  突き合わせをしない）から生じる対になる欠陥であり、両方をこのレビューで機械的に検出する**）。
  対象範囲（前回レビュー以降のコミット、または`$ARGUMENTS`指定範囲）に対し:
  1. 新規追加ファイル: `git diff --diff-filter=A --name-only <範囲> -- 'frontend/src/**' 'backend/app/**'`
     （テスト・`.module.css`は除外）を列挙し、各ファイル名を`docs/modules/`全体でgrepして
     一件も出現しないものを洗い出す。出現しなければ、`docs/modules/README.md`索引の
     「内容」列を根拠に責務が一致するモジュールを特定し対象ファイル表へ追記する。
  2. 死んだ参照: 全15ファイルからバッククォート付きのファイル名（`` `xxx.py` ``・
     `` `xxx.ts(x)` ``等）を機械的に抽出し、リポジトリ全体を`find`/grepして実在しない
     ものを洗い出す（対象範囲を絞らず毎回全件、範囲限定では削除コミットが対象範囲外だと
     見逃すため）。実在しなければ、削除の経緯コミットを確認し記載を削除・訂正する。
- **コード自身が述べる契約と実装の一致**: docstring・コメント・型が述べる前提条件
  （「◯◯は常に△△である」「xは昇順」「空配列は来ない」等）が、実装で本当に強制・検証されて
  いるかを確認する。特に次の3パターンに注意する（経緯・具体例は[_history.md](_history.md)
  「consistency.mdに『コード自身が述べる契約と実装の一致』チェックを追加」参照）:
  ①配列・辞書の`[0]`要素等への無条件アクセス（空/0件のとき何が起きるか）、
  ②同種のバリデーションが兄弟フィールド・兄弟エンドポイントの一部にしか適用されていない、
  ③コメントが主張する挙動（「常に◯◯する」「フォールバックする」）と実装が逆・不完全。
- **双子実装の対称性**: 交通ストレス⇔安全度のように「同じ構造を対で持つ」実装群
  （domain breakdown・*Override APIモデル・service糊・expression・ポップアップ等）の
  片側だけを変更したコミットが対象範囲にある場合、対になる側へ同じ変更が必要か・
  反映済みかを確認する（T120・T121-aで「片側だけ修正」が2回発生した実績）。
  **削除条件: T122・T123（レシピ共通基盤）完了で双子の糊が共通化されたら、
  本項目は削除する**（構造的解消が正であり、チェックリストでの恒久運用はしない）

### 実装 ↔ テスト
- 変更された実装に対応するテストが更新・追加されているか。テストされていない重要ロジック
- テストが実装詳細に依存していないか（privateメソッド直叩き・内部構造のスナップショット等。
  ただしFakeリポジトリのフラット契約依存は正式なインターフェース契約なので問題としない）
- 不要になったテスト（対象機能が撤去済み）・重複テスト（同じ振る舞いを複数箇所で検証）
- 過剰なmock（mockの設定がテスト本体より長い、mockがmockを返す等）と、
  実質的に意味のないテスト（実装をなぞるだけで壊れ方を検証しない、常にpassする）
- 手動同期ペアの検知テスト網羅: 新設された同期ペアにドリフト検知テストが
  セットで置かれているか
- 統合テストのskip条件: PostGIS接続不可時skipのテストが「実はずっとskipされ続けて
  検証されていない」状態になっていないか

## 出力

principles.md の標準フォーマット。Findingsには「設計・実装・テストのどれとどれの乖離か」を
明記する。乖離の解消方向（設計書を直すのか、実装を直すのか、テストを直すのか）を
Recommendationで示す。

結果を `history/YYYY-MM-DD_consistency.md` へ保存し、P0/P1は improvement-plan.md への
起票案として提示する（起票はユーザー承認後）。**コード・docs本体は変更しない**
（docsの誤記修正も起票案として提示する）。
