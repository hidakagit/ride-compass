# 設計・実装・テスト整合性レビュー

「設計 → 実装 → テスト」の3つが一致しているかを確認する。
特に「実装を変更したのに、テストや設計書が古いまま」と
「テストは通るが、設計上の意図を検証できていない」を重点的に探す。

[principles.md](principles.md) と [context.md](context.md) を先に読むこと。
設計書（docs/）を無条件に正とみなさない。実装を一次情報として突き合わせ、
乖離があれば「どちらが正か」を判断材料つきで示す。
$ARGUMENTS があればそれを対象範囲とする。無指定なら前回同種レビュー以降の
コミット（git log）で変更されたコード・docs・テストを対象の中心にする。

## 確認観点

### 設計 ↔ 実装
- docs/architecture.md（現状文書。同一コミット更新ルール）と実装の乖離。
  変更されたコードに対応する記述が現状化されているか（**差分だけでなく、対象範囲でチェック済み/
  完了マークが付いたimprovement-plan.mdのタスクを1つずつ列挙し、各タスクの主要な変更
  （新設ファイル・新設テーブル・新設APIエンドポイント・新設ドメイン概念）がarchitecture.mdの
  どこかに反映されているかを確認する。「更新されているが古い」だけでなく「対応するセクション
  自体が存在しない」を積極的に検出すること。過去にこの検出漏れが実際に発生した実績がある——
  docs/complexity-review-2026-08-16.mdは「乖離は検出されなかった」としたが、実際には静的道路属性
  P0/P1が丸ごと未文書化のまま残っていた（history/2026-08-16_all.md F-1参照）**）
- API仕様と実装の乖離: openapi.json / `types/generated/api.d.ts` が最新か
  （生成→`git diff --exit-code` 相当の確認。CIのapi-contractジョブと同じ観点）。
  **同型のドリフトが3回以上再発した実績がある**（T180・T185・T218→CLAUDE.mdへ
  ルール昇格→昇格の翌日に4回目が発生、history/2026-08-24_overall.md F-1）。
  書かれた手順・CLAUDE.mdへの格上げだけでは再発を防げなかった一方、その後の
  機械的検知の強化で収束した（history/2026-08-25_overall.md）。**同種の手動同期
  ペア（生成→diff確認という定型作業を要するもの）で2回以上の再発が観測された
  場合は、Recommendationとして「手順の再徹底」ではなく「機械的検知の追加
  （pre-commit/CI/テストでの強制）」を既定の第一候補にする。**
- データモデルとDBの乖離: `road_graph_models.py` 等のモデル定義と
  `backend/migrations/` の番号付きSQLの整合。migration未起票のスキーマ差分はないか
- ドメインルールと実装の乖離: 正準定義（domain/road.py の路面語彙、highway 3スコープ表、
  RouteSegmentDetail の符号定義等）と、SQL・フロント・docsの記述が一致しているか。
  SQLのCASE式と domain 純関数の突き合わせテストが新属性にも追従しているか
- docs/improvement-plan.md のチェック状態と実態の乖離
  （完了マーク済みタスクの完了条件が実際に成立しているか、抜き取りで確認）
- docs/logging.md のログ方針と実装の乖離（新規コードがエラー常時WARNING・
  log_external_call・1行INFOサマリの方針に従っているか）
- タイル世代の対上げ: MVT焼き込み値（CASE式・材料タグ・domain純関数）を変更した
  コミットが、対応するタイル世代定数（`ROAD_SURFACE_TILE_VERSION`等）と生成物
  （region-tile-config.json）を同一コミットで上げているか（T70・T93で対上げ漏れが
  2回発生。プロパティ削除を伴う変更はv9と同じ非互換のため、frontend先行デプロイの
  注意書きの有無も確認する）
- **双子実装の対称性**: 交通ストレス⇔安全度のように「同じ構造を対で持つ」実装群
  （domain breakdown・*Override APIモデル・service糊・expression・ポップアップ等）の
  片側だけを変更したコミットが対象範囲にある場合、対になる側へ同じ変更が必要か・
  反映済みかを確認する（T120・T121-aで「片側だけ修正」が2回発生した実績）。
  **削除条件: T122・T123（レシピ共通基盤）完了で双子の糊が共通化されたら、
  本項目は削除する**（構造的解消が正であり、チェックリストでの恒久運用はしない）

### 実装 ↔ テスト
- 変更された実装に対応するテストが更新・追加されているか。テストされていない重要ロジック
- テストが実装詳細に依存していないか（privateメソッド直叩き・内部構造のスナップショット等。
  ただしFakeリポジトリのフラット契約依存は正式なインターフェース契約なので問題としない）
- 不要になったテスト（対象機能が撤去済み）・重複テスト（同じ振る舞いを複数箇所で検証）
- 過剰なmock（mockの設定がテスト本体より長い、mockがmockを返す等）と、
  実質的に意味のないテスト（実装をなぞるだけで壊れ方を検証しない、常にpassする）
- 手動同期ペアの検知テスト網羅: 新設された同期ペアにドリフト検知テストが
  セットで置かれているか（設計原則3・5）
- 統合テストのskip条件: PostGIS接続不可時skipのテストが「実はずっとskipされ続けて
  検証されていない」状態になっていないか

## 出力

principles.md の標準フォーマット。Findingsには「設計・実装・テストのどれとどれの乖離か」を
明記する。乖離の解消方向（設計書を直すのか、実装を直すのか、テストを直すのか）を
Recommendationで示す。

結果を `history/YYYY-MM-DD_consistency.md` へ保存し、P0/P1は improvement-plan.md への
起票案として提示する（起票はユーザー承認後）。**コード・docs本体は変更しない**
（docsの誤記修正も起票案として提示する）。
