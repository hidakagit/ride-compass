# レビュー基準の自己改善

過去のレビュー結果を分析し、レビュー基準（review/*.md）そのものの改善案を作る。
**このコマンドはレビュー基準を自動的に書き換えない。** 変更提案として報告し、
ユーザーが承認した項目のみ、承認後に反映する。

## 分析対象

- `history/` の全レビュー結果（本基盤の蓄積）
- docs/ の過去レビュー（design-review / complexity-review ×2 / research-interface-review /
  ui-review / external-data-sources-review）
- docs/improvement-plan.md（起票されたタスクの傾向・完了/未着手の偏り・
  レビュー起点タスクのその後）
- 現在の review/*.md（principles / context / overall / complexity / consistency / ui / all）

## 分析手順

1. 過去レビュー結果を時系列で確認し、指摘→起票→対応→再発の流れを追う
2. **繰り返し指摘されている問題**を抽出する（2回以上出た指摘は、レビューで見つけても
   直らない構造要因がある。チェックリスト追加ではなく設計原則化・機械化
   （テスト・生成・型）の提案を優先する）
3. **毎回問題になる設計パターン**を特定する（例: 手動同期ペア、カタログ外のリテラル）
4. **現在のレビューで見逃している問題**を特定する（レビュー後に発覚したバグ・
   ユーザー指摘のうち、既存の観点でカバーされていなかったもの。git log・
   improvement-plan.md の fix 系タスクを突き合わせる）
5. **重複しているレビュー観点**を特定する（複数コマンドが同じ指摘を出している場合、
   どちらか一方の担当と決める）
6. **ほとんど価値のないレビュー観点**を特定する（毎回「該当なし」が続く、
   または指摘してもユーザーが常に棄却する観点）
7. 新しく追加すべきレビュー観点を提案する（このプロジェクトの直近の変更傾向・
   今後想定される変更（context.md）に基づく）
8. 不要なレビュー観点を削除候補にする
9. レビュー実行順序（all.md のPhase構成・READMEの推奨ワークフロー）の改善を提案する
10. context.md の陳腐化を確認する（Keep List・フェーズ・タスク状況・ファイル参照が
    現状と合っているか）

## 出力フォーマット

```markdown
# レビュー基準改善提案（YYYY-MM-DD）

## 分析サマリ
（対象期間・対象レビュー件数・主な傾向）

## 変更提案
### 提案1: <タイトル>
- 対象ファイル: review/<file>.md の<セクション>
- 種別: 追加 / 修正 / 削除 / 順序変更
- 根拠:（どのレビュー結果・どの再発事例から導いたか。事実ベースで）
- 変更案:（差分が分かる具体的な文面）
- 影響:（この変更で何が改善され、何が失われうるか）

## 削除候補（価値の低い観点）
## 見送り（検討したが提案しないもの、理由つき）
```

提案は多くても5〜7件に絞る。基準ファイルの肥大化自体がレビュー基盤の複雑化であり、
「観点の追加」と同数以上の「観点の削除・統合」を常に検討すること。

結果は `history/YYYY-MM-DD_improve.md` として保存する。
**ユーザー承認前に review/*.md を編集しない。** 承認された提案のみ、承認後の指示で反映する。
