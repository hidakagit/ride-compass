# 複雑度平衡性レビュー

「システム全体の複雑度が適切な場所に配置されているか」を確認する。
重要なのは「単純化できるか」ではなく「**複雑さが適切な場所に存在しているか**」。
複雑なドメインロジック（経路探索・評価合成・地理計算・タイル座標系）はdomain層に
集約されていれば複雑でよい。単純な変換を不必要に抽象化していれば問題。

[principles.md](principles.md) と [context.md](context.md) を先に読むこと。
過去の複雑度レビュー（docs/complexity-review-2026-08-15.md・同2026-08-16.md、
history/の同種レビュー）と**必ず突き合わせ**、指摘の再発・解消を追跡する。
$ARGUMENTS があればそれを対象範囲とする。

**overallとの分担**: 新旧混在・残骸・重複の存在検出と局所最適の連鎖は overall の担当。
本レビューは複雑さの**配置の適否**と変更コストの定量評価を担当する。
同じ事象に両方から指摘を出さない。

## 確認観点

### 過剰な複雑度
- 巨大クラス・巨大関数・巨大コンポーネント・巨大service・巨大hook
  （行数だけで機械的に判定しない。「複数の変更理由が同居しているか」で判断する。
  肥大化の検出は特定ファイルの名指しではなく下記「規模ウォッチ」で横断的に行う。
  個別に交渉済みの閾値付きKEEPがある場合はそちらを優先し、現在有効な閾値は
  context.mdのKeep Listとimprovement-plan.mdの該当タスクを正として参照する）
- 過剰な条件分岐・過剰な状態（特にフロントのuseState増殖、page.tsxのハブ状態）
- 過剰な設定（Settings項目・YAML・環境変数の増殖。使われていない設定はないか）
- 過剰なDI・過剰な抽象化・利用者が1つしかないinterface/Protocol
- 不要なレイヤー・素通しの委譲（ただしRepositoryファサードのフラット委譲は正式契約でKEEP）

### 規模ウォッチ（肥大化の汎用監視）
特定ファイルを名指しで監視するのではなく、毎回同じ手順で横断計測する:
1. 実装ファイル（テスト・生成物・CSS・migrationを除く）の行数を実測し、
   backend / frontend 各上位5件程度を**規模ウォッチ表**（ファイル・今回行数・前回行数・増分）
   として出力へ含める。前回値は history/ の前回complexityレビューの同表から取る
   （初回は 2026-08-18_complexity.md 記載の実測値を初期値としてよい）。
   **`docs/architecture.md`も同じ表に加える**（T8・T286の2回、decisions/への抽出で
   対応した実績があり、単発ではなく繰り返す成長パターンと判断する。前回値は
   T286完了時点の1,929行を初期値とする）。
2. **発火条件（いずれか）**: 前回同種レビュー比 +15%以上の成長／1,000行の新規超過／
   上位5件への新規登場。発火したファイルは行数だけで問題化せず
   「複数の変更理由が同居しているか」で精査し、必ず次のいずれかへ分類する:
   (a) 理由つきKEEP、(b) 抽出・分割の提案、(c) 閾値付きKEEPの個別設定（Keep Listへの提案）。
   `docs/architecture.md`が発火した場合の(b)は「decisions/への経緯記述の抽出」
   （T8・T286と同じ手法）を既定の選択肢とする。
3. 個別に交渉済みの閾値付きKEEP（例: MapView.tsx、T91→T123）は本ウォッチより優先する
   （発火時・対応後の次閾値運用は「出力」節のルールに従う）。

### 不足している構造化
- 重複ロジック（同じ変更理由で2箇所以上直す必要がある箇所。
  数値定数の「◯◯と揃える」コメント2箇所書きは設計原則2違反）
- 責務混在（1関数がI/Oと計算を兼ねる、serviceがdomainの判断を持つ等）
- 不明確な境界・暗黙的なルール（コメントや規約でしか守られていない整合。
  ドリフト検知テストや型・生成で機械化できるものはないか）
- カタログ集約されるべきUI語彙がコンポーネント内にリテラルで書かれていないか（設計原則8）

### 性能最適化と複雑度のバランス
- 性能最適化が複雑さの対価に見合っているか。**実測（benchmarks/・本番ログ）を伴わない
  最適化**は premature として指摘対象、実測根拠つきの最適化はKeep List入りが既定
  （ST_AsMVT・GiST遅延構築・COPYバルク等の先例）
- 逆に、実測で問題が示されているのに単純さを理由に放置されている箇所はないか
- スケールしないパターンの**存在検出**（索引不使用クエリ等）は overall の担当。
  本レビューはその対処案が複雑度に見合うかを判断する

### 変更コストの計測
代表的な変更シナリオ（評価軸追加・道路属性追加・エンジン追加・レイヤー追加）、
および**外部静的データソース追加**（新規raw層テーブル＋取込バッチ＋Edgeへの事前マッチング
バッチ（線データの場合）＋domain定数＋Repository対称メソッド＋タイル配信/プロパティ拡張＋
フロントカタログ、という6点セット。T50・T51が実例）について
「編集が必要なファイル数・箇所数」を実際に数え、
**直近のcomplexityレビュー結果（history/ の最新complexity。初回のみ
docs/complexity-review-2026-08-16.md）の変更コスト表**と比較して悪化/改善を報告する。
T292（内部軸/公開軸の階層化、2026-08-25完了）により旧レシピ機構は撤去済みのため、
以後の「評価軸追加」コストは基本のCase（評価軸追加）1本で測る。新設された
内部軸/公開軸の階層構造に特有の変更コストパターンが今後見つかった場合は、
その時点で新しいCase名を割り当てる（G'/B'/Hの再利用はしない）。
評価軸追加の1本道（context.md）から外れた箇所数の増加は最優先の指摘対象。

## 出力

principles.md の標準フォーマット。加えて以下を含める:
- **Keep List の更新案**: 前回Keep Listを再確認し、維持/追加/削除候補を明示
  （基準ファイルの書き換えはしない。提案のみ）。**前回Keep Listに閾値条件（「〜行到達時」
  「〜種類到達時」等）付きの項目があり、今回その条件が成立・対応済みと判明した場合は、
  同じ結果の中で次の閾値を必ず明示する（閾値を発火させたまま次の閾値を設定しないと、
  安全弁が一度きりで機能しなくなる。R-6→T47実施後に次の閾値が定義されず、MapView.tsxが
  1,299行まで成長して統合レビュー第1回で再発見された実績を踏まえる。
  history/2026-08-16_all.md F-3参照）**
- **変更コスト表の更新**（実測ベース）
- **規模ウォッチ表**（「規模ウォッチ」節の手順で毎回実測・前回比つき）
- **前回指摘の解消状況**（R番号・I番号との対応つき）

結果を `history/YYYY-MM-DD_complexity.md` へ保存し、P0/P1は improvement-plan.md への
起票案として提示する（起票はユーザー承認後）。**コードは変更しない。**
