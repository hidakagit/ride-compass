# 全体最適レビュー

大規模改修・リファクタリング後のコードベースを俯瞰し、
「システム全体として設計思想が一貫しているか」
「局所最適による全体の複雑化が起きていないか」を確認する。

[principles.md](principles.md) の共通原則・標準フォーマット・共通実行手順と
[context.md](context.md) を先に読むこと。$ARGUMENTS があればそれを対象範囲とする。

## 確認観点

### アーキテクチャ・構造
- レイヤー構造（api → services → domain → infrastructure）の方向が守られているか。
  domainにI/Oが漏れていないか、infrastructureがservicesへ依存していないか
- 責務分割: 各service/component が「同じ理由で変更されるもの」の単位になっているか
- 依存関係: 新たな直接依存・循環の芽・DI工場（dependencies.py）を迂回した構築が増えていないか
- データフロー: ルート生成（戦略→ポート3段階→評価→スコアリング）と
  地図レイヤー（MVT 1系統）の一本道が保たれているか。評価軸追加の1本道
  （context.md参照）から外れた実装が入っていないか

### 新旧設計の混在・残骸
- 「並行追加→設定で切替→旧削除」の3段階（設計原則9）の途中にあるものに、
  削除条件が書かれているか。条件が成立済みなのに残っているものはないか
- 旧実装・デッドコード・未使用エクスポート・テストのみが参照するコード

### 重複・不要物
- コード/ロジック/データ/設定/API/UI/概念の重複
- 不要な抽象化・wrapper・変換・fallback・状態
- 正準定義の複製（片側importでなく値のコピーになっている箇所）

**complexityとの分担**: 本レビューは「重複・残骸・新旧混在が**存在するか**」の検出と
局所最適の連鎖を担当する。個々の複雑さの**配置の適否**（抽象化しすぎ/構造化不足の判定）と
変更コストの定量評価は complexity の担当。同じ事象に両方から指摘を出さない
（存在検出＝overall、対処方針の複雑度判断＝complexity へ言及を送る）。

### 局所最適の連鎖（最重点）
「Aを改善した結果Bが複雑になった」「Bを再利用するためCの責務が曖昧になった」
「Cを抽象化した結果Dの理解が難しくなった」という連鎖を探す。
直近の変更（git log）を起点に、変更されたファイルの**呼び出し元・呼び出し先**まで読んで、
変更の都合が周辺へ漏れていないかを確認する。

### 拡張性・保守性・スケール成立性
- 変更コストシミュレーション（直近のcomplexityレビュー結果の変更コスト表。初回のみ
  complexity-review-2026-08-16.md の表A〜G）の容易度が
  悪化していないか（軸追加・エンジン変更・属性追加等の代表シナリオで机上確認）
- 「関東全域で成立するか」（設計原則8）: 全量ロード・全件転送を伴う新設計がないか
- **スケールしないクエリ・処理パターン**（過去にT64〜T69として起票された類型）:
  索引を使えない空間述語（geographyキャストのST_DWithin等）、行ごとLATERAL/サブクエリ、
  ループ内の逐次INSERT/外部API呼び出し、delete-then-reinsertによる関連データの黙殺消失。
  新規SQLとバッチ処理はこの類型に照らして確認する
- 性能最適化の**複雑度対価**の評価（この最適化は複雑さに見合うか）は complexity の担当

## このプロジェクト固有のチェック

- エンジン間で同名フィールドの意味が食い違っていないか（管理された例外はwind_scoreのみ）
- scoring（相対）/ route_preference（絶対）の役割境界が崩れていないか
- Keep List（context.md参照）記載の設計を、新しい根拠なしに問題化していないか

## 出力

principles.md の標準フォーマットに従い、Findingsを
KEEP / REMOVE / SIMPLIFY / REFACTOR / EXTEND / DEFER に分類する。
DEFERには必ずトリガー条件を付ける。

結果を `history/YYYY-MM-DD_overall.md` へ保存し、P0/P1は improvement-plan.md への
起票案として提示する（起票はユーザー承認後）。**コードは変更しない。**
