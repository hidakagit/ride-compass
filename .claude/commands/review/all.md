# 統合レビュー

4種のレビューを単純に連続実行するのではなく、相互の矛盾・トレードオフを解消した
「全体として最もバランスが良い状態」の提案までを行う。

[principles.md](principles.md) と [context.md](context.md) を先に読むこと。
$ARGUMENTS があればそれを対象範囲とする。

## 実行フェーズ

### Phase 1: 全体把握
git log で前回レビュー以降の変更を特定し、変更の中心・影響範囲・
history/ と docs/ の過去レビュー指摘の一覧を整理する。ここでは指摘を出さない。

### Phase 2: 定量メトリクス計測
[metrics.md](metrics.md) の手順で実施。Findings（P0-P3）ではなく数値のみを記録する
ロールのため、Phase 3〜7の相互確認・矛盾解消の対象には含めない。ここで得た実測値
（規模・churn・静的検査件数等）は、後続のoverall・complexityが規模・複雑度に関する
指摘のEvidenceとして参照してよい。

**Phase 3〜6 共通の省力化ルール（コンテキスト消費対策）**:
- 対象範囲が重なる同種の個別レビュー結果が history/ に**直近（それ以降に大きな変更なし）**で
  ある場合、そのPhaseは再実行せず結果ファイルを読み込み、以降の変更差分のみ確認する。
  省略・差分化したPhaseは結果に明記する
- コンテキストが逼迫する場合はPhase単位で区切り、完了したPhaseの中間結果を
  `history/YYYY-MM-DD_all.md` へ先に保存してから続きを実施してよい
  （中間保存したことをファイル冒頭に記す。全Phase完了時に統合する）
- **省力化のためPhase 3〜6のレンズ構造（overall/complexity/consistency/ui）を、
  ドメイン構造（backend/frontend等）へ置き換えてはならない**。対象が
  `principles.md`の分割閾値を超える場合、分割は各Phase（レンズ）が自分自身の担当範囲内で
  行う（分割可否・分割単位はレンズごとに異なる。詳細はprinciples.md「共通実行手順」4d・
  complexity.md冒頭・[_history.md](_history.md)参照）

### Phase 3: 全体最適レビュー
[overall.md](overall.md) の観点で実施。

### Phase 4: 複雑度平衡性レビュー
[complexity.md](complexity.md) の観点で実施。

### Phase 5: 設計・実装・テスト整合性レビュー
[consistency.md](consistency.md) の観点で実施。

### Phase 6: UI/UXレビュー
[ui.md](ui.md) の観点で実施（実機確認を含む。時間的に絞る場合は
変更のあった画面＋主要導線1周に限定し、絞ったことを明記する）。

### Phase 7: 各レビュー結果の相互確認（最重要）
Phase 3〜6 の指摘を突き合わせ、以下を処理する。

- **矛盾の解消**: 例「overallでは共通化すべき／complexityでは抽象化しすぎ」のような
  矛盾は両論併記で終わらせず、判断基準（変更理由が同じか・設計原則・変更コスト実測）に
  照らして**どちらを優先すべきかを決める**。判断根拠を明記する
- **トレードオフの評価**: 「UI上は便利だがアーキテクチャが複雑になる」
  「テスト容易性は上がるが実装が過剰になる」「性能は上がるが複雑度が大きく増える」等は、
  現在の開発フェーズ（研究優先・個人開発・低利用規模）を前提に天秤の結論を出す
- **重複指摘の統合**: 複数レビューが同じ根本原因を別の症状として指摘している場合は
  1つのFindingに統合し、根本原因側へ寄せる
- **相殺の確認**: あるレビューのRecommendationが別レビューのKEEPを壊さないか確認する

### Phase 8: 最終統合判断
- 統合後のFindingsを優先度順に並べ、KEEP〜DEFERへ分類する
- 実施順序の提案（依存関係・安全網の順。improvement-plan.md の「進め方の原則」に倣い、
  検証の自動化→境界の固定→内部の再配置の順を基本とする）
- 「全体として最もバランスが良い状態」を1段落で記述する

## 出力

principles.md の標準フォーマットに加え、Phase 7 の「矛盾と判断」を独立セクションで残す
（どの指摘とどの指摘が競合し、何を根拠にどちらを採ったか）。Phase 2（定量メトリクス計測）は
Findingsを持たないため標準フォーマットの対象外——[metrics.md](metrics.md)の出力形式に従い、
allの結果ファイル内には実測値のサマリのみを含める。

結果を `history/YYYY-MM-DD_all.md` へ保存する。Phase 2〜6の詳細は
このファイル内のセクションとしてまとめてよい（個別ファイル5本を別途保存する必要はない。
分量が大きい場合のみ分割し、allから各ファイルへリンクする）。
P0/P1は improvement-plan.md への起票案として提示する（起票はユーザー承認後）。
**コードは変更しない。**
