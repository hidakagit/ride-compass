# 共通レビュー原則（全レビュー種別で適用）

各レビューコマンド（overall / complexity / consistency / ui / all）は、実行前に本ファイルと
[context.md](context.md) を読み込み、以下の原則に従うこと。

## 最重要目標

レビューの目的は「コードを綺麗にすること」「コード量を減らすこと」「抽象化を増やすこと」ではない。

> システム全体として一貫した設計思想を維持し、必要な複雑さだけを残し、
> 不要な複雑さ・冗長性・重複・責務混在を減らし、今後の変更に強い
> バランスの取れたコードベースを維持すること

常に **局所最適** と **全体最適** を区別する。個々のコードが綺麗でもシステム全体として
複雑になっていれば問題として扱う。逆にコード量が増えていても、責務が明確になり
全体として理解・変更しやすくなっていれば必ずしも問題としない。

## 判断原則

1. **全体最適**: 個々のファイル・クラス・関数ではなく、システム全体として合理的かで判断する。
2. **局所最適への警戒**: あるコンポーネントの改善が別のコンポーネントを複雑にしていないか確認する。
   「Aを改善した結果Bが複雑になった」という連鎖を明示的に探す。
3. **複雑度の平衡**: 複雑さゼロを目指さない。複雑であるべきドメインロジック
   （経路探索・評価合成・地理計算等）には適切な複雑さを許容し、単純な処理に過剰な抽象化を導入しない。
4. **過剰な抽象化を避ける**: interface / abstract class / factory / strategy / adapter / wrapper /
   manager / helper / utility / repository / service を無条件に良い設計とみなさない。
   「なぜ必要なのか」を説明できることを重視する。
5. **抽象化不足も確認**: 同じ責務・同じ変更理由を持つ処理が複数箇所にあれば共通化を検討する。
   ただし単にコードが似ているだけなら共通化しない。
6. **変更理由を重視**: 責務分割・共通化の判断基準はコードの類似性ではなく
   「同じ理由で変更されるか」（このプロジェクトの設計原則6と同一）。
7. **冗長性の確認対象**: コード重複・ロジック重複・データ重複・設定重複・API重複・UI重複・
   概念重複・不要な変換・不要なwrapper・不要なfallback・旧実装。
8. **新旧設計の混在**: 大規模改修後の新旧混在は「意図的（切替・併存）」「移行途中」「残骸」の
   いずれかを判断する。意図的な併存には削除条件（いつ消せるか）が書かれているか確認する
   （設計原則9）。
9. **将来のための過剰設計を避ける**: 「いつか必要になるかもしれない」だけで現在の複雑度を上げない。
   DEFERにはトリガーを付け、トリガー未到達の項目を「ついで」に実装しない（設計原則10）。
10. **コード量だけで判断しない**: 理解・変更・テスト・拡張のしやすさを総合的に判断する。
11. **単純化しすぎない**: 複雑度を下げるために責務を巨大クラス・巨大サービスへ集約しない。
12. **説明可能性**: 第三者に「なぜこの構造なのか」を説明できることを重視する。

## 事実と推測を分ける（必須）

実際にコードから確認できた **事実（Evidence）** と、レビューアの **推測（Inference）**・
**提案（Recommendation）** を明確に分けて書く。

Bad: 「この設計は将来的に問題になる。」

Good:
- Evidence: 「AからBへの依存が現在5箇所存在する（`file.py:12` 等、参照箇所を列挙）。」
- Inference: 「今後同じ依存が増える場合、変更影響範囲が広がる可能性がある。」
- Recommendation: 「Bを境界として整理することを検討する。」

Evidenceには必ず `ファイルパス:行番号` または具体的なシンボル名を付ける。
実機確認（Playwright・API実行）で得た所見は、再現手順を確認してから確定する
（過去にセレクタ誤りによる誤所見が2件発生した実績がある。docs/ui-review-2026-08-16.md 訂正1・2参照）。

同様に、backend pytestとfrontend vitestを同時並行実行すると、CPU/IOリソース競合で
テストがtimeout失敗することがある（2026-08-16実測: 並走時にMapLayersPanel.test.tsxが
3件失敗→単独再実行で全green）。テストの失敗は即座に指摘として確定せず、
単独実行で再現するか確認してから記録する。

## レビュー結果の標準フォーマット

全レビューで以下を基本形とする（各コマンドで観点固有のセクションを追加してよい）。

```markdown
# <レビュー種別> レビュー（YYYY-MM-DD）

## Executive Summary

## Findings

### [P0/P1/P2/P3] <Issue タイトル>
- Problem:
- Evidence:（事実。ファイル:行番号つき）
- Impact:
- Root Cause:
- Recommendation:（推測・提案はここに）
- Scope:（影響範囲・修正規模の目安 S/M/L）
- Confidence: High / Medium / Low

## KEEP（変更しない方がよい設計。理由つき）
## REMOVE
## SIMPLIFY
## REFACTOR
## EXTEND
## DEFER（必ずトリガー条件を付ける）

## Regression / Previous Findings
（過去レビューで指摘済みの問題の再発有無、解消済みの明示）

## スコアサマリ

Findingsの件数から**機械的に**算出する（主観採点はしない。恣意性を避けるため計算式は
固定）。History内で経時比較できるよう`history/scores.md`（[history/README.md](history/README.md)
参照）へも同じ値を1行追記する。

| 指標 | 値 |
|---|---|
| P0件数 / P1件数 / P2件数 / P3件数 | |
| 総合スコア（100点満点） | `100 - (P0×20 + P1×10 + P2×3 + P3×1)`、下限0 |
| 前回同種レビューからの差分 | 総合スコア ±n（新規+n件・解消-n件、Regression節と整合させる） |
| REMOVE/SIMPLIFY/REFACTOR件数 | （技術的負債の量的目安） |
| DEFER件数（トリガー未到達） | （将来対応の積み上がり具合） |

## Overall Judgment
```

- 優先度: P0=Critical / P1=High / P2=Medium / P3=Low
- Confidence: High（コードで確認済み）/ Medium（一部推測）/ Low（推測中心）
- 該当なしのセクションは「該当なし」と1行書く（省略しない）。スコアサマリの各値も
  0件なら0と明記する（空欄にしない）

## 共通実行手順

1. 本ファイルと [context.md](context.md) を読む。
2. 過去レビューを確認する: [history/](history/) の同種レビュー（直近1〜2件）と、
   基盤構築以前のレビュー（docs/*-review-*.md、context.md に一覧あり）。
   再発チェックと「解消済み」の明示に使う。
   **docs/やimprovement-plan.md（docs/tasks/含む）がhistory/の特定ファイルを
   根拠として引用している場合、そのファイルが実際にhistory/へ保存されているかを
   確認する（`history/2026-08-26_complexity.md`が2箇所から引用されながら一度も
   保存されていなかった実績がある。docs/tasks/T356.md参照）。存在しない場合は
   P3として指摘し、遡及復元できなければ引用元へ「未保存」の注記を提案する。**
3. **レビューは本体の作業ツリーではなく専用の`git worktree`で実施する**（CLAUDE.md
   「作業ツリーの安全」節を参照。レビューは読み取り専用の調査だが、本体の作業ツリーに
   一切触れない構成にすることで、並行セッションとの衝突・誤操作のリスクをなくす）。
   対象範囲を決める（引数があればそれに従う。無指定なら「前回同種レビュー以降の変更」を
   git log / git diff で特定し、全体構造への影響と合わせて見る）。
   **対象コミットを固定する前に必ず`git fetch`を実行し、ローカルHEADとorigin/master
   （リモートの既定ブランチ）の位置関係を確認する。ローカルが遅れている場合は
   origin/masterの先端を対象コミットにする**（原則。ローカル側を対象にする特別な理由が
   あればユーザーに確認する。2026-08-22、ローカルmasterがorigin/masterより26コミット
   遅れたままレビューを実施してしまい、スライダー統合等の最新UIと食い違う古い状態への
   指摘・スクリーンショットをレポートに載せてしまった事故が実際に発生したことを受けて
   明文化。並行セッションが別ブランチ経由でmasterへマージし続ける運用のため、
   ローカルの追従遅れは常に起こりうる）。
   **開始時に対象コミット（HEAD）を記録し、Evidenceはコミット済みHEADへ固定する。**
   並行セッションがレビュー中に本体の作業ツリーを変更しうる（2026-08-18に実測。
   worktreeを分けていてもこの事実自体は変わらない）。**本体の作業ツリーで想定外の変更を
   見つけても、レビューエージェントの誤操作に見えても、絶対に自動で戻さない**
   （2026-08-18、実際に他セッションの未コミット変更を`git checkout --`で破棄してしまう
   事故が発生し、gitオブジェクト化されていなかったため復元できなかった実績がある）。
   発見した変更は「参考」として区別して記すに留め、対応が必要な場合はユーザーに確認する。
   **起票案にはT番号を仮置きしない**
   （並行セッションとの番号衝突がT119で2回発生した実績。「起票案」とだけ書き、
   番号はユーザーが起票する時点で確定する）。
4. **対象範囲の変更ファイルは全件・全文を読む**（テーマでサンプリングしない、全レンズ共通の
   機械的手順。経緯・根拠は[_history.md](_history.md)「全レンズ共通『変更ファイルは全件・
   全文を読む』手順の新設」参照）。
   a. **ベースラインコミットを確定する**: `history/`の直近同種レビューファイル冒頭に
      記録された「対象コミット」を読み、その値をベースラインとする。記録が無い場合は
      前回レビュー日時に近いコミットを`git log`で特定する。
   b. **一時ブランチを作る**: `git branch review-<レンズ名>-baseline <ベースラインSHA>`
      （`<レンズ名>`はoverall/complexity/consistency/ui。worktreeは不要、diffの基準点として
      使うだけでチェックアウトしない）。
   c. **差分規模を機械的に測る**: `git diff review-<レンズ名>-baseline...HEAD --stat`で
      変更ファイル数を確認する。
   d. **分割要否の判定（閾値固定、overall・consistencyのみ対象）**: 変更ファイル数が
      **15件超**、または変更対象ファイルの現在の合計行数（`git diff
      review-<レンズ名>-baseline...HEAD --name-only`の各ファイルを`wc -l`で合算）が
      **5,000行超**のいずれかに該当したら「分割」、いずれも未満なら「単独」。
      - **単独**（目安10ファイル以下）: 自分で対象ファイルを`Read`（diffではなくファイル
        全体）し、変更箇所の呼び出し元・呼び出し先（`Grep`でシンボル検索）まで辿って調査する。
      - **分割**: `backend/app/{domain,services,infrastructure,api,batch}`・
        `frontend/src/{components,hooks,services,app,lib}`の各ディレクトリを1シャードの単位
        とし、変更ファイルの現在行数合計が**6,000行を超えるシャードはさらに分割**する。
        各シャードを`general-purpose` Agentへ`run_in_background: true`で委任する。
        各Agentへのプロンプトには次を含める: 対象ファイル一覧（シャード内の変更ファイルの
        フルパス）／「diffではなく各ファイルを全文Readし、変更箇所の呼び出し元・呼び出し先も
        `Grep`で辿ること」という明示指示／このレンズ固有の確認観点（`overall.md`または
        `consistency.md`の該当節）／出力形式（`file`・`line`・`category`・`severity`・
        `summary`・`failure_scenario`のMarkdown箇条書き、日本語）／「編集・削除は一切行わない
        （読み取り専用）」の明記。
      - **この分割要否判定・ドメインシャーディングはoverall・consistencyにのみ適用する。
        complexity・uiは対象規模（変更ファイル数・行数）に関わらず常に単独実施する**
        （complexityの規模ウォッチ表・変更コスト表はリポジトリ全体の横断計測が主体で
        コストが差分サイズに比例せず、uiは実機確認のため並列化できない。詳細は
        [_history.md](_history.md)「2026-08-31: シャーディング規則の適用範囲を
        overall/consistencyへ限定」参照）。
      - **レンズ構造（overall/complexity/consistency/ui）そのものを、ドメイン構造
        （backend/frontend等）へ置き換えてはならない**。シャーディングは各レンズの
        担当範囲内で行うものであり、レンズを跨いだ分割単位で代替してよいという規則では
        ない（2026-08-30、統合レビュー第2回でこの誤りが発生し複雑度レンズが実質空洞化
        した実績を受けて明記。詳細は_history.md同項参照）。
   e. **集約**: 全シャード完了後、指摘を重複統合し、severity順に並べて標準Findings
      フォーマットへ統合する。
   f. **後片付け**: `git branch -D review-<レンズ名>-baseline`で一時ブランチを削除する。
5. 標準フォーマットで結果をまとめ、`history/YYYY-MM-DD_<review-type>.md` として保存する
   （命名・記載項目は [history/README.md](history/README.md) 参照）。**スコアサマリの値を
   `history/scores.md`へも1行追記する**（トレンド追跡用、history/README.md参照）。
6. P0/P1の指摘は docs/improvement-plan.md への **起票案**（タスク名・規模・トリガー）として
   提示する。improvement-plan.md 自体はユーザー承認後にのみ編集する。

## 禁止事項

- **コードを変更しない**。レビューコマンドの成果物はレビュー結果（history/への保存）と
  改善提案のみ。修正はユーザーが別途タスクとして指示する。
- **本体の作業ツリーで見つけた、自分が行ったのではない変更を戻さない**（`git checkout --`/
  `git reset`/`git stash`/`git clean`等の実行禁止）。並行セッションの作業中変更である
  可能性を常に疑い、ユーザーに確認する（CLAUDE.md「作業ツリーの安全」節、共通実行手順3参照）。
- context.md・principles.md 等のレビュー基準も、レビュー実行中に書き換えない
  （基準の改善は /review:improve の提案→ユーザー承認を経る）。
- 既に KEEP と判断され記録されている設計（context.md の「意図的な設計判断」参照）を、
  新しい根拠なしに再度問題として指摘しない。再指摘する場合は前回KEEP判断の何が
  変わったのかをEvidenceで示す。
