# UI/UXユーザーレビュー

「見た目が綺麗か」ではなく
「**初めて使うユーザーが、このシステムの目的と操作方法を理解できるか**」を評価する。

[principles.md](principles.md) と [context.md](context.md) を先に読むこと。
過去のUIレビュー（docs/ui-review-2026-08-16.md、docs/research-interface-review-2026-08-15.md、
history/の同種レビュー）と突き合わせる。$ARGUMENTS があればその画面・機能を重点対象とする。

## 実施方法（必須）

コードを読むだけのUIレビューは行わない。**実際にdev環境を起動し、Playwright（Chromium）で
一連の操作を実行して確認する**（初回表示 → 現在地/地点設定 → ルート生成 → 候補比較・選択 →
レイヤー切替 → ポップアップ確認。デスクトップ幅とモバイル幅390pxの両方）。

- 所見は**確定前に再検証**する。過去にセレクタ誤り・Next.js devインジケータの誤認で
  誤所見が2件発生した（docs/ui-review-2026-08-16.md 訂正1・2）。
  「壊れている」と書く前に、セレクタの対象要素・dev環境固有のUIでないかを確認する
- dev環境でのみ起きる事象（`next dev` のインジケータ・コンパイル遅延）は区別して記録する

## 確認観点

### 初見ユーザーの理解
- 初回表示で「何をするアプリか」「最初に何をすべきか」が分かるか（初回利用時の認知負荷）
- 主要CTA（ルート生成）までの操作導線が迷わず辿れるか
- 情報階層: 判断材料（天候・候補の評価・凡例）が重要度に応じた場所・強さで提示されているか
- 空状態（候補0件・データ未整備地域・カバレッジ外の空タイル）で
  「壊れているのか、データが無いのか、操作が足りないのか」が伝わるか
- ローディング・エラー・429拒否の表示が状況を説明できているか
- 入力方法（距離・地点指定・重み設定）の分かりやすさとバリデーションメッセージ

### 一貫性・用語
- 用語の一貫性（過去に「路面」の用語衝突・自転車インフラのラベル衝突の実績あり。
  同名で意味が違う表示・同じ意味で名前が違う表示を探す）
- 設定の3軸（反映タイミング・保存有無・配置）が系統ごとに統一されているか
  （「生成条件」と「地図の見え方」の2系統再編の方針が新規UIにも守られているか）
- 下書き→適用方式（路面絞り込み）と即時反映（単純チェック）の使い分けの一貫性

### 地図とUIの関係
- 地図上（ON/OFFチップ＋条件サマリ）とサイドバー（詳細設定）の役割分担が保たれているか
- レイヤーの色・凡例が地図上で判読できるか（ダークモード含む。
  過去にダークモード白背景×白文字・color未指定の配色バグ実績あり）
- 情報過多/不足: レイヤー同時表示時の視認性、ポップアップの項目数

### モバイル/デスクトップ
- 390px幅での主要導線（ボトムシート・タブバー・地図操作の共存）
- **対象範囲に新設・変更されたパネル・フォームがある場合（研究UI含む）、390px幅での
  収まり（横スクロール・画面外への溢れ）とタップ操作（ホバー/title依存UIが
  タップで機能するか）を必ず実機確認する**（T112・T118の2件がレビュー外で
  ユーザー/本番から発覚した実績）
- デスクトップ/モバイルでの機能差が意図通りか

### 研究用UIと一般ユーザー向けUIの区別
- 研究モード（WeightPanel・ComparisonPanel・DebugConsole等）が一般UIに漏れていないか
- 研究UIも操作可能性（タップで開く・入力できる・画面内に収まる）は一般UIと同基準で
  評価する。低い基準でよいのは見た目の洗練度のみ
- 将来の一般公開UIへの発展可能性: 現在の構造（カタログ・2系統設定）が
  一般ユーザー向けの簡略UIを作る際の障害にならないか

## 出力

principles.md の標準フォーマット。Findingsごとに「研究UI/一般UI」の別と
確認手段（スクリーンショット・実測値）を明記する。
実機確認できなかった項目は Confidence を下げて明示する。

結果を `history/YYYY-MM-DD_ui.md` へ保存し、P0/P1は improvement-plan.md への
起票案として提示する（起票はユーザー承認後）。**コードは変更しない。**
