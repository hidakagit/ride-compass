# 次のタスク選定

`docs/improvement-plan.md`の未完了タスクから、今すぐ着手できるものを優先度順に提案する。
**自動で着手はしない**（このプロジェクトの「起票・着手判断はユーザー承認後」という一貫した
方針に合わせる）。$ARGUMENTS があれば絞り込み条件として使う。

## 実行手順（機械的）

1. **候補を抽出する**: `docs/improvement-plan.md`の`- [ ]`行を全件抽出する
   （Txxxリンク・タイトル・規模・トリガー有無を含む行全体を保持する）。
2. **同期を確認する**: `git fetch origin master`を実行し、ローカルとoriginの位置関係を
   確認する（並行セッションが既に対象タスクへ着手・完了している可能性があるため。
   ずれがあればoriginの先端を正とする）。
3. **トリガー未発火のものを除外する**: 「トリガー: ◯◯」を含む行は、条件が明確に成立済み
   （日付到来・直近の会話での言及等、機械的に確認できるもの）と判断できない限り除外する。
   判定に迷う場合は除外せず「トリガー要確認」として本編の候補から分けて別枠に残す
   （理由を1行添える）。
4. **優先度シグナルを収集する**: 残った候補それぞれについて`docs/tasks/Txxx.md`を開き、
   次を収集する:
   - severity（P0〜P3。improvement-plan.mdの行またはタスク本文に明記されている場合。
     例:「P0・唯一の重大指摘」「〔P2〕」等の表記から機械抽出する）
   - 規模（S/M/L、improvement-plan.mdの行から）
   - 起票日（Txxx.mdの「状態:」行、またはimprovement-plan.mdの行の日付表記）
5. **ランク付け**:
   a. severityがあるものはP0→P1→P2→P3の順を優先する。severity表記が無いものは
      severityありの候補すべてより後ろに置く。
   b. 同severity（severity無し同士も含む）内は規模の小さい順（S→M→L→不明）。
   c. 同severity・同規模内は起票日が新しい順。
   d. 直近の会話で言及・調査した領域に近い候補があれば、同点内でわずかに優先してよい
      （選定理由に明記すること。恣意的な繰り上げをしない）。
6. **提示する**: 上位3〜5件を、タスク番号・タイトル・severity/規模・1行の根拠つきで
   提示する。「トリガー要確認」に回した候補があれば別枠で件数のみ触れる。
7. **ユーザーに選ばせる**: AskUserQuestion（`multiSelect: true`）または自由回答で選んで
   もらう。複数選択を許可する——提示した候補のうち着手したいものを1件以上まとめて
   選べるようにする。自動着手しない。
8. **着手時の接続**: ユーザーが選んだら、CLAUDE.mdの既存フロー（規模M以上は着手前に
   `docs/tasks/Txxx.md`の背景確認、「作業ツリーの安全」節のT番号衝突回避手順等）へ
   そのまま接続し、通常の実装フローへ移る（本skillの役割はここまで）。
   複数選択された場合は、提示した順（優先度順）で1件ずつ着手する——複数タスクを並行に
   進めない（このプロジェクトの「1タスク=1コミット」原則、および作業ツリーの安全上、
   同一セッションで複数タスクの変更を同時に作業ツリーへ混在させないため）。
   **他セッションが同じ作業ツリーを並行して触っている可能性を前提に、1件ごとに
   同期する**（CLAUDE.md「作業ツリーの安全」節と地続き）:
   - 次の1件へ着手する直前に必ず`git fetch origin master`し、ローカルがoriginへ
     `--ff-only`で追従できるか確認する。追従できなければ、対象タスクが並行セッションに
     既に着手・完了されていないか（`docs/tasks/Txxx.md`の状態・`improvement-plan.md`の
     チェック状態）をまず確認してから、`git merge origin/master`で取り込む
     （対象タスクが既に他セッションで完了済みなら、その1件はスキップしてユーザーへ報告し、
     選択済みの次の候補へ進む）。
   - 1件のコミット・push完了直後（次の1件へ移る前）にも同じ同期を行う——このタイミングで
     origin側に新規コミットがあれば追従してから次のfetchの起点をずらす。
   - 規模M以上でT番号を新規に採番する場合は、CLAUDE.md「作業ツリーの安全」節の手順
     （スタブだけ先にコミット・push→番号衝突が発覚したら振り直し）にそのまま従う。

## 出力フォーマット（例）

```
次の候補（トリガー未発火◯件を除外、残り◯件から上位◯件）:

1. T429 [P2/review:all] pytest -m "not postgis"が実は何もフィルタしていない問題を修正 規模S
   — CIの品質ゲートが機能していない可能性があり、修正コストも小さい
2. T425 [P1×13件/ゼロベースレビュー] 規模M
   — 複数の実バグを含む可能性が高く対応検討が必要
3. T422 規模S
   — T400再監査での発見、小さく片付けられる

（トリガー要確認: 2件 — T◯◯◯・T◯◯◯。詳細は個別に確認してください）

どれから着手しますか？
```

## 既知の調整余地（v1、今後の運用実績で見直す）

- トリガー成立判定の自動化度合い（現状は明確なものだけ自動判定、曖昧なものは
  「要確認」に逃がす設計）
- 同severity内のタイブレーク順（規模の小さい順を既定にしているが、
  「大きい方から着手したい」等の方針があれば逆転可）
- 直近の会話文脈による優先度の微調整（恣意性が強くなりすぎないか、運用しながら検証する）
