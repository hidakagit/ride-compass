# タスク振り返り

タスク（または一連の作業）が完了した直後に、そのコンテキストから「今後の別タスク・別セッションに
活かすべき教訓」を抽出し、置き場所を名指した issue として振り分ける。**このコマンドはどのファイルも
書き換えない。** 採否は起票の入口の採否の問いでユーザーが決め、採用された issue を普通のタスクとして進めて反映する
（`/review`の産出物と同じ形。`docs/conventions/flow.md`「改善を起票する」）。

## 対象

直近のセッション内で完了した作業（$ARGUMENTS があればそのタスク番号・作業内容）。
実施中に起きた次のような出来事を対象にする:
- ユーザーからの訂正・やり直し指示（アプローチが誤っていた・想定と違った）
- 「実は〜だった」という発見（ドキュメントの記載と実態が食い違っていた等）
- 既存の仕組み・ルールに隙間が見つかり、その場で埋めた対応
- 繰り返し起きている失敗パターンの再発
- 非自明な設計判断（なぜその設計にしたか、理由を残さないと後で失われる）

## 抽出手順

1. 直近のセッション内の作業を振り返り、上記5種の出来事を洗い出す。
   **一般化できないもの（このタスク限定の実装詳細・既に文書化済みの内容）は除外する**。
2. 各出来事について「これを知らずに次の似た作業をしたら、同じ手戻りが起きるか」を問う。
   起きないと判断したものは提案候補から外す。
3. 残った候補それぞれについて、置き場所をCLAUDE.md「ドキュメント階層」（表と、その下の自動の記憶の決まり）で判定する。
   そのタスク限定の背景・決定はタスクの issue に既に書かれているはずなので、本skillでは提案しない。
4. 同じ教訓を複数箇所へ重複提案しない。最も適切な1箇所を選ぶ（CLAUDE.md冒頭の階層表の
   判定基準に従う）。
5. 候補ごとに、置き場所を直す場所として開いた issue を探し（`docs/conventions/flow.md`「前後関係と組」の「探す」）、
   当たればその issue へコメントで足し、無ければ起票する（同じ文書の「改善を起票する」の「書き方」）。
   置き場所の issue の本文の「やること」に、下の変更案を書く。

## 出力フォーマット

```markdown
# タスク振り返り（YYYY-MM-DD、対象: <タスク番号/概要>）

## 提案1: <タイトル>
- 出来事: （何が起きたか、事実ベース）
- 一般化: （なぜ今後にも活きるか。一過性のものは提案しない）
- 置き場所: <CLAUDE.md本体 / docs/conventions/xxx.md / docs/architecture/xxx.md>
- 変更案: （具体的な文面、差分が分かる形）
- 置いた先: #<番号>（起票した issue か、コメントを足した issue）

## 見送り（教訓ではあるが提案しないもの、理由つき）
```

提案は多くても3〜5件に絞る（振り返りのたびに大量の追記提案をすると、CLAUDE.md冒頭が
繰り返し警告する肥大化と同じ問題を招く）。

**振り返りの中でどのファイルも編集しない。** 対象タスクのコミットにも足さない——振り返るころには、対象タスクの
Pull Request は squash でマージ済みか検証中で、足せばその確かめの外の変更になる。反映は、採用された issue の
Pull Request で行う。
