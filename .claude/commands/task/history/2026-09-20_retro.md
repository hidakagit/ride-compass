## 提案1: 層の責務（DBはデータの制約、appはふるまい、テストは今のふるまい）を構造仕様にする

- **出来事**: `road_edges.osm_way_id`にFKもNOT NULLも無く、「wayの行が無い区間」という状態を
  材料の値式10本が`CASE WHEN w.osm_way_id IS NULL THEN NULL ELSE ...`で毎回吸収していた。
  兄弟の派生表5本（way_attribute_counts・way_landcover・designation_attributes・
  edge_landcover・way_divided_carriageway）は同じFKを既に持っており、road_edgesだけが
  持っていなかった。本番の違反行は0件で、そのまま制約を張れた。
  ユーザーから「これも2回目ですけど」と指摘された。
- **一般化**: DBが緩いぶんをappが吸収し、appの吸収をテストが固定すると、直すときに全部が
  同時に落ちるため誰も直さなくなる。T968は「今ある違反を洗う」点検タスクで、閉じたら
  この線引き自体はどこにも残らない。
- **置き場所**: `docs/design-principles.md`（構造仕様15として追加）
- **変更案**:

  ```markdown
  15. **データの制約はDB、ふるまいの制約はapp、テストは「今」のふるまいの網羅**:
      派生表は親への参照（FK・NOT NULL）をDBが持つ。DBが許してしまう状態をapp側の式・分岐で
      吸収しない——吸収すると、読み出し側すべてが同じ防御を書くことになり、しかもそれが
      本番で一度も起こらない分岐として残る。appはテストの都合を意識した口を持たない
      （テスト専用の関数・引数をappへ足さない）。テストが用意する状態は、本番で実際に
      起こりうるものに限る。実例: `road_edges.osm_way_id`にFKが無いぶんを材料の値式10本が
      `CASE WHEN ... IS NULL`で吸収していた（[T956](tasks/T956.md)、migration 0046で是正）。
  ```

## 提案2: 数字を出す前に、その数字の母集団と定義を書く（所要時間も同じ）

- **出来事**: 削減行数を4回測り直し、−1,283 → −1,688 → −1,889 → −2,174 と変わった。
  母集団の取り方（コミットの件名でのgrep／出自／混在ファイルの扱い）を測るたびに変えていた。
  所要時間も「3〜5分」「40分」「2時間」と未計測の数字を出し、ユーザーから
  「水増しと当て推量、根拠に基づかないものばっかり」と指摘された。
- **一般化**: CLAUDE.mdには既に「構造について言う前に機械的に列挙する／測った主張は
  押されても変わらない」があるが、**測ってもなお変わった**。原因は母集団を先に定義して
  いなかったこと。所要時間の見積もりも同じ性質で、既存のルールが射程に入れていない。
- **置き場所**: `CLAUDE.md`（既存の「コードの構造について何か言う前に、機械的に列挙する」
  の項へ追記。新しい項は足さない）
- **変更案**: 同項の末尾へ次を追加。

  ```markdown
    **測る前に母集団の定義を書く**——定義を決めずに測ると、押されるたびに数字が変わる
    （削減行数を4回測り直して−1,283→−2,174と動いた。[T956](docs/tasks/T956.md)）。
    **所要時間も同じで、実測の無い数字を出さない**。未計測なら「未計測」と言う。
  ```

## 提案3: テストが用意する状態は、本番で起こりうるものに限る

- **出来事**: `road_edges`へFKを付けた瞬間にpostgisテスト45件が落ちた。いずれも親のwayを
  入れずに`save_graph`を呼んでおり、本番では作れない状態を前提にしていた。
  また「材料が1つも無い区間」を作るテストがあったが、真偽の材料が`COALESCE`で必ず値を持つ
  ようになった後は本番で起こりえず、テストの前提だけが生き残っていた。
- **一般化**: 本番で作れない状態をテストが作ると、その状態向けの分岐がappに残り続け、
  制約を足したときに一斉に落ちて「制約が悪い」と誤診されうる。
- **置き場所**: `docs/testing.md`（パターン8として追加）
- **変更案**:

  ```markdown
  ## パターン8: テストが用意する状態は、本番で起こりうるものに限る

  DBの制約・取込の順序から**作れない状態**をテストで作らない。作ると、その状態向けの分岐が
  実装に残り続け、後で制約を足したときに一斉に落ちる。

  - 派生行を作るテストは、親を先に入れる（区間は`osm_raw_ways`の派生のため、
    `tests/road_graph_scaffolds.py: save_ways_and_graph`が本番と同じ順を1つ持つ）。
  - 「材料が1つも無い」のように、値式が必ず値を返すぶんは作れない。その前提のテストは
    前提ごと消す（残すなら、軸の集合を差し替えて表現する）。
  ```
