## 提案1: 背景Agentの完了をmasterへ反映した直後は、ローカルのpreview devサーバーが古いコードのまま応答する
- 出来事: T423（backend/frontend合わせて50ファイル変更）がmasterへpushされた後、
  Browserペインで実機確認しようとしたところ、新設エンドポイント
  `/api/region/dynamic-way-values/gradient/...`が404を返した。原因調査の結果、
  ローカルで動かしていたbackend previewサーバー（`.claude/launch.json`定義、
  `--reload`フラグ無し）がT423マージ前から起動しっぱなしで、新しいルート登録を
  一切拾えていなかっただけだった（コード自体は正しかった）。backend
  preview再起動で即座に解消した。同様にfrontend側も、長時間稼働したdevサーバーで
  マップが「読み込み中」のまま固まる現象が発生し、こちらもfrontend preview再起動で
  解消した（原因は未特定だが、再起動で確実に直ることは2回の実績で確認済み）。
- 一般化: 「バックグラウンドAgentへ実装タスクを委任するときは`isolation: "worktree"`を
  必ず指定する」というCLAUDE.mdの既存ルールにより、Agentの作業はメインツリーの
  devサーバーに影響しない。逆に言うと、**Agent完了後の実機確認では、メインツリーの
  devサーバー自身を明示的に再起動しないと新しいコードが反映されない**という、
  worktree分離の裏返しの落とし穴がある。この手順を知らずに次の背景Agent完了後の
  実機確認をすると、同じ404/謎の固まりに遭遇し、「Agentの実装がバグっている」と
  誤診断する手戻りが起きる（実際に本セッションでも一度「T423のバグでは」と誤って
  疑いかけた）。
- 置き場所: [docs/workflow.md](../../../../docs/workflow.md)「2. 実装中」節
  （背景Agentのworktree分離について既に触れている段落のすぐ後）
- 変更案:
  ```diff
     - **バックグラウンドAgentを使う場合は`isolation: "worktree"`を必ず指定する**
       （2026-08-30、T414実装時に指定を忘れ、同じ作業ツリーを共有してしまった実績を受け
       CLAUDE.md「作業ツリーの安全」節へ明文化済み）。
  +  - **背景Agentの成果をmasterへ反映した後、実機確認する前にローカルのpreview
  +    devサーバー（backend/frontend）を明示的に再起動する**（`.claude/launch.json`の
  +    起動コマンドは`--reload`無しのため自動では新コードを拾わない。2026-08-30、
  +    T423マージ直後にbackend再起動を忘れ、新設エンドポイントが404を返す状態を
  +    一時的に「実装のバグ」と誤診断しかけた実績あり）。
  ```

## 提案2: frontend devサーバーが長時間稼働すると、原因不明のままMapLibreの初期化が止まる現象が再現する
- 出来事: 本セッション中に2回、独立したタイミングで「地図を読み込み中…」のまま
  MapLibreのcanvasが一度も描画されない（`initialTilesLoading`が晴れない）現象が
  発生した。両者に共通するのはfrontend devサーバー（Turbopack）がある程度の時間
  稼働し、複数回のFast Refresh／HMR再接続を経ていたこと。コンソールには
  `Expected value to be of type number, but found null instead.`という警告と、
  2回目にはHMR WebSocket接続失敗のログが見られたが、いずれも直接の原因とは
  確定できなかった。両回とも**frontend devサーバーをpreview_stop→preview_startで
  作り直すだけで確実に解消**し、コード側の修正は一切不要だった。
- 一般化: 今後もこの現象に遭遇する可能性が高い（2回連続で再現しているため）。
  根本原因は未解明だが、「まずdevサーバーを丸ごと再起動する」が実証済みの一番安い
  解決策であることは分かっている。この情報が無いと、次回も同じ調査
  （console/network/canvas pixel検査等）を1から繰り返すことになる。
- 置き場所: メモリ（project種別、新規） — コードリポジトリ外の運用知識であり、
  かつ本プロジェクトのdev環境（Windows・Turbopack）固有の現象のため
  `docs/`より[[memory]]が適切。
- 変更案: 新規メモリファイル`frontend-dev-server-map-load-hang.md`を作成し、
  `MEMORY.md`へ以下の1行を追記:
  ```
  - [Frontend Dev Server Map Load Hang](frontend-dev-server-map-load-hang.md) — 長時間稼働したfrontend devサーバーでMapLibre初期化が原因不明のまま止まる現象が2回再現(2026-08-30)。devサーバー再起動で確実に解消、コード修正不要
  ```

## 提案3: 背景Agentが「ハングしていないか」はOSプロセス調査より本人への直接メッセージの方が確実
- 出来事: ユーザーから「T423が1時間半動き続けている、ハングしていないか」と
  懸念が出た際、まず`Get-Process`でCPU使用量の高いプロセスを調べたが、実際には
  それらは別の（既に完了した）Agentのworktreeに残った停止し忘れのdevサーバーや
  自分自身のfrontend previewであり、T423のworktreeのプロセスとは無関係だった。
  この誤ったプロセス調査結果を一度そのままユーザーへ「ハングしていなさそう」と
  報告しかけ、直後に「これはT423のものではない」と気づいて訂正した。最終的に
  確実だったのは、Agent本人へ`SendMessage`で状況を直接尋ねること（実際には
  その返信を待たずに完了通知が届いた）と、作業ツリーのファイル更新時刻・
  `git status`で実際の変更内容を見ることだった。
- 一般化: 背景Agentの生死・進捗確認は、OSプロセス一覧からの推測（他のAgentの
  残骸と誤認しやすい）に頼らず、(1)Agent本人への`SendMessage`、
  (2)そのAgentの作業ツリー自体の`git status`/ファイル更新時刻、を優先すべき。
  この教訓が無いと、次回も誤ったプロセス調査結果をユーザーへ報告しかける
  リスクがある。
- 置き場所: メモリ（feedback種別、新規） — Claude自身の調査手法についての
  教訓で、プロジェクト外・他プロジェクトでも一般化できるため。
- 変更案: 新規メモリファイル`feedback-agent-liveness-check-method.md`を作成し、
  `MEMORY.md`へ以下の1行を追記:
  ```
  - [Feedback Agent Liveness Check Method](feedback-agent-liveness-check-method.md) — 背景Agentの生死確認はOSプロセス一覧の推測(他Agentの残骸と誤認しやすい)より、SendMessageでの直接確認・当該worktreeのgit status/ファイル更新時刻を優先(2026-08-30)
  ```
