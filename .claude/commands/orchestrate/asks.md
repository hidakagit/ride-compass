# 確認待ちをまとめて出す

確認待ちの正本は各タスクの記録で、状態の表には持たない（書き方は`docs/conventions/orchestration.md`
「ユーザーの判断待ち」節と「ユーザーへのお願いは記録に置く」節）。判断の問いの形式は
`docs/conventions/asking-user.md`が正本。先に全文読む。

1. `python scripts/orchestrate.py asks $ARGUMENTS`を実行する。origin/masterの全タスクの記録（閉じた
   タスクを含む）から、**判断**（決定の段落の無い保留の単位。中の番号付きの項目はその保留の選択肢）・
   **実施**（`## ユーザー操作（待ち）: …`）・**改善の承認**（`## 改善提案（承認待ち）: …`）が、
   種類ごと・タスクごとに出る。
2. 先頭に種類ごとの件数を置く。ユーザーへ見せる種類の名前は「決めてほしいこと」「ユーザーに実行してほしい操作」
   「入れてよいか決めてほしい改善案（まだ入れていない）」とする（「実施」「改善の承認」と書くと、司令塔が実施したもの・
   司令塔が入れた改善の承認と読める）。**操作**は1件ずつ、記録の本文を読んで、**ユーザーがこの回答だけで実行できる手順**
   として出す——開くURL・押す場所・貼るコマンドをそのまま書き、「Txxx.md参照」「手順は記録にある」で済ませない。司令塔が
   先に確かめられる部分（リポジトリ・手元の設定・読めるAPI）は確かめてから出し、ユーザーの手順を減らす。**改善案**は
   1件ずつ「何が起きたか・何を変えるか・入れたら何が変わるか」を出す。
3. **判断**は、記録の保留のままでは問いにならない。1件ずつ記録を読み、asking-user.mdの形（何の画面・
   機能か／いまどうなっているか／なぜ決めるか／各選択肢で利用者に何が起きるか。推奨を先頭に）へ
   整える。記録から背景・選択肢を補えなければ問いにせず、担当（いなければ司令塔のキュー）へ
   「保留の書き直し」として回す。画面の見た目・情報量に関わる問いには、変更前と変更後の実画面か
   モックを添える。選択式の質問（`AskUserQuestion`）で4問ずつ出す（各2〜4択、推奨を先頭に「（推奨）」）。
4. 回答・実施の報告・承認は、その`Txxx.md`へ書く作業（判断は保留の単位の中へ`**ユーザー決定（日付）**:`
   の段落、実施は見出しを`（済 日付）`へ、改善は`（承認 日付）`か`（見送り 日付）`へ）として担当の
   エージェントへ返すか、`python scripts/orchestrate.py board todo push "<Txxx>へ<何を>書く: <回答>" --priority 5`
   で司令塔のキューへ積む。記録へ書かれるまで、その待ちは一覧に出続ける。

このコマンド自身はリポジトリを書き換えない。記録への反映は担当エージェントの仕事である。
