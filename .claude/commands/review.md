# 周期レビュー

このプロジェクト唯一のレビューコマンド。4つの観点で見たうえで、**観点どうしの矛盾を
解消してから**起票案を出す。観点ごとに別々の結論を並べて終わりにしない。

$ARGUMENTS があればそれを対象範囲とする。

## 監査する対象

**維持する対象と、実コードだけ。**

| 見る | 見ない |
|---|---|
| `CLAUDE.md`・`docs/architecture/`・`docs/modules/`・`docs/conventions/` | `docs/records/`（記録） |
| `docs/improvement-plan.md`（台帳） | |
| `backend/`・`frontend/`・`scripts/`・`.github/`・`.claude/` | |

記録は**記録時点で嘘がなければよく、訂正は新しい記録で行う**。後から現在の実装と
食い違っても欠陥ではないので、監査の対象にしない。

## 産出物

**起票したタスクと、見送り判断だけ。** 生のレビュー記録は残さない。

- 直すもの → `docs/records/tasks/Txxx.md` を作り、`docs/improvement-plan.md` へ1行足す
  （どちらもユーザー承認後）
- **やらないと決めたもの → 見送りの記録として起票する。** `docs/records/tasks/Txxx.md`を
  `状態: 完了`で作り、見出し`## 判断: 見送り`の下に理由と再評価の条件を書く。台帳には
  `- [ ]`行を置かない（片付いた判断なので`/task:next`の候補に混ぜない）。ここを残さないと、
  次のレビューが同じ論点を蒸し返す——過去の見送りは
  `grep -l "^## 判断: 見送り" docs/records/tasks/*.md`で引く
- レビューを終えたら、**見た対象コミットへ注釈付きタグを打つ**:
  `git tag -a periodic-review/NNN -m "第NNN回"`（NNNは回数。`git tag --list
  'periodic-review/*' | sort | tail -1` の次）。周期レビューの発火判定はこのタグを読む

**コードもdocsも変更しない。** 誤記の修正も起票案として出す。

## 進め方

### 1. 対象範囲を決める

前回のタグ（`periodic-review/*` の最新）が指すコミットから HEAD までを中心にする。
タグが無ければ全体。`python scripts/review_checks.py trigger` が発火状況を出す。

### 2. 変更ファイルは全件・全文を読む

テーマでサンプリングしない。対象が大きいときは**観点ごとに**分割し、ドメイン
（backend/frontend等）で割らない——観点が分割の単位で、ドメインは違う。
分割してAgentへ委任するときは `isolation: "worktree"` を指定する。

**複雑度の観点だけは分割しない。** 差分ではなくリポジトリ全体の横断計測が主体で、
コストが差分サイズに比例しないため、常に単独で実施する。

機械的に出せるもの（規模・docsの整合）は先にコマンドで取り、その出力を読む:

```bash
python scripts/review_checks.py metrics
python scripts/review_checks.py size
python scripts/review_checks.py docs
```

### 3. 4つの観点で見る

観点は下の「確認観点」節。**同じ事象に2つの観点から指摘を出さない**——
存在の検出は全体最適、その対処が複雑さに見合うかは複雑度が担当する。

### 4. 矛盾を解消する（最重要）

- **矛盾**: 「全体最適では共通化すべき／複雑度では抽象化しすぎ」のような対立を両論併記で
  終わらせない。判断基準（変更理由が同じか・設計原則・変更コストの実測）に照らして
  **どちらを採るか決め、根拠を書く**
- **トレードオフ**: 「UIは便利だが構造が複雑になる」等は、現在の開発フェーズ
  （研究優先・個人開発・低利用規模）を前提に結論を出す
- **重複**: 複数の観点が同じ根本原因を別の症状として指摘しているなら、1つへ統合して
  根本原因側へ寄せる
- **相殺**: ある提案が別の観点の「このままでよい」を壊さないか確認する

### 5. 起票と見送りを決める

優先度順に並べ、**1件ずつ「起票する／見送る」を決める**。件数だけ示して個票を省略しない。

## 確認観点

### 全体最適（構造が一貫しているか・局所最適が連鎖していないか）

- レイヤーの向き（api → services → domain → infrastructure）。domainにI/Oが漏れていないか、
  infrastructureがservicesへ依存していないか
- 責務分割が「同じ理由で変更されるもの」の単位になっているか
- 依存: 直接依存・循環の芽・DI工場（`dependencies.py`）を迂回した構築
- データフロー: ルート生成と地図レイヤーの一本道が保たれているか。評価軸追加の1本道から
  外れた実装が入っていないか
- **新旧の混在**: 「並行追加→設定で切替→旧削除」の途中にあるものに削除条件が書かれているか。
  条件が成立済みなのに残っているものはないか。旧実装・デッドコード・テストだけが参照する
  コード
- 重複（コード／ロジック／データ／設定／API／UI／概念）、正準定義の複製
- 不要な抽象化・wrapper・変換・fallback。**フォールバック経路へ新機能が実装されていないか**
- **局所最適の連鎖**: 「Aを直した結果Bが複雑になった」「Bを再利用するためCの責務が曖昧に
  なった」を探す。変更されたファイルの**呼び出し元・呼び出し先**まで読む
- スケール成立性: 全量ロード・全件転送を伴う新設計がないか。索引を使えない空間述語、
  行ごとのLATERAL/サブクエリ、ループ内の逐次INSERT/外部API呼び出し、delete-then-reinsertに
  よる関連データの黙殺消失

### 複雑度（複雑さが適切な場所にあるか）

**「単純化できるか」ではなく「複雑さが適切な場所にあるか」。** 複雑なドメインロジック
（経路探索・評価合成・地理計算・タイル座標系）はdomain層に集約されていれば複雑でよい。

- 巨大クラス・関数・コンポーネント・service・hook。**行数で機械的に判定せず**
  「複数の変更理由が同居しているか」で判断する
- 過剰な条件分岐・状態（フロントのuseState増殖）・設定（使われていない設定はないか）・
  DI・抽象化（利用者が1つしかないinterface/Protocol）・素通しの委譲
- **規模ウォッチ**: `review_checks.py size` の表をそのまま出力へ含める。発火したファイルは
  (a)理由つきで現状維持、(b)抽出・分割の提案、(c)個別閾値の設定、のいずれかへ必ず分類する。
  **次の閾値を決めずに発火させたままにしない**——安全弁が鳴りっぱなしになって機能しなくなる。
  「閾値の見直し」に出たエントリ（縮んだ・消えたファイル）は、下げるか外すかを決める
  ——閾値は自動では下がらず、緩んだままだと鳴るべきときに鳴らない
- **写経の監視**: 同じ決まりごとが各所へ書き写されていないかを見る。**機械の道具は持たない**
  ——完全一致のクローンしか捕まらず、値の直書き・組み立て規則の手書き・処理順序の似た再実装は
  原理的に検出できないため、数字を見て安心する材料にしかならなかった。読んで判断する
- **不足している構造化**: 同じ変更理由で2箇所以上直す必要がある箇所、責務混在（1関数が
  I/Oと計算を兼ねる）、コメントや規約でしか守られていない整合（テストや型で機械化できないか）
- **冗長さの型**: 次は繰り返し出るので、変更の入った領域で毎回見る。
  - **嘘の戻り値型と、それが生む死んだガード** — `X | None`と宣言しながらNoneを返す経路が
    無い関数。呼び出し側に`if ... is not None:`が生え、本番では常に真のまま残る
    （`graph_service`の`tile_set`で型5箇所・ガード12箇所）。
  - **共有断片から外れた手書き** — 共有の定数・SQL断片があるのに、1箇所だけ同じものを
    手で書いている。**共有側を直しても、その1本だけが古い世界を指し続ける**
    （`material_coverage`が`FROM osm_raw_ways`を手書きし、欠損率APIが落ちていた）。
  - **同じ本体を持つ関数の対** — `set`と`set_empty`、`get`と`get_by_key`のように、
    引数以外が同じ。「〜と同じ」と書いたコメントが目印になる。
  - **参照0の公開シンボル** — importグラフで外部消費者を数える。0ならprivateにする
    （エントリポイント・FastAPIのハンドラ・CLIの`main`は除く）。
  - **多重ドア** — 1つの計算の途中結果を複数の公開関数から出している形。**同じ引数型の
    公開関数が並ぶことが手がかり**だが、それ自体は欠陥ではない（独立した実装のこともある）。
    見分けるのは「片方の出力がもう片方に丸ごと含まれるか」で、これは機械では出ない
    （`axis_display`は公開7本すべてが`(AxisDefinition)`を取り、1つの計算の別射影だった）。
  - **旧スキーマ・旧インフラを指したまま残った経路** — 個々のシンボルは実在するため
    死んだ参照として検出されない。テーブル名・接続方式・配置先を移したタスクの後に見る。
- **性能と複雑度の釣り合い**: 実測を伴わない最適化はpremature として指摘対象。逆に実測で
  問題が示されているのに放置されている箇所も見る
- **変更コスト**: 代表シナリオ（評価軸追加・道路属性追加・レイヤー追加・外部データソース追加）
  で「編集が必要なファイル数・箇所数」を数え、前回と比べて悪化/改善を報告する

### 整合性（設計↔実装↔テストが一致しているか）

**設計書を無条件に正とみなさない。** 実装を一次情報として突き合わせ、乖離があれば
「どちらが正か」を判断材料つきで示す。

- `docs/architecture/` と実装の乖離。対象範囲で完了マークが付いたタスクを1つずつ列挙し、
  各タスクの主要な変更（新設ファイル・テーブル・エンドポイント・ドメイン概念）が
  **どこかに反映されているか**を確認する。「更新されているが古い」だけでなく
  **「対応する記述自体が存在しない」を積極的に探す**
- API契約: `openapi.json` / `api.d.ts` が最新か。**同型の手動同期ペアで2回以上の再発が
  観測されたら、対応は「手順の再徹底」ではなく「機械的検知の追加」を第一候補にする**
  （置き場は実装側の道具——テスト・生成物のドリフト検査。`review_checks.py`へ足す条件は
  CLAUDE.md「検知器を足す条件は厳しい」）
- ドメインルールの正準定義（路面語彙・highway 3スコープ・符号の定義）が、SQL・フロント・
  docsで一致しているか
- 台帳の完了マークと実態（完了条件が実際に成立しているか）
- ログ方針（`docs/conventions/logging.md`）に新規コードが従っているか
- **分割元タスクの未起票フォローアップ**: 完了マーク済みの親タスクがあるとき、子タスクを
  「未起票」「別タスク」「スコープ外」等の語で検索し、各該当箇所が①起票済み番号へ
  リンクされているか②起票しないと決めた理由が明記されているか、を確認する。
  **バックグラウンド実行の完了報告を受けたときこそ重要**——ユーザーが逐次内容を確認
  できないため、この見落としに気づく機会が無い
- **共有フィールド・パターンの全消費者チェック**: 既存の共有フィールド・パターンを
  変更/廃止したとき、直接触ったファイルだけでなく、変更前の綴りをリポジトリ全体でgrepして
  取り残された消費者がいないか確認する。**対で持つ実装**（`wind_way_service.py` ⇔
  `gradient_way_service.py`、`error.tsx` ⇔ `global-error.tsx` 等）の片側だけを変えた
  コミットも同じ要領で見る
- **削除・統合された事実を語る周辺表現の残存**: 「N個の◯◯」「両方の△△」のように個数・
  組み合わせを主張する記述が変わる変更では、削除したシンボル名の逆引きgrepだけでは足りない。
  シンボルを名指ししない緩い言い回し（「従来は」「以前は」「〜と使い分ける」等、複数の
  選択肢の存在を前提にした表現全般）が残っていないか、**前後を実際に読んで都度判断する**
- **コード自身が述べる契約と実装の一致**: docstring・コメント・型が述べる前提（「常に
  △△である」「昇順」「空は来ない」）が実装で強制・検証されているか。とくに①`[0]`等への
  無条件アクセス、②同種のバリデーションが兄弟フィールドの一部にしかない、
  ③コメントが主張する挙動と実装が逆・不完全
- **トリガー付きタスクの棚卸し**: 台帳の `- [ ]` のうち「トリガー: ◯◯」を持つものを**全件**
  再評価する。`/task:next` はトリガー付きを既定で除外するため、**ここで見なければ誰も見ない**。
  各タスクについて順に: ①条件は成立したか（数えられるものはその場で数える）、
  ②**その問題は別のタスクで既に解決されていないか**（最も見落とされる）、③タスクの前提は
  まだ存在するか。結果は「発火」「未発火（根拠を1行）」「別タスクで解決済み」「前提が
  変わった」のいずれかへ分類し、**未発火には根拠を残す**
- **実装↔テスト**: 変更に対応するテストがあるか。実装詳細への依存（privateメソッド直叩き）、
  不要になったテスト、過剰なmock、**実質的に意味のないテスト**（実装をなぞるだけで
  壊れ方を検証しない、常にpassする）、PostGIS統合テストが「ずっとskipされ続けて検証
  されていない」状態になっていないか

### UI/UX（初見のユーザーが理解できるか）

**「見た目が綺麗か」ではなく「初めて使う人が目的と操作方法を理解できるか」。**

実施は次の3段で、上から順に試す。

1. **既定は `frontend/e2e/fixtures.ts`（backendモック）**。実バックエンド・実外部API・
   実DBに依存しない。**変更のあった画面＋主要導線1周は必ずここで見る**。実DBを使うと
   既定の現在地・30km周回がデータ範囲外で即失敗し、1枚あたり数分かかる
2. **実データが要る所見だけ追加で**: カバレッジ外の空タイル・配信の欠落・**出ている値の
   妥当性**は実DBでしか見えない。見られなければ**省略してよい**——「実機未確認」と明記し、
   その指摘の確度を下げる。実DBを使う確認は本体の開発環境で行い、**本体の作業ツリーへ
   変更を加えない**
3. どちらも不可ならコード精読で代替し、**その旨を冒頭に書く**

- 初回表示で「何をするアプリか」「最初に何をすべきか」が分かるか
- 空状態（候補0件・データ未整備地域）で「壊れているのか、データが無いのか、操作が
  足りないのか」が伝わるか。ローディング・エラー・429拒否の表示
- 用語の一貫性（同名で意味が違う／同じ意味で名前が違う表示）
- 設定の3軸（反映タイミング・保存有無・配置）が系統ごとに統一されているか
- 地図上（ON/OFFチップ＋条件サマリ）とサイドバー（詳細設定）の役割分担
- 凡例が地図上で判読できるか（**ダークモード含む**）
- **出ている値の妥当性**: 既知の場所を1つ選び、レンズが出している数値・色が実地と
  整合するか突き合わせる。**「正しく配信され正しく描画された、もっともらしいが間違った値」は
  これでしか出ない**。ただし同じ型を2回見つけたら観点を増やさず、材料側の妥当範囲の宣言へ移す
- **390px幅**での主要導線と、新設・変更されたパネル・フォームの収まり（横スクロール・
  画面外への溢れ）とタップ操作（ホバー/title依存UIがタップで機能するか）
- 研究用UIが一般UIに漏れていないか。研究UIも**操作可能性**は一般UIと同基準で評価する
  （低くてよいのは見た目の洗練度だけ）

**所見は確定前に再検証する。**「壊れている」と書く前に、セレクタの対象要素・dev環境固有の
UI（`next dev` のインジケータ・コンパイル遅延）でないかを確認する。

## 判断原則

1. **全体最適**: 個々のファイル・クラス・関数ではなく、システム全体として合理的かで判断する
2. **局所最適への警戒**: あるコンポーネントの改善が別のコンポーネントを複雑にしていないか
3. **複雑度の平衡**: 複雑さゼロを目指さない。複雑であるべきドメインロジックは複雑でよい
4. **過剰な抽象化を避ける**: interface / factory / strategy / adapter / wrapper を、
   利用者が1つしかないのに作らない
5. **抽象化不足も確認**: 同じ責務・同じ変更理由を持つ処理が複数箇所にあれば共通化を検討する
6. **変更理由を重視**: 責務分割・共通化の基準はコードの類似性ではなく「同じ理由で変わるか」
7. **冗長性の確認対象**: コード・ロジック・データ・設定・API・UI・概念のすべて
8. **新旧設計の混在**: 「意図的（切替・併存）」「移行途中」「残骸」のどれかを判別し、
   移行途中には削除条件を求める
9. **将来のための過剰設計を避ける**: 「いつか必要かもしれない」だけで現在の複雑度を上げない
10. **コード量だけで判断しない**: 理解・変更・テスト・拡張のしやすさを総合で見る
11. **単純化しすぎない**: 複雑度を下げるために責務を巨大クラスへ集約しない
12. **説明可能性**: 第三者に「なぜこの構造なのか」を説明できるか
13. **新しい種類の仕組みを作る前の原則点検**: 既存と技術的に別方式の配信・レンダリング機構を
    新設するときは、`docs/architecture/design-principles.md` の構造仕様が新機構にも
    適用されるかを**着手前に**点検する
14. **性能の主張は実測とセット**: `benchmarks/`・本番ログを伴わない性能最適化はpremature
15. **docsは「現状」と「経緯」を分ける**: 現状は正本（`architecture/`・`modules/`・
    `conventions/`）、経緯は記録（`records/`）
16. **「実害が無い」を理由に構造的欠陥を放置しない**: early return・一度だけの初期化・
    クロージャでの値固定等は、「現在の呼び出し元は動的な値を渡していないから今は壊れない」
    という理由だけでは許容しない。利用者に暗黙のタイミング制約を強いる実装を作らないことを、
    局所的なバグ修正より優先する

17. **テストが大きな足場を要求したら、設計の症状を疑う**: 検査のために大掛かりな
    フェイク・ハーネスを建てる必要が出たら、まず実装側が2つに分かれていないかを測る。
    足場を建てると、二重に持っているという原因が残ったまま固定される

## 事実と推測を分ける

- **読んで確かめたこと**と**推測**を混ぜない。推測なら「未確認」と書く
- 構造について言う前に**機械的に列挙する**。「2か所にある」「これが唯一の定義だ」は
  思い出しで言わず、grepかASTで数えた結果を先に出す
- **測る前に母集団の定義を書く**。定義を決めずに測ると、押されるたびに数字が変わる
- **実測の無い数字を出さない**。未計測なら「未計測」と言う

## 禁止事項

- **コード・docsを変更しない**（誤記修正も起票案として出す）
- 件数と分類だけを示して個票を省略しない
- 「◯◯を一掃する」型の起票案で、対象をタスク本文へ列挙しない（列挙した瞬間に古くなる。
  **対象の導出方法**を書く）
- 新しい自己申告のチェックを増やさない。思いついた確認は起票して人が見る。
  `scripts/review_checks.py` の検知器にするのは、CLAUDE.md「検知器を足す条件は厳しい」の
  基準を満たし、既存の検知器と母集団が重ならないときだけ
