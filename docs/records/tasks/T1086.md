# T1086. 台帳の行は担当に消させず、監査の取り込みの後に司令塔がまとめて消す

状態: 完了（2026-09-23）

## 背景

T1049の改善提案（ユーザー承認 2026-09-23）。担当がタスクを閉じるとき台帳（docs/improvement-plan.md）の自分の行を消すため、並行した担当が隣り合った行を消すと取り込み（cherry-pick）で衝突した（第1回で3回。解き方は毎回「両方消す」）。やること: (1) 規約 docs/conventions/orchestration.md の担当の完了の手順を「Txxx.mdの状態:だけを完了にし、台帳の行は消さない」に変え、司令塔が監査の取り込みの後、状態が完了の記録に対応する台帳の行をまとめて消す手順を「監査の結果」節に入れる。(2) scripts/review_checks.py docs の台帳と状態の整合の検査（task_state）が、担当の作業ブランチでは「状態: 完了なのに台帳に行が残る」を許し、masterでは許さない形にする（どう区別するかを決めて書く。許可リストを足さない）。(3) 司令塔が行を消す操作を orchestrate.py の1コマンドにする（board unpushed の手順に組み込む等）。完了条件: 2つの作業ブランチが隣り合った台帳の行のタスクを閉じても、取り込みが衝突しないことを使い捨てのリポジトリで1回見る。

## 対応方針

- **作業ブランチとmasterの区別**: 検査しているコミットのブランチを実行時の事実から取る
  （`review_checks.checked_branch`）。CI（`GITHUB_ACTIONS=true`）ではワークフローを起動したref
  （`GITHUB_REF`が`refs/heads/<名前>`のときその名前。プルリクエストの合成コミットは`refs/pull/…`なので
  「ブランチ不明」）、手元では`git symbolic-ref --short -q HEAD`。それが`MAIN_BRANCH`（`master`）の
  ときだけ「完了なのに台帳に行がある」を違反にし、それ以外では「参考」として件数と行を出す
  （終了コードに数えない）。許可リストは足していない——分けるのは「台帳の行が閉じているべき
  ブランチか」という1つの事実で、masterへ入る時点の不変条件はmasterへのpushのCIが今までどおり見る。
  残り2条件（表記が2語でない・未完了なのに行が無い）はどのブランチでも違反のまま。
- **司令塔の1コマンド**: `python scripts/orchestrate.py ledger close`（新モジュール
  `scripts/orchestration/ledger.py`。核はimportしない）。作業ツリーのHEADの台帳と記録を読み、
  `状態: 完了`の記録を指す行（番号ではなくリンク先で記録を引く）を消して、台帳だけのコミットを1つ作る。
  消す行が無ければ何もせず0で終わる（何度打っても同じ）。台帳に未コミットの変更があれば止まる。
  `board unpushed`が出す取り込みの手順の、cherry-pickとpushの間にこれを入れた。
- **監査の項目2**（`core.cmd_audit`）: 「完了なのに台帳に行がある」を止めにしない。逆に担当が
  行を消していたら「?」（衝突しうる）として出す（止めにはしない。規約の切り替わりの回では、
  消した担当が出てくるため）。
- **規約**: 「完了とpush」の完了の作法を「状態だけを完了にし、台帳の行は消さない」に、rebaseの
  衝突の段を「両方の変更を残す」に、「監査の項目」の2.を「完了の行は残っていてよい」に、
  「監査の結果」のpushの手順に`ledger close`を入れた。

## 緩和の影響（実測）

母集団はタスク記録（`TASK_FILE_RE`に合う`docs/records/tasks/*.md`）全件。作業ブランチで違反から
外れるのは3つ目の条件が効く「状態が完了の記録」で、origin/master（40617cba）時点で
**875件中807件（92.2%）**。ただし外れるのは作業ブランチでだけで、参考として同じ行を出し、
masterでは全件を今までどおり違反にする（下の検証で、行を消す前のmasterで2件を違反として検知した）。
計測は scratchpad の measure.py（`review_checks`のSTATE_RE・TASK_FILE_REで数えた）。

## 検証

使い捨てのリポジトリ（`tempfile.mkdtemp`、scratchpad の sandbox.py）で、台帳に隣り合った3行
（T1・T2・T3）を持つ土台から`orch/a`がT1を、`orch/b`がT2を閉じ、masterから切った`land`へ順に
cherry-pickした。

- **直す前**（origin/masterのスクリプトと規約。担当が行を消す）: `orch/b`のcherry-pickが
  `CONFLICT (content): Merge conflict in docs/improvement-plan.md`で止まった（第1回の事象を再現）。
- **直した後**（担当は状態だけを完了にする）:
  - 各作業ブランチの`review_checks.py docs`は終了コード0、「[参考] 完了なのに台帳に行がある: 1件」。
  - cherry-pick 2件とも終了コード0（衝突なし）。
  - そのままmasterへ進めた木で`review_checks.py docs`は終了コード1、task_stateの違反2件（T1・T2）
    ——わざと行を残した入力をmasterでは検知する。同じ木で`GITHUB_ACTIONS=true GITHUB_REF=refs/heads/orch/a`
    なら終了コード0（参考1件）、`GITHUB_REF=refs/heads/master`なら終了コード1。
  - `orchestrate.py ledger close`: 「台帳から2行を消してコミットした: T1・T2」、2回目は「消すものなし」で0。
    台帳にはT3の行だけが残り、`review_checks.py docs`（master）は終了コード0。
- この作業ツリー（`orch/R-ledger`）で`python scripts/review_checks.py docs` → 違反なし。
  `ruff check`（本体のbackend/.venvのruff）で変更した4ファイル → All checks passed。
  `python scripts/orchestrate.py ledger --help`・`board unpushed`が動くこと。

## 気づき（起票はしていない）

  監査の項目2が「?」で出すだけで壊れはしない。
- このタスク自身は、指示どおり今の規約で台帳の行を自分で消した（取り込みの手順が司令塔の
  作業ツリーで新しくなる前に入るため）。
