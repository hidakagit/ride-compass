# T1014. E2Eを「実機でしか出ないもの」の場として作り直す

状態: 完了（2026-09-23）

## 背景

E2E（`frontend/e2e/`、Playwright）は「地図UI変更は必ずPlaywrightで実機確認する」を
自動回帰検知へ移す目的で置かれたが、**何をE2Eの対象にするかの定義が無い**まま
テストが足されてきた。その結果、単体テストと同じ主張をしているもの・共通の作り物が
判定対象そのものを決めてしまっているものが混ざっている。

普通のテストの定義・実施標準（`docs/conventions/testing.md`）は整ったが、**E2Eだけは
まだ定義が無い**。E2Eは「実データ・実ブラウザでしか見えない意図」を確かめる場であり、
単体テストと同じ扱いにできない。

## 観測（2026-09-22）

### 1. 手元では1回も走らない

`playwright.config.ts`の`webServer`が`npm run build && npm run start:standalone`を
180秒の枠で起動しようとするが、この開発機では本番ビルドだけで枠を超える
（`Timed out waiting 180000ms from config.webServer` で全テストがスキップされた）。
ビルドを先に済ませれば通るが、**手順としてそうなっていない**。

### 2. 「実機」が効いた実績は、どこに偏っているか

`grep -rn "実機" frontend/src docs/modules docs/conventions docs/architecture CLAUDE.md`
＝115件。**うち64件がCSS**。内容を読むと4種類に分かれ、E2Eの対象になるのは前3つだけ。

| 観点 | 原文の例 | 機械で判定できるか |
|---|---|---|
| 1. 収まらない・潜り込む・押せなくなる | 「チップ列がズームボタンの下に潜り込む」「タブバー配下に完全に隠れて押せなくなっていた」「スクロールバーが出てしまう」「スマホだと見切れてさわれない」 | できる |
| 2. ブラウザ/OSの既定に踏まれる | Androidの既定タップハイライト、ピンチズームがページ全体の拡大に化ける、`<form>`の暗黙送信、`passive: true`で`preventDefault`が効かない | できる（実ブラウザにしか無い） |
| 3. カスケードの勝ち負け | 「unlayeredのままTailwindの`p-2`が`padding:0`に潰される」「自前サイズを詳細度で踏みつぶす」「ビルド順に依存」 | できる（計算後の値を読める） |
| 4. 読みやすさ・色 | 「風の背景色が凡例と合ってない」「縁取りが見にくい」「コントラストが強すぎて見づらい」 | **できない（人が見るしかない）** |

**観点4はE2Eの対象にしない。** 自動化しようとすると画面写真の突き合わせになり、
`CLAUDE.md`が検知器へ禁じている「保存した過去の値と比べる」形になる。

### 3. 今あるテストをこの物差しで見る

| テスト | 判定 |
|---|---|
| `mobile.spec.ts`「ヘッダーが幅に収まり、メニューが押せる」 | 観点1。仕事をしている |
| `mobile.spec.ts`「レンズの凡例が、段階の細かい軸でも幅に収まる」 | 観点1。仕事をしている |
| `mobile.spec.ts`「ルート結果を見ている間は地図タップでピンが置かれない」 | 観点2に近い（実ブラウザのイベント） |
| `smoke.spec.ts`「地図レイヤーのON/OFF切替」 | `aria-pressed`の反転だけ。**単体テストと同じ主張** |
| `smoke.spec.ts`「ルート生成→候補一覧の表示」 | 同上 |
| 観点2・3を正面から見るもの | **0本** |

### 4. 共通フィクスチャが、判定対象そのものを決めている

`mobile.spec.ts`が「凡例の幅」を見るために、共通の`e2e/fixtures.ts`へ
`FINE_STEP_AXIS_LABEL = "段階の細かい軸"`という**そのテスト専用の軸**を足している。
観点1は中身の実寸がすべてなのに、共通の作り物がその実寸を決めている。
**1本の都合が共通側へ漏れ、他の全テストがそれを引き連れて動く。**

加えて、地図スタイルは空（`{version: 8, sources: {}, layers: []}`）・`tile_versions`は空。
そのため路面・点・事故・気象のシーングループは**ソースごと作られず**、
`features/map/scene/`の式は実ブラウザを一度も通っていない。
代役地図はstyle検証を持たないため、単体テストでも通らない
（`docs/modules/frontend/static-map-layers.md`「MapLibreの式を組むときの前提」）。

## やること

1. **定義を`docs/conventions/testing.md`へ置く**（パターン4の書き換え）。
   - E2Eの対象は「実機でしか出ない」かつ「機械で判定できる」もの＝観点1〜3
   - 観点4は対象にしない（人が見る。`frontend-design-system.md`「実機確認の方法」の側）
   - **判定対象になる値を共通フィクスチャへ置かない**。共通に置いてよいのは「目的の画面まで
     進める導線」だけ（`openMobileApp`・`generateRoutes`等）。各テストは自分が測る値を
     自分で用意する
2. **系統を分ける**。決定的な回帰検知（モック・CI）と、実データで見る系統（実backend・
   実タイル）は目的が違うので同じ場所に混ぜない。実データ系はCIの完了条件に入れない
   （所要と外部依存が読めないため）。置き場と走らせ方をこのタスクで決める。
3. **既存6本を物差しに掛け直す**。単体と同じ主張のものは消すか観点1〜3の形へ書き直す。
4. **手元で走る形にする**（`webServer`の枠、またはビルド済み前提の手順）。
5. **観点2・3を1本ずつ足す**。足したら、わざと壊して落ちることを確認してから完了扱いにする。
6. `features/map/scene/`の式が実ブラウザのstyle検証を通る状態を作る
   （`tile_versions`を持つ系統を用意し、全レイヤーONで載ることを見る）。

## 完了条件

- `testing.md`に、E2Eの対象と対象外が観点として書かれている
- 既存の各テストが、その観点のどれを見ているかを言える（言えないものは消す）
- 共通フィクスチャに「判定対象になる値」が1つも無い
- 観点2・3のテストが、わざと壊した入力で落ちることを確認済み
- 手元での走らせ方が`testing.md`に書かれ、実際に通っている

## 段階C（2026-09-23）

### 観点3: Tailwindの余白ユーティリティがリセットに潰されない（`e2e/cascade.spec.ts`）— 入れた

- 母集団: デスクトップの初期画面に在る、Tailwindの余白ユーティリティ（`p-2`・`px-[0.9rem]`・
  `-mt-1`の形。`sm:`等の変種付きは除く）を持つ要素全部。期待値は、同じ親に置いた試し要素へ
  そのユーティリティの値（`calc(var(--spacing) * N)`か角括弧の中身）を`!important`で与えて
  ブラウザに計算させ、要素の計算後の余白（ユーティリティが効く辺ごと）と突き合わせる。
- 壊した入力: `globals.css`の`* { box-sizing; padding: 0; margin: 0 }`を`@layer base`の外
  （ファイル末尾）へ出した。[run 35826718509](https://github.com/hidakagit/ride-compass/actions/runs/35826718509)で
  このテストだけが落ちた（`px-2`の8pxと`py-1`の4pxが0pxに潰れた、ボタン2個×4辺）。
  壊していない側は[run 35825965232](https://github.com/hidakagit/ride-compass/actions/runs/35825965232)・

## 段階Dへの追加（2026-09-23、ユーザー承認）: 走査の母集団に画面と状態を含める

段階Cの観点2（ピンチ）・観点3（カスケード）は、確かめる要素を性質で画面から集める

手で選んでいる。要素は性質で集めても、画面と状態を手で選んでいる限り、選ばなかった状態

1. アプリの状態（画面 × 開いているシート・パネル × 幅 × モード）を母集団にする。**状態の一覧を

2. 観点1〜3の走査（収まる・押せる／ピンチ等の既定動作／カスケード）を、その全状態へ当てる。

3. 全状態へ当てた結果、新たに落ちたものは欠陥として起票する（テストを緩めて通さない）。
4. CIのe2eの所要が状態の数に比例して伸びるので、増分を実測して記録する。

### 1回目が落ちた原因: standaloneサーバーが`localhost`で待ち受けない（開発機のGit Bashだけ）

`.next/standalone/server.js`（Next.jsのビルド成果物）は待ち受けるアドレスを`process.env.HOSTNAME || '0.0.0.0'`で決める。
Git Bashの`/etc/profile`は`HOSTNAME`へ機械名を入れて**export**し（`export … HOSTNAME …`の行）、機械名はこの開発機では
IPv6のグローバルアドレスへ解決される。`netstat`で待ち受けは`[2404:…]:3100`だけで、`localhost:3100`（`::1`・`127.0.0.1`）
への接続は拒否され、webServerの起動待ち60秒で全件が落ちた。CI（ubuntuの非ログインbash）は`HOSTNAME`をexportしないため
既定の`0.0.0.0`で待ち受け、差が出ない。

**直し方**: `playwright.config.ts`の`webServer.env`へ`HOSTNAME: "localhost"`を足す（1行）。これで2回目の9本・走査1本が
通り、CIも成功した（作業ブランチ`orch/E-local`の`920bb786`、[CI run 35847534288](https://github.com/hidakagit/ride-compass/actions/runs/35847534288)、
約10分）。ただし全状態の走査の効率化（[T1078](T1078.md)）が`frontend/e2e/`と`playwright.config.ts`を触るため、
司令塔の指示でこの修正は**コミットから外し、masterへは入れていない**。**T1078へ渡す事項**:
開発機で`npm run test:e2e`を通すには、この`HOSTNAME`の固定（または同等）が要る。
