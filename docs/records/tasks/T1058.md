# T1058. 並行実行の作業ブランチでもCIを動かし、重い検査を手元から外す

状態: 完了（2026-09-23）

## 背景

並行実行では重い検査（tsc・vitest・pytest・next build・playwright）が手元の開発機1台に集中し、待ち時間の大半になっていた（T1049第1回、T1057）。リポジトリはpublicで、GitHub公式（docs.github.com/en/billing/concepts/product-billing/github-actions）によればpublicリポジトリの標準GitHubホストランナーは無料・分数の上限なし（月2,000分はFreeプランのprivateリポジトリの枠）。残る制限は同時ジョブ20本・1ジョブ6時間等（docs.github.com/en/actions/reference/limits）。2026-09の実行は課金対象0分（実行時間1,331分以上）を実測で確認した。ユーザー決定（2026-09-23）:「作業ブランチでもCIを動かす方向で進めて。将来商用化してprivateになる時にはまたルールを変える」。

対応方針:
1. ワークフローの起動条件: ci.yml と docs-consistency.yml を、master に加えて並行実行の作業ブランチ（orch/**）へのpushでも動かす。deploy-backend.yml は master のみのまま（本番デプロイは監査後の master だけ）。
2. pre-push: master 以外（orch/**）へのpushでは重い検査（tsc・prettier・docs検査等）を省き、CIに任せる。master へのpushの門は今のまま。省く範囲を変えたら、壊した入力で master 側の門が今も止まることを1件確かめる。
3. 規約: docs/conventions/orchestration.md「エージェント共通ルール」を、担当はコミットを orch/<名前> へpushしてCIに回し、報告にCIの結果（run のURLと結論）を添える形へ改める（手元で回すのは静的検査と、書きながら確かめる最小のテストだけ）。司令塔の監査はCIの結果を読む。master へは今どおり司令塔が監査後にまとめてpushする。CLAUDE.md「テスト方針」のCIの記述（「pushのたびに」等）と矛盾しないか確かめ、要れば直す。
4. 無償枠を前提にした設計の見直し: ci.yml・docs-consistency.yml のコメントと設計のうち「無償枠の消費対策」を理由にしたもの（docsだけの変更でCIを飛ばす paths-ignore・cancel-in-progress・ジョブの1本化・chromiumのキャッシュ等）を列挙し、public では理由が成り立たないことを踏まえて、残すなら今も成り立つ理由（所要時間・並列度等）へ書き換え、理由が無いものは消す。
5. private化したときのルール: docs/architecture/ の該当箇所（CI・デプロイの制約を持つ文書）へ「publicである間は分数無制限。privateにしたら月2,000分の枠が効くため、作業ブランチのCIと上記4の判断を見直す」を書く。

完了条件: orch/** へのpushでCIが走り結果が取れること（試験用ブランチで1回確かめ、runのURLを記録）、master 以外へのpushで pre-push の重い検査が走らないこと、master へのpushの門が今も止まること（壊した入力1件）、規約・CLAUDE.md・docs/architecture が新しい流れと一致していること。

## 実施内容

### 1. 起動条件

`ci.yml`・`docs-consistency.yml`の`on.push.branches`を`[master, "orch/**"]`にした。公式の
workflow-syntax（`on.push.branches`）では、パターンはrefの名前へglobで当たり、`**`は`/`を
またぐ。`branches`と`paths-ignore`を両方書くと両方を満たしたときだけ走る。`deploy-backend.yml`は
触っていない（`branches: [master]`のまま）。

### 2. pre-push

`.githooks/pre-push`は、gitが標準入力で渡すリモートrefが`refs/heads/orch/*`の行を範囲から外し、
全行がそうなら停止ファイルの確認だけで`exit 0`する。**省く対象は「master以外」ではなく
`orch/**`だけ**にした——CIが走るのは`orch/**`だけで、それ以外のブランチへのpushで検査を省くと、
どこでも検査されない経路ができる。標準入力が無い手動実行は従来どおり全部を検査する。

### 3. 規約

- `docs/conventions/orchestration.md`「完了とpush」: 「pushしない」を「masterへはpushしない。
  `orch/<名前>`へ`git push origin +<sha>:refs/heads/orch/<名前>`でpushし、CIの結論を待ち、
  緑になってからrunのURLと結論を添えて報告する」へ改めた。認証なしのGitHub APIは接続元IPごとに
  1時間60回（公式 rate-limits-for-the-rest-api）で、開発機の全エージェントとpre-pushの警告が
  同じ枠を使うため、問い合わせの間隔も書いた。
- 同「重い処理は機械全体で1本ずつ」: `orch/**`へのpushは重い処理に数えない。
  「重い処理を減らす」: 確かめる検査はCIへ回し、手元は静的検査と最小のテストまで。
- 同「完了時の監査」: 監査の項目に「CI」（止め）を足した。`scripts/orchestrate.py audit`が
  報告のshaに対するワークフローごとの最新の実行を読み、失敗・結論待ち・実行が無い・取得できない
  を指摘にする（`scripts/check_master_ci.py`の取得と絞り込みを`latest_per_workflow`・
  `is_failure`として切り出して再利用）。回の終わりに作業ブランチを消す手順も足した。
- CLAUDE.md「テスト方針」のCIの記述（`ci.yml`がpushのたびに）と「完了扱いにする前に検査器を通す」
  のpre-push・docs-consistencyの記述を、`orch/**`を含む形へ直した。
  `docs/conventions/testing.md`のmasterのCIの警告は`orch/**`へのpushでは出ない旨を足した。

### 4. 無償枠を理由にした設計の列挙と判断

`grep -rn "無償枠" .github/`で母集団を出した（ci.yml 5か所・docs-consistency.yml 1か所。
`deploy-backend.yml`の`cancel-in-progress: false`はデプロイの直列化で、無償枠が理由ではない）。
所要は2026-09-23のmasterの実行（run 35817036261・35816112562、キャッシュ外れは35649077944）の
ステップ時間を公開APIで読んだ。

| 設計 | 判断 | 根拠 |
|---|---|---|
| `paths-ignore`（docs/**・*.md） | 残す。理由を書き換え | ci.ymlのどの検査もdocs・mdを読まない（`backend/tests`・`frontend/src`でdocs配下を開く箇所をgrepし0件。参照はコメントだけ）。結果が変わらない実行を起こさない。文書はdocs-consistency.ymlが見る |
| `concurrency` + `cancel-in-progress: true`（両ワークフロー） | 消す | 同じブランチの前のコミットの結論が消える。監査は報告のshaごとの結論を読むため、打ち切りは監査の材料を消す。実例: masterの561faee0のDocs Consistencyがcancelled（run 35813739923）で、そのコミットの結論が無い |
| ジョブの1本化（backend＋API契約） | 分ける（`api-contract`ジョブを新設） | 実行全体の終わりはbackendジョブ（108〜124秒）が決めていて、その中の契約検査部分（setup-node 2〜7秒・npm ci 12〜15秒・生成3秒）はpostgresを要らない。分ければ最長のジョブがその分縮む。代償は同時実行の枠を1本多く使うことと準備の二重払い（pip install約23秒・npm ci）だが、枠の上限は並行実行の本数より十分大きい。`directory-layout.md`が既に`api-contract`ジョブと書いていた記述とも一致した |
| chromiumのキャッシュ | 消す | 外れたとき（install --with-deps 22秒＋保存4秒）と当たったとき（復元2〜5秒＋install-deps 12〜14秒）の差は約7〜12秒で、e2eジョブ（70〜97秒）は最長のジョブではないため実行全体の終わりを動かさない。条件分岐2ステップとキャッシュ1ステップを1ステップにした |

### 5. private化したときのルール

`docs/architecture/tech-stack.md`に「CIの実行枠（リポジトリがpublicである間の前提）」節を新設。
publicの間は課金も分数の上限も無いこと（公式の課金ページ）、残る制約（公式の制限ページ）、
その前提で組んだもの（作業ブランチのCI・打ち切らない・ジョブの分け方）、privateにしたら月2,000分で
支払い方法が無ければ止まること（同じ課金ページ）、切り替え前に見直す項目を書いた。

### 追加（2026-09-23、ユーザーの指示）: OSで結果が変わるテスト入力

T1020のテストが`r"C:\venv\Scripts\uvicorn.exe"`を入力にしていて、Windowsでは通り、Linuxの
CIで落ちてmasterが赤になった（6c982337。修正は08fef74aで`str(Path("venv") / "Scripts" /
"uvicorn.exe")`へ）。司令塔がテストのうちOS固有の書き方を持つものを機械的に数えた結果は
この1件だけだった。

`docs/conventions/testing.md`へ「パターン10: 期待値が実行環境（OS）で変わる入力を使わない」を
足した。書く人が守るルールで機械では確かめられないため、効かせるのは本タスクの「作業ブランチの
CI（Linux）の結論を監査で読む」流れの方である。その関係を、testing.mdのパターン10と
orchestration.md「完了とpush」の両方に書いた（masterへ入れてよいかの最終判定は作業ブランチの
CIの結論）。
