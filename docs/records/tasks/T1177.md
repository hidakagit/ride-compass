# T1177. backend の横断部品（回数制限・リクエストID・定期ジョブの失敗の記録）を定番の部品へ置き換える

状態: 未完了（2026-09-27起票）

## 背景

起票案 proposal-std-backend-middleware（2026-09-27承認。標準の道具の棚卸しから）。規模S（根拠: 回数制限の呼び出し口 check_rate_limit は変えないので、変わるのは rate_limiter.py・request_log.py・main.py・requirements.txt・test_rate_limiter.py・test_request_log.py・test_main_lifespan.py の7本の見込み）

■ 背景（画面に出ない、backend内部の話）
- 回数制限（infrastructure/rate_limiter.py）: 利用者ごとの時刻の記録から数える移動窓と、使われなくなったキーの掃除を自前で持つ。limits（MovingWindowRateLimiter と MemoryStorage）が同じことをし、期限切れの掃除もする。なお、コメントと docs/modules/backend/cross-cutting-infrastructure.md は「固定窓」と書いているが、実装は移動窓で、記述が実装と違う。
- リクエストID（infrastructure/request_log.py の一部、約30行）: X-Request-ID の引き継ぎと発行、ログへの付与、応答ヘッダへの付与。asgi-correlation-id が同じことをする。今の実装は、クライアントが送った X-Request-ID を長さも文字種も確かめずにログと応答ヘッダへ流しているが、asgi-correlation-id は既定で形式を確かめる。アクセスログのレベルの判定・日本時間の整形・500応答へのヘッダの付与は自前のまま残る。
- 定期ジョブの失敗の記録（main.py の _with_failure_log）: ジョブを1本ずつ包んでいるが、APScheduler のイベントの受け口（EVENT_JOB_ERROR）で同じ名前のロガーへ出せる。
自前にした理由は、どれも書かれていない（回数制限は「プロセス内に置く」理由だけ）。

■ やること
3つを置き換える。テスト規約の「回数制限の境界値は check_rate_limit を直接呼んで埋める」は、関数の口を保つのでそのまま使える。見込み 実装 約−60行、テスト 約−90行。依存は limits・asgi-correlation-id の2本が増える。
