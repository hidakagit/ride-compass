# T1177. backend の横断部品（回数制限・リクエストID・定期ジョブの失敗の記録）を定番の部品へ置き換える

状態: 完了（2026-09-27起票・完了）

## 背景

起票案 proposal-std-backend-middleware（2026-09-27承認。標準の道具の棚卸しから）。規模S（根拠: 回数制限の呼び出し口 check_rate_limit は変えないので、変わるのは rate_limiter.py・request_log.py・main.py・requirements.txt・test_rate_limiter.py・test_request_log.py・test_main_lifespan.py の7本の見込み）

■ 背景（画面に出ない、backend内部の話）
- 回数制限（infrastructure/rate_limiter.py）: 利用者ごとの時刻の記録から数える移動窓と、使われなくなったキーの掃除を自前で持つ。limits（MovingWindowRateLimiter と MemoryStorage）が同じことをし、期限切れの掃除もする。なお、コメントと docs/modules/backend/cross-cutting-infrastructure.md は「固定窓」と書いているが、実装は移動窓で、記述が実装と違う。
- リクエストID（infrastructure/request_log.py の一部、約30行）: X-Request-ID の引き継ぎと発行、ログへの付与、応答ヘッダへの付与。asgi-correlation-id が同じことをする。今の実装は、クライアントが送った X-Request-ID を長さも文字種も確かめずにログと応答ヘッダへ流しているが、asgi-correlation-id は既定で形式を確かめる。アクセスログのレベルの判定・日本時間の整形・500応答へのヘッダの付与は自前のまま残る。
- 定期ジョブの失敗の記録（main.py の _with_failure_log）: ジョブを1本ずつ包んでいるが、APScheduler のイベントの受け口（EVENT_JOB_ERROR）で同じ名前のロガーへ出せる。
自前にした理由は、どれも書かれていない（回数制限は「プロセス内に置く」理由だけ）。

■ やること
3つを置き換える。テスト規約の「回数制限の境界値は check_rate_limit を直接呼んで埋める」は、関数の口を保つのでそのまま使える。見込み 実装 約−60行、テスト 約−90行。依存は limits・asgi-correlation-id の2本が増える。

■ なぜ既存のタスクに入らないか
該当する未完了のタスクは無い。

## 着手時の確認（2026-09-27、担当 B-mw）

- **新しい依存の条件**: `asgi-correlation-id` 5.0.1（MIT、Python>=3.10、依存は`starlette>=0.18`だけで、
  今の`fastapi==0.115.6`が引くstarlette 0.41.3の範囲に入る）。`limits` 5.8.0（MIT、Python>=3.10、依存は
  `deprecated`・`packaging`・`typing-extensions`）。どちらもPyPIのメタデータ（`License-Expression`）で確かめた。
  版の制約（`docs/architecture/tech-stack.md`）はPythonの版がDockerfileの3.12であることだけで、両方とも入る。
- **回数制限の前提が違った**: 起票案の「limits（MovingWindowRateLimiter と MemoryStorage）が期限切れの掃除もする」は
  半分だけ正しい。`limits/storage/memory.py`の`__expire_events`（5.8.0、GitHubのmasterも同じ）は各キーの古い
  記録を切り詰めるが、空になったキーを`events`から消さない。手元の実測（`MovingWindowRateLimiter`＋`MemoryStorage`へ
1秒窓でN本のキーを1回ずつ入れ、1.5秒待ってから`__expire_events`を1回呼んだ所要。開発機）:
  期限切れのキーが1,000本→全部残り掃除1回2.4ms、1万本→39.5ms、10万本→1,186ms。掃除は問い合わせのたびに
  10ms後へ予約され、全キーを回る。今の自前の実装が5分おきにキーごと消しているもの（接続元を変えながらの
  連打で辞書が伸び続けること）が戻る。置き換えるかどうかは利用者の判断が要るので、回数制限だけを段階Bとして
  止め、ダッシュボードへ問いとして置いた。
- **記述の食い違い**: 「固定窓」の記述（`rate_limiter.py`のコメント・`test_rate_limiter.py`の説明・
  `docs/modules/backend/cross-cutting-infrastructure.md`・`docs/architecture/api-design.md`）は、実装が移動窓なので
  段階Aで「移動窓」に直した（段階Bの答えによらず正しい）。
- **ついでに見つけた文書の古さ**: `docs/conventions/logging.md`は、フロントが失敗の文言に`（req: xxx）`を含めると
  書いていたが、今の`frontend/src/lib/fetchJson.ts`は画面の文言にIDを混ぜずDebugConsoleにだけ残す。同じ節を
  直すので段階Aで直した。

## 段階A: リクエストIDと定期ジョブの失敗の記録

- **リクエストID**: `asgi_correlation_id.CorrelationIdMiddleware`（既定の設定のまま）を`main.py`で最も外側に登録し、
  `request_log.py`からIDの引き継ぎ・発行・応答ヘッダ・contextvar・ログのフィルタを消した。ログ行へは
  `CorrelationIdFilter(default_value="-")`が入れ、書式とフィルタを付ける口は`request_log.format_log_lines`の1か所
  （標準出力とリングバッファが使う）。500応答へのヘッダは`unhandled_exception_handler`が`correlation_id`から
  読んで付ける（ミドルウェアはcontextvarを巻き戻さないので、`request.state`に写す必要が無くなった）。
  挙動の差: 発行するIDが12桁から32桁の16進になる。クライアントが送ったIDはUUIDの形のときだけ引き継ぎ、
  違えば作り直す（`asgi_correlation_id`ロガーがWARNING）。画面では、DebugConsoleの`requestId`の桁だけが変わる
  （利用者向けの文言にはIDを出していない）。
- **定期ジョブの失敗**: `_with_failure_log`の包みを消し、lifespanでスケジューラへ`EVENT_JOB_ERROR`の受け口
  `_log_job_failure`を付けた。失敗はAPSchedulerが`apscheduler.executors.default`へスタックトレース付きERRORで出し、
  受け口が`ridecompass.scheduler`へジョブidと例外の1行WARNINGを出す。以前はジョブごとのロガー名とラベルで
  WARNING（トレース付き）だった。
- **テスト**: `test_request_log.py`はIDの長さ（12桁）とフィルタ単体のテストを消し、アクセスログの行に応答と
  同じIDが載ることを入口（本物のアプリ）で見る形にした。クライアントのIDはUUIDの形で送る。
  `test_main_lifespan.py`の包みの単体テストは、起動したアプリのスケジューラで失敗させたジョブが
  `ridecompass.scheduler`にWARNINGで残ることを見るテストへ置き換えた。

## 問いと答え: 回数制限の置き換え方（2026-09-27）

- **問い**（担当 B-mw、ダッシュボード T1177-rate-limiter-keys）: 回数制限を定番の部品（limits）へ置き換えると、
  来なくなった接続元の記録が消えずに溜まる。どうするか。選択肢 (1) 片付けだけを、既に使っている期限つきキャッシュ
  （cachetools）に任せる。自前の掃除のコードは消え、回数の数え方の数行だけ自前に残る。新しい依存は増えない
  （推奨） (2) 起票案どおり limits へ置き換え、記録が再起動（デプロイ）まで溜まることは受け入れる
  (3) 置き換えず、今の自前の仕組みのままにする。
- **答え**（ユーザー、2026-09-27）: (1)。
- **司令塔の指示**: `rate_limiter._hits`を直接触っているルートのテスト（accident・amedas・basemap・gsi・jma・region・
  routes_generate・weather）は、内部の辞書を触らずに公開の入口で数える形へ直す。

## 段階B: 回数制限の記録の片付けを cachetools へ任せる

- **実装**: 記録を`cachetools.TTLCache`（期限＝窓の長さ60秒、件数の上限10万）に置き、`check_rate_limit`は窓に入る
  時刻を数えて通したら書き戻す（書き戻しで期限が最後の1回から数え直しになる）。自前の掃除（`_sweep`・
  `_SWEEP_INTERVAL_SECONDS`・`_last_sweep`）と、呼び出し元がどこも渡していなかった引数`window_seconds`を消した。
  limits を使わない理由と、ロックを持たない前提（呼び出し元がすべてイベントループ上のasyncハンドラ。`check_rate_limit`の
  呼び出しは`enforce_rate_limit`の1か所だけで、ルーターからの`enforce_rate_limit(`16か所は15か所がasync defの中、
  残る1か所は同期の`region.py: _check_tile_rate_limit`の中で、その呼び出し元4か所がすべてasync def——grepとASTで数えた）は`docs/modules/backend/cross-cutting-infrastructure.md`
  「回数の記録」節へ書いた。
- **件数の上限の根拠**（開発機、`tracemalloc`）: 接続元が1回ずつ入れ替わる形で1万件3.5MB・10万件39.4MB、
  10万件×10回で70.6MB、1万件×300回（basemapの上限）で99.6MB。本番コンテナの上限6GBに対し、1回ずつの形の10万件で1%未満。
- **消えることの確認**（使い捨てのスクリプト、本物の`check_rate_limit`へ偽の時計を当てた）: 接続元1万件を入れて窓を
  出た次の1回で残りが2件（その1回10.3ms、次の1回0.023ms）。10万件で同じく2件（その1回185.4ms、次の1回0.037ms）。
  消す手間は1件につき1回で、見回りを繰り返さない（limits の MemoryStorage は同じ10万件で1回1,186msの見回りを
  10msおきに繰り返す。着手時の確認の実測）。
- **テストの片付け方**: 公開の入口だけでは、前のテストが数えた回数を消せない（`TestClient`の接続元は常に
  `testclient`でキーが変えられず、上限まで数え切る形だけにすると、後のテストが同じ窓の中で429を受ける）。そこで
  回数制限が読む時計（プロセス境界）を`conftest.py`がセッションの間だけ止めた時計へ替え、autouseの
  `rate_limit_clock`がテストごとに1窓ぶん進める。記録そのものには触らない。途中で実時計へ戻すと、進めた時計で
  数えた回数が未来の時刻として窓に残るため、戻すのはセッションの終わりだけにした。8本の消し込みのフィクスチャと
  `_hits`の差し替え2か所を消した。`test_rate_limiter.py`は同じ時計を進める形にし、掃除を見る2本（内部の辞書を
  読んでいた）を消して、窓を出た分だけが空く（移動窓）ことを見る1本を足した。
- **効いていることの確認**: `rate_limit_clock`の`advance`を外すと、`test_rate_limiter.py`・`test_weather_route.py`・
  `test_routes_generate.py`で18件が落ちた（前のテストの回数が食い込む）。戻して165件が通る。
