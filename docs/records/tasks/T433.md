# T433. ルート結果の色分けモード既定値のハードコードを解消 規模S

状態: 完了（2026-08-30）

- 背景: `routeStyleModes.ts`の`DEFAULT_ROUTE_STYLE_MODE_ID`が固定文字列`"wind"`として
  ハードコードされており、axis-catalog由来の動的モード（`supports_route_coloring`を持つ
  軸、現状はwindのみ）が実行順序として`ROUTE_STYLE_MODES`配列の先頭に来ることへ暗黙に
  依存していた。バックエンド側でwindの`supports_route_coloring`をfalseにする、または
  軸自体をunpublishすると、この定数だけが古い値のまま残り、`getRouteStyleMode`の
  「見つからなければ`modes[0]`」フォールバックにより実際の初期選択（gradient等）と
  定数の値が静かに食い違う（2026-08-30のゼロベース網羅レビュー
  [docs/zero-base-review-2026-08-30.md §4]で指摘済み、[T425](T425.md)/[T426](T426.md)の
  対応候補の1つ）。ユーザーからも「ルート結果の中の、生成したルートの色分けが固定要素な
  のをいい加減直して」と直接指摘を受けた。
- 対応方針: `DEFAULT_ROUTE_STYLE_MODE_ID`を固定文字列ではなく`ROUTE_STYLE_MODES[0].id`
  から導出する形へ変更した。`STATIC_MODES`（gradient/road/difficulty）は常に非空のため
  `ROUTE_STYLE_MODES`が空になることはなく、`[0]`は必ず存在する。これにより
  dynamicModes（axis-catalog由来）が1件も無くなった場合でも、`STATIC_MODES`の先頭
  （gradient）へ自動的にフォールバックし、定数と実際の配列内容が構造的に一致し続ける
  （二重管理の解消）。

## 実装メモ

- `frontend/src/components/Map/routeStyleModes.ts`: `DEFAULT_ROUTE_STYLE_MODE_ID`の定義を
  `"wind"`（リテラル）→`ROUTE_STYLE_MODES[0].id`（導出）へ変更。
- `frontend/src/components/Map/routeStyleModes.test.ts`: 導出元との一致を検証するテストを
  追加（`DEFAULT_ROUTE_STYLE_MODE_ID`が`ROUTE_STYLE_MODES[0].id`と一致することを確認）。
  既存の「デフォルトは風」のテストは、現状の並び（wind→gradient→road→difficulty）では
  引き続き"wind"のままなので変更していない。
- 検証: `tsc --noEmit`・`routeStyleModes.test.ts`（9件）・`page.test.tsx`（13件）・
  eslintいずれも通過。
- 見送った点: `getRouteStyleMode`の「見つからなければ`modes[0]`」フォールバック自体
  （localStorageの古い値等、正当なケースで発生しうる無警告フォールバック）は今回の
  「固定要素」という指摘の対象外と判断し変更していない。
