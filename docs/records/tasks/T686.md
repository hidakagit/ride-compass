# T686. 軸スタジオで折れ点の効き方を実データの分布として見せる 規模M

状態: 完了（2026-09-09）

## 背景

停止密度の軸（[T655](T655.md)）を較正する際、折れ点`[[0,0],[2,25],[4,50],[7,75],[12,100]]`が
妥当かどうかを軸スタジオの画面からは全く判断できず、本番タイルを1,060km分デコードして
「この折れ点だと延長の何%がどの得点帯に入るか」を手で測る必要があった。結果として
最初の較正は外れており（本番の92.3%が満点に張り付く／逆に伸ばしすぎてルート値が10に
潰れる）、実データを測って初めて分かった。

**軸スタジオは数値の入力欄をDBの構造どおり並べているだけで、判断を助けていない。**
利用者は勘で入れるしかなく、公開して地図とルートを見るまで結果が分からない。
「DBへ直接INSERTした方が楽」という感想はここから来ている（ユーザー指摘、2026-09-08）。

## 対応方針

折れ点を編集している最中に、**その折れ点で実データがどう分布するか**を画面に出す。
併せて、材料の値域を選択時点で見せること・公開済み軸の調整を1操作にすることも行う
（前者は折れ点をどこへ置くかの当たりを付けるため、後者は「調整のたびに5手」が
使いにくさの直接の原因だったため）。

## 実施内容

### 1. 折れ点の効き方を得点分布として見せる

折れ点の曲線エディタの下に、その折れ点で実データの延長が得点帯へどう散らばるかを出す。
満点への張り付きが半分を超える・0点が9割を超える場合は警告を添える。

**backendは折れ点を通す前の生値のヒストグラムだけを返し、折れ点の当てはめはfrontendの
純関数が行う**。折れ点を1つ動かすたびに通信すると編集の手応えが失われるうえ、折れ点は
区分線形の写像でしかなく、生値のヒストグラムがあればクライアントで正確に求まる。
取得のキーに折れ点を含めないため、ドラッグ中は通信しない。

母集団はWay単位（`osm_raw_ways`のページ単位抽選）で、**延長で重み付ける**。本数で数えると
短い道が多数を占めて実際に走る距離の感覚と合わない。

効果の実証: [T655](T655.md)の較正前の構成（`stop×1.0 + 交差点×0.3`、折れ点`4→100`）を
プレビューへ掛けると`0点=0.0% 中間=5.4% 100点=94.6%`と出る。本番タイルを1,060km分
デコードして手で出した結論（92.3%）とほぼ同じ数字が**1秒**で得られる。

| | 所要 |
|---|---|
| 初回（Wayの抽選＋材料の組み立て） | 1.0秒 |
| 2回目以降 | 0.00秒（`TTLCache`） |

### 2. 材料の値域を選択時点で見せる

材料選択行の下に、その材料が実データで取る値の分位（p50/p75/p90）とゼロの割合を出す。
カタログの`reference_points`はコードに書いた代表値で、実データの分布ではない。
取得できないときは何も出さない（編集の補助情報のため、他の欄の編集を妨げない）。

### 3. 公開済み軸の調整を1操作にする

公開済み軸の材料・計算式・折れ点を変えるには`check_publish_immutability`により一度
下書きへ戻す必要がある。「調整する」ボタンがその手順（非公開化→編集→保存時に再公開）を
畳む。**編集を中断した場合は下書きのまま残るため、その事実を必ず知らせる**——黙って
非公開になると、一般ユーザー向けの軸カタログから消えたことに気づけない。

### 副産物: 手書きの材料辞書が1箇所減った

区間インスペクタが材料を手書きの辞書で組み立てていた箇所を`way_scalar_materials`として
切り出し、分布プレビューと共有した。[T655](T655.md)で問題にした「材料を1つ足すと複数箇所を
直す」の残り1箇所がこれだった。

## 完了条件

- 折れ点を編集すると、その折れ点での得点分布が画面に出ること
- 明らかに外れた折れ点（延長の大半が満点に張り付く等）で警告が出ること
- 折れ点のドラッグ中に通信が走らないこと
- 公開済み軸の材料・折れ点を、複製を経ずに調整できること

## 残した論点

ルート結果で「32.5kmで26回止まります」のような**実数**を出す案は本タスクに含めない。
[T655](T655.md)で分かったとおり、ルート全体の軸値は目盛りをどう引いても自己打ち消しで
低いままになるため、走る人向けの表示は別の手当てが要る。本タスクは**軸を作る人**のための
道具であり、走る人の体感の問題は解かない。
