# T1179. 並行作業の道具が読むプロセス一覧とCPU使用率を、OSのAPIの直接呼び出しから psutil へ置き換えるか、標準ライブラリだけで書く方針を文書にする

状態: 完了（2026-09-27）

## 背景

起票案 proposal-std-procs-psutil（2026-09-27承認。標準の道具の棚卸しから）。規模S（根拠: 変わると見込むファイルは procs.py・core.py・lockrun.py・slots.py の4本）

■ 背景（画面に出ない、並行作業の道具の話）
scripts/orchestration/procs.py（121行）は Windows の API（プロセスのスナップショット・コマンドラインの読み取り）を ctypes で直接呼び、Linux では /proc を自前で解析する。core.py の cpu_percent（31行）も同様。書かれている理由は「飽和した機械へプロセスを足さないため、外部コマンドを起こさない」だが、psutil はプロセス内で動くのでこの理由は当たらない。「scripts/ は標準ライブラリだけで書く」という方針は記録（T560。review_checks について）にしか無く、生きた文書には無い。

■ 決めてほしいこと
①psutil へ置き換える（約−130行。代わりに、道具を動かすシステムの Python と、クラウドのセッションの両方へ psutil を入れる手順が要る）／②標準ライブラリだけで書く方針を残す（方針と理由を docs/conventions/orchestration.md へ書き、procs.py はそのまま）。

■ なぜ既存のタスクに入らないか
T1148 は procs.py がどの文書にも名前が出ないことを1件含むが、範囲は書式と依存の向きで、実装の置き換えは含まない。ロックをOSのファイルロックへ置き換える起票案が先に入ると、procs.py の使い道のうち「ロックの破棄の記録」が無くなる。

■ 前提の変化（T1185、2026-09-27）
ロックはOSのファイルロックへ置き換わり、lockrun.py は procs.py を使わなくなった（「ロックの破棄の記録」は無くなった）。procs.py の使い手は core.py（定期確認の枠の外の重い処理・枠の保持者の生死）と slots.py（温める処理の生死）。変わると見込むファイルから lockrun.py が外れる。

## 問いと答え

起票案の承認は「承認」だけで、①②のどちらかは決まっていなかった。着手時（担当 P-psutil）に問いとしてダッシュボードへ置いた:

- 問い: 並行作業の道具が「いま動いているプロセスの一覧」と「CPUの混み具合」を読む部分を、定番の部品（psutil）へ置き換えるか。
  選択肢1（担当の推奨）は置き換えずに理由を規約へ書く。推奨の理由は、道具はフック（エージェントを起動するときの
  スロットを渡す処理・定期確認）からシステムのPythonで動くので、psutilの入れ忘れで起動そのものが止まりうること、
  `scripts/`には部品を宣言する置き場が無いこと、T1185が同じ理由で filelock でなく標準の機能を選んだこと。
  選択肢2は置き換える。
- 答え（ユーザー、2026-09-27）: **(2) 置き換える**。「入れ忘れると起動が止まる」は置き換えない理由として認めない。
  入れ忘れは宣言と止め方で防ぐ。成熟した道具があれば使うのが方針。開発機のシステムのPythonへはpsutil 7.2.2を
  入れ済み（司令塔が`python -c "import psutil"`で確認）。

## 方針

- psutilを読むのは`scripts/orchestration/procs.py`だけにする。定期確認（core.py）のCPU使用率も`procs.cpu_percent`へ
  移す。core.pyは`review_checks.py`（docs-consistencyのCI。部品を入れない）と`new_task.py`からもimportされるので、
  core.pyからprocsを読むのは使う関数の中だけのまま（モジュールの先頭で読むと、それらもpsutilを要するようになる）。
- 自前のOS呼び出し（Windowsのtoolhelp・NtQueryInformationProcess・GetSystemTimes、Linuxの`/proc`の解析）と、
  それを前提にした分岐（`processes()`がNoneを返す経路、それを受けた「取れなければファイルのまま」「確かめられなければ
  生きているとみなす」「一覧が取れなければ空」）を消す。psutilは開発機（Windows）とCI（Linux aarch64）の両方で
  一覧を返すので、「取れないOS」は無くなる。コマンドラインが権限で読めないプロセス（`cmdline`がNone）の扱いは残す。
- **宣言の置き場は`scripts/requirements.txt`**。理由: 道具は`scripts/`の中にあり、pipの標準の形
  （`python -m pip install -r scripts/requirements.txt`）で入れられる。backendの`requirements*.txt`はbackendの
  イメージとCIの依存で、道具はbackendのvenvではなくシステムのPythonで動くため、そこへ混ぜない。CIのテスト
  （`backend/tests/test_orchestration_*.py`が道具を動かす）へは、`backend/requirements-dev.txt`が
  `-r ../scripts/requirements.txt`で同じファイルを取り込む（pipは入れ子の`-r`を、書いたファイルからの相対で解く。
  pipの`req_file.py`で確認）。版は他のrequirementsと同じく固定する。
- **止め方**: `procs.py`の先頭でpsutilのimportに失敗したら、`SystemExit`で入れ方の1行を出して止まる（例外の積み上げを
  出さない）。止まるのはpsutilを読むコマンド（門・状態・定期確認・スロットの全コマンド。WorktreeCreateフックを含む）で、
  読まないコマンド（監査・状態の表の読み書き・ダッシュボード・台帳）は入っていなくても動く——クラウドの担当が監査を
  自分で通せるように。
- ライセンス: psutilはBSD-3-Clause（商用可）。7.2.2はabi3のwheelを`win_amd64`と`manylinux aarch64`で配る
  （PyPIのJSONで確認）。CIのbackendジョブは`ubuntu-24.04-arm`なので、ソースからのビルドにならない。

  `heavy_outside_lock`から一覧がNoneのときの分岐を消した。
- `scripts/orchestration/slots.py`: `process_alive`から一覧がNoneのときの分岐を消した。
- `scripts/requirements.txt`（新設）・`backend/requirements-dev.txt`（取り込み）・`.github/workflows/ci.yml`（pipの
  キャッシュの鍵へ足す）・`scripts/remote_dev/lib.sh`（クラウドのセッションのvenvのダイジェストへ足す）。
- `backend/tests/test_orchestration_slots.py`: psutilが読めないPython（`PYTHONPATH`の先頭に、importで失敗する
  `psutil`を置く）で、WorktreeCreateフックと同じ起動役からスロットを渡させ、入れ方の1行が出て例外の積み上げが
  出ないことを見るテストを1本足した。
- `docs/conventions/orchestration.md`「環境」節: 宣言の置き場・入れ方・入っていないときに止まるコマンドと止まらない
  コマンド・CIへの取り込みを書いた。
- 開発機のbackendのvenvへ`python -m pip install -r scripts/requirements.txt`でpsutil 7.2.2を入れた（ローカルで
  `test_orchestration_*.py`を走らせるため。取り込んだあと、他のvenvでも同じコマンドで入る）。
