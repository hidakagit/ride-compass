# T537: 探索用グラフ・索引（LazyRoadGraph/routable集合/空間索引/Node対索引）をタイル集合キーでキャッシュする

状態: 完了（2026-09-02起票、[T522](T522.md)「評価ロジック全体の再点検」で判明。同日、
案aで実装・テスト・ローカル/dev DB速度サニティチェックまで完了。本番Oracle VMの
使い捨てコンテナ（東京駅30km・split済み条件）で同一エリアへ2回連続実測し、
`graph_ms+index_ms`が2,125ms→3ms（完了条件の500ms未満を達成）まで短縮したことを確認、
masterへマージ・push・本番反映済み）

- 背景: `RoadGraphEngine.prepare`は毎リクエスト、タイルキャッシュから結合したグラフに
  対して`build_lazy_road_graph`（957ms）・`compute_routable_node_ids`（726ms）・
  `build_node_spatial_index`（201ms）・`_build_node_pair_index`（165ms）を作り直しており、
  温パスのprepare約2.4秒（本番VM実測、東京駅30km・Edge 477,320件）のほぼ全てを占める。
  これらはタイル集合と0次フィルタ（`hard_filters`・`max_average_grade_percent`）だけで
  決まる純粋な派生物で、bboxは起点と距離から機械的に決まるため、同じ起点はもちろん
  近隣の起点でも同じタイル集合を共有する。
- 対応方針（2案、着手時に選ぶ）:
  - 案a（実装最小）: `frozenset(タイル集合)`（routable集合は＋0次フィルタ引数）を
    キーにしたプロセス内LRUへ4つの派生物を載せる。`graph_material_cache`と同じ寿命・
    無効化（軸定義変更は無関係、材料再取込はプロセス再起動）。メモリは同時に数件で
    足りる。
  - 案b（根本）: タイル読込時にNode/Edgeを1つのグローバルな`PyDiGraph`へ差分追加し
    （タイル境界をまたぐEdgeはedge_idで重複排除）、リクエストは結合を一切行わず
    起点・経由地の索引引きと探索だけを行う。空間索引・Node対索引もタイル単位で持ち
    結合する。T536のコスト配列も同じEdge索引に揃える。`graph_material_cache`のLRU
    退避と整合させる設計が必要。
  - どちらの場合も`_build_node_pair_index`は、逆回り候補の経路上のEdgeだけに対する
    遅延引き（`graph.edges`から`(to,from)`を逆引き）で代替できるため、全Edge分の
    索引自体を廃止してよい。
- 関連: [T536](T536.md)（独立に着手可能。両方入れば温パスは
  prepare約0.4秒＋探索約0.7秒＋評価約0.4秒＋ジオメトリ取得の見込み）。
- 完了条件: 本番同一条件で`prepare`の索引・グラフ構築ログ（`graph_ms`・`index_ms`）が
  2回目以降のリクエストで合計500ms未満、既存の`test_road_graph_engine.py`・
  `test_route_generator.py`が無修正でpass、`docs/modules/`の該当設計書を同一コミットで更新。

## 実装（2026-09-02）

### 案の選択: 案a（実装最小）を採用

着手時に判断した。理由:

- 案b（グローバル`PyDiGraph`への差分追加）は、`graph_material_cache`のLRU退避と
  整合させる設計（退避されたタイルのNode/Edgeをグローバルグラフからも取り除く、かつ
  他のタイルとエッジで共有されているNode/Edgeを誤って消さない）が必要で、実装・
  検証コストが本タスクの規模Mに対して不釣り合いに大きい。
- 案aは、`GraphService.get_search_materials_for_bbox`が既に「bboxを覆う全z12タイルの
  材料キャッシュをそのまま結合したグラフ」を組み立てている（T219）ことを利用し、
  その結合済みグラフに対する派生物（`LazyRoadGraph`・`NodeSpatialIndex`）だけを
  タイル集合キーでキャッシュする——結合ロジック自体（`graph_material_cache`・
  `tile_score_matrix_cache`の退避・鮮度管理）には一切手を入れない。既存の2つの
  タイル単位キャッシュと責務が分離したまま素直に積み重ねられる。
- 完了条件が求める「2回目以降のprepareでgraph_ms・index_msが合計500ms未満」は、
  案aでも達成できる（後述の実測: 2回目以降は0ms）。案bの「結合自体を省く」という
  根本対応が必要になるのは、結合コスト自体（dict.update等のPython処理、T522実測では
  支配的コストとして計測されていない）がボトルネックになった場合であり、現時点では
  その兆候はない。

### 実装内容

1. **`backend/app/infrastructure/search_graph_cache.py`（新設）**: `LazyRoadGraph`用
   （キー=`frozenset[(zoom,x,y)]`）・`NodeSpatialIndex`用（キー=タイル集合＋
   `hard_filters`＋`max_average_grade_percent`）の2本のプロセス内LRU（上限64件、
   `graph_material_cache`より粗い粒度のため小さめ）。無効化方針は`graph_material_cache`
   と同じ「プロセス寿命でのみキャッシュ、明示的な無効化なし」。
2. **`GraphService.get_search_materials_for_bbox`の戻り値を3タプルへ拡張**
   （`SearchMaterials`・`StaticEdgeScoreMatrix`・タイル集合`frozenset[(zoom,x,y)] | None`）。
   タイル集合は、graphが「bboxを覆う全z12タイルの材料キャッシュをそのまま結合したもの」
   （`_build_search_materials_from_tile_cache`経由）の場合のみ設定し、split鮮度が
   古くbbox限定で再構築した経路（`_build_search_materials_uncached`）はNoneを返す。
   Noneの場合、呼び出し側（`RoadGraphEngine`）はsearch_graph_cacheを一切経由しない
   ——このgraphはタイル境界と一致しない不完全な集合のため、そのままタイル集合キーで
   キャッシュへ書き込むと、後続の正規リクエスト（同じタイル集合、完全な集合）へ
   不完全な結果を返しかねない（`graph_material_cache`がこのbboxを書き込まない理由と
   同じ）。
3. **`RoadGraphEngine._build_search_graph`**: `LazyRoadGraph`の構築を
   `_get_or_build_lazy_graph(tile_set, graph)`（新設のモジュール関数）経由にした。
   タイル集合キーでヒットすれば`asyncio.to_thread`自体を経由せず即座に返る。
4. **`RoadGraphEngine.prepare`/`preview_segment`**: `compute_routable_node_ids`→
   `build_node_spatial_index`の2段階を`_get_or_build_node_index`（新設のインスタンス
   メソッド、`self._hard_filters`/`self._max_average_grade_percent`をキーに含める）
   経由にした。両メソッドが同じキャッシュを共有する（`preview_segment`が先に温めた
   索引を`prepare`が再利用できる、逆も同様）。
5. **`_build_node_pair_index`を撤去**。`_reverse_traced_edges`は、キャッシュ済み
   `LazyRoadGraph.edge_index_by_node_pair`（`build_lazy_road_graph`が並行Edge解消と
   同時に構築済み）を経路上のEdgeだけに対する遅延引きとして使う——T537の指示どおり
   全Edge分の索引自体を廃止し、新たな索引も追加していない（既存のlazy_graphの
   フィールドを再利用するのみ）。`_RoadGraphContext.node_pair_index`フィールドも
   撤去した。

### 並行Edge解消規則の変更（設計上のトレードオフ）

`build_lazy_road_graph`は元々、`edge_cost_by_id`引数の有無で2つの並行Edge解消規則を
持っていた: 引数ありなら「cost最小を採用」（T536が復活させたT363の元の意味論）、
引数省略なら「edge_idの昇順で先頭を採用」する決定的フォールバック。

タイル集合キーでキャッシュする`LazyRoadGraph`は、リクエストごとに変わるコスト
（軸重み・風・0次フィルタで変わる）を構築時点でまだ知らない。そのため
`_get_or_build_lazy_graph`は常に`edge_cost_by_id`を渡さず、決定的フォールバックのみを
使う——**cost最小方式は本タスクにより事実上使われなくなった**（`build_lazy_road_graph`
自体の関数シグネチャ・テスト[`tests/test_routing.py`]は変更していない。ドメイン層の
汎用機能として存置し、production側の呼び出し方だけを変えた）。

影響: 2つの並行Edge（同一Node間の複数Edge、実データでは稀——旧`_build_node_pair_index`
のdocstringが「同じNode対を複数のEdgeが結ぶ稀なケース」と記載）のうち、一方だけが
このリクエストの0次フィルタで除外される場合、cost最小方式なら自動的に許可される側が
選ばれるが、決定的フォールバックでは選ばれない場合がある（edge_id昇順が偶然
除外される側を指していると、その`(u,v)`ペア自体が到達不能になる）。実データで
「並行Edgeが存在する」かつ「その中の一方だけが0次フィルタ対象」という二重に稀な
条件でのみ発現し、既存の`_build_node_pair_index`自身が許容していた「多重辺は
後勝ちで曖昧」という簡略化と同種のレベルの妥協と判断し、タイル集合だけで完結する
キャッシュ（＝2回目以降のprepareでグラフ構築を丸ごと省略できる）を優先した。

### 境界ケースのテスト（T536の教訓を踏まえた対応）

T536で「ローカル単体テストは全green、本番の空タイル混在bboxで初めて例外」という
落とし穴を踏んだ実績を受け、本タスクでは以下の境界ケースを通常のテストケースと
同列にカバーした（`backend/tests/test_road_graph_engine.py`「改善計画T537」節）:

- 同一タイル集合への2回目以降の`prepare`がLazyRoadGraph・NodeSpatialIndexとも
  同一オブジェクトを再利用すること（キャッシュヒットの直接確認）。
- 異なるタイル集合（起点がタイル境界付近で1タイルずれる想定）が別エントリになり
  誤ヒットしないこと。
- 同一タイル集合でも`hard_filters`が異なればNodeSpatialIndexは別エントリになるが、
  LazyRoadGraph（トポロジのみ）は共有されること。
- タイル集合がNone（split鮮度が古いbbox限定の再構築経路）の場合、キャッシュを
  一切経由せず毎回新規構築されること（不完全な集合でキャッシュを汚さない）。
- **0次フィルタでbbox内の全Edgeが除外される境界ケース**: `compute_routable_node_ids`が
  空集合を返し、NodeSpatialIndexはbucketsが空のまま構築される。この「空だが正当な
  結果」も正しくキャッシュされ（`cache.get()`のNone=未キャッシュと、空の索引自体が
  キャッシュ済みであることを取り違えていないか）、2回目以降は構築関数
  （`build_node_spatial_index`）自体が呼ばれないことを確認。
- **bboxを覆うタイルが全て空（Edge0件）の境界ケース**: `_build_search_graph`が
  `search_materials.graph.edges`が空の時点でNoneを返し、tile_setの値に関わらず
  search_graph_cacheへ一切触れないこと（キャッシュを汚さない）。
- `infrastructure/search_graph_cache.py`自体のLRU立ち退き・キー独立性は
  `tests/test_search_graph_cache.py`で単体テスト（`graph_material_cache`の
  既存テストパターンに準拠）。

### テスト結果

`pytest backend/tests -q -m "not postgis"` 全体（1262件）green（2026-09-02実行）。
既存の`tests/test_road_graph_engine.py`・`tests/test_route_generator.py`・
`tests/test_routing.py`はいずれも**無修正でpass**（`build_lazy_road_graph`の
シグネチャ・挙動自体は変更していないため）。`tests/test_graph_service.py`・
`tests/test_routes_preview.py`は`get_search_materials_for_bbox`の戻り値が3タプルに
なった機械的な追従（タイル集合の値を新たにアサートする追加のみ、既存アサーションは
変更なし）。`tests/test_road_graph_engine.py`は`_RoadGraphContext.node_pair_index`
撤去に伴う機械的な追従（`lazy_graph=None`だったテストへ実際の`lazy_graph`を渡す、
`_build_node_pair_index`を直接呼んでいたテストを`LazyRoadGraph`経由へ書き換え）に加え、
上記の新規境界ケーステストを追加。

### ローカル/dev DB速度サニティチェック（2026-09-02、`benchmarks/bench_t537_prepare_cache.py`新設）

dev機実DB、東京駅相当の起点・distance_km=10（`bench_t536_route_generation.py`と同条件）。
対象グラフedges=318,595・nodes=123,308。`git stash`で本タスクの変更を一時的に外し
（`build_lazy_road_graph`/`compute_routable_node_ids`/`build_node_spatial_index`が
毎回作り直される旧実装）で計測すると、`graph_ms`・`index_ms`は3回連続でほぼ一定
（`graph_ms`≈1,094/1,125/1,140ms、`index_ms`≈922/906/906ms、合計約2,000〜2,050ms
——キャッシュが無いため2回目以降も一切縮まらない）。`git stash pop`で本タスクの
実装へ戻すと、1回目（`search_graph_cache`が空、cold）は`graph_ms=1,062ms`・
`index_ms=750ms`だが、**2回目・3回目は`graph_ms=0ms`・`index_ms=0ms`**
（`lazy_graph_cached=True`・`node_index_cached=True`のログで確認）——
完了条件の「2回目以降のリクエストで合計500ms未満」を大きく下回り、対象2ステージが
事実上0msまで縮んだ。`prepare_wall_ms`全体も1回目41,922ms（split鮮度確認・材料
タイルキャッシュの初回温めを含む）→2回目2,531ms→3回目2,234ms（残りはT536スコープの
`cost_ms`約1,400ms・材料取得`materials_ms`約400〜700ms、いずれもT537の対象外）。

**pushしていない**: このAgentの作業はworktree内でのローカルコミットまで。本番backendは
`backend/**`変更のpushで自動デプロイされるため、本番同一条件（東京駅30km）での
`graph_ms`・`index_ms`実測はユーザーがpush後に別途行う。
