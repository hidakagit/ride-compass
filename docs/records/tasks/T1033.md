# T1033. way_materialsだけが「生データを差し替えたら下流を作り直す」契約から外れている

状態: 未完了

## 背景

派生データのバッチは「生データを差し替えたら下流を全部作り直す」という契約を持ち、
区間の形と区間単位の材料は全消しして作り直している。

**way単位の材料テーブルだけがこの契約から外れている。**

- そのテーブルに対する`TRUNCATE`/`DELETE`/`DROP`は`backend/app`・`backend/scripts`を
  通じて**0件**（実測。取込パーティション用のTRUNCATEは別物）。触るのは
  `INSERT … ON CONFLICT DO UPDATE`だけ。
- 鮮度台帳は「親にあって子に無い行」を数える向きで、**逆向き（親から消えた道の子行）は
  台帳に出ない**。

したがって、取込で消えた道・範囲外になった道のway単位材料が**古い値を保ったまま残り、
台帳にも現れない**。

**孤児が実際に何行出ているかは未計測。**

## 対応方針

**測るところから始める。** 件数が分からないまま設計を直すと、直した効果も分からない。

1. 本番DBで孤児行を数える。`backend/scripts/run_probe.py`経由で行う
   （手で長いコマンドを組み立てない。CLAUDE.md「既に仕組み化されているもので済まないか
   を見る」）。数え方: way単位材料テーブルの行のうち、現在の生データ側に対応する道が
   存在しないものの件数と、全体に対する割合。
2. **0件なら設計の是正だけ**（契約から外れていること自体は直す）。
   **多ければ、既存の孤児をどう扱うかも決める**（消すのか、次の全面再構築まで放置して
   よいのか）。
3. 鮮度台帳に逆向き（子にあって親に無い行）を出すかを判断する。出さないと決めるなら、
   出さない理由を`docs/modules/backend/`の該当文書へ書く。

## 完了条件

- 本番での孤児行数と割合が実測され、このエントリに書かれている。
- way単位材料が、区間単位の材料と同じ契約（生データを差し替えたら作り直す）に従っている。
- **わざと1件、生データ側から道を消した状態を作り、下流に孤児が残らないことを
  確認してから完了にする。** 開発DBで行う。
