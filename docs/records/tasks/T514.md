# T514: JMAタイルプリウォームへの自前レート制御追加

状態: 完了（2026-09-01）

## 背景

T510で追加した定期プリウォーム（`jma_tile_prewarm_service.py`、10分間隔）を本番投入後、
`/api/debug/stats`の`weather:jma-tile`カテゴリで短時間に1万件超の呼出・数百件の
`http_4xx`エラーを確認した。プリウォームが列挙する約1,983タイルは、JMA側の
`basetime`/`validtime`が5〜10分おきに更新されURLパス自体が変わるため、Redisキャッシュ
（TTL20分）がほとんど効かず、ほぼ毎サイクル全量を実際にJMAへ再フェッチしている。
プリウォーム本体（`prewarm_jma_tiles`内の`_fetch_one`）は同時実行数8のセマフォ以外に
自前のレート制御を持たない——同時実行数を絞っても、各リクエストの応答が速ければ総
スループット（秒間リクエスト数）自体は青天井になり、これが`http_4xx`（JMA側のレート
制限と推測、詳細ステータスコードは今回未特定のまま）の原因になっていたと考えられる。

## 対応方針

`JmaTileClient.fetch`（実際にJMAへ問い合わせる箇所、`jma_tile_client.py`）の直前で、
秒間リクエスト数の上限（新設定`jma_tile_upstream_max_requests_per_second`、既定5.0）を
守るよう待機する仕組みを追加した。

- プリウォーム本体には手を入れず、`fetch`という「実際にJMAへ問い合わせる唯一の関数」に
  置くことで、プリウォーム経由・オンデマンド（実ユーザーのキャッシュミス時fetch）経由の
  どちらもこの1箇所を必ず通り、呼び出し元を問わずJMAへの総リクエスト数を一律に抑える。
- `JmaTileClient`はリクエストごとに使い捨てでインスタンス化される
  （`api/dependencies.py: get_jma_tile_client`・`_prewarm_jma_tile_job`）ため、
  直前フェッチ時刻はインスタンス変数ではなくモジュールレベルの状態
  （`_last_fetch_at`、`_target_times_cache`と同じ理由）として持つ。
- backendはuvicornをワーカー数指定無し＝単一プロセスで起動する構成（`Dockerfile`）の
  ため、プロセス内メモリの状態だけで実際の総リクエスト数を正しく制御できる（複数
  ワーカー・複数プロセスの構成に変わった場合は、この前提が崩れ別途調整が必要になる）。
- 既定値5.0req/sは、1,983タイル/回・10分間隔のプリウォームに対しても余裕を持って
  収まる（1983/5≒397秒 < 600秒）よう控えめに設定した。
- 待機時間自体は実フェッチの所要時間ではないため、`log_external_call`の計測
  （`elapsed_ms`、`/api/debug/stats`の集計）に含めないよう、待機を`with`ブロックへ
  入る前に済ませる。

## 実装ファイル

- `backend/app/config.py` — `jma_tile_upstream_max_requests_per_second`設定追加。
- `backend/app/infrastructure/jma_tile_client.py` — `_wait_for_upstream_rate_limit`
  （モジュールレベルのロック+直前フェッチ時刻）を新設し、`fetch`の実フェッチ直前で呼ぶ。
- テスト: `backend/tests/test_jma_tile_client.py`
  （`test_fetch_paces_requests_to_the_configured_upstream_rate`を追加。既存テストが
  レート制限の待機で不必要に実時間を消費しないよう、`no_real_upstream_rate_limit_wait`
  フィクスチャ[autouse]で`_last_fetch_at`のリセット・`asyncio.sleep`の即時化を行う）。

## 検証結果

- `pytest -q -m "not postgis"`: 1208件成功（既知の無関係な失敗なし）。
- 778件のエラーが実際にJMA側の429だったかどうかの切り分けは、この対応の効果を本番で
  観測してから判断する（`/api/debug/stats`の`weather:jma-tile`エラー数の推移で確認）。
