# T515: 風の環境グループgridFill、粗格子/詳細格子の重なりを幾何学的に切り取って二重塗りを解消

状態: 完了（2026-08-31）

## 背景

風の環境グループ面塗り（`windPenalty.ts`）で、粗い格子（`windGrid`、関東本土全域を
常時カバー）と詳細格子（`windDetailGrid`、ズームイン時に画面中心付近の狭いbboxを
カバー）を重ねて描画する際、両者の境界で半透明のfill-opacityが二重に重なり、色が
凡例と対応しなくなる問題が見つかった（ユーザー報告「色が二重に重なると、他の凡例と
色の区別がつきにくくなり、ユーザー体験としても違和感がある。割と致命的」）。

これまでの経緯（点ごとの近接判定→セル全体の包含判定、いずれも粗いセルの中心座標を
基準にした判定）はいずれも「詳細格子の取得範囲が粗い格子のセル境界と無関係な任意の
矩形（ビューポート中心±固定角度、`clampWindDetailBbox`）である」ことが根本原因で、
判定をどう工夫しても粗いセルの一部だけが詳細格子と重なる状況（部分重複）が起こり得た。

## 検討した案A（不採用）

詳細格子の取得範囲を「ビューポートに重なる粗格子セル＋外側1周ぶん」へスナップし、
その範囲に完全に含まれる粗格子セルだけを整数インデックスで丸ごと除外する案を最初に
ユーザー承認を得て実装した。しかし実装中、900点上限との組み合わせで実行不可能なことが
判明した——粗格子1セル（0.1度、約11km四方）を最も細かい詳細間隔（0.0025度）で埋める
だけで41×41=1,681点、外側1周ぶんを含めた最小範囲（3セル=0.3度）を最も粗い許容間隔
（0.01度）で埋めても31×31=961点必要になり、いずれも900点上限を超える。つまりこの案は
実用上ほぼ常に最も粗い間隔（0.02）へ格下げされてしまい、T185（ズームインしたときの
細かい格子表現）を事実上壊す。着手前に実行可能性を検算していなかったのが原因。
テストがこの格下げを検知して失敗したことで発覚し、実装を戻して案Bへ切り替えた。

## 対応方針（案B、採用）

詳細格子の取得範囲・間隔は変更せず、粗い格子セルと詳細格子の実カバー範囲が重なる場合に
**重なった部分だけを幾何学的に切り取ってから描画する**。両方とも軸に平行な矩形のため、
外部ライブラリ無しで「矩形の引き算」（最大4枚の帯への分解）だけで実装できる。

- `windPenalty.ts`:
  - `subtractRectangle(cell, hole)`: 矩形`cell`から矩形`hole`と重なる部分を取り除いた
    残りを、重ならない矩形の配列（0〜4枚）として返す純粋関数。
  - `windPenaltyCoarseGridToClippedFeatureCollection`: 粗い格子の各点について、セルを
    詳細格子の実カバー範囲（返ってきた点群の外接矩形を詳細格子の間隔ぶん外側へ拡張した
    範囲）で`subtractRectangle`し、残った矩形ぶんのFeatureを作る。1粗格子点が0〜4個の
    Featureに対応する。
  - 旧`coarseGridPointsOutsideDetailBounds`（点の配列を返す）は削除し、上記関数へ統合
    （FeatureCollectionを直接返す形へ変更）。
- `useDynamicWeatherLayers.ts`: `windPenaltyCoarsePayload`の組み立てを新関数の呼び出し
  1本に置き換え。
