# T1031. 「単一の情報源」を自称するSQLを、batchの1本だけが手で写している

状態: 完了

## 背景

`backend/app/domain/material_sql.py`は冒頭で「材料の値をSQLで導出する式の、単一の情報源」
「同じ判定式を呼び出し側ごとに独立して書くとドリフトするため、ここへ集約する」と宣言し、
生データを読む副問い合わせを関数として提供している。

`backend/app/batch/derive_raster_materials.py`は、その副問い合わせを**手書きで再現している**
（列を2つ落としただけの同じ形）。同じファイルが同じ`material_sql`から正規化のSQL断片を
importしており、それらが特定の別名を参照する前提に合わせるための写しになっている。

他の参照側（`material_coverage.py`・`road_graph_repository.py`）はいずれも関数呼び出しで、
**写しはこの1件だけ**。

生データの入れ方（`source`の値、キーのキャスト）を変えたとき、関数を直しても**この1本だけが
古い世界を指し続ける**。`.claude/commands/review.md`が「共有断片から外れた手書き」として
挙げている型そのもので、同じ形は過去に実害を出している（共有側を直したのに手書きの1本が
残り、欠損率APIが落ちた）。

## 対応方針

写している側を関数呼び出しへ寄せる。落としている列が理由で関数をそのまま使えないなら、
**列の選択を引数にする**（別の関数を増やさない——増やすと「2本目の単一の情報源」になる）。

## 完了条件

- 生データを読む副問い合わせの綴り（`source`の比較とキーのキャスト）が、
  `material_sql.py`の外に無い。
  導出: その2つの綴りを`backend/`全体でgrepし、ヒットが`material_sql.py`のみ。
- `backend/tests`のうち変更が届く範囲が通る。届く範囲は
  `pytest backend/tests -q --co`（収集のみ）と、変更したシンボルのgrepで出す。
- ラスタ材料の導出結果が変わらないことを、**別の入力で**確認する
  （修正の根拠にした式で測り直しても証拠にならない）。確かめ方はこのタスクで決めて
  ここへ書く。

## 実施（2026-09-23）

### 範囲の導出（完了条件のgrepと、背景の「写しは1件だけ」が食い違っていた）

完了条件どおり`source = 'osm_way'`と`natural_key::bigint`を`backend/app`・`backend/scripts`で
grepすると、ヒットは`derive_raster_materials.py`の1件ではなかった。背景の「写しはこの1件だけ」は
`w`の別名を材料の式へ渡す読み手に限った数え方で、道の生データを手で読む箇所は他に
`derive_way_materials.py`（通行方向の入力・上下線分離の事実表）・`derive_node_materials.py`
（ノードに集まる道の最大階級）・`derive_topology.py`（構成ノードの並びの復号）にもあった。
欠陥の性質（「取込の入れ方を変えたとき、関数を直しても手書きの側だけが古い世界を指す」）は
これらにも同じく当てはまるため、**道の生データを読む手書きをすべて**関数呼び出しへ寄せた。

grepの残り（寄せなかったもの）と判定:

- `road_graph_repository.py`の`source_runs`を引く行: 取込の記録で、生データを読まない。対象外。
- ノードの生データ（`source = 'osm_node'`）を読む手書き（`derive_node_materials.py`・
  `derive_counts.py`・`road_graph_repository.py`）: 同じ性質だが、`material_sql.py`はノードの
  読み方を持っておらず寄せる先が無い。寄せる先を作るのは別の設計判断なので
  [T1044](T1044.md)へ起票した（母集団の導出・完了条件はそちら）。
- `derived_data_freshness.py`の`f.natural_key::bigint`: ソースを引数で受ける汎用の台帳。
  T1044で判断する項目として書いた。

### 変更

- `material_sql.py`: 列の並びを`_ways_select`へまとめ、`ways_source_sql`に
  `extra_columns`（`source_features`の列をそのまま足す口）を足した。`derive_topology.py`が
  要る`payload`は材料の式が読まない列で、引数で足す（別の関数を増やさない——対応方針どおり）。
  `derive_raster_materials.py`が落としていた2列（`highway`・`surface`）は、副問い合わせが
  展開されるため読まない列を持っても費用は変わらず、引数は要らなかった。
- 4つのバッチの手書きを`WAYS_SOURCE_SQL`／`ways_source_sql(extra_columns=("payload",))`へ。
- `docs/modules/backend/static-road-attributes.md`「派生」へ、道の生データの読み方を
  `material_sql.py`だけが持つこと、列が要る段は引数で足すことを書いた。

### 検証

- **導出結果が変わらないことを別の入力で**: 開発DB（道12,029本・区間23,326本）で、
  変更前（`git show`で取り出した旧モジュール）と変更後の各SQLの結果集合を`EXCEPT ALL`で
  両向きに突き合わせた。

  | SQL | 行数（旧/新） | 旧のみ | 新のみ |
  |---|---|---|---|
  | ラスタ `_EDGE_SHAPES`（形はmd5で比較） | 23,326 / 23,326 | 0 | 0 |
  | トポロジ `_DECODE_WAYS`（構成ノードの並び・形） | 12,029 / 12,029 | 0 | 0 |
  | 上下線分離 `_WAY_FACTS` | 12,029 / 12,029 | 0 | 0 |
  | 通行方向 `direction_sql(_SOURCE_WAYS)` | 12,029 / 12,029 | 0 | 0 |
  | 最大階級 `ranked` | 44,032 / 44,032 | 0 | 0 |

  ラスタ材料そのもの（標高・土地被覆の値）は`_EDGE_SHAPES`からだけ道を読むため、その入力集合の
  一致をもって導出結果の一致とした（画素の引き方は変えていない）。
- grep: `source *= *'osm_way'`のヒットは`material_sql.py`と上記`source_runs`の1行のみ。
- 静的検査: `ruff check backend/app/domain/material_sql.py backend/app/batch/` → All checks passed。
  `scripts/review_checks.py docs` → 違反なし。
- テスト: 変更したシンボルをgrepして届く範囲を出し、`test_derive_topology.py`・
  `test_material_values.py`・`test_resolve_direction.py`・`test_tag_classification.py`・
  `test_landcover.py`・`test_elevation_values.py`・`test_material_coverage.py`・
  `test_edge_material_arrays.py` → 136 passed。
