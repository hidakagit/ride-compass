# T1093. 道路タイルに焼く真偽の材料（照明・トンネル・自転車レーン等）の条件を、材料の宣言から組み立てる

状態: 未完了（2026-09-24起票）

## 背景

背景（T965 段階Bの点検で見つけた崩れ。T955・T956の主張「材料の導出はSQL1本へ」に反する）: 真偽の材料9件（照明あり・トンネル・橋・自動車通行不可・自転車道・自転車レーン等3種・歩行者と共用の道）の「どのタグの値なら真か」を、材料カタログの value_sql（ルートの評価が読む）と、道路タイルのSQL（road_graph_repository.py の _ROAD_SURFACE_TILE_MVT_SQL、地図が塗る）が別々に書いている。例: 歩行者共用の道の bicycle が ('yes','designated') という条件が両方にある。

起きうること: 片方だけ条件を直すと、地図の色とルートの評価が同じ道で食い違う（地図では自転車レーンありなのに評価ではなし、等）。材料を1つ足すときも2か所を触る。
起きない場面: 今は条件が一致している（点検時に照合）。

直し方: タイル側を CASE WHEN (value_sql) THEN true END の形で材料カタログから組み立てる。値は変わらない見込み（COALESCE(x,false) が真になるのは x が真のときだけ）。ただしタイルのSQLの文字列が変わるので、形の署名（ROAD_SURFACE_TILE_SHAPE）が変わり、デプロイ後に路面タイルが全部作り直しになる（最初の表示が一時的に遅くなる）。生成物 region-tile-config.json の再生成も同じコミットで要る。

迷い: T956の記録は「材料の導出はタイルの符号化と分ける」と書いている。分けたのは真偽をNULLで持つかfalseで持つかの符号化で、条件式まで二重にする意図ではないと読んだ。

なぜ既存のタスクに入らないか: T955・T956は完了済み。T965（点検）の中で直すには、タイルの作り直しという利用者から見える副作用があり、規模Sの整理の範囲を超える。
