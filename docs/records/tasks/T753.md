# T753. Way単位の材料解決が舗装タグを拾えていない 規模S

状態: 完了（2026-09-12、[T720](T720.md)の本番計測中に発覚）

## 背景

`domain/axis_inspector.py: way_scalar_materials`が舗装を
`surface_attributes={_WAY_SCOPE_KEY: tags.get("surface")}`として渡しているが、
`surface`は`osm_raw_ways.surface`の専用列で、tags jsonbには入らない
（`domain/osm_adapter.py: ALLOWED_WAY_TAGS`が「highway/surface/onewayは既存の専用
フィールドで扱うためここには含めない」と宣言している）。そのため材料`surface_good`は
Way単位の経路では常に欠損する。

区間インスペクタが読む`road_graph_repository.py: _WAY_TAGS_BY_OSM_WAY_ID_SQL`も、
軸スタジオの分布プレビューが読む`_SAMPLE_WAY_MATERIALS_TEMPLATE`も、
`w.surface`をSELECTしていない。

## 実害

- 地図で道路をクリックして出る区間インスペクタで、公開軸「舗装質」が**全区間で
  「データなし」**になる。合わせて`covered_weight_fraction`（「◯%相当の軸のみで算出」）も
  実際より低く出るため、他の軸の内訳まで過小に見える。
- `scripts/measure_axis_saturation.py`が舗装質を測れない（本番で「全区間で材料が欠損」）。
  折れ点の当て方を実データで点検できる軸から1つ落ちている。

ルート評価そのもの（Edge単位、`domain/evaluation.py`）は
`road_graph_repository.get_surface_attributes`が専用列をJOINして読むため影響を受けない。

## 確認した事実（2026-09-12、本番DB）

- `osm_raw_ways`の無作為標本6,790本のうち`tags ? 'surface'`は**0本**（`lit`は50本あり、
  tags jsonb自体は機能している）。
- `measure_axis_saturation.py`を本番へ実行すると、全域・都心bboxのいずれでも
  `surface_q`が「全区間で材料が欠損」。

## 対応方針（未確定）

`w.surface`を2つのSQLの選択列へ足し、`way_scalar_materials`の引数へ通す。
`sample_way_rows`側は`WayMaterialSampleRow`へ1フィールド増える。
tagsに入らない専用列が他にもある（`highway`は既に別引数、`oneway`は
`WaySpec.direction`へ解決済み）ため、同じ取りこぼしが他の材料にも無いかを
`MaterialExtractionContext`の各フィールドについて確認してから直す。

## 完了条件

- 区間インスペクタで舗装質が算出されること（本番の任意のwayで確認）
- `measure_axis_saturation.py`が`surface_q`の分布を出せること
- Way単位で解決できるはずの材料が他に欠損していないか点検した結果を記録すること

## 対応

`w.surface`を2つのSQL（`_WAY_TAGS_BY_OSM_WAY_ID_SQL`・`_SAMPLE_WAY_MATERIALS_TEMPLATE`）の
選択列へ足し、`way_scalar_materials`／`axis_inspector_breakdown`の引数として通す。
`WayMaterialSampleRow`に`surface`が1フィールド増える。

## 他の材料の点検（完了条件3）

`MaterialExtractionContext`の各フィールドについて、Way単位の経路（`way_scalar_materials`）
が実際に値を供給しているかを見た。

| フィールド | Way単位での供給元 | 判定 |
|---|---|---|
| `highway` | 引数（専用列） | ○ |
| `way_tags` | tags jsonb | ○（下記のキー突き合わせ） |
| `distance_km` | `way_counts.length_m` | ○ |
| `elevation_attributes` | 空（ルート文脈が要る） | 意図的な欠損 |
| `surface_attributes` | **tagsから読んでいた** | 本タスクで専用列へ |
| `designated_edge_ids` | 引数（`is_designated`） | ○ |
| `metrics`（counts/poi/landcover/geometry） | 事前集計テーブル | ○ |
| `accident_years_covered` | 引数 | ○ |

extractorが`way_tags`から読むキー（`material_catalog.py`の`smoothness`・`tracktype`、
`recipe.py`経由の`bicycle`・`lanes`・`maxspeed`、`bicycle_infra_flags`の`cycleway*`）を
`ALLOWED_WAY_TAGS`と突き合わせた結果、**許可リストに無いキーは`surface`だけ**だった
（`highway`は別引数、`oneway`は`WaySpec.direction`へ解決済みで材料からは読まれない）。

## 再発防止

同じ取りこぼしを次回は機械で気づけるよう、`scripts/review_checks.py`へ検知器
`way_tag_allowlist`を足した——材料解決の経路（`axis_inspector.py`・`material_catalog.py`・
`recipe.py`）が`ALLOWED_WAY_TAGS`に無いキーを`tags`／`way_tags`から読んでいたら止める。
許可リストは実装（`osm_adapter.py`）から読むため、リストを増やせば検知器も追従する。
検知器の対象をこの3ファイルへ絞ったのは、`osm_adapter.py`（取込前の生タグを読む）と
`traffic.py`（node用の別の許可リスト）が同じ`tags.get(...)`の形で正当に別の母集団を
読んでおり、全backendへ広げると全件が誤検知になるため。

## 検証

- `tests/test_evaluation.py`へ回帰1件: 専用列から渡したときだけ`surface_good`が解決され、
  tagsへ入れても欠損したままであることを固定した。既存の区間インスペクタのテストが
  `tags={"surface": "asphalt"}`という**実データに存在しない形**を渡していたため、
  実際の形（tagsにsurfaceは無い／専用列で渡す）へ揃えた。
- 検知器はわざと違反を1件入れて落ちることを確認した（`tags.get("zzz_guard_probe")`を
  `axis_inspector.py`へ足すと1件検出、戻すと0件）。
- 本番DBでの区間インスペクタ・`measure_axis_saturation.py`の確認は、デプロイ後に
  実施する（コード側の欠損はこの変更で解消している）。
