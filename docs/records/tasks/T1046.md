# T1046. colorトークンをTailwindのテーマへ、ダークモード追従を壊さずに取り込めるか確かめる 規模S

状態: 未完了

## 背景

`docs/modules/frontend/frontend-design-system.md`に「将来の別タスク候補」として埋まっていた
もので、台帳に行が無かった（[T1032](T1032.md)で本文から落とす前に起票）。
採番時にT1045が並行セッションと衝突し、T1046へ振り直した。

いま色は`@theme`へ入れておらず、`components/ui/`を含むTailwind側は
`bg-[var(--color-surface)]`のような任意値記法で参照している。`@theme`へ素直に入れると値が
静的に固定され、`globals.css`が`@media (prefers-color-scheme: dark)`の中で`:root`を
再定義して切り替えているダークモードに追従しなくなるため（`frontend-design-system.md`
「Design Token」節）。

Tailwind v4の`@theme inline`は、ユーティリティが変数の値ではなく`var(...)`参照のまま
展開されるため、ダークモードの再定義に追従したまま`bg-surface`のような短い名前で書ける
**可能性がある**。未検証。

## 何を確かめるか

1. **公式を先に読む**（CLAUDE.md「外部の仕様について何か言う前に、公式を読む」）。
   Tailwind v4の`@theme inline`がユーティリティへどう展開されるか、テーマ変数そのものを
   `:root`（`@layer theme`）へ出力するか。
2. **同名の循環を避けられるか**。`--color-surface: var(--color-surface)`のように同じ名前で
   包むと、テーマ変数が出力される場合に自己参照になる。別の名前空間
   （例: `--color-rc-surface: var(--color-surface)`）で包む必要があるかを、ビルド後のCSS
   （`next build`の出力）で確かめる。
3. **実機で両方の配色を見る**。トークンを1つだけ取り込み、1つの部品でそのユーティリティを
   使い、`frontend/e2e/fixtures.ts`（backendモック）を使ったplaywright headlessで
   `colorScheme: "light"`／`"dark"`のそれぞれについて、その要素の`getComputedStyle`の色が
   `globals.css`の該当トークンの値と一致することを見る。

## 完了条件

- 上の1〜3の結果（公式の記述の出典、ビルド後のCSSの該当行、両配色での計算値）をここへ書く。
- 採るなら: `frontend-design-system.md`「Design Token」節のcolor行を新しい規約へ書き換える。
  既存の任意値記法をまとめて置き換えるかは別に判断し、置き換えるなら別タスクとして起票する
  （見た目を変えない一括置換は同文書の「使い分け基準」が禁じているため、判断が要る）。
- 採らないなら: 採らない理由（どの条件で壊れたか）を同節のcolor行へ1文で足す。

## 保留した場合の影響

利用者から見える害は無い。任意値記法が長いまま使われ続けるだけ。
[T1001](T1001.md)の段階C（UI基盤とCSSの共通化）で部品を作り直すと任意値記法の参照が
増えるため、採るなら段階Cより先に決めておくと書き直しが1回で済む。
