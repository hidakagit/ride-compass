# T1046. colorトークンをTailwindのテーマへ、ダークモード追従を壊さずに取り込めるか確かめる 規模S

状態: 未完了

## 背景

`docs/modules/frontend/frontend-design-system.md`に「将来の別タスク候補」として埋まっていた
もので、台帳に行が無かった（[T1032](T1032.md)で本文から落とす前に起票）。
採番時にT1045が並行セッションと衝突し、T1046へ振り直した。

いま色は`@theme`へ入れておらず、`components/ui/`を含むTailwind側は
`bg-[var(--color-surface)]`のような任意値記法で参照している。`@theme`へ素直に入れると値が
静的に固定され、`globals.css`が`@media (prefers-color-scheme: dark)`の中で`:root`を
再定義して切り替えているダークモードに追従しなくなるため（`frontend-design-system.md`
「Design Token」節）。

Tailwind v4の`@theme inline`は、ユーティリティが変数の値ではなく`var(...)`参照のまま
展開されるため、ダークモードの再定義に追従したまま`bg-surface`のような短い名前で書ける
**可能性がある**。未検証。

## 何を確かめるか

1. **公式を先に読む**（CLAUDE.md「外部の仕様について何か言う前に、公式を読む」）。
   Tailwind v4の`@theme inline`がユーティリティへどう展開されるか、テーマ変数そのものを
   `:root`（`@layer theme`）へ出力するか。
2. **同名の循環を避けられるか**。`--color-surface: var(--color-surface)`のように同じ名前で
   包むと、テーマ変数が出力される場合に自己参照になる。別の名前空間
   （例: `--color-rc-surface: var(--color-surface)`）で包む必要があるかを、ビルド後のCSS
   （`next build`の出力）で確かめる。
3. **実機で両方の配色を見る**。トークンを1つだけ取り込み、1つの部品でそのユーティリティを
   使い、`frontend/e2e/fixtures.ts`（backendモック）を使ったplaywright headlessで
   `colorScheme: "light"`／`"dark"`のそれぞれについて、その要素の`getComputedStyle`の色が
   `globals.css`の該当トークンの値と一致することを見る。

## 完了条件

- 上の1〜3の結果（公式の記述の出典、ビルド後のCSSの該当行、両配色での計算値）をここへ書く。
- 採るなら: `frontend-design-system.md`「Design Token」節のcolor行を新しい規約へ書き換える。
  既存の任意値記法をまとめて置き換えるかは別に判断し、置き換えるなら別タスクとして起票する
  （見た目を変えない一括置換は同文書の「使い分け基準」が禁じているため、判断が要る）。
- 採らないなら: 採らない理由（どの条件で壊れたか）を同節のcolor行へ1文で足す。

## 結果（2026-09-23）

### 1. 公式の記述

- Tailwind v4 公式「Theme variables」（https://tailwindcss.com/docs/theme）「Referencing other
  variables」: `inline`を付けると、ユーティリティはテーマ変数を参照せず、その**値**を使う
  （例 `@theme inline { --font-sans: var(--font-inter); }` → `.font-sans { font-family: var(--font-inter); }`）。
  付けないとユーティリティは`var(--font-sans)`を参照する。テーマ変数は既定で`:root`へ
  CSS変数として出力され、出るのは使われたものだけ（`static`で全部出す）。`@theme`は最上位に
  置く必要があり、セレクタやメディアクエリの中には書けない。
- 同「Dark mode」（https://tailwindcss.com/docs/dark-mode）: 既定の`dark:`は
  `prefers-color-scheme`。テーマ変数をダーク用に再定義する方法は書かれていない。
- 実装（v4.3.3、`packages/tailwindcss/src/theme.ts`の`resolve`）: `INLINE`が立っていれば
  `value.value`を、無ければ`var(<キー>)`を返す。`index.ts`は`REFERENCE`以外の全エントリを
  `@layer theme { :root, :host { … } }`へ出し、`ast.ts`の最適化が`USED`/`STATIC`でない
  ものを落とす。

### 2. ビルド後のCSS（同名の循環を避けられるか）

作業ツリーの`globals.css`へ次を一時的に足し、`Card`を`bg-surface-2`へ書き換えて、
`next build`が`postcss.config.mjs`経由で呼ぶのと同じ`@tailwindcss/postcss` 4.3.3
（`optimize`有効）でビルドした。`next build`そのものは回していない（作業ツリーに
`node_modules`が無く、司令塔の指示で開発機の負荷を下げていたため。Tailwindが出すCSSは
このプラグインの出力がすべてで、Next.jsはそれを結合・圧縮するだけ）。

```css
@theme inline {
  --color-surface-2: var(--color-surface-2);   /* 同名 */
  --color-rc-surface: var(--color-surface);    /* 別の名前空間 */
}
@source inline("bg-rc-surface");
```

出力の該当行（行番号はビルド後のCSS）:

| 行 | 所属 | 中身 |
|---|---|---|
| 47〜48 | `@layer theme { :root, :host {` | |
| 67 | 同上 | `--color-surface-2: var(--color-surface-2);`（**同名は自己参照として出力される**） |
| 679〜680 | `@layer utilities` | `.bg-rc-surface { background-color: var(--color-surface); }` |
| 683〜684 | 同上 | `.bg-surface-2 { background-color: var(--color-surface-2); }` |
| 830／849 | unlayeredの`:root` | `--color-surface-2: #f3f4f2;` |
| 893〜898 | `@media (prefers-color-scheme: dark) { :root {` | `--color-surface-2: #1c1c1f;` |

- 別の名前空間（`--color-rc-surface`）はテーマ層へ出力されない（`var(--color-surface)`は
  テーマのキーではないため使用済みにならない）。
- 同名は`@layer theme`へ自己参照として出るが、unlayeredの`:root`とダーク側の再定義に
  カスケードで負けるため、実効値には現れない（3.の計算値で確認）。循環になるのは、
  unlayeredの`:root`にその名前が無い場合だけで、そのときは`@theme`に書かなくても
  未定義で壊れる。
- `inline`の有無は、同名の`var()`包みでは出力が同じになる（`@theme`でも`@theme inline`でも
  ユーティリティは`var(--color-surface-2)`）。

### 3. 両配色の計算値（壊した入力を含む）

上のCSSをheadless chromium（playwright）へ流し込み、`Card.tsx`の実際のclass文字列
（`rounded-md bg-surface-2 p-2`）を持つ要素と`bg-rc-surface`の要素の
`getComputedStyle().backgroundColor`を、`globals.css`の`:root`／ダーク側の値と突き合わせた。
3通りの`@theme`を同じ手順に通した:

| 入力 | ライト | ダーク |
|---|---|---|
| 上の形（同名・別名前空間とも`var()`で包む） | 一致（`rgb(243, 244, 242)`／`rgb(255, 255, 255)`） | 一致（`rgb(28, 28, 31)`／`rgb(42, 42, 45)`） |
| 壊した入力: `@theme inline`へ値を直書き（`--color-surface-2: #f3f4f2`等） | 一致 | **不一致**（両方ともライトの値のまま。ユーティリティが`background-color: #f3f4f2`に焼き込まれる） |
| 対照: `@theme`（inline無し）へ値を直書き | 一致 | `bg-surface-2`は一致、`bg-rc-surface`は**不一致**（`:root`に再定義のある名前だけ追従する） |

したがって、`frontend-design-system.md`が持っていた「`@theme`へ入れると値が静的に固定され
ダークモード追従が壊れる」は、`inline`へ値を直書きした場合と、再定義の無い名前を置いた場合に
しか成り立たない。この記述を事実に合わせて書き直した（同文書「Design Token」のcolor行と、
`globals.css`冒頭コメントの同じ主張を削除）。

### 取り込んだときに失うもの

- 短い名前の綴り違いは何も止めない（実測）: `@source inline("bg-surfce-2 bg-[var(--color-surfce-2)]")`
  をビルドすると、警告0件で、`bg-surfce-2`はクラスが1つも生成されず（黙って効かない）、
  任意値記法の側は`var(--color-surfce-2)`を参照する規則が出る——後者は
  `frontend/src/structure/cssTokens.test.ts`が未定義トークンとして落とす。
- 同名の形は`cssTokens.test.ts`の未定義検査も素通りさせうる（テストの正規表現を読んだ
  結果で、壊した入力での実行はしていない）: 同テストは`globals.css`の
  `^\s*(--…)\s*:`に当たる行をすべて定義とみなすため、`@theme inline`の
  `--color-x: var(--color-x);`が「定義」に数えられ、`:root`に`--color-x`が無くても通る。

## 保留: 採るか、採るならどの形か（ユーザー判断）

技術的にはダークモードを壊さずに取り込めると確かめたが、規約をどちらへ倒すかは
[T1001](T1001.md)段階Cの書き方そのものを決めるため、ユーザーの判断を待つ。選択肢:

1. **採らない（現状維持）**: 任意値記法`bg-[var(--color-*)]`を続ける。綴り違いは
   `cssTokens.test.ts`が落とす。長いが、守りは今のまま。
2. **同名で採る**: `@theme inline { --color-surface: var(--color-surface); … }`を足し、
   `bg-surface`・`border-border-strong`のように書く。トークン名とクラス名が1対1で読める。
   代わりに、短い名前の綴り違いは何も止めず、`cssTokens.test.ts`の未定義検査は`@theme`の行を
   定義と数えるよう直す必要がある（`@theme`ブロックを定義の母集団から外す）。
3. **別の名前空間で採る**（例 `--color-rc-surface: var(--color-surface)` → `bg-rc-surface`）:
   テーマ層へ何も出ず、`@theme`側の`var()`の綴り違いは`cssTokens.test.ts`が今のまま落とす。
   代わりにクラス名がトークン名と一致しない。短い名前の綴り違いは2.と同じく止まらない。

2.か3.を採る場合、既存の任意値記法（`frontend/src`で21か所・7ファイル、2026-09-23の
`grep -rhoE '(bg|text|border|…)-\[var\(--color-[a-z0-9-]+\)\]'`）を置き換えるかは
別に判断が要る（見た目を変えない一括置換は同文書「使い分け基準」が禁じている）。
置き換えないなら、段階Cで作り直す部品から新しい書き方にする、という移行になる。

## 保留した場合の影響

利用者から見える害は無い。任意値記法が長いまま使われ続けるだけ。
[T1001](T1001.md)の段階C（UI基盤とCSSの共通化）で部品を作り直すと任意値記法の参照が
増えるため、採るなら段階Cより先に決めておくと書き直しが1回で済む。
