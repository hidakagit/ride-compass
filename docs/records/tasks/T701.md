# T701. 「表示範囲が広すぎます」の案内を軸レイヤーへ配線する 規模S〜M

状態: 完了（2026-09-10起票、統合レビュー第6回 I-8／2026-09-10完了）

## 背景

低ズーム時の「表示範囲が広すぎます」の案内が、**軸レイヤーに対して一度も出ない**。

`components/Map/mapLayers.ts:1970-1975`の`isRoadSurfaceGroupVisible`は
`roadSurfaceSharedLayerIds.some((id) => visibility[id])`。
第2引数を作る`buildRoadSurfaceSharedLayerIds`（同`:559-579`）は
`...dedicatedAxes.map(dedicatedWayValueMapLayerId)`と`...rampAxes.map(axisMapLayerId)`を
明示的に含めている。

しかし`components/Map/MapView.tsx`の3箇所の呼び出し
（`:2643-2652`・`:2950-2958`・`:3446-3455`）は第1引数へ
`{roadType, roadSurface, designation, tunnel, oneway}`の5キーしか渡さず、
軸レイヤーIDは常に`undefined`＝falsyで**一度も数えられない**。effectの依存配列にも無い。

MapViewは`axisVisibility`・`dedicatedWayValueVisibility`をpropで受け取っている
（`:2212`・`:2170`）が、これらは**軸idキー**、`roadSurfaceSharedLayerIds`は
**レイヤーid**（`axis:<axisId>`）で、単に展開しても噛み合わない——配線が最後まで通っていない。

## 失敗シナリオ

「路面/道路の種類」をOFFのままレンズで風やcar_stressだけをONにし、
`ROAD_TILE_MIN_ZOOM`未満まで引くと、道路が一本も塗られないのに案内が出ず
「データが無い地域」と区別できない。`MapLayersPanel.tsx:251`は
`regionZoomTooWide && roadSurfaceSharedLayerIds.includes(layerId)`でフル一覧を使う側なので
状態ドットの抑制も効かない。

## テストが通っているのに機能していない

`MapView.tsx:1966-1969`のコメントは「新規公開ramp軸を低ズームでONにしても案内が出ないままに
なるため実行時リストを渡す」と目的を明記し、`MapView.dataStatus.test.ts:144-157`・`:178-194`は
`{"axis:car_stress": true}`を直接渡して「修正済み」を主張している。
しかし**本番配線がそのキーを一度も供給しない**ため、純関数テストが通っても機能が成立していない。
さらに`MapView.tsx:3432-3433`のコメントは逆に「ramp軸はこのチェックの対象外（既知の制約）」と
書いており、**コメント同士も矛盾している**。

## 対応方針

呼び出し側で軸id→レイヤーidへ写像したうえで`axisVisibility`・`dedicatedWayValueVisibility`を
合流させ、effectの依存配列へも足す。矛盾するコメント2箇所を整理する。
**純関数テストだけでなく、配線を通したテスト**を置く（これが無いと同じ形が再発する）。

## 起票時の記述の訂正

「`axisVisibility`・`dedicatedWayValueVisibility`は**軸idキー**」という上記の記述は誤り。
`page.tsx:1186-1192`・`:1225-1234`はどちらも`axisMapLayerId(axis.axisId)` /
`dedicatedWayValueMapLayerId(axis.axisId)`をキーにしており、**すでにレイヤーidキー**である
（`MapView.tsx`のprop docstringもそう書いている）。したがって必要だったのは写像ではなく
**合流**だけで、`setStaticOverlayVisibility`の呼び出し（`MapView.tsx:2611`/`:2616`）が
既にやっている展開と同じ形。

## 実装メモ

呼び出し側で組み立てて渡す形のままだと「合流を忘れても型が通る」ため、
`isRoadSurfaceGroupVisible`の第1引数を**propsの形そのもの**へ変え、合流を関数の中へ
移した。

```ts
export interface RoadSurfaceGroupState {
  showRoadType: boolean; showRoadSurface: boolean; showDesignation: boolean;
  showTunnel: boolean; showOneway: boolean;
  axisVisibility: Readonly<Record<string, boolean>>;
  dedicatedWayValueVisibility: Readonly<Record<string, boolean>>;
}
```

これで3箇所の呼び出しは軸の表示状態を渡さないとコンパイルが通らない
（同じ形の再発を型で止める。テストを足すだけでは「純関数テストは通るが本番配線が
キーを供給しない」という今回の失敗そのものが再現しうる）。あわせて:

- `handleZoom`の`redrawPropsRef.current`分割代入へ2つのRecordを追加。
- 路面レイヤー状態のeffectの依存配列へ2つのRecordを追加
  （軸のON/OFFだけが変わったときにも再評価する）。
- 矛盾していたコメント2箇所を整理。`MapView.tsx:3432-3433`の「ramp軸はこのチェックの
  対象外（既知の制約）」は事実と逆なので撤去し、依存配列の説明へ統合した。
- `docs/modules/frontend/static-map-layers.md`へ「表示範囲が広すぎます」の案内の節を新設
  （対象一覧の単一情報源・第1引数の形をとる理由・呼び出し3箇所を記載）。

## 検証結果

- 3箇所のうち1箇所から軸の合流を外すと`tsc --noEmit`が
  `Type ... is missing the following properties from type 'RoadSurfaceGroupState':
  axisVisibility, dedicatedWayValueVisibility`で落ちることを確認。
- `MapView.dataStatus.test.ts`の`isRoadSurfaceGroupVisible`ブロックを新しい引数の形へ
  書き換え、「静的レイヤーが全てOFFでもramp軸／専用way値配信軸がONならtrue」
  （レンズで軸だけ選んだ状態＝失敗シナリオそのもの）を追加。
- フロントエンド全体: `tsc --noEmit`クリーン、`eslint src`クリーン、
  `vitest run` 126 files / 1,149 tests passed。
