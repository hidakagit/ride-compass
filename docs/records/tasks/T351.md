# T351. 派生データの世代管理・Raw→Derived系譜追跡の強化 規模M〜L（起票のみ、未着手）

状態: 完了（2026-08-30）


- 背景: T350のDB設計書レビュー（ユーザー、2026-08-27）で指摘。DB設計書自体を
  実装（`*_models.py`・`migrations/*.sql`）と突き合わせて検証済みで、以下は実際に
  裏付けが取れている:
  1. `edge_attribute_counts`/`way_attribute_counts`は`computed_at`のみを持ち、
     どの`accident_import_runs`/`osm_import_runs`の内容から計算されたかを追跡する列
     （例: `source_accident_import_run_id`）が無い。事故データを2025年版→2026年版へ
     更新した場合、`accident_points`は最新でも`edge_attribute_counts`が旧版のまま
     という状態がDB上検出不能。
  2. 「入力データのバージョン（source_version）」と「計算ロジックのバージョン
     （algorithm_version）」が`computed_at`という1つのタイムスタンプへ混在しており、
     区別されていない（例: 事故集計の半径条件を50m→30mへ変更した場合、入力データは
     同じでも再計算が必要——これを`computed_at`だけでは判別できない）。
  3. `designation_attributes`（複合PK`osm_way_id, kind`）に`route_designations.id`への
     参照が無く、同kindの複数`route_designations`行が同じWayへマッチした場合、
     どの行が実際にマッチしたか特定できない（実装確認済み、`DesignationAttributeRow`に
     該当列なし）。
  4. `osm_import_runs`/`accident_import_runs`/`designation_import_runs`という
     「取込の実行記録」自体は存在するが、そこから生データ・派生データへの追跡経路
     （FKまたは明示的な参照列）が無い。
- 対応方針（案、着手時に検討）: `edge_attribute_counts`/`way_attribute_counts`へ
  `source_version`・`algorithm_version`相当の列を追加する、または汎用的な
  `data_processing_runs`（raw→graph生成→属性計算→評価、という処理世代を横断管理する
  テーブル）を新設する、のいずれかを比較検討する。`designation_attributes`への
  `route_designation_id`列追加は比較的小さい変更で対応できる見込み。
- **T350（axis_definitions DB専有化）とは独立したタスクとして扱う**——同一のDB設計書
  レビューから同時に見つかった指摘だが、対象領域（評価軸の正本管理 vs 派生データの
  系譜管理）が異なり、1つのタスクへ混ぜるとどちらの完了条件も曖昧になる
  （2026-08-27ユーザー判断）。
- 優先度: P1（起票のみ、着手はしない）。着手判断はユーザー承認後、別途行う。

- **着手（2026-08-30、ユーザー承認）**: 対応方針を(a)（`edge_attribute_counts`/
  `way_attribute_counts`へ`source_*_import_run_id`/`algorithm_version`列を追加）に確定した。
  (b)の汎用`data_processing_runs`テーブル新設は見送った——既存の`*_import_runs`テーブル群
  （accident/osm/designation）が既に「取込の実行記録」を持っており、そこへのFK参照を
  追加するだけで用が足りるため、8バッチ全てを横断する新規テーブルを起こす投資対効果が
  薄いと判断（`docs/complexity-review-2026-08-16.md`が過去に示した「消費者が少ない段階での
  汎用化は過剰」という判断基準を踏襲）。

- **実装メモ（2026-08-30完了）**:
  - **migration `0024_derived_data_lineage.sql`**: `edge_attribute_counts`/
    `way_attribute_counts`へ`source_accident_import_run_id`・`source_osm_import_run_id`
    （いずれもFK制約付き、高水位マーク方式）・`algorithm_version`を追加。
    `designation_attributes`へ`matched_route_designation_ids`（`integer[]`、複数の
    `route_designations`行が同一`(osm_way_id, kind)`へ寄与しうるためFK1本ではなく配列）・
    `source_osm_import_run_id`を追加（`data_version`列が既にバッファ幅パラメータを
    記録済みのため`algorithm_version`は新設していない）。設計の詳細（高水位マーク方式の
    理由・配列採用の理由）は`docs/architecture.md`「派生データの系譜追跡」節参照。
  - **`precompute_edge_attribute_counts.py`/`precompute_way_attribute_counts.py`**:
    実行開始時に`accident_import_runs`/`osm_import_runs`の最新成功run idを1回だけ取得し、
    全チャンクへ同じ値＋`ALGORITHM_VERSION="v1"`を書き込む。
  - **`match_designations.py`**: `_MATCH_SQL`の`GROUP BY`へ`array_agg(DISTINCT b.id)`を追加し、
    寄与した全`route_designations.id`を`matched_route_designation_ids`へ書き込む。
    `source_osm_import_run_id`も同様に実行時点の最新成功run idを記録する。
  - **ORM側は`ForeignKey()`を持たない素の`Integer`列にした**（実機で発見）:
    `road_graph_models.py`（`edge_attribute_counts`/`way_attribute_counts`定義）へ
    `ForeignKey("accident_import_runs.id")`のようなクロスモジュール参照を書くと、
    `accident_models.py`/`designation_models.py`を一切importしないプロセス
    （`precompute_edge_attribute_counts.py`単体実行時のテストフィクスチャ等）で
    `Base.metadata.sorted_tables`/`create_all`実行時に`NoReferencedTableError`が
    発生することを確認した。実FK制約はmigration側のみが持つ設計に変更し解消した
    （既存の「ORMモデルはミラー、実制約はmigrationが正」という規約と整合）。
  - **既知の落とし穴（実機で発見・修正）**: `precompute_edge_attribute_counts.py`の
    バルクUPSERT（`CHUNK_SIZE`行×列数ぶんのバインドパラメータを1クエリに積む方式、
    T224と同型）が、列数5→8への増加でasyncpgのパラメータ上限（32,767個/クエリ）を
    超過するようになった（`CHUNK_SIZE=5000×8列=40,000`）。`CHUNK_SIZE`を4,000へ
    引き下げて解消（`4000×8=32,000`、余裕767）。
  - **検証**: dev DB実データで3バッチとも実行し正しく書き込まれることを確認
    （edge_attribute_counts 283,084行・way_attribute_counts 86,642行・
    designation_attributes 20,616行、いずれもsource_*/algorithm_versionが期待どおり
    埋まっていることをSQLで直接確認）。`match_designations.py`実行では実際に複数の
    `route_designations`行が同一Wayへ寄与するケース（例:
    `matched_route_designation_ids=[3830,4498,4499]`）を実データで確認し、単一FKでは
    表現できなかった問題が解消されたことを裏付けた。backend全1389件green
    （`pytest -m "not postgis"`、PostGIS統合テストも同一実行に含まれ全てpass）。
  - **完了条件との対応**: 背景で挙げた4問題のうち1〜3は解消（4は1〜3の解消の副産物として
    `*_import_runs`から派生データへのFK/配列参照経路が実際に生まれたため解消）。
  - **T281との関係**: T281段階3（鮮度台帳）が必要とする「生データ更新時刻 vs 派生computed_at
    の機械比較」の材料（`source_*_import_run_id`）を先行して用意した形になる。自動検知・
    自動再計算のトリガー機構自体は本タスクのスコープ外のまま（T281段階3が別途トリガー待ち）。
  - **T400との関係**: T400.mdが「勾配はT399（標高データ永続化）が完了すれば」としていた
    記述を、T399調査（2026-08-30、標高データは既に永続化済みと判明）を受けて訂正した際に
    本タスクとは無関係と確認済み（詳細はT399.md参照）。
