# T637. 洪水（ベクタ）とキキクル（ラスタ）の更新タイミングのずれを調査する

規模S。

状態: 完了（2026-09-10）

## 背景

ユーザー報告「vectorとrastorの違い・時間差で見えないデータが残っていたりで混乱する」。

災害チップの7ソースのうち洪水キキクルだけがMapLibreのvectorソース、他はrasterソースで、
`applyDynamicWeatherState`が同じ`setTiles`で更新している。MapLibreの`RasterTileSource`と
`VectorTileSource`は`setTiles`後のタイル破棄・再取得の挙動が同一ではなく、ラスタは
新しいタイルが到着するまで古い画像を表示し続ける（`raster-fade-duration`）一方、ベクタは
より早く消える。両者の`basetime`は同じ`risk/targetTimes.json`から来るため、データ上の
時刻は揃っているはずである。

## 調査結果

原因は2つあり、**どちらもズームによって危険度が消える**（時間ではなく倍率で決まる）。
起票時に見立てた`setTiles`後の破棄挙動の差ではなかった。

### 1. 在否インデックスが「補間で埋めるズーム」まで空と断定していた（主因）

気象庁のタイルは要素ごとに`zoomUse`を持ち、キキクル4種は**偶数ズームにしか実データが無い**
（実測: `.../surf/land/8/…` と `/10/…` は200、`/9/…` と `/11/…` は404）。奇数ズームは
[T641](T641.md)が親から補間して埋める設計だが、**その補間は本番で一度も動いていなかった**。

在否インデックス（`jma_tile_index.py`）は「載っていないタイル＝空」をクライアントへ伝える
仕組みで、プリウォームは実データのあるズーム（偶数）しか温めない。結果、奇数ズームは
インデックスに載らず、クライアント（`jmaTileProtocol.ts`）が**backendへ問い合わせる前に
透明タイルを返していた**——補間の入口へ到達しない。

本番のインデックスを実取得して確認（2026-09-10 07:2x JST）:

```
land  basetime=20260909221000  ズーム=[4, 6, 8, 10]  件数={4:1, 6:4, 8:8, 10:44}
```

土砂キキクルは実際に44枚ぶんの危険度が出ている時間帯だったが、**奇数ズーム（z5/z7/z9）は
インデックスに1件も無く、そのズームでは何も表示されない**状態だった。ラスタ3種も洪水も
同じように消えるため、「z10では出ているのにz9では消える」が起きる。

### 2. 洪水キキクル（ベクタ）は補間の対象外だった

[T641](T641.md)は「MVTのジオメトリ再エンコードが必要」としてベクタを対象外にし、
「洪水が奇数ズームで消えることは残るが、同じ領域にキキクル3種の面が出るため危険の
見落としには直結しない。ベクタ対応が必要になった時点で別タスクへ切り出す」と保留していた。
1を直すとラスタ3種は奇数ズームでも出るようになるため、**保留の前提（3種が出るから
気づける）が崩れ、洪水だけが消える非対称が残る**。ユーザー報告の「vectorとrasterの違い」は
これにあたる。

## 対応

### 在否インデックスへ補間ズームを載せる（`jma_tile_prewarm_service.py`）

補間結果が空になるのは親が空のときだけなので、**中身のある親タイルの4象限をそのまま
子ズームの中身ありとして載せる**（`_with_interpolated_zooms`）。プリウォームは既に親を
取得済みのため追加の取得は発生せず、平常時（どのズームにも中身が無い）は空のままなので
「取りに行かせない」効果も保たれる。

### ベクタタイルの補間を実装する（`jma_tile_interpolation.py`）

`crop_and_upscale_mvt`を追加し、ラスタと同じ経路（`api/routers/jma_tile.py`）でベクタも
補間する。画像と違い「拡大」という操作が無いため、親タイルの該当象限を切り出して
タイル内座標を2倍にし、同じextentのタイルとしてエンコードし直す。属性はそのまま引き継ぐ
（危険度`level`は切り出しで変わらない）。依存は既存の`mapbox-vector-tile`・`shapely`のみで、
追加は不要だった。

**上下の取り違えに注意が要る**: デコード結果の座標系はy軸が上向き（ライブラリの
`y_coord_down`既定値）なのに対し、象限はタイルXY（yは南向き）で表される。4象限すべてを
固定するテストを置いてある。線がタイルの継ぎ目で途切れないよう、切り出しは境界の外側へ
extentの1/128だけ余白を残す。象限に地物が1つも掛からなければ0バイト（＝地物なし）を返し、
これも書き戻して次回以降の上流問い合わせを省く。

Content-Typeは親タイルのものをそのまま使う（配信元は`.pbf`に`binary/octet-stream`を返す。
拡張子から推測せず、実際に返ってきた値を引き継ぐ）。

## 検証

- 配信元の挙動を一次情報で確認: `risk/targetTimes.json`の全37行で要素集合・basetimeが揃って
  おり、**要素ごとの時刻ずれは無い**（データ側の時間差という当初の仮説は否定）。
  タイルは偶数ズーム200・奇数ズーム404。
- 本番の`GET /api/jma-tile-index`を実取得し、奇数ズームが1件も載っていないことを確認。
- backend 1727 passed（`-m "not postgis"`）・`ruff check` クリーン。MVT補間は4象限の
  切り出し位置・座標の2倍化・属性の引き継ぎ・地物なしの0バイト応答をテストで固定。

## 残っている差（対応しない）

ラスタは新しいタイルが到着するまで前のフレームを表示し続ける（`raster-fade-duration`）
一方、ベクタは`setTiles`で即座に消える。basetimeが進む10分ごとに一瞬だけ洪水線が消える
差は残るが、これは「古い危険度が残り続ける」方向ではなく、実害が無いため触らない。
