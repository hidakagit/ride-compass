# T1158. 目的地モードでbackendが最速の基準線を先頭に固定するため、実験スロットの代表と比較パネルの説明が「最も易しい候補」と食い違う

## 背景

周期レビュー第13回（2026-09-26）の指摘。性質: 片側だけの修正（再発。is_fastestのコメントの食い違いはT904・T949で4回直された）。backendは目的地モードで所要時間が最短の基準線（road_graph_engine.select_fastest_route、所要時間で探索）を1本加えて先頭に固定し、is_fastestを付ける（route_generator.py:492-525。492行のコメントは「距離だけで選んだ」と古い）。T1126で画面の候補一覧は所要時間順に並べ直すようになり、表示には先頭固定が効かない。一方、研究モードの実験スロットの代表はbackendの並びの先頭（page.tsx:732、types/experimentSlot.ts:11「overall_difficulty昇順の先頭」）で、比較パネルの説明（ComparisonPanel.tsx:118「各列はその回の先頭候補（最も易しい1本）」）も同じ前提。目的地モードではこの先頭が基準線になり、最も易しい候補ではない。先頭固定を残す理由があるかを確かめ、無ければ外す（残すなら代表を明示的に難易度最小で選ぶ）。コメントを直す。

## 対応方針（2026-09-27、origin/master 8dedc5f2 で確かめた）

先頭固定が担っていた役割を2つに分けて、それぞれ読み手がいるかをgrepで確かめた。

1. **並びの位置（先頭）**: 読み手は無い。画面の一覧は`routeTabLabel.ts: orderByDuration`で所要時間順に並べ直し、
   基準線も`fastestRouteId`で一覧の中から自分で決める。frontendで`is_fastest`を読む実装は0件
   （`frontend/src`のgrepで当たるのは`routeTabLabel.ts`の「見ない」という注記と、テストの足場`routeFixtures.ts`だけ）。
   backendの並びの先頭を読むのは実験スロットの代表（`page.tsx: handleGenerate`の`candidates[0]`）だけで、
   それは「最も易しい候補」を期待している——先頭固定はこの唯一の読み手を裏切っていた。
2. **件数を切るときに基準線を残すこと**: 必要。`select_via_nodes`が`max_routes`件を返し、基準線が別経路なら1本増えるため
   必ず1本切る。基準線が難易度で最下位だと、固定を外しただけでは基準線が切られ、一覧の中の「+N分」の基準が
   本当の時間最短でなくなる。

したがって**先頭固定は外し、切るときの保証だけを残す**（記録の選択肢「残すなら代表を明示的に難易度最小で選ぶ」は採らない——
読み手のいない並びを保ったうえで、読み手の側に並びを無視する処理を足すことになり、保守する量が増えるだけ）。
これでbackendの並びは周回・目的地とも「総合難易度の昇順、先頭が最も易しい候補」の1つの契約になり、
frontendの注記（`page.tsx`・`experimentSlot.ts`・`ComparisonPanel.tsx`の説明）は書き換えずに正しくなる。

`max_routes`が1のときは従来どおり基準線を残さない（比べる相手が無く、残すと軸の重みが結果に現れない）。
