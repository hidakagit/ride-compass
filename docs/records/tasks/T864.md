# T864. 軸の行データは本番を正本にし、反映手順を2段にする

状態: 完了（2026-09-23、方針は既に実現済み）

未着手（2026-09-15起票、着手は別の機会）

規模: M

## 背景

DBの変更作業が複雑という指摘（ユーザー、2026-09-15）。調べた結果、複雑さはDDL側ではなく
**行データの反映手順**にある。

- `backend/migrations/`はDDLのみで、軸の行データは既に`axis_admin`のAPI経由が正。
  DDLをAPI化するのは逆効果（履歴とレビューが無くなり、まっさらなDBから再構築する経路が
  成立しなくなる）。
- 行データの手順は「開発DBをAPIで直す → 本番DBにも同じことをする → スナップショットを
  手で再ダンプしてコミット」の3段で、すべて人の記憶に依存する。開発だけ直して本番が
  取り残された事故が6回記録されている（[deployment-sync.md](../../conventions/deployment-sync.md)）。

## 方針（未着手）

軸の変更は**本番に対して行い**、開発DBは`bootstrap_fresh_db.py`で本番スナップショットから
入れ替えるだけにする。「開発だけ直して本番を忘れる」型が構造的に起こりえなくなり、手順は
「本番で直す → ダンプしてコミット」の2段になる。

## 保留することで何が続くか

上記の3段手順と、それを支える自己申告のルール（deployment-sync.md）が残り続ける。反映漏れは
検知器が無く周期レビューでも拾えないため、次に軸を触ったときに7回目が起きうる。

**ユーザー決定（2026-09-23）**: 完了として閉じる。方針は別の変更で既に実現している——`docs/conventions/deployment-sync.md`
「本番へ効かせたい軸定義の変更は、本番の管理画面で行う」が、DBは環境ごとに独立しその環境の管理画面がメンテナンスする・
リポジトリは軸の写しを持たない（再ダンプの手順は無い）と定めており、手順は「本番の管理画面で直す」の1段になっている。

## 台帳にあった補足

- 2026-09-15起票、着手は別の機会。複雑さはDDL側ではなく行データの反映手順にある。開発DBを直してから本番へ持っていく順序をやめ、本番を正本にして開発はスナップショットから入れ替える
