# T1024. 正本が、存在しない機構を1本道の追加点として名指ししている

状態: 完了（2026-09-23）

## 背景

T1001段階Aで動的気象レイヤーの描画を`features/map/scene/groups/weather.ts`へ移したが、
**正本が旧機構を現行仕様として指したまま**になっている。

- `docs/architecture/design-principles.md`の**構造仕様8（1本道の追加点）の本文**が、
  新しい動的要素の登録点として`DYNAMIC_WEATHER_RENDERERS`を名指しする。この綴りは
  リポジトリに定義が0件（`ensureDynamicWeatherLayer`・`applyDynamicWeatherState`も同じ）。
- `docs/modules/frontend/dynamic-weather-layers.md`の対象ファイル表・制御フロー図・
  **「新しい動的要素を追加する1本道」の手順**が、同じ3つの綴りを前提にしている。
- `docs/modules/frontend/static-map-layers.md`の「レイヤーを1枚足すときに触る場所」が
  「`MapView.tsx`へ描画コードを書く」と指示する。描画は`scene/groups/*`へ移っている。
  同文書の対象ファイル表の`MapView.tsx`行は「並列トラック分離・下敷き表現箇所のみ」と
  書くが、**同じ文書の本文**はそれらを`scene/groups/roadLines.ts`・`axisLines.ts`に
  帰属させている（文書が自分自身と矛盾している）。
- `docs/modules/backend/static-road-attributes.md`は、路面語彙とフロント表示グループの
  突き合わせを「フロント側の不変条件テスト（`scene/groups/declarations.test.ts`）が行う」と
  現在形で書く。このファイルは`0155a877`で削除され、同じ主張はbackendの
  `test_primary_attribute_display.py`が源泉の側で持っている（移行自体は正しい）。
- `backend/app/domain/road.py`のコメントが「タグを増減したらフロントのグループ定義の
  追従が要る」と述べるが、表示行は`material_catalog.py`の`display_axes`が持ち、
  フロントは生成物を読むだけで追従作業は発生しない。
- `frontend/src/types/generated/surface-tags.json`は、生成物のうち**唯一フロント側の
  消費者が0**。書き出しているだけで誰も読んでいない。

**これは文言の誤りではなく、手順書が実行不能だという問題である。** 構造仕様8は
「新しい機構を別方式で作る」ことを禁じているが、その手順どおりに進めようとすると
登録点が存在せず、結局その人が置き場を自分で決めることになる。正本自身が、
自分が禁じている事態を誘発している。

## 対応方針

1. 構造仕様8の登録点を現行へ訂正する（データ層モジュール新設 → `WEATHER_ELEMENTS`へ1件 →
   地図チップ登録）。
2. `dynamic-weather-layers.md`の対象ファイル表・制御フロー図・追加手順を
   `scene/groups/weather.ts`基準へ書き直す。
3. `static-map-layers.md`の「触る場所」と、対象ファイル表の`MapView.tsx`行を、
   同文書の本文と一致させる。
4. `static-road-attributes.md`の検査の帰属をbackendの後継テストへ直す。
5. `road.py`のコメントから、発生しない追従作業の指示を落とす。
6. `surface-tags.json`は「読む側を作る」か「書き出しをやめる」かを決める。消費者0の
   生成物を残すと、源泉を変えたときに誰も気づかない出力が増える。
7. frontendに残る旧綴りのコメントを落とす（撤去は`comments.md`の判定木を通す）。

**検知器は足さない。** CLAUDE.md「実装そのものを検査対象にするものは足さない」に当たり、
写し（シンボル名の一覧）を抱えて実装が変わった瞬間に黙って死ぬ。ここはT1022の導出Aと
母集団が重なるので、そちらの一掃で綴りは拾える。**このタスクが扱うのは「手順が実行
できるか」という、綴りの一致では測れない側**である。

## 完了条件

- **新しい動的気象要素を1つ足す手順を、文書だけを読んで最後まで辿れる。** 確かめ方:
  既存の要素を1つ選び、その要素がいま実際に登録されている場所を、文書の手順だけを頼りに
  特定できるかを辿る。手順が指す場所と実装が置かれている場所が一致すれば通過。
- 構造仕様8が名指しする登録点が、リポジトリに実在する。
- `static-map-layers.md`の対象ファイル表と本文の帰属が一致している。
- `surface-tags.json`の扱いを決め、決定をこのエントリへ書いた。

### 直したもの

- **構造仕様8**（`design-principles.md`）の登録点を`DYNAMIC_WEATHER_RENDERERS`から
  `features/map/scene/groups/weather.ts: WEATHER_ELEMENTS`へ直した。
- **`dynamic-weather-layers.md`**: 対象ファイル表（`MapView.tsx`の行→`scene/groups/weather.ts`・
  `scene/applyToMap.ts`の行）、制御フロー図（宣言→`applyMapScene`の道）、追加の1本道（チップを
  足すときだけ`WEATHER_LAYER_GROUPS`へ1語、という条件付きの段に直した）、重なり順の決まり方
  （辞書のキー順→段＋`WEATHER_ELEMENTS`の並び順）、`jmatile://`を付ける場所、その他の旧綴り
  （`applyDynamicWeatherState`・`DynamicWeatherMarkSpec`・`DYNAMIC_WEATHER_LAYER_IDS`）。
- **`static-map-layers.md`**: 「レイヤーを1枚足すときに触る場所」を、描画コードではなく家族の
  宣言（`scene/groups/*.ts`）へ足す形に直した。対象ファイル表の`MapView.tsx`行を実際の責務
  （sceneの入力への配線・押された地物の判定・データ取得状態の算出元）へ直し、どの表にも
  無かった`scene/mapScene.ts`・`scene/applyMapScene.ts`の行を足した。「表示層の実装」節の
  帰属も`MapView.tsx`から`scene/applyMapScene.ts`へ直した（本文と表の矛盾の解消）。
- **`static-road-attributes.md`**: 路面語彙と表示行の突き合わせの帰属を、削除済みの
  `declarations.test.ts`からbackendの`tests/test_primary_attribute_display.py`へ直した。
  「表示グルーピング」の定義場所も`roadLines.ts: ROAD_TRACKS`（生成物を絞るだけ）から
  `material_catalog.py`の`display_axes`へ直した。
- **`road.py`のコメント**: 「フロントのグループ定義の追従が要る」を落とし、表示行を揃える
  場所と、それを見るテストを書いた。
- **frontend・backendに残る旧綴りのコメント**を、判定木に通して直した（下表）。
- `map-axis-coloring.md`の旧綴りも直した。

### `surface-tags.json`の扱い（完了条件4の決定）

**書き出しをやめ、生成物を削除した。** フロントの本番・テストのどちらにも読み手が無い
（`grep -rn "surface-tags" frontend/src frontend/e2e frontend/scripts`で0件）。読む側を作る案は
採らない——路面の正準分類と表示行の突き合わせは、すでにbackendの
`test_primary_attribute_display.py`が源泉の側で持っており、フロントで同じ突き合わせを持つと
同じ不変条件を2箇所で見ることになる。`export_openapi.py`の書き出しと、その周りの
「`roadFilterAxes.test.ts`がこのJSONと突き合わせる」というコメント（どちらのファイルも
存在しない）を同時に落とした。
