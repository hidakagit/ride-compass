# T1202. 数値予報モデルの値を「予報」と呼ばず「モデルの計算値」と出し、「今日の見通し」の自前の天気アイコンを外す

状態: 完了（2026-09-27起票・完了）

## 背景

T1053で、気象庁の公式の文書が「予報と称して出す」ことと「数値予報から天気を自動で計算して出す」ことを予報業務の許可の対象と書いており、有償・無償で区別しないと分かった。ユーザーは気象庁の答えまでこの2点をやめると決めた（T1053-msm-display-until-answer (1)、2026-09-27）。

ユーザーの答え(1)の文面: 「公式の文書が「許可が要る」と書いている形だけ今やめる: 数値予報モデルの値を「予報」と呼ばず
「モデルの計算値（予報ではなく誤差を含みうる）」と出し、「今日の見通し」の天気アイコン（こちらで決めた晴れ・くもり・雨・雪）を
外す。数字と補間・ルートの風は答えまで続ける」。

## 前提の確認（2026-09-27、担当F-forecast、origin/master 54611b65）

- ダッシュボードにT1202の件は無かった。T1053の件は照会（`T1053-jma-inquiry`、未送信）・答え（`T1053-msm-display-until-answer`、
  答え(1)・送った・取り込み待ち）・件名の3件。
- 本番DBの軸定義（`axis_definitions`の`label`・`description`・`chip_label`・`panel_hint`・`shape_params`・帯の名前）に「予報」の語は
  無い（`backend/scripts/run_probe.py`で読み取り。風の軸は「風」「向かい風が弱いほど易しい」）。DBを書き換える作業は無い。

## 母集団の決め方

材料の出どころ（MSM）から、値が画面へ届く経路を辿って列挙した。MSMを読むのは`msm_client.read_series`だけで、
呼ぶのは`WeatherService`の3つのメソッド（`grep read_series|get_conditions|get_wind_forecast_lattice|get_wind_grid backend/app`）:

| 経路 | 画面 | 「予報」の呼び方・自前の天気 |
|---|---|---|
| `get_conditions` → `GET /api/weather` | 「今日」のパネル（`TodayOutlook.tsx`） | 見出し「今日の見通し」、2時間おきのコマの天気アイコン（`derive_weather_code`が雲量・降水量・気温から導く） |
| `get_wind_grid` → `/api/weather/wind-grid(-detail)` | 地図の「風」「降水」チップ（`mapLayers.ts`の説明） | 「風向・風速予報」「延長予報」「格子点予報」「モデル予報」「予報1時間刻み」「配信中の予報の長さ」 |
| `get_wind_forecast_lattice`（と出発時点の値として`get_conditions`） → ルート生成 | 区間の風（`SegmentWind.tsx`）・所要時間の注記（`RouteAxisProfile.tsx`）・風の材料の説明（`material_catalog.py`→生成物`material-catalog.json`、道の詳細・凡例・軸スタジオ） | 「12:00の予報」「予報の先を延ばして使用」「予報の格子点」「風の予報を使えなかった」「出発時刻の気象予報」 |
| `get_wind_forecast_lattice` → `WindWayService`（ルートを出す前の地図の風の塗り） | 風の軸（本番DBの文言）・風の材料の説明 | DBには無し。材料の説明は上の行と同じ |

画面の文言は`frontend/src`（生成物を含む）と`frontend/public`を「予報」「予想」「見通し」「forecast」でgrepし、上の経路に
当たるものと当たらないもの（気象庁が出した降水ナウキャスト・降水短時間予報・河川氾濫予報・「到達予想」等）を1件ずつ分けた。

## 決めたこと

- **パネルの見出しも「今日の見通し」から「今日のモデルの計算値」へ変えた**。「見通し」は予報と同じ意味で読める語で、
  気象庁の説明は「予報と称して」を言葉の字面で区切っていない。入口のボタンは「今日」のまま。見出しの下へ
  「気象庁の数値予報モデル（MSM）の計算値です。予報ではなく、誤差を含みえます。」を出す（公式の説明の推奨する明示）。
  コマの欄の名前は、天気が無くなるので「天気の流れ」から「2時間ごと」へ。
- **天気の導出は消した（置き換えない）**: `derive_weather_code`の雲量の段は読み手が無くなり、雨/雪と強さの段は
  アメダスの`derive_observed_weather_code`だけが使うのでそちらへ移した。`WeatherConditions.weather_code`・`is_day`・
  `WeatherPeriodOutlook.weather_code`、画面の`getWeatherCodeDisplay`も消した（T1053段階2の「範囲外で見つけたもの」の
  読み手のいない`weather_code`・`is_day`はこれで片付いた）。
- **雲量の同期をやめた**: 雲量を読むのは天気の導出だけだった。`FORECAST_VARIABLES`から外すと、同期と読み出しで
  扱うチャンクが1変数ぶん（1ファイル十数MB×1〜2）減る。外した変数のチャンクが本番の置き場に残らないよう、
  `_prune`を変数の一覧ではなく置き場の全ディレクトリを見る形にした（本番の`cloud_cover/`は次の同期で空になる）。
- **対象外にしたもの**（理由つき）:
  - 管理画面（`/admin`、Basic認証の内側）のシステム状況の「予報（MSM）」「予報の残り」: 利用者へ値を出す画面ではなく、
    同期の鮮度の運用表示。不特定多数へ提供していない。
  - コードの識別子・コメント・ログ・APIの説明文（`forecast_at`・`get_wind_forecast_lattice`・`/docs`に出るdocstring等）:
    画面に出る文言ではない。触ったファイルのうち、消した・変えたものを指していたコメントだけ直した。
  - 雨の材料の説明「出発時刻の予報では延ばさず」: アメダスの観測の材料で、MSMの値を予報と呼んでいない。
  - `domain/weather_display.py: WEATHER_CATEGORIES`の分類の表: WMOのコードの対訳で、導出の一覧ではない
    （霧・雷雨は以前から導かれていない）。アメダスの天気アイコンが使う。
