# T980. 一次属性の語彙が材料カタログと別に宣言されている 規模M

状態: 未完了

未着手（2026-09-20起票）。

## 背景

評価軸（DB）が参照するのは**材料だけ**である。一次属性idは軸が宣言せず、
`domain/axis_display.py: primary_attribute_ids_for()`が軸の材料を`MATERIAL_CATALOG`で
引いて`MaterialSpec.primary_attribute_id`を集めることで導出される。

にもかかわらず、一次属性の語彙そのものは`domain/registry_defaults.py:
_register_primary_attributes()`に18個のリテラルとして別に並んでいる。

実測（2026-09-20）:

| | 件数 |
|---|---|
| `registry_defaults`が宣言 | 18 |
| `MATERIAL_CATALOG`の`primary_attribute_id`から導ける | 15 |
| どの材料も指さない | 3（`bicycle_access`・`geometry`・`supply_poi`） |
| 宣言に無いのに材料が使う | 0 |

さらにフロントは同じ18個を**手書きで2つの集合へ分けて持つ**
（`primaryAttributes.ts: PRIMARY_ATTRIBUTE_LAYER_IDS` 10件 ＋
`PRIMARY_ATTRIBUTES_WITHOUT_LAYER` 8件）。ドリフト検知テストはあるが、語彙は3箇所に散る。

## 何が問題か

**材料を1つ足すときに、その材料が指す一次属性が語彙に無ければ登録が失敗する**
（`register_axis`が`inputs`を語彙で検証する）。材料の宣言だけで完結せず、別ファイルへ
1行足す手順が要る。手順を知らないと、材料を足した時点では通り、軸が公開された瞬間に落ちる。

3つの孤児（どの材料も指さない一次属性）は、その手順が片方向にしか守られていないことの
表れである——語彙からは消されない。

## あるべき形

一次属性は材料の性質なので、**`material_catalog.py`が唯一の正本**にする。

- ラベルは`MaterialSpec.primary_attribute_id`の隣で宣言する（`registry_defaults`の
  リテラル列は消える）
- 語彙は`MATERIAL_CATALOG`から導出する（`register_primary_attribute`の検証は、
  導出した集合に対して行う）
- 孤児3件は、対応する材料が無いことを確認して消すか、材料側へ移す。
  **`supply_poi`はフロントの地図レイヤー（補給・休憩POI）が使っているため、
  消す前に読み手を確認すること**

## 完了条件

- `_register_primary_attributes()`が無くなり、語彙が`MATERIAL_CATALOG`から導出される
- 材料を1つ足したとき、その材料の宣言だけで一次属性が揃う（別ファイルへの追記が要らない）
- フロントの手書き2集合が、生成物との突き合わせで完全性を検査されている
  （現状のドリフト検知テストが何を保証しているかを先に読むこと）

## 経緯

T970段階Eで`axis-catalog.json`（DB状態の写し）を撤去する際、そこに同居していた
`primary_attributes`の由来を調べて判明した。段階Eでは語彙の構造に触れず、フロントが
読んでいたラベルの取り出し先を移すだけに留めた。
