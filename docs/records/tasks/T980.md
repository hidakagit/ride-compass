# T980. 一次属性の語彙が材料カタログと別に宣言されている 規模M

状態: 未完了

未着手（2026-09-20起票）。

## 背景

評価軸（DB）が参照するのは**材料だけ**である。一次属性idは軸が宣言せず、
`domain/axis_display.py: primary_attribute_ids_for()`が軸の材料を`MATERIAL_CATALOG`で
引いて`MaterialSpec.primary_attribute_id`を集めることで導出される。

にもかかわらず、一次属性の語彙そのものは`domain/registry_defaults.py:
_register_primary_attributes()`に18個のリテラルとして別に並んでいる。

実測（2026-09-20）:

| | 件数 |
|---|---|
| `registry_defaults`が宣言 | 18 |
| `MATERIAL_CATALOG`の`primary_attribute_id`から導ける | 15 |
| どの材料も指さない | 3（`bicycle_access`・`geometry`・`supply_poi`） |
| 宣言に無いのに材料が使う | 0 |

さらにフロントは同じ18個を**手書きで2つの集合へ分けて持つ**
（`primaryAttributes.ts: PRIMARY_ATTRIBUTE_LAYER_IDS` 10件 ＋
`PRIMARY_ATTRIBUTES_WITHOUT_LAYER` 8件）。ドリフト検知テストはあるが、語彙は3箇所に散る。

## 何が問題か

**材料を1つ足すときに、その材料が指す一次属性が語彙に無ければ登録が失敗する**
（`register_axis`が`inputs`を語彙で検証する）。材料の宣言だけで完結せず、別ファイルへ
1行足す手順が要る。手順を知らないと、材料を足した時点では通り、軸が公開された瞬間に落ちる。

3つの孤児（どの材料も指さない一次属性）は、その手順が片方向にしか守られていないことの
表れである——語彙からは消されない。

## あるべき形

一次属性は材料の性質なので、**`material_catalog.py`が唯一の正本**にする。

- ラベルは`MaterialSpec.primary_attribute_id`の隣で宣言する（`registry_defaults`の
  リテラル列は消える）
- 語彙は`MATERIAL_CATALOG`から導出する（`register_primary_attribute`の検証は、
  導出した集合に対して行う）
- 孤児3件は、対応する材料が無いことを確認して消すか、材料側へ移す。
  **`supply_poi`はフロントの地図レイヤー（補給・休憩POI）が使っているため、
  消す前に読み手を確認すること**

## 完了条件

- `_register_primary_attributes()`が無くなり、語彙が`MATERIAL_CATALOG`から導出される
- 材料を1つ足したとき、その材料の宣言だけで一次属性が揃う（別ファイルへの追記が要らない）
- フロントの手書き2集合が、生成物との突き合わせで完全性を検査されている
  （現状のドリフト検知テストが何を保証しているかを先に読むこと）

## 段階A（2026-09-24、担当 W-vocab）: 着手時点で既に済んでいた

### 方針

振り出しの指示は「一次属性のラベルを`MaterialSpec.primary_attribute_id`の隣で宣言し、語彙を
`MATERIAL_CATALOG`から導き、`_register_primary_attributes()`を消す。孤児3件は読み手を数えてから
処置する。frontendには触らない」だった。着手前に今のコードを数えたところ、前提が変わっていた。

- 起票の翌日のコミット ddc18297b「一次属性の語彙を材料カタログから導く（T980）」で、backend側は
  既に直っていた（この記録だけが「未着手」のまま残っていた）。`_register_primary_attributes()`は
  消え、語彙は`material_catalog.py`へ移り、`register_defaults()`が材料の指す一次属性の欠落を
  登録時に落とす。孤児のうち`bicycle_access`・`geometry`はこのとき削除された。
- その後 T1001 段階A（c2e73ce0）で、語彙はラベルだけの表から`PRIMARY_ATTRIBUTES`
  （`PrimaryAttributeSpec`の並び。名前・幾何・地図の束ね方・タイルの系統を持つ）になり、
  frontendの手書き2集合（`PRIMARY_ATTRIBUTE_LAYER_IDS`・`PRIMARY_ATTRIBUTES_WITHOUT_LAYER`）は
  消えて、地図レイヤーは生成物`mapDisplay.layerIds`から導かれるようになった。
- 「ラベルを`MaterialSpec`の隣で宣言する」形は、今の形より悪い。一次属性は複数の材料に共有され
  （`landcover`は8材料、`cycleway`は5材料が指す）、材料を持たない属性（`supply_poi`）もあるため、
  材料側に書くと同じ宣言を材料の数だけ写すことになる。一次属性の側に1回だけ書き、材料はidで指す
  今の形を正とする。

したがってこの段階ではコードを変えず、設計書の抜け（語彙の置き場と、欠落がいつ落ちるかが
`docs/modules/backend/axis-studio.md`に書かれていなかった）だけを埋めた。

### 実測（2026-09-24、origin/master b06c44a1）

母集団: `material_catalog.PRIMARY_ATTRIBUTES`の`attr_id`（宣言）と、`MATERIAL_CATALOG`の全材料の
`primary_attribute_id`のうちNoneでないもの（材料が指す）。scratchpadのPythonで両方を読んで比べた。

| | 件数 |
|---|---|
| 宣言（重複なし） | 15 |
| 材料が指す | 14 |
| どの材料も指さない | 1（`supply_poi`） |
| 宣言に無いのに材料が指す | 0 |

効いていることの確認: `PRIMARY_ATTRIBUTES`から`tunnel`を抜いて`register_defaults()`を呼ぶと
`ValueError: 材料が指す一次属性がPRIMARY_ATTRIBUTESにありません: ['tunnel']`で落ちた。実宣言では15件が登録された。

孤児3件の読み手（`git grep`でリポジトリ全体。`docs/records/`を除く。backend・frontend/src・
frontend/e2e・frontend/e2e-live・生成物を含む）:

- `bicycle_access`: 0件（語「bicycle_access」・ラベル「自転車通行可否」とも）。削除済み
- `geometry`: 0件（`attr_id`としての出現・ラベル「区間形状」とも。語「geometry」単独は
  `PrimaryAttributeSpec.geometry`フィールド等と区別できないためこの2形で数えた）。削除済み
- `supply_poi`: 本番コード1（`frontend/src/features/map/layers/mapLayers.ts`が名前と分類の一覧を読む）・
  生成物2（`mapDisplay.ts`・`primaryAttributes.ts`）・テスト4（backend `test_primary_attribute_display.py`、
  frontend `mapLayers.test.ts`・`MapOverlayControls.test.tsx`・`MapView.state.contract.test.ts`）。
  `test_tag_classification.py`の一致は語「supply_point」の部分一致で読み手ではない。地図の分類として
  使われているため消せない。材料を持たない＝評価に効かない一次属性として、宣言に残すのが今の形

### 完了条件に対する状態

1. `_register_primary_attributes()`は無く、語彙の正本は`material_catalog.py`にある。「導出」ではなく
   同じファイルの宣言と、材料が指す集合の包含の検査である（上の理由で導出にはしない）
2. 既存の一次属性を指す材料は材料の宣言だけで揃う。新しい一次属性は、名前・幾何・地図の束ね方を
   持つため宣言が要るが、同じファイルで、忘れればビルドとテストで落ちる
3. frontendの手書き2集合は既に無く、検査する対象が無い
