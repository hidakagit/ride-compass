## 背景

2026-09-25 15:51・15:56（UTC）、T1108の生成時間の計測（本番コンテナ内からAPIで都心35.68,139.76の周回40km×3→80km×3…を順に投げるプローブ）の最中に、本番のridecompass-backendが2回OOMで強制終了・再起動した（docker events oom/die 137、dmesg: Memory cgroup out of memory, anon-rss 約6.2GB、上限 mem_limit=6442450944）。2回目は再起動直後の最初の生成（プローブの順番では都心40km）の最中で、直前のログは prepare search_statics build edges=2727110 statics_cached=False。開発DBでT1106・T1107・T1108の版を同じ条件（10kmの周回）で比べると、Pythonの割り当ての最大は94.6/90.7/94.9MB・作業セットのピークは332/325/332MBで差が無く、今回の変更ではなく以前からの問題とみられる（開発DBの道路は約9km×11kmで本番の大きさは再現できない。手元PCは総メモリ7.9GB）。段階1（S）: 配信中のコンテナとは別の一時コンテナ（同じイメージ・同じ上限6GB）で都心40km・80kmの周回を1回ずつ流し、段階ごと（探索素材の構築・前向き木・合成の時刻ビン・候補の評価）のメモリ（tracemallocの最大とプロセスのRSS）を測る。配信中のコンテナで重い生成を流して測らない（今回それで2回落とした）。段階2以降は計測の結果で決める。

## 段階2の方針（問いと答え）

**問いと答え（ユーザー 2026-09-26、会話とダッシュボード）**:
- 計測用の一時コンテナの上限→**上限6GB、先に残っていた計測用コンテナ2つを止める**。
- 段階2をどう進めるか（安全弁を先に入れて作り直す／作り直しだけ／安全弁だけ）→途中で「根本対策はできないの？同じ地点でも
  距離が違ったら全タイル取り直し？」と問われ、タイル単位の素材は再利用されるが結合した素材・探索用グラフ一式が範囲ごとに
  作り直されること、根本対策は取込範囲全体の道路網を1回だけ番号と配列で持ち範囲を切り出して使う作り直しであることを答えた。
  →**安全弁（段階2）→作り直し（段階3）の順で進める**。

## 段階2: 安全弁（2026-09-26）

- `GraphService.get_search_materials_for_bbox`（全生成経路とプレビューが通る唯一の入口）で、素材を読む前にbboxを覆うタイルの
  外接矩形に触れる区間の数を数え（`RoadGraphRepository.count_edges_in_bbox`）、`MAX_SEARCH_ROAD_EDGES`（60万）を超えれば
  `SearchAreaTooLargeError`を送出する。60万は都心40km（52.7万）の実測から、1回の生成を約3GBに収める値。都心40km・郊外80kmは通り、
  都心60km以上・郊外120kmは断られる。
- 生成器の4つの入口に写経されていた「準備して、作れなければ理由を残す」処理を`RouteGenerator._prepare`へまとめ、範囲超過は
  「探索範囲の道路が多すぎるため…距離を短くするか、経由地・目的地を起点に近づけて」の理由付きで候補0件にする。区間確認API
  （画面からは使っていない）は422。
- **守れないもの**: タイル単位の素材キャッシュは件数（2,000枚）でしか抑えておらず、範囲ごとの探索用グラフも件数（64・16件）で
  しか抑えていない。範囲を変えながら生成が続くと、上限の内側でも常駐量は積み上がる（9/25のOOMは1人が40km→80kmと順に投げたとき）。
  同時実行（プロセス全体で2本）で別の範囲を読むと、合わせて6GBに届きうる。これらは段階3で扱う。

## 段階3（未着手）: 探索素材の持ち方の作り直し

取込範囲全体の道路網を1回だけ整数の番号と列の配列で持ち、リクエストは範囲を切り出して使う。Edgeごとの文字列の鍵・`LeanEdge`・
鍵を引く辞書・タイルの結合で作る写しをなくし、範囲ごとに作り直す探索用グラフ・索引・ターン構造の複製もなくす。本番の`road_edges`は
約258万行（向き付きで約500万Edge）。キャッシュはバイト数で抑える。済んだら同じプローブ（40km・80km、使い捨てコンテナ）で測り直し、
安全弁の上限を広げるか外す。設計は着手前に案として出す。
