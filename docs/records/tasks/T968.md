# T968. デッドコードと不要なテストを総整理し、残すものをあるべき場所へ置く 規模L

状態: 未完了

着手中（2026-09-20起票、2026-09-21にユーザー指示で枠を広げた）

## このタスクが何をするか

3つを1つの作業として行う。**分けない**——同じコードとテストを3回読むことになるため。

1. **消す**: 本番の入力から到達しない実装と、それを生かしているだけのテスト。
2. **移す**: 残すと決めたテストを、あるべき場所へ置き直す。必要なテストでも、層に合わない
   場所・合わない粒度にあると、実装を直すたびに関係ない場所が落ちる。
3. **点検する**: 層ごとの責務（DB=データ／app=ふるまい／テスト=今のふるまい）が守られて
   いるか。**現行追認ではない**——守られていない箇所は、制約を正しい層へ移して分岐を消す。

起票時（2026-09-20）は3の点検だけの枠だった。2026-09-21のユーザー指示で1と2を含め、
[T963](T963.md)の「本番の入口からの到達可能性グラフ」「デッドコードの機械的な検知」
「同じ値を2か所で持っている検知」を段階1〜2として取り込んでいる。T963には`metrics`の
増減傾向を見せる話だけが残る。

## 守るべき線

- **DB**: データの制約（NOT NULL・FK・UNIQUE・CHECK）。派生表は親への参照を持つ。
- **app**: ふるまいの制約。DBが保証している前提を再確認しない。
- **テスト**: 「今」のふるまいの網羅。appにテスト専用の口を作らせない。

崩れると、DBが緩いぶんをappが吸収し、appの吸収をテストが固定し、直すと全部が同時に
落ちるため誰も直せなくなる。

きっかけは[T956](T956.md)の2つの実測。`road_edges.osm_way_id`にFKもNOT NULLも無く、
app側の材料の値式10本が`CASE WHEN w.osm_way_id IS NULL THEN NULL ELSE ...`で毎回吸収して
いた（本番の違反行は0件、兄弟の派生表5本は同じFKを既に持っていた）。同じ点検で、
`app/domain/material_sql.py`にテストからしか呼ばれない関数を1本足していたことも分かった
（`folds_tag_absence_to_false`、同タスク内で撤去）。

## 進め方（2026-09-21ユーザー指示）

**機械的に洗い出せる範囲は機械で洗い出す。そこで出ないものは、泥臭く読むしかない。**
両方やる。機械の側だけで終えると、動的参照やSQL文字列の向こう側に残ったものがそのまま
生き残る。読む側だけでやると、backend 165＋frontend 181ファイルを人の集中力に賭ける
ことになる。

境界をはっきりさせる。

- **機械で出る**: 本番の入口から辿れない定義（段階1）、同名フィールドを多く共有する
  dataclass（段階2）、FK/NOT NULLの無い派生列とそれを吸収する分岐（段階3）、テストから
  しか参照されない口・テスト同士の直接依存・そのテストだけが通す行が0行のテスト（段階4）、
  テストと実装の対応が取れないファイル・環境が過剰なテスト（段階5）。
- **機械では出ない**: 生きている経路の中にある無駄（通っているが結果を変えない分岐・
  二重の正規化・同じことを2度やる段）、写経された骨格、テストが検査している「つもり」の
  ずれ。これは段階8でモジュール単位に読む。

**読む側は必ず記録を残す**——どのモジュールをいつ読み、何を見つけ、何を見つけなかったかを
書く。書かないと、途中で止まったときに次に読む人が最初から読み直すことになる。

## 段階

**段階ごとにコミットする。** 段階1の出方を確かめてから段階6（frontend）へ進む——
到達可能性の作り方はbackendとfrontendで別物になるため、先に出方の当たりを付ける。

### 段階1: backendの到達可能性グラフを作る

**「怪しそうな書き方」をgrepして母集団を作らない。** 症状や少数の事例の特徴から母集団を
決めると、そこに無いものは定義上見つからない。本番の入力の源流から呼び出しをたどり、
たどり着かないものを孤立点として出す。

源流（エントリポイント）はこのリポジトリでは有限に列挙できる。

- FastAPIのルーター（`app/api/routers/`のエンドポイント）
- `main.py`のlifespanが起動時に走らせるもの
- バッチの`main()`（`app/batch/*.py`）
- `scripts/`・`benchmarks/`の実行可能スクリプト
- スケジュール実行（cron・ワークフロー）

**テストは源流に含めない。** 「誰からも呼ばれていない」ではなく「本番の入力から到達しない」
を出すのが目的で、テストを源流に入れるとテストが延命している実装が見えなくなる
（T956で`EdgeMaterialTable`が実際にそうなった）。

完全性は**インスタンスを全部見たこと**ではなく、次の2つに依る。どちらも短い表なので、
人が読んで「これが抜けている」と言える。

- (a) エントリポイントの列挙が閉じていること
- (b) 呼び出し辺の作り方が動的参照を取りこぼさないこと

(b)で取りこぼしやすいのは、このリポジトリが多用する**宣言テーブル経由の呼び出し**。
`MaterialSpec.extractor`のように関数をテーブルへ載せる形は静的解析から辺が見えない。
**宣言テーブル自体を列挙して辺として与える**（`MATERIAL_CATALOG`・`AXIS_DEFINITIONS`・
`MATERIAL_COVERAGE_SPECS`・`HARD_FILTER_HIGHWAY_TYPES`・`POI_COUNT_KINDS`等）。SQL文字列へ
埋め込まれた参照も辺として扱う。

**偽陽性は列挙の時点で除く**——FastAPIのルートハンドラ（デコレータ登録でコードからは
参照されない）とSQLAlchemyの宣言モデル（メタクラス経由で`Base.metadata`へ入る）。除かないと
出力の大半がこの2つで埋まる。

既知の実測（2026-09-20、T956の削除作業で判明）:

- テキストのgrepではdocstring・コメント内の言及を「使用」と数える
  （`compute_cost_from_axis_scores`が生きていると判定された）。ASTで名前の参照
  （`ast.Name`/`ast.Attribute`/`ast.alias`）だけを数えると同じ母集団から8件多く出た。
- ASTでも「app内から参照されるが本番の入口から到達しない」は出ない
  （`compute_edge_costs_bulk`）。**到達可能性の閉包が要る**のがこの段階の核心。
- app配下の公開定義685件に対し、テキストgrepで12件、ASTで23件（偽陽性を除くと15件）。

**検証**: T956で本番から外した実装を、作った仕組みが孤立点として挙げられるか。挙げられ
なければ辺の作り方（とくに宣言テーブル経由）が甘い。

### 段階2: 出た孤立点を1件ずつ処分する

出力を眺めて終わりにしない。1件ずつ**消す**か、**残す理由を観測できる形で書く**。

残してよいのは次を全部満たすときだけ（T963で決めた残す側の条件）。

1. いつ通るのかを言える
2. 通った回数が観測できる
3. 測って0件だったものは、その場で消す（別タスクへ送らない）

**同じ値を2か所で持っている形も併せて出す**。`EdgeMaterialArrays`と
`StaticEdgeScoreMatrix`が10個以上の同名フィールドを共有し、どちらもタイル単位で
キャッシュへ載るため同じ値をディスクに2組持っていた（T956）。「2つのdataclassが一定数
以上の同名フィールドを持つ」は`ast`で数えられる。

### 段階3: DBが持つべき制約をappが肩代わりしていないか

母集団の導出:

1. 派生表の親子関係を列挙する。`app/infrastructure/*_models.py`の`ForeignKey`宣言と、
   本番の`pg_constraint`（`contype='f'`）を突き合わせ、**モデル上は親を持つが
   DBに制約が無い／そもそもどちらにも無い**列を出す。
2. 1で出た列について、app側が「無いかもしれない」前提のコードを持っていないかを探す
   （`IS NULL THEN NULL`を含むSQL式、`or {}`、`is None`分岐、`COALESCE`の既定値）。
3. 制約を張れるかを本番データで測る（違反行数）。違反が0でなくても、**取込・正規化側で
   制約を守らせてから**張る——「本番データがこうだから張れない」で終えない。

本番DBへの適用まで終えて完了とする（[docs/conventions/deployment-sync.md]
(../../conventions/deployment-sync.md)に従い、開発DBのみの反映で完了扱いにしない）。

### 段階4: テストを消す（backend）

3つを別々に扱う。

1. **appにあるテスト専用の口**。母集団: `app/**`のモジュール直下の公開定義（先頭が`_`で
   ないもの）のうち、定義元以外の`app/`・`scripts/`・`benchmarks/`・`migrations/`から
   参照されず、`tests/`からのみ参照されるもの。2026-09-20時点で12件（再計測15件）。
   `reset_*`・`*_cache_size`のようにテストが状態を初期化・観測するための口は正当。
   `OsmRawPoiRow`・`decode_terrain_rgb_meters`・`osm_ways_to_way_specs`・
   `read_persisted_axis_revision`は実装に取り残された可能性がある。
2. **テストファイル同士の直接依存**。母集団:
   `grep -l "from tests\.test_\|import tests\.test_" backend/tests/test_*.py`。
   2026-09-20時点で2件（`test_wind_time_varying.py`→`test_road_graph_engine`、
   `test_gsi_tile_routes.py`→`test_terrain_rgb`）。共有ヘルパー（`tests/`直下の
   `test_`で始まらないモジュール）経由は正当で対象外。片方の都合でもう片方が壊れる
   （T956で`make_generator`のシグネチャを変えたとき実際に壊しかけた）。共有ヘルパーへ出す。
3. **何も教えないテスト**。母集団の作り方を「読んで怪しいもの」にしない。
   `pytest --cov --cov-context=test`でテストごとの実行行を取り、**そのテストだけが
   通す行が0行のテスト**を出す（他のテストが既に覆っている）。そこから人が見て、
   (a) 同じ性質の重複、(b) 実装と同じ式を再計算して比べているだけ（壊れても何も
   教えない）、(c) 消えた実装に付いていた残骸、へ分類する。**カバレッジが重なること
   自体は悪ではない**ので、0行だったものを機械的に消さない。

### 段階5: 残すテストをあるべき場所へ移す（backend）

消さないと決めたテストも、置き場所が合っていないと実装を直すたびに関係ない場所が落ちる。
**移すだけで中身は変えない**（中身を変えるなら段階4で消す判断をしている）。

判断の軸は「何を固定しているか」。

- **層**: DBの制約が保証することをappのテストが再確認していないか（段階3で制約を張ったら、
  その分岐を固定していたテストは消えるか、DB側の検査へ移る）。純関数のふるまいを
  サービス経由で検査していないか（domainのテストへ）。
- **重さ**: DBを使わずに書けるものが`postgis`マーカー付きになっていないか。母集団は機械で
  出せる——`pytest -m postgis`のテストのうち、`road_graph_session`等のDB fixtureを
  1つも使っていないものを列挙する。逆（DBを使うのにマーカーが無い）も同じ方法で出す。
- **対応**: テストファイルと実装モジュールの対応が取れているか。母集団: `tests/test_*.py`
  のうち、`app/**`に同名のモジュールが無いものを列挙し、1件ずつ「複数モジュールに
  またがる正当なもの」か「置き場所を見失ったもの」かを判断する。

### 段階6: frontendの到達可能性

backendの出方を見てから作る。源流はbackendと別物になる。

- App Routerのページ・レイアウト・APIルート（`src/app/**`のファイル規約で決まる）
- クライアントの入口（`page.tsx`が読むコンポーネント）
- 生成物（`src/types/generated/`）を読む側

TypeScriptは既存ツール（`knip`・`ts-prune`）が使えるかを先に測る——**入れるかどうかは
出力の質を見てから決める**。このリポジトリはbackend生成物の型・MapLibreのレイヤー宣言・
軸カタログ由来の動的なレイヤー生成を多用するため、素朴な未使用検知は誤検知が出やすい。

### 段階7: frontendのテストを消す・移す

段階4・5と同じことを`vitest --coverage`で行う。テスト149ファイル・1,432件が対象。
frontend固有の「あるべき場所」の軸が1つある——**DOMを使わないテストがjsdom環境のまま
になっていないか**（[docs/conventions/testing.md](../../conventions/testing.md)の
`// @vitest-environment node`）。母集団は機械で出せる（docblockが無く、
`render`/`renderHook`/`document`/`window`を1つも使っていないファイル）。

### 段階8: 機械で出ない範囲を読む

段階1〜7が出せるのは「参照が無い」「到達しない」「重なっている」「場所が合わない」まで
で、**生きている経路の中の無駄**は出ない。ここはモジュール単位に読む。

- **単位**: `docs/modules/`の区切りをそのまま使う（backend・frontendの各モジュール文書が
  対象ファイル表を持っており、読む範囲が既に閉じている）。1コミット1モジュール。
- **読むときに探すもの**: 通っているが結果を変えない分岐、同じ正規化を2度かける経路、
  写経された骨格（T956の`EdgeMaterialArrays`/`StaticEdgeScoreMatrix`が実例）、実装と同じ
  式を再計算しているだけのテスト、記載と実装がずれたモジュール文書。
- **記録**: このエントリへモジュールごとに1行——読んだ日・見つけたもの・**見つからな
  かったこと**。「何も無かった」も結果として書く（書かないと読んだかどうかが分からない）。
- **見つけたものの扱い**: その場で消せるものは消す。設計判断が要るものは別Txxxへ起票し、
  このエントリには番号だけ残す。
