# T1003. maplibre-glをv6系へ上げる 規模M

状態: 完了（2026-09-22。6.10.0へ更新し、本番ビルドで地図が描けることと、回避策を外すと描けなくなることの両方を確認した）

[T1001](T1001.md)の段階A（地図の状態適用を1経路へ）の前に行う。段階Aは`map.*`を呼ぶコードを
書き直す作業のため、後から上げると同じ場所を2回触って2回検証することになる。
**書き直しとは別のコミットにする**——地図が描けなくなったときに、上げたせいか書き直した
せいかを切り分けられなくする。

## これまで上げられなかった理由と、いま変わったこと

`docs/architecture/tech-stack.md`は「v6はWorkerのスクリプトURLを動的テンプレートリテラルで
解決し、Next.jsのバンドラが静的解析できないため地図が永久に描画されない」として`^5`へ
固定している。**この記述は既定の読み込み経路については今も正しい**（2026-09-22、
配布物6.10.0を取得して確認。`dist/maplibre-gl.mjs`に ``new URL(`./${t}`, import.meta.url)``
が残っている）。

変わったのは、**Workerの場所を自分で指定する公開APIがあると分かった**こと。

| 確かめたこと | 観測 |
|---|---|
| 最新版 | 6.10.0（`npm view maplibre-gl dist-tags`） |
| Worker URLの解決 | ``new URL(`./${t}`, import.meta.url)``（動的。docsの記述どおり） |
| 逃げ道 | `setWorkerUrl(value: string)`が`dist/maplibre-gl.d.ts`で宣言され、exportにも含まれる |
| distの構成 | `maplibre-gl.mjs`（584KB）・`maplibre-gl-shared.mjs`（514KB）・`maplibre-gl-worker.mjs`（19KB）。Workerはモジュールworkerで、sharedを相対importする |
| style-specの要求 | v6.10は`@maplibre/maplibre-gl-style-spec` `^26.4.4`（v5.24は`^24.8.1`）。完全固定している版を26.4.4へ上げる必要がある |

## 対応方針

`maplibre-gl-worker.mjs`と`maplibre-gl-shared.mjs`を静的配信し、地図を作る前に
`setWorkerUrl`でそこを指す。Workerはsharedを**自分のURLからの相対**でimportするため、
2本を同じディレクトリへ置く。

**代償**: sharedチャンクをバンドル内と静的配信で二重に配る（非圧縮514KBのファイルが1本増える）。
配信するファイルはリポジトリへ置かず、ビルド前に`node_modules`から複製する。

## なぜ今やる価値があるか

[T703](T703.md)（ポップアップのXSS到達経路、CVSS 10）の修正版がv6系にしかなく、このタスクが
閉じるまで塞げない。

## 通らなかった場合

`setWorkerUrl`でも描けないと分かったら、**v5へ戻し、観測した事実をこのエントリへ書いて
完了扱いにする**（tech-stack.mdの記述も「setWorkerUrlでも回避できない」まで具体化する）。
T703はそのまま塞げないため、別の緩和（`popupEscape.ts`の適用範囲を広げる）へ倒す判断を

## 実施内容（2026-09-22）

`maplibre-gl` 6.10.0 / `@maplibre/maplibre-gl-style-spec` 26.4.4 へ更新し、Workerを
`public/maplibre/`から配って`setWorkerUrl`で指す形にした。

**破壊的変更は8件・5ファイル**（`tsc --noEmit`の出力が母集団）:

| 変更 | 直した箇所 |
|---|---|
| 既定exportの廃止 | `jmaTileProtocol.ts`を`import { addProtocol }`へ |
| グローバル名前空間`maplibregl`の廃止 | `MapView.layerOps.test.ts`が型を直接importするように |
| `setPaintProperty`/`setLayoutProperty`のプロパティ名が型で絞られた | specのキーを機械的に流す`ensureLayerFromSpec`（`as any`が2つ消えた） |
| `createExpression`が`rootKey`必須に | テスト4箇所 |
| モックが既定exportを返していた | `jmaTileProtocol.test.ts` |

## 回避策が要ることの確認（dev/本番ビルド/E2Eで答えが違う）

`setWorkerUrl`の呼び出しを外して3通りで観測した。

| 構成 | 回避策なしの結果 |
|---|---|
| dev（Turbopack） | **描ける**（ハッシュ無しのパスで配るため、動的に組み立てたURLがそのまま当たる） |
| 本番ビルド（standalone） | **描けない**。`Failed to load module script: ... non-JavaScript MIME type of "text/html"`（Workerの要求が404のHTMLを受け取る）。canvasは残るが何も描かれない |
| E2E（9本） | **通ってしまう** |

**E2Eが「地図が描けたか」を検証していない**ことがここで分かった（DOMだけを見ているため、
Workerが死んで地図が真っ白でも緑になる）。別タスクとして起票する。

確認の手順（再現用）: 本番ビルドを作り`PORT=3010 node .next/standalone/server.js`で起動、
backendは`BASEMAP_PUBLIC_BASE_URL=http://localhost:3010/api/basemap`を渡して起動する
（基礎地図のスタイルJSONへ焼き込まれるURLがフロントのポートと一致していないとタイルが
別オリジンになる）。ブラウザで開き、`document.querySelector("canvas.maplibregl-canvas")`の
描画とコンソールのエラーを見る。
