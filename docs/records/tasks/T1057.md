# T1057. 並行実行の重い処理を機械全体で1つの枠に並べ、CPUの取り合いを無くす

状態: 未完了（2026-09-23起票）

## 背景

並行実行で重い処理（tsc・vitest・next build・playwright・pytest・npm ci・pre-push）が同じ開発機のCPUを取り合い、1本あたりの所要が何倍にも伸びる。lockrun.py のロックは種類ごと（frontend-heavy・backend-db・npm-ci・git-push）で、種類が違えば同時に走れる。2026-09-23 10:29〜12:46 の137分のロック記録では、重い処理が2本以上重なった時間が50分あった（0本36分・1本52分）。この間、T1027 の typegen+tsc+eslint+vitest 一式は R4 の npm ci（525秒）・backend テストと重なって18分かかった（tsc単独は27秒）。同時実行の上限3本はエージェントの数であり、重い処理の数を表していない。テストDBの論理的な衝突は T964（作業ツリー別DB）で塞がっており、残るのは物理的な資源の取り合いである。

対応方針: ①機械全体で共有する「重い処理の枠」を lockrun.py へ置き、種類別ロックの上位でかける（枠の数は、tsc と backend テスト1ファイルを単独・2本並行で走らせた所要の実測から決める）。②ロックを通さずに走る重い処理を無くすため、エージェントへの指示と規約（docs/conventions/orchestration.md）に「重い処理は必ず lockrun 経由・変更が届く範囲を1回」を明記する。③効いていることの確認: 並行実行1回分のロック記録で、重い処理の重なり時間が0（枠1の場合）になり、1本あたりの所要が単独実行と同程度であることを示す。前提: T1049 の管理の核（scripts/orchestration/core.py）が master に入っていること。CIを作業ブランチでも動かして手元から外す案は、GitHub Actions の無償枠（月2,000分）を使うためユーザー判断として別に扱う。

## 2026-09-23 規約で先に効かせた部分と、このタスクに残る部分

ユーザーの指示（「1、2を標準化して」）で、方針①②を規約（`docs/conventions/orchestration.md`
「重い処理は機械全体で1本ずつ」「重い処理を減らす」）へ先に入れた。コードを足さずに効かせる
ため、①は種類別のロックをやめて**全部を1つのロック名`heavy`へ寄せる**形にした（lockrun.py は
任意のロック名を受けるので、名前を揃えるだけで機械全体の枠1つになる。pushもpre-pushが検査を
走らせるので同じ枠に入れた）。

このタスクに残るもの:

1. **枠の数を実測で決める**: `tsc --noEmit` 単独の所要と、`tsc` と backend テスト1ファイル
   （例: `tests/test_axis_definition_repository.py`）を同時に走らせたときのそれぞれの所要を、
   ほかに重い処理が走っていない状態で3回ずつ測る。2本同時の所要の和が単独2本の直列の和より
   短ければ、枠を2にする（lockrun.py に枠の数の指定を足す）。短くなければ1のまま。
2. **枠の外の重い処理を見つける**: `heavy`以外のロック名（旧名 `frontend-heavy`・`backend-db`・
   `npm-ci`・`git-push`）で呼ばれたら lockrun.py が `heavy` として扱うか拒否するかを決めて
   実装する。ロックを通らずに走った重い処理は、司令塔の定期確認（`orchestrate.py check`）で
   プロセス一覧から数えて異常として出す。
3. **効いていることの確認**: 次の並行実行1回分のロック記録で、重い処理の重なり時間が0
   （枠1の場合）であること、1本ごとの所要が単独実行と同程度であることを示す。

## 2026-09-23 計測を要しない部分（残るもの2と追加）

担当: 並行実行の担当 U-lock（作業ブランチ `orch/U-lock`）。残るもの1・3は下の「未実施」。

### 方針

- **`heavy`以外のロック名はすべて拒否する**（旧名を`heavy`へ読み替えもしない）。`scripts/lockrun.py`は
  `heavy`以外の名前で呼ばれたら、走らせずに終了コード2で止まり、規約の節と「出どころを直すこと」を出す。
  範囲を旧名に限らなかったのは、実施中に司令塔から「F-localが存在しないロック名`light`を渡しても
  素通りした」と材料が届いたため——欠陥は旧名であることではなく「`heavy`以外の名前が別の枠を作り、
  `heavy`と同時に走れる」ことであり、旧名の一覧で塞ぐと思い付きの名前が漏れる。読み替えない理由:
  ①旧名は一様に`heavy`へ写らない——旧`git-push`はpushを包んでいたが、今の規約ではpushは枠に入れない。
  ②読み替えは古い手順を黙って生かし続け、出どころが直らない。拒否されたエージェントが枠を通さずに
  走らせ直す恐れは、下の定期確認が拾う。**失うもの**: これまで`selftest`等の名前でlockrun自身の
  試験を共有の`lockrun/`で回していた（記録に実績あり）が、CLI経由ではできなくなる。破棄の試験は
  関数（`acquire`に使い捨てのパスを渡す）で行えたので、今回は困らなかった。
- **枠の外の重い処理の検出**（`orchestrate.py check`）: 重い段は規約
  （`docs/conventions/orchestration.md`「重い処理は機械全体で1本ずつ」の「**対象**」の項目）に
  コード書式で挙げたものをorigin/masterの版から読み（`heavy_stages`）、別の一覧は持たない。
  プロセス一覧（新設の`scripts/orchestration/procs.py`。Windowsはtoolhelpと
  `NtQueryInformationProcess`、Linuxは`/proc`——飽和した機械へプロセスを足さないため外部コマンドを
  起こさない。実機で259プロセス・0.21〜0.23秒）のコマンドラインに段の語が現れ、`heavy`の保持者
  （`owner.json`のpid）の子孫でないものを「枠の外の重い処理」として出す。`lockrun.py`を含む
  コマンドライン（包み・待っている呼び出し）は除く。親子の両方が当たれば外側だけ出す。
  規約から段を1つも読めなければ、それ自体を異常として出す（列挙器が黙って0件を返さないため）。
  候補であって判定ではない: Bashツールの包みのように、段の語を文字列として含むだけのプロセスも拾う。
  MSYSのプロセスは親が先に終わって祖先を辿れないことがあり、同じ実行が2行に出ることがある。
- **破棄の記録**: 枠を破棄するとき、`owner.json`のpidがその時点で生きていたか・プロセス名・
  コマンドライン（pidの再利用を見分けるため）を`lockrun/breaks.jsonl`へ1行追記し、画面にも
  「保持者 pid N は生きていた／死んでいた」を出す。`log.jsonl`（`--report`とcheckが読む実行の記録）
  とは別のファイルにした——読み手が`wait_s`等を前提にしているため。破棄の規則（300秒）は変えていない。

### 検証

- 名前の拒否: `python scripts/lockrun.py <名前> -- 'echo x'`を`light`・`git-push`・`selftest`で
  → 3つとも拒否の文言・rc=2。`heavy`の経路は変えていない（名前の判定を先頭に足しただけ）。
- 破棄の記録（完了条件）: 使い捨てのディレクトリ（`tempfile.mkdtemp`）と試験用のロック名で、
  生きている保持者（`python -c "time.sleep(120)"`）と終わった保持者のpidをそれぞれ`owner.json`へ書き、
  mtimeを400秒前へ戻して`lockrun.acquire`に破棄させた。出力:
  `U-lock-test-live のロックが400秒更新されていないため破棄します（保持者 pid 5436 は生きていた、python.exe）`／
  `U-lock-test-dead …（保持者 pid 10032 は死んでいた）`。`breaks.jsonl`に`holder_alive: true`（名前・
  コマンドライン付き）と`false`の2行。本物の枠（`heavy`）と共有の`lockrun/`は触っていない。
- 段の導出と照合: 規約から`npm ci`・`next build`・`next typegen`・`tsc --noEmit`・`vitest run`・
  `pytest`・`playwright test`・`eslint`を導出。当たるべき8形（`node …\typescript\bin\tsc --noEmit`・
  `vitest.mjs run`・`eslint.js`・`python.exe -m pytest`等）と当たってはいけない4形（`git status`・
  `orchestrate.py check`・`tsc --version`・`npm run dev`）で不一致0。
- 実機の既知の1件: 初回の実行で、作業ツリー`slot-1`（F-local）が`./node_modules/.bin/tsc --noEmit`を
  lockrunを通さずに走らせているのを検出した（Bashツールの包み pid 6924 と、親が既に終わって祖先を
  辿れない`sh.exe` pid 14776 の2行）。同時に`heavy`の保持者（slot-2のplaywright、pid 18292）の子孫
  （bash→sh→node→chrome等）は出なかった。
- `orchestrate.py check`を作業ブランチの版で2回（記録なし）: 何も無いとき「異常なし」、偽の重い段
  （`python -c "sleep" pytest U-lock-dummy`）を枠の外に置いたとき「枠の外の重い処理: pytest（pid …）」を
  出した。checkの所要は約50秒（ほぼ既存の項目。追加分は上の0.2秒台）。
- 静的検査: `ruff check`（3ファイル）通過、`review_checks.py docs`違反なし。
