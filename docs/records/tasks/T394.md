# T394. GraphService.get_way_tagsが未使用の可能性〔調査のみ〕規模S

状態: 完了（2026-08-29、未使用と確定・削除）

- 背景: T392（タイル材料一式のRedis複製化）検証中、PostGIS読み取りパスを棚卸しする過程で
  `GraphService.get_way_tags`（`backend/app/services/graph_service.py`）を発見したが、
  `self._repository.get_way_tags(edge_ids)`への薄い委譲以外に呼び出し元が見つからなかった
  （2026-08-29、`grep -rn "\.get_way_tags("`で`road_graph_repository.py`のリポジトリ層
  内部呼び出し以外にヒット無し）。road_graphエンジンの実際の経路では、way_tagsは
  `SearchMaterials.way_tags`（`get_edge_materials_batch`が5材料の1つとしてまとめて返す）
  経由で取得されており、この単体メソッドは別経路として使われていないように見える。
- 影響範囲（保留した場合）: 未使用コードが残っているだけで実害・ブロックは無い（推測の
  域を出ない棚卸し中の気づきであり、実際に未使用と確定した調査ではない）。
- 完了条件（着手時に確定）: 本当に呼び出し元が無いか正式に確認する（テストコード・
  frontend連携・将来のOpenRouteServiceEngine経路等も含めて網羅的に`grep`する）。
  未使用と確定すれば削除する。何らかの理由で意図的に残している公開APIだと判明すれば、
  その理由をコード内コメントへ残した上で本タスクをクローズする。

## 対応結果（2026-08-29）

網羅的に`grep`した結果、`GraphService.get_way_tags`（複数edge_id、バッチ版）は
`RoadGraphRepository.get_way_tags`ファサード・`AttributeRepository.get_way_tags`実装への
委譲チェーン全体で、テストコード以外に呼び出し元が無いと確定した（ルーター・frontend
連携も含め該当なし）。`way_tags`は改善計画T248で`get_edge_materials_batch`（5材料統合の
1回JOINクエリ）へ統合済みで、この単体メソッドは完全に代替されていた。

**混同注意**: 似た名前の`get_way_tags_by_osm_way_id`（単一osm_way_id、改善計画T90）は
`region_service.py`（区間クリック時の車ストレス内訳表示）から現役で使われており、
**別物・削除対象外**。

削除したもの:
- `backend/app/infrastructure/road_graph_repository.py`: `AttributeRepository.get_way_tags`・
  `RoadGraphRepository.get_way_tags`ファサード
- `backend/app/services/graph_service.py`: `GraphService.get_way_tags`
- `backend/tests/test_road_graph_repository.py`: 対応する3テスト
- `backend/tests/test_graph_service.py`: FakeRoadGraphRepositoryの死んだスキャフォールド
  （`get_way_tags_call_count`・`get_way_tags`メソッド。`self.way_tags`データストア自体は
  `get_edge_materials_batch`が使うため維持）

検証: `pytest tests/test_graph_service.py tests/test_road_graph_repository.py
tests/test_road_graph_engine.py` 181件成功。
