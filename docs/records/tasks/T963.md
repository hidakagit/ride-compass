# T963: コードが増え続けていることを、誰も見ていない

状態: 完了

2026-09-19起票、2026-09-24完了（並行実行の担当W-growth）

## 背景

`scripts/review_checks.py metrics`は実装・テストの合計行数を出すが、**その時点の値だけ**で
前回との差を出さない。閾値があるのは**ファイル単位**（[T952](T952.md)で4ファイルへ個別に
設定）で、「1ファイルが太った」は捕まえても「全ファイルが少しずつ増えた」は誰にも見えない。

実測（2026-09-19時点、`metrics`）: 実装本体 62,977行・テスト 65,982行。
backend/appは5週間で5,217行→34,227行になっている（機能追加が大半だが、内訳は分からない）。

**複雑度を下げる改修をしても総量が増える**のはなぜか、という問いから出た
（ユーザー指摘）。[T956](T956.md)の作業中に見えた機構は次の2つ。

1. **追加が先に入り、削除が最後の工程になる**。新しい形を足す→本番経路を差し替える→
   古い形を消す、の順になるため、途中で止まればリポジトリは両方を抱えたまま純増する。
   [T567](T567.md)（経緯コメント一掃をモジュール単位へ分割）が残っているのも同じ形。
2. **検知器は「悪い足し方」を捕まえるが、「差し引きで減るはずが増えた」は見ない**。

## 対応方針

`metrics`は既に合計を出しているので、前回の値と比べて差を出す。保存先は
`.claude/commands/review/`のレビュー履歴。**閾値で止めるのではなく傾向を見せる**
——増えること自体は機能追加で当然に起きるため、機械的に止めると誤検知ばかりになる。

### デッドコードの洗い出しは[T968](T968.md)が引き取った

起票時はこのタスクが「入力の源流からの到達可能性グラフ」「デッドコードの機械的な検知」
「同じ値を2か所で持っていることの検知」「残す側の条件」を抱えていた。2026-09-21の
ユーザー指示でT968が総整理のタスクになり、**これらはT968の段階1〜2へ移した**。
実測・設計の中身もあちらにある。

ここに残るのは`metrics`の増減傾向を見せる話だけ。

## 2026-09-20の実測（T956の削除作業で分かったこと）

検知器を作るときに同じ穴を掘らないための材料。移した先（T968段階1）でも使う。

- **テキストのgrepでは取りこぼす**。「その名前がapp内の他ファイルに現れるか」で数えると、
  docstring・コメント内の言及を「使用」と数える。`compute_cost_from_axis_scores`は
  `evaluation.py`のdocstringに3回現れるだけだったが、この方法では生きていると判定された。
  **ASTで名前の参照（`ast.Name`/`ast.Attribute`/`ast.alias`）だけを数える**と、
  同じ母集団から8件多く出た。
- **ASTでも「app内から参照されるが本番の入口から到達しない」は出ない**。
  `compute_edge_costs_bulk`は`_evaluate_axes_bulk`を呼んでいたため参照があり、列挙に
  出なかった。1か月のあいだ「回帰テストのオラクル」として残っていたのはこれが理由。
  **到達可能性の閉包（入口から辿れるか）が要る**というのが、このタスクの核心。
- **偽陽性の型**が2つある。FastAPIのルートハンドラ（デコレータで登録され、コードからは
  参照されない）と、SQLAlchemyの宣言モデル（メタクラス経由で`Base.metadata`へ入る）。
  列挙の時点で除かないと、出力の大半がこの2つで埋まる。
- 実測値: app配下の公開定義685件に対し、テキストgrepでは「テストからしか参照されない」が
  12件、ASTでは23件（うち上記の偽陽性を除くと実質15件）。

## 実施内容（2026-09-24）

**対応方針の「保存先はレビュー履歴」は採らなかった**。保存した過去の値と比べるのは
検査ではなく報告で（CLAUDE.md「検知器を足す条件」・`review_checks.py`冒頭の設計要件）、
過去の値は`periodic-review/NNN`タグが指すコミットから導ける。`size`の前回比と同じ導き方にした。

- `review_checks.py metrics`の末尾に「総量の前回比」の表を足した。種別は実装・テスト・
  維持する文書（`docs/records/`を除く`.md`）で、今回・前回・差・増減率を出す。前回は最新の
  `periodic-review/*`タグのコミットの全追跡ファイルを`git cat-file --batch`1回で読んで数える。
  テストの判定（`.test.`・`.spec.`・`/tests/`）は既存の「うちテスト」と同じ関数へまとめた。
- `line_counts`のsha指定（`size`の前回列）も同じ`git cat-file --batch`へ寄せた（1ファイル1回の
  `git show`をやめた）。
- 副次の変化: 「うちテスト」の件数が、空のファイルを数えなくなった（「コードファイル数」と
  同じ母集団になった）。b82e3488で312→310。
- `/review`（`.claude/commands/review.md`）の複雑度の観点に「総量の傾向」の1項目を足した。
  閾値では止めず、増分を対象範囲のタスクで説明できるかを見る。

### 検証

- 別の入力との突き合わせ: `git diff --numstat --no-renames periodic-review/012`（作業ツリーまで）の
  純増を同じ種別で足した値と、`metrics`の差が一致（実装+5,005・テスト+2,378・文書+1,436）。
- わざと作った差: 前回をHEADへ差し替え（`review_tags`を置き換えて`cmd_metrics`を呼ぶ）、作業ツリーの
  実装（`backend/app/main.py`）へ7行・テスト（`backend/tests/conftest.py`）へ11行・文書
  （`docs/modules/README.md`）へ13行を足すと、差が基準（作業中の本変更の実装+56）から
  それぞれ+7・+11・+13動いた。足した行は戻した。
- `line_counts`の新旧一致: タグ時点の744パス（存在しない1件を含む）で、1件ずつの`git show`と
  `cat-file --batch`の行数の食い違い0件（どちらも735件を数え、存在しない1件はどちらも数えない）。
- `metrics`の所要: 変更後1.9秒（変更前の初回は14秒だったが、ファイル読みのキャッシュが冷えていた
  差を含むため、比較には使わない）。
