# T1081. 定期確認のフックの入口（launch.py）が、子の出力をcp932で出し直して落ちうるのを直す

状態: 完了（2026-09-23起票、同日完了）

## 背景

T1076の担当（N-help）の報告: scripts/orchestration/launch.py の標準出力はPostToolUseフックの出力としてClaude Codeが読む。子プロセス（origin/masterの版のorchestrate.py）から受け取ったUTF-8の出力を、JSONを組み直さない print(out) の分岐でそのままWindowsの既定の文字コード（cp932）で出し直すため、— のようなcp932で表せない文字が来るとUnicodeEncodeErrorで落ちる可能性がある。落ちると定期確認（20分ごとのcheck --if-due）が黙って止まる。通常の日本語だけなら落ちないが、Claude CodeがUTF-8として読めば文字化けする可能性もある。どちらも未確認。やること: まず実際に落ちるか・化けるかを、cp932で表せない文字を含む出力をフックの経路で1回流して確かめる（直す前に見る）。直すならT1076と同じく入口で標準出力をUTF-8へ整え、Claude Codeがフックの出力をどの文字コードで読むかを公式の文書で確かめてから決める。

## 実施内容

### 直す前の観測

フックの経路（`hook.sh` → `launch.py` → origin/masterの版の`orchestrate.py check --if-due`）を手で再現した
（本体の`.claude/settings.json`は触らない）。スクラッチの`t1081_repro.py`: 一時のリポジトリ（オブジェクトは
実物をalternatesで借りる）の`refs/remotes/origin/master`を「基準のsha＋子の出力を書き換えたコミット」へ向け、
`CLAUDE_PROJECT_DIR=<一時> bash -c '. "$CLAUDE_PROJECT_DIR/scripts/orchestration/hook.sh"'`へ
`board claim`を含むフック入力を流した。`PYTHONUTF8`・`PYTHONIOENCODING`は外し、標準出力はパイプ
（このときの`sys.stdout.encoding`は`cp932`）。基準は9a09b879（当時のorigin/master）。

| 場合 | 直す前 |
|---|---|
| V0 子はorigin/masterのまま | 落ちない。出力はASCIIのみ（子の`hook_context`が`json.dumps`の既定でASCIIへ逃がしている） |
| V1 子が`ensure_ascii=False`のJSONに`—`を含めて出す | **落ちる**。`UnicodeEncodeError: 'cp932' codec can't encode character '—'`、標準出力0バイト |
| V2 子がJSONでない平文に`—`を含めて出す | **落ちる**（同上、0バイト） |
| V3 子が`ensure_ascii=False`のJSON（cp932で表せる日本語だけ） | 落ちないが**化ける**。出力はcp932のバイト列で、UTF-8としては読めない |
| V1＋入口が古い（注を添える分岐） | 落ちない（`launch.py`がJSONを組み直し、`json.dumps`の既定でASCIIへ逃がす） |
| V2＋入口が古い | **落ちる**（JSONとして読めず`print(out)`へ落ちる） |

結論: **今のorigin/masterの子では落ちも化けもしない**——子（`core.hook_context`）がASCIIへ逃がしているため。
ただし`launch.py`の`print(out)`は、子が非ASCIIを1文字でも出せば落ちる（cp932で表せない文字）か化ける
（表せる文字）。子はorigin/masterの版で`launch.py`とは別に変わるので、この約束は`launch.py`の側から守れない。
落ちたときは`hook.sh`が`exit 0`で抜けるため、Claude Codeには空の出力が渡り、その回の確認（`check_if_due`は
先に`last_check`を進めている）が黙って消える。

### Claude Codeがフックの標準出力をどの符号で読むか

公式の文書には書かれていない。フックのリファレンス（https://code.claude.com/docs/en/hooks.md）と手引き
（https://code.claude.com/docs/en/hooks-guide）の全文、公式の変更履歴
（https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md）を`utf`・`encod`・`unicode`・
`codepage`等でgrepし、フックの出力の符号に触れた記述は0件だった。書かれていること: 標準出力が`{`で始まり`}`で
終わればJSONとして読む（リファレンス「JSON output」）、Windowsの既定のシェルはGit Bash（手引き）。
JSONの側の決まりはRFC 8259 §8.1（https://www.rfc-editor.org/rfc/rfc8259#section-8.1）の、閉じた系の外と
やり取りするJSONはUTF-8で符号化しなければならない、という規定。傍証として、同じClaude CodeのBashツールで
cp932のバイト列（`python -c "print('日本語—テスト'.replace('—','-'))"`をパイプへ）を出すと化けて表示された
（Bashツールの出力はUTF-8として読んでいる）。これらから、フックの出力はUTF-8で出すのが正しいと判断した
（フックそのものの読み方は公式に無く、傍証止まり）。

### 直したもの

`scripts/orchestration/launch.py`の`if __name__ == "__main__":`で、`main()`の前に
`sys.stdout.reconfigure(encoding="utf-8")`・`sys.stderr.reconfigure(encoding="utf-8")`を置いた（T1076と同じ形）。
ASCIIへ逃がしている今の出力（V0・注の分岐）はバイト列が変わらない。hook.shのもう一方の分岐（起動役を
取り出せないとき本体の`orchestrate.py`を直接動かす）は、`core.main`が既に標準出力をUTF-8へ整えている。

### 検証

直した`launch.py`を基準（9a09b879）の上に積んだコミットをorigin/masterにして、同じ`t1081_repro.py`を流した。

元の文字列のまま。V0とV1＋注の分岐は直す前と同じASCIIのみの出力（293バイト・677バイト）。
