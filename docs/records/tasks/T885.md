# T885. 開放度の軸が、並木道と市街地を同じ点数にしている

規模M。
状態: 完了（2026-09-16起票・同日実施。ユーザー指摘「開放度の扱いも再考したい。今ってその一部しか
使えない形で材料を取り込んでいる認識」から、本番の実データで確かめた）

## 今どうなっているか

`way_landcover`（[T624](T624.md)）は土地被覆の割合を8クラス分持つが、材料として配線されて
いるのは`trees_percent`と`built_percent`の2つだけである。本番の平均:

    built      81.4%  ← 配線済み
    crops      10.9%
    trees       5.7%  ← 配線済み
    rangeland   1.4%
    water       0.5%
    flooded_veg / bare / snow_ice  ほぼ0%

公開軸`openness`（開放度、カテゴリ=環境、既定重み**0.0**）の形:

    kind: breakpoint_linear / preprocess: identity
    term: trees_percent  weight -1.0
    term: built_percent  weight -1.0
    breakpoints: [[-100, 0], [-80, 30], [-20, 100]]

つまり**開放度＝樹木と建物が少ないほど高い**で、配線されていない6クラスは「遮るものでは
ない」として自動的に開けている側へ入る。この意味で6クラスは「使えていない」のではなく、
補集合として暗黙に効いている。

## 実データで確かめたこと（本番、2026-09-16）

**補集合がまとめているものは、思ったほどばらけていない。** 開放度が満点に近い道
（`trees + built <= 20`）68,112本を、最も割合の大きいクラスで分けると:

    農地  63,871本（94%）
    草地   3,594本
    水面     644本
    裸地       3本

起票前は「農地と水面と裸地が同じ『開けている』になる」ことを問題と見ていたが、実際には
94%が農地で、区別を足しても動く道はほとんど無い。**この点は問題ではない。**

**本当の問題は、樹木と建物が同じ重み（どちらも -1.0）であることの方だった。**

    樹木優位（trees >= 50 かつ built < 20）     44,120本
    建物優位（built >= 50 かつ trees < 20）  1,070,980本

この44,120本——並木道・林間の道——が、ビル街と同じ「開けていない」側の点数になる。
自転車にとってこの2つはほぼ正反対で、樹木は木陰・風よけ・景観という利点の側にある。
軸の説明も「周囲に建物・樹木などの遮るものが少ないほど易しい」と樹木を遮蔽物として
明言しており、名前と定義は一貫している。一貫しているが、**「開けている＝良い」という
前提自体が自転車では成り立たない**。

## 原則13に照らして

開放度は走行モデル（所要時間）に入らない純粋な主観の材料で、軸だけに置くのは正しい形
（[design-principles.md](../../design-principles.md)構造仕様13）。二重計上の問題は無い。
論点は軸の形だけである。

## 保留することで何が起きうるか

既定重みが0.0のため、**今すぐ誰かのルートが悪くなることはない**。ただし:

- 利用者が開放度の重みを上げると、並木道が市街地と同じだけ避けられる。「木陰の多い道を
  選びたい」という素直な使い方が、この軸では表現できない。
- 8クラスのうち6クラスが補集合として暗黙に効いている構造は、材料を足すときに毎回
  「足さなくても効いている」という判断を要求する。どの材料を足すかの議論が、そのたびに
  この形の説明から始まることになる。

## 判断: 廃止する（2026-09-16、ユーザー決定）

起票時はA〜D（樹木と建物を別の軸へ分ける／農地・水面を材料として足す／重みを非対称に
する／現状維持）を並べてAを推した。ユーザー判断は**削除**——「どう使えばいいか分からない」。

軸が答えている問いが決まっていないことが使いにくさの正体で、問いが決まってから作り直す
方が順序として正しい。木陰なら`trees_percent`、市街地なら`built_percent`で、材料は
[T887](T887.md)で8クラスすべて揃っている。

### 実施

`axis_admin` APIで本番→開発の順に unpublish → DELETE。本番は14軸→13軸、公開9→8。
利用者が見る`GET /api/axis-catalog`からも消えたことを確認した。開発DBは本番から
ダンプし直したスナップショットで入れ替え（13軸・公開8で本番と一致）。

**材料・タイルの焼き込み列・区間インスペクタの内訳表示はすべて残る。** 消えたのは軸だけ。
既定重みが0.0だったためルートの結果は変わらない。端末に重みが残っている利用者も、
`syncRoutePreferenceKeys`がカタログに無いキーを送信前に落とすため422にならない。

コード側は、`openness`を「こういう軸の例」として名指ししていた3箇所
（`axis_display.py`・`axis_preview_service.py`・`scoreDistribution.test.ts`）から
名前を外した。挙動は変えていない。

### 作り直すときに読むもの

- 樹木と建物を同じ向きで数えてはいけない理由: 上の実測（並木道44,120本）
- 1つの軸で複数クラスを足してはいけない理由:
  [design-principles.md](../../design-principles.md)構造仕様14
- 土地被覆を見るには: [T886](T886.md)（区間インスペクタの内訳・地図の面レイヤー）

## 起票時に並べた選択肢（記録）

- **A. 樹木と建物を分ける**——「木陰」と「市街地」を別の軸にする。並木道を選べるように
  なり、補集合の曖昧さも自然に解ける。材料の配線は既存の2つのままでよい
- **B. 農地・水面を材料として足す**——補集合の中身を区別する。上の実測では動く道が
  少なく、Aを入れなければ効果は薄い
- **C. 開放度のまま重みを非対称にする**——trees -0.3 / built -1.0 のように傾ける。
  軸の名前と説明は据え置きで、最も小さい変更
- **D. 現状維持**——既定重み0.0のまま、使う人が使う

Aを推す。問題の中心が「樹木と建物を同じ向きで数えていること」にあるため、そこを分けるのが
欠陥そのものへの対応になる（Cは同じ欠陥を弱めるだけで、並木道は依然として減点される）。

軸の追加・変更は`axis_admin`のAPI経由で行う（CLAUDE.md「コミット時の同期ルール」）。
材料側に変更が要るのはBを採る場合だけ。
