## 方針（2026-09-26、担当 B-decl）

母集団は2つの機械の出力の和を候補にし、1件ずつ判定する。

- **モジュール直下の大文字定数**: `frontend/src/{features,lib,app}`の`.ts`/`.tsx`（`.test.`・`.spec.`・`__tests__`を除く）で、
  行頭（インデント0）の`const NAME =`／`export const NAME =`、NAMEが大文字・数字・`_`だけのもの。origin/master（5b796bb1）で
  **259件**。記録の116件はリテラルの値に絞った数え方で、ここでは右辺が生成物・`mapDisplay`等の参照である行も含めて数え、
  参照である行は「既にbackendの宣言から引いている」として判定から外す。
- **インラインの比較**: 同じ範囲で`<`・`>`・`<=`・`>=`・`===`・`!==`の右に数値リテラルを置く行（0・1と`length`との比較を除く）。
  **26件**。

判定は「描画の都合か／源泉の性質・閾値・分類か」。前者（色・太さ・px・拡大率の段・画面の文言・操作の刻み・保存キー・
クライアントの待ち時間）は残し、後者をbackendの宣言（生成物または応答）へ移す。検知器は足さない。

進め方: 利用者に届いている食い違い（雨と雪の境）を段階1として先にコミットし、残りを段階に分ける。

## 段階1: 雨と雪の境を観測と予報で1つにする

- 常設ヘッダー（アメダス実測）の天気の分類を画面からbackendへ移した。`domain/weather.py: derive_observed_weather_code`が
  10分間の降水量を1時間あたりへ直して予報の`derive_weather_code`と同じ段で雨/雪を決め、`AmedasObservation.weather_code`
  （保存した実測から応答のたびに導く`computed_field`。Redisの形は変えない）で届く。画面は予報と同じ`weatherCategoryOf`で
  分類を引き、「晴れ」を昼夜で描き分けるだけになった。
- 境の気温は**backendの0℃へ揃えた**（画面の2℃を捨てた）。気象庁の公式ページは気温だけの境を公表していない（アメダスは
  気温と湿度で判別する。東京の平地の**積雪**の目安として「地上で1.5℃以下」はあり、湿度が低いと気温が高くても雪になるとも書く）ため、どちらの値にも公式の根拠が無い。
  値そのものの判断はダッシュボードに問いとして置いた（`T1140-snow-threshold`）。
  出典: 気象庁「南岸低気圧による東京都での課題と、大雪発生の仕組み」
  https://www.data.jma.go.jp/tokyo/shosai/chiiki/tokyo-kishou/ooyuki-nangan/nangan-kadai-shikumi.html ・
  同「推計気象分布」 https://www.jma.go.jp/jma/kishou/know/suikei_kishou/kaisetsu.html
- 利用者から見た差: 気温0℃を超え2℃以下で降水があるとき、ヘッダーが「雪」から「雨」になり、「今日の見通し」と揃う。

## 段階2: 源泉の値（取り直す間隔・段の境・重みの上限・メルカトルの限界）

画面が直書きしていた源泉の値を、backendの宣言から生成物で引く形にした。値はどれも変えていない
（在否インデックスの取り直しだけ5分→10分。backendが作り直す間隔そのものにした。遅れても間引きが効かないだけ）。

| 画面の値 | 正本（backend） | 生成物 |
|---|---|---|
| アメダス・警報等の取り直し10分 | `services/jma_amedas_service.py: AMEDAS_REFRESH_INTERVAL_MINUTES` | 新設`refresh-intervals.json` |
| 在否インデックスの取り直し5分 | `config.py: jma_tile_prewarm_interval_minutes`の既定値 | 同上 |
| 風格子の取り直し3時間 | `infrastructure/msm_client.py: DEFAULT_UPDATE_INTERVAL_SECONDS`（未同期時の既定値。実行時は配信元のメタが持つ） | 同上 |
| 無風の境0.3m/s | `domain/weather_display.py: WIND_CALM_BELOW_MS`（気象庁風力階級の風力0は0.0〜0.2m/s） | `weather-scales.json` |
| 降水の塗り・予想降水量の「-」の境0.1mm | `domain/weather.py: PRECIPITATION_MIN_MM`（天気コードの雨の判定と同じ値） | `weather-scales.json` |
| 重みの配分の1軸の上限0.6 | `domain/route_preference.py: MAX_AXIS_WEIGHT`（要求の検証には使わない） | `route-generate-config.json` |
| Web Mercatorの緯度の限界 | `domain/region.py: MAX_MERCATOR_LATITUDE` | `region-tile-config.json` |

MSMの更新間隔と在否インデックスの間隔は実行時に変わりうる（配信元のメタ・環境変数）。生成物はビルド時に決まるため
宣言の既定値を運ぶ。ずれても画面の鮮度が遅れるか取り直しが増えるだけで、表示は壊れない。

## 段階5: 地図レイヤーの説明文が評価の名前を軸カタログから引く（2026-09-27、担当 S-single）

答え(1)（下の「問いと答え: 地図レイヤーの説明文」）のとおりにした。

- 母集団: `mapLayers.ts`（origin/master 7a5c5ab8）を`軸|評価|night|難易度`で引いた22行のうち、説明文の文字列は8行。
  評価の名前・内部の呼び名を書き込んでいるのはトンネル・停止要因・風（矢印）・ルートの4か所（段階4で挙げたものと同じ）。
  残る3行は対象外: 土地被覆の「評価軸が使う「道路の周囲100mの割合」とは違い」と一方通行の「評価には影響しません」は
  材料の事実（土地被覆の材料の測り方・材料`oneway`が値の求め方を持たない）で評価の名前を書かず、専用配信の軸の
  `${axis.label}（評価軸）`は既に軸カタログの名前を引いている。
- 引き方: 一次属性を描くレイヤーは、軸カタログの既存の`primary_attribute_ids`（レイヤーの名前は属性idと同じ）で
  引ける。風の材料（`wind_drag_ratio`）は一次属性を持たないため、材料に`weather_grid_value`（読むMSM格子の値）を
  宣言し、`GET /api/axis-catalog`が軸ごとに同じ格子の値を描く気象のチップ（`weather_layer_groups`）へ解決する。
  `primary_attribute_ids`へ混ぜず別の項目にしたのは、画面が`primary_attribute_ids`を評価の下敷きの判定にも使うため
  ——下敷きは材料の道の線を隠さないためのもので、気象の記号を出しているときに評価を薄くする理由は無い。
- 文: トンネルは「評価「…」の材料の1つです」（「night軸」の一文と「夜間の危険度の判定」の言い回しは消した）、
  停止要因は「評価「…」が近傍のこれらを数えて…」、風は「「レンズ」で評価「…」を選ぶと…」。当てはまる評価が
  無ければその一文を出さない。ルートの説明は、レンズの選択肢と同じ公開中の評価の名前と「総合難易度」を並べる。
- 画面の型: `CatalogAxis`（軸カタログの1行の共通の項目）が`primaryAttributeIds`・`weatherLayerGroups`を持ち、
  `SecondaryAxisSummary`の`primaryAttributeIds`はそこから受ける。`buildMapLayers`は軸カタログを受け取る形にした。
- 最初のpushでCIのe2e（`e2e`・`e2e-scan`）が全面に落ちた: 画面がエラーの境界へ落ちていた（`undefined`の`length`）。
  e2eのモックの軸カタログ（`e2e/fixtures.ts: axisCatalogFixture`）が契約の必須項目`accident_years`を欠いており、
  従来は`buildMapLayers`の引数の既定値`[]`が穴を埋めていた。本物のbackendは必ず返す項目なので、画面に既定値を
  戻さず、モックを契約の型（`AxisCatalogResponse`）に縛って欠けた応答を作れなくした。

## 段階7: 気象庁のタイルのURLの形をbackendの宣言だけが持つ（2026-09-27、担当 S-single2）

- 母集団: 配信元のパスの形（根`bosai/jmatile/data`・系統・時刻・系列・要素id・`surf`・タイル座標・拡張子・地点のGeoJSON・
  時刻一覧の置き場）を文字で持つ箇所を、`surf/`・`jmatile/data`・`.pbf`/`.png`の選び方で引いた（テスト・記録を除く）。
  組み立て: backend `jma_tile_specs.py: jma_target_times_paths`・`jma_tile_prewarm_service.py: _tile_paths_for_layer`（と
  `_PrewarmLayer.extension`の拡張子の選び方）、画面`jmaDelivery.ts: jmaElementUrl`・`tileExtension`・`jmaTargetTimesPaths`・
  地点の`data.geojson?id=…`。読み戻し: backend `jma_tile_interpolation.py: _TILE_PATH_PATTERN`、画面`jmaTileIndex.ts:
  TILE_URL_PATTERN`・`ELEMENT_PATH_SEGMENT`（`parseJmaTileElement`）。記録の「残り」が挙げた4か所のほか、拡張子の選び方と
  地点のGeoJSONのURLも同じ事実（配信元のパスの形）なので移した。
- 置き場: `domain/jma_tile_specs.py`にパスの形を1つ持ち、`jma_url_template(element_id)`が要素ごとに系統・要素id・拡張子まで
  埋めたテンプレート（コマの項目`{basetime}`/`{member}`/`{validtime}`とタイル座標`{z}/{x}/{y}`が残る）を返す。組み立ては
  `jma_tile_path`、読み戻しは`read_jma_tile_path`（テンプレートを正規表現にして当てる）。生成物`jmaElements[]`は
  `pathGroup`・`targetTimeFiles`の代わりに`targetTimesPaths`（時刻一覧のパスそのもの）と`urlTemplate`を配る。
- 読み戻しの字種の選択: 前の担当の記録は「項目ごとの字種を宣言に持ち、生成物で配って両側が正規表現を組む」案を挙げていた。
  採らずに、**要素ごとのテンプレートそのものに当てる**形にした。系統・要素id・拡張子はテンプレートの中で文字として埋まって
  いるので、読み戻しで字種を決める必要があるのはコマの項目（1区切り`[^/?]+`）とタイル座標（数字）だけになり、項目ごとの字種の
  表が要らない。大文字の要素id（`test_jma_tile_interpolation.py`の`/surf/HRPNS/`）は宣言のどのテンプレートにも当たらないので、
  従来の`[a-z0-9_]+`の検査はそのまま効く（宣言の無い要素・描き方と違う拡張子も読まない、と一段厳しくなった）。
  Pythonと JS の名前付きグループの綴りの違いも、画面が項目名の並びを別に持つ形で避けた。
- 画面の読み戻し（`jmaDelivery.ts: readJmaTileUrl`）は、タイルで描く要素のテンプレートに実URLを当てて配信要素・コマ・
  タイル座標を返す。在否の判定（`isKnownEmptyTile`）はこれで要素とコマを引き、配信の失敗の記録（`jmaTileProtocol.ts`）は
  要素配下の前半の代わりに**そのコマのタイルのテンプレート**（描画ペイロードの`tileUrlTemplate`と同じ文字列）を持つ。
  チップの突き合わせ（`dynamicWeather.ts: tileDeliveryFailureLayerIds`）はURLを解かず、記録にペイロードのテンプレートがあるかだけを見る。
  消したもの: `parseJmaTileElement`・`jmaTargetTimesPaths`・`WeatherDelivery.path_group`/`target_time_files`・`TileCoords.head`。
- 判定して残したもの: `jma_tile_client.py: is_target_times_path`（ファイル名`targetTimes*.json`の形で時刻一覧かを見る）。
  プロキシは宣言に無いパスも中継し、そのキャッシュの持ち方を決める必要があるので、宣言のテンプレートからは導けない。理由は
  `weather-dynamic-layers.md`「配信元のパスの形」に書いた。
- プリウォームのURLの集合が変わらないこと: 全段の`_tile_paths_for_layer`を2つのコマ（系列`none`・`immed0`）で列挙し、各パスの
  `parse_tile_path`の結果（要素・z・x・y・拡張子・親のパス）と時刻一覧のパスを並べた1,381行が、変更前（origin/master 814d8782）と
  変更後でsha1 `bdb1a28c0883a7766294105b9a48248f6dbe98f6`で一致した。Redisのキー（パスそのもの）も変わらない。

## 母集団の判定（段階1〜4の時点）

大文字定数259件のうち、右辺が生成物・宣言・他の定数の参照である90件は判定外。残り169件と、インラインの比較26件を1件ずつ
判定した。移したものは段階1〜4の表のとおり。残した理由は次の分類に尽きる（定数名は代表例）:

| 残した理由 | 例 |
