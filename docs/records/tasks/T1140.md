# T1140. 画面が、backendの宣言にあるべき値・対応表・名前を自前で持ち、一部はbackendと値が食い違っている

状態: 未完了（2026-09-26起票）

## 背景

周期レビュー第13回（2026-09-26）の指摘。性質: backendが決めるべき値をfrontendが計算し直す（再発。T1001で多くを移した後の残りと新規）。値が食い違うもの: 雨と雪の境の気温がfrontend conditions/WeatherPanel/amedasWeatherIcon.ts:15で2℃、backend domain/weather.py:8で0℃（常設ヘッダーと「今日の見通し」で判定が割れる）。直書き: 配信の更新間隔3件（useWeatherConditions.ts:37、useJmaTileIndex.ts:12、useWeatherGrid.ts:19。JMAの要素は生成物のrefreshIntervalMsから読む形と混在）、段の境界（windLayer.ts:52の0.3、precipitationNowcast.ts:27の0.1、TodayOutlook.tsx:43の0.1）、重みの上限MAX_AXIS_WEIGHT=0.6（routeWeightShare.ts:8、backendに無い）、applied_max_routesの条件の写し（useRouteFormSubmit.ts:20）、MAX_MERCATOR_LATITUDE（dynamicWayValues.ts:10）、経由地ルートのid（page.tsx:99 NON_DIRECTIONAL_ROUTE_IDS。route-splicedは生成物から引く）、目的地・経由地モードの探索半径distance_kmを画面が計算して送る（page.tsx:574-580。backendの内部パラメータ）、塗る材料をshape.terms[0].materialから読み直す（routeStyleModes.ts:88-95）、道の詳細のタイルプロパティ↔材料の対応（roadFacts.ts:36-40。backendのtile_propertyは生成物に出ていない）、鮮度パネルの「作り直しが要るか」（DerivedDataFreshnessPanel.tsx:25。backendのhas_missing_rowsはテストだけが呼ぶ）。名前: 地図レイヤーの説明文が軸名・内部名を直書き（mapLayers.ts:258-259の「night軸」、277、377、418）、レイヤー名5件（起伏・降水ナウキャスト・風（矢印）・災害・ルート）がfrontend持ち。母集団の導き方: features・lib・appの非テストで、モジュール直下の大文字リテラル定数（9a234615時点116件）とインラインの比較・条件を1件ずつ「描画の都合か／源泉の性質・閾値・分類か」で判定する。後者をbackendの宣言（生成物またはAPI）へ移し、描画の都合として残すものは理由を1行書く。検知器は足さない。

## 方針（2026-09-26、担当 B-decl）

母集団は2つの機械の出力の和を候補にし、1件ずつ判定する。

- **モジュール直下の大文字定数**: `frontend/src/{features,lib,app}`の`.ts`/`.tsx`（`.test.`・`.spec.`・`__tests__`を除く）で、
  行頭（インデント0）の`const NAME =`／`export const NAME =`、NAMEが大文字・数字・`_`だけのもの。origin/master（5b796bb1）で
  **259件**。記録の116件はリテラルの値に絞った数え方で、ここでは右辺が生成物・`mapDisplay`等の参照である行も含めて数え、
  参照である行は「既にbackendの宣言から引いている」として判定から外す。
- **インラインの比較**: 同じ範囲で`<`・`>`・`<=`・`>=`・`===`・`!==`の右に数値リテラルを置く行（0・1と`length`との比較を除く）。
  **26件**。

判定は「描画の都合か／源泉の性質・閾値・分類か」。前者（色・太さ・px・拡大率の段・画面の文言・操作の刻み・保存キー・
クライアントの待ち時間）は残し、後者をbackendの宣言（生成物または応答）へ移す。検知器は足さない。

進め方: 利用者に届いている食い違い（雨と雪の境）を段階1として先にコミットし、残りを段階に分ける。

## 段階1: 雨と雪の境を観測と予報で1つにする

- 常設ヘッダー（アメダス実測）の天気の分類を画面からbackendへ移した。`domain/weather.py: derive_observed_weather_code`が
  10分間の降水量を1時間あたりへ直して予報の`derive_weather_code`と同じ段で雨/雪を決め、`AmedasObservation.weather_code`
  （保存した実測から応答のたびに導く`computed_field`。Redisの形は変えない）で届く。画面は予報と同じ`weatherCategoryOf`で
  分類を引き、「晴れ」を昼夜で描き分けるだけになった。
- 境の気温は**backendの0℃へ揃えた**（画面の2℃を捨てた）。気象庁の公式ページは気温だけの境を公表していない（アメダスは
  気温と湿度で判別する。東京の平地の**積雪**の目安として「地上で1.5℃以下」はあり、湿度が低いと気温が高くても雪になるとも書く）ため、どちらの値にも公式の根拠が無い。
  値そのものの判断はダッシュボードに問いとして置いた（`T1140-snow-threshold`）。
  出典: 気象庁「南岸低気圧による東京都での課題と、大雪発生の仕組み」
  https://www.data.jma.go.jp/tokyo/shosai/chiiki/tokyo-kishou/ooyuki-nangan/nangan-kadai-shikumi.html ・
  同「推計気象分布」 https://www.jma.go.jp/jma/kishou/know/suikei_kishou/kaisetsu.html
- 利用者から見た差: 気温0℃を超え2℃以下で降水があるとき、ヘッダーが「雪」から「雨」になり、「今日の見通し」と揃う。
