# T1200. ルート候補の is_fastest を画面が読まず、APIに読まれない項目が残っている

状態: 完了（2026-09-27）

## 背景

T1158の範囲外で見つけた。画面は最速を一覧から所要で決め、is_fastestを読まない。backendは件数を切る処理だけが読む。

## 対応方針（読み手を数えて決めた）

母集団: リポジトリ全体（`docs/records/`を除く）で`is_fastest`・`isFastest`をgrepした当たり全件（2026-09-27、origin/master 876a560b）。

| 読み手 | 場所 | 読み方 |
|---|---|---|
| 書き手 | `backend/app/services/route_generator.py: RouteGenerator._generate_destination_routes` | 基準線に`True`を立てる |
| 本番の読み手 | 同じ関数の件数を切る処理 | 基準線を切らずに残す |
| テスト | `backend/tests/test_route_generator.py`・`test_route_generation_behavior.py` | 印の位置を確かめる／基準線を探す |
| 画面 | なし（`frontend/src/features/route/routeTabLabel.ts: fastestRouteId`は一覧の所要時間の最小で決め、`is_fastest`を読まないとコメントで明言） | — |
| 生成物・fixture | `frontend/src/types/generated/`・`frontend/src/testing/routeFixtures.ts` | 型の写し |

選択肢は2つあった: ①応答から外す ②画面の最速の判定をこの項目へ寄せる。**①にした**。
②は1本道にならない——`is_fastest`は目的地モード（経由地なし）の探索だけが立て、周回・経由地・区間を乗り換えて作った候補では
立たない。画面はそれらでも基準線を出すので、一覧の所要時間から決める判定を残したまま`is_fastest`を読む分岐が増え、
判定が2本になる。①なら判定は画面の1本で、backendは件数を切るときに基準線をオブジェクトの同一性で覚えるだけで済む。
基準線は所要時間の最短を探索した経路（`road_graph_engine.py: RoadGraphEngine.select_fastest_route`は区間の所要時間をコストに探す）
なので、一覧の所要時間の最小と実質同じものを指す。

## 実施内容

- `backend/app/domain/route.py: RouteCandidate`から`is_fastest`を消した（応答の型から外れる）。
- `route_generator.py`の件数を切る処理は、評価後の候補の中の基準線をオブジェクトの同一性で覚えて残す（印を立てない）。
- テストは基準線を「一覧の中で所要時間が最小の候補」で探す形へ（`test_route_generation_behavior.py: fastest_of`）。
  既存の候補が基準線と同じ経路のときも件数を切る処理で残ることを確かめるテストを1本足した（印が消えたぶん、この経路は同一性だけが守る）。
- `export_openapi.py`→`openapi-typescript`で生成物を更新。`routeFixtures.ts`・`routeTabLabel.ts`のコメント、
  `docs/modules/backend/routing-engine.md`・`docs/modules/frontend/page-composition.md`の記述を現状へ直した。
- 応答の形の変更は、既存DBの行を読めなくする種類ではない（生成ジョブの結果は`app/infrastructure/job_registry.py`のプロセス内の辞書にしか置かず、
  永続化された`RouteCandidate`は無い）。
