# T965: 「一本化した」と書いた過去の改修が、本当にそうなっているかを棚卸しする

状態: 未完了

2026-09-19起票。段階A（20件の試し）は2026-09-24に済み、残りの進め方をダッシュボード（`T965-rest`）で問うている

## 背景

複雑度を下げる改修をしてもコードが増え続けている（[T963](T963.md)）。原因の1つは、
**旧実装が残ったまま「完了」になっていること**である。

[T956](T956.md)の作業中に実例が出た。[T546](T546.md)は「`EdgeMaterialTable`で復元コストを
Edge数に依存しなくする」を達成したが、**旧`EdgeMaterialBundle`経路は残った**。当時は意図した
並存だが、いつ解消するかを誰も持っていなかった。同じ作業中に私自身も、本番から到達しなく
なった実装を「後で消す」と言って残していた。

`docs/improvement-plan.md`の`[x]`は700件、うち「一本化・共通化・統合・撤去・削除・廃止」を
題や注記に含むものが**150件**。

## 対応方針

その150件それぞれについて、**タスクが「消した」と書いているシンボル・ファイル・経路を
いまのリポジトリでgrepする**。残っていれば、その改修は主張した状態に達していない。

結果は3つに分かれるはず。

- **消えている**: 主張どおり。何もしない
- **残っているが理由がある**（テスト専用のオラクル等）: その理由をタスクエントリへ書き足す
  ——「なぜ残すか」が書かれていないものは、次に読んだ人が本番経路だと誤解する
- **残っていて理由が無い**: 削除を起票する

あわせて、**そのタスクが残す/消すの判断に使った根拠の形**も見る。「0件だった」「使われて
いない」のように**その時点の計測だけで決めているもの**は、条件が変われば通る。
「いつなら通るのか」が書かれているかを確認し、書かれていなければ足す
（[T961](T961.md)が実例——`edge_landcover`のカバレッジ100%を見て「way側フォールバックは
死んでいる」と判定したが、実際は「いまバッチが最新」という意味でしかなかった）。

有限で、結果が白黒つく。**件数が多いので、まず20件ほどで当たりの割合を見てから残りの
進め方を決める**（全件を最初から通すと、当たりが少なかったときに費用だけ払う）。

### 母集団

**定義**: 状態が`完了`のタスク記録（`docs/records/tasks/Txxx.md`、826件）のうち、記録の題（1行目）か、
origin/master上でそのタスク番号を件名の頭に持つコミットの件名に、「何かを1つの正本・1本の実装へまとめた」ことを
表す語を含むもの。単位はタスク1件。

- 語: `一本化|1本化|一元化|寄せ|統一|置き換|置換え|統合|共通化|集約|(1|一)(本|つ|か所|箇所)(へ|に)(まとめ|畳|寄せ|絞)|へ畳|に畳|1本道|一本道`
- 当てる前に文から落とす語（語は当たるが、まとめた主張ではない）: `統合レビュー`・`統合テスト`・`統合実装`・`左寄せ`・
  `寄せた側`・`寄せるかの保留`・`T\d+(の段階|段階…)?へ(統合|寄せ)`（タスクどうしの合流）
- 数えないコミット: 件名に`起票`を含むもの・マージ（結果の主張ではない）
- 記録の題は起票時の予定だが、完了したタスクの題は「そうした」という主張として読む

**件数**: 語だけで147件、落とす語・数えないコミットを除いて**99件**（起票時の見込み約150件との差は、ほぼ
`統合レビュー`・`統合テスト`とタスクどうしの合流）。**検算**: 既知の1件
[T1044](T1044.md)（題に語が無く、コミット件名「…2つの断片へ寄せ、手書きの7か所を0にする」だけで当たる）が入ることを確かめた。

### 選び方

99件をタスク番号の昇順に並べ、Pythonの`random.Random(965).shuffle`で並べ替え、先頭から順に見た。
**見た目・配置・書式を揃えた主張**（「縦並びへ統一」「同じ見た目に統一」等）は、1つの正本・1本の実装を
主張していないので対象外として飛ばし、次を取った。先頭25件のうち対象外は5件（T417・T369・T505・T545・T372）で、
残る20件を見た。

主張が崩れている＝**同じ事実の宣言・実装が、今のmaster（`97deba4d`）に2つ以上ある**（旧い実装・二重の宣言・
写しが残る、または後から戻った）。主張の対象が後続の作り直しで丸ごと消えたものは崩れに数えない。コメント・
文書に死んだ名前が残るだけのもの、テストだけに残るものは「付随」として分けた（テストは並行する

#### 崩れていた1件（直した）

[T805](T805.md)は「較正値の宣言を1つにする」としたが、主観と時間の換算レート（P）の既定が2つあった。
較正値`evaluation.penalty_strength`の既定は0.7、`domain/evaluation.py: compose_costs_from_axis_matrix`の引数の
既定は1.0（T805より前からある）。本番の呼び出し（`road_graph_engine.py`の1か所）は必ず値を渡すので1.0は使われて
いないが、モジュール文書`evaluation-scoring.md`は「P、既定1.0」と書いており、**文書が実際の既定（0.7）と違う値を
教えていた**。引数の既定を外し（呼び出しの無い既定は宣言の二重化でしかない）、文書を較正値の宣言へ向けた。
同じ事実を主張する[T817](T817.md)（「penalty_strengthの既定値を片側importへ寄せ」、母集団の標本外の1件）も
これで同時に崩れていたことになる。

  [T1021](T1021.md)の範囲なので直していない。

#### 標本外で見つけた1件

T281を見る途中で、[T650](T650.md)（母集団の1件、標本外）の崩れが見えた。T650はバッチの起動処理
（引数の解析→ログ設定→実行）を`_common.py`の1関数へ寄せたが、後続の作り直しでその関数ごと消え、
今は`derive_topology`・`derive_node_materials`・`derive_counts`・`derive_raster_materials`・
`derive_way_materials`の`main()`が同じ骨格を1つずつ持つ。しかも各段は単独の入口（`python -m app.batch.derive_*`）を
持ち、`derive_cli.py`の「順番はここだけが持つ」と並んで**段を単独で流す扉が別にある**。単独の入口を残すかは
取込の設計判断なので、ここでは直さず改善案（ダッシュボード`T965-derive-entrypoints`）に置いた。
**当たり率には入れない**（標本の外で、無作為に選んでいない）。
