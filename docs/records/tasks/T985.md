# T985. 型注釈が正しくても、誰も照合していない 規模M

状態: 完了

2026-09-21起票。段階A（測定、担当W-types）・段階B（既存の指摘を直してCIへ足す、担当W-mypy）で完了。

## 背景

T970で`get_edges_with_geometry`の引数を`list[str]`（edge_id）から`list[LeanEdge]`
（枝そのもの）へ作り変えたとき、呼び出し側2か所がidを渡したまま残った。関東全域を
入れた新DBへ向けて実際にルート生成を走らせるまで、誰も踏まなかった。

```
AttributeError: 'str' object has no attribute 'osm_way_id'
```

**宣言は最初から正しかった。**受け側は`edges: list[LeanEdge]`と書いてあり、呼び出し側は
`list[str]`を渡していた。型検査を1回かければ只で出る食い違いである。

backendには型検査が無い（`pyproject.toml`・`requirements-dev.txt`・CIのどこにも
mypy/pyrightの指定が無い）。`ruff`は書式と未使用だけを見て、宣言と呼び出しの整合は見ない。

テストも守っていない。1374件はこの修正の前も後も通る——確定した経路へ形を取り直す一歩を
踏むテストが無い。`scripts/review_checks.py`の「位置引数の個数が定義と合わない呼び出し」は
**個数**しか見ないため、個数が合っていて型が違うこの種は素通りする。

## 対応方針

型検査を入れる。既存コードに対する初期の指摘件数を実測してから、どこまでを即時に直し、
どこからを段階的に許容するか（モジュール単位の除外）を決める。

- 実測すること: 導入時の指摘件数・実行時間・CIへ足したときの増分
- 全件を直してから入れるのか、新規の食い違いだけを止めるのかを、その数字で決める

## 完了条件

- 宣言と呼び出しの型が食い違うと、手元かCIのどちらかで**必ず**止まる
- この不整合（`get_edges_with_geometry`へ`list[str]`を渡す）を故意に戻したとき、
  実際に検知されることを確認する（「入れた」ではなく「効いている」を見る）

### 設定（`backend/mypy.ini`）

置き場はruff.toml・pytest.iniと同じ「ツールごとの個別ファイル」。設定の理由は
docs/conventions/testing.md「型検査（mypy）」に書いた。段階Aの設定から変えた・足したもの:

- `mypy_path = scripts`: 対象へ`scripts/`をそのまま入れると、`__init__.py`が無いためテストの
  `from scripts import …`と食い違い、同じファイルを`fetch_accident_csv`と`scripts.fetch_accident_csv`の
  2つの名前で見つけて起動の段で止まった。最初は`explicit_package_bases`で`scripts.<名前>`へ揃えたが、
  スクリプトの共有関数（`scripts/_stdio.py`、下の「取り込み前の指摘」）を実行時と同じ
  `from _stdio import …`で読むために、実行時の解決（`scripts/`が`sys.path`の先頭）と同じ
  `mypy_path`へ替えた。
- `platform = linux`: `benchmarks/_resources.py`の`os.getloadavg`・`resource.getrusage`が開発機
  （Windows）でだけ3件の指摘になる。本番・CIはLinuxなので、Linuxとして検査して手元とCIの答えを揃えた。
- testsは`files`に入れない（段階Aの「testsの関数の中身は見ない」から一歩進めた）。`check_untyped_defs`を
  testsだけ切っても、型注釈を持つテスト関数・フィクスチャで42件が残った（大半はテスト用の偽物を本物の
  型へ渡すもの）。全件直す決定の対象（app・scripts・benchmarks）の外で、T1021の作り直しと重なる。
- **`mypy.ini`はASCIIだけで書く**: mypyは設定ファイルをOSの既定の文字コードで読み、日本語の
  Windows（cp932）では日本語のコメント1文字で`UnicodeDecodeError`になり起動しなかった（実測）。

### 取り込み前の指摘（司令塔の/code-review high）への対応

1. `_representative_bin`が起きないはずの組み合わせを黙って0で返していた → `ValueError`で表に出す（上の一覧）。
2. 標準出力のUTF-8化を12本へ書き写していた → `scripts/_stdio.py: use_utf8_stdio`の1か所にまとめた。
   scriptsには共有モジュールが無く、既存でscriptsが読む共有の置き場（`app/batch/_common.py`）は
   設定とDB接続を読み込むため、DBに触らないスクリプト（`dead_code_survey.py`・`audit_test_rewrite.py`・
   `run_probe.py`）まで巻き込む。そこで`scripts/`の隣に置き、実行時の解決（`python scripts/<名前>.py`で
   `scripts/`が`sys.path`の先頭）に合わせて`if __name__ == "__main__":`の中で読む（テストはスクリプトを
   `scripts.<名前>`としてimportするため、モジュールの先頭では読めない）。12本とも`--help`で直接実行して
   起動を確かめた。
3. routes.pyの`assert request.destination is not None`は`-O`で消え、漏れたら500になる → 明示の分岐で
   `RoutingError`（ジョブの失敗として記録される）。同じ性質の`assert`を`app`・`scripts`・`benchmarks`で
   grepし直した: 今回足したもののうち`attributes.py`の`_row_index`は、フィールドをNoneを持たない型へ
   変えて`assert`自体を不要にした。既存の`app/domain`の`assert`（`axis_definitions.py`・`axis_display.py`等、
   段階B以前からあるもの）は今回の範囲外として触っていない。`benchmarks/bench_output_diff.py`の`assert`は
   手で走らせる比較ツールで要求処理の経路に無いため残した。
4. `ignore_missing_imports`の7ライブラリの型スタブを調べた（PyPIの配布元を確認）:

   | ライブラリ（版） | スタブ | 扱い | 外して増えた指摘 |
   |---|---|---|---|
   | PyYAML 6.0.3 | `types-PyYAML`（typeshed） | 6.0.12.20260906を固定して外した | 0件 |
   | shapely 2.0.6 | `types-shapely`（typeshed） | 2.0系の最新2.0.0.20250404を固定して外した（2.1系のスタブは本体2.1向け） | 1件 |
   | rasterio 1.5.1 | `types-rasterio`（typeshed） | 1.5.1.20260907を固定して外した | 1件 |
   | asyncpg 0.30.0 | `asyncpg-stubs`（bryanforbes、依存に`asyncpg>=0.30,<0.31`を持つ） | 0.30.2を固定して外した | 3件 |
   | APScheduler 3.11.0 | 無し（`types-APScheduler`はPyPIに無い） | 残す | — |
   | diskcache 5.6.3 | 無し（`types-diskcache`はPyPIに無い） | 残す | — |
   | mapbox-vector-tile 2.2.0 | 無し | 残す | — |

   増えた5件はどれも直した: `jma_tile_interpolation.py`の`geom_type == "GeometryCollection"`の文字列比較を
   `isinstance(clipped, GeometryCollection)`へ（shapely 2.0ではMulti系は`GeometryCollection`の子ではなく、
   判定は同じ。関数内の局所importはモジュールの先頭へ移した）、`landcover_raster.py`の`Resampling`を
   再エクスポート元の`rasterio.warp`から定義元の`rasterio.enums`へ（同じオブジェクトであることを確認）、
   `derive_topology.py`の集計の`fetchrow`がNoneを返したら`RuntimeError`（集計の問い合わせは常に1行を返す）。
   残した3つは型を照合しない（そこから来る値はAny）。3つを使う箇所は`app`の中で限られている
   （スケジューラの起動・ディスクキャッシュ・MVTのエンコード）。
5. `evaluate_axis_scalar`の`cast(float, value)`と、同じ形の`cast(SupportsFloat, …)`（`axis_preview_service.py`・
   `graph_service.py`）は`cast`のまま残した。理由:
   - 実行時の確認を足すと「数値」の型を列挙する判定を新たに抱える。材料値はDBの行・Redisの値・numpyの
     配列から来うる。`isinstance(value, (int, float))`は`numpy.int64`・`numpy.bool_`を弾き、
     `numbers.Real`も`numpy.bool_`を弾く。今は通っている値を誤って弾く危険を、確認のために増やすことになる。
   - 数値でない値が来たときは、今も黙って進まない。`str * float`は`TypeError`、`float("abc")`は`ValueError`で
     落ちる（`cast`は実行時に何もしないので、この振る舞いは段階Bの前と同じ）。
   - 項の材料がnumeric/booleanに限られることは`axis_admin.AxisDefinitionPayload._check_materials_are_known`が
     書き込み時に保証し、`graph_service.py`の`read_ms`は同じモジュールの中で数値だけが書かれる。
   - 段階Bの方針は「型注釈を実装に合わせる」で、実行時の振る舞いを変えない。確認を足すなら
     「数値でない材料値が来たら何を返すか」という仕様の判断になり、型の整合とは別の変更になる。
