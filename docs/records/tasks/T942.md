# T942. architecture.mdにT805（較正値）・edge_landcover・tile_version_serviceが存在しない 規模S

状態: 完了（2026-09-19起票・完了、統合レビュー第11回）

## 背景

規模M〜Lで新テーブル・新API・新しい管理画面タブを伴ったT805が、現状文書に1文字も反映されていない。
T919の`edge_landcover`・T848の`tile_version_service.py`も同様。
「更新されているが古い」ではなく「対応するセクション自体が存在しない」型である。

詳細は[history/2026-09-19_all.md](../../../.claude/commands/review/history/2026-09-19_all.md)。

## 対応方針

1. `docs/architecture.md`へ較正値の節を足す（テーブル・管理API・`/admin`の較正値タブ・
   `TuningEffect`の意味）。APIの一覧とデータモデルの両方に対応する記述が要る。
2. 「派生データの系譜追跡」節へ`edge_landcover`を足す（系譜の2列を持つのに、way単位のほうだけが
   列挙されている）。
3. `tile_version_service.py`（世代を実行時に組み立てて配る）を足す。あわせて撤去済み定数を
   名指ししている箇所を現在の形へ直す。
4. APIの一覧に起伏タイルのエンドポイントを足す（別の節には記載がある）。

## 再発防止

**文章のルールを足さない。** 「`backend/migrations/`に新しい`CREATE TABLE`があるのに
architecture.mdにその表名が無い」は機械的に判定できる形をしているため、まず検知器にできないかを
検討する。届かない場合だけ手順として残す。

## 実装メモ

### 追従漏れの範囲は、症状ではなく性質から出した

報告された3件（`tuning_overrides`・`edge_landcover`・`tile_version_service.py`）で終わらせず、
「migrationのDDLかORMの`__tablename__`が宣言する表名が、architecture.mdに1度も出てこない」
という性質で数えた。**表名25件のうち7件（28%）が該当**し、報告に無かった4件
（`designation_import_runs`・`osm_raw_nodes`・`raw_intersection_nodes`・
`way_divided_carriageway`・`way_geometry`）が同じ型の漏れだった。

足したもの:

- **較正値の節**（5章の末尾）: `tuning_overrides`テーブル・`GET/PUT /api/admin/tuning`・
  `/admin`の「較正値」タブ・`TuningEffect`の意味と、「プロセスを入れ替えれば効く」という
  効き方は置けないこと（T940）。APIの一覧（4章）にも両エンドポイントを足した。
- **系譜の節**へ`edge_landcover`・`way_geometry`・`way_divided_carriageway`・
  `raw_intersection_nodes`。
- **タイル世代**（`services/tile_version_service.py`）: 焼き込みSQL（形）は自動で署名される
  のに、SQLが読むテーブルの中身（世代）はビルド時の生成物に入らない——この2つを実行時に
  繋ぐ層があること。
- **起伏タイル**（`GET /api/gsi-terrain-tile/{z}/{x}/{y}.png`）をAPIの一覧へ。
- `designation_import_runs`・`osm_raw_nodes`を、それぞれ指定路線・生OSMデータの記述の中へ。
- 撤去済みの`MAP_LAYERS`・`STATIC_FILTER_AXES`の名指しを、実行時に組み立てる現在の形
  （`buildMapLayers()`・`buildStaticFilterAxes()`）へ直した。

### 検知器にした（`undocumented_tables`）

母集団は**migrationのDDLとORMの`__tablename__`の両方**。片方だけでは、ORMを持たない表
（`way_geometry`）と`create_tables()`だけで作る表のどちらかが漏れる。名前が1度でも
architecture.mdに出ていれば通す——どう書くべきかは機械には決められないが、「この表が
あることを文書が知らない」だけは分かる。

`--staged`/`--since`は変更されたファイルが宣言する表だけに絞り、全件走査では母集団全体を
見る。`DETECTOR_ENFORCEMENT`は3経路すべてで強制。

**外縁**: アプリ自身が生SQLで作る表は拾えない。実在するのは`schema_migrations`
（`migrate.py`がブートストラップ時に作る）の1つだけで、migrationで管理する表ではない。
母集団へ入れるには任意のSQL文字列を読むことになり検知器の性質が変わるため、`EDGE_GAP_NOTES`
へ理由を書いて開けたままにした。

## 検証

- `python scripts/review_checks.py mutate --case undocumented_tables`: pre-commit経路・CI経路
  ともPASS（わざと入れた新規migrationを1件検知、exit=1）。外縁は宣言どおりGAP。
- `python scripts/review_checks.py docs` 全件で違反なし（この検知器も0件）。既存の記載を
  足す前は7件検知していた。
- `python scripts/review_checks.py mutate` 全件: 正例50件PASS・外縁25件が期待どおり。
- `pytest scripts/tests/test_review_checks.py -q` 147 passed
  （残る1件`test_npx_cli_path_finds_it_next_to_the_resolved_npm_cli`はWinError 1314＝
  Windowsのシンボリックリンク権限による既存の失敗で、CIのLinuxでは通る）。

新しい記述を書いた副作用として`removed_axis_mentions`が1件鳴った（「蛇行」という語を
現行の軸として読んだ）。表現を「道の曲がり具合＝度/km」へ変えて解消。
