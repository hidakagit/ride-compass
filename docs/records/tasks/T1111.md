# T1111. backendのデプロイは、入れ替えたコンテナが /health に応答するまで待ち、応答しなければ失敗として止まる

状態: 未完了（2026-09-25起票）

## 背景

T1059で、本番と同じDockerfile・docker runの引数でも、起動が止まる状態（ワーカー2で作り直しが続く・ワーカー1で再起動の繰り返し）のままコンテナはUpでデプロイのジョブは成功扱いになることを確かめた。deploy-backend.ymlは docker run -d で終わり起動の成否を見ていない。docker run -d のあと /health が200を返すまで待ち、上限までに返らなければ docker logs の末尾を出してジョブを失敗させる。待つ上限は本番のログ（起動の開始と最初の応答の時刻）から決める。起票案 proposal-deploy-health-wait（担当 D-workers、2026-09-25 承認）

## 段階1: 応答を待つ仕組み（2026-09-26、T1112のクラウドのセッション）

`deploy-backend.yml`の`docker run -d`の直後に、`curl http://localhost:8000/health`が今ビルドしたコミット（`"commit":"$GIT_COMMIT"`）を
返すまで2秒おきに待つ段を足した。上限（`HEALTH_WAIT_SECONDS`）までに返らなければ、`docker inspect`の状態と再起動回数・
`docker logs --tail 200`を出して`exit 1`でジョブを失敗させる。応答までの秒数は毎回ジョブのログに出る（`入れ替えたコンテナが/healthに
応答するまで N秒`）。コミットを照合するのは、別のプロセスの応答を取り違えないため（旧コンテナは先に止めているが、照合は安い）。

検証: 待つ段を抜き出し、模擬の/health（指定秒後に応答する・別のコミットで応答し続ける・応答しない）へ当てた。3秒後に応答→4秒で
成功（終了コード0）、別のコミット→上限6秒で失敗（終了コード1、状態とログの末尾を出す）、応答しない→上限4秒で失敗（終了コード1）。
`yaml.safe_load`で定義が読めることを確かめた。

**上限の値は未確定**: このセッションは本番VMへ入れないため、起動から応答までの実測が取れていない。上限を仮に180秒にしてあり、実測で
決め直すまでこのタスクは閉じない（問い・操作は仕掛中のダッシュボード`T1111-measure-startup`）。起動時に走るのはDBからの軸定義と較正値の
読み込みだけで（定期ジョブは裏で動き応答を待たせない）、長くなる理由は構造上は見当たらない——実測はそれを確かめるためにも要る。
