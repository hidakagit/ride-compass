# T1091. バッチの入口（取込・派生・DBの立ち上げ）が1つずつ持つ起動処理の写しを共有の関数へ寄せる

状態: 完了（2026-09-24起票、同日完了）

## 背景

背景（T965 段階Bの点検で見つけた崩れ。T650の主張「バッチのCLI起動処理を_common.pyへ寄せる」に反する）: 派生の段ごとの入口5本はT965 段階Bで消したが、残る入口（取込の ingest_cli・派生の derive_cli・まっさらなDBの立ち上げ bootstrap_database）の main() が、ログの設定→--database-url の読み取り→設定値への代替→世代番号の更新で包んで実行、という同じ骨格を1つずつ持つ。T650はこの骨格を _common.py の1関数（run_simple_batch_cli）へ寄せたが、バッチの作り直し（T970）でその関数ごと消え、写しに戻った。

起きうること: 起動処理を直すとき（ログの形式・世代番号の更新の条件等）に3か所を同じように直す必要があり、1か所だけ直すと入口ごとに挙動がずれる。
起きない場面: 今は3か所が同じ形で揃っている。

見立ての注意: 入口ごとに引数が違う（取込は --profile 等、派生は --from）ので、共有するのは「ログ→DBのURL→世代番号の包み」の部分だけになる。共有する部分が小さい（1入口あたり5行前後）ので、寄せない（写しのまま置く）判断もありうる。T970がこの関数を消したときの判断の記録は見つけていない。

なぜ既存のタスクに入らないか: T650は完了済み。T965 段階Bの点検の中では、寄せる形（何を共有の関数へ入れるか）に設計の判断が要るため、規模Sの整理の範囲を超えるとして切り出した。同じ崩れのうち、計測スクリプト（measure_axis_saturation.py）のDB接続の写しはT965 段階Bで直した。

## T970が以前の共有関数を消した理由（着手前の確認）

`git log -S run_simple_batch_cli -- backend`で、関数を消したのはT970段階A（3aef4653b）。本文は
「`_common.py`の7定義（`run_chunked_precompute`ほか。使っていた`precompute_*`が全て削除済み）」で、
ASTで被参照0の定義を機械的に落とした一掃の1件だった。寄せる形を否定した判断ではなく、使い手が
段階C（91bc38328）で消えたための撤去である。今は同じ骨格を持つ入口が3本あるので、その理由は
成り立たない——寄せる。

## 対応

母集団: DBを書き、派生データの世代を進める入口＝`with_derived_data_revision_bump`を呼ぶ`main()`。
`with_derived_data_revision_bump`をgrepし、本番コードの呼び出し元は`ingest_cli.py`・
`derive_cli.py`・`scripts/bootstrap_database.py`の3本（他に`--database-url`を持つのは
`scripts/schema_gap.py`だけで、DBを書かず世代も進めないため外）。

- `_common.py`へ`run_batch_cli(parser, start)`を足した。ログの設定・`--database-url`の追加と
  読み取り・設定値への代替・`asyncio.run`・世代の更新をここだけが持つ。入口は自分の引数と、
  引数とDBのURLから本体のコルーチンを返す`start`だけを書く。`start`はイベントループの外で
  呼ばれるので、取込の引数検査（`parser.error`）はそのまま`start`の中に置いた。
- `with_derived_data_revision_bump`の`dry_run`引数を消した。3本とも`False`を渡しており、
  真になる経路が無かった。そのテスト（`test_dry_run_does_not_bump`）も消した。

振る舞いの差: `--help`の並びで`--database-url`が最後に出るようになった（取込は従来
`--all`と`--profile`の間）。引数・ログの形式・世代の更新の条件は変わらない。
