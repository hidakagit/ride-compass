## 段階B以降の進め方（2026-09-22、段階Aでたどり着いた形）

段階Aは「地図の状態適用を1経路へ」から始めたが、**実際に効いたのは別の軸**だった。
同じ軸を段階B以降にも当てる。会話で決めた判断は次のセッションへ届かないのでここへ残す。

### 1. フロントが「定義・宣言・源泉」を持っている時点で疑う

画面は配信されたものを出すだけ。**残ってよいのはbackendが知りえない、描画媒体の事実
だけ**——MapLibreの式の書き方、指で押せる幅、ライト/ダークで2値を持つ色、アイコンの
識別限界（WMOコードを6種へ丸める等）。それ以外（分類・束ね方・行の名前・色・閾値・
タイルの範囲・出典・レイヤーの一覧）は源泉側。

判定は「全体で唯一か」ではなく**「源泉であり、どこからも導出できないか」**。唯一でも
写しなら消える。

### 2. 照合テストがあること自体が、写しがある証拠

「生成物と一致するか」「backendと同じか」を見る検査は、**一致させたい2つがあるから**
存在する。写しを消せば検査ごと消える。逆に、写しを消したのに検査だけ残ると
`x === x` になる（実際に2件あった）。**写しを消したら、その写しを見張っていた検査も
同時に消す。**

### 3. テストが実装の内部を覗いているのは、置き場が違う印

「テストからのみ参照されるexport」は、口を閉じる前に**そこにあるべきかを見る**。

- 画面部品の中の純関数（整形・丸め・並べ替え）→ `lib/`へ移す
- 状態を地図へ当てる一連 → `features/map/scene/`へ移す
- 移せば口は正当になり、テストはそのまま使える

**他ファイルへ実行時に依存する道具を、テストから直接叩かない**——自分は何も変えて
いないのに、他人の変更で落ちるテストになる。型だけの依存・同一モジュール内は
これに当たらない（型が変われば先にコンパイルが落ちる）。

### 4. 機械の出力をそのまま処置へ繋げない

grep・参照カウントが出すのは候補。CLAUDE.md「修正の原則」に立てた（実例: 参照0の
一覧にNext.jsが読む`metadata`が入り、`viewport`とroute handlerは語の偶然で残った）。
**構文や名前で性質を決めない**——「値をimportするテストは写経だろう」と見込んだ4件は
4件とも正当だった（CSSの`@media`との突き合わせ、境界の振る舞い）。

## 段階Aの設計方針（2026-09-22、ユーザー承認）

仕様（`docs/modules/frontend/static-map-layers.md`・`map-axis-coloring.md`・
`dynamic-weather-layers.md`）から起こした。**挙動を変えないもの**:

1. **地図の中身を状態の純関数にする**。`buildMapScene(state)`（純関数）→
   `applyMapScene(map, scene, prev)`（唯一の書き手）。`setStyle`後は`prev`を空にして同じ
   関数を呼ぶため、再描画専用の経路を持たない。source/layerの追加・filter・feature-state・
   visibilityはすべてsceneが持つ——docsが「redrawから辿れない描画は消えたまま戻らない」
   「明示的に再適用しないと無色のまま残る」と暗黙の前提として警告している条件が、
   構造として発生しなくなる。
2. **`MapView`の受け口はscene 1つ＋イベント**。組み立てが純関数になるため、jsdomのcanvas
   制約で今テストが無いレイヤー登録（`static-map-layers.md`明記）を単体テストで書ける。
3. **重なり順を1つのリストへ**。段（`paintTier`）が「基礎地図の下／上」も持ち、面かどうかを
   レイヤーの`type`から推測しない。
4. **データ取得状態は記述子の1契約へ**（`mapViewLayerDataStatus`と
   `dynamicWeatherDataStatus`のマージを消す）。
5. **派生だけのフックを純関数へ**（hooks 21本のうち実際にfetchするのは4本）。

**挙動が変わるもの**（4件ともユーザーが採用を選択）:

- **A. 段（band）キーの綴りを統一する**。いまramp軸は`${axisId}-${index}`、専用way値配信軸は
  `step-N`で、ルート生成をまたいで隠した段が保たれるかが軸の種類で変わる。統一すると
  どの軸でも保たれる。**保存済みの旧キーは1回だけ無効になる**（隠していた段が一度戻る）。
- **B. 「段を隠す」を透明色へ一本化する**。`filter`（ramp軸）と透明色（専用配信軸。
  feature-stateは`filter`から読めない）の2実装を1つにする。**透明な線のクリック判定が残る**
  ため、当たり判定側も同じ非表示キーを見るよう揃える（揃えれば利用者から見た挙動は同じ）。
- **C. 初期表示の覆いを`idle`待ちからやめる**。基礎地図が描けた時点で外す
  （`INITIAL_TILES_OVERLAY_MAX_MS`は保険として短く残す）。覆いが外れるのが早くなる。
- **D. レイヤーidを規約から導出する**。id定数のexportを廃止し、記述子から導く
  （動的気象の`region-dynamic-weather-${id}-${source}-${sub}`と同じ形へ揃える）。
  テストからのみ参照されている34本のexportはここで消える。

**新しいコードの置き場**: `frontend/src/features/map/`（段階Dの目標構成の位置）。新規ファイルは
importが増えるだけで既存の参照を動かさないため、先に目標位置へ置いて段階Dの移動量を減らす。

### 時機の制約（差分に出ない／出にくいもの）

1. **再描画は連打ガードを持つ**。`style.load`が確定するまで次の`setStyle`を出さない。1回目が来ないと以後の再描画が出ない
2. **世代の到着は`isStyleLoaded()`で早期returnしない**。準備中に届くと二度と走らずタイルが永久に出ないため`runWhenStyleReady`を通す
3. **`clearRoadTileFeatureState`はソース単位で全キーを消す**。1軸だけOFFで呼ぶと、まだONの軸の色まで巻き添えになる
4. **`applyInspectedWay`はレイヤーがある間だけ効く**。`setStyle`後は再描画が復元しないと強調だけが消える
5. **refへ写す16本のeffectは、effectの宣言順に依存する**。地図を触るeffectより前に最新値が入っていることが前提

## 段階Cの方針（2026-09-22、ユーザー指示）

**実績のある既成部品を既定にする。自前で作るのは、仕様が理由を持って要求している見た目だけ。**
いまの見た目には主観で決まった部分が多く混じっており、**主観を独自部品で再現するコストは
見合わない**（ユーザー判断）。

### 主観と要求の切り分け

- **要求**（そのまま再現する）: `docs/architecture/design-principles.md`「UI仕様」と
  `docs/modules/frontend/frontend-design-system.md`に**理由が書かれているもの**。例:
  地図の視界を削らない・走行中に見るかで情報量を絞る・状態ドットの3表現・
  ドラッグ移動や高さドラッグのように既成品で表現できない振る舞い。
- **主観**（既成部品の既定へ寄せてよい＝見た目が変わることを許容する）: 理由が書かれていない
  色味・角丸・余白・境界線・影・アイコンボタンの寸法。

### 使う部品

**既に依存に入っているものを優先する**（2026-09-22時点: Radix の accordion/checkbox/dialog/
popover/tabs/toggle/toggle-group、`class-variance-authority`・`clsx`・`tailwind-merge`、
`embla-carousel-react`）。**新しい依存を足すのは、これらで賄えないと示せたときだけ。**

### 対象の出し方

`button`・`chip`・`toggle`を名前に含むCSSクラス（2026-09-22時点で23ファイル・62クラス）から。
一覧は機械で出す:

```
grep -rn "^\.[A-Za-z-]*\([Bb]utton\|[Cc]hip\|[Tt]oggle\)" frontend/src --include=*.module.css
```

### 完了条件

- 自前で残した部品ごとに、**なぜ既成品で賄えないか**を1行書く。書けないものは既成品へ寄せる
- `frontend-design-system.md`「意図的に作らない・統合しないもの」を、この作業の結果で更新する

## 分割して書いた後に、全体を最適化する工程（2026-09-22追加）

**並列で書かせると、書き手はそれぞれ局所最適を出す。誰も全体を見ないので、同じ形が人数分
生まれる。** これは書き手の失敗ではなく、分割した側が束ね直す工程を置かなかった失敗である。

実測（地図の6家族2,040行、2026-09-22）: 型定義702行（34%）・補助関数254行が家族へ散在。
`〜Style`型・`hitTargets`・`tier`が6/6家族、ソースの中身を差し替える口（`content`＋`replace`）が
5/6家族、`LayerSpecification`へのキャストが4/6家族、idの導出が4/6家族。

### 不変条件: 階層ごとにマージし、その階層以下は全体最適であること

**ある階層をマージする時点で、その階層の兄弟どうしに重複が無く、下の階層が既に括り出されて
いること。** 上へ積む前にこれを満たす——満たさないまま積むと、重複は上の階層の形として
固定され、以後は「そういう作りだから」になる。

階層は下から: ①sceneの土台 → ②家族（面・路面の線・点・軸・気象・ルート） →
③地図の合成（`MapView`の配線） → ④画面の状態 → ⑤UI基盤 → ⑥配置。

マージの直前に、その階層の兄弟すべてに対して下の判定を回す。

### 括り出すかの判定

**3つ以上の担当に同じ形が現れたら、土台へ引き上げる。** 判定は機械で出す:

```
# 同じ形が何家族に出るかを数える（形は grep で表せるものに限る）
for pat in "declareLayer" "replace: (source" "as unknown as LayerSpecification" "hitTargets"; do
  n=0; for f in frontend/src/features/map/scene/*Scene.ts; do grep -q -- "$pat" "$f" && n=$((n+1)); done
  echo "$pat: $n"
done
```

引き上げた後も「**1つ増やすときに触る場所が1箇所**」が保たれることを、各担当の報告と同じ
基準で確かめる——共通化のために足す場所が増えたら、それは別の悪化である。

### 完了条件

- 3家族以上に現れる形が残っていないこと（上のコマンドの出力で確認する）
- 引き上げの前後で、実装・テストの行数を測って記録すること（**減っていなければ、
  引き上げが失敗している**）

## 段階Aの品質（2026-09-23・周期レビュー第12回で4観点から測った結果）

### 達成できなかったこと（4観点すべてが同じ型の症状を挙げた）

## 段階Bの進め方（2026-09-23、周期レビュー第12回の実測を完了条件に取り込む）
