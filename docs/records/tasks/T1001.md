## 進め方（両面から確認する）

**「今あるものから無駄を省く」形にしない**——省くかどうかの判断基準が既存実装の形に引きずられ、
揺らぐ。[T998](T998.md)がテストで採った形を実装にも採る。単位は下記「段階」の1つ。

1. 対象の責務を**仕様から起こす**（`docs/modules/frontend/*.md`・
   [design-principles.md](../../architecture/design-principles.md)・画面の実物）。**既存実装は開かない**。
2. 起こした形で実装を書く。
3. 既存とdiffを取り、**両方向を判定する**:
   - **新版にしか無い**: 既存が持っていなかった。入れる。
   - **旧版にしか無い**: 3つに分ける。
     - **今も要る**（仕様の読み落とし・docsに書かれていない挙動）→ 残し、**なぜ仕様から起こせなかったかを
       docs側へ1行足す**。これを足さないと次に起こし直す人も同じ落とし方をする。
     - **過去の不具合を刺している**（実装から復元できない知識）→ 残し、理由を1行書く。
     - **到達しない・写経・撤去済み機構の見張り** → 消す。
4. 同じ単位でテストも起こし直す（T998の手順）。**実装を内部化すると「テストからのみ参照」の126本は
   必ず触ることになるため、テストと分けない**。

## 目標構成

1. **地図は「望ましい状態を純関数で組み立て、1本の適用器が差分を当てる」**。設計原則 構造仕様8が
   「一覧を1か所へ宣言して各経路がそれを参照する形は1本道ではない」と定めているのがこの形。
2. **`page.tsx`の状態を意味の単位へ分ける**。`localStorage`は`useStoredState`1本だけを通す。
3. **UI基盤を実体化する**（Button/Chip/Panel/Field）。CSSは`composes`前提へ。
4. **層をディレクトリに出す**: `app/`（コンポジション）→ `features/`（機能）→
   `components/ui/`（プリミティブ）→ `lib`・`services`（I/O）。
5. **到達しない公開ドアを畳む**。

## 段階Aの設計方針（2026-09-22、ユーザー承認）

仕様（`docs/modules/frontend/static-map-layers.md`・`map-axis-coloring.md`・
`dynamic-weather-layers.md`）から起こした。**挙動を変えないもの**:

1. **地図の中身を状態の純関数にする**。`buildMapScene(state)`（純関数）→
   `applyMapScene(map, scene, prev)`（唯一の書き手）。`setStyle`後は`prev`を空にして同じ
   関数を呼ぶため、再描画専用の経路を持たない。source/layerの追加・filter・feature-state・
   visibilityはすべてsceneが持つ——docsが「redrawから辿れない描画は消えたまま戻らない」
   「明示的に再適用しないと無色のまま残る」と暗黙の前提として警告している条件が、
   構造として発生しなくなる。
2. **`MapView`の受け口はscene 1つ＋イベント**。組み立てが純関数になるため、jsdomのcanvas
   制約で今テストが無いレイヤー登録（`static-map-layers.md`明記）を単体テストで書ける。
3. **重なり順を1つのリストへ**。段（`paintTier`）が「基礎地図の下／上」も持ち、面かどうかを
   レイヤーの`type`から推測しない。
4. **データ取得状態は記述子の1契約へ**（`mapViewLayerDataStatus`と
   `dynamicWeatherDataStatus`のマージを消す）。
5. **派生だけのフックを純関数へ**（hooks 21本のうち実際にfetchするのは4本）。

**挙動が変わるもの**（4件ともユーザーが採用を選択）:

- **A. 段（band）キーの綴りを統一する**。いまramp軸は`${axisId}-${index}`、専用way値配信軸は
  `step-N`で、ルート生成をまたいで隠した段が保たれるかが軸の種類で変わる。統一すると
  どの軸でも保たれる。**保存済みの旧キーは1回だけ無効になる**（隠していた段が一度戻る）。
- **B. 「段を隠す」を透明色へ一本化する**。`filter`（ramp軸）と透明色（専用配信軸。
  feature-stateは`filter`から読めない）の2実装を1つにする。**透明な線のクリック判定が残る**
  ため、当たり判定側も同じ非表示キーを見るよう揃える（揃えれば利用者から見た挙動は同じ）。
- **C. 初期表示の覆いを`idle`待ちからやめる**。基礎地図が描けた時点で外す
  （`INITIAL_TILES_OVERLAY_MAX_MS`は保険として短く残す）。覆いが外れるのが早くなる。
- **D. レイヤーidを規約から導出する**。id定数のexportを廃止し、記述子から導く
  （動的気象の`region-dynamic-weather-${id}-${source}-${sub}`と同じ形へ揃える）。
  テストからのみ参照されている34本のexportはここで消える。

**新しいコードの置き場**: `frontend/src/features/map/`（段階Dの目標構成の位置）。新規ファイルは
importが増えるだけで既存の参照を動かさないため、先に目標位置へ置いて段階Dの移動量を減らす。
