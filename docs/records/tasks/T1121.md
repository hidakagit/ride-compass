# T1121. 配信で値を受け取る評価軸（勾配のレンズ等）の線が、値があっても全部破線になるのを直し、地図の式がfeature-stateを読めない場所で使っていないかを検査する

状態: 完了（2026-09-25起票・2026-09-26完了）

## 背景

ユーザー報告（2026-09-26、スマホ）: 勾配のレンズの線が全て破線になった。原因: T1105で値が無い道を破線にしたとき、配信で値を受け取る軸（値はfeature-state）の「値が無い」の判定式をline-dasharrayへ渡した。MapLibreのline-dasharrayはfeature-stateを読めない（style-specのparametersがzoom・featureだけ）ため、どの道も値が無いと判定されて破線になる。MapLibreのスタイル検証（validateStyleMin）はこの誤りを捕まえない（実測: feature-stateを含むline-dasharrayでエラー0件）。ユーザー指示: 他も総点検し、変な依存関係ができているならシンプルにする。規模の根拠: axisLines.ts・scene.state.contract.test.ts・axisLines.test.ts・設計書で、変わるファイルは3（③7以下）。

## 実施（2026-09-26、T1112のクラウドのセッション）

- 総点検の母集団: 地図へ渡すすべてのレイヤーのpaint・layout・filterの式（`scene.state.contract.test.ts`の「出せるものを全部出した
  状態」。道路の線・点・面・評価軸（タイル値・配信値）・気象・ルート）。feature-stateを組み立てる箇所はコードに1か所だけ
  （`axisLines.ts: valueExpression`の配信値の軸）で、grepで確かめた。
- 検査: 式にfeature-stateが現れたら、そのプロパティのstyle-spec（`latest.paint_<種類>`・`layout_<種類>`）の
  `expression.parameters`が`feature-state`を含むこと、filterには現れないことを確かめるテストを足した。直す前の実装で
  落ち、引っかかったのは`road-tiles-ded1`・`road-tiles-ded2`の`line-dasharray`の2件だけ（他に読めない場所で使う式は0件）。
- 直し方: 破線へ渡す「値が無い」の条件を、地物から読める軸（タイル値）だけが持つ形にした（`dashableMissingCondition`）。
  配信値の軸で値が無い道は、色（データなし）と薄さだけで示す。取得中は破線にしない、という分岐はこれに含まれて消えた。
- 勾配のレンズで大半の道に線が出ていなかったのは別の理由: 配信値が無い道（標高が未計算の道と、向きを指定したときに直角に
  近い道。map-axis-coloring.mdの暗黙の前提）は不透明度0.15で描かれ見えていなかった。T1120（0.6）が入ると灰の実線で見える。
- T1110（太さ）の式はタイルのプロパティだけを読み、上の検査を通る。
