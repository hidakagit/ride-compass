# T586: 周回の折返し点選定（`select_loop_turnarounds`）の木の後段処理が本番で約3.3秒かかる遅延の調査・是正

状態: 完了（2026-09-05起票・同日調査・同日案Aで実装。[T585](T585.md)の本番検証で発覚。本番反映後の実測は下記「本番実測」節）

## 背景

[T585](T585.md)の本番検証（東京駅25km・`max_routes=8`、edges=477,365）のbackendログで
`select_ms=3,390ms`を観測した。[T531](T531.md)の本番実測（同条件）では`select_ms=141ms`
（うち一対全木50ms）だった。今回の`select_turnarounds`ログは
`ring_nodes=28878 examined=4000 selected=19 pool=24 tree_ms=103〜116 total_ms=3389〜3400`で、
一対全木ではなく木の後段（候補走査・同点タイブレーク・多様性間引き）に約3.3秒かかっている。
開発DB（edges=319,530）でも`tree_ms=94〜187 total_ms=16,203〜76,516`（負荷で変動）と再現する。

## 調査結果（2026-09-05、開発DB・東京駅25km・cProfile）

温パスの`select_loop_turnarounds`（累積30.76秒）の内訳:

| 関数 | 呼び出し | 累積 |
|---|---|---|
| `_diversify_ties_by_bearing`（[T554](T554.md)の同点タイブレーク） | 1 | **30.26秒** |
| `select_diverse_by_overlap`（多様性間引き、[T568](T568.md)のビットマスク版） | 1 | 0.48秒 |
| `tree_path_edge_indices`（往路復元） | 910 | 0.25秒 |
| `build_shortest_path_tree`（一対全木） | 1 | 0.19秒 |

原因は`_diversify_ties_by_bearing`の計算量。最遠点貪欲法を「同点グループ内の候補×
**既に並べた全候補**（グループをまたいだ累積、最終的に`examined`=4,000件）」の角距離行列を
1件並べるたびに作り直す形で実装しており、`np.append`/`np.delete`もその都度O(n)で走る。
合成データ（n=4,000）の実測:

| 同点の構造 | 所要時間 |
|---|---|
| 全候補が同点（1グループ4,000件） | 231秒 |
| 小数1桁で40段階（平均100件/グループ） | 6.7秒 |
| 小数1桁で400段階（平均10件/グループ） | 0.37秒 |

グループが小さくても「既に並べた全候補」との比較は候補の位置に比例して増えるため、
`examined`=4,000件の走査全体でO(n²)以上になる。T531の本番実測（141ms）はT554より前の
計測で、T554（2026-09-03）の完了時に本番同等条件の計測が行われていなかった。
T553/T557/T568は無関係（間引き自体は0.5秒未満）。

意図の確認（ユーザー、2026-09-05）: T554の目的は「同じ方向の経路ばかりにならないようにする」
こと。是正はこの意図（採用される候補が複数方位へ散ること）を保ったまま計算量を落とす。

## 対応方針（案、着手時に精査する）

推奨は案A。案Bは案Aと併用可能。

- **案A（推奨）: 方位の広がりを「並べ済みの全候補」ではなく「採用済み候補」に対して評価する。**
  現行は`select_diverse_by_overlap`で間引く前に4,000件全体を並べ替えており、比較対象の
  大半は最終的に採用されない候補である（代理指標）。意図は「採用される最大`pool_size`
  （24）件が複数方位へ散ること」なので、`select_diverse_by_overlap`の走査の中で、同点
  グループ単位に「採用済み候補との角距離の最小値が最大」の候補から順に試す形へ移す
  （グループ内で採用済みが増えるたびに再選択。計算量はO(`examined`×`pool_size`)）。
  同点でないグループ間の順序（difficulty昇順）・最初の1件が`closeness_key`最小である点・
  決定性はそのまま。`tests/test_road_graph_engine.py`のT554テスト（全同点時の象限分散・
  difficulty順序維持・決定性・車輪状フィクスチャで4象限）を仕様として維持する。
- **案B: 現行アルゴリズムのまま計算量だけ落とす。** 各候補の「並べ済み候補との角距離の
  最小値」を配列として持ち、1件並べるたびに新しい方位との距離でO(remaining)の`np.minimum`
  更新だけを行う（行列の作り直し・`np.delete`・`np.append`を廃止）。O(n²)は残るが
  n=4,000で数百ms程度の見込み。案Aを採らない場合の最低限の是正。
- **案C: タイブレークの対象を上位K件（例: 500）に限定する。** 実装最小だが、Kの根拠が
  経験則になる。

## 完了条件（案）

- 本番同等条件（東京駅25km、`backend/benchmarks/bench_t531_route_generation.py`）で
  `select_ms`がT531実測と同水準（数百ms以下）に戻ること。
- T554の既存テストがすべてpassし、候補の方位分散が実機（または合成フィクスチャ）で
  維持されること。
- `docs/modules/backend/routing-engine.md`の折返し点選定の記述を同一コミットで更新する。

## 放置した場合の影響

周回生成の温パスで約3.3秒（本番25km）が毎回上乗せされ、[T585](T585.md)で削った1.5秒を
打ち消して余りある。同点が多い重み設定（該当軸のデータが無い地域・重みを1軸へ集中させた
設定）ほど悪化し、全候補同点なら本番でも数十秒〜分単位になりうる（合成データで231秒）。

## 実施内容（2026-09-05、案A）

- `domain/routing.py: select_diverse_by_overlap`に`tie_groups`（同点グループ列）と
  `prefer(残り候補, 採用済みリスト)`（グループ内の試行順を採用済みに応じて返す。1件採用する
  たびに残り候補へ呼び直す）を追加した。`tie_groups`無しの既存呼び出し（`select_via_nodes`）は
  各itemを1件のグループとして扱い挙動は変わらない。閾値緩和の再検査は、重複率だけで
  飛ばした候補をグループ単位で保持して次の閾値で同じ仕組みで再走査する。
- `services/road_graph_engine.py`: `_diversify_ties_by_bearing`（並べ済み全候補に対する
  最遠点貪欲法）を撤去し、`_order_by_bearing_spread`（採用済み候補との方位角距離の最小値が
  大きい順、同値はリング中心近さ→Node index順、採用済み無しはリング中心近さ順）を
  `prefer`として渡す。`select_loop_turnarounds`は`difficulty_key`の連続区間を
  `tie_groups`として渡す。difficulty群の順序（主キー）・同点でない候補間の順序は不変。
- テスト: `tests/test_routing.py`に`tie_groups`/`prefer`の呼び直し順・閾値緩和の再検査の
  テスト2件、`tests/test_road_graph_engine.py`の旧`_diversify_ties_by_bearing`直接テスト3件を
  `_order_by_bearing_spread`のテスト3件（採用済み無しの順序・貪欲採用で4象限・決定性）へ
  置き換え。T554の統合テスト（車輪状フィクスチャで4象限）はそのままpass。
- `docs/modules/backend/routing-engine.md`の折返し点選定・`select_diverse_by_overlap`の
  記述を更新。
