# T1023. scene移行で置き換えられた側の残骸を撤去し、列挙器の穴を塞ぐ

状態: 完了（2026-09-23）

## 背景

T1001段階Aで地図の描画を`frontend/src/features/map/scene/**`へ移したが、**置き換えられた側が
残り、テストだけがそれを生かしている**。CLAUDE.md「置き換えた側が本番から呼ばれなく
なったら、そのテストも同時に消す」に反する。

**根本原因は撤去の漏れではなく、列挙器の穴**である。T1015で「テストからのみ参照される
export」を絞り込んだとき、**識別子がコメント本文に出るだけで「消費者あり」と数えていた**。
`redrawAllLayers`はまさにこれで生き残っている（本番の再描画は
`applyScene(map, sceneRef.current, {reset:true})`が担い、`redrawAllLayers`を呼ぶのは
契約テストだけ。非テストのヒットはすべてコメント）。CLAUDE.mdがT1001の実例として挙げる
「語が他所に出た偶然だけで残った」と同じ形が、別の向きで再発している。

読んで確かめた代表例（**網羅ではない。完全な対象は下の導出で出す**）:

- `features/map/scene/applyToMap.ts`の`redrawAllLayers` — 本番参照0。
- `components/Map/dedicatedWayValueLayer.ts` — ファイル全体が島になっており、唯一の
  入口`dedicatedWayValueColorExpression`に本番消費者が無い。生きた色式は
  `features/map/scene/groups/axisLines.ts`が持つ。
- `components/Map/valueScale.ts`の段階色の式 — 上の島からしか到達しない。
- `features/map/scene/mapScene.ts`の`sceneLayerIdsForRole` — **T1001段階A
  （`aea79db2`）で新設したものが、最初から本番参照0**。同じコミットで書いた
  `docs/modules/frontend/static-map-layers.md`が「役割からレイヤーを引くときはこれを使う」と
  規約にしているが、使う人がいない。
- `components/Map/MapView.tsx`の`redrawPropsRef` — 16フィールドを持ち、読まれるのは
  可視フラグ2つだけ。16依存の`useEffect`が毎回オブジェクトを作り直し、誰も読まない場所へ
  14フィールドを書いている。直下のコメントは「refが保持する最新値を渡すだけの薄い包み」と
  述べるが、本体はrefを読んでいない。
- 宣言に付いていないJSDocブロック — 撤去でコードだけが消え、それを説明する文が残った形。
  とくに`components/Map/mapLayers.ts`には、現行と綴りの違う段の一覧
  （`estimateLine`/`rawLine`。生きている宣言は`estimatedLine`/`observedLine`）が
  **第2の語彙宣言として**残っている。次にこれを読んだ人は存在しない綴りを書く。

## 対応方針

1. **列挙器を直し、検算してから使う。** 消費者は**import文で名指しされる参照だけ**で
   数える。コメント・同一ファイル内の使用・文字列一致を消費者に数えない。
   フレームワークが規約で読む口（`app/**/route.ts`の`GET`/`POST`、`layout.tsx`の
   `metadata`/`viewport`）は**名前の除外リストではなく位置**で判定する
   （CLAUDE.md「名前の除外リストで逃げない」）。
2. **検算**: 直す前に、既知の1件`redrawAllLayers`がこの列挙で「本番消費者0」と出ることを
   確認する。前回の列挙器ではこれが出なかった。出ないうちは列挙器がまだ穴を持っている。
3. **撤去は2段に分ける。** コードの参照が0かはコードの判定で、文には効かない。
   撤去する差分のコメント行を`docs/conventions/comments.md`の判定木へ1件ずつ通し、
   他に記録の無い横断的な判断は`docs/modules/*.md`へ昇格してから消す。
   **同じスクリプトでまとめて落とさない**（CLAUDE.md）。
4. `MapView.state.contract.test.ts`は同じ計算に2つの入口を使っている。呼び口を
   `applyScene(..., {reset:true})`へ揃えれば、テストを残したまま`redrawAllLayers`が消える。
5. `redrawPropsRef`を、実際に読まれるものだけへ縮める。
6. `static-map-layers.md`の`sceneLayerIdsForRole`の規約は、**使う人を作るか規約ごと落とすか**を
   決める。決めずに残すと、守る対象の無い規約が増える。

## 完了条件

- 上の導出（import文ベース）で「`frontend/src`の非テストファイルからの消費者が0」となる
  exportが、フレームワークの口を除いて0件。
- 検算として`redrawAllLayers`が検出されたことを、コミットメッセージへ観測値つきで残す。
- 撤去した差分のコメント行を判定木へ通した結果（昇格させたもの／落としたもの）を
  このエントリへ書く。
- `./node_modules/.bin/tsc --noEmit`と、変更が届く範囲のvitestが通る。

`dedicatedWayValueLayer.ts`を整理するとき、同ファイルの

### 撤去で見つかった、生きた側の欠陥（同じコミットで直した）

撤去する差分のコメントを判定木へ通したところ、**置き換えられた側にだけ書かれていて、
生きた側（`scene/groups/axisLines.ts`）が満たしていない振る舞い**が3つ、地図が受け付けない宣言が2つ見つかった。

1. **ramp軸の「不明」が地図に出ていなかった。** 旧`buildAxisRampColorExpression`は
   `hasUnknownFallback`な材料の欠損を灰色で塗っていたが、移行先は値の式（欠損を0へ倒す）で
   段を引くため、評価できない道が最良の段の色（緑）になっていた。凡例には「不明」の行があり、
   隠しても地図は変わらなかった。
2. **ramp軸で中ほどの段を隠すと、それより上の段まで消えていた。** 段の絞り込みが下限だけで
   `!(値 >= 下限)`を作っていたため。
3. **配信値の軸で「データなし」を隠しても値の無い道が消えなかった。** 旧`buildSteppedColorExpression`は
   透明にしていた。
4. **評価軸の線の色式が、MapLibreの式として成り立っていなかった**（最も重い）。段ごとの
   `[条件, 色]`を`cases.push(条件, 色)`で積んだうえで`...cases.flat()`で展開しており、
   `flat()`が条件の配列（`[">=", 値, 下限]`）まで1段ほどいていた。MapLibreはこの式を受け付けず、
   例外も出さずに**そのレイヤーだけを描かない**——ルート確定前のレンズ（評価軸で全道路を塗る）は、
   scene移行以降、地図に出ていなかったと考えられる。代役地図は式を検証しないため、既存の
   テストはどれも緑だった。上の1〜3を式の評価器で確かめるテストを書いた時点で落ちて見つかった。

5. **降水の延長予報（自前の格子の面）が地図に出ていなかった。** 下の不変条件を足した時点で
   `layers[4]: layer "precipitationNowcast-main-gridFill" requires a vector source`で落ちて
   見つかった。降水の`main`は配信元のラスタと自前の格子の面の2要素が同じ名前付きソースを名乗り、
   `weatherSourceId`がソース名から描き方を落としていた（T1001段階A`aea79db2`でレイヤーidの
   規則を変えたとき、旧`weatherElementRole`が持っていた描き方が名前から消えた）。ソースが1本
   （先に名乗ったラスタ）へ畳まれ、面のレイヤーはラスタのソースを指して黙って描かれなかった
   ——ナウキャスト・降水短時間予報の先（MSMの格子）の時刻を選ぶと、降水が何も出ない。
   ソース名へ描き方を戻した（`dynamic-weather-layers.md`へ理由を書いた）。

4・5を「この1本」で終わらせないため、**出せるものを全部出した状態の宣言（凡例の絞り込みも含む）を
MapLibreと同じ版のstyle検証（`validateStyleMin`）へ通す**不変条件を契約テストに足した
（`MapView.state.contract.test.ts`「地図へ渡すソースとレイヤーは、すべてMapLibreのstyle検証を
通る」）。対象は宣言から導く母集団で、レイヤーの家族が増えればそのまま対象になる。

`axisLines.ts`に「値が無いことを示す式」（ramp軸は`buildAxisRampUnknownExpression`、配信値は
feature-stateのnull）を入れ、色・濃さ・絞り込みの3つが同じ式を見るようにした。
テストは`@maplibre/maplibre-gl-style-spec`の評価器（`docs/architecture/tech-stack.md`がこの用途で
固定している）で式を実際に評価し、1本の道がどの色になるか・残るかを見る形で書いた
（`axisLines.test.ts`）。旧実装の色式テストが見ていた期待値（null→データなし、取得中は取得中の色、
隠した段だけ透明、「データなし」を隠しても取得中は残る）は、生きた実装へ当て直した。
