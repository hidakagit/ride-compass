# T1005. 応答で常に空になるフィールドが、API契約に乗っている

状態: 完了（2026-09-23）

## 何が起きているか

`RouteSegmentDetail.material_categories`（材料id→この区間の分類値）は、**配信される応答では
常に空**である。`services/road_graph_engine.py`の流れがそうなっている:

```
1830: material_category_shares = merge_material_category_shares(segments)  # ビニング前に使う
1832: segments = aggregate_segments_into_bins(segments)                    # ここで引き継がない
```

ビンへ畳むときに引き継がないのは正しい——分類値は平均できず、ビンの代表値を1つ選ぶと
延長割合が500m単位へ量子化される。割合は`RouteCandidate.material_category_shares`として
候補全体で持ち、そちらは実際に使われている。

問題は、**区間ごとの値を公開モデルのフィールドにしていること**。エンジンが上記2行のあいだ
値を持ち回るためだけに、API契約へ常に空のフィールドが1つ乗っている。

読み手は居ない（2026-09-22実測）:

```
grep -rn "material_categories" backend/app frontend/src
```

→ `road_graph_engine.py`の書き込み3箇所、frontendはテストのフィクスチャ3件が`{}`を置く
だけと生成型1件。値を読むコードは無い。

`domain/route.py`の`BIN_DROPPED_DICT_FIELDS`は、このフィールド1つを説明するためだけに
存在する宣言で、`test_route.py`がそれを検査している。フィールドを外せば宣言と検査も消える。

## 対応方針

`RouteSegmentDetail`から`material_categories`を外し、エンジンが区間ごとの分類値を
ローカルの並びとして持って`merge_material_category_shares`へ渡す。

## 先に決めること

**frontendへ波及する。** 生成型（`api.d.ts`）からフィールドが消えるため、
`page.test.tsx`・`MapView.bench.ts`・`MapView.segments.test.ts`が置いている
`material_categories: {}`が型エラーになる。[T1001](T1001.md)がfrontendを作り直している
最中のため、着手のタイミングをそちらと合わせる。

## 完了条件

- `grep -rn "material_categories" backend frontend` の結果が0件
- `BIN_DROPPED_DICT_FIELDS`とその検査が消えている
- OpenAPI生成物を同一コミットで再生成してある

規模S。

## 実施内容（2026-09-23）

- `RouteSegmentDetail.material_categories`を削除。`road_graph_engine.py: _build_segment_details`は
  区間の並びと、区間ごとの分類値（材料id→値）の並びを対で返し、`_build_candidate`が
  `zip(区間の距離, 分類値)`を`merge_material_category_shares`へ渡す。
- `merge_material_category_shares`の引数を`(距離km, 材料id→値)`の並びへ変えた（区間の器を
  経由しない）。
- `BIN_DROPPED_DICT_FIELDS`を削除。`_undeclared_dict_fields`の読み込み時検査は
  `BIN_DICT_FIELD_MERGERS`だけを見る形で残した（辞書フィールドを足してビンへの畳み方を
  書き忘れると、区間インスペクタからその値が黙って消えるため）。
- frontendのフィクスチャ（`page.test.tsx`・`e2e/fixtures.ts`）から`material_categories: {}`を削除。
  起票時に挙がっていた`MapView.bench.ts`・`MapView.segments.test.ts`は、着手時のgrepで既に
  参照を持っていなかった。
- `docs/modules/backend/routing-engine.md`・`evaluation-scoring.md`の該当記述を更新。

既存DB行への影響: `RouteSegmentDetail`/`RouteCandidate`は応答専用で、DB・Redisへ保存して
読み戻す経路は無い（backendで`model_validate`の呼び出し0件、生成ジョブの結果はプロセス内に持つ）。
古いfrontendは値を読んでいないため、デプロイの順序も問わない。
