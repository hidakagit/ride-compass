# T1180. 地図タイル（基礎地図・地理院・気象庁）のディスクキャッシュを、自前の書き込みと容量の掃除から diskcache へ置き換える

状態: 完了（2026-09-27）

## 背景

起票案 proposal-std-tile-cache-diskcache（2026-09-27承認。標準の道具の棚卸しから）。規模S（根拠: 読み書きの口（取得・保存・全消去・キーの作り方）は変えないので、変わるのは tile_cache.py・main.py・test_tile_cache.py・fake_tile_cache.py の4本の見込み）

■ 背景（画面に出ない、backend内部の話）
infrastructure/tile_cache.py は、一時ファイルからの差し替えによる原子的な書き込み、読み書きの競合の吸収、容量上限を超えたら古い順に消す掃除（起動時のジョブから呼ぶ）を自前で持つ。キャッシュの規約（docs/conventions/caching.md「ディスクを選ぶときの責任」）は「容量の上限と退避は diskcache で持ち、自前で書かない」と決めていて、同じ種類の tile_persistent_cache は T653 で diskcache へ移してある。tile_cache を外した理由はどこにも書かれていない。diskcache は既に依存にある。

■ やること
取得・保存・全消去を diskcache.Cache の包みにし、容量の設定をそのまま size_limit に渡し、起動時の掃除ジョブのうち tile_cache の部分を消す。退避方針は least-recently-stored にする（今の「最後に書いた順」と同じ挙動。least-recently-used は読むたびに書き込みが走り、タイルの読み込みは頻繁なので避ける）。形式が変わるので既存のキャッシュの実体は捨てる（本番の実測 11MB＋土地被覆 最大45MB、どれも取り直せる）。見込み 実装 約−90行、テスト 約−120行。

■ なぜ既存のタスクに入らないか
キャッシュ規約の違反を直す未完了のタスクは無い（T644 は完了済み、T636 は気象庁タイルの Redis 側）。

## 着手時に確かめた前提（origin/master 721d4c10）

- **依存**: `diskcache==5.6.3`は既に`backend/requirements.txt`にあり、`tile_persistent_cache.py`が使っている。
  新しい依存は足さない（ライセンスはApache-2.0で商用可。版の制約は`docs/architecture/`に記載なし）。
- **題名の「気象庁」**: 気象庁のタイルは`tile_cache`のディスクへは書かず（Redis、`jma_tile_redis_cache.py`）、
  `tile_cache.cache_key`（パスのSHA-256）を鍵の組み立てに借りていただけだった。ディスクの鍵は
  ファイル名ではなくなるのでハッシュ化は要らなくなり、`cache_key`は気象庁のRedisの鍵を作る
  `jma_tile_redis_cache._key`へ同じ式のまま移した（Redisの鍵は変わらない）。
- **`tile_cache`の読み手**: 基礎地図・地理院の中継（`basemap_client`・`gsi_tile_client`）、PostGISから焼いたタイルの
  配信の骨格（`tile_serving`。路面・POI・事故・土地被覆）、管理APIの全消去（`api/routers/basemap.py`）、
  起動時の掃除ジョブ（`main.py`）。口（`get`・`set`・`clear_all`）はそのまま残したので、起動時のジョブ以外の読み手は変えていない。
- **`fake_tile_cache.py`**: 口が変わらないので変更不要だった（見込みの4本のうちこれは触っていない）。
  代わりに、テストごとに置き場を一時ディレクトリへ差し替える仕組みを`conftest.py`へ寄せた（下記）。

## 実施内容

- `infrastructure/tile_cache.py`: 自前の原子的書き込み（一時ファイル＋`os.replace`）・`.bin`/`.meta`の2ファイル・
  読み書きの競合の吸収・容量の掃除（`prune_to_size_limit`）・`cache_key`を消し、`diskcache.Cache`
  （`size_limit`＝`tile_cache_size_limit_mb`、`eviction_policy="least-recently-stored"`）の薄い包みにした。
  値は`(内容, Content-Type)`のタプル。読み書きの失敗は従来どおり警告を出して未キャッシュ扱い。
  テスト用に`tile_persistent_cache`と同じ形の`use_directory`を持つ。
- `main.py`: 起動時の掃除ジョブから`tile_cache`の部分を消した（容量は`diskcache`が書き込みのついでに見る）。
  ジョブに残るのは道路網の置き場の掃除だけなので、ログの名前を`ridecompass.disk_generation_prune`にした。
- テスト: `test_tile_cache.py`から、消した自前の実装（ファイル名・2ファイルの対・原子的書き込み・掃除の順と解放量）を
  見ていたテストを消し、入口の振る舞い（未取得は無し・書いたものが型ごと返る・ディスクが書き込み／読み出しを
  拒んでも例外にせず未キャッシュ）だけを残した。容量上限での退避は`diskcache`の持ち物なので書き写さない。
  `conftest.py`の置き場の差し替え（セッション・関数の2段）を`tile_cache`にも広げ、各テストファイルが個別に
  書いていた`CACHE_DIR`の差し替え（`diskcache`は開いた後にモジュール変数を書き換えても効かない）を消した。
- 文書: `caching.md`（容量の持ち方・退避の順を選ぶ理由・土地被覆の鍵の割れ方）、`static-road-attributes.md`・
  `weather-dynamic-layers.md`（`tile_cache`の説明、気象庁はRedisであること）、`config.py`の設定のコメント。

## 本番のディスクに残る旧形式のキャッシュ

- 旧形式の実体（`/home/ubuntu/ridecompass-cache-data/tile_cache/`直下の`<64桁>.bin`・`<64桁>.meta`、書きかけの
  `*.tmp-*`）は、新しいコードからは**読まれず、容量にも数えられず、`clear_all`でも消えない**。`diskcache`は同じ
  ディレクトリに`cache.db`と2段の16進のサブディレクトリを作るだけで、旧ファイルと名前がぶつからない。
- **デプロイでは壊れない**: 旧ファイルが直下にあるディレクトリを`diskcache`で開き、書いて読めること、
  旧ファイルが残ることを手元で確かめた（下の検証）。新コードの初回はキャッシュが空の状態から始まり、
  要求されたタイルから取り直す（外部への問い合わせとPostGISでの焼き直しが一時的に増える。規模は本番実測で11MB＋土地被覆 最大45MB）。
- **残った旧ファイルは手で1回消す**（本番のディスクへの削除なので担当は実行しない。ダッシュボードにkind `操作`で置いた）。
  消さなくても害は無いが、誰も消さないまま最大数十MBが残り続ける。消すコードを起動時のジョブへ足すことはしない——
  1回だけ効いたあとは誰も通らない経路が残る。
- 旧コードへ戻した場合: 旧コードの`clear_all`はディレクトリごと消すので`diskcache`の実体も消え、旧コードは
  そのまま動く。
