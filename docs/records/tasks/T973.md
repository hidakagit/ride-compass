## 保留: DBとディスクに残る非商用データの削除（ユーザーが実行）

**何が**: 取り込んだN10/N12の実体。コードはもう読みも書きもしないが、非商用データを
保持し続けていること自体が撤去の目的に反する。

**なぜここで行わないか**: 本番DBへの破壊的操作はこの環境から行わない方針。開発DBも
並行セッションが共有しているため、削除はユーザーが行う。

**手順**（本番・開発DBの両方で。本番は`backend/scripts/run_probe.py`経由か、VM上のpsqlで）:

```sql
DROP TABLE IF EXISTS source_features_designation;  -- source_featuresの子パーティション
ALTER TABLE way_materials
  DROP COLUMN IF EXISTS designation_emergency_transport,
  DROP COLUMN IF EXISTS designation_critical_logistics;
```

あわせて、取得済みのzip（手元の`backend/data/designations/`、本番VMに同じ置き場が
あればそれも）を削除する。確認は`backend/scripts/schema_gap.py`（本番は
`run_probe.py scripts/schema_gap.py`）で、上の表・列がGAPとして出なくなることを見る。

**保留し続けた場合**: 機能上の不具合は起きない（列はNULL許容で、パーティションはどこからも
読まれない）。起きるのは、商用化の時点で非商用データを保持している状態が残ること。

この削除が済んだら、完了条件「`source_features`に`designation`パーティションが存在しない」を
満たし、このエントリを閉じられる。

**ユーザー決定（2026-09-23、判断D-010）**: 削除する（開発・本番DBの行とzip）。上の手順を
並行実行の担当が実行し、削除の前後で対象の表・列の件数と`schema_gap.py`の出力を記録する
（本番の一時停止はD-015で許容済み。ただし削除そのものは取り消せないので、実行の直前に
対象が上の表・列だけであることを読み取りで確かめてから行う）。

**訂正（2026-09-23 17:10）**: 直前の段落の「並行実行の担当が実行し」は誤り。表・列のDROPとzipの削除は
取り消せないデータの削除なので、ユーザーの承認（D-010）があっても司令塔・担当は実行しない。元の
手順どおり**実行はユーザー**。担当が行うのは読み取りだけ——削除の直前に対象が上の表・列だけで
あることの確認（件数・依存の有無）、ユーザーがそのまま貼れる実行手順の用意、実行後に
`schema_gap.py`で消えたことの確認と記録。
