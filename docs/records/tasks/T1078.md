# T1078. E2Eの全状態の走査を、状態ごとに開き直さず画面の木をたどる形にして、CIのe2eの所要を縮める

状態: 完了（2026-09-23。末尾「実装と検証」節）

## 背景

T1014段階Dの全状態の走査（frontend/e2e/all-states.spec.ts）で、CIのe2eジョブが75秒→535秒に伸びた（内訳はT1014.md「CIのe2eの所要の内訳」節）。伸びはすべて全状態の走査の4本（計768ワーカー秒、311状態、1状態あたり約2.5秒）で、状態ごとにreopen()——localStorageを戻してpage.goto('/')から開き直し、生成後ならルート生成をやり直し、1段目のスイッチを押し直す——を払っている。ユーザー提案（2026-09-23）:「A→Bと操作した先の画面で、C、D、さらにそこからE→Fと見たいものがある場合、A→Bで止めて、CとD、E→Fはいっぺんにやる」「操作を効率的にできるスクリプトで、移動作業はショートカットする」。方針: (1) 開き直しをやめ、親の状態で止めて子のスイッチを押す→検査→閉じる（元へ戻す）で木をたどる。戻せたかは親の状態の指紋（DOMの開閉の宣言・localStorage）で確かめ、戻らなかったときだけ開き直す（黙って別の状態を検査しない）。(2) 生成後の段階は、ルート生成を状態ごとにやり直さず1回の生成を使い回す。(3) 画面から導いた状態の母集団（states.ts）は変えない——速くするために見る状態を減らさない。完了条件: 同じ311状態（または同じ導出で出る全状態）を検査していることを件数で示し、直前・直後のCIのe2eジョブの所要を並べる。壊した入力（T1014段階Dと同じ2種）で今も落ちることを1回見る。T1069（P-pinch）がall-states.spec.tsへscanPinchを足すので、その後に着手する。

### 人の判断で決めたもの（機械的でない前提。この3つだけ）

| 前提 | 内容 | 根拠 |
|---|---|---|
| 幅は2通り | モバイル・デスクトップ。幅の分岐はCSSの`--breakpoint-mobile`だけなので、その両側に1つずつ置き、両側にあることを実行時に検算する（具体値は両側にあれば何でもよい） | ユーザー判断 |
| 段階は2通り | ルート生成の前と後。辿り方は開閉の部品しか押さないので、生成後にしか現れない部品（候補一覧・比較タブ・GPX出力等）へ届くには生成を1回押す必要がある。「開閉以外で画面に部品を足す操作は生成だけ」は機械では導けない（開閉以外のボタンを全部押すと、ダウンロード・クリア等の破壊的な操作が混ざる） | ユーザー判断「ページ要素が大きく変わるのはルート生成前と後の2パターンだけ」 |
| 研究モードは省く | どのモードのチェックボックスも押さない（既定の状態のまま）。今の走査はモードなし・研究モードの2通りで同じ木を巡っていた | ユーザー判断 |

### 検査の2種類（2026-09-23、ユーザー決定）

検査は、判定が読むものから2種類に分け、当てる回数を変える。どちらに入るかは検査が読むものから機械的に決まる。

| 種類 | 判定が読むもの | 当て方 | 該当する検査 |
|---|---|---|---|
| **部品の検査** | その要素と祖先の**計算後のスタイル**（ピンチはブラウザが触れた要素と祖先の`touch-action`で決め、余白は計算後の`padding`・`margin`） | **段階（生成前・生成後）ごとに、各部品1回**。辿る途中で初めて見えた部品にだけ当てる | ピンチ・余白ユーティリティ |
| **配置の検査** | 要素の**座標・寸法**・ページの幅（`getBoundingClientRect`・`scrollWidth`）。何が開いているかで変わる | 状態ごと | 押せる部品の横はみ出し・ページの横スクロール |

「閉じたら元に戻る」はどちらでもなく、遷移ごとに見る。

**同じ部品の見分け**: 要素から祖先（`html`の手前）までの、各要素の**タグと（並べ替えた）クラスの並び**が同じなら同じ部品
（ユーザー決定。案B「計算後の値そのもの」はブラウザの判定の仕組みを前提に置くため、案C「ロールと名前」は
スタイルと関係の無い見分けのため採らなかった）。CSSの規則はタグ・クラス・祖先の並びで当たるので、並びが同じなら
同じ規則が当たる。**区別しないもの**: `aria-expanded`・`data-state`等の属性で当たる規則の違い（同じ並びの部品が
状態によって別の規則を受けても、段階ごとに1回しか見ない）。

### 合否（すべて機械的に判定する）

| 検査 | 基準 |
|---|---|
| ページが横にスクロールしない | `document.scrollingElement.scrollWidth ≦ innerWidth + 1`（+1は`scrollWidth`が整数へ丸められる——CSSOM View——ことの誤差） |
| 押せる部品が画面幅からはみ出さない | 部品の矩形が`left ≧ -1`かつ`right ≦ innerWidth + 1`。「押せる部品」は**ブラウザが計算したロール**（CDPの`Accessibility.getFullAXTree`）が**WAI-ARIAの widget ロール**（操作できる部品の分類。一覧は実装時に公式の仕様から取り、出典をコードに書く）に当たるもの。矩形の面積が0のもの・`checkVisibility()`が偽のものは対象外。祖先のどれかの計算後の`overflow-x`が`auto`か`scroll`なら除く（スクロールで届く）。今の手書きのセレクタ（`button`・`a[href]`・`role="tab"`等）は廃止する |
| 余白ユーティリティがリセットに潰されない | 今と同じ（試しの要素へ値を`!important`で与え、ブラウザの計算値と要素の計算値を比べる）。**変種付き（`sm:`等）は、今の画面で条件が成り立つものだけ見る**（幅の変種は`matchMedia`で判定、`hover:`等の操作の変種はその操作をしていないので対象外）。今は変種付きを一律に除いている |
| ピンチでページが拡大しない | 2本指で開いたあと`visualViewport.scale === 1`。**モバイルだけ**（タッチを持つ文脈＝`hasTouch`でしか指の入力を送れない） |
| ピンチの対象 | 見えている要素の**中心点でヒットテストして返る要素**（指が実際に触れる要素）。地図のcanvasは除く（地図の上のピンチは`map-runtime.spec.ts`が見る）。今の8px格子は廃止する（間隔が選んだ数字だったため） |
| ピンチの操作 | 指は**画面の端まで、移動1回で開く**（今の8px×12歩は選んだ数字だったため。回数は「ピンチとして発火するか」が見える最小の回数——下の計測v5で、規則を外したビルドで1回でも2回でも同じ件数の拡大を検知した。ユーザー判断「ピンチが発火するかどうかだけ見えればいい基準で」）。開いたあと、**連続する2フレームで倍率が変わらなくなるまで**待ってから読む（今の固定200msは廃止） |
| 同じ部品へのピンチは1回 | 上の「検査の2種類」節のとおり、段階ごとに**同じ部品**（要素から祖先までのタグとクラスの並びが同じ）は1回（当初の「同じDOMノードなら省く」は、開くたびに作り直されるポップオーバー・シートの中身に効かず、計測v1のモバイルが1状態約3秒になったため置き換えた） |
| 閉じたら元に戻る | 下の「戻す」のあと、指紋が押す前と一致しなければ**違反として落とす**（通り直さない。ユーザー判断） |
| 開いた状態が1件以上ある | 辿った状態（土台を除く）が各幅・各段階で1件以上（パターン6）。今の「『ルート結果』シートと『比較』タブに届いたか」は、届くべき状態を手で名指ししているので外す |

### 辿り方（遷移は各状態へ1回だけ）

- **幅ごとに1枚のページ**で、開く → 生成前の木を辿る → 「ルート生成」を1回押す → 生成後の木を辿る。
  テストは幅ごとの2本（今の幅×段階の4本をまとめる。CIのワーカー2本で並ぶ）。
- **「開くもの」**は`aria-expanded="false"`の部品と、`role="tab"`かつ`aria-selected="false"`の部品。
  矩形の面積が0のもの・見えていないものは除く。
- **押せるものだけ押す**: 部品の中心点が画面内にあり、そこで`elementFromPoint`が部品自身か子孫を返すこと
  （上に重なっている順番はブラウザのヒットテストが決める）。押せないものは押さない（違反にもしない）。
  中心点を使うのは、Playwrightが押す点と同じだから（約束事として記録する）。押す前に判定するので、
  押せない部品に3秒のタイムアウトを払うことも無くなる。
- **押せる限り奥まで辿る**（今の「2段まで」の上限は無くす）。祖先の状態に**同じ部品**（部品の見分けが同じ）がある部品は押さない
  （兄弟のシートを行き来して回り続けることを防ぐ。ユーザー判断でノードの同一性から部品の見分けへ揃えた——開くたびに
  作り直される部品が別物として扱われ、組み合わせで状態が増えていた。計測v3→v4でデスクトップ230→44状態）。
- **戻す**: `aria-expanded`の部品は、押せるならもう一度押し、押せない（開いたものが上を覆っている）ならEscape。
  タブは、押す前に同じタブ列で選ばれていたタブを押す。
- **指紋**: ARIAの開閉の値（`aria-expanded`・`aria-selected`）を**部品の見分けごと**に集めたもの（同じ部品が複数あれば多重集合）と
  `visualViewport.scale`。**localStorageは入れない**（ユーザー判断。辿る間にページを読み直さないので、保存値はアプリの状態を
  通してしか画面に効かず、それはARIAの開閉の値で直接読める。入れると、初めての開閉で保存キーができるだけの違い——
  「キーが無い」と「`[]`」——や、ピンチの指がスライダーを動かした値の違いを「戻らない」と数える。計測v4）。
- **押したあとの待ち**: 固定の300msをやめ、フレームを単位にして「開くもの」の一覧と指紋が連続2フレームで
  変わらなくなるまで待つ。カタログのように非同期に後から届くものがあるので、その間の通信が終わるまで
  （Playwrightの`networkidle`相当）も待つ。

### CIの分け方と目標（2026-09-23、ユーザー決定）

CIのe2eは**モバイルとデスクトップをジョブの単位で分け**、**それぞれのジョブが180秒以内に終わる**ことを目標にする。
テストの前に約63秒かかる（取得・Node 4秒、`npm ci` 12秒、`playwright install --with-deps chromium` 22秒、
`next build` 約25秒。計測v1のrun 35855609985の段ごとの所要）ので、走査に使えるのは約110秒。
計測は、ジョブが開始から180秒を超えたら取り消す（ユーザー指示「3分で帰ってこなければ打ち止め」）。
走査以外のe2eのspec（計測時点で9件、段階Dで約50秒）をどちらのジョブへ載せるかは未決。

(1) 初めての開閉で保存キーができる（例: 「道路」を開いて閉じると`map-overlay-expanded-groups = []`が新しく保存される）。
(2) ピンチの2本指の片方がスライダー・つまみの上にあるとドラッグとして効く（「想定速度」20→60→58、「ルート設定」の
距離100・シートの高さ20）。(2)は検査の操作による副作用で、画面の欠陥ではない。v5（移動1回）では検査で状態が
変わったものは0件だった。

## 実装と検証（2026-09-23）

### 計測のあとに決めたこと（ユーザー判断）

- **走査以外のe2eのspecは独立したジョブで走らせる**。CIのe2eは、走査以外のspec（`e2e`）と、幅ごとの走査
  （`e2e-scan`、モバイル・デスクトップ）に分けた。
- **全状態の走査を作業ブランチ（`orch/**`）のCIでも走らせる**（上の「追加（案A）」の戻し。所要を見て判断）。
- **横スクロールする容器の中の部品は、最も近いその容器が画面の横幅に収まるかで判定する**。容器の中を無条件に
  除く形では、デスクトップの部品の約44%（819/1027件、run 35861832737）が検査から外れていた。縦にスクロールする
  容器も計算後の`overflow-x`は`auto`になるため、サイドバーの中が丸ごと外れていた。
- **余白ユーティリティの変種（`sm:`等）は対象外のまま**。`frontend/src`で使っている箇所が0件（変種の無い
  余白ユーティリティは16件で検算）のため、条件の判定を書いても通らない。

### 実装で足したこと（設計に無かったもの）

- 走査のテストは失敗しても再試行しない（`test.describe.configure({ retries: 0 })`）。モックで決定的に動くので、
  再試行は所要を倍にするだけで、失敗時に1ジョブ180秒を超えた（壊した入力のピンチで198秒）。
- 違反は段階ごとに確かめる。生成前の違反（例: 閉じても戻らない下部タブ）が生成の段取りを壊すと、違反そのものが
  見えなくなった（壊した入力の最初の回で、生成の段で時間切れになり違反が出なかった）。
- タブ列で押す前に選ばれていたタブが無いときは、黙って飛ばさず違反にする。
