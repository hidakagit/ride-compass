# T1026. 手書きの色表を消したときに一緒に落ちた「色の意味」を戻す

状態: 完了

## 背景

T1001段階Aで、手書きの色表を消して色を宣言から規則的に生成するようにした。**方向は
正しい**（フロントに手書きの色表が無くなり、凡例は地図を描いているのと同じ宣言から
作られるので原理的に食い違わない）。しかし、**表の中に埋まっていた判断が一緒に落ちた**。

読んで確かめたもの（色は生成物の実値から機械的に算出。**地図上での見え方は実機未確認**）:

1. **凡例が、地図に存在しない色を色見本つきで出す。** 点レイヤーの色式は
   `display_axes[0]`だけを使うのに、凡例は全軸を行にする。事故の点は当事者と重大度の
   2軸を持つため、**重大度の2色は地図上に1ピクセルも塗られていない**（重大度は
   半径の違いだけで表される）。
2. **死亡事故の色が意味を失った。** 前回レビュー時点は`#dc2626`（赤）で、旧コードは
   「赤＝危険という慣習的な読みが安全確認という目的に直接寄与する」と理由を明記して
   いた。現在は緑〜ティール。`palette.json`は別の場所で`evaluation_bad`に`#dc2626`を
   使い続けているため、**緑の点は「安全な地点」と読める**。
3. **名義尺度の割り当てが、軸内で最も見分けにくい色を選んでいる。**
   `material_catalog.py`の`color_slot`が宣言順の通し採番で、`nominal_color`が
   `hue = 215 + 30°×(slot%12)`。連番なので**同じ軸の中のカテゴリには常に隣接色相が当たる**。
   軸内の隣接カテゴリのCIE76 ΔE実測は、停止要因10.3 / 事故（当事者）10.9 / 路面11.2 /
   補給12.8 / 道路13.1。地図上の点は半径4pxで描かれる。
4. **スロットが12を跨ぐ軸では、凡例の途中で明度段が変わる。** 意味上のまとまりが無い
   位置で系統が分かれて見える。
5. **ダークモードで凡例の塗りが地色に沈む。** `--color-surface`（`#2a2a2d`）に対する
   コントラスト比は幹線道路`#3b4554`が1.48:1。パネルは78%透過なので実効値はさらに
   下がる（**透過込みの実測はしていない**）。

## 対応方針

**規則をやめて手書き表へ戻すのではなく、規則の側に欠けている性質を足す。**

1. **割り当て規則に「軸内は離す」を入れる。** 現在の連番は、軸内のカテゴリへ最小色差を
   割り当てる。軸内で色相を分散させる（例: 軸のカテゴリ数nに対し`12/n`刻みで配る）。
   これは`nominal_color`の引数が変わるだけで、新しい機構は増えない。
2. **意味を持つ行だけ semantic から引けるようにする。** 対象は**事故の重大度に限定する**。
   全カテゴリへ広げると手書き表への逆戻りになる。「どの行が意味を持つか」は源泉の宣言が
   持つ（画面が決めない）。
3. **凡例と地図の食い違いは、どちらへ寄せるか決める。** (a)「重大度は色を持たない
   （大きさだけ）」と凡例側で明示する、(b) 地図が2軸目も色で表す、の2択。(b)を採ると
   1つの点に2軸ぶんの色が要るため、(a)が既定。
4. 明度段の切り替わりと、ダークモードのコントラストは、規則の明度下限の見直しとして
   同時に扱う（凡例側だけ色を変えると、地図と凡例が別の色を持つことになる）。

## 完了条件

**すべて測って確かめる。測り方をここへ書く。**

- **軸内の隣接ΔE**: 生成物`frontend/src/types/generated/primaryAttributes.ts`から各軸の
  カテゴリ色を読み、sRGB→CIELabへ変換してCIE76のΔEを隣接ペアで計算する。**軸内の最小ΔEが
  閾値以上**。閾値はこのタスクで決めてここへ書く（現状の最小は10.3）。
- **凡例が出す色がすべて地図上に存在する**。確かめ方: 凡例の生成が読む軸と、色式が読む軸が
  同じであること（コードの一致で判定でき、実機を要しない）。
- **ダークモードのコントラスト**: 凡例パネルの背景（透過を合成した実効色）に対する
  各スウォッチのコントラスト比を計算し、下限を満たす。下限値もこのタスクで決める。
- 上の3つの計算を、直す**前**に現状へ当てて既知の値（軸内最小10.3、幹線道路1.48:1）が
  再現されることを確認してから、直した後に当てる（CLAUDE.md「検証は別の入力で行う」の
  裏返しで、まず計算器が正しいことを既知の値で示す）。

## 備考

この欠陥の性質は「撤去するとき、コードの撤去と文の撤去を同じ操作でまとめて落とした」
ことである。赤＝危険という判断は旧コードのコメントにしか無く、`docs/modules/*.md`へ
昇格されないまま表ごと消えた。同じ形の取りこぼしが他にもありうるため、T1023で
撤去差分のコメント行を判定木へ通す作業と、原因を共有している。

## 実施（2026-09-23）

### 測り方と、直す前の値（既知値の再現）

生成物`frontend/src/types/generated/primaryAttributes.ts`を読み、色を持つ軸ごとに
sRGB→CIELab(D65)→CIE76 ΔEを隣接ペアと全ペアで、WCAG 2.xの相対輝度でコントラスト比を
計算した（使い捨ての測定器。同じ計算は`backend/tests/test_primary_attribute_display.py`に
不変条件として入れた）。地色は次の4つ:

- 地図: 基礎地図（OpenFreeMap liberty）の`background` `#f8f4f0`（配信元のスタイルJSONで確認）
- ライトの凡例パネル: `#ffffff` 78% ＋ 下の地図 22%
- ダークの凡例パネル: `#2a2a2d` 78% ＋ 下の地図 22%（**基礎地図はダークモードでも liberty のまま明るい**）
- 透過を無視した`--color-surface`（ダーク）`#2a2a2d`

直す前: 軸内の隣接ΔE 停止要因10.3 / 事故（当事者）10.9 / 路面11.2 / 補給12.8 / 道路13.1、
幹線道路`#3b4554`対`#2a2a2d`は1.48:1——エントリの既知値がすべて再現した。透過込みの
ダークパネルに対しては最小1.02:1（石畳`#6b4587`）で、エントリの見立て（1.48より下がる）どおり。
**エントリに無かった値**: 地図の地色に対して最小1.51:1（農道・林道`#c3cad5`）——明るい分類色は
地図の上でも「薄い＝対象外」と見分けられていなかった。

### 決めた閾値

| 何を | 閾値 | 理由 |
|---|---|---|
| 分類色 対 地図の地色 | コントラスト比3:1以上 | WCAG 1.4.11（図形の非テキストコントラスト）。これを割ると「薄い＝対象外」と見分けられない |
| 列挙の軸内 | どの2行もΔE76 20以上 | 直す前の最小10.3の約2倍。下の制約の下で7行の軸まで取れる値 |
| 順序の軸内 | 隣どうしΔE76 10以上 | 濃淡だけで段を作るため、上の3:1（明度の上限）と黒に潰れない下限の間でしか取れない |
| 凡例の色見本の台 対 ダークパネル | 3:1以上 | 同上 |

### ダークモードは色の明度では直せない（エントリの見立てとのずれ）

対応方針4は「規則の明度下限の見直し」だったが、実測で成り立たないと分かった。分類色は
地図の上では常に明るい地色（`#f8f4f0`）に載り、凡例はダークモードで暗いパネル（透過込みで
相対輝度約0.095）に載る。同じ色で両方に3:1を取るには相対輝度が0.268以下（地図側）かつ
0.385以上（パネル側）で、**両立する色が存在しない**。そこで色は地図側の条件で決め、凡例の
見本を**地図と同じ地色の台**（2pxの輪）に載せた。見本の色は地図と同じまま、見本の直接の
地が地図と同じになる。台 対 ダークパネルは6.63:1。

### 変えたこと

- `display_palette.py`: 色をCIELChで作る（明度をそろえると色相によらず地色から同じだけ浮く）。
  列挙は**軸が宣言する色相の起点から、軸の行数で色相環を等分**（L\*52・C\*28、どの色相も
  sRGBに収まる）。順序はL\*18→58・C\*4→18の濃淡。明度の段が1つになったので、12を跨いだ所で
  系統が変わる問題（エントリ4）は構造上起きない。
- 宣言: 行ごとの`color_slot`を撤去し、軸の`hue_slot`へ（24個→6個）。起点は軸をまたいで
  重複させない（テストで検査）。事故の当事者は起点を青／黄土にし、**緑の点にならない**ように
  した（エントリ2の「安全な地点と読める」）。
- **色を持つのは先頭の軸だけ**（エントリ3の(a)）: 重大度の軸は`palette`を持たず、生成物にも
  色を載せない。凡例の重大度の行は灰（`semantic.legend_size_only`）の見本を**地図の点と同じ
  直径**で出す。半径は地図と凡例が同じ関数（`points.ts: pointCategoryRadiusPx`）から取る。
  凡例の色見本を出すのは地図の色式と同じ`display_axes[0]`だけ——完了条件「凡例が出す色が
  すべて地図上に存在する」はこの一致で満たす。
- 古くなった記述を直した: 農道・林道の「土の色を流用する」（色表の時代のもの）、当事者の
  「寄与しない側は中立色のまま」、設計書の「石畳は紫」「事故の当事者は評価配色
  （`AXIS_RAMP_COLORS`）」「自販機の不明側を薄い色に」。

### 保留（ユーザー判断）

**保留1: 事故の点を赤（危険）で出すか。** エントリの背景2は「死亡事故の色が意味を失った」
だが、履歴を辿ると**死亡事故は T1001 以前から地図では色を持っていなかった**（重大度は大きさ
だけ。赤が付いていたのは凡例の重大度の行だけで、それ自体が背景1の「地図に無い色」だった）。
旧コードで赤だったのは**当事者＝自転車関連の点**で、理由は「評価へ寄与する側は、評価軸の
危険側と同じ赤で出す」。一方、現行の設計書（static-map-layers.md「地図全体で共有する配色の
読み方」）は「1次に評価配色を使う例外は無い」と、まさに事故の当事者を例に挙げて明文化して
いる。対応方針2（重大度だけ semantic から引く）は、方針3の既定(a)（重大度は色を持たない）と
組み合わせると**引く先の色がどこにも描かれない**。したがって方針2は実装せず、次の選択肢を
ユーザーへ返す:

- A（今回の実装）: 当事者は中立の色相（青／黄土。緑は避けた）、重大度は大きさだけ。設計書の
  「1次に評価配色を使わない」と整合する。赤＝危険の慣習は使わない
- B: 自転車関連の点を赤（`semantic.evaluation_bad`）に戻す。設計書の原則に例外を1つ足す
- C: 地図の色を重大度にし（死亡=赤）、当事者は絞り込みだけにする（方針3の(b)に近い）。
  利用者から見える情報の出し方が変わる

**保留2: 「自販機(中身不明)」を薄く出すか。** 宣言のコメントと設計書は「同じ確からしさに
見せない」とし、旧コードは不明側を淡い色にしていたが、規則化で淡さは失われている（今回
設計書からは「薄い色」の記述を落とし、別の行に分けていることだけを残した）。薄くすると
地図の地色に対する3:1を割り、「薄い＝対象外」と同じ見え方になる。行ごとの「確からしさ」を
宣言に持たせるかは、方針2の「全カテゴリへ広げると手書き表への逆戻り」とも関わる判断のため
保留する。

どちらも、保留し続けた場合に起きるのは「今回の配色（A・薄くしない）のまま運用される」こと
で、壊れる経路は無い。

### ユーザー決定（2026-09-23）

- 保留1（事故の点の配色）: **A**。当事者は青／黄土、重大度は大きさだけ（今回の実装のまま）。
- 保留2（自販機(中身不明)を薄く出すか）: **薄くしない**。他の行と同じ濃さ（今回の実装のまま）。

どちらも実装どおりのため、コードの変更は無い。これで保留は解消し、本タスクを完了とする。
