■ 誰のための話か
backendのコードを直す人が、処理をどの層に置けばよいか迷わないこと。画面・APIの動きは、どちらを選んでも変わらない。

■ いまどうなっているか
構成の文書（docs/architecture/directory-layout.md:14-15）は依存の向きを「api → services → domain」「api → services → infrastructure」と書き、apiがinfrastructureを直接読むことを想定していない。実際はapiのrouter 15本のうち9本がinfrastructureを直接importしている（origin/masterで数えた）。多くは中継だけのもの: 基盤地図・国土地理院・気象庁のタイルの中継（basemap.py・gsi_tile.py・jma_tile.py）、稼働状態（health.py）、デバッグの操作（debug_admin.py）、ほかにルート生成の非同期ジョブの受付（routes.py）、軸の管理（axis_admin.py）、較正値（tuning_admin.py）、材料カタログ（material_catalog.py）。
この段階では約束を文書に書き、構造のテストで向きを落ちる形にする。どちらへ揃えるかで、書く約束とテストの中身が変わる。

■ 各選択肢で起きること
1. 文書の図と約束を「組み立てるものが無ければ直接呼んでよい」に直し、テストはそれ以外の向き（例: domainは他の層を読まない）を落ちる形にする。移す作業は、組み立てを持っているのにapiにあるものだけに絞れる。
2. 9本を組み立て役へ移す作業が加わる（素通しの組み立て役が数本増える）。以後「apiはinfrastructureを読まない」をテストで落とせる。

■ 推奨の理由
判断を持たない素通しの層を増やすと、読む場所が1つ増えるだけで守るものが無い。「組み立てがあるか」で線を引く方が、今の実態の多くをそのまま説明できる。なお、同じタスクで挙がっている他の点（入力の検査をどの層が持つか等）は設計原則（概念の正準定義はdomainに1か所）から決められるので問いにしていない（参照: T1131）。
