■ 誰のための話か
backendのコードを直す人が、処理をどの層に置けばよいか迷わないこと。画面・APIの動きは、どちらを選んでも変わらない。

■ いまどうなっているか
構成の文書（docs/architecture/directory-layout.md:14-15）は依存の向きを「api → services → domain」「api → services → infrastructure」と書き、apiがinfrastructureを直接読むことを想定していない。実際はapiのrouter 15本のうち9本がinfrastructureを直接importしている（origin/masterで数えた）。多くは中継だけのもの: 基盤地図・国土地理院・気象庁のタイルの中継（basemap.py・gsi_tile.py・jma_tile.py）、稼働状態（health.py）、デバッグの操作（debug_admin.py）、ほかにルート生成の非同期ジョブの受付（routes.py）、軸の管理（axis_admin.py）、較正値（tuning_admin.py）、材料カタログ（material_catalog.py）。
この段階では約束を文書に書き、構造のテストで向きを落ちる形にする。どちらへ揃えるかで、書く約束とテストの中身が変わる。

■ 各選択肢で起きること
1. 文書の図と約束を「組み立てるものが無ければ直接呼んでよい」に直し、テストはそれ以外の向き（例: domainは他の層を読まない）を落ちる形にする。移す作業は、組み立てを持っているのにapiにあるものだけに絞れる。
2. 9本を組み立て役へ移す作業が加わる（素通しの組み立て役が数本増える）。以後「apiはinfrastructureを読まない」をテストで落とせる。

■ 推奨の理由
判断を持たない素通しの層を増やすと、読む場所が1つ増えるだけで守るものが無い。「組み立てがあるか」で線を引く方が、今の実態の多くをそのまま説明できる。なお、同じタスクで挙がっている他の点（入力の検査をどの層が持つか等）は設計原則（概念の正準定義はdomainに1か所）から決められるので問いにしていない（参照: T1131）。

## 対応方針

**段階A（この段）: 契約を書き、向きを落ちる形にする。** 記録に残っていた選択は、次のように決めた（理由はどれも
プロダクトの正しさと保守する量）。

- **向きを何で落とすか: import-linter（`layers`契約）を使う。**`tests/structure/test_layer_imports.py`の走査を広げる案と比べ、
  (1) 連鎖（AがBを読み、BがCを読む）まで見る——自前のASTの走査は直接のimportしか見ない、(2) `exhaustive`で`app/`直下に
  足したものがどの段か宣言されるまで落ちる——層の母集団を手で列挙しない（構造仕様12）、(3) 契約が十数行の宣言で、
  走査の実装を保守しない、の3点で上回る。frontendの層の向きを定番の`eslint`の規則が持つのとも揃う。依存は開発用
  （`requirements-dev.txt`）だけで、本番のイメージには入らない。import-linterとgrimpはどちらもBSD 2-Clause、grimp 3.17は
  CIのaarch64（manylinux）と開発機（win_amd64）のcp312のwheelを配っている（PyPIの配布物の一覧で確かめた）。
- **既存の`test_layer_imports.py`は残す。** 守るものが違う——あちらは「本番のwebが持たないバッチ専用の依存をモジュール
  直下で引き込まない」で、関数内へ遅延させたimportは許す。import-linterは関数内のimportも数え、直下だけを見る設定を
  持たない（[T998](T998.md)の調べと同じ）。契約で`services`以下は関数内でもbatchを読めなくなったので、あちらが見るのは
  契約が許す上の層（api・main）の直下だけになった。docstringをそう直した。
- **段の並び**: `main` → `api` → `services | batch`（互いに独立）→ `infrastructure` → `config | version` → `domain`。
  servicesとbatchを独立にしたのは、HTTPの組み立てと取込の組み立てが同じものを要るならそれは下の層の持ち物だから
  （frontendの「機能同士は読まない」と同じ理由）。configをdomainの上に置いたのは、domainが環境に依存しない
  （設定を読まない）ことを落ちる形にするため。
- **apiがinfrastructureを直接呼ぶ**: ユーザーの答え(1)のとおり、素通しは認める。契約は`api`から下の全段を読める。
  「素通しか組み立てか」はimportの向きでは見えないので、directory-layout.mdに線の引き方を書いた。
- **入力の不変条件**: 値の不変条件（書き手が他にいても成り立つべきもの）は`domain`、リクエストの形（このエンドポイントが
  受ける組み合わせ）は`api`。根拠は構造仕様4（正準定義はdomainに1か所）と構造仕様16の「入口を1つにする」——
  API以外の経路（[T972](T972.md)の復元）で書いた行も同じ検査を通すため。
- **外部の応答の形**: それを取りに行く`infrastructure`の接続（取込なら`batch/source_adapters/`）が解き、上へは値で渡す。
  外部の形を知る場所を、その外部と話す部品1つにするため。
- **応答の型**: `services`の結果と同じ事実（構造仕様17）の応答は、その結果の型をそのまま応答の型に使い、apiに写しを
  置かない。写しは片方だけ直しても両方のテストが通る。
- **domainのSQL文・HTTPのパス**: 定義から作る式（材料の値式のような列に対する式）はdomainに置いてよい（構造仕様3——
  式は定義そのもの）。表を読む・書く文の全文とHTTPのルートのパスは、実行する層・受ける層が持つ。
- **domainの表示の宣言（`map_display.py`等）**: domainに置いてよい——越境ではない。どれもレジストリ（`material_catalog`・
  `weather_elements`・`registry`等）から導いており（構造仕様17）、レジストリと同じ層に要る。本番のプロセスが読まないことは
  デプロイの判定（`deploy_backend_gate.py`の`NOT_DEPLOYED`と`test_deploy_exclusions.py`）が別に持つ。
- **batch・infrastructureの業務判断**: [T1137](T1137.md)でdomainへ移り済み（上の「前提の変化」）。契約に「業務の判断は
  domainから読む」と書いた。
- **`dependencies.py`の「組み立てはすべてここに集約」**: `main.py`の定期ジョブ2本（アメダスの更新・気象庁タイルの
  プリウォーム）が、`dependencies.py`の`get_amedas_service`・`get_jma_tile_client`と同じ組み立て（同じクライアント・
  同じタイムアウト）を写して持っていた。同じ事実（構造仕様17——工場のタイムアウトを変えたら定期ジョブも変わるべき）なので、
  ジョブが工場を呼ぶ形にした（`main`は`api`より上の段なので契約の内）。HTTPの経路に工場の無い部品（起動時の軸定義・
  較正値の読み込み、MSMの同期）だけは`main.py`が組み立てる、とdocstringとdirectory-layout.mdに書いた。

**後の段階**（種類ごとに1段階。どれも向きの契約は変えない）:

- **段階B: 入力の値の不変条件をdomainへ移す。** 対象は上の表の9件。1件ずつ「API以外の経路で書かれた値にも成り立つべきか」を
  問い、成り立つべきもの（例: `axis_admin.py`の材料の混在・専用レイヤーの実装有無・材料の既知・しきい値の昇順）をdomainへ移し、
  APIのモデルと復元の経路（`admin_data_backup.py`）の両方から呼ぶ。リクエストの形（例: `routes.py`の到着地の有無）はapiに残す。
  完了の条件: 移した検査を、APIを通さず書いた行（復元）が通ることをテストで示す。
- **段階C: 応答の型の写しを消す。** 対象は上の表の11組。組ごとに構造仕様17の1問目（servicesの結果を変えたら応答も変わるべきか）を
  問い、同じ事実なら結果の型（Pydanticの`StrictModel`）を応答にそのまま使いapiのクラスを消す。部分だけ共有する組
  （`AxisMaterialBreakdownEntry`の3/6等）は共有する部分だけを差し込む。完了の条件: OpenAPIの生成物に差分が出ない
  （`export_openapi.py`→`generate:api`→`git diff --exit-code`）。
- **段階D: 外部の応答の形をinfrastructureへ寄せる。** 上の表の118件のうち、外部のHTTP応答を読むものを候補から1件ずつ選り分ける
  （件数の多い`jma_amedas_service.py`・`weather_service.py`・`warning_service.py`・`wbgt_service.py`から見る）。選り分けの定義:
  そのdictが`http_client`・外部クライアントの応答から来ているか（DBの行・自前のdictは対象外）。
- **段階E: domainのSQL文とHTTPのパスを実行する層・受ける層へ移す。** 上の表の21件と11件を1件ずつ「表を読む・書く文か／

  それらの宣言から導いていた値（例: `gsi_tiles.py`の`RELIEF_TILE_URL`はルートの接頭辞から作る）は、移した先から導く。
