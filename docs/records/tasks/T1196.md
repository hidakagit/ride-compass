3. 道具で止める: 禁じた遷移は道具が断る形にし、散らばった文を消す。

■ 規模: 調べる段はS、全体はM〜L。この設計が決まるまで、運用の道具への場当たりの直し（T1149・T1167〜T1169等）は振り出さない。

### 3. 穴と衝突の地図

**穴（遷移が定義されていない・行き先が無い）**

- **H1. 開いているが誰も持っていないタスクへの答え。** 答えを記録へ移せるのは「そのタスクのコミット」（CLAUDE.md・asking-user.md）か、閉じるときの `記録: 答え` だけ。担当のいない未完了タスクには「そのタスクのコミット」が来る時機が無く、答えはダッシュボード（asking-user.md 自身が「正本ではない」「公式の文書に記載の無い機能」と書く置き場）に溜まり続ける。持ち主は司令塔になる（件の持ち主の導き方）が、司令塔にはその答えを記録へ移す合法の遷移が無い。**2026-09-27 03:14〜04:44 の `記録: 答え` 4コミットが名指した未完了タスク28件（延べ）は、この穴へ流れ込んだ結果**（`W-flow_recordonly.py` で検算。c9d1fc6f が13件・48f17bda が9件・e6912a1f が5件・7e49a955 が1件。うち T1148・T1175 は並行の担当がいま持つタスク）。直しは記憶（feedback-records-only-commit-strict）とひな形（orch3_gen_generic.py:16）にだけ入り、リポジトリの規約には入っていない。
- **H2. 件名（kind `件名`）の生まれ方と消え方。** 「コミットしたら消える」は書かれているが、置く遷移が無い。上の実測で、今の仕掛中のタスクは件名を持っていない。CLAUDE.md は「コミットの件名はダッシュボードの件名と同じにする」と言うので、件名が無いタスクではこの規則が空回りする。
- **H3. 後始末係の出力。** 現在のタスクが番号でない担当（orchestration.md「監査の結果」、core.py `audited_keys`）は認められているが、作ってよいのが何か（記録だけのコミットか・どのタスクへか）が無い。09-27 の記録だけのコミットは、ユーザーの「後始末だけのバックグラウンドを1つ持っていても構わない」を受けて、この担当の形で作られた（記憶 feedback-coordinator-dont-hold-simple-work）。
- **H4. 1セッションの流れ。** CLAUDE.md・task/next.md の流れ（自分で `状態: 完了`＋台帳の行を消し、master へ push）と並行実行の流れ（担当は行に触らず、監査を経て司令塔が取り込む）は、同じ遷移を別の行為者・別の手順で定めている。どちらの規約にも、もう一方の流れとの関係が書かれていない。ユーザーの別セッションの軽い修正は、属するタスクの無い変更（CLAUDE.md の置き換え等）をどのコミットに入れるかでも行き場が無い（--proposal の直しが T1162 の回の終わりを待っているのはこの形）。
- **H5. 状態の語彙が2語。** `完了`/`未完了`（T986）。仕掛中・監査待ち・判断待ち・トリガー待ち・見送りは、状態の表・ダッシュボード・台帳の `— トリガー:`・本文から、道具ごとに別々に導かれる（`population_view`・`prereq_states`・`pending` の「仕掛中」）。導き方は3本あり、同じ定義か確かめる仕組みが無い。
- **H6. 門が瞬間のCPUで閉じ、開き直す出来事が無い。** `gate_reasons` は2秒の標本で CPU が90%以上なら閉じる（core.py `CPU_SAMPLE_SECONDS`・`CPU_SATURATED_PERCENT`）。重い処理は `heavy` の枠で1本ずつに並ぶので、枠の中の1本（tsc 等）だけで閉じうる。閉じた門を見直すのは次の `gate`/`check`（司令塔の道具の使用に付いたフック、待機中は CronCreate、`idle_since` の5分）だけで、負荷が引いたことを知らせる出来事は無い。
- **H8. 振り出す前に、依頼の進め方が実行できて正しいかを誰も確かめていない。** 振り出しの遷移で確かめているのは門（資源）と前提のタスクが済んだかだけで、依頼文の中身——前提のデータ・環境があるか・決まりに反していないか・起票案の選択が決まっているか——は、司令塔の注意（orchestration.md「司令塔の役割」の「前提と重なりの下調べ」）に頼る。実例（司令塔からの報告、2026-09-27）: T1195（40kmの生成の遅れの切り分け）で「手元の開発DBで新旧を測る」依頼を出したが、開発DBには40km以上を回せる道路網が無く、「性能は本番で測る」決まりにも反していた。ユーザーが気づいて止めた。T1179 は起票案の①②が未決のまま振り出し、担当が着手後に止まった。後者の「性能は本番で測る」は記憶（feedback-perf-measure-on-prod-not-dev-db）にだけあり、リポジトリの orchestration.md「環境」は「条件をそろえて交互に複数回取った中央値か、本番で取る」で開発機での計測を許している（衝突 C7）。
- **H7. 遷移を進めるのが司令塔の手だけ。** 振り出し（枠が空き門が開いたら列の先頭を起動）と取り込み（監査で通したら畳んで入れる）は、手順が機械的なのに司令塔が手で打つ。司令塔が他の仕事（ユーザーの問いへの返答・監査）にいる間は止まり、「張り付かないと進捗が上がらない」の原因になっている。確認の間隔を詰める直し（`idle_since` の5分・定期確認の要対応）は、見る頻度を上げるだけで進める手を増やさない。

**衝突（同じ遷移について置き場どうしが違うことを言う）**

- **C1. 台帳の行を誰が消すか。** CLAUDE.md 冒頭「完了したら台帳の行を消すこと」・「検査器にできず…」2.「`状態: 完了`にして台帳の行を消す」 ⇔ orchestration.md「完了とpush」「担当は台帳の行に触らない。司令塔が取り込みで消す」、ledger.py・review_checks.py も後者。
- **C2. 記録だけのコミットの範囲。** CLAUDE.md「閉じたタスクへの答え・確認の結果を移す `記録: 答え`」（狭い）⇔ asking-user.md「実装のコミットが入ったあとに出た答え・確認の結果のうち作業が生まれないもの」（閉じることを条件にしていないと読める。09-27 の司令塔はこう読んだ）⇔ 記憶「閉じるときに限る」⇔ ひな形「担当は作らない」。
- **C3. 起票の使い方。** CLAUDE.md（master）の例に `--proposal` が無い ⇔ asking-user.md・new_task.py は必須。

- ユーザーが答える画面は GitHub のものだけ（別のページを作ると GitHub との同期が要り、消す反映の流れが戻る）。

### 決めたこと（品質で決めた選択）

- **採番**: 新しいタスクは「origin/master の記録のファイル名」と「置き場の全部の issue（閉じたものを含む）の題名」に
  ある最大の番号＋1。閉じた issue も数えるのは、見送って記録を持たないまま閉じた番号を使い回さないため。記録は
  最初の段のコミットで作られるので、振った直後はまだ issue の題名にしか無い。同時に2つを振ったときは、番号の若い
  issue が勝ち、後から振った側が振り直す（書いた後に読み直して確かめる）。段を足す提案は、そのタスクの issue の
  題名と master の件名（`T1234 段階X`・`T1234-X:`）にある最後の文字の次。
- **入口は `take`**: ユーザーの操作は画面のラベルとチェックだけなので、入口（承認）・見送り・答えの取り込みを
  1つの `take` にまとめた。`take` が読むのは、開いている issue のラベルと、② で次に動かす人がユーザーの issue の
  本文とコメントだけ。答えは「最後に選択肢を並べた本文かコメントで、チェックがちょうど1つ」。
- **ユーザーが止める ② には選択肢を欠かせない**（`move … ② --by ユーザー` は `--choice` が無ければ断る）。押すだけで
  答えられる形を道具で守る。問いのコメントは道具が書くので、書式が崩れない。
- **「次に動かす人」の欄**: 状態の表の列そのもので、② では止めている人。「私の番」のビューはこの欄で絞る。
- **⑥ は閉じた issue**: 状態の欄に ⑥ を持たない（閉じたことと欄の二重持ちをしない）。
- **スロットの印を外す契機**: ④ から出る `move`（担当がスロットの中で打つ）と WorktreeRemove フック。今の
  slots.py の説明は WorktreeRemove が担当の終了では呼ばれないという観測を書いている（公式の文書は「サブエージェントが
  終わったとき」とも書く）ので、遷移の側でも外す。

### 調べて分かった事実（公式・ソース・実測）

- `gh project item-list --format json` は欄の名前の頭の1バイトを小文字にして JSON の鍵にする（cli/cli の
  `pkg/cmd/project/shared/queries/queries.go` の `camelCase`）。日本語の欄の名前では鍵が壊れるので、欄の値は
  `gh api graphql` で名前のまま読む。問い合わせは GitHub に投げて形を確かめた（Project 番号1で NOT_FOUND が返り、
  構文の誤りは無い）。
- `gh project item-edit --field <名前> --value <値>` は欄の型（単一選択・文字・日付・数値）で振り分け、欄の名前は
  大文字小文字を無視して一致させる（同じソースの `item_edit.go`・`resolve_fields.go`）。実際の Project にはまだ
  流していない。
- 開発機の git は 2.35.1 で、`git worktree list --porcelain -z`（2.36から）が無い。`-z` が無いと ASCII でない
  ロックの理由は引用符と8進の形に書き換えられる（テストで印が外れなかったことで分かった）ので、理由を ASCII にした。
- 通知: 公式の文書で、メールの設定に「自分の更新」（Your own updates）を含める項目がある。GitHub Mobile の
  プッシュとして挙がっているのは言及・割り当て・レビューの依頼・デプロイの承認。Web の受信箱とモバイルに自分の操作
  （同じアカウントで担当が書いたコメント）が届くかは書かれていない。**切り替えの前に1件で確かめる。**
- Projects の `updated:` の絞り込みは issue の作成・再開・編集・コメント・ラベル等で進み、日の単位（`@today-1d`）
  でしか比べられない。欄の書き換えで進むかは書かれていない。
- Free のプランに「Issues & Projects」と「無制限の公開・非公開のリポジトリ」が含まれる（github.com/pricing）。
- チェックボックスは、書き込みの権限のある人なら他人のコメントのものも押せる（GitHub Blog「Task lists in all
  markdown documents」2014）。この運用では全員が同じアカウントなので、どのみち自分のコメントになる。モバイルの
  アプリから押せるかは公式の文に当たれていない。
