■ やること
1. 調べる（読むだけ、段階A、S）: タスクの状態の移り方に関わる決まりの文を全部の置き場から機械で拾い、過去の事故と直しを並べて、穴と衝突の地図を作る。workflow.md を消した判断も見直す。

3. 道具で止める: 禁じた遷移は道具が断る形にし、散らばった文を消す。

■ 規模: 調べる段はS、全体はM〜L。この設計が決まるまで、運用の道具への場当たりの直し（T1149・T1167〜T1169等）は振り出さない。

### 3. 穴と衝突の地図

**穴（遷移が定義されていない・行き先が無い）**

- **H1. 開いているが誰も持っていないタスクへの答え。** 答えを記録へ移せるのは「そのタスクのコミット」（CLAUDE.md・asking-user.md）か、閉じるときの `記録: 答え` だけ。担当のいない未完了タスクには「そのタスクのコミット」が来る時機が無く、答えはダッシュボード（asking-user.md 自身が「正本ではない」「公式の文書に記載の無い機能」と書く置き場）に溜まり続ける。持ち主は司令塔になる（件の持ち主の導き方）が、司令塔にはその答えを記録へ移す合法の遷移が無い。**2026-09-27 03:14〜04:44 の `記録: 答え` 4コミットが名指した未完了タスク28件（延べ）は、この穴へ流れ込んだ結果**（`W-flow_recordonly.py` で検算。c9d1fc6f が13件・48f17bda が9件・e6912a1f が5件・7e49a955 が1件。うち T1148・T1175 は並行の担当がいま持つタスク）。直しは記憶（feedback-records-only-commit-strict）とひな形（orch3_gen_generic.py:16）にだけ入り、リポジトリの規約には入っていない。
- **H2. 件名（kind `件名`）の生まれ方と消え方。** 「コミットしたら消える」は書かれているが、置く遷移が無い。上の実測で、今の仕掛中のタスクは件名を持っていない。CLAUDE.md は「コミットの件名はダッシュボードの件名と同じにする」と言うので、件名が無いタスクではこの規則が空回りする。
- **H3. 後始末係の出力。** 現在のタスクが番号でない担当（orchestration.md「監査の結果」、core.py `audited_keys`）は認められているが、作ってよいのが何か（記録だけのコミットか・どのタスクへか）が無い。09-27 の記録だけのコミットは、ユーザーの「後始末だけのバックグラウンドを1つ持っていても構わない」を受けて、この担当の形で作られた（記憶 feedback-coordinator-dont-hold-simple-work）。
- **H4. 1セッションの流れ。** CLAUDE.md・task/next.md の流れ（自分で `状態: 完了`＋台帳の行を消し、master へ push）と並行実行の流れ（担当は行に触らず、監査を経て司令塔が取り込む）は、同じ遷移を別の行為者・別の手順で定めている。どちらの規約にも、もう一方の流れとの関係が書かれていない。ユーザーの別セッションの軽い修正は、属するタスクの無い変更（CLAUDE.md の置き換え等）をどのコミットに入れるかでも行き場が無い（--proposal の直しが T1162 の回の終わりを待っているのはこの形）。
- **H5. 状態の語彙が2語。** `完了`/`未完了`（T986）。仕掛中・監査待ち・判断待ち・トリガー待ち・見送りは、状態の表・ダッシュボード・台帳の `— トリガー:`・本文から、道具ごとに別々に導かれる（`population_view`・`prereq_states`・`pending` の「仕掛中」）。導き方は3本あり、同じ定義か確かめる仕組みが無い。
- **H6. 門が瞬間のCPUで閉じ、開き直す出来事が無い。** `gate_reasons` は2秒の標本で CPU が90%以上なら閉じる（core.py `CPU_SAMPLE_SECONDS`・`CPU_SATURATED_PERCENT`）。重い処理は `heavy` の枠で1本ずつに並ぶので、枠の中の1本（tsc 等）だけで閉じうる。閉じた門を見直すのは次の `gate`/`check`（司令塔の道具の使用に付いたフック、待機中は CronCreate、`idle_since` の5分）だけで、負荷が引いたことを知らせる出来事は無い。
- **H8. 振り出す前に、依頼の進め方が実行できて正しいかを誰も確かめていない。** 振り出しの遷移で確かめているのは門（資源）と前提のタスクが済んだかだけで、依頼文の中身——前提のデータ・環境があるか・決まりに反していないか・起票案の選択が決まっているか——は、司令塔の注意（orchestration.md「司令塔の役割」の「前提と重なりの下調べ」）に頼る。実例（司令塔からの報告、2026-09-27）: T1195（40kmの生成の遅れの切り分け）で「手元の開発DBで新旧を測る」依頼を出したが、開発DBには40km以上を回せる道路網が無く、「性能は本番で測る」決まりにも反していた。ユーザーが気づいて止めた。T1179 は起票案の①②が未決のまま振り出し、担当が着手後に止まった。後者の「性能は本番で測る」は記憶（feedback-perf-measure-on-prod-not-dev-db）にだけあり、リポジトリの orchestration.md「環境」は「条件をそろえて交互に複数回取った中央値か、本番で取る」で開発機での計測を許している（衝突 C7）。
- **H7. 遷移を進めるのが司令塔の手だけ。** 振り出し（枠が空き門が開いたら列の先頭を起動）と取り込み（監査で通したら畳んで入れる）は、手順が機械的なのに司令塔が手で打つ。司令塔が他の仕事（ユーザーの問いへの返答・監査）にいる間は止まり、「張り付かないと進捗が上がらない」の原因になっている。確認の間隔を詰める直し（`idle_since` の5分・定期確認の要対応）は、見る頻度を上げるだけで進める手を増やさない。

**衝突（同じ遷移について置き場どうしが違うことを言う）**

- **C1. 台帳の行を誰が消すか。** CLAUDE.md 冒頭「完了したら台帳の行を消すこと」・「検査器にできず…」2.「`状態: 完了`にして台帳の行を消す」 ⇔ orchestration.md「完了とpush」「担当は台帳の行に触らない。司令塔が取り込みで消す」、ledger.py・review_checks.py も後者。
- **C2. 記録だけのコミットの範囲。** CLAUDE.md「閉じたタスクへの答え・確認の結果を移す `記録: 答え`」（狭い）⇔ asking-user.md「実装のコミットが入ったあとに出た答え・確認の結果のうち作業が生まれないもの」（閉じることを条件にしていないと読める。09-27 の司令塔はこう読んだ）⇔ 記憶「閉じるときに限る」⇔ ひな形「担当は作らない」。
- **C3. 起票の使い方。** CLAUDE.md（master）の例に `--proposal` が無い ⇔ asking-user.md・new_task.py は必須。

「判断待ち」は状態ではなく、どの状態にも付きうる印（ダッシュボードに答えの無い件がある）として扱う。H1 の「開いていて持ち主の無いタスクに答えが付いた」は、この印が未着手に付いた形で、遷移を決める（下の表の「答えが出る」）。

### 選択肢と推奨（品質で選ぶ。運用の都合は理由にしない）

- **B1. 開いていて持ち主の無いタスクへの答え（H1）**
  1. （推奨）答えで作業が生まれるなら、その場でそのタスクを振り出し待ちへ積み（答えが遷移の出来事になる）、答えは最初の段階のコミットで記録へ移す。作業が生まれないなら、そのタスクの残りと一緒に次のタスクのコミットまでダッシュボードに置き、`記録: 答え` は閉じるときだけにする。理由: 1コミット＝1作業の区切りが保たれ（ユーザーが09-27に選んだ規則）、答えが放置されるのではなく振り出しに繋がる。弱点はダッシュボード（正本でない置き場）に答えが残る時間で、`pending-backup` の書き出し（今は14日）を答えのある件については消さないように直す必要がある。
  2. `記録: 答え` を未着手のタスクにも許す。答えがすぐ記録（正本）に入るが、コミットが作業の区切りでなくなり、履歴から「どこまで戻すか」が読めなくなる（CLAUDE.md が守ろうとしているもの）。09-27 にユーザーが退けた形。
- **B2. 正本の置き場**
  1. （推奨）`docs/conventions/task-lifecycle.md` を新設し、上の2つの表（状態・遷移）だけを持つ。CLAUDE.md の「1タスク=1コミット」「起票は承認制」周り・asking-user.md「記録だけを変えるコミットの例外」「起票は承認制」・orchestration.md「完了とpush」の該当文・task/next.md の手順は、表の行を指すだけにして本文を消す。道具は、すでに `rules`・`heavy_stages` が orchestration.md のブロックを読んでいるのと同じく、この表の遷移の名前を読み、遷移ごとの検査の関数が表の全行に揃っていることをテストで見る（母集団を導いた不変条件なので CLAUDE.md の基準に合う）。
  2. 状態機械をコード（`scripts/orchestration/lifecycle.py` の冒頭）に置き、文書は指すだけ。道具と定義がずれないが、ユーザーが方針を読んで決める場所がコードになる。
  3. workflow.md を案内図として戻す。規則の正本にならないので、今回の穴（衝突の優先）は埋まらない。推奨しない。
- **B3. 禁じた遷移をどこで断るか（C5）**
  1. （推奨）遷移ごとに1本の道具（採番＝new_task.py、取り込み＝畳んで入れる道具、記録へ移す＝`記録: 答え` を作る道具）にし、その道具が前提を確かめて断る。master へ入る経路を取り込みの道具と new_task.py に寄せ、1セッションの流れも同じ道具で入れる。CLAUDE.md の「pushを検査で止めない」は、重い品質の検査（テスト・lint）について言っていると範囲を書き直す（T1062 で外したのは重い検査で、遷移の確かめはgitを読むだけの数秒）。手で `git push` する経路は残るので、pre-push で「master への push は道具を経たか」だけを見るかを併せて決める。
  2. CI（docs 検査）に、push された範囲のコミットの件名と中身の組を見る検査を足す。T986 の「範囲を絞る仕組みを持たない」に反する。全件にすると過去の違反（09-27 の28件等）で常に赤になる。推奨しない。
  3. GitHub の側（ルールセットのコミットメッセージの制約等）で断る。使えるか・この契約で有効かは公式の文書を読んでから決める（段階Aでは未確認）。
- **B4. 状態の語彙（H5）**: `完了`/`未完了` の2語（T986 の判断）は保ち、仕掛中・監査待ちは状態の表から、見送りは本文でなく `状態: 完了（見送り）` の形で導けるようにするか。導き方が3本（`population_view`・`prereq_states`・`pending`）ある今の形は、1本の関数へ寄せる（推奨）。
- **B5. 遷移を誰が進めるか（H7。司令塔の追加の観点）**: 振り出しと取り込みを、司令塔の手から道具へ移す。
  1. （推奨の方向）取り込みは、監査の判断（3・5・6の項目）を司令塔に残し、`audit_result=通す` を書いた時点で道具が cherry-pick・ledger sync・畳み・push までを進める（手順は既に `board unpushed` が機械的に並べている。記憶 feedback-land-audited-immediately の「通したらすぐ入れる」とも合う）。溜めて1回で出す今の決まり（pushの時期）は、デプロイの回数の都合なので、本番への影響としてユーザーと別に決める。
  2. 振り出しは、枠が空き門が開いたら列の先頭を起動する処理を道具が持つ。手段の候補は Claude Code の Workflow（決まった手順で担当を起動・監査する。起動にはユーザーの明示の同意が要る）と、道具から `claude -p`（ヘッドレス）で担当を起動する形。後者は、Agent の `isolation: "worktree"` が今くれているスロットの受け渡し（WorktreeCreate のフック）と権限の範囲を、道具の側で決め直す必要がある。どちらも仕様（起動のしかた・権限・隔離・同時の本数）は段階Aでは公式を読んでいない。段階Bの最初に公式の文書を読んで、使えるかを確かめる。
  3. 見回りの間隔を詰める（今の直し方）。見る回数が増えるだけで、進める手は司令塔1人のまま。推奨しない。
- **B6. 門の負荷の判定（H6）**: 重い処理は `heavy` の枠で既に1本ずつなので、瞬間のCPU（2秒の標本）で門を閉じる条件は外し、枠の待ち（`lock_wait_problems`、今もある）と、続いた負荷（定期確認ごとの標本の直近の中央値等）で見る案を推す。あわせて、門が閉じたまま振り出し待ちがある状態を、負荷が引いた時点で拾う出来事（B5 の振り出しの道具が門を見直す）を置く。
- **B8. 振り出す前の依頼の妥当性（H8）**: 振り出しの遷移に「依頼を出す前に確かめること」を置く。確かめる中身は、①記録・ダッシュボードに答えの出ていない選択・`保留` が残っていないか、②前提のデータ・環境（どのDBに何があるか・本番の接続が要るか）が依頼の進め方と合うか、③依頼の進め方が決まり（測る場所・本番への書き込みをしない等）に反していないか。
  1. （推奨）①は振り出しの道具が機械で断る（ダッシュボードの書き出しと記録から導ける）。②③は、担当が着手の最初の段で「進め方の確かめ」を1段として行い、合わなければ作業に入らず問いとして置いて止まる（担当はコードとデータを実際に読める立場にある）。司令塔の下調べはその前の粗い篩として残す。
  2. 司令塔が依頼文ごとに②③の確認表を埋めてから振り出す。人の注意のまま（今と同じ種類）で、B5 で振り出しを道具へ移すと成り立たない。
  3. 振り出しの前に、依頼文をユーザーが見て承認する。確実だが、張り付かないと進まない形（H7）へ戻る。
  いずれも、③の拠り所になる決まりがリポジトリの外（記憶）にあると確かめようが無いので、B7 とあわせて正本へ入れる（C7）。
- **B7. リポジトリの外の決まり**: 記憶とひな形にある決まりのうち遷移に関わるもの（記録だけのコミットを閉じるときに限る・後始末係・司令塔は手元に溜めない等）は、B2 の正本へ入れるか捨てるかを1件ずつ決め、ひな形は `rules` の出力とタスクの注意だけを持つ形へ戻す（C6）。
