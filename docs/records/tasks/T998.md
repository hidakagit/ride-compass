# T998. テストを実装から起こし直し、既存とdiffを取る

状態: 未完了（2026-09-22起票）

## 背景

[T996](T996.md)の走査中に3ファイルを「既存テストを一切見ずに、実装だけを読んで書き起こす」
やり方で作り直したところ、3件とも**既存テストの半分以上が実装と対応していなかった**。

| ファイル | 既存 | 起こし直し | 内訳 |
|---|---|---|---|
| `backend/tests/test_axis_display.py` | 960行 / 43件 | 429行 / 47件 | 網羅率 84%→98% |
| `frontend/.../AxisComposer.test.tsx` | 978行 / 46件 | 249行 / 16件 | 30件が別コンポーネントの責務 |
| `frontend/.../AxisStudio.test.tsx` | 17件 | 17件 | 10件が実質的に別物 |

3件目の内訳が型を示している。**実装が持つ分岐のうち5つ（取得失敗の表示・下書きが空・
最後の1軸は削除できない・削除失敗・公開取り消し失敗）を既存テストは1つも見ていなかった**一方、
既存にしか無い4件はすべて別コンポーネントの責務で、1件は既に撤去された機構
（ログイン欄）が無いことの見張りだった。

同じセッションで`AxisComposer.materialValues.test.tsx`も、真偽材料には値欄自体が
描かれないため「候補セレクトが出ない」の検査が成立していなかった（常に通る）。

これは特定の改修の後始末ではない。テストが**実装から再導出されず、変更のたびに
継ぎ足されてきた**ことの結果で、その書き方はリポジトリ全体に及んでいる。

## なぜ「全部書き直す」ではないか

実装を読んで書き起こすと、**過去のバグを刺しているテストが復元できない**。実装は
「いま何をするか」しか語らないので、「この入力で落ちた」という知識は失われる。
だから作業は書き直しではなく、**起こし直して既存とdiffを取り、両方向を判定する**。

## 対象の出し方

母集団は`backend/tests/**/test_*.py`と`frontend/src/**/*.test.ts(x)`の全件。
1ファイルずつ、次の順で進める（テストファイル単位。複数の実装をまたぐテストは、
diffの結果として分割されることがある）。

### テスト行÷実装行では並べられない（2026-09-22実測）

起票時は「比が4を超えるものから」と書いたが、backendで測ると**効かなかった**。
母集団の定義は「`ast`でdocstringを除き、コメント専用行と空行を落とした行数。
対応付けは`test_<stem>.py`↔`backend/app/**/<stem>.py`」。結果、比が4を超えたのは
`test_strict_model.py`（29行/3行）の1件だけで、それは実装が3行だから大きいだけだった。
上位は3.5前後に固まっており、順序の根拠にならない。

### 順番は、下の層から上へ

下を先に固めると、上の層で見つかる他責務のテストは「**移す**」ではなく「**消す**」で
片付く——責務の行き先が既に完成しているため。逆順だと、apiから抜いた検査をdomainの
テストへ移し、そのdomainテストを後で起こし直すときに同じものをもう一度判定することになる。

## 手順

[docs/conventions/testing.md](../../conventions/testing.md)「既存テストを直さず、実装から
起こし直す」に従う。取り込みの判定は同ファイル「残すべきテストの型」、責務の宣言は
「テストは、テストだけで成立させる」節。**ここへ手順を書き写さない**——このタスクが
終わると記録は維持されなくなり、写した側だけが残る。

### docstringの写しの一掃（2026-09-22）

起こし直した30ファイルのdocstringが、**実装のコメント・docstringを裏返した写し**に
なっていた。`comments.md`は対象を「ソースコード」と書いてテストを除外しておらず、削除の
判定基準（「同じ内容が他所にあるなら二重管理」）は実装とテストの間でも成り立つ。

測り方と結果: docstringを句点で切った599文を、そのテストがimportするapp配下モジュールの
コメント＋docstringの全文と突き合わせた（difflibの比率と文字bigramのJaccardの最大値）。
0.55以上が106文。**分布に切れ目が無く（0.2〜1.0が連続）しきい値では判定できない**ため、
順序付けにだけ使い、30ファイルを1本ずつ目で見て落とした。599→371文。

判定基準は[comments.md](../../conventions/comments.md)「テストのdocstringも対象」へ移した。

同時に直した実装の歪み: `traffic.TAG_KIND_RULES`・`DIRECTION_RULES`の優先順位を、リテラルの
整数から群の並びから振る形へ（`_TAG_KIND_GROUPS`・`_DIRECTION_GROUPS`）。生成される表が
旧と完全一致（41件・18件）であることを確認し、優先順位を検査していた`TestRuleTables`
3件を削除した。

規模（母集団＝この30ファイル、基準は`8ddd761a^`）: 全行 3,541→5,100（+44%）、
説明行を除いた実行行 2,262→3,061（+35%）。写しを落とす前は全行+48%だったため、
差の4ポイントが二重管理だった分。

  唯一の例外は起こし直していなかった1本で40/40が同名だった）

**並列化の代償を1つ測った。** 担当が報告したカバレッジのうち9件は無効だった——母集団に、

### 構造仕様16は、この作業から出た（2026-09-22）

7名が独立に報告した実装の欠陥を分類したところ、約35件のうち**7割超が3つの姿**に落ちた
——黙ったフォールバック（相手が何を送るか決まっていない）、多重扉（誰が入ってよいか
決まっていない）、取り違え（何が境界を渡るか決まっていない）。別々の指摘として挙がるが、
**境界が「破られたら落ちるもの」として表現されていない**という1つのことである。

同じ時点で分岐カバレッジは26本中20本が100%だった。**網羅率はこの欠陥を検出しない。**

[design-principles.md](../../architecture/design-principles.md)の構造仕様16として立てた。
構造仕様15（データの制約はDB、ふるまいの制約はapp）は、この原則をDB↔appの境界へ当てた
ものにあたる。

実装側の未修正は44件あり、モジュール別に分類して持っている。段階1のやり直し（domain層へ
構造仕様16を当てる作業）で同じモジュールへの指摘が重なるため、**重複を排してから直す**。

### 昨日のコメント削除の監査（2026-09-22）

T967（経緯コメントの一掃）とT968（デッドコードの整理）で、backendから**119件のコメント塊**が
消えていた。2つの欠陥が報告されている——削除の可否を「参照0か」で機械的に決めたこと

可能性が高い。**B（75件）**はコードごと消えたものだが、巻き込みの設計上、**消えた関数では
なく残っている塊全体を説明していた文**が混ざる。両方を段階1やり直しの担当へ配った。

戻す条件は[comments.md](../../conventions/comments.md)に従う。**元の文をそのまま戻さない**
——経緯を落とし、今も成り立つ制約だけを現在形の一文で書き直す。

■ 背景（画面に出ない、テスト基盤の話）
backend のテストは、pytest-asyncio・pytest-xdist・pytest-cov のほかにプラグインを使っていない。大見直しではテストを大量に動かし・分け・消すので、その間は次の3つが効く。どれも設定を足すだけで、テストの書き方は変わらない。

1. pytest-testmon（変更が届くテストだけを流す）
- 今は CLAUDE.md の「変更が届く範囲だけ回す」を、grep と pytest --co で手で導いている。testmon は coverage.py でテストごとに通った行を記録し、変わった行を通るテストだけを選ぶ。
- 公式の条件（testmon.org）: 追わないのは「静的ファイル（txt・xml 等のプロジェクトの資産）」と「ネットワーク越しの外部サービス」。第三者パッケージの版と環境変数は追う。xdist には v1.4 から対応。記録は pytest の rootdir の .testmondata（TESTMON_DATAFILE で置き場を移せる）。
- この repo での注意: テストDBの中身とデータファイル（JSON の生成物等）の変化は追えないので、それらを変えたときは --testmon-noselect 等で全件を流す。testing.md の「届く範囲の導き方」にこの使い方を書き足す。CI は今のまま全件。

2. pytest-randomly（実行順をばらす）
- 公式（PyPI、v5.0.0、Python 3.10〜3.15、xdist 対応）: モジュール→クラス→関数の順に並びを混ぜ、各テストの前に random と numpy の旧い乱数の種を固定値へ戻す。--randomly-seed=last で前回の並びを再現でき、-p no:randomly で無効にできる。
- 効く理由: conftest に autouse の初期化（Redis の遮断器・タイルの置き場）があり、テスト間に隠れた順序依存がありうる。見直しで分けた・動かしたテストが元の並びでしか通らないことを、早く表に出せる。混ぜるのはモジュールの中でなので、ファイル単位でイベントループを共有する PostGIS テストの前提は崩れない見込み（採用時に1回流して確かめる）。

3. pytest-timeout（止まったテストを時間で落とす）
- 公式（PyPI、v2.4.0）: Windows では thread 方式になり、時間切れで「プロセス全体を終わらせる」。そのとき fixture の後片付けは走らない。デバッガの使用中は発火を避ける。
- 効く理由: 過去に「条件に合う点が1つも無いと探索が止まらず16.9分」「共有テストDBの取り合いで3組が滞留」という実例がある。
- この repo での注意: 時間切れでは後片付けが走らないので、作業ツリーごとのテストDBの残骸が残りうる（testing.md「残骸の片付け」の手順で消える）。上限は --durations で測ったふだんの最長の数倍にする。

### 確かめたこと（一時プロジェクト・手元の対象ファイル・作業ブランチのCI）

- **`-q`では種が出ない。** randomlyは種を実行の見出し（`pytest_report_header`）にだけ出し、`-q`は見出しを出さない
  （一時プロジェクトで、出力が`F..`から始まることを確認）。CIは`-q`で流しているので、そのままでは落ちた並びを再現
  できない。そこでCIはrunのIDを種に渡す。**CIで落ちた種（36293935373）を手元で渡すと、同じテストが同じ理由で落ちた**
  （旧版の`test_derive_counts.py`、`1 failed, 3 passed`）。
- **pytest-timeoutが入っていないと、全テストが起動時に止まる。** `pytest.ini`の`timeout`は未知の設定として
  `PytestConfigWarning`になり、`filterwarnings = error`で`INTERNALERROR`になる（一時プロジェクトで確認）。
  黙って上限が効かなくなるより良いが、**開発機の共有の`backend/.venv`へ入れてから取り込む必要がある**（下の
  「取り込むときの操作」）。
- 未宣言のマーカーは収集時に`'nosuchmarker' not found in markers`で止まる。印のあるxfailが通ると
  `[XPASS(strict)]`で落ちる。今のテストは`--strict-markers`で全件（2,191件）収集できる。`xfail`の印は0件。
- Windowsの時間切れはプロセスごと終わる（一時プロジェクトで、止まったテストの後ろのテストが流れなかった）。
- testmon: 3ファイル73件を記録した後の2回目は73件すべてを外し（`73 deselected`）、`domain/geo.py`の関数1本を
  書き換えると、その関数を通る7件だけを流した（`7 passed, 66 deselected`）。記録を取る実行は4.5秒→6.3秒。
- 上限の根拠: 1件の最長はCIで6.54秒（`--durations=40`、2,191件の全件）、開発機で23.56秒（遅いほうの
  上位を含む5ファイル78件、`--durations=15`）。どちらも`test_orchestration_slots.py`の同じ1件。開発機の最長の5倍の
  120秒に置いた。止まり方の実例（探索が止まらず16.9分）は、これで2分で落ちる。

### randomlyが見つけた順序依存と、同じ性質の直し

最初のCI（種36293935373）で`test_derive_counts.py::test_a_crossing_near_a_signal_is_counted_as_a_signal`が
`UniqueViolationError`で落ちた。原因は、ファイル単位のfixtureが作った生データと派生の表を**テストが書き換え、
後片付けで戻す**形にあった。戻し漏れが3つあった——別のテストが入れた`osm_node`の行を残す（相手が先に流れる
前提で`ON CONFLICT DO NOTHING`を書いていた）、事故の行を戻しても派生の表を作り直さない、消した道を戻しても
派生の表を作り直さない。

**性質**: ファイル単位で共有した行を、テストが書き換える。当てはまるファイルを、ファイル単位（`scope="module"`）の
データのfixtureを持つファイルから選んだ: `test_derive_counts.py`・`test_derive_elevation.py`・
`test_derive_node_materials.py`（書き換えて戻す）。`test_derive_topology.py`・`test_derive_stop_counts.py`は
読むだけ、`test_derive_landcover.py`・`test_ingest.py`はテストが1件で、順序の依存が起こりえない。
3ファイルとも、共有するのは接続とパーティションまでにし、データはテストごとに作り直す関数スコープのfixtureへ
移した。戻すための一時表と`finally`は要らなくなって消えた。規約はtesting.mdパターン2の4.へ書いた。

直した3ファイルは、CIで落ちた種と別の5つの種で全件（9件）が通った。

### 範囲外で見つけたもの

- `test_derive_stop_counts.py`の3件が、開発機ではこのファイル単独でも・並びを混ぜなくても落ちる
  （`{'…': 2, …} == {'…': 1.0, …}`）。CI（Linux）では通っている。道具を入れる前から開発機で落ちるかは確かめて
  いない（共有のvenvから外して流していない）。環境の差（PostGISの版・開発機のDB）の疑い。最終報告へ書いた。

### 取り込むときの操作

- 開発機の共有の`backend/.venv`（本体のチェックアウト）へ`requirements-dev.txt`の3本を入れる。
  **pytest-timeoutとpytest-testmonは2026-09-27に入れた**（設定が無ければ働かないため、取り込み前に入れても他の
  担当の実行は変わらない）。**pytest-randomlyは取り込みと同時に入れる**（入っているだけで並びを混ぜるため、先に
  入れると取り込み前の作業ブランチの手元の実行まで混ぜてしまう）。入れていない間は並びを混ぜないだけで、止まらない。
- CI（`orch/**`とmaster）はこの取り込みから並びを混ぜる。**他の作業ブランチのCIで、変更と無関係な
  テストが落ちたら順序依存を疑う**——落ちたrunのIDを種に渡すと手元で同じ並びになる。
