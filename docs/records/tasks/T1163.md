# T1163. 取り込んだ担当のスロットに元のコミットが残り、スロットを渡し直せなくなる

状態: 完了（2026-09-26）

## 背景

司令塔は担当のコミットを台帳・記録の変更を畳んだ別のコミットとしてmasterへ入れるため、担当側の元のコミットはどのリモートの枝からも届かず、スロットの道具（slots.pyの止まる条件）が「pushしていない成果」とみなして渡し直しを止める。2026-09-26にslot-1〜3の3本ともこの状態になり、/reviewの担当を作業ツリー付きで起動できなかった（手で中身がmasterにあることを確かめて空けた）。規約（orchestration.md「作業ツリーのスロット」）は監査で通したら印を外すとだけ決めている。取り込み済みかを件名のタスク番号とmasterから導いて、取り込んだスロットを渡し直せる形にする。起票案 proposal-slot-cleanup-on-land（2026-09-26承認）

## 着手時の確認

- 前提（`core.py`の`audited_unpushed`が「監査で通したタスクの番号から始まる件名のコミットが、監査の後にorigin/masterへ入ったか」で入ったかを導いている、`slots.py`の止まる条件が`core.unsaved_work`の`git rev-list HEAD --not --remotes=origin`を見ている）はorigin/master（5b796bb1）で成り立っていた。
- 状態の表の`audit_log`の1件は`task`・`reported_sha`・`audit_done`（分まで）・`audit_result`を持つ。古い記録には`task`が無いものがあり、`reported_sha`が数字だけのときはJSONの数として入っている（`board set`の値の読み方）。どちらも扱える形にした。表の形は変えていない。

## 対応

- 入ったかの判定を`core.py`で3つに分け（`passed_audits`・`landed_since`・`has_landed`）、`audited_unpushed`（`board unpushed`・`check`）とスロットの止まる条件の両方がこれを使う。判定の中身（タスク番号から始まる件名のコミットが監査の時刻以降にmasterへ入ったか）は変えていない。
- `unsaved_work`は、どのリモートの枝からも届かないコミットのうち、取り込み済みのもの（監査で通した報告のshaから届き、そのタスクが入ったもの）を数えない（`unlanded_commits`）。報告のshaは短縮形でもよいよう、届かないコミットの前方一致で引く。masterの履歴を読む範囲は、固定の48時間ではなく該当する監査の記録のうち最も古い監査の時刻から——スロットは回をまたいで何日も置かれうる。
- 止まる条件の他の場合（未コミットの変更・監査で通していないコミット・報告のshaより後に積んだコミット・まだmasterへ入っていないタスクのコミット・作業ツリーの中のリンク）は今のまま止める。
- `docs/conventions/orchestration.md`「作業ツリーのスロット」節と`slots.py`・`core.py`の冒頭に、取り込み済みの数え方を書いた。
