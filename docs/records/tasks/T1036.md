# T1036. 焼き込み列とtile_propertyの一致を、命名規約から生成へ移すか

状態: 完了

## 判断: 見送り（2026-09-23・周期レビュー第12回、ユーザー承認済み）

## 背景

材料の宣言が持つタイル属性名と、MVT生成SQLが出力する列名が同じ綴りでないと、
その材料は地図レンズを持てない。現在この一致を守っているのは**命名規約だけ**で、
機械的な保証が無い。同じファイルのコメントが「手で並べると、クラスを1つ足したときに
『材料は地図レンズを持つのに列が無い』形で静かに空になる」とこの危険を明記しており、
土地被覆の家族だけはそれを理由に宣言からの生成へ移してある。

## 見送りの理由

1. **現時点の食い違いは実測0件。** タイル属性を持つ材料の全件について、対応する列が
   焼き込みSQLに存在するかを突合し、欠落0・余分は識別子と表示専用の列のみだった。
2. **生成へ移しても純減しない。** 材料の値式と焼き込み式は同一ではない——タイル容量の
   ために偽値を落とす意図的な差がある。したがって値式をそのまま列として並べる単純な
   生成はできず、宣言に「焼き込み用の式」という2本目のSQLフィールドを足すことになる。
   **2つの式の差の管理を別の場所へ移すだけ**で、写しが消えたことにならない。
3. **この欠陥が現れるのは「way単位の新材料を地図に出す」ときだけ**で、その頻度は
   本周期で0回。

## 再評価の条件

**次にway単位の新材料を追加して地図へ出すタスクが来たとき**、そのタスクの中で
再評価する。そのとき見るのは「宣言だけを足して列を忘れ、地図が静かに空になる」経験が
実際に起きたかどうか。起きたなら、そのコストが上の(2)の追加フィールドのコストを
上回ったことになる。

## 再測の方法

食い違いの有無は次で機械的に出せる。判断をやり直すときはまずこれを回す:
材料カタログを import してタイル属性を持つ材料を全件挙げ、MVT生成SQLの`AS`列名の
集合と差集合を取る。第12回はこの方法で「欠落0」を得た。
