# T491. backend main.pyのlifespan（起動・終了シーケンス）を検証するテストを追加する

状態: 完了（2026-08-31）

- 背景: ユーザー依頼のテスト有効性・カバレッジ監査（2026-08-31）で、`backend/app/
  main.py`のlifespan一式（`docs/modules/backend/cross-cutting-infrastructure.md`
  「アプリ起動（main.py）」節）を検証するテストが存在しないことが判明した
  （2エージェントが独立に同じ穴を報告、一致度が高い）。既存の`test_main.py`・
  `test_health.py`等は`TestClient(app)`をcontext manager無しで生成しており、
  Starlette/FastAPIのTestClientはこの形だとlifespanイベント（startup/shutdown）を
  発火しない。実測でリポジトリ全体を`lifespan|refresh_axis_definitions|
  AsyncIOScheduler|AMEDAS_REFRESH_INTERVAL`でgrepしても、`main.py`のlifespan関数
  そのもの（起動時の一連の結線）を検証するテストは見つからなかった。特に以下が
  未検証:
  1. `refresh_axis_definitions()`が起動時に例外を送出した場合、それが捕捉されず
     アプリ起動自体が失敗すること（fail-fast設計、docs記載の重要な不変条件）
  2. APSchedulerへのJMAアメダス定期更新ジョブ登録が`next_run_time=datetime.now()`
     で起動直後にも即時実行されること（コールドスタート対策）
  3. シャットダウン時に「APScheduler停止（`wait=False`）→httpxクライアント明示close
     （`close_all_http_clients`）」の順序で実行されること
  この経路が壊れても、既存テストは何も落ちないため本番デプロイまで気づけない
  （main.py以外の個別ロジック——`refresh_axis_definitions`自体・`close_all_http_
  clients`自体等——は別途高品質にテスト済みだが、main.pyでの結線自体は未検証）。
- 対応方針: `with TestClient(app) as client:`（context manager形式）でlifespanを
  実際に発火させ、(1) `refresh_axis_definitions`をmonkeypatchで例外送出させて
  アプリ起動が失敗することを確認、(2) スケジューラへのジョブ登録引数
  （`next_run_time`等）を検証、(3) シャットダウン順序をspy/monkeypatchで検証する。
  `test_rate_limiter.py`・`test_debug_log.py`が既に持つ`time.monotonic`
  monkeypatchパターン、`test_database.py`が持つ「実引数レベルでの接続設定検証」
  パターンを流用できる。
- 規模: S〜M

## 実施内容（2026-08-31完了）

新規`backend/tests/test_main_lifespan.py`に3件のテストを追加した。
`with TestClient(app) as client:`（context manager形式）でlifespanを実際に発火させる。

1. `test_lifespan_fails_fast_when_refresh_axis_definitions_raises`: `refresh_axis_
   definitions`をmonkeypatchで`AxisDefinitionSyncError`送出に差し替え、
   `with TestClient(app):`のブロック自体が同例外で失敗する（fail-fast、捕捉されず
   アプリ起動が落ちる）ことを確認。
2. `test_lifespan_registers_amedas_job_with_immediate_next_run_time`:
   `_scheduler.add_job`をspyし、`trigger="interval"`・
   `minutes=AMEDAS_REFRESH_INTERVAL_MINUTES`・`id="refresh_amedas"`・
   `next_run_time`が呼び出し直前の時刻とほぼ一致することを検証。
3. `test_lifespan_shuts_down_scheduler_before_closing_http_clients`:
   `scheduler.shutdown`と`close_all_http_clients`の両方をspyし、呼び出し順序
   （scheduler停止が先）を検証。

**実装中に見つかった罠（テスト設計上の教訓）**: 当初`test_lifespan_registers_amedas_job_
with_immediate_next_run_time`は`with TestClient(app):`のブロック内で
`_scheduler.get_job("refresh_amedas")`を呼び返り値の`next_run_time`を検証する設計
だったが、実際に実行すると**ジョブが既に1回発火し次のinterval（10分）先へ
next_run_timeが進んでしまっていた**（実測で確認、`_refresh_amedas_job`が実際に
JMAへHTTPアクセスを試みるログも出た）。`next_run_time=datetime.now()`
（改善計画T387のコールドスタート対策）は文字どおり「ほぼ即時」発火するため、
TestClientのcontext manager内でイベントループが回っている間に本当に発火しうる
というレース条件だった。対応として`_scheduler.add_job`自体をspyして渡された
引数を直接検証する方式へ変更し（スケジューラが実際に処理する前に横取りする）、
かつ`_refresh_amedas_job`自体もautouseフィクスチャでno-opへ差し替えて実HTTP
アクセスを防いだ（`_scheduler`はモジュールレベルシングルトンのため、同じjob id
の重複`add_job`によるAPSchedulerの`ConflictingIdError`を避ける目的も兼ねて
テストごとに新しい`AsyncIOScheduler`へ差し替えている）。
- 検証: `pytest tests/test_main_lifespan.py -q`を5回連続実行し全件安定してgreen
  （レース条件を含む設計のため念入りに確認）。`pytest tests/test_main.py
  tests/test_main_lifespan.py tests/test_health.py -q`（既存テストとの非干渉確認）・
  `pytest -q -m "not postgis"`（backend全体、1184件）とも成功。
