# T1113. クラウドのセッションを再開したとき、前の回の古いpidファイルに邪魔されずにDBが起動する

状態: 完了

## 背景

T989の後片付け中（2026-09-25）、クラウドのセッションの再開で開始時のフックが db=失敗(49s)。/var/run/docker/containerd/containerd.pid が前の回の古いファイルのまま残り、dockerdがcontainerdは動いていると思い込んで待ち、時間切れで止まった。scripts/remote_dev/lib.sh の rc_ensure_dockerd が起動前にpidファイルを確かめていない。dockerd起動前に /var/run/docker.pid と containerd.pid が指すプロセスが実際にdockerd/containerdでなければファイルを消す。わざと古いpidファイルを置いて起動しDBが上がることを確かめて完了。起票案 proposal-remote-dockerd-stale-pid（担当 D-compose、2026-09-26 承認）。T989の派生

## 実施内容

- `scripts/remote_dev/lib.sh`に`rc_clear_stale_pid`を足し、`rc_ensure_dockerd`がdockerdを起動する前に`/var/run/docker.pid`と
  `/var/run/docker/containerd/containerd.pid`へ当てる。pidの`/proc/<pid>/comm`が`dockerd`・`containerd`でなければ
  （プロセスが無い・別のプロセス・中身が空）ファイルを消す。`docker info`が通る（dockerdが動いている）ときは従来どおり何もしない。
- 前提の確認（公式のソース、moby `docker-v29.3.1`＝この環境のdockerdの版）: `pkg/pidfile.Read`は`process.Alive(pid)`で生死だけを見て、
  Linuxでの`Alive`は`/proc/<pid>`が存在するか。`pidfile.Write`は生きたpidがあると「process with PID N is still running」で起動を拒み、
  `daemon/internal/libcontainerd/supervisor/remote_daemon.go`は生きたpidがあると「containerd is still running」としてcontainerdを
  起動せずに接続を待つ。したがって存在しないpidは元から害が無く、**害になるのは前の回のpidをこの回の別のプロセスが使っている場合**。
  起票時の「db=失敗(49s)」は後者（containerd.pid）と同じ症状。
- `docs/modules/`に`scripts/remote_dev/`を扱う文書は無い。`docs/architecture/setup.md`「クラウドのセッション」は挙動の粒度が
  「dockerdを起こして」までで、今回の変更で嘘になる記述は無いので触らない。

## 検証（このクラウドのセッション、dockerd 29.3.1・containerd v2.2.2）

検証の手順: composeとdockerdを止め（containerdも落ちたことを`pgrep`で確認）、pidファイルを置き、`session_start.sh db`を裏で流して
`bash scripts/remote_dev/wait_db.sh`の結果を見る。「別のプロセス」は`sleep 100000`のpid。

| 置いたpidファイル | 直す前 | 直した後 |
|---|---|---|
| 両方とも存在しないpid（999999・999998） | `DB・Redis: ok(7s)`・終了コード0 | `ok(7s)`・終了コード0（2ファイルとも「古いpidファイルを消す」） |
| docker.pidだけ別のプロセス | `DB・Redis: 失敗(33s)`・終了コード1。dockerdログ「failed to start daemon, ensure docker is not running or delete /var/run/docker.pid: process with PID 3687 is still running」 | `ok(7s)`・終了コード0 |
| containerd.pidだけ別のプロセス | `DB・Redis: 失敗(47s)`・終了コード1。dockerdログ「containerd is still running pid=5305」→15秒後「failed to start containerd: timeout waiting for containerd to start」 | `ok(8s)`・終了コード0 |
| 両方とも別のプロセス | — | `ok(7s)`・終了コード0 |

- 本物のdockerd・containerdが動いている状態で`rc_clear_stale_pid`を2ファイルへ直接呼ぶ→ログ出力なし・2ファイルとも残る。
  postgres・redisはhealthyのまま。
- 手元（`CLAUDE_CODE_REMOTE`が空・`false`・`1`）: 両方のpidファイルに別のプロセスのpidを置いた状態で`session_start.sh`（引数なし・`setup`・`db`）と
  `wait_db.sh`を流す→すべて出力なし・終了コード0、pidファイルはそのまま、dockerdは起動しない。
- `bash -n scripts/remote_dev/lib.sh`→通過。
