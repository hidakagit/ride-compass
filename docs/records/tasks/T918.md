# T918. 路面タイルの単位を、区間が読めるズームでは区間（edge）にする

状態: 着手中（段階1〜5完了、実機確認待ち）
規模: L

## 背景

[T917](T917.md)の計測で、gzip後の費用と区間単位の情報量が、ズームで逆向きに効くことが
分かった。境界をz14に置く（z14以上=区間、z13以下=way）。

同じ「区間ごとの値」をルート前はway近似・確定後は区間実値で作り分けている状態を畳む。

## 段階

- [x] 1. タイルの単位をズームで切り替える（`feature_key`追加・世代は焼き込みSQLから自動で上がる）
- [x] 2. 値の配信を`feature_key`鍵へ（低ズームはそのwayの最急へ差し替え）
- [x] 3. フロントの`promoteId`切り替え
- [x] 4. way単位で意味を持つ材料の扱いを決める
- [x] 5. 密度材料（事故・交差点・POI）を区間単位の真値へ切り替える

**段階1だけでは地図の見た目は変わらない**。フロントはまだ`osm_way_id`を`promoteId`に
しており、`feature_key`は焼かれるだけである。段階1を先に本番へ入れて実機で確かめられる。

## 段階1で見つけたこと（実DBを立てて初めて分かった）

この作業のためにローカルへPostgreSQL+PostGISを立てた。**実バグを2つ捕まえた**——
どちらも実DBが無ければpushまで気づけなかった。

**① z14以上のタイルテストが、1件も出ない状態になっていた。** 既存のタイルテストは生のwayしか
作っておらず、z14の単位が`road_edges`へ変わった瞬間に空タイルを見ていた。テスト側で
edgeも作る（`_save_ways_and_edges`）形へ直した。

**② 重複排除の鍵にwayが無く、別々の道が1本へ潰れていた。** 両端ノードの組だけを鍵にすると、
同じノード対を共有する別のway（並走する自転車道等）まで1本になる。鍵を
`(osm_way_id, LEAST(from,to), GREATEST(from,to))`へ直した。`bench_t917_edge_tile.py`も
同じ鍵へ揃えたため、**T917で測った重複排除後のフィーチャー数はわずかに少なく出ている**
（実データでの差は未計測）。

## 段階2へ持ち越す制約

**値の配信側が別の代表を選ぶと、鍵が噛み合わず色が付かない。** 重複排除で残るのは
edge_id昇順の先頭（`way-N-segM-bwd`が`-fwd`より先に来る）で、タイルと配信で同じ
`DISTINCT ON`を使う必要がある。

## 区間を持たないwayの扱い（段階1に含めた）

**edgeを1本も持たないwayは、そのままだとズームを上げたときだけ地図から消える。** 座標が
判明しているノードが2点未満のway等（`domain/graph.py: build_road_graph`）。引いた表示に
出ている道が拡大すると無くなる見え方は、データが無いことよりも壊れて見えるため、区間単位の
ズームでもway丸ごとで出すようにした（落とすとテストが1件落ちる）。

これは「除外を足す緩和」ではなく取りこぼしを塞ぐものだが、**実データでの件数は未計測**。
`benchmarks/bench_t917_edge_tile.py`がタイルごとのway総数・edge無しの件数・割合を出すので、
実DBで回して記録すること。件数が多ければ、そもそもなぜedgeが作られないのかを別途見る。


## 段階2＋3（1コミットにした理由）

段階2だけをmasterへ載せると、**backendが区間鍵を返すのにフロントは`osm_way_id`を
`promoteId`にしたまま**になり、鍵がどの地物とも一致せず色が一切付かない状態が
（エラーも警告も出ないまま）master上に存在することになる。段階2と3は分けずに1つの
コミットにした。

### 段階2で見つけた実バグ: 代表の向きに標高属性が無いと勾配が黙って落ちる

標高属性（`elevation_attributes`）は**向きごとのedge行**に付き、探索が通った向きだけ
埋まることがある。一方、区間の代表（`_TILE_FEATURE_SOURCE_SQL`の`DISTINCT ON`）は
edge_id昇順で決まり、どちらの向きが埋まっているかとは無関係に選ばれる。代表の行だけを
JOINしていると、逆向きにしか属性が無い区間は結果から静かに消える。

JOINを「その区間の**両方向の行**」（区間単位は`node_lo`/`node_hi`、way単位は
`osm_way_id`）へ直した。符号と向きが同時に反転して打ち消し合うため、どちらを拾っても
`effective_gradient`の結果は同じである（`domain/gradient.py`のモジュールdocstring）。

### 効いていることの確認

- 逆向きにだけ属性を置いたテストを追加し、**旧JOINへ戻すと落ちる**ことを確認
- `promoteId`を`osm_way_id`へ戻すと、新設したフロントのテストが落ちることを確認
- 鍵を`Number()`で数値化するとedge_idがNaNへ潰れる件は、鍵が文字列のまま保たれることを
  見るテストで固定した
- `pytest -m postgis`＝281件passed／6件failed（6件は変更前と同じ`test_precompute_way_landcover.py`。
  **後に`pyproj`を入れて全pass（289件）を確認した**。[T914](T914.md)「この環境の失敗の正体」参照）
- `pytest -m "not postgis"`＝2,038件passed／5件failed（同じく変更前から）
- `ruff check app scripts benchmarks tests`＝All checks passed
- `npx vitest run`＝145ファイル1,426件passed、`tsc --noEmit`＝`src/app/layout.tsx`の
  `LayoutProps`未定義1件のみ（変更前から同じ。stashして確認済み）

## 段階4の結論: 材料を「区間へ複製してよいか」で分ける

- **OSMのタグ由来**（`surface`・`highway`・`smoothness`・`tunnel`・`bridge`・`oneway`・
  `maxspeed_kmh`・`lanes_count`・`lit`・`designation`・`name`/`ref`等）は、way全体に
  成り立つ値である。区間へ複製するのが正しい。
- **事前集計した密度・割合**（`accident_per_km`・`intersection_per_km`・`poi_*_per_km`・
  `*_pct`）はway全体の平均で、区間ごとの差が均されている。

タイルのフィーチャーを集計して読む箇所は無い（フロントは`querySourceFeatures`を空判定に、
`queryRenderedFeatures`をクリック判定にしか使っておらず、どちらも単位に依存しない）ため、
後者を複製しても壊れはしない。

### 一度「way平均のままでよい」と書いて、撤回した

最初はここで打ち切り、密度も割合もまとめて別タスクへ回した。**判断の根拠にしたのは
「edge単位の集計はまだ無い」という思い込みで、実際にはコードのすぐ隣に答えが書いてあった**
（`road_graph_repository.py`の冒頭コメント: `edge_attribute_counts`は`road_edges`＝
ルート生成済みエリアしかカバーしないため地図表示の母集団にできない、dev実測3.6%）。

その3.6%を読んだうえで考え直すと、**この制約はz14以上には当てはまらない**。区間単位の
フィーチャーを出す枝の母集団は`road_edges`そのもので、`edge_attribute_counts`が覆う
母集団と一致する。3.6%が効くのは「地図全体の母集団にできるか」という別の問い（z13以下・
区間を持たないway）である。よって密度3種は**今すぐ区間の真値で焼ける**——これを
way平均のままにするのは、まさにこのタスクが潰そうとしている「backendは区間単位で持って
いるのに表示の直前にway単位へ落としている」そのものだった。段階5として実装した。

土地被覆だけは区間単位の集計そのものが存在しない（`way_landcover`のみ）ため、
[T919](T919.md)として残した。

## 段階5: 密度を区間の実測から出す

`_density_column_sql`が件数と長さを**必ず同じ側から**取る式を組み立てる。区間単位の
フィーチャーは`edge_attribute_counts`の件数をその区間の長さ（`road_edges.distance_m`）で、
way丸ごとのフィーチャーは`way_attribute_counts`の件数をway全体の長さで割る。片方だけを
区間にすると、区間の件数をway全体の長さで割った無意味な値になる。

**集計行がまだ無い区間はway集計へ落とす。** `precompute_edge_attribute_counts`は
`presplit_road_graph`が新しく作った区間の行をまだ持たないことがある。区間側の欠損を
そのまま出すと、バッチの実行漏れが「密度が無い道」として地図へ出る。最悪でも従来の
見え方（way平均）へ落ちるようにした。

### 効いていることの確認

- 同じway内の2区間へ事故を偏らせたテストを追加し、**way平均の式へ戻すと落ちる**ことを確認
- 落とし込み（ELSE側）を外すと、集計行の無い区間のテストが落ちることを確認

### 本番での前提

`precompute_edge_attribute_counts`が未実行・古いぶんはway平均のまま出る（壊れない）。
区間ごとの値を実際に見るには、`presplit_road_graph`→`precompute_road_node_degrees`→
`precompute_edge_attribute_counts`の順で本番バッチを流す必要がある。
