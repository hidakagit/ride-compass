# T1049. 司令塔（複数エージェントの並行実行）の運用を規約にし、回すたびに実測で改善する

状態: 未完了（2026-09-23起票）

## 背景

2026-09-23、周期レビュー第12回の指摘と台帳の残りを、司令塔が十数本のエージェント（ローカル・リモート）へ振り分けて並行で潰した。振り分け・ロック・push直列化・リモート用ルール・完了時の監査などのノウハウがセッションの一時フォルダと会話にしか無い。ユーザー指示「司令塔としての役割や管理ノウハウもルール化」「コマンドは魅力的だけど、プロセス改善していきたい。標準化できない？」。

## 方針（ユーザー承認 2026-09-23）

コマンドではなく**規約を正本にし、回すたびに実測で直す**。

- 正本: `docs/conventions/orchestration.md`（規約＝仕事のやり方の取り決め。既存の置き場）。
  エージェントに渡す共通ルールも同じ文書の節にし、指示文へは貼らず「読め」と書く
  （リモートもリポジトリを読める）。
- 道具: `scripts/lockrun.py`（ロックをgitの共通ディレクトリに置き全worktreeで共有。
  待ち・保持・終了コードを`log.jsonl`へ記録し`--report`で集計）。採番は`scripts/new_task.py`（T1047）。
- 入口: `.claude/commands/orchestrate.md`は規約を読ませるだけの呼び出し口。CLAUDE.mdは1行のポインタ。
- 改善の回し方: 回ごとに実測値を記録し、振り返りの変更案は数字の裏付けがあるものだけ当てる。

途中のユーザー指示で「ユーザーが手動で進めているタスク」節を足した（手動中の番号を受け取り、
影響のあるタスクを候補から外す。稼働中のエージェントと重なるならユーザーへ確かめる）。

## 段階2（2026-09-23）: 管理の欠如への是正

**原因の特定（ユーザー指摘）**: 表層の問題（リモート指定が実際は手元で動いていた・長時間の
停滞に気づかなかった）の下に、**確認と管理の機構が無かった**ことがある。司令塔は振り出しを
繰り返すだけで、確認は完了通知頼み（止まっているものは何も知らせてこない）、同時実行の上限が
無く、前提（リモートで動くか）を1本で確かめずに広げ、司令塔自身が実装に回っていた。

実測: リモート指定の8本はすべて手元に作業ツリーを作り（種別`local_agent`）、手元で15本が
同時に動いていた。軽いgitコマンドが60秒で時間切れ、`npm ci`に32〜39分、ロック待ち最大19分。
軽いSのタスクしか進まなかった。

**是正**: 同時実行を3本へ減らした（11本へ停止指示、応答の無い3本は強制停止）。規約に、
管理のループ（時間で回す確認）・上限と門・状態の表・異常の是正・止める手段の段階（停止ファイル
を含む）・監査をmasterへの門にする形（エージェントは作業ブランチへpushし、司令塔が監査後に
masterへ進める。ユーザー承認）を書いた。停止ファイルを`lockrun.py`とpre-pushに実装した。
定期確認はCronCreateで20分ごと。

## 段階3（2026-09-23）: 管理の核の機械化

ユーザー指示「根本対策の機械化を優先」。規約に書いた上限・門・状態の表・時間で回す確認・監査の
うち、機械的に強制されていたのは停止ファイルとロックだけで、残りは司令塔の手続きだった。

**作ったもの**（管理の核だけ。依頼で足す機能は別モジュール——下の「範囲の経緯」）:

- `scripts/orchestration/core.py`（入口は`scripts/orchestrate.py`）: 状態の表の読み書き（原子的な
  置き換え。司令塔が手で書いていた実物の形をそのまま読む）・`gate`・`check`（と`--if-due`）・
  `status`（checkが使う事実の一覧）・`audit`の機械項目とpre-pushと同じ静的検査・`board`
  （set/add/run/show/claim、司令塔のキュー`todo`、振り出し待ち`dispatch`、監査済み未push`unpushed`）。
- 確認のフック: `.claude/settings.json`のPostToolUse → `scripts/orchestration/hook.sh`（シェルの
  組み込みだけで判定し、司令塔のセッションで確認間隔を過ぎたときだけpythonを起こす）。
  PostToolUseを選んだ根拠は公式文書（https://code.claude.com/docs/en/hooks）: サブエージェントの
  道具の呼び出しでも発火し入力に`agent_id`が付く／`hookSpecificOutput.additionalContext`で文脈へ
  返せる（v2.1.238以上。手元は2.1.257）／UserPromptSubmitは利用者の入力時にしか発火しない。
  司令塔のセッションの特定は、`board claim`の直後のフックが入力の`session_id`を記録する形にした
  （道具の側からsession_idを知る公式の手段が無いため）。
- 規約の訂正: `isolation: "remote"`の誤り（公式のfrontmatterは`worktree`のみ。サブエージェントは
  常に手元、クラウドはクラウドセッションとして別扱い）、司令塔の作業の優先順位と司令塔のキュー、
  タスクの分割、エージェントはpushせずshaを報告し司令塔が監査済みを溜めて1回でpushする形、
  監査の範囲は合流点から、見込み超過は最初の振り出しからの通算で規模の予算と比べる。

**検証**（試験は実物の表のコピーと一時リポジトリで。実物の表は読むだけで、前後のsha1が一致）:

**範囲の経緯**: 振り出し後に、判断待ち・記録の保留の収集・確認依頼の規約の1本化・キューの
タスク単位化・前提（prereqs）・優先度が継ぎ足され、範囲が起動時の倍以上になった。司令塔の指示で
核と依頼側を分け、依頼側のうち実装済みのもの（判断待ち）は別コミット・別モジュールにし、

規約「タスクの分割」の根拠として引いた。
