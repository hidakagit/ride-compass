# T1197. backend の中に同じ事実を複数のファイルが持っている（タイルの画素数256・方位の表示名・設定の既定値の写し）

状態: 完了（2026-09-27起票・2026-09-27完了）

## 背景

T1170（どこまで源泉に従わせて導出するかの基準）の段階Bで、同じ事実の写しの候補を機械で数えた。多くは画面が持つ写しで
T1140 の範囲だが、次の少数はどのタスクにも入っていない。

- タイルの画素数 256 を backend の3ファイルがそれぞれ持つ
- 8方位と16方位の表示名の並びが2か所にある
- 設定（config.py）の既定値と同じ値を、配備の設定ファイルにも書いている4項目（基礎地図の公開URL・CORSの許可等）
- backend が持っているが画面へ配っていない語彙のうち T1140 に挙がっていないもの（形の種類・方位の問い合わせの項目名）

候補の出し方・一次判定は [T1170](T1170.md) の表にある。

やること: 候補を1件ずつ「同じ事実か」（設計原則 構造仕様17）で判定し、同じ事実なら1か所へ寄せて他をそこから導く。
目的が違うならその理由を記録する。規模: S（根拠: 変わるのは候補のファイル約7本の見込み）。

## 候補が今も成り立つか（origin/master 86253c6e 時点）

T1170の表の数え方のうち該当する行を、候補ごとにgrepで引き直した。4つとも今も成り立っていた。ただし「形の種類」は
T1170の段階Bの後に画面の側が契約の型から引く形になっており、写しではなくなっていた（下の判定）。

- 画素数: `backend/app`の`\b256\b` → タイルの画素数は`io_lulc_tile.py: _TILE_SIZE`・`gsi_dem_tile.py: _DEM_TILE_SIZE`・
  `landcover_raster.py: TILE_SIZE`の3つ。残りはMVTのbuffer（`ST_AsMVTGeom`の256、extentの単位で別の事実）・
  TTLCacheの上限・uint8の値域・SHA-256。
- 方位の表示名: `"北東"`を含む並びは`domain/geo.py: COMPASS_LABELS`と`domain/jma_amedas.py: _SIXTEEN_POINT_LABELS`の2つ。
- 設定: `CORS_ALLOWED_ORIGINS|DATABASE_URL|BASEMAP_PUBLIC_BASE_URL|DEBUG_MODE`に`:`か`=`が続く行 →
  `backend/.env.example`に4項目とも既定値と同じ値、`.env.example`に`DEBUG_MODE=false`、`docker-compose.yml`にCORS・基礎地図
  （既定値と同じ値）とDB（composeのホスト名で違う値）。ワークフローはCIのDB（テスト用の別の値）と配備のCORSの追記
  （本番の許可元で別の値）だけ。
- 配っていない語彙: frontendの`breakpoint_linear`と、`bearing_deg`（`services/regionApi.ts`で手で書いた問い合わせの項目名）。

## 判定と処置

| 候補 | 同じ事実か | 処置 |
|---|---|---|
| 土地被覆の取込の画素数（`io_lulc_tile.py`）と描画の画素数（`landcover_raster.py`） | 同じ。取込は`tile_classes`が返す配列を書くので、描画の一辺を変えたら取込の幅も必ず変わるべき | 取込の定数を消し、返った配列の形から幅・高さを読む |
| 標高タイルの画素数（`gsi_dem_tile.py`） | 目的が違う。地理院の配信仕様で、自前で描くタイルの一辺を変えても配信物は256のまま | 独立に持ち、理由をコメントとモジュール文書に書いた |
| 8方位と16方位の呼び名 | 同じ。どちらも利用者へ出す方位の名前で、片方だけ直すと同じ向きを画面の場所によって違う名前で出す。16方位の側のコメントは「JMA特有の割当のため別に持つ」としていたが、特有なのは番号→向きの割当（`code % 16`）だけで、並び自体は北を0とする普通の16方位だった | 16方位の並びを`domain/geo.py: SIXTEEN_POINT_LABELS`に置き、8方位はその1つおき、アメダスはそれを引く。JMAの番号の範囲（1〜16）と角度（22.5度刻み）はJMAの仕様なのでアメダス側に残した |
| `backend/.env.example`・`.env.example`の既定値と同じ値 | 同じ（既定値そのものの写し）。写した値は`.env`へコピーされた時点で固定され、既定値を直しても手元では古い値が効き続ける | 値を消し、項目の説明と上書きの仕方だけを残した（DEBUG_MODEは有効にする行`# DEBUG_MODE=true`として示す） |
| `config.py`の中のCORSの既定と基礎地図の既定 | 同じ（手元で`next dev`を起動したときのfrontendのオリジン） | 1つの宣言`_LOCAL_FRONTEND_ORIGIN`から両方を作る |
| `docker-compose.yml`のCORS・基礎地図 | 目的が違う。composeのfrontendの公開先（`ports:`）に従う値で、config.pyの既定値を変えてもcomposeのfrontendの位置は変わらない | 残し、理由をcomposeのコメントとモジュール文書に書いた |
| 形の種類`breakpoint_linear`（画面） | 同じ事実だが、既に導出済み。`features/admin/AxisStudio/axisDraft.ts`の`BackendShapeKind`が生成物の型（`BreakpointLinearShape["kind"]`）から引かれ、画面の文字列はその型で検査される——backendが名前を変えると型検査で落ちる。`recipe_then_breakpoint_linear`は編集画面だけの区別で目的が違う（同ファイルのコメントに理由がある） | 変えない |
| 問い合わせの項目名`bearing_deg`（画面） | 同じ。backendの宣言した項目名で、名前を変えたら画面も必ず変わるべき。FastAPIは宣言に無い問い合わせの項目を既定では黙って無視する（公式: https://fastapi.tiangolo.com/tutorial/query-param-models/ の「Forbid Extra Query Parameters」）ので、手で書いた名前が古くなっても誰も落ちない | 下のとおり |

問い合わせの項目名は、症状の出た`bearing_deg`1件ではなく「frontendがbackendの問い合わせの項目名を手で書いている」
性質で母集団を取った。`frontend/src`の非テストで`URLSearchParams`・`searchParams.set`・`?名前=`・`` ?${ ``を引くと、
backendの宣言した項目を手で書いていたのは`services/weatherApi.ts`（地点の取得5口の`latitude`・`longitude`、風の詳細格子の
`min_lon`等）と`services/regionApi.ts`（`bearing_deg`・`at`・`speed_kmh`）。`features/admin/adminApi.ts`のログの取得は既に
生成物の型から引いていた。タイルの`?v=`・地図のスタイルの`?t=`はbackendが宣言していないキャッシュの鍵、
`jmaDelivery.ts`の`?id=`は外部の配信元の項目で、どれも別の事実。

処置: `lib/apiPath.ts`に`apiQuery`（項目の型をそのパスのGETの宣言から引き、`?`付きの文字列を作る）を足し、上の3ファイルの
問い合わせを全部これで作る。ログの取得の自前の組み立てもこれへ寄せ、問い合わせを作る方法を1つにした。

## 本番への影響

- 本番のイメージに入る変更は`backend/app`の`config.py`・`domain/geo.py`・`domain/jma_amedas.py`・取込のアダプタ2本と
  `landcover_raster.py`のコメント。既定値・方位の呼び名・取込の画素数はどれも値が変わらない
  （生成物`frontend/src/types/generated/`は再生成して差分なし）。本番の`.env`・`deploy-backend.yml`は触っていない。
- `backend/.env.example`は`scripts/deploy_backend_gate.py: NOT_DEPLOYED`に入っており、本番の配備を起こさない。
  `.env.example`・`docker-compose.yml`は手元のcompose専用で、本番の配備（`deploy-backend.yml`はcomposeを使わない）に効かない。
- 既に手元にある`.env`（雛形からコピー済みのもの）は変わらない。雛形の値を消しても、書いていた値は既定値と同じなので挙動は同じ。
