# T1209. DB の制約と検証済みの型が保証している前提を app が守り直している箇所を消し、欠けている制約（語彙の CHECK・FK・UNIQUE）を宣言から張る

状態: 未完了（2026-09-27起票）

## 背景

周期レビュー第14回（2026-09-27）の起票案（ダッシュボード proposal-guarantees-not-reabsorbed、承認済み）。

規模L（根拠: 本番DBに制約を張る。段に切る）

■ 背景
性質: 死んだガード／DBが持つべき制約の欠け／嘘の型と死んだガード（再発: 第13回 T1145 は画面側だけ。設計原則 構造仕様15・16）。
- DB が保証済みなのに守り直す: CHECK distance_m>0 を材料の式7本が吸収（material_catalog.py:795,816・material_sql.py:123）、nullable=False 列への COALESCE（road_graph_repository.py:673-674）、NULLIF（:190,:354）、IS NOT NULL（:370）、`or {}`（:923・db_status.py:130-131）、FK が保証する `is not None`（derived_data_freshness.py:207）、max(…,0)（material_coverage.py:105）、表が無いときの分岐（tuning_overrides.py:92）。これを本番で作れない行（tags=None・length_m=None）のテストが支えている（test_road_graph_repository_contracts.py:310-339）。
- 欠けている制約: road_edges→way_materials の FK（吸収が3か所）、batch が SQL で直接書く語彙の列（way_materials.direction・node_materials.kind・source_runs.status）の CHECK（domain の検査を一度も通らない）、derived_data_meta の id=1、axis_definitions.sort_order の UNIQUE（Neumaier 加算の順に意味がある）。設計原則15の実例（design-principles.md:164「migration 0046で是正」）は今のスキーマで成り立たない。
- 検証済みの要求でも Optional のまま残り、本番から届かない raise が6件（gradient_way_service:63・wind_way_service:56,58・routes.py:218,374・axis_admin.py:231）。

■ やること
段1（コードだけ）: 型の側——要求を種類ごとの判別付きの型に検証してから渡し、専用配信の問い合わせは入力が揃ったことを型で表す1つにして422の扉を1つにし、死んだ raise を消す。
段2（本番DB）: 語彙の CHECK を material_value_checks と同じく domain の宣言から生成して張る。way_materials の行を topology の段で作り、road_edges.osm_way_id→way_materials の FK を張る。sort_order に UNIQUE。
段3: 守り直しの分岐と、それを支えるテストの行を同じコミットで消す。設計原則15の実例を今成り立つものへ差し替える。
本番DBに CHECK が実際に張られているかは段2の最初に確かめる（未確認）。

■ 見送るもの
生データ→派生の FK（取込がパーティションを TRUNCATE で入れ替えるため張れない。再評価: 取込を差分方式へ変えるとき）。highway の不在の吸収は取込が保証しているので、「取込で守らせたうえで張る」かは段2で問う。

■ なぜ既存のタスクに入らないか
T970 はユーザーの手動のタスクで、制約の吸収の撤去は含まない。
