# T955: 材料の冷パスが160秒かかり、バッチのたびに最初の利用者が待たされる

状態: 未完了

着手（2026-09-19起票）

## 背景

本番でルート生成に174秒かかった（2026-09-19 17:48、`req:b7f19819cf4d`）。

```
generate(destination) prepare_ms=165428 select_ms=6659 evaluate_ms=470 total_ms=173898
_build_search_graph edges=542999 materials_ms=160469 lazy_graph_cached=False
  missing_axis_edges=542999 missing_axis_distance_ratio=1.000
```

**探索も評価も速い**。2分半後の同条件は`materials_ms=964`・`total_ms=6336`で、
冷えているかどうかで**174秒 ↔ 6.3秒**。

`docs/records/tasks/T747.md`が記録する材料の冷パスは29〜45秒規模で、いまは108〜160秒。
世代を上げるのは日常運用（バッチを流すたびに起きる）ため、**バッチ後に最初にその範囲を
見た利用者が3分待つ**。

**周回でも同じ**。材料は探索方式より手前の段階で、周回30kmの生成も116.6秒だった
（`via-node候補を打ち切りました`のWARNINGは目的地ルート特有だが、遅さとは無関係）。

**SQLが約4割、区間ごとのPythonが約5割。** numpyのベクトル計算はどこにも現れない。

### Dは全部が区間ごとのPython

`build_static_edge_score_matrix`をcProfileで見ると（計測負荷込みで4.77秒、比率で読む）:

- `dict.get`が**329万回**（区間あたり78回）。extractorが`elevation_attributes[edge_id]`等を
  区間ごとに引いている
- `to_legacy_dicts`の中で`ElevationAttribute`（Pydantic）を**区間数ぶん作り直している**
  ——列指向の表を、区間ごとの辞書へ戻すために
- `bicycle_infra_flags`が区間あたり5回。同じwayのタグ文字列を毎回parseし直している

### 表現が4回変わる

```
SQLの行 → EdgeMaterialBundle（Pydantic） → EdgeMaterialTable（numpy列）
        → to_legacy_dicts（Pydanticへ戻す） → 抽出ループ → numpy配列 → 軸の式
```

列指向の表を作った直後に、区間ごとの辞書へ戻している。

## 「評価に必要な列を1行に持つテーブル」があったら

同じ結果を一時テーブルへ落とし（読み出し用テーブルの代役）、本番で比べた。

| | 所要 |
|---|---|
| 現行（`road_edges`へ属性テーブル群をLEFT JOIN＋指定路線は相関EXISTS） | 2,052〜2,146ms |
| 1テーブルをbboxで走査 | 749〜848ms |
| 1テーブルから列ごとに`array_agg` | 915〜929ms |
| 現行のJOINのまま`array_agg` | 2,208ms |

**JOINをやめるだけでDB側が2.5倍**（約1,250ms/タイル）。`array_agg`はDB側では効かず
（JOINのまま掛けても変わらない）、効くのは受け取るPython側である（[T956](T956.md)）。

代役テーブルは1タイル（42,134区間）で19MB。全区間5,065,850に対して約2.3GBの見当。

## 最初の見立てが外れた理由

当初「行→bundleの構築が18.8秒で主犯」と書き、行から直接列を組む実装を入れたが、
本番では24,465ms→25,912msで**まったく速くならなかった**（実装は破棄済み）。

18.8秒は**開発機のPythonで測った値**で、本番の同じ処理は1,432ms——**13倍違う**。
開発機で部品を測り、本番の全体へ一般化したのが誤りだった
（CLAUDE.md「性能は利用者から見た単位で測る」、memory`feedback-perf-measure-on-prod-not-dev-db`）。

## 材料の導出は、SQLとPythonに二重実装されている

地図タイル（`_ROAD_SURFACE_TILE_MVT_SQL`）は探索と**同じテーブル群**を引き、同じ材料を
**SQLの中で**導出している。探索は同じ導出をPythonの区間ごとのループでやっている。
`osm_way_tag_sql.py`のdocstring自身が「Python版extractorとは別に、SQL側で同じOSMタグ
分類ロジックを必要とする」と書いている。

本番の1タイル（42,134区間）で、両方が実装する材料を突き合わせた。

| | 結果 |
|---|---|
| `surface_good` `surface` `highway` `smoothness` `has_tunnel` `bridge` `maxspeed_kmh` `lanes_count` `motor_vehicle_no` `lit` `highway_is_cycleway` `cycleway_has_track` `cycleway_has_lane` `cycleway_has_shared` `shared_pedestrian_path` `tracktype` | 不一致**0件** |
| `is_emergency_transport` `is_critical_logistics` | Python側に実装が無い（`extractor=None`）。参照する軸も無い |

**SQL側はPython側の超集合で、重なる部分は完全に一致する。** SQLにできない材料は
`wind_drag_ratio`だけ（リクエスト時の天候・方位・速度から決まる）。

## 導出をSQLへ寄せても、SQLは重くならない

| | 所要 |
|---|---|
| 生の列を行で返す（現行） | 1,403ms |
| 導出込みを行で返す | 1,483ms（+80ms） |
| 導出込み＋`array_agg` | 1,436ms（−47ms） |

一方、材料が列で届いたときに残る「軸の式だけ」は**全13軸で22.9ms**（現行Dは1,150〜1,900ms）。
**評価の本体は23msで、残りは全部「材料を区間ごとのPythonで作り直す」費用だった。**

## 対応方針

段階Aだけをこのタスクの範囲とし、段階Bは条件付きで残す。**両者は性質が違う**——Aは
既存の仕組みを効率化するが、Bは新しい派生データを1つ増やす（ユーザー判断）。

### 段階A（[T956](T956.md)）: 導出をSQLへ寄せ、列で受ける

`EdgeMaterialBundle`・`from_bundles`・`to_legacy_dicts`・`MaterialExtractionContext`・
区間ごとの抽出ループが消え、表現の変換が4回から1回になる。**増える永続状態は無い。**
見込み: 1タイル7,830ms → 約3,100ms。

前提として[T960](T960.md)（SQL側の導出に期待値テストを付ける）を先に済ませる。
`tests/test_material_catalog.py`の期待値はPython側にしか当たっておらず、**Pythonの
extractorを消すなら、その期待値がSQL側に当たっている必要がある**。

### 段階B（[T958](T958.md)）: 導出結果をテーブルへ

さらに約800ms/タイル。ただし新しい派生テーブルの鮮度・世代の判定が増える。
**段階Aの後に残りを測ってから判断する。**
