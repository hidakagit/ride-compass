# T381. 地図オーバーレイの▲▼/◀▶ページ送りボタンに長押し連続送りを追加し、連打による誤タップ地図ズームを軽減 規模S（2026-08-27完了）

状態: 完了

- 背景: ユーザー指摘「押し続けるとそのまま送っていってほしい」「誤タップで背後の
  地図を拡大してしまうことがある」。T374〜T380の▲▼/◀▶（`.pageButton`）はワンタップ
  =1ステップのみで、複数ステップ送るには小さい丸ボタン（1.6rem四方）へ素早く連打する
  必要があった。連打中はhasMore/hasLessの変化に応じてボタン自体の出現・消滅が起き
  位置がわずかに動くため、タップが外れて地図キャンバス側へ着弾しやすく、それが
  2連続になると地図側のダブルタップズームとして誤って解釈されていたと考えられる。
- 対応方針: 「押しっぱなしで連続送り」を用意すれば連打そのものが不要になり、地図への
  誤タップの機会自体を減らせる。`MapOverlayControls.tsx`に`useHoldRepeat(action,
  canRepeat, delayMs=450, intervalMs=120)`フックを新設した。
  - クリック（マウス・タッチ・キーボードのEnter/Spaceいずれも最終的にonClickへ
    集約される）を「1回押した分」の唯一の実行経路として維持しつつ、pointerdown/up
    だけで「長押し中の追加リピート」を制御する。素早いワンタップはpointerdown後すぐ
    pointerupするためdelayMs待ちのタイマーが発火する前に解除され、onClickの1回だけが
    実行される。長押し時だけタイマー発火後にintervalMsごとの追加ステップが走る。
  - 長押し後に指を離すと通常どおりclickイベントも発火するが、直前にリピートが一度でも
    発火していれば「既に十分送った後の余計な1回」になるため`heldRef`で判定して無視する。
  - `canRepeat`（呼び出し側のhasMore/hasLess）は毎レンダー最新値へ同期し、タイマー
    発火のたびに確認する。ページ送りが上限/下限に達すると呼び出し元のJSXがボタン自体を
    描画しなくなり（押している最中でも起こりうる）、その瞬間pointerup/leaveがこの要素へ
    届かない可能性があるため、`canRepeat`がfalseになった時点でタイマー自身を止めて
    放置されたintervalが動き続けないようにする。
  - refの書き込みはレンダー中に行えない（react-hooks/refsルール、React 19）ため、
    action/canRepeatの同期は`useEffect`（依存配列なし、毎レンダー後）で行う。
  - 縦送り▲▼（chipRowBackward/Forward）・横送り◀▶（estimatedRowBackward/Forward）の
    計4ボタンすべてに同じフックを適用した。

- **フォローアップ（同日、ユーザー指摘「長押しすると、コピーを効かれるのが微妙に嫌」）**:
  長押し連続送りを追加したことで▲▼◀▶（中身は▲▼◀▶の文字グリフ）を長押しする機会が
  増え、iOS Safari等の「長押しでテキスト選択・コピー/共有メニューを出す」既定の
  コールアウトが誘発されるようになっていた。`touch-action: none`はスクロール/ズーム等の
  ジェスチャーだけを制御する仕様でこの種のコールアウトは対象外のため、`.pageButton`へ
  `user-select: none`（`DynamicLayerTimeSlider.module.css`のドラッグハンドルと同じ
  定番パターン）と`-webkit-touch-callout: none`（iOS Safari固有の長押しコールアウト
  自体を止める）を追加して抑止した。Playwrightで`getComputedStyle`により
  `user-select: none`が適用されていることを確認（`-webkit-touch-callout`はiOS
  Safari固有の非標準プロパティのためChromiumのCSSOMには現れず`undefined`になるが、
  スタイルシート上の宣言自体は存在しWebKit系ブラウザでは効く）。tsc/eslint/vitest
  （既存38件）green。
- **フォローアップ2（同日、ユーザー指摘「▼▶アイコンを他アイコンの幅や高さまでもう少し
  広げると操作性が増す」）**: `.pageButton`は1.6rem四方（実測約25.6px）と、他のアイコン
  チップ（`.iconChip`、実測幅約51px・高さ約43px）に比べて明らかに小さく、長押し連続送り
  （本タスク）導入でタップの正確さの重要性が増したこととも合わせてタップの当たり判定が
  狭すぎた。丸ボタンの見た目を保ったまま幅・高さを2.6rem四方（実測約41.6px、他アイコンの
  高さに近い値）へ拡大し、円の中の矢印グリフが小さく見えすぎないようfont-sizeも1.1rem
  （既定は無指定＝継承のみ）へ引き上げた。Playwrightで実測: 拡大前25.59×25.59px→
  拡大後41.59×41.59px（`.iconChip`の高さ42.66pxとほぼ一致）。スクリーンショットで
  ズームコントロール等との重なりが無いことも確認。tsc/eslint/vitest（既存38件）green。
- **フォローアップ3（同日、ユーザー指摘の変遷）**: 「▼アイコンは横幅だけ長め、▶アイコンは
  縦幅だけ長めにできないか、なるべくスペースを有効利用したい」→「丸型アイコンだと
  スペースをその分取るので角型で」。フォローアップ2の「固定サイズの正方形を拡大する」
  方式（丸ボタンのまま）をやめ、`align-self: stretch`で既に確保されている周囲の余白を
  そのまま埋める方式に変更した。stretchは常に「今いるflexコンテナのクロス軸」を埋めるため、
  縦送り（▲▼、`.wrapper`直下＝列flexの子、クロス軸=横方向）では横に長い帯、横送り
  （◀▶、`.headerLegendRow`直下＝行flexの子、クロス軸=縦方向）では縦に長い帯に自動でなる
  （T380で問題になった`align-self: center`のような軸ごとの意味の反転が起きない、
  常に「今いる場所の余白を埋める」という同じ意味になるため）。埋める側の寸法
  （縦送りなら横幅、横送りなら縦幅）はコンテナの実際の幅・高さに追従するため、推定
  グループ展開時の`.wrapper`幅変化にも自動で対応する。角型（`border-radius:
  var(--radius-md)`、`.iconChip`等と同じ丸め方）にすることで丸ボタンの四隅の無駄な
  余白も無くした。短辺側は`.pageButton`が高さ1.6rem固定・幅auto（stretchで埋まる）、
  `.pageButtonHorizontal`がその逆（幅1.6rem固定・高さauto）というシンプルな上書きで
  表現している。Playwrightで実測: ▼（縦送り、`.wrapper`の全幅を検証用に縮めた
  chipRowViewportで再現）はwidth=318px（`.wrapper`の実際の幅と完全一致）・
  height=25.59px、▶（横送り）はwidth=25.59px・height=70.64px（軸タイル行の高さぶん
  ストレッチ）、両方とも`border-radius: 10px`（角型）であることを確認。tsc/eslint/
  vitest（既存38件）green。
