# T1173. 過去24時間の累計雨量を区間ごとの材料として作り、地図で確かめられるようにしたうえで、単独の軸として公開できるようにする

状態: 未完了（2026-09-26起票）

## 背景

雨の後の走りやすさ（proposal-rain-unpaved）をユーザーの指摘で3段（①累計雨量の軸 ②舗装質の軸 ③合成の軸）に分けたうちの①。アメダスの地図JSONは既に10分ごとに取得していて、過去24時間の雨量（precipitation24h）を含む（今は10分雨量だけを保存）。新しい源泉は要らない（気象庁の防災情報JSON、data-sources.mdに記録済み）。区間ごとに最寄りの観測所の値を引く、時刻で変わる動的材料にする。材料を作って地図のレイヤーと道の詳細で確かめるのを先にし（proposal-surface-classと同じ方針）、そのうえで単独の軸として公開できる形にする。軸の公開は本番DBへの書き込み（ユーザーの操作）。起票案 proposal-rain-24h-material（2026-09-26承認）

## 問いと答え（2026-09-26、仕掛中のダッシュボード）

- **T1173-rain-windows「累計雨量の材料を、どの時間の窓で持ちますか」** → (2) 1時間雨量の履歴を持ち、窓の長さは宣言の一覧で自由に決める（例: 1・3・4・6・12・24・48・72時間）。毎正時の1時間雨量を観測所ごとに履歴で持ち（72本程度）、起動時は過去の地図JSONで72時間まで埋め戻す。窓ごとにファイル・関数を作らない。しきい値は軸の側で決め、材料は観測どおりの値を出す。
- **T1173-rain-since-stop「雨が止んでからの経過時間も材料にしますか」** → (1) 作る。同じ履歴から出し、何mm以上を雨と数えるかを宣言に持つ（雨量計は0.5mm刻み）。72時間を超えたら「72時間以上」。
- **T1173-rain-time-basis「今の観測だけで出しますか、出発時刻まで予報で延ばしますか」** → (2) 出発時刻まで予報（MSMの降水等）で延ばす。ただし気象業務法の「予報」に当たるかの確認（[T1053](T1053.md)）が済むまでやらない。段階1は今の観測だけで出す。

読み取りの調査（Q-rain、2026-09-26）: 地図JSONに`precipitation10m`・`1h`・`3h`・`24h`が入っている（観測所1,284か所）。値は`[値, フラグ]`で、フラグ5の値はnull（欠測とみられる。公式の意味は未確認）。区間への割り当ては最寄りの雨量観測所（約17km間隔）。

## 方針

- **材料の宣言は窓の長さの一覧1つ**（`domain/rain.py: RAIN_WINDOW_HOURS`）。材料id（`rain_{h}h_mm`・`hours_since_rain`）・材料カタログの行・持つ履歴の本数（一覧の最大）・配信の登録はここから導く。窓を1つ足すのは一覧へ1件足すだけ（設計原則 構造仕様8・17）。
- **「何mm以上を雨と数えるか」は天気の「降っていない」の境（`weather.PRECIPITATION_MIN_MM`）と同じ事実**として、そちらを読む（構造仕様17の1問目: 「降っていない」の境を変えたら、止んでからの時間の雨の数え方も同じく変わるべき）。雨量計は0.5mm刻みなので、今の0.1mmでは観測された雨がすべて当たる。
- **配信は既存の専用way値配信（`dynamic_way_values`）に載せる**。配信サービスの登録を「1サービス＝1材料」から「1サービスが担当する材料の一覧（`material_ids`）＋組み立て時に材料を受け取る`build`」へ一般化し、1つの`RainWayService`が雨の材料すべてを担当する（窓ごとにクラスを作らない）。軸スタジオで雨の材料を1つだけ指す軸に`dedicated_way_value_layer`を立てれば、地図のレンズと道の詳細（区間インスペクタ）に出る。frontendの変更は要らない（生成物の材料カタログだけが増える）。
- **履歴の置き場はRedisの1キー**（`jma:amedas:rain-history`）。失うと気象庁の過去の地図JSONを全本取り直すことになる（キャッシュ方針「外部への負荷を肩代わりするものはRedis」）。アメダスの定期バッチ（10分おき）が欠けている正時だけを取る。Redisが使えない間は取りに行かない（毎回「全本欠け」になって気象庁へ全本を問い合わせ続けるため）。最新の正時が2時間半より古い履歴は配らない。
- **欠測の扱い**: 窓の中に欠測の1時間があればその窓は値なし（0で足すと少なく見せる）。止んでからの時間は、雨を見つける前に欠測に当たれば値なし。最寄りの雨量計が欠測でも次に近い雨量計で埋めない。
- **ルートの評価には段階1では配線しない**。雨の材料を指す公開軸があっても、ルートの区間ではその軸は「データなし」になり、ルート生成は落ちない（下の検証）。

## 段階

- **段階1（このコミット）**: 観測の材料と地図・道の詳細。材料の宣言と計算、1時間雨量の履歴の取得と埋め戻し、専用way値配信の登録、出典の常時表記（気象庁アメダスを加工した旨）。
- **段階2（未着手）**: ルートの評価（探索・区間表示）へ雨の材料を配線する。動的材料（`REQUEST_DYNAMIC_MATERIAL_IDS`）の評価器は今は区間の方位・風しか入力に持たないため、区間の中点から最寄りの雨量計を引く入力（観測所ごとの材料の値と区間ごとの観測所の番号）を`DynamicAxisRequestContext`へ足すか、静的行列の材料列として探索前に埋めるかを、この段の最初に決める。材料の説明の「ルートの評価にはまだ使われず」をこの段で消す。
- **段階3（[T1053](T1053.md)の後）**: 出発時刻まで予報（MSMの降水）で延ばす。T1053で気象業務法の「予報」に当たるかの確認が済むまで着手しない。延ばすなら軸の`dynamic_way_value_needs_time`を立て、配信は`at`を読むようになる。
- **軸の登録（ユーザーの操作）**: 本番の軸スタジオで雨の材料を指す軸を作り、`dedicated_way_value_layer`を立てて公開する。手順は仕掛中のダッシュボードの`T1173-register-rain-axis`（kind 操作）。
