# T1210. 派生の作り直しで、段ごとに使ったソースの取込を世代に記録し、鮮度台帳と分母・タイルの鍵がそれを読む（T1203 の一般化）

状態: 未完了（2026-09-27起票）

## 背景

周期レビュー第14回（2026-09-27）の起票案（ダッシュボード proposal-derived-provenance-per-stage、承認済み）。

規模L（根拠: 本番DBに列か表を足す）

■ 背景
性質: 「機械が見ている」という嘘／片側だけの修正（再発: 第13回 T970 への追記）。
- 系譜の列が行ごとに1本（edge_materials は osm_way の run）で、事故・dem・lulc・osm_node を取り直しても台帳が stale を出さない。node_materials は行ごとに系譜が混ざる。事故の取込が無い DB では accident_count=0 が「完成」と出る。タイルの世代は派生の世代だけで決まり、生データを直接読む路面・POI・事故のタイルは、取り直すと同じ鍵のまま中身が変わる。
- source_runs の running・failed は1トランザクションの中で開閉されるため観測されない（ingest.py:155・source_models.py:66-69・db_status_service.py:102 の記述と食い違う）。'succeeded' のリテラルが6ファイル8か所、_latest_run の写しが2つ、ソース名のリテラルが source_models の外に9か所（derive_counts・derive_raster_materials・accident_repository・road_graph_repository・derived_data_freshness 等。T1131 段階Eは way・node だけを寄せた）。
- 土地被覆の有効画素が足りない区間が、台帳で「未計算」に数え続けられる（T1136 の範囲外、行き先なし）。

■ やること
1. 派生を作り直すトランザクションの中で「段ごとに使ったソースの run_id」を世代に記録（derived_data_meta の拡張か世代ごとの表）。鮮度台帳・get_accident_years・タイルの鍵がそれを読む。T1203 の accident_count_years はこの一例で、後でこれに吸収する。
2. 事故・標高・土地被覆を読む副問い合わせと「最新の成功した run」を source_models に1つずつ置き、source='…' と 'succeeded' を外で書いたら落とす構造テストを足す（寄せた後なら許可リスト無しで成り立つ）。
3. 失敗の記録を別トランザクションで残すか、status を捨てるかを決める。

■ 判断（矛盾の解消）
T1203（取り込み待ち）は今の形のまま入れる——利用者に見える分母のずれを今直せる。一般化はその後で吸収する。

■ なぜ既存のタスクに入らないか
T1203 は事故の分母だけ。T970 はユーザーの手動のタスク。
