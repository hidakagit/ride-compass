# T827. 目的地ルートが0件のとき、警告が原因を誤って名指しする

規模S。
状態: 完了（2026-09-13。原因の特定は次の再発待ち）

## 背景

本番で目的地モードの生成が0件になった際、残った証跡はこの1行だけだった。

```
select_via_nodes destination unreachable from origin, no accessible alternative found
  destination_node=osm-node-9559175027
generate(destination) engine=road_graph origin=(35.75,139.74) max_routes=4
  -> no via-node candidates prepare_ms=691 select_ms=21170
```

この文面は「目的地が到達できない場所にある」と読ませるが、実際にこの分岐へ入る条件は違う。
`find_nearest_node_indexed`（`backend/app/domain/routing.py`）は探索半径の上限を持たず索引全体を
走査するため、`None`が返るのは**bbox内のどのNodeもコストが有限でなかった**ときに限られる。
つまり起点からの前向き木が1Nodeも広がらなかった状態であり、目的地の場所とは無関係である。

利用者へ出る文面（`route_generator.py`の`last_no_candidates_reason`）も同じ誤りを引き継ぎ、
「地点や除外する道路の設定を変えて」と案内する。起点側・コスト配列側が原因なら、この案内に
従っても直らない。

調査で分かっていること（2026-09-13、本番実測）:

- ログのノード`osm-node-9559175027`の実座標は(35.8290,139.7372)。同じ起点から同じ座標を
  目的地にして本番で再実行すると4候補が3秒で返る。距離（3/8/15km）・方位・出発時刻
  （0〜48時間先）を振っても再現しない
- `select_ms=21170`は索引全体の走査と整合する（成功時は3秒）

## 対応方針

原因が確定できなかったのは、このログが「どちらの側が壊れたか」を区別しないため。次に起きた
ときにWARNING 1行で確定できるようにする。

- 起点からの到達Node数・コスト配列の非有限率・起点Nodeから出る有向Edge数を警告へ載せる
- 到達Node数が0なら目的地ではなく起点側として報告し、利用者向けの文面も分ける

## 実装

`corrected_node is None`のときに到達Node数（`np.isfinite(forward_tree.node_cost)`の数）を
見て、どちら側を名指しするかを分ける。

- 到達Node数0 → 起点側。起点Nodeから出る有向Edge数とコスト配列の有限率を警告へ載せる
- それ以外 → 目的地側。到達Node数を警告へ載せる

判定結果は`_RoadGraphContext.no_candidates_side`（`destination_correction`と同じside
channel）で`RouteGenerator`へ渡り、利用者向けの文面も分かれる。起点側のときに
「地点や除外する道路の設定を変えて」と案内すると、直らない操作を促し続けることになる。

検証:

- コスト配列を全Edge非有限にした入力で`select_via_nodes`を呼び、`origin reaches no node`が
  出て`no_candidates_side == "origin"`になることを確認（回帰テスト化）
- `RouteGenerator`側も、engineが起点側と報告したときの文面に「目的地」が現れないことを確認
- `pytest backend/tests/test_road_graph_engine.py test_route_generator.py
  test_routes_generate.py -q` → 206 passed

## 残り

**本番で起きた0件の原因そのものは未特定**。次に再発したときに、上の警告1行で起点側か
目的地側かが確定する。起点側だった場合は`out_edges`と`finite_cost_ratio`が、どちらの
仮説（起点の孤立／コスト配列の全非有限）かまで示す。
