# T1101. 風の詳細格子の間隔を決まった段階だけに限る許可リストをやめ、下限つきの範囲で受け付ける

状態: 完了（2026-09-25起票、2026-09-25完了）

## 背景

T1099で、間隔を段階に限る理由として注記が挙げていた「キャッシュ共有」はMSMへの移行（T645）で消えていたと分かった。段階に限る目的を問うたところ（ダッシュボード T1099-spacing-purpose）、答えは「(3) 理由は無い——許可リストをやめ、下限つきの範囲で受け付ける」（2026-09-25）。いま段階に依っているものが3つある: (1)画面はズームの段ごとに宣言の並びから添字で間隔を選ぶ (2)画面は間隔が変わった回だけ前回の値で補うのをやめる (3)backendの許可リスト（WIND_GRID_DETAIL_ALLOWED_SPACINGS_DEG）が間隔の下限になっている。(3)の下限は範囲の検査として残す（点数の上限はT1100で点を作る前に見る形になった）。(1)(2)のfrontend側（windLayer.ts・useWeatherGrid.ts）が段階を前提にしているので、frontendの宣言も合わせて扱う。このタスクのコミットでT1099-spacing-purposeの問いと答えをT1099.mdへ移し、T1099を閉じる（T1099には残りの作業が無い）。規模の根拠: backend 2本とテスト、frontendの読む側2本とそのテストで7以下だが、契約（API・生成物）が変わるので読む側を数えてM。起票案 kihyoan-wind-grid-spacing-range として2026-09-25承認。

## 着手時の確認（2026-09-25、担当 W-spacing）

列挙した（master 46aa6a9e）。定義（`domain/wind_grid.py`）の外で読むのは次の9ファイルで、使い方で3つに分かれる。

| 読む側 | 使い方 |

生成物の`detail_spacing_deg`（backendの既定の間隔）はfrontendに読む側が0件だった（配るだけで誰も読まない）。
`useWeatherGrid.ts`の「間隔が変わった回だけ補わない」は間隔の値を比べるだけで、段階の集合を読まない。

## 対応

- backend: 許可リスト`WIND_GRID_DETAIL_ALLOWED_SPACINGS_DEG`を消し、下限`WIND_GRID_DETAIL_MIN_SPACING_DEG = 0.0025`
  以上の値を受け付ける（下限未満は今と同じ400）。無限大・NaNは`Query(allow_inf_nan=False)`で型の検査に落とす（422）——
  下限だけにすると`inf`が通り、索引0の点の座標が`0×inf`でNaNになって500（外した状態で試すと`inf`は
  `Coordinates`の検査で、`nan`は`cannot convert float NaN to integer`で、どちらも未処理の例外になった）。
- 下限の根拠: 今の許可リストの最小値（0.0025）をそのまま使う。画面が最も拡大したとき（ズーム19以上）に求める
  間隔で、元のMSMの格子（緯度0.05度・経度0.0625度）より20倍以上細かく、これより細かくしても補間の点が増えるだけで
  情報は増えない。下げられる限界は0.0001度——座標を小数4桁へ丸める（`_lattice_coordinate`）ので、それ未満では
  別の格子点が同じ座標へ潰れ、画面の補い（緯度経度の一致で見分ける）が壊れる。下限は1回の問い合わせの重さを
  守るものではない（それは点数の上限が持つ）。
- 点数の上限はT1100の先読み（`count_wind_grid_detail_points`で数えてから作る）がそのまま効く——任意の間隔でも
  数える側と作る側が同じ索引の範囲に従う（数と実物の一致の試験を段階に無い間隔0.003・0.0137へ広げて確かめた）。
- frontend: ズームの段ごとの間隔を`windLayer.ts`自身の宣言（`{zoom, spacingDeg}`の並び）にした。値は以前の生成物の
  並びと同じ（ズーム10→0.02、13→0.01、16→0.005、19→0.0025）で、画面の見た目と問い合わせは変わらない。段の境界と
  間隔は描画の都合なので画面が持つ（設計原則 構造仕様1の「拡大率の段」）。backendとの契約は下限だけになり、
  生成物`detail_min_spacing_deg`として配り、試験が「どのズームでも下限を下回らない」を見る。
  `useWeatherGrid.ts`は変えていない——段に分けたままなので、同じ段の中では間隔が変わらず補える。
- 生成物から`detail_allowed_spacings_deg`と、読む側の無い`detail_spacing_deg`を消した。`openapi.json`・`api.d.ts`は
  変わらない（`allow_inf_nan`はスキーマに出ない）。
- 設計書: backend`weather-dynamic-layers.md`「詳細格子の座標と間隔」節へ下限と根拠・下げられる限界を、frontend
  `dynamic-weather-layers.md`「共通契約」1へ段を画面が持つことと段に分ける理由を書いた（後者は存在しない
  `windLayer.ts: WIND_GRID_DETAIL_SPACING_DEG`を指していたので直した）。

## 検証

- 試験: `test_weather_route.py`に下限ちょうど・段階に無い値（0.003・0.0137・0.03）で200かつサービスへ渡る点がその間隔の
  格子であること、下限の直下（`math.nextafter(下限, 0)`）・0・負で400、`inf`・`nan`で422、上限を超える範囲は下限と
  0.003の両方で点を作らずに400。`test_wind_grid.py`の数と実物の一致を任意の間隔へ。`windLayer.test.ts`はズーム10〜24
  （0.25刻み）と無限大で、間隔が粗くならず最も細かくても下限以上。`useWeatherGrid.test.ts`は期待値の間隔を
  `windGridDetailSpacingDegForZoom`から取る。
- わざと壊して落ちることを見た: 比較を`<=`にする → 下限ちょうどの200が落ちる。比較を`< 下限×0.99`へずらす →
  下限の直下の400が落ちる。`allow_inf_nan=False`を外す → `inf`・`nan`が未処理の例外。frontendの最後の段を0.002に
  する → 下限を下回らない試験が落ちる。
- 静的検査: `ruff check`（変更5ファイル）緑、`mypy` 195ファイル問題なし、`tsc --noEmit`（`next typegen`の後）エラー0、
  prettier（変更4ファイル、`useWeatherGrid.test.ts`のimportの折り返しを直した）・eslint（変更3ファイル）緑、
  `review_checks.py docs`違反なし。`export_openapi.py`→`openapi-typescript`で`frontend/src/types/generated/`の差分は
  `wind-grid-config.json`だけ（上記の2キーの削除と`detail_min_spacing_deg`の追加）。
- テスト: `pytest tests/test_weather_route.py tests/test_wind_grid.py tests/test_wind_way_service.py` 98 passed、
  `vitest run windLayer.test.ts useWeatherGrid.test.ts` 17 passed。
- `frontend/e2e-live/`は回していない——画面が求める間隔と描き方は変わらず（宣言の値が以前の生成物と同じ）、
