# T288. AXIS_DEFINITIONS push型更新のマルチワーカー対応〔P3〕規模S〜M — トリガー: 複数メンバーが触る状態にプロダクトが成長した時点（2026-08-29ユーザー判断、[T388](T388.md)と同じトリガー。現状は単一プロセスデプロイのため未到達）

状態: 完了（2026-09-23、[T388](T388.md)へ一本化して閉じる。ユーザー判断。末尾「閉じた理由」参照）

- **2026-08-29**: トリガーを明確化し、複数ワーカー化のメリット・デメリット整理（着手時に
  Tier 1として必ず同時対応が必要な項目の一覧）は[T388](T388.md)へ集約した。着手判断時は
  T388を起点にすること。


- 背景: レビュー指摘（レポート§6）。`AXIS_DEFINITIONS`はmutableグローバル辞書を
  「起動時＋管理API書き込み直後」の2箇所でin-place更新するpush型設計
  （`services/axis_registry_service.py`）。単一ワーカーでは安全だが、複数ワーカー化すると
  他プロセスでの軸編集が反映されない。また同一プロセス内でも「リクエスト冒頭の
  RoutePreference検証」と「後段の評価」の間にawaitを挟むため、管理API書き込みとの
  理論上の不整合ウィンドウがある（実害は管理者手動操作時のみ・確率極小）。
  対応方針（`axis_registry_meta.revision`のポーリングへ差し替え）は
  docs/records/decisions/t221-axis-registry.md「Stage D設計メモ」に記録済みで、本タスクは
  それをトリガー付きで拾えるようにする正式起票。
- 影響範囲（保留した場合）: 単一プロセスデプロイを続ける限り実害なし。複数ワーカー化を
  「別の理由」（性能等）で行う際に本タスクを見落とすと、軸スタジオの編集が一部プロセスに
  反映されない不整合が黙って起きる——複数ワーカー化のタスクを起こす際は本タスクを
  完了条件に含めること。
- 完了条件: 着手時に確定（ADRの方針どおりrevisionポーリング等へ差し替え、複数プロセスでの
  反映テストを含む）。

## 閉じた理由（2026-09-23、未完了タスクの棚卸し・ユーザー判断でT388へ一本化）

- 本文自身が「着手判断時はT388を起点にすること」と書いており、複数ワーカー化の計画
  （同時に直すべきものの一覧。本タスクの`AXIS_DEFINITIONS`もそこにある）は[T388](T388.md)が持つ。
  2本を別々に開けておく理由が無い。
- 本文の「影響範囲（保留した場合）」が恐れていた「見落とすと黙って不整合が起きる」は、
  [T1020](T1020.md)が入れた起動時の止め（`backend/app/infrastructure/single_process.py`。
  ワーカーが2以上ならlifespanで`RuntimeError`）によって、起動できない形で表に出るようになった。
- 複数ワーカー化を決めたら、T388の「着手時の進め方」どおりに、本タスクの中身
  （`axis_registry_meta.revision`のポーリングへ差し替える方針。
  docs/records/decisions/t221-axis-registry.md「Stage D設計メモ」）を含めて起票し直す。
