# T1107. ルートの風の表示を区間の通過時刻の風にそろえ、区間の詳細に使った風（予報の地点・時刻・風向風速）を出す

状態: 完了（2026-09-26）

## 背景

ユーザー質問（2026-09-25）: 風はルート途中ではそこまで走った時点の、その地点の風を使っているか。それが分かるようにしたい。調べた事実: 探索は往路・復路ごとに1時間刻み（最大4本、backend/app/services/road_graph_engine.py の TIME_BIN_HOURS・MAX_TIME_BINS）で経過時間の風を引くが、区間の表示値（_build_segment_details が読む leg.axis_arrays・material_arrays）はレグの中間の時刻の代表ビン（_representative_bin）1本だけで、区間の到達予想の時刻の風ではない（目的地ルートの復路だけは passage_hours で区間ごと）。docs/modules/backend/routing-engine.md は表示と探索コストの一致を約束しており食い違う。承認時の決定: ①表示を区間ごとの通過時刻の風にそろえる（不具合の修正）②区間の詳細に、使った風を出す（例: 出発地点の予報・12時台・東 3.2m/s）。規模の根拠: backendの区間の組み立てとAPIモデル・生成物・frontendの区間の詳細とそれぞれのテストで8〜20ファイル。

## 追加の決定（ユーザー 2026-09-25〜26、会話）

- 風予報を何時間先まで使うかの明示をこのタスクに含める（T1108の計測の報告のときの問い）。
- 実装の途中で分かったこと: 区間の「到達予想」は距離÷巡航速度で出していて、候補の「所要」（走行モデル＋停止の待ち＋曲がる待ち、
  ただし代表ビン1本の秒）とも、探索が風の時刻を決める経過時間とも別の計算だった（最後の区間の到達予想が「出発＋所要」と合わない）。
  **到達予想も所要と同じ時計にそろえる**（ユーザー決定）。

## 変更

- 経路を探索と同じ規則でたどる`_route_passages`を足した（レグの最初の区間はビン0、次の区間は前の区間を抜けた時点［曲がる待ちを足す前］の
  経過時間のビン、区間の秒はそのビンの`travel_bins_lazy`。探索のビン選び`routing.py: time_bin_of`をそのまま呼ぶ）。所要（`_estimate_duration_seconds`）と
  区間の到達予想はこのたどりの時計で出す。
- 区間の値（難易度・軸・材料）は、ビンが2本以上あるレグでは、経路上の行だけをその区間のビンの時刻で合成し直して読む
  （`_LegCostComposer.values_at_rows`。合成の`_compose_at`を、行を切り出せる`_evaluate`と2つの入口に分けた）。**全ビンの表示用配列を持ち続ける
  案は採らなかった**——ビン1本の表示用配列はbbox全体の行数（120kmの周回で約179万Edge、T1108の計測）×数本で、往路・復路の最大8本を
  リクエストの間持つことになる（配列の本数から見積もっただけで、メモリは測っていない）。
- 区間の評価に使った風を`RouteSegmentDetail.wind`（`SegmentWind`: 風速・風向・予報の時刻・延ばして使ったか）として配る。延ばして使ったのは、
  レグのビンの範囲の先の区間か、予報の期間の外で端の時刻へ寄せた区間（`WindForecastSeries.sampled_times`）。区間を約500mのビンへ畳むときは
  到達予想と同じく先頭の区間の値を引き継ぐ。
- frontendの区間の詳細に`SegmentWind`（「風 12:00の予報・東の風 3.2m/s」＋延ばした区間は「（予報の先を延ばして使用）」）を出した。(i)の説明は
  レグごとに追う時間を生成物`route-generate-config.json`の`wind_forecast_hours_per_leg`（`MAX_TIME_BINS`×`TIME_BIN_HOURS`＝4）から出す。
- 設計書: `routing-engine.md`（レグ内の時刻ビン・evaluate_loops・暗黙の前提）、`dynamic-way-values.md`、`route-settings-and-results.md`を直した。

## 検証

- `test_road_graph_engine.py`に、ビンが2本以上あるレグで区間の値・到達予想・所要が探索の使ったビンのものになること（偽の合成器で風の軸の値＝
  ビンの時刻）と、ビンの範囲の先の区間に延ばした印が付くことの2件を足した。区間の値の合成し直しを止めると2件とも落ちる。到達予想のテストは
  所要と同じ時計（区間の秒＋曲がる待ち）の期待値へ直した。曲がる待ちの関数を合計から遷移ごとの並びへ変えたので、その2件も直した。
- `pytest`（区間・経路探索・風・ルート生成に触れる12ファイル、PostGIS統合テストを除く）431 passed。ruff・mypy 指摘0件。
- frontend: `SegmentWind.test.tsx` 4件と`page.test.tsx`で126 passed。prettier・eslint・`tsc --noEmit`・knip・`review_checks.py docs`指摘0件。
  export_openapi→generate:apiの差分は`SegmentWind`の型と`wind_forecast_hours_per_leg`だけ。
- 生成にかかる時間への影響は測っていない（合成し直すのは候補ごとに経路上の行だけ）。画面では確かめていない（e2eの模擬の区間は風を持たない）。

## T1108への引き継ぎ

区間の風の説明（`SegmentWind.tsx`の(i)）は「出発地点の風の予報」と書いている。T1108で地点ごとの予報にしたら、この文と、`routing-engine.md`
「暗黙の前提のまとめ」の風の1文を直す。
