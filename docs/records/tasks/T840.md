# T840. 本番DBの状態を「鮮度」タブから見えるようにする

規模L。
状態: 完了（2026-09-14、ユーザー指示「まずは軸定義以外も含め、本番DBの状態を見える化する

## 背景

「本番へ反映したつもりで反映されていない」が繰り返し起きているが、`/admin`から確かめられるのは
派生データの陳腐化だけ（[T832](T832.md)・[T836](T836.md)）。本番DBの状態を見る手段を広げる。

**実行（作り直し）は含めない。** [T839](T839.md)へ分離し、本タスクの結果を数ヶ月見てから
判断する（ユーザー判断、2026-09-14）。

## 何を出すか（開発DBの実測で、実際に問題が見えたものを優先した）

### 1. 生データ取込の最終実行

`osm_import_runs`・`accident_import_runs`・`designation_import_runs`の最新成功run（id・
日時・対象範囲）と、**最後が失敗ならその事実**。

鮮度タブの世代比較は「最新成功run」を基準にしているため、**基準そのものが古い／失敗して
いると「全部最新」と出ても意味がない**。

### 2. 主要テーブルの行数と容量

「取り込んだつもりが入っていない」が一目で分かる。ディスク使用量（VMは150GB）も。

実測で`way_geometry`が**0行**だった（`way_landcover`は86,642行）。蛇行のway単位集計が
未実行という状態が、行数だけで分かる。

### 3. 統計情報・VACUUMの鮮度

`last_analyze`／`last_autovacuum`／`n_dead_tup`。

**実害が確認できた**: 開発DBの`elevation_attributes`・`accident_points`は`last_analyze`が
NULL（一度もANALYZEされていない）で、プランナが持つ行数推定が**43倍ずれていた**
（統計3,156に対し実数135,385）。PostgreSQLはこの統計でプランを決めるため、ルート生成の
クエリが誤ったプランを選びうる。

### 6. 接続とトランザクションの状態

接続数と`max_connections`、**`idle in transaction`の最長時間**。放置されるとVACUUMが
進まずテーブルが肥大化する（[T714](T714.md)が同じ問題を別角度で扱うが、あちらは
トリガー待ちで未着手）。

### 7. split済み範囲（`road_graph_tiles`）を地図で

どこまでsplit済みか＝**どのエリアでルート生成が冷パス（初回が遅い）になるか**。
`road_graph_tiles`は`(zoom, x, y, fetched_at)`を持つためタイル座標がそのまま入っており、
frontendには既にタイル座標→境界ポリゴンの関数（`tileRing`、勾配グリッド表示が使用中）が
ある。管理画面へ重い`MapView`を持ち込まず、ベースマップ＋ポリゴンだけの軽量な地図で足りる。

**見送ったもの**: 軸定義の内容比較（スナップショット更新忘れには無力で、形式の不整合は
起動時のfail-fastが既に検出している）、インデックスの使用状況（今困っていない）。
migrationの未適用一覧は`/api/debug/db-status`に既にあり、再利用で済む。

## 段階1の実装・検証（2026-09-14）

`GET /api/admin/db-status`（Basic認証必須）と「鮮度」タブの3枚目を追加した。層の分け方は
派生データ鮮度台帳と同じ——リポジトリは数えるだけ、判定はサービス層、表示はfrontend。

**行数は実数を数える**（統計値は`elevation_attributes`で43倍ずれていた）。1クエリで全テーブル
ぶんを数えるのに`query_to_xml`を使い、開発DB（675MB・23テーブル）で2.9秒。

**しきい値には規模の条件を併せて持たせた。** 割合や有無だけで判定すると、実データで注意が
14件出た——うち9件は1万行未満の小さなテーブルで、統計が無くてもプランナは全走査を選ぶため
打つ手が無い。`STATISTICS_WARN_MIN_ROWS`（1万行）・`DEAD_TUPLE_WARN_MIN_ROWS`（1000件）を
足して**14件→5件**になり、残ったのはすべて10万行級（母集団23件に対する除外は9件＝39%）。

**画面はテーブルを畳む。** 実データで27行になり注意すべき行が埋もれたため、注意のあるものだけを
行にし残りを「その他N件」へ畳んだ（**27行→10行**）。畳んだ側も開けば一覧が見える。

### 検証

- 開発DBの実データに対してSQLと判定を通し、取込3種別・接続・23テーブルが返ることを確認。
- 390px幅で実データを描画し、横スクロールなし（`scrollWidth 390`）・10行で収まることを確認。
- backend 1917件・frontend 1321件緑、`ruff`・`tsc --noEmit`・`eslint`とも新規の指摘なし、
  `review_checks.py docs --staged`違反なし。検査器が指摘した経緯表現（「実測で」）と新規
  ファイルの記載漏れ2件は、指摘どおり是正した。
- OpenAPIとAPI型は再生成済み。

## 段階2の実装・検証（2026-09-14）

`GET /api/admin/road-graph-tiles`（Basic認証必須）と`SplitCoverageMap.tsx`を追加した。

- **DB状態の集計とは別のAPIにした。** 地図を開いたときだけ要る一方、全域ぶんの件数になるため
  毎回運ぶと無駄になる。
- **GeoJSONはbackendで作らない。** 座標のまま返し、境界ポリゴンはfrontendが
  `Map/dynamicWayValues.ts: tileBoundsLonLat`で組み立てる（同じ規則を2箇所へ書き写さない）。
- **地図は`<details>`の中で、開いたときだけ初期化する。** MapLibreの初期化は重く、閉じたまま
  使う人に払わせる必要が無い。`MapView`の機構（レイヤー群・レンズ・ルート線）は持ち込まず、
  ベースマップとタイル境界の面だけの軽量な地図にした。

### 検証

**実データ（16タイル）＋実MapLibreで描画して確かめた。** 座標の取り違え（XYZの軸を入れ替える）は
机上では分からないため、実際に描かせて位置を見た。

- 描画範囲が東経139.57〜139.92・北緯35.53〜35.82（東京都心）と出て、16タイルが**隙間も重なりも
  無い4×4のグリッド**として並ぶことを確認。ページエラーなし。
- 座標変換・全体の範囲・タイル0件の扱いを単体テストで固定（`SplitCoverageMap.test.ts`）。
  実データの座標が日本の範囲に収まることも見る——変換式そのものより「どの軸をどこへ渡すか」を
  間違えていないことが要るため。
- frontend 1334件緑、`tsc --noEmit`・`eslint`とも新規の指摘なし。
