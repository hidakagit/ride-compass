# T1063. 作業ツリーごとのnpm ciを速くし、並行実行の立ち上がりを縮める

状態: 未完了（2026-09-23起票）

## 背景

並行実行ではエージェントごとに作業ツリーを作り、frontendの依存（実体32,000ファイル超）を作業ツリーごとに npm ci で入れ直している。node_modules はジャンクション等で共有できない（CLAUDE.md「作業ツリーの安全」: next dev が外を指すリンクを拒否し、git worktree remove --force で共有元を壊す。T768）。2026-09-23 の実測（lockrun/log.jsonl）: 10:37 に 2,452秒で失敗（rc=1、機械の飽和中）、12:31 に 525秒、13:58 に 166秒（heavy の枠で単独）。同日の第1回では npm ci に32〜39分かかった記録もある（T1049）。ユーザーが同日の朝に「重い」と指摘していたが起票されず、規約へ「作業ツリーを使い回して避ける」という回避だけが入った。作業ツリーを作るたびの数分〜数十分は、並行実行の立ち上がりを直接遅らせ、heavy の枠も塞ぐ。

対応方針（測ってから選ぶ。推測で方式を決めない）:
1. 所要の内訳を測る: 同じ作業ツリーで node_modules を消して npm ci を3回（heavy の枠で単独）、時間を「ダウンロード（~/.npm のキャッシュ命中か）」「展開と書き込み」「install スクリプト」に分けて取る（npm ci --timing の出力と、ウイルス対策のリアルタイム検査の有無で比べられるならそれも）。どこに時間が行っているかを書く。
2. 候補を公式文書で確かめてから実測で比べる。候補の例: --prefer-offline（キャッシュ命中時に問い合わせを省く）、npm のキャッシュの置き場、pnpm（内容アドレスのストアからハードリンクで配る——ジャンクションではないので next dev の制約と worktree remove の再帰削除に当たるかを公式と実測で確かめる）、本体チェックアウトの node_modules からのコピー（robocopy 等）、Windows の Dev Drive（ユーザー判断事項。ReFS とウイルス対策の非同期検査。導入はユーザーの操作）。それぞれ、所要・壊れ方（worktree remove で共有元が消えないか）・CI と本番の Dockerfile への影響を表にする。
3. 採る方式を規約（docs/conventions/orchestration.md「起動のしかた」）と CLAUDE.md「作業ツリーの安全」に反映し、作業ツリーの新規作成から最初の tsc が通るまでの時間を、採用前後で同じ条件で測って記録する。
4. Dev Drive のようにユーザーの操作・判断が要るものは、効果の実測を添えて判断待ちに出す（自分で設定を変えない）。

完了条件: 1 の内訳と 2 の比較表が記録にあり、採った方式で作業ツリーの立ち上がり（新規作成→依存が入り tsc が通るまで）が採用前より短くなったことを実測で示すこと。どれも採らないなら、その理由を実測で示すこと。
