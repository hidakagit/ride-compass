# T1063. 作業ツリーごとのnpm ciを速くし、並行実行の立ち上がりを縮める

状態: 完了（2026-09-23、[T1066](T1066.md)に畳む。種からのコピーは採らない）

## 背景

並行実行ではエージェントごとに作業ツリーを作り、frontendの依存（実体32,000ファイル超）を作業ツリーごとに npm ci で入れ直している。node_modules はジャンクション等で共有できない（CLAUDE.md「作業ツリーの安全」: next dev が外を指すリンクを拒否し、git worktree remove --force で共有元を壊す。T768）。2026-09-23 の実測（lockrun/log.jsonl）: 10:37 に 2,452秒で失敗（rc=1、機械の飽和中）、12:31 に 525秒、13:58 に 166秒（heavy の枠で単独）。同日の第1回では npm ci に32〜39分かかった記録もある（T1049）。ユーザーが同日の朝に「重い」と指摘していたが起票されず、規約へ「作業ツリーを使い回して避ける」という回避だけが入った。作業ツリーを作るたびの数分〜数十分は、並行実行の立ち上がりを直接遅らせ、heavy の枠も塞ぐ。

対応方針（測ってから選ぶ。推測で方式を決めない）:
1. 所要の内訳を測る: 同じ作業ツリーで node_modules を消して npm ci を3回（heavy の枠で単独）、時間を「ダウンロード（~/.npm のキャッシュ命中か）」「展開と書き込み」「install スクリプト」に分けて取る（npm ci --timing の出力と、ウイルス対策のリアルタイム検査の有無で比べられるならそれも）。どこに時間が行っているかを書く。
2. 候補を公式文書で確かめてから実測で比べる。候補の例: --prefer-offline（キャッシュ命中時に問い合わせを省く）、npm のキャッシュの置き場、pnpm（内容アドレスのストアからハードリンクで配る——ジャンクションではないので next dev の制約と worktree remove の再帰削除に当たるかを公式と実測で確かめる）、本体チェックアウトの node_modules からのコピー（robocopy 等）、Windows の Dev Drive（ユーザー判断事項。ReFS とウイルス対策の非同期検査。導入はユーザーの操作）。それぞれ、所要・壊れ方（worktree remove で共有元が消えないか）・CI と本番の Dockerfile への影響を表にする。
3. 採る方式を規約（docs/conventions/orchestration.md「起動のしかた」）と CLAUDE.md「作業ツリーの安全」に反映し、作業ツリーの新規作成から最初の tsc が通るまでの時間を、採用前後で同じ条件で測って記録する。
4. Dev Drive のようにユーザーの操作・判断が要るものは、効果の実測を添えて判断待ちに出す（自分で設定を変えない）。

完了条件: 1 の内訳と 2 の比較表が記録にあり、採った方式で作業ツリーの立ち上がり（新規作成→依存が入り tsc が通るまで）が採用前より短くなったことを実測で示すこと。どれも採らないなら、その理由を実測で示すこと。

### 計測の失敗: `heavy`の枠を約19分塞いだ

複製の計測（c1）で、ハードリンクの複製にGit Bashの`cp -al`を使い、**983秒**かかった。
その間`heavy`を持ち続け、他の担当の監査と司令塔のpushを6〜8分待たせた。`cp -al`は
MSYS2のエミュレーション層を通るため、同じことをPythonの`os.link`（`CreateHardLinkW`を
直接呼ぶ）でやると64秒だった（c2）。**この開発機で大量のファイル操作を測るときは、
Git Bashのコアユーティリティ（`cp`・`find`等）を使わずネイティブの道具を使う**。
また、`npm ci`の所要は機械を独占しないと正しく測れない性質なので、他の担当が動いている
時間帯に回してはいけなかった（司令塔の指摘）。残りは独占の枠で行う。

### 1. `npm ci`の内訳（同じ作業ツリーで3回）

条件: `frontend/node_modules`を`cmd /c rd /s /q`で消してから（新しい作業ツリーと同じ状態）、
`npm ci --no-audit --no-fund --timing --loglevel=http`。Node 22.23.2・npm 10.9.8。
取り方: 所要は外側の時計、内訳は`--timing`の`*-timing.json`の`timers`、キャッシュの当たり方は
デバッグログの`http cache ... (cache hit)`行（集計スクリプトはscratchpad。リポジトリには置かない）。

| 回 | node_modulesの削除 | npm ci全体 | うち展開と書き込み（`reify:unpack`） | installスクリプト（`reify:build`） | 依存木の計算（`idealTree`） | tarballのキャッシュ |
|---|---:|---:|---:|---:|---:|---|
| base1 | 86.6秒 | 136.2秒 | 121.4秒 | 1.9秒 | 0.6秒 | 581件すべて命中、取得の合計53ms |
| base2 | 25.7秒 | 192.6秒 | 166.4秒 | 3.8秒 | 0.4秒 | （同上の形。集計の正規表現を直す前の回） |
| base3 | 41.8秒 | 193.7秒 | 185.2秒 | 1.2秒 | 0.4秒 | 581件すべて命中、取得の合計16ms |

**時間のほぼ全部（89〜96%）が、展開して32,880個のファイルを書く段階にある。**
ネットワークは0（全件キャッシュ命中、再検証の問い合わせも無い）、installスクリプトは
`unrs-resolver`のpostinstall 1本で1〜4秒。

### 2. 候補の比較（公式文書で確かめた事実＋ここまでの実測）

| 候補 | 公式文書で確かめたこと | 実測 | 見立て |
|---|---|---|---|
| `--prefer-offline` | npmの設定の説明: キャッシュの鮮度確認を省き、無いものだけ取りに行く（[config](https://docs.npmjs.com/cli/v10/using-npm/config)）。`npm ci`の文書はこの設定を挙げていない | 3回とも取得は全件キャッシュ命中で再検証が0件 | **効く余地が無い**（省ける問い合わせが元から無い）。測らない |
| npmのキャッシュの置き場を変える | 同上（`cache`） | キャッシュの読みは合計16〜53ms | 効く余地が無い |
| 作業ツリーの外に置いた「種」から実体コピー（`robocopy /MT:16`） | — | 35.3秒（c1）・61.8秒（c2）。32,880件 | **`npm ci`（136〜194秒）の約3分の1**。複製先は普通のファイルなので、`git worktree remove`・`rd /s`で消しても種は壊れない。T1042の「作業ツリーの中にリンクを作らない」も満たす |
| 種からハードリンク | pnpmの文書: ハードリンクでは`node_modules`のファイルが**ストアのファイルそのもの**で、編集すると同じパッケージをリンクした全プロジェクトが変わる（[packageImportMethod](https://pnpm.io/settings/node-modules)） | `os.link`で64.2秒（c2）。`cp -al`は983秒（上の失敗） | 実体コピーより速くならず、種を壊す経路が増える。**採らない** |
| pnpm | 既定の`nodeLinker: isolated`は`node_modules/.pnpm`からのシンボリックリンク（Windowsで開発者モードが無ければジャンクション、[FAQ](https://pnpm.io/faq)）。取り込みはハードリンク/コピー（上） | 未計測 | 取り込みはストアからのハードリンクかコピーで、上の2行と同じ「3万ファイルを作る」費用に縛られる。そのうえlockfile・CI（`setup-node`の`cache: npm`）・Dockerfileの移行が要る。単独の改善としては見合わない見込み。測るなら独占の枠で`corepack`経由 |
| Dev Drive | 最小50GBの空き・管理者権限・C:ドライブは不可。信頼済みのDev Driveでは Defender が「開いた後に非同期で走査」する性能モードになる（[Dev Drive](https://learn.microsoft.com/en-us/windows/dev-drive/)・[性能モード](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-endpoint-antivirus-performance-mode)）。npmのキャッシュを置く場所としても推奨されている | **C:の空きが8.08GB**（`Get-Volume`、2026-09-23）で、最小要件の50GBに届かない | いまは作れない。ユーザー判断事項（空きを作るか・別ディスクか）。設定は変えていない |

補足: 計測時点でOneDriveのプロセスは動いておらず、`node_modules`のファイル属性は`Archive`
だけ（プレースホルダではない）。OneDriveを動かすと、リポジトリ配下の`node_modules`
（作業ツリーごとに32,880件）が同期の対象になりうる。種を作業ツリーの外（OneDriveの外）に
置く理由の1つ。

### 3. `core.hooksPath`の書き換え（anthropics/claude-code#66993）

- issueは**"not planned"で閉じられている**。Claude Codeは作業ツリーを作るとき、共有の
  `.git/config`へ`core.hooksPath`を書く。
- 公式文書（[hooks: WorktreeCreate](https://code.claude.com/docs/en/hooks#worktreecreate)・
  [worktrees](https://code.claude.com/docs/en/worktrees)）で、**作る手順の側で避ける手段は
  `WorktreeCreate`フックで既定の作成を丸ごと置き換えることだけ**。置き換えると
  `.worktreeinclude`が処理されず、Claude Codeが作業ツリーへ書く目印（定期の片付けは目印の
  無い作業ツリーを残す）と実行中のロックも既定の側の仕組みなので失われる。つまり
  **T1042（作業ツリーが自動で片付かない）を悪化させる**。採らない方向。
- 作る側ではなく**フックを受ける側で無害にする**案: gitはフックを作業ツリーの最上位を
  作業ディレクトリにして実行するので、本体の`.githooks/pre-push`の先頭で「作業ツリー自身の
  `.githooks/pre-push`があり、自分と別物ならそちらへ`exec`する」ようにすれば、`core.hooksPath`が
  絶対パスへ書き換えられても各作業ツリーの版が走る。`.githooks/pre-push`はT1062の範囲なので、
  ここでは実装せず司令塔へ回す。

## 閉じ方（2026-09-23）

ユーザー決定（2026-09-23）:「作業ツリーは総数を決めて使いまわす。その作業ツリーの枠以上の
作業はできない規約にして、毎回コピーせず保持する」。作業ツリーを消さずに使い回せば、
`npm ci`は作業ツリーを作るたびではなく`package-lock.json`が変わったときだけになるため、
上の比較で第一候補だった「種からの実体コピー」も不要になる。独占の枠で予定していた
残りの計測（`npm ci`・種からの復元・作業ツリー作成から`tsc`まで）は行わない。

このタスクで分かったことのうち、後続が使うもの:

- `npm ci`の時間のほぼ全部はファイルの書き込み（`reify:unpack`）で、ネットワークと
  installスクリプトは無視できる。**速くする手は「書く量を減らす」しか無く**、
  キャッシュ・`--prefer-offline`の調整では縮まない。
- Dev Driveは C: の空きが公式の最小要件50GBに届かず、いまは作れない。
- `core.hooksPath`の書き換え（anthropics/claude-code#66993）は"not planned"で閉じられている。
  作る手順の側で避ける公式の手段は`WorktreeCreate`フックだけ。
- 作業ツリーの数・再利用・`core.hooksPath`の扱いは[T1066](T1066.md)が引き継ぐ。
