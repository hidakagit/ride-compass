# T1203. 事故密度の分母（年数）を、今の数え上げを作った取込から読み、取込から派生の作り直しまでの間も値がずれないようにする

状態: 未完了（2026-09-27起票）

## 背景

T1172で、取込の直後から派生の作り直しが終わるまで約1時間、事故密度が実際の約6分の1で出ると分かった。分母（年数）は取込の宣言から即座に変わり、分子（件数）は作り直すまで古いまま。本番DBの列を足すので規模L。

## 段階A（2026-09-27、担当 Y-years）: 件数と一緒に入れ替わる表へ年を置く、本番の手順

### 決めたこと（記録に残っていた選択。品質で決めた）

1. **年は、件数を数える段が同じトランザクションで派生の表へ書く**（新しい表`accident_count_years`: 系譜`source_run_id`＝数えた事故の取込、
   値`years`＝その取込の宣言の年）。派生の表なので作り直しの作業用のスキーマへ写り、件数と一緒に1つのトランザクションで入れ替わる。
   読み手は`public`の表を読むので、作り直しの途中は前の件数と前の年を、入れ替えた後は新しい件数と新しい年を読む。
   - 比べた案: `derived_data_meta`（世代の1行）へ列を足し、入れ替えのトランザクションで書く。数えた取込をPythonで入れ替えまで運ぶ
     必要があり、`derive_cli --from raster`のように数の段を飛ばした作り直しでは「書かない」分岐が要る。派生の表にすれば、段を飛ばしたときは
     前の行がそのまま写って入れ替わるので分岐が要らない。
   - 派生の表にしたことで、鮮度台帳（`GET /api/admin/derived-data/freshness`）が事故の取り直しを「古い」と出すようになった。今までは
     区間・道の表の系譜がOSMの取込を指すので、事故だけを取り直しても鳴らなかった。
   - 年の写しを持つか（`source_runs.profile`を系譜で引くか）: 値の列を持たない派生の表は鮮度台帳の不変条件（`test_値の列が1本以上ある`）に
     反し、取込の記録は書いた後に変わらないので写しが古くなることも無い。写して持つ。
2. **数えた取込は、数えた事故の行の`run_id`から取る**（最新の取込からは取らない）。同じトランザクションで数える文の後に読むので、
   間に取込が入れ替えても食い違わない——取込はパーティションをTRUNCATEで入れ替えて表の排他ロックを取り、数える文が取った共有ロックは
   トランザクションの終わりまで残る。
3. **地図の説明文の年も同じ値にする**（APIの`accident_years`は1本のまま）。説明文は事故の点のレイヤーの文言で、点のタイルは生データの
   行を読む。取り込み直してから作り直すまでの間、新しく焼いた点のタイルには説明文の年より先に新しい年の点が出る。点のタイルは
   派生の世代でキャッシュされるので、その間も焼き済みのタイルは前の年のまま——点の側はもともと取込と作り直しの間で混ざる
   （下の「範囲外で見つけたもの」）。密度と説明文が同じ年を言うほうを選んだ。

### 本番の手順（1.はユーザー、2.以降は司令塔。担当は本番へ書かない）

**既存DBを新しいコードが読めなくなる変更に当たる。** 新しいコードは表`accident_count_years`を読み（軸カタログ・道の詳細）、派生の
作り直しは表を作業用のスキーマへ写す——表が無いと、読み取りの失敗として扱われ、軸カタログは事故の年を空で配り（地図の事故密度が
すべて「データなし」になる）、道の詳細は何も返さず、作り直しは最初の写しで止まる。
順序は「本番DBの移行を先に済ませてからpush」（CLAUDE.mdの1)）。表を作るだけなら古いコードは何も変わらない（読まない・写さない）。

1. **masterへ入れる前に**、本番DBで表を作り、今の件数を数えた取込の行を入れる（`sudo -u postgres psql -d <DB名>`。DB名は
   `/home/ubuntu/ridecompass-backend.env`の`DATABASE_URL`の最後の部分）:

   ```sql
   BEGIN;
   CREATE TABLE accident_count_years (
       source_run_id BIGINT NOT NULL,
       years SMALLINT[] NOT NULL,
       PRIMARY KEY (source_run_id),
       FOREIGN KEY(source_run_id) REFERENCES source_runs (run_id)
   );
   ALTER TABLE accident_count_years OWNER TO ridecompass;
   INSERT INTO accident_count_years (source_run_id, years)
   SELECT r.run_id,
          ARRAY(SELECT y::smallint FROM jsonb_array_elements_text(r.profile->'source'->'rows'->'years') AS t(y))
   FROM source_runs r
   WHERE r.run_id = (SELECT run_id FROM source_features WHERE source = 'accident' LIMIT 1);
   SELECT source_run_id, years FROM accident_count_years;
   COMMIT;
   ```

   - 表の形はORMの宣言から`CreateTable`で出した文（`schema_gap.py`で開発DBと差が無いことを見た）。行を入れる文は数の段が書く文と同じ。
   - `postgres`で作るので、持ち主を他の派生の表と同じ`ridecompass`へ移す（本番の派生の表の持ち主が`ridecompass`であることは司令塔が
     確かめた）。派生の作り直しは表を消して作業用のスキーマの表と入れ替えるため、持ち主が違うとアプリの権限で消せずに止まる。
   - 実行はユーザー（司令塔の自動の操作では本番へ書けなかった）。同じ文に持ち主の確認を足した版が司令塔の
     `.git/orchestration/coordinator/T1203_prod.sh`にある。
   - 前提: 今の区間の事故の件数が、生データの事故の行（run 8）から数えたものであること。上の着手時の確かめで満たす（取込の完了
     01:44:48 → 数の段 01:56:49、件数の合計620,539）。**この手順と2.の間に事故の取込・派生の作り直しを挟まない**——古いコードの作り直しは
     この表を書き直さない。
   - 期待: `SELECT`が`8 | {2019,2020,2021,2022,2023,2024}`を返す。所要は一瞬（副問い合わせは1行で止まる）。
2. このコミットをmasterへ入れる（CIの後、backendが自動でデプロイされる。道路網の配列の形の署名は変わらないので、デプロイの前処理は
   配列を作り直さない）。
3. 確かめ:
   ```
   curl -fsS http://localhost:8000/api/axis-catalog | python3 -c "import json,sys; print(json.load(sys.stdin)['accident_years'])"
   ```
   `[2019, 2020, 2021, 2022, 2023, 2024]`。あわせて`python scripts/run_probe.py scripts/schema_gap.py`（手元から）が
   `accident_count_years`について差を出さないこと。次に派生を作り直したとき（`derive_cli`）、表の行が数えた取込を指し直すこと。
4. 取り消し方: コミットを戻してデプロイし、その後で`DROP TABLE accident_count_years;`。表を消すのはコードを戻した後（先に消すと、
   新しいコードの軸カタログが失敗する）。1.だけを済ませて2.へ進まない場合は、表を残しても古いコードに害は無い。

### 範囲外で見つけたもの

- 事故の点のタイルは生データの行を読むのに、派生の世代でキャッシュされる。取り込み直してから作り直すまでの間は、焼き済みの
  タイル（前の取込の点）と新しく焼いたタイル（新しい取込の点）が混ざる。作り直すと世代が進んで揃う。直さない: 年を変えて取り直すとき
  だけの約1時間で、点は生データをそのまま見せるもの。揃えるには前の取込の行を残す必要があり、取込の入れ替えの作りが変わる。
  挙動は`static-road-attributes.md`「事故の帰属」へ書いた。
- 同じ形（実行時に最新の取込の宣言を読み、組になる値は派生から来る）がもう1つある: `RoadGraphRepository.is_covered`（ルート生成の
  範囲判定）はOSMの最新の取込の枠を読み、探索は派生の配列を切り出す。OSMの取込の枠を広げてから作り直すまでの間、広げた場所は
  「範囲外」ではなく「候補が無い」になる（狭めたときは逆）。直さない: 枠を変える取込はまれで、その間の誤りは断りの種類だけ。
  路面タイルの範囲判定も同じ関数を読むが、タイルは生データの道を読むので最新の取込の枠と組になっていて正しい。
