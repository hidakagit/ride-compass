# T930: 直角に近い道路の勾配を、0%（平坦）として配っていた

状態: 完了（2026-09-18）

## 背景

ユーザー指摘: ある道路に対して方角を90度に向けると勾配0%、道に沿わせると15%以上になる。

`GradientCalculator.effective_gradient`は`gradient_percent × cos(道路の向き − 走行方位)`で、
直角では0になる。**0は凡例で「平坦」を意味する値として既に使われている**ため、実際には
急な坂である道が平坦な道と同じ色で塗られ、読み手はそれを区別できない。その向きについて
言えるのは「勾配を示せない」であって「平坦だ」ではない。

## 対応

`shows_gradient(road_bearing_deg, travel_bearing_deg)`が直角から
`LENS_PERPENDICULAR_BAND_DEG`（15度）以内の道路をFalseにし、`GradientWayService`が
その道路を結果から落とす。落ちた道路は既存の契約どおり「データなし」として塗られる
（`transform_dedicated_way_values`が評価できない値を落とすのと同じ扱い）。凡例にも
既に「データなし」の段があり、そこだけ消す操作もできる。

判定は角度そのもので比べる。cosの大小で比べると、直角の左右で浮動小数の差だけ判定が
食い違う（実際に105度が「示す」側へ落ちた）。

**幅の15度に根拠は無い**。実地の地図を見て決め直す前提の初期値で、そのことをコードの
コメントにも書いてある。

## 減衰そのものもやめた（2026-09-18、ユーザー判断）

直角に落ちる手前の減衰——15%の坂が60度ずれで7.5%と表示される——もやめ、**走行方位は
符号だけを決める**形にした。道路は道路に沿ってしか走れず、その道を走るときの進行方向は
道路の向きそのもののため、方位が決められるのは「どちら向きに辿るか」だけである。cos投影は
「道は東西に伸びているが自分は北へ進む」という、存在しない状態に対する値を計算していた。

ルート評価は`average_grade`をそのまま読む（`road_graph_engine.py`）ため、**同じ坂が
レンズとルート結果で違う値になる**非対称もこれで消える（非対称自体は[T511](T511.md)にも
記録がある）。

風（`wind_drag_ratio`）のcos投影は正しいままで触っていない——風向は進行方向と独立に
決まるため、角度差が実際に抗力を変える。

## 検証結果

- **既存テスト2件が落ちたことで、直っていることを確認できた**。どちらも直角の組み合わせで
  0.0が返ることを固定していた（`test_computes_effective_gradient_per_way`・
  `test_at_argument_is_ignored`）。新しい契約へ書き換えた。
- キャッシュの2件（同じ/違う向きバケット）は、直角のままだと結果が空になり「空同士で
  一致した」「空と非空だから違う」という値を見ていない検査になるため、どちらの走行方位でも
  直角に落ちない向き（30度）へ直した。
- 追加した検査: 直角は落ちる・沿う向きと逆走は残る・直角の左右で判定が対称・サービスが
  実際に落とす（`test_perpendicular_way_is_omitted_instead_of_zero`）。
- 減衰をやめた側も、**わざと戻して落ちることを確認**した（`math.cos(diff)`を掛ける形へ
  戻すと`test_magnitude_does_not_shrink_with_the_bearing`が落ち、戻すと19件通る）。
- 向きバケットのテストは、符号が変わらない組み合わせだと値が一致してしまうため、道路の
  向きを挟んで反対側の方位へ直し、あわせて実際に作り直していること（repositoryの
  呼び出し2回）も見るようにした。
- `pytest -q -m "not postgis"` 2,057 passed / `ruff check` クリーン。
