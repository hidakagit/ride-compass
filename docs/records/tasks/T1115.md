# T1115. 勾配の材料名の直書きをやめ、各所に書き写された同じ計算を1か所にまとめる

状態: 完了（2026-09-26）

## 背景

勾配だけが材料名を文字列で直書きし、綴りがずれると区間の表示から勾配が黙って消える。区間の鍵の書式2種類・経度1度あたりの距離4か所（極付近の下限の有無がばらばら）・地図タイル座標2か所・探索範囲の矩形がエンジン内部、と同じ計算が書き写されている。直書きを定数へ置き換え、重複は同じ意味かを確かめてから1か所へ寄せる。起票案 proposal-duplicated-calculations（T1112のクラウドのセッションの棚卸し、2026-09-26承認）

## 周期レビュー第13回の決定（2026-09-26、ダッシュボード T1115-review013 から移す）

同じ計算・直書きの母集団へ次を加える（明確なものはユーザーの包括承認）。

- スカラー版と配列版を別々に実装した関数の対が7組（`evaluate_axis_scalar`/`array`、`evaluate_axes_scalar`/`_evaluate_axes_from_material_arrays`、`composite_difficulty`/`compose_costs_from_axis_matrix`、`composite_contributions`/`axis_contributions_at_row`、`distance_weighted_difficulty(_array)`、`haversine_distance_km(_array)`、`bearing_between(_array)`）。規則は「スカラー版は配列版を長さ1で呼ぶ」（`wind_drag_ratio`の形）。等価だけを見るテスト4件（test_geo.py:83,121、test_wind.py:121、test_axis_hierarchy.py:328）は一本化で消す。0次条件の判定の食い違いはT1134が先に直した。
- 折れ点を通す前の生値の求め方が3実装（axis_definitions.pyのスカラー評価の中・`_breakpoint_raw_total_array`・axis_preview_service.pyの`_raw_value`）。コスト式の逆算が2か所に写し（road_graph_engine.pyの折返し点と目的地の並べ替え。本体はevaluation.py）。
- 材料idの直書きは勾配だけでなく4材料10件（gradient_percent×5、wind_drag_ratio×3、surface_good、accident_count_per_km_year）。evaluation.pyの`if material_id in MATERIAL_CATALOG`は本番で常に真で、綴りがずれると黙って全区間が舗装路扱いになる。較正値のid `stop.{kind}_seconds`の組み立てが2か所（tuning.py）。母集団はmaterial_catalog.pyのキーでカタログの外をgrepして出す。
- Webメルカトルのタイルの境界の写し3か所（_raster_wkb.py、landcover_raster.py、derive_raster_materials.pyのSQL）。
- 寄与の式（値×重み÷重みの和）がdifficulty.pyとevaluation.pyに2つ。
- T1008と同じservices/gradient_way_service.pyを触るので着手順を揃える（今回の変更は材料idの1行だけ）。

## 着手時の確認（origin/master dbff4573）

- 背景と決定に挙がった箇所は、行番号のずれ（T1134の後）を除きすべて残っていた。
- 材料idの直書きは、`MATERIAL_CATALOG`のキーをカタログの外からASTで列挙（文字列定数のうち値がキーに一致するもの、docstring除く）して34件。うち材料idとして読むのは決定の10件で、残りはOSMのタグ・タイルの列名（`highway`・`surface`・`oneway`・`smoothness`等）、土地被覆のクラス宣言（`landcover.py: LANDCOVER_CLASSES`の割合名。材料idとして引く箇所は無い）、区間の配列の属性名（evaluation.pyの検証メッセージ）。変更後の同じ列挙は24件で、材料idとして読むものは0件。
- 経度1度あたりの距離は4か所（road_graph_engine.pyの折返し点の近接判定・周回の矩形・経由地の矩形、routing.pyの最近傍索引）。下限`1e-6`を持つのは後の2つ。下限が効くのは緯度89.99994度より極側だけで、取込範囲（日本）では結果が同じ。意図の違いではなく割る側の保護の有無の差と判断し、下限を持つ1本（`geo.km_per_degree_longitude`）へ寄せた。
- 「区間の鍵の書式2種類」は、探索の有向の辺の鍵`way-<way>-seg<n>-fwd`（`graph.edge_key`）と、路面タイルのフィーチャーの鍵`<way>-<n>`（向きを持たない。SQLで組み立て、区間インスペクタが読み戻す）。意味が違う（向きの有無）ため1つの書式にはせず、置き場を`domain/graph.py`へ揃えた（SQLの式も同じ区切りの定数から組み立てる）。

## 対応

| 項目 | 寄せた先 |

| 材料idの直書き（10件） | `material_catalog.py`のid定数（`GRADIENT_PERCENT`等）。カタログのキーにも同じ定数を使う。`material_sql.MATERIAL_ID_GRADIENT_PERCENT`は削除。常に真だったカタログの有無の判定を削除 |
| 較正値のid | `tuning.stop_seconds_parameter_id`を宣言側も使う |
| 経度1度あたりの距離 | `geo.km_per_degree_longitude`（下限あり） |
| 探索範囲の矩形 | エンジンの`_bbox_around_point`・`_bbox_covering_points`を`region.bbox_covering_points`1本へ移した（円を覆う矩形は1点を覆う矩形と同じ式）。エンジンの構造は変えていない |
| Webメルカトルのタイル境界 | `region.tile_bounds_3857`・`WEB_MERCATOR_HALF_M`。派生バッチのSQLは`region.tile_position_sql`（`_lonlat_to_tile_index`と同じ式）から組み立てる |
| 区間の鍵 | タイルの鍵の組み立て（SQL）と読み戻しを`graph.py`へ |
| 軸1本の評価の対 | `evaluate_axis_array`1本。Pythonの値で持つ入口は`evaluate_axis_values`（値の並びを配列へ並べ替えて通す）。`evaluate_axis_scalar`と、それだけが使っていた`evaluate_categorical`のスカラー分岐（とそのテスト）は削除 |
| 全軸の評価の対 | `evaluate_axes_array`（依存順の評価）1本を、ルート選び（`_evaluate_axes_from_material_arrays`）と`evaluate_axes_values`（区間インスペクタ・飽和度の計測）が共有。`evaluate_axes_scalar`は削除 |
| 合成・寄与度の対、寄与の式 | `difficulty.composite_difficulty_array`・`axis_contributions_at_row`（evaluation.pyから移した）。区間インスペクタの`difficulty.composite_difficulty`はこれを長さ1で通す（合成と寄与度を一緒に返す） |
| 生値の3実装 | `_breakpoint_raw_total_array`1本。分布プレビューは`raw_values`で標本全体を1回で求める |
| コスト式の逆算 | `evaluation.difficulty_from_cost`（式の本体の隣） |
| 距離・方位の対 | 1点の版は配列版を通す |
| 地図の値配信（専用way値） | 値ごとの評価をやめ、タイル内の全道路を1回の配列評価 |

### 残した対: 距離加重平均（`weighted_mean_by_distance` / `distance_weighted_difficulty_array`）

区間の並び（Pythonの値）を配列へ並べ替えて配列版を通すと、1呼び出しの所要が増える（開発機で計測、区間1件 0.21→7.41µs、5件 2.08→10.51µs、20件 4.21→13.75µs、200件 32.68→45.22µs）。呼び出し元はルートの区間を約500mのビンへ畳む集約（ビンごと・軸の得点／寄与度／生値／材料値のキーごと）と候補単位の集約で、1生成あたりの呼び出し回数は測っていない（司令塔の指示どおり、測れないため問いにはせず2本のまま残す）。同じ規則（値の無い区間は分母からも外す・距離の合計が0以下ならNone）は`docs/modules/backend/evaluation-scoring.md`「ルート単位の集約」に書いた。

1点の距離・方位は配列経由で1呼び出しあたり約+2〜3µs（haversine 1.07→2.77µs、方位 1.01→3.86µs）。呼び出し元は折返し点ごと・経由地の検証・NaNの方位の補完で、最も多いのは最寄りのアメダス観測所の探索（観測所の数だけ呼ぶ。`jma_amedas_service.py`、観測所千数百として1回あたり数ms増える見込み・未計測）。寄せたうえで、探索を配列版1回へ替えるのは並行担当（B-decl、T1140）がjma_amedasを触っているため今回は見送った。

### 丸めと加算について

合成の和の補償加算（`_neumaier_accumulate`）と`round1_array`の理由は「スカラー版とビット単位で一致させる」だったが、スカラー版が無くなったため、理由を「誤差の積み上がりで.X5境界の最終丸めが倒れる側を変えない」「2進の実際の値で丸める」に書き直して残した。合成に使わなくなった`compose_costs_from_axis_matrix`の`base`省略時の分岐（距離を下地にして0.1m単位へ丸める。削除済みのスカラー版のオラクルに合わせるためのもの）は、呼び出し元が常に`base`を渡しているため削除した。
