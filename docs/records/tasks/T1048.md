# T1048. CIのbackendが並列実行で時々database is lockedになる——ディスクキャッシュの差し替えがautouseの宣言順に頼っている

状態: 完了（2026-09-23）

## 背景

2026-09-23、masterのCI（0e39c422、コメントと文書だけの変更）でbackendが1件ERRORになり、次のコミットでは緑に戻った。失敗はtests/structure/test_canonical_definitions.py::test_loggers_use_the_documented_prefixのセットアップで、_clear_tile_score_matrix_cache → tile_score_matrix_cache.clear → tile_persistent_cache.clear_namespace → diskcache.Cache(...)の索引作成がsqlite3.OperationalError: database is locked。conftest.pyの一時ディレクトリへの差し替えフィクスチャは『pytestは同scope・同conftestのautouseを宣言順に近い順でセットアップする』ことに頼っており、順序が崩れると共有のbackend/data/tile_persistent_cacheをxdistのワーカー間で開き合う疑い（未検証）。赤が残るとCIの赤を本物と見分けられなくなる。

## 原因（確定）

**前提そのものが誤っていた**。pytest 8.3.4は同じスコープのautouseフィクスチャを`dir()`で
集める（`_pytest/fixtures.py`の`parsefactories`、`for name in dir(holderobj)`）ため、
**宣言順ではなく名前の辞書順**でセットアップする。`_clear_tile_score_matrix_cache`は
`_use_temp_tile_persistent_cache_dir`より名前が先なので、

- セットアップ: 差し替え**前**に`clear()`が走り、`clear_namespace`が`diskcache.Cache`を開く
- 片付け: 差し替えを元へ戻した**後**に`clear()`が走る

つまり順序が「崩れると」ではなく、**全テストが前後で必ず共有の
`backend/data/tile_persistent_cache`を開いていた**。xdistのワーカー同士がそこで同じSQLiteを
開き合い、索引作成の瞬間が重なると`database is locked`になる。

確かめ方:

- `pytest tests/structure/test_canonical_definitions.py::test_loggers_use_the_documented_prefix --setup-plan`
  で、`_clear_tile_score_matrix_cache`が`_use_temp_tile_persistent_cache_dir`より先にSETUPされ、
  後にTEARDOWNされることを表示した。
- `backend/data`が無い作業ツリーで上のテスト1本（キャッシュに触れないテスト）を回すと、
  `backend/data/tile_persistent_cache/cache.db`ができた。

## CIでの実績

GitHub APIで直近300ラン（2026-09-13〜09-23）のbackendジョブのログを走査した。
`database is locked`は**3件**（0e39c422・184b11a9・fe0b46aa）、どれも`tests/structure/`の
テストのセットアップ（`test_canonical_definitions.py`・`test_layer_imports.py`）。
同じ走査で`IntegrityError`は0件（[T415](T415.md)の切り分けに使う）。

## 再現

**この開発機（Windows、8論理コア）ではロックの競合そのものは再現しなかった**。CIの失敗は
上の3件のログを根拠にする。手元で測ったのは「共有ディレクトリへ届くか」である。

- 手順: `backend/data`を消してから`PYTHONUTF8=1 pytest -q -n auto --dist loadgroup tests/structure`
  を1回とし、3回繰り返す（CIのチェックアウト直後と同じく置き場が無い状態から始める）。
- 修正前: `database is locked` 0/3、共有ディレクトリへの到達 **3/3**
- 修正後: `database is locked` 0/3、共有ディレクトリへの到達 **0/3**
- 機構だけの再現（4プロセスが同じ新規ディレクトリのdiskcacheを`tag_index=True`で同時に開き、
  削除と書き込みを20回ずつ繰り返す）も10試行で0件だった。Linux（CI）でだけ起きる理由は
  未確認のまま（SQLiteのロックの実装がOSで異なる）。修正は共有の置き場へ届かないことを
  保証するので、ロックが起きる条件の特定には依らない。

## 対応

- `conftest.py`へセッションスコープの差し替え`_keep_tile_persistent_cache_out_of_the_checkout`
  を足した。**セッションスコープは関数スコープより必ず先にセットアップされ、後に片付く**
  ため、関数スコープのフィクスチャがどの順で動いても共有の置き場へは届かない
  （テストファイル側の`clear()`を呼ぶフィクスチャも含めて）。
- 関数スコープの`_use_temp_tile_persistent_cache_dir`は、片付けで元の実ディレクトリではなく
  ワーカーの置き場へ戻す。テストごとに空の置き場を渡す役割はそのまま。
- `_clear_tile_score_matrix_cache`と`test_derived_data_revision_service.py`の`_reset`は、
  差し替えを**引数に取って依存で順序を書く**。
- `test_tile_score_matrix_cache.py`の`_clear_around_each_test`は、conftestの
  `_clear_tile_score_matrix_cache`と中身が同一の重複だったため削除した。
- `docs/conventions/testing.md`パターン5の末尾へ「フィクスチャ同士の順序は依存で書く。
  同じスコープのautouseは名前の辞書順」を追記した。

## 検証

- `--setup-plan`で修正後の順序を表示: セッションの差し替え→`tmp_path`→関数の差し替え→
  `_clear_tile_score_matrix_cache`の順にSETUPされ、片付けは逆順。
- 上の再現手順3回: 共有ディレクトリへの到達0/3。
- 届くテスト（`test_tile_score_matrix_cache.py`・`test_derived_data_revision_service.py`・
  `test_graph_material_cache.py`・`test_tile_persistent_cache.py`・
  `test_tile_persistent_cache_prune.py`・`test_cache_generation.py`・`tests/structure`）を直列で1回。
- CIでの効果（`database is locked`が出なくなるか）は、この修正がmasterへ入った後のランで見る。
