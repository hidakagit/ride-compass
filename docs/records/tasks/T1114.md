# T1114. テスト規約に「確かめる高さ」を定め、カバレッジを「下げない」から「下げたら理由を書く」へ改める

状態: 完了（2026-09-26起票・同日完了）

## 背景

（起票案 proposal-test-height-and-coverage の本文。T1112 段階3b-2のクラウドのセッションがユーザーとのやり取りから
起こし、2026-09-26承認）

ルート生成の作り替え（T1112）で、中身の途中の手順を確かめるテスト130件は作り替えを越えられず消すしかなかった。一方、
完成した結果（公開の入口）を確かめるテスト7件は、渡し口1か所を直しただけで本体は変えずに通った。同じことはテスト規約
自身も記録している（旧テスト2,982行が型3つの撤去で全滅した）。

バックエンドとテストの棚卸し（読み取りのみ）では、テストからの内部名（`_`で始まる名前）への参照が149件、本番コードに
残るテスト専用の口が関数約10件・引数4件あった。差し替え（`monkeypatch.setattr`）150件を機械で分けると、88件（59%）は
「対象モジュールがimportした他モジュールの関数・定数を、対象の名前空間で差し替える」形だった。

### 規約のどこが押しているか（docs/conventions/testing.md、起票時点＝origin/master 3581dd0e の行番号。着手時に一致を確認）

1. 361〜363行「他モジュールの関数・サービス・例外・定数は対象の名前空間経由で触る」→ 上の88件の形をそのまま指示している。
2. 85〜107行「実装だけを読み、分岐・and/orの各項まで列挙し、分岐カバレッジで穴を塞ぐ」「起こし直す前の値を下げない」→
   テストが実装の構造の写しになる。規約は別の場所で「カバレッジは目標にしない」と書いているが、手順の「下げない」の
   ほうが実際には効き、Aで書き直して下がった分をBで埋めに行かせる。
3. 226〜229行「autouseで配ってよいのは大域状態の初期化」→ 初期化のための口がappに要り、構造仕様15「appはテストの都合を
   意識した口を持たない」と食い違う。

逆向きの条文（公開の入口で振る舞いを確かめる）は規約に1つも無い。

### 起票案の直し方

- 確かめる高さの原則を足す: 振る舞いはモジュールの公開の入口で確かめる。内部名へ直接入るのは、入力を値・配列で直接
  与えられる計算に限る。入口から条件を作りにくい場合は、その計算を小さな部品へ切り出してから確かめる。
- 1を改める: 差し替えてよいのはプロセス境界（網・ディスク・時計・外部サービス）に限る。自分のdomainの関数（走行モデル等）は
  本物を通す。
- 2を改める: 列挙の単位を分岐ではなく、公開の入口から見える振る舞いにする。カバレッジは見落としを探す道具としてだけ使い、
  「下げない」を「下げた箇所ごとに、なぜ見なくてよいかを1行書く（書けなければ見落としとして扱う）」へ変える。
- 3と構造仕様15の食い違いをどちらかに決める（大域状態を持たない形へ寄せるか、片付けの口だけを例外として明記するか）。
  決める場所だけで、既存の口を撤去する作業は含めない。
- 規約を新設したら、それに従って1本書き直して読んでから確定する（CLAUDE.md「修正の原則」）。候補は合成器のテスト
  （走行モデルを14件差し替えている）。

T998（テストを実装から起こし直す）は今の規約の手順を各ファイルへ当てる作業で、この案は手順そのものを変える。T998の残りは
新しい規約で進めることになる。

含めないもの（別の起票案にする予定）: 黙って既定値に倒す処理の洗い直し、本番に残るテスト専用の口の撤去、勾配の材料名の
直書きと重複の整理、内部依存の強いテスト3本の置き換え。

## 対応

- testing.md に「確かめる高さ」節を新設（入口で確かめる・内部名は値で与えられる計算だけ・入口で作りにくければ部品へ
  切り出す・差し替えはプロセス境界と契約の狭い層の境目と宣言のデータだけ・自分の関数を記録用に包まない）。
  差し替えの許容範囲は起票案の「プロセス境界だけ」より広げた——同じ文書の「フェイクの数は…」節が層の境目（注入される
  Service）を「契約が狭いときだけ」許し、「テストは、テストだけで成立させる」節がカタログ等の宣言データの差し替えを
  求めているため、それと食い違わないようにした。
- 手順1: 列挙の単位を振る舞いへ。`if`・`and`/`or`等の列挙は「見落としを探す手がかり」へ格下げし、入口から見えるかへ
  言い直して列挙する形に。
- 手順3・「カバレッジは目標にしない」: 「下げない」を撤去し、「下がってよい、下がった箇所ごとに理由を1行、書けなければ
  見落とし」へ。
- 名前空間の条文（旧361〜363行）: 他モジュールの関数・定数は触らない。差し替えは「確かめる高さ」が許すものだけ、その
  ときに対象の名前空間で。
- autouseと構造仕様15: **大域状態を持たない形へ寄せる側に決めた**。片付けは本番コードが既に持つ操作（`clear()`・
  `monkeypatch`での一時差し替え）だけで書き、appへ片付けの口を足さない。本番の操作で片付けられない大域状態は実装側の問題
  として扱う。既存の口の撤去はそのモジュールを触るときに行う（起票案どおり撤去作業は含めない）。
- CLAUDE.md「テスト方針」へ要点1行。

### 規約に従って書き直したテスト1本

起票案の候補（合成器のテスト＝`test_road_graph_engine.py`）はT1112（ルート生成の作り替え、別セッションで作業中）の範囲と
重なるため避けた。重ならないものから、自分のdomainの関数・定数を対象の名前空間で差し替えている形を
`grep -n 'monkeypatch.setattr([a-z_]*, "[a-z]' backend/tests/*.py`（ルート生成・Redis・設定・網を除いた25行）から選び、
`backend/tests/test_weather_route.py`の詳細格子の上限2件（対象 `app/api/routers/weather.py` の `get_wind_grid_detail`）を
書き直した。

- 上限ちょうど/1つ超え: 旧版はルーターの名前空間で定数`WIND_GRID_DETAIL_MAX_POINTS`を差し替えて境界を作っていた。
  新版は本物の定数から「1行×上限ちょうどの列」の範囲を組み立てる（端を格子点の中間に置いて浮動小数の揺れを避ける）。
- 広すぎる範囲の拒否: 旧版は`generate_wind_grid_detail_points`をルーターの名前空間で記録用に包み「点を作らない」を
  確かめていた。新版は入口の結果（400と文言・天候サービスへ問い合わせない）だけを確かめる。
  **「作る前に断る」という順序は入口から観測できないので確かめなくなった**（範囲は`WIND_GRID_BBOX`へクリップされ、
  最小間隔で全域でも約98万点に収まるため、作ってしまっても応答は返る。止まるのはイベントループの秒単位の停滞で、
  時間でしか見えない）。理由はルーターの該当行の隣のコメントが既に持つ。これは規約の変更で見なくなる実例として、
  規約の条文（「入口の結果に現れないなら、テストでは確かめず、理由を実装の隣のコメントが持つ」）へそのまま反映した。
- 読んだ結果: 書き直した2件は対象の名前空間を1度も差し替えず、ファイルから`monkeypatch`が消えた。境界のテストは
  上限の値が変わっても（格子の幅に収まる限り）直さずに通る形になった。規約の文言どおりに書いて歪みは出なかったが、
  上の「順序の約束」は規約だけでは判断が決まらなかったため条文を足した。
