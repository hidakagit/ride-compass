# T976. 基礎地図タイルを第0層から出す 規模M

状態: 完了（2026-09-23、済み・不要として閉じる）

未着手（2026-09-20起票）。**段階D（関東再構築）より前に決めること。**

## 背景

`openfreemap_tile` アダプタが取り込む基礎地図のベクタタイルは、`source_features` の
`basemap` パーティション（第0層）に入っている。タイル1枚が1行で、`payload` にpbfの実体、
`geom` にタイルの範囲（POLYGON）、`attrs` に z/x/y と配信元のURLテンプレートを持つ。

**第0層の他のソースはすべて派生の入力になっている**（DEM→標高、LULC→土地被覆、OSM→道路網、
事故→件数）。基礎地図タイルだけは何も導出せず、ブラウザへそのまま流すだけの描画資材である。
それが取込のrun・鮮度・カバレッジの仕組みを丸ごと背負っている。

## 規模（2026-09-20実測）

- 開発DB（都心のみ）: 30枚 / payload **18 MB**（平均 614 KB/枚）
- `source_profile.yaml` の `target.bbox = [34.9, 138.4, 37.2, 140.9]`（関東）を
  z14（配信元のmaxzoom、プロファイルの指定値）で覆うタイル数: **15,065枚**
- 上の平均で換算すると **約 8.8 GB**

比較のため、現行の `road_edges`（有向枝5,065,850行・索引込み）が **3,719 MB**。つまり
**第0層で最大の表が、何も導出しないタイルの複製になる**。

**この数字の但し書き**: 614 KB/枚は開発DBの都心30枚の平均で、密度が高い側に寄っている。
山間部・海域のタイルは軽いため関東全域の実値はこれより下がる。正確な値は取り込まないと
分からないが、桁の判断には足りる。

**まだ起きていない**——本番は旧スキーマのままで `source_features` が無い。段階Dで
関東を再構築した瞬間に作られる。

## DBに持つ基準に該当しない

T970で決めた基準は「**手動で置き換えるもの。一般的に1年以上は陳腐化しないもの**」である。
基礎地図タイルはこれを満たさない。

- OpenFreeMapは[公式ページ](https://openfreemap.org/)で「We also provide **weekly** full
  planet downloads」と書いており、タイルは週次で焼き直されている
- 元になるOSMは[公式ページ](https://www.openstreetmap.org/copyright)によれば1日300万編集

実際に取り込んでいる7ソースのうち、基準を外れるのはこれだけである。

| ソース | 更新の周期 | 基準 |
|---|---|---|
| OSM（我々の抽出） | 手動で取り直す | 該当 |
| DEM | ほぼ静的 | 該当 |
| 土地被覆 | 年1回 | 該当 |
| 事故統計 | 年1回 | 該当 |
| 指定路線 | 数年に1回 | 該当 |
| **基礎地図タイル** | **週次で焼き直される** | **該当しない** |

## 第0層の他のソースと内容が重複する

OpenFreeMapは公式ページで「The map data comes from **OpenStreetMap**」と明記している。我々は
別途OSMを取り込んでいるため、**道路網が2つの形でDBに在る**。

- `source_features(osm_way)` — 我々の抽出。ノード列・タグ付きで、導出の入力になる
- `source_features(basemap)` — 同じOSM由来の道路をz14向けに一般化してタイルへ焼いたもの

タイルにはさらに建物・水域・土地利用・地名など**我々が取り込んでいない層**も入っており、
8.8GBの大半はそちらと見られる（未検証。1枚デコードして層ごとの内訳を測れば確かめられる）。

## 決めること

1. **DBから出す**。上記のとおり基準を満たさないので、残す場合はその理由を書くこと。
   [docs/conventions/caching.md](../../conventions/caching.md)の「保持層は共有範囲×寿命の2軸で選ぶ」「失っても自前の
   PostGISから復元できるものはプロセス内かディスクへ置く」に照らしても、配信元から取り直せる
   ものをDBへ置く理由が要る
2. 置き場所（ファイルシステム／オブジェクトストレージ／配信元へ直接）。DBを離れると鮮度・
   カバレッジの仕組みから外れるので、「古くなったことをどう気づくか」を代わりに決める。
   週次で焼き直されるものを我々が何か月も抱えると、地図だけが古くなる
3. z14で全域を持つ必要があるか。実際に利用者が見るズーム・範囲の分布を測ってから決める
4. 取込パイプライン（`openfreemap_tile`アダプタ・`source_profile.yaml`のエントリ）を
   どうするか。第0層を離れるなら、アダプタの枠組みに乗せる理由も無くなる
