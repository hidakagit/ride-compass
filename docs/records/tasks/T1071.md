# T1071. 並行実行の道具がCIの結論を認証なしのAPIで読み、上限（1時間60回）に当たる

状態: 完了（2026-09-23）

## 背景

並行実行の道具（scripts/orchestration/core.py の audit の「CI」の項、scripts/check_master_ci.py）と規約（docs/conventions/orchestration.md「完了とpush」の3.）は、GitHub の Actions の結論を認証なしの API で読む。認証なしは接続元のIPごとに1時間60回まで（docs.github.com の REST API rate limits）で、開発機の全エージェントと司令塔が同じ枠を使う。2026-09-23、担当が2回この上限に当たり（R7: HTTP 403、R7のaudit: 「CIの結論を取得できない」）、R7は途中から自分で git credential fill のトークンを使う認証付きへ切り替えた。司令塔の手元の補助スクリプトも同じくトークンを使っている。

対応方針: CIの結論を読む処理を1か所（scripts/orchestration/ の関数）にまとめ、git credential fill のトークンがあれば Authorization: Bearer を付け、無ければ認証なしで読む。トークンを出力・ログ・例外文に出さない。リダイレクト先（ログのダウンロード等）へ認証ヘッダを渡さない（GitHub の公式文書でリダイレクトの扱いを確かめる）。audit と check_master_ci.py と規約の手順3をそれを使う形に直し、規約から「認証なしで読める」「60回」の注意を実態に合わせて書き直す。

完了条件: 認証付きの問い合わせで X-RateLimit-Limit が認証なしの60より大きいことを応答ヘッダで確かめる。トークンが取れない環境（credential が無い）でも認証なしで動くことを確かめる。トークンが出力に出ないことを、わざと例外を起こす入力で確かめる。

## 実施内容

- `scripts/orchestration/github.py`（新設）: GitHubのREST APIを読む1か所。`git credential fill`
  （`GIT_TERMINAL_PROMPT=0`・`GCM_INTERACTIVE=never`で聞き返させない。10秒で打ち切り）でトークンが
  取れれば`Authorization: Bearer`を付け、取れなければ認証なしで読む。失敗はトークンを含まない
  短い理由（`HTTP 403`・`URLError`等の型名）だけを返し、例外を外へ出さない。
  `python scripts/orchestration/github.py`で今の枠（認証の有無・上限・残り）を出す。
- **リダイレクト**: GitHubの公式文書（REST APIのベストプラクティス）は「どの問い合わせもリダイレクト
  されうる。301/302/307はLocationへ問い合わせ直す」とし、ワークフローのログのダウンロードは
  1分で切れる別のURLへの302である。一方、Pythonの`urllib`のリダイレクト（3.12の
  `HTTPRedirectHandler.redirect_request`）は、内容の見出し以外を全部新しい要求へ写す——普通の
  見出しで付けたAuthorizationは、別のホストへもそのまま渡る。そこで`add_unredirected_header`で
  付けた（リダイレクトで作り直す要求へ写されない）。
- `scripts/check_master_ci.py`の`fetch_runs`と、`scripts/orchestration/core.py`の監査の「CI」の項が
  これを使う。監査は取得できないときに、理由・認証の有無・残りの枠を出す。
- 規約`orchestration.md`「完了とpush」の3.を、この関数と監査コマンドを使う形に直し、「認証なしで
  読める」「60回」の注意を実態（トークンがあれば認証付き、無ければ認証なし）に合わせた。
