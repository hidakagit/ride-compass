# T574: refresh_derived.py実行後にタイル永続キャッシュ版数が上がらず本番へ反映されない

状態: 完了（2026-09-04起票・同日完了）

## 背景

2026-09-04、T552（重み付き軸の欠損比率計測）の一環で本番へ`refresh_derived.py`
（[T281](T281.md)段階2）を実行したところ、DB側（`edge_attribute_counts`等）は
更新されたにもかかわらず、実際のルート生成が改善を反映しないという不具合を発見した。

原因は`refresh_derived.py`が`graph_material_cache.py`・`tile_score_matrix_cache.py`の
コメントに既存記載されている運用ルール（precompute系バッチ実行後は
`TILE_MATERIALS_CACHE_VERSION`・`TILE_SCORE_MATRIX_CACHE_VERSION`を手動で上げる）に
従っていなかったこと。`refresh_derived.py`はこれらのバッチ（
precompute_edge_attribute_counts・precompute_elevation_attributes・
precompute_road_node_degrees・precompute_way_attribute_counts）をまさに実行する
オーケストレーションスクリプトだが、実行後にバージョン文字列を上げる処理も、
上げ忘れを検知する仕組みも持たない。

## 対応方針

コード側でこの版数管理を自動化する（`refresh_derived.py`実行時に自動でバージョンを
書き換える等）のではなく、既存の`ROAD_SURFACE_TILE_VERSION`と同じ「手動で上げる」
運用方針をそのまま踏襲した。理由: このプロジェクトの派生データキャッシュは
版数を上げるべきタイミングが「precomputeバッチの実行」だけでなく「保存形式・
構築ロジック自体の変更」（コードレビューでしか判断できない）も含むため、実行時の
自動判定では原理的に不十分。手動運用を機械的に補強する形（コメントへの明記・
docs/disaster-recovery.mdの運用手順化）で対応した。

## 実施内容（2026-09-04完了）

- `graph_material_cache.py`: `TILE_MATERIALS_CACHE_VERSION`を"2"→"3"。
- `tile_score_matrix_cache.py`: `TILE_SCORE_MATRIX_CACHE_VERSION`を"1"→"2"。
- 両ファイルの「以下を実行したときはこの値を手動で上げること」コメントへ
  `app/batch/refresh_derived.py`を実行した場合も対象であることを明記。
  あわせて、上げ忘れた場合の実際の影響範囲（プロセス再起動をまたいでも
  ディスク経由で古いタイルが復元され続け、未訪問タイルだけ新しい値になる
  ——「一部だけ更新されたように見える」ため気づきにくい）を正確な記述へ修正
  （旧コメントは「次回デプロイでプロセスが再起動した瞬間」とだけ書いており、
  稼働中プロセスでも未訪問タイルなら即座にディスクフォールバック経由で
  古い値を掴む点が抜けていた）。
- `docs/disaster-recovery.md`「4. refresh_derived.py」節へ、定常運用（稼働中DBへの
  実行）の場合は完了後に両バージョンを同一コミットで上げてpushすることを明記
  （新規/被災環境のbootstrap直後はディスクキャッシュが元々空のため対象外と明記）。
- 本番の`tile_persistent_cache`（materials・score_matrix、449MB）はユーザー承認を得た上で
  `sudo rm`により手動クリア済み。クリア後、未ウォームなbbox（大宮駅30km）で再計測した
  ところ`missing_axis_distance_ratio`が0.698→0.132へ改善したことを確認し、原因特定が
  正しいことを実地検証済み（詳細は[T552](T552.md)参照）。
- バージョン文字列の変更はpush後にdeploy-backend.ymlの自動デプロイで本番backendが
  再起動され、新世代のディスクキャッシュ運用に切り替わる（今回手動クリアした分は
  既に解消済みだが、今後同種のバッチ実行時に同じ手順を踏み忘れても、この版数上げ
  自体は今回のコミットで完了しているため無関係）。
