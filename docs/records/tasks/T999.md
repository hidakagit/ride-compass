# T999. ジョブの保持時間とフロントの待機上限が、コメントだけで結ばれている

状態: 未完了（2026-09-22起票）

## 背景

ルート生成の非同期ジョブは、backendが`_JOB_TTL_SECONDS`（`app/infrastructure/job_registry.py`）
のあいだ結果を持ち、frontendが`MAX_POLL_DURATION_MS`（`src/services/routeApi.ts`）まで
ポーリングする。**前者は後者以上でなければならない**——短いと、まだ待っているフロントが
掃除済みのjob_idを引き、10分待った末に結果ではなく「ジョブが見つかりません」を見る。

いまは両方600秒で、ちょうど境界に立っている。この制約は`job_registry.py`のコメントに
1行あるだけで、frontend側には何も書かれておらず、検査も無い。frontend側だけを
延ばす変更は、何も落とさずに通る。

## 対応方針の候補

- frontendの待機上限を、ビルド時生成物（`route-generate-config.json`の`client_tuning`）
  経由でbackendの宣言から受け取る。既に`splice.min_stretch_km`が同じ経路を通っており、
  新しい仕組みを足さずに済む（`frontend/src/hooks/useAxisCatalog.ts`の`CLIENT_TUNING_IDS`）。
- そこまでせず、backend側のテストで`_JOB_TTL_SECONDS`と生成物の値の関係だけを固定する。

どちらにするかは着手時に決める。**両方に数字を書いたまま「揃えること」とコメントで
書くのは対象外**——いまと同じ状態になる。

## 完了条件

frontendの待機上限を延ばす変更を1つ書いてみて、**検査が落ちる**ことを確認する
（CLAUDE.md「修正の原則」——効いていることを見てから完了にする）。
