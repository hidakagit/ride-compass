# T958: 評価が要求する形のまま読める区間テーブルを持つ

状態: 完了（2026-09-26、前提が消えたためクローズ）

未着手（2026-09-19起票。採番時にT957が並行セッションと衝突し、T958へ振り直した。**トリガー: [T956](T956.md)完了後に冷パスを再測定し、残りがまだ問題になる場合**）

## 背景

探索が要求するのは常に「あるz12タイルの全区間の材料」という単一の形なのに、それを毎回
`road_edges`へ属性テーブル群をLEFT JOINし指定路線を相関EXISTSで判定して組み立てている。
本番実測で、同じ結果を1テーブルから走査すると2,052ms→800ms（[T955](T955.md)）。

書き込み側がバッチごとに分かれているのは正しい。用意していないのは**読み出しの形**である。

詳細はこのファイルへ追記する。

## これは効率化ではなく、仕組みを1つ増やす提案である

[T955](T955.md)の段階A（[T956](T956.md)）が既存の経路を効率化するのに対し、こちらは
**新しい派生テーブルを1つ増やす**。増えるのは実体だけでなく、「どのバッチが走ったら
これは古いか」の判定で、これは`docs/modules/backend/batch-pipeline-dependencies.md`が書いている
「派生データの取り残しで軸が黙って抜け落ちる」クラス（T74・T101・T242の本番障害）である。

稼ぎは1タイルあたり約800ms（SQL 2,052ms→800ms、本番実測）。段階Aが7,830ms→約3,100msを
稼ぐのに対する上乗せ分でしかない。**段階Aの後に実測してから判断する**（ユーザー判断）。

## 誰が冷パスを測るか（2026-09-23、[T1028](T1028.md)）

条件の前半（[T956](T956.md)完了）は成立済み。T956が残した冷パスの値は「同一実行内の比
3.6倍／5.0倍」だけで、[T955](T955.md)の表と比べられる1タイルの絶対値（ms）が無い。
**測るのは親の[T955](T955.md)**——T955の完了条件へ「段階A後の冷パスを本番で測り直し、
本タスクの要否をここへ書く」を足した。T955がその値で判定するまで本タスクは未発火のまま。

## T955の判定（2026-09-23）: 条件は成立、着手の可否はユーザー判断で保留

[T955](T955.md)が段階A後の冷パスを本番コンテナ内で測り直した（測り方と表はT955
「段階A後の冷パス」）。

| | 段階A前 | 段階A後 |
|---|---|---|
| 1タイル（約4万区間、3巡の中央値） | 7,830ms | 2,751〜3,401ms |
| うちB（材料のSQL＋転送） | 2,575ms（SQL）＋1,432ms（Python） | 1,376〜1,391ms（SQL）＋約140ms |
| うちA（トポロジ） | 1,566ms | 1,225〜1,895ms |
| 1リクエスト（z12を4×4枚、約55万区間）の材料段 | 160,469ms | 42,099〜52,892ms |

**残りはまだ問題である**（冷えた範囲を最初に見る利用者が42〜53秒待つ）。本タスクの
トリガー「残りがまだ問題だと判定した場合」は成立した。

**ただし本タスクの範囲（Bの読み出し表）だけでは解消しない。**T955「評価に必要な列を
1行に持つテーブル」節の代役テーブル
（列ごとの`array_agg`で915〜929ms）から見込める稼ぎは1タイル約450〜500ms、16枚で約7〜8秒
（見込み、未計測）。いまはAがBと同じ規模で残っており、本タスクはAに触れない。

**保留（ユーザー判断）**: 新しい派生テーブルを1つ増やすかどうかは、起票時から
ユーザー判断とされている。選択肢:

1. [T959](T959.md)（世代を上げた直後に主要エリアを先に焼く）を先に入れ、本タスクは見送る。
   主要エリアでは冷パスの長さに関係なく「最初の利用者が待つ」が消える。主要エリアの外は
   42〜53秒のまま残る
2. 読み出し表をAのトポロジ（区間の端点・距離等）まで含む形に設計し直してから着手する。
   A・Bの両方を1回の走査にでき、稼ぎは最大になるが、表の鮮度判定は同じだけ増える
3. 当初の範囲（Bのみ）で着手する。稼ぎは1リクエスト約7〜8秒

判断が出るまで、本タスクは未着手のまま台帳に残す。

**ユーザー決定（2026-09-23、判断D-007）**: [T959](T959.md)（主要エリアを先に焼く）は進める
（完了済み）。本タスク（区間の評価に必要な列を1行に持つ新しい派生テーブル）は、その効果を
先に本番で実測して、作り替えるかどうかの検討材料にする——実測してから作るかを改めて
ユーザーに諮る。実測の中身は上の表と同じ条件（1タイル・z12の4×4枚の材料段）で、
代役テーブルを使ったときの差を取る。

## クローズ（周期レビュー第13回、2026-09-26）

問い（周期レビュー第13回、2026-09-26。ダッシュボードの件T958-close）: 「ルート探索の作り直し（T1112）で前提が無くなった2つのタスク（T958・T959）を閉じますか」。選択肢は(1)閉じる: 前提（地図の区画ごとに材料を読む遅い経路）が無くなったため。初回の遅さは承認済みの計測の起票案で扱う (2)残す: 道路網全体の配列の読み込みを速くする目的で、中身を書き直して続ける。
