# T582: 本番VMのネットワーク許可ルールを設計どおりに是正する（SSH 22番の全開放・iptablesの5432無制限行）

状態: 未完了

保留（2026-09-05起票・同日調査の上で保留判断。トリガー: 本格公開の意思決定）

## 保留理由（2026-09-05）

現状確認の結果、対応方針1（OCI側`0.0.0.0/0 TCP22`行の削除）を実行すると、自宅の
グローバルIPが動的（固定IPでない）であるため、IPが変わった際にSSHで入れなくなる。
復旧手段自体は存在する（OCIコンソールはIP制限を受けておらず`oci iam network-sources
list`で確認済み、ブラウザからいつでもログインしセキュリティリストの管理者IP行を
更新できる）が、気づくまでSSH不可になる運用上の摩擦が生じる。現時点では本番運用が
個人開発フェーズであり、SSHが全世界へ開いていること自体の実害（鍵認証のみ・
パスワード無し）は限定的なため、この摩擦を許容するメリットが薄いとユーザーが判断し、
対応方針1・2（VM内iptablesの22番を管理者IP限定へ絞る案）ともに保留とした。

対応方針3（VM内iptablesの5432無制限行の削除）についても、調査時点で
`133.200.74.65/32`（管理者IP）専用のiptables許可行が5432番に存在しない
（既存のiptablesルールは無制限行と`74.220.48.0/24`・`74.220.56.0/24`＝Renderレンジの
みで、管理者IP限定行は無い）ことが判明した。無制限行だけを削除すると、管理者IPからの
直接psql接続経路（利用実績の有無は本タスクでは未確認）が失われる可能性があるため、
SSH問題と合わせて保留した（着手時は管理者IP専用行の追加要否から検討する）。

**ユーザー決定（2026-09-23）**: (a) 5432番をRenderのレンジへ開けている許可は**消す**。(b) SSH 22番は**絞らない**
（全開放のまま保留を続ける。自宅のIPが動的で、変わるたびに入れなくなる摩擦を避ける）。

## 背景

[T580](T580.md)のUDP 443開放作業で、本番VM（Oracle Cloud、`ridecompass-vcn`）の許可ルールを
読み取ったところ、設計（docs/osm-pbf-import.md 11章: 22番は管理者IPのみ、5432番は管理者IP＋
Renderのアウトバウンドレンジのみ）と食い違う行が2つ見つかった。

1. OCIセキュリティリスト（Default Security List for ridecompass-vcn）のIngressに、管理者IP
   限定の行（`133.200.74.65/32 TCP 22`）とは別に`0.0.0.0/0 TCP 22`の行が残っている。VM内
   iptablesは22番を絞っていないため、OCI側のこの行が唯一の門になっており、実質SSHが全開放。
2. VM内iptablesに`-A INPUT -p tcp --dport 5432 ... ACCEPT`（送信元無制限）の行がある。
   OCI側で5432は管理者IP＋Renderレンジに絞られているため実害は無いが、OCI側のルールを
   誤って緩めた場合に二層目の防御が効かない。

## 対応方針

1. OCIコンソール（または`oci network security-list update`）で`0.0.0.0/0 TCP 22`のIngress行を
   削除する。作業前に現在のIPv4（`curl -4 ifconfig.me`）が管理者行と一致していることを
   確認する（一致していれば削除しても現在のSSHは切れない。自宅IPが変わって入れなくなった
   場合はOCIコンソールから管理者行のIPを更新して復旧）。
2. VM内iptablesの5432無制限行を削除し、`netfilter-persistent save`で永続化する
   （管理者IP・Renderレンジの各行は残す）。
3. docs/osm-pbf-import.md 11章の記載と実際のルールが一致することを、`oci network
   security-list get`と`iptables -S INPUT`で最終確認する。

## 影響（放置した場合）

SSHがパスワード無し鍵認証のみとはいえ全世界から到達可能なままになる。本番DBホストの
攻撃面が設計より広い状態が続く。

- **5432番をRenderのレンジへ開けている理由が、今の構成に無い**。本番のbackendはOracle Cloud VM

  Renderの送信元レンジはRenderの全利用者で共有されるため、この許可は**他人のサービスから
  DBのポートへ到達できる**状態を作っている。
- SSH 22番の全開放も起票時のまま残っている（本番の現状は未確認）。

**着手時の進め方**:
1. 本番の現状を読み直す（`oci network security-list get`・VM内の`iptables -S INPUT`）。
   2026-09-05以降に誰かが変えている可能性がある。
2. 上の「対応方針」の1・2に加え、**5432番のRenderレンジの行（OCI側・iptables側とも）を
   消してよいかを判断する**。消す前に、RenderのサービスからDBへ繋ぐものが本当に無いか
   （Renderのダッシュボードで、frontend以外のサービス・cronジョブの有無）を確かめる。
3. 設計の記述（`docs/osm-pbf-import.md` 11章等、5432番を「管理者IP＋Renderレンジ」と書いている

## 着手前の読み取り（2026-09-23 18:58、司令塔）

本番VMの`sudo iptables -S INPUT`（既定のポリシーACCEPT、末尾で`REJECT`）:

- 5432番: **送信元を問わない許可**（`-A INPUT -p tcp --dport 5432 -m state --state NEW -j ACCEPT`）と、
  Renderのレンジ`74.220.48.0/24`・`74.220.56.0/24`の許可が2行。**無制限の行がある限り、Renderの2行を消しても
  VMの手前では何も変わらない**——実際に塞いでいるのはOCIのセキュリティリストの側（未読）。
- 8080番: 管理者IP`133.200.74.65/32`とRenderの2レンジ（frontendからbackendへの中継。消さない）。
- 22番: 送信元を問わない許可（(b)の決定どおり残す）。
- PostgreSQLは`0.0.0.0:5432`で待ち受け、`pg_hba.conf`は`hostssl ridecompass ridecompass 0.0.0.0/0 scram-sha-256`。
- 本番のbackendコンテナは`network_mode: host`で`localhost:5432`へ接続する（`-i lo`の許可で通る。5432の外向きの
  許可を消しても影響しない）。
- **開発機は本番DBへ公開IP（`193.123.166.150:5432`）で直接つないでいる**（`backend/.env.oracle.local`の
  `DATABASE_URL`、`backend/scripts/run_probe.py`の手元実行が使う）。今の自宅IPは`133.200.74.65`。5432番を
  塞ぐなら、この経路を残すか（管理者IPの行を足す）SSH経由へ変えるかを一緒に決める必要がある。

**次にやること（担当）**: OCIのセキュリティリストを`oci network security-list get`で読み（読み取り）、5432番の
Ingressを列挙する。Renderのダッシュボードにfrontend以外のサービス・cronジョブが無いことはユーザーに確かめて
もらう。そのうえで、OCI側・iptables側の消す行と足す行（管理者IPの5432）を、ユーザーがそのまま貼れる手順として
`## ユーザー操作（待ち）`に書き、設計の記述（`docs/osm-pbf-import.md` 11章等）を残したルールに合わせて直す。
