# T1186. 画面から backend を呼ぶ部分を openapi-fetch へ置き換え、応答の型を API の定義から自動で決める

状態: 未完了（2026-09-27起票）

## 背景

起票案 proposal-std-openapi-fetch（2026-09-27承認。標準の道具の棚卸し・T1152の担当から）。規模M（根拠: API を呼ぶ本番のファイルが12本（grepで実測）、テストを足して20本以下の見込み）

■ 背景（画面に出ない、画面側の内部の話）
画面側は backend の API 定義から型を生成している（openapi-typescript）。パスの綴りは lib/apiPath.ts で API 定義と突き合わせているが、応答の型は呼び出しごとに手で書いている（例: 管理画面の API 呼び出しだけで22か所）。backend の応答の形が変わっても、手で書いた型は追従せず、型検査で気づけない。openapi-fetch は openapi-typescript と対になる部品で、パス・メソッド・クエリ・応答の型を API 定義から推論する。比べた記録はどこにも無い。

■ やること
lib/fetchJson.ts の骨格（通信のログ・x-request-id・タイムアウトと通信エラーの区別・日本語の文言・422 の詳細の整形）は openapi-fetch の middleware として残し、呼び出し側を置き換える。apiPath.ts とそのテストは要らなくなる。摩擦: 既定値のある項目が任意扱いになる型の補正（types/route.ts の Required<>）を、推論した型にも掛ける必要がある。管理画面の接頭辞の差し替えは middleware で行う。見込み 実装 約−100〜−150行、テスト 約−30〜−60行。依存が1本増える。
データ取得の骨格を TanStack Query へ置き換える起票案と同じ呼び出し口を触るので、両方承認されたら順番を決める（こちらを先にすると、TanStack Query 側は型付きの呼び出しをそのまま使える）。

■ なぜ既存のタスクに入らないか
T1145 は写しの型（軸カタログの行を手書きの型4つへ写している）を含むが、範囲はその4つで、API 呼び出しの型付けの方式は含まない。
