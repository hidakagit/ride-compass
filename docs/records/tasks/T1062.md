# T1062. 検査の置き場を手元・作業ブランチCI・デプロイ前CIの3層に分け、pre-pushから重複を外す

状態: 未完了（2026-09-23起票）

## 背景

ユーザーと合意した検査の置き場（2026-09-23）:「直接触った影響範囲だけローカルではテストして、前提テストは作業ブランチCIでやる。preフックからは同じテストは除く」。T1058 で作業ブランチ（orch/**）のCIとそこへのpushでのpre-push省略は入ったが、次の2つの穴のため、masterへのpushのpre-push（ruff・prettier・tsc・OpenAPIドリフト・review_checks docs）は外せない状態にある。
(1) CI（ci.yml）は prettier を見ていない。2026-09-23の並行実行で prettier の崩れによる差し戻しが3回あり、止めたのは監査とmasterへのpre-pushだけだった。
(2) .github/workflows/deploy-backend.yml は on: push: branches: [master] で起動し、CIの結果を待たずに本番へデプロイする。masterへ入るのは、作業ブランチで個別にCIを通ったコミットを司令塔が組み合わせたもので、組み合わせた木は作業ブランチのCIを通っていない。したがって今はmasterへのpre-pushが「本番に出る前の唯一の検査」になっている。

対応方針:
1. ci.yml の frontend ジョブに prettier --check を足す（手元の pre-push と同じ対象・同じ設定）。
2. backend のデプロイを master の CI 成功後に起動する形へ変える。書き方（workflow_run の conditions・head_sha の扱い・paths の絞り込みをどう保つか）は GitHub 公式文書（docs.github.com の Events that trigger workflows / workflow_run）を読んでから決める。frontend のデプロイ経路（どこへ・何をきっかけに）も確かめ、同じ扱いにできるか・できないならなぜかを書く。影響: CI が赤の間はデプロイされない。急ぎの修正も CI の完了（現状1分半〜3分）を待つ。workflow_dispatch による手動デプロイは残す。
3. 1・2 が master に入ってから、.githooks/pre-push から CI と重複する検査（ruff・prettier・tsc・OpenAPIドリフト・review_checks docs）を外す。残すのは停止ファイルの確認と check_master_ci.py の警告だけ。外す前後で master への push の所要時間を測って記録する。
4. CLAUDE.md（「完了扱いにする前に検査器を通す」の push 直前の記述・テスト方針のCIの記述）、docs/conventions/orchestration.md（監査の機械項目・まとめpushの手順）、docs/conventions/testing.md の記述を新しい置き場に合わせる。

完了条件: CI が prettier の崩れで落ちること（壊した入力1件、作業ブランチで run の URL を記録）、master の CI を失敗させた場合に backend のデプロイが起動しないこと（試験の方法は本番へ出さない形で設計し記録する。例: 試験用ワークフローで workflow_run の条件だけを確かめる）、pre-push が停止ファイルの確認と警告だけになっていること、文書が新しい置き場と一致していること。

## 段階A: CIにprettierを足し、backendのデプロイをmasterのCI成功後に起動する（2026-09-23、L-env）

### 書き方の選択（公式文書で確かめたこと）

GitHub公式「Events that trigger workflows」の`workflow_run`節:

- 起動元の結論に関係なく起動する（成功だけに絞るには`github.event.workflow_run.conclusion`で条件を書く）。
- `GITHUB_SHA`は「Last commit on default branch」で、CIを通ったコミットではない（`head_sha`を別に読む必要がある）。
- 「This event will only trigger a workflow run if the workflow file exists on the default branch」
  ——作業ブランチでは起動しないので、masterへ入れる前に試せない。
- `paths`で絞れない。

GitHub公式「Reusable workflows」（reference）:

- 同じリポジトリの`./.github/workflows/<file>`は、呼び出し元と同じコミットのファイルが使われる。
- 呼ばれた側の`github`コンテキストは呼び出し元のもの（`github.sha`がpushされたコミット）。
- 呼び出すジョブで`needs`・`if`・`concurrency`・`secrets: inherit`が使える。
- ジョブの`needs`が失敗するとそのジョブはskippedになる（既定の`success()`）。

**採用: `ci.yml`の最後のジョブが`needs: [backend, api-contract, frontend, e2e]`で`deploy-backend.yml`を呼ぶ
（`on: workflow_call`）。** `workflow_run`より、(1) CIを通ったコミットがそのまま`github.sha`になり、
(2) 作業ブランチで同じファイルのまま試せる。`workflow_dispatch`（手動）は残した。

**`paths`の絞り込みは`scripts/deploy_backend_gate.py`へ移した。** `workflow_call`は`paths`を持てない
（`workflow_run`も同じ）。起点は「直前のpush」ではなく「本番で動いているコミット」（VMのコンテナの
`GIT_COMMIT`をSSHで読む）にした。直前のpushとの差分では、CIが赤で出せなかったコードの変更を、
テストだけを直した次のコミットが運ばず、次にbackendを変えるまで本番へ出ない穴ができる。
判定は: 本番のコミットが分からない→出す／同じ→出さない／CIを通ったコミットの方が古い（後から終わった
古い実行）→出さない／新しい→差分に`DEPLOY_PATHS`（GitHubの`paths`と同じ規則。上から当て最後に
当たったものが勝つ、`*`は`/`を跨がず`**`は跨ぐ）に当たるファイルがあれば出す／履歴が分かれている→出す。
出すのはCIを通ったそのコミット（VMで`git fetch --depth 1 origin <sha>`）で、masterの先端ではない。
判定とデプロイは1つのジョブにし、そのジョブに`concurrency: deploy-backend`を置いた（呼び出し側と
呼ばれた側の両方に同じ組を置くと、公式の注意のとおり取り合いになりうるため片側だけ）。
`backend/tests/structure/test_deploy_exclusions.py`は、除外の一覧をワークフローではなく
`DEPLOY_PATHS`から読むように変えた（移設後も同じ10件・173ファイルを受け取ることを確かめた）。

**frontend（Render）は同じ扱いにできない。** RenderはGitHubのpushで直接デプロイし、リポジトリに
設定が無い（`render.yaml`も無い）。Render公式（render.com/docs/deploys）に自動デプロイの設定
「After CI Checks Pass」があり、そのコミットのチェックが全て成功（skipped・neutralを含む）したときだけ
デプロイする（チェックが0件のコミットは出さない）。切り替えはRenderのダッシュボードの操作なので、
ユーザー確認事項にした。

### prettierをCIへ

`frontend`ジョブの`npm ci`の直後に`./node_modules/.bin/prettier --check "src/**/*.{ts,tsx,css}"`
（pre-pushと同じ対象。設定は`frontend/.prettierrc.json`・`.prettierignore`をそのまま読む）。

**足した時点でmasterが31ファイルで落ちた**（試験の緑のはずの実行 run 35829187212 がprettierで赤）。
pre-pushは変更したファイルしか見ないため、崩れたまま入ったファイルが残っていた。31ファイルを
`prettier --write`で整えた（`weatherApi.test.ts`はprettierのメソッドチェーンの折り返しが1回で
収束せず、2回目で安定した）。差分は31ファイル +161/−152。空白を全て除いて比べると24ファイルで
差が残り、その内訳は末尾カンマの追加53・削除14、型リテラルの末尾`;`の削除2、JSXを包む括弧・
アロー関数の本体を包む括弧の削除3と置換1——どれも構文上の記号で、挙動は変わらない。
