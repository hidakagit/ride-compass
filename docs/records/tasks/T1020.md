# T1020. 上流への秒間上限が、ワーカーを増やすと黙って倍になる

状態: 完了（2026-09-23）

## 背景

[T1012](T1012.md)で`jma_tile_client.py`のテストを起こし直したとき、上流への
秒間リクエスト上限を持つ`_last_fetch_at`がモジュール大域であることが、コメントで
「backendが単一プロセス構成であることに依存している——ワーカーを増やすと実効の
秒間リクエスト数がその倍数になる」と明記されているのを確認した。

`backend/Dockerfile`のCMDは`uvicorn`を`--workers`なしで起動しており、
**今は正しい**。

## 何が問題か

`docs/architecture/design-principles.md`構造仕様16「境界は、破られたときに落ちる形で
表現する」に反する。ワーカーを増やしても**何も落ちない**——上限が黙って倍になり、
気象庁の非公式APIへの負荷が増えるだけで、増やした本人も気づけない。

性能改善でワーカーを増やす日に効く種類の欠陥で、そのとき誰もこのコメントを読まない。

## やること

次のどちらかを選ぶ。**選ぶ前に、どちらが本当に要るかを決めること**——
プロセス間で共有する状態を足すのは、上限が実際に効いている頻度に見合うときだけ。

- **(a) 落ちる形にする**: 起動時にワーカー数を読み、1より大きければ起動を止める
  （fail-fast。`refresh_axis_definitions`と同じ方針）。上限の実装は変えない
- **(b) プロセス間で持つ**: 直前フェッチ時刻をRedisへ置く。ワーカーを増やしても
  上限が守られるが、実フェッチのたびにRedisへ1往復増える

判断材料として、**実際に秒間上限で待っている回数**を先に測る
（`/api/debug/stats`か、`_wait_for_upstream_rate_limit`の待ち発生をログへ出して
本番で1日分）。待ちがほぼ発生していないなら(a)で足りる。

## 完了の条件

1. (a)(b)のどちらを採ったかと、その根拠になった実測値がタスク記録にある
2. (a)なら、ワーカー2で起動して実際に止まることを見た。(b)なら、2プロセスから
   同時に叩いて上限が守られることを見た
3. コメントの「単一プロセス構成であることに依存している」が、採った側に合わせて
   書き直されている

## 規模

S〜M（測る時間を含む）

## 実施内容（2026-09-23）

**(a) 落ちる形にする**を採った。

### 根拠

判断材料として挙げていた「秒間上限で実際に待っている回数」は**測っていない**。測る前に、
(b)では境界が表現されないことが分かったため:

- プロセス内に持つ状態は秒間上限だけではない。変更前の`backend/app`を「単一プロセス」「プロセス内」
  「プロセス単位」「プロセスごと」でgrepすると22ファイルに当たり、そのうち状態を持つものとして
  ジョブ台帳（`job_registry.py`。別ワーカーへ届いたポーリングからジョブが見えない）・
  レート制限（`rate_limiter.py`。上限がワーカー数倍）・軸定義と較正値の反映
  （`axis_registry_service.py`・`tuning_overrides.py`。管理APIの書き込みが受けたワーカーにしか
  反映されない）・APSchedulerの定期ジョブ（`main.py`。ワーカー数だけ重なって走る）がある。
- (b)で秒間上限だけをRedisへ移しても、これらはワーカーごとに分かれたまま残り、ワーカーを
  増やしてよい状態にはならない。どの頻度の実測値が出ても(a)は要る。

### 実装

- `app/infrastructure/single_process.py`（新規）: `uvicorn_worker_count(argv, environ)`が
  uvicornのCLI定義（`make_context`）で引数を解釈し、`--reload`なら1・未指定なら
  `WEB_CONCURRENCY`という既定の決め方だけをuvicornの`Config`（0.34）に合わせる。
  `require_single_worker`が2以上なら`RuntimeError`を送出する。
- `main.py`のlifespanの最初で呼ぶ。ワーカーは`multiprocessing`のspawnで起動され、親の
  `sys.argv`を受け継ぐ（`multiprocessing/spawn.py`が`sys_argv`を子へ渡して復元する）ため、
  ワーカーの中からuvicornに渡された引数が読める。
- `jma_tile_client.py`のコメント「backendが単一プロセス構成であることに依存している
  ——ワーカーを増やすと実効の秒間リクエスト数がその倍数になる」を、採った側に合わせて
  「プロセスをまたいでは効かないため、ワーカーを複数にした起動は`single_process.py`が止める」
  へ書き直した（完了条件3）。
- `docs/modules/backend/cross-cutting-infrastructure.md`へ「1プロセスの境界」節と対象ファイル表の
  行、起動図の(0)を足し、`weather-dynamic-layers.md`の秒間上限の節から参照した。

## 検証

- `pytest tests/test_single_process.py -q` → 11 passed（引数・`--workers=4`・`WEB_CONCURRENCY`・
  引数が環境変数に勝つ・`--reload`・`python -m uvicorn`・Windowsのパス・uvicorn以外）。
- 本物の`app.main`のlifespanへ、ワーカー2のときの`sys.argv`
  （`uvicorn app.main:app ... --workers 2`）で入ると、`RuntimeError`（`workers=2`）で止まることを
  見た。
- 完了条件2の「ワーカー2で起動して実際に止まることを見た」は、この開発機（Windows）では
  満たせなかった。機能を持たない最小のASGIアプリでも、uvicornのワーカーがlifespanへ入る前に
  消えて作り直され続け（`Child process [...] died`の繰り返し）、変更と無関係にワーカー複数の
  起動がそもそも成り立たない。WSL・Dockerも入っていない。
