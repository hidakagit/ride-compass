# T1183. 画面側のデータ取得の骨格（取り消し・最新の応答の判定・読み込み中と失敗の状態・定期取得）を TanStack Query へ置き換える

状態: 完了（2026-09-27起票、2026-09-27完了）

## 背景

起票案 proposal-std-fetch-hooks（2026-09-27承認。標準の道具の棚卸し・T1152の担当から）。規模L（根拠: 取得の骨格を持つ本番のファイルが15本（grepで実測）、対応するテストが約10本、Provider と package.json を足して20本を超える見込み。段階に切って進める）

■ 背景（画面に出ない、画面側の内部の話）
「新しい部品を書く前に標準の道具で済まないかを先に確かめる」ルールで既存コードを棚卸しした。画面側のデータ取得は、「取り消しの印（let cancelled）」「連番で最新の応答だけを採る」「読み込み中・失敗・一度届いたか」の状態、「定期的に取り直す」を、フックごとに書き直している（本番15ファイル。例: 軸カタログ・材料カタログ・天気・警報の定期取得・管理画面の分布）。lint の規則を避けるための Promise.resolve().then(...) も本番に9か所ある。これらは TanStack Query の既定の動き（同じキーの重複排除・失敗しても前の値を残す・refetchInterval・retry）そのもので、ライブラリと比べた記録は docs/records も含めてどこにも無い。

■ やること
- 段階A（S）: 対応表を作る。各フックの約束（例: 結果を取っておかずマウントのたびに最新を取る／一度届いたら失敗で巻き戻さない／失敗も覚える）が TanStack Query の設定へ1対1で写せるか確かめ、写せないもの（例: 定期取得を止めたら「一度届いた」を戻す挙動、取り損ねた地点を前回の値で補う合成）を列挙する。
- 段階B以降: 共有度の高いもの（軸カタログ・材料カタログ）から置き換え、テストのうち重複排除・取り消し・世代番号を見ている部分を消す。
- 見込み: 実装 約−400〜−460行、テスト 約−450〜−600行。依存 @tanstack/react-query が1本増える。

■ なぜ既存のタスクに入らないか
T1145（画面側の写経の整理）は「管理画面の2つのフックが同じ取得の骨格」を1件として含むが、範囲はその写経の解消で、ライブラリへの置き換えは含まない。承認されたら T1145 の記録へ「取得の骨格の写経はこのタスクへ移る」と書き足す。API 呼び出しを openapi-fetch へ置き換える起票案と同じ呼び出し口を触るので、両方承認されたら順番を決める。

**既定の方針（全フック共通、`lib/queryClient.ts`）**:
- 自動の再試行（既定3回・倍々の間隔）は切る。失敗の表示が数秒遅れ、backendのレート上限（429）へ重ねて当たる。
  今のフックはどれも再試行しない。
- 画面へ戻ったとき・通信が戻ったときの取り直しは切る。今のどのフックも持たない約束で、走行中のスマホでアプリを
  行き来するたびに通信が増える。入れるなら取得ごとの約束として別に決める。
- **Providerを置かず、クライアントを`useQuery`の第2引数で渡す**（v5の公開の引数。`useQueryClient`は引数があれば
  文脈を見ない、`node_modules/@tanstack/react-query/src/QueryClientProvider.tsx`）。Providerを置くと、取得するフックを
  含む部品を描くテスト（段階C・Dで管理画面・地図の部品のテストの大半）がすべて包みを要する。サーバーでの描画は
  呼ぶたびに新しいクライアントを作り、利用者をまたいで共有しない（サーバーでは`gcTime`の既定が無期限で、使い回すと
  キーが残り続ける。`query-core/src/removable.ts`）。
- 再試行の既定はブラウザで3回・間隔`min(1000×2^n, 30000)`ミリ秒（`query-core/src/retryer.ts`）。

**テストの扱い**: 消すのは重複排除・取り消し・世代番号（どれもライブラリの既定の動き）を見るテスト。残すのは、
このリポジトリの約束（届いた応答から何を導くか・失敗をどう見せるか・いつ取り直すか）を入口で見るもの。
キャッシュはテストの間で残るので、テストごとに空から始める（段階Bは既存の`vi.resetModules`で読み込み直す形を
そのまま使った。部品を描くテストが増える段階Cで、`afterEach`の`getQueryClient().clear()`と比べて決める）。

## 段階C: 管理画面

段階Aの表の管理画面の行（`useScoresPreview`・`useMapBandsOfThresholds`・`useAxisValueDistribution`・`useMaterialDistribution`・
`useMaterialValues`・`TuningPanel`・`BackendStatus`・`SystemStatusPanel`・`AxisStudio`の一覧）を、表の写し方どおりに置き換えた。
写せないものは出なかった。

- 自前の取り消しの印・連番のref・`Promise.resolve().then`・読み込み直しの合図（`reloadToken`）・材料の分布のモジュール内の
  `Map`を消した。管理画面に残る自前の取得は、押したときだけ取る3本（`ReportCard`・`BackendLogsPanel`・`TileCachePanel`。
  段階Aで母集団の外に置いた）だけ。
- 各フックに残した約束: 下書きのプレビュー2本は「落ち着いた入力と今の入力が違えば前の答えを出さない」（キーは落ち着いた
  入力、比較は今までどおり）。分布は「取り直している間は前の分布を出したまま読み込み中」（`placeholderData: keepPreviousData`。
  従来の`{ ...prev, loading: true }`と同じ見え方）と「使わない間は分布なし」（`enabled: false`でも同じキーの値は残るので、
  フックが明示的に空を返す）。材料の分布は「画面を開いている間は材料ごとに1回、失敗も覚える」（`staleTime`・`gcTime`を無期限、
  失敗は取得の関数の中で`null`へ変える）。材料の値一覧は「切り替えた直後に前の材料の値を返さない」（前の値を残す指定を付けない）。
  較正値は保存した行を`setQueryData`で差し替え、軸スタジオは操作の後に`refetch`する。
- 消したテスト: StrictModeの二重実行で1回しか取らない（`useAxisValueDistribution`・`useMaterialDistribution`）・後から届いた
  古い応答／古い失敗で上書きしない（`useAxisValueDistribution`・`useMapBandsOfThresholds`・`useMaterialDistribution`・
  `useMaterialValues`・`TuningPanel`・`BackendStatus`）。どれも同じキーの重複排除とキーごとの結果というライブラリの既定の動き。
  足したテスト: 分布を取り直している間に前の分布を出したまま読み込み中にする（`keepPreviousData`はこのリポジトリが選んだ約束で、
  従来はテストが無かった）。
- テストの間の隔離: `vitest.setup.ts`の`afterEach`で、描いたものを外したあとに`getQueryClient().clear()`する（段階Bで保留した
  判断）。部品を描くテスト（軸スタジオ・較正値等）はフックのテストのように読み込み直しで空から始められないため。

**画面の差**（どれも同じ入力には同じ答えが返る取得で、キャッシュが残る5分の間だけ起きる）:
- 一度見た入力（折れ点・しきい値・分布の形・材料）へ戻ると、前に届いた答えを即座に出し、裏で取り直す（従来は取り直しが
  終わるまで空か読み込み中）。材料の分布は従来どおり取り直さない。
- 「開発者」タブの接続の表示・軸スタジオの一覧を開き直すと、前の結果を出したまま裏で確かめ直す（従来は「確認中」・空から）。
- 較正値の「読み込み直す」を押すと、取り直しの間「読み込み中…」を出す（従来は最初の読み込みのときだけ出した）。

**段階Dの判断材料**:
- 取得の結果はライブラリが`setTimeout(0)`の区切りで購読者へ知らせる（`query-core/src/notifyManager.ts`の既定の`scheduleFn`）。
  `await act(async () => resolve(x))`の直後に同期で確かめるテストは値がまだ届いておらず落ちる（段階Cで4件、`waitFor`へ直した）。
  段階Dの定期取得のテストは偽の時計（`vi.useFakeTimers`）を使うものがあるため、時計を進めないと結果が届かない。
- `enabled: false`にしても同じキーの値はキャッシュに残り、`data`として返り続ける（分布のフックで確かめた）。`usePolledFetch`の
  「止めたら『一度取った』を戻す」をそのまま写すなら、`enabled`が偽の間はフックが明示的に未取得を返し、再び表示したときは
  取り直しが終わるまで「読み込み中」にする形になる。キャッシュの値を即座に見せる（地図のチップが読み込み中を経ない）かは
  段階Dで、チップの状態の導出（`mapLayers.ts: deriveFetchLayerStatus`）と合わせて決める。

## 段階D: 地図・天気

段階Aの表の残り（`usePolledFetch`とその利用者・`jmaDelivery.ts`の進行中の共有・`useDedicatedWayValues`・
`useWeatherConditions`・`RoadInspectorPopup`）を置き換え、`usePolledFetch.ts`とそのテストを消した。これで対応表が尽き、
母集団（段階A）の本番ファイルに残る自前の骨格は`useLocation.ts`（対象外と判定済み）だけ
（`grep "Promise.resolve().then|let cancelled|requestSeq|latestRequestId|inFlight"`で本番は`useLocation.ts`と
`MapView.tsx`の地図の片付けの印だけ）。

**判断1: 止めたら「一度取った」を戻すか**（表の「写せない」の1件目）。**戻さない**——消している間だけフックが
「まだ取りに行っていない」を返し、再び出したときはキャッシュに残る前の値（時刻一覧・格子。読み手が消えてから5分）を
すぐに出して裏で取り直す。理由（品質）:
- 正しさ: 状態の導出（`deriveFetchLayerStatus`）が誤るのは「消している間に取得済みを返す」ときだけで、これは
  無効の間に未取得を返すことで保たれる。再表示時に出す前の値は、定期の取り直しの周期の間に出している値と同じ種類の
  古さ（周期＋最大5分）で、取り直しが届けば置き換わる。チップが「読み込み中」を経ないのは、値を出している以上
  事実どおり。
- 保守する量: 忠実に写すには「有効にしてから一度取り終えたか」を別の状態で持ち、`dataUpdatedAt`と比べる形になり、
  ライブラリの既定と逆向きの約束を1本だけ抱える。戻さない形はフックが無効の間に空を返す1行で済む。

**判断2: `useWeatherGrid`のキーをまたぐ補い**（表の「写せない」の2件目）。**refを持たず、キャッシュから引く**——詳細格子の
取得の関数が、同じ間隔のキーのうち最後に届いた格子を`getQueryCache().findAll`で引き、今の範囲の中の点だけで補う。
粗い格子は自分のキーの前の値（`getQueryData`）で補う。理由（品質）:
- 正しさ: refで持つ形は、範囲を動かした後に前の範囲の応答が届くとrefを古い範囲の格子で上書きしうる（取得の関数が
  refへ書くため、キーごとの結果というライブラリの守りが効かない）。キャッシュから引く形は、各キーの値がそのキーの
  応答だけで決まり、補う元は読むだけになる。間隔が変わったら補わない約束は、キーの先頭に間隔を置くことで同じになる。
- 保守する量: 補う元の状態（ref2本と、失敗・無効で空へ戻す分岐）が消え、取得の関数1つに収まる。
- 差: 補う元は「直前の範囲の格子」から「同じ間隔で最後に届いた格子（キャッシュに残る間）」になる。直前の範囲の格子は
  最後に届いた格子なので、ふつうは同じもの。詳細格子の取得に失敗した後の取り直しでも、失敗前の格子から補う
  （従来は失敗で補う元を捨てていた）。

**表の見立てと違ったもの**:
- **`useQueries`は`keepPreviousData`をキーをまたいで効かせない**（観測者をキーのハッシュで対応付け、キーが変わると新しい
  観測者になる。`query-core/src/queriesObserver.ts: #findMatchingObservers`）。表は`useDedicatedWayValues`を「軸ごとの
  `useQueries`＋`keepPreviousData`」で写すとしていたが、それでは取り直しの間に前の値を残せない。全軸ぶんを1つのキー
  （軸ごとのリクエストキーの並び）の`useQuery`で取り、その中で軸ごとの答えを軸のキーで`fetchQuery`する2段にした
  （入力の変わらない軸は取り直さない約束はここで保つ）。失敗を含む軸の答えは`staleTime`を0にして取っておかない
  （従来はキーが変わるまで失敗のまま）。
- **配信要素ごとの`useQueries`では、同じファイルを読む要素の周期がずれる**。表は「配信ごとの`useQueries`（キー＝時刻一覧の
  パス）」としていたが、後から表示した要素の周期が先の要素とずれ、同じファイルを周期ごとに2回取る。キーと周期を
  ファイルごとに持ち（間隔はそのファイルを読む表示中の要素の最短）、要素ごとの時系列はフックがファイルの行から
  組む形にした。`jmaDelivery.ts`は取得（`fetchJmaTargetTimesFile`）と読み方（`jmaFramesOf`）を分けて出し、
  一部のファイルだけ取れないときの扱いはフックへ移った。
- **定期の取り直しは既定では画面が裏にある間止まる**（`refetchIntervalInBackground`の既定が偽、
  `query-core/src/queryObserver.ts: #updateRefetchInterval`）。画面へ戻ったときの取り直しを切っている（段階B）ため、
  止めると戻ってから1周期（格子は1時間）古い値が残る。従来の`setInterval`と同じく裏でも続ける既定を`queryClient.ts`へ足した。

**画面の差**（起票案で合意した範囲の中。どれも取得の骨格の既定から来る）:
- 降水・風・災害のチップを消して再び出すと、前に取った時刻一覧・格子（5分以内）をすぐに描き、チップは読み込み中を
  経ない（従来は取り直すまで何も描かず読み込み中）。
- 詳細格子（ズームした風・延長降水）: 風のチップを出し直したときも前の範囲の詳細格子をすぐに出す（従来は粗い格子から）。
- 天気・アメダス・警報: 地点を変えて取り直している間に前の失敗の文言を出し続けない（従来は取り直しが終わるまで残った）。
- 道の詳細（`RoadInspectorPopup`）: 同じ道を同じ走行の条件・重みで5分以内に開き直すと、押さずに前の評価を出す。
  走行の条件は押したときのものに留める——表の「キー＝(道・条件・重み)」をそのまま今の条件で引くと、出発時刻が
  「今」へ5分刻みで進むたびに開いている評価が消える（従来は条件が変わっても評価を残していた）ため、従来の見え方を保った。
- 専用配信の軸: 取得に失敗した軸は、別の軸の入力が変わって全体を取り直すときに一緒に取り直す（従来は自分の入力が
  変わるまで失敗のまま）。
