# T1025. 見た目の値を1つ変えるだけで本番backendが入れ替わる

状態: 未完了

## 背景

T1001段階Aで、画面がベタ書きしていた表示値（線の太さ・点の半径・不透明度・破線の刻み・
陰影の光源角度など）を源泉へ移し、`backend/app/domain/`の`map_display.py`・
`display_palette.py`・`weather_display.py`が持つようにした。源泉の一本化そのものは
達成できている（frontendの非テストコードに残る`#rrggbb`リテラルは4件まで減った）。

**置き場を決めるときに、デプロイ境界を確認していなかった。**

- これら3モジュールの公開名を`backend/app/**`から読む箇所は**0件**（実測）。読むのは
  `backend/scripts/export_openapi.py`（生成スクリプト）と`backend/tests/`だけで、
  本番プロセスはこれらを一度も import しない。
- 一方`.github/workflows/deploy-backend.yml`の`paths`は`backend/**`（除外は
  `backend/benchmarks/**`のみ）。**線の太さを3pxから4pxにするだけで、VM上の
  `docker build`→起動確認→コンテナ入れ替えが走る。**

「同じ理由で変更されるもの」の単位になっていない。px値は視覚設計の理由で変わり、
backendの層は経路探索・評価の理由で変わる。両者を同じデプロイ単位に入れたことで、
**無変更の本番プロセスを視覚調整のたびに入れ替えている**。

あわせて、`display_palette.py`の`DisplayPalette`型（`Literal["ordered","nominal"]`）は
参照0で、同じLiteralが`registry.py`にインラインで再宣言されている。

## 対応方針

**源泉の置き場は動かさない。** 表示値をbackendの宣言が持つこと自体は、フロントが
写しを持たないための設計であり、周期レビュー第12回でもその効果が確認されている。
直すのは**デプロイ境界の側**。

1. `deploy-backend.yml`の`paths`から、本番プロセスが読まない表示値モジュールを除外する。
2. 除外してよいことを先に確かめる。確認すべきは「これらのモジュールの変更が、
   生成物（`frontend/src/types/generated/`）を経由してのみ画面へ届き、本番backendの
   振る舞いを一切変えないこと」。`export_openapi.py`がどこで走り、生成物がコミット
   されているかを読んで確かめる。
3. `DisplayPalette`の二重宣言を1本にする。

## 完了条件

- **わざと表示値だけを変えたコミットを1本push し、`deploy-backend.yml`が発火しないことを
  見てから完了にする**（CLAUDE.md「『実装した』ではなく『効いている』を確認して完了に
  する」）。逆に、本番プロセスが読むファイルを変えたコミットでは従来どおり発火することも
  同時に確かめる——**緩めた側だけを見て「発火しなくなった」で終えない**。
- `map_display.py`・`display_palette.py`・`weather_display.py`の公開名に、
  `backend/app/**`からの消費者が引き続き0であることを再測する（将来ここへ本番が読む値が
  混ざると、除外が誤りになる）。この再測方法をエントリに残すこと自体が、除外の前提を
  次の人へ渡す手段になる。
- `DisplayPalette`の宣言が1箇所。

## 実施（2026-09-23）

### 除外の範囲

エントリは表示値3モジュールの除外を方針にしていたが、欠陥の性質は「本番プロセスに届かない
変更でコンテナを入れ替える」ことなので、同じ性質のものを機械的に列挙して一緒に外した
（ワークフロー自身のコメントも「イメージに入る変更だけを対象にする」と書いていた）。

| 分類 | 導き方 | 外したもの |
|---|---|---|
| イメージに入らない | `backend/Dockerfile`のCOPYは`app`・`scripts`・`requirements.txt`・`requirements-batch.txt`だけ。`git ls-files backend`のうちそれ以外 | `tests/**`・`pytest.ini`・`ruff.toml`・`requirements-dev.txt`・`.env.example`（`benchmarks/**`は既存） |
| イメージに入るが本番が読まない | `backend/app/**`からのimport 0件（grep）・デプロイが実行しない | 表示値3モジュールと、それだけを読む`scripts/export_openapi.py` |

`backend/scripts/`の他のスクリプトは運用者が本番コンテナ内で走らせうる（`run_probe.py
--in-container`等）ため外していない。個々に「本番で走らないか」を判定する根拠が無い。

**緩和の影響（実測）**: 追跡ファイル345件のうち、デプロイ対象が338→186件（152件が外れる。
うち144件が`tests/`）。2026-08-24以降のmasterのfirst-parentコミット1,650件に旧/新の`paths`を
当てると、発火は589→542件（−47件、8%）。外れる47件はテスト・生成スクリプト・表示値だけを
変えたコミットで、本番のコードを変えたものは無い（件名で確認。例: 表示値の移設
`2ae22a01`・`c6b79c8b`、テストだけの`3e9e64f4`）。計測スクリプトは使い捨て（コミット単位の
近似で、まとめてpushしたぶんは合算されない）。

### 除外の前提を守る仕組み

「外したモジュールを本番側が読まない」という前提は、崩れても何も落ちない（古い値で
動き続ける）。そこで`backend/tests/structure/test_deploy_exclusions.py`を足した。母集団は
ワークフローの`!`パターンとDockerfileのCOPYから導き、イメージへ入るコードのうち外して
いない`.py`から、外した`.py`への参照（関数内の遅延import・`importlib`へ文字列で渡す形を含む）を
探す。外したパターンが実在のファイルに1件も当たらないときも落とす。

**再測の方法**（この検査を使わずに確かめたいとき）:
`grep -rnE "map_display|display_palette|weather_display" backend/app` の結果が各モジュール
自身の定義行以外0件であること。

効き目の確認: `app/main.py`へ関数内の`from app.domain import map_display`と
`importlib.import_module("app.domain.weather_display")`を、ワークフローへ実在しない
`!backend/nonexistent.txt`を一時的に足して実行し、2件とも落ちることを見た
（`app/main.py -> app.domain.map_display`・`app/main.py -> app.domain.weather_display`・
`['backend/nonexistent.txt']`）。戻して`2 passed`。

### `DisplayPalette`

参照0のため、置き換えずに`display_palette.py`側の宣言を消した（`registry.py`の
`DisplayAxisSpec.palette`のLiteralが唯一の宣言）。この変更は表示値モジュールだけを変える
コミットとして単独でpushし、デプロイが走らないことの確認に使う。
