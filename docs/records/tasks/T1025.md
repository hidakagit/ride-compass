# T1025. 見た目の値を1つ変えるだけで本番backendが入れ替わる

状態: 未完了

## 背景

T1001段階Aで、画面がベタ書きしていた表示値（線の太さ・点の半径・不透明度・破線の刻み・
陰影の光源角度など）を源泉へ移し、`backend/app/domain/`の`map_display.py`・
`display_palette.py`・`weather_display.py`が持つようにした。源泉の一本化そのものは
達成できている（frontendの非テストコードに残る`#rrggbb`リテラルは4件まで減った）。

**置き場を決めるときに、デプロイ境界を確認していなかった。**

- これら3モジュールの公開名を`backend/app/**`から読む箇所は**0件**（実測）。読むのは
  `backend/scripts/export_openapi.py`（生成スクリプト）と`backend/tests/`だけで、
  本番プロセスはこれらを一度も import しない。
- 一方`.github/workflows/deploy-backend.yml`の`paths`は`backend/**`（除外は
  `backend/benchmarks/**`のみ）。**線の太さを3pxから4pxにするだけで、VM上の
  `docker build`→起動確認→コンテナ入れ替えが走る。**

「同じ理由で変更されるもの」の単位になっていない。px値は視覚設計の理由で変わり、
backendの層は経路探索・評価の理由で変わる。両者を同じデプロイ単位に入れたことで、
**無変更の本番プロセスを視覚調整のたびに入れ替えている**。

あわせて、`display_palette.py`の`DisplayPalette`型（`Literal["ordered","nominal"]`）は
参照0で、同じLiteralが`registry.py`にインラインで再宣言されている。

## 対応方針

**源泉の置き場は動かさない。** 表示値をbackendの宣言が持つこと自体は、フロントが
写しを持たないための設計であり、周期レビュー第12回でもその効果が確認されている。
直すのは**デプロイ境界の側**。

1. `deploy-backend.yml`の`paths`から、本番プロセスが読まない表示値モジュールを除外する。
2. 除外してよいことを先に確かめる。確認すべきは「これらのモジュールの変更が、
   生成物（`frontend/src/types/generated/`）を経由してのみ画面へ届き、本番backendの
   振る舞いを一切変えないこと」。`export_openapi.py`がどこで走り、生成物がコミット
   されているかを読んで確かめる。
3. `DisplayPalette`の二重宣言を1本にする。

## 完了条件

- **わざと表示値だけを変えたコミットを1本push し、`deploy-backend.yml`が発火しないことを
  見てから完了にする**（CLAUDE.md「『実装した』ではなく『効いている』を確認して完了に
  する」）。逆に、本番プロセスが読むファイルを変えたコミットでは従来どおり発火することも
  同時に確かめる——**緩めた側だけを見て「発火しなくなった」で終えない**。
- `map_display.py`・`display_palette.py`・`weather_display.py`の公開名に、
  `backend/app/**`からの消費者が引き続き0であることを再測する（将来ここへ本番が読む値が
  混ざると、除外が誤りになる）。この再測方法をエントリに残すこと自体が、除外の前提を
  次の人へ渡す手段になる。
- `DisplayPalette`の宣言が1箇所。
