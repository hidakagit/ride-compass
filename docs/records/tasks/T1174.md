# T1174. 軸の合成に掛け算（または閾値で効かせる形）を足すと、ルート生成がどれだけ重くなるかを測り、入れるかを決める

状態: 未完了（2026-09-26起票）

## 背景

proposal-rain-unpavedの③「雨の後の走りやすさ」を①累計雨量と②舗装質の合成で作るには、今の軸スタジオの合成（重み付きの足し算）では「雨が多く、かつ未舗装のときだけ難しい」を表せず、掛け算か閾値で効かせる形が要る。ユーザー: 「掛け算を持ち込むとルート生成が重くなるからだったはず。どれだけ重くなるのか計測してから決めたい」。調べる段階: 都心40・60・80kmで、今の合成と掛け算を足した試作とで段階別所要（とくに時刻ごとのコストの合成）とメモリを比べる。T1161（ルート生成の計測、進行中）と同じ手順・環境（本番VMの使い捨てコンテナ）を使う。入れるかと実装は結果を見て決める。起票案 proposal-rain-product-cost（2026-09-26承認）

## 段階1（2026-09-27、担当 M-mult）: 試作と、本番で測る手順

### 試作の形

- 軸の形`BreakpointLinearShape`に`combine`（`"sum"`既定／`"product"`）を足した。積は項（材料×重み）を掛け合わせ、
  前処理・折れ点は和と同じ。欠損は和と同じ規則で、寄与なしの項（`required=False`の欠損）は積の単位元1になる。
  0〜100の得点2つは重み0.1ずつで積が0〜100に収まる（③なら「雨の軸×舗装質の軸」）。
- **閾値で効かせる形は別に作らない**。段差の折れ点を持つ軸（例: 雨5mm未満→0・以上→100）を項にすれば同じ積で
  書けるため、形を2つ持つと評価・地図・内訳のすべてで分岐が2本になる（保守する量）。
- 2項以上の積は、地図のrampを導かない（タイルの式は項の和しか表せない）・生値の単位を付けない。
- **`combine`は契約（OpenAPI）に載せていない**（`SkipJsonSchema`）。軸スタジオの画面は積を編集も保持もできず
  （画面の下書きは`combine`を持たないので、保存すると和へ戻る）、折れ点の参考点のプレビューも1つ目の項だけを見る。
  入れると決めたら、契約・画面・プレビューを同じ段で揃える（下の「入れるなら残るもの」）。**この段のコミットは計測の
  ための試作で、採否が決まるまでmasterへは入れない**。

### 重さの出どころ（コードから読んだ見込み。本番の計測で確かめる）

- 積そのものは、項1つあたり配列の掛け算1回で、和の足し算1回と同じ量（`_breakpoint_raw_total_array`）。
- 重さを変えうるのは「**時刻で変わる軸に重みが付くか**」で、和か積かではない。合成器（`_LegCostComposer`）は、
  時刻で変わる公開軸（今は風に依る軸）の重みがすべて0なら合成を1回だけ行い、時刻のビンごとには所要時間×倍率を
  掛けるだけにする（`_time_invariant_composition`）。1本でも重みがあれば、ビンごとに`compose_costs_from_axis_matrix`を
  通し直す（時刻で変わらない軸の和`_fixed_axis_sums`は1回だけ）。本番の既定の重みは風の軸が0なので、今は前者を通る
  （T1161の本番計測で、合成`c_costs`が全区間ぶんでは1回だけ）。
- したがって③の重さは、雨の材料をどう配線するか（[T1173](T1173.md)段階2で決める）で決まる:
  - **観測だけで持ち、探索の前に静的な列として埋める**なら、③は時刻で変わらない軸で、静的スコア行列を作るときに
    1回だけ評価される。ビンごとの合成は増えない。
  - **動的材料（`REQUEST_DYNAMIC_MATERIAL_IDS`）として持つ**なら、③に重みが付いた時点で合成がビンごとになる
    （和で作っても同じ）。雨を予報で延ばす段（T1173段階3）ではこちらになりうる。

- 以前の判断: [T624](T624.md)「組み込み方針」に「軸の合成は線形のまま崩さない（ユーザー指示）」がある。そこで退けたのは
  風の動的計算（専用way値配信）へ開放度の係数を掛ける案で、理由は配信の「同一タイル内は同値」が崩れて作り直しが大きく
  なることと非線形な相互作用を持たせないこと。重さの計測はしていない。入れるかを決めるときはこの指示と並べて判断する。

   合わせてから流す）。
2. 3本を試作のshaから取り出し、`M-mult_vm.sh`・`M-mult_probe.py`と同じ置き場へ置く
   （`git show <試作のsha>:backend/app/domain/axis_definitions.py > axis_definitions.py`等）。
3. `python F-fast_ssh.py M-mult_vm.sh M-mult_probe.py axis_definitions.py axis_display.py axis_raw_value.py`
   （F-fast_ssh.pyはVMの`/tmp/f-fast/`へ送って走らせる。`M-mult_vm.sh`は最後にそこを消す）。
   距離ごとに使い捨てコンテナ（上限6GB）を1本起動し、同じプロセスで軸の集合だけを替えて
   `warmup,base,sum_dyn,prod_dyn,prod_static,base`の順に周回を生成する。軸は本番DBから読んだものに、プロセスの
   中だけで計測用の1本（重み1、公開）を足す（DBへは書かない）:
   - `base`: 足さない。`warmup`は同じ中身の1本目（起動直後の読み込みを比べる対象から外す）
   - `sum_dyn`: 時刻で変わる公開軸（風）×時刻で変わらない公開軸（路面の見込みを読む軸）の和
   - `prod_dyn`: 同じ2軸の積（雨を予報で延ばした③の最悪の形）
   - `prod_static`: 時刻で変わらない公開軸2本の積（雨を観測だけで静的な列として持つ③の形）
4. 見る値（summaryの行。括弧は呼ばれた回数）:
   - `base`→`sum_dyn`: 時刻で変わる軸に重みが付いて合成がビンごとになる重さ。`compose`・`c_costs`の回数と合計、
     `c_fixed_sums`。
   - `sum_dyn`→`prod_dyn`: 和を積にした重さ。`c_axis_eval`（動的な軸の評価）の1回あたり。見込みは差なし。
   - `base`→`prod_static`: `score_matrix`の差だけが出る見込み。
   - `peak`（要求ごとのVmHWM）と`rss_after`。
   - `valid`: 足した軸の値のある区間の割合（`compose:`がビンごとの合成、`matrix:`が静的スコア行列）。時刻で変わる
     軸は`matrix:0.000`が正しく、`compose:`が0に近ければその行は測れていない。
   - `total`を比べるときは`trace_return`の回数と`trace_per_call`を並べる（折返し点を探した本数で数百ms動く。
     [T1195](T1195.md)）。基準の数字は[T1161](T1161.md)「本番での確かめ（段階6・7）」（40km 4.3〜4.8秒、
     60km 8.8秒、80km 11.9秒・ピーク4.1GB）。
