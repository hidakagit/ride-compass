# T1076. scripts/new_task.pyの--helpがWindowsの既定の文字コード（cp932）で落ちるのを直す

状態: 完了（2026-09-23起票、同日完了）

## 背景

python scripts/new_task.py --help がUnicodeEncodeError: 'cp932'で落ち、使い方が読めない（PYTHONIOENCODING=utf-8を付ければ読める）。出力の文字コードを整える処理が--helpの経路より後にあるため。改善提案（T1049、2026-09-23ユーザー承認）。方針: 引数の解析より前に標準出力・標準エラーの文字コードを整える（scripts/lockrun.pyと同じsys.stdout.reconfigure）。完了条件: PYTHONIOENCODINGを付けない素のWindowsのコンソールで --help が表示されること（直す前に落ちることを1回見てから直す）。同じ形（argparseの--helpより後で文字コードを整える）のscripts/*.pyを機械的に列挙し、当てはまるものを同じコミットで直す。

## 実施内容

### 直す前の再現

`PYTHONIOENCODING`・`PYTHONUTF8`を外したPowerShellから`python scripts/new_task.py --help`を実行し、
`UnicodeEncodeError: 'cp932' codec can't encode character '—'`（説明文のdocstringにある`—`）で
終了コード1になることを見た。このときの`sys.stdout.encoding`は`cp932`。

落ちるのは標準出力がパイプかリダイレクトのとき（エージェントのBash/PowerShellツール、`| more`等）。
Pythonの公式文書（`sys.stdout`の項）によれば、Windowsで本物のコンソールへ出すときは3.6以降UTF-8
（PEP 528）、パイプ等のコンソール以外はロケールの符号（ここではcp932）になる。cp932で符号化できない
文字（`—` U+2014・`〜` U+301C等）が出力に1つでもあると落ち、日本語の大半は符号化できるため、
説明文に該当の文字が無いスクリプトは今は落ちていない。

### 母集団と列挙

母集団: `scripts/**/*.py`と`backend/scripts/**/*.py`（指示の`scripts/*.py`・`backend/scripts/*.py`に
`scripts/orchestration/`を足した）のうち、`if __name__ == "__main__"`を持つ入口。ASTで
`parse_args`/`parse_known_args`の行、`sys.stdout`/`sys.stderr`の`reconfigure`の行、`ArgumentParser`・
`add_argument`等の文字列引数（`description=__doc__`ならdocstring）にcp932で符号化できない文字が
あるかを出した（スクラッチの`enum_encoding.py`）。あわせて、argparseを持つ全入口の`--help`を、
`PYTHONIOENCODING`・`PYTHONUTF8`を外した子プロセス（標準出力はパイプ、`stdout.encoding=cp932`）で
実際に走らせて終了コードを取った（スクラッチの`help_cp932.py`）。

結果（入口25本、argparseを持つもの18本）:

- **argparseを持ち、解析より前に文字コードを整えていない: 16本**
  - 整えていない: backend/scripts/の13本（audit_test_rewrite・bootstrap_database・dead_code_survey・
    drop_orphan_test_databases・fetch_accident_csv・fetch_dem_tiles・fetch_osm_pbf・
    measure_axis_saturation・measure_gradient_outliers・measure_poi_freshness・measure_vending_types・
    run_probe・schema_gap）、scripts/review_checks.py、scripts/orchestration/launch.py
  - 解析より後で整える: scripts/new_task.py
  - うち`--help`が実際に落ちたのは4本（new_task・drop_orphan_test_databases・measure_axis_saturation・
    run_probe）。静的な列挙で「cp932で符号化できない文字あり」とした4本と一致した（既知の1件
    new_task.pyが両方で出ることで列挙器を検算）。残りは説明文が今たまたま符号化できるだけで、
    `—`を1つ足せば同じく落ちる。
- 解析より前に整えている: scripts/lockrun.py・scripts/orchestration/core.py（orchestrate.pyの入口）
- argparseを持たない入口（check_db_connection・export_openapi・fetch_lulc_raster・check_master_ci・
  deploy_backend_gate・orchestrate.py・orchestration/github.py）は`--help`の形に当たらないので対象外。

### 直したもの（15本）

`if __name__ == "__main__":`の直後、`main()`を呼ぶ前に
`sys.stdout.reconfigure(encoding="utf-8")`・`sys.stderr.reconfigure(encoding="utf-8")`を置いた
（argparseの使い方・エラーは標準エラーへも出るので両方）。`main()`の中ではなく入口に置くのは、
テストが`main(argv)`を直接呼ぶスクリプト（measure_*等）でpytestの差し替えた標準出力に触れないため。
new_task.pyは`main()`内の解析後にあった`try: reconfigure … except AttributeError`を消して入口へ移した。

対象外にした1本: **scripts/orchestration/launch.py**。形は当てはまるが、`--help`の文字列はすべて
ASCII（`--project`だけ）で落ちえない。標準出力はWorktreeCreate等のフックの出力としてClaude Codeが
読むため、符号を変えるとフックの受け手の見え方が変わる。フックの出力の符号が正しいかは`--help`とは
別の問題なので、ここでは触らず報告に回した。

### 検証

- 直した後、同じ`help_cp932.py`で18本の`--help`を再実行し、全18本が終了コード0。
  new_task.pyの`--help`をファイルへリダイレクトし、`—`がUTF-8で1件出ていることを見た。
- `ruff check`（CIと同じ`backend/`で`app scripts benchmarks tests`、および`scripts/new_task.py`・
  `scripts/review_checks.py`）: All checks passed。
- テスト: 変更は`__main__`の分岐の中だけで、テストから届かない（`backend/tests`で名前が出るのは
  test_measure_axis_saturation.pyのみで、関数を直接呼ぶ）。テストは回していない。
