# T714. precompute系バッチの長時間トランザクションを観測できるようにする 規模S

状態: 未着手（2026-09-10起票、統合レビュー第6回）
— トリガー: 次にprecompute系のバッチを本番で長時間回すとき、その最中に`/admin`「鮮度」タブの
「接続とトランザクションの状態」を見る。そこで`idle in transaction`の最長時間がバッチの
実行時間に張り付いていたら着手する

## 背景

[T660](T660.md)が導入した`app/batch/_common.py:116-133`の`stream_id_chunks`は、
読み取り専用セッション（サーバーサイドカーソル）を**バッチ全体の実行時間ぶん開いたままにする**。
docstringは「書き込みは別セッションで」とだけ述べ、読み取り側トランザクションが
長時間開き続ける点には触れていない。

とくに`precompute_elevation_attributes.py`はchunkごとにGSI標高APIへ外部HTTPを行い、
数十万Edgeの初回バックフィルで数時間規模になる。本範囲で「全edge_idを先読みしてセッションを閉じる」
方式からこのストリーミングへ変わった。理屈の上では:

- カーソルを持つトランザクションが数時間 idle in transaction のまま残り、
  その間 xmin が進まずDB全体でVACUUMが死行を回収できない
- `idle_in_transaction_session_timeout`を設定した環境では途中でセッションが切られ、
  `async for`が例外で落ちてバッチが中断する（それまでのchunkはcommit済みのため部分的に進んだ状態で終わる）

`precompute_way_landcover.py`（ラスタ読み込み）も同じ形の長時間ループを持つ。

## なぜ今は直さないか（トレードオフの判断）

T660は本番500万Edgeへの外挿で**peak 55.9MB→1.1MB（約1.5GB→一定）という実測根拠**を持つ
（principles.md 判断原則14「性能の主張は実測とセット」）。
一方この懸念は**本番で観測された事実ではない**。方式をロールバックするのは釣り合わない。

## 対応方針（トリガー発火時）

**観測する手段は既にある**。[T840](T840.md)が`/admin`「鮮度」タブへ「接続とトランザクションの
状態」（接続数・`max_connections`・`idle in transaction`の最長時間）を出した。起票時に
「まず足す」としていた部分はこれで埋まっている——足りないのは手段ではなく、**バッチを
回している最中に実際に見ること**である。

見ないまま同じ方式は増えており、[T919](T919.md)（`precompute_edge_landcover.py`）が3本目として
本番で実走した。次にこの形のバッチを本番で長時間回すときが、追加の作業なしで測れる機会になる。

張り付いていた場合にのみ「chunkごとに読み取りセッションを開き直す（keyset分割へ戻す）」を
検討する。`geom`順の要件によりkeysetではなくカーソルを採用した経緯（T660）を踏まえること。
