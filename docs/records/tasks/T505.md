# T505: モバイルUI全体の省スペース化（ボタン・余白の統一的な圧縮）

状態: 完了（2026-08-31。ブラウザでの実機確認は未実施）

## 背景

ユーザーがスマホ実機で操作中、「特定の1箇所ではなく、ボタンの大きさや余白が全体的に
大きい。全般的に省スペース設定に統一したい」とのフィードバックがあった。

過去（T299フォローアップ、`frontend/src/app/globals.css:353-361`）にモバイル向け
「全ボタン一律44px」というブランケットルールを敷いた際、チップ(36px)・ラジオ項目(32px)等の
意図的に小さいコンポーネントまで踏み潰す不具合が実機で見つかり、個別調整へ方針転換した
実績がある。今回は逆方向（縮小）だが、`min-height: 44px`のテキスト入力（iOS自動ズーム
防止）・`1.4rem`角のチェックボックス（タップ領域確保）等、大きいのに意図的な箇所も
混在するため、単純な一括CSSルールでは同種の事故が起きうる。

## 対応方針（ユーザー承認済み、2026-08-31）

「今の見た目を完全再現しなくてよい」という前提のもと、以下の順で進める。

1. モバイル表示される主要パネル・コンポーネント全体を洗い出し、意図的なサイズ指定
   （コメントで理由が明記されているもの: タップ領域確保・iOS自動ズーム防止等）を
   リストアップし、それらは変更しない。
2. それ以外の余白（padding/margin/gap）・ボタン/フォント サイズを、モバイル向けに
   縮小した値へ統一的に詰める。ピクセル単位で現状を完全再現する必要はない。
3. 可能な範囲で共通トークン（`--space-1〜4`等、`globals.css`）経由の値に寄せ、
   ハードコードされた直書きremが混在する状態を減らす（副次目標、本筋を妨げない範囲で）。

## 実装メモ

洗い出しの結果、モバイル表示される主要パネル（RouteSettingsPanel・BottomSheet・
MapLayersPanel・MapOverlayControls・page.module.css等）の大半は、過去の複数回の
「実機フィードバック対応」タスク（T34・T41・T299フォローアップ・T374・T404・T419・
T495〜T504等）を通じてコンポーネント個別に既にかなり圧縮済みだった。特に
MapOverlayControls・BottomSheet・page.module.cssのタップ領域（44px系）・iOS自動ズーム
防止（16px）・ピンチズーム競合対策（touch-action）は、いずれもすべて**トークンを
参照しないハードコードされたリテラル値**として実装されており、次のいずれかの
理由で意図的に保護されている（Exploreエージェントによる全文横断調査で確認済み、
変更していない）。

- タップ領域確保: `.app-bottom-sheet input[type=checkbox]/[role=checkbox]`(1.4rem)・
  `.app-bottom-sheet input[type=text/number]`・`label`(44px)・`.tabButton`(44px)・
  `.layerTitle`(mobile、44px)・`.locateButton`(44px)
- iOS自動ズーム防止: `.app-bottom-sheet input[type=text/number]`のfont-size 16px
- 意図的に小さいピル型（ブランケット44pxルールが踏み潰した反省の実例として
  globals.cssのコメントに名指しされている）: `LayerChip.module.css .chip`(36px)・
  `MapLayersPanel.module.css .modeItem`(32px)
- 視覚的な相対サイズ関係が固定されている: MapOverlayControlsの`.expandToggle`(1.6rem)・
  `.visibilityCheckbox`(1.1rem)・`.visibilityInfoButton`(1.2rem)
- ドラッグ当たり判定の意図的な拡張: `RouteSettingsPanel.module.css .stackBarHandle`
  （幅16px、視覚的な線より広く取っている）

一方、`--space-1〜4`・`--font-size-sm/md`という共通トークン自体は、これらの保護対象
から独立しており（保護対象はいずれもハードコード値でトークンを参照しない）、かつ
RouteSettingsPanel・BottomSheet・MapLayersPanel・page.module.css・RouteAxisProfile・
RouteList・ComparisonPanel・WeightPanel等、モバイルで表示される大半のパネルが既に
この共通トークン経由で余白・フォントサイズを指定している。そのため、個別ファイルを
1件ずつ手で詰めるのではなく、**このトークン自体をモバイル（640px以下）でのみ
圧縮する1箇所の変更**によって、保護対象に触れずに広範囲へ一括で効かせられると判断した
（ユーザー指示「個別cssの設定規模をこの際減らしていきたい」とも合致する）。

- `frontend/src/app/globals.css`: `@media (max-width: 640px) { :root { ... } }`を
  新設し、`--space-1〜4`を0.25/0.5/0.75/1remから0.2/0.4/0.55/0.75remへ、
  `--font-size-sm/md`を0.8/0.85remから0.75/0.8remへ、モバイルのみ圧縮する。
- 同ファイルの`@layer base`内、汎用`button`・`input[type=text/number]`の既定padding
  （従来ハードコードの`0.5rem 0.9rem`・`0.4rem 0.6rem`）を、上記共通トークン
  （`var(--space-2) var(--space-3)`・`var(--space-1) var(--space-2)`）へ置き換えた。
  個別のモバイル用ルールを増やさずとも、上記の:root圧縮に自動追従する
  （ユーザー指示「個別CSSの設定規模を減らしたい」に沿い、標準の1つの仕組みへ寄せた）。
- `page.module.css`の`.weatherHeader`/`.mobileActionBar`（モバイルで常時表示される
  上部バー2つ）と`RouteSettingsPanel.module.css`の`.hardFilters`は、トークンに
  対応しない中途半端なハードコード値（`0.35rem`・`0.3rem`）だったため、近い値の
  `var(--space-1)`へ置き換えた。ピクセル単位の完全再現よりも、共通の仕組みへ揃える
  ことを優先した（ユーザー承認済み「今を完全再現しなくていい」）。
- MapOverlayControls.module.css（623行、ピンチズーム競合・タッチ判定を巡る実機
  フィードバックの多重の修正履歴を持つ最もデリケートなファイル）は、対象コンポーネントの
  padding/サイズ自体が既にハードコードの小さい値（0.3rem前後）で共通トークンを
  参照していないため、このタスクでは変更していない。

## 検証結果

- backend側の変更なし。
- frontend: `npx vitest run`（page.test.tsx・RouteSettingsPanel・BottomSheet・
  MapLayersPanel・MapOverlayControls・useIsMobile.test.ts）141件成功、既存の回帰は無い
  （CSSのプロパティ値変更のみでクラス名・DOM構造は変えていないため、想定どおり）。
  Node.jsでの手動ブレースバランスチェックでCSSの構文崩れが無いことも確認した。
- **ブラウザでの実機/プレビュー確認は実施できなかった**: 作業ツリーがこのセッションの
  開始時点で既に他セッションのfrontend devサーバー（port 3010、`.claude/launch.json`の
  `frontend`設定）に占有されており、同一プロジェクトディレクトリで別ポートの
  2つ目のdevサーバーを起動する試みも（`.next`ビルドキャッシュの競合が疑われる形で）
  即座にクラッシュし安定起動しなかったため、Browserペインでの視覚検証はできなかった。
  `.claude/launch.json`への一時追加は動作確認後に元へ戻し、他セッションの環境には
  影響を残していない。ユーザーには実機（スマホ）で見た目を確認してもらう必要がある。
