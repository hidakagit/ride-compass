# T1201. 時刻で変わる軸を重み付きで足し算に入れると、ルート生成が3〜4割遅くなる

状態: 完了（2026-09-27）

## 背景

T1174の計測で見つけた（各方式1回ずつ）。60kmで8.5→11.2秒、80kmで最大17.5秒。軸の値の計算が掛け算の場合の約10倍。本番は今風の重みが0で表に出ていない。

## 原因

T1174の段階別の所要で、足し算（sum_dyn）と掛け算（prod_dyn）の差は動的軸の評価（`evaluate_axis_array`）の1回あたりの所要だけに出ていた
（呼ばれる回数は同じで、60kmで72回2,531ms対250ms）。その中の小数1桁への丸め（`axis_templates.py: round1_array`）が、×10がちょうど
`.5`に乗った要素だけPythonの`round()`を1要素ずつ呼んでいた。小数1桁の得点2つを0.5倍ずつ足した値は、半数近くの要素が`.5`に乗る
（開発機の合成データ100万要素で44.8%。掛け算の0.1倍ずつでは0.4%、1項の軸では0%）。この要素ごとの呼び出しが1回あたり数十msになり、
時刻のビンごとに評価し直す動的軸では回数ぶん積み上がる。本番の軸だけのときの`.5`に乗る要素は0.05%で、表に出ていなかった。

同じ形は合成（`difficulty.py: composite_difficulty_array`も`round1_array`で丸める）にもあり、同じ重みの2軸だけを合成する要求でも起きる
（開発機の合成データ50万要素で、重み1・1なら44.8%、本番の既定の重み0.08・0.15なら0%）。この修正は両方に効く。

## 対応

`.5`に乗った要素の決め直しを配列のまま行うようにした（`_round1_on_half`）。値を`仮数 × 2**-shift`の整数に直し、10進の中点
`(2*lower + 1)/20`との大小を整数で正確に比べる。中点に等しい（2進で正確に表せる、例: 0.25）ときは`round()`と同じく偶数の側へ丸める。
Pythonの`round()`とビット単位で一致する契約はそのまま（スカラーの経路`BreakpointLinearShape`の`round(…, 1)`と地図の段のしきい値が、
配列の得点と同じ値になる必要があるため）。標準の道具で済むか: `np.round`は`.x5`の境界で`round()`と食い違い、`decimal`・`fractions`は
要素ごとのPythonの処理で今と同じ遅さになるため、整数の比較を書いた。

## 計測（2026-09-27、本番VMの使い捨てコンテナ）

配信中のイメージ（7a5c5ab8。イメージの`axis_templates.py`はorigin/masterの変更前と同じmd5）で、都心（35.68, 139.76）発の周回を
60・80kmで生成した。軸はプロセスの中だけで1本足す（T1174のsum_dynと同じ: 風と路面の良否を0.5ずつ足し、重み1）。1つのコンテナの中で
base・sum_dynを交互に3回ずつ（起動直後の1本目は比べない）、今の丸めのコンテナと、直した`axis_templates.py`だけを重ねたコンテナを並べた。
計測の道具はscratchpadの`P-dynsum_vm.sh`・`P-dynsum_probe.py`（T1174の`M-mult_probe.py`を写した）。

同じ条件の3回のばらつきは0.6秒以内で、今の丸めでの差（3.7〜4.6秒）は本物だった。直したあとの差は60kmで3.7→1.6秒、80kmで4.6→1.8秒。
軸の評価の側の丸めに通った全要素のうち`.5`に乗った要素は、本番の軸だけで0.05%、足した軸があると12.6%（60km・80kmとも）。
合成の側の丸め（`difficulty.py`）では、この計測の重みでは0件だった。

**残る差（60kmで1.6秒、80kmで1.8秒）の内訳**: 時刻で変わる軸に重みがあると、合成をビンごとに行う——時刻で変わらない軸の重み付き和
（`axis_weighted_sums`、全区間ぶん1回で0.4〜0.8秒）と、ビンごとの合成（`compose_costs_from_axis_matrix`、base比+0.45〜0.75秒）。
これは足し算に限らず掛け算でも、既存の風の軸に重みを付けたときでも同じにかかる合成の手間（T1174の「①」）で、丸めの欠陥ではない。
残りは足した軸そのものの評価（丸めを含め0.4〜0.7秒）と、折返し点の本数の違い（生成ごとに候補数が変わる）。
