# T365. 目的地（終点）を指定できるルート生成への拡張・ルート結果のクリアボタン 規模M（2026-08-27完了、T365-2でUI再設計）

状態: 完了


- 背景: T364で経由地（中継地）指定を実装した直後、ユーザーから追加要望
  「経由地、あるいは目的地を指定することはできないか。目的地指定がある場合は
  現在地に戻らず目的地までのルーティングとする。無い場合はこれまで通り周回コース」
  （2026-08-27）。T364の`generate_via_waypoints`は常に起点へ戻る周回
  （`full_waypoints = [origin, *waypoints, origin]`）だけを扱っており、
  終点が起点と異なる経路（片道ルーティング）は未対応だった。
- UI設計方針（ユーザー選択、2026-08-27）: 経由地ピンと見た目・追加方法を分ける
  ため、地図コントロールに「目的地専用の追加ボタン」を新設する方式を採用
  （地図タップの見た目・ボタン種類を増やす他の2案は不採用）。ボタン押下で
  次の1タップだけ「目的地を置く」モードになり（既存の地物クリック判定もこの
  1タップだけは迂回する）、配置後は自動的に通常のタップ（経由地追加/地物詳細）
  へ戻る。目的地は最大1点、ピンをタップすると解除できる（経由地ピンの削除と
  同じ操作感）。
- 対応方針:
  1. backend: `RouteGenerateRequest`に`destination: Coordinates | None`を追加。
     `generate_via_waypoints`に`destination`引数を追加し、指定時は
     `full_waypoints`の終点を起点ではなく`destination`にする（経由地のみの
     場合は従来通り起点で終わる周回のまま）。`road_graph_engine.trace_loop`は
     終点座標が起点と一致する場合のみ`context.origin_node`を再利用し、
     一致しない場合は`find_nearest_node_indexed`で独立にスナップするよう
     一般化する（ループの場合の挙動は無改修で回帰確認）。`prepare`のbbox計算に
     渡す点集合にも`destination`を含める。
  2. frontend: `MapView.tsx`に`destination`表示用の単一マーカー（経由地ピンとは
     別色、旗アイコン等）と、「目的地を設定」ボタン押下後の次の1タップだけ
     destinationセットへ振り替えるarm状態を追加。`page.tsx`に
     `destination`/`destinationArmed`のstate・ハンドラを追加し、
     `handleGenerate`のリクエストに含める。
  3. `RouteList.tsx`は目的地ルート（`id==="route-destination"`想定）も
     `route-waypoints`と同様「〜方向」を付けず`direction_label`
     （「目的地ルート」想定）をそのまま表示する。
  4. 追加要望「ルートをクリアすることはできないか」も同時対応: 生成済みの
     候補一覧・地図上の描画・選択状態をリセットする「ルートをクリア」ボタンを
     ルート結果表示部に追加する（`routes`/`selectedRouteId`/`generatedConditions`
     をリセット、経由地・目的地のピン自体は消さない——別々の「クリア」操作として
     ユーザーが選べるようにする）。
- **T365-2: UI再設計（同日中、実機フィードバック2件を受けて）**:
  1つ目のフィードバック「スマホで地図タップしてもボタンが出てこない」は
  devサーバー再起動待ちの見かけ上の問題で実装バグではなかった（ユーザー確認済み）。
  2つ目のフィードバック（スクリーンショット添付）「経由地・目的地の操作パネルが
  地図上のレイヤーチップ列と重なって邪魔、アイコンだけにしてレイアウトを工夫して
  ほしい」を受けて地図上の浮動パネル自体を見直していたところ、ユーザーから
  「周回モードと目的地モードを切り替え、周回は距離指定・目的地は目的地/経由地指定、
  距離と生成ボタンがあるエリアでコンパクトに切り替え表示できないか」という
  より踏み込んだ再設計案が提示され、そちらを採用した。
  - `RouteForm.tsx`（distance/generateボタンと同じ場所、デスクトップ・モバイル両方の
    呼び出しで共通）に`routeMode`（"loop"|"destination"）のセグメントトグルを追加。
    周回モードは従来通り距離入力を表示、目的地モードは距離入力の代わりに
    経由地件数チップ（📍N+✕クリア）と目的地ボタン（🏁、未設定/武装中（点滅）/
    設定済みの3状態を1ボタンで循環、武装中に再度押すとキャンセル可能——初版には
    無かったキャンセル手段をここで追加）を表示する。
  - 地図上の浮動パネル（`.waypointControl`、T364/T365の初版実装）は完全に廃止。
    経由地・目的地の可視化は既存の地図マーカー（番号付きピン・🏁旗）のみで行う。
  - モード切り替え自体は経由地・目的地のstateを破棄しない（周回⇔目的地を行き来
    しても地図上のピンは保持され、目的地モードへ戻れば復元される）。ただし
    **生成リクエストにはrouteMode==="destination"のときだけwaypoints/destinationを
    含める**（周回モードでは地図にピンが残っていても無視し、常に8方位探索を行う）。
    地図への表示・タップでの追加受付も同様に`MapView`の新規prop
    `pinPlacementEnabled`（`routeMode==="destination"`と同値）で制御する。
  - 目的地モードは距離を入力させないため、`handleGenerate`が地図上の経由地・目的地
    から`distance_km`を自動算出する（フロント側に球面距離計算のユーティリティが
    無かったため`haversineKm`を新設。起点から最も遠い指定点までの距離+1km、
    `MAX_DISTANCE_KM`(100)で頭打ち。backend側`_check_waypoints_within_range`
    バリデーション、routes.py参照、を必ず満たす値にする必要があるための計算）。
  - `conditionsDirty`（「条件が変更されています」ヒント）はモードとgeneratedConditions
    のroute_modeが一致しない場合もdirty扱いにし、目的地モードで生成した直後に
    無関係な自動算出distance_kmとdistanceInputの差分で誤ってdirty表示されないよう
    loopモード時のみ距離を比較する分岐を追加した。
  - テスト: `RouteForm.test.tsx`にモード切り替え・目的地モードのバリデーション
    （経由地・目的地とも未指定なら送信不可）・各ボタンのコールバック配線を検証する
    新規テスト6件を追加。frontend全体693件成功、tsc/eslintクリーン。実機
    （dev server）でも周回⇔目的地の往復・目的地の武装/設定/解除サイクルを確認済み。
