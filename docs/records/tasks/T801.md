# T801. ターンの費用を較正する

規模S〜M。
状態: 未完了

実施中（段階1［較正の前提を整える］をmasterへ反映済み、残りは較正そのもの＝実走待ち。2026-09-13起票、[T790](T790.md)の段階2a-4から切り出し）

**パラメータ化は[T805](T805.md)へ委譲した**（2026-09-16、ユーザー判断）。変えられるようにする対象と、管理画面が面倒を見る対象を別々に決めると必ずズレるため、宣言を1つにしてそこから導く。本タスクに残るのは「値をいくつにするか」だけ。

## 背景

[T790](T790.md)段階2aで入れたターンの費用は**方位差だけで決める暫定値**（左折2秒・右折12秒・
Uターン60秒・直進とみなす方位差30度まで・上位道路の横断8秒・同右左折15秒、
`domain/routing.py: TurnCostSpec`）。

本番の柏→王子では、軸設定に沿った候補の右左折が64〜74%減り、上位道路との交差も51〜73%減った
うえ距離も短くなった（T790に実測あり）ので方向は合っている。残るのは値の妥当性。

T790の作業中、ユーザーから「2a-4（パラメータ化）までは不要」との判断があった——後から気軽に
較正できるかどうかが論点で、DB変更と本番バッチを伴わないなら急がない、という意図。
`TurnCostSpec`はdataclassのため、リクエストパラメータ化しなくてもコード変更だけで変えられる。

## 対応方針

- 実走で確認する（走ってみて右折の多さ・横断の苦労がどう変わったか）
- 値を見直す。信号の有無を見るようになる（[T800](T800.md)）と横断の費用の置き場所が変わるため、
  T800の後に較正する方が手戻りが少ない（**T800は2026-09-15に本番まで完了**。上位道路の
  横断・右左折の費用は信号の無い交差点でだけ付くようになった）
- **信号判定の半径もここで較正する**（[T800](T800.md)から渡された分）。ノードから何m以内の
  信号POIを「その交差点の信号」とみなすかで結果が大きく動く——T800の実測では半径を
  10m→60mに広げると、幹線が集まる交差点のうち信号ありとみなす割合が37.4%→67.9%まで変わり、
  頭打ちが無いためデータからは正しい値が決まらない。現在の40mは同じ交差点の点をまとめるのに
  使っている値を流用しただけで、較正されていない。広げるほど横断の費用が付かなくなる
- 値を変えられるようにする仕組みは[T805](T805.md)が持つ（本タスクでは作らない）

## 関連

- **ターン制限（OSMの`no_left_turn`等のrelation）はいま取り込んでいない。** 辺基準グラフなら
  表現できる（遷移を落とすだけ）。取り込むかは別途判断する——取り込みバッチ側の作業が要る

## 段階1: 較正の前提を整える（2026-09-16完了）

信号判定の半径が、**同じ交差点の点をまとめる距離（`POI_CLUSTER_EPS_M`）の値をそのまま
流用**していた。問うていることが違う2つ（「同じ停止か」と「この交差点に信号があるか」）が
1つの定数を共有しており、まとめる距離を較正で動かすと走行モデルの横断の費用まで一緒に動く。
較正しようにも、独立に動かせる状態になっていなかった。

`domain/traffic.py: SIGNAL_MATCH_RADIUS_M`として分けた（値は40mのままで挙動は変わらない）。
半径をSQLパラメータへ落とす`signal_radius_params()`も、どちらの定数を読むかがテストから
見える形にしてある。

### 検証（わざと壊して落ちることを見た）

- `signal_radius_params()`を`POI_CLUSTER_EPS_M`へ戻す → 新設した2件
  （まとめる距離を動かしても半径は動かない／半径は自分の定数で動く）がどちらも落ちた。
- backend: `pytest -q -m "not postgis"`・`pytest -q -m postgis`・
  `ruff check app scripts benchmarks tests`。
