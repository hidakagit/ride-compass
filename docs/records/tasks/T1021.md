## 何を守るか

`docs/conventions/testing.md`の「既存テストを直さず、実装から起こし直す」の7段手順。
T998・T1012で守れていなかった点は次のとおりで、**ここを外すと同じ結果になる**。

- **既存のテストファイルを開かずに書き始める。** `git show`・`git log -p`・grepの結果としても
  中身を見ない。旧版を開いてよいのは手順4以降で、目的は「今のソースからは導けない過去の
  事情」（回帰・実データ由来）だけ。構造を写すために開かない
- **旧版を物差しにしない。** diffしない／「落とした」と言わない／旧版にあったからという
  理由で足さない／一致率で出来を語らない
- **対象ファイル以外の実装を読まない。** 他モジュールの**関数・サービス・例外・定数**は
  テストへ直接importせず、対象モジュールの名前空間経由で触る。**ただし対象の公開
  シグネチャが要求する型は直接importしてよい**——差し替えても何も切り離せず、契約が
  未検査になるだけだから。T998では区別せず「1本だけ」としたため、`LeanNode`/`LeanEdge`を
  duck typingした偽のデータ型が生まれた（`test_routing.py`の`FakeNode`・`FakeEdge`・
  `FakeGraph`）。**実物がfrozen dataclassなら必ず実物を作る**
- **列挙の母集団を機械で導いて件数を書く。**「実装を全部読んだ」は列挙ではない。
  **列挙器そのものの穴を疑う**——2通りで数えて食い違いを見る（T1012では名前ベースの
  数え方が`_FieldsRecorder`を数え落とし、`setattr`の文字列ベースが拾った）
- **分岐カバレッジは検出器であって母集団ではない。** 未到達を埋める前に3問を通し、
  埋めなかったものは理由を1行ずつ残す
- **「列挙漏れ」と判定したら、なぜ導出から漏れたのかを次に導出する人が読む場所へ1行戻す**

## 進め方（T1012で確立した形）

1. 群ごとに、置き換え前のテスト件数・行数・行/分岐カバレッジを**実行して**取る
2. 汚染されていないエージェントを`isolation: "worktree"`で起動する
   （CLAUDE.md「作業ツリーの安全」）。指示書には上の「何を守るか」をそのまま入れ、
   **手順1〜3を終えるまで旧版に触れないこと**を`git show`も含めて明示する。
   実装は変更させない（欠陥は報告のみ。判定は人が行う）
3. 成果物へ機械監査を当てる——①実装の変更の有無 ②テストからの`app.*`直接import本数
   ③テストが触る`<対象>.X`の内訳（自ファイル定義／他モジュール由来）
   ④`--cov-context=test`で「実装へ1行も入らないテスト」 ⑤行・分岐カバレッジ。
   **報告の自己申告を鵜呑みにしない**（T1012では実装の変更2件が申告どおりか実体で確認した）
4. 「そのテストは要るか」の3問と「本番で作れない入力」の突き合わせは人が読む
5. 欠陥の要確認は`testing.md`「要確認の出し方」に従う（聞くかどうかを先に決める→
   ①利用者への約束を1文→②問題が顕在化する場面を1つ→③設計書・コード・テストの主張を
   3行→④選択肢は2つ）

**環境**: `PYTHONUTF8=1`必須。worktree配下に`.venv`は無いので本体チェックアウトの
`backend/.venv/Scripts/python.exe`を使う。カバレッジのモジュール指定は**ドット記法**
（パス記法は無報告になる）。`njit`を通る対象は`NUMBA_DISABLE_JIT=1`で測り直す。
長いヒアドキュメントは失敗するのでスクリプトはファイルへ書いてから実行する。
