# T975. 外部データの許諾条件を、採用時に必ず問われる仕組みにする 規模M

状態: 完了（2026-09-20起票、2026-09-23完了）

## 背景

2026-09-20、T970のDB設計中に国土数値情報の緊急輸送道路（N10）・重要物流道路（N12）が
**使用許諾条件「非商用」**であることが判明した。両方とも公開評価軸（car_stressの加点）と
地図レイヤーに出ており、削除が必要になった（[T973](T973.md)）。

問題は見落としそのものより、**問われる場所がどこにも無かった**ことである。ソースを採用する
とき・評価軸へ組み込むとき・以後のレビューのいずれでも、許諾条件を確認する手順が存在しない。
実際、発見のきっかけはユーザーの「ソースの取得元が公式に言っているものを参照してください」
という指示であり、こちら側の点検では出てこなかった。

RideCompassは**将来商用になりうる前提で扱う**（ユーザー方針、2026-09-20）。「今は非商用だから」
で判断を先送りしない。

## やること

### (a) 正本を作る: `docs/data-sources.md`

外部ソースごとに「提供元・公式ページのURL・使用許諾条件・商用可否・出典表記の要件・
加工した旨の要否・確認日」を持つ表を置く。**コードからは導けない制約**なので、
[docs/architecture.md](../../architecture.md)と同じ位置づけになる
（[docs/modules/README.md](../../modules/README.md)「このディレクトリが扱わない領域」へ追記する）。

### (b) 機械化できるかを、既存の検知器の全体像と突き合わせてから決める

母集団は機械的に取れる見込みがある——`backend/app/batch/source_adapters/__init__.py` が
「ソースを足す唯一の追加点」で、`@register_adapter("...")` の登録名が全件列挙できる。
だが**検知器にすると決めていない**。`review_checks.py` には既に29本あり、合わせて何を
覆っているかを誰も見ていない（[T966](T966.md)、未着手）。既存との母集団の重なり・
既存の不備なのか新規なのか・機械化の価値を突き合わせずに足すと、本数だけ増える。

**T966が済んでから判断する。** それまでは(a)の正本を置くところまでにする。

### (c) CLAUDE.mdへ必読の節を1つ足す

短く、詳細は`docs/data-sources.md`へのポインタにする。CLAUDE.md冒頭が警告している肥大化を
招かないこと。書く内容は次の3点に絞る:

- RideCompassは将来商用になりうる前提で扱う
- 外部データソースを追加・利用するときは提供元の公式ページで使用許諾条件を読み、
  `docs/data-sources.md` へ記録する
- 詳細は `docs/data-sources.md` 参照

## 実施内容（2026-09-23）

### (a) 正本: `docs/architecture/data-sources.md`

起票時の置き場`docs/data-sources.md`は、`docs/architecture.md`が章へ分割された（T979）後の
構成に合わせ、`docs/architecture/`の1章として置いた（「コードからは導けない外部の制約」は
この階層の役割）。`docs/architecture/README.md`の章表と、`docs/modules/README.md`
「このディレクトリが扱わない領域」へ行を足した。

表は全件の一覧であり、`docs/conventions/documentation.md`の「全件の一覧を書かない」に
当たる。一覧そのものが目的（公式ページにしか無い条件の記録）でコード側に等価な表現が無い
ため、同文書の例外節へ対象ファイル表と並べて明記した。

**母集団は取込アダプタより広い**。起票時の完了条件は「`source_adapters/__init__.py`の登録数と
一致する行」だったが、アダプタを持つのは取込バッチが扱うソースだけで、実行時に取りに行く
ソース（基礎地図・MSM・気象庁の防災情報・WBGT・逆ジオコーダ）はアダプタを持たない。
母集団はコードに現れる外部ホストから取った:

```bash
git grep -h -o -E "https?://[a-zA-Z0-9.-]+" -- backend/app backend/scripts frontend/src | sort -u
```

→ 外部の提供元は `download.geofabrik.de`（OSM）・`cyberjapandata.gsi.go.jp`／`maps.gsi.go.jp`
（地理院タイル）・`mreversegeocoder.gsi.go.jp`・`www.npa.go.jp`・
`io-10m-annual-lulc.s3.us-west-2.amazonaws.com`（`livingatlas.arcgis.com`は出典のリンク）・
`tiles.openfreemap.org`・`openmeteo.s3.amazonaws.com`・`www.jma.go.jp`・`www.wbgt.env.go.jp`。
`www.openstreetmap.org`・`react.dev`・`www.topografix.com`・`localhost`等はデータの取得先では
ない（出典リンク・コメント・XML名前空間・開発用）。アダプタの登録
（`osm_pbf_way`・`osm_pbf_node`・`gsi_dem_tile`・`io_lulc_tile`・`npa_honhyo`）はすべて表の
いずれかの行の「取りに行く場所」に載っている。

各行は提供元の公式ページを2026-09-23に読んで埋めた（URLは表にある）。起票時の調査表から
変わった点:

- 地理院タイルの規約は「国土地理院コンテンツ利用規約」（PDL1.0準拠）。
- 気象庁は利用規約がPDL1.0準拠であることに加え、**気象業務法の制約**（第17条 予報業務の許可・
  第23条 警報の制限）を別に挙げている。
- 環境省WBGTはサイトがPDL1.0準拠だが、**電子情報提供サービスは同規約の適用外**。
- 逆ジオコーダは公開APIとしての利用条件自体が無い。

商用可否を確定できなかった3件は「要確認」とし、[T1053](T1053.md)へ起票した。表記の要件と
画面を突き合わせて見つかった不足（Open-Meteo・環境省WBGTの出典が画面に無い）は
[T1052](T1052.md)へ起票した——正本を作った直後にその手順どおり1周回して2件出たことを、
この仕組みが働く確認とした。

### (b) 機械化: 作らない

結論は**検知器を作らない**。T966の完了を待たずに決めた根拠:

- CLAUDE.md「検知器を足す条件は厳しい」に当たる。「登録されたアダプタごとに表の行がある」を
  見る検知器は、アダプタの登録という**実装そのもの**を検査対象にし、アダプタ名と表の行の
  対応（写し）を抱える。T966が調べる「既存の検知器との重なり」を見るまでもなく、この基準で
  外れる。起票時にT966を待つとしたのは、検知器が29本あった時点の判断で、その後T986で
  3本まで棚卸しされ、足す条件自体が明文化された。
- 母集団がアダプタで閉じていない。上の通り、実行時に取りに行くソースはアダプタを持たず、
  アダプタだけを見る検知器は「全ソースに行がある」という誤った安心を出す。
- 見たいのは利用条件の**中身**で、行の有無ではない。中身は公式ページを読む以外に確かめ
  られない。

代わりに、採用の手順を**問われる場所**へ置いた: CLAUDE.md（毎セッション読まれる）の必読節と、
data-sources.mdの「使い方」（新しく使う前・使い方を変える前に読む／不明なら採用しない／
推測で埋めない）。

### (c) CLAUDE.mdの必読節

「外部データの利用条件（必読）」を「コミット時の同期ルール」の前に足した。見出しを含め
6行（本文4行）。書いたのは起票時の3点（商用前提・公式で読んで記録・詳細は正本）と、
「商用利用が不可・不明なものは採用しない」。
