# T1138. 同じ道・同じ時刻の風が、ルートを出す前（地図の色・区間の詳細）と後（ルートの区間）で別の規則で引かれる

状態: 完了（2026-09-26）

## 背景

周期レビュー第13回（2026-09-26）の指摘。性質: 同じ計算の重複・片側だけの修正（再発）。ルート後（T1108）はweather_service.get_wind_forecast_latticeで区間の中点に最も近い格子点（0.05°×0.0625°、domain/wind.py:79-80,110）、予報の範囲外は端へ寄せてextendedとして出す（wind.py:140-163）。ルート前はwind_way_service.py:100-115がタイル中心を0.02°格子へ寄せた1点、範囲外は値なし（servicesに独自の_nearest_time_index）で、区間インスペクタも同じ経路（dependencies.directional_materials）。dynamic_materials.py:84-87は評価器を「動的材料を評価する唯一の経路」と書くが、ルート前はwind_drag_ratioのスカラー版を直接呼ぶ。まず調べる段階: ルート前の近似（利用者の方位を全道路へ一律に当てる）を残すかを決め、格子と時刻の選び方をdomainの1か所へ寄せる。少なくとも「唯一の経路」の記述を直す。

## 問いと答え

問い（ダッシュボード`T1138-prewind`、2026-09-26）: ルートを出す前の地図の風の色分けを残しますか。残すなら、天気予報の範囲の外の時刻はどう塗りますか。
選択肢: (1) 残す。予報の地点の選び方をルートの後と同じにし、範囲の外は今どおり塗らない（推奨）／(2) 残す。範囲の外もルートの後と同じく最後の時刻の風で塗り、地図に印を出す／(3) ルート前の地図では風の色分けをやめる。

答え: (1)（2026-09-26）。

## 方針

設計原則 構造仕様17（源泉に従わせるかは「同じ事実か」で決める）に照らし、ルートの前後で「予報の地点と時刻の選び方」は同じ事実なので1か所にする。走行方位（前は利用者の1つの方位、後は区間の実際の向き）はルートの前には決めようがないため揃える対象にしない。範囲の外の時刻の扱いは答え(1)どおり前後で違えたままにする。

- 地点: `domain/wind.py: WindLattice`（MSMと同じ緯度0.05度・経度0.0625度）を、ルート前もそのまま使う。ただし従来の`covering`は格子を**範囲の南西の角から**数えていたため、同じ道でも探索範囲ごとに（ルートを出すたびにも）別の格子点へ寄りえた。格子を緯度・経度0度から数えた固定の線に揃え、どの範囲に敷いても同じ地点は同じ格子点へ寄るようにした。
- 各道の「中ほど」は両端の平均。区間単位のズームではルートの区間の中点（`mid_lat`/`mid_lon`、両端ノードの平均）と同じ点になる。タイルの鍵を引くSQLが中ほども返すようにした（`get_feature_keys_in_tile`→`get_feature_midpoints_in_tile`）。タイルをまたぐ道の中ほどはタイルの外にありうるため、格子はタイルと全中ほどを覆う範囲に敷く。
- 時刻: `WindForecastSeries`の選び方（指定時刻に最も近い予報の時刻、端へ寄せたかの印）を使い、端へ寄せたとき（予報の範囲の外）は塗らない。servicesにあった独自の`_nearest_time_index`は消した。
- 値: ルート前も`evaluate_dynamic_material_arrays`（`DynamicAxisRequestContext`）を通す。これで「動的材料を評価する唯一の経路」の記述が事実になった。
- 区間インスペクタ（`dependencies.directional_materials`）は`WindWayService`をそのまま呼ぶので、追加の変更なしに同じ規則になる。
