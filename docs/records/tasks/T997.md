# T997. 旧スキーマのテーブルを指したまま残っている経路を洗う

状態: 未完了（2026-09-22起票）

## 背景

[T996](T996.md)の全件走査中に、生データのテーブルを作り直した後も**旧テーブル名を指したまま
残っている経路**が複数見つかった。現行のテーブルは`source_features`（`source`列で種別を分ける）・
`road_edges`・`edge_materials`・`way_materials`・`node_materials`等で、`osm_raw_ways`・
`osm_raw_pois`・`osm_raw_nodes`・`road_nodes`・`elevation_attributes`・`edge_attribute_counts`・
`accident_points`・`osm_import_runs`・`accident_import_runs`はORMにも開発DB（本番スナップショット
由来）にも存在しない。

同一セッションで直した分は[T996](T996.md)のコミットに含む。

- `infrastructure/material_coverage.py`が`FROM osm_raw_ways AS w`を手書きしていた。共有断片
  `domain/material_sql.py: WAYS_SOURCE_SQL`は新スキーマへ移っており、**この1本だけが取り残されて
  いた**。材料の欠損率APIは全体が`UndefinedTableError`で落ちていた（実行して確認）。
- `domain/material_catalog.py`の`gradient_percent`の`present_count_sql`が
  `elevation_attributes`を数えていた。値は`edge_materials.average_grade`にある
  （同じ材料の`value_sql`は既に`em.average_grade`を指していた）。

## 残っているもの

### 1. `/api/debug/...`の健全性表示が恒久的に null

`api/routers/health.py`の`_KEY_TABLES`（`osm_raw_ways`・`osm_raw_pois`・`road_edges`・
`accident_points`）と`_IMPORT_RUN_TABLES`（`osm_import_runs`・`accident_import_runs`）のうち、
`road_edges`以外は存在しない。`_table_row_count`は欠落を例外にせず`None`を返す設計のため
**落ちないが、「バッチが本番で一度も走っていない」という誤った信号を出し続ける**。
この表示はまさにその判断のために置かれている。

対応: 現行スキーマで同じ問いに答えるテーブル・列へ置き換える（取込の実行履歴は
`source_runs`が持つ）。置き換え先が無い項目は表示から外す。

### 2. `scripts/measure_gradient_outliers.py`（371行）が1クエリも通らない

全SQLが`elevation_attributes`・`osm_raw_ways`・`road_edges.edge_id`・`re.highway`を参照する。
`road_edges`の列は`(osm_way_id, segment_index, from/to_node_id, geom, distance_m, bearing_deg,
reverse_bearing_deg, source_run_id)`で`edge_id`も`highway`も無い。
`docs/modules/frontend/static-map-layers.md:29`がこれを運用手順として案内している。

対応: 現行スキーマで書き直すか削除するかを決める。削除するならdocsの案内も同時に消す。

### 3. `docs/modules/backend/batch-pipeline-dependencies.md`が存在しないパイプラインを説明

`import_pbf.py`・`presplit_road_graph.py`・`precompute_road_node_degrees.py`・
`precompute_edge_attribute_counts.py`・`precompute_elevation_attributes.py`・
`precompute_way_attribute_counts.py`・`match_designations.py`の7本はいずれも存在しない
（`find backend -name`で0件）。現行は`ingest_cli.py`（`source_profile.yaml`＋アダプタ）→
`derive_cli.py`の2本。テーブル名も同様に旧いまま。

**2026-09-23、[T1022](T1022.md)で実施済み**: 文書ごと削除した。現行のバッチ（取込・派生の
段・鮮度台帳・世代の繰り上げ）は`docs/modules/backend/static-road-attributes.md`が既に
説明しており、削除した文書にしか無い現行の事実は無かった。唯一のリンク元
（`routing-engine.md`）は張り替えた。

### 4. `batch/source_profile.py`の`SourceSpec.columns`/`tags`が効いていない

YAMLから読んで`source_runs.profile`へ記録するだけで、絞り込みとしてどこも適用していない
（「列の絞り込み」という名前と説明が実態と違う）。消すとYAML契約と本番の記録内容が変わるため、
どちらへ寄せるかの判断が要る。

## 完了の条件

1〜4それぞれについて、置き換え・削除・据え置きのどれかを決めて実施済み。1は
`/api/debug`を実際に叩いて値が入ることを確認する。2は削除なら参照元のdocsも同時に消す。

## 探し方

`grep -rn "osm_raw_\|road_nodes\|elevation_attributes\|edge_attribute_counts\|accident_points\|
_import_runs" backend/app backend/scripts docs --include=*.py --include=*.md`。
ORMの実テーブルは`grep -rn "__tablename__" backend/app/infrastructure`で導く。

## 母集団の拡張（2026-09-23・周期レビュー第12回で判明）

**上の「探し方」の母集団が狭く、このままでは半分が残る。** 第12回の実測では、旧テーブル名の
残存は`docs/records`を除く全追跡ファイルに広く分布しており、うち相当数が
`backend/app backend/scripts docs`という現行の走査範囲の**外**にあった。

とくに重要なのは、**利用者・運用者が画面で読む文言に混ざっているもの**である。

- 材料カタログの材料が持つ「判定根拠」の説明文に旧テーブル名が書かれており、これは
  管理APIで配られて**軸スタジオの「材料」タブでホバー時に運用者へ表示される**。
- 同じ画面のⓘポップオーバーの本文が、母集団の説明として旧テーブル名を名乗っている
  （**画面に出る嘘**）。
- 飽和度の測定スクリプトが、存在しない集計テーブルを運用者向けメッセージで案内している。

このほか、欠損率を測るモジュールの docstring が旧スキーマで母集団を説明している
（SQL は[T996](T996.md)で新スキーマへ直したが**説明文だけが旧のまま**）、
`docs/conventions/testing.md`が存在しないテスト足場を名指ししている、
frontendのコメント・テストの docstring にも残っている。

### 探し方（差し替え）

上の grep の対象を次へ広げる。**`docs/records`と`node_modules`を除く全追跡ファイル**:

```
git ls-files | grep -v '^docs/records/' | xargs grep -n \
  "osm_raw_\|road_nodes\|elevation_attributes\|edge_attribute_counts\|way_attribute_counts\|accident_points\|_import_runs"
```

### 完了条件（差し替え）

「1〜4それぞれについて決めて実施済み」を、**上の grep が0件**へ変える。項目を数え上げる
形だと、母集団の外にあるものが完了条件から漏れる（第12回で実際に漏れた）。

**着手順**: 利用者・運用者に見える文言（材料の説明文・ⓘの本文・スクリプトのメッセージ）を
先に直す。コメントや docstring より実害が直接的で、かつ直すのが安い。
