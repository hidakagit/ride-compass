# T1087. 担当の所要の1行のCI待ちを、監査のときにGitHubから取って書き足す

状態: 完了（2026-09-23）

## 背景

T1049の改善提案（ユーザー承認 2026-09-23）。担当の記録の「所要（並行実行）:」の行は完了のコミットの時点で書くため、その後のCI待ちが「不明」になる（第1回のほぼ全担当）。予算（所要の実績の80パーセンタイル、scripts/orchestration/core.py）はこの行を読むので、CI待ちの分が実績から抜ける。やること: 担当はCI待ちを「不明」のまま書いてよいことにし、orchestrate.py audit が報告のshaの作業ブランチのCIの開始から結論までの時間を GitHub（scripts/orchestration/github.py、T1083のキャッシュ）から取り、所要の行へ書き足す文（または書き足しのコミットを作る手順）を出す。司令塔はそれを取り込みに含める。規約の「完了とpush」「監査の結果」を合わせて直す。完了条件: 第1回の担当の記録1件（例: T1083.md）に当てて、CI待ちの分が埋まった行が出ることを見る。予算の計算がその行を読めることも確かめる。

## 方針

- **完了のコミットのCIは、行の「うち」とは別の欄にする**。所要の行の実時間は「依頼→完了のコミット」で、完了のコミット自身のCIはその後の時間。これを`CI待ち`へ足すだけにすると、予算が使う作業そのものの時間（実時間−枠待ち−CI待ち）が、含まれていない時間を引かれて短く出る。そこで監査は行の末尾へ`完了のコミットのCI N分（監査で追記: 作成 HH:MM → 結論 HH:MM）`を足し、`core.parse_effort`はこの分を実時間とCI待ちの**両方へ**足す（作業そのものの時間は変わらず、実時間の側に完了後のCIが入る）。綴りは`CI待ちN分`の正規表現に拾われないものにした。
- **担当の「不明」は、作業ブランチのCIの実行から埋める**。担当が数で書けなかったCI待ち（`CI待ち不明`・`CI待ちはこのコミットの後（不明）`等）は、依頼の時刻から完了のコミットのCIの作成までに`orch/<名前>`で作られたCIの実行の区間の和（重なりは1回に数える）で置き換える。規約のCI待ちの定義「pushからCIの結論まで」と同じ量。依頼の時刻が読めない行（T993等の「依頼 … 不明」）は置き換えず、数で書かれていれば担当の値を残す。
- **時間の取り方**: 報告のshaに対するワークフローごとの最新の実行（監査が項目「CI」で既に取っているもの）の、最も早い`created_at`から最も遅い`updated_at`まで。ジョブの時刻（T1083のキャッシュ）は待ち行列の時間を含まず、担当が待つ時間（pushから結論まで）より短く出るので使わない。問い合わせが増えるのは「不明」の置き換えが要るときの作業ブランチの実行の一覧1回だけ。
- **書き込み**: 監査は差分（元の行・書き足した行）と、書き込むコマンド`python scripts/orchestrate.py effort-ci <名前> <sha> --base <基点>`を出す。`effort-ci`は書き足しのコミットを自分で作り（`ledger close`と同じ形）、書き足せない行（CIが結論待ち・作業ツリーに元の行が無い等）は理由を出して飛ばし、終了コード0で返す——取り込みの手順の連結を、所要の行の書き足しだけで止めないため。取り込みの手順は cherry-pick → effort-ci（担当ごと）→ ledger close → push の順で、`board unpushed`が出す1行と規約「監査の結果」の両方へ入れた（T1086の取り込み後の差し戻しで、司令塔の指示により追加）。

## 見送り

- **第1回の記録に既にある「不明」の行を遡って埋めること**はしない。記録は維持しない（docs/records/README.md）ため。埋めると規模札Sの作業そのものの時間が5件に届き、予算の根拠が実時間から作業の時間へ切り替わる——遡って埋めたいなら、それはユーザーの判断として別に決める。

## 注意

- 担当が書く完了の時刻は分単位で、完了のコミットのCIの作成がそれより前の分に入ることがある（T1083: 完了20:53・CIの作成20:52）。この1分程度は実時間へ二重に入る。
