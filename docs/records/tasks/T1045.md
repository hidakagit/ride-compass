# T1045. commit・pushが重いときがある——pre-pushの門を、検査を落とさずに速くする

状態: 完了（T1062 で pre-push の検査を CI へ移したため対象が消えた）

## 背景

ユーザー指摘（2026-09-23）: 「commitやpushが非常に重い時がある。このフックの仕組みを
機能劣化させず高速化できない？」。周期レビュー第12回の指摘を7本の並行エージェントで
潰している最中、pushのたびにpre-pushフックが数分かかり、その間に他者のpushが割り込んで
rebaseのやり直しが連鎖した（司令塔側でpushをロックで直列化して止血済み）。

## 結論（2026-09-23、L-env）

[T1062](T1062.md)で、pre-pushの検査（ruff・prettier・tsc・OpenAPI生成物のずれ・`review_checks.py docs`）を
すべてCIへ移した。masterのCIが全部通るまでbackendのデプロイは起動しないので、「検査を落とさない」は
CIの側で満たされる。フックに残ったのは停止ファイルの確認とmasterのCIが赤いときの警告だけで、
速くする対象が無くなった。

実測（T1062.mdの計測と同じもの）:

- 外す前: 旧フックのmaster宛ての所要が中央値4.92秒（3.59・4.92・12.13秒。計測した作業ツリーに
  `node_modules`が無く、prettier・tsc・OpenAPIの段は飛んだ）。飛んだtscの段は、`scripts/lockrun.py`の
  記録で41・74・131秒（2026-09-23の3件）。
- 外した後: master宛て中央値1.21秒（2.24・1.09・1.21秒。ほぼ`check_master_ci.py`のAPI1回）、
  `orch/**`宛て0.20秒。司令塔の実測では、masterへのpushが60〜91秒から8秒になった。

旧フックが**pushするコミットではなく作業ツリーを検査していた**欠陥（prettierとtscが手元のファイルを
読むため、通過記録の鍵に作業ツリーの状態を入れて回避していた）も、フックが検査をしなくなったので
対象外になった（CIはpushされたコミットを取り出して検査する）。

### L3の作業ツリーの途中の枝（`l3-t1045-wip`、11c818fd）

読んで確かめた（変更はしていない）。未検証・未pushのWIPで、2か所を変えている:

- `.githooks/pre-push`: 外部コマンドの起動を減らし、docs検査とmasterのCI確認を裏で並行に走らせる
  高速化。T1062でフックから検査そのものが無くなったため、対象ごと消えた。
- `scripts/review_checks.py`: `docs`が追跡ファイルの中身を1本ずつ開かず、`git cat-file --batch`
  1回でblobから読む（Windowsで負荷時にファイルを開く操作が重いため）。これはフックの外でも走る検査の
  高速化だが、いまこの検査はpushの経路に無く、手元で担当が明示的に1回回すだけになった。現在の
  所要は2.11〜3.42秒（この作業ツリーで3回、`python scripts/review_checks.py docs`）。

どちらも上の結論と食い違わない。枝は取り込む必要が無く、捨ててよい（消すかは司令塔の判断）。
