# T1176. 警報・洪水予報の区域を、国土地理院の逆ジオコーダではなく気象庁の区域の境界データから引く

状態: 完了（2026-09-27）

## 背景

起票案 proposal-jma-area-geocode（2026-09-26承認）。T1053-gsi-reverse-geocoder の答え(1)から。jma_warning_client.py が地点の区域を国土地理院の逆ジオコーダ（利用規約が無く商用利用に触れていない、data-sources.md で要確認）へ毎回問い合わせている。気象庁の「市町村等（気象警報等）」区域の境界GISデータ（気象庁ホームページの利用規約。着手時に公式で確かめ data-sources.md へ）を取得し、地点→区域コードを手元で引く形へ置き換え、逆ジオコーダへの問い合わせを撤去する。境界はファイルで持ちプロセス内で引く見込み（PostGISへ入れるなら本番DBへ書くのでL）。区域コードが今と同じになることは代表の地点で移行時に1回確かめ、残すテストは入力に対するあるべき区域コード。境界データの更新（市町村の合併等）を追う手順を書く。画面の表示は変わらない。

## 実施（2026-09-27、担当G-geo、origin/master 79624328）

前提の確認: 今のコードで`jma_warning_client.fetch_municipality_code`（逆ジオコーダ）を`warning_service.py`・
`flood_service.py`が呼び、`jma_area.municipality_code_to_class20_code`が市区町村コードの末尾へ`00`を付けて
区域のコードにしていた。ダッシュボードにT1176の件は無く、T1053-gsi-reverse-geocoderの答え(1)が出発点。

### 利用条件（公式で確認、2026-09-27）

- [予報区等GISデータ](https://www.data.jma.go.jp/developer/gis.html): 「市町村等（気象警報等）」をzip（シェープファイル、
  JGD2011）で配る。利用上の留意点に「気象庁ホームページの利用規約を遵守ください」とある。
- [気象庁ホームページ利用規約](https://www.jma.go.jp/jma/kishou/info/coment.html): 権利表記の無いコンテンツは
  公共データ利用規約（第1.0版）に準拠（商用可）。適用外はロゴ等と別ルールを明示したものだけで、GISデータについての
  別段の定めは無い。加工したら出典とは別に加工した旨を書く。
- 結論: 商用可。data-sources.mdへ行を足し、逆ジオコーダの行は使わなくなったので消した。

### 分かったこと（区域は市町村と1対1ではない）

- 配布物（`20260226_AreaInformationCity_weather_GIS.zip`、153,789,367バイト、Last-Modified 2026-02-26）は1,821図形。
  区域のコードは1,805種類で、area.json（2026-09-27取得）の`class20s`の1,805件と過不足なく一致した。残る16図形は
  コードが空（北方領土・帰属の決まっていない埋立地等）。
- 区域のコードのうち89件は末尾が`00`でない（市町村を分割した区域。例: 仙台市東部`0410001`、奈良市西部`2920101`、
  横浜市の区域`1410012`等）。**市町村コード＋`00`の方式では、これらの区域に入る地点は区域が引けず、警報・洪水予報が
  常に「なし」になっていた**（area.jsonに`0410100`・`2920100`が無い）。
- 代表の地点で逆ジオコーダ（6回）と突き合わせた（入力: 境界は上の配布物、area.jsonは同日取得）:

| 地点 | 境界から | 逆ジオコーダ＋`00` | 結果 |
|---|---|---|---|
| 千代田区（東京駅 35.6812,139.7671） | 1310100 | 1310100 | 一致 |
| 鎌倉市（鎌倉駅 35.3192,139.5467） | 1420400 | 1420400 | 一致 |
| 箱根町（箱根湯本 35.2323,139.1069） | 1438200 | 1438200 | 一致 |
| 藤沢市（江の島 35.2995,139.4800） | 1420500 | 1420500 | 一致 |
| 仙台市（仙台駅 38.2682,140.8694） | 0410001 仙台市東部 | 0410100（area.jsonに無い） | 旧方式は解決できない |
| 奈良市（奈良駅 34.6851,135.8048） | 2920101 奈良市西部 | 2920100（area.jsonに無い） | 旧方式は解決できない |

- 自己一致: 全1,805区域について区域の内点（`point_on_surface`）を引き、1,805件とも自分の区域を返した。

### 方針と実装

- 持ち方: 起票案の見込みどおりファイルで持ちプロセス内で引く（本番DBへは書かない）。点と多角形の判定は
  shapelyの`STRtree`（含む判定→無ければ`query_nearest`）で、自前の索引は書かない。シェープファイルの読み取りは
  pyshp（MIT、純Python）を`requirements-batch.txt`へ足した——backendの既存の依存にシェープファイルを読むものが無く
  （shapely・rasterioはベクタのファイル形式を読まない）、取得スクリプトだけが使うのでwebの経路には入らない。
- `scripts/fetch_jma_area_boundaries.py`: 置き場（`data/jma_area/<版>.json`）に今の版があれば何もしない。無ければzipを
  `fetch_verified`で落とし、コードの空の図形を落として区域ごとに0.0001度で簡略化し、区域のコード→WKB（16進）の
  JSONで書く。zipと他の版のファイルは消す。`deploy-backend.yml`がコンテナを入れ替える前に呼ぶ（土地被覆ラスタの
  取得と同じ位置・同じ「落ちたら止める」）。
- `infrastructure/jma_area_boundaries.py`: 置き場を最初に引いたときに1回だけ読み（`asyncio.to_thread`）、地点を含む区域、
  無ければ0.01度以内の最寄りの区域を返す。読めなければWARNINGを出してNone。
- `domain/jma_area.resolve_area`は区域のコードを直接受け取る。境界が返したコードがarea.jsonに無ければWARNING
  （境界の版が古いときの検知）。`municipality_code_to_class20_code`と逆ジオコーダの取得・キャッシュは撤去した。
- 境界データの更新を追う手順は[weather-dynamic-layers.md](../../modules/backend/weather-dynamic-layers.md)
  「警報の区域の境界」の「版の上げ方」に書いた。

### 測った値（開発機）

- 元の境界の頂点14,116,959。0.0001度で簡略化して約208万、置き場のファイル約66MB。
- 変換（シェープファイルの読み取り＋簡略化）78秒、ピークのワーキングセット約660MB（デプロイでは`--memory=2g`で走らせる）。
- backendでの読み込み5〜10秒、読み込み後の常駐の増加約80MB（全区域を引いても増えない）。1回の引き当て約0.04ms
  （含む判定。距離から引くと約2.7ms）。

### 範囲外で見つけたもの

- 本番backendの常駐が約80MB増える。探索範囲の上限（`services/graph_service.py`の`_RESERVED_BYTES`＝2GB、生成以外の
  ための取り置き）の内側に収まる見込みだが、本番の常駐の実測は取っていない。直さない（取り置きの余裕を測る材料として
  報告に書いた）。
- 洪水予報の電文の`class20Codes`は、気象庁が別に配る「市町村等（指定河川洪水予報）」の区域の体系で、警報の区域と
  分割の仕方が同じかは確かめていない（`class10Codes`での一致は変わらず効く）。直さない（今回の置き換えの前後で
  洪水予報の突き合わせ方は同じ）。
- 警報・洪水予報の区域を引く境界データの出典の表記は、[T1052](T1052.md)の母集団（data-sources.mdの表のうち画面に
  出る値の計算に使われる行）に入る。直さない（T1052の範囲。司令塔へ報告した）。
- 撤去した逆ジオコーダは[T1053](T1053.md)の項目1が前提にしていた。T1053は仕掛中のため、前提が変わったことは
  ダッシュボードにkind 決定（`T1053-gsi-replaced-by-t1176`）で置いた。
