# T1027. 失敗・空・待ちの伝え方を1本の規約へ揃える

状態: 未完了

## 背景

**判定は正しく効いているのに、その結論が画面へ届かない。** 実装ごとに出口が違うため、
同じ失敗が経路によって別の見え方をする。

読んで確かめたもの（コード精読。E2Eはこの範囲では使えなかった——後述）:

- **レイヤーの取得状態が`title`にしかない。** 「読み込み中です」「この範囲に表示できる
  データがありません」「データの取得に失敗しました」という文言の参照は全2箇所で、
  **どちらも`title=`**。画面に出るのは0.5remの状態ドットだけで、それも`aria-hidden`。
  **本プロジェクトの主用途はスマホで、`title`は出ない。** チップをONにしても何も描かれない
  とき、「壊れている／エリア外／ズーム不足」が判別できない。空タイルの検出ロジック自体は
  正しく動いている。
- **通信エラーの日本語化が1経路しか通らない。** `fetchJson.ts`の`wrapNetworkError`を
  `true`で渡す呼び出し元は管理画面の1件だけ。一般画面は全経路で素の`Error`が伝播し、
  `TypeError: Failed to fetch`・`TimeoutError: signal timed out`が日本語UIの中へそのまま
  出る（「取得に失敗しました: {error}」の形で本文に出る画面がある）。なお
  `routeApi.ts`は「ネイティブな英語メッセージをそのまま表示するのを避ける」と明記して
  包み直しているが、その防御はポーリング経路にしか入っていない。
- **429（混雑）の見え方が経路ごとに違う。** backendは日本語のdetailを返すが、
  ルート生成POSTでは読める／地図タイルではMapLibreのイベント経由でstatusもdetailも失われ
  汎用文言（しかも`title`）／レンズでは戻り値の形でdetailが消える／気象警報はfail-openで
  握りつぶされ**警告バッジが出ないだけ**／アメダスは本文が「観測値なし」になり取得失敗と
  データ欠測が同じ文字列になる。
- `routeApi.ts`はポーリングの連続失敗を原因に関わらず「ネットワークの不調で繰り返し
  失敗しました」と断定する。429も「ジョブが見つかりません」もここで消える。
- **絞り込み中であることが、畳んだチップから分からない。** 絞り込みの状態は保存される
  ため、次回訪問時に一部が欠けた地図を「データが無い」と読む。

**共通原因は1つ**: 判定（空タイル検出・`ApiError.status`）は既に揃っているのに、
出口が`title`1本しかない。個別に直すと同じ場所を3回触ることになるため、1本にまとめる。

## 対応方針

1. **先に規約を決める。** 「失敗・空・待ち」をどこへ、どの粒度で出すかを
   `docs/modules/frontend/`の該当文書へ書いてから実装する。決める論点は
   (a) 常時見える場所（▶パネル／チップ自身／トースト）、(b) `title`と`aria-label`の
   対称性、(c) 原因（429・ネットワーク・空）を利用者に見せる粒度。
2. `wrapNetworkError`は**既定を逆にする**（包むのを既定にし、素のErrorを出したい所だけ
   opt-out）か、表示側で包むかを決める。現状は「防御が既定でオフ」で、1箇所だけが
   オンにしている。
3. 429のdetailが経路の途中で失われる箇所（タイル・レンズ）は、**失うこと自体が正しいのか**を
   判断する。MapLibreのイベントからstatusを取れない制約なら、その制約を文書へ書いて
   汎用文言で正しいと確定させる（制約でないなら直す）。

## 完了条件

- 規約を文書化し、上の各経路がその規約に従っている。
- **スマホ幅（390px）で、レイヤーの取得状態が`title`以外の手段で読める。**
- 日本語UIの中に、外部由来の英語例外メッセージが本文として出る経路が無い。確かめ方:
  `fetchJson`の失敗経路をたどり、素の`Error`が画面のテキストへ到達する経路を数えて0。
- `aria-label`にあって視覚表示に無い情報が無い（走行条件バーの現在値がこの形になっている。
  読み上げ利用者に届き視覚利用者に届かないという逆転が起きている）。

## 備考: 確認手段について

この指摘はすべて**コード精読**による。E2E（`frontend/e2e/fixtures.ts`）を使えなかった
理由は2つあり、どちらも[T1014](T1014.md)の射程に入る:

1. worktreeに`frontend/node_modules`が無く、`playwright.config.ts`の`webServer`が
   `npm run build && npm run start:standalone`を180秒枠で起動するため、ビルドだけで
   枠を超える。
2. 仮に通しても**今回作り直したシーングループがそもそも生成されない**。`fixtures.ts`は
   地図スタイルを空（`sources:{}`・`layers:[]`）・タイル世代を空で渡すため、
   ソースが1つも作られない。配色・凡例・寸法は1つも実ブラウザを通らない。

**2はT1014の完了条件へ効く**——「E2Eを実機でしか出ないものの場として作り直す」なら、
シーングループが生成される最小の入力を fixtures が渡せることが条件になる。

## 実施（2026-09-23、1コミット）

規約は`docs/modules/frontend/page-composition.md`「失敗・空・待ちの伝え方」へ置いた
（fetch骨格`fetchJson.ts`の正本と同じ文書。階層は「実装粒度の取り決め」なのでmodules）。
静的レイヤー・レンズの各文書からはそこを指す。規約の4点: ①空と失敗の文言を混ぜない、
②失敗の文言は常に日本語（出所はbackendの`detail`か`messages.failure`だけ）、③常時は状態の
合図まで・文は1タップ奥・`title`だけに状態を持たせない、④原因の粒度は利用者の次の行動が
変わる単位まで。

経路ごとの処置:

- **通信エラーの日本語化**: `wrapNetworkError`オプションを撤去し、`requestOk`が常に
  `messages.failure`＋`[通信エラー]`/`[タイムアウト]`の日本語`Error`へ包む（英語の元文言は
  `cause`とdebugLogにだけ残す）。opt-outを使う呼び出し元は0件だったため、既定を逆にする
  のではなく選択肢ごと消した。Next.jsの管理APIプロキシ（`lib/adminApiProxy.ts`）が
  `detail`へ`error.message`（"fetch failed"）を埋めていた経路も同じ形へ揃えた。
- **ポーリングの連続失敗**: 「ネットワークの不調で」の断定をやめ、最後の失敗の文言
  （429のdetail・`[通信エラー]`・404のdetail）を括弧で添える。
- **アメダス**: 「観測値なし」→「観測値を取得できません」。backendは観測所の解決失敗・
  欠測・上流失敗を区別せず502にするため、失敗側へ倒した。原因（429のdetail等）は`title`。
- **レイヤーの取得状態**: チップの▶パネルに、ドットを出している間は状態の文を凡例の上へ
  出す（凡例の無いチップも状態がある間は▶を出す）。レンズはポップオーバーの見出し下へ出す。
  常時の見た目（ドット）は変えていない。
- **タイル・レンズの429**: 汎用文言のまま正しいと確定した。MapLibre 6.10の`AJAXError`は
  `status`を持つが本文は`Blob`で、`detail`を同期的に読めない（`node_modules/maplibre-gl/
  dist/maplibre-gl.d.ts`で確認）。原因に関わらず利用者の行動（待つ）は同じで、状態は
  次の取得サイクルで解除される。

## 保留（ユーザー判断）

いずれも「画面に常時何を出すか」で、対応方針とUI原則（走行中の情報量を増やさない・
説明はⓘの奥）だけでは決まらない。保留中も上の処置は独立に効いている。

1. **警報・注意報／暑さ指数／氾濫予報の取得失敗を画面へ出すか。** → **ユーザー決定（2026-09-23）:
   (b) 出す。実装済み。** 失敗している間だけ常設ヘッダーへ「未取得」の印（三角アイコン＋
   枠線のみの小さなピル）を1つ出し、タップで取得できていない出所と失敗の文言を読ませる。
   成功時は何も増やさない。`useWeatherConditions`が失敗した出所を`warningFetchFailures`で
   返し、`WarningBadgeList`が印を描く。backend内部の失敗はfail-openの空応答で届くため
   この印には現れない（フロントが拾えるのは通信エラー・429等だけ）。
2. **絞り込み中であることを畳んだチップから分かるようにするか。** 絞り込みは保存される
   ため、次回訪問時に一部が欠けた地図を「データが無い」と読みうる。選択肢: (a) 現状維持
   （▶を開けば分かる）、(b) 絞り込み中のチップへ状態ドットと同じ大きさの印を足す。
3. **走行条件バーの現在値を視覚表示へ出すか。** 完了条件「`aria-label`にあって視覚表示に
   無い情報が無い」はここに当たる。`aria-label`と`title`の非対称の解消は
   [T1034](T1034.md)の4で扱う（`title`の追加）が、`title`はスマホで出ないため、視覚利用者に
   値を届けるには常時表示を足すことになる。選択肢: (a) `title`追加まで（T1034）、
   (b) アイコンの下へ値（例:「9:30」「22km/h」）を常時出す。
4. **失敗をドットより強く知らせるか**（トースト等）。規約3は「常時は合図まで」としたが、
   合図がドット1つで足りるかは実機で見て決める事項。

保留1はユーザー決定により実装済み。2〜4は判断待ちのため、状態は未完了のまま。

完了条件のうち「規約の文書化」「390pxで`title`以外で状態が読める」「英語の例外文が本文に
出る経路0」は満たした。最後の数え方: `requestOk`の`catch`（fetch自体の失敗）は常に日本語へ
包み、`!response.ok`はbackendの`detail`か`failure[HTTP n]`、本文の解析失敗は
`parseFailure`——`fetchJson.ts`から素の`Error`が出る経路は0。骨格を通らない`fetch()`は
`jmaTileProtocol.ts`（MapLibreへ失敗を返すだけで文言を画面に出さない）と
`adminApiProxy.ts`（今回揃えた）だけ。**射程外として残るもの**: backend自身が英語で返す
`detail`（FastAPI/Pydantic標準の422の`msg`・未定義パスの"Not Found"）と、fetchではない
クリップボードの失敗（`hooks/useCopyToClipboard.ts`がDOMExceptionの文言を添える）。残るのは上の保留（とくに3が完了条件の4つ目に当たる）。
検証のコマンドと観測値はコミットメッセージにある。
