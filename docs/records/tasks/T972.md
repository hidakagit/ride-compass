# T972. 取り直せないデータのバックアップを持つ 規模M

状態: 未完了

調査済み・未着手（2026-09-20起票）。[T970](T970.md)の検討中に見つかったが、
データ層の設計とは別の話（運用）なので分離した。

## 背景: 軸定義は外部から取り直せない唯一のデータ

当時の復旧手順（[archive](../archive/disaster-recovery-before-t970.md)）はバックアップ
からの復元ではなく、**全部作り直す**形になっていた（「バックアップ」「pg_dump」「restore」
への言及は文書内に0件）。軸定義だけはスナップショットから投入していた。

本番DBを失ったときの復旧手段を分類ごとに見ると:

| 分類 | 復旧手段 |
|---|---|
| 生データ | 外部に正本がある。取り直せる |
| 派生データ | 生データから再計算できる |
| 運用の記録（import runs） | 失われるが実害は小さい |
| **管理データ（`axis_definitions`・`axis_registry_meta`・`tuning_overrides`）** | **再作成不能** |

軸スタジオで積み上げた調整は他のどこにも無い。**`backend/fixtures/
axis_definitions_snapshot.json`は「正本の二重化」ではなく、唯一のバックアップである。**

## 決めること

方針の案は「日次で取得し、最大N日保持」。ただし**置き場**を決める必要がある。

| 想定する障害 | 同一VM上に置いたダンプで復旧できるか |
|---|---|
| 誤操作で`axis_definitions`を壊す | ○ |
| DBのディスクが壊れる（DBは`/dev/sdb`、ルートは`/dev/sda`） | ○ |
| **VMそのものを失う** | **×**（ダンプも一緒に消える） |

3番目が、バックアップを持つ一番の動機である（このプロジェクトはOracle Cloud側の事故を
一度経験している）。**同一VM上の保持だけでは足りない。**

対象は管理データ3表で数十KB。10GBのDB全体をバックアップする話ではない。

## 保留（ユーザー判断）: 管理データ（軸の定義・調整値）のバックアップを、本番サーバーの外のどこへ置くか（2026-09-23 依頼）

利用者への約束: 本番のサーバー（VM）を丸ごと失っても、軸スタジオで積み上げた軸の定義と調整値が戻ること。

いま: 軸の定義・軸の版・調整値の3表（数十KB）は本番DBにしか無く、バックアップは無い（リポジトリ側の写しは
[T970](T970.md)段階Eで撤去済み）。VMを失うと、たとえば勾配レンズの13段階の調整を含め、軸スタジオで作ったものが
すべて消え、作り直しになる。
起きない場面: 道路・事故・標高等の生データとそこから計算する値は外部から取り直せるので、この話の対象外。

1. **（推奨）GitHubの定期ジョブ（デプロイで既にVMへ入れる）が毎日3表を書き出し、GitHub側に保管する。** 保持は
   GitHubの上限の最長90日。新しい鍵・契約が要らず、Oracle Cloud側の事故と独立に残る。
2. **Oracle Cloudのオブジェクトストレージ（無料枠）へVMから毎日置く。** バケットと鍵の作成がユーザーの操作になる。
   VMと同じアカウントの中に残るため、アカウント単位の事故には弱い。
3. **開発機が毎日VMから取ってくる。** 開発機が動いていない日は取れない。

保留した場合: バックアップの置き場が決まらないため、本タスクの残り（定期のバックアップ・まっさらなDBを立てる入口・
復旧手順書の書き直し）がすべて止まる。その間にVMを失うと管理データは戻らない。

**ユーザー決定（2026-09-23）**: 1（GitHubの定期ジョブが毎日3表を書き出し、GitHub側に保管する。保持は最長90日）。

## 段階A（2026-09-26）: 書き出しと戻しの入口

- 母集団は宣言から導く: 表の`info`に`orm_base.IRREPLACEABLE`の印を付けた表が対象（`axis_definitions`・`tuning_overrides`に付けた）。
  全表を載せたmetadataを返す`orm_base.declared_metadata()`を足し、`create_tables()`・`scripts/schema_gap.py`・バックアップの
  3者が同じ入口で全表を読む（それまで`create_tables`と`schema_gap.py`が同じimportの並びを2か所に持っていた）。
- 個人情報・認証情報の混入の確かめ（ORMの宣言から列挙）: ORMの表は`axis_definitions`・`derived_data_meta`・`edge_materials`・
  `node_materials`・`road_edges`・`source_features`・`source_runs`・`tuning_overrides`・`way_materials`で、利用者・認証の表は無い。
  印の付いた2表の列は、`axis_definitions`が軸id・並び順・形（JSONB）・既定の重み・表示名・説明・区分・公開の印・0次条件（JSONB）・
  地図チップの表示要素・時間帯・表示のしきい値とラベル・配信の印・更新時刻、`tuning_overrides`が較正値のid・値・更新時刻で、
  個人情報・認証情報・APIキーの列は無い。
- `scripts/admin_data_backup.py dump`: 標準出力へJSON（`dumped_at`・`git_commit`・表ごとの行）。アプリが起動時に行う読み込み
  （`load_axis_definitions`［`refresh_axis_definitions`から検算の部分を切り出した］・`load_tuning_values`）に通らない中身なら何も出さずに失敗する。
- `restore`: 空の表にだけ入れる（`--replace`で同じトランザクションの中で入れ替える）。入れた後に同じ読み込みで検算し、通らなければ
  ロールバックする。宣言に無い表・列は止め、バックアップに無い表は空のまま進む。
- 空の軸の表のときの起動失敗の文言が「管理API経由でしか入りません」と言っていたので、戻しの入口も指すようにした。

■ コメント（pg_dumpで取ったら？）への返答（2026-09-26）
取り方をpg_dumpにするのは筋がよく、書き出しの自前スクリプトより単純になります。ただし今回止まった理由は「取り方」ではなく「置き場」（本番のデータを公開の成果物・Release資産へ平文で出すこと）なので、pg_dumpに替えても置き場が同じなら同じ判定で止まる見込みです。
使うなら次の2点を押さえます。
- 丸ごとではなく軸の定義・較正値の表だけを取る（pg_dump -Fc -t <表>）。DB全体には標高の生データだけで12GBあり、VMの空き（29.0GB、T978）では丸ごとの書き出しを日々置く余裕が無い。生データ類は配信元から取り直せるので、守る対象は軸の表だけでよい。
- 戻すときは pg_restore で入り、今の restore が行っている「アプリが読み込めるかの検算」は無くなる（戻した後に起動して確かめる手順を手順書へ足す）。
VMの外の置き場は要るので、pg_dumpにするなら非公開の置き場（Oracle Cloudの非公開のObject Storage、またはバックアップ専用の非公開リポジトリ）と組むのが自然です。これを選択肢4として足しました。判定が通るかは書いてみるまで分かりません。

■ 利用者への約束
本番のサーバー（VM）を丸ごと失っても、軸スタジオで作った軸の定義と較正値が戻ること。

■ いまどうなっているか
- 段階A（作業ブランチ orch/B-backup、監査待ち）で、書き出しと戻しの入口はできた: backend/scripts/admin_data_backup.py の dump（標準出力へJSON。アプリが起動時に読み込めない中身なら何も出さずに失敗）と restore（空のDBへ戻し、アプリと同じ読み込みで検算してから確定）。本番DBを失ったときの手順は docs/conventions/deployment-sync.md「本番DBを失ったとき」。
- 残る段階B: 毎日VMへSSHで入って dump を打ち、GitHub Actionsの成果物（90日）とRelease資産の最新1件（上書き）へ置く定期ジョブ（.github/workflows/ の1本。既存の ORACLE_VM_HOST・ORACLE_VM_SSH_KEY のシークレットを使うので新しいシークレットは要らない。Releaseへ書くため permissions: contents: write を持つ）。
- これを書こうとしたところ、担当の実行環境（Claude Codeの自動許可の判定）が「本番のデータを誰でも見られる場所へ出す」書き込みとして拒否した。ダッシュボードの答え(1)（平文で公開してよい）はこれを許す判断だが、実行環境の判定は担当の側からは越えられない（越えようとしてはいけない）ため、書かずに止めた。
起きない場面: 段階Aの入口は定期ジョブが無くても使える。VMへSSHで入れる人は、deployment-sync.md の手順で手元へ書き出しておける（毎日ではない）。

■ 保留した場合
定期のバックアップが無いまま。その間にVMを失うと、最後に手で書き出した時点より後の軸の調整は戻らない（手で一度も書き出していなければ全部戻らない）。初回の手動実行と、手順書どおりの復元の確かめ（小bbox。答えT972-restore-check）も、定期ジョブの後に置くので止まる。

2. ユーザーが書く: 担当の実行環境の判定には触れない。書く中身: 毎日（正時を避けた時刻）とworkflow_dispatchで起動し、SSHで「sudo docker run --rm --network=host --env-file /home/ubuntu/ridecompass-backend.env ridecompass-backend:latest python scripts/admin_data_backup.py dump」の標準出力をファイルに受け、actions/upload-artifact（retention-days 90）と、gh release（タグ admin-data-backup、無ければ作る）への upload --clobber で置く。
3. 非公開へ変える: 答え(1)を取り直す。判定が変わるかは書いてみるまで分からない。
4. pg_dump＋非公開の置き場: 書き出しの入口が単純になり、公開の置き場へ出さない。段階Aの dump/restore（自前の約260行とテスト120行）は残さずに消し（置き換えではなく削除）、手順書（deployment-sync.md）を pg_restore の形へ書き直す。

■ 推奨の理由
1。置き場と見える範囲はユーザーが既に決めていて、設計も入口もできている。残りは書き込みの許可だけ。

### 問い: 管理データ（軸の定義・較正値）の pg_dump を、どの非公開の置き場へ毎日置きますか

- 件: `T972-private-store`（kind 保留、書き手: 司令塔（第3回、T972-workflow-refused の答え(4)から））
- 選択肢: (1) Oracle Cloud の Object Storage の非公開バケット（VMと同じクラウド。VMから直接置く）／(2) バックアップ専用の非公開の GitHub リポジトリ（GitHub Actions の定期ジョブが置く）（推奨 1）
- 答え: (1) Oracle Cloud の Object Storage の非公開バケット（VMと同じクラウド。VMから直接置く）（2026-09-26）
- 取り込み: (1) Object Storage の非公開バケット。T972 段階B（pg_dumpで定期に置く・段階Aの自前コードを消す）を振り出し待ちに積んだ。バケットの作成と権限はユーザーの操作として担当が手順を置く

■ 前提（T972-workflow-refused の答え(4)）
取り方を pg_dump（axis_definitions・tuning_overrides の2表だけ、-Fc）に替え、置き場を非公開にする。段階Aの自前の書き出し・戻し（約260行とテスト）は段階Bで消す。

■ 各選択肢で起きること
1. Object Storage の非公開バケット: VM上の毎日の定期実行（cron か systemd の timer）が pg_dump を打ち、OCI CLI でバケットへ置く。古い版はバケットの保持ルール（例: 90日）で消える。VMを丸ごと失ってもバケットは残る（VMとは別の資源）。要るユーザーの操作: バケットを作る・VMがバケットへ書ける権限（インスタンスプリンシパルの動的グループとポリシー）を入れる。Oracle Cloud の無料枠に Object Storage 20GB があり、2表のダンプは数百KB程度の見込み（未計測）。
2. 非公開の GitHub リポジトリ: GitHub Actions の定期ジョブが SSH で VM に入り pg_dump を受け取り、専用の非公開リポジトリへ置く（コミットか Release 資産）。要るユーザーの操作: 非公開リポジトリを作る・そこへ書けるトークンをシークレットに登録する。VMの外（GitHub）に置くので、Oracle Cloud のアカウントごと失っても残る。今回の実行環境の拒否は「公開の場所へ出す」ことが理由だったので、非公開なら通る見込みだが、書いてみるまで分からない。

■ 推奨の理由
1。VMの中で完結し、本番のデータがGitHub（CIのログや成果物）を通らない。定期実行の仕組みもVMに閉じる。2はアカウントごと失う事態にも耐えるが、トークンの管理が1つ増える。

## 段階B（2026-09-27）: pg_dumpを毎日Object Storageの非公開バケットへ置き、段階Aの自前の書き出し・戻しを消す

前提は上の答え（T972-workflow-refused の(4)、T972-private-store の(1)）: 取り方は`pg_dump -Fc -t <表>`（DB全体は取らない）、
戻しは`pg_restore`、置き場はOracle Cloud Object Storageの非公開バケット（VMから直接置く）。段階Aの自前の
`dump`/`restore`は置き換えではなく削除。

### VMからObject Storageへ置く手段（公式で確かめたもの／未確認のもの）

公式で確かめたもの（2026-09-27に読んだ）:

- インスタンス・プリンシパル（[Calling Services from an Instance](https://docs.oracle.com/en-us/iaas/Content/Identity/Tasks/callingservicesfrominstances.htm)）:
  VMは動的グループに入れ、ポリシー`Allow dynamic-group <名前> to <動詞> <資源> in compartment <名前>`で権限を受ける。
  証明書は自動で作られ1日に何度も入れ替わる。OCI CLIは`--auth instance_principal`（または`OCI_CLI_AUTH=instance_principal`）。
  動的グループのルールは`instance.id = '<OCID>'`の形（[Writing Matching Rules](https://docs.oracle.com/en-us/iaas/Content/Identity/dynamicgroups/Writing_Matching_Rules_to_Define_Dynamic_Groups.htm)）。
- 権限（[Object Storage policy reference](https://docs.oracle.com/en-us/iaas/Content/Identity/Reference/objectstoragepolicyreference.htm)）:
  `PutObject`は、その名前のオブジェクトが無ければ`OBJECT_CREATE`、あれば`OBJECT_OVERWRITE`を要る。条件の変数
  `target.bucket.name`でバケットを絞れる。`request.permission`で個々の権限に絞る書き方は
  [Object Lifecycle Management](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usinglifecyclepolicies.htm)の例文にある。
- OCI CLIの公式コンテナイメージ`ghcr.io/oracle/oci-cli`（[Working with the OCI CLI Container Image](https://docs.oracle.com/en-us/iaas/Content/API/SDKDocs/clicontainer.htm)）:
  インスタンス・プリンシパルで打てる例が載っている。パッケージのページ（github.com/oracle/docker-images/pkgs/container/oci-cli）に
  linux/arm64がある（VMはaarch64）。
- `oci os object put`（[CLIリファレンス](https://docs.oracle.com/en-us/iaas/tools/oci-cli/latest/oci_cli_docs/cmdref/os/object/put.html)と
  ソース`objectstorage_cli_extended.py`）: `--force`が無いと、置く前に`head_object`で既存を確かめる（読む権限が要る）。
  `--no-overwrite`もこの確かめを通る。`--force`なら確かめずに置く。128MiB以下は1回で置く。
- 事前認証リクエスト（PAR、[Using Pre-Authenticated Requests](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usingpreauthenticatedrequests.htm)）:
  バケット単位のPARで書き込める。期限は必須だが上限は無い。書き込みのPARは`OBJECT_CREATE`と`OBJECT_OVERWRITE`の両方を持つ。
- 無料枠（[Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)）:
  Object Storageは3つの層の合計20GB・月5万リクエスト。**ホームリージョンだけ**。
- systemd（Ubuntu 24.04のman）: `Persistent=true`は最後に起動した時刻をディスクに持ち、止まっていた間に過ぎた回を
  timerが有効になったときに1回打つ。`OnCalendar=`はIANAの時間帯を後ろに付けられる。`RuntimeDirectory=`は
  `/run/`の下に作られユニットが止まると消える（既定0755）。`PrivateTmp=`は私用の名前空間の`/tmp`を作る。
- PostgreSQL 18の文書: `pg_dump`は自分より新しいメジャー版のサーバーからは書き出さない。`-t`は依存する他の
  オブジェクトを書き出さない。`--strict-names`は各`-t`が1つ以上の表に当たることを要る。`-Fc`は既定で圧縮。
  `pg_restore --single-transaction`は全体を1つのトランザクションで打つ（`--exit-on-error`を含む）。

未確認のもの（本番の初回実行で分かる。ユーザーの操作の手順に確かめ方を入れた）:

- `OBJECT_CREATE`だけのポリシーで`oci os object put --force`が通ること（公式の表からの推論）。
- コンテナの中から（`--network=host`）インスタンス・プリンシパルの証明書を取れること（公式の例は網の指定なし）。
- VMでpostgresユーザーのpeer認証が有効なこと（Ubuntu・PGDGの既定）と、ホストの`pg_dump`が18であること（サーバーと
  同じPGDGのパッケージで入る。tech-stack.md）。
- `systemctl link`した作業コピーのユニットを`enable`できること。
- 動的グループをDefault以外のアイデンティティ・ドメインに作ったときのポリシーの書き方（`'<ドメイン>'/'<名前>'`）。

### 決めたこと（品質＝正しさ・保守する量で決めた）

- **認証はインスタンス・プリンシパル**、PARは採らない。PARはVMに期限の長い秘密（URL）を置き、しかも書き込みのPARは
  上書きも許すので、URLが漏れるかVMが乗っ取られると既に置いたバックアップを書き潰せる。インスタンス・プリンシパルは
  VMに秘密を置かず、ポリシーを`OBJECT_CREATE`だけに絞れる——置いたものの読み出し・上書き・削除がVMからはできない。
- **OCI CLIは公式のコンテナイメージで打つ**。ホストへ入れる（インストールスクリプト・pip）と、Pythonと依存の保守が
  VMに1つ増える。dockerは既にある。
- **`pg_dump`はホストのもの**。イメージ（python:3.12-slim、Debian）の配布物はサーバー（PGDGの18）より古く、`pg_dump`が
  書き出しを断る。PGDGをイメージへ足すと組み立てが1段増える。ホストの`pg_dump`はサーバーと同じ版で入り、aptで一緒に上がる。
- **表とDB名は宣言から導く**: デプロイ済みのイメージで`scripts/admin_data_dump_args.py`を打ち、印（`IRREPLACEABLE`）の付いた表を
  `--table=`で、DB名を`DATABASE_URL`から出す。シェルに表の名前を書かない（印を足せば次の書き出しから入る）。接続は
  postgresユーザーのpeer認証で、パスワードをコマンドラインに出さない。
- **定期はsystemdのtimer**（cronではない）。`Persistent=true`でVMが止まっていた日の分を起動時に打て、出力はjournalに残り、
  `systemctl list-timers`で前回・次回が見える。cronは取り逃しを打ち直さず、出力の行き先（メール）がVMに無い。
  ユニットとシェルは`backend/ops/`に置き、VMの作業コピー（デプロイがコミットへ揃える）を`systemctl link`で指す——
  中身の変更がデプロイで届く。`backend/**`はデプロイの判定の対象なので、ここを変えるとコンテナの入れ替えも起きる
  （作業コピーを揃えるのがデプロイだけなので、除外しない）。
- **消す規則を持たない**（問いの本文の例「90日で消す」から変えた）。開発DBでの実測で1回5,738バイト（軸7件・較正値0件）で、
  1年で約2MB。年齢で消す規則は、定期が止まったまま90日過ぎるとバックアップを全部消す——T972-dormant-expiryで問うたのと
  同じ落とし穴になる。規則が無ければ、止まった日が続いても最後のものが残る。
- **戻しはスキーマごと入れ替える**（`pg_restore --clean --if-exists --single-transaction`）。データだけを入れる形
  （`--data-only`）は表に行があると主キーで止まり、先に空にする段（表の名前を要る）と、1つのトランザクションにまとめる
  工夫が要る。`--clean`は表の定義も書き出した日の本番のもので入れ替え、1つのトランザクションなので途中で落ちれば何も
  変わらない。まっさらなDBでも（`bootstrap_database.py --to schema`の後）、表を壊しただけでも同じ1コマンドで済む。
  2表へはほかの表から外部キーが無い（`ForeignKey`をgrepして確かめた）ので落とせる。
- **戻した中身の検算は起動に任せる**（ユーザーの答え）: 書き出し・戻しの時点ではアプリの読み込みを通さない。戻した後に
  backendを起動し直し、`/health`とログの「軸定義をDBから読み込みました」を見る手順を手順書に足した。
