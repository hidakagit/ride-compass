# T575: `_tile_grid_cache`（DEMタイル解析済みグリッド）にサイズ上限が無くOOMを起こす

状態: コード対応完了（2026-09-04起票・同日完了）。本番への再実行はユーザー確認後に別途実施。

## 背景

2026-09-04、[T552](T552.md)対応方針4の先行調査（全8軸への計測拡大）で、`gradient`軸が
本番で76.5%欠損している実態が判明した。原因を遡ると、`refresh_derived.py`の
⑦`precompute_elevation_attributes`が本番（関東本土全域、road_edges約500万件）で
同日発生したOOMインシデント（[docs/disaster-recovery.md](../disaster-recovery.md)参照）
以降、完走できておらず11.6%しか進捗していないことに行き着いた。

コード調査の結果、`backend/app/infrastructure/elevation_client.py`の
`_tile_grid_cache`（GSI DEMタイルの解析済みグリッド、256×256セル/タイル、キー=
`(dem_type, tile_x, tile_y)`）にサイズ上限が無いことが根本原因と特定した。同ファイルの
既存コメントが「対象範囲が関東圏に留まる現状の運用規模では実害が無いと判断...将来
対象範囲が全国規模まで広がる場合は上限つきLRUへの変更を検討する」としていたが、
関東規模で既にその想定を超えていた。

`precompute_elevation_attributes.py: _fetch_all_edge_ids`がEdgeを地理的に並べ替えず
DB取得順のまま処理するため、実行が進むほどキャッシュは関東全域に散らばったタイルを
溜め込む。本番DBを2%サンプリングした概算では、道路網が触れるz14 DEMタイル数は
少なくとも約4,400枚（サンプル増加でも頭打ちしておらず実際はさらに多い可能性）。
1タイルのグリッドはPython上約2.5〜3MBを占めるため、4,400〜8,000枚を溜め込むと
11〜24GB以上になる計算で、本番VMの物理メモリ12GBと矛盾なく一致する。

**この問題はバッチ専用ではない**: `_tile_grid_cache`はモジュールグローバルのため、
本番backend本体（`api/dependencies.py: get_elevation_attribute_service`、未split
エリアへの初回アクセス時に同じ`ElevationClient`を使う経路）にも同じ無制限成長の
リスクが存在する。

## 対応方針

`_tile_grid_cache`へ、このコードベースに既存の同種パターン（`graph_material_cache.py:
_LRUCache`・`search_graph_cache.py: _TileKeyedLru`と同じタイルキー式LRU）でサイズ
上限を設ける。ディスク側（`tile_cache.py`、生DEMタイル本文）は既にTTL無しで永続化
済みのため、メモリキャッシュから追い出されてもネットワーク通信なしのローカル
ファイル読み出し＋再パースのみで復元でき、再取得コストは小さい。

## 実施内容（2026-09-04完了）

- `backend/app/infrastructure/elevation_client.py`: `_tile_grid_cache`を素の`dict`から
  `OrderedDict`へ変更し、`_remember_tile_grid`（`graph_material_cache.py: _LRUCache.set`
  と同じ定型処理）経由で書き込むよう統一。`DEFAULT_MAX_TILE_GRIDS = 500`（1タイル約
  2.5〜3MBとして最大約1.5GB相当）。参照時（キャッシュヒット）も`move_to_end`し真の
  LRUにした（旧実装は挿入順のみでアクセス順を反映しない疑似LRUだった）。
- `docs/modules/backend/elevation.md`「DEMタイル方式」節の「サイズ上限は設けていない」
  という記載を実装に合わせて更新。
- テスト: `tests/test_elevation_client_cache.py`へ
  `test_tile_grid_cache_evicts_least_recently_used_beyond_cap`を追加（上限を2へ
  monkeypatchし、3タイル目を読むと最も長く使われていない1タイル目が追い出されることを
  確認）。既存8件を含め全9件pass。`pytest -q -m "not postgis"`（1373件）green。

## 所要時間の見積もり（2026-09-04、今朝のクラッシュ時ログより）

本番の`/home/ubuntu/refresh_derived_prod.log`（今朝のインシデント発生時の実行ログ）に
残っていたチャンク別所要時間（`precompute_elevation_attributes.py`のINFO、
chunk_size=2,000）を実測値として使用:

- 185チャンク完了時点でクラッシュ。chunk 3以降は安定して平均約4.0〜4.1秒/チャンク
  （chunk 1は初回タイル取得でキャッシュが空のため20.1秒、chunk 50〜185の区間で
  増加傾向は見られず、メモリ肥大化はクラッシュ直前まで速度に影響していなかった）。
- 残りEdge数（2026-09-04時点でelevation_attributes未計算分）: 約444万件
  （5,025,067件 − 582,355件）。
- 残りチャンク数: 約2,221チャンク（444万件 ÷ 2,000件）。
- 概算所要時間: 2,221チャンク × 約4.1秒 ≈ **約2.5時間**（DB取得順の残り93%が同じ
  傾向を保つ前提の外挿であり、確定値ではない。GSI側のレート制限有無も長時間連続実行では
  未検証）。
