# T639. 「地図データを再読み込み」ボタンのサーバー側操作とブラウザ側操作を分離し、サーバー側を管理画面へ移す

規模M。

状態: 完了（2026-09-10完了）

## 背景

`app/page.tsx: renderMapSettingsSectionBody`の「地図データを再読み込み」ボタン
（`setRefreshToken`）は、1アクションで性質の異なる2つの操作を同時に行っている。

| | 操作 | 影響範囲 |
|---|---|---|
| ① | `POST /api/basemap/refresh`（`regionApi.ts: refreshBasemapCache`） | **サーバー側**のファイルキャッシュを全削除。基礎地図だけでなく路面ベクタタイル等も含めて消える（`tile_cache.clear_all()`）ため、**全利用者**に影響する |
| ② | `map.setStyle()`＋`redrawAllLayers`（`MapView.tsx`の`refreshToken` useEffect） | **押した人のブラウザ**の地図インスタンスのみ |

影響範囲が「全利用者」と「自分の画面だけ」という桁違いのものが、1つのボタンに乗っている。
一般利用者向けの地図画面に置かれているため認可もかけられない（`basemap.py: basemap_refresh`の
コメントに、管理API共通の認可境界`require_admin_basic_auth`を付けると一般利用者のボタンが
401になるため付けられない、と記されている）。

`page.tsx`には「このページが持つ地図インスタンス（refreshToken）に紐づくため、/adminへは
移設せずここに残す」というコメントがあるが、これは②を理由に①の置き場所まで決めてしまって
おり、分離すれば成り立たなくなる（同一コミットで書き換える）。

## 対応方針（案）

①と②を別の操作として分ける。

- **①サーバー側キャッシュのクリア**: `/admin`（軸スタジオ・研究/開発者ツール）へ移す。
  移した先では`require_admin_basic_auth`をかけられるため、`basemap.py`側の認可も
  併せて見直す。押しても押した人の画面は変わらないため、「消しました。各利用者の表示へは
  次回読み込み時、遅くとも`BASEMAP`の`max-age`（10分、`api/cache_policy.py`）で反映されます」
  といった結果表示が要る。
- **②ブラウザ側の再描画**: 地図画面に残すか廃止するかを決める。通常のページリロードで
  同じ結果が得られるなら、`refreshToken`機構（`page.tsx`のstate・`MapView.tsx`の
  useEffect・`styleReloadPendingRef`の連打ガード）ごと畳める。残す場合はサーバー側を
  呼ばない純粋なクライアント操作にする。

②を廃止する場合は`MapView.tsx`から`refreshToken` propと関連するテストも消えるため、
影響範囲の確認（`MapView`のprop契約・既存テスト）が要る。

## 保留した場合の影響

一般利用者が、自分の画面を直すつもりで**全利用者向けのサーバーキャッシュを消せる**状態が
続く。実害は「消えた直後のアクセスが遅くなる」程度で壊れはしないが、影響範囲の異なる操作が
1つのボタンに同居していること自体が、認可をかけられない原因になっている。

## 関連

[T632](T632.md)で基礎地図の`Cache-Control`を`BASEMAP`（10分）にした際、この`max-age`が
「ボタンを押した効果が現れるまでの最大の遅れ」になる点を判断材料にした。分離後は押すのが
管理者だけになるため、遅れの位置づけも変わる。

## 対応

対応方針（案）どおり①と②を分けた。②は**廃止せず、サーバー側を呼ばない純粋な
クライアント操作として地図画面に残した**。

### ①サーバー側キャッシュのクリア → `/admin`

- `POST /api/basemap/refresh` → `POST /api/admin/basemap/refresh`へ移し、
  `require_admin_basic_auth`を付けた。入口は管理画面`/admin`の「鮮度」タブに新設した
  `TileCachePanel.tsx`だけになる（`DerivedDataFreshnessPanel`が「古いかどうかを見る」のに対し、
  こちらは「古いものを捨てる」操作側のため同じタブに並べた）。
- 経路は他の管理APIと同じ「同一オリジンのroute handler経由」に揃えた
  （`app/admin/api/basemap-refresh/route.ts` → `proxyToBackendAdmin`）。
  ブラウザは`/admin`読込時のBasic認証セッションをそのまま再利用するため、
  クライアント側は資格情報を持たない。
- **レート制限（`basemap_refresh_rate_limit_per_minute`）は撤去した。** これは
  「認証が無いこと」への代替の歯止めとして置かれていたもの（撤去前のコメントがそう述べていた）で、
  認可境界の内側へ入った時点で存在理由が無くなる。設定値も同時に削除した。
- `cache_policy.py`の個別エントリ`("/api/basemap/refresh", NO_STORE)`も撤去した。
  移設後のパスは既存の`("/api/admin/", NO_STORE)`が同じポリシーで覆うため、
  個別に持つと同じ決まりごとが2箇所になる。`policy_for_path`のdocstringが
  最長一致の例としてこのペアを挙げていたため、実在する
  `/api/weather/amedas`と`/api/weather`の組へ差し替えた（テストも同じ組へ）。

### ②ブラウザ側の再描画 → 地図画面に残す

`MapView.tsx`の`refreshToken` effectから`refreshBasemapCache()`の呼び出しを外し、
`setStyle`＋`redrawAllLayers`だけにした。ボタンの表示名も
「地図データを再読み込み」→「**地図の表示を再描画**」へ変え、
`page.tsx`側のコメント（「地図インスタンスに紐づくため/adminへは移設せずここに残す」）を
分離後の理由へ書き換えた。

`refreshToken`機構ごと畳む案も検討したが採らない。ページ全体の再読み込みでは生成済みの
ルート候補が消えるため、「地図だけを組み直す」入口はページリロードでは代替できない。
`styleReloadPendingRef`の連打ガードは`setStyle`の重なりに対するもので、サーバー呼び出しの
有無とは無関係なため残す。

`services/regionApi.ts`の`refreshBasemapCache`は撤去し、管理API側の
`services/basemapAdminApi.ts: refreshTileCache`へ移した。T328の回帰テスト
（HTTPエラー時に「失敗 (HTTP xxx)」と「失敗 (通信エラー)」を二重ログしない）は
共有骨格`lib/fetchJson.ts`に対する検証のため、移設先の`basemapAdminApi.test.ts`へ引き継いだ。
