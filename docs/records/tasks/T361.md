# T361. axis_definitionsのfresh bootstrapをmigrationシードからDBスナップショット取込みへ転換（migration/API二重管理の恒久解消） 規模M〜L（2026-08-27完了）

状態: 完了


- 背景: T360（本番反映作業の直前に発覚、2026-08-27）で、T353がaxis_definitionsの
  変更をmigrationではなくaxis_admin APIの直接操作で行った結果、fresh bootstrap
  （CI・新規開発環境・disaster recovery等、まっさらなDBへ全migrationを順に適用する
  経路）では削除済みの軸が復活する不整合が発生した。T360では発生済みの不整合を
  個別migration（0022）で解消したが、これは対症療法に過ぎない。
  **「軸定義の変更経路がmigrationとAPIの2つ存在する限り、両者の同期漏れは構造的に
  再発し続ける」**というのが根本原因（ユーザー指摘、2026-08-27）。
- 対応方針（ユーザー承認済み、方針B）: `axis_definitions`テーブルの**データ**を
  migrationでシードする運用そのものをやめ、完全にランタイムデータとして扱う。
  fresh bootstrap時は、空のテーブルへmigrationでシードするのではなく、**本番の
  現在の状態をダンプしたものを取り込む**運用に切り替える（テーブル構造＝DDLは
  引き続きmigrationで管理する。データ＝行の内容だけを対象とする）。
  これにより「API経由で自由に調整できる」という軸スタジオの設計思想（T353で
  確立: shape_paramsの値は唯一の正解が無い継続的チューニング対象であり、監査証跡・
  ロールバックは過剰品質）と、「fresh bootstrapとの整合性」を両立できる。
  検討すべき論点（着手時に詰める）:
  1. ダンプの取得タイミング・方法（本番デプロイの都度自動化するか、手動運用にするか）。
  2. dev/CI環境の初期化フロー（`tests/test_migrate.py`のブートストラップテストが
     「まっさらなDBへmigration適用→ダンプ取込み」の2段階になることへの対応）。
  3. 「新規軸の追加・削除もmigrationで行う」というT353で確立した運用ルール（CLAUDE.md）
     も、本方針への統一に伴い見直しが必要になる可能性がある（新規軸追加もAPI経由に
     一本化するか、DDL相当の変更のみmigrationに残すか）。
  4. ダンプにテスト用途以外の機微情報が含まれないことの確認（axis_definitions自体は
     評価ロジックのみで個人情報等は含まないが、念のため）。
- 優先度: P2相当（実害はT360と同様、軸一覧の一時的な不整合に留まる）。着手判断は
  ユーザー承認後、別途行う。

- **実装内容（2026-08-27完了）**: 上記4論点への回答を含め、以下を実施した。

  1. **論点1（ダンプのタイミング）**: 手動運用を採用（自動化しない）。軸の
     shape_params調整自体が既に「本番反映は別途」という手動フロー（T353）のため、
     スナップショット更新もその延長に置くのが自然と判断した。デプロイパイプラインへ
     自動組み込みする案も検討したが、低頻度な操作のためリスク（誤ってスナップショットの
     生成元DBを取り違える等）の方が上回ると判断した。
  2. **論点2（dev/CI初期化フローの2段階化）**: `backend/scripts/
     bootstrap_ci_db.py`（CI用）・新設`backend/scripts/bootstrap_fresh_db.py`
     （新規dev環境・disaster recovery用、`create_tables()`→`apply_pending_migrations()`
     →スナップショット読み込みの3段を1本化）の2スクリプトへ実装した。
     `tests/test_migrate.py`のブートストラップテストも
     `create_tables→apply_pending_migrations→load_axis_definitions_snapshot`の3段を
     通しで検証するよう拡張した（新規テスト2件も追加、下記）。
  3. **論点3（新規軸add/deleteの運用ルール見直し）**: 見直しを実施。CLAUDE.mdの
     該当節を「軸の新規追加・削除・shape_params調整は**すべて**axis_admin API経由、
     migrationは`axis_definitions`/`axis_registry_meta`のテーブル構造（DDL）のみを
     管理し、以降の新規migrationへ軸の行データを追加しない」へ更新した（0014〜0022の
     過去の行データ入りmigrationは、このプロジェクトの標準運用どおり書き換えない）。
  4. **論点4（機微情報の確認）**: `axis_definitions`は評価ロジック（shape_params・
     重み・表示メタデータ）のみで個人情報・認証情報等は一切含まないことを実装時に
     再確認した。

  **設計（migration/API二重管理の解消方法）**: 過去のmigration（0014〜0022）を
  書き換える案は「既存migrationは書き換えない」という標準運用に反するため採らず、
  かつ新規に「行を削除するmigration」を追加する案も、通常のデプロイパイプライン
  （`scripts/apply_migrations.py`、本番へ毎回実行される）経由で本番の生きたデータを
  意図せず消してしまう危険があるため採らなかった。代わりに:
  - `app/infrastructure/axis_definitions_snapshot.py`（新設）に
    `dump_axis_definitions_snapshot`/`load_axis_definitions_snapshot`を実装。後者は
    **無条件に**テーブルを空にしてから投入する（空チェックはしない）設計とし、
    fresh bootstrap専用ツール（`bootstrap_ci_db.py`・`bootstrap_fresh_db.py`）からのみ
    呼ぶ。通常のアプリ起動経路（`main.py`のlifespan・`services/axis_registry_service.py:
    refresh_axis_definitions`）や、稼働中のDBへ繰り返し実行される`app/batch/
    import_pbf.py`等からは意図的に呼ばない——呼ぶと、デプロイやバッチ実行のたびに
    本番の生きた軸データ（API経由でチューニング済みかもしれない）がスナップショットの
    内容で黙って上書きされる事故になるため。`refresh_axis_definitions`の
    「テーブルが空なら`AxisDefinitionSyncError`で起動自体を失敗させる」という
    fail-fast方針（T349/T350）はこの変更後も維持し、自動修復は入れなかった
    （fresh bootstrapツールを踏まずにアプリを起動しようとした場合は起動が落ちるのが
    正しい挙動という判断を踏襲）。
  - `AxisDefinitionRepository`（`app/infrastructure/axis_definition_repository.py`）へ
    `count()`・`delete_all()`・`set_revision()`を追加（既存の`upsert`/`delete`/
    `get_revision`と組み合わせてスナップショットの読み書きを実装するための最小限の
    追加）。
  - `backend/scripts/dump_axis_definitions_snapshot.py`（新設）: 現在のDB
    （DATABASE_URL）の内容を`backend/fixtures/axis_definitions_snapshot.json`へ
    ダンプするCLI。本番/devでAPI経由の軸変更を行った後、これを手動実行して
    リフレッシュしコミットする運用（論点1）。
  - `backend/fixtures/axis_definitions_snapshot.json`（新設）: 初期スナップショット。
    実際の本番DBへは接続できないため（このセッションはローカルのまっさらな
    PostGISへ`create_tables()`→全22 migration適用のみを行い、その結果＝13軸を
    ダンプした内容——現時点でmigrationのシード内容とスナップショットの内容は
    数値として一致する。本番/devでAPI経由の変更が別途入っている場合は、
    `dump_axis_definitions_snapshot.py`を本番へ向けて手動実行し再生成すること）。
  - `backend/Dockerfile`へ`COPY fixtures ./fixtures`を追加（デプロイイメージ内から
    `bootstrap_fresh_db.py`等を実行できるようにするため、`migrations`/`scripts`と
    同じ扱いに揃えた）。
  - `tests/test_migrate.py`: 既存のブートストラップテストを
    「migration適用→スナップショット読み込み」の2段まで検証するよう拡張し、
    新規テスト2件（`test_load_axis_definitions_snapshot_round_trips_with_dump`・
    `test_load_axis_definitions_snapshot_replaces_existing_rows`）を追加した。

  **検証**: ローカルにPostgreSQL 16＋PostGIS 3を用意し（本タスクのため新規セットアップ）、
  `pytest tests/test_migrate.py`（8件）・`pytest tests/ -k axis`（248件）・
  `pytest tests/`全体（1,278件、osmium依存の2ファイル[test_import_pbf.py・
  test_pbf_source.py、本タスクと無関係]を除く）がすべてPASSすることを確認した
  （`test_evaluation_bulk.py`の4件は、このセッションのサンドボックスで`numpy`==2.5.2/
  `scipy`==1.18.1が取得できずやや古いバージョンで代替インストールした環境起因の
  既知の失敗——git stashしてこのタスクの変更を含まない状態でも同じ4件が失敗することを
  確認済みで、本タスクの変更とは無関係）。`bootstrap_fresh_db.py`・
  `dump_axis_definitions_snapshot.py`・`bootstrap_ci_db.py`の3スクリプトはいずれも
  ローカルDBに対して実機実行し、期待どおりの挙動（migrationのシード13行→
  スナップショットの13行へ置き換え、`refresh_axis_definitions`がその後正常に
  読み込める）を確認した。

  **未実施・引き継ぎ事項**: 本番DBには接続していない（このセッションからは到達
  できず、CLAUDE.mdの方針どおり無断でも触れない）。本番/devの実際のaxis_definitions
  が、ここでコミットした初期スナップショット（migrationのシード内容と同一）から
  既に乖離している場合（API経由の追加チューニングが入っている場合）は、ユーザーの
  判断で`dump_axis_definitions_snapshot.py`を本番/devへ向けて実行し、生成された
  差分を確認のうえコミットし直すこと（残作業はT377として起票）。
