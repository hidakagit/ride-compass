# T1198. 軸スタジオで他の軸が参照している軸を削除でき、本番のbackendが次の起動で止まりうる

状態: 完了

## 背景

T1131段階Bの範囲外で見つけた。削除の処理が参照を確かめず、残った軸が存在しない軸を指したまま本番DBに残る。起動時の軸の読み込みは不整合で止まる。

## 着手時に確かめた前提（origin/master 4b2fa353）

- 起動時の読み込み（`services/axis_registry_service.py: refresh_axis_definitions`）は、0行と、
  `domain/axis_definitions.py: check_axis_definition`に通らない軸（参照先の軸が同じ読み込み結果に無い等）を
  `AxisDefinitionSyncError`にし、起動を止める。
- `AxisRegistryAdminService.delete`が見ていたのは「最後の1軸」と「公開済み」だけで、参照は見ていなかった。
  内部軸は下書きのまま公開軸から参照されるので、参照されている軸がそのまま消せる。消すと
  commitの後の`refresh_axis_definitions`が`AxisDefinitionSyncError`を送出し（管理APIは500）、行は消えたまま
  DBに残り、次の起動が止まる。ガードを外した状態で新しいテストを流して再現した（下の「検証」）。
- 画面（`AxisStudio.tsx`）は参照を自前で数えて確認ダイアログを出し（`axesReferencing`。`shape`だけを見て
  0次条件の参照を数えない）、「評価対象外になります」と伝えて削除を通していた。T323の決定
  （一律拒否はしない。内部軸を意図的に整理したい場面がある）に基づくが、その前提だった「消すと評価
  できなくなるだけ」は、読み込みが参照の不整合で止まるようになった今は成り立たない。
- ダッシュボードにT1198の件は無かった（`pending-backup`をgrep、0件）。

## 対応方針

- 範囲は性質から決めた: 「書いた後の状態を起動時の読み込みが受け入れるか確かめずに確定する」書き込み。
  管理サービスの書き込み（create・update・delete・unpublish）を列挙し、判定の入力（軸の集合・各軸の中身）を
  変えるcreate・update・deleteに、確定する前の判定を置いた。unpublishは判定が読まない`is_published`だけを
  変え、前の状態は読み込みを通っている（起動できている）ので、置いても通らない経路になるため置かない。
- 判定は写さない: 読み込みの判定（0行と`check_axis_definition`）を`_loading_problem`へ切り出し、
  `refresh_axis_definitions`と書き込みの両方がそれを呼ぶ。「最後の1軸は削除できない」の個別のガードは
  同じ判定の0行の側に含まれるので消した。
- T323の「一律拒否はしない」は引き継がない。参照されている軸を消した状態は本番が起動しない状態で、
  確かめて通す選択肢が無い。内部軸を整理したい場面は、参照している軸を先に直すか消せば今も成り立つ
  （断るときの文は、参照している軸と理由を名指す）。ユーザーの価値判断が要る選択ではないと判断した。
- 画面は判定を持たない: `axesReferencing`・確認ダイアログ・最後の1軸での削除ボタンの無効化を撤去し、
  backendの409の理由を一覧の上の誤りとしてそのまま出す（既存の`actionError`の表示）。
