# T1059. ワーカーを複数にした起動が本番の形（Linux・Docker）で実際に止まるかを見る

状態: 完了（2026-09-25）

## 背景

T1020でワーカーが複数なら起動を止める仕組みを入れたが、この開発機（Windows）ではuvicornのワーカーがlifespanまで届かず、実際に止まるところを見ていない（ユーザー決定D-009で別途起票）。

## 何を見るか

本番と同じイメージ（`backend/Dockerfile`）を、CMDの末尾へ`--workers 2`を足して（または
`-e WEB_CONCURRENCY=2`で）起動し、次の3つを観測する。本番のコンテナは入れ替えない——
使い捨てのコンテナを別名・別ポートで立てる（本番VM上でやるなら`--network=host`のまま
ポートだけ変える）。

1. 各ワーカーのlifespanが`RuntimeError`（`backendは1プロセスでしか正しく動かない（workers=2）`）
   で止まり、どのワーカーもリクエストに応答しない（`curl`で`/health`が繋がらない）。
2. uvicornの親プロセスが止まったワーカーを**起動し直し続けるか**。uvicorn 0.34の
   `supervisors/multiprocess.py: keep_subprocess_alive`は、死んだワーカーを0.5秒ごとの監視で
   作り直すため、起動が止まったまま同じエラーのログが流れ続けると読める。実際にそうなるか、
   そのときログの量（`--log-opt max-size=10m --log-opt max-file=5`で頭打ちになるか）を見る。
3. `--workers`なし（本番のCMDそのまま）では従来どおり起動し`/health`が応答する。

## なぜ要るか

T1020の完了条件2「ワーカー2で起動して実際に止まることを見た」は、開発機（Windows）では
満たせなかった。機能を持たない最小のアプリでも、uvicornのワーカーがlifespanへ入る前に
消えて作り直され続ける（変更と無関係に起きる）。観測できたのは「本物の`app.main`の
lifespanへ、ワーカー2のときの`sys.argv`で入ると止まる」ことまでで、spawnされたワーカーが
親の`sys.argv`を受け継ぐことは`multiprocessing/spawn.py`（`sys_argv`を子へ渡して復元する）で
確かめただけである。

2の結果次第で、デプロイの失敗を検知できるかが変わる。`deploy-backend.yml`はコンテナを
`docker run -d`で入れ替えたあと起動の成否を見ていないため、止まり続ける状態でもデプロイは
成功扱いになる（ワーカーを増やす変更を入れた本人が気づくのは、利用者の画面が全部落ちてから）。

## 完了の条件

1〜3の観測結果（コマンドと出力の要点）がこの記録にある。2で作り直しが続くなら、
デプロイ後に`/health`を待つ確認を`deploy-backend.yml`へ足すかどうかを起票する。

## 観測の結果（2026-09-25、担当 D-workers）

**結論**: 1〜3とも記録の見立てどおり。ワーカー2では各ワーカーがlifespanの`RuntimeError`で止まり、
uvicornの親プロセスが**生きたまま作り直しを続ける**。コンテナは`Up`のまま・Dockerの再起動回数は0で、
外から見える失敗の印は「`/health`に繋がらない」ことだけである。作り直しが続くため、完了の条件に従い
「デプロイ後に`/health`を待つ確認を`deploy-backend.yml`へ足す」起票案を仕掛中のダッシュボードに置いた
（doc_id `proposal-deploy-health-wait`）。

### 環境（本番との違い）

Linuxのクラウドコンテナ（4コア）で`dockerd`（Docker 29.3.1）を起動して観測した。前提を今のコードで確かめた:
uvicornは`backend/requirements.txt`で`uvicorn[standard]==0.34.0`、イメージ内も0.34.0。止める検査は
`app/infrastructure/single_process.py`の`require_single_worker`で、`app/main.py`の`lifespan`の先頭で呼ばれる
（DB・Redisに触る前に止まるので、1・2はDB無しで観測できる）。

この環境のネットワーク方針でDocker Hub（429）とdeb.debian.org（403）に届かなかったため、`backend/Dockerfile`を
変えずに、**観測用の写し**（リポジトリに置かない）でイメージを作った。元との違いは依存の取得経路だけ:

- ベース`python:3.12-slim`は公開ミラー（`mirror.gcr.io`と`public.ecr.aws`の2か所で同じダイジェスト
  `sha256:2f17fc04…`）から取得し、同名へ付け直した。Python 3.12.14・Debian 13.7・glibc 2.41。
- `apt-get install libexpat1`の代わりに、ホスト（Ubuntu 24.04、glibc 2.39）の`libexpat.so.1.9.1`を同じ場所へ置いた。
  `import app.main`が`rasterio`を読み、無いと`ImportError: libexpat.so.1`で起動前に落ちることを確かめてから入れた。
- `pip install -r requirements-batch.txt`は、ホストで同じ要件をcp312・manylinux向けに`pip download`した
  wheel（59本）から`--no-index`で入れた（ビルドは`--network=none`）。

起動の引数は`deploy-backend.yml`の本番の`docker run -d`と同じ（`--restart unless-stopped --network=host
--log-opt max-size=10m --log-opt max-file=5`、CMDの引数もそのまま）で、ポートだけ変えた。`--memory`・
ボリューム・`--env-file`は付けていない。本番DBへは繋いでいない。

### 1. ワーカー2では各ワーカーが止まり、`/health`は繋がらない

```
docker run -d --name t1059-w2 --restart unless-stopped --network=host \
  --log-opt max-size=10m --log-opt max-file=5 rc-t1059 \
  uvicorn app.main:app --host 0.0.0.0 --port 8765 --proxy-headers --forwarded-allow-ips='*' --no-access-log --workers 2
curl -sS -m 3 http://127.0.0.1:8765/health
```

- ログ: `Started parent process [1]`のあと、2つのワーカーがそれぞれ`Waiting for application startup.`→
  `RuntimeError: backendは1プロセスでしか正しく動かない（workers=2）。…`（`app/main.py`133行→
  `single_process.py`38行）→`Application startup failed. Exiting.`
- `curl`は起動3秒後・13秒後・約1分半後のいずれも`Failed to connect … Couldn't connect to server`（000）。
  uvicornは親がソケットをbindするが、listenは各ワーカーのサーバー起動で行われるため、接続そのものが拒否される。
- `-e WEB_CONCURRENCY=2`（`--workers`なし、ポート8766）でも同じく`workers=2`の`RuntimeError`で止まり、20秒後も`/health`は000。

### 2. 親は作り直しを続ける（止まらない）

- 監視は記録の読みどおり`supervisors/multiprocess.py`の`run`が`should_exit.wait(0.5)`ごとに
  `keep_subprocess_alive`を呼び、死んだワーカーを`Child process [N] died`と出して作り直す。
- 実際の作り直しの周期は**約7秒**（2ワーカーずつ。例: `Started server process`が14:05:49・14:05:56・
  14:06:03）。0.5秒は死活確認の間隔で、作り直しの間隔ではない。イメージ内で`import app.main`だけで1.8〜1.9秒
  かかる（3回測った）。7秒の残りの内訳は未計測。
- 約2分半で`Started server process`・`Child process … died`・`RuntimeError`がいずれも44回（同数）。
  その間`docker inspect`は`status=running`・`RestartCount=0`のまま（親が生きているのでDockerの再起動は起きない）。
- **ログの量**: json-fileの実ファイルが47秒で+42,741B（約0.9KB/秒、1日約79MB）。`max-size=10m`×5世代=50MBには
  約15時間で達し、以後はローテーションで頭打ちになる（ディスクを食い続けはしない。代わりに古いログ、つまり
  最初の失敗の原因は約15時間で消える）。
- **CPU**: cgroupの`cpuacct.usage`で60秒の平均が1コアの**64%**（4コアの環境）。瞬間値は作り直しの瞬間に
  223%まで上がる。作り直しの間、本番VMのCPUをこの分だけ使い続ける。
- `docker stop -t 90`は2.4秒で終わり、終了コード0（`Waiting for child process`→`Stopping parent process [1]`）。
  止め方の側に問題は無い。

### 3. ワーカー無し（本番のCMDそのまま）では起動し、`/health`が応答する

lifespanは軸定義・較正値をDBから読む（`refresh_axis_definitions`・`refresh_tuning_values`。Redisは起動時には
触らない）。この環境のPostgreSQL 16（PostGIS無し）に使い捨てのDBを作り、lifespanが読む3つの表
（`axis_definitions`・`axis_registry_meta`・`tuning_overrides`）だけをORMの宣言から`create_all`で作った。
Redisもこの環境のものを起動して`REDIS_URL`で渡した。

- 表が空のままでは`AxisDefinitionSyncError: axis_definitionsテーブルが空です…`でlifespanが止まった。このときは
  親ごと終了するため、`--restart unless-stopped`のDockerが再起動を繰り返した（約40秒で`RestartCount=8`）。
  **ワーカー1での起動失敗も、デプロイの側からは同じく見えない**（コンテナは再起動を続けるだけ）。
- 観測用の軸を1本（`gradient_percent`を読む下書き、重み0）を`AxisDefinitionRepository.upsert`で入れて再起動すると、
  約3秒で`GET /health -> 200`（`{"status":"ok","commit":null,…}`）。20秒後も200、`RestartCount=0`。
  プロセスは`uvicorn`の1本だけ（`docker top`）。

### 起票案

2で作り直しが続き、デプロイのジョブは`docker run -d`で終わるため、この状態でもデプロイは成功扱いになる。
「デプロイ後に`/health`が200を返すまで待ち、返らなければログの末尾を出してジョブを失敗させる」起票案（規模S）を
仕掛中のダッシュボードに置いた。3で見たとおり、ワーカー1での起動失敗（Dockerの再起動の繰り返し）も同じ確認で捕まる。
