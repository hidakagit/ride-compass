# T470. ゼロベース網羅レビュー§8(frontend hooks/services/lib)の残指摘7件対応

状態: 完了（2026-08-31）

- 背景: [T426](T426.md)棚卸し結果の§8（frontend/src/hooks/ + services/ + lib/）、有効7件。
  元は[zero-base-review-2026-08-30.md](../zero-base-review-2026-08-30.md)の§8。
- 対象7件（severity・file:line・要旨。P1の2件[API_BASE_URL 7重複、キキクル/線状降水帯
  エラーstate欠如]は別タスクで対応済みのため対象外）:
  1. `useWeatherGrid.ts`(L35)・`useWindAxisPenalties.ts`(L16-19)・
     `useDynamicWeatherLayers.ts`(L65-68) P2: `500`msデバウンス定数が3ファイルへ
     独立定義（設計原則2違反）。
  2. `useAxisCatalog.ts`(L160-180)・`useMaterialCatalog.ts`(L16-44)・
     `useMaterialValues.ts`(L33-51)・`useDynamicWeatherLayers.ts`(5箇所) P2:
     「cancelledフラグ+Promise+catch」の同型フェッチ骨格が最低8箇所で手書き重複。
  3. `regionApi.ts`の`fetchAxisInspector`(L112-149)/`refreshBasemapCache`(L203-245)
     P2: 同一ファイル内2関数がほぼ同型の約30行ブロックを独立に持つ。
  4. `useMaterialCatalog.ts`(L16-44)と`useAxisCatalog.ts`(L123-139) P2:
     `useAxisCatalog`は同時マウント時二重フェッチ対策(`inFlightCatalogFetch`)済みだが
     `useMaterialCatalog`には無い。
  5. `useStoredState.ts`(L54-63) P3: `key`が動的に変化するケースで前の`key`の値が
     残り続ける。
  6. `evaluationAxes.ts`(L61-71, L84-93) P3: 説明文が`PREFERENCE_AXIS_DESCRIPTIONS`に
     無い場合`?? ""`で黙って空文字。
  7. `debugStatsApi.ts`(L5-35) P3: `ExternalCallStats`/`DebugStats`が手書き型として
     二重管理（backend側OpenAPI無型応答のため正当な例外の可能性あり、着手前に要判断）。
- 対応方針・実装メモ:
  1. `500`msデバウンス定数を`useDebouncedValue.ts: MAP_FETCH_DEBOUNCE_MS`へ集約し、
     `useWeatherGrid.ts`/`useDynamicWayValues.ts`/`useDynamicWeatherLayers.ts`の3ファイルの
     独立定義（各ファイルが「同じ値を使う」とコメントで示し合わせるだけだった）を撤去。
  2. 「cancelledフラグ+Promise+catch」の同型フェッチ骨格: `useDynamicWeatherLayers.ts`に
     5箇所（降水ナウキャスト・降水短時間予報・雷竜巻ナウキャスト・キキクル・線状降水帯
     予測マップ）あった独立実装を、新設`usePolledFetch.ts`（マウント時に即座に1回
     フェッチ＋以降intervalMsごとに再フェッチ、cancelledフラグでの古いレスポンス
     反映防止を1箇所に集約）へ統合した。単体テスト8件を新設。残り3箇所
     （`useAxisCatalog.ts`/`useMaterialCatalog.ts`/`useMaterialValues.ts`）はポーリング
     ではない一発フェッチで、それぞれ二重フェッチ排除・レンダー中の同期リセット・
     依存materialIdという固有の事情を持つため、汎用hookでの統合は見送った
     （useEffectの依存配列を可変長で受け渡す設計はreact-hooks/exhaustive-depsの検証を
     壊す既知の落とし穴でもある）。
  3. `regionApi.ts`の`fetchAxisInspector`/`refreshBasemapCache`が独立に持っていた
     約30行のPOST共通骨格（fetch→通信エラー処理→!response.ok確認→エラーボディ解析→
     整形Errorをthrow）を、ファイル内プライベートヘルパー`postAndCheckOk`へ集約した
     （`routeApi.ts: postJson`と同じ「POST系はGET用`lib/fetchJson.ts`とは別に各ファイル内で
     持つ」という既存方針を踏襲。ボディの有無・成功時のレスポンス解釈は呼び出し側ごとに
     異なるためそこはヘルパーの外に残した）。副次効果として`refreshBasemapCache`の失敗時も
     `fetchAxisInspector`と同じくエラーボディからdetailを抽出するようになった（従来は
     固定文言のみ、拡張であり後退ではない）。
  4. `useMaterialCatalog.ts`へ`useAxisCatalog.ts`と同じ同時フェッチ排除
     （`inFlightMaterialCatalogFetch`）を追加。現状`useMaterialCatalog`は`<AxisComposer>`
     単独からのみ呼ばれ同時マウントの実害は無いが、将来複数箇所から呼ばれる構成になっても
     同種の2重フェッチバグを再発させない予防的な統一。
  5. `useStoredState.ts`: `key`が動的に変わり新しい`key`に保存値が無いケースで、
     `raw==null`のとき早期returnして前の`key`で復元した値が残り続けるバグを修正
     （`raw==null`・deserialize失敗のいずれもdefaultValueへ明示的に戻すよう変更）。
     現状の呼び出し側（page.tsx/admin/page.tsx）はいずれも静的keyのため未発生だったが、
     将来keyが動的化した場合に備えた修正。回帰テスト2件追加。
  6. `evaluationAxes.ts`の`PREFERENCE_AXIS_DESCRIPTIONS[axisId] ?? ""`（説明文が無い場合の
     黙った空文字フォールバック）は、ランタイムの挙動自体を変えるのではなく、
     `evaluationAxes.test.ts`へドリフト検知テスト（全軸が空でない説明文を持つことを
     確認）を追加する形で対応した。このファイルはモジュール読み込み時に定数を組み立てる
     設計のため実行時にwarnログを出す自然な場所が無く、この手のテストによるビルド時
     検知が既存のPREFERENCE_AXES関連テスト群（axisId集合の一致確認等）と一貫する。
  7. `debugStatsApi.ts`の手書き型（`ExternalCallStats`/`DebugStats`）は、調査の結果
     **正当な例外と判断（対応不要）**。backend側`health.py: debug_stats()`が`-> dict`
     という型無しの戻り値注釈のままで、OpenAPI生成物側もこのエンドポイントのレスポンス
     スキーマが`{"type": "object", "additionalProperties": true}`という完全に無型の
     ものになっていることを確認した（backend側にPydanticモデルが無い限り生成物経由の
     型付けができない）。バックエンド側にレスポンスモデルを追加すれば手書き型を撤去
     できるが、backend/frontend両方にまたがる別スコープの改善のため、バックグラウンド
     タスクとして切り出した（[T481](T481.md)として正式に起票・2026-08-31完了。
     2026-08-31 T478で本文を追記）。
