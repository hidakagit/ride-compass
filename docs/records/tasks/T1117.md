# T1117. データが欠けたとき黙って既定値で計算している箇所を洗い出し、利用者に知らせるか断るかを決める

状態: 完了（2026-09-26起票・同日完了）

## 背景

風の予報が読めないとルートの所要を無風で、勾配が欠けた道を平地、停止要因が欠けた道を待ち0秒として黙って計算する。例外処理89件のうち広い例外で既定値を返す・握りつぶすもの10件、狭い例外で既定値・無視40件。母集団を機械で出し、縮退が起きる実データ上の条件と利用者から見た差を1件ずつ書き、影響があるものは知らせる・断る・今のままを問いにする。起票案 proposal-silent-fallbacks（2026-09-26承認）

## 段階1: 母集団と振り分け（2026-09-26、T1112のクラウドのセッション）

### 母集団の定義（機械で出した。同じ手順で誰が出しても同じになる）

- **A**: `backend/app`の`except`節のうち、節の本体（入れ子の関数定義を除く）に`raise`を含まないもの。AST走査。**65件**。
- **B**: ルートの所要時間・コストを組み立てる経路のモジュール（`services/road_graph_engine.py`・`route_generator.py`・
  `graph_service.py`・`weather_service.py`、`domain/cycling_speed.py`・`traffic.py`・`wind.py`・`evaluation.py`・
  `dynamic_materials.py`・`road_network.py`・`routing.py`・`hard_filters.py`・`route.py`、`infrastructure/road_network_store.py`）の
  `np.nan_to_num(…)`・既定値付きの`.get(k, 既定値)`・`x or 定数`・`if x is None: return 定数`。AST走査。**22件**。
- Bの`if x is None: return None`（12件）は、結果が無いことを呼び手へそのまま返す制御で、既定値への置き換えではないため外した。
  Bの走査は「欠損をゼロ配列で置き換える」形（`np.zeros`）を拾わない——風の欠損（`road_graph_engine.py`の`wind_inputs is None`の
  分岐）はこの穴に当たり、棚卸しの既知の1件として手で足した。

### 直したもの（利用者から見える振る舞いは変わらない）

設計書weather-dynamic-layers.mdの「呼び出し元が出発時点のスナップショットへ倒す」は、出発時点の値も同じMSMを読むため同時に
読めず、実際には無風になる——記載を直した。

`WeatherService`の3か所は例外を握るだけでログを出さないが、原因は1段下の`msm_client.read_series`が`log_external_call`
（カテゴリ`msm:read`、失敗は抑制付きWARNINGに原因付きで出る）で既に残している。一度`WeatherService`側にも警告を足したが、
これと重複するため取り下げた。見誤ったのは、`except`節の本体だけを見て「ログが無い」と判定したため——**母集団Aの「ログの水準」の列は
節の中だけを見ており、呼び出し先が既に記録している形を拾わない**。この列で「ログ無し」と出た件は、呼び出し先の`log_external_call`を
確かめてから判定する（WBGTの2件も同じ見方で見直したが、`wbgt_service`の2件は取得後の値の読み取りで、呼び出し先の記録の外にある）。

### 問い（仕掛中のダッシュボード、答えが出たらこのタスクのコミットで記録へ移す）

- `T1117-wind-unavailable`: 風の予報が読めないとき、ルートの所要時間をどう出すか（知らせる〔推奨〕／断る／今のまま）
- `T1117-missing-materials`: 標高や信号・一時停止のデータが無い道を、所要時間でどう扱うか（先に本番で割合を測る〔推奨〕／今のまま／すぐ添える）

**未計測**: 本番で勾配・停止要因の件数が欠けている区間の割合。クラウドのセッションの開発DBは空で測れない。手元のセッションで
`backend/scripts/run_probe.py`から、道路網の配列（`road_network_store.current()`）の`numeric_values`で`gradient_percent`と
`stop_count_material_ids()`の列のNaNの割合を、本数と距離の両方で出す。

## 答え（仕掛中のダッシュボード、2026-09-26）

- `T1117-wind-unavailable`（風の予報が読めないとき）: **(1) 知らせる**——ルートは出し、候補に「風の予報を使えなかったため、
  無風として所要時間を出しています」と添える。
- `T1117-missing-materials`（標高や信号・一時停止のデータが無い道）: **(3) すぐに候補へ「データの無い区間が◯%」と添える**
  （推奨は(1)先に本番で割合を測る、だったが、測る前に表示を足す方を選んだ）。

## 段階2: 知らせる（2026-09-26、T1112のクラウドのセッション）

- backend: `RouteCandidate`に`wind_unavailable`（所要時間を無風で計算した）と`missing_travel_data_share`（勾配か停止要因の件数の
  値が無く、平地・待ち無しとして数えた区間の距離の割合、0〜1）を足した。どちらも`road_graph_engine.py: _LegCostComposer`が、
  所要時間の計算（`_travel_time_seconds`が`nan_to_num`で欠けを置き換える列、`_evaluate`の無風の分岐）と同じ条件で求める。
  割合はビンへ畳む前のEdge単位で数え、`_build_candidate`が候補へ載せる。停止要因の材料は軸の構成と無関係に道路網から運ばれる
  ため（`stop_count_material_ids`）、欠けは道路網の値の欠けそのもの。
- frontend: 候補の中身（`RouteAxisProfile`）の所要時間のすぐ下に、風の注記と「データの無い区間が◯%（坂・信号の無い道として
  所要時間を出しています）」を出す。割合は丸めて1%以上のときだけ出す（0%を並べても判断の材料にならない）。
- 本番での割合は未計測のまま。表示が入れば、候補ごとの実際の値がそのまま画面に出る。
- 設計書: route-settings-and-results.md（注記の出し方）、weather-dynamic-layers.md（無風の計算を知らせること）。
