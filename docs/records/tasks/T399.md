# T399. 標高データを永続化する設計検討

状態: 完了（2026-08-30、調査のみ。結論: 追加の永続化設計は不要——既に完了済み）

- 発端: 地図×評価軸の再設計セッション（2026-08-29〜30）で、「勾配（gradient）軸が
  なぜ地図の自動表示対象にならないか」を精査した際に判明した。理由は2つ重なっている:
  (1) 勾配は進行方向に依存する符号付きの値（登り坂プラス・下り坂マイナス）であること、
  (2) それ以前に**標高データ自体が国土地理院APIから都度取得しDBへ恒久保存しない設計**
  （`material_catalog.py`の`gradient_percent`コメント、docs/architecture.md「標高計算の
  アルゴリズムと既知の制約（Step5）」参照）であり、そもそも焼き込める・キャッシュできる
  永続化済みの元データがどこにも無い。
- 風（気象グリッド、Open-Meteo経由でSQLite/[[T398]]でRedis化検討中）と違い、標高は
  地形という本来「変わらないデータ」のはずなのに、現状は永続化されておらず取得の
  たびに国土地理院APIを叩いている。永続化すれば(a) 都度のAPI呼び出しコスト削減、
  (b) 「道路」グループへ勾配の絶対値（登り/下りの符号を除いた「坂の急さ」だけ）を
  自動導出対象として追加できる可能性、の2つの副産物が見込める。
- **なぜ現状は永続化していないのか、意図的な設計判断か単なる未着手かを最初に
  確認する必要がある**（docs/architecture.md「標高計算のアルゴリズムと既知の制約」
  「標高DEMタイルキャッシュ（改善計画T10、elevation_client.py）」の既存記述を
  まず読み、DEMタイルキャッシュと何が違うのか・永続化しない理由が明記されているかを
  確認してから設計に入る）。
- トリガー: ユーザーが着手を判断した時点。

- **調査結果（2026-08-30完了）**: タスク本文の指示どおり、まず「現状なぜ永続化していないのか、
  意図的な設計判断か単なる未着手か」をコードから直接確認した。結論: **どちらでもなく、
  標高データは既に2つの層で永続化済みであり、`material_catalog.py`の`gradient_percent`
  コメント（「標高は国土地理院APIから都度取得しDBへ恒久保存しない設計」）が古い記述の
  まま残っていただけだった**（T218a・T10で状況が変わった後、このコメントだけ追従して
  いなかった）。
  1. **DEMタイル本体**: 改善計画T10で`infrastructure/tile_cache.py`（ファイルキャッシュ、
     TTL無し＝DEMは不変データのため恒久）へ永続化済み（`elevation_client.py`）。
  2. **Edge単位の計算済み標高属性**（`average_grade`等）: 改善計画T218aで新設した
     PostGIS `elevation_attributes`テーブルへ永続化済み。埋め方は2経路——
     `app/batch/precompute_elevation_attributes.py`（全道路網一括バッチ）と、
     `ElevationAttributeService.get_attributes_for_graph`が`repository`を渡された
     場合の遅延書き込み（`api/dependencies.py`が`road_graph_use_repository`設定
     ON時にrepositoryを渡す。T283でこの設定の既定値がtrueへ変更済みのため、現在は
     本番の通常のルート生成リクエスト経由でも新規エリアの標高属性が自動的に
     累積永続化されていく）。
  3. **バックフィルの実施状況**（副次的に確認）: 全道路網一括バッチ
     （`precompute_elevation_attributes`実行）自体は2026-08-23の時点で
     「本番DB書き込みを伴うため保留、別途判断」のまま止まっており、専用の追跡
     タスクが無かった（[T281](T281.md)段階3の「T242残課題」という一言参照でしか
     追えない状態）。ただし上記2の遅延書き込み経路が本番の既定動作になった
     （T283）ことで、一括バックフィルをしなくても利用実績のあるエリアから
     自然に埋まっていく設計に既になっている。**一括バックフィル自体は「無いと
     動かない」ブロッカーではなく「初回だけ体感が遅い（未訪問エリアで都度GSI
     問い合わせが走る）」という体感速度の最適化に格下げされている**——本タスクの
     スコープ（標高データの永続化設計）そのものとは別の関心事のため深追いはしない。
  - **material_catalog.pyの修正**: `gradient_percent`材料の古いコメントを訂正した
    （本コミットに含む）。タイルへ焼き込めない本当の理由は「永続化されていないから」
    ではなく、`average_grade`が進行方向依存の符号付き値（同じOSM Wayでも往復2方向で
    異なる値を持ちうる）で、方向を持たない静的なMVTタイルのプロパティ1個には
    表現できないため（風向風速と同じ制約）。
  - **[T400](T400.md)（地図×評価軸の連動モデル再設計）との関係**: T400は「勾配も
    T399（標高データ永続化）が完了すれば同じ仕組みに乗せられる」としてT399を
    前提条件に挙げていたが、**永続化そのものは今回の調査時点で既に満たされている
    ことが判明した**。T400が実際に必要としているのは「永続化」ではなく、T400
    セクション2で設計中の**方向依存材料を地図表示へ乗せる新しい配信層**
    （風と同様、way自身の実際の向きを使って評価値を計算し、`way_id`をキーに
    Redisへキャッシュ→軽量APIで配信→フロントの`setFeatureState`で合成）である。
    その計算の入力データ（Edge単位の`average_grade`）は上記2の`elevation_attributes`
    テーブルから既に取得できる状態にあるため、T400側が実装に着手する際は
    「データが無いので先に永続化を設計する」というブロッカーは無く、直接
    Redis配信層の実装から始められる（T400.mdの該当記述はこの調査結果を反映して
    別途更新する）。
  - **結論**: 標高データの永続化設計として新たに行うべき作業は無い。本タスクは
    調査のみで完了とする。
