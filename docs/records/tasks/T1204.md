# T1204. 地図をズームしたまま正時をまたぐと、詳細な風・降水の格子が1時間前の値を指すかもしれない

状態: 完了（2026-09-27）

## 背景

T1144段階Cの範囲外で見つけた（コードを読んだだけ）。useWeatherGrid.tsの詳細な格子は定期の取り直しを持たず、過去の時刻を切り落とす処理も取ったときにしか走らない。まず時計を進めるテストで再現を確かめる。

## 再現（着手時のorigin/master 814d8782）

- 時刻の列: backendの`/api/weather/wind-grid`・`wind-grid-detail`は、取った時点の正時から先を返す
  （`backend/app/infrastructure/msm_client.py: _read_series_sync`の`start = (now // 3600) * 3600`）。粗い格子と詳細格子は
  取った時刻が違えば先頭の時刻が違う。
- 切り詰めはTanStack Queryの`select`で、`select`は取得の中身か関数の参照が変わったときしか走り直さない
  （`@tanstack/query-core` 5.104.0）。正時をまたいで止まっているだけでは、粗い格子も詳細格子も切り詰め直されず、
  両方とも同じだけ古いので位置はずれない——**ずれるのは、どちらか一方だけが取り直されたとき**。
- 描く値は、粗い格子で作ったコマの**位置**（`ref.index`）で詳細格子の配列を引いていた（`useDynamicWeatherLayers.ts: payloadOf`）。
- 時計を進めるテスト（`useWeatherGrid.test.ts`へ一時的に置いた。粗い格子の初回は10時から、3時間後の取り直しは13時から、
  詳細格子は10時からを返す）で、10:30にズームしたまま3時間進めると、粗い格子の先頭は`13:00`・詳細格子の先頭は`10:00`
  だった。位置0は13時のコマだが、詳細格子では10時の値を描く——題名の「1時間前」どころか**3時間前**を指した。
  逆に、正時をまたいでから画面を動かすと詳細格子だけが取り直され、1時間**先**の値を描く。
  前回の値で補った点（`mergeWindGridKeepingStale`）も、取った時刻が違えば同じ位置が別の時刻を指していた。

## 対応方針

欠陥を成立させている性質は「取った時刻が違う格子の値を、別の格子で数えた位置で引く」こと。当たる箇所は
①粗い格子のコマの位置で詳細格子を引く、②前回の値で補った点を最新の応答の点と同じ位置で引く、の2つ。
切り詰めの時機を揃える（詳細格子にも取り直しを持たせる）だけでは、粗い格子と詳細格子の取り直しの周期がずれる間の
食い違いが残るので採らない。**値は位置ではなく時刻で引く**ことにした:

- コマ（`weatherSources.ts: StageFrameRef`）は格子の時刻の値を持つ。描き方（`windArrows`・`precipitationCells`）は点ごとに
  その時刻の位置を引き（`windLayer.ts: timeIndexOf`）、その時刻を持たない点は描かない。
- どちらの格子で描くかは時刻ごとに決める（`windLayer.ts: gridAtTime`）。詳細格子がその時刻を持てば詳細格子、無ければ
  粗い格子——詳細格子は取った時刻の分だけ予報の先の端が手前で終わるので、持たない時刻を空にせず粗い格子で描く。
- 「今」が属する1時間より前を落とすのは`select`（取った時点の時計）をやめ、時系列を作るとき（`gridStageFrames`）に
  出発時刻のフックの`now`（5分刻みで進む）で行う。これで切り詰めが時計に従い、`select`と詳細格子の`trimDetail`が消えた。
- 詳細格子にも粗い格子と同じ取り直しの間隔（配信元MSMの更新の間隔）を持たせた——ズームしたまま置いておくと古い
  ランの値を出し続けていた。
