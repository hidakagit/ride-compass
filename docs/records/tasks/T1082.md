# T1082. 降水短時間予報（rasrf）の配信要素と時刻一覧の在り処を源泉へ宣言する

状態: 完了（2026-09-23起票・2026-09-24完了）

## 背景

T1080で気象のデータ層は配信要素idとパスの系統を源泉（mapDisplay.weatherElements）から引く形になったが、降水の60分〜15時間先（降水短時間予報、要素rasrf・系統rasrf）はbackendのWEATHER_ELEMENTSにもJMA_TILE_SPECSにも宣言が無く、precipitationNowcast.tsが要素idと系統を手で持つ。時刻一覧の在り処（jmaNowcastFrames.ts: JMA_TARGET_TIMES_PATHS）もbackendのプリウォームと画面が別々に持つ。

## なぜT1080で片付けなかったか（決めることがある）

降水の名前付きソース`precipitationNowcast/main`のラスタは、選んだ時刻によって**2つの配信要素**
（60分以内=`hrpns`/系統`nowc`、60分〜15時間=`rasrf`/系統`rasrf`）から届く。今の宣言
`WeatherElement`は1要素=1配信要素idで、（チップ, ソース, 描き方）が一意という不変条件
（`test_map_display.py`）があるため、`rasrf`を2件目として足すことはできない。形を決める必要がある:

- 案A: `WeatherElement.jma_element`を「時刻の段ごとの配信要素の並び」にする（生成物の形が変わり、
  画面の`weather.ts`・`jmaNowcastFrames.ts: declaredJmaElement`も追従）。ソースのズーム範囲は
  段の間で一致することを不変条件にする。
- 案B: 60分〜15時間先を別の名前付きソースにする（描き方・重なり順・データ取得状態の集約が変わる）。

また`rasrf`を`JMA_TILE_SPECS`へ足すと、backendの奇数ズーム補間（`source_zoom_for_interpolation`）が
`rasrf`のタイルにも効き始める。`rasrf`の`zoomUse`・`maxNativeZoom`は一次情報で未確認
（`sjfcstmap`と同じく公式ページが設定を外部化していない可能性がある）。**今は`rasrf`が仕様に無いため
奇数ズーム（z5/z7/z9）の短時間予報が空タイルになっている疑いがある**（未確認）。

## やること

1. 気象庁の公式ページが読み込む設定ファイルで`rasrf`の`zoomUse`・`maxNativeZoom`を確かめる
   （`docs/modules/backend/weather-dynamic-layers.md`「要素ごとのズーム上限」節の出典の取り方と同じ）。
   あわせて、開発機から`/api/jma-tile/bosai/jmatile/data/rasrf/.../surf/rasrf/9/...`を1枚取り、
   奇数ズームが空かを実測する。
2. 案A/Bを選び（ユーザー確認）、`rasrf`を源泉へ宣言して`JMA_TILE_SPECS`へ仕様を足す。
3. 時刻一覧の在り処: 画面の`JMA_TARGET_TIMES_PATHS`とbackendのプリウォーム
   （`services/jma_tile_prewarm_service.py`の`_*_TARGET_TIMES`）が同じ事実を別々に持つ。
   要素ごとの時刻一覧（`nowc`は`targetTimes_N1/N2/N3`へ分かれる）を配信元の仕様として
   backendへ宣言し、両方がそこから引く。

## 保留すると何が起きるか

backendが降水短時間予報の要素idや系統、時刻一覧の在り処を変えても、画面は古い値でURLを組み立て、
タイルは404→空タイルに倒れて地図から黙って消える（`jmaTileProtocol`は404を失敗として記録しない）。
奇数ズームの空タイルの疑いが本当なら、降水の60分〜15時間先はズームによって出たり消えたりしている。

## 一次情報の確認（2026-09-23）

- **公式の設定ファイル**: 「今後の雨」（`https://www.jma.go.jp/bosai/kaikotan/`）が読み込む
  `bosai/kaikotan/table/kaikotan.properties__061a966c27254fd9b2e4.xml`（HTMLから取得したファイル名）に、
  `<element id="rasrf" group="rasrf">`の`<imageType id="rasrf" type="tile" … zoomUse="even">`・
  `<maxNativeZoom>10</maxNativeZoom>`（コメント「画像が実在する最大ズームレベル」）がある。
  **同じファイルに`sjfcstmap`も`zoomUse="even"`・`maxNativeZoom`10で載っていた**——T633以来
  `verified=False`（公式で未確認）だった線状降水帯予測マップも一次情報で確定した。
  `hrpns`は`bosai/nowc/table/nowc.properties__7d6f7d8dc6f16a416574.xml`で`zoomUse="even"`・10。

## 対応方針

- **案Aを選んだ**（`WeatherElement.jma_element`を時刻の段ごとの並び`jma_elements`へ）。根拠:
  - 一次情報で`hrpns`と`rasrf`のズーム仕様が一致した（案Aの前提「段の間でソースのズーム範囲が一致」が
    配信元の事実として成り立つ）。
  - 画面では今も1本のラスタのソースのURLが時刻で差し替わっているだけで、案Aはその実態をそのまま
    宣言する。案Bは名前付きソースが2本になり、描き方・重なり順・データ取得状態の集約が変わる
    （画面の振る舞いが変わる）。案Aは画面の見え方を変えない（奇数ズームで消えていた短時間予報が
    出るようになるのは不具合の修正）。このため、ユーザー確認は要らないと判断した。
- **生成物の形**: `weatherElements[].jmaElements`を`[{id, pathGroup, targetTimeFiles}]`（時刻の段の順）に
  した。要素直下の`jmaElement`・`pathGroup`は消した。`tile`（ズーム範囲）は段の全要素の仕様から導き、
  食い違えば`map_display.weather_element_tile()`が`ValueError`で生成を落とす。
- **`rasrf`を`JMA_TILE_SPECS`へ**（`rasrf`系統・even・10）。これでプロキシが`rasrf`の奇数ズームを
  親から補間する（`source_zoom_for_interpolation("rasrf", z)`がz5→4・z7→6・z9→8を返す。従来はNone）。
  `sjfcstmap`の`verified=False`は一次情報で確定したため外し、読む側が無くなった`JmaTileSpec.verified`を
  消した（参照はフィールド宣言と`sjfcstmap`の1件だけだった）。
- **時刻一覧の在り処**: `jma_tile_specs.py`に系統ごとのファイル（`JMA_TARGET_TIME_FILES`、設定ファイルの
  `<timeFile>`）と、複数ファイルの系統（nowc）での要素ごとの分け方（`JMA_TARGET_TIME_FILES_BY_ELEMENT`、
  実物の`elements`）を置き、`jma_target_time_files()`が引く。**系統の全ファイルを読む形にしなかった**
  ——雷の時刻一覧（N3）が取れず降水の2ファイルが取れたとき、雷は「失敗」ではなく「行が0件」になり、
  取得失敗が画面のデータ取得状態に出なくなる。プリウォームは`jma_target_times_paths()`から、画面は
  生成物の`targetTimeFiles`から時刻一覧を取りに行く（`_RISK_TARGET_TIMES`等と`JMA_TARGET_TIMES_PATHS`を消した）。
- **画面のデータ層**: `jmaDelivery(鍵, 段)`が段の配信要素を返し、`jmaTilePayload`・`fetchJmaTargetTimes`は
  それを受ける。`fetchJmaTargetTimes`は宣言のファイルを全部取りに行き、行をつなげて返す
  （一部だけ取れなければ部分的に返し、全部失敗したときだけ投げる——降水ナウキャストが従来N1/N2で
  持っていた振る舞いを、宣言に沿って一般化した）。ファイル単位で未解決のフェッチを共有するので、
  キキクル4要素を要素ごとに引いても往復は1回のまま。降水ナウキャストの`isForecast`はファイルの別でなく
  `validtime > basetime`で決める（雷・竜巻と同じ規則。N1の行はvalidtime=basetime、N2はvalidtime>basetime）。
  段の番号（`NOWCAST_STAGE`・`SHORT_RANGE_STAGE`）だけは降水のデータ層が名指す——段ごとに時刻一覧の
  読み方が違う（実況の外挿の2ファイル／数値予報のランの選び方）ため。フレームの内部参照の
  `source: "rasrf"`は要素idと紛らわしいため`"shortRange"`へ改名した。
