# T1182. 軸の分布の分位点・ヒストグラムと軸の依存順の計算を、自前のループから numpy と標準ライブラリへ置き換える

状態: 完了（2026-09-27）

## 背景

起票案 proposal-std-axis-numeric（2026-09-27承認。標準の道具の棚卸し・T1152の担当から）。規模S（根拠: 変わると見込むファイルは axis_preview_service.py・axis_definitions.py・measure_axis_saturation.py とそのテスト3本の計6本）

■ 背景（管理画面の軸スタジオの分布表示と、軸の評価順の内部の話。数値の結果は変えない前提）
- services/axis_preview_service.py の、延長で重み付けた分位点（weighted_quantiles）とヒストグラム（_distribution）は Python のループで書かれている。分位点の定義（累積の重み÷合計が q 以上になる最初の値）は numpy 2.x の np.quantile(weights=, method="inverted_cdf") と同じで、ヒストグラムは np.histogram(weights=) で書ける（範囲外を端の階級へ寄せる今の挙動は np.clip で保つ）。測定スクリプト measure_axis_saturation.py も同じ関数を使う。
- domain/axis_definitions.py の topological_axis_order は、深さ優先の自前のトポロジカルソートと循環検出。標準ライブラリの graphlib.TopologicalSorter が同じことをし、循環の経路も返す。ただし並びが変わる（今は深さ優先、graphlib は幅優先）。docstring は「挿入順を保つ（合成の加算のビット一致の要件）」を求めているので、並びが評価結果に効くかを先に確かめる。
どちらも、自前にした理由は書かれていない。

■ やること
分位点とヒストグラムを numpy へ置き換える（既存の振る舞いのテストはそのまま使える）。依存順は、並びの変化が結果に効かないと確かめられたら graphlib へ置き換え、効くなら残す理由を docstring へ書く。見込み 実装 約−35〜−55行。

■ なぜ既存のタスクに入らないか
該当する未完了のタスクは無い。

## 実施（2026-09-27）

### 分位点とヒストグラム（`services/axis_preview_service.py`）

- 分位点は`np.quantile(weights=長さ, method="inverted_cdf")`へ置き換えた。numpy 2.5.2（`backend/requirements.txt`に既にある。
  新しい依存は無い）の実装（`lib/_function_base_impl.py`）を読み、重みの累積÷合計を`searchsorted(side="left")`で引き、
  範囲を超えた添字を最後の要素へ寄せる——今のループと同じ定義であることを確かめた。numpyの浮動小数へ`round`を当てると
  `np.round`になり端数`.x5`を別の側へ丸めるため、`float`へ戻してから丸める。
- ヒストグラムは**`np.histogram`を使わず、`np.bincount`にした**。記録の方針どおり`np.histogram`＋`np.clip`で書いて旧実装と
  乱数の標本3,000件で突き合わせると、3件で階級の割合が隣の階級へ移った（最大0.62）。値が階級の境界ちょうどにあるとき、
  `np.histogram`は自分の`linspace`の境界と比べて割り当て、旧実装は`int((値−下限)÷幅)`で割り当てるため、浮動小数の誤差で
  別の側へ倒れる。どちらが正しいとも言えない（報告する境界は4桁へ丸めた値）ため、「数値の結果は変えない」前提を優先し、
  旧実装と同じ式（切り捨ての添字を`np.clip`で端へ寄せ、`np.bincount`で延長を足す）にした。書き直した後の突き合わせは
  3,000件で分位・階級・境界・ゼロの割合・総延長とも食い違い0件。
- 描画範囲の外（p99×1.2より上）を端の階級へ寄せる挙動はテストが無かったため、`_distribution`の入口で「外れ値の延長が
  最後の階級に入り、割合の合計が1になる」テストを1本足した（寄せを外すと、`np.bincount`の長さが階級数を超え
  境界との`zip(strict=True)`で落ちる。`np.histogram`版では合計が0.995になるのを確かめた）。
- `measure_axis_saturation.py`は`weighted_quantiles`を呼ぶだけで、変更は要らなかった。

### 依存順（`domain/axis_definitions.py: topological_axis_order`）

**並びは結果に効くため、graphlibへ置き換えず深さ優先を残し、理由をdocstringへ書いた。**

- 効く経路: `evaluation.py`の静的スコア行列は`axis_arrays`を`topological_axis_order`を公開軸へ絞った並びで作り
  （`_stack_columns`がその並びを列にする）、`difficulty.py: _axis_terms`がその並びで項を作って`_neumaier_accumulate`が
  先頭から足す。つまり公開軸の相対順が合成の加算順で、`axis_definition_models.py`も`sort_order`を加算順として扱う。
- 深さ優先では、どの軸からも参照されない軸（公開軸。参照される軸は`check_internal_axis_not_published`が公開を拒む）は
  外側のループでだけ出るため、挿入順（`sort_order`）を保つ。
- graphlib（Kahn法）では、公開軸A（内部軸Xを参照）・公開軸B（参照なし）の挿入順で`X, B, A`となり、公開軸の並びが
  `B, A`へ入れ替わる（scratchpadで実行して確かめた。深さ優先は`X, A, B`）。本番にも内部軸を参照する公開軸（車の圧迫感）
  があるため、置き換えると加算順と列の並びが変わる。
