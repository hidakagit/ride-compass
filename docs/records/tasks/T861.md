# T861. 観測しか持たないレイヤーが、配信の遅れのぶんだけ常に時刻範囲の外にある

状態: 完了（2026-09-15。起票同日。[T859](T859.md)の調査中に発見。T860として起票したが並行セッションが同番号を先にpushしたためT861へ振り直した）

## 背景

雷放電位置データ（liden）は予測フレームを持たず、`trimToCurrentAndFuture`が最新の実況より
前を切り捨てるため、フレーム列は実質1件（最新の観測）になる。一方`frameIndexForTime`の
範囲判定の許容幅は1秒で、共有時刻がその1件より1秒でも後ろなら`null`を返して何も描画しない。

気象庁の配信には観測から公開までの遅れがあり、実データで確認した（2026-09-15 18:50:21 UTC
時点、`targetTimes_N3.json`）:

    liden最新フレーム 20260914184500 = 5.4分前（全37件が観測、5分刻み、予測フレームは無い）

共有時刻が「今」であるかぎり常に最新フレームより後ろにあるため、**雷放電位置データは
災害チップをONにしても描画されない**。同じ性質を持つのは、予測フレームを持たず観測だけで
構成されるレイヤー全般。降水（ナウキャストに60分先までの予測がある）や雷・竜巻
（予測フレームがある）はこの形にならない。

T859で共有時刻を5分刻みで「今」へ追従させたが、この件はそれとは独立に残る（追従後の
共有時刻も、配信の遅れのぶんだけ最新フレームより後ろになりうる）。

## 論点

「観測しか無いレイヤーにとって、共有時刻が最新観測より後ろにあることは範囲外なのか、
それとも『最新の観測を見せる』が正しいのか」を決める必要がある。範囲外で描かない現在の
規約は予測を持つレイヤーには正しく、観測だけのレイヤーには当てはまらない可能性がある。
キキクル4種は同じ理由で既に共有タイムラインから外してある（`riskMap.ts`）。

## 解消していないことの確認（2026-09-15）

T859（共有時刻の「今」への追従）で直っている可能性があったため、実データで測った:

    最新フレーム(UTC) 2026-09-14T22:55:00 / 5分刻みの共有時刻 2026-09-14T23:00:00
    差 5.0分 → frameIndexForTime は null（描画されない）

## 決定

**予測を持たないレイヤーは、共有時刻が配信の遅れのぶん後ろにあっても最新の観測を出す。**
共有時刻は「いつの予測を見るか」を選ぶためのもので、予測を持たないレイヤーにはその選択が
無い。ただし利用者が意図して先の時刻を選んでいるとき（出発時刻を明日にした等）は描かない
——「1時間後の落雷」は存在せず、古い観測をその時刻の値として出すのは誤り。

許容の幅は`OBSERVATION_DELAY_TOLERANCE_MS`（20分）。実測の遅れ5〜10分の倍を上限に取る。

キキクル（共有タイムラインに乗せない）との違いは、フレーム列を持つかどうか。キキクルは
配信が「現在の危険度」の単一値のみでフレーム列自体が無い。雷放電はフレーム列を持つ
（5分刻みの観測が37件）ため、タイムラインに乗せたまま選び方だけを変える。

## 実装

`dynamicWeather.ts: observationIndexForTime`（新設）を`useDynamicWeatherLayers`の雷放電が
使う。他のレイヤー（予測を持つ降水・雷・竜巻）は`frameIndexForTime`のまま。

## 検証

- `dynamicWeather.test.ts`（新規5件）: 遅れのぶんは最新観測・許容超えはnull・範囲内は
  従来どおり・過去は範囲外・空はnull。
- `useDynamicWeatherLayers.test.ts`（新規1件）: **配信の遅れを再現した結線の検査**
  （最新フレームが共有時刻の5分前でもpayloadが届く）。既存のliden検査はフレームを共有時刻
  ちょうどに置いており、時刻判定を意図的に避けていたため、この不具合を捕まえられなかった。
- **検査が効くこと**: `observationIndexForTime`を`frameIndexForTime`へ戻すと、この結線の
  検査だけが落ちる。
