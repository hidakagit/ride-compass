# T1185. 重い処理を1本ずつに絞るロックを、ディレクトリの作成による自前の方式からOSのファイルロックへ置き換える

状態: 完了（2026-09-27）

## 背景

起票案 proposal-std-lockrun-os-lock（2026-09-27承認。標準の道具の棚卸し・T1152の担当から）。規模S（根拠: 変わると見込むファイルは lockrun.py・procs.py・core.py の3本。7以下）

■ 背景（画面に出ない、並行作業の道具の話）
scripts/lockrun.py はロックをディレクトリの作成で取る。この方式では保持者が殺されるとロックが残るため、「30秒ごとに印を更新する」「5分更新が無ければ破棄する」「破棄したら保持者の生死を記録する（そのために procs.py でプロセス一覧を読む）」「Windows の共有違反で消せないときに消し直す」を次々に足してきた。T1049 には「放したはずのロックが消えずに残り、後ろの全員が5分待った」実害の記録がある。OSのファイルロック（filelock、または標準ライブラリの msvcrt.locking／fcntl.flock を約20行）なら、保持者のプロセスが死んだ時点でOSが放すので、これらはまとめて要らなくなる。OSロックを選ばない理由はどこにも書かれていない（冒頭の「finally が走らない」は自前ロックを後始末する理由で、OSロックには当たらない）。

■ やること
取得と解放をOSロックへ置き換え、更新の印・破棄・破棄の記録・消し直しを消す。残すもの: 停止ファイル、入れ子の呼び出し、10分の打ち切り、実行の記録（log.jsonl と --report）、保持者の表示（owner.json はロックとは別のファイルにする）。見込み 約−60〜−70行。

■ 着手時に確かめること
python が殺されて bash の子だけが残った場合、今は5分後に破棄されるが、OSロックでは即座に放される（重い子が生き残ったまま次の処理が始まりうる）。10分の打ち切りで子を殺す既存の処理で足りるかを確かめる。ロックファイルを今と同じ git の共通ディレクトリ（OneDrive 配下）に置いてよいかも確かめる。

■ なぜ既存のタスクに入らないか
T1148（並行実行の道具の書式の読み書きの整理）も lockrun.py の文（停止中は push を始めない）の食い違いを1件含むが、範囲は台帳・記録の書式と依存の向きで、ロックの方式は含まない。同じファイルを触るので、どちらかを終えてから着手する。「プロセス一覧を psutil へ」の起票案とも関係する（こちらが先に入ると、procs.py の使い道が1つ減る）。

## 対応（2026-09-27、担当 L-lock）

### 着手時に確かめたこと

- **前提**: origin/master（72a90b15）の`scripts/lockrun.py`は起票案の記述どおり（mkdir・30秒の更新・5分の破棄・`breaks.jsonl`・消し直し）。
  T1148は未着手で同じ回に走っていないため、こちらを先に入れた。ダッシュボードの起票案の件に答え（承認）以外の決定・コメントは無かった。
- **標準ライブラリか`filelock`か**: 標準ライブラリ（`msvcrt.locking`／`fcntl.flock`）にした。`scripts/`には依存を宣言する
  置き場（requirements）が無く、道具はシステムのPythonで動く。`filelock`は開発機のシステムのPythonに入ってはいた（3.25.2）が、
  何かの推移的な依存として入っているだけで、宣言の無い依存に道具のロックを載せることになる。中身は同じOSの呼び出しで、
  足りない機能も無い。新しい依存は足していない。
- **公式の挙動**: Pythonの`msvcrt.locking`は「今のファイル位置からnバイトを錠し、ファイルの終わりを越えてよい」、`LK_NBLCK`は
  錠せなければ`OSError`（docs.python.org/3/library/msvcrt.html）。WindowsのLockFileは「プロセスが錠したまま終わるかファイルを
  閉じると、OSが錠を外す。ただしその時間は資源次第なので明示的に外すことを勧める」「ハンドルを継いだ子プロセスには錠した範囲への
  アクセスは与えられない」「ファイルの終わりを越えて錠してよい」（learn.microsoft.com …/nf-fileapi-lockfile）。`os.open`の記述子は
  既定で継がれない（PEP 446）ので、Linuxの`flock`でも子のbashは錠を持たない。つまりどちらのOSでも、錠を持つのはlockrunの
  pythonのプロセスだけである。
- **pythonが殺されてbashの子だけが残った場合（起票案の「着手時に確かめること」の1つ目）**: 10分の打ち切りでは足りない——
  打ち切りはpythonの中の`proc.wait(timeout=…)`なので、python自身が殺されると走らない。実測（下の検証B）でも、保持者のpythonだけを
  殺すと、待ち手は2.4秒後に取り、殺された側の子（`sleep 20`）は15.5秒後まで走り続けた。旧方式でも守れていたのは破棄の5分までで、
  性質は同じ（旧方式は最大5分遅れて並ぶ、新方式はすぐ並ぶ）。起きる頻度は、旧方式の`breaks.jsonl`（`finally`が走らずに枠が残ると
  必ず1行書かれる）が3f77702a（2026-09-23 22:22）以降0件で、ファイル自体が存在しない。同じ期間の`log.jsonl`は932回。
  並んだときの害は所要が伸びることだけで（テストDBは作業ツリーごと、T964）、正しさは壊れない。このため子を錠に結び付ける仕組み
  （WindowsのJob Object等）は足さず、制約として`lockrun.py`の冒頭に1文で書いた。
- **ロックのファイルをgitの共通ディレクトリ（OneDrive配下）に置いてよいか（2つ目）**: 置いてよい。ロックはOSのカーネルの状態で、
  ファイルは錠の的にすぎず中身を書かない（OneDriveが同期する中身の変化が無い）。検証はOneDrive配下の作業ツリーの中に作った
  一時リポジトリの`.git/lockrun/`で行い、排他・解放とも期待どおりだった。

### 変えたもの

- `scripts/lockrun.py`: 取得を`lockrun/heavy.lock`へのOSのファイルロック（5秒おきに非ブロッキングで試す）に、解放を錠の解除と
  記述子を閉じることに置き換えた。更新の印（ハートビートのスレッド）・5分の破棄・破棄の記録（`breaks.jsonl`と`procs`の読み取り）・
  消し直しを消した。保持者の表示は`lockrun/heavy.owner.json`（ロックのファイルとは別。Windowsの錠は読み取りも拒むため）へ移し、
  取得の時刻`at`を足した。停止ファイル・入れ子の呼び出し・10分の打ち切り・`log.jsonl`と`--report`はそのまま。
  ロックのファイルは消さない（消すと待っている側と作り直した側が別のファイルを掴む）。
- `scripts/orchestration/core.py`: 定期確認の「ロック保持」と「枠の外の重い処理」が読む保持者を`heavy_holder`へまとめた。
  保持者のファイルは放した後も残るので、書かれたpidのlockrunがまだ動いているときだけ保持者とみなす（pidの使い回しに備えて
  コマンドラインに`lockrun.py`があるかも見る）。以前はディレクトリがあること自体が保持の印だった。
- `scripts/orchestration/procs.py`: 冒頭の使い手の説明からlockrunを外した。
- T1179の記録へ前提の変化（lockrun.pyがprocsを使わなくなった）を1行書いた。

### 移り方（旧方式と新方式が同時に使われる間）

各担当は自分の作業ツリーの`scripts/lockrun.py`を走らせるので、このコミットを含まない土台の作業ツリーでは旧方式
（`lockrun/heavy`ディレクトリ）が、含む作業ツリー（取り込み後に振り出した担当・司令塔の本体）では新方式（`lockrun/heavy.lock`）が
使われる。2つは別の名前を見るので**互いを排他しない**。検証Cで、旧→新・新→旧のどちらの順でも2本が並んで走ることを確かめた
（終了コードは両方0。互いのファイルを壊したり、旧方式の破棄が新方式のファイルへ向いたりはしない）。
害は並んだ間の所要の伸び（T1057の実測で軽い側が単独の2.4倍）だけで、テストDBは作業ツリーごと（T964）なので正しさは壊れない。
移行のための互換の実装（新方式が旧方式のディレクトリも見る等）は、片方向しか守れず後で消す残骸になるので入れていない。

- **重なりの窓**: 取り込んだ時点で稼働中の担当が、origin/masterへrebaseするまで。担当はpushの前に必ずrebaseするので、
  窓は長くてもその回の担当が終わるまで。司令塔が窓を無くしたいなら、稼働中の担当が他にいないときに取り込む。
- **窓の間の見え方**: 新しい`orchestrate.py check`の「ロック保持」は旧方式の保持者を出さない（旧方式のディレクトリを読まない）。
- **後片付け**: 旧方式の保持者が殺されて`lockrun/heavy`ディレクトリが残った場合、新方式はそれを見ないので害は無いが、
  窓が閉じた後に残っていれば消してよい（司令塔の操作。担当はしない）。
