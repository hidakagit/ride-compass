# T398. 風グリッド（Open-Meteo）のキャッシュをSQLiteからRedisへ移行する検討

状態: 完了（2026-08-30）

- 発端: 地図×評価軸の再設計セッション（2026-08-29〜30）で、軸スタジオが作る「道路」グループの
  軸（車ストレス等）とは別に、「環境」グループ（標高・気象）を新設し、風は面表示
  （時刻＋方位スライダー＋`gridFill`）に統一する方針を決めた。この面表示の裏側データ
  （`WindGridPoint`、Open-Meteo経由）は現状`cache_db.py`のSQLite永続キャッシュ
  （T195、標高キャッシュと相乗り）を使っているが、JMAアメダス連携（T387）は既にRedisを
  導入済みのため、キャッシュ基盤をRedisへ1本化できないか、という提案がユーザーから
  出た。
- 想定作業: `weather_client.get_forecast_many`のL1（プロセス内メモリ）→L2（現状SQLite）
  →実フェッチという既存の3段構成のうち、L2をRedisへ置き換える。TTL・失敗時のstale
  フォールバック許容幅（T195で30分→3時間、24時間へ拡大済み）等の既存の運用値は
  そのまま踏襲できるか確認が必要。
- **注意**: Redis化は「環境グループの風表示」を支えるキャッシュの高速化・基盤統一が
  目的であり、「道路グループの軸をタイルへ焼き込む」話とは別（風は進行方向依存・
  時刻依存のため、Redis化してもMVTタイル焼き込みの対象にはならない、という整理が
  同セッションで確定済み）。
- トリガー: ユーザーが着手を判断した時点。標高キャッシュ（同じcache_db.py）を含めて
  検討するかは着手時に確認する。

- **実装メモ（2026-08-30完了）**: 標高キャッシュは対象外とした——`cache_db.py`の
  `elevation_cache`テーブル・`get_elevation`/`set_elevation`は改善計画T10（DEMタイル化）で
  既に削除済みで、着手時点の`cache_db.py`は`wind_forecast_cache`テーブルのみを持つ
  ファイルになっていたため、検討の余地なく風グリッドの1テーブルだけが対象だった。
  - **新規`backend/app/infrastructure/wind_forecast_cache.py`**: JMAアメダス連携（T387）・
    road_graph_tiles cache-aside（T390）と同じRedis cache-asideパターン
    （`redis_client.get_redis_client`/`redis_available`/サーキットブレーカー、
    fail-open）で`get_wind_forecast_many`/`set_wind_forecast_many`を実装。
    キー`wind:forecast:{lat}:{lon}`、値はJSON化した`[fetched_at, data]`、
    TTLは`WIND_GRID_STALE_FALLBACK_MAX_AGE_SECONDS`（24時間）に合わせた——それを
    超えたエントリはweather_client.py側のstale fallback判定でもどのみち使われなく
    なるため、Redis側で先に失効しても挙動は変わらない。road_graph_tilesと異なり
    PostGIS等の正本フォールバックは持たない設計（Open-Meteoへの再フェッチが常に
    可能なため、cache-asideの正本＝外部API自体という整理）。
  - **`weather_client.py`**: `cache_db`への参照を`wind_forecast_cache`へ差し替え。
    関数シグネチャ・呼び出し側インターフェースは無変更。
  - **`cache_db.py`を全体削除**: ユーザー指示「SQLite実装がこれでRideCompass全体から
    不要になるなら削除してRedisに一本化したい」を受け、風グリッドキャッシュの移行で
    唯一の永続化用途が消えたことを確認した上で完全撤去した。唯一の非キャッシュ用途
    だった`DATA_DIR`定数（地図タイル・路面ベクタタイルのファイルキャッシュの保存先、
    SQLiteとは無関係）は`tile_cache.py`へ移設。`backend/data/ridecompass_cache.db`
    自体は本番・devとも次回のデータ生成で単に参照されなくなるだけの残置ファイルで、
    削除の緊急性は無い（gitignore対象、DBスキーマでも本体データでもないため）。
  - **テスト**: `test_cache_db.py`を削除し、`test_road_graph_tile_cache.py`と同型の
    フェイクRedis（mget/pipeline.setのみ実装）で`test_wind_forecast_cache.py`を新設。
    `test_weather_client_cache.py`・`test_wind_service.py`のSQLite一時DBフィクスチャも
    同じフェイクRedisパターンへ置換。壊れたエントリ（JSON解析失敗）がfail-openで
    「未キャッシュ」扱いになることの回帰テストも追加。
  - **検証**: backend全1386件green（PostGIS統合テスト除く、`pytest -m "not postgis"`）。
    DB・OpenAPI契約・フロントへの影響なし（内部キャッシュ基盤の入れ替えのみ、外部
    インターフェース不変のため）。architecture.md「気象グリッドのRedis永続キャッシュ」
    節ほか関連箇所（ファイルツリー・Open-Meteo 429対策節・Redisキャッシュ基盤節）を
    同一コミットで追従。
