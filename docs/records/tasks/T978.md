# T978. 標高タイルの取込が、製品を1つ選んで残りを捨てている 規模M

状態: 未完了

段階1（取得・取込・派生のコードとテスト）済み。段階2（本番での取り直し）は操作を待っている（2026-09-26）。

## 背景

`gsi_dem_tile.py` の `_fetch_one` は、製品を優先順に試して**最初に200を返したものでタイルを
確定し、残りの製品を取得しない**。

```python
order = [product] + [p for p in DEM_TYPE_PRIORITY if p != product]
for candidate in order:
    if response.status_code == 200:
        return candidate, response.text   # ここで打ち切る
```

これは2つの点で層を間違えている。

**① 生データ層の契約を破っている。** `SourceFeatureRow` は「外部が持っていた属性をそのまま
入れる袋で、取込の時点では何も捨てない」と宣言しているが、200を返した他の製品を捨てている。

**② 「最良を選ぶ」は導出である。** しかも配信元は**画素ごと**と明記している。

> 地理院地図の標高は、指定した地点において整備されている最も計測精度の良い標高タイルの、
> 最大ズームレベルのピクセル座標における値を表示します。そのため、航空レーザ測量（DEM1A）の
> データが存在しない箇所では、航空レーザ測量（DEM5A）→写真測量（DEM5B, DEM5C）→
> 1/2.5万地形図等高線（DEM10B）の順で存在する最も計測精度の良い標高タイルの値が参照され、
> その地点の標高値として採用されます。
>
> 出典: https://maps.gsi.go.jp/development/hyokochi.html

いまの実装は**タイル単位**で1製品を採るため、選んだ製品の欠測画素が、他の製品に値があっても
埋まらない。

## あるべき形

| 層 | 持つもの |
|---|---|
| 生データ | 200を返した**製品ごとに1行**。`natural_key` は既に `dem5a/15/x/y` と製品を含むので鍵の変更は不要 |
| 導出 | 画素ごとに DEM5A→DEM5B→DEM5C→DEM10B の順で、最初に値のあるものを採る |
| 欠測 | どの製品にも値が無い画素はNULL。配信元が宣言した欠測（「標高値が存在しない画素には「e」の文字が格納されている。」https://maps.gsi.go.jp/development/demtile.html ） |

### 製品ごとにズームが違う

配信元が公表している最大ズームレベル（https://maps.gsi.go.jp/development/hyokochi.html ）:

| データID | 格子間隔 | 整備範囲 | 標高精度（標準偏差） | 最大ズーム |
|---|---|---|---|---|
| DEM1A | 約1m | — | 0.3m以内 | 17 |
| DEM5A | 約5m | — | 0.3m以内（格子内に航空レーザ計測点が無い場合は2.0m以内） | 15 |
| DEM5B | 約5m | 都市域周辺等 | 0.7m以内 | 15 |
| DEM5C | 約5m | 一部の島嶼部等 | 1.4m以内 | 15 |
| DEM10B | 約10m | — | 5m以内 | 14 |

**DEM10Bはz14までなので、いまのプロファイル（z15）では常に404を返す。** 各製品をその最大
ズームで取り、導出側でズーム差を吸収する必要がある（z15の画素の親z14画素を見る）。

### 404が3つの意味を持つ

配信元の404は「整備区域外」「一時障害」「その製品はこのズームを出していない」のどれかだが、
コードは区別していない（`if status == 404: 次の候補へ`）。前2つの区別は[T603](T603.md)・
[T605](T605.md)・[T852](T852.md)で扱い済み。3つ目は未対応で、z15では`dem`が全タイルで404に
なるため、フォールバックの4番目が**絶対に発火しない死んだ枝**になっている。製品ごとに
その最大ズームで取れば、この意味は消える。

## 回収できる量（実測、2026-09-20）

開発DBで欠測の多いタイルに対し、DEM10B（z14）が埋められた画素:

| z15タイル | dem5aの欠測 | dem5bで埋まる | dem（10B・z14）で埋まる |
|---|---|---|---|
| 29106/12907 | 55,230 | 0 | 94（0.2%） |
| 29105/12907 | 47,662 | 0 | 48（0.1%） |
| 29107/12906 | 31,803 | 0 | 303（1.0%） |
| 29106/12906 | 9,560 | 0 | 2,308（24%） |

**大半は埋まらない。** 配信元が「地図上で水部になっている地域では、標高値がデータに入って
いない場合や、正確な値が入っていない場合があります」と言うとおり、水部はどの製品にも値が
無い。

**この変更はデータが目に見えて増えるから行うのではなく、層の切り方が間違っているから行う。**
回収量を成果指標にしないこと。

## DEM1Aは含めない

[T223](T223.md)で調査済み・見送り。その3つの理由のうち、今回の設計で解消するものと残る
ものがある。

- PNG形式のデコードが要る → **弱くなった**。変換式は配信元が明記している
  （`x = 2^16 R + 2^8 G + B`、`x = 2^23`が無効値、分解能`u = 0.01m`、無効値の画素は
  `(R,G,B)=(128,0,0)`。https://maps.gsi.go.jp/development/demtile.html ）
- カバレッジが全国均一でない（約46%） → **画素ごとの合成なら問題にならない**
- **OSM形状点の間隔（多くは5m超）に対し1m格子の恩恵がほぼ出ない → 変わらない**

3つ目が残る。我々はOSMの形状点で標高を拾うため、格子を細かくしても拾う点が増えない。
DEM1Aが効くのは、区間内のサンプリング間隔を5m未満へ細かくしたときで、それはT223の
再検討条件にそう書かれている。加えてDEM1Aは最大ズーム17でタイル数がz15の16倍になる。

## 完了条件

- 1つのタイル座標に対し、200を返した製品ぶんの行が `source_features` に在る
- 導出が画素ごとに優先順で採ることを、両方の製品に値がある画素・片方だけの画素・どちらにも
  無い画素の3ケースで確認する
- `dem`（DEM10B）へのリクエストがz14で行われ、z15での無駄な404が消えていることを
  取込ログで確認する
- 取込の所要とリクエスト数の増分を実測し、このエントリへ記録する（配信元は寄付・税で
  運営されている。無駄な往復を増やさない）

## 問いと答え

**問い（2026-09-26、ダッシュボード`T978-fetch-scope`）**: 標高タイルの下位の製品（DEM5B・5C・10B）を、全タイルで
取りますか、欠けた画素のあるタイルだけで取りますか。

1. 全タイルで、配信元が返す全製品を取る（記録の「あるべき形」どおり）（推奨）
2. 欠けた画素のあるタイルだけ、次の製品を取る

問いの時点の見積もり: 1は追加の要求が約10万回、2は約5.6万〜7.5万回（欠けを持つタイルが54%あるため、減らせるのは
3〜5割）。埋まる画素はどちらも同じ。2は取得が中身を見て次を取るかを決めるぶん1段複雑になり、使い方を変えたら
取り直しになる。

**答え（2026-09-26）**: (1) 全タイルで、配信元が返す全製品を取る。本番へ入れる前にVMのディスクの空きを測る。

## 着手時の前提の確かめ（origin/master 78964a5b）

背景に引いた`_fetch_one`は、起票後に取得と取込が分かれ（取込はHTTPを叩かない）、`backend/scripts/fetch_dem_tiles.py`
へ移っていた。欠陥は同じ形で残っていた——最初に200を返した製品で打ち切り、区域外の印（`_absent/<z>/<x>/<y>.none`）も
製品を跨いで1つだった。取込（`source_adapters/gsi_dem_tile.py`）は`stored_product`で優先順に最初に見つかった1製品だけを
読み、派生（`derive_raster_materials.py`）は`SELECT DISTINCT z`の1値だけを使っていた（製品が2つのズームを持つと
黙って片方を捨てる）。

## 対応（段階1）

層ごとに持つものを分けた。

| 層 | 持つもの | 置き場 |
|---|---|---|
| 宣言 | どの製品をどのズームで取るか（`grid.products`: 製品→ズーム） | `source_profile.yaml` |
| 配信元の事実 | URL・画素の値を採る順（DEM5A→5B→5C→10B） | `dem_tile_store.PRODUCT_PRIORITY` |
| 取得 | 宣言した製品を全部、それぞれのズームで全タイル。404は製品ごとに印（`_absent/<製品>/<z>/<x>/<y>.none`） | `scripts/fetch_dem_tiles.py` |
| 生データ | 手元にある製品×タイルごとに1行（`natural_key`は元から製品を含む） | `gsi_dem_tile.py` |
| 導出 | 製品を順に1つずつ流し、まだ値の無い頂点にだけ、その製品のズームで番地を出して画素を引く | `derive_raster_materials.derive_elevation` |

- 製品の順を知らない製品がプロファイルに書かれたら、読み込みの時点で止める（`DemGrid.__post_init__`）。派生も、順を
  知らない製品・1製品に2つのズームがあれば止める——どちらもどの値を採るかを決められない。
- 派生は上の製品に値のある頂点で下の製品を読まない。読む画素は、欠けた頂点のぶんだけ増える（本番で標高が付かなかった
  区間は2.1%。T970段階Dの実測）。
- 取込は、印も本文も無い（まだ試していない）タイルを製品ごとに数えてWARNINGで出す（これまではINFOで、どの製品かも
  出なかった）。
- 取得の完了ログに製品ごとの往復の数を出す（完了条件の「リクエスト数の増分」を、本番の実行ログからそのまま読める）。
- DEM1Aを含めない判断は変えず、理由を`docs/modules/backend/elevation.md`へ書いた（記録にしか無かったため）。
- 設計書の乖離も直した: `elevation.md`は取込の格納先を`payload`・読み方を`attrs`（幅・高さ・型・尺度・欠測値）と
  書いていたが、実装は`raster`（`rast`列）で、`attrs`は尺度と幅だけ。

## 段階2: 本番での取り直し（未実施）

担当では流さない（本番DBへの書き込みと約10万回の取得）。手順はダッシュボードの操作`T978-prod-refetch`に置いた。

### 本番の実測（読み取りのみ、2026-09-26、`run_probe.py --in-container`）

| | 値 |
|---|---|
| 置き場`/app/data/dem`のファイル | dem5a/15 45,611件・dem5b/15 623件・旧形式の区域外の印`_absent/15` 13,306件 |
| `source_features`の標高 | 12 GB（dem5a z15 45,611行・dem5b z15 623行）。DB全体18 GB |
| ディスク（`/app/data`と`/`は総量・使用量が同じで、同じディスクと見られる） | 総量50.9 GB・使用21.9 GB・**空き29.0 GB** |

取込範囲を覆うタイルはz15で59,540枚（45,611＋623＋13,306と一致）、z14で15,065枚。

### 見込み

- **要求の数**: 旧形式の印を製品ごとの印へ移せば107,533回（dem5a 623・dem5b 45,611・dem5c 46,234・dem z14 15,065）。
  移さないと、旧形式の印13,306枚ぶんをz15の3製品で叩き直して147,451回になる。旧形式の印は「z15でdem5a・5b・5c・demの
  どれも404」を意味するので、dem5a・5b・5cの印へそのまま移してよい。
- **取得の所要**: 未計測。上の小さな実測（20回で1.4秒、並列8）から、1秒あたり15〜60回として30分〜2時間の見込み。
- **容量**: 1行あたり約0.26 MB（12 GB／46,234行。rasterは圧縮されていない）。取込後の標高は
  0.26 MB ×（46,234 ＋ demの取得枚数（最大15,065）＋ dem5b・5cの取得枚数）。demだけで最大約3.9 GB増える。
  dem5b・5cが返す範囲は未計測で、取得を終えるまで分からない。
- **取込の間の一時的な容量が足りない**: `ingest_source`は、そのソースの全行を一時表（`_stage_dem`）へ積んでから
  パーティションを入れ替え、コミットまで旧い行を残す。取込の間は「旧い標高12 GB ＋ 一時表N ＋ 新しいパーティションN」
  （Nは取込後の標高の大きさ）が同時に在る。dem5b・5cが1枚も返さなくてもN ≥ 12＋3.1 GBで、2N ≥ 30 GBが空き29.0 GBを
  超える（取得したタイルのファイルも同じディスクに増える。1枚の大きさは未計測）。
  **今のディスクのまま、今の取込の手順では入らない**。避け方を問いとしてダッシュボード`T978-disk-peak`に置いた
  （取込の前に標高の生データを空にする／VMのディスクを増やす）。
