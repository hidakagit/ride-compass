# T532: 探索中の風評価を時変化（時刻依存の到達時刻ベース再評価）に対応する

状態: 完了（2026-09-01起票、ユーザー提案。2026-09-05に対応方針を確定し同日実装——時間展開グラフ
ではなく「通過時刻の幾何的な静的推定＋往路/復路別の事前合成コスト配列」方式。
前提タスク[T585](T585.md)[`round1_array`のベクトル化]・[T586](T586.md)を先に完了。
仮定巡航速度の画面指定（ユーザー要望、同日）も含む。本番実測は末尾「本番実測」節）

- 背景: 現行の探索（`road_graph_engine.py`）は「風は出発時点の起点付近の風を
  ルート全体に一様適用する（探索中は到達時刻が未確定のため、区間ごとの推定
  到達時刻の風は使わない）」という簡略化を採用している（`_build_search_graph`
  docstring明記）。ロードバイクは自動車と異なり時速20〜30km程度で、100kmの
  ルートには4〜5時間かかりうるため、出発時点の風のまま終盤の区間まで評価すると、
  実際の走行時には風向きが変わっている可能性が高い。
- ユーザー提案（2026-09-01）: 時変グラフ（Time-Dependent Graph）の導入。
  ノードに到達した時点の`g_score`（スタートからの累計コスト・実時間）から
  「今何時頃にここに到達するか」を概算し、その到達予想時刻の風データ（1時間
  予報のグリッドデータ等）をオンデマンドで参照してコストを決定する。これにより
  「午後から向かい風になるから午前中のうちにこっちのルートで帰ってこよう」
  という走行方位・時間帯を跨いだ高度なルーティングが可能になる。
- 前提の再検討（2026-09-05、`/task:next`実行時にT529の状態を見直した際に発覚）:
  起票時点では[T529](T529.md)（探索コストのlazy評価化、rustworkx+A*、`edge_cost_fn`が
  Edgeごとに都度呼ばれる設計）を基盤として想定していた——到達時刻を都度見て風データを
  オンデマンドで引き直す処理は、Edgeごとに呼ばれるコールバックがあって初めて自然に
  差し込める。しかしT529は本実装に着手される前に[T536](T536.md)へ置き換わり、
  T536は**逆方向**のアーキテクチャ（探索前にbbox全体のコスト配列を1回だけ構築し、
  A*はその配列への素の`list.__getitem__`のみを行う。「探索中にPythonの関数フレームを
  一切作らない」ことが高速化の核心）を採用して完了・本番反映済みである
  （[T530](T530.md)は完了）。
  つまり本タスクが前提としていた「Edgeごとに都度呼ばれるコールバック」という差し込み
  ポイント自体がもう無い。時変コストを導入するには、T536の「探索前に1回だけ配列を
  構築する」設計と両立する形を新たに設計する必要があり、旧`edge_cost_fn`ベースの想定は
  そのままでは使えない。→ 下記「対応方針」で解決。

## 現状の挙動と、時間依存化が素朴には困難な理由（2026-09-05、`/task:next`実行時の深掘り）

**現状（本タスク未着手時点）の挙動**: 風評価は起点1点・呼び出し時点の現在時刻のスナップ
ショット（`WeatherService.get_conditions`、`RoadGraphEngine.prepare`が1リクエストにつき
1回だけ取得）を、bbox内の全Edgeへ一様に適用している（`domain/evaluation.py:
_evaluate_wind_penalty_array`は`weather.wind_speed_ms`・`weather.wind_direction_deg`という
単一のスカラー値と各Edge自身の`bearing_deg`配列から`wind_speed_ms * cos(wind_direction_deg
- bearing_deg)`をベクトル計算するのみで、Edgeの位置や到達予想時刻は一切参照しない）。
したがって**「今は追い風の区間でも、実際にそこへ到達する数時間後には向かい風に変わって
いる」というケースを現状は評価できていない**。

**探索中にコストを動的に決める方式が取れない理由**: 探索本体（`domain/routing.py:
shortest_path_node_ids_lazy`）はrustworkx（Rust実装）の`rx.astar_shortest_path`を
直接呼んでおり、`edge_cost_fn`のシグネチャは`Callable[[int], float]`——Edge indexのみを
受け取り、探索中の経路状態（現在の累計コスト・到達予想時刻）を一切受け取れない。
T536は「探索前にコスト配列を1回だけ構築し、A*は`cost_list.__getitem__`のような
素のlistアクセスだけを行う」ことで高速化しており（Pythonの関数フレームを探索中に
作らない）、この契約を保ったままEdgeごとに動的な時刻依存コストを注入する余地が無い。
一対全木（`select_loop_turnarounds`、scipyのDijkstra）も同様に静的なコスト配列を前提にする。

**速度の扱い**: 累積距離から経過時間を求めるには速度が要る。既存の`ASSUMED_SPEED_KMH = 20.0`
（`domain/wind.py`、区間詳細の到達予想時刻表示で既に使用中）をそのまま転用する。重要なのは
これが**風・勾配に依存しない一律の定数**であること——速度自体を向かい風で遅くなる等、
動的にしようとすると「時間の計算に速度が要り、速度が風[＝時間依存コスト]に影響される」
という循環が生まれ設計が破綻する。速度を定数のまま据え置く限り、Edgeごとの所要時間は
`distance_m`と同じく探索前に静的に決まる値として扱える。

## 対応方針（2026-09-05確定。ユーザー要望「今のルーティング実行速度をなるべく落とさず実現できる方式」）

### 方式: 通過時刻をEdgeの位置から静的に推定し、往路/復路ごとにコスト配列を事前合成する

T536の契約（探索前に配列を1回作る、A*/Dijkstraは`list.__getitem__`しか行わない）を
そのまま保つ。探索アルゴリズム・グラフ構造・A*ヒューリスティックは一切変えない
（時間展開グラフは作らない）。変えるのは「配列を作るときに、Edgeごとに違う時刻の風を
引く」ことだけ。

1. **通過時刻の静的推定**: 各Edgeを「いつ通過するか」を、探索中の経路状態ではなく
   Edgeの位置だけから推定する。周回はフロンティア方式（[T531](T531.md)）により
   「起点からの往路（一対全木）」と「折返し点から起点への復路（A*）」の2レグに
   構造上分かれており、それぞれのレグでの通過時刻は起点からの直線距離で近似できる:
   - 往路: `t_e = t0 + DETOUR × d(起点, e) / v`
   - 復路: `t_e = t0 + T_total − DETOUR × d(e, 起点) / v`、`T_total = 目標距離 / v`
     （距離フィルタが目標±許容を強制するため周回の総所要時間は定数として扱える）
   - `d`は直線距離（`_estimate_distances_m`と同じhaversine、Edge中点に対して）、
     `v = ASSUMED_SPEED_KMH`、`DETOUR`は道なり距離/直線距離の経験的比（定数、初期値1.3。
     往路木が求まった後は`tree.length_m / 直線距離`の中央値として実測できるためINFOログへ
     出して較正する）。
   - 精度の考え方: 風の時間解像度は1時間＝20km分の走行。直線距離推定の誤差
     （迂回率のばらつき±20%×片道15km≒3km≒9分）はこの解像度より十分小さく、
     「往路の終盤〜復路で風向が変わる」という本タスクが捉えたい現象を表現するには足りる。
2. **時別風予報の入手**: 起点の48時間分・1時間刻みの風向風速は、`WeatherClient.get_forecast`
   （`get_conditions`が使う単一地点取得）の応答`hourly.wind_speed_10m`/`wind_direction_10m`
   として**既に取得済み**（同じTTLキャッシュ）。追加のAPI呼び出しはゼロ。空間変化
   （bbox内で風が違う）は本タスクでは扱わない（下記「派生候補」）。
3. **Edgeごとの風ペナルティ**: `wind_penalty[e] = speed[h(t_e)] × cos(dir[h(t_e)] − bearing_e)`
   （`h`は最近傍1時間のindex、numpyのgather。73万Edgeで数十ms）。
4. **レグ別コスト配列**: 往路用・復路用の2本を`compose_costs_from_axis_matrix`で合成し、
   一対全木には往路用、復路A*（retrace倍率の差し替え含む）には復路用を渡す。
   風軸の重みが0・風予報が取れない・往復で全Edgeの時刻バケットが同一（短距離）なら
   復路配列は往路配列を共有し追加コストをゼロにする。

### 速度への影響（2026-09-05、開発機の合成データ実測に基づく見積り）

### 検討して不採用にした案

- **時間展開グラフ**（ノードを(地点, 時刻バケット)へ複製）: グラフが時刻バケット数倍に
  膨らみ（5時間×30分刻みで10倍）、prepare・メモリともに悪化。T536の「1本の配列」契約とは
  両立するが本末転倒。
- **探索中コールバックで到達時刻依存コスト**: rustworkx/scipyのシグネチャ上不可能で、
  T536が排除したPythonフレームを戻すことになる。
- **2パス反復**（1パス目の経路の実到達時刻で風を引き直し再探索）: 1時間解像度に対する
  精度向上は僅少で探索段階が2倍。必要になれば本方式の上に後付けできる（`passage_hours`
  配列を実経路由来に差し替えるだけ）。
- **速度を風で可変にする**: 上記「速度の扱い」の循環。

- Open-Meteoの時別系列は48時間分。`t0 + T_total`が範囲外（深夜出発の長距離等）は末尾へ
  クランプする（`WindWayService._nearest_time_index`は範囲外を「不明」にするが、

  night_only`）も同じ`passage_hours`で「日没後に通過するEdgeだけ重みを掛ける」時変化に

  最寄り格子点を引けば、時刻gatherと同じ形の2次元gather（格子, 時刻）で載る。

- `wind_time_varying=True`（風軸の既定重み>0で時変化が有効）。往路レグの通過予定時刻は
  0.01〜1.58h（20km/h）、復路レグは起点到着1.25h（=25km÷20km/h）基準で−0.33〜1.24h
  （負値・範囲外は系列の端へクランプ）。30km/h指定では0.01〜1.05h／−0.22〜0.83hと速度に
  応じて縮む。
- 復路レグの合成（約200ms）は`select_ms`に含まれ、温パスの`total_ms`は[T586](T586.md)
  反映時（2,130〜2,141ms）と同水準の2,220〜2,582ms。`cost_ms`（往路合成＋lazy行順の索引
  構築）は約540msで、T585反映時（約190ms）からの増分は時別gather・Edge中点距離・索引配列の
  分。
- `detour_ratio_median=1.19`（往路実距離÷直線距離の中央値、東京駅周辺）。`ROUTE_DETOUR_RATIO`
  =1.3はやや過大で、通過予定時刻を最大1割ほど遅めに見積もる。1時間解像度の風には影響が
  小さいため据え置き、他地域の値も見てから較正する（必要になれば別途起票）。
