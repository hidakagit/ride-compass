# T1035. batchの2つのSQLが、駆動側の取り方で余分な仕事をしている

状態: 未完了

## 背景

第12回の全体最適の観点で見つかった、SQLの駆動方向に起因する2件。
**どちらも所要時間は未計測。**

1. **事故の最近傍検索が1件につき2回走り、かつタイブレークが無い。** 事故を最寄りの
   区間へ割り当てるSQLで、**同一の相関KNN副問い合わせが、取り出す列だけを変えて
   2本並んでいる**。`LATERAL (… LIMIT 1)`なら1回で両列が取れる。
   さらに距離以外のタイブレークが無いため、**等距離のタイで2本が別の区間を指しうる**
   （＝事故が存在しない区間へ集計される）。**タイで食い違う実例は未確認。**
2. **信号の近接判定が「信号の数」ではなく「全ノードの数」に比例している。**
   ノード材料の全行を駆動側にし、1行ごとに相関EXISTSを回す。信号側の集合を駆動側に
   すれば、当たったノードだけのUPDATEになる。索引自体は前置フィルタで効くが、
   索引プローブの回数が全ノード分になる。取込範囲を広げる方向で効いてくる形。

## 対応方針

**性能の主張は実測とセットにする**（CLAUDE.md）。

1. **先に現行の所要時間を測る。** 本番DBで測る（開発DBはスペック・前提が違いすぎて
   性能測定に適さない）。`backend/scripts/run_probe.py`経由。
2. 1については、**タイブレークの欠如は性能と独立した正しさの問題**なので、所要時間の
   結果によらず直す。同じ順序で両列を取ることが目的で、`LATERAL`への書き換えは
   その手段。
3. 2については、測った結果が十分速ければ**直さないと決めてよい**。その場合は
   「現状の所要時間」と「直さないと決めた」ことをこのエントリへ書く。

## 完了条件

- 1について: 両列が**同一の1回の最近傍探索**から取れている。等距離のタイでも
  両列が同じ区間を指すことを、人工的なタイを作って確認する。
- 2について: 直したなら**直す前後の所要時間が本番で実測**され、このエントリにある。
  直さないと決めたなら、現状の所要時間と判断理由がある。
- 「2回→1回」のような回数の主張は、回数だけでなく所要時間で裏付ける
  （利用者から見た単位で測る）。
