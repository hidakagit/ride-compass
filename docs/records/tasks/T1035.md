# T1035. batchの2つのSQLが、駆動側の取り方で余分な仕事をしている

状態: 完了

## 背景

第12回の全体最適の観点で見つかった、SQLの駆動方向に起因する2件。
**どちらも所要時間は未計測。**

1. **事故の最近傍検索が1件につき2回走り、かつタイブレークが無い。** 事故を最寄りの
   区間へ割り当てるSQLで、**同一の相関KNN副問い合わせが、取り出す列だけを変えて
   2本並んでいる**。`LATERAL (… LIMIT 1)`なら1回で両列が取れる。
   さらに距離以外のタイブレークが無いため、**等距離のタイで2本が別の区間を指しうる**
   （＝事故が存在しない区間へ集計される）。**タイで食い違う実例は未確認。**
2. **信号の近接判定が「信号の数」ではなく「全ノードの数」に比例している。**
   ノード材料の全行を駆動側にし、1行ごとに相関EXISTSを回す。信号側の集合を駆動側に
   すれば、当たったノードだけのUPDATEになる。索引自体は前置フィルタで効くが、
   索引プローブの回数が全ノード分になる。取込範囲を広げる方向で効いてくる形。

## 対応方針

**性能の主張は実測とセットにする**（CLAUDE.md）。

1. **先に現行の所要時間を測る。** 本番DBで測る（開発DBはスペック・前提が違いすぎて
   性能測定に適さない）。`backend/scripts/run_probe.py`経由。
2. 1については、**タイブレークの欠如は性能と独立した正しさの問題**なので、所要時間の
   結果によらず直す。同じ順序で両列を取ることが目的で、`LATERAL`への書き換えは
   その手段。
3. 2については、測った結果が十分速ければ**直さないと決めてよい**。その場合は
   「現状の所要時間」と「直さないと決めた」ことをこのエントリへ書く。

## 完了条件

- 1について: 両列が**同一の1回の最近傍探索**から取れている。等距離のタイでも
  両列が同じ区間を指すことを、人工的なタイを作って確認する。
- 2について: 直したなら**直す前後の所要時間が本番で実測**され、このエントリにある。
  直さないと決めたなら、現状の所要時間と判断理由がある。
- 「2回→1回」のような回数の主張は、回数だけでなく所要時間で裏付ける
  （利用者から見た単位で測る）。

## 実施（2026-09-23）

### 本番での現状（`backend/scripts/run_probe.py`経由、読み取りのみ）

本番の規模: 区間2,582,177本・ノード材料2,102,784点・事故108,409件・信号ノード126,102点。
UPDATEはEXPLAIN ANALYZEせず、読み取りに等価なSELECTへ書き換えて測った。信号の判定は
バッチと同じ一時表（`_signal_nodes`）を要るため、トランザクション内で作ってROLLBACKした
（永続の表へは書いていない）。

| 対象 | 変更前 | 変更後 |
|---|---|---|
| 事故の最近傍（SELECT相当、温まった状態） | 10,382 ms | 4,782 ms |
| 信号の近接判定（SELECT相当） | 173,876 ms | 9,845 ms |

### 1. 事故の最近傍

- **見積もりとのずれ**: 背景は「1件につき2回」だったが、本番の実行計画では**3回**走っていた。
  集計側の`WHERE osm_way_id IS NOT NULL`がプランナによって走査条件へ押し込まれ、同じ
  相関KNNがもう1本増えていた（SubPlan 1が`loops=108409`、残る2本が`loops=98023`ずつ）。
- `CROSS JOIN LATERAL (… ORDER BY 距離, e.osm_way_id, e.segment_index LIMIT 1)`へ書き換え、
  両列を同じ1回の探索から取る。本番の計画は`Index Scan … Order By`（距離）＋
  `Incremental Sort`（Presorted Keyが距離）で、KNNの索引はそのまま効いている。
- **タイの実例**: 最寄りと2番目が同じ距離の事故が**94件**あった。旧SQLはそのうち**47件**を
  鍵の最小でない区間へ付けていた（索引の並び次第）。**2本の副問い合わせが実在しない組を
  指した件数は0件**（`matched 98,023 / phantom 0`）——同じ計画・同じスナップショットのため、
  本番では食い違いは起きていなかった。変更後はタイを区間の鍵の小さい方へ決定的に付ける。
  集計の旧新差: 値が違う区間92本、総重みは旧新とも99,385.0で一致（付け替わっただけで
  失われていない）。
- 人工的なタイ: `backend/tests/test_derive_counts.py`（新規）で、3本の道が接するノードの
  真上に事故を置き（3区間とも距離0）、事故が1件のまま鍵の最小の区間へ付くことを確かめる。
  **旧実装でもこのテストは通った**（上と同じく、旧の2本は同じ計画で同じ行を返すため）。
  テストが効いていることは、タイブレークを`e.osm_way_id DESC`へわざと逆にして落ちる
  （`(300, 0, 1.0) != (100, 0, 1.0)`）ことで確認した。

### 2. 信号の近接判定

- 173.9秒は`derive_node_materials`の段の大半で、しかも旧UPDATEは**全2,102,784行を
  書き換えていた**（値が変わらない行も）。直さない理由が無いので直した。
- 信号側を駆動にした: `_signal_nodes`に位置（`geom`）を持たせ、信号1点ごとに半径内の
  ノードを索引で探し（126,102回）、当たったノード（214,560点）だけを`true`にする。単独で
  流し直したときのために、先に「前回`true`だった行」だけを`false`へ戻す。id照合用の
  一意索引は使わなくなったので作らない。
- 1回目の書き換え（信号idでノードの生データへ結合してから近傍を探す形）は**284.7秒と逆に
  遅くなった**——プランナが生ノード786万点の側を駆動にした。位置を一時表へ持たせて結合を
  1段減らした形で9.8秒になった。
- 旧新の一致: 本番で「信号付きになるノード」の集合を旧新それぞれ求め、件数（214,560）と
  id列のmd5（`58193586…`）が一致。
- テスト: `backend/tests/test_derive_node_materials.py`（新規）。半径内のノード・信号
  ノード自身は`true`、遠いノードは`false`。流し直すと根拠の無くなった`true`が外れる
  （戻しの処理を外すと落ちることを確認）。

### 変更したもの

- `backend/app/batch/derive_counts.py`: `_EDGE_ACCIDENTS`をLATERAL＋タイブレークへ。
- `backend/app/batch/derive_node_materials.py`: `_source_nodes`（列を足せる形）、
  `_SIGNAL_NODES`に位置、`_CLEAR_SIGNALS`新設、`_UPDATE_SIGNALS`を信号駆動へ。
- `docs/modules/backend/static-road-attributes.md`「事故の帰属」: タイのときの付け先。

### 本番への反映

コードの変更だけで、既存DB行の形は変わらない。**事故の集計値は次に`derive_counts`を
流したときにタイ47件ぶん付け替わる**（区間92本の値が変わる、総量は不変）。バッチの
再実行はこの作業では行っていない。
