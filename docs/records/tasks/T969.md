# T969: アーキテクチャの総点検（層の契約と越境・到達可能性・知識の重複・レビュー基盤の棚卸し）

状態: 未完了

未着手（2026-09-20起票）

## 背景

[T956](T956.md)で、複雑度を下げる改修が長く効いていなかった理由が具体的に分かった。
4つの層で同じ形の歪みが同時に出ていた。

1. **DBが持つべき制約をappが吸収していた**。`road_edges.osm_way_id`にFKもNOT NULLも無く、
   「wayの行が無い区間」という状態を材料の値式10本が`CASE WHEN ... IS NULL`で毎回吸収して
   いた。兄弟の派生表5本は同じFKを既に持っており、本番の違反行は0件だった。
2. **appにテスト専用の口があった**。`folds_tag_absence_to_false`はテストからしか呼ばれない
   のにapp配下にあった（同タスク内で撤去）。
3. **本番から到達しないコードが「オラクル」名目で残っていた**。`compute_edge_cost`は
   [T240](T240.md)の対応方針の時点で「回帰テストのオラクルとして存続させる」と書かれ、
   それを置き換えた`compute_edge_costs_bulk`まで同じ理由で残り、1か月近く残骸だった。
4. **テストがテストを検証していた**。新旧2実装の等価だけを見るテスト、宣言を書き写した
   テスト、タイルSQLをテスト側で組み直して突き合わせるテストがあった。

**既存の仕組みでは見つからない。** `/review:all`は2026-09-19（前日）に実施済みで、
上のどれも挙がっていない。理由は構造的で、`/review:overall`・`/review:complexity`は
人がコードを読んで気づく形（問題を作った本人が同じ目で見る）、`scripts/review_checks.py`の
検知器29本は母集団が「識別子と参照」「テキストの型」で、**層の責務**と**入口からの
到達可能性**を見るものが1本も無い。DBのスキーマとappの前提を突き合わせるものも無い。

## 対応方針

**このタスクは事実の棚卸しに徹し、直さない。** 直すのは各点検が出した母集団に対して、
既存の[T963](T963.md)・[T965](T965.md)・[T966](T966.md)・[T967](T967.md)・[T968](T968.md)が
行う。**総点検→各タスクでダブルチェック**の順にするのは、今の状態が信用できないため
（ユーザー判断、2026-09-20）——各タスクのエントリに書かれた前提自体が古い可能性があり、
先に現物から事実を出し直す。

判断を混ぜず、**母集団の導出方法と件数**を出す。各点検は「何を列挙したか」「いくつか」
「代表例」を記録し、1件ごとの可否判断は後続タスクへ渡す。

### 点検0: 何を・どこに持ち、何を担保するかを定義する

**層の責務を語る前に、ここが要る。** システムが扱うものは5種類あるが、
**基準が書かれているのはキャッシュだけ**で、残り4つは未定義のまま動いている。

| 分類 | 今どこにあるか | 基準の有無 |
|---|---|---|
| 外部ソース | DB（`osm_raw_ways`・`osm_raw_nodes`・`osm_raw_pois`・`accident_points`） | 無し |
| 派生データ | **DBとキャッシュに分かれている**。DB側11表（`road_edges`・`road_nodes`・`edge_attribute_counts`・`way_attribute_counts`・`elevation_attributes`・`way_landcover`・`edge_landcover`・`raw_intersection_nodes`・`designation_attributes`・`way_divided_carriageway`・`route_designations`）、キャッシュ側（タイル材料・スコア行列） | **分ける基準が無い** |
| 管理データ（業務ルール） | **DBとコードに分かれている**。DB側（`axis_definitions`・`axis_registry_meta`）、コード側（`MATERIAL_CATALOG`・`HARD_FILTER_*`・`POI_COUNT_KINDS`等） | **分ける基準が無い** |
| キャッシュ | プロセス内 / Redis / ディスク | **[docs/conventions/caching.md](../../conventions/caching.md)に2軸の基準あり。ただし「正本を持たないもの」に限定しており、postgresとの線引きは対象外と宣言している** |
| 生成物 | ファイル（`axis-catalog.json`・`openapi.json`・`region-tile-config.json`） | 片側流れの原則（構造仕様9）あり。生成タイミング・再生成の責務は未定義 |
| 運用の記録 | DB（`osm_import_runs`・`accident_import_runs`・`designation_import_runs`・`road_graph_tiles`） | 無し |

**この未定義が具体的に何を壊したか**（T956での実例）:

- 「派生表なら親が必ずある」という性質が言語化されていないため、`road_edges`にFKが
  無いまま誰も気づかず、app側の値式10本がその状態を吸収していた。
- 材料の値の求め方（管理データ）が、Pythonのextractorとタイル焼き込みSQLとカバレッジ集計の
  3か所にあり、どれが正本かの基準が無かった。

### 同じ問いは以前に出ており、切り縮めて答えられている

ユーザーから「キャッシュ・Redis・ファイル・postgres、どこに何を持つか決めているのか」
という問題提起があった。これに対して作られたのが[docs/conventions/caching.md](../../conventions/caching.md)
（2026-09-07新設）だが、冒頭で**正本を持つものを対象外と宣言している**。

> ここで扱うキャッシュはすべて、失っても呼び出し元が再取得・再計算すれば正しい答えに
> 戻れるものに限る。キャッシュが唯一の持ち主になっている状態を作らない。

つまり4つのうち**キャッシュの内側（プロセス内・Redis・ディスク）だけ**を決め、
**postgresとの線引きは扱っていない**。続く[T647](T647.md)は「キャッシュ方針を機械的に
強制する」で、さらに内側へ進んでいる。問いの範囲が答える側の都合で縮んだまま閉じられた。

**点検0はこの切り縮めを戻す。** 対象は「正本を持つものを含めた全体」で、
`caching.md`が対象外と宣言した境界そのものを決める。

### 保持先が「設計の分類」ではなく「測定時点の運用状態」で決められている

[T651](T651.md)（2026-09-07、Redisを残すか撤去するかを実測で決める）の判断根拠:

| 実測 | 値 |
|---|---|
| キー数 / メモリ | 3,195キー / 5.19MB |
| ヒット率 | 17.8% |
| プロセス構成 | **単一プロセス** |
| ルート生成系のキー | **0件（計測時点でルート生成が走っていなかったため）** |

この結果から「Redisの価値はほぼ1点（再起動をまたぐ温存）に縮んでいる」と結論し、
[T652](T652.md)でルート生成の2つのcache-asideを削除した。いま残っているRedisの用途は
ほぼ外部API（JMA）のキャッシュだけ。

**問題は結論ではなく、判断の立て方**:

- 「ルート生成系0件」は**走っていなかったから0**と自分で注記したうえで、材料にしている。
- 根拠の中心が「**いま単一プロセスだから**」——これは運用状態であって設計の分類ではない。
  T651自身が「将来のワーカー複数化を踏まえ」と書いており、**判断が将来ひっくり返ることを
  認識しながら現在の状態へ実装を合わせている**。

点検0は、保持先を**分類（外部ソース・派生・管理・キャッシュ・生成物）と、その分類が要求
する性質**から決める。測定値は「その基準を満たすか」の検算に使い、基準そのものにしない。
T651・T652の判断も、この基準で検算する（結論が同じでも、根拠を置き直す）。

### 点検0が答えるべき問い

1. **分類の定義**: 5分類（+運用の記録）の境界を書く。どれにも当てはまらないもの・2つに
   またがるものを出す。
2. **置き場所の基準**: 分類ごとに「DBへ持つのはどういうときか」を書く。とくに
   **派生データがDBとキャッシュに分かれている基準**——`docs/conventions/caching.md`の「失っても自前の
   PostGISから復元できるものはプロセス内かディスクへ置く」は**キャッシュ側の基準**で、
   派生表そのものをDBへ置く基準ではない。再計算コスト・再現可能性・参照頻度のどれで
   決めるのかを言語化する。
3. **管理データの置き場所**: 評価軸は`axis_definitions`（DB、API経由でしか変えない）、
   材料カタログは`MATERIAL_CATALOG`（コード、デプロイでしか変わらない）。**同じ業務ルール
   なのに変更の経路が違う**理由を書く。書けないなら、どちらかへ寄せる判断を起票する。
4. **何を担保するか**: 分類ごとに、DBが保証すべきもの（NOT NULL・FK・UNIQUE・CHECK・
   DEFAULT・型・カスケード）を書く。**派生データなら親への参照は必須**、のように分類から
   導ける形にする——表を1つずつ見て決める形にしない。
5. **失われたときどうなるか**: 分類ごとに、消えたときの復旧手段（再取込・再計算・
   スナップショット・復旧不能）を書く。復旧不能なものがどれかを明確にする。

### 過去のレビューはこれを扱っていない（実測）

- レビュー履歴17回に「何をDBへ持つか」「永続化の基準」を扱ったものは**0件**。
- `/review:overall`・`/review:complexity`のレンズ本文に、DB・永続化に関する観点は
  **1行も無い**（grepで0件）。「全体として設計思想が一貫しているか」を問うレンズが、
  システムが何をどこに持つかを一度も問うていない。

この結果は点検6（レビュー基盤の棚卸し）の入力にもなる。

### 置き場所

定義は`docs/design-principles.md`（構造仕様）か`docs/architecture.md`のどちらかへ置く。
**点検1の層の契約は、この定義の上にしか書けない**ため、点検0を先に終える。

### 点検1: 層の契約を書き下し、越境を種類ごとに列挙する

**先に契約を書く。** 今どこにも「どの層が何に責任を持つか」が書かれていない
（`docs/design-principles.md`構造仕様7がトランザクション境界、15がDB/app/テストの線を
持つだけで、層の一覧と契約は無い）。FKは今回見つかった**1つの事象**であり、そこから
点検を設計すると再び症状ベースになる。

まず層と契約を書き下す（案。着手時に現物を読んで確定する）:

| 層 | 持つもの | 持ってはいけないもの |
|---|---|---|
| DB（PostGIS） | 点検0で定義した種類のデータと、その種類に要る制約 | 点検0で「持たない」と決めたもの |
| `app/domain` | ふるまい（評価・分類・合成）。純関数と宣言 | 外部の形（SQL文字列・HTTP・ファイルパス）、DBが保証している前提の再確認 |
| `app/infrastructure` | 外部との接続（DB・HTTP・ファイル）と、その形の変換 | 業務判断 |
| `app/services` | オーケストレーションとトランザクション境界 | 評価の中身 |
| `app/api` | HTTP境界（入出力の形・認可・エラー変換） | 評価の中身 |
| `app/batch` | 取込・事前集計 | webが読む層からの参照（既存検知器あり） |
| frontend | 表示と解釈 | backendが決めるべき値の再計算 |
| tests | 「今」のふるまいの網羅 | 本番で作れない状態、本番の式・順序の写し |
| 生成物 | 片側へ流れる（backend→frontend） | 逆流 |

そのうえで、**越境の種類ごとに**母集団を導出する。

1. **DBの仕事をappが吸収**: モデルの`ForeignKey`宣言・`nullable`・`unique`と、本番の
   `pg_constraint`（f/u/c）・`attnotnull`・`attidentity`・`pg_attrdef`を突き合わせる。
   制約が無い列について、app側が「無いかもしれない」前提で書いている箇所
   （SQL式の`IS NULL THEN`、`COALESCE`の既定値、`or {}`、`is None`分岐、
   重複排除の`DISTINCT`/`set()`）を出す。**FKだけでなく、NOT NULL・UNIQUE・CHECK・
   DEFAULT・型（数値を文字列で持っていないか、分類が文字列か）も同じ扱いで見る。**
2. **appの仕事がSQLへ漏れている**: `app/infrastructure/**`のSQL文字列から、業務判断
   （分類・しきい値・重み・表示の符号化）を含むものを出す。**材料の値式を
   `MaterialSpec.value_sql`としてSQLへ寄せた[T956](T956.md)の判断自体を、この基準で
   検算する**——「surface_goodは良い舗装か」は業務判断ではないのか。SQLへ置いたのが
   正しいなら、なぜ正しいかを契約の側へ書く。
3. **domainが外部の形を持っている**: `app/domain/**`が持つSQL文字列・HTTPの形・
   ファイルパス・環境変数を出す。**`app/domain/material_sql.py`はSQL断片の集合で、
   T956で「材料が何から導かれるかはdomainの知識だから」とdomainへ置いた。この判断も
   検算対象**（同じ理屈なら、他のSQLもdomainへ来るべきことになる）。
4. **infrastructureが業務判断を持っている**: 2の裏。`_ROAD_SURFACE_TILE_MVT_SQL`の
   CASE式のように、表示の符号化と材料の導出が同じ場所にあるもの。
5. **appにテスト専用の口**（旧点検4をここへ畳む）。
6. **frontendがbackendの値を再計算している**: 設計原則「解釈はクライアントに」が
   どこまでで、どこからが再計算かの線を引き、越えているものを出す。
7. **生成物の逆流**: `axis-catalog.json`・`openapi.json`・`region-tile-config.json`を
   backend側が読んでいないか（構造仕様9の片側importが守られているか）。

各越境について「件数」と「代表例」を出す。**1件ごとの可否は判断しない**。

### 点検2: 本番の入口からの到達可能性

- 入口を列挙する: `main.py`が登録するFastAPIルーター、`app/batch/*`の`main()`、
  `backend/scripts/*`、`lifespan`が起動するジョブ。
- そこから`app/**`を辿って到達する定義の閉包を出し、**到達しない公開定義**を列挙する。
- 偽陽性の型を除く（デコレータ登録のルートハンドラ、SQLAlchemyの宣言モデル）。
  取りこぼしの型は[T963](T963.md)の「2026-09-20の実測」節を参照（テキストのgrepでは
  docstringの言及を使用と数える。ASTの名前参照でも到達可能性は見えない）。

### 点検3: 同じ知識が2か所にある箇所

- SQLの式・列の並び・合成の順序のように、**片方だけ変わると静かに食い違う**ものを探す。
- 導出方法: `app/**`と`tests/**`から同一のAST部分木（一定ノード数以上）を出す。
  frontendのテキストクローンは既存の`/review:duplication`（jscpd）が見ているため、
  そちらと母集団が重ならない範囲（backendのAST）に限る。

### 点検4: テストがテストを検証している箇所

- 母集団: `tests/**`のうち、(a)2つの実装の出力一致だけを見るもの、(b)レジストリ・
  カタログのリテラルを書き写して突き合わせるもの、(c)本番の式・順序をテスト側で
  組み直しているもの。
- (a)(b)は`docs/conventions/comments.md`・CLAUDE.mdの判定基準が既にあるため、それに照らして列挙する。

### 点検5: 検知器29本の棚卸し

- 1本ずつ「母集団の導出方法」「強制経路（`DETECTOR_ENFORCEMENT`）」「全件実行での
  現在の検出数」「そのうち誰も直していない期間」を表にする。
- 母集団が重なっている組を出す。参考表示のみの検知器について、**出力が実際に減っているか**
  を履歴（`.claude/commands/review/history/`）から確かめる。2026-09-20時点の全件実行で
  参考は140件（うち経緯コメント103件）あり、誰も直していない。
- [T966](T966.md)と母集団が重なる。**T966が先か、この点検がT966の入力になるか**を
  着手時に決める（重複して同じ表を2回作らない）。

### 点検6: 周期レビューが構造的な指摘を出さないのはなぜか

**過去には全ソースを読み直す形のレビューがあり、止まっている。**

| 形 | 時期 | 出したもの |
|---|---|---|
| 全体最適レビュー（全ソース・DB設計をゼロから再読） | 第8回2026-08-24・第9回2026-08-25 | 起票案A〜F＋知見4件（T285〜T288）、材料供給への投資・migration未適用の恒久対策など |
| ゼロベース網羅レビュー（code-review max×9分割） | 2026-08-30 | P1 13件・P2/P3 72件（T425・T426→T463〜T471） |
| `/review:all`（overall/complexity/consistency/uiのレンズ） | 2026-08-16〜継続、17回 | 個別の事象のみ。**アーキテクチャの規則についての指摘は0件** |

前2つは**全ソースを読み直す**形で、構造の指摘を実際に出していた。止まった後は
`/review:all`（成果物を見るレンズ）だけが回り、以後は事象しか出ていない。

**依頼が却下されてきた経緯**（ユーザー指摘、2026-09-20）: 「全体最適になっているか」
「責務が偏っていないか」という構造レビューの依頼は複数回あったが、そのたびに
「それはreviewで同じ仕組みがあるから」と退けられた。CLAUDE.mdの
「既に同じ目的の仕組みがあるかを確かめる」は**検知器を足すときの歯止め**であって、
構造レビューの依頼を却下する理由に使うものではない。



**17回の`/review:all`で、「欠陥を生んでいる規則」の指摘は一度も出ていない。**
挙がるのは個別の事象（このレイヤーが壊れる・このdocsが撤去済みの名前を指す・このガードが
発火しない）で、構造に近いものも検知器についての2件だけ（2026-09-15 F-2「検知器が母集団を
手で列挙している」、2026-09-16 F-2「0件は母集団に入っていないだけ」）。
**アーキテクチャの規則についての指摘は0件。**

CLAUDE.md「修正の原則」の「範囲は性質から導く——症状が出た場所でなく、欠陥を成立させて
いる性質で決める」を、**レビュー自身が守っていない**。レンズの問いが「一貫しているか」
「複雑さの置き場は適切か」という成果物への問いのため、成果物レベルの欠陥しか出ない。
出力もP0/P1/P2の事象リストで、事象を直す方へ誘導している。

- 履歴17回の指摘を、「個別の事象」「事象を生んでいる規則」に分類して件数を出す。
- 同じ性質の指摘が複数回繰り返されているもの（再発）を出す。再発は「1件ずつ直した」
  ことの証拠で、規則を直していれば起きない。
- レンズの問い（`overall.md`・`complexity.md`・`consistency.md`）が、規則を問う形に
  なっていない箇所を特定する。
- **結論として、レンズを直すのか・廃止して別の形にするのかまでを出す**
  （[T966](T966.md)の「検知器を足す前に全体と突き合わせる」と同じ判断を、レビュー基盤
  そのものへ適用する）。**止まった「全ソースを読み直す」形を戻す選択肢を必ず検討に含める**
  ——レンズを直すより、そちらが実際に構造の指摘を出していた。
