# T1044. ノードの生データを読む綴りが、共有断片を持たないまま手書きで散っている

状態: 完了

## 背景

T1031で道の生データ（`source = 'osm_way'`）の読み方を`domain/material_sql.py`の
`ways_source_sql`/`ways_lookup_sql`へ寄せ、`backend/app`・`backend/scripts`で
`source = 'osm_way'`の副問い合わせを手書きしている箇所を0にした。

ノードの生データ（`source = 'osm_node'`）には同じ役の関数が無く、`source`の比較と
キーのキャスト（`natural_key::bigint`／`natural_key = x::text`）が読み手ごとに手書きされている。
取込の入れ方（`source`の値・キーの型）を変えたとき、道の側は関数1本を直せば済むが、
ノードの側は手書きの全箇所を探して直すことになり、1つでも漏れればその読み手だけが古い世界を
指し続ける（T1031の背景にある「共有側を直したのに手書きの1本が残る」と同じ形）。

起票時点（2026-09-23）の grep で、`backend/app`配下の該当は派生バッチ
（`derive_node_materials.py`・`derive_counts.py`）と`road_graph_repository.py`
（タイル配信のPOI・区間の端点・ノード座標の読み出し）にまたがる。件数はここへ固定しない
——下の導出で数え直すこと。

## 対応方針

- ノード版の関数を`material_sql.py`へ足す（道と同じく「生データの読み方の単一の情報源」は
  このモジュールが持つ）。形は道に合わせる: 全件を読む副問い合わせと、キー1件を主キーで
  引く副問い合わせ（照合はtextのまま——`ways_lookup_sql`のdocstringにある索引の理由は
  ノードでも同じ）。
- 手書きの箇所を関数呼び出しへ寄せる。性能に効く箇所（タイル配信・材料の読み出し）は、
  照合がtextのまま主キーで引けていることを`EXPLAIN`で確認してから置き換える
  （bigintへキャストして突き合わせる形へ変えると、索引が使えず総当たりになる）。
- `infrastructure/derived_data_freshness.py`の`f.natural_key::bigint`は、ソースを
  引数（`:source`）で受ける汎用の台帳で、ノード専用の読み手ではない。これを関数へ寄せるか
  （全ソースのキーがbigintという前提を1か所に置く）は、このタスクで判断して結果を書く。

## 完了条件

- 導出: `backend/app`・`backend/scripts`を`source *= *'osm_node'`でgrepし、ヒットが
  `material_sql.py`（と、`source_runs`を引く取込記録の参照＝生データを読まない行）だけ。
  `source_runs`の行かどうかは1件ずつFROM句を見て判定し、判定をこのエントリへ書く。
- 置き換えた各SQLについて、変更前後の結果集合が一致することを開発DBで確かめる
  （`EXCEPT ALL`を両向きに取り、どちらも0行。T1031と同じ方法）。
- `backend/tests`のうち変更が届く範囲が通る（`pytest backend/tests -q --co`と、
  変更したシンボルのgrepで範囲を出す）。

## 実施内容（2026-09-24）

### 母集団

- 定義: `backend/app`・`backend/scripts`のうち、`source_features`からノードの生データを読むSQL。
- 列挙: `grep -rnE "source *= *'osm_node'" backend/app backend/scripts` → 7件（`derive_counts.py` 1・
  `derive_node_materials.py` 2・`road_graph_repository.py` 4）。`backend/scripts`は0件。
  依頼時の「約35件」は`osm_node`の部分一致（列名`osm_node_id`・`read_osm_nodes`等を含む）で、
  生データを読む行は上の7件だけだった。
- 名前が直接出ない形の検算: `grep -rnE "source *= *([$][0-9]|:[a-z_]+|'[{])"`で、ソースを引数・
  f文字列で渡す読み手を出した。4件で、どれもノードの生データを読まない——
  `derive_node_materials.py`・`derive_topology.py`の`_latest_run`（FROM `source_runs`＝取込記録）、
  `derive_raster_materials.py: _tiles`（呼び出しは`"dem"`・`"lulc"`だけ）、`derived_data_freshness.py`
  （下記）。このgrepがf文字列の形を拾えることは、既知の`_tiles`が出たことで確かめた。

### 寄せた先

`material_sql.py`へ`NODES_SOURCE_SQL`（全件）と`nodes_lookup_sql(key_expr)`（キー1件、照合はtext）を
足した。読み手ごとの形:

| 読み手 | 形 |
|---|---|
| `derive_node_materials.py: _source_nodes`（種別・信号ノード） | `NODES_SOURCE_SQL`（全件を流す段） |
| `derive_node_materials.py: _UPDATE_SIGNALS`（信号の近傍） | `NODES_SOURCE_SQL`（空間索引で絞る） |
| `derive_counts.py: _CLUSTER_SQL` | `nodes_lookup_sql('nm.osm_node_id')` |
| `road_graph_repository.py: _POI_TILE_MVT_SQL` | `NODES_SOURCE_SQL`を空間索引で絞り、`node_materials`を主キー（bigint）で引く向きへ入れ替えた |
| `road_graph_repository.py: _EDGE_MATERIAL_ARRAYS_FROM`（区間の両端） | `nodes_lookup_sql('re.from_node_id')`・`('re.to_node_id')` |
| `road_graph_repository.py: _TOPOLOGY_NODES_SQL` | `unnest(:node_ids)`＋`nodes_lookup_sql`。idをtextへ直す仕事が呼び出し側（`str(i)`）からSQL側へ移った |

寄せたあと`source *= *'osm_node'`のヒットは`material_sql.py`の2行（`NODES_SOURCE_SQL`・
`nodes_lookup_sql`）だけ。`source_runs`を引く行は`$1`で渡すためこのgrepには出ない（上の検算で判定済み）。

### `derived_data_freshness.py`の`f.natural_key::bigint`は寄せない

被覆の母数を数える汎用の台帳で、ソースは表の宣言（`covers(...)`）から来る。今`covers`を宣言している
のは`osm_way`だけで、ノードの生データは読まない。寄せるなら「ソース名→キーの読み方」の対応を
`material_sql.py`に持たせることになるが、読み手が1本で、宣言されたソースのキーはどれもOSMのid
（bigint）である。ノードを母数にする表が宣言されたときにも、この1行はそのまま成り立つ。
