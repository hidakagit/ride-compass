# T964. PostGIS統合テストが、並行セッション間で同じDBを共有している 規模S

状態: 完了（2026-09-19起票・2026-09-20完了、T950の完了検証で4件が偽の失敗を出したことから）

## 背景

`backend/tests/conftest.py`の`TEST_DATABASE_URL`が既定で単一のDBを指すため、同じ作業ツリー
群で動く複数のセッションが同じ行を同時に書き換える。落ちるのはテストの中身と無関係な
ファイルで、単独実行では通る。

[T950](T950.md)の完了検証で実際に起きた姿:

| | 結果 | 所要 |
|---|---|---|
| `pytest -m postgis`（並行セッションが稼働中） | 323 passed / **4 failed** | 6分15秒 |
| 落ちた4件だけを単独で再実行 | 4 passed | **7秒** |

落ちたのは軸レジストリ2件・事故取込1件・道路ノード次数1件で、そのとき触っていた範囲
（`scripts/`・`backend/benchmarks/`・コメント1行）とは接点が無い。同種の誤読は以前にも
起きている——「単体実行でも失敗する」という報告がコードのバグではなく共有DBの競合だったと
判明した事例があり、4プロセス同時実行で再現も取れている。

**害は「たまに落ちる」ことではなく、落ちた側が毎回それを切り分けさせられること。** 偽の
失敗は自分の変更を疑う時間を必ず消費し、切り分けを飛ばせば逆に本物の回帰を「どうせ競合」と
見送る。落ちるファイルが変更と無関係なぶん、どちらの誤りも起きやすい。

## 調べた事実（2026-09-19）

- 接続先を決めているのは`backend/tests/conftest.py`の`TEST_DATABASE_URL`**1箇所だけ**。
  PostGIS統合テスト22ファイルはすべてそこからimportしており、URLを自前で組み立てている
  ファイルは無い（`grep -rn TEST_DATABASE_URL backend scripts`）。
- 既に環境変数`TEST_DATABASE_URL`で上書きできる。分離する仕組みが無いのではなく、
  **既定値がセッション間で同じ**ことだけが問題。
- テーブル作成は`road_graph_engine`フィクスチャが`CREATE EXTENSION postgis`＋
  `Base.metadata.create_all`でモジュール単位に行う。

## 対応（2026-09-20）

**既定のDB名を作業ツリーの場所から導く**（`ridecompass_test_<ディレクトリ名>_<絶対パスの
ダイジェスト>`）。同じ作業ツリーでは同じDBを再利用するので、作成の費用は初回だけ。
`TEST_DATABASE_URL`を明示したときの挙動は変えていない（CIはこの経路）。

### 定数ではなく関数にした理由

行き先は**用意を試みるまで決まらない**（作れなければ共有DBへ退避する）ため、
`TEST_DATABASE_URL`という定数を`postgis_database_url()`へ置き換え、22ファイルの参照を
機械的に差し替えた。用意そのものは`pytest_collection_modifyitems`で1回だけ行う——
**同期のまま・イベントループの外で・PostGISテストが選ばれているときだけ**実行できる
唯一の場所だから。`-m "not postgis"`の実行には接続を1本も足さない（ローカルの接続確立は
1回0.6秒で、import時に無条件で繋ぐ設計は取れない）。

名前を`test_`で始めていないのは、pytestがテスト関数として収集してしまうため（最初の実装で
実際に収集され、`PytestReturnNotNoneWarning`が出た）。

### 拡張はテンプレートから複製して持ってくる

空のDBを作っても`CREATE EXTENSION postgis`はsuperuserを要求する（postgisはtrusted拡張では
ない）ため、**拡張を持つDBを複製する**形にした。`ridecompass_test`を複製元として
`ridecompass_test_template`を1回だけ作り、以後はそこから複製する。複製元に残っていた
アプリ側の表は**複製した側で**落とす——複製元で掃除すると、その途中の姿を別のセッションが
複製しうる。落とす対象は名前で並べず、拡張が持ち込んだ表（`spatial_ref_sys`等）でないことを
`pg_depend`から導く。

### 同時に用意しようとしたとき

PostgreSQLは`CREATE DATABASE`の競争に負けた側へ、宣言的な42P04（duplicate_database）では
**なく**23505（unique_violation）を返すことがある。片方だけを捕まえていたため、2セッション
同時の実測で片側が共有DBへ退避していた（1回目の実測で発覚し修正）。複製元が使用中のとき
（`ObjectInUseError`）は短く待って試し直す。

### 権限が無い環境

ロールに`CREATEDB`が無ければ共有DBへ退避し、その旨と付け方を1行出す。**分離されないだけで、
PostGISテストが走らなくなることはない。** 環境ごとに何が要るかは
[docs/conventions/testing.md](../../conventions/testing.md)「テストDBは作業ツリーごとに分かれる」にある
（開発機は1回だけ`ALTER ROLE ridecompass CREATEDB;`、CIと本番は何もしない）。

### 残骸の片付け

作業ツリーを消してもDBは残るため`backend/scripts/drop_orphan_test_databases.py`を置いた
（docs/conventions/caching.md「世代番号を使うなら、旧世代を削除する導線をセットで用意する」と同じ形）。
**どのDBがどの作業ツリーのものかはDB自身のコメントに書く**——名前から推測しない。
コメントが絶対パスでないもの（テンプレート・この仕組みより前に手で作られたDB）は判定の
対象から外す。既定は一覧だけで、`--drop`を付けたときだけ落とす。

## 検証

2つ目の作業ツリーを一時的に作り、**同じPostGISテストを両方で同時に実行**した
（`tests/test_precompute_road_node_degrees.py` + `tests/test_axis_registry_service.py`、各43件）。

| | A（既存の作業ツリー） | B（2つ目） |
|---|---|---|
| 対照: 両方を同じDBへ向ける | **15 failed** / 28 passed | **14 failed** / 29 passed |
| 本タスク後: 既定のまま（各自のDB） | **43 passed** | **43 passed** |

対照は`TEST_DATABASE_URL`で共有DBへ向けて取った。**片側だけの成功を根拠にしない**という
完了条件のため、同じ組み合わせで両側を測っている。

残骸の片付けも実地で確かめた: 2つ目の作業ツリーを`git worktree remove`した後、
スクリプトがそのDBだけを「残骸」と判定し、`--drop`で落とし、使用中のDBとテンプレートは
残った。

全体: backend `ruff check app scripts benchmarks tests` クリーン、
`pytest -q -m "not postgis"` 2,127 passed、`pytest -q -m postgis` **327 passed**、
`python scripts/review_checks.py docs` 違反なし。frontendは変更なし。

**所要も併せて記録する**——起票のきっかけになった実行（共有DB・並行セッション稼働中）は
323 passed / 4 failed で6分15秒だったのに対し、分離後は327件すべて通って**1分14秒**。
偽の失敗が消えただけでなく、同じDBを奪い合わなくなったぶん所要が5分の1になった。

## 完了条件

- [x] 既定で、別々の作業ツリーから同時に`pytest -m postgis`を走らせても互いに落とさない
  （2セッション同時実行で実測する。片側だけの成功を根拠にしない）
- [x] 増えたDBを落とす手段があり、その手順が書かれている
- [x] `TEST_DATABASE_URL`を明示したときの挙動は変わらない

## 扱わないもの

- devポート・CPU/IOの共有。これらも並行セッション間で奪い合うが、**遅くなるだけで偽の
  失敗にはならない**ため、このタスクでは触らない。
- xdistのワーカーごとの分離。DBを分ける軸が違う（作業ツリー単位 vs ワーカー単位）。
  postgisを並列化しても速くならない実測は[docs/conventions/testing.md](../../conventions/testing.md)にある。
