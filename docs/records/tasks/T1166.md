# T1166. スロットを渡すたびに走るnpm ci（平均6.8分）が、振り出しの時間に乗っている

状態: 完了（2026-09-26）

## 背景

2026-09-23〜26の重い処理の枠の記録（.git/lockrun/log.jsonl）で、スロットを渡すときの `npm ci` は14回・保持96分・1回平均6.8分（最大526秒）。2026-09-26の第3回では、最初の担当（T1134）を渡すときに package-lock.json が前回から変わっていたため506秒かかり、その間は担当が着手できず、枠も塞いだ。今は WorktreeCreate フックが渡すその場で、前回の印（frontend/node_modules/.slot-package-lock.sha1）と違えば npm ci を走らせる（slots.py）。直す方向: masterの package-lock.json が変わった時点（取り込み・定期確認）で、空いているスロットを先に温めておき、渡すときには走らない形にする。効いたかは、package-lock を変えたあとの振り出しで、渡してから担当の最初の道具の呼び出しまでの時間で確かめる。T1163（取り込んだスロットの渡し直し）と同じ slots.py を触る。第3回の改善（派生元 T1162）。

## 着手時の確認

- 前提（`slots.py`の`ensure_deps`が渡すその場で印と`package-lock.json`のsha1を比べて`npm ci`を走らせる、WorktreeCreateフックは本体の`scripts/orchestrate.py slot hook-create`を時間切れ1800秒で呼ぶ）はorigin/master（6bbe597e、T1163の後）で成り立っていた。
- 着手時点の実物: slot-1〜3の3本とも担当に渡されていて、3本の印はorigin/masterの`package-lock.json`と同じだった。空いたスロットで本物の`npm ci`を走らせる確認はできないので、一時的なリポジトリで1回だけ行った（下の検証）。

## 対応

- 温める処理（`slot warm`）: 空いている（印の無い）作成済みのスロットのうち、依存の印がorigin/masterの`package-lock.json`と違うものに`slot warm-<pid>`の印を付け、最新のorigin/masterへ作り直して`heavy`の枠で`npm ci`し、印を外す。担当に渡しているスロットと、渡し直しを止める条件（未コミットの変更等）に当たるスロットには触らない。作っていないスロットは作らない（作るのは渡す側）。
- **どこで起こすか: 定期確認（`check`）が裏で起こす。** `check`は冷えた空きスロットがあれば`slot warm`を切り離したプロセスで起こし、「スロットの温め: …」の1行だけを出して待たずに返る。理由: `npm ci`は枠の待ちを含めて10分を超えうるので、同期で走らせると確認の結果が返らず次の確認も止まる。取り込みの手順に1行足す案は司令塔の注意に頼るうえ、master を変えるのは取り込みだけではない（手動のセッションのpush）。`check`は確認間隔ごとに時間で回るので、masterの`package-lock.json`がどの経路で変わっても次の確認で温まる。起こした処理の出力は`<orchestrationディレクトリ>/warm.log`（起こすたびに上書き）。
- 渡す側（`hook-create`）: 温めている途中のスロットしか空いていなければ、温め終わるのを最長1200秒（フックの時間切れ1800秒より短い）待ってから渡す。温める処理が死んで印だけが残ったら（pidのプロセスが無い、またはそのpidのコマンドラインが温めのものでない）、印を外して渡す。
- `slot list`に、スロットの依存がorigin/masterと同じか（渡すとnpm ciが走るか）を出す。
- 定期確認はorigin/masterの版の道具（`<gitの共通ディレクトリ>/orchestration/tools/<sha>/`）で走るので、書き出す道具に`scripts/lockrun.py`を足した（温める処理が枠を取るため）。
- 状態の表（board.json）の形は変えていない。温めの印は`git worktree lock`の理由だけに持つ。
- 規約`docs/conventions/orchestration.md`の「起動のしかた」「作業ツリーのスロット」「重い処理を減らす」の`npm ci`の文を直した。
