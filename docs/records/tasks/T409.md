# T409. axis_definitions.display_override列の削除

状態: 完了（2026-08-30）

- 背景: T404でcar_stress/stop_density/accidentの3軸（従来display_overrideを使っていた
  唯一の利用者）をdisplay_thresholds_overrideへ移行し、3軸ともdisplay_overrideはNULLへ
  戻し済み。`domain/axis_definitions.py: AxisDefinition.display_override`・
  `domain/axis_display.py: axis_display_for()`のフォールバック分岐・DBカラム
  （`axis_definitions.display_override`）・`AxisDefinitionRow.display_override`・
  `axis_definition_repository.py`の(逆)シリアライズ・`axis_admin.py`のPayload/Response
  フィールドは、いずれも非推奨のまま残っている（後方互換のセーフティネットとして
  意図的に残置、T404参照）。実際に不要になったことを確認したうえで、コード側の
  フィールド・DBカラムを削除する。
- 完了条件（想定、着手時に精査すること）:
  - dev DB・本番DBの`axis_definitions`テーブルで、全行の`display_override`がNULLである
    ことを確認する。
  - `AxisDefinition.display_override`・`AxisDisplaySpec`（`registry.py`、他に利用者が
    無ければ）・`axis_display_for()`のdisplay_override分岐・`axis_admin.py`の
    `display_override`フィールド（Payload/Response両方）・`AxisDefinitionRow.
    display_override`・`axis_definition_repository.py`の対応する(逆)シリアライズを削除。
  - DBカラム自体の削除はCLAUDE.mdの「axis_definitionsテーブルの構造変更（DDL）は
    backend/migrations/で行う」原則に従い、新規migration（`ALTER TABLE axis_definitions
    DROP COLUMN display_override`）を追加する。
  - OpenAPI再生成（`export_openapi.py`→`npm run generate:api`）、フロント側で
    `display_override`を参照している箇所（`AxisComposer.tsx`のdraft.displayOverride
    素通し保持等）があれば削除する。
  - `tests/realistic_axis_fixtures.py`・関連テストからdisplay_override参照を削除。

## 本番反映

- コード側の変更（backend/frontend）は本コミットに含まれる。migrationファイル
  （0026）もコミットに含まれるため、pushすると`.github/workflows/deploy-backend.yml`が
  本番へ自動デプロイする。
- 本番DBへの`DROP COLUMN`適用は、CLAUDE.mdの「既存DBの行データを新しいコードが
  読めなくなる変更を含むbackend変更は、本番DBのデータ移行を完了させてからpush」の
  対象として意識しておくこと——ただし本migrationは全行NULLの列を削除するだけで
  データ損失は起きず、新コード（display_overrideを一切読み書きしない）は移行前の
  本番DB（カラムがまだ残っている状態）に対しても問題なく動作する（余分な列がある
  だけで、SQLAlchemyのORM層は未知の列を無視する）。そのため理論上は本番DBへの
  適用より先にpushしても即座に壊れることは無いはずだが、**実際に本番DBへ
  migration 0026を適用するタイミング（pushと同時か、別途SSHで後日か）は
  ユーザー判断に委ねる**（このセッションでは本番DBへの接続情報を持たないため、
  適用そのものを行っていない）。
