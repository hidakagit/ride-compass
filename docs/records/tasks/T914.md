# T914. 標高の面レイヤが、勾配の無い所まで塗りつぶす

状態: 完了（2026-09-17）
規模: M

## 背景

ユーザー指摘「標高図とか常時色付きのものを見ると前より違和感ある。基礎地図の土地の色が
なくなってしまってるから」。

面レイヤの規則「値のある所だけ塗る」（[T913](T913.md)で整理）に照らすと、標高図
（国土地理院 色別標高図）だけが全画素を無条件に塗っている。東京の低地では一様な色になり、
基礎地図の土地の情報を消すだけで坂の在りかは出ない。

**不透明度を動かしてきたのは、この違反を濃さで埋め合わせようとしていたからである**。
共通の1値が「全面を覆う側の都合」に引っ張られ、そのたびに降水の薄い色が巻き添えになった
（0.65→0.4→0.32→0.7→0.55）。

## 対応

**起伏（陰影）を別のレイヤーとして足す。** 地理院の標高タイル（DEM）から傾きを取り、
斜面にだけ陰影を乗せる。MapLibreの`hillshade`は傾きが0の画素を透明にするため、平地では
基礎地図の土地の色がそのまま残る。

**色別標高図は残す**（ユーザー判断）。「この場所が何mか」と「どこに坂があるか」は別の問いで、
前者を見たいときは土地の色が塗り替わるのがそのレイヤーの目的そのもの。チップを
「標高図」「起伏」の2つに分け、名前で何が出るかを区別できるようにした。

### 配信元のエンコードは変換が要る

地理院はセンチメートル単位の符号付き整数を2の補数で置き、標高が無い画素へ決め打ちの値
（2^23）を入れる。MapLibreの`raster-dem`が読むTerrain-RGBは-10000mを原点とする0.1m刻みの
符号なし整数で、無効値の表し方を持たない。MapLibreの`custom` encodingでは2の補数も無効値も
扱えないため、backendで変換する（`domain/terrain_rgb.py`、純関数）。

**無効値は海抜0mへ倒す**。そのまま大きな数として渡すと、標高のある画素との境界がすべて
数万メートルの崖になり、陰影が黒い縁で埋まる。

変換後のタイルはキャッシュしない。ネットワークを使うのは変換前の取得だけで、そちらは
`GsiTileClient`がディスクへ持つ。

### 名前を実態へ合わせた

`GsiReliefTileClient`は色別標高図の名前だったが、標高タイルも同じプロキシを通るため
`GsiTileClient`（`gsi_tile_client.py`）へ改めた。製品ごとの解釈は持たず、パスで指定する
だけのプロキシであることが名前に出る。ルーター・依存・設定値・テストファイル・
文書の参照も揃えた。

## 効いていることの確認

- 変換を経路から外す（`return content`に戻す）と、復号して値を照合するルートテストが
  1件だけ落ちる。戻すと8件とも通る。
- 影・光の色から共通の濃さを外す（素の色にする）と、起伏のレイヤー登録のテストが1件落ちる。
- 変換の単体テストは、0m・12.34m（0.1m刻みへ丸める）・3776m・海面下（2の補数）・無効値・
  タイルの大きさと画素の並びを固定した。
- backend: `pytest -q -m "not postgis"`＝2,038件passed／5件failed。5件は変更前でも同じ
  ように落ちた。**このときの「依存のバージョンが揃わない」という説明は誤りだった**
  （実際の内訳は下記「この環境の失敗の正体」）。`ruff check app scripts
  benchmarks tests`＝All checks passed。`-m postgis`はDBが無く未実行。
- frontend: `npx vitest run`＝1,420件passed、`npx eslint src`＝rc 0、`npx tsc --noEmit`は
  `src/app/layout.tsx:31`の`LayoutProps`のみ（`.next`が無い環境で変更前から出る）。
- 生成物: `export_openapi.py`はDB接続が要るためこの環境では走らない（軸定義をDBから読む）。
  DB接続を要しない`app.openapi()`だけを出力して現行と突き合わせ、**差分が
  `/api/gsi-terrain-tile/{z}/{x}/{y}.png`の1パスだけ**であること（`ValidationError`
  スキーマの差は環境のFastAPI/pydanticのバージョン由来）を確認したうえで、その1パスだけを
  `openapi.json`へ入れ`npm run generate:api`をかけた。

## 後から見つかった漏れ: キャッシュポリシーの対応表

新しいエンドポイントを足したのに`api/cache_policy.py`の`_ROUTE_POLICIES`へ1行足すのを
忘れており、masterのCIが赤になった（`test_every_route_has_a_cache_policy`）。

**この実行環境ではこの失敗が見えなかった。** 入っていたFastAPIが`requirements.txt`のピン
（0.115.6）より新しく（0.141.1）、included routerが`app.routes`の下でネストされるため
アプリのルートが1本も見えなかった。対になるテスト
（`test_every_policy_entry_matches_a_real_route`）が対応表の全エントリを「どの実ルートにも
一致しない」と報告する側だけが落ち、「ポリシーの無いルート」の側は母集団が空のまま
素通りしていた。**同じファイルの2本のテストのうち、環境が壊している方だけを見て
「環境起因」と片付けると、もう片方が隠す本物を見落とす。**

## この環境の失敗の正体（後から特定した）

このタスクを含むセッション中、落ちる11件をすべて「rasterioのピンがPython 3.11と合わない」
と説明していた。**誤りだった。** 依存を揃えて確かめた内訳:

| 失敗 | 実際の原因 | 直し方 |
|---|---|---|
| `test_precompute_way_landcover`系7件 | `pyproj`が入っていないだけ（`requirements-batch.txt`側の依存） | `pip install pyproj` |
| `test_admin_route_authorization`・`test_cache_policy`各1件 | FastAPIがピンより新しくルートが`app.routes`から見えない | ピン（0.115.6）へ揃える |
| `test_evaluation_bulk`2件 | numpy 2.5.2がPython 3.12以上を要求し、2.4.6で浮動小数の丸めが変わる | この環境では直せない |

揃えた後は`pytest -m postgis`が289件全passになる（「6件は環境起因」という報告は事実と
違った）。`requirements-batch.txt`は`-r requirements.txt`を内包するため丸ごとは入らない
（rasterioのピンがPython 3.12以上を要求する）が、足りない依存を個別に入れれば揃う。

ポリシーは色別標高図（`/api/gsi-relief-tile/`）と同じ`PERMANENT`にした——同じ国土地理院の
DEMタイルを決定的に変換して返すだけで、配信元は更新しない。
