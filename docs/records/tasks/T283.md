# T283. `road_graph_use_repository`設定の名称・既定値の再考〔P3〕規模S — トリガー: 次のconfig.py変更のついで、または新環境構築時

状態: 完了（2026-08-29）


- 背景: レビュー指摘（レポートF-6）。T222（DBなし構成撤去）・T247（road_graph既定化）を
  経て、この設定の実質的な意味は「地図レイヤー（路面/POI/事故タイル）・標高キャッシュ・
  ORSエンジン路面評価のDB利用」フラグへ変わったが、名称は旧来のまま。既定`False`のため
  本番・新環境で設定を忘れると**ルート生成は動くのに地図レイヤーがすべて空**という
  気づきにくい縮退になる（既定エンジンがDB必須になった今、「DBはあるのにこのフラグだけ
  False」という中途半端な状態が最頻の罠）。
- 内容: 名称変更（例: `map_layers_use_db`等）または既定値`True`化（DB接続失敗時は既存の
  空タイルフォールバックが効くため安全側は保てる）を比較し、どちらかを実施する。
  `.env.example`のプロファイル表も追従する。
- 完了条件: 変更の実施＋.env.example追従＋architecture.md該当箇所の更新。

## 対応結果（2026-08-29）

名称変更（`map_layers_use_db`等）と既定値`True`化を比較し、**既定値`True`化**を採用した
（レビュー指摘の核心は「既定Falseによる気づきにくい縮退」であり、改名だけではこのリスクは
解消しない。改名はさらに`.env.example`・本番/開発の`.env`・docs全体の参照箇所を広く
書き換える必要がありリスク・作業量が見合わないと判断した）。

- `backend/app/config.py`: `road_graph_use_repository`の既定値を`False`→`True`へ変更。
  DB接続失敗時は既存の空タイルフォールバック（`vector_tile.py: encode_empty_road_surface_tile`
  等）が効くため、DBが無い環境でも既定Trueのまま安全側に倒れる（単に空タイルが返るだけで
  クラッシュしない。`get_session_factory()()`はSQLAlchemyの遅延接続のため、セッション生成
  自体は接続失敗しない）ことをコードで確認済み。
- `backend/.env.example`: 「開発（DBなし）」プロファイルは引き続き明示的に`false`を書く
  （このプロファイルはコード既定のtrueと異なる値を意図的に選ぶため、明示が必須である旨を
  コメントへ追記）。
- `docs/architecture.md`: DB行（19行目付近の表）へ既定値変更の経緯を追記。
- 影響確認: 本番・ローカル開発（ネイティブPG）の`.env`はいずれも既に明示的に`true`を
  設定済みのため無変更で影響なし。CI（`ci.yml`）はこの環境変数を明示せず実質コード既定値に
  委ねているが、`road_graph_use_repository`を参照する5テストファイル
  （test_accident_service.py・test_dependencies.py・test_health.py・
  test_material_catalog_routes.py・test_region_service.py）はいずれも`monkeypatch`または
  `dependency_overrides`で明示的に値を制御しており、既定値変更の影響を受けないことを
  ソース確認済み（test_material_catalog_routes.pyは2026-08-28に同種の環境依存問題を
  一度踏んで修正済みの実績あり）。
- 検証: backend `pytest -q -m "not postgis"` 1386件成功、`test_road_graph_repository.py`
  単体100件成功（いずれも既存の全件green、既定値変更前の1389/103からT394の3テスト削除
  ぶんを差し引いた件数と一致）。
