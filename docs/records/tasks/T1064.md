# T1064. 本番とCIのGEOS・PROJをPGDGの版へ上げ、土地被覆を作り直す

状態: 未完了（2026-09-23起票）

## 背景

ユーザー決定（2026-09-23、判断D-019）: 本番DBのGEOS・PROJを、Ubuntu標準の版（GEOS 3.12.1・PROJ 9.4.0）からPostgreSQL公式リポジトリ（PGDG）の版（GEOS 3.14.1・PROJ 9.8.1）へ上げる。本番の一時停止は許容（D-015と同じ扱い。ユーザー「本番一時的に止まっても問題ない」）。

事前の調査（公式のNEWSとpostgis.net/docsを突き合わせ、2026-09-23）: 変わりうる経路は backend/app の derive_raster_materials.py の土地被覆の帯（ST_Buffer(geography) 100m−10m と ST_Difference）だけで、GEOS 3.12.2〜3.13.1 の buffer 修正（GH-995・1056・978・1200・1233）と交点計算（GH-937）が届く。区間の長さ・距離・方位（geographyの測地計算）・タイルの線と点・ST_ClusterDBSCAN・4326→3857変換には届かない。3.13.0 の「長さ0の線を点として扱う」は、本番の road_edges 2,582,177件に長さ0が0件（run_probe.py で実測）のため届かない。T1061 で CI は本番と同じ版（GEOS 3.12.1・PROJ 9.4.0）を /noble 指定で入れている。

手順（順序を守る）:
1. 変更前の記録（本番、読み取りのみ）: SELECT postgis_full_version()、edge_materials の lc_* 各列について件数・平均・分位点、比較用に固定した区間のサンプル（例: 区間idで1万件）の lc_* を取って残す。
2. CI を新しい版へ: ci.yml の GEOS・PROJ の /noble 指定を外し、PGDG の版が入ることを作業ブランチ（orch/**）の CI の注釈「DB」で確かめる。全件が通ること。docs/architecture/tech-stack.md の「DBの版（本番が正本）」節の版を更新する。master へはまだ入れない。
3. 本番を上げる: apt で libgeos・proj（PostGIS が依存するパッケージ）だけを PGDG の版へ上げる。PostgreSQL を再起動し、SELECT postgis_full_version() で GEOS 3.14.1・PROJ 9.8.1 が読み込まれていることを確かめる。backend の /health と、ルート生成・タイル1枚が通ることを確かめる。
4. 2 の CI 変更を master へ入れる（本番と CI の版が揃った状態にする）。
5. 土地被覆を作り直す: 本番で derive_raster_materials を回し直し、1 のサンプルで lc_* の新旧を比べる（変わった区間の数・差の最大と分布）。見込みを大きく超える差（例: 1区間で数%以上）があれば、その区間の帯の形を ST_HausdorffDistance・ST_Area(ST_SymDifference) で調べて報告する。
6. 開発機（Windows、PostgreSQL 18.6・PostGIS 3.6.2）の版は本タスクの範囲外。差を tech-stack.md に書く。

完了条件: 本番と CI の postgis_full_version の GEOS・PROJ が一致（3.14.1・9.8.1）、本番の /health・ルート生成・タイルが通る、lc_* の新旧比較が記録にある、tech-stack.md が新しい版を正本として書いている。

## 性能の新旧比較（ユーザーの関心の中心、2026-09-23 追記）

ユーザー「どちらかというと、レスポンス改善があったか？が知りたい」。版を上げる前と後で、
**本番で、同じ条件で**次を測り、表にする（CLAUDE.md「性能は利用者から見た単位で測る」。
開発DBでは測らない）。

| 測るもの | 利用者から見た単位 | 測り方 |
|---|---|---|
| ルート生成 | 応答時間 | 出発点・距離を固定した代表の要求（周回と目的地の両モード、短・長の距離）を各5回以上。キャッシュの効き方を揃える（1回目を捨てるか、冷たい状態を揃える）。backendの1行INFOサマリのステージ別所要も添える |
| 地図タイル（道路・事故・POI） | 1枚の生成時間 | 代表のz/x/yを数十枚、タイルのキャッシュを通らない経路で生成し、所要を比べる。バイト列のハッシュも新旧で比べ、同じか違うかを記録する（違えば件数） |
| 土地被覆のバッチ（derive_raster_materials） | バッチ全体の所要 | 上の手順5の作り直しの所要を、変更前に同じ範囲で1回測ったものと比べる |

呼び出しの経路から見た事前の見立て（未計測）: ルート生成の重い部分はメモリ上の探索で、DBの
距離・近傍計算はgeographyの測地計算なのでGEOSを通らない。タイルでGEOSを通るのは、枠から
はみ出す線のクリップ（GEOSClipByRect）だけ。GEOSを最も使うのは土地被覆のバッチ。したがって
利用者の応答への効果は小さく、差が出るならバッチと見ている。**この見立てと実測がずれたら、
結論より先にずれを報告する**（CLAUDE.md「見積もりとずれたら」）。
