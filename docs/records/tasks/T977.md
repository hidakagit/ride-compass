# T977. 地図の説明文がデータの収録範囲をベタ書きしていて、実データと食い違う 規模S

状態: 完了（2026-09-20起票、2026-09-21完了）

## 背景

`frontend/src/components/Map/mapLayers.ts` の事故レイヤーが、収録年を文字列でベタ書きして
いた。

```
description: "警察庁交通事故統計オープンデータ[関東7都県、2022〜2024年]の発生地点を表示"
panelHint:   "…[本票、関東7都県・2022〜2024年]の発生地点です。…"
```

実データは**2024年のみ**（108,409件）。`source_profile.yaml` が `years: [2022, 2023, 2024]`
と宣言していたのに取り込み直していなかったためで、利用者には3年ぶんあるように見えていた。

正しい値はDBにある。`source_runs.profile` が取込時の宣言を丸ごと持っており、
`RoadGraphRepository.get_accident_years_covered()` はそこから年数を数えている（だから
`accident_count_per_km_year` の正規化は壊れていなかった）。**UIだけが二重に持って、
ずれていた。**

取込対象は2024年度のみへ揃えた（2026-09-20、ユーザー判断）。

## やること

### (a) 嘘の除去（対応済み）

2箇所の「2022〜2024年」を「2024年」へ直す。

**母集団は「その年の配布ファイル」で定義する。** 警察庁の配布単位は暦年（ページの表記は
「２０２４年（令和６年）」、ファイルは「本票_01-12月」）であって年度ではないので、
「2024年度」と書くと4月〜翌3月を指してしまい提供元の単位とずれる。

母集団をファイルで定義すれば、点レイヤーと密度は同じ母集団を見るので符合する。点を
発生年で絞ると、点が密度の母集団の部分集合になって**かえって符合が壊れる**。

### (b) 構造の対応（残り）

ベタ書きのままだと、来年のデータへ入れ替えた瞬間にまた食い違う。年は
`source_runs.profile` を正本として、UIへ配る。

経路の候補: 軸カタログは既にフロントが実行時に取得しており（`page.tsx` の
`useAxisCatalog()`）、backend側の `axis_catalog.py` は同じ `get_accident_years_covered()`
を呼んで `material_runtime_scales` を組み立てている。ここへ収録年そのものを載せれば、
新しい口を作らずに済む見込み。ただし `mapLayers.ts` の `description` / `panelHint` は
静的な設定オブジェクトのため、実行時の値を差し込む形へ変える必要がある。**そこの設計が
このタスクの本体。**

変更したら[CLAUDE.md](../../../CLAUDE.md)「コミット時の同期ルール」に従い、
`export_openapi.py` → `npm run generate:api` を同一コミットで行う。

### (c) 未確認の記述

同じ `panelHint` に次の一文がある。

> 2019〜2021年は本票のCSV形式が異なるため未対応です。

**この主張は確認していない。** 警察庁のオープンデータ index は2019年以降を掲載している
が、2019〜2021のファイル定義書は2022年以降と同じURL形式（`.../<年>/fileteigisyo_<年>.xlsx`）
には無く、突き合わせていない。2022〜2024は68列で完全に同一であることは確認済み。

(b)に着手する際、この一文の裏を取るか、取れないなら消すこと。**確認していない主張を
利用者へ出し続けない。**


## (b)の対応（2026-09-21）

**年の正本を取込の宣言1箇所にし、表示はそれを受け取るだけにした。**

- `RoadGraphRepository.get_accident_years()`が`source_runs.profile`の`rows.years`を
  そのまま返す。`get_accident_years_covered()`（分母）は`len()`で導く——同じ値を2本のSQLで
  持たない。
- `RegionService.get_accident_years()`が同じ方針（DB例外は空へ倒す）で運び、
  `GET /api/axis-catalog`が`accident_years`として配る。`material_runtime_scales`も
  この年数から作る（既存のキャッシュ経路＝探索用の年数は触っていない）。
- `buildMapLayers(rampAxes, dedicatedAxes, accidentYears)`が説明文を組み立てる。
  年の言い方は`coverageYearsLabel`——1年ならその年、続いていれば範囲、飛んでいれば並べる。
  **取れていないときは年に触れない**（取得前に既定の年を出すと、それが正しく見える）。

## (c)の確認

「2019〜2021年は本票のCSV形式が異なるため未対応です」は**現物に無い**
（`grep -n "未対応" frontend/src/components/Map/mapLayers.ts` → 0件）。(a)で年を直した
ときに一緒に消えている。裏を取る対象そのものが無くなったため、これ以上は追わない。

## 検証（2026-09-21）

- 開発DB: `SELECT profile->'source'->'rows'->'years' ...` → `[2024]`
- `GET /api/axis-catalog` → `accident_years: [2024]`、
  `material_runtime_scales: {'accident_count_per_km_year': 1.0}`
- 実機（開発サーバー・Chromium 1280×900、地図の「スポット」を開く）: 事故チップの
  説明文が `警察庁交通事故統計オープンデータ[関東7都県、2024年]の発生地点を表示[設定は▶から]`。
  **DBの値と一致**。なお`panelHint`側（「表示する項目を選ぶ」パネルの個別ⓘ）はこの操作では
  導線が開けず、実機では見ていない——同じ`accidentCoverage`から作るため文面は一体。
- `tests/test_region_service.py` 10件（年を配る／年数は年の数から導く／DB例外は空）、
  `src/components/Map/mapLayers.test.ts` 5件（1年・連続・飛び・順不同・空）。
- `tsc --noEmit`・`ruff check` クリーン。OpenAPIとAPI型を再生成済み。

## 一般化の確認

`mapLayers.ts`の`description`/`panelHint`を機械的に見た
（`grep -nE "[0-9]{4}年|[0-9]+件|[0-9]+都県|未対応"`）。年・件数のベタ書きは事故レイヤー
だけだった。ただし**範囲の「関東7都県」は残っている**——これもDB（取込のbbox）に正本が
あるが、bboxから都県名は機械的に導けない（対応表が要る）。[T991](T991.md)へ分けた。

## 完了条件

- 収録年の表示が `source_runs.profile` に由来し、再取込で自動的に追従する
- 実機の地図でⓘを開き、表示された年が `SELECT profile->'source'->'rows'->'years' FROM
  source_runs WHERE source='accident' ORDER BY run_id DESC LIMIT 1` と一致することを確認する
- (c)の一文が、裏の取れた記述になっているか消えている
- `git diff --exit-code -- frontend/src/types/generated/` がクリーン

## 一般化

同じ形（**DBに正本があるのに、UIが文字列で二重に持つ**）が他のレイヤーにもないかは見て
いない。`mapLayers.ts` には各レイヤーの `description` / `panelHint` が並んでおり、データの
範囲・件数・更新時期に触れている記述は他にもありうる。(b)の設計を決めるときに一度だけ
全レイヤーを見ること。
