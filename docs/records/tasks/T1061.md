# T1061. CIとdocker-composeのDB・実行環境を本番の版とアーキテクチャに揃える

状態: 完了（2026-09-23）

## 背景

CI（GitHub Actions）と docker-compose が、本番と違う版のDBで合否を決めている。2026-09-23の実測（本番は run_probe.py --in-container で select version()・postgis_lib_version()、開発機は backend/.env の DATABASE_URL へ同じ問い合わせ）: 本番 PostgreSQL 18.6（aarch64）・PostGIS 3.6.4、開発機 18.6・3.6.2、CI と docker-compose.yml は postgis/postgis:16-3.4（PostgreSQL 16・PostGIS 3.4）。CIは本番より2つ古いメジャー版で PostGIS 統合テストを判定しており、関数・プランナーの挙動差があれば CI で通って本番で違う形になりうる。同じ日に「開発機（Windows）で通ったテストが Linux の CI で落ちる」（T1020のテスト、08fef74a で修正）が起き、判定する環境を本番に揃えることが根本対策とユーザーと確認した。T1058 で作業ブランチでもCIが走るようになったため、CIの判定がmasterへの門の中心になっている。ほかの版: Python は CI（setup-python 3.12）と本番（backend/Dockerfile の python:3.12-slim）で一致。Node は package.json の engines 22.x を CI と frontend/Dockerfile が共に読む。CPUアーキテクチャは本番 aarch64・CI x86_64。

対応方針:
1. 本番の版を正本として決める: 本番DBのPostgreSQL・PostGISの版を docs/architecture/（tech-stack.md の構成の節）に書き、CI と docker-compose がそれに従うことを明記する。本番の版を上げたらここと両方を同時に上げる。
2. イメージの選定: Docker Hub の公式ページ（hub.docker.com/r/postgis/postgis のタグ一覧）で PostgreSQL 18・PostGIS 3.6 のタグと、arm64 を含むかを確かめてから選ぶ（推測でタグを書かない）。ci.yml の services と docker-compose.yml を同じタグへ揃える。
3. 版の変化でテストが落ちたら、テスト側の都合で古い版へ戻さない。落ちた原因（関数の挙動差・プランの差）を取り、本番で同じことが起きていないかを run_probe で本番に当てて確かめる。
4. アーキテクチャ: GitHub 公式（docs.github.com の GitHub-hosted runners の表）で public リポジトリの arm64 ランナー（ubuntu-24.04-arm 等）の提供と条件を確かめ、backend ジョブを本番と同じ aarch64 で回せるかを判断する。回せるなら backend ジョブを移し、所要時間を移行前後で比べて記録する。
5. 本番の backend イメージ（backend/Dockerfile）の中でテストを回す形（OSのライブラリ GEOS・PROJ・pyosmium 等まで本番に揃う）も候補として所要時間と得失を測り、採るかを記録する。採らないなら理由を書く。

完了条件: ci.yml と docker-compose.yml の PostGIS が本番と同じメジャー版になり、作業ブランチ（orch/**）のCIで全件が通ること（runのURLを記録）。docs/architecture に本番の版が正本として書かれていること。4・5 の判断と実測が T＊.md にあること。

## 実施内容（2026-09-23、L-env）

### 本番の版（run_probe、読み取りのみ）

`backend/scripts/run_probe.py --in-container`で本番コンテナから引いた値:

- `version()`: PostgreSQL 18.6 (Ubuntu 18.6-1.pgdg24.04+2) on aarch64-unknown-linux-gnu
- `postgis_full_version()`: POSTGIS="3.6.4"、GEOS="3.12.1"、PROJ="9.4.0"（DB側。Ubuntu 24.04のパッケージ）
- コンテナ: aarch64、Python 3.12.14、shapely 2.0.6（wheel同梱のGEOS 3.11.4）、pyproj 3.7.2（同梱のPROJ 9.5.1）

`18.6-1.pgdg24.04+2`はPostgreSQL公式のaptリポジトリ（PGDG）の版の書き方で、本番はUbuntu 24.04へPGDGのパッケージを入れている。

### 外部の仕様（公式で確かめたもの）

- **Docker Hub**（`hub.docker.com/v2/repositories/postgis/postgis/tags`と同リポジトリの説明文）: 18系のタグは`18-3.6`・`18-3.6-alpine`・`18-master`（ほかにrc1）。`18-3.6`はdebian:trixie・PostgreSQL 18・PostGIS 3.6.4。**どのタグもamd64だけ**（説明文「Supported architecture: `amd64` (x86-64)」、タグのimagesもamd64のみ）。PostgreSQL 18以降のイメージは`VOLUME`が`/var/lib/postgresql`へ変わった（17以前は`/var/lib/postgresql/data`）。
- **GitHub**（docs.github.com「GitHub-hosted runners reference」）: publicリポジトリの標準ランナーにarm64の`ubuntu-24.04-arm`・`ubuntu-22.04-arm`・`ubuntu-26.04-arm`があり、publicリポジトリでは標準ランナーの利用が無料・無制限と書かれている。ランナーイメージ（actions/runner-imagesの`Ubuntu2404-Arm64-Readme.md`）はUbuntu 24.04.5・Docker 28・PostgreSQL 16.15（サービス無効）を持つ。PG16はPGDGから入れたあとリポジトリ設定を消している（同リポジトリの`install-postgresql.sh`）。
- **PostgreSQL公式**（postgresql.org/download/linux/ubuntu/）: PGDGはnoble（24.04）のarm64を配布する。設定は`/usr/share/postgresql-common/pgdg/apt.postgresql.org.sh`（同スクリプトは`-y`で確認なし、最後に`apt-get update`まで行う）。PGDGの`noble-pgdg/main/binary-arm64/Packages`に`postgresql-18 18.6-1.pgdg24.04+2`と`postgresql-18-postgis-3 3.6.4+dfsg-2.pgdg24.04+1`がある——本番の`version()`と同じ文字列。

### 方針2からの逸脱: ci.ymlはイメージを使わない

方針2は「ci.ymlのservicesとdocker-compose.ymlを同じタグへ揃える」だったが、`postgis/postgis`がamd64しか配らないため、方針4（backendをaarch64へ）を採るとサービスコンテナにできない。**ci.ymlはランナーへPGDGから本番と同じパッケージを入れ、docker-compose.ymlは`postgis/postgis:18-3.6`**にした。揃えたのはメジャー版（PostgreSQL 18・PostGIS 3.6）で、正本はdocs/architecture/tech-stack.md「DBの版」。`18-3.6`のイメージ自体がテスト一式を通すことは下の実験Aで確かめた。

### 判断

- **方針4: 採る。** backendジョブを`ubuntu-24.04-arm`へ移した。本番とアーキテクチャ・OS（Ubuntu 24.04）・DBの配布元とパッケージ名まで揃い、ジョブは移行前より速い（75〜78秒、移行前82〜105秒）。ラベルは`ubuntu-24.04-arm`に固定する（`ubuntu-latest`は2026-10-19からUbuntu 26へ移ると実行時の注釈が告知しており、本番VMの24.04から離れる）。ランナーにあるPG16のクラスタは5432番を塞ぐため先に落とす。
- **方針5: 採らない。** Cは本番のイメージのOSライブラリまで揃うが、Pythonの依存はwheelが自前のライブラリ（GEOS・PROJ等）を同梱するためBでも本番と同じものが入り、Cでだけ見える差は「wheelに同梱されないOSのライブラリ」（例: rasterioが要る`libexpat`。Dockerfileが明示的に入れている）に限られる。その壊れ方は`deploy-backend.yml`がコンテナを入れ替える前に走らせる`import app.main`で止まる。対してCは毎回キャッシュの無い`docker build`とコンテナ内でのdev依存の導入を払い（ジョブ88秒、Bより10秒長い）、ruffを回す場所も別に要る。
- **方針3**: 版を上げて落ちたテストは無かった（A・B・Cとも2068件成功）。本番へ当てて確かめる対象は生じなかった。

### 追加で見つけた差: DB側のGEOS・PROJ

Bを確定版にした最初の実行（2288fdec、run 35821784940、成功）の注釈`DB`が
`PostgreSQL 18.6 (Ubuntu 18.6-1.pgdg24.04+2) on aarch64 … / PostGIS 3.6.4 / GEOS 3.14.1-CAPI-1.20.5 / PROJ 9.8.1`
だった。PostgreSQLとPostGISは本番と同じ文字列だが、**GEOS・PROJは本番（3.12.1・9.4.0）より新しい**。
PGDGの`Packages`を読むと、`postgresql-18-postgis-3`の依存は`libgeos-c1t64 (>= 3.12.0)`・
`libproj25 (>= 7.1.0)`で、PGDGは`libgeos-c1t64 3.14.1-2.pgdg24.04+1`・`libproj25 9.8.1-1.pgdg24.04+1`も
配っている。Ubuntu本体（ports.ubuntu.comの`noble`）は`libgeos-c1t64 3.12.1-3build1`・
`libproj25 9.4.0-1build2`・`proj-data 9.4.0-1build2`・`libgdal34t64 3.8.4`で、本番の
GEOS 3.12.1・PROJ 9.4.0・GDAL 3.8.4と一致する（本番はUbuntu本体の版を使っている。ホストの`dpkg`は
run_probeの届かない場所なので、版の一致からの判断）。GDALはPGDGの版が別名（`libgdal39`）のため
CIでもUbuntu本体の3.8.4になる。

対応: CIは`libgeos-c1t64/noble libproj25/noble proj-data/noble`でUbuntu本体の版を指定する
（proj-dataも揃えないと、PROJのライブラリと座標系データベースの版がずれる）。注釈`DB`へGDALの版も
出すようにした。**本番のVMで`apt upgrade`をすると、PGDGが設定されているなら本番のGEOS・PROJが
PGDGの新しい版へ上がりうる**——そのときはCIの指定を同じ変更で外す（tech-stack.md「DBの版」）。

### 変更

- `.github/workflows/ci.yml`: backendジョブを`ubuntu-24.04-arm`＋PGDGの`postgresql-18`・`postgresql-18-postgis-3`（GEOS・PROJはUbuntu本体の版）へ。実行ごとにDBの版（PostgreSQL・PostGIS・DB側のGEOS・PROJ・GDAL）を注釈`DB`へ出す——本番との差が実行のたびに見える。
- `docker-compose.yml`: `postgis/postgis:18-3.6`。ボリュームのマウント先を`/var/lib/postgresql`へ、名前を`postgres18-data`へ（旧版のボリュームは新しい版で開けないため）。
- docs/architecture/tech-stack.md「DBの版（本番が正本）」を新設。README.mdの目次、setup.md（Composeのボリュームの扱い）を追従。

docker-composeは開発機にDockerが無いため起動していない（`yaml.safe_load`で構文と値だけ確かめた）。同じイメージ`postgis/postgis:18-3.6`がテスト一式を通すことは実験Aで確かめた。

最終のコミットのCIの実行（runのURLとDB注釈）は、コミットに自分のURLを書けないため、完了の報告に添える。
