# T1061. CIとdocker-composeのDB・実行環境を本番の版とアーキテクチャに揃える

状態: 未完了（2026-09-23起票）

## 背景

CI（GitHub Actions）と docker-compose が、本番と違う版のDBで合否を決めている。2026-09-23の実測（本番は run_probe.py --in-container で select version()・postgis_lib_version()、開発機は backend/.env の DATABASE_URL へ同じ問い合わせ）: 本番 PostgreSQL 18.6（aarch64）・PostGIS 3.6.4、開発機 18.6・3.6.2、CI と docker-compose.yml は postgis/postgis:16-3.4（PostgreSQL 16・PostGIS 3.4）。CIは本番より2つ古いメジャー版で PostGIS 統合テストを判定しており、関数・プランナーの挙動差があれば CI で通って本番で違う形になりうる。同じ日に「開発機（Windows）で通ったテストが Linux の CI で落ちる」（T1020のテスト、08fef74a で修正）が起き、判定する環境を本番に揃えることが根本対策とユーザーと確認した。T1058 で作業ブランチでもCIが走るようになったため、CIの判定がmasterへの門の中心になっている。ほかの版: Python は CI（setup-python 3.12）と本番（backend/Dockerfile の python:3.12-slim）で一致。Node は package.json の engines 22.x を CI と frontend/Dockerfile が共に読む。CPUアーキテクチャは本番 aarch64・CI x86_64。

対応方針:
1. 本番の版を正本として決める: 本番DBのPostgreSQL・PostGISの版を docs/architecture/（tech-stack.md の構成の節）に書き、CI と docker-compose がそれに従うことを明記する。本番の版を上げたらここと両方を同時に上げる。
2. イメージの選定: Docker Hub の公式ページ（hub.docker.com/r/postgis/postgis のタグ一覧）で PostgreSQL 18・PostGIS 3.6 のタグと、arm64 を含むかを確かめてから選ぶ（推測でタグを書かない）。ci.yml の services と docker-compose.yml を同じタグへ揃える。
3. 版の変化でテストが落ちたら、テスト側の都合で古い版へ戻さない。落ちた原因（関数の挙動差・プランの差）を取り、本番で同じことが起きていないかを run_probe で本番に当てて確かめる。
4. アーキテクチャ: GitHub 公式（docs.github.com の GitHub-hosted runners の表）で public リポジトリの arm64 ランナー（ubuntu-24.04-arm 等）の提供と条件を確かめ、backend ジョブを本番と同じ aarch64 で回せるかを判断する。回せるなら backend ジョブを移し、所要時間を移行前後で比べて記録する。
5. 本番の backend イメージ（backend/Dockerfile）の中でテストを回す形（OSのライブラリ GEOS・PROJ・pyosmium 等まで本番に揃う）も候補として所要時間と得失を測り、採るかを記録する。採らないなら理由を書く。

完了条件: ci.yml と docker-compose.yml の PostGIS が本番と同じメジャー版になり、作業ブランチ（orch/**）のCIで全件が通ること（runのURLを記録）。docs/architecture に本番の版が正本として書かれていること。4・5 の判断と実測が T＊.md にあること。
