# T1072. 定期確認のフックが本体のチェックアウトの古い道具を動かし、古い判定を黙って出す

状態: 完了（2026-09-23）

## 背景

定期確認のフック（.claude/settings.json の PostToolUse → scripts/orchestration/hook.sh → orchestrate.py check --if-due）は、$CLAUDE_PROJECT_DIR（セッションを始めたディレクトリ＝本体のチェックアウト）の道具を動かす。本体のチェックアウトは master が進んでも手で早送りしない限り古いままで、2026-09-23 17:11 には T1065（状態の表の写しの除去）以前の古い core が走り、移行後の表を読めずに「例: None」と誤表示した。司令塔が本体を手で早送りし続けるのは、同じ道具を本体と master の二か所に持つ二重持ちで、忘れた時点で定期確認が黙って古い判定をする。

対応方針: フックが常に最新の道具で判定する形を設計する。候補（公式文書と実測で確かめてから選ぶ）: (a) フックが司令塔の作業ツリー（状態の表に記録した司令塔のセッションの作業ディレクトリ）の道具を動かす、(b) フックが origin/master の版の道具を読んで動かす（git show で一時ファイルへ、または worktree を使わず git の中から読む）、(c) 本体のチェックアウトが origin/master より古いとき、定期確認が異常として出す（最低限の検知）。本体のチェックアウトを自動で書き換える案は採らない（ユーザーの作業ツリーであり、並行セッションが触りうる）。フック自体（hook.sh）が古い場合の扱いも決める。

完了条件: 本体のチェックアウトを古い版に置いたまま、定期確認が最新の判定を返すこと（または古いことを異常として出すこと）を、壊した入力で確かめる。

## 選んだ形と理由

公式文書（code.claude.com/docs/en/hooks）: `${CLAUDE_PROJECT_DIR}`は「セッションを始めたプロジェクトのルート」で、
作業ツリーへ入っても本体のチェックアウトを指したまま動かない。フックの設定・スクリプトの直接の編集は
セッション中もファイル監視で拾われる。

- **(a)は採らない**: 司令塔のセッションの作業ディレクトリ（フック入力の`cwd`）は多くが本体のチェックアウト
  そのもので、作業ツリーであってもmasterへ早送りされている保証が無い。二重持ちの置き場を1つ替えるだけになる。
- **(b)を採る**: 道具の正本はorigin/masterなので、gitの中から直接読めば二重持ちが無くなる。`git fetch`は
  担当のpush・監査・司令塔の操作のたびに走っており、origin/masterは確認に必要な鮮度で進んでいる。
- **(c)は入口についてだけ使う**: 入口の`hook.sh`は設定（`. "$CLAUDE_PROJECT_DIR/scripts/orchestration/hook.sh"`）
  から本体の作業ツリーのファイルとして読まれ、(b)で置き換えられない。そこで、本体の`hook.sh`の中身が
  origin/masterの版と違えば、確認の結果に「フックの入口が古い」と添える。

## 実施内容

- `scripts/orchestration/launch.py`（新設）: 起動役。origin/masterの道具（`scripts/orchestrate.py`・
  `scripts/check_master_ci.py`・`scripts/orchestration/`）を`<gitの共通ディレクトリ>/orchestration/tools/<sha>/`へ
  書き出し（shaごとに1回。一時ディレクトリへ書いてから改名し、別のshaの書き出しは消す）、そこから
  `check --if-due`を`--repo <本体>`付きで走らせる。本体の`hook.sh`のblobとorigin/masterの版を比べ、違えば注を添える。
  書き出せないときは本体の道具で走らせ、その旨を注に出す。
- `scripts/orchestration/hook.sh`: 確認を起こすとき、起動役を`git show origin/master:scripts/orchestration/launch.py`で
  取り出して動かす。取り出せない（origin/masterに起動役が無い版）ときだけ本体の道具で走らせる。
- `docs/conventions/orchestration.md`「管理のループ」: フックがorigin/masterの版の道具で確認すること、入口が古いと
  出たら本体を早送りすること、入口が起動役を知らない版のままだと効かないことを書いた。

**残る手作業は1回だけ**: 入口そのものは本体から読まれるので、この変更がmasterに入ったあと本体のチェックアウトを
1回早送りする（それ以後の道具の変更は早送りなしで効く。入口が変わったときは確認の結果に出る）。

## 検証

壊した入力（`scratchpad/t1072_test.sh`）: 一時のリポジトリ（オブジェクトは実物をalternatesで借りる）の作業ツリーへ
古い版（78b1276d。予算の行を出す前の道具）を置き、`refs/remotes/origin/master`を新しい版へ向け、実物の表の写しと
司令塔のセッションを置いて、`CLAUDE_PROJECT_DIR=<一時> bash -c '. "$CLAUDE_PROJECT_DIR/scripts/orchestration/hook.sh"'`へ
司令塔のセッションのフック入力を流した。

| 場合 | 結果 |
|---|---|
| 1. 入口・道具とも古い版 | 予算の行が出ない（古い道具が走る。入口が起動役を知らないので防げない＝上の1回の早送り） |
| 2. 入口だけ新しい版、道具は古い | 予算の行が出る（origin/masterの道具が走った）。`tools/<新しいsha>/`ができる |
| 3. 入口に1行足してorigin/masterと違える | 予算の行と「注: フックの入口…がorigin/masterの版と違う」が出る |
| 4. origin/masterを起動役の無い版にする | 本体の道具で走る（予算の行なし）。落ちない |
| 5. origin/masterを道具を書き換えたコミットへ進める | 新しいshaへ書き出し直し、書き出した`orchestrate.py`の末尾が書き換えた行。古いshaは消えた |
