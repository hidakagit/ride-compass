# 軸スタジオに何をさせるか（値の入力ではなく、試した結果が見えること）

軸定義（`axis_definitions`の行データ）を変える手段として、軸スタジオのGUIに何を担わせるかの
決定。正本がDBであることは変えない（[T361](../tasks/T361.md)）。

ステータス: 決定（2026-09-17、ユーザー判断）

## 背景

軸スタジオには繰り返し手が入っているが、同じ不満が戻ってくる——2026-09-08「軸スタジオ
使いにくいね・・・直接DBにInsertした方が楽かなって思うくらい」（[T686](../tasks/T686.md)で
分布プレビューを追加）、2026-09-17「数値をポチポチ手打ちするなら、apiで裏更新するのと
同じ」。改善のたびに**入力欄の作り込み**を足してきたが、利用者がやりたいのは入力ではなく
**較正**（実データを見て根拠のある値を決めること）なので、入力欄をいくら磨いても効かない。

## 決定

**書き込みの入口は各環境の軸スタジオ（GUI）**。本番の軸を変えるときは本番の軸スタジオで
変更し、その時点で本番DBが更新される。開発環境のDBは検証用に分かれており、本番と内容を
揃える対象ではない。環境をまたいで内容を転送する仕組み（DB間のコピー、ファイルを正本に
した適用）は**作らない**——正本のDBに対して第2の入力経路を増やすだけで、ずれの管理を
自分で生み出す。

**軸スタジオが投資するのは「読む・試す」側**。

- 公開軸の一覧・各軸の形・重み・公開状態・材料の欠損割合を読む。
- **実データの分布で効き方を確かめる**（`DistributionPreview`、[T686](../tasks/T686.md)）。
  値を決める前に「この折れ点だと延長の94.6%が満点」と分かること自体がGUIの存在理由。
- 段階分け（`display_thresholds_override`）を変えたときに、**段階の並びと地図の色が
  その場で見える**こと（[T922](../tasks/T922.md)）。
- 公開/非公開の切り替えと、壊す操作の拒否理由の提示。

**やらないこと**: 値の入力体験をこれ以上作り込むこと。値を並べて打つ作業は、まとめて貼れる
入力欄があれば足りる。入力の作り込みは較正の役には立たない。

**履歴（誰がいつ何を変えたか・ロールバック）は持たない。** 軸の値は唯一の正解が無い継続的
チューニングの対象で、監査証跡・ロールバックは過剰品質だと既に判断している
（[T361](../tasks/T361.md)の背景に残るT221・T353の判断）。

## 変更後に残る手順

fresh bootstrap（CI・新規環境・disaster recovery）が読むスナップショット
（`backend/fixtures/axis_definitions_snapshot.json`）は、本番DBを変えた後に
`backend/scripts/dump_axis_definitions_snapshot.py`で手動更新する（[deployment-sync.md](../../conventions/deployment-sync.md)）。
これはファイルを正本にする話ではなく、**まっさらなDBへ実データを用意するためのダンプ**である。
