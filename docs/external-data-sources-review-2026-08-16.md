# 外部静的データソースの設計検討（調査報告・2026-08-16）

[roadbike_ridability_data_sources.md](../roadbike_ridability_data_sources.md)（外部API・オープンデータの収集結果）を、
現行アーキテクチャ（[architecture.md](architecture.md)・[static-road-attributes-plan.md](static-road-attributes-plan.md)）に
突き合わせ、「組み込めるか」「目的（ロードバイクの走りやすさ評価）に合致するか」を判定した。

**評価方針**: 「目的適合度」と「組み込みコスト」は独立の軸として扱う。
組み込みコストが高くても、データの精度・内容が目的に合致するものは
**調査ゲート付きの採用候補**として残す（不採用にするのは「内容が目的に合わない」
「既存データと重複する」ものだけ）。

---

## 1. 判定の前提: 現行アーキテクチャの受け入れ口

外部データが「組み込める」かどうかは、既存のどの取込・対応付けパターンに乗るかで決まる。

| パターン | 機構 | 実績 | 新規外部データへの適用 |
|---|---|---|---|
| A. way属性 | `osm_raw_ways.tags` → 分類関数 → MVT/評価 | P0/P1で確立 | OSMタグ限定（許可リスト追加＋再取込のみ） |
| B. 点データ→密度/フラグ | 専用テーブル＋`ST_DWithin`空間結合（stop POI・交差点で確立） | P1で確立 | **取込元がOSMである必要はない**。緯度経度付きの点データなら同型で乗る |
| C. ラスタタイル重ね描き | MapLibre rasterソース（GSI色別標高図で確立） | Step10で確立 | 表示のみ。評価には使えない |
| D. 線データのコンフレーション | 外部の線形データ→`road_edges`/OSM wayへの対応付け | **未整備** | 新機構が必要。バッファマッチ（`ST_DWithin`＋highway種別ガード）から始めるのが現実的 |
| E. メッシュ/ポリゴンの面的付与 | `ST_Intersects`でエッジへ付与 | 未整備（技術的には単純） | メッシュ統計・気候系 |

パターンB・Cはコスト小。パターンDは対応付けの精度検証込みでコスト大だが、
「指定路線か否か」のような2値属性なら誤対応の実害が小さく、易しい入口がある。

評価軸を増やす場合は、P1で確立した1本道
（`evaluate_axis_difficulties`拡張＋`route_preference.yaml`重み追加＋`RouteCandidate`集約値）に乗せる。
`scoring.yaml`（おすすめ度・相対評価）へ入れるかどうかは軸ごとに都度判断
（現行7軸はすべて不採用の非対称で統一中）。

## 2. ソース別判定

凡例 — 目的適合度/組み込みコスト: ◎○△✕ / 判定: **採用候補**（優先度付き）・**調査ゲート**（フィージビリティ確認後に採否）・**既計画**・**不採用**

### 2.1 OSM系（調査資料§1）— 大半はP0/P1で実装済み

highway・surface・smoothness・cycleway系・bicycle・motor_vehicle・lanes・maxspeed・
oneway・tunnel・bridge（way）、信号・横断歩道・一時停止・踏切（node）、交差点密度は
**実装済み**。width(0.3%)・shoulder(0.0%)はカバレッジ実測でP2据え置き確定済み。

資料で挙がっているが未判断だったタグの関東全域カバレッジを実測した
（`measure_tag_coverage.py`の集計器を対象タグ差し替えで再利用、kanto-latest.osm.pbf 取込対象way）:

| タグ | 全体 | 幹線 | 生活道路 | 自転車専用（cycleway/track） |
|---|---|---|---|---|
| `tracktype` | 3.5% | 0.0% | 0.2% | **23.2%** |
| `lit` | 1.0% | 4.8% | 0.5% | 0.2% |
| `width` | 0.3% | 0.4% | 0.3% | 0.4% |
| `incline` | 0.1% | 0.2% | 0.1% | 0.1% |
| `shoulder` | 0.0% | 0.0% | 0.0% | 0.0% |
| `hazard` | 0.0% | 0.0% | 0.0% | 0.0% |
| `class:bicycle` | 0.0% | 0.0% | 0.0% | 0.0% |

（対象way 1,312,048件。幹線172,776 / 生活道路949,416 / 自転車専用189,856）

- **判定: OSM系の新規採用なし**。`class:bicycle`（資料が「目的に合致」とした走りやすさ直接タグ）・
  `hazard`・`lit`はいずれも関東で実用カバレッジが無く、評価にも表示にも使えない。
  資料自身の補足（class:bicycleは付与が限定的）が実測で裏付けられた形。
  `tracktype`のみtrack限定なら23.2%あり、未舗装路の締固め度表示としてのP2据え置き
  （既判断）の妥当性を確認
- `barrier`（node: 車止め・ゲート）は今回のway実測の対象外。stop POI機構（パターンB）に
  相乗り可能なので、サイクリングロードの車止め減速が気になった時点で`classify_stop_poi`への
  種別追加として検討すればよい（P2）
- `incline`は既判断どおり不要（DEM/標高系と重複）

### 2.4 xROAD系（§4）

| データ | 適合度 | コスト | 判定 |
|---|---|---|---|
| 舗装点検DB（MCI・ひび割れ率・わだち・平坦性） | ◎（**全ソース中で目的適合度最高クラス**。路面の物理実測値であり、OSM `smoothness` 0.1%の穴を埋め得る唯一級のデータ） | 大（位置参照が路線番号＋距離標KPの10m区間単位。**データ取得APIは利用登録申請制で、利用料金の案内もあり・2026-08-16確認**（API仕様書自体は公開・2026-06更新）。地図表示用緯度経度の登録もあるがAPI応答に含まれるかは未確認。対象は直轄国道全線＋登録済み自治体道） | **調査ゲート付き採用候補**。下記の調査タスクを先行させる |
| 交通量API（JARTIC） | △→○（実測交通量そのものだが、常時観測点は直轄国道の約2,600地点で**面的カバレッジが決定的に不足**。エッジ属性には使えない。さらに**取得できる過去データは5分値1ヶ月・1時間値3ヶ月のみ**で、静的属性に欲しい年平均系の値は直接得られない） | 中（WFS準拠GeoJSON/CSV・登録不要（規約同意のみ）を確認済み・2026-08-16。ただし年平均を作るには**自前で定期収集して蓄積する運用**が必要） | **条件付き採用候補**: エッジ属性ではなく**trafficStressモデルの較正・検証データ**として使う（観測点近傍エッジの推定LTSと実交通量の突き合わせ。研究インターフェースPhase2の比較環境と相性が良い）。まず限定期間のスナップショット収集で較正に足りるか試す |
| DRM-PF API | ✕（OSMネットワークと役割重複） | 大（**APIマニュアルは有償会員限定と確認済み・2026-08-16**。無償のベクトルサイトも道路管理者向け） | **不採用**（重複に加え利用条件も合わない） |
| 橋梁・トンネル点検DB | △（構造物の健全性≠走行面の品質） | 大 | **不採用** |

**舗装点検DBの調査ゲート**（採否はこの結果で決める。順に確認し、どこかで✕なら見送り）:
0. データ利用の申請条件と利用料金（無償枠の有無）。JICEへの問い合わせが必要な見込み
1. API/ダウンロードデータに地図表示用の緯度経度（または区間線形）が含まれるか
2. 関東での収録範囲: 直轄国道以外（自治体登録道路）がどの程度あるか
   （直轄国道はtrafficStress 4の道が中心のため、それしか無いなら効果が限定される。
   ただし幹線を避けられない接続区間の路面良否は判断材料になるため、直轄のみでも即✕ではない）
3. 10m区間データを`road_edges`へバッファマッチ（パターンD）した際の対応付け精度

補足: 資料未掲載だが同系の**道路交通センサス**（区間別の年平均日交通量）は、JARTICより
面的カバレッジがあるものの位置参照が区間表形式でコンフレーション難度が最も高い。
舗装点検DBの調査ゲート3（パターンDの精度検証）を通過できた場合にのみ再訪する。

### 2.5 警察庁 交通事故統計（§5）— 新規採用の第一候補

| 観点 | 評価 |
|---|---|
| 適合度 | ◎ 既存7軸のどれとも重複しない「実績ベースの安全性」軸。当事者種別コードで自転車関連事故を抽出可能 |
| コスト | 小 **パターンBそのまま**。緯度経度付き年次CSV（度分秒→10進変換のみ注意）→ 専用点テーブル → `get_stop_poi_counts`と同型の`ST_DWithin`集計 → `accident_density`（件/km） |
| 表示 | 静的レイヤー（kind=static）としてMVT/circleレイヤー追加も既存機構で可能 |

設計上の注意:
- **テーブルは`osm_raw_pois`と分ける**（取込元が非OSM。世代管理も年次更新で別物）。
  取込は専用バッチ（CSV→PostGIS）で、`osm_import_runs`同様の取込記録を残す
- **交通量との交絡**: 事故件数は交通量に比例しがちで、trafficStressと部分的に同じ情報を
  持つ。軸として独立させる価値は「幹線でも事故の少ない区間／生活道路でも多い区間」の
  識別にあるので、重み初期値は控えめにし研究IFで効きを確認する
- 自転車当事者限定だと疎になりすぎる可能性があるため、全事故件数と自転車関連件数の
  両方を保持し、密度算出時にどちらを使うか選べる形にする（カバレッジ実測してから決定）
- 評価軸追加の1本道（7軸→8軸）に乗せる。`scoring.yaml`への追加是非は都度判断の対象
  （現行の非対称を崩す積極的理由は無い見込み）

### 2.6 自転車インフラ・ルート指定系（§6）

| データ | 適合度 | コスト | 判定 |
|---|---|---|---|
| ナショナルサイクルルート | ○（お墨付き区間のボーナス評価・表示） | **小**（機械可読データの公開を確認済み・2026-08-16: 太平洋岸自転車道はエリア別KML（近畿地整サイト）、つくば霞ヶ浦りんりんロードはGPX（つくば市サイクリングガイド等）。KML/GPX→GeoJSON変換は機械的） | **採用候補（低優先P2）**。関東DB圏内の該当は太平洋岸自転車道（千葉・神奈川区間）とりんりんロード（茨城）の2ルートのみ。用途を2段に分ける: ①**表示レイヤー**（kind=static）はルート線形をそのまま独自ソースとして描くだけでコンフレーション不要＝コスト小 ②**評価ボーナス**はエッジへの対応付けが必要で、N10/N12と同じ「該当か否か」の2値バッファマッチ（易しい部類）。大半は`highway=cycleway`で既に好スコアになるため評価への増分は小さく、①先行が妥当。OSM relation（`route=bicycle`）取込でも代替可能なため、relation機構をP2で作る場合はそちらへ統合 |
| 自治体自転車ネットワーク計画 | △（内容は良いが形式が自治体ごとにバラバラでスケールしない） | 特大 | **不採用**（特定地域の手動補正データとして将来個別判断） |

### 2.7 汎用ルーティングAPI（§7）

**不採用**。T21でopenrouteserviceの`extra_info=surface`依存を撤去し、属性は自前DB空間マッチへ
統一した経緯がある（[architecture.md](architecture.md)「路面判定は1系統へ統一済み」）。
Mapbox/GraphHopperの属性APIを足すのはこの設計判断の逆行であり、情報源としてもOSM由来で
自前PostGISと同一。

### 2.8 気候系（§8）

**不採用（当面）**。動的天候はOpen-Meteoで走行時点の実予報を取得済みで、平年値より目的に
合っている。恒常的な向かい風傾向・凍結リスクは「季節別のおすすめ」のような機能が
生まれた時点で再訪する。

## 4. 実行計画・設計（検証対象の各項目）

§3の優先順位に沿って、取込→保持→対応付け→評価/表示の各段を既存機構との対応で設計する。
共通方針:

- **保持は既存スキーマの型に揃える**: 点データは`osm_raw_pois`型（選別済み点＋GiST）、
  Edge派生値は`elevation_attributes`型（edge_id PK・data_version・calculated_at付き）、
  取込記録は`osm_import_runs`型。マイグレーションは既存の連番SQL（0006〜）
- **rawと派生の分離**を外部データにも適用: 外部ソースの生値テーブルと、
  エッジへ対応付けた派生テーブルを必ず分ける（再対応付け・再取込を独立にやり直せる）
- **評価軸の増やし方は1本道**（`evaluate_axis_difficulties`＋`route_preference.yaml`＋
  `RouteCandidate`集約値）。`scoring.yaml`への追加是非は軸ごとに都度判断
- **見える化先行**: P0の前例に合わせ、評価組み込みの前に表示レイヤーで実データの
  見え方・カバレッジを確認する
- ログは docs/logging.md 準拠（取込は1行INFOサマリ、エラー・0件はWARNING常時）
- 着手時は improvement-plan.md へタスク起票し、本節の該当項を参照させる

### 4.1 警察庁事故データ → 事故密度軸（優先1）

**取得**（2026-08-16訂正、URL構造を実機確認済み）: 警察庁オープンデータの本票CSV
（年次、2019年〜。Shift_JIS・緯度経度は度分秒連結表記）は
`https://www.npa.go.jp/publications/statistics/koutsuu/opendata/{year}/honhyo_{year}.csv`
という年号だけで組み立てられる予測可能なURLで、2019〜2024年の全年で同一命名規則
（`honhyo_`/`hojuhyo_`/`kosokuhyo_`）を確認済み。ログイン・利用登録不要、robots.txtにも
制限なし、直接GETでHTTP 200・text/csvを確認済み（2024年分62.8MB）。**当初「入手はユーザー作業」
としていたのは誤りで、バッチが年次リストからURLを組み立てて直接取得できる**。コード表
（当事者種別等、`codebook_{year}.xlsx`）も同一規則だが、こちらは`involves_bicycle`の分類
ロジックを書く際に一度参照すれば足りるため実行時取得の対象にしない。

### 4.2 GSI DEMタイル化（優先2＝既計画T10の実行設計）

**保持**: 新テーブル・新ライブラリなし。DEMタイル（テキスト形式、256×256標高値）を
**既存`tile_cache`**（ファイル・SHA-256フラット化）へ `gsi/dem/{type}/{z}/{x}/{y}` のパスで
相乗りさせる。DEMは不変データのためTTLなし。PostGIS rasterは導入しない（新規導入物ゼロの
原則）。

**実装**: `ElevationClient`の中身を「点API問い合わせ」から「点→タイル座標→タイル取得
（キャッシュ優先）→周囲4格子の双線形補間」へ差し替える（呼び出し側I/F不変）。
欠損時のフォールバック鎖 DEM5A→DEM5B→DEM10B、全欠損はNone（現行方針のまま）。
既存のSQLite点キャッシュは廃止（T10の「1系統化」）。`elevation_attributes`（Edge派生）は
そのまま。

**効果と検証**: 生成1回あたり最大256点の外部呼び出しが、タイル単位（近接点は同一タイル）へ
1〜2桁減る。検証は既存点APIとの突き合わせ（無作為1,000点で|Δ標高|の分布、1m以内率を確認）。
これが済むとサンプリング密度の上限（現行32点）を引き上げる余地も生まれる。

### 4.3 指定路線の共通機構: N10/N12＋ナショナルサイクルルート（優先4・6を統合）

「線形で与えられる指定情報をエッジへ対応付ける」機構は1つ作って共用する
（パターンDの初回実装。舗装点検DBが通過した場合もこの機構を流用する）。

**保持**（migration 0007）:

```
route_designations                   -- 外部指定線形の生値（raw層）
  id       SERIAL PK
  kind     TEXT NOT NULL   -- emergency_transport | critical_logistics | national_cycle_route
  name     TEXT / pref_code TEXT / attrs JSONB
  source   TEXT NOT NULL   -- ksj_n10 | ksj_n12 | mlit_kml | gpx（+ source_version）
  geom     LINESTRING 4326 GiST
designation_attributes               -- Edge派生（elevation_attributes型）
  edge_id  TEXT FK(road_edges) ON DELETE CASCADE
  kind     TEXT NOT NULL             -- PK(edge_id, kind)
  matched_ratio FLOAT NOT NULL       -- エッジ長のうちバッファ内だった割合（判定根拠を保持）
  data_version TEXT / calculated_at timestamptz
```

**取込**: `app/batch/import_designations.py`。GeoJSON（N10/N12）・KML（太平洋岸）・
GPX（りんりんロード）それぞれ薄いreaderで共通スキーマへ。

**対応付け**: `app/batch/match_designations.py`（**事前計算バッチ**。線×線の割合計算は
評価時導出には重く、Edge派生の事前計算には`elevation_attributes`の先例がある）。
判定: `ST_Length(ST_Intersection(edge.geom, ST_Buffer(designation, 20m))) / ST_Length(edge.geom)
≥ 0.5` で該当。バッファ幅・閾値は`domain/designation.py`（新規）の定数が正準。
highway種別ガード（例: national_cycle_routeはmotorway系エッジと対応させない）。
OSM再取込時は再実行（`data_version`にOSM取込runと指定データ版の両方を記録）。

**評価/表示**:
- N10/N12 → `traffic_stress_level`に補正引数を追加（指定該当で+1、既存クランプ内）。
  表示は路面MVTへ`designation`プロパティを焼き込み（JOIN 1つ・タイル世代bump）、
  `roadFilterAxes`に軸1つ
- ナショナルサイクルルート → まず**フロント静的GeoJSONの独自線ソースで表示のみ先行**
  （DB不要・即日規模。出典明記）。評価ボーナス（bicycle_infra側への加点）が欲しくなった
  時点で上記機構へ載せ替え

**検証**: 国道16号・6号など既知路線の目視確認、matched_ratio分布の確認、
バッファ10/20/30mの比較で誤対応（並行する側道・歩道の巻き込み）を実測してから確定。

### 4.5 JARTIC交通量 — trafficStress較正（優先5）

評価パイプラインには入れない。**1回のスナップショット収集→分析で完結**させ、
定期収集はその結果が較正に不足する場合のみ検討する（停止条件を先に決めておく）。

**収集**: `backend/scripts/collect_jartic.py`（手動実行）。関東bboxの常時観測点について
1時間値（取得可能な過去3ヶ月分）をWFS GetFeatureで取得。`log_external_call`で囲む。

**保持**: **dev機PostgreSQLのみ**（研究用データを本番Oracleに置かない。本番に置くのは
評価・表示に使うデータだけ、という分離）:

```
traffic_stations(station_id PK, name, road_name, geom POINT GiST)
traffic_hourly(station_id FK, observed_at timestamptz, direction, volume INT,
               PK(station_id, observed_at, direction))
```

規模概算: 関東の観測点数百×24h×90日×2方向で数百万行・数百MB（dev機で十分）。

**分析**: 観測点→最近傍エッジ（ST_DWithin 30m＋highway一致ガード）→エッジの
`traffic_stress_level`と日平均交通量の分布比較（LTS 2/3/4の段階間で交通量分布が単調に
分離しているか）。分離が悪い場合は`TRAFFIC_STRESS_BASE_BY_HIGHWAY`・補正規則の見直し
材料とする。研究IF Phase2の比較環境に結果を接続。
