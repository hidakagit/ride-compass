# 評価モデルの層構造（概観）

「この道は走りやすいか」を数字にするまでの段。**実装粒度はここには無い**——材料の解決から
合成コストまでは[評価・スコアリング](../modules/backend/evaluation-scoring.md)、軸の定義と
評価式は[軸スタジオ・評価軸定義](../modules/backend/axis-studio.md)が持つ。

非技術者向けの説明は[how-route-scoring-works-plainly.md](../how-route-scoring-works-plainly.md)。

## 4つの段

```
0次: ハード制約   そもそも探索グラフへ入れるか（スコアに一切登場しない）
      ↓
1次: 材料         道路そのものの正規化された値（路面・車線数・停止要因の密度・勾配・風…）
      ↓
2次: 評価軸       材料を束ねて 0〜100 の difficulty にする単位。軸スタジオが管理する
      ↓
3次: 合成コスト   公開軸を利用者の重みで合成し、所要時間へ割増として掛ける
```

**この4段はそれぞれ変える人が違う。** 0次と1次は「事実をどう取るか」でコードが決め、
2次（軸の形）は管理者が軸スタジオで決め、**重みだけが利用者のもの**である。

## 段ごとの性格

- **0次は0/1で、重みを持たない。** 該当した道路は探索グラフに入らず、コストも
  difficultyも持たない。「通行できない」と「走りにくい」を混ぜないための分離で、
  後者は必ず2次以降で表す。
- **1次は正規化された生データに限る。** 人間が読むための分類ラベル（「自転車レーンあり」
  のような優先順位付きの多値）は材料にしない。分類の順位付けが軸の重み付けと二重になる。
- **2次の軸は単体で評価できる。** ある軸の良し悪しは、その軸が出す値だけで判断できる
  ようにする（[設計原則](design-principles.md)構造仕様11）。軸どうしの依存は、
  非公開の内部軸を公開軸の材料として参照する階層でのみ表す。
- **3次は掛け算である。** コストは `所要時間 × (1 + P × difficulty/100)` で、
  難易度は所要時間への割増として効く。**物理の損失（実際に時間を失う）は走行モデルが
  持ち、主観の損失（同じ時間でも嫌さが違う）が軸**という分担で、両方を持つ現象
  （風・勾配・停止の待ち）の軸の既定重みは0にする——二重計上は利用者が重みを上げるという
  明示的な選択の結果でなければならない（構造仕様13）。

## 軸の数も名前もコードに無い

公開軸の一覧・axis_id・既定重みは`axis_definitions`テーブルが持ち、軸スタジオのGUIから
増減する。**コード変更もデプロイも伴わない**ため、この文書にも軸の一覧を置かない
（現物は`GET /api/axis-catalog`で引く）。

軸を1つ足すときに通る道は1本だけで、取込の宣言 → 派生 → 材料の値式 → 軸定義、
と進んで frontend には何も足さない（構造仕様3）。

## 得点と生値を両方返す

0〜100の得点は目盛りの引き方に依存する相対評価で、同じ生値でも区間として見るかルート
平均として見るかで意味が変わる。そのため得点の隣に、目盛りに依存しない**生値**（折れ点を
通す前の値）を単位付きで添える。単位が定まらない合成軸は、代わりに材料まで分解した
絶対量を返す。
