# T605. 恒久404（疎な格子・整備区域外）の未キャッシュ問題の横展開是正

状態: 完了（2026-09-05）

## 背景

T603で「JMAタイルの404は珍しくない正常系」として502/WARNING扱いを是正したが、ユーザーから
「疎な格子状タイルを受け取ったときどうあるべきか検討した？」との指摘。404そのものは
`log_external_call`のerror集計から外したが、確認済みの404を一切キャッシュしていないため、
同じ欠損タイルへ毎回上流へ問い合わせ続けてしまう（`elevation_client.py`の`_CoverageGap`と
同じ思想が必要）。他の外部クライアントで同種の問題が無いか監査した上で是正する。

## 監査結果（他の外部クライアントへの横展開要否）

| クライアント | 判定 | 理由 |
|---|---|---|
| `jma_tile_client.py` | 要対応 | 降水・浸水想定区域等の疎な格子状タイル。ズーム/場所によって存在しないz/x/yが珍しくない正常系（T603の対象そのもの） |
| `gsi_relief_tile_client.py` | 要対応 | 色別標高図の整備区域外（404）が珍しくない正常系。`elevation_client.py`のDEMタイルと同じGSIホスト・同じ状況 |
| `elevation_client.py` | 対応済み（既存） | `_CoverageGap`センチネルで既に同じ設計を実装済み。今回の実装はこれを参照実装として踏襲した |
| `basemap_client.py` | 対応不要 | OpenFreeMapは惑星全体を1つのタイルピラミッドとして配信する構成で、JMA/GSIのような地理的な疎さ（未整備区域）を持たない。スタイルJSON・スプライト・グリフ・タイルの404はズーム範囲外リクエストや上流障害等の異常系である可能性が高く、他の失敗と区別せずerror集計・WARNINGへ乗せる現状の扱いのままで妥当と判断し、変更していない |

## 対応方針・実装内容

`jma_tile_redis_cache.py`に`TileNotFound`センチネル（`TILE_NOT_FOUND`）と`set_not_found(path)`を
追加。実際のタイル本体と同じキー・TTL（20分）で`{"not_found": true}`を保存し、`get`がこれを
検知すると`TILE_NOT_FOUND`を返す。`jma_tile_client.py`の`fetch`は404確認時に
`targetTimes*.json`ならプロセス内`TTLCache`へ直接`TILE_NOT_FOUND`を、それ以外は
`jma_tile_redis_cache.set_not_found`を呼ぶ。`get_cached`/`get`は`TileNotFound`を受け取ると
呼び出し元の契約に応じて使い分ける（`jma_tile.py`はそのまま404を返す、`get`経由の呼び出し元
[プリウォームバッチ等]は従来通りNoneへ揃える）。

`gsi_relief_tile_client.py`は`elevation_client.py`の`_CoverageGap`と同じ設計で
`ReliefTileNotFound`センチネルを新設。確認済み404はプロセス内メモリのみ（上限付きLRU、
`tile_cache.py`の永続ファイルキャッシュへは書かない）に記憶し、GSI側の整備区域が将来
広がった場合にプロセス再起動だけで再取得の機会が来るようにした。
