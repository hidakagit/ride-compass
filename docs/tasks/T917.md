# T917. 路面タイルをedge単位にしたときの費用を測る

状態: 完了（2026-09-17）
規模: S

## 背景

ユーザー指摘「今後、edge単位の情報をフロントが知っていたほうがいいこともあるのではないかと
思っている。地図上の区間毎の向かい風、区間毎の予想速度や時間など」。

同じ「区間ごとの値」に**2つの世界がある**。

| | ルート確定前 | ルート確定後 |
|---|---|---|
| 単位 | way丸ごと（タイルが`osm_raw_ways`由来） | 区間（`RouteSegmentDetail`、geometry付き） |
| 値 | 代表edge1本の近似×cos(走行方位)（`DISTINCT ON (re.osm_way_id)`） | その区間の実進行方向・実到達時刻での実値 |
| 経路 | `GET /api/region/dynamic-way-values`（way_id→値） | ルート応答に同梱（`axis_difficulties`） |

**backendは最初から全部edge単位で計算している**（`road_edges`・`elevation_attributes`）。
way単位は、タイルがway geometryしか持たないせいで表示の直前に落としている射影である。
このまま区間ごとの値（向かい風・予想速度・時間）を足すと、ルート前用のway近似とルート後用の
区間実値を毎回2つ作ることになり、[design-principles.md](../design-principles.md)構造仕様3・8
（追加点は1本道）から離れていく。

単位を揃えられるかは**タイルがどれだけ重くなるか**で決まる。モバイルで使うアプリのため、
ここを推測で決めない。移行の可否を決めるための計測だけを先に行う。

## 測るもの

`backend/benchmarks/bench_t917_edge_tile.py`（実DB・実データ）。

- **大きさ**: 同じタイルをway版・edge版で焼いたときの生バイト数・**gzip後のバイト数**・
  フィーチャー数。本番はベクタタイルを圧縮して配信するため、**判断はgzip比で行う**
- **生成時間**: 同じSQLの実行時間（キャッシュを経由しない生の生成）
- **重複**: `road_edges`はforward/backwardを別行で持つ。両端ノードの組
  （`LEAST/GREATEST(from_node_id, to_node_id)`）で排除した場合の数も併せて出す。
  **geometryの正規化では見分けられない**——`ST_Normalize`はLINESTRINGの向きを揃えない

対象は道路密度の異なる9タイル（東京駅・板橋区・八王子のz12〜15）。密度が費用を決めるため
1タイルでは判断しない。

プロパティは3版とも同じ集合へ揃えてある（比べたいのは単位の違いであってプロパティの多寡では
ない）。本番タイルはLEFT JOINでより多くの列を持つため、**絶対バイト数は本番と一致しない。
way比だけを判断に使う**。

## この計測では扱わないこと

way単位で意味を持つ材料（`intersection_count_per_km`等、way全体を母数に数えた値）をedgeへ
複製したときの意味のずれ。数字が許容範囲だった場合に、移行タスク側で判断する。

## 実行方法

`backend/`ディレクトリから、`DATABASE_URL`をローカルDBへ上書きして:

```
python -m benchmarks.bench_t917_edge_tile
```

## 1回目の計測（2026-09-17）と、そこで見つかった器の欠陥

非圧縮バイト数は取れたが、**2つの欠陥で判断材料として不完全だった**。

**生成時間は測れていなかった。** `DISTINCT ON`のサブクエリの外に空間フィルタを置いていたため、
タイルごとに`road_edges`を全件重複排除してから絞っていた。どのタイルでも8.3〜9.8秒と
**タイルの中身に依存しない一定値**だったのがその証拠（両方向そのまま版は0.010〜0.446秒で、
単純なサブクエリのため空間索引が効く）。同じ物理区間の両方向は同じ形状のため、先に絞ってから
重複排除しても結果は変わらない。フィルタをサブクエリ内へ移した。

**転送量で測れていなかった。** 本番は`response_compression.py`がベクタタイルを
gzip（compresslevel=3）して返す。重複したプロパティ索引はよく縮むため、**生バイトの比率は
転送量の比率を過大に見せる**。同じcompresslevelで縮めた後のバイト数を併記するようにした。

対象タイルも9件へ増やした（z14/z15を厚くした。境界をどこに置くかの判断材料）。

### 1回目の生バイト（比率は再計測で置き換える）

| ズーム | way | edge（重複排除） | 生バイト比 |
|---|---|---|---|
| z15 | 7,449 | 11,901 | 1.60x |
| z14 | 23,392 | 41,533 | 1.78x |
| z13 | 180,554 | 422,547 | 2.34x |
| z12 | 593,709 | 1,526,838 | 2.57x |

**起票時の見積もり（+20〜40%）は外れていた。** MVTがプロパティを辞書で共有するから安い、
という読み自体は当たっていたが、効いていたのは分割による頂点の重複とフィーチャーヘッダの方で、
低ズームほどwayが長く交差点を多く跨ぐため比率が上がる。

重複排除は両方向版から30〜50%落としており、両端ノードの組による判定は期待どおり効いている。

配信範囲はz12〜15（`ROAD_TILE_MIN_ZOOM`/`MAX_ZOOM`）のため、z12の値は本番の話である。
**way版の593KBも既に重い**ことが併せて見えた。

### 読み取ったこと

**gzip後の比率は生バイトより小さい**（1.23〜1.81倍、生バイトでは1.60〜2.57倍）。
重複したプロパティ索引はよく縮むため、生バイトで判断していたら費用を過大に見積もっていた。

**費用と情報量がズームで逆向きに効く。** gzip比はz15の1.23〜1.56倍からz12の1.81倍まで
上がる（低ズームほどwayが長く交差点を多く跨ぐため分割数が増える）。一方z12は1pxが約38mで、
交差点で切った区間は数pxにしかならず塗り分けても読めない。**費用が跳ね上がるズームと、
区間単位の情報量が消えるズームが一致している**——境界をz14に置く根拠はこれである
（z14+1画面9タイルで+90KB、z12なら+2.4MB）。

**生成時間は問題にならない**（重複排除版で最大0.391秒、z14以上では0.022秒以下）。
1回目に見た8.3〜9.8秒は器の欠陥（空間フィルタの位置）だった。

**重複排除は期待どおり効いている**（両方向版から30〜50%落とす）。

なお重複排除の鍵は、この計測の後に[T918](T918.md)段階1で
`(osm_way_id, LEAST/GREATEST(node))`へ直した（両端ノードの組だけを鍵にすると、同じノード対を
共有する別のwayまで潰れる）。**上表の重複排除後のフィーチャー数はわずかに少なく出ている**
——比率の大小関係と境界の判断は変わらない。

移行は[T918](T918.md)で実施した。
