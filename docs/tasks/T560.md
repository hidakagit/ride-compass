# T560: 周期レビュー（`/review:all`）の負荷軽減——トリガー見直しと機械的チェックのスクリプト化

状態: 完了（2026-09-03）

## 背景

2026-09-03の`/review:all`第4回は、Explore Agent 16件の同時起動でAPIのセッション上限に
当たり中断し、sonnetへ引き継いで4〜6件ずつ直列化して再開したところ、完走まで約40分
（中断前の作業を含めると2時間超）を要した。ユーザーから「負荷が高すぎて現実的でない」と
指摘を受けた。原因は個々のAgentの遅さではなく仕組み側にある:

- **トリガーが早すぎる**: 「20タスク完了」条件が、このプロジェクトのタスク粒度
  （3日で約100件完了）では3日ごとに発火する（第3回2026-08-31→第4回2026-09-03）。
- **毎回フル構成**: 差分の大小に関係なく8フェーズ・4レンズ・14シャードを全部回す。
- **同じファイルをoverallとconsistencyが別々のAgentで読み直す**: ドメインシャード7件×2レンズ
  =14件のExplore Agentを直列化するだけで1時間を超える。
- **機械化できる作業をAgentでやっている**: 死んだ参照・新規ファイルの記載漏れ・状態行の照合・
  規模ウォッチの実測・メトリクスは、スクリプトで数秒で終わる。

## 対応方針（ユーザー承認済み: 案1・案3、および「同じファイルを4回読む」への対処）

1. **トリガーの見直し**（`.claude/commands/review/README.md`「定期的なレビュー」節）:
   「7日 or 20タスク」→「**14日経過** or **実装コード（テスト・生成物除く）の変更行数が
   前回レビューの対象コミットから20,000行以上**（挿入＋削除）」。分割元タスク完了直後の
   条件は維持。閾値の較正: 第3回→第4回（`cab1441..89c94cd`、3日間）の実装変更は
   11,548行だったので、現在の異常に速いペースでも約5日、通常ペースでは14日側が先に来る。
   判定は`python scripts/review_checks.py trigger`で機械的に行う。
2. **機械的チェックのスクリプト化**（`scripts/review_checks.py`、標準ライブラリのみ）:
   - `docs`: docs/modulesの死んだ参照・記載粒度違反・新規実装ファイルの記載漏れ、
     improvement-plan.mdの`[x]/[ ]`とdocs/tasks「状態:」行の照合、history/・docs/tasksへの
     死んだリンク（consistency.md「設計 ↔ 実装」節の機械的部分＝旧C8シャード）。
     `--staged`をpre-commit（`scripts/pre-commit-docs-consistency.sh`、`pre-commit.sh`へ追加）から
     呼び、新しく書き足した行・新規ファイルだけを止める（既存違反で無関係なコミットを
     止めない）。全件監査は`/review:consistency`実行時に結果を貼る。
   - `size`: 規模ウォッチ表（complexity.md）。前回値と個別閾値を
     `history/size_watch.json`に持ち、+15%／1,000行超過／上位新規登場／閾値超過を判定する。
     レビュー完了時に`--update`で前回値を更新する。
   - `metrics`: 定量メトリクス（metrics.md）。`--full`でテスト件数・tsc/eslint・npm auditも計測。
   - `trigger`: 上記1の判定。
3. **overallとconsistencyのシャード共有**（`principles.md`共通実行手順4d、`all.md`）:
   `/review:all`で両レンズを同時に回すときは、ドメインシャードを1回だけ切り、1シャード1Agentへ
   両レンズの観点を渡して**レンズごとに独立した節**で出力させる（14件→7件）。レンズ構造を
   ドメイン構造へ置き換えない2026-08-31のルールは維持（集約はレンズ単位で行う）。
   「差分だけ読む」方式は、2026-08-30に「全件・全文を読む」へ改めた経緯（サンプリングで
   P0/P1がゼロになった）と矛盾するため採らない。

見送った案（ユーザー未承認のまま）: 案2「常設の軽量版（consistencyのみ）とフル版の分離」。
軽量化のデメリット（overallが担う局所最適の連鎖・重複実装の検出と、Phase 7の相互矛盾の
統合判断が周期から抜ける）を判断材料として提示済み。
