# T855. 難易度の帯へ距離の次元を与え、面積で負荷を表す

状態: 完了（2026-09-14）
規模: M

当初T854で採番したが、並行セッションが同番号を先にmasterへ載せたためT855へ振り直した。

## 背景

総合難易度（距離加重平均）と負荷（平均×距離）が、候補パネルに別々の数字として
並んでいる。後者は前者から距離を掛けただけの派生量のため、2つ並ぶと「どちらが
このルートの評価なのか」が読み取れない（ユーザー指摘「総合難易度の位置づけが
分からなくなってきた。負荷で代替してよくない？」）。

負荷で代替はできない——区間の色分け・軸別内訳の合計一致・実験間の比較は、いずれも
距離で正規化された0-100の絶対基準を必要とする。

## 対応方針

`AxisContributionBar`の帯は、すでに長さが総合難易度を表している（幅100%＝難易度100の
目盛りで、余りが下地として見えている）。ここへ高さ＝距離を与えると、塗られた矩形の
面積がそのまま負荷になり、色ごとの面積が軸別の負荷になる。数字を1つ減らすのではなく、
1つの図が両方を持つ形にする。

## 実装

- `frontend/src/lib/difficultyLoadBar.ts`（新規）: `baselineDistanceKm`（高さ1.0とする距離＝
  一覧の中で最も短い候補）と`loadBarHeightRatio`（基準に対する比を1.0〜
  `LOAD_BAR_MAX_HEIGHT_RATIO`へ収める）。基準を一覧の中だけで決めるのは
  `routeTabLabel.ts: fastestRouteId`と同じ理由——目標距離やbackendの値から取ると、周回
  モードと目的地モードで基準の意味が変わる。
- 帯の高さはCSSカスタムプロパティ`--load-bar-height-ratio`で与える（既定1.0は各CSSが
  持ち、倍率を渡さない呼び出し側＝区間の内訳は従来どおりの帯になる）。`page.tsx`が一覧の
  行（`outcomeTabScoreTrack`）と候補の中身（`RouteAxisProfile`→`AxisContributionBar`）へ
  同じ基準で計算した倍率を渡す。
- 一覧の行のバーは角丸（999px）をやめた。高さが可変になると、丸めた形は「太さの違う
  スイッチ」に見えて長さ×高さの矩形として読めない。
- (i)の説明に、バーの読み方（長さ＝総合難易度／高さ＝距離／面積＝負荷、色ごとの面積が
  軸別の負荷）を足した。上限で頭打ちにするぶん面積の比は負荷の比と完全には一致しないため、
  負荷の数値は併記したまま残す。

## 検証

- `npx vitest run src/lib/difficultyLoadBar.test.ts`（7件）、
  `AxisContributionBar.test.tsx`（14件）、`page.test.tsx`の新規1件。
- 効いていることの確認: `loadBarHeightRatio`の比の計算をわざと`1`固定へ壊すと、
  純関数のテスト2件と`page.test.tsx`の新規1件が落ちる（`expected '1' to be '2'`）ことを
  見てから戻した。
- 実機（headless chromium、開発DB・35.66/139.70・16km周回で8候補）: 一覧の行の倍率は
  1.00〜1.53（高さ5.6〜8.6px）、選択中候補の内訳バーは1.23（12.3px）。距離が長い候補ほど
  厚い矩形になり、総合難易度が低くても面積が大きい候補（例: 14.8km/難易度61 と
  12.1km/難易度69）が一覧の中で見分けられる。

## 残り

- 周回モードでは候補の距離が目標距離の近傍へ集まるため、高さの差は小さい（上記実機でも
  1.0〜1.53）。負荷の違いが視覚として大きく出るのは目的地モードと、距離を変えて生成し
  直したときの比較。これは表現の問題ではなく候補集合の性質のため、対応しない。
