## 材料辞書統合＋EdgeCostResult.model_construct化（2026-09-01、T533派生）

T529実装（rustworkxのlazy A*、探索が実際に訪れたEdgeのみコスト計算）後も、Edge単位の
コスト計算自体（`compute_edge_cost`）がなお1リクエストあたり最大24回×訪問Edge数ぶん
呼ばれるホットパスであるため、その内部を実データ（渋谷相当bbox、24.7万Edge、
ローカルdev DB）で検証した。

1. **材料辞書の統合（EdgeMaterialBundle）**: `get_edge_materials_batch`（T248で
   クエリ自体は1回のJOINへ統合済み）が戻り値だけ4つの辞書（surface_attributes/
   edge_attribute_counts/way_tags/elevation_attributes）+designated_edge_idsの集合へ
   再分割していた技術的負債を発見し、Edge ID→統合済み1オブジェクト
   （`@dataclass(frozen=True, slots=True)`のEdgeMaterialBundle、`domain/attributes.py`）
   へ書き換えた。**実測: 辞書アクセスのみを切り出すと3.5倍速いが、`compute_edge_cost`
   全体を通した公平な比較では速度差はほぼ無かった（1.02倍、誤差の範囲）**——
   `compute_edge_cost`自体の内部処理（軸別スコア算出）が支配的で、辞書アクセスの差は
   誤差に埋もれるため。ルーティングの速度改善への寄与は見込めないが、T248の技術的
   負債是正・コードの一貫性向上として実施価値ありと判断し実施した（同種の負債が他にも
   無いかの横断監査は[T533](T533.md)として別途起票済み）。
2. **EdgeCostResult.model_construct化**: cProfileで内部プロファイリングした結果、
   bulk版`compute_edge_costs_bulk`は既に`EdgeCostResult.model_construct(...)`で
   Pydanticバリデーションをスキップしていたが、実際の探索ホットパスで使われる
   スカラー版`compute_edge_cost`だけが通常のフルバリデーション付きコンストラクタを
   使っていた不整合を発見。同じ`model_construct`パターンへ揃えた（渡す値はすべて
   内部計算済みの正しい型で、numpy値の混入が無いことも`evaluate_breakpoint_linear`の
   `float(...)`明示キャスト等で確認済み）。**実測: 24.7万Edge全件のcompute_edge_cost
   実行がmedian 6026ms→5564ms（約1.08倍、8%改善）**。

いずれもバックエンド全体1229件green（`pytest -q -m "not postgis"`）。本番未反映
（次項で反映・サンプリング実測予定）。

`compute_edge_axis_scores`自体（軸別スコア算出、タグ正規化）が`compute_edge_cost`の
累積時間の6割超を占め、これは評価ロジックそのものであり軸スタジオの自由度を保ったまま
安全に削れる部分ではない。副次的に`topological_axis_order`のキャッシュキー計算
（`AXIS_DEFINITIONS`全軸を毎回舐めてタプルを組み立て直す処理、呼び出しごとに約4us）も
見つかったが、`AXIS_DEFINITIONS`が複数のテストファイル・本番の`refresh_axis_definitions`
から直接`clear()+update()`で書き換えられる構造のため、安全な高速化には軸定義変更の
検知機構自体の設計変更が必要で、効果（全体の5%程度）に見合わないと判断し見送った。

## 本番環境での再現・内訳調査（2026-09-01）

開発機での251秒・355秒という実測が開発機固有のリソース競合（並行Claude Codeセッション等、
[[parallel-worktree-resource-contention]]参照）によるものか切り分けるため、本番
（Oracle VM、`https://193.123.166.150/`、backend/.env.oracle.localのSSH鍵で接続）へ
直接`POST /api/routes/generate`を2回投げ、`GET /api/admin/debug/logs`
（Basic認証、`ridecompass-backend.env`に`ADMIN_BASIC_AUTH_USERNAME=admin`/
`ADMIN_BASIC_AUTH_PASSWORD=admin`——**この認証情報が極めて弱い値である点は本タスクの
スコープ外の別問題として後述**）で実測ログを取得した。起点・距離は開発機と同一
（`(35.6817502, 139.7634149)`・周回30km）。

**1回目（未split・冷パス、`req:c2e14abc7655`）**: `total_ms=103590`
（`prepare_ms=77686 trace_ms=15382 evaluate_ms=10521`）。開発機の251〜355秒より
明確に速いが、依然として支配的にprepareが遅い。ログのタイムスタンプから、
`prepare_ms=77686`の内訳は次のとおりほぼ全て説明できた（`GraphService.
get_or_build_graph_with_attributes`の既存ログ+ログ間のタイムスタンプ差分で算出）:

| ステージ | 所要時間 | 内容 |
|---|---|---|
| `_ensure_tiles_cached`+`_ensure_split_up_to_date`（2回、後述） | 約63ms | Redis cache-aside+PostGIS `LIMIT 1`判定。無視できる規模 |
| `get_way_specs_with_closure`（closure_ms） | 9,918ms | bbox内Way＋近傍Wayの取得（このbboxはway=107,328件） |
| `build_road_graph`（build_ms、`asyncio.to_thread`保護済み） | 8,790ms | 交差点分割（CPU） |
| `save_graph`（save_ms） | 26,946ms | 分割結果の永続化。primary_edges=333,529・primary_ways=82,840・nodes=128,524。**単独最大のステージ** |
| `get_edge_materials_batch`（materials_ms、uncachedフォールバック経路） | 17,428ms | 333,529 Edge分のsurface/attribute_counts/way_tags/elevation/designated一括取得 |
| **無計測の残差**（wind取得＋evaluate_graph＋build_sparse_graph＋prepareの索引構築） | **約13,821ms** | ログのタイムスタンプ差分（materials_ms終了18:27:19.566〜prepare終了推定18:27:33.387）から逆算。後述の追加計測で正式に内訳化した |

（`get_way_specs_with_closure`〜`save_graph`は`get_or_build_graph_with_attributes`の
`rebuild`ログ1行に`closure_ms=9918 build_ms=8790 save_ms=26946 total_ms=46200`として
まとまっている。`_build_search_materials_uncached`の`materials_ms=17428`と合わせて
63,628ms、`prepare_ms`全体77,686msとの差13,821msが上表の残差）

**この無計測の残差＝evaluate_graph（探索コスト計算、333,529 Edge対象）・
build_sparse_graph・`prepare()`内の索引構築（`build_node_spatial_index`・
`_build_node_pair_index`）は、いずれも同期関数で`asyncio.to_thread`による保護が
無い**——`get_or_build_graph_with_attributes`の`build_road_graph`が同種の理由
（改善計画T261、T105のCPU専有→ヘルスチェック無応答→強制再起動と同型の障害を受けた対応）で
`asyncio.to_thread`化済みなのと対照的。つまりこの約13.8秒間、実行中のuvicornワーカーの
イベントループが丸ごと塞がれ、他の同時接続リクエスト（`/health`含む）も応答できない
状態になっている可能性が高い。

**2回目（split済み・タイルキャッシュ経由、`req:e82585369dc4`、1回目の約5分後）**:
`total_ms=24744`（`prepare_ms=23510 trace_ms=820 evaluate_ms=414`）。ログに
`get_or_build_graph_with_attributes rebuild`も`_build_search_materials_uncached`も
出現せず、想定どおり高速経路（`_build_search_materials_from_tile_cache`）を通った。
**それでも`prepare_ms=23510`と、`graph_service.py`のdocstringが述べる「真の温パス
4.9秒」（改善計画T248、別の小規模エリアでの実測）よりはるかに遅い**——これは、
上記「無計測の残差」約13.8秒（evaluate_graph等のCPUバウンド処理）がキャッシュの有無に
関わらず発生する固定コストであり、この規模（Edge数十万件級）のbboxでは温パスでも
下限として乗ってくることを示唆する（DB/タイルキャッシュがどれだけ効いても、
このCPU計算自体を高速化・並列化しない限り数秒〜十数秒を切れない）。

**開発機の「2回目(355秒)が1回目(251秒)より悪化」という異常は本番では再現しなかった**
（本番2回目は1回目の1/4以下に短縮）。これは開発機固有のリソース競合が2回目悪化の
主因であり、コード自体の欠陥ではない可能性を支持する（引き続き確定はできないが、
本番の一貫した挙動がより信頼できるシグナルと考える）。

Redis経由キャッシュの失敗（`[cache:edge-geometry-redis] failed after 605ms/2742ms`、
`タイル材料キャッシュのバックグラウンド温めに失敗 error=TimeoutError()`×2）も本番で
確認できたが、いずれも`prepare_ms`ではなく`trace_ms`区間・レスポンス送出後の
バックグラウンド処理で発生しており、影響は数秒未満に留まる——Redisが主因でないという
既存の結論（下記）を追認するのみ。
