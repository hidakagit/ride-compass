# T522: ルート生成が異常に遅くなる事象の調査（prepare段階＝探索用グラフ構築が支配的）

状態: 調査継続中（2026-09-01起票、同日中にbackendの構造化ログで原因箇所を特定）

- 背景: T518の実機確認中（開発機、中心部東京30kmループ生成）、通常想定より大幅に遅い
  （3〜6分）ルート生成に遭遇した。当初`GET /api/debug/stats`でRedisキャッシュ呼び出しが
  軒並みTimeoutErrorだったことから「Redis疎通不能→高コストな直接計算のfallback多発」を
  主因と推測したが、`GET /api/admin/debug/logs`（T517、Basic認証必須。認証情報は
  backend/.env: ADMIN_BASIC_AUTH_USERNAME/PASSWORD）で`route_generator.py`の
  ステージ別所要時間サマリログ（`generate engine=... prepare_ms=... trace_ms=...
  evaluate_ms=... total_ms=...`）を直接確認したところ、**この当初の推測は誤りだった**
  ——Redisは主因ではなく、`prepare()`（探索用グラフ構築、`road_graph_engine.py:
  _build_search_graph`／`GraphService.get_search_materials_for_bbox`）自体が支配的に
  遅いことが判明した。

- **実測ログ（2026-09-01、backend構造化ログより該当4件を全件引用）**:
  ```
  02:24:57 origin=(35.68,139.76) target_km=30.0 -> candidates=6
    prepare_ms=251140 trace_ms=20891  evaluate_ms=39188 total_ms=311219
  02:34:20 origin=(35.70,139.74) target_km=30.0 -> no context (road data unavailable)
    prepare_ms=219
  02:39:57 origin=(35.73,139.71) target_km=30.0 -> no context (road data unavailable)
    prepare_ms=16
  03:00:48 origin=(35.68,139.76) target_km=30.0 -> candidates=6
    prepare_ms=355516 trace_ms=2844   evaluate_ms=2265  total_ms=360625
  ```
  - 候補が実際に見つかった2件（同一起点で2回）は、**`prepare_ms`だけでtotal_msの
    80〜99%を占める**（251.1秒/311.2秒＝81%、355.5秒/360.6秒＝99%）。`trace_ms`
    （8方位のDijkstra探索）・`evaluate_ms`（候補評価・軸別difficulty計算、Redis
    キャッシュのfallback先である`region:gradient-way-values`/`region:wind-way-penalty`
    はこの中に含まれる）は、2回目にいたっては合計5秒程度に過ぎず、遅延の主要因ではない。
  - **「起点付近の道路データが未整備」（no context）の2件は`prepare_ms`が16ms・219ms
    と極めて高速**——ユーザー質問への回答: 道路データ未整備そのものは遅延の原因では
    なく、むしろ最速で終わる経路（グラフ構築の入口で早期return）である。今回「文京区
    付近が遅いのでは」という懸念は誤りだったと判明した。
  - 2回目（355.5秒）が1回目（251.1秒）より悪化している点は、プロセス内タイル単位
    キャッシュ（`_build_search_graph`のdocstring「同一エリアへの2回目以降のリクエストは
    DBへ一切アクセスしない」という設計意図）が実際には効いていない、または他の要因で
    上書きされていることを示唆する——本タスクの主要な未解明点。

- 分かっていること:
  - Redisサーバー自体は健全（生TCPで`127.0.0.1:6379`へ直接PINGを送ると即座に`+PONG`が
    返る、過負荷やダウンではない）。`app/infrastructure/redis_client.py`は接続・応答
    タイムアウトを意図的に0.2秒へ短縮設定済み、10秒のサーキットブレーカーも実装済みで、
    `dynamic_way_value_cache.py`のfail-open設計も仕様通り機能している——Redis周りは
    実装上の欠陥ではなく、**当初の主因という推測自体が誤りだった**（stats単体では
    「エラー件数」しか見えず、「そのエラーが遅延の何%を占めるか」を見誤った）。
  - `prepare()`＝`_build_search_graph`＝`GraphService.get_search_materials_for_bbox`
    （bbox内のトポロジ＋材料をz12タイル単位のプロセス内キャッシュ経由で取得）が支配的に
    遅い。半径計算は`radius_km = distance_km/3`・`margin_km = max(2.0, radius_km*0.3)`
    （`route_generator.py`: `RADIUS_RATIO`・`road_graph_engine.py`: `BBOX_MARGIN_RATIO`/
    `BBOX_MARGIN_MIN_KM`）で、30km指定なら半径約13kmのbbox（中心部東京の稠密な道路網を
    広範囲にカバーする規模）になる。
  - 背景で`jma_tile_prewarm_service`（T509系、約10分間隔で1983タイルを毎回フル取得、
    1回34〜94秒）が動いている。1回目の生成（02:19:46頃〜02:24:57）とは時間的に重ならず、
    2回目（02:54:48頃〜03:00:48）は02:58:44完了の予熱ラン（開始約02:57:10）と一部
    重なるが、重なりは94秒程度に留まり355秒の遅延全体を単独では説明できない——
    寄与している可能性はあるが主因と断定はできない。
- 分かっていないこと（要調査）:
  - `get_search_materials_for_bbox`のプロセス内タイルキャッシュが実際に機能しているか
    （同一bboxへの2回目の呼び出しがなぜ悪化したのか）。キャッシュの生存期間・キー設計・
    プロセス再起動有無を要確認。
  - `prepare()`内部でどのステップ（DB問い合わせ・グラフ構築・`evaluate_graph`でのコスト
    計算・`build_sparse_graph`）が具体的に何秒かかっているかの内訳が無い——現状の
    ログは`prepare_ms`を1つの塊としてしか出していない。ステージをさらに細分化した
    タイミングログが要る。
  - 本番環境（OCI VM）でも同様の事象が起きうるかは未検証。開発機固有のリソース競合
    （並行Claude Codeセッション等、[[parallel-worktree-resource-contention]]参照）が
    寄与している可能性はあるが、`prepare_ms`が総時間の8〜9割を占めるという構造自体は
    リソース競合の有無に関わらず起きうる問題に見える。
  - ユーザー体験への影響範囲: 中心部東京・30km・周回モードでのみ確認。距離が短い場合や
    データ密度が低いエリアでも同程度の`prepare_ms`が発生するのか（bbox内の道路密度に
    比例するなら、都心以外では問題にならない可能性がある）は未確認。
- 次の調査候補:
  1. `_build_search_graph`/`get_search_materials_for_bbox`内部にステージ別タイミング
     ログを追加し、DB問い合わせ・グラフ構築・コスト計算のどこが支配的かを特定する。
  2. 同一bboxへの2回目呼び出しがプロセス内キャッシュを実際にヒットしているか
     （ログ・キャッシュヒット率）を確認する。
  3. 他セッションが稼働していない静かなタイミングで同じ生成を再実行し、`prepare_ms`が
     改善するか（＝リソース競合の寄与度）を確認する。
  4. 距離・エリアを変えた複数条件で`prepare_ms`を比較し、道路密度との相関を確認する。

- **再現条件（2026-09-01実測、開発機）**: 起点座標`(35.6817502, 139.7634149)`
  （千代田区・両国寄り、周回モード・距離30km・既定重み）で2回generateを実行し、
  backendログの`prepare_ms`実測値で**251秒・355秒**（いずれも候補は6件生成に成功）。
  起点座標`(35.70,139.74)`・`(35.73,139.71)`（いずれも文京区付近、同条件）は
  「起点付近の道路データが未整備」で`prepare_ms=219ms`・`16ms`という対照的な速さで
  早期終了した——両者の差は「候補探索に入れたかどうか」であり、道路データの疎密自体は
  低速要因ではない。
