# T522: ルート生成が異常に遅くなる事象の調査（Redisキャッシュ全滅→高コストな直接計算の多発）

状態: 調査継続中（2026-09-01起票）

- 背景: T518の実機確認中（開発機、中心部東京30kmループ生成）、通常想定より大幅に遅い
  （3分以上）ルート生成に遭遇した。`GET /api/debug/stats`を確認すると、Redisバックエンドの
  外部呼び出し（`cache:dynway-wind-redis`・`cache:dynway-gradient-redis`・
  `cache:edge-geometry-redis`・`cache:road-tile-redis`等）が軒並み100%`TimeoutError`
  だった。一方で`region:gradient-way-values`（238回、合計約188秒）・
  `region:wind-way-penalty`（238回、合計約117秒）という直接計算（Redisキャッシュがヒット
  しない場合のfallback経路）の累計時間が、体感の遅延（3分超）とほぼ一致した。
- 分かっていること:
  - Redisサーバー自体は健全（生TCPで`127.0.0.1:6379`へ直接PINGを送ると即座に`+PONG`が
    返る、過負荷やダウンではない）。
  - `app/infrastructure/redis_client.py`の接続・応答タイムアウトは意図的に0.2秒へ短縮
    設定済み（本番はOCI VM上で`--network=host`前提）、10秒のサーキットブレーカー
    （`redis_available()`/`_CIRCUIT_COOLDOWN_SECONDS`）も実装済みで、単純な「タイムアウト
    設定漏れ」ではなさそう。
  - `app/infrastructure/dynamic_way_value_cache.py`はRedis失敗時fail-open（未キャッシュ
    として直接計算へフォールバック）する設計で、フォールバック自体は仕様通り動作している。
  - 遅延の直接原因は「Redisキャッシュが1件もヒットせず、`region:gradient-way-values`/
    `region:wind-way-penalty`という比較的重い直接計算を候補ごとに238回ずつやり直して
    いる」こと。
- 分かっていないこと（要調査）:
  - **なぜRedisクライアントが疎通できていないか**が未確定。開発機で`node.exe`6個・
    `python.exe`2個（backendが899MB）が同時稼働・全体CPU使用率約40%という状況を確認して
    おり、他の並行Claude Codeセッション/devサーバーとのCPU競合でbackendのasyncio
    イベントループが遅延した可能性を仮説として持っているが、実証はできていない
    （[[parallel-worktree-resource-contention]]参照）。他の可能性（長時間稼働している
    開発用backendプロセスでのRedis接続プールの劣化、redis-pyクライアント側の別の問題等）も
    否定できていない。
  - 本番環境（OCI VM、`--network=host`）でも同様の事象が起きうるかは未検証。開発機固有の
    リソース競合が原因であれば本番非該当の可能性が高いが、断定するにはCPU負荷が低い
    タイミングでの再現確認、または本番の`/api/debug/stats`実測が必要。
  - ユーザー体験への影響度: 開発機で30km・中心部東京という重めの条件でのみ確認しており、
    通常の距離・エリアでも同程度に遅延するかは未確認。
- 次の調査候補: (1) 他セッションが稼働していない静かなタイミングで同じ生成を再実行し
  Redisタイムアウトが再現するか確認する、(2) 本番`/api/debug/stats`のcache:*系の
  cache_hit_rateを確認する、(3) 再現する場合はredis-pyクライアントの接続プール設定
  （現状は`redis.from_url`のデフォルトプール、明示的なプールサイズ指定は無い）を疑う。
