# T828. MSMの「配信が滞っています」が、正常運用でも定期的に点灯する

規模S。
状態: 未着手（2026-09-13起票）

## 背景

システム状況パネルが「配信が滞っています（バックエンドのWARNINGログを確認）」を表示したが、
配信も同期も正常だった。

2026-09-13 19:33 JST時点の配信元メタ（`https://openmeteo.s3.amazonaws.com/data/jma_msm/static/meta.json`）:

| 項目 | 値 |
|---|---|
| `last_run_initialisation_time` | 09/13 03:00 UTC（12:00 JST） |
| `last_run_availability_time` | 09/13 06:30 UTC（15:30 JST） |
| `update_interval_seconds` | 10800（3時間） |
| `data_end_time` | 09/15 19:00 UTC（残り32.5時間） |

backendが持つ値は配信元と完全に一致し、`msm:meta`・`msm:chunk`・`msm:read`のエラーは0件。
同期は成功しており、単に配信元が次のrunをまだ出していない。

`_STALE_RUN_THRESHOLD_HOURS = 6`（`backend/app/infrastructure/msm_client.py`）が低すぎる。
定常運用でのrun経過時間の最大値は「更新間隔 + 公開遅れ」であり、同ファイルのコメント自身が
公開遅れを3.5〜5時間と書いている。つまり正常時でも最大8時間まで育ちうる値に対して、6時間で
発報している。上の実測でも公開遅れは3.5時間・更新間隔は3時間で、次のrunが届く直前には
必ず6.5時間へ達する——毎サイクル末尾で点灯する。

## 影響

- 実害の無い状態で赤字が出るため、本当に配信が止まったときに区別が付かない
- パネルは「バックエンドのWARNINGログを確認」と促すが、確認しても異常は無い

## 対応方針

しきい値を手で置かず、配信元が配っているメタから導く（`update_interval_seconds`と、
`last_run_availability_time - last_run_initialisation_time`で分かる実際の公開遅れ）。
`remaining_hours`側のしきい値（12時間）は予報終端までの余裕であり、この問題とは別。
