# T722. タスク提案・着手が対象領域の正本ドキュメントを読むようにする 規模S

状態: 完了（2026-09-12。読む側の手順を直し、正本側の穴1件を埋めた。起票は2026-09-11、[T703](T703.md)の記載見直しで露見）

## 背景

`maplibre-gl`を5系に固定している理由——v6はWorkerのスクリプトURLを動的テンプレート
リテラルで解決し、Next.jsのバンドラが静的解析できずに地図が永久に描画されない——は、
**プロジェクト初日から[docs/architecture.md](../architecture.md)へ記録されている**。
症状・原因・回避策・再検討の条件まで書かれており、内容にも置き場所にも不足は無い。

それにもかかわらず[T703](T703.md)は「6系へ更新する 規模M」として起票され、その後の
複数回のタスク提案でも制約が一度も参照されなかった。

## 原因: 読む側が`docs/tasks/Txxx.md`しか開いていない

`/task:next`の手順は「`improvement-plan.md`の`- [ ]`行を抽出 → 各`docs/tasks/Txxx.md`を
開く → 順位付け」で閉じている。**タスクファイルに書かれていない制約は、提案の時点で
存在しないのと同じ**になる。

### 対処として採らない案: タスクファイルへ導線を書き足す

最初に考えたのは「`T703.md`から`architecture.md`へリンクを張る」「`package.json`の
ピン留め理由を別ファイルへ書く」という、辿れるようにする方向だった。**これは根本対策に
ならない**（2026-09-11ユーザー判断）:

- すべてのタスクファイルへ関連ドキュメントの導線を書き並べることになり、**ドキュメントを
  構造化して分けた意味が消える**。タスクファイルがリンク集になる。
- 書き漏らせば同じことが起きる。「漏らさず書く」に依存する対策は、漏れたときに機能しない。
- 新しいタスクを起票するたびに、そのタスクが触る全領域の制約を起票者が把握している前提が
  必要になる——把握していないから見落とすのに、前提が循環している。

正しい向きは**読む側**を直すこと。ドキュメントは領域ごとに構造化されているのだから、
**タスクの対象領域から正本を引く**のが自然な引き方で、タスクファイルを索引にするのは
構造を無視した引き方だった。

## 対応方針

### 1. 提案・着手の手順へ「対象領域の正本を読む」を入れる

`.claude/commands/task/next.md`の優先度シグナル収集（手順4）と、CLAUDE.mdの着手フローへ、
タスクの対象領域から正本を引く一手を入れる。既に同型のルールが1つある——CLAUDE.mdの
「既存モジュールへの修正・追加に着手する際は、対象となる`docs/modules/*.md`を必ず先に
精読する」。**これが`docs/modules/`にしか掛かっていない**のが穴で、
`architecture.md`が持つ領域（依存のピン留め・デプロイ順序・プラットフォーム制約）には
同じ歯止めが無い。

領域と正本の対応は既に`docs/modules/README.md`の索引が持っている。依存・デプロイ・
実行環境の制約は`architecture.md`側にあるため、そこを引く条件を明示する。

### 2. `architecture.md`を機械チェックの対象に入れる

`scripts/review_checks.py`の死んだ参照・死んだ識別子・記載粒度の各チェックは
**`docs/modules/`だけが対象で`architecture.md`を見ていない**。起票時に手で同じ検査を
当てたところ、45件の参照のうち大半は経緯記述（「T350時点で既に撤去済み」等、正当）
だったが、**1件は現在の設計と逆のことを書いていた**:

> 日本語ラベルはbackend側では持たず、frontend側`lib/materialValueLabels.ts`が単一の情報源

実際はbackendの`MaterialSpec.value_labels`が単一ソースで、このファイルは存在しない。
読んだ人を逆方向へ送る記述で、手で探さなければ見つからなかった。

`architecture.md`は経緯も書く文書のため、`docs/modules/`と同じ基準（経緯記述を違反とする）
はそのまま当てられない。**死んだ参照だけ**を対象にするのが現実的で、
外部APIのパス（`targetTimes.json`等、リポジトリのファイルではない）を誤検知しない形が要る。

## 保留することで何が起きうるか

- 同じ型の見落としが繰り返される。ピン留めしている依存は`maplibre-gl`だけではない
  （`@maplibre/maplibre-gl-style-spec`は`24.10.0`とキャレット無しの完全固定）。
- `architecture.md`の記述が現状と食い違っても、次に手で全文を読むまで気づけない。
  2,694行あり、毎回読むことは期待できない。

## 完了条件

- タスクの提案・着手の手順が、対象領域の正本を読まずに通過できないこと
- `architecture.md`の死んだ参照が機械的に検知されること

## 実施内容（2026-09-12）

### 1. 提案・着手の手順へ「対象領域の正本を読む」を入れた

| 置いた場所 | 内容 |
|---|---|
| CLAUDE.md（着手フロー） | 既存の「`docs/modules/*.md`を先に精読」の隣へ、**依存ライブラリのバージョン・デプロイ・実行環境に触る変更は`architecture.md`の該当箇所も着手前に読む**を追加。理由を「これらの制約はコードからは導けず、あの文書だけが持つ」の一文で書いた |
| `docs/modules/README.md` | 「このディレクトリが扱わない領域（正本は別にある）」節を新設。領域→正本の対応表と、判断の目安（**その制約を、コードだけを読んで知れるか**）を置いた |
| `.claude/commands/task/next.md`（手順4） | 優先度シグナルの収集へ「そのタスクが触る領域の正本に、方針と矛盾する制約が書かれていないか」を追加。矛盾が見つかったタスクは**候補から外さず「方針の見直しが要る」と添えて提示する**——実現不能な方針のまま着手するのが最悪で、次に悪いのは黙って候補から消すこと |

**この1点は機械で強制できない**（「読んだか」は検査できない）。代わりに**引き先を一意にした**
——`docs/modules/README.md`の索引1枚から辿れる形にし、「どこを読むべきか自分で考える」
部分を無くした。

### 2. 正本側の穴を1つ埋めた（手順を実際に辿って見つけた）

新しい手順どおりに「依存のバージョン制約 → `architecture.md`」を辿ってみたところ、
`maplibre-gl`の制約は見つかるが、**`@maplibre/maplibre-gl-style-spec`（`24.10.0`完全固定）の
理由がどこにも無い**ことが分かった。理由は`improvement-plan-archive/README.md`（当時の記録）に
一行あるだけで、手順の引き先からは辿れない——本タスクが問題にしている構造そのものが、
2つ目の依存でも成立していた（起票時の「保留すると何が起きうるか」で予測したとおり）。

`architecture.md`「技術選定」へ追加した: このパッケージの式評価器は**テストが**式の正しさを
検証するために使い、**地図が実際に評価に使うのは`maplibre-gl`が内部に持つ同パッケージ**。
両者の版がずれるとテストが通る式が実機で別の意味になりうるため、`maplibre-gl`の依存範囲
（5.24.0では`^24.8.1`）に収まる版をキャレット無しで固定する。

### 3. 完了条件2（`architecture.md`の死んだ参照の機械検知）は既に満たされていた

[T723](T723.md)が検知器を新設し、[T724](T724.md)が既存75件を0件にして全件スキャンでも強制へ、
[T739](T739.md)が`undeclared_dead_refs`を`full`強制へ戻している。起票時に挙げた誤った記述
（「日本語ラベルは…frontend側`lib/materialValueLabels.ts`が単一の情報源」）も
`architecture.md`からは消えている。

ただし**2の追記が検知器に引っかかった**——`createExpression`はテストだけが使う外部APIで、
テスト本体をcorpusから外している設計のため「実装に存在しない」と判定された。
バッククォートを外して迂回するのではなく、判定側を直した: **import文に現れる名前は、
自前か依存先かを問わず解決できる実在の名前**として救済する。テスト本体の
アサーションや文字列に残る旧名はimport文には現れないため、改名の取り残しを見逃す側には
効かない。

緩和の影響を実測した: 新たに「実在する」側へ移るのは8件（`TestClient`・`createExpression`・
`get_origin`・`renderHook`・`waitFor`の外部API5件と、`build_loop_graph`・`make_generator`・
`installApiMocks`の自前テストヘルパー3件）で、**いずれも実在を確認した**。
`WeightPanel`・`zzzGuardProbeIdent`（mutateのプローブ）は救済されない。

### 検知器にしなかったもの（測ってから）

`docs/`全体へ死んだ参照の検知を広げる案を測った:

| 母集団 | 件数 | 中身 |
|---|---|---|
| `docs/**`（modules・architecture以外）25ファイル | 142 | 大半が`docs/decisions/`（ADR＝当時の決定の記録。`RouteScorer`・`ORSClient`等を正当に名指しする） |
| 記録文書を除き、テストを含むcorpusで判定 | 10 | うち`docs/osm-pbf-import.md`も移行の記録文書 |
| 記録文書をすべて除いた「現状を語る」文書だけ | 5 | **本物は1件**（`docs/logging.md`の存在しない例示）。残り4件は外部ライブラリ・OSコマンド名 |

本物1件に対し誤検知4件で、しかも誤検知はすべて「外部の名前」——自前の実装に無いのが
正常なもので、名前の一覧を持たずに区別する手段が無い。検知器にはせず、見つかった1件は
手で直した（`log_external_call`の「取得できないのが正常」の例として存在しない値
`no_elevation`を挙げていた。実際の実装は`result="ok"`＋`status=404`で表す）。

## 検証結果

- 手順の引き先が実際に制約へ着地することを辿って確認（`docs/modules/README.md`の表 →
  `architecture.md`「技術選定」→ maplibre-glのv6制約・style-specの固定理由）。
  **この確認の過程で2の穴が見つかった**ため、手順が機能することの実例にもなっている。
- import救済の影響: 新たに実在扱いになる8件を全件確認。`python scripts/review_checks.py mutate`
  → **全30件PASS**（既存の検知器が1つも鳴らなくなっていない）。
- `pytest scripts/tests/test_review_checks.py` → 88 passed（import救済が効くこと・テスト本体に
  残る旧名には効かないことを固定。リポジトリ全体を読むキャッシュをテストごとに落とす
  autouseフィクスチャも入れた——実行順で結果が変わる状態になっていた）。
- `pytest -q -m "not postgis"` → 1,828 passed。`ruff check app scripts benchmarks tests` → All checks passed。
- `tsc --noEmit`・`eslint` → 指摘なし。`python scripts/review_checks.py docs` → 違反なし。
