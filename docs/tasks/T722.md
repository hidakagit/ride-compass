# T722. 依存のピン留めの理由を、そのピンから辿れるようにする 規模S

状態: 未着手（2026-09-11起票、[T703](T703.md)の記載見直しで露見した構造）

## 背景

`maplibre-gl`を5系に固定している理由——v6はWorkerのスクリプトURLを動的テンプレート
リテラルで解決し、Next.jsのバンドラが静的解析できずに地図が永久に描画されない——は、
**プロジェクト初日から[docs/architecture.md](../architecture.md)へ記録されている**。
症状・原因・回避策・再検討の条件まで書かれており、内容にも置き場所にも不足は無い。

それにもかかわらず、[T703](T703.md)は「6系へ更新する 規模M」として起票され、
その後の複数回のタスク提案でも制約が一度も参照されなかった。

## 何が起きていたか

制約は書かれていたが、**そこへ辿り着く導線が1本も無かった**。

| 経路 | 状態 |
|---|---|
| `T703.md` → 制約 | リンクなし・言及なし |
| `architecture.md` → `T703` | 言及なし（相互リンクが両方向で欠落） |
| `package.json`の`"maplibre-gl": "^5.24.0"` | JSONのためコメントを書けず、ピン留めの理由が現物に残っていない |
| `CLAUDE.md` | `architecture.md`は「アーキテクチャ全体は参照」という位置づけで、タスク提案時の必読ではない |

タスク選定（`/task:next`）は`improvement-plan.md`の`- [ ]`行と`docs/tasks/Txxx.md`だけを
読む手順になっている。**タスクファイルが制約へリンクしていなければ、制約は提案時に
存在しないのと同じ**になる。

これは「ドキュメントを書いても読まれない」問題ではなく、**書いた場所と読む場所が
繋がっていない**問題である。読み手を増やす（必読を増やす）方向で解こうとすると
CLAUDE.md肥大化と同じ失敗をなぞるため、繋ぎ方の側で解く。

## 保留することで何が起きうるか

- 同じ型の見落としが繰り返される。ピン留めしている依存は`maplibre-gl`だけとは限らず、
  `@maplibre/maplibre-gl-style-spec`（`24.10.0`、キャレット無しの完全固定）も同型。
- 依存更新の提案が「上げられない理由」を知らないまま出てくるため、毎回同じ検証を
  やり直すか、検証せずに着手して初日の壁へぶつかる。
- 症状が「エラー」ではなく「地図が出ない」ため、CIでは捕まらない。

## 対応方針（案）

1. **相互リンクを張る**（即座にできる最小手当て）。`T703`→`architecture.md`の該当節は
   記載見直しで対応済み。逆向き（`architecture.md`→`T703`）も張る。
2. **ピンの理由を現物から辿れるようにする**。`package.json`はコメントを持てないため、
   別ファイル（例: `frontend/DEPENDENCY_PINS.md`）へ「固定している依存・理由・
   再検討の条件・正本へのリンク」を置き、`package.json`と同じディレクトリに並べる。
3. **機械的に検知する**。`scripts/review_checks.py`へ、「固定・範囲制限されている依存が
   ピン理由の一覧に載っているか」を見るチェックを足す。載っていなければ違反。
   `review_checks.py docs`は既にpre-commitとCIで走っているため、追加費用は小さい。
   （`find_bare_basemodel_violations`・`find_redis_skeleton_violations`と同じ流儀。）

3までやるかは費用対効果で決める。対象の依存が数件なら1・2で足りる可能性がある——
まず**ピン留めしている依存を数え上げる**ところから始める。

## 完了条件

- 固定・範囲制限している依存それぞれについて、ピンから理由へ辿れること
- 依存更新を提案する経路（`/task:next`・レビュー）が、その理由を読まずに通過できないこと
