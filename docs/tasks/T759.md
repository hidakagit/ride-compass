# T759. 候補一覧の一覧性: タブの溢れ・数値の比較・地図からの選択

規模M〜L。
状態: 完了（2026-09-13）

## 背景

候補を見比べて採用ルートを決める導線が、タブの往復と暗算に依存している。本番実測:

- 候補タブ列はデスクトップで`scrollWidth`=671 / `clientWidth`=247（8件中3件が見える）、モバイルで679 / 372。横スクロールの手掛かり（端のフェード・矢印・件数）が無い。研究モードで「比較」タブを開くと末尾へスクロールし候補1〜5が隠れる
- タブは順位と距離だけを持つ。20km周回8候補の総合難易度/負荷は22/490・24/449・26/496・26/586・27/603・29/633・30/652・30/494で、候補8（16.3km）は負荷が候補3より低いが順位は最後で、全タブを開かないと分からない
- 地図上の未選択候補は灰色の細線（`#64748b`、幅2.5）で、クリック処理は選択中ルートの区間にしか無く、地図から候補を選べない
- デスクトップのサイドバーは結果を全部読むのに縦スクロールが要る（`aside`の`scrollHeight`=1614 / `clientHeight`=764）
- 一般ユーザーが同一生成内の候補どうしを比較する手段は無い（研究モードの比較タブは「生成回ごとの代表候補」の比較）。前回レビュー（2026-08-30）F-7の未対応分

個票は[history/2026-09-12_ui.md](../../.claude/commands/review/history/2026-09-12_ui.md)のF-9・F-10・F-15・F-21。

## 調査項目（設計課題として扱う）

1. **候補を見比べる単位**。走行中のスマホで「候補を選ぶ」ときに要る情報は何か（距離・総合難易度・負荷・方位）。タブの表記を増やすのか、タブとは別に一覧（1行1候補、難易度のバー付き）を置くのか。情報量を増やさない方針（[design-principles.md](../design-principles.md)「走行中に見るかを基準に情報量を絞る」）との整合
2. **タブ列の溢れ**。一覧を置くならタブ列自体が要るか。残すなら溢れの表現
3. **地図からの選択**。未選択候補線へのクリックで`selectedRouteId`を切り替える。当たり判定は区間クリック（`DETAIL_HIT_LAYER_ID`）と競合しないか。線の色（灰）を候補ごとに区別するかは[T754](T754.md)の色空間の分離と合わせて決める
4. **サイドバーの縦の長さ**。軸別難易度の一覧を既定で全軸出すか、寄与のある軸だけにするか
5. 目的地モードの「最短」基準線と「+0.8」表記は既に候補比較の材料になっている。周回モードにも同種の基準（最も易しい候補との差）を出せるか

## 完了条件

- 8候補を生成し、タブを1つも開かずに「どの候補が最も易しく、どれが最も短いか」が読めることをスクリーンショットで示す（デスクトップ・390px幅の両方）
- 地図上の候補線から候補を切り替えられること

## 決定（調査項目1・2、ユーザー判断2026-09-13「横タブだと限界がある。縦タブにできる？
左に並べる。タブ以外のスペースに今の残り部品をUI工夫して収まるよう再配置する」）

候補一覧を**左の縦タブ**（`Tabs.Root orientation="vertical"`）にし、右に選択中候補の中身を
置く2カラムへ変えた。横並びのタブは候補が増えたぶん列が伸びるだけで、溢れた候補は存在ごと
見えなくなる（実測で必要幅が表示幅の3倍近く）。縦なら幅の制約から外れ、行の中へ距離と
総合難易度を並べられる。

- 行の表記: 「順位（目的地モードの基準線は「最短」）・距離・総合難易度（数値と長さ）」。
  一覧の中で最も距離が短い候補には「最短」を添える——並び順は総合難易度の昇順なので
  「最も易しい」は先頭で読めるが、「最も短い」は別の軸のため印が要る（`shortestDistanceRouteId`）。
- 情報量: 1行に増えたのは総合難易度だけ。走行中に候補を選ぶ場面で要る値で、これが無いと
  候補ごとにタブを開いて戻る操作が要る（[design-principles.md](../design-principles.md)
  「走行中に見るかを基準に情報量を絞る」の判定として、開く回数を減らす側に働く）。
- 狭幅（640px以下）では一覧に高さの上限を付け、中を縦スクロールさせる——下部シートを
  候補数で押し上げないため（[T778](T778.md)「シートは低いほどよい」と両立させる）。
  横スクロールと違い、シート自体の操作と同じ向きなので溢れに気づける。
- デスクトップのサイドバーは2カラムぶんの幅が要るため280px→380pxへ広げた。

## 地図からの選択（調査項目3）

未選択候補の線は細く（2.5px）指で狙えないため、透明で太い当たり判定
（`ROUTES_HIT_LAYER_ID`、幅18px）を重ね、地物の`routeId`で候補を切り替える
（`MapViewProps.onRouteSelect`）。選択中候補の区間詳細（`DETAIL_HIT_LAYER_ID`）とは別の
ハンドラで、一般道路網のポップアップは両方をガードして開かない。

## 検証

Playwright（`e2e/fixtures.ts`のモックへ本番実測と同じ8候補の距離・総合難易度を流し込む）:

- デスクトップ1280x900: 8候補すべてが1画面に並び、タブを1つも開かずに「最も易しい＝先頭
  （22）」「最短＝16.3km（印付き）」が読める
- 390x812: 同じ行が6件ぶん見え、残りは一覧内の縦スクロール。シートの高さは変わらない
- 地図上の候補線を押すと選択が切り替わる（クリック位置を変えながら、候補3・候補2へ
  切り替わることを確認）
- 単体テスト: `shortestDistanceRouteId`2件、候補featureが`routeId`を持つこと1件
  （地図からの選択がこのプロパティに依存するため）
