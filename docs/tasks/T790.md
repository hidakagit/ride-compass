# T790. 探索の状態を「交差点」から「有向区間」へ移す（ターン展開グラフ）

規模L。
状態: 未着手（2026-09-13起票）

## 背景

実走フィードバック（目的地モード・柏→王子・停止密度2/3・蛇行1/3）の3件——「交通量の多い道を
突っ切る・右折のコストがばかにならない」「凸凹したよくわからない回り道」「生活道路を
ぐるぐる走る」——は、いずれも**交差点で何をするか（直進・右折・横断）がコストに現れない**
ことから来ている。

コストはEdge単位の`distance_m × (1 + P × difficulty / 100)`だけで、A*
（`domain/routing.py: shortest_path_node_ids_lazy`）の状態は交差点ノード。同じ交差点でも
進入方向によって先の最適解が変わるため、ターンに費用を付けるとノード単位の最短コストが
一意に決まらなくなり、いまの状態の取り方のままでは載せられない。

グラフ自体は既に有向（一方通行は扱えている）。足りないのは状態の取り方。

## 何を作るか

探索の状態を有向区間へ移す（ノード＝有向Edge、辺＝ターンの辺基準グラフ）。ターンの費用は
秒で決め、既存のコスト単位（m）へ換算して足す（想定巡航速度は`assumed_speed_kmh`があり、
時速20kmなら1秒＝約5.6m）。距離と直接比較できる形になるため、「右折1回＝何m遠回りするのと
同じか」を較正できる。

ターンの費用を決める材料は交差点ノード側の属性:

- 信号の有無（`osm_raw_pois`のsignal）
- 交差する道の最大highway階級（`osm_raw_ways.node_ids`の隣接から導出。
  `_REBUILD_RAW_INTERSECTION_NODES_SQL`と同じ形で求まる）
- 進入方位と退出方位の差（`road_edges.bearing_deg`）

信号のある交差点の直進より、信号の無い交差点で上位階級の道を横断・右折する方が高い、という
順序を表せることが要件（実走で最も苦労した形が、いまは費用ゼロになっている）。

## 段階

### 段階1: 性能プロトタイプ（実装より先に測る）

設計の是非ではなく**性能が成立するかどうかが判断の中身**のため、先に測る。

- 状態数は有向Edge数（都心30km四方で約56万）、遷移は平均次数ぶん（150〜200万の見込み）
- [T536](T536.md)で0.37秒まで詰めた探索時間が、状態数3〜4倍でどうなるか
- `prepare_ms`・キャッシュサイズ（`search_graph_cache`・CSR）への影響
- 計測は本番DBで行う（開発DBは前提が違い性能測定に向かない）

ここが通らなければ設計から考え直す。

### 段階2以降（段階1の結果を見て決める）

| 対象 | 影響 |
|---|---|
| `LazyRoadGraph`・`build_lazy_road_graph` | ノード/辺の意味が変わる |
| コスト配列（`_LegCostComposer.compose`） | Edge単位の配列はそのまま残せる。ターンの費用を別配列として足し、「ターンindex→進入Edge index」の対応表で引き直す |
| 一対全木（`build_shortest_path_tree`・CSR） | 「ノードへの到達」が「有向区間への到達」になる |
| 周回生成（フロンティア方式・折返し点選定） | 折返し点の選び方を見直す。Uターンの抑制もここで表せるようになる |
| キャッシュ鍵（`cache_identity`・`search_graph_cache`） | 構造が変わるため世代を上げる |

## 前工程を先に整える場合の条件

交差点ノードの分類（信号の有無・交差する道の最大階級）は、ターン展開後もそのまま使う入力の
ため、近似の材料として先に整えても捨てない。ただし**ノード側の属性として持ち、Edgeへ
畳み込んだ値を`road_edges`の列やMVTタイルへ焼かないこと**——Edge側へ焼くと同じ事実が
2箇所に出て、ターン展開したとき片方が古くなる。

畳み込みによる近似では「交差点を通ること自体を嫌う」までしか表せず、右折と直進横断は
区別できない。近似で止める前提にしないこと。
