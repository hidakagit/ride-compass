# T790. 評価基準の単位を決め直す（所要時間＋主観的割増）

規模L〜XL。
状態: 完了（2026-09-13。段階A〜Dまで実装し本番反映・レスポンス計測まで済ませた。較正と
交差点ノードの属性は[T799](T799.md)〜[T802](T802.md)へ切り出した）

## 何が変わったか（完了サマリ）

**探索のコストの単位が「距離に難易度の割増を掛けた合成量」から「体感の所要時間（秒）」に
なった。**

```
コスト = 区間の所要時間 × (1 + penalty_strength × difficulty/100)
```

区間の所要時間は走行モデル（巡航速度→ホイール出力→走行方程式を解く）＋停止の待ち、ターンの
待ちは遷移ごとに秒で足す。利用者の好み（軸の重み）をすべて0にすると素の所要時間になり、
それが基準線（`select_fastest_route`）と同じ物差しになる——**基準線が定義から出る**。

実走フィードバック4件への対応:

| 報告 | 対応 |
|---|---|
| 交通量の多い道を突っ切る／右折のコスト | 探索の状態を有向区間にしてターンの費用を持てるようにした（段階2a）。本番の柏→王子で右左折が64〜74%減、上位道路との交差も51〜73%減 |
| 凸凹したよくわからない回り道 | 同上。距離も短くなった（候補3は36.3→28.3km） |
| 生活道路をぐるぐる | 同上 |
| GPXが繋がって見えない | [T786](T786.md)で間引きをRamer-Douglas-Peuckerへ。実データ25.2km/1453点で最大ずれ116.6m→3.0m |

風は「難易度」から「速度への入力」になり、探索が出発からの経過時間をラベルとして持ち回って
その時刻の風で引き直す（段階D）。一対全木・2点間探索ともnumbaへ移り、scipy依存が消えた。

**本番レスポンスは段階2a比で+2,400ms**（周回30km・温パス 3,105→5,483ms）。増分の主は走行
モデルそのもので、時刻ビンの費用はほぼ無い（目標30kmの周回はビン1本に収まる）。

### 作業中に見つけて直した欠陥

いずれも**物理（走行モデル）の入力が、軸の構成に依存する器から取られていた**という同じ型:

- 勾配が走行モデルへ届いていなかった（`material_arrays`は軸が分解した材料しか持たない）。
  **坂で一切減速していなかった**
- 停止の秒も同じ経路で、停止密度の軸を非公開にすると静かに消える状態だった
- `time_varying`の判定が風の軸の重みに依存しており、重み0で速度計算まで時刻固定に落ちた

加えて、実データでしか出ない欠陥を開発DBの実行で1件（並行Edgeがあると探索用グラフと
スコア行列の行が食い違い、ルート生成が丸ごと落ちる）。

## 背景

いまのエンジンの設計原理は「**探索中には何も計算しない**」（[T536](T536.md)。コストを
事前合成した配列にし、A*へは`list.__getitem__`だけを渡すことで8.3〜17.7秒→0.37秒）。
この原理が、性質の違う3種類の依存を同じ理由で排除している。

| 排除されている依存 | いまの近似 | 残差 |
|---|---|---|
| 到達時刻（風・夜間、将来の渋滞・降雨） | 基準点からの直線距離×迂回率÷仮定速度で推定し、レグ単位で配列を合成（[T532](T532.md)） | 実経路長ではない。レグ内では時刻が変わらない |
| 進入方向（交差点での直進・右折・横断） | 無し | 右折・無信号での幹線横断が費用ゼロ |
| 実走速度 | 画面指定の固定値（`assumed_speed_kmh`） | 風・勾配で変わるのに固定（速度↔風の循環を切るため） |

夜間軸も出発時点の昼夜判定を全Edgeへ一様適用したまま（T532が派生候補(a)として残した分）。

風とターンは代表例にすぎない。時刻に依存する材料は今後も増える（渋滞・降雨・気温）。その
たびに探索の外側で近似を足す構造をやめ、**材料の種類が増えても探索の設計を変えなくて済む**
状態にするのが出発点だった（2026-09-13ユーザー方針「ごく限られた実測ケースで近似し、
中途半端に考えるよりも、根本解決を望む」）。

## 課題設定の訂正（2026-09-13、段階2a完了後）

**当初このタスクを「探索の状態の次元を増やす（進入方向・到達時刻）」と定義したが、それは
課題を小さく捉えていた。実際の課題は「評価基準の単位を決め直す」ことで、状態の次元の拡大は
その一部でしかない。**

段階2aでターンの費用を**秒**で定義した時点で、時間という次元を持ち込んでいる。ところが
`秒 × 速度`でメートルへ換算してコストへ足した——時間を距離へ引き戻して、既存の距離ベースの
合成量に合わせた。結果、いまのコストは

```
distance × (1 + P × difficulty/100)  +  ターンの秒 × 速度
   ↑ 距離ベースの主観的合成量            ↑ 時間を距離へ戻したもの
```

という混ざった量で、物理的に意味のある単位が1つも無い。停止も勾配も風も「難易度」として
距離側にいて、ターンだけが時間から来ている。

**そうした理由は、既存のコスト体系へ合わせるのが最小変更だったから**（単位を揃えるという
面倒な方を避けた。この振る舞い自体は[T798](T798.md)）。

正しい課題設定:

> **コスト = 所要時間 ＋ 主観的な割増**
> 時間側: 風・勾配（速度低下）、停止（待ち）、ターン（待ち・減速）
> 割増側: 車の圧迫感・路面・事故密度・自転車インフラ（安全性／快適性。時間には写らない）

これなら基準線＝時間最短が定義でき、候補は「+12分／圧迫感が半分」というトレードオフとして
表せる。時刻依存（風）も、単位が時間になって初めて素直に収まる（風＝速度低下＝所要時間の
増加であり、難易度ではない）。[T787](T787.md)も「折れ点の較正」ではなく「停止を秒として
定義する」という単位の話になる。

## 目指す設計

1. **材料に依存の種類を宣言させる**（静的／到達時刻依存／進入方向依存）。軸定義による合成は
   いまのままで、探索が宣言を見て扱いを変える。`dynamic_way_value_needs_time`等の既存
   フラグの延長線上に置く。
2. **探索の状態を有向区間にし、到達時刻をラベルとして持ち回る**。
   - 進入方向は状態を増やすしかない（進入方向で先の最適解が変わり、単調でもない）ため、
     状態＝有向Edge・辺＝ターンの辺基準グラフにする。
   - 到達時刻は経路に沿って単調で追い越しが起きない（FIFO。渋滞でもこの性質は保たれる）
     ため、状態は増やさずラベルで足りる。**時間展開グラフは要らない**（T532が「10倍に
     膨らむ」として不採用にしたものは、ここでも採らない）。
   - 実走速度は到達時刻が正しく持てれば副産物として解ける（その区間の風・勾配から実速度を
     出して次の到達時刻へ送る）。いまの循環はここで切れる。

ターンの費用は秒で決め、既存のコスト単位（m）へ換算して足す（時速20kmなら1秒≒5.6m）。
費用を決める材料は交差点ノード側の属性——信号の有無（`osm_raw_pois`のsignal）・交差する道の
最大highway階級（`osm_raw_ways.node_ids`の隣接から導出、`_REBUILD_RAW_INTERSECTION_
NODES_SQL`と同じ形）・進入方位と退出方位の差（`road_edges.bearing_deg`）。信号のある交差点の
直進より、信号の無い交差点で上位階級の道を横断・右折する方が高い、という順序を表せることが
要件（実走で最も苦労した形が、いまは費用ゼロ）。

## 最大の未確定: 探索の実装基盤

`rustworkx`のA*は`edge_cost_fn(edge_index)`しか呼べず、**C実装の中から「いまの到達時刻」を
渡す口が無い**。時刻ビンごとに配列を用意しても、どのビンを引くかを探索が教えてくれないため
回避できない。到達時刻をラベルで持つ以上、いまの基盤のままでは実現できない。

判断の分かれ目になる見込みの材料:

- 2点間探索は、lazy A*が**全Edgeの2.79%しか評価しない**（`routing.py: LazyRoadGraph`の
  docstring）。評価対象は1〜2万状態程度で、Python実装のA*でも収まる可能性がある。
- **厳しいのは周回生成**。フロンティア方式は起点からの一対全最短経路木をscipyで張り、全状態を
  訪れる（都心30km四方で約56万有向Edge）。ここを時刻依存にするのはPythonでは成立しない。
  「木は静的コストで張り、候補を絞ってから時刻依存で精査する」2段構えになる見込みで、
  **周回生成の設計そのものの見直し**を含む。規模がXLへ寄るのはここ。
- 既製エンジン（Valhalla等、リクエスト時コスティングと時間依存を持つ）への載せ替えも選択肢に
  入るが、軸をユーザーが定義して重みをリクエストごとに変えるRideCompassの中核と両立するかは
  未調査。

`routing.py`の「探索アルゴリズムを独断で変更しない／独自の経路探索アルゴリズムの実装は
しない」という原則との関係も整理する。時間依存A*は標準的な手法で新規性のある独自
アルゴリズムではないが、rustworkxのC実装から離れる判断そのものは明示的に行う。

## 実装基盤の候補調査（2026-09-13、文献・ドキュメント調査のみ。実測はしていない）

必要な要件は「**探索中に、その状態の到達時刻を見てコストを決められる**」こと。

### 汎用グラフライブラリは要件を満たさない

`rustworkx`（コールバックへ到達時刻を渡す口が無い）・`scipy.sparse.csgraph`（コールバック
自体が無い）・`networkx`（weight関数は`(u,v,data)`のみ・純Python）・`python-igraph`・
`networkit`（重みは辺の静的属性）は、いずれも「コストは辺の静的属性」という前提で割り込め
ない。`graph-tool`はBoost GraphのC++ visitorで割り込めるが、開発機（Windows）への導入が
現実的でない。

### 既製ルーティングエンジンは「重み」までは合うが「材料」が合わない

GraphHopperのcustom modelは`edge_weight = edge_distance / (speed × priority) +
edge_distance × distance_influence + turn_penalty`で、リクエストごとにJSONで送れる
（flex/hybridモード）。`allow_turn_penalty_in_request`でターンの費用も実行時に渡せる。
RideCompassのコスト式とは`priority = 1/(1 + P×difficulty/100)`で写像でき構造は近い。

ただしcustom modelが読めるのはimport時に焼き込んだ静的なencoded valueで、**風・勾配のように
リクエストごとに値そのものが変わる材料は載らない**。RideCompassの動的材料（到達時刻の風・
走行方位・想定速度）は既製エンジンの想定外にある。pgRoutingの`pgr_trsp`は辺基準でコストを
SQLで渡せるが、同じ制約に加え、毎リクエストSQLでコストを計算するため事前合成した配列より
遅くなる公算が大きい。

- GraphHopper custom models: https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md
- pgRouting pgr_trsp: https://docs.pgrouting.org/latest/en/pgr_trsp.html

### Valhallaだけは機能要件を満たす（論点は移植量）

Valhallaは`DynamicCost`を派生させると`EdgeCost`（区間）とは別に**`TransitionCost`
（交差点・ターン）をオーバーライドできる**。`date_time`による時間依存ルーティングを持ち、
タイルに重みを焼かないrun-time costing設計（OSRMと違う点）。**3つとも要件を満たす**ため、
上記「既製エンジンは材料が合わない」はGraphHopperには当てはまるがValhallaには当てはまらない
——C++を書く前提ならコスト関数は何でも書ける。

論点は機能ではなく「どこに何を置くか」。

| | 自前実装（numba / Rust拡張） | Valhalla |
|---|---|---|
| 探索 | 自分で書く | Valhallaの資産を使う |
| 材料の抽出・保持 | いまのまま（PostGIS・MVTタイル・静的スコア行列） | Valhallaのタイル（mjolnir）へ焼く。独自材料を足すには本体改造 |
| 軸定義の評価 | いまのまま（Python、DBが正本） | costing optionsのJSONで渡しC++側で評価する設計は可能。材料がタイルに無ければ動かない |
| 軸を1本足す操作 | DB操作だけ | タイル再生成が要る |
| 風・勾配のような動的材料 | いまのまま（リクエスト時に合成） | 自前の`DynamicCost`内で外部から引く。可能だが設計は重い |
| 移植量 | 探索だけ | 評価系ごとC++へ |

Valhallaを採る判断は「エンジンを借りる」ではなく**評価系をC++へ移す**判断になる。比較すべきは
「探索を速くするコスト」対「評価系を移植するコスト」で、段階1の訪問状態数が分かればこの
判断の前提（自前実装で足りるか）が数字で決まる。Valhallaのタイルへ独自材料を足す難易度は
未測定。

- Valhalla dynamic costing: https://valhalla.github.io/valhalla/sif/dynamic-costing/
- Valhalla `DynamicCost`（`TransitionCost`を含む）: https://github.com/valhalla/valhalla/blob/master/src/sif/dynamiccost.cc

### 収穫: 辺基準グラフを物理的に展開しなくてよい

Geisberger & Vetter「Efficient Routing in Road Networks with Turn Costs」
（https://link.springer.com/chapter/10.1007/978-3-642-20662-7_9 ）は、交差点ノードへ
ターンコストの表を持たせ、グラフ自体は展開しない表現を示している（辺基準グラフに対して
前処理時間3.4分の1・空間2.4分の1で、クエリ時間は変わらない）。探索の状態は有向Edgeのままで
よく、遷移先は元のグラフの出力辺から導き、ターンの費用はノードの表から引く。**メモリ増と
グラフ構築時間はほぼ回避でき、残るのは探索そのものの回数だけになる**。

### 残る候補

numbaでのJIT、またはRust拡張（pyo3 + maturin。本番はOracle Cloud VMのためビルド環境の確認が
要る）。どちらも探索を自分で書くことになるため、`routing.py`の「独自の経路探索アルゴリズムの
実装はしない」との関係を明示的に判断する（時間依存A*・ターンコスト付きA*は標準的な手法で、
新規性のあるアルゴリズムの発明ではない）。

## 段階

### 段階1: 実装基盤が成立するかの検証

方式の成否を決めるため、実装より先に測る。近似で足りるかを測るのではない。測るべき量は
次のように分解できる:

```
探索時間 = 訪問状態数 × 1状態あたりのコスト
           ↑ 言語非依存      ↑ 実装基盤に依存
```

**訪問状態数を先に測れば、基盤ごとの所要時間は見積もれる**（現行rustworkxの実績値から
1状態あたりのコストが逆算できる）。全基盤を実装せずに判断するため、この順で進める。

1. 訪問状態数の実測。状態＝有向区間・ラベル＝到達時刻・ターンコスト有りのA*（まずはPython
   実装、グラフは展開せずノードのターン表から引く）で、都心25km級の目的地ルート1本を解き、
   訪問状態数・経路の右左折回数・経路長を現行の`shortest_path_node_ids_lazy`と比べる。
   現行は全Edgeの2.79%しか評価しない（`routing.py: LazyRoadGraph`）ため、ターンを入れた
   ときに訪問がどれだけ増えるかが分岐点になる
2. 1の結果から基盤（numba / Rust拡張 / 純Python）を選び、選んだ基盤で探索時間を実測する。
   `prepare_ms`・メモリも[T536](T536.md)の現行値と比べる
3. 周回生成の一対全木を「静的コストで張って時刻依存で精査する」2段構えにしたとき、候補の質
   （非優越ソート後の並び・多様性）が保てるか
4. 性能の計測は本番DBで行う（開発DBは前提が違い性能測定に向かない）

ここが通らなければ設計から考え直す。

### 段階1の実測（2026-09-13、dev DB。`backend/benchmarks/bench_t790_turn_expanded.py`）

条件: 蒲田付近(35.5617,139.7161)→王子(35.7528,139.7386)、直線21.3km・経路25.5km、重みは
既定。bbox内 nodes=76,960 / directed_edges=194,471。時刻依存コストはビンごとに一定率を
掛けた模擬（実データの風はビンごとに`compose`し直せば同じ構造で入る）。

| 探索 | 訪問状態数 | 訪問割合 | 経路長 | 左折 | 右折 | 所要 |
|---|---|---|---|---|---|---|
| 現行 rustworkx A*（状態＝ノード） | — | — | 389区間 | — | — | 64ms |
| 状態＝ノード（自前Python、正しさの確認用） | 52,639 | 68.4% | 25.50km | — | — | 142ms |
| 状態＝有向区間・ターン費用なし | 132,249 | 68.0% | 25.50km | 35 | 33 | 614ms |
| 状態＝有向区間・ターン費用あり | 132,982 | 68.4% | 25.56km | 27 | 26 | 927ms |

自前のノード版は現行rustworkxと同じ389区間の経路を返す（実装の正しさの確認）。

**1. ターンの費用は効く**。右左折の合計が68回→53回（22%減）で、経路長は25.50→25.56km
（+60m、0.2%）。わずかな遠回りと引き換えに曲がる回数が2割減る。実走で報告された「凸凹した
回り道」「生活道路をぐるぐる」に直接効く量。

**2. 状態数の増加はグラフの構造比そのもの**（194,471 / 76,960 = 2.53倍）。ターンの費用を
入れても訪問状態数はほぼ変わらない（132,249→132,982）ため、ターンは探索の広がりを増やさない。

**3. A*のヒューリスティックが実データでは弱い**。訪問割合は状態の取り方によらず68%で、
`LazyRoadGraph`のdocstringにある2.79%（合成グリッドグラフ）とは桁が違う。コストが距離の
1〜2倍に膨らむのに下界が直線距離のため、実質ダイクストラに近い探索になっている。
**これは現行エンジンにも当てはまる性質**で、ヒューリスティックを強める余地がある（本タスクとは
別の改善）。

**4. 1状態あたりの時間**は rustworkx 約1.2μs・自前Python（ノード）約2.7μs・自前Python
（有向区間＋ターン）約7.0μs。辺基準をrustworkx並みの実装効率にできれば160ms前後、ターンの
計算を足して200〜300ms程度の見込み。numbaならさらに下がる。

### 合意した骨子（2026-09-13のユーザーとの議論）

### コストの形

```
コスト = 所要時間 ＋ 主観的な割増
```

### 3層に分ける

| 層 | 内容 | 人による違い | 設定する場所 |
|---|---|---|---|
| 1. 物理法則 | 空気抵抗∝速度²、重力∝勾配 | なし | 固定 |
| 2. 個人パラメータ | 出力・体重・空気抵抗（＝向かい風や坂への強さ） | あり（**実力**） | プロフィール |
| 3. 主観的な好み | 危ない道を避けたい、風が嫌い | あり（**価値観**） | 軸の重み |

**2と3は別の操作**。2は「同じ向かい風でも実際に速度が落ちにくい」＝所要時間の予測が変わり
**基準線そのものが動く**（実力のある人の時間最短は別の経路になりうる。これは現実として正しい）。
3は「遅くなる量は同じだが、時間を損してでも風の弱い道を選びたい」＝候補の選び方が変わり
基準線は動かない。

### 個人パラメータは巡航速度だけで始める（段階1）

体重・出力・ケイデンスは一般の利用者が答えられない。一方、**平地・無風の巡航速度は答えられ、
そこから出力が逆算できる**（空気抵抗∝速度³）。「向かい風に強い／弱い」の差の多くは「そもそも
速い／遅い」で説明でき、巡航速度は`assumed_speed_kmh`として**既に画面から指定できる**。

段階2以降（「坂が得意／苦手」＝パワーウェイトレシオ相当、走行実績からの推定）へは後から
広げられる——**要素は変わらず導出式が精緻になるだけ**のため。

### 基準線は定義から出る

主観の重みを全部0にしたとき＝時間最短＝基準線。**いまの構造では基準線が定義できず**
（重み全部0は「向かい風でも遅くならない・登りでも遅くならない架空の世界」になる）、距離最短を
あてがっていた。

### いまの構造の何が壊れているか

- **物理を軸にしている**ため、「風の重み0」で物理法則を無効にできてしまう
- 重みは正規化された配分のため、**物理と好みが同じパイを奪い合う**（圧迫感を重視すると風が
  効かなくなる）

### 軸は主観だけを扱う

風・勾配・路面・停止・ターンの**速度や待ちへの効きは軸の外**（走行モデル）。ただし
**材料は両方に現れてよい**——勾配は「速度が落ちる（物理）」と「きつい坂は避けたい（主観）」の
2つの効き方を持つ。風も同じ（遅い＋しんどい）。

## 決定（2026-09-13の議論で確定）

### コストの形は「合成」

```
コスト = 所要時間 ＋ 主観的割増
```

時間と主観を1つの数へ合成して最小化する。厳密な多目的最適化（時間と主観のパレート最適解の
集合を求める）は状態ごとに複数ラベルが要り、いまの規模（443k状態）では現実的でない。
**将来、換算レートを振って複数回探索しパレートフロントを近似する形へ広げられる**ようにして
おく（探索を複数回呼ぶだけで済む）。

### 走行モデル（所要時間）

| | 内容 |
|---|---|
| 入力 | **巡航速度のみ**（既存の`assumed_speed_kmh`） |
| 導出 | ホイール出力 P |
| 標準値 | CdA=0.32m²、Crr=0.005、質量80kg、ρ=1.225kg/m³ |
| 区間ごとの速度 | P と（勾配・向かい風成分・路面のCrr補正）から走行方程式を解く |

- 速度の逆算は`v`の3次方程式になる。**探索中には解かない**——勾配・路面は静的、風は時刻
  依存なので、**コスト配列を合成するときに区間ごと（風は時刻ビンごと）へ事前計算**する。
  ベクトル化したニュートン法（初期値に無風時の解や1つ前のビンの解を使えば反復が減る）
- **下りの上限**（安全速度）と**登りの下限**（これ以下は押して歩く）でクリップする。入れないと
  急な下りで非現実的な速度になり、激坂で所要時間が発散する
- **駆動系の伝達効率は段階1では不要**。巡航速度から逆算するのは「ホイールでの出力」で、他の
  条件でも同じ量を使うため相殺される。外部の出力値（FTP等）を入力させる段階で入れる

### 主観的割増

```
主観的割増 = 全体レート × Σ( 軸の重み × 軸の値 )
```

| | 何を決めるか | 利用者への見せ方 | 現在の対応物 |
|---|---|---|---|
| 軸どうしの配分 | 圧迫感 vs 事故 vs インフラ… | 重みスライダー（いまのまま） | 軸の重み |
| 主観 vs 時間 | 安全のために何分余計にかけてよいか | 「速さ⇄快適」1本、または「基準線+◯分まで」 | **`penalty_strength`の後継** |

較正は「**軸の値100の道を1km走るのは、値0の道より体感◯分長い**」の◯を1つ決めるだけでよい
（軸間の配分は重みが担う）。主観のため実測はできない。いまの既定`penalty_strength=1.0`は
「難易度100の道は距離が2倍に相当」の意味なので、「所要時間が2倍に感じる」が素直な対応。

### 風・勾配の二重性

| 「向かい風／坂に弱い」の意味 | どこで表現するか |
|---|---|
| **実際に速度が落ちる** | **走行モデル。軸ではない**——遅い人ほど大きく落ちるのは式から出る（向かい風5m/sで、20km/h巡航の人は42%減、30km/h巡航の人は25%減） |
| **遅くなる以上に避けたい** | **軸**（任意。重み0でよい） |

同じ巡航速度での差（車種・ポジション＝CdA）は段階2の入力であって、軸ではない。軸で補正すると
物理と二重になる。

### 基準線

主観の重み（または全体レート）を0にしたとき＝**時間最短**。周回モードでも意味を持つ——距離が
固定なので「止まらずに流れる周回」になる。「あえて登りたい」は主観側で表す。

## まだ決めていない論点

1. **周回モードの基準線**。距離を指定するモードでは「時間最短＝平均速度最大」になるが、それが
   「最も優秀」か（トレーニング目的なら、あえて登ることもある）
2. **合成するか、分けたまま見せるか**。`時間＋割増`を1つの数にして最小化するか、時間と主観を
   2つの量としてパレート最適な候補を並べるか。**現在の実装は両者が混ざっている**
   （コストは合成なのに、候補選定は非優越ソート）
3. **主観の単位**。体感時間への加算か、時間への倍率か

## 移行の設計（2026-09-13時点の整理。未決の論点は下記）

### 所要時間の構成要素

| 要素 | 時間としての式 | 要るもの | 現状 |
|---|---|---|---|
| 走行 | 距離 ÷ 実効速度 | 実効速度のモデル | **固定速度**（`assumed_speed_kmh`）。勾配・風・路面は「難易度」側にいる |
| 停止 | 回数 × 1回あたりの秒 | 停止種別ごとの秒（信号・踏切・一時停止） | 密度→折れ点→難易度（[T787](T787.md)） |
| ターン | 遷移ごとの秒 | 較正 | **秒として実装済み**（段階2a） |

### 実効速度のモデル

自転車の速度は物理で決まる（出力＝空気抵抗＋転がり抵抗＋重力）。必要な入力は基本速度
（平地・無風での巡航）と、勾配・向かい風・路面の補正。`wind_drag_ratio`（風）・
`gradient_percent`（勾配）・`surface_good`（路面）はすべて材料として既にあり、いまは
「難易度」へ写している。同じ材料を「速度」へ写し直すことになる。

### 主観的割増に残るもの

車の圧迫感・事故密度・自転車インフラ・開放度・路面の不快さ。**時間には写らない**
（同じ速度で走れても、危ない道は避けたい）という性質のもの。

### 移行の段階（案）

1. **所要時間を出せるようにする**（表示のみ。探索は現状のまま）。実効速度モデル＋停止の秒＋
   ターンの秒。ここで「この候補は何分かかるか」が言えるようになる
2. **基準線を時間最短にする**（`select_shortest_distance_route`→時間最短）
3. **比較表示をトレードオフにする**（「+12分／信号半減」）
4. **探索のコストを「時間＋主観的割増」にする**（風・勾配・停止を時間側へ移す）
5. **時刻依存（段階2b）を時間ベースで入れる**

段階4まで来ると、風は「難易度」ではなく「速度」なので、段階2bは「到達時刻で速度を引き直す」
形になる。**この順序なら2bを一度だけ作れる**（先に2bを作ると、風を難易度として時刻依存化した
部分を作り直すことになる）。

### 未決の論点（着手前に決める）

1. **実効速度モデルをどこまで持つか**。体重・出力・空気抵抗係数まで持つのか、勾配と風だけの
   簡易補正にするのか。利用者に何を入力させるか（いまは巡航速度のみ）
2. **軸（`axis_definitions`）の扱い**。風・勾配は「速度への影響」になるため、いまの軸
   （難易度を返す）とは別の種類になる。軸の定義を拡張するのか、速度側は軸の外に出すのか
3. **主観的割増の形**。所要時間に対する倍率（`時間 × (1 + 割増)`）か、時間への加算
   （「危ない道は体感◯分増し」）か
4. **停止の秒の根拠**。信号待ちの期待値をどう決めるか（T787で測りかけた部分）
5. **表示**（ルート結果パネル・比較タブ）をどう変えるか。所要時間が主役になる

## 基準線とコストの単位（2026-09-13、ユーザーとの議論から。段階2bより先に決める）

### いまの構造の問題

- コストは`distance_m × (1 + P × difficulty/100)`で、**時間でも距離でもない合成量**。
  「重み付けを度外視して最も優秀」を測る軸が無い
- 基準線（`select_shortest_distance_route`）は**距離最短**。信号・ターン・勾配・風による
  時間の損失を一切見ないため、「最も優秀な経路」ではない
- 候補と基準線の比較は距離差（「+4.0km」）だけで、**払った対価しか見せず、何を買ったのかを
  見せていない**

### あるべき姿

基準線は**重み付けを度外視して最も優秀な経路＝時間最短**。利用者が重みを付けた結果は、
基準線に対するトレードオフとして表れる:

> 基準線より12分多くかかる。代わりに信号が半分、右折が1/3。

**時間では基準線を上回れない**（定義上それが最短）。上回るのは利用者が重みを付けた観点で、
候補の価値は常にトレードオフとして表れる。

### 2つの水準

| | 内容 | 影響 |
|---|---|---|
| **(a) 基準線と比較表示だけ時間ベース** | 候補の選び方は難易度のまま。基準線を時間最短にし、比較を「+12分／信号半減」で出す | 中。所要時間を正しく出す仕組みが要る |
| **(b) コスト自体を時間ベース** | 難易度を時間へ写し（危険な道は体感時間が長い等）、探索を時間で解く | 大。軸の意味の定義し直しを含む |

**(a)が先**。(b)をやるにしても「所要時間を正しく出せる」ことが前提になる。

| 要素 | 状態 |

### 段階2bとの関係

所要時間が正しく出れば、通過時刻の推定精度も上がる（現在は「基準点からの直線距離×迂回率÷
仮定速度」）。2b（時刻依存）と同じ土台の上にある。

## 段階A・Bの実装結果（2026-09-13）

### 段階A: 走行モデルと所要時間

`domain/cycling_speed.py`を新設した。利用者が指定する**平地・無風の巡航速度**からホイール
出力を逆算し、走行方程式`P = (½ρCdA(v+w)² + Crr·m·g + m·g·grade)·v`を`v`について解いて区間
ごとの速度を出す（`v`の3次方程式になるため二分法。numpyでベクトル化）。

一定出力のままでは平地20km/hの人が勾配5%で時速4.6km（押して歩く速度）になり現実と合わない
ため、**登坂時は出力が漸増する**（`CLIMB_POWER_PER_GRADE`、上限`MAX_CLIMB_POWER_RATIO`で
クランプ）。下りは`MAX_DESCENT_SPEED_KMH`で頭打ち、解が歩く速度を下回る区間は
`WALKING_SPEED_KMH`（押して歩く）にする。風は向かい風成分だけでなく横成分も抵抗へ入れる
（`wind_drag_ratio_array`と同じ式）。

候補の所要時間 ＝ 区間の走行時間 ＋ 停止の待ち（`domain/traffic.py: stop_seconds`）＋
ターンの待ち。ルート結果パネルへ表示する（`formatDuration.ts`・`RouteAxisProfile`）。

### 段階B: 基準線を時間最短へ

`select_shortest_distance_route`→`select_fastest_route`。コスト配列に区間ごとの所要時間を、
遷移にターンの待ちをそのまま秒で渡す（`speed_ms=1.0`）。A*のヒューリスティックも秒の下界
（直線距離÷`MAX_DESCENT_SPEED_KMH`）にする。レグの分割位置は距離の半分から**所要時間の
半分**へ変えた。

`RouteCandidate.is_shortest_distance`→`is_fastest`。候補タブの表記は「最短」→「最速」、
他候補に添える対価は`+4.0`（km）→`+12分`（`extraDistanceLabel`→`extraDurationLabel`）。

**これで「重み付けを度外視した最優秀＝時間最短」が定義から出るようになった**。従来の距離
最短は、風・勾配・信号を無視した架空の物差しだった。

## 段階Cの実装結果（2026-09-13）

### 探索のコストを体感の所要時間にした

```
コスト（秒） = 区間の所要時間 × (1 + penalty_strength × difficulty/100)
```

区間の所要時間は走行モデル（勾配・風）＋停止の待ち、ターンの待ちは遷移ごとに秒で足す。
**エンジン全体でコストの単位が秒に揃った**ため、ターンの秒をコストの単位へ直す係数
（`speed_ms`）が探索の全関数から消えた。A*のヒューリスティックも秒の下界
（直線距離÷`MAX_DESCENT_SPEED_KMH`）になる。

`penalty_strength`の意味が「距離が何倍か」から**「主観 vs 時間の換算レート」**へ変わった。
P=1は「難易度100の道は体感で所要時間2倍」。P=0は好みを一切見ない＝時間最短で、
`select_fastest_route`の基準線と同じ物差しになる——**基準線が重みの極限として定義から出る**。

一対全木は実距離に加えて**素の所要時間**も積算する（`edge_seconds`）。コストには割増が
乗っているため、difficultyの逆算（`(cost/seconds - 1)/P`）には割増前の値が要る。

副次的に、コストの丸め（0.1単位）を秒では行わないようにした。距離の0.1mは無視できるが
秒の0.1は短い区間の数%にあたり、difficultyの逆算に丸め由来の差が出る（折返し点の
並べ替えが壊れることを`test_select_turnarounds_ring_lower_bound_clamped...`の失敗で検出）。

### 段階Aのコードに欠陥が2つあった

**1. 走行モデルに勾配が届いていなかった。** 所要時間の算出が勾配を`material_arrays`
（＝内訳として画面へ見せる材料の辞書）から読んでいたが、この辞書へ入るのは**軸が分解した
材料だけ**で、本番の軸構成に`gradient_percent`は無い。結果、勾配が常に0として扱われ、
**走行モデルが坂で一切減速していなかった**（探索コストと画面の所要時間表示の両方）。
静的スコア行列が常に持つ生配列（0次フィルタの勾配しきい値と同じ列）から読むよう修正。

既存の`test_prepare_applies_precomputed_gradient_to_search_cost`がこれを見逃したのは、
「急坂 > 平地」しか見ておらず**勾配軸の割増だけで成立してしまう**ため。勾配軸の重みを0に
した上で差が出ることを要求する`test_search_cost_slows_down_on_a_climb_even_when_the_
gradient_axis_is_off`を追加し、旧実装へ戻して落ちること（`climb_cost == flat_cost`）を
確認した。

**2. 同じ性質の潜在バグ。** 停止の秒も同じ辞書から`poi_*_per_km`を読んでおり、停止密度の軸
を非公開にした瞬間に所要時間から停止の待ちが静かに消える状態だった。走行モデルが要る材料を
`domain/traffic.py: stop_count_material_ids`として宣言し、軸構成に関わらず常に運ぶようにした。

**欠陥の性質**: 走行モデル（物理）の入力を、表示用の経路（軸の構成に依存する器）から
取っていた。物理は軸の公開/非公開で変わってはいけない。

所要時間の実装も1本へ寄せた（表示用の`_estimate_duration_seconds`が探索のコストの下地
`travel_seconds_full`をそのまま読む）。2実装あると片方だけ直したときに静かに食い違う。

### 較正へ送るもの（別タスク）

**物理を写した軸の既定重みが、走行モデルと二重に効く。** 本番スナップショットの既定重みは
風0.26・停止密度0.20・勾配0.15・舗装0.19で、配分の8割が走行モデルと同じ現象を見ている。
設計上は「実際に遅くなる（走行モデル）」と「遅くなる以上に避けたい（軸）」の別物だが、
**既定値が0でない限り、利用者は一度の意図で二重に払う**。

停止密度はずれの大きさも分かっている。[T787](T787.md)が測った現行の実効値は停止1回＝
200〜400m相当の迂回で、走行モデル側の信号21秒は20km/h巡航で約117m相当——**軸側が1.7〜3.4倍**。

既定重みの変更は`axis_definitions`のDB行データ操作（軸スタジオAPI＋本番反映）のため、
コードの変更とは切り離す。

**舗装は走行モデルへまだ繋がっていない**（`cycling_speed.speed_ms`は`crr`引数を受け取れるが
呼び出し側が渡していない）。路面のCrr補正を入れるかは、値決めと一体のため較正タスクで判断する。

## 段階Dの実装結果（2026-09-13）

### 探索が「出発からの経過時間」を持ち回る

コスト配列を`(時刻ビン, 状態)`の2次元で渡せるようにし、探索は自分の経過時間からビンを選んで
コストと所要時間を引く。ビンの幅は`TIME_BIN_HOURS`（0.5時間、風の予報は1時間刻みのため
それより細かく切っても元データの解像度を超えない）、本数の上限は`MAX_TIME_BINS`。

従来は各区間の通過時刻を**基準点からの直線距離÷仮定速度**で推定していた
（`estimate_passage_hours`）。これが実際の経過時間に置き換わる。

一対全木もscipyからnumbaのDijkstraへ移した。時刻で変わるコストは、コストを辺の静的な属性と
みなすライブラリでは表せないため。副次的に`build_turn_expanded_csr`（毎回のlexsort・
concatenate）と実距離のポインタジャンプ積算が落ち、`domain/routing.py`からscipy依存が消えた。

**1ラベル法**（状態ごとにコスト最小の1本だけを保つ）である点はコードと文書に明記した。
コストは時間そのものではないため、「コストは高いが早く着く」経路を捨てる近似になる。

### 後ろ向き木の扱い（3案から「後ろ向きは静的」を採用）

目的地モードの後ろ向き木は、目的地から遡るため各状態の到達時刻が決まらず時刻ビンを使えない。
段階2bの論点に挙げた3案のうち**案2（後ろ向きは静的）**を採った。残り2案は候補ごとに追加の
探索が要り、このタスクで最優先に置いたレスポンスへ直接響くため（案1は2点間探索の実測
179〜257ms×候補数、案3は目的地モードの探索がおよそ倍）。

ただし静的のまま放置はせず、**前向き木が出した実際の到達時間を後ろ向きレグの通過時刻として
渡す**ようにした（`compose(passage_hours=...)`）。直線距離からの推定より実態に近く、候補は
`ALTERNATIVE_MAX_STRETCH`以内に制限されるためずれもその範囲に収まる。前向き木が届かない
区間だけ直線距離の推定へ落ちる。

近似が残るのは**目的地モードの復路側だけ**。周回モードは往路が前向き木、復路が前向きA*で、
どちらも実際の経過時間を持ち回る。

### 同じ型の欠陥がもう1つあった

`time_varying`（時刻で風を引き直すか）の判定が**風に依存する軸の重みが0より大きいか**を
条件にしていた。風が軸だけの存在だった頃は正しかったが、段階Cで風が走行モデルの入力に
なった後は、**風の重みを0にすると速度計算まで時刻固定に落ちる**。段階Cで直した勾配・停止と
同じ「物理が軸の設定に依存する」型。条件を「風の予報があれば常に」へ直した。

### 残した判断

**区間表示（`_build_segment_details`）は代表ビン（レグの中間地点が入るビン）を読む。**
区間ごとに対応するビンを引くには全ビンの表示用配列（軸別スコア・寄与度・材料値）を
メモリに保持する必要があり、得られるのは表示値が最大で半レグぶん実態へ寄ることだけ。
**経路そのものを決める探索は実際の経過時間を使う**ため、ここは代表値で足りると判断した。

### 何に時間が増えたか

段階2a比で+2,400ms。内訳は**走行モデル（所要時間の物理）そのもの**が主。

- `prepare` +818ms: コスト合成が区間ごとの所要時間も解くようになった（走行方程式の二分法）
- `select` +893ms: 復路レグの合成（700ms）。往路は時刻ビンが1本に収まりprepareの結果を
  そのまま使う
- `trace` +525ms: 2点間A*が到達時刻ラベルを持ち回るぶん

**時刻ビンそのものの費用はほぼ無い**——目標30kmの周回はレグ0.75時間で1本に収まるため
（100km級で3本）。最適化前に8,350msだったのは、ビンの幅を予報より細かく取り、かつビンごとに
全軸を合成し直していたため。

### 最適化で何をしたか

1. **軸合成が軸数にほぼ比例していた**（実測 10軸274ms / 2軸74ms / 1軸48ms、開発DB319,530区間）。
   時刻で変わるのは風に依存する軸だけなので、それ以外の重み付き和を1回だけ求めて使い回す。
   代表以外のビンは軸別寄与度・材料値を組み立てない
2. **速度の逆算が反復ごとに配列を確保し直していた**（12反復×5本）。バッファを用意して
   その場演算にした（354ms→139ms）
3. **ビンの幅を予報の刻み（1時間）へ揃え、ビンの開始時刻で評価する**。`sample`は最も近い
   正時を引くため、中心時刻だと隣り合うビンが同じ予報時刻を引くことがあった（実測で
   コストが完全に一致＝時刻依存が効いていなかった）

合成1本あたり（開発DB・319,530区間）: 表示用779→503ms、探索用779→246ms。

### 採らなかった案

- **二分法をnumbaで書き直す**: 79.8msで、numpyのその場演算版74msと変わらない。コンテナ
  起動ごとのJITコンパイル代だけ増える
- **二分法の反復を12→8へ減らす**: 速度は変わらない一方、平地・無風で巡航速度に一致しなく
  なる（0.38%ずれる）

## 段階2の実装計画（2026-09-13確定、段階1の実測を踏まえて）

2a→2c→2bの順で進める。構造（辺基準化）を先に入れ、その上に質（交差点属性）と時刻を乗せる
ことで手戻りを避けるため。

#### 2a: 辺基準化とターンの費用（依存追加なし、一対全木は+6ms）

- **2a-1**: `domain/routing.py`へ辺基準の展開構造とターンの費用を足す（既存の経路は変えない
  純粋な追加）。グラフは物理的に増やさず遷移は既存のCSRから導き、一対全木へ渡すときだけ
  scipy用のCSRを組む
- **2a-2**: 一対全木（`select_loop_turnarounds`・`select_via_nodes`・
  `select_shortest_distance_route`）を辺基準へ切り替える
- **2a-3**: 2点間探索（`trace_loop`・`trace_loop_from_turnaround`・`preview_segment`）を
  辺基準へ切り替える。2a-2で使われなくなった`build_shortest_path_tree`・
  `tree_path_edge_indices`系・`build_csr_structure(reverse=True)`の撤去も、2点間探索の
  切り替えで`shortest_path_node_ids_lazy`の要否が決まってから一括で行う
- **2a-4**: ターンの費用のパラメータ化（いまは方位差だけの暫定値）

#### 2c: 交差点ノードの属性（実走の指摘「信号のない幹線横断」）

`road_nodes`へ信号の有無・接続する道の最大highway階級を持たせ、バッチで事前計算する
（`precompute_road_node_degrees.py`と同じ形）。ターンの費用がこれを読むことで「信号のある
交差点の直進より、信号の無い交差点で上位階級の道を横断・右折する方が高い」を表せる。
**Edgeへ畳み込んだ値を`road_edges`の列やMVTタイルへ焼かない**。

#### 2b: 時刻依存の状態化（numba導入、一対全木は+49ms）

到達時刻をラベルとして持ち回る探索をnumbaで実装する。`architecture.md`「技術選定」への
numba追加・`requirements.txt`・本番VMでのビルド確認を含む。1ラベル法（コスト最小で確定）は
**近似**である点（RideCompassのコストは時間ではないため、厳密解には多ラベル法が要る）を
実装と文書の両方へ明記する。

## 見積もりと実測の乖離（このタスクで起きたこと）

段階1の検証で出した見積もりが、組み上げた全体では合わなかった。**部品を1つだけ測って全体を
判断した**ことが共通の原因で、同じ型の誤りを3回している。

| 見積もり | 実測 | 何を見落としたか |
|---|---|---|
| 一対全木は**+6ms**（83ms vs 77ms） | 周回で**+190ms**、目的地で**+1,500ms** | 測ったのは木1本のdijkstra時間。実際は前向き・後ろ向きの2本＋scipy用CSRの組み立て2回＋繋ぎ目の合成（130万遷移のlexsort） |
| 周回生成が難所、規模はXLへ寄る | 周回は**ほぼ同等**（2,480→2,493ms）、目的地だけが2.1倍 | 周回は繋ぎ目の合成を使わない。難所は目的地モードだった |
| 段階2bは「numbaのA*に時刻ラベルを足すだけ」 | **目的地モードの設計変更を含む** | 後ろ向き木は目的地から遡るため各状態の到達時刻が決まらない。段階1で測った「時刻依存の一対全木132ms」は前向きの想定で、後ろ向きは検証していない |

**運用上の反省**: 1つ目の乖離（周回の+190ms）には段階2aの本番計測で気づいており、この
ファイルへ1行書いた。しかし報告では「劣化なし」とまとめ、目的地モードを測らないまま段階2bを
別タスクへ切り出そうとした。**見積もりと実測がずれた時点で、ずれ自体を報告する**。
この振る舞い自体への対応は[T798](T798.md)。

**この結果として本番に残っている形**: 風のために骨格を組み替えたのに風は従来のまま
（レグ別スナップショット）で、目的地モードだけ2.1倍遅く、ターンの効果だけが入っている。
設計として選んだ形ではなく、段階ごとにデプロイを重ねた結果。段階2bまで進めて解消する。

## 段階2bの論点（切り出さずこのタスクで解く）

時刻依存を入れると、目的地モードのvia-node方式（前向き木＋後ろ向き木をNodeで繋ぐ）が
そのままでは成立しない。後ろ向き木は目的地から遡るため、各状態に「何時に着くか」が決まらない
ため。周回モードは前向き木＋復路の2点間A*で、どちらも起点から時刻が積み上がるので延長線上に
ある。

選択肢:
1. 後ろ向き木を使わず、目的地モードも前向き探索だけで解く（候補の作り方から変える）
2. 後ろ向き木は静的コストで張り、前向きだけ時刻依存にする（近似。現行のレグ別スナップ
   ショットの延長）
3. 2パス反復（1回目の経路から通過時刻を確定し、2回目で引き直す。[T532](T532.md)が将来案として
   残していた）

## 前工程を先に整える場合の条件

交差点ノードの分類（信号の有無・交差する道の最大階級）は、再設計後もそのまま使う入力のため
先に整えても捨てない。ただし**ノード側の属性として持ち、Edgeへ畳み込んだ値を`road_edges`の
列やMVTタイルへ焼かないこと**——Edge側へ焼くと同じ事実が2箇所に出て、状態を移したとき片方が
古くなる。畳み込みによる近似では「交差点を通ること自体を嫌う」までしか表せず、右折と直進
横断は区別できない。
