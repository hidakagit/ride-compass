## 実施範囲の判断

3件とも実施した（見送りなし）。backend側の語彙分離（5-6・5-7）を先に片付けてから
frontendの汎用化（5-1）へ進んだ——frontendがフェッチのクエリパラメータを軸カタログから
導出するには、backend側で`needs_time`/`needs_speed`を軸カタログへ公開する必要があり、
依存の向きがbackend→frontendだったため。

## 対応内容

### 5-6・5-7: 軸idと材料idを別の名前空間として分離する（backend）

この機構には名前の似た2つのidがある。**軸id**（`axis_definitions.axis_id`、例`wind`）と
**材料id**（`material_catalog.py`のキー、例`wind_drag_ratio`）で、前者がルーティング・
ファクトリ登録・キャッシュ名前空間を、後者が「サービスが返す生値を軸定義のどの材料として
評価するか」を決める。従来はこの2つがどちらも`material_id`という名前で呼ばれていた。

| 旧 | 新 |
|---|---|
| `DynamicWayValueMaterial`（`material_id`フィールド） | `DedicatedWayValueAxis`（`axis_id`フィールド） |
| `dynamic_way_value_materials()` | `dedicated_way_value_axes()` |
| `_DYNAMIC_WAY_VALUE_SERVICE_FACTORIES` | `_DEDICATED_WAY_VALUE_SERVICE_FACTORIES` |
| `implemented_dynamic_way_value_material_ids()` | `implemented_dedicated_way_value_axis_ids()` |
| `get_dynamic_way_value_service(material_id)` | `get_dedicated_way_value_service(axis_id)` |
| `GET /api/region/dynamic-way-values/{material_id}/...` | `GET /api/region/dynamic-way-values/{axis_id}/...` |
| `wind_way_service.AXIS_ID`（未参照の死んだ定数） | `WindWayService.axis_id`（クラス属性） |
| `gradient_way_service.MATERIAL_ID`（実体は軸id） | `GradientWayService.axis_id`（クラス属性、キャッシュ名前空間に使う） |

パスパラメータ名は変わるが**実際のURL文字列は変わらない**（`/wind/14/...`のまま）ため、
フロントの呼び出し・既存のキャッシュキーはいずれも無変更で通る。OpenAPIのパステンプレートと
`operationId`は変わるため生成物（`api.d.ts`/`openapi.json`）を同一コミットで更新した。

再発防止として`backend/tests/test_dedicated_way_value_services.py`を新設し、登録済みの
全サービスについて (1) `axis_id`属性＝ファクトリの登録キー、(2) `material_id`が材料カタログの
既知材料、(3) 2つが同じ値でない、を機械的に検査する。(3)は「片方の属性しか持たない写経」
（＝2つの名前空間の区別が付いていない実装）を検出するためのもの。

### 5-1: レイヤー登録・カタログ・可視性・フェッチを軸カタログから導出する（frontend）

ramp軸が既に持っていた汎用機構（`RampAxis` + `axisMapLayerId` + `buildAxisOverlayLayers`）と
同じ形を専用way値配信軸にも用意し、軸ごとのハードコードを撤去した。

| 汎用化したもの | 新設・変更 |
|---|---|
| 軸一覧 | `axisLayers.ts: DedicatedWayValueAxis` / `dedicatedWayValueAxesFromCatalogAxes` / `DEDICATED_WAY_VALUE_AXES`、`useAxisCatalog`の`dedicatedAxes` |
| レイヤーID | `dedicatedWayValueMapLayerId(axisId)`（`${axisId}Axis`）・`dedicatedWayValueLineLayerId(axisId)`（`region-${axisId}-axis-line`）。`MapLayerId`の`"windAxis"`/`"gradientAxis"`リテラルと`WIND_AXIS_LAYER_ID`/`GRADIENT_AXIS_LAYER_ID`定数を撤去 |
| レイヤーカタログ | `buildMapLayers(rampAxes, dedicatedAxes)`が記述子を生成（手書きの2エントリを撤去） |
| 地図UIからの除外 | `isAxisStudioLayer`をビルド時静的json由来のID集合ではなく記述子の`axisStudioLayer`フラグで判定。`OverlayLayerChip`にも同フィールドを追加 |
| MapLibreレイヤー登録 | `buildStaticOverlayLayers(axisOverlayLayers, dedicatedAxes, ...)`が`dedicatedAxes`をmapして生成 |
| ズーム範囲外判定 | `buildRoadSurfaceSharedLayerIds(rampAxes, dedicatedAxes)` |
| 表示ON/OFF | `MapViewProps.showWindAxis`/`showGradientAxis`を`dedicatedWayValueVisibility: Record<string, boolean>`へ統合（`axisVisibility`と同じ形） |
| feature-stateのクリア判定 | `shouldClearDedicatedWayValueFeatureState(visibility)`——2引数の`!a && !b`から、軸の件数に依存しない全称判定へ |
| フェッチ | `useDynamicWayValues`（軸ごとに1インスタンス）を`useDedicatedWayValues`（軸の配列を受け取る1インスタンス）へ置き換え |
| クエリパラメータの取捨 | 軸カタログの`dynamic_way_value_needs_time`/`_needs_speed`（backendへ新規公開）から導出 |

**`isAxisStudioLayer`の判定をID集合からフラグへ移した理由**: 旧`DEDICATED_WAY_VALUE_LAYER_IDS`は
ビルド時静的な`axis-catalog.json`から作られており、実行時フェッチで現れた軸（＝軸スタジオで
新規公開した3件目）はこの集合に入らない。一方レイヤー記述子は実行時カタログから生成される
ため、3件目だけが「記述子は在るが除外判定には掛からない」状態になり地図チップへ漏れ出る。
記述子自身が生成元の情報を持つ形にすれば、この2つの経路が食い違うこと自体が起こらない。

**フックを1本化した理由**: Reactのフック規則により、実行時に増減しうる軸の件数だけフックを
呼ぶことはできない。軸ごとのインスタンス化を続ける限り「3件目の軸には`page.tsx`へ
`useDynamicWayValues(...)`を1行足す」という手作業が残り、指摘①（レンズにも地図にも
現れない）が再発する。

**時刻依存でない軸を巻き添えで再フェッチしない**という既存の性質は、軸ごとのリクエストキー
（軸id＋その軸へ載せるパラメータ＋向き＋対象タイル集合）を持たせて維持した。旧実装では
「勾配の`useDynamicWayValues`へ`at`をundefinedで渡す」という呼び出し側の書き分けで実現して
いたもので、軸カタログの`needsTime`から導出する形へ移した。回帰テスト
「時刻が変わっても、時刻に依存しない軸は再フェッチしない」で固定している。

**gradientFillだけは軸id`gradient`を名指しする**。環境グループの勾配面表示は専用way値配信の
汎用機構ではなく勾配固有のレイヤー（`gradientGridFill.ts`、`GRADIENT_FILL_LAYER_ID`）で、
評価軸グループの線とは独立にON/OFFできる一方、値は同じway単位データの集計で作れるため
フェッチ対象に加える必要がある。名指しの箇所を1つに閉じるため`GRADIENT_AXIS_ID`定数を
`gradientGridFill.ts`へ置き、`page.tsx`（フェッチ対象の決定）と`MapView.tsx`（面の表示宣言の
引き当て）の両方がこれを参照する。

## 撤去した手書き文言について

`mapLayers.ts`の`windAxis`/`gradientAxis`記述子が持っていた`label`（「風（評価軸）」）・
`chipLabel`（「風軸」）・`description`・`panelHint`（各5〜8行の説明文）は、
`isAxisStudioLayer`により地図上チップ（`MapOverlayControls`）・サイドバー
（`MapLayersPanel`）の両方から除外されるため、**どの画面にも表示されない文言**だった
（記述子自身のコメントにも「実際に使われているのは(1)`MapLayerId`型の定義、(2)
`buildRoadSurfaceSharedLayerIds`への登録の2点のみ」と明記されていた）。汎用化に伴い、軸自身の
データ（`label`・`chip_label`・`panel_hint`）から埋める形へ置き換えた。将来この説明文を
実際に表示したくなった場合の置き場所は軸スタジオの`panel_hint`フィールド（ramp軸が
`panelHint ?? note`で使っているのと同じ経路）で、コード側に軸ごとの文言を戻す必要はない。
