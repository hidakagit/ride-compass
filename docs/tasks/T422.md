# T422. 「環境」グループに合成面データ用のプレースホルダー構造を用意する（T400節1の未実装分）

状態: **見送り（2026-08-30、ユーザー判断）**——実際に合成面データを環境グループへ追加する
具体的なニーズが出るまで着手しない。トリガー: 環境グループ向けの合成面データを追加する
判断をした時点（着手時にこのタスクへ戻ること）。

あわせて確定した関連ルール（2026-08-30、ユーザー訂正込み）: 地図UIの排他ドメイン原則
（線同士・面同士・点同士は重ねない、線と面は重ねてよい）に対する例外は、**個別レイヤーIDの
列挙ではなく「防災カテゴリ・常にオンにすべきもの」という性質による一般化されたルール**として
扱う（現在の初期値でこれに該当するのはキキクル4種[`landslideRisk`・`heavyRainRisk`・
`inundationRisk`・`linearRainbandRisk`]だが、これは結果であって定義ではない）。今後
環境グループへ新規追加する合成面データ（本タスクが実現する場合含む）は、同じ「防災・常時
オン」という性質を持たない限りこの例外の対象にならず、原則どおり単一選択の排他ドメインに
従う。

**既知の実装との食い違い（2026-08-30発見、本タスクとは別に対応要）**: 現在の実装
（`frontend/src/app/page.tsx`の`FIXED_LAYER_VISIBILITY_DEFAULTS`・`isDynamicGroupLayer`
判定）は、上記の「性質による一般化ルール」ではなく**4つのレイヤーIDを直接列挙する
ハードコード**になっている。新しい防災系レイヤーが増えるたびにこの列挙へ追記が必要な
設計で、「防災カテゴリなら常時ON」を宣言的に表現できていない。理想的には
`MapLayerDescriptor`へ`alwaysOnByDefault`のような宣言的フィールドを持たせ、
`FIXED_LAYER_VISIBILITY_DEFAULTS`の算出・排他ドメインの初期値適用ロジックの両方が
それを参照する形へリファクタすべきだが、影響範囲の精査が必要なため本タスク（T422、
見送り中）とは別に、着手判断が必要な小さな改善として記録のみ残す（起票はまだしていない、
着手する場合は改めてタスク化すること）。

- 背景: [T400.md](T400.md)「1. パネルの最上位グルーピング」節に「『環境』グループの
  『推定』枠（対象データを軸スタジオ的に合成した面データ）は現状空だが、将来増える可能性を
  見込み構造だけ用意しておく」という決定があったが、[T406](T406.md)の実装ではこの
  プレースホルダー構造が作られていない（`mapLayers.ts`・`MapOverlayControls.tsx`の
  環境グループは標高図・降水ナウキャスト等の生データのみで構成されており、将来の合成面
  データ用の枠が無い）。T400.md本文には「（ユーザー: 『わからない。今まだ研究段階だから
  断定できない』）」という注記があり、優先度が低いまま実装時に見落とされたと見られる。
- 影響: 現時点では実害なし（環境グループに合成面データ自体が存在しないため、枠が無くても
  何も困らない）。ただし将来、環境グループ向けの合成面データ（例: 複数の気象材料を合成した
  指標等）を追加する際、この構造が無いまま「道路グループの評価軸と同じ扱いにする」等の
  場当たり対応になるリスクがある。
- 対応方針（未検討）: 優先度は低い。環境グループに実際に合成面データを追加する具体的な
  ニーズが出た時点で、改めて構造を設計するのでも間に合う可能性がある——着手前に
  「今すぐ構造だけ用意する」か「実際のニーズが出るまで待つ」かをユーザーへ確認すること。
