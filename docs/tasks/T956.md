# T956: 材料の導出をSQLへ寄せ、受け取りを列にする（[T955](T955.md)段階A）

状態: 着手（2026-09-19起票）

## 背景

材料は列指向（`EdgeMaterialTable`）で持つのに、DBからは1行ずつ受けてPythonで組み立て、
評価の直前に`to_legacy_dicts`で区間ごとの辞書へ**戻して**いる。導出（OSMタグの解釈）も
区間ごとのPythonで毎回やり直している。

[T955](T955.md)の本番実測で、これが冷パスの大半だと分かった。

| | 所要（42,134区間） |
|---|---|
| 軸の式だけ（全13軸） | **22.9ms** |
| 現行のD（`to_legacy_dicts`＋抽出ループ＋軸の式） | 1,150〜1,900ms |
| 現行のB 行→`EdgeMaterialBundle` | 1,432ms |
| 導出をSQLへ入れたときのSQLの増分 | **+80ms** |
| `array_agg`で列にしたときのSQLの増分 | **−47ms** |

**評価の本体は23ms。**残りは材料を区間ごとのPythonで作り直す費用で、SQLへ移しても
DB側はほとんど増えない。

## 対応方針

`MaterialSpec`が持つ導出を、区間ごとのPython関数からSQL式へ移す。読み出しは列ごとの
`array_agg`で受け、numpyへそのまま渡す。

消えるもの: `EdgeMaterialBundle`、`EdgeMaterialTable.from_bundles`、`to_legacy_dicts`、
`MaterialExtractionContext`、`_evaluate_axes_bulk`の抽出ループ、`ElevationAttribute`/
`EdgeAttributeCounts`のDBからの再構築。**表現の変換が4回から1回になる。**

`wind_drag_ratio`だけはリクエスト時に決まるためPython側に残る（現状も`extractor`を
持たず`DYNAMIC_MATERIAL_EVALUATORS`が配列を作る形で、この分岐は変わらない）。

### Pythonのextractorは消す（残さない）

「答え合わせのオラクルとして残す」は成立しない——2つの実装が一致しても正しさの証明には
ならず、検知できるのは片方だけを変えたことだけである。正当性を担保しているのは
`tests/test_material_catalog.py`の人が書いた期待値であり、**それをSQL側に対して実行する
形へ移すのが移行の本体**（[T960](T960.md)）。extractorを残せば材料の定義が2か所のままで、
このタスクの目的が果たせない。

### 移す先は3経路ある

`resolve_materials`の利用者は`_evaluate_axes_bulk`（探索）・`compute_edge_axis_scores`
（区間表示）・`axis_inspector`（区間インスペクタ、way単位）。後ろの2つは1件ずつの都度
呼び出しのため、SQLを1回投げる形にする。

## 注意: 列がずれても誰も気づかない

列ごとに`array_agg`するとき、**すべての列が同じ`ORDER BY`を持つ**必要がある。
1つでも違えば値が列間で静かに食い違い、エラーは出ない。区間idの配列を正本にし、
組み立てたあとに他の列の長さと並びが一致することを検査する。

## 設計

### SQL式はdomainに置く

`MaterialSpec`が持つ導出を、Python関数（`extractor`）からSQL式（`sql`）へ移す。式は
いま`infrastructure/osm_way_tag_sql.py`にあるが、**材料が何から導かれるかはdomainの知識**の
ため`domain/`へ移し、タイル配信・カバレッジ集計・軸スタジオの値列挙はそこを参照する形にする
（現状と同じく1箇所を共有する構成は保つ）。

式はテーブルのエイリアス（`w`＝`osm_raw_ways`、`re`＝`road_edges`等）を前提にする。これは
既存の断片と同じ約束で、読み出し側がFROM句を組み立てる。

### キャッシュする表は、生値の列を捨てて材料の列にする

本番1タイル（42,134区間）の材料テーブルは10.5MBで、内訳は`landcover_percents` 24.6%・
`elevation_calculated_at` 13.4%・`way_tags` 10.3%・`edge_ids` 9.5%。復元は52msで、
ここは冷パスの問題ではない（[T546](T546.md)が既に列指向化した成果）。

`way_tags`（タグの辞書を区間数ぶん）は、Python側でタグを解釈するために持っている。導出が
SQLへ移れば要らなくなり、代わりに導出済みの材料の配列（真偽はbool配列、数値はfloat64配列）が
入る。土地被覆・標高・件数は**いまの列がそのまま材料**なので変わらない。

### `get(edge_id)`は残す

経路が確定したあとの数百区間について、`road_graph_engine`が標高属性を、区間表示が
`EdgeMaterialBundle`を引く。ここは区間数が小さく冷パスの費用ではないため、表から
その場で組み立てる今の形を保つ。`ElevationAttribute`の表示用フィールド
（`data_source`・`calculated_at`等）は材料ではないが、この用途のために列として残す。

### `_evaluate_axes_bulk`は材料の配列を受け取る

いまは「区間ごとの辞書 → `MaterialExtractionContext` → extractor → 配列」。これを
「配列をそのまま受け取る」へ変える。動的材料（`wind_drag_ratio`）と、グラフから直接作る列
（`distance_m`・`bearing_deg`・`mid_lat`/`mid_lon`・0次フィルタのフラグ）は今のまま残る。

### 消す順序

1. タイル経路（`_get_or_build_tile_materials`）をSQL導出＋列受け取りへ
2. 区間表示（`compute_edge_axis_scores`）と区間インスペクタ（`axis_inspector`）をSQLへ
3. `extractor`・`MaterialExtractionContext`・`resolve_materials`・`EdgeMaterialBundle`を消す

**1だけを入れて止めない**——止めると材料の定義が2か所のまま残り、このタスクの目的が
果たせない。性能は1で出るが、複雑度は3まで行って初めて下がる。

### 注意: 本番は自動デプロイされる

`deploy-backend.yml`が`backend/**`の変更を検知して本番へ出す。途中の状態をpushしない。

### キャッシュ鍵

`EdgeMaterialTable`の列構成が変わるため`cache_identity.shape_digest`が別の署名を出し、
古いディスクキャッシュは復元されない（手でリビジョンを上げる必要は無い）。**入れ替えの直後は
全タイルが冷パスになる**ため、[T959](T959.md)（ウォームアップ）の要否がここで効いてくる。

## 真偽の材料は`COALESCE(..., false)`で閉じる

タイルSQLの`CASE WHEN 条件 THEN true END`は「該当しない」と「判定できない」をどちらも
NULLへ畳む（タイルからキーを省くための符号化）。これをそのまま材料の導出に使うと、
`bicycle_infra_quality`が「自転車道が無い」と「分からない」を同じものとして評価する。

**材料の導出はタイルの符号化と分ける。** 読み出し経路の`way_tags`は該当Wayが無くても
空辞書になる（`EdgeMaterialBundle.way_tags`）ため、extractorはタグ不在をFalseとして返す。
`MATERIAL_VALUE_SQL`は`COALESCE(..., false)`で閉じ、これと同じ2値にする。

## 実装の記録

### 段階1: 材料の導出をSQLへ（完了）

`MATERIAL_VALUE_SQL`（材料id→値を求めるSQL式）を`domain/material_sql.py`へ置き、
`get_edge_material_arrays`が`array_agg`で列として受け取る。探索の両経路
（タイルキャッシュ経由・split鮮度が古いときのbbox限定再構築）が新経路を通る。

**材料の持ち方はdtypeごとの2次元配列**（数値・真偽・カテゴリ）。材料ごとに配列を分けた
最初の実装は、ディスク復元を10.47MB/86〜95msから13.92MB/340msへ**悪化させていた**
——小さい配列とPythonリストを多数解くより、大きな連続配列を解くほうが速い。
`StaticEdgeScoreMatrix`が既に採っている「値の行列＋idの並び」へ揃えたところ
12.27MB/30〜41msになった（ユーザー指摘）。同じ文字列を共有させる
（`_shared_strings`）だけで`elevation_calculated_at`が1,440KB→380KBになる。

区間そのものの列（距離・方位・中点・highwayフィルタ）も同じクエリで受け取る。これを
グラフのオブジェクトからPythonで組んでいたぶんが、行列構築156msのうち114msだった。

### 残り

- 区間インスペクタ（`axis_inspector.way_scalar_materials`）・軸スタジオのプレビュー
  （`axis_preview_service.load_way_sample`）をSQLへ。**同じ式にway向けのFROMを与える**
  形にする（式は`re`/`c`/`e`/`el`/`wl`/`d`のエイリアスを前提にしているため、wayの行から
  同じ形のエイリアスを組み立てれば使える）。
- スカラー経路（`compute_edge_axis_scores`・`compute_edge_cost`）を、材料値を受け取る形へ。
  本番の呼び出し元は無く、軸の式を突き合わせるオラクルとしてのみ使われている。
- `extractor`・`MaterialExtractionContext`・`resolve_materials`・`EdgeMaterialBundle`・
  旧`EdgeMaterialTable`・`to_legacy_dicts`・`tests/material_arrays_scaffold.py`の削除。
