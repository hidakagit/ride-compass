# T584: 材料`no_lit`（街灯なし）を`lit`（街灯あり）へ正規化し、専用の反転機構を撤去する

状態: 完了（2026-09-05起票・同日完了、ユーザー指摘。3段階すべて実施: 第1デプロイ
[`lit`材料追加・`no_lit`を非推奨エイリアス化]→本番・dev DB両方の夜間軸定義を
axis_admin API経由でno_lit依存からlit依存へ移行→第2デプロイ[`no_lit`・反転機構
[`tile_property_inverted`/`TileInputSpec.invert`]を一式削除]。詳細は下記
「実装（第1デプロイ分）」「軸定義移行（本番・dev）」「実装（反転機構の削除、第2デプロイ分）」
参照）

## 背景

管理画面「材料」タブ（[T577](T577.md)・[T583](T583.md)）を見たユーザーから、「他の真偽値材料は
『該当あり=true』なのに`no_lit`だけ『無いこと=true』で逆転している」という指摘があった。

- 真偽値材料は`has_tunnel`・`bridge`・`motor_vehicle_no`・`cycleway_has_track/lane/shared`・
  `shared_pedestrian_path`がすべて「該当あり=true」。`no_lit`だけ「`lit=yes`でない=true」で、
  抽出器は`tag_equals_extractor("lit", "yes", negate=True)`という特例（`domain/material_catalog.py`）。
- この反転を地図の色分け（ramp自動導出）まで通すため、`MaterialSpec.tile_property_inverted`→
  `registry.RampInput.invert`→`domain/axis_display.py`（3箇所）→API型`invert`→フロント
  `hooks/useAxisCatalog.ts`・`components/Map/axisLayers.ts`という専用の経路が、この1材料のためだけに
  存在する（他に`tile_property_inverted=True`の材料は無い）。設計原則「材料ごとの作り込みを
  避け、汎用の仕組みだけで表現する」に反する。
- 材料タブでは「街灯なし 90.4%欠損（確定値として評価）」と表示され、直感と逆に読める。

こうなっている理由は、夜間軸（`night`、公開済み）が「街灯なし(重み50)＋トンネル(重み50)」の
加点合計として作られており、フラグをすべて「ペナルティ方向でtrue」に揃えたかったこと、および
「タグ不明＝街灯なし（安全側）」という判断がこの向きの方が書きやすかったことによる。しかし
フラグは全部がペナルティ方向ではなく（自転車道系は「良い」方向）、向きは軸側の重みで表現できる
ため、材料をペナルティ方向に揃える必然性は無い。

## 対応方針

1. **材料の正規化**: `no_lit`を`lit`（ラベル「街灯あり」、`lit=yes`でtrue、タグ不在はfalse＝
   `missing_semantics="definite"`のまま）へ置き換える。抽出器は`tag_equals_extractor("lit", "yes")`
   （`negate`引数自体を撤去）。`tile_property="lit"`はそのまま、`tile_property_inverted`は
   フィールドごと削除し、`registry.invert`・`axis_display`の反転分岐・API型`invert`・
   フロントの`invert`処理を撤去する（`export_openapi.py`→`npm run generate:api`で生成物を同期）。
   `domain/night.py: resolve_night_flags`の`no_lit`も`lit`へ。
   `infrastructure/material_coverage.py: MATERIAL_COVERAGE_SPECS`の`no_lit`→`lit`
   （判定式は同じ`lit`タグの有無、source文言を「タグ不在は街灯なし扱い」のまま）。
2. **夜間軸の等価な書き換え**: 現行`terms=[no_lit(50), has_tunnel(50)]`・
   `breakpoints=[(0,0),(100,100)]`を、`terms=[lit(-50), has_tunnel(50)]`・
   `breakpoints=[(-50,0),(50,100)]`にする。街灯あり・トンネルなし=0、どちらも該当なし=50、
   街灯なし・トンネル=100で、現行と全組み合わせで同じスコアになる（`MaterialTerm.weight`は
   モデル上は負値可）。
3. **本番の適用順序**（[T396](T396.md)と同じ構図: 公開済み夜間軸のDB行が`no_lit`を参照しており、
   コードから消してpushすると`refresh_axis_definitions`の検証で本番backendが起動失敗する）:
   1. 第1デプロイ: `lit`を追加し、`no_lit`は非推奨エイリアス（同じ抽出器の否定、材料カタログ
      には出さない）として残す。
   2. 本番の軸定義をaxis_admin API経由で移行（夜間軸をunpublish→PUT[上記2]→republish。
      公開軸は不変のため複製ではなくこの手順）。`dump_axis_definitions_snapshot.py`で
      `backend/fixtures/axis_definitions_snapshot.json`を更新しコミット。dev DBも同様に移行。
   3. 第2デプロイ: `no_lit`エイリアスと反転機構を削除。
4. 事前に確認する点: 軸スタジオの重み入力UI（`AxisComposer`）が負値を受け付けるか、
   rampの自動導出（`domain/axis_display.py: derive_ramp_inputs`、真偽値項の加点合計を
   閾値へ変換する）が負の重みを正しく扱うか。扱えない場合は、`derive_ramp_inputs`側を
   「重みの符号で色の向きを決める」汎用処理にする（反転フラグの復活はしない）。

## 事前確認（対応方針4、負の重みの扱い）

コード調査で確認済み（実装変更は不要と判明）:
- frontend `AxisComposer.tsx`のterm係数入力（`SliderNumberField`、`min={-10}, max={10}`の
  スライダー＋制約なしの数値入力欄）は既に負値を受け付ける（改善計画T397フォローアップの
  コメントに「範囲外の値[旧flag_sumの加点50等]は数値欄から直接入力する想定」と明記あり）。
  breakpointsのx値入力欄（`NumberField`）も`min`指定なし。
- backend `derive_ramp_inputs`のboolean項処理は`true_value=term.weight`をそのまま渡すだけで
  符号を一切見ないため、負の重みも無改修で正しく動作する。`_boolean_terms_thresholds`の
  部分和計算（`combinations`+`sum`）も符号に依存しない。

## 軸定義移行（本番・dev、2026-09-05）

`scripts/`ではなく一時スクリプト（scratchpad、コミット対象外）でaxis_admin API
（Basic認証）を叩き、dev→本番の順で`night`軸をunpublish→PUT（`terms=[lit(-50),
has_tunnel(50)]`・`breakpoints=[(-50,0),(50,100)]`）→republishした。

- **同値性の事前検証**: `evaluate_axis_scalar`で旧shape（`no_lit(50)+has_tunnel(50)`,
  breakpoints`[(0,0),(100,100)]`）と新shape（`lit(-50)+has_tunnel(50)`,
  breakpoints`[(-50,0),(50,100)]`）を、街灯あり/なし×トンネル有無の全5パターンの
  `night_materials()`出力で比較し、全パターンでスコアが完全一致することを確認してから
  適用した。
- **適用結果**: dev・本番とも`display.thresholds`が`[25.0, 75.0]`→`[-25.0, 25.0]`
  （地図色分けの区切りとして等価）に自動更新されたことをAPI応答で確認。
- **fixtures更新**: `backend/fixtures/axis_definitions_snapshot.json`の`night`エントリの
  `shape`のみを本番の値に合わせて手動更新した（`dump_axis_definitions_snapshot.py`の
  全件ダンプは使わなかった——本番DBには本タスクと無関係な進行中の変更[`wind`軸のunpublish・
  breakpoints変更等、revision 38→47の差]が別途あり、無関係な変更を一緒くたに巻き込むと
  fresh bootstrap環境が中途半端な状態を引き継ぐリスクがあるため、night軸1エントリのみの
  最小差分に留めた。他の軸の差分は本タスクのスコープ外のため未対応のまま残る）。
  `pytest tests/test_migrate.py`（fresh bootstrap検証）green。
