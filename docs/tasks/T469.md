# T469. ゼロベース網羅レビュー§7(backend/services)の残指摘6件対応

  [zero-base-review-2026-08-30.md](../zero-base-review-2026-08-30.md)の§7。
- 補足: 同じ§7にあった`openrouteservice_engine.py`のコメント長大指摘は、レビュー自身が
  「実害無し」と結論し、かつT462（openrouteserviceエンジン削除）で当該ファイル自体が
  削除予定のため本タスクの対象外。
- 対象6件（severity・file:line・要旨。P1の2件[jma_amedas_service.py/region_service.pyの
  WARNING未出力]は別タスクで対応検討中のため対象外）:
  1. `elevation_attribute_service.py`(L58-90) P2: GSI標高APIの一時障害で全点None化した
     Edgeもそのまま永続化され以後リトライされない（elevation_service.py[T462削除対象]

  2. `axis_registry_service.py`の`create`(L148-179)/`update`(L181-204) P2: 読み取りと

  3. `region_service.py`(L356, 388, 411) P3: 複数メソッドのDB障害WARNINGが抑制機構

  4. `graph_service.py: _warming_tiles`(L24-77) P3: タイルキャッシュ温め失敗時に

  5. `wind_way_service.py: get_way_values`(旧`get_way_wind_penalties`) P3:

  6. `route_scorer.py`(L61) P3: `weight_sum == 0`の厳密浮動小数点比較。
- 対応方針・実装メモ:
  1. `elevation_attribute_service.py: get_attributes_for_graph`: GSI一時障害で全点Noneに
     なったElevationAttribute（`compute_elevation_attribute`が返す、start_elevation_m等
     全フィールドNone）を永続化から除外した。以前はそのまま`save_elevation_attributes`へ
     渡っており、`elevation_attributes`に行が存在する＝キャッシュ済み扱いになるため、
     GSI復旧後も二度と再問い合わせされなかった。永続化しないことで次回呼び出し時に
     missing扱いへ戻り再試行される。回帰テスト2件追加（全滅時は非永続化・再試行される、
     部分欠損は従来どおり永続化される）。
  2. `axis_registry_service.py`のcreate/update/delete/unpublish: 読み取り→Python側検証→
     書き込みのTOCTOUレースを、`AxisDefinitionRepository.acquire_write_lock()`
     （PostgreSQLのトランザクションスコープadvisory lock、pg_advisory_xact_lock）で
     直列化した。asyncio.LockではなくDBレベルのロックにしたのは、このファイル冒頭の
     「将来複数ワーカー化する際は」という既知の制約を踏まえ、複数プロセス構成でも機能する
     ようにするため。実際に別トランザクションをブロックすることを確認する回帰テストを追加
     （advisory lockが機能していることの直接証明）。
  3. `region_service.py`の3箇所（区間インスペクタ・事故データ収録年数・材料値一覧）の
     DB障害WARNINGを`log_throttled_warning`経由へ統一。**追加スコープ（T426棚卸しでは
     未検出）**: `_tile_from_repository`（路面/POIタイル配信の主経路、パン/ズームのたびに
     大量に呼ばれる最も高頻度な箇所）も同じ未抑制のWARNINGだったため、CLAUDE.mdの
     「共有パターン変更時は取り残された消費者をgrepで確認する」原則に基づき同様に修正した。
  4. `graph_service.py: _maybe_warm_tile_cache`: タイル材料キャッシュの温め失敗後、
     即座に無条件で再試行され続ける（対象bboxを含むリクエストのたびにトリガーされる）
     問題に対し、region_service.py: `_last_build_check`/`_GRAPH_CHECK_TTL_SECONDS`と同じ
     設計（試行ごとに一定時間[300秒]は同じタイルへの再試行を抑える）のクールダウンを
     追加した。成功時は次回のキャッシュヒット判定で到達しないため実質は失敗時の再試行
     間隔として働く。回帰テスト3件追加（クールダウン中はスキップ・経過後は再試行・
     失敗時に試行時刻が記録される）。
  5. `wind_way_service.py: get_way_values`が`tile_serving.py: serve_cached_tile`骨格を
     再利用していない件は、調査の結果**対応不要**と判断。`serve_cached_tile`はファイル
     システムの`tile_cache`が保持する静的タイルバイト列（PBF/MVT、`content_type`付き）を
     対象とした骨格だが、`wind_way_service.py`/兄弟サービスの`gradient_way_service.py`
     （同じ統一インターフェースを持つと本タスクの背景欄でも明記されている）はいずれも
     `dynamic_way_value_cache.py`（Redis、`dict[way_id, float]`表現、時刻バケット・
     bearing_deg込みキー）という別のキャッシュ層・別のデータ形状を一貫して使っており、
     `serve_cached_tile`とはそもそも噛み合わない。2つの「タイル」という言葉が指す対象が
     構造的に異なるだけで、重複実装ではなく適切な別レイヤーの使い分けだった。
  6. `route_scorer.py`の`weight_sum == 0`厳密比較も、調査の結果**対応不要**と判断。
     `weight_sum`を構成する`distance_weight`/`difficulty_weight`はいずれも
     `Field(ge=0)`でAPI境界にて非負が保証されており（`api/routers/routes.py:
     ScoringWeights`）、非負の値だけを加算する限り浮動小数点の桁落ち・打ち消し合いは
     原理的に発生しない（全項が正確に0.0のときのみ合計が正確に0.0になる）。厳密比較を
     `math.isclose`等へ変えても挙動は変わらず、変更自体が不要と判断した。
- 検証: `tsc`は対象外（backendのみの変更）。変更した各backendファイルについて`pytest`

  成功（elevation_attribute_service/axis_registry_service/axis_definition_repository/
  region_service/region_routes/graph_service/accident_routes/axis_catalog_routes/
  material_catalog_routes/route_scorer、計180件成功）。
