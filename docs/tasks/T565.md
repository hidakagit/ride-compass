# T565: ルート直下README.mdの陳腐化是正

状態: 完了（2026-09-03）

## 背景

ルート直下`README.md`が初期プロトタイプ段階（Step 1〜10）の実装ログのまま更新されておらず、
`openrouteservice`委譲（改善計画T462で撤去済み）・`scoring.yaml`/`RouteScorer`（改善計画T401・
T548で撤去済み）等、既に存在しないコンポーネントを現役の仕様として説明していた。

## 対応

コードを直接確認して裏取りしたうえで全面書き換えた。

- **Step 1〜10の実装ログ節を撤去**し、現在の機能を「主な機能」として現状形（〜できる、
  〜する）で6項目に要約。詳細・厳密な数値（評価軸の本数等、頻繁に変わる）はハードコード
  せず[docs/architecture.md](../architecture.md)・[docs/modules/README.md](../modules/README.md)
  へ誘導する形にした。
- **既に存在しないものへの言及を削除・訂正**: `openrouteservice`委譲・`scoring.yaml`・
  `RouteScorer`・`wind_score`/`road_score`/`total_score`（いずれもコード上に実体が
  無いことを`grep`で確認済み）。ルーティングエンジンはroad_graph一本である旨に統一。
- **セットアップ手順の実際の動作を検証**:
  - Docker Compose起動: `docker-compose.yml`にはRedisサービスが存在する（改善計画T387で
    追加）のに旧READMEは未記載だったため追記。
  - ローカル個別起動（frontend）: 旧READMEの`cp .env.example .env.local`は
    `frontend/.env.example`というファイル自体が存在せず実行不可能な手順だった
    （`NEXT_PUBLIC_API_URL`は`frontend/src/lib/apiBaseUrl.ts`で未設定時
    `http://localhost:8000`にフォールバックするため、そもそも必須ではない）。手順を
    `npm install && npm run dev`のみへ簡略化した。
  - `curl`のAPI疎通確認例は`backend/app/api/routers/routes.py: RouteGenerateRequest`の
    現行フィールド（`distance_km`/`distance_tolerance_km`/`route_type`）と照合し、
    変更不要と確認した。
  - ルート直下に存在するが旧READMEが一切触れていなかった`restart-dev.bat`/
    `stop-dev.bat`（Windows向けローカル再起動・停止スクリプト）・`scripts/`
    （`review_checks.py`等のリポジトリ横断ツール）を「構成」節へ追記。
- **関連する陳腐化を同一コミットで是正**: ルート直下`.env.example`の
  `ROUTING_ENGINE`/`OPENROUTESERVICE_API_KEY`（`config.py`に対応フィールドが存在しない
  死んだ設定値）を削除し、`docker-compose.yml`の同名変数に触れていた古いコメントも訂正した。

docs/modules/*.mdへの変更は無い（README.md・`.env.example`・`docker-compose.yml`・
`docs/improvement-plan.md`のみ）ため、CLAUDE.md「毎タスク完了時の即時チェック」のうち
docs/modules記載粒度チェック・新規ファイルのdocs/modules追記チェックはいずれも対象外
（新規ソースファイルの追加・既存共有フィールドの変更/廃止も無し）。

## 追記（2026-09-03、ユーザー指摘「一般ユーザ向けに平易な言葉で記載してほしい」）

初版は開発者向けの技術用語（Road Graph・PostGIS・評価軸・overall_difficulty等）のまま
冒頭から書かれており、「何ができるアプリなのか」が伝わりにくいという指摘を受けた。
冒頭に「RideCompassでできること」を新設し、技術用語を使わず利用者目線（「坂道は避けたい」
「車の通りが少ない道を優先したい」等）で6項目に書き直した。既存の「主な機能」節は
「主な機能（開発者向け）」へ改名してそのまま残し、技術的な説明は開発者向け節以降へ
集約する構成にした（一般ユーザー向けの説明と開発者向けの技術説明を混在させない）。
