# T393. 本番Redisにmaxmemoryと退避ポリシーが未設定〔P2〕規模S

状態: 未完了

- 背景: T392（タイル材料一式のRedis複製化）の実測検証中に本番Redisの設定を確認したところ
  （2026-08-29）、`maxmemory=0B`（無制限）・`maxmemory_policy=noeviction`（メモリ上限到達時に
  古いキーを自動追い出さず、新規の書き込み自体を拒否する設定）のままだった。T387導入時から
  この設定は変わっておらず、明示的に決めた設定ではなく単なる既定値放置と見られる。
- 現状の使用量: 実測時点で`used_memory_human=1.76M`とごく小さい（T387のroad_graph_tiles
  マーカー・T390のsplit鮮度マーカー/edge geometryキャッシュ・JMA気象データがいずれもTTL付き
  かつペイロードが小さいため）。VM全体は11GB中、実測時空き約9.7GB。**現時点で実害は無い**。
- リスク（保留し続けた場合の影響範囲）: 本タスクを放置したまま将来Redisの用途を拡張する
  （例: T392着手、または新規のJMAデータ種別追加等でペイロードが大きい/TTLの長いキーが
  増える）と、上限なしにメモリを消費し続け、PostgreSQL・backendアプリと**同居するVM全体の
  メモリを圧迫**しうる。`noeviction`のため、Redis自体のメモリ上限に達すると新規書き込みが
  拒否される（road_graph_tile_cache.py・road_edge_geometry_cache.py等の書き込み関数は
  いずれもtry/exceptでfail-openする設計のためアプリ自体がクラッシュすることは無いが、
  「キャッシュ書き込みが常に失敗しPostGISへ毎回フォールバックする」という性能劣化状態に
  静かに陥る）。より深刻なのは、Redisプロセス自体がシステムメモリを圧迫し**VM全体のOOM
  （PostgreSQL・backendアプリがOOM Killerに巻き込まれる）を誘発するリスク**で、こちらは
  fail-open設計の対象外——本タスクの見落としに気づかないまま用途拡張を重ねると、ある時点で
  突然VM全体の可用性問題として顕在化しうる。
- 対応方針（着手時の設計メモ）: OCI VM上のRedis設定（`/etc/redis/redis.conf`等）へ
  `maxmemory`（VM全体11GBのうち、PostgreSQL・backendアプリの必要分を差し引いた安全な値、
  例えば2〜4GB程度を目安に要検討）と`maxmemory-policy`（現行キーは概ねTTL付きのため
  `volatile-lru`、TTL無しキーが将来増える想定なら`allkeys-lru`）を明示的に設定し、
  `systemctl restart redis-server`で反映する。設定後、`redis-cli config get maxmemory`等で
  反映確認し、docs/architecture.mdのRedis基盤節へ設定値と根拠を追記する。
- トリガー: 緊急性は低いが、T392（タイル材料一式のRedis複製化）に着手する場合は
  ペイロードサイズが跳ね上がるため**本タスクを先に完了させることを前提条件とする**。
  それ以外の一般的なタイミング（次のRedis関連変更のついで等）でも対応してよい。
