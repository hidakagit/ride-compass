# T510: JMA動的タイルの429対策（レート制限順序修正＋Redisキャッシュ＋定期プリウォーム）

状態: 完了（2026-08-31）

## 背景

ユーザー報告「地図を頻繁に動かすと429が出る（`/api/jma-tile/...`）」。調査の結果、
429の直接原因はJMAサーバー側のレート制限ではなく**backend自前のレート制限**
（`enforce_rate_limit`、`jma_tile.py`）で、**キャッシュヒットしていてもこのレート制限が
消費される**構成だった（`enforce_rate_limit`が`jma_tile_client.get(path)`より先に
呼ばれていた）——同じ範囲を往復パンしただけで、実際の外部フェッチが発生していなくても
429にカウントされていた。

ユーザーは「常にRedisに定期導入。Redisからしか見ないのはダメ？」という根本解決の方向性を
希望した。調査の結果、このリポジトリには「Redisは正本を持たないcache-asideの高速化層で
あり、障害時は必ず今までのフェッチ経路へfail-openする」という一貫した設計原則が
`docs/architecture.md`に明文化されていることが分かった（`road_graph_tile_cache.py`が
唯一「Redisを正本にしない」パターンを取る理由も、マーカーを失うとルート生成が自動復旧
不能な形で失敗する、という具体的な障害シナリオに基づく）。文字通り「Redisからしか見ない」
（フォールバック無し）にすると、Redis自体が疎通不能な間・プリウォームが対象外の範囲への
パンで「今なら見えていた地図が何も表示されない」という現状より悪化する退行を生むため、
この原則に合わせ「Redis優先で読み、無ければ即座に今と同じオンデマンドフェッチへ
フォールバックする」設計を採用した。

**もともとキャッシュ専念（プリウォームなし）だった理由**: `docs/tasks/T412.md`（この
プロキシ自体を新設したタスク）を確認したところ、「プリウォームを検討した上で意図的に
見送った」という記録は無い。T412が解決していた課題は「各ユーザーのブラウザが直接JMAへ
fetchしていたため利用者数に比例して負荷が線形に増える」ことで、backend経由のオンデマンド
fetch+キャッシュだけでその課題は解決できた。「1人のユーザーが未取得のタイルへ連続パンする
とレート制限にすぐ達する」という今回の問題は当時想定されておらず、単に「その時点の課題に
対しては最小の実装で足りていた」というだけだった。

## 対応方針（3点セット）

### Part 1: キャッシュヒットをレート制限のカウント対象外にする（根本原因への直接対応）

`JmaTileClient`を`get_cached`（キャッシュのみ参照）・`fetch`（外部フェッチのみ、キャッシュ
書き戻し込み）・`get`（`get_cached`→ミスなら`fetch`の一括呼び出し）の3メソッドへ分割した。
`jma_tile.py`は`get_cached`でヒットすれば`enforce_rate_limit`を一切経由せず即座に返し、
ミスのときだけ`enforce_rate_limit`→`fetch`を呼ぶ。

### Part 2: タイル本体のキャッシュ先をファイル（tile_cache.py）からRedisへ移す

新規`backend/app/infrastructure/jma_tile_redis_cache.py`を`wind_forecast_cache.py`と同じ形
（get/set関数、fail-open、`record_redis_failure`/`record_redis_success`、例外を外へ
伝播させない）で作成。キーは`tile_cache.py`の`cache_key(path)`（元`_cache_key`、Redis
キャッシュからも参照できるよう公開関数へ改名）と同じsha256方式を踏襲し`jma:tile:{hash}`。
値は`redis_client.py`が`decode_responses=True`のため、`{"content_type":...,
"body_b64":base64エンコード済み文字列}`をJSON文字列化して保存する。TTLはプリウォーム
間隔（10分）より余裕を持たせ20分。targetTimes.jsonのキャッシュ（プロセス内`TTLCache`、
2分TTL）は変更していない。

### Part 3: 定期プリウォームバッチ

`main.py`の既存`_refresh_amedas_job`パターン（`AsyncIOScheduler`、`trigger="interval"`、
`next_run_time=datetime.now()`で起動直後にも即時実行）をそのまま踏襲し、新規
`backend/app/services/jma_tile_prewarm_service.py`を10分間隔（`settings.
jma_tile_prewarm_interval_minutes`）で実行する。

- 地理範囲は`domain/wind_grid.py: WIND_GRID_BBOX`（関東本土、アプリの実運用範囲）。
- ズーム範囲は各レイヤー自身の`maxzoom`（超過ズームはMapLibreがクライアント側で拡大表示
  するだけで追加通信が発生しないため、レイヤー自身のmaxzoomが実質的な上限になる）。
- タイル列挙は`domain/region.py: tiles_covering_bbox(bbox, z)`（既存関数、そのまま再利用）。
- キキクル3種・線状降水帯予測マップは未来フレームを持たず「現在」の1エントリのみ、
  雷/竜巻ナウキャストは複数の予報フレームを持つが直近の実況フレームのみプリウォーム対象
  にする（フレーム数が多いレイヤーの全量プリウォームは省コストの原則に反するため）。
- プリウォーム本体は`JmaTileClient.get()`を呼ぶだけ（Redis書き込みはget()内部の副作用、
  プリウォーム専用の別書き込み経路は持たない）。

### floodレイヤーの`maxzoom`を14→11へ変更（ユーザー了承済みのトレードオフ）

検討過程で、洪水キキクル（flood、ベクタタイル）だけ`maxzoom:14`（他は10〜11）だったため
プリウォーム対象から除外する案を提示したところ、ユーザーから「そもそも洪水以外はz12以降
拡大しても表示されない？ならば他も全てそういう整理にするのはありでは」という指摘を受けた。
確認したところ、他6レイヤーは自前のmaxzoomがそのまま「これ以上ズームしても追加の通信が
発生しない」上限になっている一方、flood単独だけJMA配信元（`properties.xml`）の宣言する
zoom範囲をそのまま踏襲しており、RideCompass側の意図的な画質判断ではなかった。ベクタ
タイルのためmaxzoomを下げてもラスタのような拡大時のボケは生じない（既存の簡略化された
ジオメトリを拡大表示するだけ）。ユーザー了承（「常時オンの情報なので、ある程度割り切りは
必要かもしれない」）を得て、`frontend/src/components/Map/MapView.tsx`の
`floodRisk.main.vector.maxzoom`を14→11へ変更し、全7レイヤーを一律プリウォーム対象に
揃えた（非対称な除外扱いが不要になった）。

## タイル数・Redis想定消費メモリの試算

`WIND_GRID_BBOX`・各レイヤーのmaxzoomから計算（プロセスはPlan中に`python`で実測）:

| レイヤー | ズーム範囲 | タイル数 |
|---|---|---|
| キキクル・土砂/大雨/浸水/洪水（各） | z4-11 | 399×4 |
| 線状降水帯予測マップ | z4-10 | 129 |
| 雷/竜巻ナウキャスト（各） | z4-10 | 129×2 |
| **合計（1スナップショットあたり）** | | **1,983タイル** |

Redis想定消費メモリ（タイル平均8KB〜30KBで試算、base64化の約1.33倍込み）: 定常状態
（TTL20分・間隔10分で新旧2世代同居）で約41MB〜155MB。本番Redisの`maxmemory 2GB`に対し
悲観ケースでも1割弱で、既存用途（アメダス・風予報・road_graph_tilesマーカー）を圧迫する
規模ではないと判断した。実際のタイルサイズは未計測のため、将来Redisのメモリ使用量を
実測して確認することが望ましい。

## 検証結果

- `pytest -m "not postgis"`: 1212件成功（既知の無関係な既存失敗1件
  [`test_wind_way_service.py::test_at_none_defaults_to_now_without_raising`、別セッションの
  既存コミットが原因、T510の変更とは無関係、別タスクとして起票済み]を除く）。
- frontend: `tsc --noEmit`・`eslint src/`・`vitest run`（897件）すべて成功。
- Browserペイン実機確認（`localhost:3010`）: land/rain_mesh/inundのキキクルタイルが
  `/api/jma-tile/...`経由で正常にfetch（200）されることを確認し、Part1+2（レート制限
  順序修正＋Redisキャッシュ）がend-to-endで機能していることを確認した。floodレイヤー
  自体は今回のBrowserペインのセッションでタイルリクエストが一度も発生せず、
  `maxzoom`変更の見た目上の効果（z12以降での拡大表示）を直接確認できなかった——
  targetTimes.jsonには`flood`要素が存在することを確認済みで、原因はflood特有の
  レンダリングパイプライン（`useDynamicWeatherLayers.ts`/`MapView.tsx`のvectorTile分岐）
  側にある可能性が高く、T510の変更（maxzoomの数値自体は`map.addSource`呼び出しへ
  正しく渡っていることをコード読解で確認済み）とは別の問題と判断し、別タスクとして
  起票した。
- プリウォームバッチ自体の実機動作（Redis書き込み件数・所要時間の実測）は今回未実施
  （ローカルdev環境でのRedis起動状況に依存するため）。本番デプロイ後、ログ
  （`jma tile prewarm 完了 tiles=... fetched=... errors=... total_bytes=...`）で
  実測することが望ましい。
