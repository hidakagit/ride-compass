# T538: タイル材料キャッシュの冷パス（デプロイごとに29秒）を永続化または起動時予熱で解消する

状態: 未着手（2026-09-02起票、[T522](T522.md)「評価ロジック全体の再点検」で判明）

- 背景: `graph_material_cache`（z12タイル単位のトポロジ＋材料）はプロセス内メモリのみで、
  `deploy-backend.yml`がデプロイのたびにコンテナを再起動するため、その後の最初の
  利用者が毎回DB読み出し（本番VM実測29.3秒、東京駅30km・16タイル）を負担する。冷パスの
  主因はDB問い合わせと行の走査で、Pydantic構築は10万行で0.4秒に過ぎず削れない
  （T522.md）。T536の静的スコア行列も同じくプロセス寿命のため同じ問題を持つ。
- 対応方針（候補、着手時に選ぶ）:
  - タイル単位の材料（`SearchMaterials`、T536後はスコア行列も）をディスク
    （`backend/data`配下、`tile_cache.py`のDEMタイルと同じ考え方）またはRedisへ
    直列化して永続化し、起動後の初回アクセスでDBではなくそこから読む。無効化は
    PBF再取込・precomputeバッチ実行時にファイル世代を上げる（MVTのタイル世代定数と
    同じ流儀）。
  - 起動時に主要エリア（直近のリクエストで使われたタイル集合を記録しておく、または
    設定で列挙）を`jma_tile_prewarm_service`と同じ方式でバックグラウンド予熱する。
    全域（関東7都県）の常駐は本番のメモリ上限（6GB）に対して非現実的なため、対象は
    絞る。
- 関連: [T536](T536.md)・[T537](T537.md)（永続化対象が増える）、
  [T523](T523.md)（フロントのポーリングタイムアウトは冷パスで到達しやすい）。
- 完了条件: デプロイ直後の最初のリクエスト（東京駅30km）で`materials_ms`が5秒未満、
  再取込・precompute後に古いキャッシュが使われないことのテスト、`docs/modules/`の
  該当設計書を同一コミットで更新。

## T536本番反映時に再確認した冷パス実測（2026-09-02）

T536（探索コストの静的行列化）を本番へ反映する過程で、同一条件（東京駅30km、split済み）の
冷パスを2回実測する機会があり、いずれも本節の課題がそのまま現役であることを確認した。

- 使い捨てコンテナでの初回リクエスト（デプロイ直後相当）: `materials_ms=39229ms`
  （`_build_search_graph`ログ、edges=477,320・nodes=181,224）
- 実際のデプロイ直後、稼働中コンテナへの初回リクエスト: `prepare_ms=45545ms`
  （`trace_ms=795ms`・`evaluate_ms=102ms`はいずれも高速——T536の効果は冷パスでも
  探索部分には及ぶが、`prepare`の大半を占める材料取得自体は無傷）

いずれもT522記録時点の29.3秒より長い（39〜45秒）。T536でEdgeごとのPython処理を
排除したことで探索・コスト計算は速くなったが、`GraphService._get_or_build_tile_materials`
のDB読み出し自体には手を入れていないため、この節の課題（冷パス）は影響を受けていない
——本節の背景で予告していた「T536の静的スコア行列も同じくプロセス寿命のため同じ問題を
持つ」がそのまま該当する形。数値の増加（29.3秒→39〜45秒）はDB側の負荷状況等による
ばらつきの範囲内と考えられ、T536自体が冷パスを悪化させたという明確な根拠は無い
（materials取得のロジック自体はT536で変更していない）。

デプロイのたびに（T537・T540はもちろん、今後の全backend変更で）この冷パスが再発する
ため、優先度を上げる材料としてここに記録する。着手順序の判断はユーザー確認事項として
残す。
