## 訂正後の契約（材料非依存、T400.md節2から転記）

「道路自身に紐づかない外部条件が関与する材料」は全て以下の状態機械に従う。**「必要パラメータ」
だけが材料ごとに違い、それ以外（状態機械そのもの）は共通**:

| 状態 | パラメータの出所 | 塗る対象 |
|---|---|---|
| ルート未確定 | ユーザーがその材料の必要パラメータを指定した値 | 視界内の**全道路**へ一律適用（他の評価軸[car_stress等]と同じ「全道路を色分け」という描画パターンに揃える） |
| ルート確定後 | ルート自身の各地点の実到達時刻（・実進行方向、その材料が向きに依存する場合のみ） | **ルート線のみ**。ルート以外の道路は無色に戻す |

風の必要パラメータ＝時刻＋向き（`WindCalculator.wind_penalty(wind_speed_ms, wind_direction_deg,
travel_bearing_deg)`、[wind.py](../../backend/app/domain/wind.py)）。雨の必要パラメータ＝
時刻のみ（向きに依存しない）。

- **環境グループ（面）と評価軸グループ（線）は、ルート未確定時は同じ1つのパラメータ入力を
  共有する**——2つの独立した表現ではなく、1つのユーザー操作（パラメータ指定UI）が面塗り
  （`gridFill`）と線塗り（各道路への評価計算適用）の両方を駆動する。表示のON/OFF自体は
  別チップのまま（環境=area、評価軸=lineと排他ドメインが異なるため、両方同時にONにもできる）。
- **ルート確定後**: パラメータ指定UIは消え、評価軸チップと既存`routeStyleModes`の対応モードを
  1つに統合する（二重に存在させない）。着色対象はルート線のみに絞る（ルート未確定時のように
  視界内の全道路を塗り続けるわけではない）。

## 本タスクで実装する具体例: 風

風は「時刻＋向き」の2パラメータが必要な材料として、上記契約の最初の実装対象にする。
UI・バックエンドとも、後続材料（雨等）が同じ契約へ素直に乗れるよう「風固有の分岐」を
最小限にとどめること（例: パラメータの集合を材料ごとの宣言として持たせる、時刻のみで
済む材料では向き入力UIを出さない、等）。

### T405実装のうち作り直しが必要な部分

- **`get_way_bearings_in_tile`（`road_graph_repository.py`）は不要になる可能性が高い**:
  訂正後の契約では、ある道路の風penaltyは「その道路の最寄り風グリッド点の値」と「ユーザーが
  指定した単一の向き（全道路共通）」から決まり、道路自身の向きは計算に関与しない。着手時に
  本当に不要か確認すること。
- **Redisキャッシュのキー設計（`wind_way_penalty_cache.py`）の再検討が必要**: 旧設計は
  `way_id + 時刻バケット`をキーにしていた（道路自身の向きは固定値のため、時刻だけが変数
  だった）。訂正後は向きもユーザー指定の変数になるため、`way_id + 時刻 + 向き`の3次元キー
  空間になる。ユーザーごとに向きが異なりうる以上キャッシュヒット率が下がる可能性があり、
  「way単位でRedisへキャッシュする」という設計自体が今も最適か（例: タイル単位・時刻バケット・
  向きバケットでまとめて計算しキャッシュする方が効率的では）を着手時に再検討すること。
- **エンドポイント（`/api/region/dynamic-way-values/wind/{z}/{x}/{y}`）にクエリパラメータの
  追加が必要**: 現状は時刻（`at`）のみ受け付ける。向き（`bearing_deg`等）も受け取れるように
  拡張する必要がある。パス自体に`wind`を直書きしている点も、雨等の後続材料を見据えるなら
  `{material_id}`化を検討する余地がある（[T411](T411.md)のスコープと重なる、着手時にT411も
  合わせて読むこと）。
- 新規: 時刻＋向きの連続回転スライダー（コンパス型UI部品、新規実装が必要——時刻スライダーと
  同じ横スクロールルーラーの流用は円環データのため技術的に困難）。時刻のみで済む材料
  （雨等）が将来この契約に乗るときは向き入力を出さない設計にすること。
- 新規: 環境グループの`gridFill`面表示（[wind.py](../../backend/app/domain/wind.py)の
  `wind_penalty`を格子点ごとに適用、降水延長予報と同じ既存レンダラーを流用）。
- 新規: ルート確定後、パラメータ指定UIを消し評価軸チップと`routeStyleModes`の「風」
  モードを統合する導線。
- 新規: ルート確定後、視界内の全道路の色を消し（`removeFeatureState`等）ルート線のみへ
  絞り込む処理。

## 未検討事項

- 環境（面）・評価軸（線）を両方同時にONにしたときの視認性（線を面の上に重ねて見づらくないか）
  は実機確認が必要。
- 契約自体は雨にもそのまま適用できるはずだが、**雨を実際に評価軸グループの材料として
  実装するタスクは本タスクのスコープ外**（現状、雨/降水は「環境」グループの生データ
  [`precipitationNowcast`]としてのみ存在し、軸スタジオの材料にもなっていない。実装する
  場合は別タスクとして起票すること）。
- バックエンド配信機構（Redis way_id→値配信等）を材料間でどこまでコード共有するかは
  [T411](T411.md)のスコープのまま——本タスクは契約（設計）の材料非依存化はするが、
  実装（コード）の汎用化はT411の判断（2例目が実際に増えたら共通部分を抽出）を変更しない。

## 実装内容（2026-08-30完了）

着手前に`get_way_bearings_in_tile`が本当に不要か再確認した結果、**T414.md起票時点の想定どおり
不要と確定**した——訂正後の契約では走行方位はユーザー指定の単一値（全道路共通）になるため、
道路自身の向き（ST_Azimuth）を計算する理由が無くなった。

### backend

- `backend/app/infrastructure/road_graph_repository.py`: `get_way_bearings_in_tile`
  （`_WAY_BEARINGS_IN_TILE_SQL`、ST_Azimuth・geographyキャスト・LATERAL結合込みの複雑な
  クエリ）を撤去し、`get_way_ids_in_tile`（`_WAY_IDS_IN_TILE_SQL`、タイル内のway_id一覧を
  返すだけの単純なクエリ）へ置き換えた。`RoadGraphRepository`ファサードの委譲メソッドも
  同様に置き換え。
- `backend/app/infrastructure/wind_way_penalty_cache.py`: **キー設計を作り直した**
  （起票時の懸案どおり再検討が必要だった）。訂正後の契約では「同じタイル内の全wayは
  常に同じwind_penalty値を持つ」（風グリッドをタイル中心1点で代表させる既存の近似＋
  走行方位が全道路共通のため）。そのため、旧`way_id + 時刻バケット`キー（way_idの数だけ
  キーが増える）を`(z, x, y, 時刻バケット, 向きバケット) → スカラー値1個`という
  はるかに小さいキー空間へ縮小した。向きは連続値（コンパススライダー）のためそのまま
  キーへ使うとキャッシュヒット率がほぼ0になる問題があり、5度刻みのバケット
  （`BEARING_BUCKET_DEG`、`bearing_bucket()`）で丸めることで解決した
  （wind_penalty=speed×cos(角度差)は5度程度の丸め誤差では体感できるほど変化しない）。
- `backend/app/services/wind_way_service.py`: `get_way_wind_penalties`が`bearing_deg`
  引数を受け取るよう変更。タイル内のway_id一覧を取得→タイル単位のキャッシュ確認→
  ミス時は風グリッド（タイル中心の最寄り格子点）とbearing_degから`WindCalculator.
  wind_penalty`を1回だけ計算→その値をway_id一覧全件へ均等に割り当てる、という設計に
  変わった（way_idごとの個別計算・個別キャッシュが不要になった）。
- `backend/app/api/routers/region.py`: `GET /api/region/dynamic-way-values/wind/{z}/{x}/{y}`
  に必須クエリパラメータ`bearing_deg`（0〜360度）を追加。パスの`{material_id}`化（T411の
  検討事項）は本タスクでは行わない——T411は「2例目（勾配等）が実際に増えたら共通部分を
  抽出する」という判断のままで、風1例のみの現時点でエンドポイントパスを一般化する
  積極的な理由が無いため、意図的に見送った。
- OpenAPI生成物（`frontend/src/types/generated/`）を`export_openapi.py`→
  `npm run generate:api`で再生成、diffはbearing_deg追加のみでクリーン。

### frontend

- `frontend/src/components/Map/windPenalty.ts`（新設）: backend `WindCalculator.
  wind_penalty`のJS移植（`windPenalty()`）と、環境グループのgridFill用
  FeatureCollection組み立て（`windPenaltyGridToCellFeatureCollection`、
  `precipitationNowcast.ts`の`precipitationGridToCellFeatureCollection`と同型）、
  fill-color式（`windPenaltyFillColorExpression`、評価軸グループ`windAxisLayer.ts`と
  同じ`WIND_AXIS_THRESHOLDS`を共有し配色を統一）を持つ。環境グループのgridFillは
  **追加のAPI呼び出しをしない**——風の矢印（windVector）が既にブラウザへ取得済みの
  風グリッド（`useWeatherGrid`のeffectiveGrid）から、コンパススライダーの値を使って
  クライアント側だけで計算できるため。
- `frontend/src/components/WindBearingSlider/`（新設）: 時刻＋向きのうち「向き」を
  指定するコンパス型UI部品。T400.md「未決定だった論点の決着」節の事前調査どおり、
  自前SVG実装ではなく`@fseehawer/react-circular-slider`（TypeScript完全対応・
  依存ライブラリ無し・MIT、v3.3.5、npm installで導入）を採用した。`value`/`onChange`の
  制御コンポーネントとして使え、`knobPosition="top"`で0度=真上（北）に固定できるため
  コンパスの見た目と素直に一致する。時刻は既存の共有タイムライン
  （`DynamicLayerTimeSlider`）をそのまま流用し、向きだけこの新規コンポーネントが担う
  （「時刻＋向きの連続回転スライダー」という起票時の表現は、実装してみると「時刻は
  既存ルーラーのまま、向きだけ新規の円環UI」という形に落ち着いた——時刻を無理に円環化
  する意味は無く、円環データである向きだけが新規実装を要した）。
  touch-action: noneをラッパーへ指定し地図のパン・ズームジェスチャーとの競合を避ける
  対策はしたが、**実機（実デバイスのタッチ操作）での最終確認は未実施**（開発機のみで
  作業、実機確認可能な環境がある場合は改めて確認すること、T400.mdが要検証事項として
  明記していた点）。
- `frontend/src/hooks/useDynamicWeatherLayers.ts`: `windBearingDeg`を新規オプションに
  追加し、`windPenaltyPayload`（環境グループのgridFill、GeoJSON）と
  `dynamicLayerTargetTime`（windAxis側と共有する時刻そのもの）を新たに返すよう拡張。
- `frontend/src/components/Map/MapView.tsx`: 環境グループの風penalty gridFillは
  **`DYNAMIC_WEATHER_RENDERERS`汎用機構に乗せず**、windAxisと同型の bespoke な
  ensure/apply関数（`ensureWindPenaltyFillLayer`/`applyWindPenaltyFillGeojson`）で
  実装した——汎用機構は「1つの`DynamicWeatherLayerId`につき`payload`は単一の`kind`
  （raster/gridFill/gridMarkのいずれか1つ）」という前提（`applyDynamicWeatherState`の
  可視性判定が`payload?.kind === X`のため）で、windVectorの矢印（gridMark）と
  penalty面塗り（gridFill）を**同時に**表示したいT414の要件とは噛み合わなかった
  （precipitationNowcastのraster/gridFillは「時間帯によってどちらか一方だけ」という
  排他関係のため、この前提の上に成立している）。
  また、`showWindAxis`がfalseへ切り替わる瞬間（ルート確定・手動OFFいずれも含む）に
  `map.removeFeatureState`で全道路ぶんのfeature-stateを明示的にクリアする
  `clearWindAxisFeatureState`を新設した——旧`applyWindAxisPenalties`は（パン・ズームで
  一部way_idが新しい応答へ含まれなくなる通常時向けに）意図的に古い値を残す設計だが、
  T414の契約は「ルート確定後はルート以外の道路を無色に戻す」ことを明示的に要求している
  ため、この2つは別の関心事として分離した。
- `frontend/src/app/page.tsx`:
  - `windBearingDeg`状態（既定0度=北）を新設し、環境（gridFill）・評価軸（windAxis）
    両方のフェッチ・計算へ同じ値を渡す。
  - `showWindAxis = layerVisibility.windAxis && !hasDetail`・
    `showWindPenaltyFill = showWindVector && !hasDetail`——**ルート確定時は無条件で
    無効化する**。
  - windAxisチップは、ルート確定中（`hasDetail`）は`disabled: true`にし、
    タイトルを「ルート確定後は『生成したルートの色分け』の『風』で確認できます」へ
    差し替える。**「評価軸チップとroute StyleModesの『風』モードを1つに統合する」は、
    文字どおりの1クリック導線の統合ではなく、「片方（windAxisチップ）を無効化し、
    もう片方（既存のroute StyleModes「wind」モード、`routeStyleModesFromCatalogAxes`が
    axis-catalogの`supports_route_coloring`から既に自動生成していた既存機構）へ
    案内する」という形で実装した**（設計上の判断、下記「調査で判明した既存実装」参照）。
  - コンパススライダー（`WindBearingSlider`）は`(showWindVector || layerVisibility.
    windAxis) && !hasDetail`のときだけマウントする（`DynamicLayerTimeSlider`の隣）。

### 調査で判明した既存実装（T414起票時には気づいていなかった点）

`docs/tasks/T400.md`「3. ルートクリック内訳の拡張」「5. 候補順位付け」節の実装
（T352等）により、**ルート確定後の風の色分けは既に`routeStyleModesFromCatalogAxes`
経由で正しく実装済みだった**——axis-catalogの`wind`軸が`supports_route_coloring: true`を
持ち、`RouteSegmentDetail.axis_difficulties.wind`（ルート生成時点で区間ごとの実進行方向・
実到達時刻を使って計算済み）を色分けに使う`routeStyleModes`の"wind"モードが、
「ルート設定/結果パネル」の「生成したルートの色分け」セクションに既に存在していた。
これはT414契約の「ルート確定後: ルート自身の実値・ルート線のみへ着色」を**既に満たして
いる**——今回追加実装したのはルート未確定側（windAxisチップの作り直し・コンパス
スライダー・環境gridFill）と、ルート確定時に旧windAxisチップの一律色分けを終了させる
処理のみで、ルート確定側の計算ロジック自体に変更は無い。
