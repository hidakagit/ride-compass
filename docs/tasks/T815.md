# T815. 目的地の補正で生成直後にdirty印が点灯するのを直す

規模S。
状態: 完了（2026-09-14。統合レビュー第8回のP1、2026-09-13起票）

## 背景

backendが目的地を補正して返したとき（`corrected_destination`）、`app/page.tsx:1592-1605`は
比較キーの`destination`だけを補正後へ差し替えているが、**同じキーに入る`distance_km`は
補正前の目的地から算出した値のまま**残る。

`handleGenerate`が`setDestination(corrected)`するため、次のレンダーで
`buildCurrentGenerationInput`は補正後の座標で`Math.ceil(haversine)+1`を再計算する。結果、
利用者が何も触っていないのに`conditionsDirty`が真になり、ヘッダーの`dirtyDot`
（モバイルはタブのドット）が点灯する。

1594行のコメントは「conditionsDirtyが直後に誤ってtrueにならないように揃える」と書いているが、
揃っているのは`destination`だけ。

`page.test.tsx:846`のフィクスチャがまさにこの条件（起点35.7597/139.7387、指定35.681/139.767
≈9.1km→`distance_km=11`、補正後35.70/139.70≈7.5km→`distance_km=9`）で、**この不具合を
踏んでいながら緑のまま通る**——`conditionsDirty`を検証するテストがリポジトリ全体で0件のため。

実害は、dirty印が常時点灯することで**本当に条件を変えたときの合図が意味を失う**こと。
[T758](T758.md)がこの印を設計した目的（設定を変えている場所から再生成の必要が見える）が
損なわれる。

## 対応方針と結果

`buildCurrentGenerationInput`へ目的地の差し替え引数を足し、補正後は**同じ組み立てを通して
入力を作り直す**。フィールドを個別に差し替える形をやめたので、そのフィールドから導かれる値
（`distance_km`）が取り残される、という取りこぼし自体が起きない。

テストを2本足した——「目的地が補正されても、生成直後は条件変更の印が点かない」
「生成後に条件を変えると、条件変更の印が点く」。`conditionsDirty`を検証するテストは
リポジトリ全体で0件だった。

## 検証結果

- 効いていることの確認: 実装をわざと旧形（`destination`だけ差し替え）へ戻すと、
  「目的地が補正されても、生成直後は条件変更の印が点かない」が
  `expected document not to contain element, found <p ...>`で落ちる。戻して再度通ることを確認。
- `npx vitest run` → 142ファイル 1343 passed、`tsc --noEmit`は既存の`LayoutProps`のみ、
  `eslint` 0件。
- 距離はスライダー（`type="range"`）のため、条件変更は`fireEvent.change`で動かしている
  （`user.clear`は編集可能な要素にしか使えない）。
