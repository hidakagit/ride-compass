# T531: フロンティア基準の周回ルート生成（往路探索→折り返し点決定→復路コスト書き換え）

状態: 未着手（2026-09-01起票。T529実装中にユーザー提案、意図的にT529とは分離。
T529完了後の着手を想定）

- 背景: 現行の周回ルート生成（`route_generator.py`・`road_graph_engine.py`）は、
  起点を中心に8方位を固定し、各方位ごとに幾何学的に計算した2つの経由地点（三角形）を
  Dijkstra/A\*で結ぶ設計。この方式は指定距離との乖離が生じうる（幾何学的な経由地点が
  実際の道路網上でどれだけの距離になるかは探索してみないと分からないため）。
- ユーザー提案（2026-09-01、T529実装中）: Dijkstra法が「コストが等しい同心円状」に
  外側へ広がる性質（フロンティア）を利用した別方式:
  1. 起点からDijkstraを開始し、指定距離（例: 片道20km相当）に達したノード群
     （フロンティア）をピックアップする
  2. フロンティア上のノードから折り返し地点を1つ決定する（景観・自転車道の有無・
     ランダム等の基準）
  3. 折り返し地点から起点へ戻る経路をもう一度探索する。このとき往路で通った道
     （およびその周辺）のコストを一時的に数倍へ跳ね上げる
  4. 復路は「往路と違う、まだ通っていない道」を自然に選び、1本の周回（輪っか）が
     できあがる
- **T529とは意図的に分離**（両者とも合意済み）: T529は「同じアルゴリズム・同じ出力を
  保ったまま高速化する」ことを新旧エンジン一致テストで検証する設計にしている。ここへ
  ルートの形（アルゴリズム）自体を変える変更を混ぜると、この検証が成立しなくなる。
- **T529との相性**（着手時期をT529完了後にする理由）: 現行のscipy一括評価（bbox全体の
  コストを事前に固定した行列にする）方式では、「往路で通った道のコストを一時的に
  書き換えて復路を再探索する」ためにbbox全体のコスト計算をやり直す必要があり高コスト。
  T529のlazy評価（`edge_cost_fn`がEdgeごとに都度呼ばれる設計、`docs/tasks/T529.md`参照）
  なら、cost_fnクロージャ内で「このEdgeは往路で使用済みか」を判定してコストを
  割り増すだけで実現できる——T529の基盤があって初めて現実的な実装コストで成立する。
- 検討が必要な点（未着手のため未確定）:
  1. 「指定距離に達したノード群（フロンティア）」の具体的な取得方法
     （`rustworkx.dijkstra_shortest_path_lengths`で全ノードへの距離を計算し、
     目標距離±許容範囲のノードを抽出する等）
  2. 折り返し地点の選定基準（ユーザー提案は「景色が良い場所・自転車道がある場所・
     ランダム」の3案、どれを採用するか、あるいは複数候補を生成してスコアリングで
     選ぶか）
  3. 「往路で通った道の周辺」の定義（往路のEdgeそのものだけか、一定距離以内の
     並行道路も含めるか）とコスト割り増しの倍率
  4. 既存の8方位固定方式との共存/置き換え方針（後方互換性・段階移行の要否）
  5. 現行の「逆回り候補評価」（改善計画T274、`_reverse_traced_edges`）との関係整理
     （フロンティア方式は元々「往路と違う復路」を狙うため、逆回り合成ロジックの
     位置づけが変わる可能性がある）
  6. **生成するルート候補数を指定可能にする**（2026-09-01、ユーザー追加提案）。
     現行は「8方位固定」が候補数の上限を実質的に決めているが、フロンティア方式は
     「フロンティア上から折り返し地点をN個選ぶ」という形に一般化しやすく、
     8方位という固定概念自体を置き換えられる可能性がある。リクエストパラメータ
     （`RouteGenerateRequest`）に候補数を追加するか、既定値のみ変更可能にするか等、
     API設計も含めて検討する。
