# T531: 公開軸重み駆動のフロンティア方式による周回ルート生成（候補数max_routes指定可能化）

状態: 完了（2026-09-03着手・同日完了。本番同等環境での実測・実機確認・全テストgreenまで
実施。2026-09-01起票、T529実装中のユーザー提案。同日に設計を推敲し確定。
前提としていたT529[lazy評価]は[T536](T536.md)[静的スコア行列＋リクエスト時ベクトル計算]
で発展的に解消済みで、コスト配列は任意の探索から参照できるため前提条件は満たされている）

## 背景

現行の周回ルート生成（`route_generator.py`・`road_graph_engine.py`）は、起点を中心に北から
時計回り8方位を固定し、各方位ごとに幾何学的（`destination_point`によるユークリッド円）に
決め打ちした2つの経由地点を結ぶ設計。「候補生成が幾何学的、選別だけがスコア駆動」という
構造のため、公開軸の重みを極端に振っても候補の形は変わらない。

起票時のユーザー提案（2026-09-01）: Dijkstra法が「コストが等しい同心円状」に外側へ広がる
性質（フロンティア）を利用し、①起点からDijkstraで指定距離に達したノード群を拾う→②折返し
地点を決める→③往路で通った道のコストを一時的に跳ね上げて復路を探索する→④往路と違う道を
通る1本の周回ができる、という方式。T529（同じ出力を保った高速化）とは意図的に分離した。

ユーザー要望（2026-09-01〜03）で確定した事項:

- 「8方角作成を変えたい。公開軸の比率で最適なルートで距離が近いものを上位n件表示したい」
  「自転車インフラ100%であれば、ほぼサイクリングロードしか選ばれないようなイメージ」
- 候補生成自体を軸重み駆動へ転換する（8方位を密にするだけの案は却下）
- 上位n件の「n」はユーザーが指定できるようにする
- 距離の近さは今まで通り厳格フィルタ（±distance_tolerance_km）を維持し、スコアと混ぜない
- 推敲の結果、実現案や実装が元案から変わることは問題ない（2026-09-03、ユーザー明言）

## 設計判断（起票時の「検討が必要な点」1〜6の解決）

1. **フロンティア取得**: 起点からの一対全Dijkstra（軸重み付きコスト）を
   `scipy.sparse.csgraph.dijkstra`（`return_predecessors=True`、`limit`指定）で1回。
   rustworkxの`dijkstra_shortest_path_lengths`は前任者木を返さず、Edgeごとに
   `list.__getitem__`コールバックへ戻るため採用しない（開発機の合成グリッド
   [14万ノード・56万Edge]で982ms対137〜258ms）。
2. **折返し点の選定基準**: 「景色・ランダム」ではなく**往路の距離加重平均difficulty**
   `(cost/len_c − 1)/penalty_strength`の昇順（コスト式`cost = dist×(1+P×difficulty/100)`の
   逆算。最終ソートに使う`overall_difficulty`と同じ物差し）。`len_c`は前任者木に沿った
   往路の**実距離**（下記）。
3. **「往路で通った道」の定義**: 往路Edgeそのもの＋同一Node対の逆方向Edge
   （`lazy_graph.edge_index_by_node_pair[(to, from)]`）のみ。周辺並行道路は含めない。
   倍率は有限（`RETRACE_PENALTY_MULTIPLIER = 8.0`、実測調整前提）、infにはしない。
4. **8方位固定との共存/置き換え**: 完全置き換え（`DIRECTIONS_DEG`・`_loop_waypoints`・
   `RADIUS_RATIO`を`generate_loops`から撤去。`generate_via_waypoints`は無変更）。
5. **T274逆回り合成との関係**: **削除しない**。周回の逆走は生成方法に依存せず常に物理的に
   意味があり（勾配・風で評点が変わる、T274の発端）、`_build_best_candidate`は任意の
   Edge列ループに対して追加I/Oゼロで動く。docstringの「方位ごと」の文言だけ直す。
6. **候補数の指定**: `RouteGenerateRequest.max_routes: int = Field(ge=1, le=15, default=8)`を
   新設し`GenerationConditions.max_routes`へエコー。フロントに件数入力欄を追加。

## アルゴリズム（`generate_loops`のみ対象、`generate_via_waypoints`は無変更）

1. `prepare()`: 従来どおりbbox・`LazyRoadGraph`・軸重み付き`cost_list`を構築する。半径
   ヒューリスティックは`RADIUS_RATIO = 1/3`→`TURNAROUND_RADIUS_RATIO`（初期値0.4、
   実測で調整）。0.5にするとbbox面積が現行比2.25倍になりprepare・メモリ・タイルキャッシュ
   ヒット率に効くため、実道路の迂回率（概ね1.3）を踏まえ0.4から始める。半径不足時は
   Dijkstraがbboxで自然に切れリングが欠けるだけで壊れない。
2. **CSR構造のキャッシュ**（新規、`infrastructure/search_graph_cache.py`）: `lazy_graph`と
   同じタイル集合キーで、CSRの`indptr`/`indices`と「CSR data順→lazy Edge index」の順列を
   キャッシュする。リクエストごとには`cost_array[perm]`でdata配列だけ差し替える
   （構造構築は初回のみ約155ms）。旧`SparseRoadGraph`/`build_sparse_graph`/
   `shortest_path_node_ids_sparse`/`routable_node_ids`（productionから未参照）はこの
   新構造で置き換えて撤去する。
3. **一対全木**（新規、`domain/routing.py`）: `dijkstra(csr, indices=origin,
   return_predecessors=True, limit=(1+P)×ring上限)`で`cost`と`pred`を得る。前任者木に沿った
   実距離`len_c`は、`(pred[v], v)`のCSR位置を`searchsorted`で一括検索し、ポインタジャンプ
   （log2(木の深さ)回のベクトル演算）で積算する（開発機223ms。素朴なPythonループは
   1,253ms、numpyスカラーのループは8.6秒だったため実装方式を固定する）。検算テストは
   Python走査との一致で行う。
4. **リング抽出**: `len_c ∈ [D/2 − tol/2, D/2 + tol/2]`（Dは目標距離、tolは
   `distance_tolerance_km`）。固定比率±15%ではなく許容幅から導出し、ユーザーが許容を
   狭めたとき自動追従させる。**最短実距離ではなく軸コスト最適経路の実距離で定義する**
   のが要点。自転車インフラ100%のように往路が大きく遠回りする設定ほど、最短実距離
   基準のリングでは往路だけで目標半分を超え、距離フィルタで全滅するため。
5. **ランキングと多様性間引き**: リング内ノードを設計判断2の指標で昇順ソート（同点は
   node index昇順で安定ソート、T363の決定性教訓）。上位から順に、前任者木から往路Edge集合を
   復元し（上位40件で約19ms）、採用済み候補との往路重複率（距離加重）が
   `TURNAROUND_MAX_OVERLAP_RATIO`（初期値0.6）を超えるノードと、近接
   （`MIN_TURNAROUND_SEPARATION_KM = 1.5`）のノードを飛ばす。近接間引きだけでは同一
   コリドー（例: 荒川CR上の隣接ノード）が上位を独占し、往路の9割を共有するほぼ同一の
   ループがn件並ぶため、重複率の間引きが本質。n件埋まらなければ第2パスで閾値を緩める。
   **タイブレーク**（2026-09-03、ユーザー質問「周囲に自転車インフラがほぼ無い場合」を受けて
   明文化）: 重みを振った軸のデータが周囲に無い場合、全Edgeのdifficultyが同じ値
   （例: 自転車インフラ100%で全て100）になり、コスト倍率が一様＝コスト最適経路が最短経路に
   一致してリングは普通に埋まる（生成は失敗しない）。このとき指標はほぼ全候補で同点になる
   ため、ランキングのキーは`(round(平均difficulty, 1), |len_c − D/2|, node index)`の
   タプルとし、微差（99.8対100.0のようなノイズ）でなく「往路実距離が目標半分に近い順」で
   決める。
6. **往路A\*は不要**: 往路は前任者木の経路そのもの（同じコスト関数でA\*をかけ直しても同じ
   経路）。探索は候補ごとに**復路1本**のみ。
7. **復路探索**（`road_graph_engine.py`）: 往路Edge＋逆方向Edgeのcost_list該当indexを
   `RETRACE_PENALTY_MULTIPLIER`倍に**差し替え、try/finallyで復元**してからA\*
   （`cost_list`のコピーは1回10.7ms、pool 24で約0.26秒と無視できないため）。復路探索は
   同期・直列（T536対応方針5）のためこの差し替えは安全だが、将来`to_thread`並列へ戻すと
   壊れる罠になるため、その旨をコメントとテスト（並列化検知）で固定する。復路の
   ヒューリスティック配列（目的地=起点）はリクエストで1回計算し全候補で共有する。
   T540の早期打ち切りは「len_c＋起点への直線距離＞上限」の1判定として残す。
8. **逐次処理＋早期停止**: 候補は`asyncio.gather`ではなくランク順の逐次ループで処理し
   （T536で`trace_loop`は同期・直列化済みでgatherに並列の意味は無い）、距離フィルタ
   合格が`max_routes`件に達した時点で停止する。プール上限
   `min(40, max(12, max_routes×3))`は保険。
9. **距離フィルタをhydrate前へ**: 距離はlean Edgeの`distance_m`で確定できるため、
   `get_edges_with_geometry`（DB往復）は`evaluate_loops`側へ移し、合格候補だけに行う
   （現行は`trace_loop`内で候補ごとにDB往復してから棄却している）。
10. `evaluate_loops`→`overall_difficulty`昇順ソート（T548）は変更なし。ただしソートキーは
    小数1桁で比較し、同点は現行どおり評価前の「目標距離との差が小さい順」の前整列を安定
    ソートで引き継ぐ（上記タイブレークと同じ理由。周囲に該当軸のデータが無い場合、結果は
    実質的に目標距離に近い順で並ぶ）。先頭`max_routes`件へ
    スライスし、idを`route-00..`へ再採番する。`direction_label`は
    `bearing_between(origin, turnaround)`から`compass_label`で導出する（表示専用、
    候補選定には使わない）。

対象グラフ edges=129,504・nodes=52,698（T536と同条件）。

|---|---|---|---|---|---|
| 冷（タイル・グラフキャッシュ無し） | 8,360 | 125（15） | 47 | 1,468 | 10,000 |
| 温1回目 | 1,094 | 125（15） | 31 | 406 | 1,656 |
| 温2回目 | 860 | 109（15） | 47 | 234 | 1,250 |

- T536時点の同条件（8方位×3レグ=A\* 24本）の温`trace_ms`は329〜375msだったが、本方式の
  「候補選定＋復路探索」は合計140〜170msで、探索段階は旧方式より速い（往路A\*が不要になり、
  復路も9本で早期停止するため）。一対全木（scipy＋ポインタジャンプ）は13万Edge規模で15ms。

  9件を復路探索し8件合格・1件距離フィルタ棄却→`candidates=8`。上位2,000件のリングNodeは
  同じコリドーへ密集しやすく、`max_routes=15`ではプールが不足しうる（`examined`上限の
  引き上げ、または間引きの高速化[T553/T554で同じ箇所を触る際に検討]）。
- `prepare_ms`温パスの残り（`cost_ms`≈560ms、bbox全体のコスト合成）は本タスク以前からの
  値で本方式による増加ではない。`materials_ms`の変動はRedis未起動（dev環境）のタイムアウト
  待ちを含む。

### dev実DB品質確認（2026-09-03、東京駅・20km±5km、`scratchpad/quality_check.py`相当）

- リングを`目標/2 ± 許容/2`（往路7.5〜12.5km）で置いた初版は、既定重みで復路が往路より
