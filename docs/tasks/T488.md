# T488. JMA系等シンプル外部APIクライアントの「TTLCache参照＋fetch＋エラー処理」定型文を共通ヘルパーへ抽出

状態: 完了（2026-08-31）

- 背景: ユーザーからのプロジェクト規模監査の依頼を受け、`backend/app/infrastructure/`配下の
  外部APIクライアント群（`jma_amedas_client.py`・`jma_warning_client.py`・`wbgt_client.py`・
  `flood_client.py`等）を精読した結果、`weather_client.py`（Open-Meteo）が持つtenacity再試行・
  サーキットブレーカー的挙動・2段キャッシュは他クライアントへ複製されておらず（意図的な設計、
  問題なし）、代わりに「`cachetools.TTLCache`を引く→hit/missを`log_external_call`のfieldsへ
  記録→miss時に`httpx`で取得→`raise_for_status()`→`response.json()`→
  `except (httpx.HTTPError, ValueError) as exc: fields["result"]="error"; fields["error"]=repr(exc);
  fields["error_type"]=error_type_label(exc); return None`という8〜10行の定型文が、
  `jma_amedas_client.py`（3箇所）・`jma_warning_client.py`（3箇所）・`wbgt_client.py`（2箇所）・
  `flood_client.py`（1箇所）に計約10箇所、ほぼ一字一句同じ形で繰り返されていることが判明した
  （合計80〜100行規模）。
- 対応方針: `cache.get(key)`/取得先URL・パラメータ/パーサ（json or 生テキスト）/キャッシュへの
  書き戻しキーだけが呼び出し元ごとに異なる薄いラッパーのため、
  `async def cached_fetch_json(cache, key, category, fetch)`のような小さな共通ヘルパーへ
  抽出できる（`material_catalog.py`の`raw_way_tag_extractor`等汎用extractorファクトリと
  同じ発想）。抽出先は既存の`app/infrastructure/`直下に新規モジュール（例:
  `simple_api_client.py`）を作るか、`debug_log.py`へ寄せるかは実装時に判断する。
  `weather_client.py`（tenacity再試行・2段キャッシュを持つ特殊経路）・
  `jma_tile_client.py`/`elevation_client.py`/`basemap_client.py`（TTLCache以外のキャッシュ
  バックエンドを使うため定型文の形が異なる）は対象外のまま据え置く。
  既存の挙動（キャッシュTTL・fields記録内容・戻り値の型）を一切変えない、内部実装のみの
  リファクタとする。
- 期待効果: 行数削減そのものより、次にJMA系の新規エンドポイントを1本追加する際のコストが
  「エラーハンドリング込み30行のコピペ」から「共通ヘルパー呼び出し1行＋固有パラメータ」へ
  下がる点。
- 規模: S

## 実施内容（2026-08-31完了）

- 新規`backend/app/infrastructure/simple_api_client.py`に
  `cached_fetch(cache, key, category, fetch, *, catch=(httpx.HTTPError, ValueError),
  **log_fields)`と`UnexpectedShapeError`（`ValueError`のサブクラス、常に
  `error_type="unexpected_shape"`固定文字列で記録される）を新設。
- `jma_amedas_client.py`（`fetch_station_table`・`fetch_latest_observation_time`の2箇所。
  `fetch_observation_map`はそもそもキャッシュを持たない別パターンのため対象外のまま
  据え置いた）・`jma_warning_client.py`（3箇所全部）・`wbgt_client.py`（2箇所全部）・
  `flood_client.py`（1箇所）を`cached_fetch`経由へ書き換えた。
- **既存挙動の完全維持を`catch`引数で担保**: 呼び出し元ごとに元々の例外捕捉範囲が
  異なっていた（`fetch_municipality_code`だけ`AttributeError`も捕捉、
  `fetch_latest_observation_time`は`.json()`を呼ばないため`httpx.HTTPError`のみ）ため、
  それぞれ`catch=`で明示的に指定し直し、fields記録内容（`cache`/`result`/`error`/
  `error_type`）・戻り値の型を一切変えずに移行した。
- 検証: 4クライアントの既存テスト（31件）・関連サービス層のテスト（計67件）が
  無変更のまま全件green（振る舞いが変わっていないことの直接的な裏付け）。新設した
  `test_simple_api_client.py`（7件）で`cached_fetch`自体の契約（キャッシュヒット/ミス・
  既定/カスタム`catch`タプル・`UnexpectedShapeError`の固定error_type・log_fieldsの
  受け渡し）を検証。`pytest -q -m "not postgis"`（backend全体、1184件）green。
- `docs/modules/backend/weather-dynamic-layers.md`へ新設ヘルパーの節を追記（対象ファイル
  表・設計意図・対象外にした理由）。
