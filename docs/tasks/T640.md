# T640. 点データタイルの配信をレイヤー名パラメータで1実装へ汎用化する

規模M。起票のみ・実装未着手。

## 背景

点データのレイヤーを1つ増やすたびに、API・サービス・リポジトリを一式新設する構造になって
いる。事故は`api/routers/accidents.py`・`services/accident_service.py`・
`infrastructure/accident_repository.py`が丸ごと独立して存在し、停止POI・補給POIは
`region.py`側に別の一式がある（両者は同一の`stop_poi` source-layerを`kind`値集合で
分けており、POI同士は既に相乗りしている）。

生成SQLの骨格はどちらも同じで、違うのは対象テーブルと持ち出す属性だけである。

```sql
SELECT ST_AsMVT(mvt.*, :layer_name, :extent, 'geom') FROM (
    SELECT ST_AsMVTGeom(ST_Transform(<table>.geom, 3857), ST_TileEnvelope(:z,:x,:y), :extent, 256, true) AS geom,
           <属性...>
    FROM <table>
    WHERE ST_Intersects(<table>.geom, ST_MakeEnvelope(:xmin,:ymin,:xmax,:ymax, 4326))
) mvt WHERE mvt.geom IS NOT NULL
```

## 対応方針（案）

レイヤー名をパスパラメータにして、1実装で捌く。

```
/api/region/point-tiles/{layer}/{z}/{x}/{y}.pbf     layer = accidents | stop_poi | ...
```

材料タイル（`/api/region/dynamic-way-values/{material_id}/{z}/{x}/{y}`、
[dynamic-way-values.md](../modules/backend/dynamic-way-values.md)）が既に同じ形で風と勾配を
1実装で捌いているため、この形はプロジェクト内に前例がある。レイヤー定義（テーブル名・
持ち出す属性・タイル世代）をレジストリへ登録し、新しい点レイヤーの追加が1エントリで済む
状態にする。

**座標系は現状維持**（`EPSG:4326`で保存し`ST_Transform(geom, 3857)`で配信）。事故・POI・
路面すべて既に同一の扱いのため、揃え直す作業は発生しない。

タイル世代（`ACCIDENT_TILE_VERSION`・`POI_TILE_VERSION`）はレイヤーごとに独立して持てる
形を維持する（片方の焼き込み値を変えたときに、もう片方のキャッシュまで捨てないため）。

## 検討したが採らなかった案: 1エンドポイントへの統合

事故とPOIを1本のタイルへまとめる案を検討したが、**通信は分離したまま実装だけを1本化する**
上記の案を採る。まとめない理由:

- **3レイヤーとも既定OFF**（`page.tsx: FIXED_LAYER_VISIBILITY_DEFAULTS`の
  `stopPoi`/`supplyPoi`/`accidents`）。ONにした人だけが取る現状に対し、統合すると
  「事故だけONの人にPOIが、POIだけONの人に事故が」配られる。
- 点データは軽くない。実測（gzip後）は z14都心で事故2,962B・POI7,556B、z12郊外で
  事故46,255B・POI60,005B。z12では合計106KB/タイルとなり、画面40枚なら約4MBが
  不要側へ流れうる。
- 統合の主な利点であるリクエスト数の半減は、[T632](T632.md)のブラウザキャッシュ
  （`BATCH_TILE`＝1時間）で再取得が消えたため、初回のみの利得に縮んでいる。

## 保留した場合の影響

新しい点レイヤー（将来の駐輪場・給水所等）を追加するたびに、API・サービス・リポジトリ・
タイル世代定数・フロントのソース定義を一式書き足す作業が発生し続ける。既存機能が壊れる
類の問題ではないため、次に点レイヤーを追加する必要が生じた時点が着手の目安になる。
