# T622: 経緯コメント機械スキャナ（review_checks.py: NARRATIVE_PATTERN）のカバレッジ穴を塞ぐ

状態: 未着手（2026-09-05起票、T567[frontend/axis-studio.mdモジュール]作業中に発覚）

## 背景

T567でfrontend `AxisComposer.tsx`を精読した際、機械スキャナ（`scripts/review_checks.py`の
`find_source_narrative_violations`、pre-commitフックの実体）の推定件数（8件）を大幅に
超える約60箇所の経緯コメントが実際には残っていた。原因を切り分けたところ、性質の異なる
2つの穴が判明した。

1. **JSX `{/* ... */}` コメントは一切検出されない**（構造的な穴）。
   `comment_only()`（review_checks.py）はts/tsx行を`stripped.startswith(("/**", "/*",
   "*/", "*"))`で判定しているが、JSXコメントの開始行は`{/* ...`という形で先頭が`{`のため
   このどの接頭辞にも一致せず、コメント行として認識されない。継続行（2行目以降、`*`接頭辞
   を付けない書き方が多い）も同様に非コメント扱いになる。JSDocコメント（`/** ... * ... */`、
   各行が`*`で始まる慣習）は`*`接頭辞判定でこの関数自体は正しく拾えている。
2. **JSDocコメントはこの関数では拾えているが、`NARRATIVE_PATTERN`正規表現自体が
   実際の書き方より狭い**（正規表現の精度不足）。例:
   - `改善計画T[0-9]+で`はTxxxの直後に「で」を要求するため、`改善計画T345: ...`のような
     コロン区切りの書き方には一致しない（実際のコードでは「で」より「:」区切りの方が
     多かった）。
   - `実機報告20`・`ユーザー指摘20`・`ユーザー要望20`は直後に年（"20"）を要求するため、
     「実機フィードバックへの対応」「というユーザー指摘」のように年を伴わない書き方を
     見逃す。
   - `コードレビュー指摘の修正`・`実バグ`・`UIレビュー`・`ゼロベース網羅`等、
     docs/comments.mdが禁止する経緯記述の言い回しのうち正規表現に含まれていないものが
     複数ある（これらはこれまで完全に手動読解頼みだった）。

この結果、頻繁に更新されるホットファイル（AxisComposer.tsx等）ほど「pre-commitが通って
いるから経緯コメントは無いはず」という期待に反して、新規コミットのたびにJSDoc/JSX形式で
経緯コメントが追加され続け、機械的な強制が実質機能していなかった。

## 影響範囲（保留した場合）

このタスクを起票のみで保留し実装を後回しにする場合、T567の残りモジュール
（frontend 6モジュール）でも同様にJSDoc/JSX内の経緯コメントが機械スキャナの推定件数
より大幅に多く残っている可能性が高く、各モジュール着手時に手動の全文読解で都度
発見・対応する必要がある（T567側は個別ファイルの精読で対応済み・対応予定のため
ブロッカーではないが、非効率）。より深刻なのは、T567完了後の「恒久防止」という
T566/T570の目的が、JSX形式・コロン区切りT-tag・年なしユーザー指摘等の経緯コメントに
関しては実質達成されていない点——新規に追加されるこの形式の経緯コメントは今後も
pre-commitをすり抜け続ける。

## 対応方針（未確定、実装時に決める）

- `comment_only()`にJSX `{/* ... */}` ブロックの検出を追加する（開始行が`{/*`、終了行が
  `*/}`のブロックとして扱う、複数行にまたがる状態をどう持つかは実装時に設計する）。
- `NARRATIVE_PATTERN`を実際の書き方（コロン区切りT-tag、年なしユーザー指摘、
  コードレビュー指摘/実バグ/UIレビュー/ゼロベース網羅等）に合わせて拡張する。
- 拡張後にfull scan（`python scripts/review_checks.py docs`）を一度走らせ、
  既存コードベース全体で新たに検出される既存分の経緯コメント件数を確認する
  （T567の残りモジュールの見積もりが変わりうる）。
