# T455. T423・T440・T442が更新した軸定義フィールドの本番DB反映が実装記録から確認できない

状態: 完了（2026-08-31）

- 背景: `統合レビュー(局所最適の連鎖検出、overall)`
  （`.claude/commands/review/history/2026-08-31_overall.md`F-1）の指摘。T440（規模L、
  「ルート結果・ルート設定パネルの色分けを軸スタジオへ完全同期する」）の実装は、
  `gradient`/`surface_q`の`supports_route_coloring`・`gradient`の
  `display_thresholds_override`・`wind`/`gradient`の`dedicated_way_value_layer`を
  axis_admin API（unpublish→PUT→republish）経由で設定することを前提にしている。この
  API呼び出しが**本番DBに対しても行われたのか、実装記録から確認できない**
  （`docs/tasks/T423.md`・`T440.md`・`T442.md`のいずれにも「本番」という語が一度も
  登場しない）。
- Impact: 本番DBの`gradient`/`surface_q`/`wind`が旧来の既定値
  （`supports_route_coloring=false`・`dedicated_way_value_layer=false`・
  `display_thresholds_override=null`）のままだった場合、本番では
  (1) `routeStyleModesFromCatalogAxes`がgradient/surface_qのルート結果色分けモードを
  選択肢に出さない、(2) `isDedicatedWayValueLayerId`がwind/gradientを含まないため
  ルート設定パネルの「地図で色分け」トグルが機能しない、(3) gradientのプレルート表示は
  既定の`GRADIENT_BOUNDARIES`にフォールバックする——規模Lタスクとして「完了」扱いの
  T440の主要な価値が、本番ユーザーには一切届いていない可能性がある。
- Root Cause: 「軸の行データ変更はaxis_admin API経由に一本化する」設計（T348→T350）は
  「開発DBで確認した」ことと「本番DBへ反映した」ことを区別する明示的な完了条件を
  持たない。CLAUDE.mdの「コミット時の同期ルール」節は破壊的変更の本番同期タイミングは
  明記しているが、「非破壊的だが機能欠落を招くケース」（今回のような、クラッシュはしない
  が新機能が本番で無効なまま）は対象外になっている。
- 対応方針:
  1. 本番の`GET /api/axis-catalog`を確認し、gradient/surface_q/windの
     `supports_route_coloring`・`display_thresholds_override`・`dedicated_way_value_layer`が
     期待値と一致するか検証する。
  2. 乖離していれば、開発DBに対して行ったのと同じaxis_admin API操作
     （unpublish→PUT→republish）を本番DBに対しても実施し、その後
     `dump_axis_definitions_snapshot.py`でスナップショットを再ダンプ・コミットする
     （T442と同様の手順）。
  3. CLAUDE.mdの「コミット時の同期ルール」へ、「axis_admin API経由でDB行データを
     変更した場合、開発DBと本番DBの両方に適用したことをタスク完了条件へ明記する」旨を
     追記することを検討する（`/review:improve`経由での提案が妥当）。
- Confidence: Medium（本番DBへの直接アクセスでの検証はできておらず、実装記録に本番への
  言及が一度もないという状況証拠と、過去の同型同期漏れの実績[T294・T353・T360・T396、
  T409の副次的発見]からの推論）。
- 規模S（検証のみ）〜M（本番反映が必要だった場合）。

## 実施記録（2026-08-31完了）

- **検証**: 本番`GET /api/axis-catalog`（`https://193-123-166-150.sslip.io`、commit
  `1fc9a44`稼働中）を確認したところ、懸念どおり乖離を確認した。想定より対象が広く、
  当初疑っていた3フィールドだけでなく`category`・`show_map_icon`も含めて古い値の
  ままだった:
  - **gradient**: `category`(推定→観測)・`show_map_icon`(false→true)・
    `supports_route_coloring`(false→true)・`display_thresholds_override`(null→
    `[-2,2,6,10]`)・`dedicated_way_value_layer`(false→true) の5フィールド全てが未反映
  - **wind**: `category`(推定→動的)・`show_map_icon`(false→true)・
    `dedicated_way_value_layer`(false→true) の3フィールドが未反映
    （`supports_route_coloring`は既に一致していた）
  - **surface_q**: `supports_route_coloring`(false→true) の1フィールドのみ未反映
    （他は一致）
  - `category`(推定→観測)の乖離は2026-08-30 07:47の`63d959c`（軸スタジオ経由の
    dev DB変更、T440とは別のタイミング）由来で、T440以前から本番未反映のまま
    残っていたことが判明した——「T423・T440・T442が原因」という当初の推測より
    根が深く、**dev DBへのaxis_admin API変更が本番へ反映されるタイミングそのものが
    存在しない**（誰かが明示的にunpublish→PUT→republishを本番へ実施しない限り
    永遠に乖離したまま）という運用上の穴であることを確認した。
- **反映**: `backend/fixtures/axis_definitions_snapshot.json`（開発DBの正本、直近
  `efc35d8`=T442完了時点のダンプ）を正としてPUTペイロードを構築し、3軸それぞれ
  `POST .../unpublish` → `PUT .../{axis_id}`（Basic認証、ユーザー提供の本番admin
  credentials使用）を実施。全リクエストHTTP 200、`GET /api/axis-catalog`再取得で
  全フィールドがスナップショットと完全一致することを確認した。
- **スナップショット再ダンプ**: 今回はdev DB側のデータは変更していない（本番を
  dev側の既存の正しい値へ合わせただけ）ため、`dump_axis_definitions_snapshot.py`の
  再実行は不要（実行しても差分は出ない）。
- **未対応のまま残す提案（対応方針3）**: CLAUDE.mdの「コミット時の同期ルール」への
  追記提案は`/review:improve`経由が妥当な導線のため、本タスクでは実施せず提案のみに
  留める。「axis_admin API経由のDB行データ変更は、本番反映を明示的なタスク完了条件に
  含める」旨をどこかで明文化する余地は残っている。
