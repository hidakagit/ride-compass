# T832. road_edges・road_nodesへ書く事前計算の陳腐化が、どこにも現れない

規模M。
状態: 未着手（2026-09-13、[T814](T814.md)完了時に分離）

## 背景

鮮度台帳（`GET /api/admin/derived-data/freshness`）に載るのは、派生**テーブル**へ書き込む
バッチだけである。`road_edges`・`road_nodes`の列へ直接書くバッチは、その列に系譜
（`source_*_import_run_id`・`algorithm_version`）を持たないため、載せる手段が無い。

- `precompute_edge_curvature` → `road_edges.curvature_deg_per_km`（**ルート評価が読む**）
- `precompute_road_node_degrees` → `road_nodes.degree`

**実害**: PBF再取込のあとにこのバッチの実行だけを忘れると、新規splitされたEdgeは
`curvature_deg_per_km`がNULLのまま残る。蛇行軸は重みの再正規化で薄まり、**警告も欠損表示も
無いまま評価から抜ける**。管理画面の「鮮度」タブを見ても、そこにこの2つは現れない。
[T654](T654.md)が次回のPBF再取込待ちで止まっており、まさにその局面が近い。

[T814](T814.md)で網羅性の検査は「台帳に無いなら理由を書かせる」形になり、この2件は理由つきで
`PRECOMPUTE_NOT_IN_LEDGER`へ登録した——**理由を書いて消えるのは検査であって実害ではない**。

母集団の実測（2026-09-13）: `precompute_*.py`は7件、うち台帳の世代比較に載るのが4件、
完成度（行数差分）で別枠に載るのが`precompute_elevation_attributes`の1件、
載せる手段が無いのが上記2件（**7件中2件＝29%**）。

## 対応方針（どちらを採るかは着手時に決める）

- **(a) 系譜列を足す**: `road_edges`・`road_nodes`へ`source_osm_import_run_id`等を追加する。
  台帳の既存の世代比較へそのまま載る。migrationと本番バックフィルが要る（規模が大きい側）。
- **(b) 完成度チェックを汎用化する**: 現在`elevation_attributes`専用に作り込まれている
  「`road_edges`との行数差分」（`ElevationCompletenessEntry`・`elevation_uncalculated_count`・
  API側の専用フィールド）を、**「この表のこの列がNULLの件数」を宣言で足せる形**へ広げる。
  migrationは不要で、NULLが残っていること自体を管理画面へ出せる。軸を1本足すたびに
  フィールドを増やす作りにしないこと（design-principles.md構造仕様3）。

(b)が軽く、実害（NULLのまま無警告で抜ける）を直接塞ぐ。ただし「古い版で計算された値が
入っている」ケースは(b)では見えない——NULLではないため。両方の性質を踏まえて選ぶ。
