# T832. road_edges・road_nodesへ書く事前計算の陳腐化が、どこにも現れない

規模M。
状態: 完了（2026-09-14。[T814](T814.md)完了時に分離）

## 背景

鮮度台帳（`GET /api/admin/derived-data/freshness`）に載るのは、派生**テーブル**へ書き込む
バッチだけである。`road_edges`・`road_nodes`の列へ直接書くバッチは、その列に系譜
（`source_*_import_run_id`・`algorithm_version`）を持たないため、載せる手段が無い。

- `precompute_edge_curvature` → `road_edges.curvature_deg_per_km`（**ルート評価が読む**）
- `precompute_road_node_degrees` → `road_nodes.degree`

**実害**: PBF再取込のあとにこのバッチの実行だけを忘れると、新規splitされたEdgeは
`curvature_deg_per_km`がNULLのまま残る。蛇行軸は重みの再正規化で薄まり、**警告も欠損表示も
無いまま評価から抜ける**。管理画面の「鮮度」タブを見ても、そこにこの2つは現れない。
[T654](T654.md)が次回のPBF再取込待ちで止まっており、まさにその局面が近い。

[T814](T814.md)で網羅性の検査は「台帳に無いなら理由を書かせる」形になり、この2件は理由つきで
`PRECOMPUTE_NOT_IN_LEDGER`へ登録した——**理由を書いて消えるのは検査であって実害ではない**。

母集団の実測（2026-09-13）: `precompute_*.py`は7件、うち台帳の世代比較に載るのが4件、
完成度（行数差分）で別枠に載るのが`precompute_elevation_attributes`の1件、
載せる手段が無いのが上記2件（**7件中2件＝29%**）。

## 対応方針（どちらを採るかは着手時に決める）

- **(a) 系譜列を足す**: `road_edges`・`road_nodes`へ`source_osm_import_run_id`等を追加する。
  台帳の既存の世代比較へそのまま載る。migrationと本番バックフィルが要る（規模が大きい側）。
- **(b) 完成度チェックを汎用化する**: 現在`elevation_attributes`専用に作り込まれている
  「`road_edges`との行数差分」（`ElevationCompletenessEntry`・`elevation_uncalculated_count`・
  API側の専用フィールド）を、**「この表のこの列がNULLの件数」を宣言で足せる形**へ広げる。
  migrationは不要で、NULLが残っていること自体を管理画面へ出せる。軸を1本足すたびに
  フィールドを増やす作りにしないこと（design-principles.md構造仕様3）。

(b)が軽く、実害（NULLのまま無警告で抜ける）を直接塞ぐ。ただし「古い版で計算された値が
入っている」ケースは(b)では見えない——NULLではないため。両方の性質を踏まえて選ぶ。

## 決定と実装（2026-09-14）

**(b) 完成度チェックの汎用化を採った。** (a)（系譜列の追加）はmigrationと本番バックフィルを
伴い、実害（NULLのまま無警告で抜ける）を塞ぐには重い。(b)なら宣言1行で載る。

`infrastructure/derived_data_freshness.py`へ`CompletenessSpec`／`COMPLETENESS_SPECS`を新設。
「母集団テーブル」と「未計算とみなす述語」を宣言し、`build_completeness_sql`が母集団件数と
未計算件数を1回の走査で数える。elevation専用だった作り込み
（`ElevationCompletenessEntry`・`road_edges_total`・`elevation_uncalculated_count`、
API・frontendの専用フィールド）は畳んで`completeness`の一覧にした——**1件増やすたびに
フィールドを増やす作りにしない**（design-principles.md構造仕様3）。frontendは返ってきた行を
並べるだけで、対象を手書きしない。

**列名だけでは未計算を表せないことが分かった。** `road_nodes.degree`は
`NOT NULL DEFAULT 0`で、未計算（＝PBF取込時の初期値）と本当に次数0の行を区別できない。
宣言を「列名」ではなく「述語＋但し書き（`note`）」にし、但し書きは画面へそのまま出す——
0件でも正常と言い切れないことが読み手に伝わらなければ、判断を誤る。

`PRECOMPUTE_NOT_IN_LEDGER`は空に戻った（[T814](T814.md)で理由つき除外にした3件がすべて
完成度の枠へ載ったため）。網羅性テストは世代比較・完成度のどちらかに載っていれば通る。

## 検証

**開発DBの実データに対して、宣言から組んだSQLを実行して確かめた**（3件とも動作）。同時に
この台帳が可視化すべき事象そのものが観測できた:

| 対象 | 母集団 | 未計算 |
|---|---|---|
| `elevation_attributes` | 319,530 | 184,145（57.6%） |
| `road_edges.curvature_deg_per_km` | 319,530 | **319,530（100%）** |
| `road_nodes.degree` | 138,163 | 14,535（10.5%） |

開発DBでは蛇行の列が**全件未計算**——蛇行軸は重みの再正規化で薄まり、警告も欠損表示も無い
まま評価から抜けていた。まさにこのタスクが想定した状態が現に起きており、台帳がこれを
「未計算あり」として出す。**本番の値はデプロイ後に`/admin`「鮮度」タブで確認する**
（開発DBは部分データのため、この数字を本番の結論にはしない）。

- 網羅性検査の実効性: どちらの枠にも載せていないバッチを1本置くと
  `assert not {'precompute_zzz_probe'}`で落ち、消すと通ることを確認。
- テスト: backend 1904件（postgis除く）緑・frontend 1311件緑、`ruff`・`tsc --noEmit`・
  `eslint`とも新規の指摘なし。OpenAPIとAPI型は再生成済み（`GET /api/admin/derived-data/
  freshness`のレスポンスは`elevation`から`completeness`へ変わる破壊的変更。影響は`/admin`の
  「鮮度」タブのみで、backendとfrontendのデプロイがずれる間その枠だけが表示できない）。
