# T924: 軸の更新を1画面にする（ウィザードを撤去し、依存は表示の切り替えで表す）

状態: 完了（2026-09-17）

## 背景

軸スタジオの編集は4ステップのウィザード（`AxisComposer.tsx`、1,444行に4ステップ分の描画・
ナビゲーション・例外が同居）で、「値を直す」だけの操作でも順送りになる。ステップの必要性を
実在する依存と突き合わせると、依存に由来するのは「後段が前段の選択で具体化する」という性質
だけで、これは1画面でも表示の切り替えで表せる。

| 実在する依存 | 内容 |
|---|---|
| 形の種類 → パラメータ欄 | 折れ線か分類かで入力欄の種類が変わる |
| 材料 → 折れ点の横軸 | 材料が決まらないと単位・値域・参考点・分布が出せない |
| 形 → 地図の色分けスケール | `abs`＋単一材料なら符号付き生値、それ以外は難易度 |

`基本情報`ステップに至っては何にも依存していない。ウィザードが編集に合っていないことは
実装自身が認めており、公開済み軸だけステップを飛ばして最終画面から開く例外
（`restrictedDisplayOnly`）が入っている。

## 対応方針

ステップを畳むのではなく、**依存3つを画面の表示切り替えへ移す**。

- 形の種類 → パラメータ欄: 「なめらか評価／ぴったり評価／かけあわせ評価」という呼び名の
  3択をやめ、**選ぶのは「点数のもとになるもの」1つだけ**にする。材料の`dtype`（数値／
  はい・いいえ／種類）と他軸参照かどうかで`shapeKind`が決まり、対応する入力欄だけが出る。
  呼び名の3択は、材料を選べば確定する情報を利用者へ聞き直していたうえ、材料と矛盾する
  組み合わせ（数値材料に「ぴったり評価」）も選べてしまっていた。
- 材料 → 折れ点の横軸: 材料未選択のうちは折れ点まわりを出さない（同じ節の中の出し分け）。
- 形 → 地図の色分けスケール: 既に親（`AxisStudio`）が軸カタログの分類から色を決めて渡す
  形になっている（T922）ため、節を分ける理由にならない。

あわせて**点数の入力自体を簡単にする**。折れ点の並びは保存形式であって入力欄ではない
——実在する軸の大半は2点の直線で、曲線は実データを見て決めるもの（較正、T925）。既定の
入力は「0点にする値・100点にする値・効き方」だけにし、折れ点の表と曲線エディタは
`<details>折れ点を直接いじる</details>`へ畳む。

## 実装メモ

- `AxisComposer.tsx`は状態・検証・保存と節の組み立てだけを持つ本体（1,444行→338行）に
  なり、節の中身を`AxisScoringSection.tsx`（点数の決め方）・`AxisMapDisplaySection.tsx`
  （地図表示・公開）へ、共有の入力部品を`AxisFormFields.tsx`へ、材料の生値→折れ点の横軸の
  変換を`axisScoring.ts`へ分けた。
- `SECTIONS`は順番を持たない検証の識別子になり、`validateStep`は`validateSection`へ。
  保存時に対象の節をまとめて検証する。制限モード（公開済み軸）は`display_publish`だけを
  描画・検証する（描画していない節を検証すると、入力欄が無いのにそこへ誘導される
  行き止まりになる）。
- **フォームへ`noValidate`、数値入力へ`step="any"`**。1画面にして全ての欄が同時に検証
  対象へ入った結果、既定重み（値0.1、`step="0.01"`）がブラウザの制約検証で不一致と判定され、
  **何の表示も出ないまま保存だけが効かなくなった**。`form.checkValidity()`を出す一時テストで
  原因を特定し、検証は`validateSection`に一本化した。
