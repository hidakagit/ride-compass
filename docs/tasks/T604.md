# T604. 降水延長予報gridFillの「未着色」が取得失敗によるものか閾値未満によるものか区別できない

状態: 完了（2026-09-05、診断のうえコード変更なしでクローズ）

## 背景

ユーザー報告「画面の右端が塗られない」（本番、デフォルト地点[王子]・降水レイヤON・出発時刻
9/6 15:00で再現）を調査。実機の`api:windGridDetail`デバッグログ2件（リクエストbbox・
spacing_deg・応答`points`件数）を、`generate_wind_grid_detail_points`と同じ計算式で
検証したところ、いずれもリクエストしたbboxから理論計算した格子点数と実際の`points`件数が
完全に一致した（24=24、9=9）。つまり**取得失敗によるデータ欠落は無かった**。

## 再検証（2026-09-05、T608完了を受けて）

T608でdynamicWeatherDataStatusによる統一IF化を行った後、本タスクのトリガー
「取得失敗と正常値ゼロを区別する統一的な仕組みが実装された時点」に該当するため再検証した。

`precipitationGridToCellFeatureCollection`（`precipitationNowcast.ts`）を確認したところ、
延長予報gridFillが「見えなくなる」経路は2つあり、いずれも見た目が同一（透明・無着色）:

1. 格子点の値が欠損（`point.precipitation_mm[frameIndex] ?? null`）→ セル自体をFeature
   Collectionから除外する。
2. 格子点の値が`PRECIPITATION_NONE_THRESHOLD_MM`（0.1mm/h）以下→MapLibreのfilterで
   意図的に非表示にする（「ほぼ降水なし」の間引き）。

T608の`dynamicWeatherDataStatus`はレイヤー全体（フェッチ自体が失敗/読込中か）を見る
仕組みであり、格子点1つ1つの「欠損」と「ほぼ0」を区別する仕組みではない。つまり
**本タスクが指摘していたセル単位の曖昧さは、T608の統一IF化では解消されない**。

元のT604調査（bbox理論格子点数と実際の`points`件数の完全一致）はデータが丸ごと
欠落したのではないことの確認であり、この結論と矛盾しない。JMA/Open-Meteoの延長予報は
通常欠損なく返るため、報告された「右端が塗られない」は取得失敗ではなく、ほぼ確実に
「閾値未満（0.1mm/h以下）の正常な間引き」だったと判断できる。

セル単位で欠損と正常値ゼロを見分ける第3の表現（COLOR_LOADING/COLOR_NO_DATA相当）を
新設する案をユーザーへ提示したところ、費用対効果が低いと判断され、現状の診断（バグではなく
正常な間引き）をもって完了とする判断を得た。コード変更は行わない。
