# T853. masterのCI警告が、同じコミットが緑でも鳴る

規模S。
状態: 完了（2026-09-14。[T835](T835.md)で入れた警告を使っていて見つけた）

## 背景

[T835](T835.md)の`scripts/check_master_ci.py`（pre-pushフックが呼ぶ）が、**同じコミットの
同じワークフローに成功した実行があるのに「赤いままです」と警告した**。

実測（`2b01388f`をpushした直後）:

| ワークフロー | run_number | conclusion |
|---|---|---|
| Docs Consistency | 644 | cancelled |
| Docs Consistency | 645 | **success** |
| CI | 1051 | cancelled |
| CI | 1052 | **success** |

同じコミットへ続けてpushしたため2組の実行が同じ秒に作られ、先に始まった側がconcurrency設定で
打ち切られている。警告は打ち切られた側を拾っていた。

原因は「ワークフローごとに最も新しい実行」をAPIの並び順の先頭で決めていたこと。並びは
`created_at`の降順だが、**同じ秒に作られた実行どうしの順序は保証されない**——実際に644
（打ち切り）が645（成功）より前に来ていた。

**実害は警告そのものが信用されなくなること。** push直前の警告は「赤いCIへ新しい変更を
積まない」ためのもので、緑のときに鳴る回数が増えるほど、本当に赤いときの1回が素通りする。
T835自身が「赤が常態になると、CIが通ったことを完了の根拠にできなくなる」と書いている。

## 対応と結果

ワークフローごとの「最新」を`run_number`（ワークフロー内で単調に増える）の最大で決める。
同値・値なしのときは並び順のまま先頭を残す（`run_number`を持たない応答でも従来どおり動く）。

**`cancelled`・`timed_out`を赤として数える扱いは変えない。** 最新の実行が打ち切りで
終わっているなら、成功していない以上「CIが通った」を完了の根拠にはできない——これは
T835が`test_cancelled_and_timed_out_count_as_red`で固定した判断で、今回見つけた誤検知は
「打ち切られた実行を最新と取り違えた」ことが原因であって、打ち切りの扱いではない。

## 取り違えた点（記録）

最初の実装で2つ間違えた。**どちらもCIが落として気づいた。**

1. **`cancelled`を赤から外した。** T835が意図して固定していた判断
   （`backend/tests/test_check_master_ci.py`）を、その存在に気づかないまま覆していた。
2. **テストを`scripts/tests/`へ新規作成した。** 同じ対象のテストが
   `backend/tests/test_check_master_ci.py`に既にあり、二重になった（CIのbackendジョブは
   `backend/tests`を集めるため、新旧の契約が正面衝突して落ちた）。

書く前に「同じ対象のテストが既にあるか」を探していれば両方とも起きなかった。実測した
ケースは既存のファイルへ足し、新設した方は削除した。

## 検証結果

- **直していないと落ちること**: 実測した4件（Docs Consistency 644/645・CI 1051/1052）を
  そのまま入力にした`test_a_run_cancelled_by_concurrency_does_not_hide_the_success_of_the_same_commit`が、
  修正前の実装（並び順の先頭勝ち）では「Docs Consistencyが赤」を返して落ちる。
- `pytest backend/tests/test_check_master_ci.py -q` → 10 passed。
- `python scripts/check_master_ci.py` は、緑のコミット（`2b01388f`）では何も出さず、
  実際に赤いコミット（`d54d1404`、下記）では「CI: failure」を出す。
