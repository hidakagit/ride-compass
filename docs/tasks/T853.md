# T853. masterのCI警告が、同じコミットが緑でも鳴る

規模S。
状態: 完了（2026-09-14。[T835](T835.md)で入れた警告を使っていて見つけた）

## 背景

[T835](T835.md)の`scripts/check_master_ci.py`（pre-pushフックが呼ぶ）が、**同じコミットの
同じワークフローに成功した実行があるのに「赤いままです」と警告した**。

実測（`2b01388f`をpushした直後）:

| ワークフロー | run_number | conclusion |
|---|---|---|
| Docs Consistency | 644 | cancelled |
| Docs Consistency | 645 | **success** |
| CI | 1051 | cancelled |
| CI | 1052 | **success** |

同じ秒に2組の実行が作られ、先に始まった側がconcurrency設定で打ち切られている。
警告は`cancelled`の側を拾っていた。

原因は2つある。

1. **「ワークフローごとに最も新しい実行」をAPIの並び順の先頭で決めていた。** 並びは
   `created_at`の降順で、同じ秒のものどうしの順序は保証されない。実際に644（打ち切り）が
   645（成功）より前に来ていた。
2. **`cancelled`を赤として数えていた。** 打ち切られた実行は「失敗した」ではなく
   「結論が出ていない」で、実行中（`in_progress`）と同じ区分にあたる。

**実害は警告そのものが信用されなくなること。** push直前の警告は「赤いCIへ新しい変更を
積まない」ためのもので、緑のときに鳴る回数が増えるほど、本当に赤いときの1回が素通りする。
T835自身が「赤が常態になると、CIが通ったことを完了の根拠にできなくなる」と書いている。

## 対応と結果

- ワークフローごとの「最新」を`run_number`の最大で決める（ワークフロー内で単調に増える値で、
  同じ秒でも順序が確定する）。
- `cancelled`を赤から外す。`in_progress`と同じく結論が出ていない区分として扱う
  ——`check_master_ci.py`は元から「取得できない・遅い・形が違うときは黙って素通しする」
  設計で、判断材料が無いときに鳴らさない方針と揃う。

判定そのものを`scripts/tests/test_check_master_ci.py`で固定した（この経路は実行するたびに
ネットワークへ出るため、手で確かめると気づくまでが遅い）。

## 検証結果

- **直していないと落ちること**: 実測した4件（Docs Consistency 644/645・CI 1051/1052）を
  そのまま入力にしたテストが、修正前の実装では「Docs Consistencyが赤」を返す。
- `pytest scripts/tests/test_check_master_ci.py -q` → 6 passed。
- `python scripts/check_master_ci.py`（master=`2b01388f`）→ 出力なし（緑）。
  修正前は「警告: masterのCIが赤いままです（2b01388f …） - Docs Consistency: cancelled」。
