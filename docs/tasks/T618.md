# T618. 候補選定をパレート非劣解へ再設計し、難易度の総量を併記する 規模M

状態: 完了（2026-09-06）

## 背景

ユーザー指摘（2026-09-06）「今のルーティングエンジンに、距離も評価に加えたい。距離がどれ
だけ短いかも重み付けにつかえない？　昔は距離と難易度を組み合わせて使ってたけど、違和感
あって消した。今度は別の問題が。難所があっても、距離が長く遠回りした方が常に最適判断
されてユーザの判断余地がない」。

探索コスト（`cost = 距離 × (1 + P × Σ wᵢ × 難易度ᵢ / 100)`）には距離が入っているが、
**候補の選び方と並べ方には一切入っていない**。折返し点選定（`select_loop_turnarounds`の
`np.lexsort((ring, closeness_key, difficulty_key))`）は難易度が主キーで距離は同点
タイブレーク止まり、最終順位も`overall_difficulty`昇順のみ。この難易度が距離加重
「平均」であるため、遠回りして難所を1つ避けるほど値が下がり、距離は目標±許容の
ハードフィルタを通れば全部同格に扱われる——許容範囲の上限いっぱいまで遠回りしたルートが
構造的に有利になる。目的地モード（`select_via_nodes`、`ALTERNATIVE_MAX_STRETCH`倍以内の
フィルタ＋平均difficulty順）も同型。

T401時代の`total_score`（距離の重み＋難易度の重みの合成）へ戻す案は採らない。
[T531](T531.md)で「距離の近さは厳格フィルタを維持し、スコアと混ぜない」とユーザーが
明言しており、合成スコアは比較不能な2つを1つの数字へ潰して重み配分が判断を先取りして
しまう（過去の「違和感」の正体）。

## 方針（ユーザー判断 2026-09-06）

1. **候補をパレート非劣解で選ぶ**。「ある候補Bより短く、かつBより易しい候補Aが存在する
   なら、Bは誰にとっても選ぶ理由がないので落とす」だけで絞る。残った候補は必ず
   「短いが難しい ↔ 長いが易しい」のトレードオフ関係になる。距離と難易度を合成せず、
   重みも帯の幅も決めなくてよい。
2. **難易度の総量（Σ 区間距離×難易度）を候補ごとに併記する**。平均は距離で正規化されて
   遠回りに甘いが、総量は「走り切るのにどれだけしんどいか」に近く遠回りが正直に不利に
   なる。順位には使わず判断材料として出す。

## 実装内容

### パレート非劣解による候補選定

- `domain/routing.py: pareto_front_mask(minimize_a, minimize_b, *, quantum_a, quantum_b)`:
  2つの「小さいほど良い」指標について非劣解を示す真偽配列を返す純関数。aの昇順に走査し
  bの最小値を更新するだけのO(n log n)。`quantum_*`は「実質同じ」とみなす粒度で、比較前に
  各指標をこの単位へ丸める——粒度が無いと1m短いだけの候補が互いに非劣解として全件残り、
  フィルタとして働かない。
- 周回（`select_loop_turnarounds`）: `np.lexsort((ring, closeness_key, difficulty_key,
  ~on_front))`で非劣解を先頭群へ。プールが埋まらないときのために劣解も順序を保って残す。
  同点グループ（`tie_groups`）の区切りも`difficulty_key`だけでなく非劣解かどうかを見る
  （非劣解群の末尾と劣解群の先頭が同じdifficultyのとき、混ぜると劣解が先に試されうる）。
- 目的地（`select_via_nodes`）: 同じ関数を経路長・difficultyへ適用する。

**設計判断の訂正（実装中に既存テストが検出）**: 周回側の第1指標を当初「往路実距離」に
したところ、`test_select_turnarounds_ring_lower_bound_clamped_when_tolerance_exceeds_target`
（T557の回帰テスト）が落ちた。難易度が同じなら短い方が非劣解になるため、起点のすぐ近く
（20m）で折り返す候補がリング中心付近の候補を劣解として押し出していた。**周回では距離は
「短いほど良い」ではなく「目標に近いほど良い」**ため、第1指標をリング中心からのずれ
（`closeness_key`）へ変更した。目標より短すぎる往路も長すぎる往路も対称に扱われる。
目的地ルートは目標距離を持たないため、そちらは経路長そのままでよい。

### 難易度の総量

- `domain/difficulty.py: difficulty_load(segments)`: 距離加重平均×距離合計。difficultyが
  Noneの区間の扱いは平均と一致させる（区間ごとに積分して欠損を飛ばすと、データの無い
  区間が多いルートほど総量が小さく見えてしまう）。
- `RouteCandidate.difficulty_load`として返し、`_with_overall_difficulty`が平均と同時に付与。
  並び順には使わない。
- frontend: `RouteAxisProfile`が総合難易度の隣へ「負荷（難易度×距離）」として併記し、
  (i)で「総合難易度は距離で割った平均のため遠回りするほど下がる／負荷は総量」を説明する。
