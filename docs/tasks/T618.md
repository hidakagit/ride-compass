# T618. 候補選定をパレート非劣解へ再設計し、難易度の総量を併記する 規模L

状態: 着手中（2026-09-06起票）

## 背景

ユーザー指摘（2026-09-06）「今のルーティングエンジンに、距離も評価に加えたい。距離がどれ
だけ短いかも重み付けにつかえない？　昔は距離と難易度を組み合わせて使ってたけど、違和感
あって消した。今度は別の問題が。難所があっても、距離が長く遠回りした方が常に最適判断
されてユーザの判断余地がない」。

探索コスト（`cost = 距離 × (1 + P × Σ wᵢ × 難易度ᵢ / 100)`）には距離が入っているが、
**候補の選び方と並べ方には一切入っていない**。折返し点選定（`select_loop_turnarounds`の
`np.lexsort((ring, closeness_key, difficulty_key))`）は難易度が主キーで距離は同点
タイブレーク止まり、最終順位も`overall_difficulty`昇順のみ。この難易度が距離加重
「平均」であるため、遠回りして難所を1つ避けるほど値が下がり、距離は目標±許容の
ハードフィルタを通れば全部同格に扱われる——許容範囲の上限いっぱいまで遠回りしたルートが
構造的に有利になる。目的地モード（`select_via_nodes`、`ALTERNATIVE_MAX_STRETCH`倍以内の
フィルタ＋平均difficulty順）も同型。

T401時代の`total_score`（距離の重み＋難易度の重みの合成）へ戻す案は採らない。
[T531](T531.md)で「距離の近さは厳格フィルタを維持し、スコアと混ぜない」とユーザーが
明言しており、合成スコアは比較不能な2つを1つの数字へ潰して重み配分が判断を先取りして
しまう（過去の「違和感」の正体）。

## 方針（ユーザー判断 2026-09-06）

1. **候補をパレート非劣解で選ぶ**。「ある候補Bより短く、かつBより易しい候補Aが存在する
   なら、Bは誰にとっても選ぶ理由がないので落とす」だけで絞る。残った候補は必ず
   「短いが難しい ↔ 長いが易しい」のトレードオフ関係になる。距離と難易度を合成せず、
   重みも帯の幅も決めなくてよい。
2. **難易度の総量（Σ 区間距離×難易度）を候補ごとに併記する**。平均は距離で正規化されて
   遠回りに甘いが、総量は「走り切るのにどれだけしんどいか」に近く遠回りが正直に不利に
   なる。順位には使わず判断材料として出す。
