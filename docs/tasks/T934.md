# T934: 信号の点が、1交差点あたり2.58個のまま地図へ出ている

状態: 実装済み・本番反映待ち（2026-09-18起票）

## 背景

日本のOSMは1つの信号交差点を流入路ごと・横断歩道位置ごとの複数ノードで描く。この前提は
プロジェクト内で既に一度扱っていて、**停止密度を数える側**は`ST_ClusterDBSCAN`で同じキーの
点をまとめてから数えている（`road_graph_repository.py: _POI_COUNTS_BODY`、eps は
`domain/traffic.py: POI_CLUSTER_EPS_M`）。

一方**地図タイルを焼く側**（`road_graph_repository.py: _POI_TILE_MVT_SQL`）は、タイル矩形に
交わる`osm_raw_pois`を1ノード1フィーチャでそのまま出す。クラスタ化も、ズームによる出し分けも、
件数の上限も無い。フロントは`circle`レイヤーで半径を固定して描くので、`symbol`のような
衝突判定も働かず、重なった点はすべて描かれる。

**同じ現象に対して、数える側は畳んでいるのに見せる側は畳んでいない**——これが利用者から見た
「同じ交差点なのに信号が何個も出る」の正体である。

## 実測（本番DB、2026-09-18）

集計側と同じ定義（`_POI_COUNT_KIND_EXPR`。`highway=traffic_signals`と、
`highway=crossing`かつ`crossing`タグが`signals`を含むものの両方を信号として扱う）で数えた。
クラスタ化も集計側と同じ`ST_Transform(geom, 3857)`上で行い、物差しを揃えている。

| | |
|---|---|
| `highway=traffic_signals` | 75,644 |
| `crossing=*signals*` | 55,072 |
| 実質的な信号ノード | 130,716 |
| eps=25 でまとめた塊 | 57,364 |
| eps=40 でまとめた塊 | 50,760 |
| eps=60 でまとめた塊 | 49,109 |
| 1塊あたりのノード数（eps=40） | 2.58 |

塊の大きさは単独が28,210で最多だが、5個の塊が3,591・8個の塊が2,180あり、1つの交差点が
8点で描かれる例が実数として存在する。z12のタイル1枚あたりの信号ノードは平均314・最大5,108。

epsを25から60へ広げても塊の数は57,364→49,109（14%）しか動かない。**まとめる/まとめないの
差（130,716→50,760、61%減）に比べてepsの選び方の影響は小さい**ため、既に較正済みの
`POI_CLUSTER_EPS_M`をそのまま使う根拠になる。

## 同時に見つかった、別口の欠陥

フロントの凡例`STOP_POI_CATEGORIES`（`staticAttributeLayers.ts`）は取込時の`kind`生値と
1対1で組まれていて、backendが`_POI_COUNT_KIND_EXPR`で行っている「信号の2通りの書かれ方を
1つへ寄せる」を再現していない。その結果、**実質的な信号の42%にあたる`crossing=*signals*`が
地図上では「横断歩道」の色で出ている**。

まとめる処理をサーバ側へ入れるなら、出力する`kind`も集計側の寄せ方へ揃えることになるため、
この欠陥は同じ変更の中で解消できる。逆に言えば、寄せ方を揃えずにクラスタ化だけ入れると
「横断歩道として塗られた信号」が残る。

## 対応方針の候補

| 案 | 内容 | 評価 |
|---|---|---|
| A | タイルSQLの中でその場でクラスタ化する | 前計算の置き場が要らない。z12の最悪タイル5,108点に対するDBSCANの費用が未計測 |
| B | まとめ済みの点を持つテーブルを前計算し、タイルはそれを読む | タイルは速い。取込・バックフィルの導線と、元の点との二重管理が増える |
| C | 交差点ノードへ紐付ける | **採らない**。[T655](T655.md)が評価側で同じ案を「交差点の外にある単独信号を落とす」として不採用にしており、表示でも同じ理由がそのまま効く |

MapLibre側のクラスタリング（`cluster`オプション）は**使えない**。geojsonソース専用で、
POIタイルはvector tileソースであり、z12〜15の全域配信という現行設計とgeojson化は両立しない。
**集約はサーバ側でやるしかない。**

## 決めること

- 案Aと案Bのどちらか。まずz12の最悪タイル（5,108点）でDBSCANの実測を取り、案Aが成立するかを
  見てから決める。成立するなら案Aの方が持ち物が増えない。
- **ズームによって畳み方を変えるか。** z15まで拡大したときに個々の信号ノードが見えた方が
  良い場面があるなら、低ズームだけ畳むことになる。ここを変えるとタイルの署名がズームごとに
  変わる点に注意。
- 停止要因の他の種別（横断歩道が信号より多い）も同じ扱いにするか、信号だけにするか。
  横断歩道は信号より点が多く、同じ理屈がそのまま当てはまる。

## 決めた内容（2026-09-18）

**案Aを採る。** 本番で案Aの費用を測った結果、持ち物が増える案Bを選ぶ理由が無かった。
下表は選択部分（`ST_AsMVT`のエンコードを除く）を3回実行した中央値。

| タイル | 現行の点数 | 現行 | まとめ後 | まとめ後 | 削減 |
|---|---|---|---|---|---|
| z12（最も点が多い1枚） | 23,408 | 95.1ms | 13,123 | 483.6ms | 43.9% |
| z13 | 5,072 | 56.1ms | 2,925 | 86.8ms | 42.3% |
| z14 | 1,654 | 6.4ms | 836 | 14.9ms | 49.5% |
| z15 | 410 | 5.4ms | 193 | 9.4ms | 52.9% |

最悪の1枚で+389msだが、これは関東で最も点が密な1枚であり、かつタイルはキャッシュされる。
z13以下の実用域では+30ms未満に収まる。

**ズームによる出し分けはしない。** z15でも削減率は52.9%で、低ズームの43.9%より大きい。
同じ交差点を描く複数ノードは拡大しても同じ交差点であり、ズームを変える理由が無い。まとめ方を
ズームで変えないため、拡大縮小で点が分裂・合体して見えることもない。

**地図へ出す`kind`は、信号の寄せ方だけを数える側と揃える。** 起票時は集計キー
（`POI_COUNT_KINDS`）へ全面的に揃えることを想定していたが、それだと「徐行」が「一時停止」へ、
「ハンプ・狭さく」が「車止め」へ畳まれ、地図から区別が消える。これは今回の欠陥とは無関係な
情報の削減なので採らない。寄せるのは信号（2通りの書かれ方）だけにし、述語を
`_SIGNAL_CROSSING_PREDICATE`として1箇所に置いて数える側と共有する。この選択により
`poi-kinds.json`・フロントの凡例定義は変更不要になった。

**停止要因は全種別をまとめる。** 横断歩道も信号と同じく交差点ごとに複数ノードで描かれる。
補給POIはまとめない（別々の実体のため。`cluster_key`をノードidにして1点1塊に落とす）。

## 実装

- `road_graph_repository.py`: `_SIGNAL_CROSSING_PREDICATE`を新設し、`_POI_COUNT_KIND_EXPR`
  （数える側）と`_POI_TILE_KIND_EXPR`（地図へ出す側）の両方がこれを読む。
  `_POI_TILE_MVT_SQL`が停止要因を`POI_CLUSTER_EPS_M`でまとめ、構成ノードの重心を1点として
  出す。タイル境界で塊が切れないよう`ST_Expand`で外側まで読み、重心がタイル内に入るものだけを
  出す（`_POI_TILE_CLUSTER_PAD_DEG`）。
- タイルの署名は`POI_TILE_SHAPE`がSQLから導出するため自動で変わる（手で世代を上げない）。

## 検証

- PostGIS統合テストを4件追加（`test_road_graph_repository.py`）。同じ交差点の信号が1点に
  なること・その位置が重心になること・`crossing=*signals*`が信号として出ること・
  信号でない横断歩道は寄せないこと・補給POIはまとめないこと。
- **効いていることの確認**: `cluster_eps_m`を0.001へ潰して実行し、まとめの2件が
  期待どおり落ちることを見た（`2 failed, 1 passed`）。潰す前は7件すべて通る。
- 残り: 本番反映後に、1つの交差点が複数点で描かれていた実在の地点を実機で確認する。
