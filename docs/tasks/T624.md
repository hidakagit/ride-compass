# T624. 開放度（遮蔽物）推定軸の新設 規模M/L（設計済み・実装未着手）

状態: 設計済み・実装未着手（2026-09-06起票、同日に設計を確定）

## 背景

ユーザー実機報告（荒川サイクリングロード、向かい風3m/s）「かなりしんどかった」に対し、
風の評価軸の計算値（難易度約38/100、「軽い向かい風」帯）とのギャップを調査した過程で
浮上した案。Open-Meteoの気象モデル自体（JMA、最良でもLFM 2km格子）が、河川敷のような
遮蔽物の無い場所の局地的な吹き抜けを原理的に捉えられないため、風の格子解像度をいくら
上げても解決しない（[T623](T623.md)参照）。地形・建物・植生による「開けている度合い」を
別の材料として持つ案が代替として浮上した。

## 組み込み方針（決定事項）

- **独立した静的軸として実装する**（風の材料計算への組み込みはしない）。既存の
  静的材料と同じ「バッチで道路ごとに事前計算→専用テーブルへ保存→軸スタジオで
  breakpoints設定」という枠組みをそのまま踏襲する。天候APIへの依存を増やさない。
  風の動的計算（`WindWayService`）へ開放度係数を掛け合わせる案（[T414](T414.md)の
  「同一タイル内は同値」という設計が崩れ規模L相当の作り直しになる上、軸同士を乗算する
  非線形結合になり下記の制約に反する）は不採用。
- **軸の合成は線形のまま崩さない**（ユーザー指示）。現在のルーティングコストは
  `cost = distance × (1 + P × Σ wᵢ × 難易度ᵢ / 100)`という各軸の重み付き線形和
  （`docs/decisions/t12-routing-scale.md`不変条件1）。開放度軸も他の軸と同じ
  `breakpoint_linear`形状で材料値→難易度0-100を出し、この線形和へそのまま乗るだけに
  留める。他の軸の値を読んで係数を変える・軸同士を掛け合わせる、といった非線形な
  相互作用は持たせない。
- **閾値による加算ではなく、開放度に応じた連続値**として表現する（分岐処理を新設しない）。

## 依頼文の前提のうち設計で補正した点（上記クラス体系以外）

1. **最も近い前例は勾配軸ではない**。勾配（`gradient_percent`）は「符号付き・進行方向
   依存」のためMVTタイルへ焼き込めず、専用のway_id→値配信（`dedicated_way_value_layer`、
   `GradientWayService`、Redisキャッシュ、`bearing_deg`必須のエンドポイント）を要する
   特殊経路である。開放度は**方向にも時刻にも依存しない**ため、この経路は不要で、
   前例として本当に近いのは`way_attribute_counts`（Way単位の空間集計バッチ→MVT焼き込み→
   `derive_ramp_inputs`によるramp地図表示の自動導出）と`designation_attributes`
   （Way単位の派生テーブルを`road_edges.osm_way_id`経由で評価へ結合）の2つ。この前例に
   乗ると、新サービス・新エンドポイント・フロントエンドのコード変更が一切不要になる
   （設計原則2「新しい軸を追加するときfrontendのコード変更が一切不要」をそのまま満たす）。
2. **軸の行データはmigrationでINSERTしない**（CLAUDE.md「コミット時の同期ルール」）。
   `backend/migrations/`には新テーブルのDDLだけを置き、軸定義は`axis_admin` API
   （軸スタジオ）で作成し、`dump_axis_definitions_snapshot.py`でスナップショットを
   再ダンプする。
3. **バッチはDBホスト上では走らない前提**。`import_pbf.py`等のバッチはローカル開発機
   または`--memory`上限付きの別コンテナから本番DBへ接続して実行し、依存は
   `requirements-batch.txt`に分離されている（本番webイメージには入らない）。本番DBは
   backendと同じ12GBのOracle Cloud VMに同居し、重いバッチでVM全体がOOMになった実績がある
   （`docs/disaster-recovery.md`「既知のリスク」）。この前提がラスタ処理の置き場の判断
   （後述「論点2」）を左右する。
4. **静的軸であることの限界を明記する**: 開放度は無風の日にも同じ値を返すため、重みを
   固定すると「開けた道は常に減点」になる（荒川CRのような人気ルートが常に不利になる）。
   本設計では「風が強い日にユーザーがこの軸の重みを上げる」という運用を前提にし、
   予報風速に応じて重みを自動で効かせる仕組み（`time_scope="night_only"`と同型の
   「リクエスト文脈による重みのゲート」）はトリガー付きDEFERとして本タスクの対象外に
   する（下記「見送り・DEFER」参照）。

## 設計

### 論点1: 「開放度」の指標定義とバッファ半径

**方針転換（2026-09-06、実装着手時にユーザーと再検討）**: 当初案（Trees/Built画素比率を
Python側で`openness_percent`1本の連続値へ合成し、単一のnumeric材料として登録する）は
撤回した。理由は次の2点:

1. **材料段階での加工が合成先の軸を分かりにくくする**。「遮蔽=Trees/Built、それ以外=
   開放」という分類判断がPython関数（`domain/landcover.py`）に固定されると、軸定義
   （軸スタジオのGUI）を見ただけでは何が難易度に寄与しているかが分からない。
2. **カテゴリ型（1way=1ラベル）は連続値より情報量が少ない**。1つの道路の周囲100m
   リングには10m画素が数百〜数千個入り、実際には複数クラスが混在する（例:
   木40%・建物30%・開けた土地30%）のが普通。これを「dominant_class」1つに潰すと
   混在の情報（正確な割合）を失う。連続値（クラスごとの割合%）の方が明らかに
   情報量が多い——検討時に一度「1つのcategorical材料にする」案も出たが、この理由で
   不採用にした。

**確定方針**: 土地被覆クラスごとの割合を**そのまま独立したnumeric材料**として登録し
（1クラス=1材料、単位%、加工なし）、「どのクラスをどれだけ難易度に寄与させるか」は
Python側の分類関数ではなく**軸スタジオの`terms`（重み付き線形結合）**で表現する。
これにより「遮蔽=Trees+Built」という当初の判断は、コードではなく軸定義の
`terms: [{material: "trees_percent", weight: 1.0}, {material: "built_percent", weight: 1.0}]`
として可視化され、後から軸スタジオでこの重みを調整する場合もバッチ再実行が不要になる
（`terms`の重み付き線形結合そのものがクラス重み付けの機構であり、材料側に重み表を
持つ必要は無い——という当初案の着想自体は維持しつつ、間に挟んでいた「材料側で
先に2値化する」処理を無くした）。

```
<class>_percent = 100 × <class>画素数 / 有効画素数
有効画素 = リング内の画素のうち No Data(0)・Clouds(10) 以外
リング   = 道路centerlineの外側100mバッファ − 内側10mバッファ（UTM座標系でメートル指定）
```

8クラス（water/trees/flooded_veg/crops/built/bare/snow_ice/rangeland）全てについて
上式で`<class>_percent`（0〜100、%）を計算しテーブルへ保持する（次節スキーマ）。
初期の「開放度」軸が実際に使うのは`trees_percent`・`built_percent`の2件のみだが、
残り6件も同じ式で同じテーブルに並んで存在するため、評価パイプラインへ材料登録する
コストだけで（バッチ再実行無しに）将来いつでも使える。

- **道路自身の画素を除くリング形状にする理由**: Esri版の分類では道路面自体がBuilt areaに
  なるため、幅の広い道路ほど「建物に囲まれている」と誤って読まれる。測りたいのは道路の
  *周囲*であり道路面ではないので、内側10m（片側5m≒2車線道路の半幅）を除外する。
- **半径100mの根拠**: 障害物の風下側で風が回復するまでの距離は障害物高さの10〜20倍
  （建物10m→100〜200m）。10m画素で100mリングなら1本の道路（長さ数百m）あたり数百〜
  数千画素が入り統計的に安定する。50mでは隣接1列の建物しか見えず、200mでは河川敷の
  対岸の市街地まで拾って河川敷の開放度が下がる。**半径・内径はバッチの引数
  （既定100/10）とし`algorithm_version`に含めて記録する**。較正（論点4）で50/100/200mを
  同じ参照道路で比較してから既定値を確定する。

### 論点2: ラスタ処理の実装場所 → Python（rasterio）によるバッチ側処理を採用

| 観点 | PostGIS raster（`postgis_raster`拡張＋`ST_Clip`/`ST_ValueCount`） | Python（rasterio＋shapely＋numpy、バッチ側） |
|---|---|---|
| 本番DBへの影響 | 拡張の追加インストール・GDALドライバ設定（`POSTGIS_GDAL_ENABLED_DRIVERS`）・関東分のラスタ（10m、約25,000×26,000画素≒650M画素）をテーブルとして常駐させる。DBはbackendと同じ12GB VMに同居しており、94万wayぶんの`ST_Clip`をDB側で回すとOOM実績のあるホストにさらに負荷が乗る | DBには派生スカラー（way単位の行）だけが入る。ラスタは`kanto-latest.osm.pbf`と同じ「バッチ実行機のローカルファイル」の扱い |
| 設計原則との整合 | ラスタ（生データ）をDBへ実体化する。原則6「派生は再生成可能、導出できるものを実体化しない」の趣旨と噛み合いにくい | 生データはファイル、DBは派生のみ。既存の標高（GSI DEMタイルをPythonでパース・補間し、結果だけを`elevation_attributes`へ保存）と同じ分担 |
| 依存の追加先 | DB側（拡張）＋`raster2pgsql`CLI | `requirements-batch.txt`のみ（`rasterio`・`pyproj`。`shapely`・`numpy`は既存）。本番webイメージには入らない（`osmium`と同じ分離） |
| 性能 | 1wayごとに`ST_Clip`→集計。PostGIS rasterはタイル単位の集計が重く、100万件規模では時間がかかりやすい | 1wayあたり「ウィンドウ読込（COGの内部タイル、GDALブロックキャッシュが効く）＋小さなマスクのラスタライズ＋`np.bincount`」でミリ秒級。地理的順序（`ORDER BY geom`、標高バッチと同じ）で処理すればブロックキャッシュのヒット率が上がる。関東の対象way（`osm_raw_ways`でhighway非NULL、約94万〜）で単一プロセス数十分〜1時間程度の見込み。`multiprocessing`で分割可 |
| 柔軟性 | SQLで書けるのは集計まで。リング形状・UTM変換・無効画素除外はSQLが複雑になる | domain純関数（後述）にそのまま書ける。将来Edge単位へ切り替える場合も同じ関数を使える |

**採用: Python側**。決め手は「本番DBへ拡張・常駐ラスタ・重い集計を持ち込まない」
（VM同居・OOM実績）と「既存の標高バッチと同じ分担（ラスタはPythonで読み、結果だけDB）」の
2点。PostGIS raster案は、将来バッチ実行環境がDBと分離されて余裕ができ、かつSQLだけで
完結させたい動機が生まれた場合の代替として記録に残す。

### DBスキーマ（migration `0032_add_way_landcover.sql`、DDLのみ）

```sql
CREATE TABLE IF NOT EXISTS way_landcover (
    osm_way_id           bigint PRIMARY KEY REFERENCES osm_raw_ways(osm_way_id) ON DELETE CASCADE,
    valid_pixels         integer NOT NULL,        -- No Data・Clouds除外後の画素数
    water_percent        real NOT NULL,           -- 以下8列: 有効画素に占める割合（0〜100、%）
    trees_percent        real NOT NULL,
    flooded_veg_percent  real NOT NULL,
    crops_percent        real NOT NULL,
    built_percent        real NOT NULL,
    bare_percent         real NOT NULL,
    snow_ice_percent     real NOT NULL,
    rangeland_percent    real NOT NULL,
    data_source          text NOT NULL,           -- 'esri-io-lulc'
    data_version         text NOT NULL,           -- 例 '2025'（使用した年次マップ）
    computed_at          timestamptz NOT NULL,
    source_osm_import_run_id integer REFERENCES osm_import_runs(id) ON DELETE SET NULL,
    algorithm_version    text                     -- 例 'v1-ring10-100'（リング径を含める）
);
```

- **Way単位（`osm_way_id`）にする理由**: 地図タイルの母集団は`osm_raw_ways`全域で
  `road_edges`（ルート生成済みエリアのみ、関東全域で約500万行）では不足する
  （`way_attribute_counts`が並存している理由と同じ）。評価側は
  `road_edges.osm_way_id`で結合すれば済み（`designation_attributes`→`is_designated`と
  同じ経路）、行数も約94万で済む。開放度は100mスケールで緩やかに変わる量なので、
  交差点で分割されたEdge単位まで細かくしても得られる情報は少ない。長いway（河川敷の
  数kmのway等）で周囲が途中で変わるケースが較正で問題になったら、同じdomain関数を
  `road_edges.geom`に適用するEdge単位テーブルへ切り替える（関数はジオメトリの出所を
  知らない設計にしておく）。
- 8列全て「有効画素に占める割合を100倍しただけ」の生値で、Python側での2値化・合成は
  一切行わない（情報欠落を最小化する。上記「方針転換」参照）。MVT SQL（タイル焼き込み）と
  バッチ（Python）が同じ式（画素数→%）を重複して持たないよう、**式の正準定義を
  `domain/landcover.py`の1箇所に置く**（原則4）。バッチだけがこの関数を呼び、SQLは
  列を読むだけにする。
- ORMミラー`WayLandcoverRow`を`road_graph_models.py`へ追加する（`WayAttributeCountsRow`と
  同じく、単体実行時の`NoReferencedTableError`を避けるため`source_osm_import_run_id`は
  素の`Integer`で持ち、FKはmigration側のみ）。
- 鮮度台帳: `derived_data_freshness.py: GENERATION_FRESHNESS_SPECS`へ
  `GenerationFreshnessSpec(table_name="way_landcover", sources=(OSM取込,),
  algorithm_version_current=precompute_way_landcover.ALGORITHM_VERSION)`を1件追加
  （SQLは宣言から自動生成される）。`data_version`（年次マップの年）は世代比較の対象に
  しない（外部データの更新は手動判断のため）。
- `/health`（`api/routers/health.py: _KEY_TABLES`）へ`way_landcover`を追加し、
  バッチ未実行を0件検知の対象にする。

### 材料計算ロジック（`domain/landcover.py`、新規・純関数のみ）

```python
LULC_WATER, LULC_TREES, LULC_FLOODED_VEG, LULC_CROPS, LULC_BUILT, LULC_BARE, LULC_SNOW_ICE, LULC_CLOUDS, LULC_RANGELAND = 1, 2, 4, 5, 7, 8, 9, 10, 11
LULC_INVALID_VALUES = frozenset({0, LULC_CLOUDS})       # 分母から除外
MIN_VALID_PIXELS = 20                                    # これ未満は「値なし」（行を作らない）

def class_percentages(counts: Mapping[int, int]) -> LandcoverPercentages | None
```

`class_percentages`は8クラスそれぞれの画素数を有効画素数で割って100倍するだけの
単純な集計で、どのクラスが「遮蔽」かの判断は一切含まない（その判断は評価パイプライン側の
軸定義`terms`に委ねる、上記「方針転換」参照）。`LandcoverPercentages`はPydanticモデル
（`EdgeAttributeCounts`と同じ流儀）で`way_landcover`の割合8列＋`valid_pixels`と1対1。
テストはこの純関数に対して境界値（全画素Clouds→None、全画素Built→built_percent=100かつ
他クラス=0、最小画素数未満→None）を書く。

### バッチ（`batch/precompute_way_landcover.py`、新規）

```
① 対象way抽出: osm_raw_ways（geom IS NOT NULL AND highway IS NOT NULL）から
   way_landcoverに行の無いway_idをanti-joinで抽出し ORDER BY geom（地理的順序）で返す
   （精度改善バッチ⑦[標高]と同じ増分実行。--recompute で全件洗い替え）
② ラスタを rasterio で開く（複数ファイル可。各wayは重心を含むファイルで処理）
③ CHUNK_SIZE=5,000 ごとに:
     - geomを EPSG:4326→ラスタのCRS（EPSG:32654）へ pyproj で変換
     - ring = line.buffer(outer_m) − line.buffer(inner_m)
     - ringの外接矩形に対応するウィンドウを読み、rasterio.features.geometry_mask で
       ring内画素を選び np.bincount でクラス別画素数
     - domain/landcover.py の純関数で割合・材料値を算出（Noneなら行を作らずWARNINGを
       件数集計へ）
     - ラスタ範囲外のway（ウィンドウが取れない）は行を作らない（欠損＝unknown）
     - INSERT ... ON CONFLICT (osm_way_id) DO UPDATE で系譜列ごとUPSERT
       （source_osm_import_run_idはチャンクごとに直前取得、⑥⑧と同じ）
④ 完了サマリ1行INFO（対象件数・書込件数・範囲外件数・画素不足件数・所要時間）
```

- CLI: `--raster <path>...`（必須、複数可）・`--buffer-m 100`・`--inner-m 10`・
  `--data-version <年>`（省略時はファイル名から推定）・`--recompute`・`--dry-run`・
  `--database-url`。8列全てが「画素数→%」という同じ単純な式のraw値のため、
  当初検討していた`--from-fractions`（割合列から別の材料列だけ再計算するモード）は
  不要になった（方針転換により「割合列」と「材料列」が同じものになったため）。
- `ALGORITHM_VERSION`はリング径を含む文字列（`f"v1-ring{inner}-{outer}"`）にし、径を
  変えると鮮度台帳が「古い版」と判定するようにする。
- メモリ: ウィンドウ読込のみでラスタ全体は読まない。GDALのブロックキャッシュ上限
  （`GDAL_CACHEMAX`）を明示し、本番向け実行は`docs/disaster-recovery.md`の
  `--memory`ルールに従う。
- `refresh_derived.py: _STAGES`へ第3グループの末尾（⑨`match_designations`の後）に
  ⑩として追加する。ラスタのパスは`config.py`の`lulc_raster_paths`（環境変数、
  カンマ区切り）から読み、未設定なら**失敗させる**（黙って飛ばすと「バッチ未実行で軸が
  静かに欠落する」既知の障害モードを再生産するため）。ラスタを用意できない環境向けに
  `--skip-landcover`を明示的に指定した場合だけWARNINGを出して飛ばす。
- 再実行トリガー: OSM再取込（way集合の変化）・年次マップの更新（`--recompute`＋
  `--data-version`）・リング径の変更（`--recompute`）。
  実行後は`ROAD_SURFACE_TILE_VERSION`と`TILE_MATERIALS_CACHE_VERSION`/
  `TILE_SCORE_MATRIX_CACHE_VERSION`を上げる（既存⑧と同じ運用）。

**軸定義**（`axis_admin` API経由、下書きで作成→較正→公開。migrationには書かない）:

```json
{
  "axis_id": "openness", "label": "開放度", "chip_label": "開放度", "category": "推定",
  "description": "周囲に建物・樹木などの遮蔽物が少ない[開けている]道ほど難しい",
  "panel_hint": "衛星画像の土地被覆データから、道路の周囲100mに建物や樹木がどれだけ多いかを推定した値です。河川敷や田園地帯など建物・樹木が無い道で高くなります。風の強い日に重みを上げて使う想定です。",
  "shape": {"kind": "breakpoint_linear", "preprocess": "identity",
            "terms": [
              {"material": "trees_percent", "weight": 1.0, "required": false},
              {"material": "built_percent", "weight": 1.0, "required": false}
            ],
            "breakpoints": [[20, 0], [60, 30], [90, 100]]},
  "default_weight": 0.0,
  "dedicated_way_value_layer": false,
  "display_thresholds_override": [30, 50, 70, 85],
  "display_band_labels_override": ["市街地", "住宅地", "やや開けている", "開けている", "吹きさらし"],
  "icon_id": "<既存アイコンから選ぶ>", "show_map_icon": true, "time_scope": "always"
}
```

- `terms`が「遮蔽=trees+built」という当初の判断をコードではなく軸定義として表現する
  （上記「方針転換」参照）。将来この重みだけを軸スタジオで調整する場合もバッチ再実行は
  不要（材料の生値は変わらないため）。
- `preprocess="identity"`・両termとも`tile_property`ありのnumeric材料・方向非依存なので、
  `derive_ramp_inputs`が地図のramp表示を自動導出する（`terms`が複数でも、境界値の集合を
  合成した閾値化に対応済み——`stop_density`/`accident`等の既存の複数term軸と同じ
  扱い）。フロントは`GET /api/axis-catalog`から受け取るだけでコード変更ゼロ
  （`axisLayers.ts`冒頭の契約どおり）。レンズ（地図の色分け）にも他のramp軸と同様に
  自動で現れる。
- `default_weight`は0にする（上記「静的軸の限界」のとおり、無風の日には効かせない方が
  自然。ユーザーが風の強い日に重みを上げる）。重み0でも公開軸として並び、レンズで
  色分けは見られる（UI仕様「消さずに薄くする」）。既定重みを0以外にする判断は較正後に
  ユーザーと決める。
- breakpointsの初期値は仮置き（論点4で較正）。
- 区間インスペクタ（`axis_inspector_breakdown`）はway単位で値が引けるため
  `available=True`で返せる（勾配・風のような「単独wayでは算出不能」の扱いにはならない）。
- 公開後、開発DB・本番DBの両方へ同じ定義を反映し`dump_axis_definitions_snapshot.py`で
  スナップショットを更新してコミットする（`docs/deployment-sync.md`）。

### 論点3: CC BY 4.0の帰属表示

現状の帰属表示はMapLibreのAttributionControl一本で、各データ源は`MapView.tsx`の
`addSource(..., { attribution })`に文字列で載せている（気象庁="気象庁"、Open-Meteo=
"Open-Meteo"、地理院タイル=リンク付き定数`GSI_RELIEF_ATTRIBUTION`）。backend側に注入
機構は無い。したがって:

- **`ROAD_TILE_SOURCE_ID`（路面MVTタイルのソース）の`addSource`へ`attribution`を追加する**
  （開放度はこのタイルのプロパティとして焼き込まれるため、出口はここ1箇所）。文言は
  リンク付き定数`ROAD_TILE_ATTRIBUTION`として`GSI_RELIEF_ATTRIBUTION`と同型に置く。
  例: `土地被覆: <a href="https://livingatlas.arcgis.com/landcover/">Esri, Impact Observatory, Microsoft</a> (CC BY 4.0)`。
  正確な表記はLiving Atlasのアイテムページ「Credits」欄に合わせて実装時に確認する。
- 同じソースには現状OSM（路面本体）・国土数値情報N10/N12（指定路線）・警察庁（事故密度）
  の帰属も未設定のまま積み残っている。本タスクで`attribution`を新設する際に、これらも
  同じ文字列へまとめて載せる（別タスクに分けるほどの量ではなく、同じ1行の中で済む）。
  事故点タイル（`ACCIDENT_TILE_SOURCE_ID`）・POIタイルの未設定は本タスクの範囲外
  （帰属表示の総点検は別途起票する、下記）。
- 材料の`description`・軸の`panel_hint`には「衛星画像の土地被覆データ」程度の説明を
  書くに留め、法的な帰属はAttributionControl側で満たす（既存の`mapLayers.ts`の説明文と
  同じ切り分け）。

### 論点4: breakpointsの較正

風（[T599](T599.md)）は本番の同一条件で走行速度を変えて実測したが、開放度は静的値
なので**分布と参照道路**で較正する:

1. 開発DBに対し、都心〜荒川〜多摩川〜田園を含む小bbox（例: 35.60–35.85N,139.60–139.95E）で
   バッチを径50/100/200mの3回実行し（`algorithm_version`で区別、開発DBのみ）、
   `trees_percent + built_percent`（軸のterms合成と同じ式）のヒストグラム（10%刻み）と、
   参照道路（荒川CR、江戸川CR、多摩川CR、都心の幹線[山手通り等]、住宅街の生活道路、
   街路樹の多い道[表参道等]、田園地帯の農道、海岸沿い[湘南は範囲外のため千葉側]）の
   値を並べる。
2. 参照道路の並び順が体感（河川敷・海岸＞田園＞郊外住宅地＞街路樹の道≒都心）と一致する径を
   採用し、既定値を確定する。一致しない場合は内径（道路面除外幅）の調整を先に試す。
3. 上記分布のパーセンタイルからbreakpointsを決める（例: 下位40%を難易度0、河川敷相当
   [上位5%]を100）。軸スタジオ（下書き軸）で設定し、レンズで地図を見て段階ラベルの
   境界が地形の印象と合うかを確認する。ここまでは開発DBだけで完結する。
4. 本番へ全域バッチを実行→軸を公開→スナップショット更新。
5. 実走の較正（風の強い日に荒川CRを走った体感と、風軸＋開放度軸の合成難易度の比較）は
   公開後の運用で行い、結果を本ファイルへ追記する。開放度軸のbreakpointsは風軸の
   breakpointsとは独立に扱う（風軸を再較正しない）。

### 論点5: 既存の軸追加フロー・データパイプラインとの整合

- **DDLはmigration、行データはAPI**: `0032_add_way_landcover.sql`はテーブル作成のみ。
  軸`openness`は軸スタジオで作り、スナップショットを再ダンプする。
- **デプロイ順序**（migrationは起動時に自動適用されず`scripts/apply_migrations.py`で
  手動適用する。`deploy-backend.yml`は`backend/**`のpushで自動デプロイする）:
  1. 本番DBへ`apply_migrations.py`で0032を適用（空テーブルができるだけで既存コードには
     無影響）。
  2. backendコードをpush（自動デプロイ）。`way_landcover`が空でも`LEFT JOIN`で材料が
     欠損（unknown）になるだけで、軸はまだ存在しないため合成にも影響しない。
  3. 本番でバッチ実行（`--memory`上限付き）、`ROAD_SURFACE_TILE_VERSION`等の版数上げを
     含むコミットをpush。
  4. 軸スタジオで軸を作成・較正・公開、スナップショット更新をコミット。
  逆順（コードより先に軸を作る）は`refresh_axis_definitions`が未知材料でfail-fastする
  ため不可。1と2の間隔が空いても問題は無い。
- **バッチDAG**（`docs/batch-pipeline-dependencies.md`）: ⑩として第3グループ
  （`osm_raw_ways`起点、`road_edges`非依存）へ追加。前提は①のみ。再実行トリガー早見表へ
  「OSM再取込→⑩追随」「年次マップ更新→⑩`--recompute`」を追加。`refresh_derived.py`の
  段としても追加（ラスタパス未設定時の扱いは前節）。
- **ドキュメント同期**（同一コミット）: `docs/modules/backend/static-road-attributes.md`
  （バッチ・テーブル）、`evaluation-scoring.md`（材料2件・`MaterialExtractionContext`）、
  `docs/architecture.md`（新テーブル・新バッチの現状記述）、`docs/batch-pipeline-
  dependencies.md`、`docs/disaster-recovery.md`（ラスタの手動取得手順・
  `refresh_derived.py`の前提）。新規ファイル（`domain/landcover.py`・
  `batch/precompute_way_landcover.py`）はチェック4に従い`static-road-attributes.md`の
  対象ファイル表へ追記する。

## 見送り・DEFER（トリガー付き）

- **予報風速に連動した重みゲート**（`time_scope`と同型の「リクエスト文脈で重みを
  0倍にする」仕組みを、出発時刻の予報風速がしきい値未満なら開放度軸に適用する案）:
  軸間の乗算ではなくリクエスト文脈によるゲートなので線形合成の枠組みは崩さないが、
  「気象条件で静的軸の重みが変わる」という新しい概念になる。トリガー: 開放度軸を公開して
  運用した結果、「毎回手で重みを変えるのが煩わしい」というユーザー判断が出た時点で
  別タスクとして起票する。
- **Edge単位テーブルへの切替**: 論点1の較正で長いwayの内部変動が問題になった場合のみ。
- **帰属表示の総点検**（事故点タイル・POIタイルの`attribution`未設定、Open-Meteoの
  「気象庁の予測に基づく」併記方針の未反映）: 本タスクとは独立の既存の穴。本タスクの
  完了時に別タスクとして起票する（起票しないと次に気づく機会が無い）。
- **建物高さ（PLATEAU等）による遮蔽の高さ方向の考慮**: 土地被覆の2次元割合では
  高層ビル街と低層住宅地が同じ「Built」になる。トリガー: 較正で都心と郊外住宅地の
  区別が付かず実害が出た場合。

## 保留した場合の影響

このタスクを着手しない間、河川敷等の遮蔽物が無い場所での風の体感と評価軸の値との
乖離は残る。ただし風の評価軸自体は正しく計算されている（[T619](T619.md)・[T623](T623.md)で
確認済み）ため、「バグではなく地形要因をモデルが表現できていない」という既知の限界として
運用上は許容できる。
