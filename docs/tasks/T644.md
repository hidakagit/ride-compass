# T644. サーバー側キャッシュの保持方式を精査し、重複した骨格を共通化する

規模L。起票のみ・実装未着手。

## 背景

全エンドポイントのサーバー側キャッシュを一覧にした結果（2026-09-07）、保持方式が
**モジュールごとに独立して育っており、考え方が統一されていない**ことが分かった。

### 1. Redis cache-asideの骨格が4モジュールで重複

`jma_tile_redis_cache`・`dynamic_way_value_cache`・`road_edge_geometry_cache`・
`road_graph_tile_cache`が、いずれも次の同じ骨格を独立に書いている
（`redis_available`/`get_redis_client_or_none`/`record_redis_failure`/
`record_redis_success`の出現回数は順に16・12・16・24）。

```python
if not redis_available(): return <未キャッシュ>
client = get_redis_client_or_none()
if client is None: return <未キャッシュ>
with log_external_call(...) as fields:
    try: ...
    except Exception as exc:
        record_redis_failure(); fields["result"] = "error"; ...
        return <未キャッシュ>
    record_redis_success()
```

`simple_api_client.py: cached_fetch`が、プロセス内`TTLCache`側で同じ問題
（「TTLCache参照→ミス時のみfetch→エラー処理→書き戻し」の重複）を1箇所へまとめている。
Redis側の対応物は`redis_json_cache.py`として既にあるが、**利用者は`jma_tile_index.py`
1つだけ**で、上記4モジュールは移行されていない。

### 2. バイナリの扱いが1モジュールだけ違う

`jma_tile_redis_cache`だけがbase64+JSON包装をしている（`redis_client.py`が
`decode_responses=True`で文字列前提のため）。バイナリ用の接続を1つ用意すれば包装は不要で、
CPUとメモリ（1.33倍）を節約できる（[T636](T636.md)で個別に起票済み。本タスクへ統合するか
判断する）。

### 3. プロセス内キャッシュが2方式

`cachetools.TTLCache`（警報・WBGT・洪水予報・`targetTimes`）と、自前のLRU
（`OrderedDict`＋上限で追い出し。`elevation_client._tile_grid_cache`・
`graph_material_cache._LRUCache`・`gsi_relief_tile_client`の404記憶）が混在する。
後者は件数上限が要件でTTLを持たないため`TTLCache`とは前提が違うが、追い出し処理を
各自で書いている点は共通で、1箇所へ寄せられないかは検討されていない。

### 4. TTLの決め方に共通の基準が無い

2分・10分・15分・20分・30分・1時間・3時間・24時間が混在する。上流の更新間隔に合わせたもの
（アメダス15分＝バッチ10分＋余裕）、キャッシュ共有率で決めたもの（`targetTimes`2分）、
根拠がコメントに書かれていないものが混ざっている。「何に合わせた値か」を型か命名で
表現できると、値の妥当性をレビューできる。

### 5. 「空である」という事実の持ち方が3層に散っている

同じ「取りに行っても得るものが無い」という事実を、層ごとに別の形で持っている。

| 仕組み | 覚えるもの | 減らす経路 |
|---|---|---|
| `jma_tile_redis_cache`の`TILE_NOT_FOUND`（[T605](T605.md)） | 上流に**存在しない**パス（404） | サーバー→上流 |
| `jma_tile_redis_cache`のタイル本体 | 200で返った**空タイルの実体**（334バイト） | クライアント→サーバー（同一`basetime`内のみ） |
| `jma_tile_index`（[T635](T635.md)） | 200で返るが**中身が空**という事実 | クライアント→サーバー（要求自体を発生させない） |

[T635](T635.md)の導入により、**空タイルの実体をRedisへ持つ意味が薄れた**。クライアントが
そのタイルを要求しなくなったためである（実測では運用範囲498枚のうち374枚が空で、
実体としておよそ125KB／base64包装後166KBを20分保持している）。プリウォームがインデックス
生成のために取得する経路では引き続き通るため単純に削除はできないが、「空だと分かって
いるタイルは実体ではなくフラグで持つ」形に寄せられないかは検討の余地がある。

`TILE_NOT_FOUND`（404）と「200＋空タイル」を別々に扱っている点も、上位から見れば同じ
「得るものが無い」という1つの事実であり、統合できるかを含めて整理する。

### 6. ファイルキャッシュの無効化手段が2つ

世代番号（`ROAD_SURFACE_TILE_VERSION`等をキーへ埋める）と`tile_cache.clear_all()`
（[T639](T639.md)の「変わらないデータを更新」ボタン）が併存する。前者は世代を上げた
瞬間から新旧が別キーになり安全だが、後者は全消しのため他レイヤーのキャッシュまで巻き添えに
する。

## 対応方針（案）

方針の正本は[docs/caching.md](../caching.md)（本タスクの起票を受けて整備）。移行はそこへ書いた形へ寄せる。

段階的に進める。一度に全部を書き換えると、キャッシュはどれも「壊れても機能は止まらない」
fail-open設計のため**不具合が表に出ず静かに劣化する**危険がある。

1. **薄い共通ヘルパー**（可用性チェック・ログ・fail-open・JSON包装を内包したget/set）は
   `redis_json_cache.py`として既にある。新規のRedisキャッシュはこれを使う。
2. 既存4モジュールを順に移行する。移行のたびに、そのキャッシュのTTLの根拠をコメントへ
   明示する（上記4の整理を兼ねる）。
3. バイナリ接続の導入（[T636](T636.md)）と、プロセス内キャッシュの方式統一を検討する。
4. ファイルキャッシュの無効化を世代番号へ寄せられるか検討する（`clear_all`が要る場面を
   洗い出す）。
5. 「空である」という事実の持ち方（上記5）を整理する。特に、空タイルの実体をRedisへ
   保持し続ける必要があるかを[T635](T635.md)の実績を踏まえて見直す。

## 保留した場合の影響

新しいキャッシュを足すたびに同じ骨格が写経され、モジュール数が増え続ける。実際、
[T635](T635.md)の実装中に**12個目の同型モジュール（`jma_tile_index.py`）を書き始めて
いた**ことがこのタスクの発端である。fail-open設計のため個々の写経ミス（`record_redis_
failure`の呼び忘れ等）は表に出ず、Redis障害の検知だけが静かに欠ける、という壊れ方をする。
