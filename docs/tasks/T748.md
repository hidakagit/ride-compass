# T748. 手で列挙している母集団を洗い出し、導出へ置き換える 規模M

状態: 完了（2026-09-12。起票は2026-09-11、[design-principles.md](../design-principles.md)構造仕様12の適用）

## 背景

統合レビュー第6回・第7回で「検知できない修正をしてしまう」型の指摘が繰り返し出た。
原因は個別の修正の質ではなく、**検査の母集団が「書いた時点の実例の書き写し」になっている**
ことにある。書いた時点では導出と書き写しは同じ結果を返すため見分けがつかず、
差が観測できるのは新しいメンバーが増えた瞬間＝既に見逃した後になる。

型別の推移がこれを裏づけている。集合を導出に変えた領域（軸の1本道）は指摘が
8件→3件へ減り、手で数えている領域（docs/コメントのずれ、写経）は13→17件・6→13件へ増えた。

## 対応方針

**一度きりの棚卸し**として、母集団を手で書いている箇所を洗い出し、導出できるものを
置き換える。個別に判明済みのものは各タスクが持つ（[T728](T728.md)・[T730](T730.md)・
[T731](T731.md)・[T736](T736.md)・[T740](T740.md)・[T747](T747.md)）ため、
本タスクは**まだ誰も気づいていないものを見つける**ことが目的。

探し方（それ自体を手で列挙しないよう、機械的な手掛かりから入る）:

- テスト・検知器の中のリテラル集合（`== dict[str, float]`のような型の名指し、
  軸id・材料id・ファイル名の配列、`glob("precompute_*.py")`のようなパターン）
- 「◯箇所だけ」「現在はN件」と書いたコメントの近くにある列挙
- 除外リスト（`*_ALLOWLIST`・`AXES_WITHOUT_*`・`continue`で飛ばしている条件）

各箇所について、(a) 導出へ置き換える、(b) 過剰検出のコストが実害を上回るため手動に留める
（理由をその場に書く）、のいずれかへ分類する。

## 完了条件

- [x] 洗い出した箇所が(a)(b)のいずれかへ分類され、(a)は置き換えが済んでいること
- [x] (b)に留めたものは、何を手動にしたかと理由がその場に書かれていること
- [x] 「手書きの一覧の更新漏れを検出するための検査」が新たに増えていないこと

## 棚卸しの結果

機械的な手掛かり（`*_ALLOWLIST`/`*_EXCLUDE`等の定数名、個数を語るコメント、実装中の
リテラル集合、テストの固定件数）でリポジトリ全体を走査し、見つかった母集団を分類した。

### (a) 導出へ置き換えた

**派生データ鮮度台帳の網羅性**。`test_generation_freshness_specs_cover_exactly_the_four_tables`
が、台帳に並ぶ4テーブル名をそのまま書き写して照合していた。これは新しいメンバーが増えた
ときに何も言わない形——「今ある4件が今ある4件と一致する」は、台帳へ載せ忘れた5件目が
あっても通る。母集団を`app/batch/precompute_*.py`側から引き、`ALGORITHM_VERSION`を
宣言するバッチがすべて台帳に載っていることを検査する形へ変えた。

**この置き換えで、誰も気づいていなかった欠落が1件出た**: `precompute_way_curvature.py`が
`ALGORITHM_VERSION`を宣言し、出力先の`way_geometry`は`algorithm_version`列も
`source_osm_import_run_id`列も持っている（台帳へ載る形に作られている）のに、
`GENERATION_FRESHNESS_SPECS`へ登録されていなかった。管理画面「鮮度」タブに
`way_geometry`の行が出ず、蛇行の事前計算が古いままでも誰も気づけない状態だった。
登録して解消した。

**鮮度台帳のテストフィクスチャ3件**。`_counts()`（4テーブルぶんのGenerationFreshness
Countsを並べる）・`_fresh_counts()`（同じくルートのテスト側、`way_landcover`の版数
`"v1-ring10-100"`を書き写していた）・`assert len(report.generations) == 4`。いずれも
`GENERATION_FRESHNESS_SPECS`から組み立てる形へ変えた。書き並べたままだと、台帳へ1件
足した瞬間に`build_freshness_report`の`zip(strict=True)`が落ち、実装ではなくテストの
書き写し漏れを直す作業が発生する（今回まさにそれが起きた）。

**地図オーバーレイのクリック判定**。`buildInteractiveLayerIds`が
`layer.key !== "elevation" && layer.key !== "gradientFill" && !layer.key.startsWith("axis:")`
という除外リストでクリック対象を決めていた。新しいレイヤーは既定でクリック対象になり、
専用ポップアップを持たなければ「カーソルはクリック可能を示すのに実際は何も起きない」と
いう非対称な劣化が静かに増える（T425・T457と同型）。`OverlayLayerEntry`へ
`interactive: boolean`を**必須フィールド**として足し、各レイヤーが定義の場で答える形にした
——TypeScriptがレイヤー追加時に答えを強制するため、除外リスト側の更新漏れという概念自体が
消える。

### (b) 手動のまま残したもの（理由をその場に書いた）

- `REDIS_SKELETON_ALLOWLIST`・`BARE_BASEMODEL_ALLOWLIST`（`scripts/review_checks.py`）:
  例外の理由が個別の事情（バイナリ値・pipeline一括読み書き・骨格そのもの）で、性質から
  導けない。各エントリの隣に理由が書かれており、増えるたびに書く運用が成立している。
- `cache_identity.py`のリビジョン5件（[T747](T747.md)）: 「形は変わらないが読み先の
  データを作り直した」という、コードからは観測できない次元。
- `_MATERIAL_VALUE_COLUMN_EXPR`（`road_graph_repository.py`）: 軸スタジオの値サジェストが
  対応する材料の部分集合。未登録の材料は候補が出ないだけで、静かな誤りにはならない。
- `MATERIAL_COVERAGE_SPECS`＋`MATERIAL_COVERAGE_EXCLUSIONS`: 既に(a)相当。材料カタログ
  全件を回り、どちらにも無い材料があれば`material_coverage_service.py`が実行時に失敗する。
- `refresh_derived.py: _STAGES`: 既に(a)相当。`app/batch/precompute_*.py`をglobで引いて
  登録漏れを検査するテストがある（本タスクで鮮度台帳へ入れたのと同じ形）。

### 見つからなかったもの

「個数を語るコメント」の走査で出た候補は、ほぼ全てが**「ここ1箇所だけに置く」という
集約の宣言**（`jma_tile_content.py`・`hard_filters.py`・`evaluation.py`等）で、数え上げでは
なかった。`jma_amedas.py`の「全1,286観測所」は外部データの実測値で、これは書いてよい側
（[documentation.md](../documentation.md)）。
