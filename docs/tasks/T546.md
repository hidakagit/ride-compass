# T546: タイル材料キャッシュを列指向表現へ変え、デプロイ直後の復元を5秒未満にする（T538の再検討案C1）

状態: 実装完了・本番未検証（2026-09-02。対応方針1〜7を実装し、境界ケース・往復テスト
（実データ規模相当のfixture）・軸編集後のスコア行列一致テストを含む全テストがpass。
その後の本番使い捨てコンテナ検証で判明した`tile_score_matrix_cache`の別不具合
[下記「フォローアップ」節参照]も修正済み。pushはユーザー確認後に別途実施——本ファイル
完了条件のうち「本番の使い捨てコンテナで`materials_ms`5秒未満」の本番実測はこの実装
セッションの作業範囲外として引き継ぐ）

## 背景（ボトルネックの特定、2026-09-02）

T538は`SearchMaterials`（`LeanRoadGraph`＋`dict[str, EdgeMaterialBundle]`）と
`StaticEdgeScoreMatrix`をタイル単位でpickle永続化した（`infrastructure/
tile_persistent_cache.py`）。本番実測はDB冷パス39〜55秒→ディスク経由20.7〜21.5秒で、
完了条件「デプロイ直後の`materials_ms`5秒未満」に届かず、`asyncio.gather`＋
`asyncio.to_thread`によるタイル間並列化も効果が無かった（T538.md末尾）。

開発機でworktreeに残っていた実データのキャッシュファイル（12タイル・256,070 Edge・
108MB）を読み取り専用で計測し、原因を確定した:

| 計測 | 結果 |
|---|---|
| 実ファイル12タイルの`pickle.loads`合計 | 9,218ms（T538.mdのディスク経路全体の実測9,187msとほぼ同値＝ディスク経路の所要時間はunpickle時間そのもの、ファイル読み込みは無視できる） |
| Edge1本あたりの復元コスト | 約36µs。本番の477,320 Edgeへ換算すると約17秒で、本番実測20.7秒と整合（VMは開発機の約1.2倍遅い） |
| 合成1タイル（3万Edge）の`StaticEdgeScoreMatrix`復元 | 2ms（numpy配列のため問題外） |
| 同じ内容を列指向（numpy配列＋idリスト）で保存した場合の復元 | 19ms（約40倍速い） |
| 2スレッド同時`loads` | 逐次比1.01倍（GILで完全に直列化。T538の並列化が効かなかった理由） |
| 1タイルのメモリ常駐量 | 約3KB/Edge（東京駅30kmの1リクエストで約1.4GB。`DEFAULT_MAX_TILES=2,000`の上限は本番コンテナ6GBに対して過大） |

cProfileの内訳は、`_pickle.loads`のC部分が全体の約2割、残り8割が
`dataclasses._dataclass_setstate`（Python 3.12はslots dataclassの復元でオブジェクト
ごとに`dataclasses.fields()`を呼ぶ）とPydantic `BaseModel.__setstate__`
（`ElevationAttribute`・`EdgeAttributeCounts`、1タイルあたり約6万個）だった。
すなわち「pickleが遅い」のではなく「Edge1本ごとにPythonオブジェクトを再構築する
表現そのものが遅い」。ホストのページキャッシュはコンテナ再作成後も残るため、
デプロイ直後でもディスクI/Oは元々ボトルネックではなかった。

## 対応方針（案C1: 材料を列指向テーブル＋edge_id単位の遅延ビューにする）

T536・T537の後、`SearchMaterials.materials`の全件をPythonオブジェクトとして
必要とする消費者はほぼ無い（`road_graph_engine.py`で確認済み）:

- 経路上のEdge（数百本）だけを`get(edge_id)`で引く: `_fetch_elevation_attributes`
  （`elevation_attribute`）・`_aggregate_road_score`・`_build_segment_details`（`surface`）。
- 全件を見る唯一の箇所は`compute_routable_node_ids`（`_get_or_build_node_index`）だが、
  T537でタイル集合キーにキャッシュ済みで、判定に使う情報はスコア行列の
  `is_motorway`/`is_trunk`/`no_bicycle`/`gradient_percent`列と同じもの
  （`compute_hard_filter_excluded`の配列版で導出できる）。
- スコア行列の再構築（軸定義編集で`tile_score_matrix_cache.clear()`された後の経路）は
  `build_static_edge_score_matrix`→`_evaluate_axes_bulk`が辞書入力を要求する。

設計:

1. `domain/attributes.py`へ`EdgeMaterialTable`を追加する。列は`edge_ids`、`surface`、
   `way_tags`（dictのリスト）、標高7列の`float64`配列（欠損はNaN）＋「行の有無」boolマスク、
   件数3列＋マスク、`is_designated`、`data_source`/`calculated_at`。`get(edge_id)`は
   edge_id→行indexの辞書経由で`EdgeMaterialBundle`をその場で組み立てて返し、現在の
   辞書と同じ意味論（way_tagsは`{}`とNoneを区別、`attribute_counts`/`elevation_attribute`は
   行が無ければNone）を保つ。`from_bundles()`と、`_evaluate_axes_bulk`向けの
   `to_legacy_dicts()`を持たせる。正準定義は引き続き`EdgeMaterialBundle`1箇所
   （設計原則4）で、テーブルは軸も材料カタログも知らない（原則3・8に触れない）。
2. DB冷パス（`_get_or_build_tile_materials`のmiss側）は無変更にする。行→bundle→
   スコア行列構築までは今のまま、キャッシュへ入れる直前に`from_bundles()`でテーブル化する。
   ディスクヒット経路はテーブルをそのまま使う。
3. グラフ側はC1では`LeanRoadGraph`を維持し、保存時に列（edge_id/from/to/distance/
   bearing/osm_way_id/highway、node_id/lat/lon/osm_node_id）へ分解、復元時に
   `LeanNode`/`LeanEdge`を作り直す（合成計測で118ms/タイル）。`geometry`は常に空リスト
   （`_topology_rows_to_road_graph`参照）のため列に持たない。
4. `tile_persistent_cache.py`は無変更（pickleの中身が配列群になるだけ。pickle protocol 5
   でnumpy配列はほぼゼロコピーで復元されるため`np.savez`へ変える必要は無い）。
   `TILE_MATERIALS_CACHE_VERSION`を"2"へ上げる（保存形式の変更）。
   `TILE_SCORE_MATRIX_CACHE_VERSION`は据え置き。
5. `compute_routable_node_ids`はテーブルを受け取る形へ変えるか、スコア行列の配列から
   導出する形へ変える（後者が望ましいが、`_get_or_build_node_index`の引数にスコア行列を
   通す変更が要る。着手時にどちらか選ぶ）。

   **判断（着手時、2026-09-02）: 後者（スコア行列の配列から導出）を採用した。**
   `road_graph_engine.py: _build_search_graph`は元々`compute_hard_filter_excluded`で
   `hard_filter_excluded`配列（コスト配列を`inf`にするための0次フィルタ除外判定、
   `score_matrix.edge_ids`と同じ行順）を1回だけ合成済みで、`compute_routable_node_ids`が
   従来行っていた「`materials.get(edge_id)`→`is_edge_allowed`」というEdgeごとの判定は、
   この配列の対応するインデックスが`False`かどうかと完全に同値。呼び出し元
   （`_build_search_graph`→`_SearchGraph.edge_ids`/`hard_filter_excluded`→
   `_get_or_build_node_index`→`compute_routable_node_ids`）がこの配列をそのまま渡す形へ
   変更したことで、`compute_routable_node_ids`は`EdgeMaterialBundle`/`EdgeMaterialTable`
   への依存を完全に無くせた——テーブルを受け取る案（前者）だと、materials自体は
   ディスク復元済みで軽量でも、bbox全体ぶんの`.get(edge_id)`ループ（Edgeごとの
   `EdgeMaterialBundle`再構築）が残ってしまい、案C1の主眼（Edge単位の材料復元を経路上の
   Edgeだけに限定する）と矛盾する。後者は「コスト計算と同じ0次フィルタ判定を2箇所で
   別々に計算する」という以前の設計（cost用の`compute_hard_filter_excluded`とnode index用の
   `is_edge_allowed`が独立した実装だった）も解消し、両者のドリフトリスクを構造的に無くす
   副次効果があった。
6. `tile_persistent_cache.get`に「ファイル読み込みms・unpickle ms・バイト数」を分けて
   記録し、リクエスト単位の1行INFOサマリへ載せる（`docs/logging.md`の方針。以後の
   回帰をログ1行で追えるようにする）。
7. 並列度の設定: 既存の`asyncio.gather`＋`to_thread`は残し、`config.py`へ
   `tile_cache_load_max_concurrent`（既定`min(4, os.cpu_count())`）を追加して
   semaphoreで縛る。**ただしC1で残るCPUコストは`LeanEdge`再構築のPythonループなので、
   コア数を増やして効くのはI/Oとnumpy部分だけ**。コア数で線形に速くなるのは案C2
   （後述）まで進めた場合で、この点は`routing-engine.md`へ明記する。

見込み: 復元は列指向約20ms＋オブジェクト再構築約118msの約140ms/タイル。16タイルで
開発機約2.2秒、本番換算約2.5〜3秒（完了条件5秒未満に余裕あり）。メモリ常駐量は
材料部分が約10分の1になる。

## 比較した他案と採否（未起票のものはその理由）

| 案 | 判定 |
|---|---|
| A. `ProcessPoolExecutor` | 不採用。子で復元した結果を親へ返す際に再pickle→親で再unpickleとなり、同じ`__setstate__`コストが親のメインスレッドへ直列で戻る。返す表現が安く復元できる形なら最初からプロセスは要らない。6GB上限内でメモリ複製も増える |
| B. `LeanEdge`/`LeanNode`へ`__reduce__`を定義するだけ（形式はpickleのまま） | 単独では不採用。合成計測でグラフ部分は253→118ms/タイルだが、Pydanticの`ElevationAttribute`/`EdgeAttributeCounts`は`model_construct`でも約7.5µs/個で残り、20秒→10〜12秒止まり。C1の項目3はこの案の考え方を含む |
| C2. グラフも完全列指向（`LeanEdge`オブジェクト自体を持たず、`LazyRoadGraph`をindex配列から直接構築） | 見込み約0.5秒、復元がnumpyのみになりGILを解放するためコア数で並列化できる。`RoadGraphLike`の消費者（`build_lazy_road_graph`・`_reverse_traced_edges`・区間詳細のフォールバック等）に広く手が入るため**C1の本番実測後に必要なら別番号で起票する**（C1で完了条件を満たす見込みのため現時点では起票しない） |
| D. 起動時バックグラウンド予熱 | 遅延を隠すだけで短縮しない。現状の36µs/Edgeでは全域予熱がDB同居の2コアを長時間占有し、3KB/Edgeでは全域常駐も不可能。C1の後なら「直近に使ったタイル集合を`backend/data`へ記録し起動時に先読み」が数秒で済むため意味が出る（対象選定は地理的ヒューリスティックではなく最後に使われた順の記録で十分）。**C1の本番実測後、体感上まだ必要なら別番号で起票する** |
| E. バッチ側（T539のpresplitと同じ全域走査）でキャッシュファイルを事前生成 | 「そのタイルの初回」のDB冷パス40〜55秒を解消する別の段。C1で保存形式が小さくなってから検討する。**未起票（C1完了後に必要なら起票）** |
| Redis・uvicorn `--workers`・blue/green | 効果無し。Redisは同じunpickleコスト、複数workerは各プロセスが別々に冷える、blue/greenは`--network=host`構成で不可（`deploy-backend.yml`のコメント参照） |

## 実装リスク

- 意味論のずれ: way_tagsの`{}`とNoneの区別、`attribute_counts`/`elevation_attribute`の
  「行なし=None」をNaNやマスク列で表現し直すため、既存テスト（`EdgeMaterialBundle`/
  `SearchMaterials`を参照する13ファイル）が依存する挙動を壊しうる。全Edgeについて
  `table.get(edge_id) == 元のbundle`が成り立つ往復テストを実データ相当のfixtureで必須にする。
- 軸編集直後の経路: `to_legacy_dicts()`経由で構築したスコア行列が、bundleから構築した
  行列と一致するテストが必要（ずれるとルートの軸別色分けだけが変わる）。この経路の
  `ElevationAttribute`477k個の構築（数秒）は、元々Edgeごとの抽出ループが走る重い経路で
  DB冷パスと同じ頻度でしか通らないため許容する。
- 空タイル: T536で本番発覚した0件タイル混在ケースで、shape `(0, k)`の配列を正しく扱う
  境界テストを最初から入れる。
- 精度: 標高・件数は`float64`のまま保存する（元値は丸め済み）。
- 版数更新: C1を載せたデプロイ直後は各タイルの初回だけDB冷パスが1回走る（現行と同じ
  一回限りの費用）。完了条件の本番計測は「2回目のコンテナ」（T538.mdのA→B手順）で行う。
- T538がまだmasterへ未pushの場合、本タスクはT538のpush後に着手する（同じファイル群を
  編集するため）。

## フォローアップ: `tile_score_matrix_cache`のディスクキャッシュが毎起動で無駄に再構築される不具合（2026-09-02）

上記の実装完了後、コーディネーターセッションによる本番Oracle VM使い捨てコンテナ検証
（コンテナA=キャッシュ書き込み→コンテナB=同じホスト側ボリュームを引き継いだ新規
コンテナ）で、以下の非対称が発覚した:

```
_build_search_materials_from_tile_cache tiles=16 memory=0 disk=16 db=16 disk_read_ms=469.4 disk_unpickle_ms=5358.9 disk_bytes=126679302 materials_ms=14407
```

材料（`graph_material_cache`、16タイル）はディスクキャッシュに正しくヒットする一方、
スコア行列（`tile_score_matrix_cache`、16タイル）は毎回`db`（ディスクキャッシュを
使わず`build_static_edge_score_matrix`で再計算）になっていた。コンテナ内で該当ファイルを
直接pythonから読むと正常に読み込めること（`source=disk`）、エラー・警告ログが一切
出ていないことから、ファイル自体は無傷で「見えなくなっている」わけではないと判明した。

**原因（T536時点から存在、T546が新たに作ったものではない）**: `refresh_axis_
definitions`（`main.py`のlifespanから**アプリ起動のたびに必ず1回**呼ばれる、
軸編集APIの成功直後にも呼ばれる）が、軸定義の内容が実際に変わったかどうかに関わらず
無条件で`tile_score_matrix_cache.clear()`（メモリ・ディスク両方を即座に削除）を
呼んでいた。このためコンテナBは、自身の起動シーケンス内で（Aが書き込んだ直後の）
スコア行列ディスクキャッシュを自ら削除してから最初のリクエストを処理していた——
コンテナ内での手動確認時にはBが既にスコア行列を再構築・再永続化した後だったため
ファイルは正常に見えた。`materials_ms`14.4秒のうち約6割（8.6秒程度）がこの不要な
再構築に費やされていたと見られる。`benchmarks/bench_t538_persistent_cache.py`は
`refresh_axis_definitions`を1回しか呼ばない（「プロセス再起動」をメモリキャッシュの
みクリアして模す設計）ため、この不具合をローカルでは検出できていなかった。

**修正**: `axis_registry_meta.revision`（DB1行、軸定義の追加・更新・削除のたびに
インクリメントされる単調増加カウンタ。従来は将来のマルチプロセス対応・監査用の記録に
留まり実際の無効化には未使用だった）を使い、`tile_score_matrix_cache.py`に
`sync_disk_cache_with_axis_revision(revision)`を新設した。ディスクへ最後に永続化した
時点のrevisionを予約タイル座標（`_REVISION_MARKER_TILE = (-1, 0, 0)`）へ記録し、
`refresh_axis_definitions`から渡された現在のrevisionと一致すればディスクキャッシュを
温存する（メモリだけクリア）。不一致（軸定義が実際に変わった）または未記録（初回
デプロイ）ならこれまでどおり`clear()`する。`axis_registry_service.py: refresh_axis_
definitions`はこの関数を呼ぶよう変更し、`AxisRegistryMetaRow`のdocstringも実態に
合わせて更新した。

**検証**: ローカルdev DBで、コンテナA/B/Cを別々のPythonプロセスとして再現した
（各プロセスの起動時に`refresh_axis_definitions`を1回呼ぶ、実際のアプリ起動と同じ
順序）。
- 修正前: A（cold, db=24）→B（新規プロセス、`disk=12 db=12`——スコア行列だけ再構築）。
- 修正後: A（cold, db=24）→B（新規プロセス、`disk=24 db=0`、`materials_ms=3531`）。
  さらに`axis_registry_meta.revision`を実際にインクリメント（軸編集を模す）した後の
  C（`disk=12 db=12`——材料は温存、スコア行列だけ正しく無効化）→D（revision不変、
  `disk=24 db=0`）で、正当な軸編集は引き続き正しく検知・反映されることも確認した。
- 新規テスト: `tests/test_tile_score_matrix_cache.py::TestSyncDiskCacheWithAxisRevision`
  （6件、`sync_disk_cache_with_axis_revision`の単体テスト）・
  `tests/test_axis_registry_service.py`の2件（`refresh_axis_definitions`経由の統合
  テスト、revision不変時の温存／revision変化時の無効化）。
- `pytest backend/tests -q -m "not postgis"`: 1335 passed（+6）。`-m postgis`: 238
  passed（+2）。

## 引き継ぎ（本番実測）

本番の使い捨てコンテナでの`materials_ms`5秒未満の実測・A→B手順の再確認は、この実装
セッションの作業範囲外（pushを行わず、本番へのデプロイもしていない）。push・本番検証は
ユーザー確認後に別セッションで行う。上記フォローアップ修正により、ローカル計測では
`materials_ms`が更に短縮している（3.5秒台）ため、本番でも完了条件（5秒未満）へ近づく
見込み。
