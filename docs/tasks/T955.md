# T955: 材料の冷パスが160秒かかり、バッチのたびに最初の利用者が待たされる

状態: 着手（2026-09-19起票）

## 背景

本番でルート生成に174秒かかった（2026-09-19 17:48、`req:b7f19819cf4d`）。

```
generate(destination) prepare_ms=165428 select_ms=6659 evaluate_ms=470 total_ms=173898
_build_search_graph edges=542999 materials_ms=160469 lazy_graph_cached=False
  missing_axis_edges=542999 missing_axis_distance_ratio=1.000
```

**探索も評価も速い**。2分半後の同条件は`materials_ms=964`・`total_ms=6336`で、
冷えているかどうかで**174秒 ↔ 6.3秒**。

`docs/tasks/T747.md`が記録する材料の冷パスは29〜45秒規模で、いまは108〜160秒。
世代を上げるのは日常運用（バッチを流すたびに起きる）ため、**バッチ後に最初にその範囲を
見た利用者が3分待つ**。

**周回でも同じ**。材料は探索方式より手前の段階で、周回30kmの生成も116.6秒だった
（`via-node候補を打ち切りました`のWARNINGは目的地ルート特有だが、遅さとは無関係）。

## 冷パスの内訳（本番、2026-09-19）

`materials_ms`はタイルごとの材料構築の合計で、内訳は出していない。段階的に測った。

| 測ったもの | 所要 |
|---|---|
| 1タイル（z12/3638/1612、42,144区間）のDB実行時間（`EXPLAIN ANALYZE`） | **1.9秒** |
| 同じクエリのSQL＋転送（WAN越し。本番はlocalhostなのでもっと速い） | 6.9秒 |
| 行→`EdgeMaterialBundle`（`ElevationAttribute`・`EdgeAttributeCounts`はPydantic） | **18.8秒**（1件445µs） |
| `EdgeMaterialTable.from_bundles`（列指向への詰め替え） | 1.5秒 |

**DBは1.9秒しか使っていない。** 残りはPython側で、しかも**18.8秒かけて作ったオブジェクトは
1.5秒かけて列へ詰め替えた直後に全部捨てられる**。本番（DBと同一VM）で1タイル8〜10秒、
16タイルで160秒というログの数字と整合する。

### 外部（国土地理院）は関係しない

標高だけは値を作るときに外部から取るが、それは`precompute_elevation_attributes`バッチの
話で、探索側は`elevation_attributes`を`LEFT JOIN`で読むだけである。本番は
`elevation_attributes`が`road_edges`と同数（5,065,850行）で未計算が無く、
`road_graph_engine._fetch_elevation_attributes`の「未計算の区間だけその場で取る」経路も
発火していない。**160秒に外部呼び出しは含まれていない。**

## 原因: 冷パスだけが列指向化から取り残されている

`_get_or_build_tile_materials`のコメントが、そう書いたうえで残している。

```python
# DB冷パス自体（行→bundle構築）は無変更にし、キャッシュへ入れる直前に
# from_bundles()で列指向テーブル化する
```

ディスクからの復元は`EdgeMaterialTable`（列指向）で**Edge数に依存しない**形になっている
（[T546](T546.md)）。同じ問題がDBから作る経路に残っていて、そこだけEdge数に比例する。

## 対応方針

**行から直接`EdgeMaterialTable`を組む。** ただし列の並びを2箇所に持たない
（[design-principles.md](../design-principles.md)構造仕様4、`EdgeMaterialTable`自身が
「正準定義は引き続き`EdgeMaterialBundle`1箇所」と宣言している）。

- `EdgeMaterialTable`へ**行を1つずつ受け取るビルダー**を持たせ、列の確保と書き込みを
  そこだけが知る形にする。
- `from_bundles`はビルダーへbundleを流す薄い口にする（既存の呼び出し元は変えない）。
- リポジトリは同じビルダーへ**SQLの行をそのまま**流す口を持つ。`EdgeMaterialBundle`・
  `ElevationAttribute`・`EdgeAttributeCounts`を作らない。
- `get_edge_materials_batch`（bundleを返す既存の口）は残す——
  `_build_search_materials_uncached`が使っている。

見込み: 18.8＋1.5秒 → 2秒程度。1タイル10秒→2〜3秒、16タイル160秒→30〜50秒。

**これでも遅い。** ウォームアップ（世代を上げた直後に主要エリアを先に焼く）は別に要る。
根本側を先に削っておけばウォームアップ自体も軽くなるため、順序はこちらが先
（ユーザー判断）。

## 記録: 調査の途中で誤った整理をした

「標高は他の属性と違って外部から取る」ことを**取得のコストの表**として書いたため、
「ルート生成のたびに外部を叩いている」と読める形になった。正しくは、外部が要るのは
**DBへ入れるとき（バッチ）だけ**で、**読むときは4つとも同じくSQL**である。
ユーザーの「DEMをSQLで引く形にできれば速いのでは」という問いは、この誤った表からの
自然な推論だった。
