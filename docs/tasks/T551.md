## 背景

目的地ルート（`generate_via_waypoints`、`destination`指定、T365）は現在、起点→目的地の
軸コスト最適路を1件だけ返す。周回のN件化（T531）と同じ部品で、目的地ルートも
`max_routes`件の互いに異なる候補を返せるようにする。

周回は「目的地＝起点のvia-node問題」であり、目的地が起点と同じ場合だけ前向き木と後ろ向き木が
同じ道を往復するため復路にretraceペナルティ付きA\*が要る。目的地が別の場所なら2本の木の
経路は自然に別の道になるので、この特殊処理が丸ごと落ち、候補ごとの探索がゼロになる。

## 対応方針（via-node方式）

1. 起点からの前向き木（T531と同じ`dijkstra(csr, indices=origin, return_predecessors=True)`）
   と、目的地からの**後ろ向き木**（CSRの転置に対する同じDijkstra。転置構造と順列も
   タイル集合キーで`search_graph_cache`へキャッシュ）を各1回。bboxは既存の
   `_bbox_covering_points`（目的地ルートは周回より小さい）。
2. 全ノードについて経由路の長さ`len_f + len_b`と平均difficulty
   `((cost_f + cost_b)/(len_f + len_b) − 1)/P`をベクトル計算し、長さが最良路の
   `ALTERNATIVE_MAX_STRETCH`（初期値1.3倍）以内のノードを候補にする。
3. 平均difficulty昇順に並べ、前向き経路と後ろ向き経路が同じEdgeを共有するノード
   （行って戻る形）と、採用済み候補との重複率が閾値超のノードを飛ばしながら
   `max_routes`件採る。最良路そのものは上位に必ず入り、その経路上の全ノードは重複率100%で
   1件に潰れる。
4. 採用分だけhydrate→`evaluate_loops`→`overall_difficulty`昇順→id採番。

探索コストは木2本（開発機合成グリッドで各0.14〜0.26秒）で候補数に依存せず、現行1件生成と
同等かむしろ改善が見込める（増えるのは評価件数分のみ）。

## 決定事項・スコープ

- **距離の意味**: 目的地ルートは`distance_km`をbbox見積りと経由地範囲ガードにしか使って
  いない。v1は「最良路に近い代替案」（伸び率フィルタ）とする。「目的地まで30kmで行きたい」
  という遠回り指定（周回と同じ目標±tolフィルタ）はフィルタ条件の差し替えだけで実現できる
  ため後続で判断する。
- **経由地を伴う目的地ルート**: 経由地が1つ以上あるとレグごとに代替案が組合せで増えるため、
  v1は「起点→目的地のみ」をN件対象とし、経由地指定時は従来通り1件のまま。
- **id・タブ表示**: `route-destination`は固定idで、page.tsxが`NON_DIRECTIONAL_ROUTE_IDS`
  の完全一致で「方向」を付けない判定をしている。`route-destination-00`形式にして前方一致へ
  変え、タブラベルへ順位番号を入れる（T531のタブ変更と揃える）。
- `max_routes`はT531で新設するリクエストパラメータをそのまま使う（目的地ルートでも有効に
  なる旨をdocstring・docs/modulesへ明記）。

## 実装（2026-09-04）

対応方針どおり実装した。

1. **転置CSR（後ろ向き木の基盤）**（`domain/routing.py`）: `build_csr_structure`・
   `build_search_graph_statics`へ`reverse: bool = False`を追加した（別関数にせず
   既存関数へ分岐を持たせる案を採用——CSR構築のロジック自体はキー式`u*node_count+v`→
   `v*node_count+u`の1点しか変わらないため）。`build_shortest_path_tree`はCSR構造の
   向きを一切気にしない実装のため無変更のまま転置CSRを渡せる。新規に
   `tree_path_edge_indices_to_source`（後ろ向き木でtargetから目的地までの経路を
   target→目的地の順のEdge index列で返す。転置CSR上の`predecessor[X]=P`が実グラフの
   `X→P`という辺を表すため、既存`tree_path_edge_indices`とはEdge検索の引数順が逆で
   最後の反転が不要）を追加した。
2. **転置CSRのキャッシュ**（`infrastructure/search_graph_cache.py`）: 4本目のタイル
   集合キーLRU`_reverse_search_statics_cache`（`get_reverse_search_statics`/
   `set_reverse_search_statics`）を追加し、`invalidate_tile_set`/`clear`の対象へ含めた。
3. **`select_via_nodes`**（`services/road_graph_engine.py`）: 起点からの前向き木
   （既存の`context.statics`をそのまま使う）と目的地からの後ろ向き木
   （`_get_or_build_reverse_search_statics`で構築・キャッシュ）を各1回求め、
   全Nodeの合成コスト・経由路長をベクトル計算してALTERNATIVE_MAX_STRETCH（1.3）
   以内のNodeへ絞り込む。平均difficulty昇順（最良路のNodeは常に先頭へ回し、伸び率の
   許す範囲でより低difficultyの経路が上位に来ても「最良路は必ず結果に含まれる」を
   ランキングと独立に保証する）に並べ、`select_diverse_by_overlap`で「行って戻る形」
   （前向き・後ろ向きの経路が同じ物理区間を共有するNode、`_loop_edge_lengths_by_
   physical_segment`で進行方向を無視して判定）と重複率超過のNodeを除外しつつ
   `max_routes`件採る。候補ごとの追加探索が発生しないため、選定結果の`TracedLoop`が
   そのまま最終候補になる（周回の`trace_loop_from_turnaround`に相当する再探索ステップが
   無い）。`_RoadGraphContext`へ`tile_set`フィールドを追加し、`select_via_nodes`が
   タイル集合キーで転置CSRを引けるようにした。
4. **`RouteGenerator`**（`services/route_generator.py`）: `LoopRoutingEngine`
   Protocolへ`select_via_nodes`を追加。`generate_via_waypoints`は`destination`指定かつ
   経由地が無い場合だけ新設の`_generate_destination_routes`（prepare→select_via_nodes→
   evaluate_loops→overall_difficulty昇順→`route-destination-00`形式へid振り直し）へ
   分岐し、経由地を伴う場合は従来どおり`trace_loop`による単一経路のまま
   （id・direction_labelの上書きも無変更）。`max_routes`引数を新設し、
   `api/routers/routes.py`から素通しする。
5. **frontend**（`page.tsx`）: `NON_DIRECTIONAL_ROUTE_IDS`を`route-waypoints`のみに
   絞り、`route-destination`プレフィックスの前方一致判定を別に持たせた。目的地ルートは
   「方向」は付けないが、複数件になりうるため順位番号は付ける（経由地ルートは順位番号も
   付けない）。

## 追加実装: 候補件数入力欄の目的地モード対応（2026-09-05）

実装時（2026-09-04）の変更対象ファイルはbackendとpage.tsx（id前方一致・タブラベル）に
絞っており、`RouteForm.tsx`の候補件数入力欄は対象に入れていなかった。この結果、backendは
`max_routes`件生成できるようになった一方、目的地モードでは`RouteForm.tsx`側が候補件数入力欄
自体を常に非表示にしたままだったため、ユーザーがUIから件数を指定する手段が無かった
（ユーザー報告「目的地をN件選択できる改修って終わってる？選択できない」で発覚）。

対応: `RouteForm.tsx`に`maxRoutesRelevant = routeMode === "loop" || waypointCount === 0`を
導入し、周回モードに加えて経由地の無い目的地モードでも候補件数入力欄を表示・検証するよう
変更した（経由地を伴う目的地ルートはbackendが引き続き常に1件へ固定するため対象外のまま）。
併せて`page.tsx`の`generatedConditions`へ`maxRoutesRelevant`を追加し、`conditionsDirty`判定
（候補件数変更の検知）も同じ条件へ揃えた。周辺の「目的地モードはbackendが候補件数を常に
1件へ固定し無視する」という誤った前提のコメント（`page.tsx`・`RouteForm.tsx`）と
`docs/modules/frontend/route-settings-and-results.md`の記述を是正した。

`RouteForm.test.tsx`に経由地の有無で入力欄の表示・検証が切り替わるテストを追加し、
`page.test.tsx`の既存回帰テスト（改善計画T557、経由地を伴う目的地モードでの空欄フォール
バック）は経由地なしケースとは別の経路になったため、経由地を追加する新しいテストヘルパー
（MapViewスタブの`onWaypointAdd`ボタン）を使う形へ分離した。

実機確認（2026-09-05、Browserペイン、dev backend＋frontend、東京都北区付近）: 目的地モードで
地図をタップして目的地を設定→候補数欄に「3」を入力→ルート生成すると、タブが
「1. 目的地ルート 2.2 km」「2. 目的地ルート 2.0 km」「3. 目的地ルート 1.8 km」の3件になり、
地図上にも周回経路が表示された。`docs/tasks/T551.md`「完了条件」の「実機確認: 目的地指定で
N件が地図上で互いに異なる道を通り、max_routesが効く」のうちUIから件数を指定できることは
これで満たした。本番同等条件での`total_ms`計測は引き続き未実施（デプロイ後に別途行う）。
