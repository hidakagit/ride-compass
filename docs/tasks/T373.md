# T373. chipRow/estimatedFlatRowをJSポインタドラッグによる手動スクロールへ切替（アイコン上からのドラッグでもスクロール可能に） 規模S（2026-08-27完了）

状態: 完了


- 背景: T371完了後もユーザー報告「スクロールは相変わらずできない」「アイコンの上に
  指でスクロールするのはできないの？」が続いた（2026-08-27）。T372（並行セッション、
  同日）が地図マーカー側の同種のtouch-action漏れを発見・修正したのと同時期に、
  こちらは地図チップ（`MapOverlayControls.tsx`）側で別の原因を特定した。
- 根本原因: `.iconChip`（各アイコンボタン自身）が既に`touch-action: none`を持っていた
  （地図とのピンチズーム競合を避ける既存対策、実機フィードバック起因）。touch-actionは
  子孫方向へ制限が積み重なる仕様のため、タッチの起点がボタン自身だと祖先
  （`.chipRow`/`.estimatedFlatRow`）側にT370で付けた`pan-y`/`pan-x`は一切効かない
  ——T371時点ではこの優先順位を見落としていた。
- 対応: ブラウザのネイティブタッチスクロールに頼るのをやめ、`MapOverlayControls.tsx`に
  `useDragScroll`（pointerdown/pointermove/pointerup/pointercancelを自前で拾い
  scrollLeft/scrollTopへ反映する汎用フック）を新設し、`.chipRow`（縦）・
  `.estimatedFlatRow`（横）双方へ適用した。touch-actionはブラウザの「ネイティブな」
  スクロール処理だけを無効化するもので、pointerイベント自体の配信は妨げないため、
  `.iconChip`の`touch-action: none`と共存できる。ドラッグと判定した場合（移動量が
  閾値[6px]を超えた場合）は続けて発火するclickイベントをキャプチャフェーズで止め、
  意図しないON/OFF切り替え・展開トグルを防ぐ。CSS側は`.chipRow`/`.estimatedFlatRow`
  自身のtouch-actionも`pan-y`/`pan-x`から`none`へ変更し（JS側で完全に代替したため
  ネイティブ処理と二重に効かないように）、`overscroll-behavior: contain`も追加した
  （ユーザー報告「スマホだと縦スクロールしようとしてページ再読込を誤動作してしまう」
  ＝pull-to-refreshへの対応、touch-action: noneだけでも防げるはずだが念のための
  多重防御）。
- 検証: 実タッチ入力ではなく、合成`PointerEvent`をアイコンボタン自身へ`dispatchEvent`
  する形で検証した（`el.scrollLeft`への直接代入では実際の操作を検証したことにならない
  と気づき、T371の反省を踏まえて改めた）。アイコン上から40pxドラッグ→scrollLeft/Topが
  正しく追従し、直後のclickが抑止されることを確認。6px未満の小さな移動では抑止されず
  通常のタップ（ON/OFF切り替え）が機能することも確認。実際にスクロール可能な幅/高さを
  超えるオーバーフローが存在する条件（横: 7軸タイル、縦: ビューポートを縮めてchipRowの
  max-heightを実際に超えさせた状態）の両方で確認済み。`el.setPointerCapture`は
  合成イベントでは`NotFoundError`を投げるため（実タッチでは正常に動作する想定）
  try/catchで握りつぶす防御も追加した。frontend全体691件成功、tsc/eslintクリーン。
- 未解決の限界: 実機（本物のタッチ/マウスドラッグ）での最終確認はこのセッションの
  実行環境（Browserペインが実際には表示されない）ではできていない。合成イベントでの
  検証はロジックの正しさを裏付けるが、実デバイスでの体感（慣性スクロールの有無等）は
  次回ユーザーに確認いただきたい。
