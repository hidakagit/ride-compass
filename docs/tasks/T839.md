# T839. 派生データの作り直しを、管理画面から要求できるようにする

規模L。
状態: 着手（2026-09-14、ユーザー要望「管理者画面からそのままバッチ実行できない？　実サーバに
入ってコマンドを叩ける条件は限られている」から）

## 背景

[T836](T836.md)で「鮮度」タブは**何が作り直し待ちか**と**次に打つ1コマンド**まで出せるように
なったが、そのコマンドを打つにはVMへSSHで入る必要がある。入れる条件は限られており、
気づいてから直すまでの間が空く。

## 制約（先に調べた。ここが設計を決める）

**backendのプロセス内でバッチを走らせてはいけない。** `refresh_derived.py`を本番（関東本土
全域、road_edges約500万件）へメモリ上限なしで実行したところ、⑦`precompute_elevation_
attributes`の途中でVM全体のメモリが枯渇し、**SSH・HTTPとも6時間14分応答不能**になった実績が
ある（[disaster-recovery.md](../disaster-recovery.md)「既知のリスク・対策」）。対策として
「本番で重いバッチを実行する際は必ず`docker run --memory=<上限>`を指定する」が運用ルールに
なっている。backendコンテナは`--memory=6g`のため、その中で走らせれば最悪コンテナごと
OOM killされ、**サービス全体が止まる**。

補足: 検証実績の「④〜⑨全段階成功、196.4秒」は東京都心の小bbox（ways 41,555）での数字で、
関東本土全域（way 133万）ではない。時間・メモリともこの数字を外挿しない。

一方、**実行そのものはweb依存だけで可能**である。バッチ専用依存（rasterio/pyproj）を実際に
使うのは⑩`precompute_way_landcover`だけで、それも関数内の遅延importになっている
（[T630](T630.md)の修正）。`--skip-landcover`を付ければ残りの段はbackendイメージで動く
（土地被覆はラスタが手元データのため、管理画面からは回せない）。

## 対応方針

ユーザー選択（2026-09-14）は**フラグ方式**——管理画面からVMへ権限を渡さない。

1. 管理画面は「実行要求」をDBへ1行書くだけ（`POST /api/admin/batch-jobs`、Basic認証）。
   同じ種別がqueued/runningなら拒否する（多重起動の防止）。
2. VM上のsystemd timerが定期的に要求を拾い、**`docker run --rm --memory=<上限>`**で
   バッチを実行して結果をDBへ書き戻す。backendコンテナにはdocker socketを渡さない。
3. systemd unit/timerの設置は`deploy-backend.yml`が冪等に行う（同ワークフローは既に
   VM上で`sudo`付きの自己修復処理をしている——CORS_ALLOWED_ORIGINSの追記）。
   **VM側の手作業セットアップを増やさない。**
4. 管理画面は要求の状態（待ち／実行中／完了／失敗、終了コード、ログ末尾）を表示する。

**上限を超えたらコンテナだけがOOM killされ、jobはfailedとして残る**——ホストは無事という
形にする（安全に失敗する）。

## 段階

- 段階1: テーブル・要求API・状態API・ランナー・systemd設置（backend側一式）
- 段階2: 「鮮度」タブからの実行と状態表示（frontend）
