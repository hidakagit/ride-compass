# T687. 軸単体で経路を評価できるよう、得点の隣に物理量を出す 規模M

状態: 完了（2026-09-09）

## 背景

ルート結果の軸の値（0〜100）だけでは、その軸単体で経路の良し悪しを判断できない。
実際に走ってストレスのあった経路が停止密度10と出て「楽に見える」という報告があった
（2026-09-08）。

原因は目盛りの引き方ではなく、**同じ生値が区間とルートで意味が変わる**こと。

| 生値 | 区間として見ると | ルート平均として見ると |
|---|---|---|
| 0.8回/km | 静かな裏道（幹線は4.8〜7.4回/km） | 32kmで26回止まる＝多い |

区間の分布に合わせて目盛りを引くとルート値は低く出る。ルートの分布に合わせると区間側で
幹線がすべて満点に潰れ、ルーターが最悪の道を選り分けられなくなる。**1つの目盛りで両方を
正直にはできない。** さらにルート値は重みを上げるほどルーターがそれを最小化するため、
目盛りをどう引いても低い値へ戻る（[T655](T655.md)の再較正で実証: 4.1→2.9）。

「他の軸（自転車インフラ91.5・車の圧迫感59.3）を見れば悪い経路だと分かる」という説明は、
**軸を独立して扱えるという設計の否定**になるため採らない（ユーザー判断、2026-09-09）。

## 対応方針

得点（相対評価）の隣に**絶対の事実**を併記する。「約26回」と言われれば、他の軸を見ずに
判断できる。

検討した3案のうち、ユーザーが3案目（単位が定まる軸だけに絞って併記する）を選んだ:

| 案 | 内容 | 判断 |
|---|---|---|
| 1 | 他の軸（自転車インフラ・車の圧迫感）と併せて読む案内を足す | 却下。軸を独立して扱う設計の否定 |
| 2 | ルート値専用の目盛りをもう1本引く | 却下。同じ軸が2つの得点を持ち、区間とルートで数字が食い違う |
| 3 | **単位が定まる軸に限り、得点の隣に生値を単位付きで併記する** | 採用。単位を持たない合成軸には何も出さない |

## 実装

### 生値の単位（`domain/axis_display.py: raw_value_unit`）

`BreakpointLinearShape`で、重み0以外の全termの材料が材料カタログ上で同じ`unit`を持つとき
だけその単位を返す。`CategoricalShape`・単位を持たない材料・異なる単位の混在（＝合成軸）は
`None`。判定は材料カタログから導出するため、軸ごとの分岐・対応表を持たない。

重みが負の項が混じる軸も対象外にした（和が物理量の符号を反転したものになる）。

さらに、**単位が揃っているだけでは和の意味は保証されない**。開放度の`樹木% + 建物%`は
単位こそ%で揃うが、母数の違う割合どうしの和は何も表さない。物理でいう示量／示強の区別が
必要で、足せるのは回・件・個のような個数と、それを同じ距離で割った密度だけ。
`MaterialSpec.additive`として材料側に持たせ、**項が2つ以上のときだけ**この条件を課す
（項が1つならそもそも和ではないため。勾配の「平均3.2%」は意味を持つ）。

この条件を入れる前は、開放度が「重みが負」という別の理由でたまたま弾かれていただけで、
正の重みで単位だけ揃う無意味な軸は作れてしまう状態だった。

現在の公開軸での結果:

| 軸 | 生値の単位 |
|---|---|
| 停止密度 | `回/km` |
| 事故密度 | `件/(km・年)` |
| 勾配 | `%` |
| 車の圧迫感（内部軸の合成）・夜間（真偽値）・路面（カテゴリ） | なし（何も出さない） |
| 開放度 | なし（重みが負、[T689](T689.md)） |

### 材料カタログの単位の欠落を埋めた

この判定を入れて初めて、`stop_count_per_km`・`intersection_count_per_km`・
`accident_count_per_km_year`・`maxspeed_kmh`が`unit`を持っていないことが分かった。
ラベルには`停止密度(回/km)`のように単位が書かれているのに、`MaterialSpec.unit`は
空文字のままだった（`unit`は「無次元・真偽値・カテゴリ値だけが空文字」という契約）。
これを埋めたことで事故密度が`件/(km・年)`を出せるようになった。

なお本番の停止密度軸は[T655](T655.md)で作り直した`poi_*_per_km`版で、これらは最初から
`回/km`を持っており、単位の欠落の影響を受けていなかった。開発DBと
`backend/fixtures/axis_definitions_snapshot.json`が較正前の構成のままだったため、
作業中は「埋めないと停止密度が出せない」と誤って判断していた。

### 生値の算出（`domain/axis_definitions.py: axis_raw_value_array`）

折れ点を通す前の`terms`重み付き和を配列で返す（`_breakpoint_raw_total_array`）。全材料が
欠損している行はNaN。単位が定まらない軸・**リクエストごとに変わる材料（風）を参照する軸**は
対象外——静的スコア行列は`weather=None`で組み立てるため、後者は生値がNaNにしかならない。

### 運搬（区間 → ルート）

`BulkAxisEvaluation.axis_raw_arrays` → `StaticEdgeScoreMatrix.axis_raw_values`（列の並びは
`raw_axis_ids`。`axis_ids`とは別の並びになるため独立して持つ）→
`LegCostArrays.axis_raw_arrays` → `RouteSegmentDetail.axis_raw_values` →
`merge_axis_raw_values`（`merge_axis_difficulties`と同じ距離加重平均）→
`RouteCandidate.axis_raw_values`。

`StaticEdgeScoreMatrix`はディスクキャッシュへpickleされる`frozen`/`slots`
dataclassのため、新しい2列は**末尾へ既定値付きで**足し、`_SCORE_MATRIX_REVISION`と
`SCORE_MATRIX_COLUMN_SIGNATURE`を同時に上げた（列を足して世代を上げ忘れると、旧世代の
pickleから復元した際に末尾の列が欠落する。[T655](T655.md)で本番障害の実績あり）。

### 表示（`components/RouteAxisProfile/axisRawValue.ts`）

`GET /api/axis-catalog`が新しく返す`raw_value_unit`と、`RouteCandidate.axis_raw_values`を
突き合わせて表示文を組み立てる。単位が`◯◯/km`のときだけ候補の走行距離を掛けた実数を
続ける（`%`のような量は距離を掛けても意味を持たない）。

```
停止密度  10  0.80回/km・約26回
```

「10点」だけでは楽な経路に見えるが、「32.5kmで約26回止まる」なら他の軸を見ずに判断できる。

### 「回」は重み付きの回数（判断済み）

生値は`terms`の重み付き和のため、停止密度の「約26回」は重み込みの値であって実際に
26回止まるという意味ではない（現行の較正では踏切×1.5・一時停止×0.3）。それでも
そのまま「約26回」と出す。重みは「踏切は信号1.5回分きつい」という**体感の重み付け**で
あり、走る人にとっては実回数より体感回数の方が判断材料として適切なため。

判別が材料カタログの`unit`・`additive`という手書きメタデータに依存することも許容する。
機械的に導けるのは「足せる量どうしか」までで、その和が軸の名前と一致するかまでは
判定できない。軸を作る人が意味の通る材料を選ぶ前提を置く。

## 残課題

生値を出せるのは単位が揃い重みが正の軸だけで、車の圧迫感（内部軸の合成）・夜間
（真偽値材料）・開放度（重みが負）は対象外のまま。[設計原則](../design-principles.md)11を
これらの軸はまだ満たしていないため、[T689](T689.md)として分離した。
