# T818. 周回モードの候補一覧にも所要時間の比較材料（最速の印・+N分）を出す

規模S。
状態: 完了（2026-09-14。統合レビュー第8回のP1、2026-09-13起票。本番実機で確認）

## 背景

[T790](T790.md)段階Bで基準線の定義を「距離最短」から「**所要時間最短**」へ変え、候補タブに
「基準線から何分余計にかかるか」（`+12分`）を出す設計にした。ところが基準線の印`is_fastest`は
**目的地モードでしか付かない**（`services/route_generator.py:572`）。

そのため周回モードの一覧は`app/page.tsx:1912`の`最短`——`shortestDistanceRouteId`が決める
**距離**最短の印——だけを出し、`最速`も`+N分`も一度も出ない。本番（`77055ad6`）で周回30kmを
8件生成して確認したところ、タブは`1 29.2km · 33`／`5 26.6km 最短 · 47`で、時間の比較材料は
どこにも無かった。

結果として、同じ列に「最速」（時間）と「最短」（距離）という**2つの最上級がモードによって
出し分けられ**、利用者は何と何を比べているのか分からない。T790が「軸設定に沿ったルートを走る
対価を候補一覧で見せる」ために入れた`+N分`が、**主用途である周回モードでは機能していない**。

## 対応と結果

**ユーザー判断: 「最速」＋「+N分」に統一し、距離の「最短」はやめる**（2026-09-14）。
同じ列に時間と距離の2つの最上級が並ぶと何と比べているのか読めなくなるためで、
行あたりに増える文字は最大1つに収まる。

- 基準線を`fastestRouteId`——**一覧の中で`estimated_duration_seconds`が最小の候補**——
  から決める形にした。backendの`is_fastest`は見ない（目的地モードでしか付かず、
  主用途の周回モードでは基準線が一度も決まらない）。同着は先に来た方（並び順は総合難易度の
  昇順なので、易しい方）。
- タブは「順位番号 距離km」を常に持ち、基準線の行へ`最速`、他の行へ`+N分`を添える。
  目的地モードで順位番号の位置を`最速`に置き換えていた出し分けは無くなり、両モードで
  同じ形になった。
- 距離の`最短`と`shortestDistanceRouteId`は撤去した。

  ```
  周回30km・8件生成（変更前 → 変更後）
    1  29.2km          ▮▮▮    33        1  29.2km  +8分    ▮▮▮    33
    5  26.6km  最短    ▮▮▮▮   47        5  26.6km  最速    ▮▮▮▮   47
  ```

### 見送り（今後もやらない）

`is_fastest`を周回モードでも付ける案（対応方針3）は見送る。付けると
`route_generator.py`の先頭固定が周回へも効いて並び順が変わるが、**表示側だけで
「何と比べた+N分か」は成立する**ため、並び順を動かす理由が無い。`is_fastest`は引き続き
backendが目的地モードで付ける先頭固定の印として残り、`lib/routeSplice.ts:
insertByDifficulty`がその1件を難易度順の外として扱う。

## 検証結果

- **効いていることの確認**: `fastestRouteId`を`is_fastest`基準の実装へ戻すと、
  `routeTabLabel.test.ts`の5件と`page.test.tsx`の「周回モードでも「最速」と超過分を出す
  （backendのis_fastestは付かない）」が落ちる。
- `page.test.tsx`は実物の`Home`を描画してタブのアクセシブル名を見る。周回2件
  （6,300秒・5,820秒）で`2 26.6km 最速`・`1 29.2km +8分`が出て、`最短`を含むタブが
  1つも無いことを確認している。
- `npx vitest run` → 142ファイル 1350 passed、`tsc --noEmit`は既存の`LayoutProps`のみ、
  `eslint src`は既存の警告1件のみ。
