# T818. 周回モードの候補一覧にも所要時間の比較材料（最速の印・+N分）を出す

規模S。
状態: 未着手（統合レビュー第8回のP1、2026-09-13。本番実機で確認）

## 背景

[T790](T790.md)段階Bで基準線の定義を「距離最短」から「**所要時間最短**」へ変え、候補タブに
「基準線から何分余計にかかるか」（`+12分`）を出す設計にした。ところが基準線の印`is_fastest`は
**目的地モードでしか付かない**（`services/route_generator.py:572`）。

そのため周回モードの一覧は`app/page.tsx:1912`の`最短`——`shortestDistanceRouteId`が決める
**距離**最短の印——だけを出し、`最速`も`+N分`も一度も出ない。本番（`77055ad6`）で周回30kmを
8件生成して確認したところ、タブは`1 29.2km · 33`／`5 26.6km 最短 · 47`で、時間の比較材料は
どこにも無かった。

結果として、同じ列に「最速」（時間）と「最短」（距離）という**2つの最上級がモードによって
出し分けられ**、利用者は何と何を比べているのか分からない。T790が「軸設定に沿ったルートを走る
対価を候補一覧で見せる」ために入れた`+N分`が、**主用途である周回モードでは機能していない**。

## 対応方針

1. `lib/routeTabLabel.ts: fastestDurationSeconds`を、backendの`is_fastest`に依存せず
   **一覧内の最小`estimated_duration_seconds`**から導く形にする（両モードで成立する）。
2. 周回モードでも所要時間最小の候補へ印を付ける。「最速」（時間）と「最短」（距離）を
   同じ列に併記すると読みにくいため、**どちらを出すか／両方出すかはユーザーと詰める**
   （`docs/design-principles.md`「主用途は走行中のスマホ、情報量を増やさない」）。
3. backendの`is_fastest`を周回モードでも付けるかは別の判断。付けると
   `route_generator.py:584-587`の先頭固定（`max_routes >= 2`のとき）も周回へ効くため、
   並び順が変わる。**今回は表示側だけで閉じる案を第一候補とする。**
