# T537: 探索用グラフ・索引（LazyRoadGraph/routable集合/空間索引/Node対索引）をタイル集合キーでキャッシュする

状態: 未着手（2026-09-02起票、[T522](T522.md)「評価ロジック全体の再点検」で判明）

- 背景: `RoadGraphEngine.prepare`は毎リクエスト、タイルキャッシュから結合したグラフに
  対して`build_lazy_road_graph`（957ms）・`compute_routable_node_ids`（726ms）・
  `build_node_spatial_index`（201ms）・`_build_node_pair_index`（165ms）を作り直しており、
  温パスのprepare約2.4秒（本番VM実測、東京駅30km・Edge 477,320件）のほぼ全てを占める。
  これらはタイル集合と0次フィルタ（`hard_filters`・`max_average_grade_percent`）だけで
  決まる純粋な派生物で、bboxは起点と距離から機械的に決まるため、同じ起点はもちろん
  近隣の起点でも同じタイル集合を共有する。
- 対応方針（2案、着手時に選ぶ）:
  - 案a（実装最小）: `frozenset(タイル集合)`（routable集合は＋0次フィルタ引数）を
    キーにしたプロセス内LRUへ4つの派生物を載せる。`graph_material_cache`と同じ寿命・
    無効化（軸定義変更は無関係、材料再取込はプロセス再起動）。メモリは同時に数件で
    足りる。
  - 案b（根本）: タイル読込時にNode/Edgeを1つのグローバルな`PyDiGraph`へ差分追加し
    （タイル境界をまたぐEdgeはedge_idで重複排除）、リクエストは結合を一切行わず
    起点・経由地の索引引きと探索だけを行う。空間索引・Node対索引もタイル単位で持ち
    結合する。T536のコスト配列も同じEdge索引に揃える。`graph_material_cache`のLRU
    退避と整合させる設計が必要。
  - どちらの場合も`_build_node_pair_index`は、逆回り候補の経路上のEdgeだけに対する
    遅延引き（`graph.edges`から`(to,from)`を逆引き）で代替できるため、全Edge分の
    索引自体を廃止してよい。
- 関連: [T536](T536.md)（独立に着手可能。両方入れば温パスは
  prepare約0.4秒＋探索約0.7秒＋評価約0.4秒＋ジオメトリ取得の見込み）。
- 完了条件: 本番同一条件で`prepare`の索引・グラフ構築ログ（`graph_ms`・`index_ms`）が
  2回目以降のリクエストで合計500ms未満、既存の`test_road_graph_engine.py`・
  `test_route_generator.py`が無修正でpass、`docs/modules/`の該当設計書を同一コミットで更新。
