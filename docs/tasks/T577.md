# T577: 材料ごとの欠損割合を管理画面で可視化する

状態: 完了（2026-09-04起票・同日実装。push・本番デプロイ・本番での実測は別セッションの判断に委ねる）

## 背景

2026-09-04、[T552](T552.md)対応方針4（surface_q軸の取込側既定値補完の要否判断）の
検討中に、材料`surface`（OSMのsurfaceタグ）が本番DB全体で85.0%欠損していることが
判明した。同じ調査で`elevation_attributes`（gradient軸の材料元）も88.4%欠損して
いたが、こちらは⑦precompute_elevation_attributesの未完走という運用上の問題
（[T575](T575.md)・[T576](T576.md)参照）で、根本原因が全く異なる2つの欠損が
同時に見つかったことになる。

いずれも発見手段は手作業のSQLクエリだった。`/api/material-catalog/{material_id}/values`
（既存API）は材料が取りうる値の一覧を返すのみで、NULL/未取得の割合は一切扱っていない。
管理画面・APIのどちらにも、材料ごとの欠損割合を継続的に把握する仕組みが無い
（surfaceに限らず全材料が対象外）。

## 方針（ユーザー判断、2026-09-04）

欠損データについて、取込側で既定値を推測して埋める（対応方針4的なアプローチ）のでは
なく、**欠損の実態を可視化し、埋めるかどうかの判断は利用側（軸定義・評価ロジック）へ
委ねる**方針を採る。この可視化の仕組みが本タスクの対象。

イメージ: 管理画面に材料一覧（`material_catalog.py`のレジストリが既に持つ全材料）と、
各材料の欠損割合（該当primary_attribute_idを持つEdge/Way総数に対する、値が
NULL/未取得のEdge/Wayの割合）を表示する。

## 対応方針・設計判断（2026-09-04）

1. **「欠損」の定義は元データ（タグ・派生テーブル行）の不在とし、評価上の扱いを併記する**。
   [T552](T552.md)の計測で分かったとおり、評価パイプラインの「材料が欠損したEdge比率」は
   材料によって0%になる（タグ不在を「非該当」という確定値として扱う設計のため）。その
   数値だけ見せると「タグは無いが評価できている」材料と「タグは無く評価もできない」材料の
   区別が付かない。そこで欠損数は常にタグ/行の不在で数え、`missing_semantics`
   （`"unknown"`=不明値として評価対象外、`"definite"`=確定値として評価）を別列で示す。
   この値は`MaterialSpec.bool_default`からは導出しない（`bool_default="nan"`でも
   `bicycle_infra_flags`がタグ不在をFalseとして扱う自転車インフラ系5材料があり、
   実際の扱いはextractor実装で決まるため、宣言テーブル側に明示する）。
2. **母集団はWay（`osm_raw_ways`全行）とEdge（`road_edges`全行）の2種**。OSMタグ由来の
   材料はWay単位で数える（T552の手作業SQLと同じ母集団、走査も軽い）。Edge単位の派生
   テーブル由来（`elevation_attributes`・`edge_attribute_counts`）はEdgeで数えるが、
   派生テーブルの`edge_id`が`road_edges`へのFK（ON DELETE CASCADE）であることを使い、
   派生テーブル側の行数だけを数えて「値ありEdge数」とし、500万行規模の`road_edges`との
   JOINを省く。Way側は全材料を`count(*) FILTER`で1回の走査にまとめる。
3. **材料id→判定式は宣言テーブル（`MATERIAL_COVERAGE_SPECS`）＋対象外一覧
   （`MATERIAL_COVERAGE_EXCLUSIONS`、理由付き）**。`MATERIAL_CATALOG`の全材料がどちらか
   一方に必ず載ることをテストで強制し、材料追加時の登録漏れを検知する。判定式は
   `_ROAD_SURFACE_TILE_MVT_SQL`の正規化式と揃える（整合性テストあり）。対象外は
   `wind_penalty`（動的計算）・`oneway`（NOT NULL列）・`designation`系4材料
   （行の有無がそのまま確定値）。
4. **認可はBasic認証必須（`/api/admin/`配下）**。既存の`GET /api/material-catalog`系は
   認可不要だが、本APIは`osm_raw_ways`/`road_edges`の全表走査を伴い、認可なしに公開すると
   繰り返し呼ぶだけでDBを圧迫できてしまう。管理画面`/admin`からのみ使う想定のため、
   `axis_admin.py`/`debug_admin.py`と同じ`require_admin_basic_auth`で保護し、フロントは
   同一オリジンのroute handler（`proxyToBackendAdmin`）経由で呼ぶ。DB例外は
   `axis_admin.py`と同じく503へ変換する（診断用APIのため空レポートへ倒さない）。
5. **サーバー側キャッシュは持たない**。管理画面側で「集計する」ボタン押下時のみ実行し、
   `computed_at`を表示する。バッチ実行直後に古い値が見える混乱を避けるため、TTL
   キャッシュより「毎回その場で数える」方が診断用途には素直と判断した。本番規模
   （Way約133万・Edge約500万）での所要時間は未計測のため、backendセッションはルート生成用の
   長い`command_timeout`（180秒）、フロントの転送タイムアウトは90秒にしてある。

## 開発DBでの実測（2026-09-04）

開発DB（東京都心南部、Way 86,642件・Edge 319,530件）に対し集計1回=1.05秒。本番
（Way約133万・Edge約500万、およそ15倍）へ単純に外挿すると15〜20秒程度で、フロント側の
転送タイムアウト90秒・backendの`command_timeout`180秒に収まる見込み。開発DBでの主な値:
surface 60.8%（`unknown`）・gradient_percent 57.8%（`unknown`）・maxspeed_kmh 84.4%・
smoothness 99.7%・no_lit 90.8%（`definite`）・stop/intersection/accident 4.0%・highway 0.0%。

## 残課題・引き継ぎ

- 本番での実測（所要時間・実際の欠損割合）は未実施。T552の手作業SQL（surface 85.0%、
  elevation_attributes 88.4%）と同じ数値が管理画面で再現できることを、本番デプロイ後に
  「材料」タブで確認する。所要時間が90秒（フロント側転送タイムアウト）に近づく場合は、
  route handler（`COVERAGE_PROXY_TIMEOUT_MS`）とbackendの`command_timeout`の両方を見直す。
- 欠損割合は件数ベース（距離加重ではない）。T552の`missing_axis_distance_ratio`（距離加重）
  とは母集団も物差しも異なるため、両者の数値を直接比較しないこと。距離加重版が必要になった
  場合は`WayMaterialCoverageSpec`へ`ST_Length`ベースの集計列を足す形で拡張できる。
