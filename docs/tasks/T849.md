# T849. 鮮度台帳が、バッチの対象外の行を「未計算」と数え続ける

規模S〜M。
状態: 完了（2026-09-14。ユーザー報告「鮮度台帳をつくり直しても未計算が残っている」から）

## 背景

本番で`refresh_derived`を完走させても`road_edges.curvature_deg_per_km`の未計算が
5,047,354件中2件残る。これは作り直せば消える取りこぼしではなく、**バッチが永久に対象外に
している行**である——`precompute_edge_curvature`の対象は`distance_m > 0`に絞られ（長さ0では
度/kmを測れない）、台帳側の判定は`curvature_deg_per_km IS NULL`のため、計算されない行を
未計算として数え続ける。

結果として台帳は「すべて最新」へ到達できない。常に「N件が作り直し待ち」と出続ける表示は、
そのうち誰も読まなくなる。

way単位では同じ問題が既に解かれている（`WayGeometryRow`が「行が無い＝未計算、列がNULL＝
算出不能」の2状態を持つ）。road_edgesの列は1つしか無く、その区別を表せない。

## 対応方針

ユーザー指示（2026-09-14）は**個別対応をやめて標準化すること**——「バッチのSELECTと鮮度台帳の
SELECTを揃えるように標準化してほしい。1つ1つの個別・特別対応は望まない」。

`CompletenessSpec`へ`in_scope`（担当バッチが処理できる行の条件）を足し、**この宣言を唯一の
情報源にする**。

- 台帳: 未計算の集計を`(in_scope) AND (uncalculated)`で絞る。母集団は全件のまま
  （「全体のうち何件か」を読むための数のため。ユーザー選択）。
- バッチ: 対象を選ぶselectを`text(SPEC.in_scope)`から組み立て、関数名も`target_stmt`へ揃える。
- 更新SQL（`road_graph_repository.py`）も同じ宣言から組み立てる。

条件の書き写しは`test_owner_batches_select_their_targets_from_the_declared_scope`が弾く。

### 他の宣言も点検した（ユーザー指摘「これは他も揃ってる？」）

- `elevation_attributes`: バッチは行が無いEdgeを全件対象にする。対象外の条件は無い（`in_scope`
  は既定の`TRUE`）。残る48件は「対象だが値が出ない」で別の問題（[T850](T850.md)）。
- `road_nodes.degree`: 単一UPDATEで全行が対象。対象外の条件は無い。`degree = 0`が未計算と
  次数0を区別できない件は従来どおり`note`で開示する。
- 世代比較側（`GENERATION_FRESHNESS_SPECS`）は派生テーブルに在る行だけを見るため、バッチが
  対象外にしたwayはそもそも行を持たず数えられない。`way_geometry`は測れないwayにも
  `algorithm_version`付きの行を作る（列だけNULL）ため、こちらも整合している。

## 実装メモ

- `in_scope`の既定は`TRUE`。全行が対象のバッチは何も書かなくてよく、`target_stmt`も要らない
  （テストはその場合を飛ばす）。
- ガードの限界: バッチ側が`text("distance_m > 0")`と**同じ文字列**を手で書いた場合は通る。
  値は一致しているため即座の害は無いが、片方だけ変えたときのずれは防げない。

## 検証結果

- `pytest -q -m "not postgis"` → 1944 passed、`pytest -q -m postgis` → 286 passed、
  `ruff check app tests` → All checks passed。
- 実DBでの確認: 長さ0のEdgeを1件作ると、母集団2件・未計算1件（測れる方だけ）になることを
  `test_curvature_completeness_ignores_edges_the_batch_cannot_measure`で固定した。
- ガードの実効性: バッチ側の対象条件を`RoadEdgeRow.distance_m > 0`（宣言を使わない書き写し）
  へわざと戻すと`test_owner_batches_select_their_targets_from_the_declared_scope`が落ちる。
  戻して再度通ることを確認。
