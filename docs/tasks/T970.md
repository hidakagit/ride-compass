# T970. データの置き場所と形を決め直す 規模L

状態: 実装中（2026-09-20起票）。段階Dで本番を新しい形で作り直している。[T969](T969.md)点検0を対話で実施した結果の設計と決定を、
ここへ積む。実装は未着手。

## 背景

何をDBへ持つかの基準がどこにも無く、置き場所が「そのとき動いていた運用状態」で決まって
きた。生データ・派生データ・管理データ・運用の記録のうち、基準があるのはキャッシュだけ
だった（[docs/caching.md](../caching.md)）。

β版は関東全域、正式版は全国へ広げる。現状の形のまま全国化すると147GiBのボリュームに対し
約139GB（95%）で入らない。

## 決定1: 外部ソースの生データをDBへ置く条件

次を**すべて**満たすものだけ、生データをDBへ持つ。

1. **手動で取り直さなければ最新が反映されない**（目安: 1年以上陳腐化しない）
2. **母集団を自分で確定でき、その量が容量に見合う**
3. **手元の別の生データから作れるものを、二重に持たない**

判定順は2→3→1ではなく、どれか1つでも落ちれば持たない。

| 対象 | 判定 |
|---|---|
| OSM・事故統計・指定路線・標高（DEM）・土地被覆（LULC） | DBへ生データを置く |
| **基礎地図（OpenFreeMapのベクタタイル）** | **条件1と条件3で落ちる**（[T976](T976.md)） |
| 気象（雨雲・アメダス・警報・MSM・洪水・暑さ指数） | 条件1で落ちる。キャッシュのまま |
| GSI色別標高図・標高タイル（dem_png） | 条件3で落ちる。自前のDEMから描く |

**訂正（2026-09-20）**: 基礎地図を当初この表で「DBへ置く」側に入れていたが、誤りだった。
条件に当てて確かめていない。実際には2つ落ちる。

- 条件1: OpenFreeMapは[公式ページ](https://openfreemap.org/)で週次のプラネット配布を
  明記しており、タイルは週次で焼き直される。1年どころか数週間で陳腐化する
- 条件3: OpenFreeMapのデータ源はOSM（公式ページに明記）で、そのOSMを我々は別に持っている。
  道路網を二重に持っている

条件3は同じ表の`dem_png`を落とすのに使っている基準であり、基礎地図にだけ適用していなかった。
容量の影響は関東のz14タイル15,065枚で約8.8GB（開発DB実測614KB/枚からの換算）。対応は
[T976](T976.md)。

Redisは現状維持（外部への負荷を肩代わりするものだけ）。利用を広げない。制約が厳しくなる
とき、またはβ版を終えるときに実状と合うか再精査する。

### 絞り込み（母集団の宣言）

取込プロファイルをOSM専用から全ソース共通へ広げ、runごとに丸ごと記録する。**全国化は
bboxと行条件の指定を変えて取り直すだけ**にする。

- OSMの行の絞り込みは現状維持（通行しうるhighway種別＋自転車可のfootway/path）
- **OSMのタグの絞り込みは廃止**（許可リストをやめ、全タグを持つ）
- ラスタのズームは**元データの分解能から導く**。UIの都合で決めない
  （DEM5A=5mメッシュ→z15、LULC=10m画素→z14）。
  配信元がそれ以上を持たないことは実測で確認済み（z16以降は404）

## 決定2: 生データの共通フォーマット

```sql
CREATE TABLE source_runs (
    run_id      bigserial PRIMARY KEY,
    source      text        NOT NULL,
    status      text        NOT NULL,
    started_at  timestamptz NOT NULL,
    finished_at timestamptz,
    origin      jsonb       NOT NULL,   -- 取得元URL・ファイル名・配信元のタイムスタンプ
    profile     jsonb       NOT NULL,   -- そのとき適用した絞り込みの宣言を丸ごと
    counts      jsonb       NOT NULL
);

CREATE TABLE source_features (
    source      text     NOT NULL,
    natural_key text     NOT NULL,
    run_id      bigint   NOT NULL REFERENCES source_runs (run_id),
    geom        geometry(Geometry, 4326) NOT NULL,
    attrs       jsonb    NOT NULL DEFAULT '{}',
    payload     bytea,
    PRIMARY KEY (source, natural_key)
) PARTITION BY LIST (source);
```

- `attrs`は「解釈できる属性の袋」、`payload`は「解釈の要る配列実体」（ラスタ画素・
  OSMの参照ノードid列・タイル本体）
- ラスタは**タイル1枚＝1行**。これで点・線・面が同じ骨格に乗る
- パーティションにするのは、**生データの置き換えを`DETACH`＋`ATTACH`にする**ため。
  これが「生データを差し替えたら下流が洗い替わる」の入口になる

**事故統計の属性は袋（`attrs`）で持つ**。実列にすると4.4倍安いが（開発DBで実測:
袋345MB／実列78MB、303,455行換算）、ソースごとにDDLが要り「同一フォーマット」が成立
しなくなる。差は全国で2.8GBで、見込み総量に対して2.1%。

## 決定3: road_edges の形

**この節は決定11が差し替えた（2026-09-20）。** 「区間1本＝1行、有向グラフはメモリ上で
作る」は誤りで、有向の構造をDBへ戻した。以下のDDLと容量の試算は採らない。判断の経緯は
記録として残す。

```sql
CREATE TABLE road_edges (
    osm_way_id    bigint   NOT NULL REFERENCES osm_raw_ways (osm_way_id) ON DELETE CASCADE,
    segment_index smallint NOT NULL,
    from_node_id  bigint   NOT NULL REFERENCES osm_raw_nodes (osm_node_id),
    to_node_id    bigint   NOT NULL REFERENCES osm_raw_nodes (osm_node_id),
    geom          geometry(LineString, 4326) NOT NULL,
    distance_m    real     NOT NULL,
    bearing_deg   real     NOT NULL,
    source_run_id bigint   NOT NULL REFERENCES source_runs (run_id),
    PRIMARY KEY (osm_way_id, segment_index)
);
-- GiST索引は持たない（空間の絞り込みは osm_raw_ways 側で行う）
```

変更点と根拠:

- **区間1本＝1行**（逆向きの行をやめる）。逆向きペアはジオメトリの完全な逆順で、距離も
  同じ（標本975件すべて）。向きが持つ情報は方位（+180°）・勾配（符号反転）・通行可否
  （`osm_raw_ways.direction`）で導ける。有向グラフは`build_road_graph`がメモリ上で作る
  実行時の構成物であり、表が両向きを持つ必要はない
- **識別子を複合自然キーへ**。`edge_id`は`way-{数値}-seg{数値}-{fwd|bwd}`という文字列で
  23.1バイト、ノードは`osm-node-{数値}`で20.0バイト。文字列を組み立てているのは
  `domain/graph.py`の3行だけで、**解析している箇所はbackend・frontendとも0件**
  （不透明なトークンとして扱われている）。ノードが`osm_raw_nodes`への本物のFKになる
- **`highway`を持たない**。`osm_raw_ways.highway`の複製
- **`updated_at`を`source_run_id`へ**。現在の`road_edges`は系譜列を1つも持たず、OSMを
  取り込み直しても古いと判定できない
- **GiST索引を持たない**。空間の絞り込みは親wayのGiSTで行い、`osm_way_id`（新主キーの
  先頭列）で区間を引く

GiSTを外す判断の実測（本番、3地点×z12〜16の15タイル。過剰取得＝way経由で引いたときの
行数の比）:

| z | 過剰取得 | 所要時間 |
|---|---|---|
| 12（グラフ読み込みの粒度） | 1.00〜1.03倍 | 同等（1件だけ+19%、他は速い側） |
| 14〜16（路面タイルの粒度） | 1.08〜1.37倍（絶対数は数十行） | 同等かway経由が速い |

wayのGiSTは1,333,000件でroad_edgesの5,067,000件より小さく、索引が小さいぶん有利に働く。
**バッチ4本（POI割り当て・事故割り当て・土地被覆リング・標高）の実行計画は未確認**で、
実装時に確かめる。

## 決定4: 第1層（生データだけを入力にする派生）の形

### 粒度の整理

| 層 | 点 | 線（粗） | 線（細） | 面 |
|---|---|---|---|---|
| 生データ | osm_node / accident | osm_way / designation | — | dem / lulc |
| 派生 | `node_materials` | `way_materials` | `edge_materials` ＋ `road_edges` | **持たない** |

**wayは面ではなく粗い線**で、区間と同じものの粗さ違いである。面の派生（`tile_materials`）は
不要——面の生データを読む出口は「タイル表示（生ラスタから直接描く）」と「材料（線ごとの
リングで集計）」の2つだけで、どちらも面の中間結果を必要としない。

### 表の構造がバッチの写しになっていた

way単位の計算済み値が4表・4バッチに分かれ、`osm_raw_ways`を4回走査し、主キー索引を4つ
（196MB）持ち、系譜を4セット×1,333,039行持っていた。内容が違うのではなく、書いた
バッチが違うだけである。3本は`run_chunked_precompute`＋`select(OsmRawWayRow.osm_way_id)`＋
`CHUNK_SIZE=5_000`という同一の骨格で、同じ母集団を走っていた。

**粒度ごとに1表にする。**way単位の材料が増えても列が1本増えるだけで、表もバッチも
増えない（構造仕様8「1本道の追加点」）。

### 点データの歪み

点を持つ表が5つあり、母集団が重なっていた（実測）:

- `osm_raw_pois`の75%（317,465件）は`osm_raw_nodes`にもある同じOSMノード
- `road_nodes`（1,871,229）は`osm_raw_nodes`の完全な部分集合
- `osm_raw_pois.kind`は取込時の分類器の出力＝**生データの表に派生が混ざっている**

タグを全保持すると決めたので、分類は取込から外して派生側へ移せる。生データは
`source_features(source='osm_node')`へ統合する。

### 「交差点」の定義が2つあった

| | 数え方 | 使う側 |
|---|---|---|
| `raw_intersection_nodes` | `osm_raw_ways.node_ids`の隣接頂点を数える | way粒度の`intersection_count`（地図） |
| `road_nodes.degree` | `COUNT(DISTINCT 隣接グラフ頂点)` | 区間粒度の`intersection_count`（評価） |

実測: 後者は前者の厳密な部分集合で、30,399件が食い違う（うち26,512件は
`road_nodes.degree = 2`）。食い違うノードから3,000件を抜いて測ると、**接続する区間は
平均5.82本（両向きなので約2.9本）なのに、異なる隣接グラフ頂点はちょうど2.00**——
2本の枝が同じ次の交差点へ向かうと`DISTINCT`で潰れる。

つまり**同じ「交差点数」という材料が、地図と評価で違う値になっている**。評価側は26,512
箇所を数え落とす。根本は、グラフの位相としての次数（探索が使う）と、そこに集まる道の
本数（材料が使う）という別のものに同じ列を使っていること。

**`branch_count`（集まる道の本数）1つへ統一**し、way粒度・区間粒度の両方がこれを使う。
グラフの位相としての次数は保存しない（探索はメモリ上でグラフを組むときに数える）。

### way粒度を残す理由

路面タイルは z12〜15 で、区間粒度へ切り替わるのが z14。**way粒度が使われるのは z12・z13
の2段だけ**。区間から集約して作れるかを本番で測った（way数はA/Bで完全一致し、同じ母集団を
作れることは確認済み）:

| 地点 | z | 現行 | 区間から集約 |
|---|---|---|---|
| 都心 | 12 | 33.1 ms | **1,276.3 ms** |
| 都心 | 13 | 10.9 ms | 27.7 ms |
| 郊外 | 12 | 22.2 ms | 62.9 ms |
| 山間 | 12 | 8.7 ms | 10.0 ms |

z13は問題ないが、z12の都心が重い。本番の路面タイル生成は z12 で1.23秒なので約2倍になる。
**way粒度は「z12のタイルのため」に残す**——これが唯一の理由で、他の理由は無い。
（都心z12だけ非線形に遅く、プランが切り替わっている可能性がある。1件だけの観測。）

`divided`と`designation`はそもそも区間版が無く、道1本の性質なのでway粒度が正しい。

### 区間の材料が欠けたときのway値へのフォールバックは廃止する

`edge_landcover`の充足率は 2,399,882 / 2,611,210 区間 = **91.9%**。残り8%はway値
（道全体の平均）を受け取り、隣の区間と違う定義の値になる。way粒度を残すこととは別問題で、
**区間側を100%埋めてフォールバックの経路自体を無くす**。

### 定義

```sql
CREATE TABLE node_materials (
    osm_node_id         bigint   PRIMARY KEY REFERENCES osm_raw_nodes (osm_node_id),
    kind                text,                             -- 分類器の出力（今の osm_raw_pois.kind）
    branch_count        smallint NOT NULL DEFAULT 0,      -- そこに集まる道の本数
    has_traffic_signals boolean  NOT NULL DEFAULT false,  -- 半径内に信号があるか
    max_highway_rank    smallint NOT NULL DEFAULT 0,
    source_run_id       bigint   NOT NULL REFERENCES source_runs (run_id)
);
-- geom は持たない（source_features から引く）。GiSTも持たない——本番の索引統計で
-- idx_road_nodes_geom は 5,055,354 回使われているが、タイル配信でもルート生成でも
-- 1回も増えず、バッチ側の履歴と判明した（利用者の経路では使われていない）。

CREATE TABLE way_materials (
    osm_way_id         bigint   PRIMARY KEY REFERENCES osm_raw_ways (osm_way_id) ON DELETE CASCADE,
    accident_count     real     NOT NULL,
    intersection_count smallint NOT NULL,
    poi_signal         smallint NOT NULL,   -- POI_COUNT_KINDS の宣言から生成する固定列
    poi_crossing       smallint NOT NULL,   -- （jsonbの袋をやめる）
    poi_stop           smallint NOT NULL,
    poi_level_crossing smallint NOT NULL,
    poi_barrier        smallint NOT NULL,
    lc_valid_pixels    integer  NOT NULL,
    lc_water real NOT NULL, lc_trees real NOT NULL, lc_flooded_veg real NOT NULL,
    lc_crops real NOT NULL, lc_built real NOT NULL, lc_bare        real NOT NULL,
    lc_snow_ice real NOT NULL, lc_rangeland real NOT NULL,
    divided            boolean  NOT NULL,
    designation_emergency real,             -- N10 のマッチ率。無指定はNULL
    designation_logistics real,             -- N12
    source_run_id      bigint   NOT NULL REFERENCES source_runs (run_id)
);
-- length_m は osm_raw_ways.geom から ST_Length で導く（持たない）
-- matched_route_designation_ids は読み手が0件のため落とす
```

廃止: `raw_intersection_nodes`（`branch_count >= 3`で引く）・`way_attribute_counts`・
`way_landcover`・`way_divided_carriageway`・`designation_attributes`・`road_nodes`。

| `road_nodes` → `node_materials` | 732 MB | 約 120 MB |

## 決定5: 第2層（区間粒度の派生）を`edge_materials`へ統合する

**この節のDDLは決定11が差し替えた（2026-09-20）。** `edge_materials`は独立した表を
やめ、`road_segments`へ統合した。統合の根拠（1対1をバッチのコードが守っていた）は
決定11にある。

3表を1つにする。`road_edges`とはキーを共有するが表は分ける——形状・トポロジと材料は
更新のきっかけが違う（形状はwayの再分割時、材料は事故やLULCの更新時）。

### 向きの重複が第2層へ波及していた（実測）

| | 行数 | fwd | bwd | キー |
|---|---|---|---|---|
| `edge_attribute_counts` | 5,065,850 | 2,610,982 | 2,454,868 | `edge_id`（向き込み） |
| `elevation_attributes` | 5,065,850 | 2,610,982 | 2,454,868 | `edge_id`（向き込み） |
| `edge_landcover` | 2,610,177 | — | — | `(osm_way_id, node_lo, node_hi)`＝向き非依存 |

`edge_attribute_counts`が持つのは事故数・交差点数・POI数で、**向きで変わらない値**を2倍
持っている。`elevation_attributes`は向きで変わるが導ける——標本783ペアのうち773件（98.7%）
で`average_grade`が符号反転、5件が同値（平坦）。列の対応は機械的
（start↔end、gain↔loss、average_gradeは符号反転、max↔minは入れ替えて符号反転）。

`edge_landcover`は既に向き非依存のキーを自前で合成していた。路面タイルのSQLが
`LEAST/GREATEST`で同じことを実行時にやっているのと合わせ、**同じ回避が2箇所で独立に
発生している**。主キーを`(osm_way_id, segment_index)`にすれば両方消える。

### 定義

```sql
CREATE TABLE edge_materials (
    osm_way_id    bigint   NOT NULL,
    segment_index smallint NOT NULL,

    -- 未計算はNULL（バッチごとに埋まる時期が違うためNOT NULLにできない）
    accident_count     real,
    intersection_count smallint,
    poi_signal smallint, poi_crossing smallint, poi_stop smallint,
    poi_level_crossing smallint, poi_barrier smallint,

    -- 順方向の値だけ持つ。逆向きは読み出し時に入れ替え・符号反転で導く
    start_elevation_m real, end_elevation_m  real,
    elevation_gain_m  real, elevation_loss_m real,
    average_grade     real, max_grade        real, min_grade real,

    lc_valid_pixels integer,
    lc_water real, lc_trees real, lc_flooded_veg real, lc_crops real,
    lc_built real, lc_bare  real, lc_snow_ice    real, lc_rangeland real,

    source_run_id bigint NOT NULL REFERENCES source_runs (run_id),

    PRIMARY KEY (osm_way_id, segment_index),
    FOREIGN KEY (osm_way_id, segment_index)
        REFERENCES road_edges (osm_way_id, segment_index) ON DELETE CASCADE
);
```

行は`road_edges`と同時に作り（全列NULL）、各バッチは自分の列を`UPDATE`する。

**副産物**: 完成度の判定が一様になる。今は表ごとに違う述語を持ち
（`NOT EXISTS(...)`・`degree = 0`・`max_highway_rank = 0 AND EXISTS(...)`）、
「未計算と本当に0を区別できない」という注記が付いている。NULLで表せば
「その列がNULLの行数」で足りる。

**精度**: `elevation_attributes`は7列すべて`float8`だが、標高をcm精度で持つのに`real`で
足りる。`accident_count`も`float8`から`real`へ。

**訂正**: 先に`edge_landcover`の充足率を91.9%と報告したが、`reltuples`（プランナ用の
推定値）を実数として使った誤り。`count(*)`では 2,610,177 / 2,611,210 = **99.96%**
（欠けは1,033区間）。フォールバックが効く範囲は小さいが、経路自体を無くす方針は変えない。

|---|---|---|
| 3表の本体 | 2,117 MB | |
| 主キー索引 3本 | 874 MB | 1本 約 90 MB |
| **計** | **2,991 MB** | **約 515 MB（−83%）** |

## 決定6: 生データの差し替えは3段で完結させる

### 今は2段で、温めるのが利用者になっている

```
1. 生データを入れる
2. 派生を再計算して世代を上げる   ← ここで終わり
```

`derived_data_meta.revision`は**システム全体で1つのカウンタ**で、どのバッチが成功しても
同じ値が上がる。これを鍵に含むキャッシュ（路面/POI/事故タイル・探索材料・スコア行列）が
一斉に無効になり、次に来た利用者が冷パスを踏む。

冷パスの実測（[T546](T546.md)・[T522](T522.md)）:

| | 実測 |
|---|---|
| 探索材料のDB冷パス | 39〜55秒 |
| 12タイル・254,052区間の真の冷パス | 34,969 ms（2.9秒/タイル） |
| way単位の勾配 | 809 ms/エントリ |

標高だけ差し替えても、土地被覆タイル・事故タイル・停止要因POIタイルという**無関係な
キャッシュまで捨てる**。

### 決めること

**(a) キャッシュの鍵をソース別の世代で作る。**`source_runs`をソースごとに持つので、
そのキャッシュが実際に読んだソースのrunだけを鍵に含められる。事故タイルはDEMの
差し替えで無効にならない。

**(b) 手順を3段にする。**

```
1. 生データを新しいrunで入れる
2. 派生（node/way/edge_materials）を再計算する
3. キャッシュを作り直してから世代を切り替える   ← 新設
```

3が[T546](T546.md)の「E. バッチ側で事前生成」（同タスクで**未起票**のまま残っていた段）に
当たる。事前生成の所要は、関東のz12タイル1,020枚（`road_graph_tiles`の実数）×2.9秒 =
**約50分**、全国で約8.6時間。派生の再計算と合わせても夜間バッチの枠に収まり、利用者に
数十秒を払わせる理由が無い。

正規化して表をまたぐようにした以上、ソースを洗い替えたときの影響範囲が広がるのは
避けられない。キャッシュ層を分離して事前生成を持つのは、その正当な対価として受け入れる。

## 決定7: 外部から取得した値の置き場をそろえる（気象層）

### 分かれ方に基準が無かった

6つとも外部ソースで、どれも外部への負荷を肩代わりしているのに、3つが共有の置き場、
3つがプロセス内にあった。`docs/caching.md`の基準（「Redisへ置くのは外部への負荷を
肩代わりするものだけ」）ではこの分かれ方を説明できない。しかも同文書は「外部フェッチを
肩代わりしているキャッシュをプロセス内に置くと、上流へのリクエストがワーカー数に比例して
増える」と書いている。

`flood`（洪水予報）と`jma_warning`（警報）は**全国分を1リクエストで取る電文**で、
`jma_amedas`とまったく同じ性質なのに、プロセス内にあった。

### 「いつ取るか」と「どこへ置くか」は別の軸

混同すると、WBGTのように「リクエスト駆動が正しいが、置き場は共有であるべき」ものを
扱えない。WBGTの実態:

| | 取得単位 | TTL |
|---|---|---|
| 地点マスタ（CSV） | 全国約840地点を1リクエスト | 24時間 |
| 予測値（`getForecastData`） | **地点（forecast_no）ごと** | 1時間 |

サイト側が「自動化ツールからの高頻度アクセスは控えて」と明記しているため、全840地点の
先読みは逆効果（840リクエスト/時間）。**取り方はリクエスト駆動のまま**が正しい。一方
置き場を共有にしないと、ワーカーが増えたぶん同じ地点を別々に取りに行く。

### 基準

> **外部から取得した値は、共有の置き場（Redis）へ置く。**プロセス内へ置いてよいのは、
> プロセス寿命で消えることに意味がある否定キャッシュだけ。**大きくてファイルとして扱う
> もの（MSMの`.om`）はディスク。**
>
> **いつ取りに行くか**は置き場と独立に決める。外部の1リクエストが多数の利用者ぶんを
> 賄えるならスケジューラが定期取得し、リクエスト経路は読むだけにする。利用者ごと・
> 地点ごとに取るものだけリクエスト駆動にしてよい。

| ソース | いつ取るか | どこへ置くか |
|---|---|---|
| jma_tile（雨雲・キキクル） | スケジューラが先読み | Redis（現状維持） |
| jma_amedas（実測） | スケジューラ | Redis（現状維持） |
| jma_warning（警報） | 全国1回なのでスケジューラへ寄せる | **Redisへ移す** |
| flood（洪水予報） | 全国1回なのでスケジューラへ寄せる | **Redisへ移す** |
| wbgt 地点マスタ | 全国1回・24時間TTL | **Redisへ移す** |
| wbgt 予測値 | リクエスト時のまま（地点ごと・自粛要請） | **Redisへ移す** |
| msm（予報） | スケジューラ | ファイル（本番56MB。`.om`はパスで読む形式） |
| GSIタイルの404（整備区域外） | リクエスト時 | プロセス内（**意図的にプロセス寿命へ縛っている**——整備区域が広がったとき再起動で再取得の機会が来るように） |

容量の懸念は無い。本番Redisは 1.92MB / 2GB（0.1%）しか使っておらず、移すのは小さな
JSON/CSVだけ。「Redisの利用を積極的に広げない」方針とも矛盾しない——新しい種類の用途を
足すのではなく、**既にRedisにあるべきものを揃えるだけ**で、ルートの材料や派生データを
Redisへ持つ話ではない。

### 気象をDBへ持つ話ではない

条件1（手動で取り直さなければ最新が反映されない）で落ちる。ただし**過去の気象は時間が
経てば「1年以上固定」になる**——今は捨てている。「昨年の同じ時期はどうだったか」を
使いたくなったらDB側の話になるが、今の出口にその要求は無いので対象外。

## 第3層（材料→軸スコア）の扱い

3つのキャッシュのうち`graph_material_cache`は、**DBの表をタイル単位でpickleしたもの**で、
存在理由は「DBの読み出しが遅い」（冷パス2.9秒/タイル）ことだけ。その遅さの原因が
第1・2層で直そうとしているものそのものである（5表のLEFT JOINが1つに、結合キーが23B→10B、
走査する行が半分）。**キャッシュが要らなくなるかは直してから測る**。今は判断しない。

`tile_score_matrix_cache`の存在理由は速度ではない（材料があれば行列は25ms）。軸定義を
編集したときに材料まで捨てずに済ませる**無効化の粒度**の分離で、これは正当。変えない。

`dynamic_way_value_cache`は鍵に時刻・向き・速度のバケットを含む動的材料の配信で、
静的な材料とは別物。混ぜて論じない。

## 決定8: migrationの仕組みを捨て、スキーマ変更は「測ってGAPを埋める」手順にする

### 積み上げた履歴と本番のスキーマは一致していない（実測、2026-09-20）

ORMの`Base.metadata`が宣言する形と、本番の実スキーマを突き合わせた。

```
本番の表 24 / ORMが宣言する表 22
■ 本番にあってORMに無い表: derived_data_meta, schema_migrations
■ 6表で、本番にあってORMが宣言していない外部キーが計8本
```

実物（`pg_get_constraintdef`）:

```
edge_attribute_counts_source_accident_import_run_id_fkey
  FOREIGN KEY (source_accident_import_run_id) REFERENCES accident_import_runs(id) ON DELETE SET NULL
```

対するORM側は `source_accident_import_run_id: Mapped[int | None] = mapped_column(Integer,
nullable=True)` で、`ForeignKey`の宣言が無い。同種が`way_attribute_counts`・
`edge_landcover`・`way_landcover`・`way_divided_carriageway`・`designation_attributes`にもある。

**`create_tables()`で新規環境を作ると、本番より外部キーが8本少ないDBができる。**
migrationが足したものをモデルが知らないまま、誰も突き合わせていなかった。

既存の検知器「ORMの列宣言とmigrationのDDLの食い違い（全件）」は**0件と報告している**。
名前のとおり列しか見ておらず制約を見ない、かつ**比較相手がソース同士**で本番ではない。

### migrationでないとできないことは無い

- **過去の断面へ戻す運用は想定されていない**（`migrate.py`が「downgradeは持たない最小構成」と明記）
- **意図の記録**は設計書で足りる（実行可能である必要が無い）
- **失敗時の復旧**はバックアップで足りる
- **1回ずつ本番を進める**ことは使い捨てのパッチで足りる
- 残るのは「止めずに、既存データを保ったまま進める」だけ。βは作り直しで約1日（実測からの
  外挿: `import_pbf`は東京都心41,555wayで547.9秒→関東32倍で約5時間、`way_landcover`全件
  63.5分、`edge_landcover`約1.5時間、`elevation_attributes`は6時間超でOOMした実績）。
  本番利用がほぼ無い今は止められる

### 何を守るために作られたか（記録を確認した）

[docs/decisions/pre-static-attributes-gate.md](../decisions/pre-static-attributes-gate.md)
決定3（2026-08-16）:

> `create_tables`に冪等ALTER×6・インデックス追加/削除・バックフィルUPDATEが**起動時関数
> として蓄積**している。（略）**起動時に全歴史を再実行する方式は保守コストが線形に悪化する**。

**守ろうとしたのは「起動のたびに全歴史のALTERを再実行するのをやめること」で、これは
達成されている。**「積み上げた履歴が正しいことの保証」は当初から目的に入っていない。

そして選択肢は A（最小migration機構）／B（Alembicフル）／C（現状維持＝`create_tables`への
追記）の3つで、**3つとも「起動時関数 vs migration方式」の枠の中**だった。「変更のたびに
使い捨てのSQLを1回当てる」「作り直す」は検討されていない。問題が「どのmigration方式か」
として立てられたため、**「そもそも仕組みが要るか」は一度も問われなかった**。当時は
Supabase・都心25km圏・容量400MB制約で、作り直しは今より安かった。

### 決定

**捨てる。**

|---|---|
| `backend/migrations/*.sql` | 47本 |
| `backend/app/infrastructure/migrate.py` | 105行 |
| `schema_migrations` テーブル | |

```
  1. 本番の実スキーマを測る
  2. あるべき姿とのGAPを出す
```

## 決定9: 正本は本番DB。リポジトリにあるのは宣言とバックアップ

「スキーマの正本をORMモデルに置くか`schema.sql`に置くか」という問いは、**どちらも正本
ではない**ので成り立たなかった。

```
正本             : 本番DB
あるべき姿の宣言 : ORMモデル（機械可読・1か所）
意図・判断の記録 : DB設計書（人が読む。実行も比較もしない）
一致の保証       : GAP検知器（本番 vs ORM宣言）← 今は無い
本番を失ったとき : ORM宣言から create_tables() ＋ 生データ ＋ 管理データのバックアップ
```

軸定義と同じ構造である。

| | 正本 | リポジトリのもの | 一致を保証するもの |
|---|---|---|---|
| 軸定義 | 本番DB | スナップショット＝**バックアップ** | 無い（[T972](T972.md)） |
| スキーマ | 本番DB | ORMモデル＝**あるべき姿の宣言** | 無い（実測で外部キーが8本ずれていた） |

**「正本が2つに割れる」という懸念は、両方を正本だと思っていたから出たもの**だった。
片方が正本で片方が宣言なら割れない。ずれるだけで、それは測れば分かる。

残る要求は1つ。**あるべき姿は機械可読な形で1か所に書かれていること**——GAP検知器が読んで
本番と突き合わせられなければ、宣言としての役目を果たさない。ORMモデルで足りる（今日の
GAP測定がそれで動いた）。`PARTITION BY LIST`が表せなければ同じ場所に補助の宣言を足す。
正本の話ではない。

## 決定11: 区間と有向枝の形（決定3・決定5を差し替える、2026-09-20）

決定3の「区間1本＝1行、有向グラフはメモリ上で作る」は**誤りだった**。`road_edges`が
FROM/TOを持つ構造を捨て、一方通行の表現をアプリへ逃がしていた。対話で全面的に見直し、
以下を承認した。決定3のDDLと決定5のDDLは、この節が置き換える。

### 形

生データ層は`source_features`（`source`でLISTパーティション）のまま。区間は実表1本で、
**位相・形状・材料をすべて持つ**（決定5の`edge_materials`は統合して廃止）。**有向枝は
ビュー**で、区間から向きごとに1〜2行を導く。

```
source_features(osm_way)  node_ids bigint[] / geom / attrs
        ↓ 分割（Pythonバッチ。位置範囲 start_ord..end_ord を決める）
road_segments  位置範囲・形状・距離・方位・材料          ← 実表
        ↓ ビュー（向きごとに1〜2行、方位と標高を読み替え）
road_edges                                              ← 実体を持たない
```

### 分割が正しいことをDBで担保する

| 担保したいこと | 宣言 |
|---|---|
| 区間同士が重ならない | `EXCLUDE USING gist (osm_way_id WITH =, int4range(start_ord, end_ord) WITH &&)` |
| 前の区間の終わり＝次の始まり | `(osm_way_id, prev_index, start_ord)` の自己参照FK。`prev_index`は`NULLIF(segment_index - 1, -1)`の生成列で、先頭はNULLになりMATCH SIMPLEで素通りする |
| 先頭が1から始まる | `CHECK (segment_index > 0 OR start_ord = 1)` |
| 形状が位置範囲と辻褄が合う | `CHECK (ST_NumPoints(geom) = end_ord - start_ord + 1)` |
| 実在するwayを指す | `feature_id`（生成列）への、複合でないFK |
| 成功した取込から作られた | `source_run_success`へのFK |

開発DBで7ケースを実行して確かめた（すべてロールバック）。先頭の投入は通り、飛んだ区間・
重なる区間・1始まりでない先頭・途中の区間の削除はすべて弾かれ、環状を中間で切った2本は
通った。`btree_gist`拡張が要る。

### 宣言できないまま残るもの

- 最後の区間がwayの終端で終わること（wayの`array_length(node_ids, 1)`が要る＝他表参照。
  CHECKも生成列も他表を参照できない）
- 形状がwayのその区間と実際に一致すること（同上。頂点数の一致までは行内で縛れる）
- `distance_m`が`geom`の長さと一致すること（`ST_Length(::geography)`がIMMUTABLEでない）
- 派生層が生データ層を覆っていること（FKは向きが逆。**制約ではなく台帳の仕事**）

最後の1つは`derived_data_freshness.py`へ「生データの母数に対する行の欠け」を足して対応した
（2026-09-20）。対象は宣言から導く——`derived_models.covers("osm_way")`を鍵の列へ付けた表が
`source_features`のその母数と突き合わされ、派生表どうしは宣言済みの外部キーから親を辿る。
覆わないことが設計である表（`node_materials`）には付けない。

### 写しが隠していた欠陥（2026-09-20）

軸カタログのビルド時の写しを撤去したところ、`RouteSettingsPanel`が**取得前に
`routePreference`を`{}`へ潰していた**ことが分かった。保存済みの重みが消える。

写しがあった間なぜ気づけなかったか:

- **「まだ分からない」が型から消えていた。** 写しがあると`defaultWeights`は起動直後から
  全公開軸ぶん埋まっており、未取得と取得済みが値から区別できない。区別が要らないので、
  区別する分岐も書かれず、テストも書かれない
- **分岐が要ることはフック自身が明記していた。** `useAxisCatalog`は`loaded`を持ち、
  「`loaded`を要求する処理では未確定状態を区別しなければならない」と書いている。
  `page.tsx`は従い、`RouteSettingsPanel`は従っていなかった。**従わない代償が
  ゼロだった**ため、抜けが表に出ない
- **観測に必要な状態が到達不能だった。** この欠陥が見えるのは「軸が0件だと確定している」
  瞬間だけで、写しがある限りその瞬間は存在しない。既存のテスト
  （`not.toHaveBeenCalled`）は当時も通っていたが、理由が違った——「一致していて同期不要」
  ではなく「写しがたまたま正しかった」から通っていた

**フォールバックは間違った値を隠すだけでなく、要るはずの分岐が抜けていることも隠す。**
後者は「値が合っているか」を見るテストでは捕まらない（[T970](T970.md)で`loaded`の
ガードを足して解消）。

### 軸カタログの写しを消して失ったテスト（2026-09-20）

`AxisComposer.cosmeticRoundTrip.test.tsx`を削除した。**公開済み軸を「表示だけ編集」したとき、
フォームが編集欄を持たないフィールドを作り直して送っていないか**を、実在する全公開軸を
母集団にして見ていた回帰テストである。

母集団は`backend/fixtures/axis_definitions_snapshot.json`（実DBのダンプ）だった。
**フォームの既定値と同じ軸を1件置いたテストは通ってしまう**ため、母集団は「既定と違う値を
持つ実在の軸」でなければ意味がなく、写しを消した以上フロントからは作れない。

backendは`is_cosmetic_only_update`の判定側を持つが、守る対象が違う——こちらは
「触っていないのに保存が拒否される」というフォーム側の欠陥で、判定が正しくても起きる。
軸定義を外から供給できるようになったら（[T972](T972.md)）戻せる。

### 端点→ノードはFKで縛る（台帳ではない、2026-09-20）

`road_edges.from_node_id`/`to_node_id`が`node_materials`に行を持つことは、**親子の向きが
そのまま**なので外部キーで書ける。台帳の仕事ではない。

行が無いと探索が既定値（信号なし・階級0）を黙って読み、ターンの費用が実際より安く出る。
報告より阻止が適切な性質のため制約にした。

開発DBで確認: 既存23,322行すべてに制約を張れ（＝不変条件は成立済み）、存在しないノードを
指す行は`IntegrityError`で弾かれた（検証はロールバック）。

一方「タグが種別に分類される点」の側は覆いを測らない。母集団を出すには台帳が`classify()`を
再実行することになり、分類器が誤っていれば台帳も同じだけ誤る（宣言の書き写し）。

### 判断の根拠（すべて本番実測、2026-09-20）

**有向枝を実表にせずビューにする。** 同じ列・同じ索引で作り直して比べると、有向にする
代償は行の倍増ぶんである。

| | 行数 | 本体 | 索引込み |
|---|---|---|---|
| 無向の区間 | 2,610,982 | 512 MB | 694 MB |
| 有向の枝 | 5,065,850 | 996 MB | 1,350 MB |

決定3が挙げた3,719 MBとの差は、`edge_id varchar`の主キー（370 MB）・端点の索引2本
（378 MB）・`osm_way_id`の索引（122 MB）・肥大を含んでおり、向きの代償ではなかった。

ルート探索はz12タイル単位でトポロジを読み、メモリLRU→ディスクpickleへ寄せる
（`graph_service._get_or_build_tile_materials`）。DBを叩くのはタイルが冷えているときだけ。
30km四方はz12タイル16枚で、**全部冷えている最悪の1回**が次のとおり。

| | 16枚合計 | 行数 |
|---|---|---|
| ビューから有向を読む | 348.0 ms | 484,143 |
| 区間表を読みPythonで展開 | 158.9 ms | 271,913 |

**形状は列で持つ。** 1表・geom列・GiSTで、z12タイル3枚を読む。

| | 3枚合計 | 容量 |
|---|---|---|
| 形状を列で持つ | 38.1 ms | 574 MB |
| 読むときにwayの頂点から組む | 1,649.7 ms | 229 MB |

345 MBで43倍。持つ。

**端点は持たない。** `node_ids[start_ord]`で引く。本番52,112行で124.7 ms 対 123.5 ms
（差1%）。同じ「複製か導出か」で形状と答えが割れるのは、費用が2桁違うため。

**逆向きの方位は`(bearing + 180) mod 360`で導く。** 本番2,454,642対の実測で、保存されて
いる両向きの差が180度からずれる量は中央値0.000228度・p99 0.002286度。`reverse_bearing_deg`
列は撤去する。

**分割はSQLへ移す（2026-09-21に訂正。決定12）。** 同じ規則をSQLで書いて開発DBで
突き合わせたところ、区間23,322本・`(way, 区間)`の食い違い0件・端点の食い違い0件で
**完全に一致した**。値は長さが平均0.192%（測地線のぶんSQLが正確）、方位が平均0.074度ずれる。

**当初ここには「SQLが約4倍遅いので移さない」と書いていたが、その測定は無効だった。**
Python側は区間の本数を数えるだけで、形状も長さも方位も作らず、WKB化もDBへの書き戻しも
していなかった（`total = sum(len(split_segments(...)))`）。SQL側は形状を組み、測地線長と
方位を出し、表へ書いていた。**違う仕事の所要を並べて125 ms対493 msと書いていた。**

無効さの証拠は当時も書いてあった——「Python側の仕事が整数配列を歩くだけで元々安く」。
それを測定をやり直す理由ではなく、結論の説明として使ったのが誤り。

条件を揃えて測り直した（入口は同じ`node_ids`と形状、出口は`road_edges`と同じ列・同じ
主キーの表、成果物は8列すべて、始点＝終点の区間は両者から除外、交互に3回の最短値）。
成果物は完全一致（行数・端点・形状の差0、長さ最大差0.050 m、方位最大差0.127度）。

| way | 区間 | Python | SQL（球） |
|---|---|---|---|
| 3,007 | 5,085 | 910 ms | 549 ms |
| 6,014 | 11,370 | 1,535 ms | 1,124 ms |
| 12,029 | 23,318 | 3,359 ms | 1,596 ms |

3規模ともSQLが速い。**倍率（1.37〜2.11）は3点・ばらつき20%では決まらず、関東全域への
外挿には使えない。この表が示すのは「4倍速い」の反証だけで、規模を超えた優劣ではない。**

**移す根拠は速度ではない。** 生データも派生もDBにあり、間にPythonを置く意味論上の理由が
無い（決定12）。分割の正しさは表に張る宣言的制約が担保するので、INSERTの実行者は
担保の根拠にならない——この一文は当初から変わらず、どちらへも効かない。

## 決定12: 派生はDB内で完結させる（2026-09-21）

### 決め方

速度で決めていない。**派生の入力も出力もDBにあり、間にPythonを置く理由が無い**という
一点で決めた。今のPythonは1,000万頂点をDBから出し、Pythonオブジェクトにし、WKBへ
詰め直し、COPYで戻している。跨ぐ理由の無い境界を跨いでいる。

規模の測定は判断に使っていない。関東全域での優劣は測っていないし、**測っても行動は
変わらない**（段階Dは1回流せば所要が確定し、外れても夜間に回すという行動は同じ）。

### 原則

**Pythonが持つのは規則であって、データではない。**

### 規則の渡し方（既存の3つの型だけを使う。新しい仕組みを足さない）

| 型 | 既存の実例 | 使う場面 |
|---|---|---|
| 定数注入（`$1`） | `SIGNAL_RADIUS_M`・`POI_CLUSTER_EPS_M` | しきい値・半径 |
| 対応表注入（`(VALUES …)`） | `HIGHWAY_RANK` → `_UPDATE_MAX_RANK_TEMPLATE` | タグ→値の引き当て |
| 式注入（domainがSQL断片を持つ） | `material_sql.py`の`FATAL_SQL`等 | 等値で書けない判定・計算 |

対応表注入は`_UPDATE_MAX_RANK_TEMPLATE`が自前で文字列を組んでいる。4箇所へ増えるので
`(VALUES …)`を組む関数を1本にまとめる。

### 段ごと

| 段 | 今Pythonがしていること | 設計 |
|---|---|---|
| topology | ノード列と形状を全件読む／通過回数／形状・長さ・両方位／COPY／`node_materials`を`executemany` | **判断ゼロの運搬のみ。SQL 1文へ** |
| nodes | `classify_stop_poi`・`classify_supply_poi`・`is_traffic_signal` | 判断を対応表へ。読み込みと書き戻しは消滅 |
| counts | なし | 変更なし |
| raster/標高 | 形状を全件読む／画素を引く／`compute_elevation_values` | 画素引きをSQLへ、値の出し方を式注入へ |
| raster/土地被覆 | 帯ごとにタイルを開き`shapely.prepare`で数える | **未確定。後述** |
| ways | `resolve_direction` | 判断を対応表へ |

### 判断が表に落ちることを現物で確かめた

4つとも「優先順位付きの (タグ名, 値) → 値」の引き当てで、優先順位はPythonのif順から
表の`priority`列になる。等値で書けないのは2つだけで、これは式注入にする。

- `classify_vending_machine`: `vending`が`;`連結 →
  `string_to_array(lower(attrs->>'vending'), ';') && ARRAY[…]`
- `is_traffic_signal`: `highway=crossing` かつ `crossing` に`signals`を含む → `LIKE`

### 標高は拡張も生データの持ち方の変更も要らない

画素は`payload`の`bytea`のまま`get_byte`で引ける（`offset = (py*width + px) * 2`、
リトルエンディアンの符号付き16bit）。**`postgis_raster`は不要で、決定2へ手が戻らない。**
`compute_elevation_values`はウィンドウ関数へそのまま写る（欠損跨ぎの除外は
`ord - lag(ord) = 1`、gain/lossは`sum(greatest(...)) FILTER`、橋・トンネルの両端だけ
使う分岐は`CASE`）。しきい値は定数注入なので、値の出し方はdomainが持ったままになる。

### 土地被覆だけは書いてから決める

帯とタイル画素の重なりを数える部分は、素直にSQLで書くと画素を行へ展開することになり、
Python版が`shapely.prepare`で127.3秒→19.9秒にした効きがSQL側にある保証が無い。
案1は`postgis_raster`で`ST_Clip`（依存が1つ増える）、案2は外接矩形で絞って
`generate_series`。**他の4段と違い「書けるか」が未確認なので、1回書いてから決める。**

### 移行の関門

1. SQL版の出力を現Python版と全列で突き合わせ、差0を確認する
2. 差0が出てから旧実装を消す（先に消さない）
3. 段ごとに独立に行う（5段まとめてやらない）

NULLが残らないことは既存の鮮度台帳がそのまま検査になる。新しい検査は作らない。

### 環状の区間をここで閉じる

決定11の「始点＝終点の区間は中間でもう1回切る」は**まだどちらの実装にも入っていない**
（開発DBに4本、本番に1,685本残っている）。`ST_Azimuth`が未定義になるため、SQLへ移す
ときに切る位置へ中点を足して閉じる。このため移行の関門の「差0」は、自己ループを含む
wayでは成り立たない（`segment_index`がずれる）。**そのwayだけ分けて突き合わせる。**

### 副産物

Python版が同時に抱えるメモリ（開発DB実測28.0 MB、関東換算で約3.7 GB＋α）は問題ごと
消える。DB内で完結すれば、ピークを決めるのは`work_mem`という設定値でデータ量ではない。

### 影響

`derive_topology.py` 195行・`derive_node_materials.py` 164行・
`derive_raster_materials.py` 309行・`derive_way_materials.py`の`_load_directions`が対象。
`derive_counts.py` 220行と`derive_cli.py` 78行は変更なし。土地被覆の結論次第で
`numpy`・`shapely`が派生バッチから外れる。

### 通行の向き

`way_materials.direction`を**`allowed_orientation`へ改名**する。保持しているのは「wayの
ノード列の順に進めるか、逆に進めるか、両方か」だけで、同じ表にある`bearing_deg`（方位）
とは別物である。値は`both`/`forward`/`backward`のまま。

**way単位のまま置く。** `oneway`はwayに付くタグで1本のway内で一定なので、区間へ持たせても
情報が増えない。読み出しは既に`way_materials`へ結合しているので追加費用がない。決定4で
検討した区間側の`traversable`列は廃止する。

ビューの結合は`INNER JOIN`。行が無いときに`COALESCE(..., 'both')`で既定値を作るのは、
DBが持っていない事実を捏造することになる。

### 環状の区間

始点と終点が同じ区間が本番に**1,685本**あり、そのうち**1,572本は両向きの方位がどちらも
0.000度**になっていた（最長1,411 m）。閉じた線に始点→終点の方位は定義できないため。
ロータリーや環状の生活道路として正しく実在する道なので取り込む。

分割の規則に1つ足す: **始点と終点が同じ区間は、中間の位置でもう1回切る**。`A → A`が
`A → M → A`になり、両方とも端点が異なるので方位が定義できる。環状のwayに限らず、同じ
ノードを2度通るwayでも同じ形の区間ができるので、「始点＝終点の区間」全般に当てはめる。

### 距離0の区間

本番2,611,210本のうち距離0は**2本**。1本は`LINESTRING EMPTY`（本物の欠陥）、もう1本は
実在する4.8 cmの区間が`round(_length_m(points), 1)`で0へ丸められたもの。短い区間自体は
正当で、1 m未満が1,782本あり`trunk`が22本・`primary`が49本含まれる。

**丸めを撤去したうえで**`CHECK (distance_m > 0)`と
`CHECK (NOT ST_IsEmpty(geom) AND ST_NumPoints(geom) >= 2)`を張る。

### 生データ層に足すもの

`node_ids bigint[]`を親に足す。`payload`を配列型にはできない——ラスタの画素とベクタタイルの
本体が同じ袋に入っており、1つの配列型に収まらないため、osm_way専用の列を別に持つ。子
パーティションだけに列を足すことはできない（「パーティションに列は追加できません」）ので、
親に付けて他ソースはNULLにし、osm_wayの約束を子のCHECKで縛る。

ソースごとの約束は子パーティションの冒頭へ書く。**書いてよいのは提供元の出典と原文だけ**で、

```sql
-- 「死者数」桁数3・「交通事故により24時間以内に亡くなった者の人数をいう。」
--   → 値は '000' 形式。重み付けが数える対象は24時間以内の死亡に限られる
-- 「本票番号」「都道府県警察署等ごとの一連番号をいう。」
--   → 年をまたぐと振り直される。natural_keyに年を含める根拠
-- 「当事者種別」51=「軽車両－自転車」/ 52=「軽車両－駆動補助機付自転車」
-- 「地点　緯度（北緯）」桁数9・「経度（東経）」桁数10・「緯度は世界測地系（度分秒）とする。」
--   → 桁の内訳は定義書に無い。9桁/10桁から DD(D)+MM+SSsss と解釈している
-- 配布は暦年単位（ページの表記は「２０２４年（令和６年）」、ファイルは「本票_01-12月」）
CREATE TABLE source_features_accident PARTITION OF source_features FOR VALUES IN ('accident');
ALTER TABLE source_features_accident
  ADD CHECK (GeometryType(geom) = 'POINT');
```

子パーティションと、そこへ張るソースごとのCHECK・一意索引は取込の側が作る。

### 成功した取込へのFK

派生行が成功したrunを指していることを、**派生側に列を足さずに**担保する。成功した取込
だけが載る薄い表をソースでパーティションし、その子をFKで指す。

派生表は既にある`source_run_id`（8バイト）でこの子を指すだけなので、**追加の容量は0**。
`source`と`status`を生成列で持つ案（派生1,500万行に対し約330 MB）は採らない。この形なら
`status`を短く符号化する必要もないので`'succeeded'`のまま置く。

`_close_run`が成功時にこの1行を足す。忘れると派生が1行もINSERTできなくなるので、忘れた
ことが即座に分かる。

### マテリアライズドビューは採れない

分割をマテリアライズドビューにする案を検討したが、開発DBで試して不可と分かった。

| | |
|---|---|
| 一意索引・GiST索引 | 張れる |
| CHECK・EXCLUDE | **張れない**（`ADD CONSTRAINT`できない） |
| マテビューを参照するFK | **張れない**（テーブルではない） |
| マテビューから他表へのFK | **張れない** |

普通のビューも参照先にできない。T970が入れようとしている宣言的制約をすべて失う。

| `derive_topology.py`・`derive_node_materials.py`の`raise` | 「先に取込を通せ」＝処理順序 |

## 段階Bの条件を書き直す

「6ソースが入る」は**6本の取込経路を書く**とも読める。それでは共通フォーマットにした意味が
無い。取込は1本にする。

```
共通の取込経路（1本）
  ├ プロファイルを読む（どのソースを、どの絞り込みで）
  ├ source_runs へ run を起こす
  ├ ソースアダプタから (natural_key, geom, attrs, payload) を1件ずつ受け取る ← ここだけがソース別
  ├ source_features の該当パーティションへ COPY
  └ run を成功で閉じる（件数・origin・profile を記録）
```

形状を保存するので導出できること自体は変わらないが、**導き方が違う**。読み出し側は
逆順の始点・終点から求め直す。

### 段階C（途中）: ノードに付く値を埋めた

`app/batch/derive_node_materials.py`。**種別は取込ではなくここで付ける**——取込は外部の

```
内訳: crossing 9,179 / traffic_signals 2,794 / stop 1,490 / level_crossing 62 / barrier 57 …
結果: 27,427点（うち信号が近い 10,896 / 階級が付く 15,078 / 枝3本以上 11,955）
```

#### 空間の索引で107秒→3.0秒

`ST_DWithin(a::geography, b::geography, m)`は**geometryのGiSTを使えない**。`&&`と
`ST_Expand`の前置フィルタを先に置いて矩形で絞ると、107秒が3.0秒になった（35倍）。
既存の`_RECOMPUTE_NODE_TRAFFIC_SIGNALS_SQL`が同じ形にしていたのは、これが理由。

生データのパーティションには取込時にGiSTを張るようにした（`ensure_partition`）。生データは
範囲や近さで引かれる（事故を区間へ、信号を交差点へ割り当てる）ので、索引が要る。

判断なので`domain/traffic.py: is_traffic_signal`へ置き、バッチはそれを呼ぶ。

## 要確認: 停止要因を区間へ割り当てる規則が、向きの廃止で変わる

**ユーザーの確認が要る判断**。実装は進めるが、較正に影響するので明示しておく。

旧実装の規則（`_POI_COUNTS_BODY`のコメント）:

1. **そのwayの構成ノードだけ**を対象にする（距離だけで拾うと、交差する別の道の信号まで数える）
2. **区間の始点にあるノードを除く**——交差点のノードは「入る区間」と「出る区間」の両方が
   持つため、両方が数えると1回の停止が2回になる。「止まるのは区間を走り終えるところなので、
   到着側（終点側）の区間が持つ。**有向Edgeのため逆向きの区間でも同じ規則が成り立つ**」
3. 同じ種別の点を40mでまとめてから数える（日本のOSMは1つの信号交差点を流入路ごとの
   複数ノードで描く）

**規則2は有向Edgeであることに依存している。**区間を1本1行にすると、A→Bと走るときは
Aが交差点Jを持つが、B→Aと走るときはBの終点はJではないので数えられない。

### 採る規則: 端点を半分ずつ持つ

```
区間の停止要因 = 0.5 × (始点の停止要因) + 0.5 × (終点の停止要因)
```

経路上の中間ノードは前後の区間が0.5ずつ持ち、合計1回になる。**向きに依らない**。
経路の端のノードだけ0.5になるが、経路長に対して無視できる。

### 影響

**値が旧実装と変わる。**軸の較正（`axis_definitions.shape_params`のbreakpoint）は旧実装の
分布に対して調整されているため、そのままでは効きがずれる。段階Dの後に分布を測り直して、
較正を見直す必要がある。

規則1（そのwayのノードだけ）と規則3（40mのまとめ）は変えない。

## 決定12の実施記録: 標高をDB内へ移した（2026-09-21）

### 効いていたのは圧縮であって、拡張ではなかった

面の画素をSQLから引くと、最初は**開発DBで100秒級**かかった（Pythonの同じ段が2.1秒）。
`payload`は131 KBで必ずTOASTへ出るため、**1回のアクセスごとに値全体が伸長される**。

`postgis_raster`（3.6.2、導入可）も試したが、**決め手は`SET STORAGE EXTERNAL`（圧縮
しない）の方だった**。条件をそろえて測り直した結果（開発DB、頂点20,000点、結合件数を
毎回確認、`pg_attribute.attstorage`で保存方式を確認、2回の最小値）:

| 保存 | 読み方 | 1点あたり | 実体（dem 132枚） |
|---|---|---|---|
| 圧縮（既定） | `get_byte`×2 | 1.369 ms | 5.81 MB |
| 圧縮 | `substring`→`get_byte` | 0.635 ms | 5.81 MB |
| 圧縮 | `ST_Value`（raster） | 0.418 ms | 5.81 MB |
| **非圧縮** | **`substring`→`get_byte`** | **0.0149 ms** | 17.30 MB |
| 非圧縮 | `ST_Value`（raster） | 0.0285 ms | 17.31 MB |
| 非圧縮 | `get_byte`×2 | 0.073 ms | 17.30 MB |

**非圧縮の`bytea`をスライスで読むのがrasterより速い。** 拡張は要らず、決定2（生データの
共通フォーマット）も変えない。`payload`は`bytea`のままで、変えたのは2つだけ:

- `source_features.payload`を`SET STORAGE EXTERNAL`にする（表を作った直後にDDLで当てる。
  親へ当てれば以後のパーティションも引き継ぐ）
- 画素は`substring(payload from i*w+1 for w)`で**必要なバイトだけ**取り出してから読む

代償は**面のデータが約3.4倍**（開発DBの実測で5.85→19.66 MB）。関東のDEMでは段階Dで
実測する。`payload`が小さいソース（OSMのノードid列）はTOASTへ出ないので影響しない。

**索引は足さない。** タイルは開発DBで132枚しかなく、プランナはハッシュ結合を選ぶ。
`btree(tx, ty)`を足すと入れ子ループになってタイルを読み直す計画になりうる。

### ここまでの計測で何度も数字が動いた理由

止めたつもりのクエリが**サーバ側に残って後続を汚していた**（`TaskStop`はクライアントを
殺すだけ）。以後、調査のセッションでは`SET statement_timeout`を置く。もう一つは、
**保存方式・結果件数・他に走っているクエリ・母集団の4つを固定せずに測り始めた**こと。
最後にこの4つを先に書いてから測ったら1回で終わった。

### 距離は測地線（楕円体）で測る——球にしていたのは誤り

topologyの段で`ST_Length(geography, false)`（球）を使い、コメントに「方位と近似を
そろえる方が説明しやすい」と書いた。**本当の理由は、旧Python（haversine）と一致させて
移行の関門を通すためだった。**測り方を検査の都合で選んでおり、相談もしていない。

楕円体へ直して測った差（開発DB、23,318区間）:

| | 旧Python（haversine） | 新SQL（測地線） |
|---|---|---|
| 合計距離 | 1,528,260.0 m | 1,528,260.0 m（**−0.0005%**） |
| 1区間あたりの相対差の平均 | — | +0.0033% |
| 絶対差のp99 / 最大 | — | 0.472 m / 2.337 m |
| 長くなった / 短くなった | — | 11,587本 / 11,731本 |

**偏りは打ち消し合い、実害の差は無い。**所要も変わらない（topology 3.0秒、球のとき
3.3秒）ので、近似する理由が無い。なお「球は日本の緯度で0.1〜0.5%の系統的な偏りを持つ」
と一度書いたが、**これも測らずに言ったもので誤り**だった（実測 0.0005%）。

## 決定13: 面のソースは`raster`で持つ（2026-09-21、決定2を広げる）

### 仕事の形が2つあり、片方は拡張でしか安くならない

- 標高は**1点の画素を引く**。`bytea`を非圧縮にして`substring`で読めば足りる
- 土地被覆は**帯（道の周囲100m）に重なる画素を全部数える**。帯1本あたり1,108画素

後者をSQLで書けるかを、帯1,000本・同じ集合・2回の最小値で測った。

| 案 | 帯1本 | 23,326本換算 |
|---|---|---|
| 素のSQL（画素を行へ展開） | 5.09 ms | 119秒 |
| 画素を点にしてGiST＋空間結合 | 3.31 ms ＋ 一度きり16.2秒 | 93秒 |
| **`ST_Clip` + `ST_ValueCount`** | **0.299 ms** | **7.0秒** |
| （現行Python） | — | 21.6秒 |

**空間索引は効かない。**索引が弱いのではなく、判定する対象が「少数の大きな図形」では
なく「大量の小さな点」だから。開発DBの36枚だけで画素表は236万行になり、関東規模では
8億行で成立しない。

値は完全に一致した。素のSQLとの差44行はすべてクラス0（欠測）で、`ST_Clip`が外すため
——domainはもともと欠測を分母から外すので、`ST_Clip`の側が欲しい形である。

### 決定

面のソース（`dem`・`lulc`）は`source_features.rast`（`raster`型、`SET STORAGE EXTERNAL`）
で持ち、`payload`は使わない。標高もそちらから引く（1つの表現にする）。

`attrs`に残すのは`product`・`year`・`x`・`y`・`z`・`missing`と、rasterが持てない`scale`、
そして`width`。**幅だけは残す**——画素の番地を算術で出すために要り、rasterから読むと
そのたびにタイルの画素が実体化される。型・欠測値・位置はrasterの値自身が持つので書かない。

取込の変換は軽い（WKBの組み立て1枚0.28 ms＋書き込み5 ms）。`payload`の画素の並びが
raster WKBのバンド部分とそのまま同じで、**61バイトのヘッダを前に付けるだけ**だった。

**代償**: `create_tables()`が`postgis_raster`を要求する（CI・新規環境・本番。
スーパーユーザー権限が要る）。容量は変わらない（非圧縮のrasterとbyteaが同じ大きさ）。

### 画素の番地は算術で出す

`ST_Intersects(rast, 点)`でタイルを絞ると、当たり判定のたびに画素が実体化される
（標高10.5秒）。外枠（`geom`）だけで絞って1枚に決めると、境界線上の点が隣のタイルへ
割り当たり**27区間の値が落ちた**。タイル番号と画素位置を算術で出す形にすると、rasterに
触らずに1枚・1画素へ確定し、**6.7秒**で値は完全一致した。

### Python版との完全比較（開発DB、23,326区間・16列）

|---|---|
| `lc_valid_pixels`（数えた画素数） | 違い **0** |
| `lc_flooded_veg`・`lc_crops`・`lc_bare`・`lc_snow_ice` | 違い **0** |
| `lc_water`・`lc_trees`・`lc_built`・`lc_rangeland` | 97〜1,341本、**最大0.005ポイント**（REAL列の丸め順） |
| 標高7列（`substring`版と） | すべて違い **0** |
| 標高・勾配（Python版と） | 標高は違い0、勾配のみ既報の意図した差 |

### 所要

`derive_cli`を端まで: topology 2.5 / nodes 2.6 / counts 3.3 / raster 24.1 / ways 4.1 =
**36.5秒**（Python版の記録は55.8秒。ただし`counts`・`ways`は今回変えていないのに
6.3→3.3・7.0→4.1と動いており、差の一部は機械の状態である）。

変えた段だけで見ると topology 6.5→2.5秒、raster 31.4→24.1秒。

土地被覆19.5秒の内訳は**帯の作成9.2秒**・索引0.3秒・数え上げ7.4秒・書き込み2.6秒で、

**並列2が最適で、それ以上は悪化する**（VMは2 vCPU）。改善の上限は1.78倍で、
ルート生成全体では88.4秒→約56秒の見込み。

直列なのは`GraphService`がセッションを1本しか持たず、`AsyncSession`の同時アクセスを
`_repository_lock`で防いでいるため。並列化にはその前提を崩す必要がある。

### DB設定の範囲での改善: JITを切る（2026-09-21）

材料の取得は材料ごとにCASE式を並べるため式が非常に多い。PostgreSQLのJITは式を機械語へ
コンパイルしてから実行するが、**この規模ではコンパイル代を回収できていない**。

1.6万区間ぶんの材料取得を`EXPLAIN (ANALYZE)`で見たもの:

```
jit=on   JIT: Functions: 45
         Timing: Generation 5.5ms, Inlining 109.3ms, Optimization 369.2ms,
                 Emission 440.7ms, Total 924.7ms
         Execution Time: 1605.6 ms
jit=off  Execution Time:  678.6 ms
```

**1,605msのうち925ms（58%）がコンパイルそのもの**で、実処理の678msより高い。

タイル25枚での比較（on/offを交互に2回ずつ。ばらつきは0.3秒以内）:

| | jit=on | jit=off |
|---|---|---|
| 形の取得（式が少ない） | 24.6秒 | 22.8秒 |
| 材料の取得（式が非常に多い） | 49.2秒 | **29.0秒** |

**式が多いクエリだけが大きく改善する**——JITのコンパイル代が原因という説明と整合する。

`ALTER DATABASE ... SET jit = off`で新DBへ適用した。ルート生成（冷）は88.4秒→64.8秒。

### 冷えたルート生成の推移（関東全域・皇居30km周回・同一条件）

| | 所要 |
|---|---|
| 旧DB＋旧コード | 223秒 |
| 新DB＋新コード（当初） | 308.5秒 |
| ＋形の取得の入れ子ループ解消 | 88.4秒 |
| ＋`jit = off` | **64.8秒** |

### 実行計画を機械的に洗う試みは失敗した

実装が持つSQLを集めて`EXPLAIN (GENERIC_PLAN)`を当て、非効率の兆候を検出する仕組みを
書いた。13本中10本の計画は取れたが、**既知の非効率2件をどちらも検出できなかった**
（修正前の形の取得・ノードの取得）。わざと通して確かめたので、「要確認0件」を
健全さの証拠として報告せずに済んだ。

`GENERIC_PLAN`は値を束ねないため、**実際の値で起きる計画の劣化が見えない**
（ノードの取得は`GENERIC_PLAN`では入れ子ループだが、実際の値では全件走査＋ハッシュへ
倒れる）。機械的に洗うには実際の値で`EXPLAIN ANALYZE`する必要があり、各SQLの引数を
用意する作業になる。
