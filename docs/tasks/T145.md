# T145. 地図レイヤーパネルをレジストリ駆動にし、三次（合成コスト）を既定表示レイヤーとして

状態: 完了（2026-08-31、対応不要と判定）

  新設する 規模L →（2026-08-19、T145a/T145bへ分割・方針再定義）

- 背景: 設計プロンプトのレイヤー表。現状の`mapLayers.ts`は10レイヤーが個別列挙で、
  「常時表示は合成コストのみ」に対応する三次レイヤー自体が存在しない。一次・二次は
  レジストリ（T137、ただしフロント側は別途TypeScript版が必要）から動的に列挙し、軸を
  増やしてもレイヤーパネル・凡例の改修が不要な構造にする。
- 分割の経緯（2026-08-19）: ユーザーと方針を協議し、当初案の「二次レイヤーの動的生成」を
  具体化する過程で2つの重要な制約を確認した。(1) 現行タイルは全ユーザー共有キャッシュ
  （Cache-Control: max-age=3600）のため、レシピ依存の軸最終値をサーバー側で焼き込むと
  研究モードの重み上書き（将来的にはユーザー別レシピ、T141のJSON/DB化が布石）と矛盾する。
  (2) 逆にaccident/stop_density軸は入力データ（事故点・POI集計）自体がタイルに無いため、
  クライアント側expressionでは原理的に計算できない。この2つから、アプリ自身の層構造を
  配信アーキテクチャへ写す「**事実はタイルに、解釈はクライアントに**」方針を採択した:
  一次属性・事前集計カウント（レシピ非依存の事実）はサーバー焼き込み、二次軸スコア
  （レシピ依存の解釈）はクライアントexpressionで計算する。三次（合成コスト）レイヤーは
  本タスクのスコープから外す（係数検証が別途必要なため、実施時期はユーザー判断）。

## 再調査結果（2026-08-31、340件以上のタスクを経た現状との突き合わせ）

起票（2026-08-19）から1年以上・340件超のタスクが経過しており、評価モデル・地図表示の
アーキテクチャ自体がT137〜T152（層構造再設計）・T163〜T169（チップ再編）・T277〜T350
（材料/軸のDBレジストリ化）・T396〜T397（軸合成ロジック再設計）・T400〜T421（地図×評価軸
連動モデル再設計）・T440（色分け完全同期）を経て大きく作り直されている。着手前に現状の
コードを直接確認した結果、本タスクの2つの目標はいずれも**別の形で解消済み**と判明した。

1. **「一次・二次はレジストリから動的に列挙し、軸を増やしてもレイヤーパネル・凡例の
   改修が不要な構造にする」→ 達成済み**。`frontend/src/components/Map/mapLayers.ts:
   buildMapLayers`/`buildStaticOverlayLayers`は`rampAxes`（実行時の軸カタログ）を
   引数に取り、二次(ramp)軸のオーバーレイレイヤーを`buildAxisOverlayLayers(rampAxes)`
   から動的に組み立てる（本セッションでT416/T428着手時にこのファイルを直接確認・
   一部編集して確認済み）。軸スタジオで新規公開した軸は、コード変更なしにレイヤー
   パネル・凡例へ自動反映される（`docs/modules/frontend/static-map-layers.md`
   「本文中最上位グルーピング」節参照）。T145起票時点で懸念していた「10レイヤー個別
   列挙」問題のうち、**個数が増減しうる軸レイヤーの部分**は既に解消している
   （静的な観測レイヤー[道路種別・路面・トンネル等]17件は、種類が増減しない一次データの
   ため個別宣言のままだが、これはT292以降の設計判断として妥当——1次データは種類が
   固定的で、レジストリ化してもコード量は減らず可読性が下がるだけ）。
2. **「三次（合成コスト）を既定表示レイヤーとして新設する」→ 別の形で解消・現行設計と
   非両立と判明**。「合成コスト」という概念自体は`frontend/src/components/Map/
   routeStyleModes.ts: DIFFICULTY_MODE`（総合難易度）として実装済みだが、これは
   T145が想定した「ルート確定前から地図全体に敷く背景レイヤー」ではなく、**ルート確定後の
   選択中ルートだけを塗る色分けモードの1つ**（`RouteSegmentDetail.difficulty`を読む）。
   この違いは設計ミスではなく、T145自身が2026-08-19時点で発見していた技術的な壁
   （「レシピ依存の軸最終値をサーバー側で焼き込むと研究モードの重み上書きと矛盾する」）を
   踏まえた必然的な帰結: 合成コストはユーザーが調整可能な評価軸の重み（route_preference）に
   依存する値のため、特定のルートに紐づかない「地図全体・全道路ぶんの合成コスト」を
   常時計算・表示する背景レイヤーは、重みが変わるたびに視界内の全道路を再計算する
   重い処理になる（個々の評価軸[car_stress等]がbackground rampレイヤーとして表示
   できるのは、重みに依存しない単一材料のスコアだからで、合成コストとは前提が異なる）。
   T400系列（地図×評価軸連動モデル再設計）はこの技術的制約を踏まえ、「ルート確定前は
   個別評価軸を選んで確認する・ルート確定後に初めて合成コストを見る」という現在の
   設計を意図的に採用しており、これはT145の目標を断念したのではなく、T145自身が
   指摘した制約への正しい解として別の場所（ルート結果色分け）に実装されたと判断できる。
- **結論**: 上記2点よりCLAUDE.md・docs/design-principles.mdに反する構造上の問題は
  現存しないと判断し、本タスクは「対応不要」として完了扱いとする。コード変更は無い
  （ドキュメント上の判断記録のみ）。
