# T608. 動的気象レイヤーのデータ取得状態をMapLibreソースイベント非依存の統一IFへ再設計

状態: 完了（2026-09-05）

## 背景

T606（キキクル4種の地図上チップ化+dataStatusドット拡張）・T607（風/勾配road-valueの
COLOR_LOADING導入）の完了後、ユーザーから「動的に取得する（日々変化する）レイヤは、
これですべて『読込中』と『取得済みだが値なし』が区別がつくようになった？」と監査を依頼された。

調査の結果、`buildLayerDataSources`（T87、MapLibreのソースイベントから状態を算出）が
チップ付き動的気象レイヤー9種（降水ナウキャスト・風・雷・竜巻・雷放電位置データ・
キキクル4種）を対象に含めていたが、これらは実際の外部フェッチが自前のJSコード
（`usePolledFetch`等）で行われ、結果を`map.getSource(id).setData(...)`/`setTiles(...)`で
流し込むだけのため、MapLibreのソースイベント（`sourcedataloading`/`sourcedata`/`error`）は
フェッチの待ち時間・失敗を一切観測できないと判明した（ラスタ/ベクタタイルのkindであっても、
実タイル取得の前段にある「フレーム一覧[targetTimes.json等]の取得」自体が自前のJSフェッチの
ため、そちらが失敗するとpayloadが`undefined`のままレイヤーが非表示になり続け、MapLibre側には
何のイベントも発生しない）。加えて`useDynamicWeatherLayers.ts`が既に集計していた
`dynamicLayerLoading`/`dynamicLayerError`は`page.tsx`のどこからも参照されていなかった
（死んだ戻り値）。

ユーザーへ「elevationはともかく、それ以外は外部から情報を取ってきて判定して保持する仕組みは
一緒なはず」と指摘を受け、windVectorを含む全9レイヤーを、MapLibreのソースイベントに頼らず
各要素のフェッチ自身（`usePolledFetch`/`useWeatherGrid`）が持つloading/errorから直接算出する
1つの統一関数（`dynamicWeatherStatus`）へ揃える方針で対応した。

## 対応方針・実装内容

- `hooks/useDynamicWeatherLayers.ts`: `dynamicWeatherStatus(loading, error, hasPayload)`
  という1つの純粋関数を新設。判定順序は`useLayerDataStatus.ts: computeLayerDataStatus`と
  同じ「エラー中 > 読込中 > 読込済みだが値なし」。9レイヤー全てがこの関数を通り、
  `dynamicWeatherDataStatus: Partial<Record<DynamicWeatherLayerId, LayerDataStatus>>`として
  返す。`currentRiskFrames`（キキクル4種共有）・`linearRainbandFrames`（線状降水帯予測
  マップ）のフェッチから`loading`を新たに取り出して使う（従来`data`/`error`のみ参照）。
  従来の集約`dynamicLayerLoading: boolean`/`dynamicLayerError: string | null`
  （どこからも参照されていなかった）は撤去した。
- `components/Map/MapView.tsx`: `buildLayerDataSources`から動的気象レイヤー9種の
  エントリ・`PRIMARY_DYNAMIC_WEATHER_SOURCE`・`primaryDynamicWeatherSourceId`を撤去した
  （T87のMapLibreソースイベント追跡とdynamicWeatherDataStatusの二重管理を避けるため）。
  `elevation`（自前のJSフェッチ層を持たない国土地理院ラスタタイル）のみT87の対象として残る。
- `app/page.tsx`: `useState`だった`layerDataStatus`を`mapViewLayerDataStatus`
  （改善計画T87、MapViewの`onLayerDataStatusChange`が更新）へ改名し、
  `dynamicWeatherDataStatus`（`useDynamicWeatherLayers`の戻り値）とマージした
  `layerDataStatus`を`useMemo`で導出する形へ変更した（両者はキーが重ならないため優先順位は
  不問）。`useDynamicWeatherLayers`の呼び出し・このマージ処理を、これに依存する
  `overlayLayers`（`MapOverlayControls`向けチップ配列）のuseMemoより前へ移動した
  （レンダー順の制約——`overlayLayers`が`layerDataStatus`を参照するため）。
