# T458. DYNAMIC_WAY_VALUE_MATERIALSが軸スタジオのdedicated_way_value_layerと独立したハードコード辞書になっている

状態: 完了（2026-08-31）

- 背景: モジュール設計書作成のため`backend/app/domain/dynamic_way_values.py`を実コードで
  確認したところ、`DYNAMIC_WAY_VALUE_MATERIALS`（`{"wind": ..., "gradient": ...}`という
  軸id→`needs_time`/`needs_bearing`メタデータの辞書）が、`AxisDefinition.
  dedicated_way_value_layer`（DB・軸スタジオ経由で編集可能なフラグ）とは**完全に独立した
  ハードコード辞書**になっていることが判明した（`domain/axis_definitions.py`とは別ファイル、
  DB由来ではない）。`api/routers/region.py`の`GET /api/region/dynamic-way-values/
  {material_id}/...`・`api/dependencies.py`がこの辞書を直接参照する。
- Impact: `docs/design-principles.md`構造仕様2「軸ごとにfrontend側のファイル・関数・定数・
  propを持たない。新しい軸を追加するときフロントのコード変更が一切不要（軸スタジオでの登録
  のみで完結する）状態を仕様とする」の**backend版の同型違反**。現状、3件目の動的材料を
  追加するには(1)軸スタジオで`dedicated_way_value_layer=true`を設定、
  (2)`DYNAMIC_WAY_VALUE_MATERIALS`へ手でエントリを追加してコード変更・再デプロイ、の
  2箇所が必要——軸スタジオの登録だけでは完結しない。
  `services/axis_registry_service.py: _CODE_COUPLED_AXIS_IDS`にgradientが残っている
  直接の原因でもある（このハードコードがある限りgradientの行削除は安全でない）。
- 対応方針（未検討）: `needs_time`/`needs_bearing`を`AxisDefinition`の新規フィールドとして
  軸スタジオから設定可能にし、`DYNAMIC_WAY_VALUE_MATERIALS`を`AXIS_DEFINITIONS`から
  `dedicated_way_value_layer=true`の軸を抽出して導出する形へ置き換える。着手前に
  既存2軸（wind/gradient）のneeds_time/needs_bearing値がDB側フィールドと矛盾なく移行
  できるか確認すること。
- Confidence: High（`region.py`・`dependencies.py`の実際の参照箇所を直接確認済み）。
- 規模M（軸スタジオのフィールド追加＋backend参照箇所の置き換え＋移行）。

## 実施記録（2026-08-31完了）

対応方針どおり、`needs_time`/`needs_bearing`を`AxisDefinition`の新規フィールド
（`dynamic_way_value_needs_time`/`dynamic_way_value_needs_bearing`）として軸スタジオから
設定可能にし、`DYNAMIC_WAY_VALUE_MATERIALS`（固定dict）を`AXIS_DEFINITIONS`から
`dedicated_way_value_layer=true`の軸を抽出する関数`dynamic_way_value_materials()`へ置き換えた。

- `domain/axis_definitions.py`: `AxisDefinition`へ2フィールド追加（`dedicated_way_value_layer`
  と同じ「軸の評価ロジックから自動導出できない工学的事実」という位置付け）。
- DB: migration `0028_axis_definitions_dynamic_way_value_needs.sql`（DDLのみ、
  `0027`と同じ方針）、`axis_definition_models.py`・`axis_definition_repository.py`
  （row↔definition往復）・`axis_admin.py`（`AxisDefinitionFields`へ追加、GUI編集UIは
  time_scope等と同様に現時点で未対応）を配線。
- `domain/dynamic_way_values.py`: `DYNAMIC_WAY_VALUE_MATERIALS`（固定dict）を
  `dynamic_way_value_materials()`（`AXIS_DEFINITIONS`由来の動的導出関数）へ置き換え。
  呼び出し元（`api/dependencies.py: get_dynamic_way_value_service`・
  `api/routers/region.py: region_dynamic_way_values`）を追従。material_id→サービス実装
  本体の組み立て（`_DYNAMIC_WAY_VALUE_SERVICE_FACTORIES`、T460）は別軸のまま維持
  （Python実装本体の登録は宣言だけでは代替できないため、意図的にスコープ外）。
- `services/axis_registry_service.py`: `_CODE_COUPLED_AXIS_IDS`から`gradient`を除去
  （空集合になったが、将来のハードコード再発に備え仕組み自体は残す）。
- **開発DB backfill**: 一回限りのスクリプト（`AxisRegistryAdminService.unpublish`→
  `update(is_published=True)`、axis_admin APIと同じ手順をDB直結で実施、実行後削除）で
  wind（needs_time=True, needs_bearing=True）・gradient（needs_time=False,
  needs_bearing=True）を実際の値へbackfillした。`dump_axis_definitions_snapshot.py`で
  スナップショットを再生成・コミット（[docs/deployment-sync.md](../deployment-sync.md)の
  「開発DB・本番DB双方への適用を一体の作業として扱う」ルールに従い、**本番DBへの反映は
  この完了記録の時点では未実施**——本番反映を別途実施すること）。
- テスト: `test_dynamic_way_values.py`（AXIS_DEFINITIONSベースの導出ロジックへ全面書き換え）・
  `test_region_routes.py`（`DYNAMIC_WAY_VALUE_MATERIALS`直接monkeypatchから
  `AXIS_DEFINITIONS`へのダミー軸差し込みへ変更）・`test_axis_registry_service.py`
  （実在軸依存の「拒否」テストを、架空axis_idを`_CODE_COUPLED_AXIS_IDS`へmonkeypatchする
  汎用テストへ置き換え、gradientを「削除許可」側へ移動）・`test_axis_definition_repository.py`・
  `test_axis_admin_routes.py`（新規往復テスト追加）・`tests/realistic_axis_fixtures.py`
  （wind/gradientのdedicated_way_value_layer等を実DB値と一致させ更新）。
- docs: `docs/architecture.md`・`docs/modules/backend/axis-studio.md`・
  `docs/modules/backend/dynamic-way-values.md`を現状へ更新。
