# T540: 周回探索で距離許容を超えた時点でレグ3を探索しない早期打ち切り

状態: 完了（2026-09-02起票、[T522](T522.md)「評価ロジック全体の再点検」で判明。
回帰・境界テストでpush前の正しさを確認済み、pytest全件[postgis含む]1581件green。
T536後は`trace_ms`全体への寄与が5〜8%程度に縮小しているため、本番での定量的な
before/after計測は完了条件に含めず、正しさの担保（テスト）のみをもって完了とする）

- 背景: `RoadGraphEngine.trace_loop`は各方位で3レグ（起点→A→B→起点）を順に探索し、
  距離フィルタは`RouteGenerator.generate_loops`が全レグ完了後に適用する。本番VM実測
  （東京駅30km、許容±5km）では8方位中2方位（38.9km・47.8km）が棄却され、その分の
  レグ3探索が無駄になった。
- 対応方針: `trace_loop`へ距離上限（`distance_km + distance_tolerance_km`）を渡し、
  レグ1＋レグ2の累計が上限を超えた時点で`RoutingError`相当の「距離超過」として
  打ち切る（`generate_loops`側は`filtered_out`と同じ扱いで集計し、
  `no_candidates_reason`の文言も従来と同じ「指定距離から外れました」へ寄せる）。
  レグ3の下限（B→起点の直線距離）を足しても上限を超える場合も同様に打ち切れる。
  経由地指定ルート（`bearing=None`）は距離フィルタを行わないため対象外。
- 関連: [T536](T536.md)（探索が高速化すれば効果は小さくなるが、無駄な探索を減らす
  意味は残る）、[T531](T531.md)（フロンティア方式では別の構造になる）。
- 完了条件: 打ち切りが距離フィルタと同じ集合を棄却する（結果の候補集合が変わらない）
  回帰テスト、`test_route_generator.py`の既存テストがpass。

## 実装メモ

- `domain/errors.py`に`RouteDistanceExceededError(RoutingError)`を追加。通常の
  `RoutingError`（経路そのものが見つからない等）と区別し、`RouteGenerator.
  generate_loops`が距離フィルタ棄却（`filtered_out`）と同じ扱いで集計する。
- `LoopRoutingEngine.trace_loop`（Protocol）・`RoadGraphEngine.trace_loop`へ
  `max_distance_km: float | None = None`引数を追加。`generate_loops`は
  `distance_km + distance_tolerance_km`を渡し、`generate_via_waypoints`
  （`bearing=None`）は渡さない（対象外のまま）。
- `RoadGraphEngine.trace_loop`内の`_trace_segments`が各レグ完走後に累計距離
  （`context.graph.edges[edge_id].distance_m`合計、hydrate不要）を積算し、最終レグへ
  入る直前に`context.graph.nodes`の実座標同士の直線距離（`haversine_distance_km`）を
  最終レグの下限として加算した値が上限を超えるかを`_distance_limit_certainly_exceeded`
  （新規の小さな純関数、境界は棄却しない側`>`に倒す）で判定する。超えていれば最終レグの
  A*探索を呼ばず`RouteDistanceExceededError`をraiseする。
- `generate_loops`の結果集計ループへ`RouteDistanceExceededError`の分岐を追加し、
  従来の`filtered_out`（全レグ完了後の距離フィルタ棄却数）へ早期打ち切り数を合算する。
  ログ・`no_candidates_reason`は分岐を増やさず、そのまま流用。

## 検証結果

- 回帰テスト（`backend/tests/test_road_graph_engine.py`）:
  `test_early_cutoff_rejects_exactly_what_post_hoc_distance_filter_would`で、
  早期打ち切り無し（`max_distance_km=None`）版が「距離超過で完走するがpost-hoc
  フィルタで棄却されるはずの候補」を返すこと、同じ入力へ早期打ち切りを有効にすると
  `RouteDistanceExceededError`で打ち切られること、許容範囲内の方位は打ち切り有無に
  関わらず同じ距離のTracedLoopを返すことを確認。
  `test_early_cutoff_skips_final_leg_search_entirely`で、レグ3のEdgeを完全に削除した
  グラフでも早期打ち切りが機能していれば`RouteDistanceExceededError`
  （もし機能せずレグ3を実際に試みていたら代わりに汎用`RoutingError`「no path found」
  になるはずの状況）になることを確認し、レグ3の探索自体が省略されていることを
  間接的に立証。
- 境界テスト: `test_distance_limit_certainly_exceeded_boundary`で
  「レグ3の下限を足すとちょうど上限に一致する」（棄却しない）・「わずかに超える」
  （打ち切る）・「レグ1+レグ2だけで既に上限超過（下限ゼロでも成立）」の3ケースを
  純関数レベルで確認。
- 既存テスト: `test_route_generator.py`・`test_road_graph_engine.py`は
  `LoopRoutingEngine.trace_loop`のシグネチャ変更に伴い`FakeEngine.trace_loop`へ
  `max_distance_km=None`引数を追加した以外は無修正でpass（62→66件・26→30件、
  いずれもgreen）。`pytest backend/tests -q -m "not postgis"`全体も1343件green。
- 実DB計測（開発機ネイティブPostgreSQL、東京都心南部データ、distance_km=30・
  tolerance_km=5、`open_route_generation_setup`経由でAPI層を介さず`generate_loops`を
  直接複数回呼び出し）: 早期打ち切りが実際に発火する起点（road_nodes上の実ノード、
  8方位中2方位が距離超過）で比較したところ、打ち切り対象の2方位は`trace_loop`
  `wall_ms`が約47ms→約31ms（3レグ→2レグ）に短縮された一方、8方位合計の`trace_ms`
  全体では数十ms（全体の5〜8%程度）の縮小に留まった。**T536（探索の静的行列化＋
  ベクトル化）により1レグあたりのA*探索が既に十数〜数十msまで高速化済みのため、
  レグ1本の省略で得られる絶対的な短縮幅も同程度まで縮小しており、T540起票時点
  （本番VM実測でレグ3探索が数秒〜十数秒を占めていた頃）に想定していたほどの効果は
  もはや無い。** それでも「距離フィルタで確実に棄却される候補の探索を省く」という
  正しさ自体は保たれており、退行や副作用は確認されなかった。
