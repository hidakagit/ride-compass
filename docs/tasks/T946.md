# T946. 較正値（T805）の後始末 規模M

状態: 完了（2026-09-19起票・2026-09-20完了、統合レビュー第11回のP2/P3）

## 背景

T805が導入した較正値の仕組みのうち、宣言から導けていない箇所と、層構造の逸脱。
対象は[history/2026-09-19_all.md](../../.claude/commands/review/history/2026-09-19_all.md)「Findings（P2）」の「較正値（T805）」節（20〜24。25は[T936](T936.md)が扱う）。

## 対応（2026-09-20）

### 23: ORMとmigrationの食い違い

`tuning_overrides.updated_at`はmigration 0043の`CREATE TABLE`にあるのにORMが持って
いなかった。fresh bootstrapは`create_tables()`→`apply_pending_migrations()`の順で走り、
ORMが先に表を作るため`CREATE TABLE IF NOT EXISTS`は何もしない。migrationで表ができた
環境にはこの列があり、fresh bootstrapで作った環境には無い状態だった。

**同じ性質の箇所を先に数えた**。migrationがCREATEする16表のうち食い違いは1表だけで、
レビューが挙げたこの1件が唯一の実例。数え方はmigrationのDDL（CREATE/ADD/DROP/RENAMEを
古い順に畳む）とORMの列宣言の突き合わせ。**正規表現で読んだ結果がSQLAlchemyの実メタ
データと23表すべてで一致する**ことを別途確かめてから使っている。

再発は`scripts/review_checks.py`の検知器にした（`orm_migration_column_drift`）。既存の
`declared_tables`が表の名前だけを見るのに対し、こちらは列まで見る——母集団は重ならない。

あわせて`read_overrides`の救済を**SQLSTATE 42P01（表が無い）だけ**に限定した。
`ProgrammingError`を丸ごと受けていたため、**列が足りないだけでも「上書きが1件も無い」と
して飲み込み、較正値が黙って既定値へ戻る**。この修正の過程で、列の無いDBに対して実際に
その経路を通り、限定後はその場で落ちることを確認している。

### 20: フロント側の独自既定

`stretchAlternativeGroups`の`minSplitLengthKm`が`?? 0`で、引けないと**共有地点すべてで
区間を割る**（較正したのとは別の切り方）。省略できない引数にし、呼ぶ側は引けなければ
乗り換えの候補を作らない形にした。

実際に効くのは**backendの宣言からこのidが消えた/綴りが変わったとき**（カタログが届く前も
ビルド時生成物が値を持つため）。フロントが読むidを`CLIENT_TUNING_IDS`へ集め、生成物に
在ることをテストで固定した。

### 21: 効き方の対応表の手書き複製

`TuningPanel`が効き方→見出しの対応表を持っており、生成型が`string`なので綴りの型検査も
効かなかった。backendが効き方を1つ足すと、画面はそれを知らず名前の無いまとまり
（「その他」）へ落とす——値は出るが「何をすれば効くのか」だけが失われる。

見出しを`TuningEffect`自身に持たせ（メンバーは値と見出しの両方を必ず書く形なので、
書き忘れはクラス定義時に落ちる）、APIが`effect_title`として各項目へ添える。並び順も
backendが宣言順で返し、画面は返ってきた順にまとめるだけにした。

### 22: ルーターがcommitする

`session.commit()`/`rollback()`を持つルーターはリポジトリ全体でここ1本だけだった
（[design-principles.md](../design-principles.md)構造仕様7）。`services/tuning_service.py`へ
移し、書き込みの直後にプロセス内の値まで反映するところも含めてサービスが持つ。

### 24: route handlerのテストが0本

`/admin/api/tuning`と`/admin/api/tuning/[paramId]`のテストを足した（兄弟の
axis-definitionsと同じ形）。較正値のidは必ずドットを含むため、ドットがそのまま通ることを
別の1本で固定している。

## 途中で撤回したもの

テストDBに`updated_at`が無い状態を「ALTERを流して揃える手順」として仕組み化しようとし、
スクリプトとdocs/testing.mdの節を作ったが、**両方とも撤回した**。テストDBの表はORMの
`create_all`から作られ、複製元の表は作成直後に落とされる（`tests/conftest.py`）ので、
正しい対処は**自分の作業ツリーのDBを落として作り直させる**だけだった。症状（列が無い）
への手順を作る前に、その状態がどうやって生まれるかを見ていなかった。

## 検証

| わざと戻した内容 | 落ちたもの |
|---|---|
| ORMから`updated_at`を落とす | `orm_migration_column_drift`が「migrationにだけある」で検知 |
| どのmigrationにも無い列をORMへ足す | 同検知器が「migrationに無い」で検知 |
| 生成物から較正値のidを落とす | `フロントが読む較正値は、どれもビルド時生成物に在る`（新設） |
| idのドットを`%2E`へ変換する | route handlerのテスト2本（新設） |
| 効き方の見出しを画面側の固定文言へ戻す | `TuningPanel`のテスト2本 |

`updated_at`は、作業ツリーのテストDBを落として作り直し、ORMから列が作られることまで
確認した（再現時は`UndefinedColumnError`で落ちていた）。

「その他」へ落ちることを固定していたテストは、**劣化の許容**だったので置き換えた——
新しい効き方がその見出しのまま出ること、「その他」が出ないことを見る。

全体: backend `ruff check app scripts benchmarks tests`・`pytest -q -m "not postgis"`・
`pytest -q -m postgis`、frontend `tsc --noEmit`・`eslint`・`prettier --check`・
`vitest run`、OpenAPI再生成後の生成物クリーン、
`python scripts/review_checks.py docs` 違反なし。
