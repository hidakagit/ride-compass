# T960: 材料の導出SQLに、人が書いた期待値のテストが無い

状態: 完了（2026-09-19）

## 背景

材料の導出は2か所にある——`material_catalog.py`のPython extractor（探索）と
`osm_way_tag_sql.py`＋タイルSQL（地図配信・カバレッジ集計・軸スタジオの値列挙）。

**期待値のテストはPython側にしかなかった**（`tests/test_material_catalog.py`）。SQL側の式を
検証するテストは無く、地図が配っている色は検証されていない導出から出ていた。

[T955](T955.md)の調査で本番の1タイル（42,134区間）を手で突き合わせ、両方が実装する材料は
すべて一致することは確かめたが、CIは何も見ていなかった。

## 対応

`tests/test_osm_way_tag_sql.py`を新設した。人が書いた入力と期待値を1つの表で持ち、
**同じ期待値をSQL側とPython側の両方へ当てる**。

実DBへ接続するがテーブルは作らない——断片は`FROM osm_raw_ways AS w`を前提にエイリアス`w`
だけを参照するため、同じ列を持つCTEを`w`と名付ければ式そのものを評価できる。
式は`osm_way_tag_sql.py`の定数から組み立て、テストへ書き写さない。

## 見つかったもの1: `surface`材料がPython側だけ正規化されていなかった

`MATERIAL_CATALOG["surface"]`のコメントは「OSMのsurfaceタグ生値（正規化: lower/btrim）」と
宣言しているが、`_extract_surface`は`osm_raw_ways.surface`をそのまま返していた。SQL側は
`lower(btrim(w.surface))`。`surface_good`（`classify_osm_surface`が正規化）・`smoothness`
（`normalize=True`）とも揃っていない。

`_extract_surface`へ正規化を足した（宣言とSQLが一致していて実装だけが外れていたため、
SQL側を正とした）。

**実害は今は無い**: 本番の`osm_raw_ways.surface`（201,712行）に正規化で値が変わるものは
0件で、`surface`をカテゴリで使う軸も無い。ただし軸スタジオから作成でき、OSMのタグは
第三者が編集するため、値が入った瞬間に地図と探索で違う分類になる。

## 見つかったもの2: 真偽の材料は、SQL側の表現力が足りない

タイルSQLは`CASE WHEN 条件 THEN true END`で「該当しない」と「判定できない」をどちらも
NULLへ畳む（フィーチャーからキーを省いてタイルを軽くするための符号化）。extractorは
way_tagsがあればFalse、無ければNoneを返し、この2つを区別する。

例外は`surface_good`だけで、SQL側も`true`/`false`/NULLを区別する。「路面タグ不明」を
「路面が悪い」と混同しないという要求が、符号化より優先された唯一の材料である。

いまの両者に言えるのは「SQLがtrueを返すのはPythonがTrueのときだけ」までで、テストも
そこまでを固定している。[T956](T956.md)で導出をSQLへ移すときは
`CASE WHEN w.tags IS NULL THEN NULL ELSE 条件 END`へ変え、falseを表せるようにする必要がある
（畳んだままだと、`bicycle_infra_quality`が「自転車道が無い」と「分からない」を
同じものとして評価する）。

- **効いていることの確認**: `LIT_NORMALIZED_SQL`を`lit`から`lighting`へ書き換えると
  「舗装・街灯あり・制限速度40・2車線」のSQL側が落ちる（`assert None == True`）。戻して
  35 passedを再確認した。
- `pytest tests/test_osm_way_tag_sql.py tests/test_material_catalog.py tests/test_evaluation.py -q`
  → 148 passed
