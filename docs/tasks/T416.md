# T416. 洪水キキクル（`.pbf`形式）の実装検討（T410で他3種のキキクルと異なり見送り）

状態: 完了（2026-08-31）

- 背景: [T410](T410.md)（キキクル+線状降水帯予測マップの実装）で、土砂・大雨・浸水
  キキクルと線状降水帯予測マップの4レイヤーはラスタタイル（PNG画像）として実装したが、
  洪水キキクル（`flood`）だけは`.pbf`（Mapbox Vector Tile）形式でデータ表現が異なるため
  同じ方式では実装できず、「別方式が必要になり、本タスクのスコープ外（別タスク起票が
  必要なら追って検討）」として見送られていた。以降タスク番号を振られないまま埋もれていた
  （2026-08-30、CLAUDE.md「分割元タスク完了前のフラグ回収」ルール新設に伴う既存docs監査で
  発覚）。
- 補足: `frontend/src/components/Map/mapLayers.ts`の氾濫危険情報（`flood_client.py`・
  `floodForecasts`、T212/T257等）は河川の氾濫**警報**（点/バッジ表示）であり、本タスクの
  対象である洪水キキクル（**危険度分布**の面的なラスタ/ベクタタイル表示）とは別機能・
  別データソースのため混同しないこと。
- 影響: 「現在の防災リスク」という括りで土砂・大雨・浸水・線状降水帯の4種は地図上に
  表示できるようになったが、洪水（河川氾濫由来の浸水想定）だけ同じ括りから欠けている。
  実害は「4種類のキキクルのうち1種類だけ見られない」という機能の不完全さのみで、
  既存表示が壊れる等の破綻はない。
- 対応方針（未検討、着手時に決定）: 洪水キキクルの`.pbf`タイルの実際のURL・スキーマを
  T410と同じ手順（`https://www.jma.go.jp/bosai/risk/`をBrowserペインで操作し
  `read_network_requests`で実タイルURLを裏取り）で確認し、MapLibreの`vector`ソースとして
  読み込めるか、それとも独自のデコード・描画が必要かをまず切り分ける。

## 調査結果（2026-08-31、着手時の実機確認）

Browserペインで`https://www.jma.go.jp/bosai/risk/`を操作し「浸水・洪水 重ね表示」を
ONにして`read_network_requests`で実際の通信を確認、加えて`risk.properties.xml`
（`vectorTileLayerStyles`定義、JMA公式のスタイル関数がそのまま埋め込まれている）を
直接fetchして解析した。

- **URL/取得方式**: 他3種（土砂・大雨・浸水）と完全に同型
  （`.../risk/{basetime}/{member}/{validtime}/surf/flood/{z}/{x}/{y}`）で、拡張子だけ
  `.pbf`。`targetTimes.json`も共通（`elements`配列に`"flood"`が含まれる）で追加のfetch
  エンドポイントは不要。**backend側の変更は一切不要と判明**——`jma_tile_client.py`の
  プロキシは`bytes, content-type`をそのまま透過するpath丸ごと方式（拡張子・
  Content-Typeの判定を一切していない）のため、`.pbf`もノーコードでそのまま流れる。
- **スキーマ**: source-layer名は`flood`（`vectorTileLayerStyles`のプロパティキーが
  Leaflet.VectorGrid.Protobufの仕様上そのままsource-layer名になる、`risk.properties.xml`
  で確認）。フィーチャーは河川をなぞるLINE形状で、プロパティ`level`（1〜4の危険度、
  既存の`RISK_LEVEL_COLORS`と完全に同じ配色: 1=`#f2e700`黄・2=`#ff2800`赤・
  3=`#aa00aa`紫・4=`#0c000c`黒）・`type`（"nation"等の河川管理区分、未使用）を持つ。
  MapLibre GL JSは標準のMapbox Vector Tile形式をvectorソースとしてネイティブ対応する
  ため、pbfのデコード・パースに独自実装は一切不要。
- **feature-stateも不要と判明**: 当初「ベクタタイル＋feature-state式スタイリングは
  対応外」と見送っていたが、実際はJMA配信元のタイル自体に表示値（`level`）が
  プロパティとして焼き込み済みのため、風/勾配のway_id値配信（feature-state方式）とは
  性質が異なり、MapLibreのpaint式（`["get","level"]`のmatch）だけで色分けできる。
  gridFill/gridMarkより実装は単純。
- **平常時（level無し）の扱い**: JMA公式サイトは薄い水色（`#3cffff`）の基準線として
  常時描画するが、本アプリは他3種のラスタタイル（平常時は透明）と挙動を揃えるため
  `level>=1`のフィーチャーのみ表示する方針とした。
- **関連するが対象外の製品**: 同じtargetTimes.jsonのelementsに`flood_mesh`・
  `designated_river(_nation)`・`inland_flood`（内水氾濫、texture塗りの別スキーム）・
  `flood_riskline`も存在するが、本タスク（洪水キキクルのみ）のスコープ外として
  未実装のまま残す（将来別タスクが必要なら`risk.properties.xml`の`vectorTileLayerStyles`
  該当ブロックを参照すること）。

## 実装（2026-08-31）

調査の結果、実装は十分小さくまとまると判断し同日中に完了させた。

- `dynamicWeather.ts`: 「表現は2パターンのみ+rasterTile例外」という設計原則コメントを
  更新し、`DynamicWeatherRenderPayload`へ`{kind:"vectorTile", tileUrlTemplate}`を追加
  （feature-state不要のためペイロード自体はrasterTileと対称的にURLのみ運ぶ）。
  `ALWAYS_ON_DYNAMIC_WEATHER_LAYER_IDS`へ`floodRisk`を追加（他3種と同じ「常時マウント・
  チップ無し」防災カテゴリ、`mapLayers.ts`側の変更は不要——他3種もMapLayerIdを持たない）。
- `riskMap.ts`: `CurrentRiskFrames`へ`flood`フィールドを追加、`fetchCurrentRiskFrames`が
  同じtargetTimes.jsonから`flood`要素も抽出するよう拡張（追加fetch無し）。
  `tileUrlTemplate`に拡張子引数（既定`"png"`、洪水のみ`"pbf"`）を追加。
  `floodRenderPayload`を新設。
- `MapView.tsx`: `DynamicWeatherVectorSpec`（source-layer名・色/太さ式・フィルタ用
  valueProperty/minValueToShow）を新設し`DynamicWeatherRendererSpec`へ追加。
  `RISK_LEVEL_COLORS`をimportし`FLOOD_RISK_LINE_COLOR_EXPRESSION`
  （level→色のmatch式）・`FLOOD_RISK_LINE_WIDTH_EXPRESSION`（zoom依存の太さ）を新設。
  `DYNAMIC_WEATHER_RENDERERS.floodRisk`エントリを追加。`ensureDynamicWeatherLayer`/
  `applyDynamicWeatherState`（raster/gridFill/gridMarkの3分岐と同じ形）へ`spec.vector`
  分岐を追加（`type:"vector"`ソース+`type:"line"`レイヤー、`setTiles`でURL差し替え）。
- `useDynamicWeatherLayers.ts`: `floodRiskPayload`を追加（他3種と同じ
  「frames[0]があれば常時表示」方針）、`dynamicWeather`オブジェクトへ`floodRisk`エントリ
  を追加。
- テスト: `riskMap.test.ts`へ`floodRenderPayload`（kind=vectorTile・拡張子.pbf確認）・
  `fetchCurrentRiskFrames`のflood抽出を追加。`useDynamicWeatherLayers.test.ts`の
  `EMPTY_CURRENT_RISK_FRAMES`フィクスチャへflood追加（型エラー修正、既存の
  landslideRisk/heavyRainRisk/inundationRisk自体もこのフックレベルでは専用テストを
  持たない既存の粒度に合わせ、flood単体の新規フックテストは追加していない）。
- 検証: `npx tsc --noEmit`・変更ファイルの`eslint`・`npx vitest run`（frontend全体、
  872件）すべて成功。**実機（Browserペイン）確認は今回未実施**——作業ツリーが並行
  セッションのdevサーバーと共有状態だったため、自セッションで別のdevサーバーを
  起動すると衝突するリスクを避けた。次回このリポジトリでdevサーバーを起動した際に
  「防災」系レイヤー（土砂・大雨・浸水キキクルと同様、常時表示・チップ無し）として
  洪水キキクルの実際の描画（現状は全国的に危険度が低くlevel>=1のフィーチャーが
  存在しない可能性が高いため、河川沿いに色付き線が見えないこと自体は異常ではない）
  を確認することが望ましい。
