# T843. 乗り換え先の道の上にある分岐へ、そのまま乗り継げるようにする

規模M。
状態: 完了（2026-09-16。段階1は2026-09-14、段階2は2026-09-16）

## いまできること・できないこと

[T838](T838.md)で、元ルートと候補が同じ地点を通る所で区間を割り、区間ごとに別の候補を
選べるようになった。合成したルートを作り直せば、それを元にもう一度編集もできる。

できないのは、**一度の編集の中で「乗り換え先の道の上にだけある分岐」へ進む**こと。代替は
常に「いまの元ルートとの差」として求めるため、候補Bの道へ乗り換えた後、そのBの道の途中で
候補Cへ移る、という鎖は`作る→再編集`を挟まないと組めない。

## backendへの影響（2026-09-14に確認）

**合成の受け口は無改修で足りる。** `road_graph_engine.py: build_traced_from_edge_ids`は
送られたEdge id列について「このグラフに実在し・順につながり・起点から始まる」ことだけを
検証する。列がどの候補から来たかは問わないため、`元+B+C+元`のような鎖もそのまま評価できる。

ただし2点、backend側の論点がある。

- **終点を検証していない**。起点と連結性は見るが、最後のEdgeが目的地へ着くかは見ない。
  いまは合成が元ルートの末尾を必ず残すため起こらないが、自由に鎖を組めるようにすると
  「つながってはいるが目的地に着かない」列が評価され、候補一覧へ並びうる。
- **ノードidを返していない**。フロントは「同じ地点か」を座標の完全一致で判定している
  （どちらも同じグラフのノード由来なので実質一致する）。候補どうしを突き合わせて鎖を
  伸ばすほど、この代用が効かない場面の影響が読みにくくなる。

## 段階

1. **フロントだけで組む**（backend無改修）。選択のたびに「いまの組み合わせ」を元に区間を
   計算し直す。合成後のEdge列とつなぎ合わせた座標列はフロントで組める（各候補の
   `geometry.coordinates`と`edge_point_offsets`から切り出して連結する）。これで乗り換え先の
   道の上の分岐も次の一手として現れ、`作る→再編集`の往復も要らなくなる。
2. **backendがノードid列を返す**（`edge_ids`と並べて）。座標一致の代用をやめる。併せて
   合成の検証へ終点の確認を足す。

## 論点

- 選択肢の数。候補が8本あると候補どうしの接点は一気に増える。T838で入れた「10区間で畳む」
   だけでは足りない可能性が高い
- 鎖が同じ地点を2度通る形（折り返し）を作れてしまう。backendは連結性しか見ないため、
  フロント側で弾くか、backendの検証を足すか

## 段階1の実装（2026-09-14。列挙をやめ、地図で1手ずつ選ぶ形へ）

最初は「区間ごとに、端から端まで通る道を全部作って並べる」形で実装したが、乗り換え地点が
k個あると組み合わせが2^k個になり、上限で打ち切る＝**選べるはずの道を黙って捨てる**ことに
なる。継いだ道は複数候補にまたがるため地図の帯も描けない。ユーザー指摘を受けて作り直した。

**選ぶのは地図、パネルは結果だけ**にする。

- `lib/routeSplice.ts: buildSplicedShape`が「いまの組み合わせ」の形（Edge列＋座標＋Edge境界）を
  組む。次に選べる区間はこの形との差として求めるため、**乗り換えた先の道の上にある分かれ道が
  そのまま次の帯になる**。列挙も上限も要らない
- 適用した乗り換えは積み上げる（`appliedAlternatives`）。各要素の範囲はその時点の形に対する
  位置のため途中だけは外せない——戻せるのは直前の1手（ユーザー判断）
- 座標やEdge境界を持たない候補では、経路のつなぎ替えだけを行う（区間の割り直しはできないが
  差し替えは成立する）
- パネルはルート結果と同じ指標（距離・所要・総合難易度・負荷）で元と編集後を並べる。
  軸別は2本のバーを並べず、**差だけの1本**（中央が0、左が楽になった側、長さが変化量、色は
  軸チップと同じ）。動きが0.1未満の軸は出さない
- 「編集後」は評価してから入る。区間を選ぶたびに投げない方針は変えていない

検証:

- `buildSplicedShape`の単体テスト（座標とEdge境界のつなぎ直し・積み重ね・座標が無い候補）
- パネルのテスト（指標・差分バー・1つ戻す・評価中の抑止）
- 地図の帯タップで乗り換わり、合成したルートからさらに乗り換えられることを`page.test.tsx`で確認
- 実機相当（Playwright・モバイル幅390px）で新しいパネルを撮って確認
- `npx vitest run` 142ファイル1335件 passed、`tsc --noEmit`・`eslint`クリーン

## 段階2の実装（2026-09-16）

### backendが`node_ids`を返す

`RouteCandidate.node_ids`（`edge_ids`より1件多く、`node_ids[i]`が`edge_ids[i]`の始点、
末尾が終点。`edge_point_offsets`と同じ形）。フロントは「候補どうしが同じ地点を通るか」を
座標の完全一致で見ていたのをやめ、グラフが持つ同一性をそのまま使う
（`routeSplice.ts: splitPairedStretch`）。`buildSplicedShape`もEdge idと同じ位置で
Node idを継ぐ——継ぎ目のNodeは両者で同じ（共有地点でしか乗り換えない）ため、相手側は
差し替える区間の始点だけを取り、終点はこちら側の続きが持つ。

### 合成の検証へ終点の確認を足す

`build_traced_from_edge_ids`は起点と連結性しか見ておらず、**途中で止まる列が評価に成功して
候補一覧へ並びえた**。`destination`を渡したときだけ最後のEdgeの終点を確かめる。

終点は起点と同じ`find_nearest_node_indexed`で解く。目的地がメインの道路網から孤立していて
backendが補正した場合でも、フロントは補正後の地点を条件として持ち直しており
（`page.tsx`の`corrected_destination`→`generatedConditions.input`）、合成もその地点で
送られるため、比べる相手は元の候補が実際に終わったNodeになる。

### 同じ地点を2度通る鎖は、フロントが弾く

**backendには足さない判断にした。** 折り返しは走れはするので「経路として成立しない列」では
なく、backendが`RoutingError`で落とすと地図のタップが（`prepare`を挟んだ後に）エラーへ
変わる。この画面で折り返しを選びたい場面は無いため、**選択肢として出さない側**で止める
（`routeSplice.ts: createsRevisit`。当てると元の経路の別の地点へ戻る代替を
`stretchAlternativeGroups`が落とす）。

見るのは差し替えで新しく入る内側のNodeだけ。両端は元と共有する地点で、差し替えで消える
内側のNodeとぶつかっても折り返しにはならない。元ルートのNode集合は候補ごとに作り直さず
1回だけ組む。

**backendの検証とフロントの抑止で担当を分ける**という整理になった——backendは「経路として
成立するか」（実在・連結・起点・終点）、フロントは「選ばせてよいか」（折り返し）。

### 検証

- `routeSplice.test.ts`へ折り返し除外の2件（当てると戻る代替は出さない／元と触れない道は
  これまでどおり選択肢になる）。既存の区間分割テストの足場は座標一致からNode idへ書き換えた
- `test_road_graph_engine.py`へ終点検証の3件（着かない列を落とす／着く列は通す／
  `destination`を渡さなければ終点を見ない）
- **どちらも効いていることを確認した**: 終点の検証・折り返しの除外をそれぞれ外すと、
  その新テストだけが落ちる
- `npx vitest run` 142ファイル1383件 passed、`tsc --noEmit`・`eslint`クリーン
- backend `pytest -q -m "not postgis"`、`ruff check app tests scripts`
- OpenAPI生成物を再生成（`node_ids`の追加ぶん）

## 残り

段階2で挙げた3点は完了。論点として残っていた「選択肢の数」（候補が8本あると接点が増える）は
段階1で列挙をやめた時点で解消している——次に選べる区間は「いまの組み合わせ」との差として
その都度求めるため、組み合わせを先に並べる必要が無い。

## 実機で直したもの（2026-09-14）

- **いま作っているルートを地図へ描く**。乗り換えても地図は元の候補線のままで、「乗り換え部分が
  薄い灰色、元が太い灰色」で区別できなかった。乗り換えと同じ暖色の太い実線
  （`SPLICED_ROUTE_LAYER_ID`、縁取り付き）を候補線の上へ重ねる。破線＝乗り換えられる先、
  実線の太い線＝いま通る道、で読み分ける
- **差分バーの端の文言を記号へ**。「← 楽になった」「きつくなった →」は口語的で幅も取るため
  `−`と`＋`だけにし、中央へ`0`を置く
- **中央の0を目立たせる**。1pxの薄い線では左右どちらへ出ているか読めなかった。2pxの前景色へ
  変え、棒より上下へはみ出させて目盛りとして立てる

## 省スペース化（2026-09-14）

実機で10行ぶん（約260px）まで伸びていたため5行以下へ詰めた。**削ったのは情報ではなく器**。

- 「元／編集後」の列見出し → 1セルに`6.0→7.7km +1.8`を収めるので不要
- `− 0 ＋`の行 → 記号をバーと同じ行の両端へ移し、0は中央線そのものが担う
- 「N回乗り換え」の行 → 見出しへ`N回`
- 「1つ戻す」の行 → アイコン（`UndoIcon`）にして操作列へ。併せて**全部戻す**
  （`UndoAllIcon`）も足した。どちらも乗り換えが1つ以上あるときだけ出す

指標は2列×2行で、半分ごとに同じ列幅を共有させて（`grid-template-columns: subgrid`）
2行の`→`の位置を縦に揃える。評価前は矢印も出さない（行き先が無いのに→だけ残さない）。

実機で測って**127px**（乗り換え前、モバイル幅390px）。

## 実機の指摘3件（2026-09-14）

- **指標の列がずれる**（「所要」と「28分」が縦に揃わない）。半分ごとに1つのgridで5列を
  共有するつもりが、行ごとにラッパのdivを挟んでいたため列幅が行ごとに決まっていた
  （`subgrid`頼みの書き方をやめ、5つの要素をgridの直接の子にした）
- **表示が±0なのに色が付く**。色の判定を生の差で行っていたため、`+0.02km`のように画面へ
  「±0」と出る差でも増減の色が付いていた。**表示する桁で丸めた値**で判断する
- **合成したルートが2本並ぶ**。区間を全部その候補の道へ乗り換えると出来上がりは既存の候補
  そのものになるが、無条件に1本足していた。同じEdge列の候補が既にあれば**増やさずそれを
  選ぶ**。併せて「作る」の連打でも2本入らないよう、実行中フラグをrefで持つ（disabledは
  再レンダーを待つため、その手前の2回目を止められない）
