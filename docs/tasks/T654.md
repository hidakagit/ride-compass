# T654. OSM取込対象（層0）へ自転車の停止要因を追加する 規模S

状態: 実施中（宣言・分類・集計キーの追加は2026-09-10に反映済み。実データは次回PBF再取込待ち）

## 背景

`osm_raw_pois`へ取り込むノードの種類は`backend/app/batch/import_profile.yaml`が宣言する。
現在の対象は信号・横断歩道・一時停止・徐行（`highway=*`）と車道用踏切
（`railway=level_crossing`）だけで、**車止め（`barrier=*`）が入っていない**。
河川敷サイクリングロード等で自転車を停止・降車させる最大の要因が、DBに存在しない。

停止要因のデータは3層あり、やり直しコストが層ごとに3桁違う。

| 層 | 何を決めるか | やり直しコスト | 方針 |
|---|---|---|---|
| 層0 取込 | どの種類のノードを持つか | **数時間**（PBF再取込） | **迷ったら取る**（本タスク） |
| 層1 タグ | ノードのどのタグを持つか | **数時間**（PBF再取込） | 分類根拠と通行可否は残す |
| 層2 集計キー | 数え上げをどう分けるか | 数分（バッチ再実行） | 迷ったら分けない（[T655](T655.md)） |

起票時は層1を「変更不要（`pbf_source.py`がノードのタグを全件保存しているため）」と
していたが、着手時に**誤り**と判明した。`pbf_source.py`は全タグを読むものの、DBへ書く前に
`osm_adapter.py: ALLOWED_NODE_TAGS`（当時は`highway`/`railway`/`crossing`/`shop`/`amenity`の
5キー）で絞っており、`barrier`・`bicycle`・`access`は捨てられる位置にあった。層1もやり直しに
PBF再取込が要るため、層0と同じ「迷ったら残す」で扱う（下記「実装」参照）。

開発DBで確認したところ、信号ノードが持つタグキーは`highway`と`crossing`だけ、踏切の
`crossing:barrier`は0件だが、これは取込で捨てているのではなく**日本のOSMがそう書いていない**
ことによる。

## 追加する取込対象（実施済み）

件数はKanto PBF（Geofabrik、2026-08-15取得、タグ付きノード1,220,034件）の実測。

### 採った

| タグ | 何か | 関東の件数 |
|---|---|---|
| `barrier`（20値、下記） | 車止め・ゲート類 | 36,310 |
| `traffic_calming`（9値、下記） | ハンプ・狭さく等の減速構造 | 1,671 |
| `railway=crossing` | 歩行者・自転車用の踏切 | 2,629 |
| `railway=tram_crossing` / `tram_level_crossing` | 路面電車の踏切 | 225 |

`barrier`の採用値: `cycle_barrier`(3,980)・`bollard`(21,975)・`gate`(8,535)・
`lift_gate`(695)・`turnstile`(610)・`block`(477)・`chain`(270)・`swing_gate`(38)・
`yes`(414)・その他小口（`stile`・`kissing_gate`・`wicket_gate`・`hampshire_gate`・
`bump_gate`・`sliding_gate`・`rope`・`log`・`planter`・`height_restrictor`・
`motorcycle_barrier`、計約320）。

`traffic_calming`の採用値: `choker`(1,201)・`hump`(203)・`bump`(127)・`chicane`(98)・
`table`(29)・`mini_bumps`(6)・`rumble_strip`(6)・`cushion`(1)・`yes`(14)。

**起票時の想定との差**:

- `barrier=chicane`は関東に**0件**だった。食い違い柵は`traffic_calming=chicane`(98)として
  書かれている。起票時の一覧をそのまま実装していたら1件も取れていない。
- `traffic_calming`は「日本の生活道路で増加中／要検討」としていたが、実データでは
  `choker`（狭さく）が1,201件と最多で、ハンプ系より一桁多い。層0の原則（迷ったら取る、
  やり直しはPBF再取込＝数時間）に従い採った。
- 起票時の一覧に無かった`turnstile`・`chain`・`yes`等も採った。**すべて1つの`kind`
  （`barrier`）へ落ちるため、値を増やしても材料の候補は増えない**——「材料の候補が
  数千個になる」という下記の懸念は、タグキーを増やす場合の話で、1キー内の値には
  当てはまらない。

### 採らなかった（件数と理由）

| タグ | 関東の件数 | 理由 |
|---|---|---|
| `barrier=kerb` | 9,488 | 段差。`lowered`(3,908)＋`flush`(1,557)が過半で、`raised`は105件(1.1%)のみ。停止要因としての識別力が無い |
| `barrier=toll_booth` | 1,271 | 料金所。自動車専用道路上にあり、取込対象の道路（層0のhighway一覧）には乗らない |
| `barrier=entrance` | 330 | 塀・柵の開口部＝通れる点 |
| `barrier=fence` / `wall` / `guard_rail` / `jersey_barrier` | 100前後 | 道に沿う構造物で、渡る点ではない |
| `traffic_calming=island` / `no` | 32 | 中央島・「減速構造なし」の明示。進行を妨げない |
| `highway=mini_roundabout` | **3** | 日本では稀という起票時の想定どおり |
| `highway=street_lamp` | 11,229 | 街灯の有無は既にwayのタグ（`lit`）として持っている |
| `highway=turning_circle` / `motorway_junction` | 4,016 | 自転車の停止と無関係 |
| shop / amenity の追加 | — | 補給POIは別目的。停止密度の議論に混ぜない |

「OSM wikiにあるものを全部取る」は採らない。**タグキー**を無制限に増やすと`osm_raw_pois`が
実質「地図全部」になって取込時間と容量が跳ね上がり、材料の候補も数千個になって
[T655](T655.md)で決めた「人間が重みを判断できる粒度」が崩壊するため。判定基準は
「自転車が止まる・降りる・大きく減速する原因になりうる点か」の一点に絞る。

## 実装（2026-09-10）

起票時は「`import_profile.yaml`へルールを足すだけ」の想定だったが、**それだけでは1件も
取り込まれない**ことが着手時に判明した。取込は「プロファイルで拾う→`domain/traffic.py`の
分類器が`kind`を返す→書く」の順で、分類器が`None`を返したnodeは黙って捨てられる
（`osm_adapter.py: osm_node_to_poi_spec`）。同じ理由で、起票時の「層1は変更不要（タグを
全件保存しているため）」も誤りだった——`pbf_source.py`は全タグを読むが、DBへ書く前に
`ALLOWED_NODE_TAGS`（当時5キー）で絞っており、`barrier`・`bicycle`・`access`はすべて
捨てられる位置にあった。

そのため次をまとめて変更している。

| 層 | 変更 |
|---|---|
| 0 取込 | `import_profile.yaml`へ`barrier_nodes`・`traffic_calming_nodes`を追加、`railway_level_crossings`を`railway_crossings`（4値）へ拡張 |
| 0 分類 | `domain/traffic.py`へ`StopPoiKind`の3値（`barrier`・`traffic_calming`・`railway_crossing`）と採用値の集合を追加。優先順位は railway → highway → barrier → traffic_calming |
| 1 タグ | `ALLOWED_NODE_TAGS`へ`barrier`・`traffic_calming`・`bicycle`・`access`を追加（車止めが併せ持つ通行可否を、後から再取込せずに使えるようにする） |
| 2 集計 | `POI_COUNT_KINDS`へ`barrier`（「車止め・減速構造」）を1キー追加。`railway_crossing`は`level_crossing`へ、`traffic_calming`は`barrier`へ畳む |

派生する変更: 材料`poi_barrier_per_km`が`POI_COUNT_KINDS`から自動生成され、路面タイルの
列（`poi_barrier_per_km`）とPOIタイルの`kind`値が増えるため、`ROAD_SURFACE_TILE_VERSION`
20→21・`POI_TILE_VERSION` 3→4・両`precompute_*_attribute_counts.py`の`ALGORITHM_VERSION`
v1→v2を上げ、生成物（`poi-kinds.json`・`material-catalog.json`・`region-tile-config.json`）を
再生成した。フロントは`STOP_POI_CATEGORIES`へ3種を追加（踏切2種は`aliasKeys`で凡例1行へ
まとめる）。

### 再発防止

プロファイルと分類器の片側変更は、どちらもテストが赤くならないまま「何も起きない」形で
失敗する。`tests/test_import_profile.py`へ、プロファイルがnodeとして受理する全ルール・
全値の組み合わせが分類器で必ず`kind`を得ること・そのkindが集計対象（`STOP_POI_KINDS`）に
入ることを検証するテストを追加した。

## 残っている作業

**実データはまだ入っていない。** 取込対象の変更はPBF再取込（数時間）を伴うため、起票時の
方針どおり次回の地図データ更新に相乗りさせる。再取込の際に必要な手順:

1. `import_pbf.py`でPBFを再取込（`osm_raw_pois`へ新しいkindが入る）
2. `precompute_edge_attribute_counts.py`・`precompute_way_attribute_counts.py`を再実行
   （`ALGORITHM_VERSION`をv2へ上げたため、再実行するまで鮮度台帳は`is_stale`を出し続ける）
3. `osm_raw_pois`へ`barrier`・`traffic_calming`・`railway_crossing`のkindが入っていることと、
   `poi_counts`に`barrier`キーが出ることを確認する

再取込までの間、新しい材料`poi_barrier_per_km`は全区間0（キー無し＝0件として読む）になる。
軸で使うのは実データが入ってからにすること。
