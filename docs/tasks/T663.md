## 対応方針と実装

2件とも実施した（見送りなし）。タイトルどおり**書き込み時に拒否する**（GUI導線を塞ぐ）のを
主とし、1-9は配信側の失敗の返し方も併せて直した。

### 1-8 動的材料と静的材料の混在

動的軸はリクエストごとに`evaluate_dynamic_axis_arrays`で再評価され、そこへ渡るのは
「タイル単位でキャッシュ済みの**公開軸スコア**」と「動的材料」だけ。静的材料の配列は
渡らないため、混在させた軸は`evaluate_axis_array`の`materials[term.material]`で
KeyErrorになり`/api/routes/generate`ごと500になる。再現を確認した:

```
evaluate_axis_array(<wind_drag_ratio + gradient_percent の軸>, {"wind_drag_ratio": ...})
→ KeyError: 'gradient_percent'
```

`AxisDefinitionPayload._check_dynamic_and_static_materials_are_not_mixed`で書き込み時に
拒否する。軸参照（他の軸のaxis_id）は静的材料ではないため対象外——静的材料が必要なら
その部分を別の軸へ切り出し、公開軸として評価された結果を軸参照で読む形にできる。

### 1-9 配信の実装が無い軸の`dedicated_way_value_layer`

`dynamic_way_value_materials()`は軸定義から導出するためGUIの宣言だけで増えるが、実際に
way_id→値を組み立てるサービス本体（`api/dependencies.py`の
`_DYNAMIC_WAY_VALUE_SERVICE_FACTORIES`）はコード側の登録が要る。宣言だけが先行すると
`_build`がKeyErrorになり、その軸のタイルが**全て500**（404でないためフロントの
「データなし」フォールバックも効かない）。

- **書き込み時**: `_check_dedicated_layer_is_implemented`で、実装が登録済みのaxis_idに
  限る。実装済みidは`implemented_dynamic_way_value_material_ids()`（`dependencies.py`）
  として公開した。
- **配信側**: ファクトリ未登録を未知の`material_id`と同じ扱い（404）にした。既存データや
  API直叩きに対する保険で、500にするとフロントのフォールバックが効かないため。

あわせて、`dynamic_way_values.py`のdocstringと`docs/modules/backend/dynamic-way-values.md`
の「軸スタジオで宣言するだけで自動反映される」という記述を、実装登録が別に要ることが
分かる形へ直した（レビューが矛盾として挙げた箇所）。

## 既存データへの影響

`fixtures/axis_definitions_snapshot.json`の全14軸を新しい検証にかけ、抵触0件を確認した
（`dedicated_way_value_layer`を持つのはwind・gradientの2軸で、どちらも実装済み）。

## 検証

- 既存テスト2件（`dedicated_way_value_layer`/`dynamic_way_value_needs`の配線確認）は
