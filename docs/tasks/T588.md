# T588: `test_lifespan_registers_jma_tile_prewarm_job_with_immediate_next_run_time`がフルスイートでのみ失敗する

状態: 完了（2026-09-05起票・同日完了。[T532](T532.md)の最終検証で発覚、ユーザー指示で起票）

## 背景

`backend/tests/test_main_lifespan.py::test_lifespan_registers_jma_tile_prewarm_job_with_immediate_next_run_time`
が、`pytest -q -m "not postgis"`（全件）およびファイル単位（`pytest tests/test_main_lifespan.py`、
4件で約40〜50秒）では失敗し、同じテストを単体指定で実行すると成功する（約6秒）。T532の
変更前のmaster（e9951eb〜d5d209b）でも同じ結果で、T532とは無関係の既存の不安定化。
JMAタイル予熱ジョブを`next_run_time=datetime.now()`で登録し即時実行を期待する検証が、
先行テストの負荷でlifespan起動に時間がかかると許容差を超える（時間依存）疑いがある。

## 原因

`app/main.py: lifespan()`は起動のたびに`get_http_client(10.0)`・`get_http_client(15.0)`を
呼ぶ（httpxクライアントのウォームアップ）。`infrastructure/http_client.py`のモジュール
docstringが明記するとおり、この開発機（.venvがOneDrive同期フォルダ内）では
`httpx.AsyncClient`生成（SSLコンテキスト構築）が1回あたり約1秒かかる。このコストを
避けるためにtimeoutごとにクライアントをキャッシュ（`_clients`辞書）する設計だが、
`with TestClient(app):`のexit時にlifespanのシャットダウン段が`close_all_http_clients()`を
呼び`_clients`を毎回空にするため、`test_main_lifespan.py`の4テストはそれぞれ独立に
`with TestClient(app):`で起動→終了を行い、**テストのたびにこの約1秒×2回のコストを
払い直す**構造になっていた。

`test_lifespan_registers_jma_tile_prewarm_job_with_immediate_next_run_time`は
ファイル内3番目のテストで、先行する2テスト（`test_lifespan_fails_fast_when_refresh_
axis_definitions_raises`・`test_lifespan_registers_amedas_job_with_immediate_next_run_time`）
も同じ起動→終了サイクルを踏むため、実行順・システム負荷次第でこのコストが
アサーションの許容差（5秒）へ食い込みやすい位置にあった（単体実行では1サイクル分
[約2秒]で済むため許容差内に収まる）。

## 対応

本ファイルの4テストはいずれも`_refresh_amedas_job`/`_prewarm_jma_tile_job`を
無害化済みで、`get_http_client`が返すクライアントの中身を実際には使わない
（lifespan起動時のウォームアップ呼び出しの引数・回数だけが関心事のテストではない
ため、戻り値そのものは無関係）。既存の`_isolated_scheduler`autouseフィクスチャへ
`monkeypatch.setattr(main_module, "get_http_client", lambda timeout: None)`を追加し、
実`httpx.AsyncClient`生成（＝実SSLコンテキスト構築）自体を回避した。

**検証**: 修正前は`pytest tests/test_main_lifespan.py`単体実行で約40〜50秒
（環境依存のSSL構築コストの蓄積）だったが、修正後は1.87秒（4件）まで短縮。
`pytest -q`（backend全件、postgis込み1728件）を2回連続実行し、対象テストを含め
安定してgreenであることを確認した。

## 放置した場合の影響

フルスイートが常に赤1件になり、他タスクの回帰検知の信頼性が下がる（「既知の1件」として
読み飛ばす運用が定着すると本物の失敗を見落とす）。
