# T460. get_dynamic_way_value_serviceのサービス組み立てがmaterial_idのハードコードif/else分岐になっている

状態: 完了（2026-08-31）

- 背景: モジュール設計書作成のため（背景Agent経由で）`backend/app/api/dependencies.py`の
  `get_dynamic_way_value_service`を実コードで確認したところ、`_build`関数が

  ```python
  def _build(repository):
      if material_id == "wind":
          return WindWayService(repository=repository, weather_service=weather_service)
      return GradientWayService(repository=repository)
  ```

  という**ハードコードされたif/else分岐**でサービスを組み立てていることが判明した。
  `domain/dynamic_way_values.py`のモジュールdocstring自身は「新しい動的＋向きあり材料を
  追加するときは、ここへ1エントリ足すだけでエンドポイントのバリデーション（region.py）・
  キャッシュのbucket化（dynamic_way_value_cache.py）へ自動的に反映される」と主張しているが、
  これは事実の半分（バリデーション・キャッシュ側）のみを反映しており、サービス組み立て側は
  この主張に反する。
- [T458](T458.md)（`DYNAMIC_WAY_VALUE_MATERIALS`辞書自体が軸スタジオと独立している問題）とは
  **別ファイル・別メカニズムの同根の1本道違反**。T458の対応方針（`AXIS_DEFINITIONS`から
  `dedicated_way_value_layer=true`の軸を抽出する形への置き換え）が実現しても、
  `WindWayService`/`GradientWayService`という異なるPythonクラス（コンストラクタ依存が
  異なる——前者は`weather_service`を追加で要求）を材料idから解決する箇所自体は、
  material_id→ファクトリ関数の登録テーブルのような形へ別途一般化しない限り残る。
- Impact: 設計原則8「拡張可能なレジストリは常に1本道の追加点を持つ」への違反。3つ目の
  動的材料を追加する際、T458の対応が完了していてもなお、この`_build`関数への分岐追加が
  別途必要になる。
- 対応方針（未検討）: material_id→サービスファクトリ（コンストラクタ引数の解決を含む
  callable）の登録テーブルを設け、`_build`をそのテーブル参照へ置き換える。T458の
  `DYNAMIC_WAY_VALUE_MATERIALS`拡張と同じタイミング・同じ設計判断で一緒に検討するのが
  自然（着手順序はT458を先行させ、その結果決まるデータ構造に合わせてこちらのファクトリ
  登録も設計するとよい）。
- Confidence: High（`api/dependencies.py`の`get_dynamic_way_value_service`実装を背景Agent経由で
  直接確認済み）。
- 規模S（T458と同時に着手するなら追加コストは小さい。単独では登録テーブルの新設のみ）。

## 実施記録（2026-08-31完了）

- T458（`DYNAMIC_WAY_VALUE_MATERIALS`自体の拡張）は本タスク着手時点で未着手のままだったが、
  ユーザーが本タスク単独での着手を選択したため、規模S想定どおり「登録テーブルの新設のみ」の
  単独実装とした（T458はスコープ外のまま）。
- `api/dependencies.py`へ`_DYNAMIC_WAY_VALUE_SERVICE_FACTORIES`（material_id→ファクトリの
  dict、`(repository, weather_service) -> WindWayService | GradientWayService`という
  統一シグネチャ）を新設し、`get_dynamic_way_value_service`内`_build`のif/else分岐を
  このdict参照へ置き換えた。3つ目の動的材料を追加する際は、このdictへ1エントリ足すだけで
  よくなった。
- キー集合の整合性（`_DYNAMIC_WAY_VALUE_SERVICE_FACTORIES`は`DYNAMIC_WAY_VALUE_MATERIALS`
  の部分集合である必要がある）はコメントで明記し、片方だけ更新した場合は`_build`が
  KeyErrorで即座に失敗する設計（fail-fast、無音の分岐漏れより検知しやすい）とした。
  起動時の整合性検証までは本タスクのスコープに含めなかった（登録頻度が低く、
  KeyErrorによる検知で十分と判断）。
- `tests/test_dependencies.py`へ`TestGetDynamicWayValueService`を新設し、
  `get_dynamic_way_value_service`を実DB接続なしで直接呼び出す既存方針
  （`road_graph_use_repository=False`）を踏襲した回帰テスト3件を追加（wind→
  WindWayService+weather_service注入、gradient→GradientWayService、未知material_id→None）。
- **検証**: `pytest tests/test_dependencies.py tests/test_region_routes.py
  tests/test_wind_way_service.py tests/test_gradient_way_service.py`計56件すべて通過。
