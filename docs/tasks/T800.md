# T800. 交差点ノードの属性を事前計算する（信号の有無・接続する道の最大階級）

規模M。
状態: 完了（2026-09-15。本番バックフィルまで実施。較正は[T801](T801.md)。2026-09-13起票。[T790](T790.md)の段階2cから切り出し）

## 背景

実走フィードバック「交通量の多い道を突っ切る／右折（車線跨ぎ）のコストがばかにならない。
基幹道路をまたぐ横断が非常に苦労」への対応。

T790段階2aでターンの費用は入り、**接続する道の最大highway階級が進入した区間より上位なら
横断・右左折に費用を足す**ところまでは実装済み（`domain/traffic.py: highway_rank`で比べる）。
ただし階級は探索時にEdgeの属性から都度比べており、**信号の有無は見ていない**。

信号のある交差点の待ちは停止密度の材料（`poi_signal_per_km`）が数えているため二重にしない、
という理由で今は見ていない。しかし実走の苦労は「信号の**無い**幹線横断」に集中している。
これを表すには、交差点ノードごとに「信号があるか」「集まる道の最大階級は何か」を持つ必要がある。

## 対応方針

`road_nodes`へ信号の有無・接続する道の最大highway階級を持たせ、バッチで事前計算する
（`precompute_road_node_degrees.py`と同じ形）。ターンの費用がこれを読むことで「信号のある
交差点の直進より、信号の無い交差点で上位階級の道を横断・右折する方が高い」を表せる。

**Edgeへ畳み込んだ値を`road_edges`の列やMVTタイルへ焼かないこと**——Edge側へ焼くと同じ事実が
2箇所に出て、状態を移したとき片方が古くなる。畳み込みによる近似では「交差点を通ること自体を
嫌う」までしか表せず、右折と直進横断を区別できない。

## 調査項目

- `road_nodes`のスキーマ変更（DDL migration）と本番バックフィルの手順
- 停止密度の材料（信号の数）との二重計上をどう避けるか。T790で停止の待ちは走行モデルへ
  移ったため、「待ち」と「横断の怖さ」を別物として置けるようになっている

## 段階1: データ側（2026-09-15）

`road_nodes`へ2列を足し、事前計算するバッチを作った。

- migration `0041_add_road_node_intersection_attributes.sql`:
  `has_traffic_signals`（既定`false`）・`max_highway_rank`（既定`0`）
- 集計SQLは`DerivedGraphRepository`側（`recompute_node_traffic_signals`・
  `recompute_node_max_highway_rank`）、バッチ
  `precompute_road_node_intersections.py`はそれを呼ぶだけ（既存のprecomputeと同じ規約）
- `refresh_derived.py`の⑭段として登録。`docs/batch-pipeline-dependencies.md`にも追記

**既定値はどちらも「このバッチ導入前と同じ挙動になる側」へ倒してある**。
`has_traffic_signals=false`＝信号が無い扱いなので、いまと同じく上位の道を渡るときは
必ず追加の秒数が付く。`max_highway_rank=0`は探索側の導出（読み込んだ部分グラフから
同じ値を出す）を下回るため、DB側の値は下限を上げる方向にしか効かない。
本番バックフィル前にデプロイしても経路は変わらない。

### 信号の判定と半径（実測、開発DB 138,163ノード）

信号は交差点そのもののノードではなく流入路ごと・横断歩道位置ごとの別ノードとして
描かれるため、`osm_node_id`の一致では拾えない。同じ交差点の点をまとめるのに使っている
距離（`POI_CLUSTER_EPS_M` = 40m）を半径にした。**この値は結果を大きく動かす**——
上位の道（rank 4以上＝primary以上）が集まる交差点12,583件のうち「信号あり」になる割合:

| 半径 | 信号あり | 割合 |
|---:|---:|---:|
| 10m | 4,708 | 37.4% |
| 20m | 5,971 | 47.5% |
| 30m | 6,607 | 52.5% |
| **40m** | **7,287** | **57.9%** |
| 60m | 8,550 | 67.9% |

**頭打ちが無い**ため、データからは「正しい半径」が出てこない。40mを採ったのは既に
同じ交差点の点をまとめるのに使っている値だからで、較正された値ではない。半径を広げると
「信号あり」が増え、そのぶんターンの費用が下がる（＝幹線横断を避けなくなる）。
較正は[T801](T801.md)の対象に含める。

### 所要（開発DB、138,163ノード）

8.7秒（`max_highway_rank`の単一UPDATEが1.9秒、信号の空間結合が7チャンクで6.8秒）。

### 検証

- `tests/test_road_graph_repository.py`へ4件追加（階級は最上位で決まる／順位表に無い道は0／
  近傍の信号で印が付き遠いノードには付かない／信号を伴わない横断歩道は数えない）
- **半径が効いていることを確かめた**: 信号POIを交差点ノードから約15m離した位置に置いた
  うえで、`signal_radius_m`を0にすると近傍判定のテストだけが落ちる。同一座標に置いた
  最初の版は半径0でも通ってしまい、半径を検証できていなかった
- `tests/test_refresh_derived.py`の「全段へdatabase_url・dry_runが渡る」テストが対象
  モジュールを手で並べていたため、`_STAGES`から導く形へ直した（並べたままだと段を足した
  ときにその段だけ本物が走り、渡し漏れも検出できない）
- `pytest tests/test_road_graph_repository.py tests/test_refresh_derived.py
  tests/test_precompute_road_node_degrees.py -q` → 125 passed
- `ruff check app scripts tests` → All checks passed

## 段階2: 探索側（2026-09-15）

ノード属性を探索まで運び、ターンの費用を条件付きにした。

- `Node`・`LeanNode`・`NodeLike`へ`has_traffic_signals`・`max_highway_rank`を足し、
  `get_graph_in_bbox`/`get_graph_topology_in_bbox`のSELECTと
  `LeanRoadGraph.__reduce__`（pickleの列）へ通した
- `build_turn_expanded_structure`が**信号の無い交差点でだけ**上位階級の横断・右左折へ
  秒数を足す。`TurnCostSpec`のコメントにあった「信号の有無は見ない——待ちは停止密度の
  **軸**が数えている」という根拠は、[T790](T790.md)で停止の待ちが走行モデルへ移った時点で
  事実と違っていた（設計原則13の分け方でいえば、いま二重になっているのは軸ではなく
  走行モデルの側）
- ノードの階級は「部分グラフからの導出」と「DBの事前集計値」の大きい方を採る。
  未集計の0が導出値を下げることはない

### 途中で見つけて直したもの

1. **タイル材料キャッシュの署名が、同じ値に入っているグラフを見ていなかった**。
   `TILE_MATERIALS_CACHE_VERSION`は`EdgeMaterialTable`だけを`shape_digest`していたが、
   キャッシュ値（`SearchMaterials`）は`LeanNode`/`LeanEdge`も抱えている。ノードへ列を
   足しても鍵が動かず、**足した列が既定値のまま返り続ける**——`shape_digest`が防ぐはずの
   ものがそのまま起きる形だった。3つとも署名へ入れ、どれか1つを欠くと鍵が変わることを
   テストで固定した
2. **派生データ鮮度台帳の未計算判定**。`road_nodes.degree`と同じく
   `max_highway_rank`もNOT NULL DEFAULT 0で未計算と区別できないが、順位の付く道が接して
   いるのに0なら未計算だと言い切れる。そこへ絞ることで、自転車道・歩道だけのノード
   （開発DBで20,360件＝全体の15%）が常時「未計算」として残り続けるのを避けた
   ——常に出続ける警告は読まれなくなる

### 検証

- `tests/test_routing_turn_expanded.py`へ3件追加（信号のある交差点では足さない／信号の列を
  渡さないときは列の導入前と同じ／DBの階級は下限を上げるだけで下げない）
- **効いていることを確認**: 信号による分岐を外すと、信号のテストだけが落ちる
- `tests/test_graph_material_cache.py`の署名テストを、キャッシュ値がpickleするdataclass
  全部を材料とし、どれか1つを欠くと鍵が変わることまで見る形へ書き直した
- `pytest -q -m "not postgis"`／`ruff check app tests scripts`

## 段階3: 本番バックフィル（2026-09-15）

デプロイ済みイメージを使い、本番VMで実行した（デプロイのmigration適用と同じ形）:

    sudo docker run --rm --network=host --memory=3g --memory-swap=3g       --env-file /home/ubuntu/ridecompass-backend.env       ridecompass-backend:latest       python -m app.batch.precompute_road_node_intersections

**1,871,229ノード・145.1秒**（`max_highway_rank`の単一UPDATEが67.6秒、信号の空間結合が
94チャンクで77.5秒）。開発DB（138,163ノード・8.7秒）から13.5倍の母集団で17倍の所要という
ほぼ線形の伸びで、単一UPDATE側も想定どおり収まった。

### 開発DBとの違い

上位の道（primary以上）が集まる交差点で「信号あり」になる割合は、開発DB（東京都心南部）の
**57.9%**に対し本番（関東本土全域）は**33.8%**（42,434/125,676）。都心より信号の無い
幹線交差点が多く、**この変更の効きは本番の方が大きい**——横断の費用が付く交差点が
2/3を占める。

### 反映の確認

バッチ完了後に本番でルート生成を1回投げ、backendのログに
`派生データ世代の変化を検知しキャッシュを破棄しました revision=10`が出ることを確認した
（タイル材料・スコア行列のディスクキャッシュが捨てられ、新しいノード属性を含むグラフで
組み直される）。デプロイもpushも要らない経路。
