# T793. ベンチマークの変更で本番backendがデプロイされる

規模S。
状態: 完了（2026-09-15。2026-09-13起票）

## 背景

`.github/workflows/deploy-backend.yml`の`paths`は`backend/**`で、`backend/benchmarks/`の
変更もデプロイ（VM上での`docker build`＋コンテナ入れ替え）を起こす。[T790](T790.md)段階1で
ベンチマークスクリプトを追加したとき、実際に本番のビルドとコンテナ再起動が走った。

`backend/Dockerfile`がイメージへ入れるのは`app`・`fixtures`・`migrations`・`scripts`・
`requirements.txt`だけで、**`benchmarks`はイメージに含まれない**（本番計測はホスト側へ置いて
マウントする）。つまりこのデプロイは本番の動作を何も変えないまま、ビルド時間とコンテナ
入れ替え（`docker stop -t 90`のグレース待ちを含む）だけを消費する。

## 対応と結果

このワークフローは**2つの仕事**をしている。混ぜて考えると必ずどちらかを損なう。

1. **VMの作業コピーを最新にする**（`git reset --hard`）。ベンチマークはVM上でこのコピーから
   実行するため、`backend/benchmarks/`の変更もVMへ届く必要がある。
2. **イメージを作り直してコンテナを入れ替える**（`docker build`→migration→
   `docker stop -t 90`→`run`）。要るのは`backend/Dockerfile`がCOPYするものが変わったときだけ。

**振り分けはワークフローの中で行う**。`paths`は`backend/**`のまま（ここで除外すると1が
できなくなる）で、`git reset --hard`の後に「イメージに入るものが変わったか」を見て、
変わっていなければそこで終える。

```sh
BEFORE="${{ github.event.before }}"   # 押される前のmasterの先端
NEEDS_REBUILD=1
if [ -n "$BEFORE" ] && git cat-file -e "$BEFORE^{commit}" 2>/dev/null; then
  IMAGE_CHANGES=$(git diff --name-only "$BEFORE" "$AFTER" -- backend/ .github/workflows/deploy-backend.yml     ':(exclude)backend/benchmarks/**' ':(exclude)backend/tests/**')
  [ -z "$IMAGE_CHANGES" ] && NEEDS_REBUILD=0
fi
```

**判断できないときは必ず作り直す**（`workflow_dispatch`・force push・浅いクローンで前の
コミットを辿れない等）。差分を取るために`git fetch`の深さを1から50へ広げた——`--depth 1`では
直前のコミットが手元に無く、振り分けが常に「判断できない」へ落ちる。

イメージに入らないのは`benchmarks/`（VM上で実行するもの）と`tests/`（走らせるのは`ci.yml`で、
このワークフローはテストに一切触れない）。**この判定は`backend/Dockerfile`のCOPY対象と対**で、
片方を変えたらもう片方も見る必要がある（ワークフロー側にもそう書いた）。

### 最初に入れた形（誤り）とその理由

最初は`paths`から`backend/benchmarks/**`・`backend/tests/**`を除外し、「除外の範囲は
Dockerfileのcopy対象外という一点で決めた」と書いた。**これは別々の2つの問い**
——コンテナの作り直しが要るか／VMへ届く必要があるか——**を1つの基準に丸めたもの**で、
ベンチマークがVMへ届かなくなる副作用を「手で`git pull`すればよい」と脇へ置いていた。
ユーザー指摘（2026-09-15「ベンチマークを動かしたいのと、copy対象外とは別の話？」）で
気づき、上の形へ入れ替えた。[T798](T798.md)が扱う「結論に合う基準を作って反する事実を
補足扱いにする」型そのもの。

## 検証結果

**除外が効いていること**（2026-09-15、masterへの連続した2つのpushで観測）:

| push | 変更したもの | 起動したワークフロー |
|---|---|---|
| `3c7ccaa2` | `deploy-backend.yml`ほか | **Deploy Backend to Oracle VM**（success）・CI・Docs Consistency |
| `0f052d4e` | `backend/benchmarks/`の1ファイルのみ | CI・Docs Consistency（**Deployは起動せず**） |

この観測は`paths`で除外していた形のもので、**入れ替えた後は「Deployは起動するが、
ビルドとコンテナ入れ替えはしない」が正しい姿**になる。入れ替え後の観測値は下記。

変更前は、[T802](T802.md)でベンチマークを1本足しただけで
`Deploy Backend to Oracle VM 390`が走っていた（2026-09-14、本番の動作は何も変わらず
ビルドとコンテナ入れ替えだけを消費）。
