# T880. docs検査1回の所要を短くする（mutateが10分規模になっている）

規模M。
状態: 完了（2026-09-15。起票も同日。[T871](T871.md)の作業中に`mutate`が10分超かかることに
気づき、内訳を計測した。当初T879として起票したが、並行セッションが同番号を先にpushした
ため振り直した）

## 背景

`scripts/review_checks.py mutate`（検知器が実際に鳴るかの監査、`docs-consistency.yml`が
毎push実行）が**10分規模**かかる。`.claude/commands/review/README.md`は長く「約20秒」と
書いていた。

`mutate`は「検知器の数 × 2経路（pre-commit・CI）」ぶん`docs`を子プロセスで実行する構造の
ため、**`docs`1回の所要がそのまま42倍になる**。つまり遅いのは`mutate`ではなく`docs`。

## 計測（2026-09-15、開発機）

`docs --keys --staged` 1回 = 15〜20秒。関数ごとの内訳（`perf_counter`で実測。cProfileは
オーバーヘッドで3倍以上に膨らむため使わない）:

| 所要 | 関数 | 内容 |
|---:|---|---|
| 7.6秒 | `find_source_comment_dead_identifier_refs` | 全782ファイルのコメント分離＋識別子の実在判定 |
| 3.4秒 | `historical_axis_ids` | スナップショットのgit履歴走査（**本タスク起票時に0.3秒へ改善済み**） |
| 1.6秒 | `source_corpus` | 実在判定用のソース全文の連結 |
| 1.2秒 | `find_doc_constant_drift` | |
| 1.1秒 | `find_map_redraw_gaps` | |

`find_source_comment_dead_identifier_refs`の内訳をさらに測ると、`split_source_comments`
（tokenize＋ASTでコメント行を特定、782ファイル）は**2.05秒**しかない。残る5.6秒は
`find_dead_identifier_refs`側——バッククォート内の各トークンについて
`identifier_exists(token, corpus)`を呼び、**巨大な1本の文字列に対して`in`を走らせている**
（corpusは実装＋テスト全文の連結）。トークン数×corpus長のオーダーになる。

## 保留することで何が起きうるか

- CIが毎pushで10分を使う。他のジョブと合わせるとフィードバックが遅い
- pre-commitの`docs --staged`も15〜20秒かかる。コミットのたびに待つ
- **検知器を足すほど線形に伸びる**。母集団を広げる改善（[T871](T871.md)）とは方向が
  逆向きに効くため、次に検知器を足すときの抑止力になる

## 対応方針（案。着手時に見直す）

1. **`identifier_exists`の照合を、文字列包含から集合の参照へ変える**。corpusを一度だけ
   トークンへ割り、`set`で持てば1トークンあたりO(1)になる。**綴りの単純な包含判定という
   契約は変えない**（部分一致を許している箇所があるなら、その意図を先に確認する）
2. `source_corpus`と`find_source_comment_dead_identifier_refs`が別々に全ファイルを読んで
   いるなら、1回にまとめる
3. 上記で足りなければ、`mutate`側で`docs`の実行を検知器1つぶんへ絞れないかを検討する
   （現在は毎回すべての検知器を回して、目的の1つの件数だけを見ている）

## 完了条件

- `docs --keys --staged`1回の所要を計測してこのエントリへ書く（改善前後）
- **検知結果が変わらないこと**を確認する——`docs`のフル実行の出力が改善前と一致すること。
  速くなった代わりに拾えなくなった、が起きていないことを示す
- `mutate`全件PASSが維持されること

## 段階1の実装（2026-09-15）

計測し直すと、`docs`のフル実行で最も重いのは起票時に挙げた
`find_source_comment_dead_identifier_refs`ではなく**`find_removed_axis_mentions`の
28.6秒**だった（起票時は`--staged`だけを測っており、この関数が全ファイルを走る全件
モードを見ていなかった）。1行ごとに撤去済みid1本ずつ`re.search`を回すため、
行数×id数のオーダーになっていた。

直した内容（**どれも判定の契約は変えていない**）:

| 変更 | 内容 |
|---|---|
| `find_removed_axis_mentions` | 全idを1本の選択肢正規表現へまとめ、1行1回の走査にした。加えてファイル単位の前フィルタを置いた（折り返しで割れた綴りを落とさないよう、実装側は改行を畳んだ姿で見る） |
| `identifier_exists` | corpusを一度だけ単語へ割った集合を先に見る。集合に在れば包含も必ず成り立つため判定は変わらず、集合に無いものだけが従来の包含判定へ落ちる |
| `read_text` | 1回の実行中は内容を保持する（同じファイルを7,000回以上読み直していた） |
| `split_source_comments` | (path, text)でメモ化 |
| `source_corpus` | 同じファイル一覧に対し1回の実行で4回呼ばれていたためメモ化 |
| `find_map_redraw_gaps` | `--since`経路で2回呼ばれていたためメモ化 |

メモ化のキーには`REPO_ROOT`を含めた（テストが一時ディレクトリを差し込むため）。

### 所要（開発機、`docs --keys`）

| 経路 | 改善前 | 改善後 |
|---:|---:|---:|
| 全件 | 43.6秒 | 6.8秒 |
| `--since HEAD~5` | 17.9秒 | 7.3秒 |
| `--staged`（差分なし） | 6.7秒 | 5.0秒 |

### 検知結果が変わらないことの確認

`docs --keys`の全件出力と`--since HEAD~5`の出力が、改善前後で**1行も違わない**
（`diff`で確認）。`pytest scripts/tests` 97 passed（既存の環境依存1件を除く）。

## 段階2の実装（2026-09-15）

`mutate`は1回の`docs`実行で**自分の検知器の節しか読まない**のに、毎回すべての検知器を
回していた。`docs`へ`--only <検知器キー>`を足し、選ばれなかった検知器は計算も出力も
しないようにした（`cmd_docs`の`sections`を遅延評価へ。60箇所を機械変換）。

**配線の検査（`unwired_detectors`）はキーを全件のまま見る**——絞ったせいで「強制すると
宣言したのに繋がれていない検知器」を見逃す状態にはしない。

段階1のメモ化が`guard_probe`側を壊していたのも直した。あちらは検査ではなく違反の
作り込み側で、同じファイルを書き換えては読み直す。とくに`guard_probe_post_stage`は
`guard_probe_mutations`が書き換えた後の姿を必要とするため、内容を保持する`read_text`
ではなく直読みへ分けた（この経路は`mutate`では`PASS`のままだったが、プローブの意図
＝作業ツリーにだけ撤去の断りを足す、が壊れていた）。

## 結果

| | 起票時 | 段階1後 | 段階2後 |
|---|---:|---:|---:|
| `mutate`全件（CIが毎push実行） | 10分規模 | 332秒 | **86秒** |
| `docs --keys` 全件 | 43.6秒 | 6.8秒 | 6.8秒 |
| `docs --keys --since` | 17.9秒 | 7.3秒 | 7.3秒 |
| `docs --keys --staged` | 6.7秒 | 5.0秒 | 5.0秒（`--only`付きなら0.9〜3.5秒） |

## 完了条件の確認

- **検知結果が変わらないこと**: `docs --keys`の全件出力と`--since HEAD~5`の出力が、
  改善の前後で**1行も違わない**（`diff`）
- **`mutate`全件PASSが維持されること**: 全42件PASS
- `pytest scripts/tests -q` 97 passed（既存の環境依存1件を除く）、
  `ruff check` 13件（変更前と同数）

## 台帳にあった補足

- 2026-09-15完了。mutate全件が10分規模→86秒、docsの全件実行が43.6→6.8秒。判定の契約は変えていない［全件出力が改善前後で1行も違わないことをdiffで確認］。最大の要因は起票時の見立て［包含判定］ではなくfind_removed_axis_mentionsの28.6秒で、撤去済みid1本ずつ正規表現を回して行数×id数のオーダーになっていた。加えてmutateの各プローブがdocsへ--onlyを渡し、自分の検知器だけを回すようにした
