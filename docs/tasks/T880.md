# T880. docs検査1回の所要を短くする（mutateが10分規模になっている）

規模M。
状態: 未着手（2026-09-15起票。[T871](T871.md)の作業中に`mutate`が10分超かかることに
気づき、内訳を計測した。当初T879として起票したが、並行セッションが同番号を先にpushした
ため振り直した）

## 背景

`scripts/review_checks.py mutate`（検知器が実際に鳴るかの監査、`docs-consistency.yml`が
毎push実行）が**10分規模**かかる。`.claude/commands/review/README.md`は長く「約20秒」と
書いていた。

`mutate`は「検知器の数 × 2経路（pre-commit・CI）」ぶん`docs`を子プロセスで実行する構造の
ため、**`docs`1回の所要がそのまま42倍になる**。つまり遅いのは`mutate`ではなく`docs`。

## 計測（2026-09-15、開発機）

`docs --keys --staged` 1回 = 15〜20秒。関数ごとの内訳（`perf_counter`で実測。cProfileは
オーバーヘッドで3倍以上に膨らむため使わない）:

| 所要 | 関数 | 内容 |
|---:|---|---|
| 7.6秒 | `find_source_comment_dead_identifier_refs` | 全782ファイルのコメント分離＋識別子の実在判定 |
| 3.4秒 | `historical_axis_ids` | スナップショットのgit履歴走査（**本タスク起票時に0.3秒へ改善済み**） |
| 1.6秒 | `source_corpus` | 実在判定用のソース全文の連結 |
| 1.2秒 | `find_doc_constant_drift` | |
| 1.1秒 | `find_map_redraw_gaps` | |

`find_source_comment_dead_identifier_refs`の内訳をさらに測ると、`split_source_comments`
（tokenize＋ASTでコメント行を特定、782ファイル）は**2.05秒**しかない。残る5.6秒は
`find_dead_identifier_refs`側——バッククォート内の各トークンについて
`identifier_exists(token, corpus)`を呼び、**巨大な1本の文字列に対して`in`を走らせている**
（corpusは実装＋テスト全文の連結）。トークン数×corpus長のオーダーになる。

## 保留することで何が起きうるか

- CIが毎pushで10分を使う。他のジョブと合わせるとフィードバックが遅い
- pre-commitの`docs --staged`も15〜20秒かかる。コミットのたびに待つ
- **検知器を足すほど線形に伸びる**。母集団を広げる改善（[T871](T871.md)）とは方向が
  逆向きに効くため、次に検知器を足すときの抑止力になる

## 対応方針（案。着手時に見直す）

1. **`identifier_exists`の照合を、文字列包含から集合の参照へ変える**。corpusを一度だけ
   トークンへ割り、`set`で持てば1トークンあたりO(1)になる。**綴りの単純な包含判定という
   契約は変えない**（部分一致を許している箇所があるなら、その意図を先に確認する）
2. `source_corpus`と`find_source_comment_dead_identifier_refs`が別々に全ファイルを読んで
   いるなら、1回にまとめる
3. 上記で足りなければ、`mutate`側で`docs`の実行を検知器1つぶんへ絞れないかを検討する
   （現在は毎回すべての検知器を回して、目的の1つの件数だけを見ている）

## 完了条件

- `docs --keys --staged`1回の所要を計測してこのエントリへ書く（改善前後）
- **検知結果が変わらないこと**を確認する——`docs`のフル実行の出力が改善前と一致すること。
  速くなった代わりに拾えなくなった、が起きていないことを示す
- `mutate`全件PASSが維持されること
