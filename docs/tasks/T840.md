# T840. 本番DBの反映漏れを、派生データ以外も管理画面から確かめられるようにする

規模M。
状態: 未着手（2026-09-14、ユーザー要望「本番dbへの反映漏れとか多くの課題がこれまでにあった
認識。それを自分からチェックして再実行できるとありがたい。この派生データに限らず、他ないか
確認して」から）

## 背景

「本番へ反映したつもりで反映されていない」が繰り返し起きている。`/admin`から確かめられるのは
現状**派生データの陳腐化だけ**（[T832](T832.md)・[T836](T836.md)）。

洗い出した結果、本番DBの状態に起因する反映漏れは次の3つ（コード側の生成物ドリフトは
pre-commitとCIが既に機械的に止めているため対象外）。

### 1. 軸定義の本番反映漏れ（**6回の実績**）

開発DBだけ反映して完了扱いにし、本番だけ古い軸定義のまま取り残される
（[deployment-sync.md](../deployment-sync.md)にT294・T353・T360・T396・T440系列・T458の
6回が記録されている）。`backend/fixtures/axis_definitions_snapshot.json`は手動運用の
スナップショットで、本番DBと食い違っても誰も気づかない。

**検出できる**: 本番の`AXIS_DEFINITIONS`（本番DBから読み込み済み）とコード同梱の
スナップショットを突き合わせ、差分のある軸id・フィールドを出す。

### 2. migrationの適用状況

`deploy-backend.yml`がDDL migrationを自動適用するようになった（[T349](T349.md)）が、
適用済みかどうかを画面から確かめる手段が無い。migration未適用のまま新コードが動いて本番が
落ちた実績がある（[T74](T74.md)）。

**検出できる**: `schema_migrations`テーブルと`backend/migrations/`のファイル一覧を突き合わせる。

### 3. 生データ取込の最終実行

`osm_import_runs`・`accident_import_runs`・`designation_import_runs`に記録はあるが、
「最後にいつ・どこまで取り込んだか」を画面から見られない。派生データの鮮度判定はこの
run idを基準にしているため、**基準そのものが古いことに気づけない**。

**検出できる**: 各テーブルの最新成功runのid・完了時刻・対象範囲を出す。

## 対応方針

「鮮度」タブと同じ器へ足す——読み手にとっては「本番が意図した状態になっているか」という
1つの問いで、判定方式の違いは開いた先に書けばよい（[T836](T836.md)で世代比較と完成度を
同じ行へ揃えたのと同じ考え方）。**読み取りのみ**で、書き込み・再実行は含めない
（再実行は[T839](T839.md)）。
