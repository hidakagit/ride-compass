# T405. 動的要素の二重表現（風の環境/評価軸表示、Redis経由way_id→値配信）

状態: 完了（2026-08-30）→**要作り直し（2026-08-30訂正、詳細下記）**

- **2026-08-30訂正**: 下記の実装（評価軸グループの風の色は「道路自身のOSM格納方向・現在時刻
  固定」で計算）は、実機フィードバックで発覚した設計ミスに基づいていたことが判明した。
  正しい契約は「ルート未確定時はユーザーが指定した(時刻,向き)を全道路へ一律適用、ルート確定後は
  ルート自身の実進行方向・実到達時刻を使いルート線のみ着色」（訂正後のT400.md「2.」節参照）。
  本タスクの実装（`wind_way_service.py`・`wind_way_penalty_cache.py`・
  `get_way_bearings_in_tile`・`/api/region/dynamic-way-values/wind/{z}/{x}/{y}`エンドポイント・
  フロントの`windAxisLayer.ts`）は道路自身の向きを前提にしており、この契約と一致しないため
  作り直しが必要。作り直しの計画は[T414](T414.md)へ統合した（以下は「何が実際に作られたか」の
  歴史的記録として残す）。
- 背景（当時の理解、上記訂正参照）: 詳細はT400.md「2. 動的要素（時刻・向き等）を含む材料は
  『環境』と『道路』の二重表現を持つ」参照。環境グループの風は時刻＋方位（連続回転）スライダー＋
  `gridFill`で面表示。評価軸グループの風は、風グリッドの値とway自身の方位から`wind_penalty`を
  計算し`way_id`をキーにRedisへキャッシュ、新設の軽量APIとMapLibreの`setFeatureState`で道路
  タイルと合成して線色分けする。ルート確定後は環境グループの風チップと既存`routeStyleModes`の
  風モードを統合する。
- スコープ: 今回実装したのは「評価軸グループとしての風」の基盤（Redis配信層＋
  setFeatureState連携）のみ。「環境」グループの風（時刻＋方位スライダーの連続回転UI、
  `gridFill`面表示）とルート確定後の`routeStyleModes`統合はT400.md記載の別タスク（未起票）で
  あり、本タスクのスコープ外（意図的に着手していない）。
- 実装内容:
  - backend:
    - `backend/app/domain/wind_grid.py`: `nearest_grid_point`を新設。任意の地点から
      `generate_wind_grid_points`と同じ固定ラティス上の最寄り格子点を返す純粋関数。
      way_id→wind_penalty配信層がタイル中心のような任意座標に対する風を求める際、既存の
      固定格子点キャッシュ（weather_client.pyのcache_key丸め精度と整合）を再利用するために使う。
    - `backend/app/infrastructure/road_graph_repository.py`: `RoadSurfaceTileQuery.
      get_way_bearings_in_tile`（`_WAY_BEARINGS_IN_TILE_SQL`）を新設。指定タイル範囲の
      `osm_raw_ways`から`way_id→bearing_deg`をまとめて返す（`_ROAD_SURFACE_TILE_MVT_SQL`と
      同じカバレッジ判定・`ST_Intersects`フィルタを共有するが、MVTエンコードは行わない）。
      bearing_degは`ST_Azimuth(...::geography)`（geographyキャスト）で求める——**設計判断**:
      migration 0013（road_edges.bearing_degのバックフィル）はgeometry型のままST_Azimuthを
      呼んでおり、これは経度1度の実距離が緯度で変わることを無視した平面近似で、実測
      約6度もdomain/geo.py: bearing_between（球面三角法）とずれることが実装時に判明した
      （NODE1-NODE2間、緯度35.7度付近）。geographyキャストで測地線方位角を使うと差は
      約0.12度まで縮小し、テストで検知できる形にした
      （`test_get_way_bearings_in_tile_matches_domain_bearing_between`）。既存の
      `road_edges.bearing_deg`自体（平面近似のまま）を訂正する対応は本タスクのスコープ外
      （影響範囲の精査が別途必要なため、気づいた事実としてコードコメントに残すのみ）。
      `RoadGraphRepository`ファサードへも委譲メソッドを追加。
    - `backend/app/infrastructure/wind_way_penalty_cache.py`（新設）: `way_id`＋1時間バケット
      （`wind:way-penalty:{osm_way_id}:{hour}`）をキーとしたRedis cache-aside層。同じwayが
      複数タイル・複数ズームへ跨って現れても風グリッド・DBへの再問い合わせを避ける設計。
      TTLは`weather_client.WIND_GRID_CACHE_TTL_SECONDS`（3時間）に合わせた
      （キー自体に時刻バケットを含むため、TTLはGCの役割のみ）。
    - `backend/app/services/wind_way_service.py`（新設）: `WindWayService.
      get_way_wind_penalties(z, x, y, at)`。bearing取得→Redisキャッシュ確認→不足分のみ
      `WeatherService.get_wind_grid`＋`WindCalculator.wind_penalty`で計算→Redisへ書き戻し、
      という薄いオーケストレーション層。repository未接続・カバレッジ外・風データ取得不能等は
      いずれも空dictへグレースフルデグレード。
    - `backend/app/api/routers/region.py`: `GET /api/region/dynamic-way-values/wind/{z}/{x}/{y}`
      を新設（クエリパラメータ`at`省略時は現在時刻）。路面・POIタイルと同じレート制限・座標
      検証・DB接続プールのsemaphoreを共有する。
    - `backend/app/api/dependencies.py`: `get_wind_way_service`を新設（`get_region_service`と
      同じ「`road_graph_use_repository`無効時はrepository未注入」パターン）。
  - frontend:
    - `frontend/src/components/Map/windAxisLayer.ts`（新設）: DOM/MapLibre非依存の純粋関数
      （`tilesCoveringViewport`＝ビューポートを覆う道路タイルXYZ座標の算出、
      `mergeWindWayPenalties`＝複数タイル応答の統合、`windAxisColorExpression`＝

      `rampColorForBand`/`COLOR_UNKNOWN`を流用）。
    - `frontend/src/services/regionApi.ts`: `fetchWindWayPenalties`を新設。失敗時は例外を
      投げず空オブジェクトへフォールバック（背景の色分けレイヤーという補助的機能のため）。
    - `frontend/src/hooks/useWindAxisPenalties.ts`（新設）: `useWeatherGrid`のdetailGrid取得
      effectと同型のパターン（ビューポートを500msデバウンス→タイル単位でまとめてfetch→
      `Map<number, number>`へ統合）。
    - `frontend/src/components/Map/MapView.tsx`: `ROAD_TILE_SOURCE_ID`のvector sourceへ

    `GET /api/region/dynamic-way-values/wind/14/14551/6447`をcurlで直接叩き、実データ
    （関東本土、300件超のway_id→wind_penalty、値域は概ね±1.4m/s——今回の実測時点の
    風速と整合）を確認。フロントの「動的」チップグループに新規チップ「風軸」が現れ、
    クリックでON/OFF切替できること、ONにすると現在のビューポートを覆うタイル分
    （3×3=9件等）へ`/api/region/dynamic-way-values/wind/{z}/{x}/{y}`が実際にfetchされ
    全件200 OKで返ること、コンソールにwindAxis関連のエラーが出ないことを確認した。
    ベースマップ自体（sprite/glyph）が別要因（`BASEMAP_PUBLIC_BASE_URL`のファイル
    キャッシュがポート変更前の値を保持——既知の挙動、`docs/*/basemap-tile-cache-survives-
    restart`参照）で読み込めず地図が視覚的に空白のままだったため、実際に道路線へ色が
    付く様子そのものの目視確認はできなかった（`map.setFeatureState`呼び出し自体は
    MapLibreの標準APIでありユニットテスト・型チェックの対象外だが、fetchからの値受け渡し
    経路は上記のとおり実機で確認済み）。
