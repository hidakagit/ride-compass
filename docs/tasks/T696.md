# T696. 目的地モードの「最短」ルートが0次ハードフィルタを迂回する問題を直す 規模S〜M

状態: 未着手（2026-09-10起票、統合レビュー第6回 I-2。**最優先・本レビュー唯一のP0級の実害**）

## 背景

`services/road_graph_engine.py`の`select_shortest_distance_route`が、前向き木・後ろ向き木の
コスト配列に`context.statics.edge_length_m`（純粋な実距離）を**コスト・距離の両方**へ渡している
（`:1265`・`:1270`）。そのため0次ハードフィルタで除外されたEdgeを通る経路を返す。

対比: 軸重み経路は`:1093`が`context.legs[0].cost_list`、`:1134`が`inbound.cost_list`を渡す。
このコスト配列は`:299`で
`cost_array = np.where(self._hard_filter_excluded, np.inf, cost_array)`とinf化されており、
**通行可否はこのコスト配列だけが表現している**。距離木はその唯一の表現を迂回している。

迂回されるフィルタの範囲（`domain/hard_filters.py:117-145` `compute_hard_filter_excluded`）:

- `motorway` / `trunk`（自動車専用道路・幹線道路）
- `no_bicycle`（OSM `bicycle=no`、**法的に通行禁止**）
- **`max_average_grade_percent`（利用者が指定する勾配上限）**

既定は`DEFAULT_HARD_FILTERS = {"no_bicycle", "motorway", "trunk"}`（同`:35`）で、
`hard_filters=None`＝利用者が何も触らない状態でも全フィルタが有効。

しかもこの経路は`services/route_generator.py:481-497`で**条件分岐なしに必ず1本追加**され、
同`:511` `candidates.sort(key=lambda c: not c.is_shortest_distance)`で**先頭固定**される。
`_build_segment_details`が読む`leg.difficulty_array`はinf化**前**の配列のため、
区間表示も通常の難易度を示し、除外対象の道を通っている手掛かりが1つも出ない。

## 対応方針

距離木のコスト配列にも`_hard_filter_excluded`によるinf化を適用する
（`np.where(excluded, np.inf, edge_length_m)`をコスト配列として渡し、距離配列は生のままにする）。

## テストの書き直しが必須（**修正すると既存テストが赤くなる**）

`backend/tests/test_road_graph_engine.py:1460-1479`
`test_select_shortest_distance_route_ignores_axis_cost`は、最短側のEdgeを`highway="trunk"`に
設定して`shortest.data == ["e-0-out", "e-0-in"]`をアサートしている。コメントは
「trunkにして**軸コストを高くし**」と述べるが、trunkは0次ハードフィルタ対象で
`make_generator`の既定（`hard_filters=None`）では当該Edgeのコストは高いのではなく`inf`＝通行不可。
`ranked[0]`が遠回りを選ぶのは「trunkを避けた」のではなく「trunkを通れない」ためであり、
**このテストはフィルタ迂回をそのまま期待値として固定している**。

修正時は`trunk`ではなく実際に軸コストだけが高いEdgeを使う形へ書き直す。
テストが赤くなることを「修正が間違い」と読まないこと。

`docs/modules/backend/routing-engine.md:365-372`の`select_shortest_distance_route`節も
0次フィルタの扱いに一切触れていないため、同時に追記する。
