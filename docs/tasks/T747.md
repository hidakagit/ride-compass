# T747. キャッシュ鍵を1体系にし、導出できるものは手で書かない 規模M

状態: 完了（2026-09-12。起票は2026-09-11。ユーザー指摘「同期作業のミスを減らすためには、手動をやめよう。
バージョンアップする時の、バージョン番号は１体系にして他は必要ならそこから導出しよう」。
[design-principles.md](../design-principles.md)構造仕様12の適用）

## 現状: 7つの定数が別々の場所に散り、導出しているのは1つだけ

| 定数 | 場所 | 決め方 |
|---|---|---|
| `ROAD_SURFACE_TILE_VERSION` | `services/region_service.py` | 手 |
| `POI_TILE_VERSION` | 同上 | 手 |
| `ACCIDENT_TILE_VERSION` | `services/accident_service.py` | 手 |
| `TILE_MATERIALS_CACHE_VERSION` | `infrastructure/graph_material_cache.py` | 手 |
| `CACHED_TABLE_SIGNATURE` | 同上 | 手（**テストが2行で計算している**） |
| `_SCORE_MATRIX_REVISION` | `infrastructure/tile_score_matrix_cache.py` | 手 |
| `SCORE_MATRIX_COLUMN_SIGNATURE` | 同上 | 手（**テストが2行で計算している**） |
| `TILE_SCORE_MATRIX_CACHE_VERSION` | 同上 | **導出**（材料世代との複合） |

frontend側は`region-tile-config.json`（生成物）経由で受け取るため手動同期ではない
（`services/regionApi.ts:53,66,76`）。**手で維持しているのはこの7つだけ。**

唯一の導出である`TILE_SCORE_MATRIX_CACHE_VERSION`は、T719で材料世代だけを上げたときに
正しく機能した（統合レビュー第7回のKEEP）。**効く形は既にこの中にあり、1箇所にしか
適用されていない。**

## 対応方針: 1つのモジュールと1つの合成規則

`app/infrastructure/cache_identity.py`（唯一の正本）を新設し、すべてのキャッシュ鍵を
そこで組み立てる。各キャッシュは**自分が依存するものだけ**を宣言する。

- **形（shape）は必ず導出する**——列構成は`dataclasses.fields(...)`から、タイルは
  焼き込みSQL文字列から署名を計算する。手で写した署名定数は置かない。
- **手で書くのは「形は変わらないが意味を変えた」ときのリビジョンだけ**。それも
  この1ファイルへ集め、隣に「いつ上げるか」を書く。
- 合成は1つのヘルパで行い、キャッシュごとに別の流儀を作らない。

```python
ROAD_SURFACE_TILE_VERSION = cache_identity("road-surface", sql=_ROAD_SURFACE_TILE_MVT_SQL)
TILE_MATERIALS_CACHE_VERSION = cache_identity("materials", columns=EdgeMaterialTable)
TILE_SCORE_MATRIX_CACHE_VERSION = cache_identity(
    "score-matrix", columns=(EdgeMaterialTable, StaticEdgeScoreMatrix))
```

### 全キャッシュで1つの番号を共有はしない（判断）

「1つの番号を全キャッシュで共有」にすると、スコア行列の合成ロジックを直しただけで
路面タイル全体が無効化される。**1体系とは「鍵の決め方が1つ」であって「番号が1つ」では
ない**——各キャッシュは依存するものだけを合成する。

### ソースコードのハッシュ化はしない（判断）

「意味を変えた」まで機械的に捕まえるには、値を作る関数のソースをハッシュする必要があるが、
**採らない**。この形にすると純粋な改名やコメント修正でも全キャッシュが無効化され、
8日で556コミットという変更速度では実質的に毎デプロイでコールドスタートになる。
**利用者が既に「初回生成が前より遅い」と感じている**（デプロイ4回のうち3回でキャッシュ
世代が変わったことが原因）状態を悪化させる。過剰な無効化のコストが実害を上回る、
構造仕様12の例外条項に当たる。

## 消えるもの

- 手書きの署名定数 **2つ**（`CACHED_TABLE_SIGNATURE`・`SCORE_MATRIX_COLUMN_SIGNATURE`）
- 「上げ忘れを注意する」だけのテスト **2本**
  （`test_graph_material_cache.py`・`test_tile_score_matrix_cache.py`の署名照合）
- 「列を変えたら版を上げる」という手順（列を変えたら鍵が自動で変わる）
- 「タイルの焼き込み値を変えたら世代を上げる」という手順（SQLを変えたら鍵が自動で変わる）
- CLAUDE.md「コミット時の同期ルール」のうちタイル世代の項
- 7箇所に散った「◯◯と同じ流儀」という相互参照コメント

## 残るもの（理由つきで1ファイルへ集める）

- 「形は変わらないが意味を変えた」ときのリビジョン。現状の想定は材料の抽出ロジックと
  スコア行列の合成ロジックの2つ。上げ忘れても**形の変化は鍵が捕まえる**ため、
  残るリスクは「同じ形で違う意味の値が残る」場合だけに縮む。

## 実装メモ

`app/infrastructure/cache_identity.py`を新設。`cache_identity(revision, *shape_sources)`が
`<リビジョン>-<形の署名>`を返し、`shape_digest`がdataclassなら列名の並び、それ以外は
文字列化した内容（MVT生成SQL）から署名する。

鍵は**形が定義されている場所の隣**で組み立てる。タイル世代は焼き込みSQLの隣
（`road_graph_repository.py`・`accident_repository.py`）へ移し、`region_service.py`・
`accident_service.py`はそれをimportしてキャッシュパスを組み立てるだけにした——SQLを
別モジュールから読むために private 名を跨いで import する形を避けるため。

手で上げるリビジョンは5つとも`cache_identity.py`へ集め、それぞれの隣に「いつ上げるか」を
書いた。署名が捕まえない次元は1つだけ残る: **同じSQL・同じ列のまま、読み先のテーブルの
中身をバッチで作り直したとき**（PBF再取込・precompute系）。

| 鍵 | 旧 | 新 |
|---|---|---|
| `ROAD_SURFACE_TILE_VERSION` | `24` | `24-a126de5b444a` |
| `POI_TILE_VERSION` | `4` | `4-8a09aa93ddeb` |
| `ACCIDENT_TILE_VERSION` | `1` | `1-cf2793dd94a9` |
| `TILE_MATERIALS_CACHE_VERSION` | `12` | `12-35e0a21445a5` |
| `TILE_SCORE_MATRIX_CACHE_VERSION` | `12-11` | `11-e4f9a384ffb7`（材料世代を署名の材料に含む） |

材料側の署名`35e0a21445a5`は、撤去した手書き定数`CACHED_TABLE_SIGNATURE`と**同じ値**に
なった（導出が旧来の手動運用を再現していることの確認になる）。

### 本番への影響: 一度だけ全キャッシュが無効化される

鍵の形が変わるため、タイル3種・材料・スコア行列のディスクキャッシュが**このデプロイで
一度だけ**全部missする。材料の冷パスは29〜45秒規模で、利用者が既に感じている
「初回生成が前より遅い」を一時的に悪化させる。以後は形が変わらない限り起きない
（むしろ、これまで「念のため上げる」で起きていた無駄な世代上げが無くなる）。
旧世代のディスク実体は`prune_stale_disk_generations()`が回収する。
