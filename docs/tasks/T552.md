# T552: 重み付き軸がすべてデータ欠損のEdgeのコストを「最良扱い」から「bbox平均difficultyで補完」へ変える

状態: 作業中（2026-09-03起票・同日、対応方針2・3を実装。対応方針1[本番同等bboxでの
欠損比率計測]・4[取込側の補完の要否判断]が未着手のため完了条件を満たしておらず未完了。
[T531](T531.md)推敲時のユーザー質問「候補がデータ欠損Edgeへ偏っている場合、自然なルートに
近づける拡張はできるか」を受けて起票。T531とは独立に着手可能だがコスト式の意味論に触るため
別番号で切り出した）

## 背景

コスト式`cost = distance × (1 + P × composite/100)`は、composite difficultyがNaN
（リクエストで重みを振った軸すべてで材料が欠損）のEdgeを`penalty_multiplier = 1.0`、
つまりdifficulty 0相当の「最良の道」として扱う（`domain/evaluation.py:
compose_costs_from_axis_matrix`のNaN分岐、スカラー版`compute_cost_from_axis_scores`も同じ）。
一部の軸だけ欠損なら残りの軸で再正規化される（「データ無しは除外」方針）が、全軸欠損の
補完値は未定義のままこの挙動になっている。自転車インフラ100%のような単一軸の重み設定では、
タグ未取得の道路がサイクリングロードと同じコストになり、T531のフロンティア方式では
そうした道を優先的に折返し候補へ拾う方向に働く。

## 対応方針

1. **実態把握を先に行う**: `_build_search_graph`のINFOサマリへ「重み付き軸がすべてNaNの
   Edge比率（件数・距離加重）」を追加し、本番同等bbox（東京駅30km等）で計測する。比率が
   1%未満なら2のみ、それ以上なら4（取込側）も検討する。
2. **補完**: 全重み付き軸がNaNのEdgeのcompositeを、同じリクエストのbbox内でデータのある
   Edgeの**距離加重平均difficulty**で補完する（`compose_costs_from_axis_matrix`へ
   ベクトル演算を1段追加。固定定数[50等]ではなくリクエスト内の実データ由来にし、軸名に
   依存しない汎用処理にする）。スカラー版`compute_cost_from_axis_scores`はbbox平均を
   引数で受け取る形に揃え、`tests/test_evaluation_bulk.py`のビット単位一致オラクルを維持する。
3. **表示は変えない**: 区間表示（`_build_segment_details`）のdifficulty・axis_difficultiesは
   「データ無し＝None」のまま。探索コストのみ補完し、その旨を`docs/design-principles.md`へ
   「全軸欠損Edgeの探索コストは補完値、表示は欠損のまま」として明記する（T536で揃えた
   探索と表示の一致に、意図的な例外を1つ作ることになるため必ず文書化する）。
4. **取込側の補完（比率次第）**: highway種別から材料の既定値を埋めて欠損自体を減らす案。
   取込バッチと本番再取込が要るため、1の計測結果を見てから別タスクとして判断する。

## 関連（2026-09-03追記）

2026-09-03の`/code-review`（[T557](T557.md)項目3）で、探索コストだけでなくT531の折返し点
ランキング（`(cost/len − 1)/P`の逆算、`road_graph_engine.py: select_loop_turnarounds`）でも
全軸欠損Edgeが「難易度0＝最良」として扱われ、`overall_difficulty`（NaN除外）と物差しが
食い違うと指摘された。本タスクの対応方針2（補完）を入れれば逆算値も補完値を反映するが、
ランキング側で「NaN区間の距離割合」を別途扱うかはT557で判断する。

## 完了条件

- 合成データで「全軸欠損Edgeのcostが、データありEdgeの距離加重平均difficultyに対応する
  コストと一致する」「一部欠損は従来どおり再正規化」「全Edge欠損ならcost=distance」の
  テストがpass、`tests/test_evaluation_bulk.py`のオラクル一致が維持される。
- 本番同等bboxでの欠損比率をT552.mdへ記録し、`pytest -q -m "not postgis"`green。
- `docs/design-principles.md`・`docs/modules/backend/evaluation-*.md`（該当設計書）を
  同一コミットで更新。

## 実装（2026-09-03、対応方針2・3）

- `domain/difficulty.py`に`distance_weighted_difficulty_array`（`distance_weighted_difficulty`
  のnumpyベクトル化版、NaN=None・欠損除外して残りの距離で再正規化・全欠損/距離合計0は
  Noneを返す）を追加。
- `domain/evaluation.py: compose_costs_from_axis_matrix`（bulk版）に、
  `distance_weighted_difficulty_array(composite, distance_m)`で求めたbbox内平均を、
  composite=NaNのEdgeのcost算出だけへ代入するステップを追加。戻り値の`composite`・
  `axis_contributions`（表示用）はNaNのまま変えない。bbox平均自体が無ければ（bbox全体が
  欠損）従来どおりcost=distance_m。
- `domain/evaluation.py: compute_cost_from_axis_scores`（スカラー版）・`compute_edge_cost`に
  `bbox_mean_difficulty: float | None = None`引数を追加（既定Noneは従来どおりの挙動、
  `tests/test_evaluation.py`の既存オラクルテストは無変更で通過）。呼び出し元が
  bulk側と同じ値を渡せばcostがビット単位で一致することを
  `test_compose_costs_from_axis_matrix_bbox_mean_fallback_matches_scalar_oracle`で検証。
- `services/road_graph_engine.py: _build_search_graph`のINFOサマリへ
  `missing_axis_edges`（重み付き軸がすべてNaNのEdge件数）・`missing_axis_distance_ratio`
  （距離加重比率）を追加（対応方針1の実態把握用）。
- テスト: `tests/test_difficulty.py`（`distance_weighted_difficulty_array`4件）、
  `tests/test_evaluation.py`（`compute_cost_from_axis_scores`の補完適用/非適用2件、
  `compose_costs_from_axis_matrix`の全欠損Edge補完・全Edge欠損時cost=distance・
  オラクル一致の3件）を追加。`tests/test_evaluation.py`の
  `test_compute_cost_from_axis_scores_signature_has_no_primary_attribute_names`
  （T142の完了条件テスト）は許容パラメータ集合へ`bbox_mean_difficulty`を追加して更新。
- `docs/design-principles.md`「構造仕様」へ原則10「探索コストと表示difficultyの一致」
  （既存原則の明文化＋本タスクの例外を追記）、`docs/modules/backend/
  evaluation-scoring.md`へ`compute_cost_from_axis_scores`・`compose_costs_from_axis_matrix`・
  「探索コストの既定経路」節の3箇所を更新。
- **対応方針1（本番同等bboxでの欠損比率計測）・4（取込側の補完の要否判断）は未実施**:
  本セッションの実行環境には実際のOSM道路網データ（本番同等bboxで`import_pbf`を実行した
  結果）が無く、追加したINFOサマリ（`missing_axis_edges`/`missing_axis_distance_ratio`）を
  実データで計測できなかった。対応方針1の計測（東京駅30km等の実bboxでこのINFOログを
  観測する）を先に行い、比率が1%以上であれば対応方針4（取込側でのhighway既定値補完）の
  要否を別途判断する必要がある——本タスクの完了条件のうち「本番同等bboxでの欠損比率を
  T552.mdへ記録」は満たせていない。次にこの計測を行うセッションが、本番/dev環境で実際に
