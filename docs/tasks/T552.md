# T552: 重み付き軸がすべてデータ欠損のEdgeのコストを「最良扱い」から「bbox平均difficultyで補完」へ変える

状態: 完了（2026-09-03起票・同日、対応方針2・3を実装。2026-09-04、対応方針1
[本番同等bboxでの欠損比率計測]を全8軸へ拡大して実施、対応方針4[取込側の補完の要否判断]
は見送りと判断し完了（詳細下記）。[T531](T531.md)推敲時のユーザー質問「候補がデータ
欠損Edgeへ偏っている場合、自然なルートに近づける拡張はできるか」を受けて起票。T531とは
独立に着手可能だがコスト式の意味論に触るため別番号で切り出した）

## 背景

コスト式`cost = distance × (1 + P × composite/100)`は、composite difficultyがNaN
（リクエストで重みを振った軸すべてで材料が欠損）のEdgeを`penalty_multiplier = 1.0`、
つまりdifficulty 0相当の「最良の道」として扱う（`domain/evaluation.py:
compose_costs_from_axis_matrix`のNaN分岐、スカラー版`compute_cost_from_axis_scores`も同じ）。
一部の軸だけ欠損なら残りの軸で再正規化される（「データ無しは除外」方針）が、全軸欠損の
補完値は未定義のままこの挙動になっている。自転車インフラ100%のような単一軸の重み設定では、
タグ未取得の道路がサイクリングロードと同じコストになり、T531のフロンティア方式では
そうした道を優先的に折返し候補へ拾う方向に働く。

## 対応方針

1. **実態把握を先に行う**: `_build_search_graph`のINFOサマリへ「重み付き軸がすべてNaNの
   Edge比率（件数・距離加重）」を追加し、本番同等bbox（東京駅30km等）で計測する。比率が
   1%未満なら2のみ、それ以上なら4（取込側）も検討する。
2. **補完**: 全重み付き軸がNaNのEdgeのcompositeを、同じリクエストのbbox内でデータのある
   Edgeの**距離加重平均difficulty**で補完する（`compose_costs_from_axis_matrix`へ
   ベクトル演算を1段追加。固定定数[50等]ではなくリクエスト内の実データ由来にし、軸名に
   依存しない汎用処理にする）。スカラー版`compute_cost_from_axis_scores`はbbox平均を
   引数で受け取る形に揃え、`tests/test_evaluation_bulk.py`のビット単位一致オラクルを維持する。
3. **表示は変えない**: 区間表示（`_build_segment_details`）のdifficulty・axis_difficultiesは
   「データ無し＝None」のまま。探索コストのみ補完し、その旨を`docs/design-principles.md`へ
   「全軸欠損Edgeの探索コストは補完値、表示は欠損のまま」として明記する（T536で揃えた
   探索と表示の一致に、意図的な例外を1つ作ることになるため必ず文書化する）。
4. **取込側の補完（比率次第）**: highway種別から材料の既定値を埋めて欠損自体を減らす案。
   取込バッチと本番再取込が要るため、1の計測結果を見てから別タスクとして判断する。

## 関連（2026-09-03追記）

2026-09-03の`/code-review`（[T557](T557.md)項目3）で、探索コストだけでなくT531の折返し点
ランキング（`(cost/len − 1)/P`の逆算、`road_graph_engine.py: select_loop_turnarounds`）でも

## 対応方針1（本番同等bboxでの欠損比率計測、2026-09-04実施）

本番backendへ実際にルート生成をリクエストし、`missing_axis_edges`/
`missing_axis_distance_ratio`のINFOログを観測した。この過程で計測を大きく妨げる
2件の別問題を発見・対応した（詳細は各タスク参照）:

1. **本番の派生データが95%以上未計算だった**: 計測の前提として最新の派生データが
   必要だったため`refresh_derived.py`（[T281](T281.md)段階2）を本番で初実行したところ、
   ⑦`precompute_elevation_attributes`の途中でメモリ枯渇によりVM全体が6時間14分
   応答不能になるインシデントが発生（スワップ0Bが一因、対策済み。詳細は
   [docs/disaster-recovery.md](../disaster-recovery.md)「既知のリスク・対策」参照）。
   復旧後、メモリ上限を指定して残り段階を完了させ全件更新した。
2. **タイル永続キャッシュの版数が古いままだった**: 上記1完了後も計測結果が変化せず、
   `refresh_derived.py`がディスク永続キャッシュの版数を上げる既存運用ルールに従って
   いなかったことが原因と判明（[T574](T574.md)として起票・対応完了）。

この2件の対応後（本番キャッシュを手動クリアし未ウォームなbboxで再計測）に得られた
実測値:

| bbox（起点・距離） | 対象軸（重み） | edges | missing_axis_edges | missing_axis_distance_ratio |
|---|---|---|---|---|
| 大宮駅30km（35.9066, 139.6234） | gradient/stop_density/accident（各0.2、night時間帯外で0扱い） | 737,341 | 106,658 | **0.132**（13.2%） |

比率は1%を大きく超えているため、対応方針の分岐に従い**対応方針4（取込側の欠損補完）の
要否判断が必要**な水準。ただし、この13.2%には正しく除外されるべき値も混入している
可能性が高い点に注意——`night`軸は`RoutePreference.with_time_scope`により日中は
自動的に重み0へ上書きされる設計だが、本計測はAPIへ渡した`route_preference`の
生の重み（night=0.0を明示指定）で送っており、`missing_axis_edges`算出自体は
「リクエストで重みを振った軸」ベースであり時間帯上書き後の実効重みを見ていない
可能性がある（`_build_search_graph`のこのログが上書き前後どちらの重みを参照している
かは未確認、対応方針4着手前に要確認）。また`car_stress`・`surface_q`・
`bicycle_infra_quality`・`wind`は本計測では重み0（対象外）のため、これらの軸で
欠損比率が変わる可能性も未計測。

**次のセッションへの引き継ぎ**: 対応方針4（取込側でのhighway既定値補完の要否判断）に
着手する前に、(a) 上記night軸の重み解釈を`_build_search_graph`のコードで確認する、
(b) 対象を全8軸へ広げて再計測する、(c) どのhighway種別・材料が欠損の主因かを
`edge_attribute_counts`等をSQLで直接確認する、の3点を先に行うこと。

## 対応方針4の先行調査（2026-09-04、同日内に完了）

上記(a)〜(c)を実施した。

**(a) night軸の重み解釈**: `road_graph_engine.py: _build_search_graph`のコードを確認。
`preference = self._route_preference.with_time_scope(active_scopes)`（time_scope上書き）
は`missing_axis_mask`算出より前に適用されている（402行目→430行目）。さらに
`domain/evaluation.py: compose_costs_from_axis_matrix`は重み0の軸を`weighted_weight_sums`
へ一切加算しない設計（`np.where(valid, weight, 0.0)`、重み0なら有効データの有無に
関わらず0）。つまりnight軸の時間帯上書きは欠損判定に混入せず、13.2%という数値は
正しい。懸念は解消。

**(b) 全8軸への計測拡大**: 大宮駅30kmで各軸単独（重み1.0）の`missing_axis_distance_ratio`
を計測。

| 軸 | missing_axis_distance_ratio |
|---|---|
| gradient | 76.5% |
| surface_q | 82.9% |
| stop_density | 0.0% |
| car_stress | 0.0% |
| accident | 0.0% |
| bicycle_infra_quality | 0.0% |
| night | 未計測（time_scope上、日中は単独計測不可） |
| wind | 対象外（動的軸、材料欠損の概念が無い） |

stop_density/car_stress/accident/bicycle_infra_quality が軒並み0%なのは、これらの
材料抽出ロジックが「タグ不在＝定義された否定値」として扱う設計のため（`edge_attribute_counts`
はDB側で100%カバー済み、`bicycle_infra_flags_or_none`はcyclewayタグ不在を「自転車
インフラなし」という確定値として扱う）。

**(c) 欠損主因のSQL調査**: 本番DB全体で確認。

- **gradient（DB全体で88.4%欠損、582,355/5,025,067件）**: 原因はOSMデータの疎さでは
  なく、[T574](T574.md)発見のタイル永続キャッシュ版数問題を解消した後も、
  ⑦precompute_elevation_attributesが今朝のOOMインシデント（[T575](T575.md)参照）
  以降完走していなかったこと。純粋な運用上の未完了であり、**対応方針4（取込側の
  推測補完）の対象外**——バッチを安全に完走させれば解消する（[T575](T575.md)で
  根本原因のOOMバグを修正済み、[T576](T576.md)でバッチ自体も高速化済み。本番での
  実際の完走はこれらとは別に改めて実施する）。
- **surface_q（DB全体で85.0%欠損、1,130,127/1,329,632件）**: `osm_raw_ways.surface`
  タグがOSM生データ側にそもそも記録されていない、真の欠損。こちらが対応方針4が
  本来想定していた対象。

## 対応方針4の最終判断: 見送り

surface_qについて、highway種別から材料の既定値を推測して埋める案（対応方針4）は
**見送る**。理由:

1. 対応方針2・3（本タスクで実装済み）により、探索コストは既に「全欠損Edgeにbbox平均
   difficultyを代入する」形で補完済み。T531（周回フロンティア方式）が「データ欠損Edge＝
   最良の道」として不自然に優先してしまう、本タスクの起票理由となった問題への対策は
   これで十分機能する。
2. 取込側（material）で既定値を埋めると、表示用のdifficulty（区間ごとの路面品質表示）
   まで「本当は不明なのに、それらしい値」を出すことになり、対応方針3で明文化した
   design-principles.md原則10「探索コストと表示difficultyの一致（欠損は表示上も
   欠損のまま）」と衝突する。
3. 既存コードにも同じ判断の前例がある——`material_catalog.py`の`bool_default`
   （真偽値材料のタグ不在時の扱い）は既定で"false"（タグ不在=確定的な否定）だが、
   `surface_good`と自転車インフラ系5材料は明示的に"nan"（タグ不在=不明、確定値と
   混同しない）を選んでいる。surface由来の材料は既にこのシステム内で「不明を推測で
   埋めない」側の設計を採用済み。
4. これは「T552のバグ修正の延長」ではなく「highway種別から路面品質を推定する新しい
   予測ロジックの新設」という、スコープの異なる別機能に相当する。

代わりに、欠損データは埋めずに可視化し、判断を利用側（軸定義）へ委ねる方針とし、
そのための管理画面を[T577](T577.md)として別途起票した（ユーザー判断、2026-09-04）。
