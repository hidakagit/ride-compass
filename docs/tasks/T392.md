# T392. タイル材料一式（graph_material_cache）のRedis複製化〔調査のみ・保留〕規模M — トリガー: デプロイ直後のレイテンシがユーザー体験上の問題になった時点、または複数メンバーが触る状態にプロダクトが成長し複数ワーカー化（T388）に着手する時点（2026-08-29ユーザー判断、T388と同時に再検討）

状態: 保留（2026-08-29ユーザー判断）

- 背景: T390（`is_split_up_to_date`・`get_edges_with_geometry`のRedis cache-aside化）
  完了後、ユーザー指示「DB全般を見直して」の続きとして、`graph_material_cache.py`
  （z12タイル単位の道路グラフトポロジ＋5材料一式、いわゆる「splitデータ」本体）を
  Redisへ複製する案を検証した（PostGISは正本のまま、Redisは読み取り高速化用の
  複製に限定する——T387/T390と同じcache-asideパターン。road_edges/road_nodes
  自体をRedis専業へ移設する案ではない。単一ワーカー稼働の現状でも「デプロイの
  たびにこのプロセス内キャッシュが全消去される」問題への対策として検討した）。
- 本番実測（2026-08-29、コンテナ内で一時スクリプトを実行、ユーザー承認済み。
  スクリプトは実行後にコンテナ・VM双方から削除済み、正本データは無変更）:
  - 単一タイル（エッジ9,081件）: PostGIS cache-miss 691.3ms → Redis想定
    （読み出し+デシリアライズ）76.5ms（約9.0倍）。JSONペイロード約3.4MB。
  - **30km周回1件ぶん（王子起点、16タイル、道路データ56.3万エッジ・21.2万ノード）**:
    PostGIS cache-miss合計37,142ms → Redis想定合計12,112ms（**約3.1倍**）。
    JSONペイロード合計約299.4MB。Redis書き込み（初回投入）197ms。
- 効果の限定的な性質: このキャッシュが効くのは**「プロセスにとって初回アクセス
  （デプロイ直後・新規エリア）」の場合のみ**。同一プロセス内で2回目以降の
  リクエストは既存のin-processキャッシュ（`graph_material_cache`本体）が
  ヒットし、Redisを挟んでも到達できない真の温パス（本番実測4.9秒、
  docs/architecture.md「_maybe_warm_tile_cache」周辺コメント参照）の方が
  常に速い。つまりRedis化しても「37秒」と「4.9秒」の中間（12秒）にしかならず、
  かつ効くのは限定的なタイミングのみ。
- 見送り判断の理由（2026-08-29ユーザー判断）:
  1. **投資対効果がT390の2箇所（is_split_up_to_date・get_edges_with_geometry、
     数ms→コンマ数msへほぼ無視できるコストに短縮）より大幅に弱い**
     （3.1倍止まり、かつ効くタイミングが限定的）。
  2. **メモリリスクが実装コストに見合わない**: 30km周回1件で約300MB、関東7都県
     全域が対象範囲のため理論上の最大キャッシュ量はさらに大きい（実際は使われた
     エリアのみ遅延投入されるため理論値までは膨らまないが、上限設定なしでは
     危険）。本番Redisの現在の設定を確認したところ`maxmemory=0B`（無制限）・
     `maxmemory_policy=noeviction`（上限到達時に古いキーを追い出さず書き込み
     拒否）で、退避ポリシー未設定のまま大容量キャッシュを追加するとPostgreSQL・
     backendアプリと同居するVM全体（11GB、実測時空き約9.7GB）のメモリを圧迫する
     リスクがある。
- 影響範囲（保留した場合）: 現状は既存のin-processキャッシュが定常状態を
  十分カバーしており実害は無い。保留し続けることでブロックされるのは
  「デプロイ直後・新規エリア初回アクセスの応答が遅い（数十秒級）」状態の
  緩和のみで、緊急性は無い。ただしbackendが複数ワーカー構成へ移行する場合
  （[T388](T388.md)と同じトリガー）は事情が変わる——複数ワーカーでは
  in-processキャッシュがワーカー間で共有されないため、「別ワーカーが既に
  温めたタイルを、たまたま自分が最初にリクエストしたワーカーは知らない」
  という状況が常時発生するようになり、その場合はRedis複製の価値がT388・T390と
  同様に大きく上がる。T388着手時は本タスクも合わせて再検討すること。
- 対応方針（着手時の設計メモ、保留中は変更しない）: 着手する場合は
  T387/T390と同じcache-asideパターン（PostGISが正本、Redisは複製、`save_graph`
  成功直後の書き戻し・PBF再importでの無効化）を踏襲しつつ、**着手前に必ず
  Redisへ`maxmemory`＋退避ポリシー（`allkeys-lru`等）を設定**すること。
  シリアライズ形式もJSON以外（msgpack・pickle等、Pydanticの`model_construct`で
  バリデーションを省略する等）を比較検討し、Python側オブジェクト再構築コスト
  （実測の支配的要因、37秒中PostGIS実行部分を除いた12秒がこれに相当）を
  できるだけ削れないか確認する。
