# T910. 最寄りNodeの探索が、条件に合うNodeが無いとき総当たりへ落ちる

規模S。
状態: 完了（2026-09-16。[T906](T906.md)から分離——性能の話で、直す前に利用者から
見た単位での実測が要る）

## 背景

`domain/routing.py: find_nearest_node_indexed`は、述語（自転車で通れる道に接している等）を
満たすNodeをバケット格子から近い順に探す。**述語を満たすNodeが1つも無いとき、探索半径が
格子全体へ広がりバケット数の3乗規模のセル走査に落ちる**。

起きるのは「起点・目的地の周囲に条件を満たす道が無い」ときで、まさに応答が遅いと困る場面
（利用者は結果が出ないまま待つ）。

## 直す前に測ること

`docs/CLAUDE.md`「修正の原則」——性能は利用者から見た単位で測る。関数1本の計測で判断しない。

1. **どのくらいの頻度で起きるか**。本番のログから、`find_nearest_node_indexed`が空振りした
   リクエストの割合を出す（該当ログが無ければ足すところから）。
2. **利用者から見た遅さ**。ルート生成1回の応答時間のうち、この走査が占める割合を実測する。
   占めていなければ直す価値は無い（**この探索が遅いこと自体は問題ではない**——遅いのが
   利用者に届いているかが問題）。
3. 直すなら、打ち切り（走査するリング数の上限）と「見つからなかった」の返し方をセットで
   決める。黙って総当たりするより、早く諦めて理由を返す方が利用者には良い。

## 実測（2026-09-16）

### 本番ログからは頻度が出せなかった

`docker rm`で旧コンテナごと消えるため、**本番のログはその時点の稼働ぶんしか残らない**
（確認時点で129行・約2時間ぶん。ローテーション済みファイルも0件）。backendへpushするたびに
デプロイが走る運用では、この経路の頻度を過去に遡って数えることはできない。
加えて、この探索へ入ったこと自体はログに出ていない（出るのは到達Node数0の場合だけ）。

### 走査量は「遅い」ではなく「止まる」だった

半径の上限が`len(index.buckets) + 1`——**バケット数**であり、リング数として意味のある値では
なかった。述語が1つも真にならないとこの上限まで伸び、走査は半径の3乗で増える。

| バケット数 | 述語が一度も真にならないとき | 通常（述語なし） |
|---|---|---|
| 64 | 83.6 ms | 0.08 ms |
| 210 | 3.13 秒 | 0.10 ms |
| 462 | 34.0 秒 | 0.06 ms |
| 1,444（半径30km相当） | **16.9 分** | 0.03 ms |

`find_nearest_node_indexed`は`asyncio.to_thread`を通さずイベントループ上で呼ばれるため、
**その間backend全体が応答しない**。利用者から見た単位で測るまでもなく、これは性能の
チューニングではなく可用性の問題だった。

### テストが守っていた「スナップできない」は、本番では成立していなかった

上限がバケット数だったため、小さなグラフ（テスト）では数リングで打ち切られ「遠すぎて
スナップできない」ように見え、**本番規模では実質無制限**（数千リング＝数千km）だった。
この差に、利用者向けの挙動を確かめる3つのテストが乗っていた——
`test_preview_segment_returns_none_when_no_path_exists`・
`test_generate_via_waypoints_returns_empty_when_a_waypoint_cannot_be_snapped`・
`test_select_via_nodes_returns_empty_when_destination_is_unreachable`。
3つとも通っていたが、本番では同じ入力が別の結果になる。

## 直したこと

1. **半径の上限を索引が占める範囲から導く**。その外側にはどれだけ広げてもセルが1つも無い。
   走査量は462バケットで34.0秒→1.6ms、30km規模で16.9分→6.3ms。結果は変わらない
   （範囲を覆う正方形まで必ず見るため、最近傍は取りこぼさない）。
2. **覆う範囲の外を指した点は寄せない**（索引のセル境界＋1セルの余裕）。読み込んだ
   グラフの外をクリックしたとき、遠くの道へ黙って寄せた結果を返さない。
3. **目的地の補正に距離の上限を入れる**（`MAX_DESTINATION_CORRECTION_KM = 1.0`、
   ユーザー判断）。[T602](T602.md)の狙いは「タップした先が孤立した小塊なら、すぐ近くの
   本線へ移す」で、それより遠くへ動かすと利用者が指した覚えのない場所を通るルートになる。
   超えたら補正せず`no_candidates_side="destination"`を立てて候補なしを返す。

打ち切り（本文の「3.」で挙げた案）は入れていない。範囲から導く上限で走査が
ミリ秒に収まったため、リング数の人為的な上限は要らなくなった。

## 検証（わざと壊して落ちることを見た）

- 半径の上限を`len(buckets)+1`へ戻す → 新設した
  `test_find_nearest_node_indexed_stops_at_the_index_extent_when_nothing_matches`が落ちた
  （1.5秒→9.1秒。走査セル数を索引の範囲から導いた上限と突き合わせているため、時間では
  なくセル数で判定していて不安定にならない）。
- `max_distance_km`を外す → `test_select_via_nodes_returns_empty_when_destination_is_unreachable`
  が落ちた（20km離れたNodeへ補正して1本返してしまう）。
- backend: `pytest -q -m "not postgis"` 2,006件green・`pytest -q -m postgis` 280件green・
  `ruff check app scripts benchmarks tests` 通過。
- `python scripts/review_checks.py docs` → exit 0。
