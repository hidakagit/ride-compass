# T910. 最寄りNodeの探索が、条件に合うNodeが無いとき総当たりへ落ちる

規模S。
状態: 未着手（2026-09-16起票。[T906](T906.md)から分離——性能の話で、直す前に利用者から
見た単位での実測が要る）

## 背景

`domain/routing.py: find_nearest_node_indexed`は、述語（自転車で通れる道に接している等）を
満たすNodeをバケット格子から近い順に探す。**述語を満たすNodeが1つも無いとき、探索半径が
格子全体へ広がりバケット数の3乗規模のセル走査に落ちる**。

起きるのは「起点・目的地の周囲に条件を満たす道が無い」ときで、まさに応答が遅いと困る場面
（利用者は結果が出ないまま待つ）。

## 直す前に測ること

`docs/CLAUDE.md`「修正の原則」——性能は利用者から見た単位で測る。関数1本の計測で判断しない。

1. **どのくらいの頻度で起きるか**。本番のログから、`find_nearest_node_indexed`が空振りした
   リクエストの割合を出す（該当ログが無ければ足すところから）。
2. **利用者から見た遅さ**。ルート生成1回の応答時間のうち、この走査が占める割合を実測する。
   占めていなければ直す価値は無い（**この探索が遅いこと自体は問題ではない**——遅いのが
   利用者に届いているかが問題）。
3. 直すなら、打ち切り（走査するリング数の上限）と「見つからなかった」の返し方をセットで
   決める。黙って総当たりするより、早く諦めて理由を返す方が利用者には良い。
