# T870. 派生データ世代のガードを、材料を実際に読む経路へ移す

規模S〜M。
状態: 未着手（2026-09-15起票。統合レビュー第9回のP0）

## 背景

[T847](T847.md)で新設した「バッチが派生データを書き直したらディスクキャッシュを捨てる」
TTLガードが、材料ディスクキャッシュを実際に読む経路から一度も呼ばれていない。**split鮮度が
最新の定常状態では本番で一度も発火しない。**

`ensure_caches_match_db`の本番呼び出し元はリポジトリ全体で
`services/graph_service.py:228`の1箇所のみで、置かれているのは
`get_or_build_graph_with_attributes`。一方`get_search_materials_for_bbox`
（`graph_service.py:299-348`）は`_ensure_split_up_to_date`が真なら
`_build_search_materials_from_tile_cache`（`:341-348`）へ直行し、
`get_or_build_graph_with_attributes`を通らない。冷パス（`:350-353`）だけが通る。
`region_service.py:60-68`のバックグラウンド構築も`is_split_up_to_date`が真なら即returnする。

**タスク記述・docstring・実装・テストの4者が別々の場所を指している**:

- [T847](T847.md):82 は呼び出し点を「`GraphService.get_search_materials_for_bbox`の先頭」と
  宣言している（**こちらが正**）
- `derived_data_revision_service.py:38`のdocstringは存在しない`main.py` lifespanの
  `force`呼び出しを名指しする（grepで0件。`force=True`の呼び出し元はテストのみ）
- `test_graph_service.py`の追加はFakeに`get_derived_data_revision`を生やしただけで、
  呼ばれることを検査していない

## 保留することで何が起きうるか

本番で`refresh_derived.py`を再実行すると`derived_data_meta.revision`は進むが
`osm_raw_ways.split_at`は変わらないため、backendはタイル材料ディスクキャッシュを
世代照合せずに復元し続け、**プロセスを再起動するまで古い材料でルートを生成する**。
症状は「未訪問タイルだけ新しい」局所的な形で現れるため気づけない。
T847.mdが動機として名指しした「`refresh_derived.py`の再実行がまさにこの形」そのもの。

## 対応方針

- 呼び出しを`get_search_materials_for_bbox`の先頭（宣言どおりの位置）へ移す
- `force`のdocstringは実在する呼び出し元だけを書く（無いならテスト専用と明記するか撤去）
- `test_graph_service.py`へ「`get_search_materials_for_bbox`を呼ぶと
  `get_derived_data_revision`が引かれ、世代が変われば材料キャッシュが消える」を1件足す

移した後、**わざと`derived_data_meta.revision`を進めて「温まったタイルへの2回目の
リクエストでディスクキャッシュが捨てられる」ことを実際に観測してから**完了扱いにする
（CLAUDE.md「『実装した』ではなく『効いている』を確認して完了にする」）。
