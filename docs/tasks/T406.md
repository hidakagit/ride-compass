# T406. パネル構成再編（道路/評価軸/環境/スポットの4チップ・3排他ドメイン）

状態: 未着手（[T400](T400.md)節1からの分割）、実装準備調査は完了（2026-08-30）

- 背景: 詳細はT400.md「1. パネルの最上位グルーピングを『道路』『評価軸』『環境』『スポット』
  の4チップ・3排他ドメインへ再編」参照。旧「観測/推定/動的」グルーピングを廃止し、対象ベースの
  4チップへ再編する。「道路」と「評価軸」は幾何が線のため選択の排他ドメインを共有。UIは新規
  発明せず既存のチップ＋ⓘ設定パネル（T169・T216）を流用し、選択方式をチェックボックスから
  ラジオボタンへ変更する。T405（風の評価軸表示）と合わせて検討すると手戻りが少ない可能性あり。

## 実装準備調査（2026-08-30、Explore調査済み。着手前に必ず現状のdiffを再確認すること）

**重要**: T405（別セッションで並行実装中）がここに挙げたファイル（`mapLayers.ts`等）に
触れている可能性が高い。着手前に必ず最新の状態を`git fetch`・実ファイルの読み直しで
確認すること（この節は調査時点のスナップショット）。

### 現行カタログは4分類へ機械的に再分類可能

`frontend/src/components/Map/mapLayers.ts: buildMapLayers`（166-418行目）の既存フィールド
（`category`・`dataNature`）だけで、追加のデータモデル変更なしに4グループへ分類できることを
確認した:

- **道路**（線）: `category==="roadCondition"`（roadType/roadSurface/designation/tunnel/oneway）
- **評価軸**（線）: `dataNature==="composite"`（`axis:${axisId}`、`RAMP_AXES`/`useAxisCatalog`から
  動的生成済み）
- **環境**（面）: `category==="terrain"||"weather"`（elevation/precipitationNowcast/windVector/
  thunderNowcast/tornadoNowcast）
- **スポット**（点）: `category==="trafficSafety"||"amenity"`のうち`dataNature`が`composite`でない
  もの（stopPoi/supplyPoi/accidents。`axis:accident`等のramp軸とは別物なので要区別）
- `route`（生成されたルート本体）は`category`未指定で単独チップのまま、排他ルール対象外
  （T400方針どおり）

### 変更が必要な箇所（5系統、具体的な行番号つき）

1. **`frontend/src/app/page.tsx: handleLayerToggle`（645-650行目）** — 中心的な変更点。現状は
   `setLayerVisibility((prev) => ({ ...prev, [id]: on }))`のみで排他制御が一切無い。ONにした際、
   同一排他ドメイン（道路↔評価軸の共有ドメイン／環境単独／スポット単独）に属する他の全レイヤーIDを
   OFFにするロジックを追加する。ドメイン判定には新しい「排他ドメインID」導出関数が要る
   （`category`/`dataNature`だけでは道路と評価軸が別カテゴリ値のため同一ドメインと判定できない）。
2. **`frontend/src/components/Map/MapOverlayControls.tsx: buildChipGroups`（103-117行目）** —
   「観測/推定/動的」3分類ロジックを4分類（道路/評価軸/環境/スポット）へ置き換え。
3. **`MapOverlayControls.tsx`のチップ描画3ブランチ**（`group:composite`1149-1254行目、
   `group:raw`1262-1323行目、`group:dynamic`1328-1381行目）— 4分岐への書き換え、または汎用化。
   `DATA_NATURE_ICONS`（139-143行目）・`MAP_LAYER_DATA_NATURE_LABELS`等（mapLayers.ts 96-117行目）
   も新4グループ用のラベル・アイコン辞書へ置き換え。
4. **`renderVisibilitySettings`（910-1013行目）** — 引数`scope: "raw"|"composite"|"dynamic"`の型を
   新4スコープへ変更。**要確認事項（下記参照）**。
5. **localStorageキーの名前空間**: `MAP_OVERLAY_HIDDEN_IDS_STORAGE_KEY`（178行目）のキー形式
   `${scope}:${id}`のprefix語彙、`GROUP_VISIBILITY_KEYS`（170行目、`group:composite`等3値）を
   新4キーへ。旧prefixのゴミが残ることは実害なしとして許容する既存方針（646行目コメント）を踏襲。

### 要確認事項（実装着手時に最初に解決すること）

調査の結果、**「チェックボックス→ラジオボタン化」の対象が2つのUI層のどちらを指すか、
T400.mdの文言だけでは一意に決まらない**ことが判明した:

- (A) グループ内メンバーのON/OFF本体（`ChipButton`の`onTap`→`onToggle(member.id, !member.on)`、
  実際に地図にレイヤーが出るかどうかを決める主選択）
- (B) ⓘボタンで開く「表示する項目を選ぶ」設定パネル内の表示/非表示チェックボックス
  （`renderVisibilitySettings`、943-1013行目。これは「そのチップ自体を選択肢一覧に出すか
  隠すか」というメタ設定で、地図の表示ON/OFFとは別の状態軸）

T400.md本文の意図（「各グループ内は完全な排他選択、1つだけ選べる」）およびT400.md冒頭の
ユーザーとの合意経緯から判断すると、**排他化すべきは(A)（実際にどのレイヤーが地図に出るか）
である可能性が高い**——(B)はあくまで「選択肢一覧に何を並べるか」というフィルタで、
排他とは別次元の設定として現状のまま残せる。ただし断定はできないため、実装着手時に
この解釈で進めてよいかユーザーへ確認すること。

### 参考: 既存の排他選択パターン

`frontend/src/app/page.tsx: renderRouteColorSectionBody`（1122-1180行目）が、ルート線の
色分けモード（風/勾配/舗装/総合難易度）を`@radix-ui/react-radio-group`で実装している
（単一の文字列state＋`onValueChange`という型はT406の要件と一致）。ただし`MapOverlayControls.tsx`
側は`createPortal`を使うポータル式`ChipButton`構造のため、Radixをそのまま持ち込むか、
同等ロジック（選択時に同一ドメイン内の他IDをOFFにする関数）を自前実装するかは実装時の判断。
