# T651. Redisを残すか撤去するかを実測で決める 規模M

状態: 完了（2026-09-07）。結論はRedisの用途を外部連携へ絞ること。実装は[T652](T652.md)

## 背景

[docs/caching.md](../caching.md)の整備中に本番を実測した結果、**Redisが現在提供している
価値がほぼ1点（プロセス再起動をまたいでキャッシュを温かく保つこと）に縮んでいる**ことが
分かった。

本番実測（2026-09-07 20時JST）:

| 観測 | 値 |
|---|---|
| キー数 / メモリ | 3,195キー / **5.19MB**（`maxmemory` 2GB） |
| ヒット率 | 17.8%（`keyspace_hits` 151,099 / `misses` 698,250） |
| backendのプロセス構成 | **単一プロセス**（`uvicorn app.main:app`、`--workers`指定なし） |

キーの内訳は`jma:amedas` 1,286・`wind:forecast` 1,053（[T645](T645.md)で削除したコードの
残骸。TTLで自然消滅する）・`jma:tile` 818・`jma:tile-index` 1。ルート生成系
（`road_edge_geometry` / `dynamic_way_value` / `road_graph_tile`）は**0件**だった
（計測時点でルート生成が走っていなかったため）。

**単一プロセスであるため、「プロセス間で共有する」というRedis最大の利点は現状働いていない。**
APSchedulerのバッチもリクエスト処理も同じプロセス内にいる。データ量5MBはプロセス内へ
持っても支障のない規模である。

再起動で失った場合の損害も、ルート生成系を除けば小さい:

| データ | 再起動で失うと | 損害 |
|---|---|---|
| JMAタイル | プリウォームが10分以内に再充填 | 小（`basetime`が5〜10分で変わり元々入れ替わり続けている） |
| アメダス | 起動直後のバッチが1リクエストで全国分を再取得 | ほぼ無し |
| ルート生成系 | PostGISへフォールバック | **未検証** |

## 決めたいこと

Redisを撤去して「プロセス内キャッシュ＋ディスク」の2層構成にするか、残すか。撤去できれば
[T644](T644.md)の大半（Redis cache-asideの骨格重複・base64包装・サーキットブレーカー）が
不要になる。

**判断を保留している唯一の材料がルート生成系のRedisヒットの寄与**である。ここだけが
「PostGIS往復を減らす」という実利があり得る。[T387](T387.md)に「PostGIS単体比5.9倍高速」と
あるが、これは往復1回あたりの比較で、ルート生成1回あたりの総時間への寄与は測られていない。

## 計測の設計

プロセス内キャッシュ（L1）が効いてしまうと差が出ないため、**コンテナ再起動でL1を空にした
状態で比較する**。

1. **Redisあり・L1なし**: コンテナ再起動 → 直後にルート生成1回 → 所要時間と
   `/api/debug/stats`の`cache:*`カテゴリを記録
2. **Redisなし・L1なし**: ルート生成系のキーを削除（`road_edge_geometry:*`・
   `dynamic:*`・`road_graph_tile:*`）→ コンテナ再起動 → 同じ地点でルート生成1回 → 同様に記録
3. 2回とも同一の出発地点・距離・設定で行い、PostGIS側のページキャッシュ状態を揃えるため
   間隔を空けすぎない

**注意**: 本番でコンテナ再起動2回とルート生成2回を行う。再起動はデプロイと同じ操作
（`docker stop -t 90` → `run`）だが、実施前にユーザーへ確認すること。

## 判断基準

- ルート生成1回の総時間への寄与が**1秒未満**なら、Redisを撤去してプロセス内＋ディスクへ
  寄せる（[T644](T644.md)の対象が大幅に縮む）
- 数秒以上稼いでいるなら残す

## 計測結果（2026-09-07、本番VM）

出発地点(35.6812, 139.7671)・30km・許容5kmで固定。各runの前にコンテナを再起動して
プロセス内キャッシュ（L1）を空にした。ウォームアップで一度生成し、Redisを充填してから開始。

| run | Redis | 所要 | 備考 |
|---|---|---|---|
| A | あり（温） | **13.9秒** | `cache:edge-geometry-redis` hit率100%・`cache:road-tile-redis` hit率100% |
| B | 無し（該当キー削除） | **14.2秒** | 同 hit率0% |
| A2 | あり（温） | **13.9秒** | |
| B2 | 無し（該当キー削除） | **14.1秒** | `cache:edge-geometry-redis` calls=2 hit率0% avg=38ms |

**Redisの寄与は0.2〜0.3秒（1.4〜2%）** で、2往復とも安定して1秒を大きく下回った。
`road:edge:geom`は2,794キーあるが、読み出しは`mget`2回に集約されているため、ミスしても
PostGISへの往復が2回増えるだけで済んでいる。

## 判断: Redisは残し、用途を外部連携へ絞る

計測はRedis全廃の判断材料として始めたが、**将来ワーカーを複数化する可能性がある**という
ユーザー判断（2026-09-07）を受けて、Redis自体は残すことにした。プロセス内キャッシュは
ワーカーごとに独立するため、外部フェッチを肩代わりしているキャッシュ（JMAタイル・アメダス）は
共有できないと上流へのリクエストがワーカー数に比例して増える。

一方、ルート生成系（`road:edge:geom`・`road:tile:fetched`・`dynway`）は正本が自前のPostGISで、
寄与も0.2〜0.3秒しかない。**これらはプロセス内へ移す**（[T652](T652.md)）。

基準は「外部への負荷を肩代わりしているかどうか」として
[docs/caching.md](../caching.md)へ書いた。

## 前提が変わる条件

将来 `uvicorn --workers` の複数化、または blue/green デプロイ（複数コンテナ同時稼働）へ
進む場合、プロセス間共有が必要になりRedisの価値は復活する。現状は`--network=host`で
単一ポートを占有するため blue/green ができない（[docs/architecture.md](../architecture.md)
のデプロイ節参照）。**撤去を選ぶ場合、この前提もセットで記録すること。**
