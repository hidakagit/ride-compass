# T555: T531後に残ったbackendの古いコメント（8方位gather前提）とデッドコード（`destination_point`）のクリーンアップ

状態: 完了（2026-09-03起票・同日完了。[T531](T531.md)のbackend側docs同期作業中に見つかった
コード側の乖離2件が起点）

## 背景

T531で周回生成が8方位固定＋`trace_loop`の`asyncio.gather`並列から、フロンティア方式
（折返し点候補を逐次探索し、実ジオメトリは`evaluate_loops`が候補ぶんまとめて1回取得）へ
転換した結果、`GraphService.get_edges_with_geometry`のロック根拠コメントが実態と食い違い、
旧`_loop_waypoints`だけが呼んでいた`domain/geo.py: destination_point`が本番コードから
未参照（テストのフィクスチャ座標生成のみ）になった。

## 対応方針

1. **`_repository_lock`は撤去せず、根拠コメントを実態へ合わせる**。ロックの現役の役割は
   `_get_or_build_tile_materials`のキャッシュmiss時DB問い合わせ（タイルごとにgatherで
   並行、T538フォローアップ）の直列化であり、`get_edges_with_geometry`側は
   `evaluate_loops`（候補評価のgather開始前に1回）・`preview_segment`（1回）の逐次呼び出し
   しか無いため、ロック取得は「将来の並列化で前提が崩れたときの保険」と明記する。
   撤去しない理由: ロック自体は`_get_or_build_tile_materials`に必要で残るため、
   `get_edges_with_geometry`から外しても得られるものが無く、外した場合に
   `evaluate_loops`のgather内へrepository到達経路を足す将来の変更で同一`AsyncSession`
   同時使用クラッシュ（docs/decisions/road-graph-migration.md）が再発する側だけが残る。
2. **`destination_point`は`app/domain/geo.py`から削除し、テスト専用ヘルパー
   `backend/tests/geo_fixtures.py`へ移す**（デッドコード監査T321の「テスト専用になった
   export は削除しテスト側を書き換える」と同じ判断）。`test_road_graph_engine.py`の
   合成グラフ（8方位スポーク等）・`test_geo.py`の`bearing_between`/`haversine_distance_km`
   検証が「起点から方位θへ距離d進んだ点」を必要とするため、関数自体は削除せず置き場所を
   変える。`test_geo.py`の`destination_point`単体テスト4件はヘルパーの自己テストになる
   ため削除した（`haversine_distance_km`/`bearing_between`の検証がヘルパーの距離・方位の
   正しさを間接的に担保する）。
3. **同種の「8方位gather前提」の残存コメントを`backend/app`全体でgrepし、事実と食い違う
   ものをまとめて直す**（N→1の個数削減リファクタ後は削除シンボルの逆引きだけでなく、
   名指ししない周辺表現も広く確認する、というT462の教訓）。過去形で書かれた経緯説明
   （`attributes.py`「最大24回＝8方位×3レグ呼ばれていた」・`route_generator.py`「旧8方位
   方式」・`jma_amedas.py`）は正しい記述のため触らない。

## 実装メモ

- `graph_service.py`: `__init__`のロック根拠コメント・`get_edges_with_geometry`のdocstring
  （並行セッションがT531のdocs同期と同時に一度更新していた「同一リクエスト内の他の並行
  処理[標高取得等]と同時に走りうる構造は残る」という記述は、`evaluate_loops`が
  `get_edges_with_geometry`をgather開始前に`await`し切る構造のため事実と異なり、本タスクで
  上記1の内容へ置き換えた）。
- `road_edge_geometry_cache.py`モジュールdocstring・`road_graph_repository.py:
  get_edges_with_geometry` docstring: 「`trace_loop`から8方位ぶん並列に呼ばれる」→
  「`evaluate_loops`が候補ぶんまとめて1リクエスト1回」。T390当時の本番実測値は経緯として残置。
- `road_graph_engine.py`: `_RoadGraphContext.node_index`・`prepare`のコメント「最大17回」
  （8方位×2経由地＋起点）、`_bbox_around_point`のdocstring「8方位全ての経由地点をカバー」、
  `_fetch_elevation_attributes`の「候補数[最大8]倍」（`max_routes`は上限15）、
  `_build_candidate`引数説明の「方位ごとの経路」、`_route_composite_difficulty`の
  「同じ方位の順方向・逆回り候補」、索引候補絞り込みの「8方位すべてのDijkstra探索が失敗」。
- `domain/routing.py: NodeSpatialIndex` docstringの「最大17回」。
- `weather_service.py`: 「8方位分の候補が確定済みでも…（route_generator.pyのgatherは
  trace_loopのみreturn_exceptions=True保護対象）」→ 天候は`RoadGraphEngine.prepare`が探索前に
  1回取得しNoneなら評価なしで続行する、という現在の構造へ。
- `domain/geo.py`: `destination_point`と、それだけが使っていた`Coordinates` importを削除。
- `tests/geo_fixtures.py`新設、`tests/test_geo.py`・`tests/test_road_graph_engine.py`のimportを
  差し替え。
- docs: `docs/modules/backend/routing-engine.md`（ロック節・設計上の注意の箇条書き・
  `domain/geo.py`節）・`docs/architecture.md`（`geo.py`・`test_geo.py`の行）を同一コミットで追従。
