# T964: 「一本化した」と書いた過去の改修が、本当にそうなっているかを棚卸しする

状態: 未着手（2026-09-19起票）

## 背景

複雑度を下げる改修をしてもコードが増え続けている（[T963](T963.md)）。原因の1つは、
**旧実装が残ったまま「完了」になっていること**である。

[T956](T956.md)の作業中に実例が出た。[T546](T546.md)は「`EdgeMaterialTable`で復元コストを
Edge数に依存しなくする」を達成したが、**旧`EdgeMaterialBundle`経路は残った**。当時は意図した
並存だが、いつ解消するかを誰も持っていなかった。同じ作業中に私自身も、本番から到達しなく
なった実装を「後で消す」と言って残していた。

`docs/improvement-plan.md`の`[x]`は700件、うち「一本化・共通化・統合・撤去・削除・廃止」を
題や注記に含むものが**150件**。

## 対応方針

その150件それぞれについて、**タスクが「消した」と書いているシンボル・ファイル・経路を
いまのリポジトリでgrepする**。残っていれば、その改修は主張した状態に達していない。

結果は3つに分かれるはず。

- **消えている**: 主張どおり。何もしない
- **残っているが理由がある**（テスト専用のオラクル等）: その理由をタスクエントリへ書き足す
  ——「なぜ残すか」が書かれていないものは、次に読んだ人が本番経路だと誤解する
- **残っていて理由が無い**: 削除を起票する

あわせて、**そのタスクが残す/消すの判断に使った根拠の形**も見る。「0件だった」「使われて
いない」のように**その時点の計測だけで決めているもの**は、条件が変われば通る。
「いつなら通るのか」が書かれているかを確認し、書かれていなければ足す
（[T961](T961.md)が実例——`edge_landcover`のカバレッジ100%を見て「way側フォールバックは
死んでいる」と判定したが、実際は「いまバッチが最新」という意味でしかなかった）。

有限で、結果が白黒つく。**件数が多いので、まず20件ほどで当たりの割合を見てから残りの
進め方を決める**（全件を最初から通すと、当たりが少なかったときに費用だけ払う）。
