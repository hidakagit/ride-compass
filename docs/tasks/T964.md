# T964. PostGIS統合テストが、並行セッション間で同じDBを共有している 規模S

状態: 未着手（2026-09-19起票、T950の完了検証で4件が偽の失敗を出したことから）

## 背景

`backend/tests/conftest.py`の`TEST_DATABASE_URL`が既定で単一のDBを指すため、同じ作業ツリー
群で動く複数のセッションが同じ行を同時に書き換える。落ちるのはテストの中身と無関係な
ファイルで、単独実行では通る。

[T950](T950.md)の完了検証で実際に起きた姿:

| | 結果 | 所要 |
|---|---|---|
| `pytest -m postgis`（並行セッションが稼働中） | 323 passed / **4 failed** | 6分15秒 |
| 落ちた4件だけを単独で再実行 | 4 passed | **7秒** |

落ちたのは軸レジストリ2件・事故取込1件・道路ノード次数1件で、そのとき触っていた範囲
（`scripts/`・`backend/benchmarks/`・コメント1行）とは接点が無い。同種の誤読は以前にも
起きている——「単体実行でも失敗する」という報告がコードのバグではなく共有DBの競合だったと
判明した事例があり、4プロセス同時実行で再現も取れている。

**害は「たまに落ちる」ことではなく、落ちた側が毎回それを切り分けさせられること。** 偽の
失敗は自分の変更を疑う時間を必ず消費し、切り分けを飛ばせば逆に本物の回帰を「どうせ競合」と
見送る。落ちるファイルが変更と無関係なぶん、どちらの誤りも起きやすい。

## 調べた事実（2026-09-19）

- 接続先を決めているのは`backend/tests/conftest.py`の`TEST_DATABASE_URL`**1箇所だけ**。
  PostGIS統合テスト22ファイルはすべてそこからimportしており、URLを自前で組み立てている
  ファイルは無い（`grep -rn TEST_DATABASE_URL backend scripts`）。
- 既に環境変数`TEST_DATABASE_URL`で上書きできる。分離する仕組みが無いのではなく、
  **既定値がセッション間で同じ**ことだけが問題。
- テーブル作成は`road_graph_engine`フィクスチャが`CREATE EXTENSION postgis`＋
  `Base.metadata.create_all`でモジュール単位に行う。DBさえ分かれていれば、この経路は
  そのまま使える。

## 対応方針

**既定のDB名を作業ツリー単位で導く。** `TEST_DATABASE_URL`が未設定のとき
`ridecompass_test_<worktree名>`を組み立て、そのDBが無ければ作る。環境変数での明示指定は
今までどおり優先する。

- 作業ツリー名から導くため、同じテーマのセッションでは同じDBが再利用され、PostGIS拡張の
  作成（初回のみ数秒）を毎回払わない。別の作業ツリーで動く並行セッションとは構造的に
  衝突しない。
- 副産物として、`test_migrate.py`が共有DBをmigration適用済みにして他のテストを巻き込む
  既知の事故も消える（まっさらなDBを要求するテストが、自分専用のDBを持つため）。
- 手元で`pytest-xdist`が使えなかった理由の一部もこれのため、並列化の再検討ができるように
  なる（このタスクでは並列化まで踏み込まない）。

**DBを増やすなら、落とす導線をセットで用意する**（docs/caching.md「世代番号を使うなら旧世代を
削除する導線をセットで」と同じ形）。作業ツリーを片付けるときに対応するDBも落とせる手段を
併せて置く。

スキーマ分離（同一DB内で`search_path`を分ける）は採らない。DB作成権限が要らない利点は
あるが、PostGIS拡張の解決と`public`を前提にするmigrationテストの兼ね合いを1件ずつ確認する
必要があり、上より高くつく。

## 完了条件

- 既定で、別々の作業ツリーから同時に`pytest -m postgis`を走らせても互いに落とさない
  （2セッション同時実行で実測する。片側だけの成功を根拠にしない）
- 増えたDBを落とす手段があり、その手順が書かれている
- `TEST_DATABASE_URL`を明示したときの挙動は変わらない

## 扱わないもの

- devポート・CPU/IOの共有。これらも並行セッション間で奪い合うが、**遅くなるだけで偽の
  失敗にはならない**ため、このタスクでは触らない。
