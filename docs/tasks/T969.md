# T969: アーキテクチャの総点検（層の責務・到達可能性・知識の重複・検知器の棚卸し）

状態: 未着手（2026-09-20起票）

## 背景

[T956](T956.md)で、複雑度を下げる改修が長く効いていなかった理由が具体的に分かった。
4つの層で同じ形の歪みが同時に出ていた。

1. **DBが持つべき制約をappが吸収していた**。`road_edges.osm_way_id`にFKもNOT NULLも無く、
   「wayの行が無い区間」という状態を材料の値式10本が`CASE WHEN ... IS NULL`で毎回吸収して
   いた。兄弟の派生表5本は同じFKを既に持っており、本番の違反行は0件だった。
2. **appにテスト専用の口があった**。`folds_tag_absence_to_false`はテストからしか呼ばれない
   のにapp配下にあった（同タスク内で撤去）。
3. **本番から到達しないコードが「オラクル」名目で残っていた**。`compute_edge_cost`は
   [T240](T240.md)の対応方針の時点で「回帰テストのオラクルとして存続させる」と書かれ、
   それを置き換えた`compute_edge_costs_bulk`まで同じ理由で残り、1か月近く残骸だった。
4. **テストがテストを検証していた**。新旧2実装の等価だけを見るテスト、宣言を書き写した
   テスト、タイルSQLをテスト側で組み直して突き合わせるテストがあった。

**既存の仕組みでは見つからない。** `/review:all`は2026-09-19（前日）に実施済みで、
上のどれも挙がっていない。理由は構造的で、`/review:overall`・`/review:complexity`は
人がコードを読んで気づく形（問題を作った本人が同じ目で見る）、`scripts/review_checks.py`の
検知器29本は母集団が「識別子と参照」「テキストの型」で、**層の責務**と**入口からの
到達可能性**を見るものが1本も無い。DBのスキーマとappの前提を突き合わせるものも無い。

## 対応方針

**このタスクは事実の棚卸しに徹し、直さない。** 直すのは点検2〜6が出した母集団に対して、
既存の[T963](T963.md)・[T965](T965.md)・[T966](T966.md)・[T967](T967.md)・[T968](T968.md)が
行う。**総点検→各タスクでダブルチェック**の順にするのは、今の状態が信用できないため
（ユーザー判断、2026-09-20）——各タスクのエントリに書かれた前提自体が古い可能性があり、
先に現物から事実を出し直す。

判断を混ぜず、**母集団の導出方法と件数**を出す。各点検は「何を列挙したか」「いくつか」
「代表例」を記録し、1件ごとの可否判断は後続タスクへ渡す。

### 点検1: 層の責務（DB ↔ app）

- 派生表の親子関係を列挙する。`app/infrastructure/*_models.py`の`ForeignKey`宣言と、
  本番の`pg_constraint`（`contype='f'`）・`pg_attribute.attnotnull`を突き合わせ、
  **モデルにもDBにも制約が無い親参照列**を出す（`backend/scripts/run_probe.py`）。
- 1で出た列について、app側が「無いかもしれない」前提で書いている箇所を探す
  （SQL式の`IS NULL THEN`、`COALESCE`の既定値、`or {}`、`is None`分岐）。
- 各列について、制約を張った場合の違反行数を本番で測る。

### 点検2: 本番の入口からの到達可能性

- 入口を列挙する: `main.py`が登録するFastAPIルーター、`app/batch/*`の`main()`、
  `backend/scripts/*`、`lifespan`が起動するジョブ。
- そこから`app/**`を辿って到達する定義の閉包を出し、**到達しない公開定義**を列挙する。
- 偽陽性の型を除く（デコレータ登録のルートハンドラ、SQLAlchemyの宣言モデル）。
  取りこぼしの型は[T963](T963.md)の「2026-09-20の実測」節を参照（テキストのgrepでは
  docstringの言及を使用と数える。ASTの名前参照でも到達可能性は見えない）。

### 点検3: 同じ知識が2か所にある箇所

- SQLの式・列の並び・合成の順序のように、**片方だけ変わると静かに食い違う**ものを探す。
- 導出方法: `app/**`と`tests/**`から同一のAST部分木（一定ノード数以上）を出す。
  frontendのテキストクローンは既存の`/review:duplication`（jscpd）が見ているため、
  そちらと母集団が重ならない範囲（backendのAST）に限る。

### 点検4: appにテスト専用の口

- 母集団: `app/**`のモジュール直下の公開定義のうち、定義元以外の`app/`・`scripts/`・
  `benchmarks/`・`migrations/`から参照されず、`tests/`からのみ参照されるもの。
  2026-09-20の実測で15件（うち`reset_*`・`*_cache_size`のようなテストが状態を初期化・
  観測する正当な口を含む）。点検2の閉包で置き換えられるなら、そちらへ寄せる。

### 点検5: テストがテストを検証している箇所

- 母集団: `tests/**`のうち、(a)2つの実装の出力一致だけを見るもの、(b)レジストリ・
  カタログのリテラルを書き写して突き合わせるもの、(c)本番の式・順序をテスト側で
  組み直しているもの。
- (a)(b)は`docs/comments.md`・CLAUDE.mdの判定基準が既にあるため、それに照らして列挙する。

### 点検6: 検知器29本の棚卸し

- 1本ずつ「母集団の導出方法」「強制経路（`DETECTOR_ENFORCEMENT`）」「全件実行での
  現在の検出数」「そのうち誰も直していない期間」を表にする。
- 母集団が重なっている組を出す。参考表示のみの検知器について、**出力が実際に減っているか**
  を履歴（`.claude/commands/review/history/`）から確かめる。2026-09-20時点の全件実行で
  参考は140件（うち経緯コメント103件）あり、誰も直していない。
- [T966](T966.md)と母集団が重なる。**T966が先か、この点検がT966の入力になるか**を
  着手時に決める（重複して同じ表を2回作らない）。

### 点検7: 周期レビューが構造的な指摘を出さないのはなぜか

**過去には全ソースを読み直す形のレビューがあり、止まっている。**

| 形 | 時期 | 出したもの |
|---|---|---|
| 全体最適レビュー（全ソース・DB設計をゼロから再読） | 第8回2026-08-24・第9回2026-08-25 | 起票案A〜F＋知見4件（T285〜T288）、材料供給への投資・migration未適用の恒久対策など |
| ゼロベース網羅レビュー（code-review max×9分割） | 2026-08-30 | P1 13件・P2/P3 72件（T425・T426→T463〜T471） |
| `/review:all`（overall/complexity/consistency/uiのレンズ） | 2026-08-16〜継続、17回 | 個別の事象のみ。**アーキテクチャの規則についての指摘は0件** |

前2つは**全ソースを読み直す**形で、構造の指摘を実際に出していた。止まった後は
`/review:all`（成果物を見るレンズ）だけが回り、以後は事象しか出ていない。

**依頼が却下されてきた経緯**（ユーザー指摘、2026-09-20）: 「全体最適になっているか」
「責務が偏っていないか」という構造レビューの依頼は複数回あったが、そのたびに
「それはreviewで同じ仕組みがあるから」と退けられた。CLAUDE.mdの
「既に同じ目的の仕組みがあるかを確かめる」は**検知器を足すときの歯止め**であって、
構造レビューの依頼を却下する理由に使うものではない。



**17回の`/review:all`で、「欠陥を生んでいる規則」の指摘は一度も出ていない。**
挙がるのは個別の事象（このレイヤーが壊れる・このdocsが撤去済みの名前を指す・このガードが
発火しない）で、構造に近いものも検知器についての2件だけ（2026-09-15 F-2「検知器が母集団を
手で列挙している」、2026-09-16 F-2「0件は母集団に入っていないだけ」）。
**アーキテクチャの規則についての指摘は0件。**

CLAUDE.md「修正の原則」の「範囲は性質から導く——症状が出た場所でなく、欠陥を成立させて
いる性質で決める」を、**レビュー自身が守っていない**。レンズの問いが「一貫しているか」
「複雑さの置き場は適切か」という成果物への問いのため、成果物レベルの欠陥しか出ない。
出力もP0/P1/P2の事象リストで、事象を直す方へ誘導している。

- 履歴17回の指摘を、「個別の事象」「事象を生んでいる規則」に分類して件数を出す。
- 同じ性質の指摘が複数回繰り返されているもの（再発）を出す。再発は「1件ずつ直した」
  ことの証拠で、規則を直していれば起きない。
- レンズの問い（`overall.md`・`complexity.md`・`consistency.md`）が、規則を問う形に
  なっていない箇所を特定する。
- **結論として、レンズを直すのか・廃止して別の形にするのかまでを出す**
  （[T966](T966.md)の「検知器を足す前に全体と突き合わせる」と同じ判断を、レビュー基盤
  そのものへ適用する）。**止まった「全ソースを読み直す」形を戻す選択肢を必ず検討に含める**
  ——レンズを直すより、そちらが実際に構造の指摘を出していた。
