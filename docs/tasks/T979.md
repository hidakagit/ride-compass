# T979. 文書を読み手で分け直す 規模M

状態: 未着手（2026-09-20起票、ユーザーと合意した構成を記録）。

## 背景

`docs/` 直下に性格の違う文書が同居している。T970で「提供元の仕様をどこへ書くか」「列の命名
規則をどこへ書くか」を決めようとした際、置き場が決まらず、同じ事実を3箇所（コードの
docstring・DDLコメント・テストのdocstring）へ書いてしまった。

CLAUDE.mdの階層表は既に4つの層を定義しているが、**その層に入らないものが `docs/` 直下へ
流れ込んでいる**——凍結されたレビュー記録6本（約1,900行）・完了した計画2本・タスク台帳。

## 決めた構成

| 読み手 / 性格 | 場所 | 備考 |
|---|---|---|
| **サイクリスト** | `README.md` | ここだけ。`how-route-scoring-works-plainly.md` は取り込んで削除する |
| **開発者・モジュール外**（構成・技術選定・API・データモデル・運用の制約・**コードから導けない外部の事実**・セットアップ） | `docs/architecture/` | いまの `architecture.md` 2,399行を章ごとのファイルへ分割する（分割は許可されている） |
| **開発者・モジュール内の構造契約** | `docs/design-principles.md` ＋ `docs/modules/*.md` | 現状のまま |
| **トピック別の詳細方針** | `docs/<topic>.md` | CLAUDE.md階層表が既に定義。`testing`・`logging`・`caching`・`comments`・`documentation`・`workflow`・`deployment-sync`。現状のまま |
| **レビュー基盤** | `.claude/commands/review/` | CLAUDE.md階層表が既に定義。現状のまま |
| **タスク** | `docs/improvement-plan.md`（台帳）＋ `docs/tasks/Txxx.md` | 台帳を方針と同居させない |
| **上のどれにも当てはまらない、過去となった文書＝メンテナンスしないもの** | **`docs/archive/`** | 新設 |

## 詳細仕様と外部仕様の分け方（この再編の前提）

- **外部仕様＝ユーザが把握する必要があるもの**。サイクリストが把握すべきものは`README.md`、
  開発者が把握すべき構造契約は`design-principles.md`
- **詳細仕様＝ユーザが把握不要なもの → テスト**。構造仕様15が既に
  「テストは『今』のふるまいの網羅」と定めている
- **同じ事実を2箇所へ書かない**。ドキュメント記載方針が「個数・全件の一覧を書かない」と
  定めているため、列挙が必要なものは構造的に文書へ書けず、テストへ寄る

実例（T970で決めたもの）:

| 事実 | 置き場 |
|---|---|
| 獲得標高は橋・トンネルでは積まない | `README.md`（表示される数字の意味） |
| 事故の密度は2024年の配布ファイル1年ぶん | `README.md` |
| 提供元の使用許諾・仕様（原文と出典） | `docs/architecture/` とDDLのコメント |
| 向きで変わる列の命名規則 | 列の宣言のそばに一言 ＋ テストが強制 |
| `reversed_material_expression("max_grade") == "-m.min_grade"` | テストのみ |
