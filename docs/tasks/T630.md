# T630. キキクルで拡大すると色が消える・描画が遅い 規模M（完了）

状態: 完了（2026-09-06起票・同日完了）

## 背景

ユーザー実機報告（本番）「キキクルで拡大すると色が消える」「あとそもそも描画が遅い」。
デバッグログ上は429・404のいずれも発生していないとのユーザー確認済み。

## 調査経過（2026-09-06）

- **却下**: `DYNAMIC_WEATHER_RENDERERS.disaster`のキキクル4種が`maxzoom: 11`（奇数）である点
  （JMAナウキャスト系が2024年12月以降偶数ズームのみ配信という外部情報と符合するように
  見えた）を最初の仮説にしたが、ユーザーが実機で取得した実エラーのzoomが`7`（低ズーム・
  偶奇どちらの理論とも無関係）だったため棄却。
- **却下**: 出発時刻ピッカーの既定値（デバイス現在時刻、ユーザー観測で19:20）とJMA公式サイトの
  最新データ時刻（19:10）のズレを疑ったが、`useDynamicWeatherLayers.ts`のキキクル4種payload
  （`landslideRiskPayload`等、327〜344行目）は`dynamicLayerTargetTime`を一切参照せず
  `targetTimes.json`の最新1件（`frames[0]`）をそのまま使う設計のため、「19:20」は
  無関係な出発時刻表示だと判明。
- **有力候補**: ユーザーが実機コンソールで採取した実エラー:
  ```
  [map:error] AJAXError: Failed to fetch (0): https://193-123-166-150.sslip.io/api/jma-tile/
  bosai/jmatile/data/risk/20260906101000/immed0/20260906101000/surf/flood/7/113/50.pbf
  {"sourceId":"region-dynamic-weather-disaster-flood-vector"}
  ```
  ステータス`(0)`はアプリ（FastAPI）まで到達する前の失敗（TLS/QUIC/接続層）を示唆し、
  backend側`enforce_rate_limit`（429）にもJMA上流の404にも該当しない＝ユーザーが
  デバッグログで429/404を確認できなかったことと整合する。`docs/architecture.md`
  「同時接続数上限との競合」・[T580](T580.md)/[T581](T581.md)（本番VMのnginxをHTTP/2+HTTP/3
  [QUIC]化、`NEXT_PUBLIC_TILE_BASE_URL`でタイルをbackend直接配信）の経緯と合わせると、
  QUIC（UDP 443）はモバイル回線・一部ネットワークで不安定/遮断されることがあり、ズームで
  一斉に発生する大量のタイル要求（disasterチップ7ソース＋基礎地図＋路面＋POI＋事故＋標高）が
  重なるタイミングで接続確立に失敗する、という筋が候補として残っている。
- **却下**: QUIC/HTTP-3不安定説。ユーザーに確認したところWi-Fiで発生しており、モバイル回線
  限定の話ではなかった。

## 真因（2026-09-06判明）: 本番backendがクラッシュループしていた

ユーザーから「dbサーバが502で落ちた」との報告を受け調査したところ、上記のFailed to fetch等の
症状は無関係な別の**進行中の本番障害**が主因だったと判明した。

並行セッションが投入した[T624](T624.md)段階1のコミット（`238e109`、19:26:55 JST デプロイ、
まさにユーザーが最初にエラーを観測した19:28:27の直前）で、`infrastructure/derived_data_
freshness.py`（webアプリが起動時に必ず読み込むモジュール）が`batch/precompute_way_
landcover.py`から`ALGORITHM_VERSION`定数をモジュール直下でimportするようになった。ところが
`precompute_way_landcover.py`は冒頭で`import rasterio`/`import pyproj`しており、この2つは
`requirements-batch.txt`限定の依存（本番webイメージ=`Dockerfile`には`requirements.txt`しか
入らない）。結果、**本番backendコンテナは起動する瞬間に`ModuleNotFoundError`でクラッシュし、
`--restart unless-stopped`により再起動→同じ理由でクラッシュを無限に繰り返す状態**になって
いた。`deploy-backend.yml`は`docker run -d`が返った時点で成功判定するため、この起動失敗を
検知できずデプロイ自体は「success」と表示され続けた（GitHub Actions run #232実績）。

**修正**（`a322f55`、`master`へ直接push・デプロイ済み）: `precompute_way_landcover.py`の
`import rasterio`/`import rasterio.errors`/`import rasterio.features`/`import pyproj`を、
実際に使用する2箇所（`count_pixels_in_ring`関数内・`_RasterSource.__init__`内）へ遅延させた。
rasterio/pyproj未インストール環境で、修正前は`ModuleNotFoundError`が実際に再現し、修正後は
`app.main.app`まで含めて正常にimportできることを確認済み（仮想環境を作りrequirements.txt
[batch除く]のみをインストールして検証）。

このクラッシュループが「そもそも描画が遅い」（backendが502を返し続けタイル・API双方が
失敗）の直接原因だった可能性が高い。

## 「色が変になる」報告（2026-09-06、backend復旧後の再報告）について: バグではないと判明

backend復旧後、ユーザーから改めて「本番で色が変になるバグ再現している」との報告と、拡大前後の
スクリーンショット2枚を受けた。拡大前は洪水キキクル（河川沿いの赤・黄の線）のみが見え、
拡大後に大雨/土砂キキクルのメッシュ（黄→オレンジ→紫の面塗り、房総半島の広範囲）が新たに
出現していた。

ユーザーに同じ場所・同じタイミングでキキクル公式サイトを確認してもらったところ、**公式サイトも
同様に黄〜オレンジ〜紫の広範囲な塗りになっている**ことを確認した。つまりRideCompassの表示は
（見た目が急に派手になって驚くとしても）実際の気象庁データを正しく反映しており、コード側の
バグではないと判断した。拡大前に見えていなかったのは、面塗りタイルの読み込みタイミングの
問題（上記のbackendクラッシュループで読み込みが遅延・失敗していた時間帯と重なっていた
可能性が高い）であり、バックエンド復旧後は正常な読み込み待ちとして説明がつく。

## 対応不要と判断した項目

- 奇数ズームクランプ説・出発時刻ズレ説・QUIC不安定説はいずれも実機証拠と矛盾し却下済み
  （上記「調査経過」参照）。
- キキクルの色そのもの（メッシュの範囲・配色）はコード変更不要。

## 再発（2026-09-06、backend復旧後）: 「詳しくなると洪水しか出ない」「zoom11が重い」

backend復旧・「色が変になる」報告の解決後、ユーザーから改めて2件の実機報告があった。

1. 「ある拡大率より詳しくなると河川の氾濫情報（洪水キキクル）しか出ない。荒くなると大雨等も
   出る」。
2. 「Zoom11ぐらい、画面が重すぎる」。

### 調査1: raster/vectorでmaxzoom超過時の挙動が異なる（確認済み、未解決）

`MapView.tsx`をgrepし、`disaster`チップの表示可否をズームで明示的に切り替えるアプリ側コードは
存在しないと確認した。heavyRain/landslide/inundation（raster）とflood（vector）は
`maxzoom`の数値自体はいずれも11で同じ。

npm経由で`maplibre-gl@5.24.0`本体（`dist/maplibre-gl-dev.js`）を取得し実際に読んだところ、
`VectorTileSource`は`reparseOverscaled = true`を明示的に持つのに対し`RasterTileSource`は
持たない（コンストラクタに存在しない＝false相当）という、ライブラリ内部での本物の差異を
確認した。`coveringTiles`関数はこのフラグの有無で`maxzoom`超過時の`OverscaledTileID`の
組み立て方を分岐させる。ユーザー報告（rasterは詳細ズームで消え、vectorのfloodは残る）と
方向性は一致するが、この差異がWebGL描画のどの段階で実際に「消える」結果になるのかは
`drawRaster`/`drawTiles`関数を読んでも特定できておらず、**未解決のまま**（実機での
`[map:request]`ログ有無の確認をユーザーへ依頼中）。

### 調査2・修正: zoom11で「災害」チップの全ソースが同時にsetTilesされ続けていた（規模S、修正済み）

zoom11は`heavyRain`/`landslide`/`inundation`/`flood`の`maxzoom`と一致する。この付近では
各レイヤーがネイティブ解像度のタイルを新規に大量取得する必要があり、房総半島全体が写る
広さの表示では概算で1レイヤーあたり約70枚×4レイヤー≒280枚のタイル取得・PNGデコード・GPU
テクスチャアップロードが同時に発生する（`360°/2^11≒16km四方/タイル`から算出）。これ自体は
表示範囲とレイヤー数から来る負荷でコード側の不具合ではない。

ただし調査の過程で、**この負荷がズーム時の一度だけでなく、使用中も繰り返し発生する**
別の实装上の問題を発見した。`applyDynamicWeatherState`を呼ぶ`useEffect`
（`MapView.tsx`、旧行番号3344付近）の依存配列は`dynamicWeather`オブジェクト全体で、
これは風・降水・雷・落雷等いずれか1要素が変化するだけ（5〜10分おきの各種ポーリングで
必ず何かは更新される）でも新しい参照になる。この結果、`applyDynamicWeatherState`は
`DYNAMIC_WEATHER_LAYER_IDS`の全グループぶん毎回再実行され、tileUrlTemplateが前回から
一切変わっていないheavyRain/landslide/inundation/flood等のソースに対しても
`rasterSource.setTiles()`/`vectorSource.setTiles()`が無条件に呼ばれていた。MapLibreの
`setTiles()`は同じURLでも無条件にソースをリロードし読み込み済みタイルを破棄して
取得し直す仕様のため、5〜10分おきに280枚規模の再読み込みが繰り返されていたことになる。

**修正**: `applyDynamicWeatherState`に`setTilesIfChanged`ヘルパーを追加し、`WeakMap`で
ソースごとの前回適用URLを記録、変化が無ければ`setTiles`を呼ばないようにした
（`MapView.tsx`）。`applyDynamicWeatherState`をテスト用にexportし、
`MapView.dynamicWeatherLayers.test.ts`へ回帰テスト2件（同一URL連続適用で1回のみ・
URL変化時は再度呼ばれる）を追加。`vitest run`・`tsc --noEmit`・`eslint`で確認済み。

これはzoom11の初回スパイク自体を無くすものではないが、**同じ表示状態を維持している間の
繰り返し再読み込みは無くなる**ため、「画面が重すぎる」の体感の一部改善が見込める。
zoom11自体の負荷低減（表示レイヤー数を減らす等のUX判断）は本タスクでは行わず、
ユーザーとの「一部レイヤーだけONにすると軽くなるか」の切り分け結果を待って判断する。
