# T630. キキクルで拡大すると色が消える・描画が遅い 規模M（調査中）

状態: 調査中（2026-09-06起票）

## 背景

ユーザー実機報告（本番）「キキクルで拡大すると色が消える」「あとそもそも描画が遅い」。
デバッグログ上は429・404のいずれも発生していないとのユーザー確認済み。

## 調査経過（2026-09-06）

- **却下**: `DYNAMIC_WEATHER_RENDERERS.disaster`のキキクル4種が`maxzoom: 11`（奇数）である点
  （JMAナウキャスト系が2024年12月以降偶数ズームのみ配信という外部情報と符合するように
  見えた）を最初の仮説にしたが、ユーザーが実機で取得した実エラーのzoomが`7`（低ズーム・
  偶奇どちらの理論とも無関係）だったため棄却。
- **却下**: 出発時刻ピッカーの既定値（デバイス現在時刻、ユーザー観測で19:20）とJMA公式サイトの
  最新データ時刻（19:10）のズレを疑ったが、`useDynamicWeatherLayers.ts`のキキクル4種payload
  （`landslideRiskPayload`等、327〜344行目）は`dynamicLayerTargetTime`を一切参照せず
  `targetTimes.json`の最新1件（`frames[0]`）をそのまま使う設計のため、「19:20」は
  無関係な出発時刻表示だと判明。
- **有力候補**: ユーザーが実機コンソールで採取した実エラー:
  ```
  [map:error] AJAXError: Failed to fetch (0): https://193-123-166-150.sslip.io/api/jma-tile/
  bosai/jmatile/data/risk/20260906101000/immed0/20260906101000/surf/flood/7/113/50.pbf
  {"sourceId":"region-dynamic-weather-disaster-flood-vector"}
  ```
  ステータス`(0)`はアプリ（FastAPI）まで到達する前の失敗（TLS/QUIC/接続層）を示唆し、
  backend側`enforce_rate_limit`（429）にもJMA上流の404にも該当しない＝ユーザーが
  デバッグログで429/404を確認できなかったことと整合する。`docs/architecture.md`
  「同時接続数上限との競合」・[T580](T580.md)/[T581](T581.md)（本番VMのnginxをHTTP/2+HTTP/3
  [QUIC]化、`NEXT_PUBLIC_TILE_BASE_URL`でタイルをbackend直接配信）の経緯と合わせると、
  QUIC（UDP 443）はモバイル回線・一部ネットワークで不安定/遮断されることがあり、ズームで
  一斉に発生する大量のタイル要求（disasterチップ7ソース＋基礎地図＋路面＋POI＋事故＋標高）が
  重なるタイミングで接続確立に失敗する、という筋が候補として残っている。
- **未確認**: Wi-Fi/セルラーいずれでも再現するか、単発の緩やかなアクセスでも起きるか
  ズーム時のバーストでのみ起きるか、はユーザーへ確認中。
