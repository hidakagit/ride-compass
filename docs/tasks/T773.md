# T773. ルート結果タブの中身を減らす 規模M

状態: 完了（2026-09-12起票・完了。ユーザー指示「ルート結果タブの再編は、今のタブ内をもっと
シンプルにしてから改めて詰めたい」から。[T769](T769.md)の前段にあたる）

## 背景

「ルート結果」は生成結果を見る画面だが、候補1本ぶんのタブに公開軸すべての難易度一覧と
「重み付き寄与度」の内訳が縦に並ぶ。[T759](T759.md)が測ったとおりデスクトップの
サイドバーは`scrollHeight`=1614 / `clientHeight`=764で、読み切るのに2画面ぶんある。

パネルをどう分けるか（[T769](T769.md)）の前に、**1つの候補を読むのに必要な情報量自体**を
減らす。分ける前に減らさないと、分けた先が同じ密度のまま増えるだけになる。

## measurement（着手時に実施）

Playwrightの実ブラウザ（e2eのAPIモック＋軸カタログの実データ）でルート結果タブを描画し、
ブロックごとの実高さを測った。高さそのものではなく、**軸が増えても変わらない2つの定数**を
取るのが目的:

- 1行の基本の高さ … デスクトップ19px / モバイル390px 18px
- 2段目（生値または材料内訳）が付くと … +18px / +17px

つまり軸一覧の高さ ＝ 軸の本数×基本 ＋ 2段目を持つ軸の本数×2段目で、**ルート結果の縦は
公開軸の本数に正比例して伸びる**（総合難易度・負荷の数字だけが軸数に依らない固定分）。
着手時点の実測値はデスクトップでルート結果の本体562px（うち軸一覧355px）、
モバイルで444px（うち軸一覧334px）。

## 決定（ユーザーとの合意、2026-09-12）

当初の案は「未使用軸の横棒グラフをたたむ」「物理量表示をポップアップにする」の2つで、
初回の提示ではその時点の既定重み（重み0が2軸）を根拠に前者の効きが小さいと述べた。
**特定の公開軸の集合で効果を測るのは誤り**というユーザー指摘（「公開軸はこれからも
増えていくと思うし、ルートに使うかどうかはユーザ次第」）を受けて、係数として導き直した:

- **材料内訳をポップオーバーへ移す**（案1）は、**係数**を下げる。削る量は
  `material_breakdown`を持つ軸の本数×2段目の高さで、重みに依らず公開軸に比例する。
  加えて[設計原則](../design-principles.md)「数値は3層で見せる」（パネル側の物理量は
  軸1本につき生値1つまで、材料値の一覧は区間の詳細のまま）の是正でもあり、
  大きさに関係なく入れるべきもの。
- **重み0の軸を畳む**（案2）は、**比例の対象そのもの**を「公開軸すべて」から「その
  ユーザーが重みを与えた軸」へ変える。効果は重み0の軸数×行の高さで、公開軸が増えるほど・
  ユーザーが軸を絞るほど大きくなり、上限が無い。

よって案2→案1の順で両方を実施した。畳む対象は**重みで決まるものに限る**（値が無い
「データなし」の軸は畳まない——ユーザーの選択ではないため、読みたい軸が黙って隠れる）。

## 実装メモ

- 折りたたみの開閉行は`<li>`＋素のbutton（`aria-expanded`）で、共通の`Disclosure`
  （Radix Accordion）は使わない。Root/Item/Header/Contentが`<ul>`直下へ入るとマークアップが
  壊れ、開いた軸行が別のグリッドへ移って列が使用中の軸と揃わなくなるため（一覧は行ではなく
  `<ul>`側がグリッドで、各行は`display: contents`）。
- 行から内訳が消えたことで`DEFAULT_BREAKDOWN_VISIBLE`（行に出す件数の上限）は不要になり
  撤去した。ポップオーバーは「この軸の内訳（続き）:」から「この軸の内訳:」へ変わり、全件出る。
- `unusedBadge.module.css`は`RouteAxisProfile`側では「データなし」専用になった（「未使用」は
  `LensControl`が引き続き使う）。共有ファイルの説明を実態へ合わせた。

## 検証結果（実装後、同じ実ブラウザ計測）

| | デスクトップ | モバイル390px |
|---|---|---|
| ルート結果の本体 | 562px → **454px**（開いた状態でも496px） | 444px → **342px** |
| 軸別難易度の一覧 | 355px → **247px** | 334px → **232px** |

畳んだ軸を開いても、得点セルの左端は全行で一致（デスクトップ231px・モバイル349px）し、
列は使用中の軸と揃ったままであることを確認した。

**1画面には収まっていない**: モバイルの結果シートは`scrollHeight`=397 /
`clientHeight`=353で、44px はみ出したまま（着手前は499/353）。残りはタブ列・総合難易度の
数字・寄与度バーで、いずれも軸数に依らない固定分のため本タスクの2案では削れない。

テストは意図的な変異3件（畳む条件へ「データなし」を混ぜる／折りたたみを常時展開にする／
内訳を行へ戻す）でいずれも落ちることを確認した。
