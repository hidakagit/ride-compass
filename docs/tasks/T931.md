# T931: 幹線道路に実地ではあり得ない勾配が付く

状態: 未着手（2026-09-18起票）

## 背景

ユーザー指摘: レンズで15%以上と出た道路は、実地では道に沿って走っても15%など絶対に無い
幹線道路である。向きの扱い（[T930](T930.md)）とは別に、**値そのものが実態と合っていない**。

`average_grade`は`(終点標高 − 始点標高) ÷ 区間長 × 100`（`domain/attributes.py:
compute_elevation_attribute`）で、標高は国土地理院のDEM。疑うべき経路が2つある。

## 1. way単位のズームでは、そのwayの「いちばん急な区間」を代表にしている

`_FEATURE_GRADIENT_INPUTS_IN_TILE_SQL`は`ORDER BY src.feature_key,
abs(ea.average_grade) DESC`で代表を選ぶ。z14未満ではfeature_keyがwayのため、
**1本の幹線道路全体が、その中のいちばん急な1区間の値で塗られる**。短い1区間の異常値が
道路全体を染める。

平均を取ると崖を下って上り返す道が0%になるため最大値にした、という経緯がSQLのコメントに
ある。どちらも一長一短で、「異常値1件が全体を染める」側の弊害を測っていない。

## 2. 区間単位でも、DEM由来の値に歯止めが無い

- 区間長が短いほど、DEMの誤差がそのまま大きな%になる（交差点で切った幹線道路の区間は
  数十mになりうる。10m標高メッシュの誤差が数mあれば10%を超える）。
- **橋・トンネル・掘割を区別していない。** DEMが返すのは地表面の標高で、路面の高さでは
  ない。高架や掘割の区間は地形の起伏をそのまま勾配として受け取る。
- 算出時の上限・異常値の検知が無い（`compute_elevation_attribute`）。

## 影響は地図だけではない

同じ`average_grade`をルート探索の0次ハードフィルタ（`hard_filters.py:
max_average_grade_percent`）が読む。異常値が付いた区間は、利用者が上限を設定している
ときに**黙って経路から除外される**。地図の色が変なだけでは済まない。

## 調べること

- 実データで`abs(average_grade)`の分布を取り、上位が短い区間・橋・トンネルに偏っていないか。
- 指摘のあった道路のosm_way_idを特定し、区間ごとの`average_grade`・区間長・
  `start/end_elevation_m`を並べて、どの経路で異常が生まれているかを見る。
- way単位ズームの代表の選び方（最大 vs 長さ重み付き平均）を、実データの両方の弊害を
  数えてから決める。
