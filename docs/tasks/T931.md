# T931: 幹線道路に実地ではあり得ない勾配が付く

状態: 着手（2026-09-18。way単位ズームの代表を直した。DEM由来の値そのものの手当は未着手）

## 背景

ユーザー指摘: レンズで15%以上と出た道路は、実地では道に沿って走っても15%など絶対に無い
幹線道路である。向きの扱い（[T930](T930.md)）とは別に、**値そのものが実態と合っていない**。

`average_grade`は`(終点標高 − 始点標高) ÷ 区間長 × 100`（`domain/attributes.py:
compute_elevation_attribute`）で、標高は国土地理院のDEM。疑うべき経路が2つある。

## 1. way単位のズームでは、そのwayの「いちばん急な区間」を代表にしている

`_FEATURE_GRADIENT_INPUTS_IN_TILE_SQL`は`ORDER BY src.feature_key,
abs(ea.average_grade) DESC`で代表を選ぶ。z14未満ではfeature_keyがwayのため、
**1本の幹線道路全体が、その中のいちばん急な1区間の値で塗られる**。短い1区間の異常値が
道路全体を染める。

平均を取ると崖を下って上り返す道が0%になるため最大値にした、という経緯がSQLのコメントに
ある。どちらも一長一短で、「異常値1件が全体を染める」側の弊害を測っていない。

## 2. 区間単位でも、DEM由来の値に歯止めが無い

- 区間長が短いほど、DEMの誤差がそのまま大きな%になる（交差点で切った幹線道路の区間は
  数十mになりうる。10m標高メッシュの誤差が数mあれば10%を超える）。
- **橋・トンネル・掘割を区別していない。** DEMが返すのは地表面の標高で、路面の高さでは
  ない。高架や掘割の区間は地形の起伏をそのまま勾配として受け取る。
- 算出時の上限・異常値の検知が無い（`compute_elevation_attribute`）。

## 影響は地図だけではない

同じ`average_grade`をルート探索の0次ハードフィルタ（`hard_filters.py:
max_average_grade_percent`）が読む。異常値が付いた区間は、利用者が上限を設定している
ときに**黙って経路から除外される**。地図の色が変なだけでは済まない。

## 調べること

- 実データで`abs(average_grade)`の分布を取り、上位が短い区間・橋・トンネルに偏っていないか。
- 指摘のあった道路のosm_way_idを特定し、区間ごとの`average_grade`・区間長・
  `start/end_elevation_m`を並べて、どの経路で異常が生まれているかを見る。
- way単位ズームの代表の選び方（最大 vs 長さ重み付き平均）を、実データの両方の弊害を
  数えてから決める。

## 段階1: 計測の器（2026-09-18）

原因を断定する前に測る（[T917](T917.md)が路面タイルのedge化で取った順序と同じ）。
`backend/scripts/measure_gradient_outliers.py`（参照専用）が、上の疑い2つと、代表の
選び方・ルート探索への影響を1回の実行でまとめて出す。

| 出す表 | 読み取り方 |
|---|---|
| 区間長の帯ごとの`\|勾配\|` | 短い帯ほど大きければ、区間長がDEM誤差を拡大している |
| 橋・トンネルの別 | 構造物側が高ければ、地表面の標高を路面として読んでいる |
| way単位の代表: 最大 − 長さ重み付き平均 | 乖離が大きいほど「1区間の異常値がway全体を染める」 |
| ハードフィルタで落ちる区間 | しきい値ごとの除外区間数・割合・延長。地図の色だけの問題でないことを数で見る |
| 最も急な区間の上位 | osm_way_id・区間長・両端標高・橋/トンネルを並べ、原因を目で確かめる |

実行（backendディレクトリから）:

```
.venv/bin/python scripts/measure_gradient_outliers.py
.venv/bin/python scripts/measure_gradient_outliers.py --database-url <対象DB> --top 50
```

**本番DBに対して実行した結果をここへ貼ってから段階2（対処）を決める。** 緩和（上限・
除外・代表の変更）はどれも「検査対象から外す件数と母集団に対する割合」を測ってから入れる。

各帯の区間数×10%超の割合を積むと、ハードフィルタ表の160,534とほぼ一致する（160,440、丸め差）。

`14,030×17.98% + 86,743×21.10% = 20,825区間`で**13.0%**。

- 極端値（100%超）を作っているのは純粋に**長さ数mの区間**で、橋・トンネルは関係しない。
- 実用上効く10〜20%帯では橋・トンネルの濃度が7倍高い。2つの経路は**同じ層を作っていない**。
- **ただし2つを足しても58%（重複を無視した上限）にしかならない。** 残りは「50m以上・
  構造物でもない」区間で、山間の実勾配かもしれないし3つ目の原因かもしれない。250m以上の
  再上昇（3.42%）もここに含まれる。**実勾配だと決め打ちしない**——決め打ちすると手当が
  効いたかを後から測れない。

## 段階2: 対処を決めるための計測（2026-09-18）

段階1で「どこが原因か」は分かったが「どこで切るか」の数字が無い。器へ4つ足した。

- 短い側の細分（5m未満 / 5〜10 / 10〜15 / 15〜25m）——上位50件が0.5〜16.5mのため、
  切る位置は25mより手前にあるはずだが、帯が粗くて見えない。
- しきい値表の上限拡張（25/30/40/50/100%）——物理的にありえない値の件数。舗装公道の
  最急は世界でも35%前後で、40%超は全件が誤りと言えるが、件数を知らずに上限は入れられない。
- **対処案ごとに勾配なしへ落ちる件数・割合・延長**（下限長5〜25m、上限20〜40%、橋トンネル
  除外）——緩和は影響を測ってから入れる。
- 橋・トンネル×区間長のクロス集計——構造物自体が原因か、短さと重なっているだけか。
  `average_grade`は両端の標高だけで決まるため、トンネルの両端が坑口なら値は正しいはずで、
  17.98%が10%超という濃さには説明が要る。

### 器が効いていることの確認

ローカルのPostgreSQL 16へ、答えの分かっている10区間（極短の±336.7%・短い橋・長い橋・
長いトンネル・本物の急坂を含む）を入れて全表を実行した。5m未満の帯が336.70で分離され、
クロス集計は短い橋（60.0）と長い橋（12.0）を別の行に分ける。`blanked_km_ratio`の計算で
`round(double precision, integer)`が存在せず落ちたため`::numeric`を足した（この確認で発見）。

## 実機の見え方から分かったこと（2026-09-18）

利用者が指した道（墨田・荒川の低地の長い幹線）は、**長距離が一様に濃い青**（下り10%超の帯）で
塗られていた。周囲の道は短い区間ごとに色が変わっているのに、この道だけ1色が続く。

**この見え方は、ここまで主因と読んでいた「短い区間のDEMノイズ」では説明できない。**
それなら1本の道の中で色がばらつく。一様に長い1色になるのは次のどちらか。

1. way単位ズームで、そのwayの**いちばん急な1区間**が道全体を染めている
2. その道が1本の長いedgeで、両端の標高差が誤っている

どちらも分布では見えない。**集計だけで方針を決めようとしていたのが誤りで**、地図で見えて
いる1本を現物で確かめる必要がある。段階1・2の集計（50m未満で66%、橋トンネル13%）は
「裾がどこから来るか」の答えであって、**利用者が困っている見え方の答えとは限らない**。

器へ現物確認の口を2つ足した。

- `--near 経度,緯度 [--radius-m 200]`: その地点の周辺の区間を|勾配|降順で一覧
- `--way <osm_way_id>`: その1本のwayの全区間を一覧

`--way`の確認: ローカルのPostgreSQLへ「1,162mの幹線（0.2/-0.1/0.3%）の中に12mだけ-12.4%」を
入れると、代表（最急）が-12.4%になり**way全体がその色で塗られる**形がそのまま並ぶ。
`--near`はPostGIS（`ST_DWithin`・`geography`）を使うためこの環境では未検証
（本番で最初に実行するときは`--way`から試すのが安全）。


## 現物で確認した原因（2026-09-18、way 669058097）

本番で実際に指摘された道を引いた。2,026m・25区間・すべて`primary`で、**24区間は−1.0〜+0.4%の
平坦**（標高2.4〜3.8mの低地）。例外は1つだけ。

```
way-669058097-seg0-fwd | 19.1m | +15.3% | 2.1m → 5.0m
```

`tile_representative` 15.3 に対し `weighted_avg` 0.4。**19.1mの1区間が2,026m全体の代表値に
なっていた**。way単位ズームは「いちばん急な区間」を代表にする設計だったため、19mのために
2kmが最濃色で塗られていた。

**seg0の値が本物かどうかに関係なく、代表の選び方が誤り**である。19mの実在する急坂であっても、
2kmの平坦路をその色で塗ってよい理由は無い。

## 対応: 代表を長さで重み付けた平均にする（2026-09-18）

`_FEATURE_GRADIENT_INPUTS_IN_TILE_SQL`の代表選択（`DISTINCT ON` + `abs(average_grade) DESC`）を
やめ、フィーチャーに属する区間を長さで重み付けて平均する。

元のSQLのコメントは「区間の平均を取ると、崖を下って上り返す道が両端の標高差で0%になる」ことを
理由に最大値を選んでいたが、**比較対象が違っていた**。打ち消しが起きるのは符号付きの平均で、
絶対値で平均すれば起きない。今回はユーザー判断で**符号付き**を採った（登り／下りの塗り分けに
符号が要るため）。崖を下って上り返す道が0%になる制約は残る。

向きの扱いが要点。`road_edges`は同じ区間を両方向2行で持ち符号が逆のため、そのまま足すと必ず
0になる。**フィーチャーの基準方位（ジオメトリの始点→終点）とのcosの符号**で各行を揃えると、
両方向の行が同じ値を返し、重複は重みの分母と分子へ同じだけ効いて打ち消える（重複排除が要らない）。

`ST_Azimuth`は**geographyへキャストする**。`geometry(4326)`のままだと経度緯度を平面として
扱った角度になり、緯度35度で真の方位と約6度ずれる（テストが`bearing_between`との不一致として
検出した）。

### 効いていることの確認

- 本番のway 669058097を模したPostGIS fixture（25区間・19mだけ+15.3%）を作り、**リポジトリの
  実SQLをそのまま**走らせた。z13（way単位）で **−15.3 → +0.08** へ変わる。この+0.08は本番の
  実データから手計算した値（両端の標高差1.6m ÷ 2,026m）と一致する。z14（区間単位）の値は変化なし。
- 回帰テスト`test_get_feature_gradient_inputs_in_tile_does_not_let_one_segment_paint_the_whole_way`
  を追加。**旧実装（最急を代表）へ戻すと落ちる**ことを確認した。
- 既存のPostGISテスト2件が落ちたのは、返る`(勾配, 向き)`の生の符号を固定していたため。
  どちらの向きの行を代表にしても`effective_gradient`の結果は同じなので、**組で読む形**へ
  書き換えた（表現の違いを欠陥と読まないため）。
- `pytest -m postgis` 298 passed / `-m "not postgis"` 2,057 passed / `ruff` クリーン。

### デプロイ時の注意

**この修正は即座には見えない。** 勾配のタイル値はディスクキャッシュ（`dynamic_way_value_cache`、
TTL 24時間）に載り、その鍵は`ROAD_SURFACE_TILE_SHAPE`で決まる——このSQLを変えても鍵は
変わらないため、既に焼かれた値は期限切れまで残る。すぐ反映したい場合は`dynway`名前空間の
エントリを消す必要がある（管理画面の「タイルキャッシュを全消去」は`tile_cache`が対象で、
こちらは消えない）。

## 段階3: DEM由来の値そのものへの手当（2026-09-19）

### 使っているDEMの公称精度を確かめたら、「短い区間＝DEMノイズ」の筋が崩れた

`elevation_client.py: DEM_TYPE_PRIORITY`は`dem5a → dem5b → dem5c → dem`の順で引く。
国土地理院が公表している標高精度（標準偏差）は **DEM5A 0.3m以内・DEM5B 0.7m以内・
DEM10B 5.0m以内**（DEM5Aでもメッシュ内に測定点が無ければ2.0m以内）。関東の市街地は
DEM5Aが行き渡っている。

**0.3mの誤差では、19.1mの区間に15.3%（＝2.9mの標高差）は作れない。** 段階1・2で見た
「短い区間ほど|勾配|が大きい」という分布は事実だが、その原因をDEMの**ノイズ**と読むのは
公称精度と合わない。より筋が通るのは、DEMが**路面でない地物の標高を正しく返している**
という読みである——短い区間の端点が高架の取付・擁壁・護岸・掘割の縁に落ちると、地面の
標高としては正しい値が、道の勾配としては誤りになる。これは橋・トンネルの問題
（地表面≠路面）と**同じ根**であり、2つを別々の原因として数えていたのが誤りだった可能性がある。

**したがって一律の下限長は採らない。** 段階2で「短い側に崖が無いので恣意的」と書いたが、
理由はそれだけではなく、**そもそも切る根拠になっていた仮説（ノイズ）が成り立たない**。

### 入れたもの: 物理的にありえない値を「データなし」にする

`domain/attributes.py: MAX_PLAUSIBLE_AVERAGE_GRADE_PERCENT = 40.0`。舗装された公道として
ありうる最急が世界でも35%前後のため、これを超える値は道の起伏ではない。超えた区間は
`average_grade`を持たせない（標高そのものは残す）。

0次ハードフィルタは値の無い区間を除外しない（`hard_filters.py`）ため、**誤った値で黙って
経路から外すより安全側**になる。[T930](T930.md)の「示せない向きは値を持たせずデータなしに
する」と同じ扱い。

影響（本番実測）: 5,276件・61.9km。勾配のある5,065,800区間に対し**0.104%**（延長では0.013%）。

`max_grade`/`min_grade`（形状点ペアごとの最大・最小）には同じ上限をかけていない。これらは
保存と返却だけで評価にも表示にも使われていないため、値を落とす利点が無い。

### 残っていること: 橋・トンネルをどう扱うか（判断待ち）

段階2の実測で、橋・トンネルは短さとは独立の要因と分かっている（25m以上に限っても
10%超の濃度が7.3倍）。DEMが返すのは地表面なので、**高架や長いトンネルの勾配は
「測り間違い」ではなく「別のものを測っている」**。とりうる案は3つで、どれも見え方が変わる。

| 案 | 内容 | 影響（実測） |
|---|---|---|
| 1 | 橋・トンネルの区間は勾配を持たせない | 100,773区間・4,418.4km（件数1.99%・延長0.89%）が「データなし」になる。山岳路は連続して欠ける |
| 2 | 構造物の前後の取付から内挿する | 欠けない。実装は重く、取付側の値が正しい前提に乗る |
| 3 | そのまま（現状） | 山岳路の高架・トンネルが実態と違う勾配で塗られ続ける |

案1は1区間あたりが長く（件数1.99%に対し延長0.89%＝平均44m）、山岳路でまとまって
欠けうる。**利用者の見え方に関わる判断のため、決めてから実装する。**
