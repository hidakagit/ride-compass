# T421. ルート結果パネルの候補サマリ・色分けモード・おすすめ度説明を評価軸カタログ駆動へ見直す

状態: 未着手（起票のみ）

## 背景

実機フィードバック（2026-08-30）で以下3点が指摘され、調査の結果いずれも事実と確認したが、
これまでのセッションで正式なタスクとして起票せず放置していた（構造マップ[Artifact]の
オレンジ印としてのみ記録し、実際のタスクエントリへ変換していなかった——CLAUDE.mdの
「分割元タスク完了ゲート」ルールが防ごうとしている抜けと同種のものを、このセッション自身の
会話の中でも起こしていた）。

1. **候補一覧（`RouteList.tsx`）冒頭の「おすすめ度」説明文（`SCORE_HINT`）の意義が
   伝わっていない**: `おすすめ度は${SCORING_AXES.map(...).join}を重み付けして算出`という
   文言。`SCORING_AXES`自体はT401で「距離の合わせ込み・総合難易度」の2項目へ単純化済みで
   カタログ駆動だが、説明文として何を言っているのか分かりにくいという指摘。
2. **候補ごとのサマリ行に、獲得標高・向かい風・舗装率だけが特別扱いで表示される**
   （`RouteList.tsx`: `route.elevation_gain_m`・`route.wind_score`・`route.road_score`を
   直接参照）。これらは`backend/app/domain/route.py`の`RouteCandidate`が持つ**旧
   scoring.yaml時代のレガシーフィールド**（T401でRouteScorerの候補順位付け自体からは
   もう使われなくなったが、値自体は`road_graph_engine.py`・`domain/attributes.py`で
   引き続き実計算・格納されている）で、`RouteAxisProfile`（T402、`axis_difficulties`
   ベースで軸カタログの増減に自動追従する）とは別系統。「べた書きせず評価軸に追随させる」
   という以前の指示に反している。
3. **「生成したルートの色分け」（`routeStyleModes.ts`）の一部も同種の懸念がある**:
   `routeStyleModesFromCatalogAxes`は`supports_route_coloring`フラグを持つ軸（現状は
   風のみ）をカタログから動的生成しており、この部分は既にべた書きではない。ただし
   `STATIC_MODES`（`gradient`/`road`/`difficulty`の3種）は固定実装で、コード内コメントに
   「符号付き値・真偽値・全軸合成という性質のため汎用パターンに乗らない」という設計上の
   理由が明記されている。この3種が(2)と同列の「単なる見落とし」なのか、正当な設計上の
   例外なのかの切り分けが必要（詳細は下記「調査結果の要約」参照）。

## 調査結果の要約（このタスクの起票時点で判明済み、着手時の再確認は不要）

- `SCORING_AXES`（`frontend/src/lib/evaluationAxes.ts`）: T401で既にカタログ駆動化済み
  （distance_weight/difficulty_weightの2項目）。**説明文自体の分かりやすさ**が課題であり、
  データ源の問題ではない。
- `RouteList.tsx`のサマリ行: `elevation_gain_m`/`wind_score`/`road_score`は
  `RouteCandidate`の実フィールドで値自体は正しい（壊れたデータではない）が、**表示するか
  どうか・どの3項目を選ぶかが固定でハードコードされている**点が問題。
- `routeStyleModes.ts`: 風は既にカタログ駆動（T352）。`gradient`/`road`/`difficulty`の
  3種は「向きの符号・真偽値・全軸合成」という技術的理由で汎用パターンに乗らない設計上の
  例外として明記されている——ただし、この理由付け自体が今も妥当か（(2)の指摘と同じ目線で
  見直す価値があるか）は着手時に再検討すること。

## 対応方針（未確定、着手時に目的から設計すること——[[feedback-purpose-first-design]]の
教訓を踏まえ、実装可能性からではなく「候補一覧を見る人が何を知りたいか」から出発する）

- 「おすすめ度」説明文は、簡潔化するか、[T418](T418.md)で評価軸がルート設定パネルへ
  統合された後の文脈（重み配分UIのすぐ近くに既に説明があるなら重複を避ける）を踏まえて
  再検討すること。
- 候補サマリ行の獲得標高・向かい風・舗装率は、固定3項目のべた書きをやめ、`axis_difficulties`
  （ユーザーが実際に重みを付けている軸、または上位N軸等）から動的に構成する方式へ
  変更することを検討する。ただし獲得標高（`elevation_gain_m`）・距離のような「軸の評価値
  ではなく走行の物理的な事実」を完全に排除すべきかは要検討（向かい風[m/s]・舗装率[%]は
  それぞれ風軸・路面軸の評価値と同じ計算元だが、獲得標高は軸の合成値ではなく単純な物理量
  であり、性質が異なる可能性がある）。
- `routeStyleModes.ts`の`STATIC_MODES`（gradient/road/difficulty）は、コード内の設計理由
  （符号・真偽値・全軸合成）が実際に汎用パターン化を阻む本質的な制約か、単に「まだ
  汎用化していないだけ」かを再検証すること。
