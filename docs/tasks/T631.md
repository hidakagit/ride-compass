# T631. 目的地の名前検索（ジオコーディング）機能の追加 規模L

状態: 設計検討中（2026-09-06起票）・実装未着手

## 背景

ユーザー相談「ルート設定タブで、目的地を名前から検索して設定したい。どんな手段があるか」
への対応検討。現状、目的地は地図タップ（緯度経度直接指定）のみで、frontend・backend
どちらにも地名検索（ジオコーディング）の仕組みは無い。backendはOSMのPBFを取り込み済み
（`backend/app/batch/import_pbf.py`）だが、`osm_raw_pois`は走行属性用に絞った限定
サブセットのみで、一般的な地名・住所を引ける索引にはなっていない。

ユーザーの実際のユースケース: 「普通の街角（有名な観光地・ランドマークに限らない）を
目的地指定して検索したい。ナビ利用も想定する」——住所レベルの精度が必要で、単純な
固有名詞の完全一致検索では不十分。

## 検討した選択肢と判断

### 1. データソース: OSM vs 外部ジオコーディングAPI

- ヒット数（マッチ率）は一般に外部API（特にGoogle）が優位——個人商店・チェーン店・
  新規開業施設等のロングテールな名称に強い（事業者からの継続的な情報提供パイプライン
  があるため）。
- ただし日本はOSMコミュニティの活動が活発な地域の一つで、住所・主要POIに関しては
  Nominatim（OSM）でも商用サービスに匹敵する精度が出るという評価がある。
- 外部API料金相場（2026-09-06調査時点）: Google Geocoding（無料枠月10,000件、超過
  $5/1,000件目安）・Mapbox（無料枠月100,000件だが**一時利用限定**、恒久保存に制限）・
  LocationIQ（無料枠1日5,000件、有償$49/月〜）・Geoapify（無料枠1日3,000件）。
  GoogleとMapboxはいずれも結果を自前DBへ恒久保存することに利用規約上の制限があり、
  Open-Meteoで多用しているような「結果をキャッシュしてクォータ節約」という設計が
  そのまま使えない可能性が高い。

### 2. 自前簡易ジオコーダ vs Nominatimセルフホスト

自前実装（既存`import_pbf.py`パイプラインの`name`タグ索引化、pg_trgm等）も検討したが、
以下の理由で見送り、Nominatimセルフホストへ方針決定した:

- ユーザー方針: 「既にあるものを再開発はしたくない」。
- 用途が「普通の街角」まで含む住所レベルの検索であり、単純な名前の完全一致/部分一致
  では不十分。表記ゆれ・住所階層の構造化解析・あいまい検索等、Nominatimが長年かけて
  磨いてきたロジックを自前で再現するのは非現実的。
- ナビ利用も想定するため、検索結果の網羅性・精度がより重要（観光地・ランドマークに
  限定した軽量検索では要件を満たさない）。

## リソース見積もり（2026-09-06時点、概算）

### インポート時（初回構築）

| 項目 | 見積もり |
|---|---|
| ディスク（全国想定） | 実データ20〜35GB程度（作業用に60〜80GB確保推奨）。日本のpbf圧縮2.3GBに対し、大陸規模の実績[圧縮比の約10〜15倍に膨張]から比例換算 |
| RAM | 16GB以上推奨（32GBあるとインデックス構築が速い） |
| CPU | 4vCPU以上 |
| ディスク種別 | NVMe推奨 |
| 所要時間 | 数時間〜半日程度 |

（参考: 本アプリ自身のOSM生データ層は関東本土実測1,779MB→全国換算約9GB
[docs/tasks/T127.md]。Nominatimは独自スキーマ・索引を持つため上記とは別建てのDB容量。）

### 稼働時（クエリ提供のみ）

数GB程度（4〜8GB目安）のRAMで足りる規模。重いのはインポート時のインデックス構築のみ。

### 既存インフラとの関係（重要な制約）

- 現行backend VMはOracle Cloud `VM.Standard.A1.Flex`（ARM、2 OCPU/12GB、東京
  リージョン、DBと同居）。**以前T624検討時に「重いバッチでVM全体がOOMになった実績」が
  記録されており**、Nominatim用の別PostgreSQLインスタンス（独自拡張[hstore/unaccent/
  ICUトークナイザ]を持つ）を同居させるのはリスクが高い。**関東限定に対象範囲を絞っても
  この制約は変わらない**（データ量は小さくなるが、2 OCPU/12GBという限られたリソースへの
  同居リスクの本質は変わらないため）。
- Oracle Always Free枠（Ampere A1）は2026-06-15にOracle側で無告知で4 OCPU/24GB→
  2 OCPU/12GBへ半減されており、既存backend VMがこの枠を使い切っている。**新規
  Nominatim用インスタンスはAlways Freeの対象外＝有償（Pay As You Go）前提**になる。
- 対応方針: **別インスタンスへ分離**する。全国想定なら4 OCPU/24GB（Oracle A1.Flex
  PAYGレートで概算月$55）、対象範囲を関東限定に絞るなら2 OCPU/8GB程度（概算月$23）
  でも足りる見込み。関東限定なら後から全国展開する際にこの別インスタンスだけを
  リサイズすればよく、本番アプリのVMには手を触れずに済む。

### クラウド事業者比較（Oracle/AWS/GCP）

- Oracle Cloud（A1.Flex、ARM）: $0.01/OCPU時間+$0.0015/GB時間（公式レート、確度高）。
  既存backendと同じベンダー・リージョンのため運用対象を増やさずに済む。
- AWS（Graviton、`m7g`系）: 同等スペックで概算月$140〜150（相場観、要現地確認）。
- GCP: Tokyo（asia-northeast1）にはARM（Tau T2A）が提供されておらず、x86
  （N2/E2）になるためコストメリットが薄い（概算月$140前後、要現地確認）。
- 総合判断: Oracle Cloudで有償インスタンスを1台追加するのが最も筋がいい
  （単価の安さ・同一ベンダーでの運用一本化の両面で）。

## 保留した場合の影響

現状（地図タップのみ）のままだと、目的地を正確な地名・住所で指定したいユーザー
（普通の街角・ナビ利用目的）の使い勝手が改善されないまま残る。ただし緊急度の高い
バグ・既存機能の不具合ではないため、対象範囲・優先順位の判断待ちとして保留して良い。
