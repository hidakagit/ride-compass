# T620. 風・勾配（dedicated_way_value_layer軸）のフェッチ失敗を既存の失敗バナーへ表示する 規模M

状態: 完了（2026-09-06起票・同日実装完了）

## 背景

T619（レンズで風を選ぶと全灰色になるバグ、タイムゾーン変換漏れ）の調査中に見つかった、
独立したUX課題。

現在、地図の路面タイル等の他レイヤーは`useLayerDataStatus`（`mapLayers.ts:
LayerDataStatus`/`LAYER_DATA_STATUS_LABELS`）が`loading`/`empty`/`error`を判定し、
`MapLayersPanel`が「データの取得に失敗しました」等のバナーを表示する。

一方、風・勾配（`dedicated_way_value_layer`軸）はこの機構の対象外
（`mapLayers.ts: buildRoadSurfaceSharedLayerIds`のコメント参照）。理由は、これらの実データが
ベクタタイルのプロパティではなく別経路のfetch（`regionApi.ts: fetchDynamicWayValues`→
`hooks/useDynamicWayValues.ts`）で来るため、`useLayerDataStatus`が見ているMapLibreの
`sourcedata`/`error`イベントに現れないこと。

さらに`fetchDynamicWayValues`自身が「通信失敗」と「本当にその範囲にデータが無い
（backend側のグレースフルデグレードで空dictが返った場合も含む）」を区別せず、どちらも
同じ`{}`へ倒す設計になっている（`regionApi.ts`のコメント「補助機能はサイレントに
フォールバック」参照）。そのため地図は無言の全灰色になり、ユーザーは「バグなのか、単に
このエリアにデータが無いだけなのか」を区別できない。

## 対応方針（着手前の想定と実装時の乖離）

着手前の想定は「`MapLayersPanel`の既存バナー機構でそのまま表示する」だったが、着手前に
`docs/modules/frontend/static-map-layers.md`・`map-axis-coloring.md`・
`page-composition.md`を読んだところ、windAxis/gradientAxisは`isAxisStudioLayer`により
`MapOverlayControls`・`MapLayersPanel`のどちらにも一切表示されない設計（表示ON/OFFの
唯一の起動導線は地図上部中央の`LensControl`、レンズ）と判明した——`RouteSettingsPanel`にも
風/勾配の「地図に表示」個別チェックボックスは無く、`showWindAxis = lens === "wind" &&
lensBackgroundShown`のように`lens`から直接導出される。つまり`MapLayersPanel`側には
そもそも風/勾配のチップ行自体が存在せず、そこへバナーを付ける対象が無い。

このため対応方針を「`LensControl`のピルへ、既存の`LayerDataStatus`（"loading"/"empty"/
"error"、`mapLayers.ts`）と同じ小さな状態ドット（`LayerChip`と同じ視覚表現）を付ける」へ
変更して実装した。専用の新しい表示コンポーネントは作らず、既存の3状態表現をLensControlという
別の消費者から再利用する形にとどめている（design-principles.mdの汎用設計方針に沿う）。

1. `fetchDynamicWayValues`の戻り値を`Record<string, number>`から`{ values, error }`へ
   変更し、通信失敗（HTTPエラー・ネットワークエラー）を「本当に空」と区別して呼び出し元へ
   伝える。
2. `useDynamicWayValues.ts`の戻り値へ`error: boolean`を追加（複数タイルの結果をOR集約）。
3. `useDynamicWeatherLayers.ts`が内部に持っていた`dynamicWeatherStatus`
   （loading/error/payloadの有無から`LayerDataStatus`を1つ決める純粋関数）を
   `mapLayers.ts: deriveFetchLayerStatus`として切り出し、両方の呼び出し元で共有した
   （定義を1箇所にする）。
4. `page.tsx`が`lens`がwindAxis/gradientAxisを指す間だけ`deriveFetchLayerStatus`で
   `lensFetchStatus`を算出し、`LensControl`の新しい`dataStatus`propへ渡す。
5. `LensControl.tsx`がピルに`dataStatus`ドット（`LayerChip.module.css`と同じクラス名
   規約の`statusDot`/`statusDot_loading`/`statusDot_empty`/`statusDot_error`）と
   `title`（`LAYER_DATA_STATUS_LABELS`）を追加する。

副作用として、`mapLayers.ts`のwindAxis/gradientAxis記述子コメントに残っていた古い記述
（「地図上チップとしては撤去し、ルート設定パネルの『風』行から起動する形へ移設した」・
存在しない`mapColorLayerIdFor`への言及）を、現在の実態（LensControlが唯一の起動導線）へ
同一コミットで修正した。

影響ファイル: `regionApi.ts`・`regionApi.test.ts`・`useDynamicWayValues.ts`・
`useDynamicWayValues.test.ts`・`useDynamicWeatherLayers.ts`・`mapLayers.ts`・
`LensControl.tsx`・`LensControl.module.css`・`LensControl.test.tsx`・`page.tsx`。

- `regionApi.test.ts`・`useDynamicWayValues.test.ts`・`useDynamicWeatherLayers.test.ts`・
  `mapLayers.test.ts`・`LensControl.test.tsx`を更新・追加し（HTTPエラー/通信エラー時の
  `error: true`、いずれかのタイル失敗時の集約、`dataStatus`未指定/`"error"`時のピル
  `title`）、対象ファイルのみ実行してグリーンを確認した。
- 実装が安定した時点でフロントエンド全体（`npx vitest run`・`npx tsc --noEmit`・
  `npx eslint .`）を実行し、既存のtsc失敗（`layout.tsx`のLayoutProps、本タスクと無関係・
  変更前から存在）以外に新規のエラー・警告が無いことを確認した（vitestは1025件全て
  グリーン、eslintは0件）。
- `scripts/review_checks.py docs --staged`で本タスクの差分に経緯コメント混入・
  docs/modules記載漏れが無いことを確認した。

## 保留した場合の影響

（実装済みのため解消——参考として着手前の記録を残す）着手しない間、風・勾配のフェッチが
本当に失敗した場合（Open-Meteo障害・DB障害等）も地図は無言で全灰色のままだった。
