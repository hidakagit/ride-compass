# T720. 停止密度の飽和解消を本番の軸インスペクタで確認する 規模S

状態: 未着手（2026-09-11起票、[T655](T655.md)の完了条件から分離）

## 背景

[T655](T655.md)の完了条件のうち「停止密度の難易度が全wayで100に張り付いていないこと
（本番の軸インスペクタで確認）」だけが、本番環境の操作を伴うため未確認のまま残っている。
他の3条件（Contextのフィールド削減・種別別の保持・横断歩道の重み0）はコードとテストで
確認済み。

[T655](T655.md)が飽和を確認した測定は**本番**（東京都心のwayを無作為抽出して全件100.0、
タイル6枚555kmで延長の92.3%が飽和点超え）だったのに対し、直し方の効果を測ったのは
**開発DB**（3,000 Edge・191.9km）である。開発DBでは「4回/km以上が占める延長」が41.2%→17.0%
（信号のみなら8.7%）へ下がったが、同じ改善が本番の密度でも起きているかは測っていない。

## 保留することで何が起きうるか

- 停止密度が本番でも飽和したままなら、「ストップアンドゴーが少ないルート」は依然として
  作れない。軸の重みをいくら上げても候補道路がほぼ同点のためルートが変わらず、
  **症状はエラーではなく「重みが効かない」という無言の形**で出る。
- [T719](T719.md)の判断1（`intersection_count_per_km`を軸として復活させるか）が、
  停止側の本番分布を入力にできないまま止まる。

## 確認手順

計測部分は`backend/scripts/measure_axis_saturation.py`として用意済み
（[T719](T719.md)と同じ2026-09-11。軸スタジオの分布プレビューと同じ母集団・同じ材料の
組み立てを使い、違いは折れ点を通した**後**の難易度を見る点）。軸インスペクタで手作業で
無作為抽出する代わりに、延長で重み付けた分位点と上端・下端の割合が一度に出る。

1. 本番のbackendが読むDBに対して実行する:

   ```
   python scripts/measure_axis_saturation.py
   ```

   公開軸すべてを一覧する。停止密度だけ見るなら`--axis <軸id>`、サンプルを広げるなら
   `--sample-percent`。

2. 停止密度の「上端」（難易度95以上が占める延長の割合）が大半を占めていないことを見る。
   [T655](T655.md)の起票時点では合成値`stop + 0.3×intersection`で延長の92.3%が飽和点超え
   だった。開発DBでの直し後の実測では「4回/km以上」が41.2%→17.0%へ下がっている。

3. 張り付いている場合は折れ点
   （現在`[(0.0,0.0),(0.5,20.0),(1.5,50.0),(3.0,75.0),(5.0,100.0)]`）を実測の分位点から
   引き直す。折れ点の調整は軸スタジオ経由（unpublish→PUT→republish、CLAUDE.md
   「コミット時の同期ルール」）で行い、[deployment-sync.md](../deployment-sync.md)の
   完了条件に従う。

## 完了条件

- 本番のDBに対して`measure_axis_saturation.py`を実行し、停止密度の上端の割合を
  本タスクへ記録すること
- 張り付いていた場合は折れ点を引き直し、引き直した値と引き直し後の実測を記録すること

## なぜ自動化して終わりにしないか

この計測をCIや起動時チェックへ組み込むことは**しない**。飽和は「壊れている」とは限らず、
本当に全区間が難しい軸（都心の停止密度など）もありうる。閾値で機械的に落とすと、
正しい軸を落とすか、通すために閾値を意味の無い値まで緩めるかのどちらかになる。
判断は人が見て行い、機械は数字を出すところまでにする。
