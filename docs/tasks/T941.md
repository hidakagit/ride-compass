# T941. 区間インスペクタだけが土地被覆をway単位で読み、地図の色と内訳が食い違う 規模M

状態: 完了（2026-09-19起票・完了、統合レビュー第11回）

## 背景

T919の「区間の行があればそちら、無ければway単位へ落とす」規則が、消費者3つのうち
区間インスペクタにだけ適用されていない。インスペクタAPIが受け取るのは`osm_way_id`のみで、
クリックされた区間を特定する手段が現在の契約に無い。

詳細は[history/2026-09-19_all.md](../../.claude/commands/review/history/2026-09-19_all.md)。

## 対応方針

`_landcover_value_column`のdocstringが「揃えないと、地図に出ている値と採点が使う値が食い違う」と
明記した、まさにその食い違いが消費者1つに残っている。

1. 区間インスペクタのリクエストへ区間の鍵を足し、区間が特定できるときは区間単位で読む。
   現在APIが受け取るのは`osm_way_id`のみで、MVTは区間の鍵も焼いているのにクリックされた区間を
   特定する手段が契約に無い。
2. `docs/modules/backend/evaluation-scoring.md`が土地被覆の読み出し元をway単位のまま書いている
   点も同時に直す（同期間に`static-road-attributes.md`は113行更新されたのに、こちらは0行）。
3. `get_edge_materials_batch`の欠損判定だけが単一クラスの決め打ちで、SELECT列も辞書も
   `WIRED_LANDCOVER_KEYS`から導出しているのに揃っていない（構造仕様12の局所的な逸脱）。

## 実装メモ

### 区間を特定する手段を契約へ足した

路面タイルは区間単位のズームで`feature_key`（区間のid）を焼いているのに、インスペクタの
リクエストは`osm_way_id`しか運んでいなかった。`feature_key`を省略可能なフィールドとして足し、
フロントはクリックしたフィーチャーのものをそのまま送る。**way単位のズームで押した道の
`feature_key`はosm_way_idの文字列**で、`road_edges`に一致せずway単位の読み出しへ落ちる——
呼ぶ側がズームを見て送り分ける必要はない。

読み出しは`get_feature_landcover(osm_way_id, edge_id)`で、切り替えの規則は評価経路
（`_landcover_value_column`）と**同じ式を使う**。別々に書くと、片方だけ直したときに
同じ道の同じ場所で地図の色と内訳の数字が食い違う（それが本タスクの症状そのもの）。

### 欠損判定を宣言から導いた

3箇所が1クラス（`trees_percent`）の名指しで「値なし」を判定していた。SELECT列も辞書も
`WIRED_LANDCOVER_KEYS`から導出しているのに、判定だけが手書きだった（構造仕様12の局所的な
逸脱）。行→レコードの組み立てを`_landcover_record`へ寄せ、判定は
`_LANDCOVER_PERCENT_COLUMNS`（`_LANDCOVER_UPSERT_COLUMNS`の`_percent`で終わる列）から導く。

| わざと戻した内容 | 落ちたテスト |

| インスペクタをway単位の読み出しへ戻す | `test_region_service.py`の区間インスペクタ2件 |
| 区間単位の読み出しを止める | 「区間の行を読む」「値なしでway側へ戻さない」 |
| 識別子をサービスへ渡さない | 「クリックされたフィーチャーの識別子が届く」 |
| 欠損判定を1クラス決め打ちへ | 「一部のクラスだけがNULLでも値のあるクラスは渡す」 |

最後の1件は**当初検知できなかった**。インスペクタ側で試したが、`LandcoverPercentages`は
各クラスを必須のfloatで持つため「一部だけNULL」という行をそもそも表現できず、新旧どちらの
判定も一致してしまう。差が出るのは`float(value or 0.0)`で受ける評価経路
（`_landcover_percents_or_none`）の方で、テストをそちらへ移して検知するようにした。
