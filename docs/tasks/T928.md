# T928: タイル世代が上がった瞬間、視界のすべてを取り直して詰まる

状態: 着手（2026-09-18起票。段階1の計測で主犯候補が1つ消えた。原因は未特定）

## 背景

2026-09-18の朝、勾配レンズの値取得（`GET /api/region/dynamic-way-values/gradient/…`）が
15秒のタイムアウトを1分以上続けて1件も返らなかった。時間を置いたら解消した。

世代が変わった瞬間に起きることが一度に重なる:

- `derived_data_revision_service.ensure_caches_match_db`が`tile_cache.clear_all()`で
  焼き済みタイルを全消去する（基礎地図・DEMも同じ入れ物のため一緒に落ちる）。
- 配信するタイル世代が変わるため、フロントはタイルのソースを作り直し、**視界のタイルを
  全系統ぶん一斉に取り直す**。
- 取り直したタイルはすべてキャッシュミスで、PostGISからの焼き直しになる。
- 焼き直しと`dynamic-way-values`は同じsemaphore（`road_tile_max_concurrent=6`）と
  同じDB接続プールを共有する。

1枚あたりの焼き直しはz14で0.015〜0.03秒（[T917](T917.md)の実測）なので、4枚が冷えている
だけでは15秒に届かない。**「全部まとめて取り直す」と「全部消す」が同時に起きる瞬間に何が
起きているかを実測する**ことがこのタスクの主題で、原因の断定はまだしていない。

## 調べること

- 世代が上がった直後の実際の同時リクエスト数と、semaphore待ちの滞留時間。
- `tile_cache.clear_all()`が基礎地図・DEMまで落とすことの寄与（消さずに済む分離ができるか）。
- 全系統・全タイルを同時に取り直す以外の順序（世代は変わったが実体は同じ、という場合を
  区別できるか）。

## 段階1: 世代直後の実測（2026-09-19、本番）

[T931](T931.md)・[T933](T933.md)の本番反映で`derived_data_meta.revision`を13→14→15と
3回進めた直後に測った。**焼き済みタイルが全消去された直後という、このタスクが問題にする
状態そのもの**である。

クライアントはHTTP/2で1本の接続へ多重化する（ブラウザと同じ形。理由は下の「測り方の落とし穴」）。

| 測ったもの | 中央値 | 最大 |
|---|---|---|
| 冷えた視界27枚（路面・POI・事故 各9枚を同時） | 1.857s | 2.672s |
| 同じ視界の2回目（温まっている） | 0.095s | 0.116s |
| 冷えた路面9枚だけ | 0.869s | 1.598s |
| 冷えたPOI 9枚だけ | 0.117s | 0.151s |
| 冷えた事故9枚だけ | 0.113s | 0.176s |

- **冷と温の差は約20倍**で、これは「全部まとめて取り直す」費用が実在することを示す。
- **費用のほぼ全部は路面タイル**。POI・事故は冷えていても0.12秒で、同時に取り直しても
  待ちを作っていない。
- 27本を同時に投げると路面単独（0.869s）の倍以上（1.857s）になる。同時実行の上限
  （`road_tile_max_concurrent=6`）での待ちが乗っているぶんである。

### 主犯候補が1つ消えた

報告された症状は`dynamic-way-values`が15秒のタイムアウトを1分以上続けることだった。
**冷えたタイル48枚を同時に取り直している最中に同じエンドポイントを叩いても、初回0.871秒・
以降0.033秒で返る。**

つまり**「キャッシュ全消去＋視界の一斉取り直し」だけでは15秒に届かない**——2.7秒が上限で、
1桁足りない。起票時に「原因の断定はまだしていない」と書いたとおりで、実際に断定できない
ことが確かめられた。残る材料は、今回の計測が再現していない次の2つである。

- **道路グラフの再構築**（`_maybe_trigger_graph_build`）。今回の計測対象はすべて構築済みの
  エリアで、`graph_build_semaphore`とDB接続プールの取り合いは起きていない。
- **基礎地図・DEMの取り直し**。`tile_cache.clear_all()`はこれらも落とすが、外部（OpenFreeMap・
  国土地理院）への再取得を伴うため、自前のPostGISから焼き直す路面タイルとは費用の性質が違う。

### 測り方の落とし穴（記録しておく）

最初の計測はhttpxの既定（HTTP/1.1）で27本を同時に投げ、**全27本が502**になった。これを
「世代直後は詰まる」と読むところだったが、同じタイルを単発で引くと200が返る。**27本ぶんの
TLS接続を別々に張ったことが原因**で、同じ27本をHTTP/2の多重化（1接続）で投げると全て200に
なる。本番のnginxはHTTP/3＋HTTP/2で応答する構成（[T580](T580.md)）で、ブラウザは1接続へ
多重化するため、**利用者はこの502を踏まない**。

計測の道具が利用者と違う経路を通ると、存在しない主犯を作る。ただし「別々の接続を多数
張ると502になる」こと自体は事実なので、HTTP/2が効かない経路（プロキシ・古いクライアント）
が出てきたときのために書き残す。

### `tile_cache`を系統ごとに消せるか（調べること2つ目への答え）

消せる。現在のキーは`cache_key(path)`＝パスのsha256で系統の情報が消えるが、**パスは書き込む
時点では分かっている**。ファイル名を`<系統>-<ハッシュ>.bin`の形にすれば、参照側の引き当ては
今と同じまま、`clear_all`だけを系統単位へ絞れる。フラットに保つ理由（Windowsでの
ディレクトリとファイルの名前衝突回避）も損なわない。

ただし**これを入れる根拠はまだ無い**。上の実測では基礎地図・DEMの取り直しが待ちを作って
いるかを測れていない（基礎地図のスタイルJSONは温まった状態で34msだった）。先に外部取得の
費用を測る。
