# T814. 鮮度台帳がbatchをトップレベルimportする依存を断ち、台帳の網羅性の穴を塞ぐ

規模S〜M。
状態: 未着手（統合レビュー第8回のP1、2026-09-13）

## 背景

### 1. 依存の向きが逆で、本番webイメージが起動失敗しうる

`app/infrastructure/derived_data_freshness.py:23-26`がinfrastructureから
`app/batch/precompute_*.py`を4本**モジュールトップでimport**しており、batch側は
`road_graph_repository`（infrastructure）をimportし返す循環になっている。

かつwebイメージは`requirements.txt`しか入れない（`backend/Dockerfile:5-6`、rasterio等は
`requirements-batch.txt`のみ）。そのため`precompute_*`のどれかにbatch専用依存の
トップレベルimportを1行足すと、**テストとCIはbatch依存が入っているため緑のまま通り、
本番webイメージだけが**`api/routers/derived_data_freshness.py`→
`infrastructure/derived_data_freshness.py`のimport連鎖で`ModuleNotFoundError`を起こして
backendが起動失敗する。

現在この規約を守らせているのは`precompute_way_landcover.py:88-90`の「ここでのみ読み込む」
というコメント1つだけで、検知器もテストも無い。

### 2. 台帳の網羅性テストが、版数を宣言しないバッチを素通りさせる

`tests/test_derived_data_freshness.py:140-170`の母集団は「`precompute_*.py`のうち
`ALGORITHM_VERSION`を宣言しているもの」であるため、版数を宣言しなければ台帳に載らなくても
テストを通る。`precompute_edge_curvature.py`がこれに該当し、`ALGORITHM_VERSION_NOT_IN_LEDGER`も
空のままで理由の記録が無い。

結果、`way_geometry`（地図・軸スタジオ用）は台帳に載ったが、**ルート評価が実際に読む**
`road_edges.curvature_deg_per_km`は載らず、`road_edges`に系譜列自体が無い。PBF再取込後に
`precompute_edge_curvature`の実行だけを忘れると、新規splitされたEdgeはNULL
（＝蛇行軸が重み再正規化で薄まって無警告で評価から抜ける）のまま残るが、
`GET /api/admin/derived-data/freshness`にはその陳腐化がどこにも現れない。同じ穴は
`precompute_road_node_degrees`（`road_nodes.degree`）にも当てはまる。

## 対応方針

1. 台帳が必要とするのは`ALGORITHM_VERSION`定数だけなので、**モジュールをimportせずに読む**
   （定数を依存の無いモジュールへ寄せる、またはASTで読む）。依存の向きを
   infrastructure→batchから断つ。
2. 網羅性テストの母集団を「版数を宣言しているもの」から「`precompute_*.py`のすべて」へ広げ、
   載せない場合は`ALGORITHM_VERSION_NOT_IN_LEDGER`へ理由つきで明示させる。
3. `precompute_edge_curvature`・`precompute_road_node_degrees`の扱いを決める（系譜列を足すか、
   理由つきで除外するか）。**除外を足すなら、対象から外す件数と母集団に対する割合を実測して
   このエントリへ書く**（CLAUDE.md「修正の原則」）。
4. 1は**わざと壊して確認する**——`precompute_*`の1本へweb側に無い依存のトップレベルimportを
   足し、`api/routers/derived_data_freshness.py`のimportが落ちることを確かめる。
