# T539: 交差点分割（split）を実行時ではなくPBF取込後のバッチで全域に済ませる

状態: 実装・テスト完了（2026-09-02。本番実行は未実施）

- 背景: 未splitエリアへの初回リクエストは`get_or_build_graph_with_attributes`の再構築
  経路（closure取得9.9秒＋`build_road_graph`8.8秒＋`save_graph`26.9秒、本番実測
  T522.md「本番環境での再現・内訳調査」節）がリクエスト内で走り、さらにタイル
  キャッシュも温まらない（`_maybe_warm_tile_cache`の後追い温めが別途走る）。
  `app/batch/`には分割を事前に行うバッチが無く、`precompute_elevation_attributes`等は
  `road_edges`が存在するEdgeしか対象にできないため、未splitエリアは標高等の事前計算
  からも漏れる。
- 対応方針: 取込済み全タイル（`road_graph_tiles`）をz12タイル単位で走査し、
  `GraphService.get_or_build_graph_with_attributes`と同じ再構築経路（closure→
  `build_road_graph`→`save_graph`）を順に適用する`app/batch/presplit_road_graph.py`を
  追加する。既存の`is_split_up_to_date`判定を使い、split済みタイルはスキップして
  冪等にする。実行順は`import_pbf`→本バッチ→各precomputeバッチ（`docs/osm-pbf-import.md`
  の手順へ追記）。実行時の再構築経路は、再取込後にバッチを回し忘れた場合の安全網として
  残す。
- 関連: [T538](T538.md)（冷パスの別の段）。過去の本番バックフィル漏れの実績
  （T74・T101、改善計画参照）を踏まえ、新規事前計算は本番実行まで完了条件に含める。
- 完了条件: 本番の取込範囲全域でバッチ実行後に`is_split_up_to_date`が全タイルTrue、
  以後の`get_or_build_graph_with_attributes rebuild`ログが出ないことを確認、バッチの
  冪等性テスト、`docs/osm-pbf-import.md`と`docs/modules/`の該当設計書を同一コミットで更新。

## 実装（2026-09-02）

`backend/app/batch/presplit_road_graph.py`を新設。`road_graph_tiles`から取込済み全z12
タイルを取得し、タイルごとに`RoadGraphRepository.is_split_up_to_date`で判定してから
未split分だけ`GraphService.get_or_build_graph_with_attributes`（実行時と同じ再構築経路）を
呼ぶ。ロジックを二重実装せず既存publicメソッドをそのまま呼ぶ設計のため、
`graph_service.py`・`road_graph_repository.py`自体への変更は無い（新規ファイル1本のみ）。
`--dry-run`で対象タイル数のみログ出力、`--database-url`で接続先を指定可能（他の
precomputeバッチと同じCLI規約）。

`docs/batch-pipeline-dependencies.md`を更新: 本バッチを④として追加し、既存の
④〜⑧（road_edges起点の派生計算・osm_raw_ways起点の派生計算）を⑤〜⑨へ繰り下げた。
併せて、旧文書が「①（import_pbf）でroad_edgesが存在すること」としていた前提が実態と
異なっていた点（road_edgesは実行時の遅延構築でのみ生成され、import_pbf自体は生成しない）
を本バッチの追加で正しい記述へ修正した。

**テスト**: `tests/test_presplit_road_graph.py`（PostGIS統合テスト、`ridecompass_test`）。
未split→バッチ実行→road_edges生成、再実行してもエラーなく完走する冪等性、dry-runが
書き込みを行わないことを確認。

**本番実行時のDB負荷について（ユーザーとの設計確認、2026-09-02）**: バッチが処理中の
タイルへ生トラフィックが同時にアクセスすると、両者とも独立に`closure取得→
build_road_graph→save_graph`を実行し、PostgreSQLの行ロックで一方が他方の完了を待つ
（edge_idが決定論的なため最終的には同じ結果へ収束し、データ破損はしない）。バッチ全体の
実行時間中（全域規模だと数時間）は本番VM（2vCPU）のCPU/IOを生トラフィックと奪い合う点も
含め、**低トラフィック時間帯に実行する運用上の配慮で対応する方針とし、コード側での
レート制限は追加しないと決定した**（このタイル間の競合自体はT539が無くても今日から
存在するもので、T539は競合が起こりうるタイル数を増やすだけという整理）。

**本番実行時のDB容量増分の見積もり**: dev DB（東京都心南部16タイル、実測で約93%
split済み）を計測すると、split後（road_edges+road_nodes）は生データ層
（osm_raw_ways+osm_raw_nodes）の約2.5倍のサイズになる。関東7都県全域の生データ層
実測値（1,364MB、`docs/osm-pbf-import.md`12章）へ当てはめると、全域presplit実行で
road_edges/road_nodesだけで**約3.4GB**、後続のprecomputeバッチ（`edge_attribute_counts`・
`elevation_attributes`）も全域へ追随実行するなら合計**5〜6GB程度**の増加と見積もられる
（Oracle Cloud・ブロックストレージ150GBに対しては十分収まる規模）。

## 検証結果

`pytest tests/test_presplit_road_graph.py tests/test_graph_service.py
tests/test_road_graph_repository.py tests/test_batch_common.py -q` 139件green。
`pytest -q -n auto`のフルスイート実行で無関係な15件の失敗が出たが、個別に逐次実行すると
大半が再現せずxdist並列実行時のDB競合（既知の環境要因）と判明。1件
（`test_import_accidents.py::test_upserts_same_accident_id_on_rerun`）は単体実行でも
再現する既存バグの可能性があり、T539とは無関係のため別タスクとして起票する
（`presplit_road_graph.py`は`accident_import_runs`等の事故データ関連テーブルに
一切触れないことを確認済み）。
