# T621. 候補ルートを分岐点で乗り換えられるようにする（区間のいいとこ取り） 規模L

状態: 設計中（2026-09-06起票、実装未着手）

## 背景

ユーザー指摘（2026-09-06）「目的地への生成ルートを見てると、各セクションのいいとこ取りを
したいのに、って思うことがある」。ユーザー判断で、実現手段は**候補同士を分岐点で乗り換える**
（地図上で候補Aを見ながら「ここからはBの道」を選ぶと、Aの前半＋Bの後半が1本のルートに
なる）と決定した。

## 調査で判明した現状の制約

- **経由地を1つ置くと候補が1本になる**。`generate_via_waypoints`は経由地ありのとき
  `trace_loop`で単一経路のみを生成し`max_routes`を無視する（[T551](T551.md)、レグごとに
  代替案が組合せで増えるためv1では対象外とした判断）。「候補Aの良い区間を経由地として
  ピン留めして再生成」というやり方でいいとこ取りをしようとすると、その瞬間に比較相手が
  消える。
- **`RouteSegmentDetail`がノードIDを持たない**（座標4つ・距離・軸別difficultyのみ）。
  区間は「サンプル点i→i+1」でbackendが切ったもので、同じ道を通っていても候補ごとに
  切れ目の位置が違いうるため、**frontendで座標一致から合流点を求めるのは不正確**。
  合流点はグラフのノードIDで求める必要がある。
- 一方で**合流点自体は豊富にある**見込み。候補の間引き閾値が重複率0.6
  （`TURNAROUND_MAX_OVERLAP_RATIO`）のため候補同士は最大6割の道を共有し、共有Edgeの
  端点はすべて共有ノードになる。目的地ルートは前向き木・後ろ向き木を共有して経由ノード
  だけを変える生成方式（`select_via_nodes`）のため、起点付近と目的地付近を共有し中間が
  分かれる構造になりやすい。意味のある「分岐点」は共有区間が途切れる地点。

## 未決の論点

1. **合成をどこで行うか**（他の論点を左右するため最初に決める）。backendに合成APIを置くと
   評価の再集約（`overall_difficulty`・`difficulty_load`・`axis_difficulties`・
   `axis_contributions`）に既存のPython実装をそのまま使えるが、backendはステートレスの
   ため合成のたびに候補を送り返すか生成時の候補をキャッシュする必要がある。frontendで
   行うと集約ロジックをTypeScriptで書き直すことになり二重メンテになる。
2. **分岐情報をいつ返すか**。候補生成時に全ペアぶん計算して返すか、乗り換え操作時に都度
   計算するか（候補8本なら28ペア）。
3. **合成したルートの居場所**。新しい候補として一覧へ追加するか、選択中の候補を置き換えるか。
   追加ならA+B+Cのように乗り換えを繰り返せる。
4. **UIの操作**。地図上で分岐点にマーカーを出す案が素直だが、候補8本ぶんの分岐点をすべて
   出すと地図が埋まる。「表示中の候補と次点との分岐点だけ」等の絞り方の設計が要る
   （走行前の作業のため多少の複雑さは許容できるが、実装前にユーザーと詰める）。
5. **通行の妥当性**。同じノードでつなぐ限り有向グラフ上の経路としては成立する。そのノードで
   実際に曲がれるか（進入禁止・turn restriction）まで見るかどうか——現状の生成でも同じ
   前提のため、揃えるなら追加チェックは不要。

## 保留した場合の影響

- ユーザーは引き続き「候補Aのこの区間とBのこの区間を組み合わせたい」を実現できない。
  経由地でのピン留めは、置いた瞬間に候補が1本になるため代替手段にならない。
- `RouteSegmentDetail`へノードIDを持たせるかどうかが未決のまま残る。区間データを使う
  他の機能（区間クリック詳細・比較パネル）が増えるほど、後から足す際の影響範囲が広がる。
- 論点1（合成の場所）を決めないまま部分的にfrontend側で座標一致の合成を作ると、区間境界の
  ズレで合流点を取りこぼす実装が残り、後で作り直しになる。
