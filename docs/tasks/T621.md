# T621. 候補ルートを分岐点で乗り換えられるようにする（区間のいいとこ取り） 規模L

状態: 設計完了・実装未着手（2026-09-06起票。2026-09-12に段取り1まで完了し、
対象範囲・論点1〜5・APIの形・見せ方がすべて決定。次は段取り2のbackend）

## 背景

ユーザー指摘（2026-09-06）「目的地への生成ルートを見てると、各セクションのいいとこ取りを
したいのに、って思うことがある」。ユーザー判断で、実現手段は**候補同士を分岐点で乗り換える**
（地図上で候補Aを見ながら「ここからはBの道」を選ぶと、Aの前半＋Bの後半が1本のルートに
なる）と決定した。

## 調査で判明した現状の制約

- **経由地を1つ置くと候補が1本になる**。`generate_via_waypoints`は経由地ありのとき
  `trace_loop`で単一経路のみを生成し`max_routes`を無視する（[T551](T551.md)、レグごとに
  代替案が組合せで増えるためv1では対象外とした判断）。「候補Aの良い区間を経由地として
  ピン留めして再生成」というやり方でいいとこ取りをしようとすると、その瞬間に比較相手が
  消える。
- **`RouteSegmentDetail`がノードIDを持たない**（座標4つ・距離・軸別difficultyのみ）。
  区間は「サンプル点i→i+1」でbackendが切ったもので、同じ道を通っていても候補ごとに
  切れ目の位置が違いうるため、**frontendで座標一致から合流点を求めるのは不正確**。
  合流点はグラフのノードIDで求める必要がある。
- 一方で**合流点自体は豊富にある**見込み。候補の間引き閾値が重複率0.6
  （`TURNAROUND_MAX_OVERLAP_RATIO`）のため候補同士は最大6割の道を共有し、共有Edgeの
  端点はすべて共有ノードになる。目的地ルートは前向き木・後ろ向き木を共有して経由ノード
  だけを変える生成方式（`select_via_nodes`）のため、起点付近と目的地付近を共有し中間が
  分かれる構造になりやすい。意味のある「分岐点」は共有区間が途切れる地点。

## 起票時に挙げた論点（結論は「決定（2026-09-12）」節）

1. **合成をどこで行うか**（他の論点を左右するため最初に決める）。backendに合成APIを置くと
   評価の再集約（`overall_difficulty`・`difficulty_load`・`axis_difficulties`・
   `axis_contributions`）に既存のPython実装をそのまま使えるが、backendはステートレスの
   ため合成のたびに候補を送り返すか生成時の候補をキャッシュする必要がある。frontendで
   行うと集約ロジックをTypeScriptで書き直すことになり二重メンテになる。
2. **分岐情報をいつ返すか**。候補生成時に全ペアぶん計算して返すか、乗り換え操作時に都度
   計算するか（候補8本なら28ペア）。
3. **合成したルートの居場所**。新しい候補として一覧へ追加するか、選択中の候補を置き換えるか。
   追加ならA+B+Cのように乗り換えを繰り返せる。
4. **UIの操作**。地図上で分岐点にマーカーを出す案が素直だが、候補8本ぶんの分岐点をすべて
   出すと地図が埋まる。「表示中の候補と次点との分岐点だけ」等の絞り方の設計が要る
   （走行前の作業のため多少の複雑さは許容できるが、実装前にユーザーと詰める）。
5. **通行の妥当性**。同じノードでつなぐ限り有向グラフ上の経路としては成立する。そのノードで
   実際に曲がれるか（進入禁止・turn restriction）まで見るかどうか——現状の生成でも同じ
   前提のため、揃えるなら追加チェックは不要。

## 保留した場合の影響（起票時）

- ユーザーは引き続き「候補Aのこの区間とBのこの区間を組み合わせたい」を実現できない。
  経由地でのピン留めは、置いた瞬間に候補が1本になるため代替手段にならない。
- `RouteSegmentDetail`へノードIDを持たせるかどうかが未決のまま残る。区間データを使う
  他の機能（区間クリック詳細・比較パネル）が増えるほど、後から足す際の影響範囲が広がる。
- 論点1（合成の場所）を決めないまま部分的にfrontend側で座標一致の合成を作ると、区間境界の
  ズレで合流点を取りこぼす実装が残り、後で作り直しになる。

## 決定（2026-09-12）

### 対象範囲: 目的地ルートのみ

ユーザー判断。周回は「同じ地点へ戻る」制約があり、途中で別候補へ乗り換えると戻れる保証が
無くなる（乗り換え先の後半は別の経路で起点へ戻る前提で組まれている）。目的地ルートは
終端が固定なので、共有ノードでつなげば必ず目的地へ着く。

### 論点1（合成をどこで行うか）: backend。**これは選択肢ではなかった**

起票時は「backendに置くと候補を送り返す必要がある／frontendに置くと集約ロジックの二重
メンテ」というトレードオフとして書いていたが、[design-principles.md](../design-principles.md)
**構造仕様1が既に決めていた**——フロントエンドは軸固有のロジック・計算式・閾値を持たない。
`overall_difficulty`・`axis_contributions`の集約は軸の重みを使った計算式そのものなので、
frontendで合成するという選択肢は最初から存在しない。

さらに**構造仕様10**（Edgeコストは一度だけ計算し、探索と表示が同じ値を共有する）により、
合成結果は既存候補と同じ評価経路——`evaluate_loops`——を通す必要がある。
「前半の値と後半の値を距離加重で混ぜる」近似は、構造仕様10が禁じている二重計算になる。

**この論点が未決のまま残っていたのは、正本を読まずに局所の事実だけで判断しようとしたため**
（2026-09-12ユーザー指摘「局所判断だけで、設計全体を決めるべきではない」）。
[T722](T722.md)で入れたばかりの「着手前に対象領域の正本を読む」を、自分に適用していなかった。

### 論点2（分岐点をどう求めるか）: 候補へ`edge_ids`を載せ、frontendは集合演算だけを行う

`segments`は使えない——約500m単位へビニング済み（`route.py`の`RouteCandidate.segments`
直後のコメント参照）で、Edge境界＝グラフのノードと一致しない。座標一致で合流点を求めると
区間境界のズレで取りこぼす（起票時の「保留した場合の影響」で予測したとおり）。

候補へ経路のEdge id列を載せれば、frontendは**共有Edgeの連なりが途切れる位置**を集合演算で
出せる。これは軸固有の計算式ではなく経路の同一性の判定なので、構造仕様1に抵触しない。

合成の指定もEdge idで行う（「候補Aのこのidまで＋候補Bのこのid以降」）。座標や区間番号で
指定すると、backend側で再びノードへ解決する処理が要る。

### 論点3（合成したルートの居場所）: 新しい候補として一覧へ追加する

A+B+Cのように乗り換えを繰り返せる（起票時の想定どおり）。`max_routes`の上限とは別枠で
数える——上限は「生成が何本探すか」の指定であり、ユーザーが作った合成ルートを押し出す
理由が無い。

### 論点4（UIの操作）: 表示中の候補 × 全候補の分岐点を出す

ユーザー判断。起票時の懸念は「候補8本ぶんの分岐点をすべて出すと地図が埋まる」だったが、
モックで確認したところ**マーカーの数は候補数ではなく分岐位置の数に比例する**——候補が
同じ木を共有して分かれるため、1つの分岐点が複数の乗り換え先を持つ
（モックでは候補8本が3つのマーカーへ集約され、それぞれ5本・7本・2本の乗り換え先を持った）。

**ただしこれはモックの仮定に乗った観測であり、実データの測定ではない**。
`select_via_nodes`が前向き木・後ろ向き木を共有する生成方式である以上そうなる見込みだが、
段取り1で実データを測って確認する（埋まるなら絞り方を設計する）。

### 論点5（通行の妥当性）: 追加チェックはしない

構造仕様10により合成後の`evaluate_loops`が同じEdgeコストで正しく再評価するため、
生成時と同じ前提が自動的に揃う。起票時の「揃えるなら追加チェックは不要」で正しかった。

## 段取り1（測る）の結果（2026-09-12）

### APIの形: `generate`にモードを足す（別エンドポイントにしない）

決め手は**合成が`prepare()`を避けられない**こと。`road_graph_engine.py`の
`evaluate_loops`は`context.graph`を参照し、その`context`は`prepare()`の産物である。
合成は探索をやり直さないが、`prepare()`は必ず通る。

`prepare()`の所要時間は測り直すまでもなく[T532](T532.md)に本番実測が残っていた
（2026-09-05、東京駅25km・`max_routes=8`・Edge 47.7万件）:

| 回 | `prepare_ms` | `total_ms` |
|---|---|---|
| 1回目（デプロイ直後＝冷） | 22,516 | 23,421 |
| 2回目（温） | 1,252 | 2,229 |
| 3回目（温） | 1,268 | 2,582 |
| 4回目（温） | 1,272 | 2,220 |

温パスの`prepare()`は生成全体の過半を占め、冷は22.5秒。**合成のコスト曲線は生成と
同じ形**（`prepare`が支配的）になるため、202＋ポーリングのjob機構が合成にも要る。
別エンドポイントにすると投入・進捗・取得をもう一式書くことになるので、
[構造仕様8](../design-principles.md)に従い`generate`へモードを足す。

### `edge_ids`は既にbackend内部にある

`evaluate_loops`が`for edge_id in t.data`と書いているとおり、**`TracedLoop.data`は
road_graphエンジンでは経路のEdge id列そのもの**。論点2の「候補へ`edge_ids`を載せる」は
新しい計算ではなく`RouteCandidate`へ通すだけで、合成側も「Aの前半＋Bの後半」で
`TracedLoop`を組めば既存の`evaluate_loops`がそのまま食える。

### 分岐点の個数（本番VM実測、2026-09-12）

東京駅→船橋駅相当（約20km、`max_routes=8`＋最短経路で候補9本、edges=208,844）を
`benchmarks/bench_t621_divergence.py`で計測した。

| | 実測 |
|---|---|
| マーカー個数 | **8〜12個**（平均9.6） |
| 合成経路の連結 | **156/156件** |
| `prepare_ms` | 温630／冷59,320（冷は`materials_ms=58,181`が支配） |

**論点4は起票時の懸念（地図が埋まる）が正しく、モックを根拠にした見立て
（「候補8本が3マーカーへ集約される」）は外れた。** モックは候補が同じ木を共有して
1点から分かれる形を仮定していたが、実データはそうならない。

一方で**連結は全件成立**したため、論点5（追加の通行チェックはしない）は実データで
裏付けられた。

#### 分布には構造がある

- **起点付近に密集**: ほぼ全候補が0.35／0.89／1.33／1.57／2.06／2.70km付近に4〜6個。
  20km級のルートを1画面に収めた縮尺では1点に重なる。
- **目的地付近にも密集**: 例えばroute-01は23.35／23.96／25.37kmの3個、いずれも
  乗り換え先は最短経路1本だけ。
- **中間は疎で、大半が最短経路宛て**: route-00は10個中8個が「乗り換え先=1件、最短経路」。
  距離だけで選ぶ最短経路は軸重み付きの候補と構造的に別物のため、何度も交差しては離れる。

#### 絞り込みは、個数ではなく「生む経路の違い」で決める

「同じ乗り換え先が連続するマーカーを畳む」は素直に見え、route-00なら10個→3個になる。
**しかしそれは2.49kmで最短経路へ乗り換えるのと12.11kmで乗り換えるのを同じものとして
捨てることになり、全く違う経路を1つに潰す。**

判断に要るのはマーカーの個数ではなく、そのマーカーが生む経路がどれだけ違うかで、
これは測らないと分からない（CLAUDE.md「緩和は影響を測ってから入れる」）。測った:

| 同じ乗り換え先を持つ隣り合うマーカーが生む経路の違い | 組数（全84組） |
|---|---|
| 0.5km未満（実質同じ経路） | 22組 (26%) |
| 0.5〜2km | 30組 (36%) |
| 2km以上（別の経路） | 32組 (38%) |

**畳んで良いのは4組に1組だけ。** 入れていたら選択肢の74%を静かに捨てていた。しかも
0.5km未満を全部落としてもマーカーは平均9.6個→約7個にしかならず、地図が埋まる問題は
解決しない。**絞り込みでは解決しない**というのがこの実測の結論。

### 区間の個数と長さ（本番VM実測、2026-09-12）

| | 実測 |
|---|---|
| 1ペアあたりの区間数 | 最小1・最大8・**平均2.2個** |
| 区間の長さ（156区間） | 5km以上 **50%**／1〜5km 17%／0.2〜1km 19%／0.2km未満 14% |

マーカーが候補あたり9.6個あったのは**相手8本をまとめて出していたため**で、相手を1本に
絞れば平均2.2個になる。

### なぜそうなるか（実測ではなく生成方式から出る）

**1ペアの実測で判断すべきではない**（2026-09-12ユーザー指摘「限定的な例で判断するのでは
なく、ロジック的に考えて」）。上の数字は`select_via_nodes`の作りから導ける。

候補はすべて**同じ2本の木**から作られる——起点を根とする前向き木
（`build_shortest_path_tree(..., origin_index)`）と、目的地を根とする後ろ向き木。
候補は「via-nodeまでの前向き木の経路＋via-nodeからの後ろ向き木の経路」。

木では根から各ノードへの経路が一意で、**2ノードへの経路は最小共通祖先で1度だけ分かれ、
二度と合流しない**。したがって候補AとBは前向きで1度分かれ後ろ向きで1度合流し、
**差は必ず1つの連続した区間になる**。実測の「最小1」はこの下限そのもの。

**その1区間の長さにも下限がある**。採用条件の`VIA_NODE_MAX_OVERLAP_RATIO = 0.6`
（=`TURNAROUND_MAX_OVERLAP_RATIO`、緩和時0.85）により候補どうしの重複は6割以下で、
区間は1つなので**差の区間は経路の40%以上**を占める——20kmなら8km以上、50kmなら20km以上。
`ALTERNATIVE_MAX_STRETCH = 1.3`も比率のため、距離が伸びるほど許される寄り道の絶対量が
増え、via-nodeを直線から遠くへ置ける。**距離が伸びて増えるのは区間の数ではなく長さで、
方角から違う差になる。**

**例外は最短経路だけ**。`select_shortest_distance_route`は距離だけのコストで**別の木**を
作るため、軸重み付きの木と何度も交差する。実測で1本だけ8区間だったのも、平均2.2を
押し上げているのもこれ。

この導出は0.2km未満の14%の扱いも決める——重複率の縛りを受けないのは最短経路ペアだけ
なので、**路地1本分の区間は最短経路との比較からしか出ない**（軸候補どうしには構造上
現れない）。

### 見せ方: 区間（帯）で見せる



元のユーザー指摘は**「各セクションのいいとこ取りをしたい」**——区間の話だった。一方
本タスクの設計は「分岐点で乗り換える＝Aの前半＋Bの後半」という**点**の操作になっている。

実データは両方の見方ができる。route-00とroute-08は8箇所で分かれるが、これは
**8個の分岐点**であると同時に**2本が別々の道を通る8つの区間**でもある。2本は共有ノードで
必ず合流するため（連結156/156がその性質を裏付ける）、**どの区間を相手側へ差し替えても
経路として成立する**。区間として見せれば地図上は帯が8本になり、区間ごとに切り替えられる
なら論点3が欲しかったA+B+Cの重ね合わせも自然に出る。

上の導出により、区間モデルは地図を埋めない——軸候補どうしの比較では帯が**常に1本**で、
しかも経路の40%以上を占める大きな差になる。点モデル（Aの前半＋Bの後半）は区間モデルの
部分集合（連続した後半だけを選ぶ操作）にあたり、途中の1区間だけを相手の道にできない。

モック: https://claude.ai/code/artifact/267655b7-12e2-4e2a-aae6-9e169f3761b1
（分岐位置と区間数は本番実測値、区間の終了位置と距離・難易度の増減は仮置き）

**最短経路も他の候補と同じ扱いにする**（2026-09-12ユーザー判断「まず同じ見せ方で
考えたい。拡張が必要かどうかは実機で使い勝手を見てからがいい」）。この1本だけ帯が
細かく多い（実測8区間）が、比較相手は一度に1本のため8本が上限で、他の候補を選んで
いる間は現れない。特別扱いを先に作ると、実機で要らないと分かったときに軸ごとの
分岐を1つ残すことになる。

実機で見るべきは「最短経路を選んだときだけ帯が読めない」かどうか。読めなければ
そのときに別Txxxとして起票する（このタスクの本文へ残さない——`[x]`化した時点で
機械抽出から漏れるため）。

### 計測スクリプトの使い方

```
python -m benchmarks.bench_t621_divergence
```

本番VMでは`benchmarks/`がDockerイメージに同梱されないため、稼働中コンテナとは別の
使い捨てコンテナへマウントして実行する（[T551](T551.md)と同じ形）。

`_generate_destination_routes`と同じ手順（`prepare`→`select_via_nodes`→最短経路の追加）
で実候補を作り、各候補を「表示中」と見立てたときのマーカー個数・起点からの距離・
乗り換え先の数を出す。併せて**合成経路がグラフ上で連結しているか**（前のEdgeの
`to_node_id`＝次のEdgeの`from_node_id`）を数えるので、論点5の前提も実データで確かめられる。

分岐点を求める部分（`benchmarks/_divergence.py`）は**計測のための実装で、製品の実装では
ない**——乗り換えUIはfrontendが同じ集合演算をTypeScriptで行う（論点2）。実データを
待たずに固定できるよう、Edge id列に対する単体テストを別途置いた。
