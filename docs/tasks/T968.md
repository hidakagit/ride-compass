# T968: 層ごとの責務（DB=データ／app=ふるまい／テスト=今のふるまい）を点検する

状態: 未着手（2026-09-20起票）

## 背景

[T956](T956.md)で、`road_edges.osm_way_id`にFKもNOT NULLも無く、その結果として
「wayの行が無い区間」という状態をapp側の材料の値式10本が`CASE WHEN w.osm_way_id IS NULL
THEN NULL ELSE ...`で毎回吸収していたことが分かった。本番データの違反行は0件で、
兄弟の派生表5本（`way_attribute_counts`・`way_landcover`・`designation_attributes`・
`edge_landcover`・`way_divided_carriageway`）は同じFKを既に持っていた。
つまり**DBが持つべき制約をappが肩代わりしていた**。

同じ点検で、`app/domain/material_sql.py`にテストからしか呼ばれない関数を1本足していた
ことも分かった（`folds_tag_absence_to_false`、同タスク内で撤去）。**appがテストの都合を
意識した実装**である。

守るべき線は次の3つ。これが崩れると、DBが緩いぶんをappが吸収し、appの吸収をテストが
固定し、直すと全部が同時に落ちるため誰も直せなくなる。

- **DB**: データの制約（NOT NULL・FK・UNIQUE・CHECK）。派生表は親への参照を持つ。
- **app**: ふるまいの制約。DBが保証している前提を再確認しない。
- **テスト**: 「今」のふるまいの網羅。appにテスト専用の口を作らせない。

## 対応方針

### 点検1: DBが持つべき制約をappが吸収していないか

母集団の導出:

1. 派生表の親子関係を列挙する。`app/infrastructure/*_models.py`の`ForeignKey`宣言と、
   本番の`pg_constraint`（`contype='f'`）を突き合わせ、**モデル上は親を持つが
   DBに制約が無い／そもそもどちらにも無い**列を出す。
2. 1で出た列について、app側が「無いかもしれない」前提のコードを持っていないかを探す
   （`IS NULL THEN NULL`を含むSQL式、`or {}`、`is None`分岐、`COALESCE`の既定値）。
3. 制約を張れるかを本番データで測る（違反行数）。違反が0でなくても、**取込・正規化側で
   制約を守らせてから**張る——「本番データがこうだから張れない」で終えない。

### 点検2: appにテスト専用の口が無いか

母集団の導出: `app/**`のモジュール直下の公開定義（先頭が`_`でないもの）のうち、
定義元以外の`app/`・`scripts/`・`benchmarks/`・`migrations/`から参照されず、
`tests/`からのみ参照されるもの。2026-09-20時点で12件（うち8件は`reset_*`・
`*_cache_size`のようなテストが状態を初期化・観測するための口で、これは正当。
残り4件`OsmRawPoiRow`・`decode_terrain_rgb_meters`・`osm_ways_to_way_specs`・
`read_persisted_axis_revision`は実装に取り残された可能性がある）。

この列挙は「シンボルが参照されているか」までで、**本番の入口から到達するか**は見ていない
（`compute_edge_costs_bulk`はapp内から参照されていたためこの列挙に出なかった）。到達可能性
まで見る検知器は[T963](T963.md)の題材で、そちらと母集団が重なる——**先にT963の結論を見てから
検知器を足すか決める**。

### 点検3: テストファイル同士が直接依存していないか

母集団の導出: `grep -l "from tests\.test_\|import tests\.test_" backend/tests/test_*.py`。
2026-09-20時点で2件（`test_wind_time_varying.py`→`test_road_graph_engine`の
`ORIGIN`/`_prepare_context`/`build_loop_graph`/`make_generator`、
`test_gsi_tile_routes.py`→`test_terrain_rgb`の`gsi_tile`）。共有ヘルパー
（`tests/`直下のtest_で始まらないモジュール）経由の参照は正当で、これは対象外。

直接依存は、片方のテストの都合でもう片方が壊れる（実際にT956で`make_generator`の
シグネチャを変えたとき、参照元に気づかないまま壊しかけた）。共有ヘルパーへ出す。

## 完了条件

- 点検1の母集団（FKもNOT NULLも無い派生列）が列挙され、1件ずつ「制約を張った」か
  「張れない理由を実測つきで書いた」かのどちらかになっている。
- 点検2の12件（2026-09-20の再計測では15件）が1件ずつ「テストのための正当な口」か
  「取り残し」かに分類され、後者は削除されている。FastAPIのエンドポイント・ORMモデルは
  デコレータ/メタクラス経由で使われるため偽陽性——列挙の時点で除く。
- 点検3の直接依存が0件になっている。
- appからDBの制約を肩代わりする分岐が消えていること（点検1の2で出た箇所が0件）。
