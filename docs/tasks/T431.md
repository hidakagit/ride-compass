# T431. RouteCandidateのレガシー個別フィールド（stop_density等9個）を末端消費者ゼロ化後に廃止するか検討

状態: 未着手（起票のみ、2026-08-30・T421/横展開チェックで発見）

- 背景: [T421](T421.md)でRouteList.tsx、本タスクの起票と同時にComparisonPanel.tsxが
  `axis_difficulties`駆動へ移行すると、`backend/app/domain/route.py: RouteCandidate`の
  `elevation_gain_m`・`wind_score`・`road_score`・`stop_density`・`car_stress_score`・
  `bicycle_infra_score`・`intersection_density`・`accident_density`の8フィールド
  （＋関連する`total_score`・`score_breakdown`）は、**フロントエンドの表示消費者がゼロになる**
  見込み（route.py自身のdocstringも「旧来の軸1対1固定設計の名残...軸増減に追従しない」と
  明記済み）。
- 書き込み側（値の計算元）は`backend/app/infrastructure/road_graph_repository.py`・
  `backend/app/services/road_graph_engine.py`に残っている——これらの計算自体を止めるか、
  APIレスポンス（`RouteCandidate`のPydanticモデル、OpenAPI契約）からフィールドを完全に
  除去するかは、外部消費者（研究モード用に直接API呼び出ししているスクリプト等が無いか）の
  洗い出しが必要な、T421より大きな話。
- 対応方針（未検討）: ComparisonPanel.tsx移行後に改めてフィールドの読み取り消費者を
  全件grepし、本当にゼロになったことを確認してから着手判断する。除去する場合は
  OpenAPI再生成・型生成物の追従が必要（CLAUDE.md「コミット時の同期ルール」）。
