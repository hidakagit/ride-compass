# T649. ディスク永続キャッシュの世代滞留を止める（694MBの死蔵） 規模S〜M

状態: 完了（2026-09-07。当初T648として採番したが並行セッションと衝突したためT649へ振り直した）

## 背景

[docs/caching.md](../caching.md)の整備にあたり本番のディスク保持を実測したところ、
`tile_persistent_cache`（タイル材料・スコア行列のpickle）に**参照されない世代が
積み上がっていた**。

本番VM `/home/ubuntu/ridecompass-cache-data/tile_persistent_cache`（2026-09-07 20時JST）:

| namespace/世代 | サイズ | 最終書き込み | 現行コードから参照されるか |
|---|---|---|---|
| `materials/v2` | 119MB | 09-04 09:08 | されない |
| `materials/v3` | 178MB | 09-04 10:06 | されない |
| `materials/v4` | 398MB | 09-05 08:31 | されない |
| `materials/v5` | 存在しない | — | 参照先（現行世代） |
| `score_matrix/v5` | 8KB | 09-06 20:00 | される |

ディスク保持の合計791MB（他に`msm` 87MB・`tile_cache` 11MB）のうち、**695MBが
現行コードから読まれない実体**である。3日でこの量が積み上がっており、放置すると
デプロイ（＝世代を上げる変更）のたびに増え続ける。

世代番号による無効化は「参照先が切り替わる」ことは保証するが、**ディスクでは古い実体が
消えない**。TTLを持つ層（Redis・TTLCache）ではこの問題が起きないため、ディスクへ世代番号を
持ち込んだ時点で削除手段が必要だったが、用意されていなかった。

`tile_persistent_cache.clear_namespace(namespace)`は存在するが、namespace全体（＝現行世代
も含む）を消すため世代交代には使えず、呼び出し元も`refresh_derived`等の限られた経路のみ。

## 対応方針（着手時に確定）

案A（推奨・安価）: 起動時またはディスク書き込み時に、**現行世代以外のディレクトリを削除**する。
`tile_persistent_cache`へ「このnamespaceで有効な世代は1つだけ」という前提を持たせ、
`set`の初回呼び出し時などに旧世代を掃除する。すぐ効き、実装も小さい。

案B（**却下**）: Redisへ寄せる。読み出し速度・RAM占有の両面で不利であることを本番で
実測した（[docs/caching.md](../caching.md)「速度は判断材料にならない」）。

| 経路 | 中央値（14MBのpickle） |
|---|---|
| ディスク read（ページキャッシュ命中） | 2.0 ms |
| Redis GET（localhost） | 18.9 ms |
| ディスク read（cold） | 26.3 ms |
| unpickle（両経路で共通） | 263.1 ms |

Redisは読み出しが遅いうえ、400MB規模を11GBのVM（PostgreSQLと同居）のRAMへ恒久的に
載せることになる。`maxmemory-policy`が`volatile-lru`のため、TTLを付けないキーは退避対象に
すらならず、上限到達時は書き込みエラーになる。**置き場所としてはディスクが正しく、
欠けているのは掃除だけ**である。案Aで進める。

**副次的な発見**: 読み出しの支配項はI/Oではなくunpickle（263ms）だった。ディスク永続化の
効果を上げたいなら、保持層ではなくシリアライズ形式の見直しが効く（本タスクの範囲外。
必要なら別途起票する）。

## 補足（要確認）

`materials/v5`の実体が0件である点は、**世代を上げた後に本番でタイル材料の再構築が
一度も起きていない**ことを示す（`set_tile_materials`は無条件に書くため、書かれていない＝
呼ばれていない）。世代を上げるたびに398MB規模の再充填が必要になる運用が妥当かどうかも、
着手時に併せて確認する（[T538](T538.md)で永続化を入れた目的＝デプロイ後のコールド
レイテンシ回避が、世代を上げた直後には効いていないことになる）。

## 完了条件

- 世代を上げた後、旧世代のディレクトリがディスクに残らないこと
- 現行世代の読み書きが従来どおり動くこと（`tile_persistent_cache`のテスト）

## 実装（案Aを採用）

- `tile_persistent_cache.prune_stale_generations(namespace, keep_version)`を追加。
  namespace配下の`v{keep_version}`以外のディレクトリを削除し、解放バイト数を返す
- 利用側（`graph_material_cache`・`tile_score_matrix_cache`）が自分の現行世代定数を
  渡す薄い入口`prune_stale_disk_generations()`を持つ。世代定数の所有者が掃除の
  責任も持つ形にした
- `main.py`のlifespanでAPSchedulerへ一度きりのジョブとして登録し、**起動直後に1回**
  実行する（世代を上げたコードがデプロイされた直後がこのタイミング）。数百MB規模の
  削除になりうるため`asyncio.to_thread`でイベントループを塞がない。解放量はINFOで記録する
- 失敗しても起動は続行する（掃除はディスク容量の問題であって機能要件ではない）
