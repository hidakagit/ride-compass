# T900. backendのCIが、同じコードでも通ったり落ちたりする

規模M。
状態: 未着手（2026-09-16起票。統合レビュー第10回の起票分を実施している最中に観測）

## 背景

masterの`CI`ワークフローの`backend`ジョブ（`python -m pytest -q -n auto --dist loadgroup`）が、
**同じコードでも通ったり落ちたりする**。2026-09-16に連続して積んだコミット列で観測した範囲:

| コミット | backendジョブ |
|---|---|
| `05c96456`（T886後始末） | 失敗 |
| `a9bf19d2`（レビュー結果の記録のみ。**backendのコードを1行も変えていない**） | 失敗 |
| `2641fe4e`（T889） | 失敗 |
| `826ec001`・`4d33752a`・`159b3fbd`（T890〜T892） | 成功 |
| `3c538172`（T893。変更は`scripts/`のみでbackendのテストは1件も触っていない） | 失敗 |
| `388cd642`・`bd19edde`（T894・T895） | 成功 |

**backendのコードを変えていないコミットでも落ちている**ため、個々の変更が原因ではない。
手元では`-m "not postgis"` 2,001件・`-m postgis` 280件とも安定して緑で、開発機は
pytest-xdistが使えない（直列実行、`docs/testing.md`「開発機でのbackendテストの回し方」）ため**並列実行に
固有の問題は手元では再現できない**。

## 保留することで何が起きうるか

**「CIが通ったこと」を完了の根拠にできなくなる。** 赤が常態になると、本物の赤が埋もれる
——[T834](T834.md)・[T835](T835.md)で実際に2日間気づかれなかった型であり、
`scripts/check_master_ci.py`はそれを知らせるために作られている。その仕組み自体が
「いつもの赤」で鈍る。

## 調べる順序（未着手）

1. 失敗したジョブのログを読み、落ちているテストが毎回同じかを見る（GitHubのUIから。
   公開APIのログ取得は認証が要る）。
2. 同じなら、そのテストがxdistのどのグループへ割り当てられるか
   （`pytest.mark.xdist_group(name="postgis")`）と、共有資源（テストDB・一時ディレクトリ・
   環境変数）を疑う。`docs/testing.md`の「PostGIS統合テストはファイル単位でエンジン・
   イベントループを共有する」設計と、`-n auto`のワーカー数（CIランナーのコア数）の
   組み合わせが最有力。
3. 毎回違うなら、順序依存（`-p no:randomly`を外した状態での実行順）を疑う。
