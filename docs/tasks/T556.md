# T556: 本番のsplit済み範囲を周回生成の新bbox（目標距離の0.4倍＋マージン）に合わせて拡大する

状態: 完了（2026-09-03。本番Oracle VMへSSH接続可能な環境から着手・同日完了）

## 背景

T531でRoad Graph取得bboxの半径が目標距離の1/3倍から0.4倍（`route_generator.py:
TURNAROUND_RADIUS_RATIO`）へ広がった。東京駅30kmでは半径15.6km（12km＋マージン3.6km）に
なり、本番DBのsplit済み範囲（[T539](T539.md)のバッチが対象にした`road_graph_tiles`登録済み
1,020タイル、関東7都県全域には未到達）を超えて`is_split_up_to_date=False`になる
（T531の本番計測はこのため25km[旧30kmと同じbbox半径13km]で実施した）。

未split範囲を含むbboxへの初回リクエストは`get_or_build_graph_with_attributes`の再構築
（closure取得＋`build_road_graph`＋`save_graph`＋materials一括取得、T522本番実測で45秒超）へ
入る。旧方式では同じ起点・距離で収まっていたbboxが新方式では収まらないケースがあり、
利用者から見ると「30km指定が急に遅くなる」退行になりうる。T531の完了条件のうち
「本番同等条件（東京駅30km）での計測」もこの範囲拡大が済むまで実施できない。

## 対応方針

1. **実態把握**: 本番DBで`road_graph_tiles`の登録範囲（z12タイルの外接範囲）と、主要な起点
   （東京駅・王子・横浜等、`docs/tasks/T522.md`・T536で使った計測地点）に対する30km・50km・
   100km（`MAX_ROUTE_DISTANCE_KM`）のbboxがどこまで収まるかを照会し、不足タイル数を見積もる
   （`backend/app/batch/presplit_road_graph.py`は登録済みタイルのみ対象のため、未登録タイルは
   登録から必要）。
2. **範囲拡大**: 関東本土7都県の取込範囲（`osm_raw_ways`が存在する範囲）に対応するz12タイルを
   `road_graph_tiles`へ登録し、`presplit_road_graph.py`を本番で再実行する（T539は532タイル
   再構築で601.9秒。全域では所要時間・DBサイズの見積りを先に出し、深夜帯等の実行時間を決める）。
   本番DBへの書き込みを伴うため、[docs/deployment-sync.md](../deployment-sync.md)の完了条件に
   従い、実行前後のsplit済み率・`road_graph_tiles`件数を記録する。
3. **暫定策の要否判断**: 2の完了まで時間がかかる場合、`TURNAROUND_RADIUS_RATIO`を一時的に
   1/3へ戻して旧方式と同じbboxに収める選択肢がある（折返し候補の到達範囲が狭まる代わりに
   退行を防ぐ）。1の見積りで「主要地点の30kmが未split」と分かった時点で判断する。
4. **T531の未完了計測**: 2の完了後、`benchmarks/bench_t531_route_generation.py`で東京駅30kmを
   本番使い捨てコンテナから計測し、[T531](T531.md)の検証結果へ追記する。

## 調査メモ（2026-09-03、本セッション。本番DB操作は未実施）

`road_graph_tiles`への登録経路をコード上で確認した。`app/batch/presplit_road_graph.py`は
**既に`road_graph_tiles`にある行だけ**を対象にsplitするバッチであり、新規タイルの登録
自体は行わない（新設ファイルではない）。タイル行を新規に増やす経路は
`app/batch/import_pbf.py: _mark_tiles`（`--bbox`引数で指定した範囲をROAD_GRAPH_TILE_ZOOM
単位へ変換し`INSERT ... ON CONFLICT DO NOTHING`）だけであり、`--bbox`省略時はマークしない
設計（PBFヘッダのbboxは抽出ポリゴンの外接矩形にすぎないため）。つまり対応方針2
「範囲拡大」は、`presplit_road_graph.py`を直接拡張するのではなく、**関東7都県相当の
`--bbox`を指定して`import_pbf.py`を本番で再実行する**（既存`osm_raw_ways`と同じ
PBF抽出ファイルに対して行えば、行データはON CONFLICT UPSERTのため冪等）→その後
`presplit_road_graph.py`を実行、という2段の手順になる。

**本セッションでは実行できない**: `road_graph_tiles`の現況照会（対応方針1「実態把握」）
・`import_pbf.py`/`presplit_road_graph.py`の本番実行（対応方針2）は、いずれも本番
Oracle Cloud VM上のPostgreSQLへの接続を要する。本番DBへは`.github/workflows/
deploy-backend.yml`が使う`secrets.ORACLE_VM_HOST`/`secrets.ORACLE_VM_SSH_KEY`経由の
SSHでのみ到達可能で、このリモートセッション（Claude Code on the web、ネットワークは
プロキシ経由のHTTPSのみ）にはSSH鍵・本番DATABASE_URLのいずれも渡されていない。
`backend/.env.example`・`.env.example`にも本番接続情報は含まれない（意図的に
リポジトリ管理外）。

対応方針1・2は、本番VMへSSHできる環境（過去にT539等を本番実行したセッション、または
ユーザー自身の手元）でのみ実行可能。本タスクは状態を「未着手」のまま残し、実行者へ
上記2段の手順を引き継ぐ。

## 実態把握の結果（2026-09-03、本番VMへSSH接続できる環境から実施、読み取り専用）

上記の懸念（「road_graph_tiles未登録の範囲へ入り再構築が走る」＝新規タイル登録が必要）は
主要地点では発生していなかった。`road_graph_tiles`登録済み1,020タイルは経度138.34〜140.98・
緯度34.81〜37.23（関東主要部）を完全に矩形で埋めており、東京駅・王子・新宿・門前仲町の
30km/50km/100km bbox（半径15.6/26.0/52.0km）はいずれも必要タイル数（25/64/196件）が
全件登録済みだった。`is_split_up_to_date`判定の元になる`osm_raw_ways.split_at`の鮮度を
`geom &&`（bboxオーバーラップ、`_primary_way_conditions`未適用の概算）で確認したところ、
東京駅・王子・新宿・門前仲町の30km bboxはいずれも**stale_ways=0**（完全split済み）。
横浜（30km bbox、82,958way中）のみstale_ways=1,908件が残っていた。全域では
`osm_raw_ways`1,329,632件中stale_ways=183,527件（split済み86.2%、[T539](T539.md)完了直後の
84%からわずかに向上——通常のルート生成リクエスト経由の`GraphService`再構築パスで
自然に進行したと推測）。

**対応方針の実態に合わせた修正**: 「範囲拡大」（`import_pbf.py --bbox`での新規タイル登録）
は不要と判明。必要だったのは「既存登録範囲内の残りタイルのsplit」であり、
[T539](T539.md)と同じ`presplit_road_graph.py`の再実行で対応した。

## 対応実施記録（2026-09-03、本番Oracle VM）

- `presplit_road_graph.py`（dry-runなし）を本番で実行: `rebuilt=66 skipped=954
  （既にsplit済み） elapsed=117.1s`。全1,020タイルを走査。
- 実行後の再照会: `osm_raw_ways`全体のsplit済み率が86.2%→**95.8%**（stale_ways
  183,527件→55,895件）。横浜30km bboxのstale_waysは1,908件→**0件**。
- 東京駅30km bbox（半径15.6km）は`benchmarks/bench_t531_route_generation.py`実行時の
  ログで`is_split_up_to_date=True`と直接確認（[T531.md](T531.md)「東京駅30kmの本番計測」
  節に実測値を追記）。
- 全域の残stale_ways 55,895件は、`road_graph_tiles`登録範囲の縁（周辺部、`osm_raw_ways`が
  存在するが利用頻度が低くまだ`GraphService`経由でも`presplit_road_graph.py`経由でも
  splitされていない領域）に分布していると見られるが、本タスクの完了条件（主要起点の
  30km bboxがsplit済みになること）には影響しないため詳細な内訳調査は行っていない。
