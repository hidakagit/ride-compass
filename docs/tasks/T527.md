# T527: axis_difficulties型キャスト・useAxisCatalog複数インスタンスの型安全性調査

状態: 未着手（2026-09-01起票、T524見送り分の追跡）

- 背景: T524（T518コードレビュー対応）で、Confidence Lowのまま見送った2件の
  型安全性・データ整合性リスク。
  1. **`RouteCandidate.axis_difficulties`の型キャストが実際のAPIスキーマの任意性を
     握りつぶしている**（pre-existing、T518が新規に持ち込んだものではない）:
     `frontend/src/types/route.ts:40`の`RouteCandidate`型は
     `Omit<Required<Schemas["RouteCandidate"]>, "geometry" | "segments" |
     "score_breakdown">`で`axis_difficulties`を必須扱いにしているが、生成済み
     OpenAPI型（`frontend/src/types/generated/*.ts:1328,1491`）では
     `axis_difficulties?:`と任意になっている。`RouteAxisProfile.tsx`の
     `axes.filter((axis) => axisDifficulties[axis.axisId] != null)`は
     `axisDifficulties`自体が`undefined`であるケースを想定しておらず、backendが
     このフィールドを省略したレスポンスを返すことが実際に起きれば、候補を選択した
     瞬間にページ全体がクラッシュする。T518以前は「全体プロファイル」タブを
     開くという明示的な操作をしないと到達しなかったが、T518後は`selectedCandidate`
     設定と同時に自動描画されるため到達条件が広がった。
  2. **`useAxisCatalog()`の別インスタンス間で軸配列が食い違うと、2パネルの色ドットが
     不一致になりうる**: `page.tsx`と`RouteSettingsPanel.tsx`は、それぞれ独立に
     `useAxisCatalog()`を呼んでいる（共有ストアではなくコンポーネントごとの
     `useState`）。フェッチタイミング・失敗時のフォールバック
     （`PREFERENCE_AXES`静的リスト）が2箇所で食い違うと、`axisCatalog.axes.length`
     も食い違い、`stackBarColorForIndex(index, length)`の結果が2パネルでズレる
     （モバイルのBottomSheetでRouteSettingsPanelが再マウントされ、その再フェッチ
     だけが失敗/タイミングがズレる、というかなり狭いレースコンディション）。
- 見送った理由: いずれもレビュー時点でConfidence Low（1が実際にbackendで起こり
  うるかは未検証、2は発生頻度が低いレースコンディション）。まず実際に起こりうる
  条件かどうかの調査から始める必要があり、T524のスコープでは着手しなかった。
- 対応方針: (1) backend側が`axis_difficulties`を実際に省略するケースがあるか
  （`domain/route.py: RouteCandidate`のdocstring・生成経路を確認）調査し、
  あり得るなら`RouteAxisProfile`側で`axisDifficulties ?? {}`等の防御を入れるか、
  型キャスト自体を見直す。(2) `useAxisCatalog`を共有ストア化する（複数コンポーネント
  間でフェッチ結果を1つに統一する）か、少なくとも軸id→色のマッピングを1箇所
  （例えば`useAxisCatalog`の返り値自体）へ集約し、`stackBarColorForIndex`の
  直接呼び出しを分散させないようにする。
