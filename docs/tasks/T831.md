# T831. 段階の体感ラベルが、ルート後の凡例では使われない

規模S。
状態: 完了（2026-09-14。[T809](T809.md)完了時に分離）

## 背景

`display_band_labels_override`（「市街地」「住宅地」…のような段階ごとの体感ラベル）は、
ルート前の専用way値レイヤーの凡例（`dedicatedWayValueLegend`）だけが使い、ルート後のルート線
凡例（`routeStyleModes.ts: buildRangeSteppedMode`）は数値レンジしか出さない。同じレンズを
選んでいるのに、ルートを生成すると凡例の言葉が消えて数字だけになる。

ラベルを持つ軸は実際にある（風・開放度・停止密度）。とくに開放度の`22.5〜41.7`のような
写像後の数字（[T809](T809.md)）は、それ単体では何を指すのか読めない——ラベルが要る側の代表例。

## 対応方針

`dedicatedWayValueLegend`と同じ扱いにする。要素数が段階数と一致する間だけ数値レンジの前へ
添える防御も揃える——[T809](T809.md)の写像は折れ線が飽和する範囲で段階を畳むため、
**ラベルの件数と段階数が食い違う軸が実在する**（停止密度は5ラベル・4段階）。どちらを正とするか
（ラベルを畳む／ラベルを捨てて数値だけにする／軸の折れ線を較正し直す）はこのタスクで決める。

## 決定と実装（2026-09-14）

**ラベルは出す。件数が段階数と合わない軸は出さない**（畳んでずらす案・軸の較正案は採らない）。

ずらして添えると嘘になる。停止密度の最上位の段階は写像後「7回/km以上すべて」を指すのに、
ラベルを1つずらして詰めると「83m以下で1回停止」（＝12回/km以上）と表示される——実際には
143m以下すべてを含む。**数値レンジだけの方が読み手を誤らせない**。較正で飽和そのものを
解くのが筋だが、それは実データの分布を見て決めることなので[T833](T833.md)へ分離した。

- 判定を`mapColorLegend.ts: bandLabelsForBandCount`へ出し、ルート前
  （`dedicatedWayValueLegend`）とルート後（`routeStyleModes.ts: buildRangeSteppedMode`）が
  同じ関数を使う。ルート前にあった同じ規則のインライン判定はこれへ置き換えた（同じ規則を
  2箇所へ書き写さない）。
- 凡例の表記もルート前と揃えた（`ラベル（数値レンジ）`）。

## 検証

**ラベルが出ない軸を軸idで名指しせず、「写像で畳まれたか」という性質で固定した**
（較正で飽和が解ければ、その軸はラベルが出る側へ自動的に移り、テストはそのまま通る）。

両方向でわざと壊して落ちることを確認した:

| 壊し方 | 結果 |
|---|---|
| ラベルを常に添えない（修正前の挙動） | 2件落ちる（性質のテスト・表記のテスト） |
| 件数を確かめずに添える（嘘表示になる側） | 1件落ちる（`axis_abdaded0be20（畳まれた=true）: expected true to be false`） |

実測（公開軸のうち体感ラベルを持つもの）: 風・開放度はラベル5件＝段階5で一致しラベルが出る。
停止密度はラベル5件・段階4で不一致のため数値のみ（[T833](T833.md)）。

テスト: frontend 1309件緑、`tsc --noEmit`・`eslint`とも新規の指摘なし
（`layout.tsx`の`LayoutProps`・`ComparisonPanel.test.tsx`の未使用importは未変更ファイルの既存分）。
