# T848. タイルへ焼き込む世代だけ、いまも手で上げる運用が残っている

規模M。
状態: 着手中（2026-09-18。A案［実行時に配る］で実装［ユーザー判断］）

## 背景

T847で材料キャッシュの世代はDBが正になり、バッチを回せば手作業なしで追随するようになった。
一方`cache_identity.py`の`ROAD_SURFACE_REVISION`・`POI_REVISION`・`ACCIDENT_REVISION`
（タイルへ焼き込む側）は手で上げる運用のまま残っている。上げ忘れると、既に配信済みの
タイルが古い値のまま返り続ける——材料側で直したのと同じ形の欠陥が、配信側に残っている。

単純にDBへ移せない理由がある。これらの世代は生成物`region-tile-config.json`を通じて
フロントへ配られるため、実行時に変えるとフロントが知っている世代とずれる。解くには
「配信側の世代をどうフロントへ伝えるか」から決める必要がある。

## 実際に踏んだ形（2026-09-18、[T919](T919.md)）

上げ忘れだけが問題ではないと分かった。**手で上げる操作が1回ではなく2回要る**うえ、
2回目のほうが気づきにくい。

T919は(1)タイルSQLを変え、(2)本番へデプロイし、(3)precomputeバッチで本番DBの中身を
作った。(1)は形の署名が自動で捕まえるので世代が変わる。ところが(2)と(3)のあいだに配信された
タイルは、**新しい世代の鍵のまま古い（way単位の）値で焼かれてキャッシュへ載る**。世代は
もう変わらないので、行が入っても自動では直らない。直すには(3)の完了後に`ROAD_SURFACE_
REVISION`をもう一度手で上げるしかなく、この2回目は`cache_identity.py`のコメントにも
書かれていない（「precomputeバッチのときに上げる」とは書いてあるが、**バッチの完了後**とは
書いていない）。

デプロイとバッチの順序を入れ替えても解けない。バッチを先に流すと、まだ古いSQLを持つ
本番が新しいテーブルを読まないまま走り続けるだけである。

## 解き口: 実行時に配る経路は既にある

起票時に挙げた「実行時に変えるとフロントが知っている世代とずれる」は、**同種の値で既に
解かれている**。較正値（`domain/tuning.py`）は管理画面から変わる値で、生成物ではなく
軸カタログAPIの応答（`api/routers/axis_catalog.py`の`client_tuning`）に載せて実行時に
配っている。タイル世代を同じ経路へ載せ、値そのものはT847がDBへ移した世代
（`derived_data_meta.revision`）から導けば、手で書き換える定数は消える。

### 残る設計上の問い

**初回描画までのあいだ、どの世代を使うか。** 生成物の値をフォールバックに残すと、実行時の
値が届かない不具合がフォールバックに隠れて長く気づかれない（このプロジェクトで既に起きた
失敗の形）。カタログの応答を待って地図のソースを作る、あるいはURLから世代を外して
ETag/Cache-Controlで再検証させる、のどちらへ倒すかが本題になる。後者は配信のキャッシュ
寿命を長く取れている理由そのもの（URLに世代が入っていること）を崩すため、影響を測ってから
決める。

## 実装（A案、2026-09-18にユーザー判断）

タイル世代を**実行時に配る**。値は手で書く定数をやめ、T847がDBへ移した世代
（`derived_data_meta.revision`）と、既にある形の署名（`cache_identity.py`）から組み立てる。
配る経路は較正値が既に使っている軸カタログの応答へ相乗りさせる（起動時に1回取るものに
乗せ、取得を増やさない）。往復の実測は0.05〜0.18秒（本番backend、`/api/axis-catalog`、
16.8KB。TLS確立を含む初回が0.179秒、以降0.053〜0.063秒）。

**フロントは応答を待ってからタイルのソースを作る**。生成物の値をフォールバックに残すと、
実行時の値が届かない不具合がフォールバックに隠れて長く気づかれない。

### 読んで分かった追加の前提（起票時に見えていなかった）

**ディスクキャッシュの経路に世代が入っている**（`region_service.py: _tile_cache_path`が
`region/road-surface/v{世代}/{z}/{x}/{y}.pbf`）。世代を実行時の値にすると、世代が変わる
たびに別のディレクトリ木ができ、古い実体が残り続ける（docs/caching.md「世代番号を使うなら
旧世代を削除する導線をセットで用意する」）。

材料キャッシュ側には同じ問題に対する前例がある
（`graph_material_cache.sync_disk_cache_with_derived_data_revision`が、世代が変わったときに
ディスクの記録と突き合わせて捨てる）。タイル側も同じ形で、世代が変わったら古い世代の
ディレクトリを消す導線を同じコミットへ含める。

### 完了条件

- `ROAD_SURFACE_REVISION`・`POI_REVISION`・`ACCIDENT_REVISION`（手で上げる定数）の撤去
- 世代を実行時に組み立て、軸カタログの応答で配る
- フロントは応答を待ってタイルのソースを作る（生成物へフォールバックしない）
- 世代が変わったらディスクの旧世代を消す
- **バッチを回すだけで、手で何も触らずタイルが更新されることを確認する**（わざと古い世代の
  タイルを残した状態から）
