# T922: 軸スタジオで段階を設計できるようにする（しきい値のまとめ入力とプレビュー）

状態: 完了（2026-09-17起票・同日完了）

## 背景

地図の色分けしきい値の編集UIは「+ しきい値を追加」で境界値を1件ずつ増やす形しか無く、
段階数が増えるほど операция が手作業になる（勾配を1%刻み13件へ変えるだけで、追加ボタン9回と
個別入力13回）。結果としてAPIを直接叩く方が速くなり、**軸スタジオを通さない変更が常態化する**
——GUIが正規の入口である前提（[T361](T361.md)・CLAUDE.md「コミット時の同期ルール」）が
実運用で崩れる。

もう1つ、編集中に**結果を確かめる手段が無い**。段階数・各段階のレンジ・地図で塗られる色は
保存してアプリを開くまで分からず、「細かくしすぎて隣の色が見分けられない」ことも
その場では気づけない。

## 対応方針

[decisions/axis-definition-maintenance-split.md](../decisions/axis-definition-maintenance-split.md)
で分担を先に決めた（読むこと・試すことはGUI、決めたものを配ることはスクリプト）。本タスクは
そのうちGUI側——**試した結果がその場で見えること**——だけを扱う。確定値の反映は
[T923](T923.md)のスクリプトが持つ。

- 境界値は1つの欄へまとめて入力する（区切りは問わない）。**入力体験をこれ以上作り込むことは
  しない**——値を並べて打つ作業はエディタとスクリプトの方が速く、記録も残る。ここで必要なのは
  「試しに動かせる」最小限。
- 入力した段階が**その場で見える**ようにする。段階数・各段階のレンジ・地図で塗られる色を、
  地図の凡例と同じ関数（`mapColorLegend.ts: buildRangeLegendBands`・`valueScale.ts:
  bandColorsFor`）で描く。軸スタジオ側は「その軸がどちらの経路で地図に出るか」の判定を
  持たず、軸カタログの実際の分類を親が引いて渡す。

## 検証結果

- `npx vitest run`（フロントエンド全体）パス。`npx tsc --noEmit`・`npx eslint src`ともに
  新規の指摘なし。
- ローカル（`next dev`、テスト用の管理者資格情報）で新規軸の作成画面を開き、境界値13件を
  1回の貼り付けで入れて「14段階になります」とレンジ一覧が出ることを実機で確認した。
  地図に出る経路がまだ無い軸のため色は付かず、その旨の注記が出ることも確認した。
- わざと壊して検知できることを確認: 昇順・重複の検査を外すと2件が落ちる
  （`axisDraft.thresholds.test.ts`・`AxisComposer.test.tsx`）。
