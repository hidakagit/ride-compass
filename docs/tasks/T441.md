# T441. ルート候補0件の原因をGUI（デバッグログ）まで届ける+debugLogの重大度監査 規模M

状態: 完了（2026-08-30）

## 背景

ユーザーが本番（Oracle Cloud VM）で30km周回ルート生成を試み、最終的に候補0件で失敗した
インシデントの調査から着手。原因はバックエンドの`RouteGenerator`が`logger.warning`で
既に記録していた（`prepare()`がNoneを返した「道路データ未整備」、または全方位が経路探索
失敗/距離フィルタで落ちた「候補0件」）が、この情報を確認する手段がSSHでのサーバーログ
閲覧しかなく、GUI（デバッグログ・エラーメッセージ）からは「距離を変えて試してください」
という原因不明の汎用文言しか見えなかった。

調査の過程でユーザーから「ログビューワにWARNINGまで出せる？」「info/warn/errorすべて
出るべきものが出ているか全モジュール確認して」という追加依頼があり、debugLogの重大度
監査も本タスクに含めて実施した。

## 対応内容

### Part A: バックエンド診断理由のGUIへの伝播

- `backend/app/services/route_generator.py`: `RouteGenerator`にインスタンス属性
  `last_no_candidates_reason: str | None`を追加。`generate_loops`/
  `generate_via_waypoints`が候補0件で`return []`する各分岐（`prepare()`がNone・
  全方位trace失敗・全方位距離フィルタ落ち・経由地ルートのtrace失敗）で、既存の
  `logger.warning`と同じ情報源から人間可読な理由文字列を組み立てて設定する
  （`_describe_no_traced_reason`ヘルパー新設）。インスタンスは
  `api/dependencies.py: _build_route_generation_setup`がリクエストごとに新規生成する
  ため、インスタンス属性のまま並行リクエスト間で競合しない（関数シグネチャを
  `list[RouteCandidate]`のまま変えずに済み、既存の呼び出し元・テスト45件超への
  破壊的変更を避けられる）。
- `backend/app/api/routers/routes.py`: `RouteGenerateResponse`へ
  `no_candidates_reason: str | None = None`を追加。`_run_generate_job`が
  `candidates`が空のときだけ`setup.generator.last_no_candidates_reason`を転記する。
- OpenAPI/frontend型生成物を同期（`export_openapi.py`→`npm run generate:api`）。
  **注意**: 同時に`axis-catalog.json`にT440由来の軸データドリフト
  （`supports_route_coloring`・`display_thresholds_override`・
  `dedicated_way_value_layer`が、fresh bootstrap時の`axis_definitions_snapshot.json`
  スナップショットの内容へ巻き戻る形の差分）が生成されたが、これは本タスクと無関係な
  既知の問題（CLAUDE.md記載のT353/T360と同型、スナップショットの手動リフレッシュ漏れ）
  のため`git checkout`で除外し、本タスクの差分（`api.d.ts`・`openapi.json`の
  `no_candidates_reason`追加のみ）だけをコミットした。スナップショットの再ダンプは
  別タスクとして扱う（本タスクでは未対応）。
- `frontend/src/services/routeApi.ts`: `GenerateRoutesResult`へ`noCandidatesReason?: string`
  を追加。`generateRoutes`が`routes.length === 0 && no_candidates_reason`のとき
  `debugLog("api:route", reason, {jobId}, "warn")`で記録した上で、呼び出し元へ
  `noCandidatesReason`を返す。
- `frontend/src/app/page.tsx`: `handleGenerate`が候補0件のとき、
  `noCandidatesReason ?? 従来の汎用文言`をエラーメッセージとして表示する。

### Part B: debugLogの重大度（info/warn/error）監査

ユーザー依頼を受け、`debugLog(...)`の全呼び出し箇所（grepで全件確認）を棚卸しした結果、
`DebugLogLevel`型・`DebugConsole`の`[data-level="warn"]`CSSは元から用意されていたにも
かかわらず、**"warn"レベルが実際には1件も使われていなかった**（"error"16箇所・"info"
[既定値含む]多数、"warn"0件）ことが判明。以下3箇所で重大度が実態と合っておらず修正した:

1. `frontend/src/services/routeApi.ts`（ポーリング失敗時のリトライログ）: リトライで
   回復する可能性が高い一時的な状態（今回のインシデントで実際に次のポーリングで成功した
   実績あり）を"error"にしていた。"warn"へ変更。5回連続失敗し諦める場合は呼び出し元
   （page.tsx）が例外をcatchした時点で別途"error"記録される。
2. `frontend/src/components/Map/MapView.tsx`（`handleMapError`）: スタイル読み込み前の
   致命的エラーと、読み込み後に起きる個別タイル1枚の一過性エラー（パン/ズーム中の
   キャンセル等、次の取得サイクルで自然に解消する）を区別せず一律"error"にしていた。
   `__rcStyleReady`フラグで判定し、致命的な場合のみ"error"、それ以外は"warn"へ変更。
3. `frontend/src/hooks/useDynamicWeatherLayers.ts`（降水ナウキャスト・降水短時間予報・
   雷/竜巻ナウキャスト・キキクル・線状降水帯予測マップの計5箇所）: いずれも
   `window.setInterval`で定期的に自動再取得する設計（1回の失敗は次のサイクルで
   自然に回復しうるフェイルソフト）だが一律"error"にしていた。"warn"へ変更。

上記以外（`fetchJson.ts`・`regionApi.ts`・`axisAdminApi.ts`の各種HTTP失敗ログ等）は
リトライ機構を持たない一発勝負の失敗のため、"error"のままが適切と判断し変更していない。
バックエンド側（docs/logging.md方針: エラー・429拒否・候補0件はWARNING以上）は
`route_generator.py`の`logger.warning`・`debug_log.py: record_rate_limit_rejection`
（`_throttled_warning`）で既に満たされていることを確認済み（変更不要）。
