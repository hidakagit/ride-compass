# T632. 応答のHTTPキャッシュヘッダを一元管理する仕組みと全エンドポイントへの適用

規模M（起票時は「JMAタイルプロキシへの付与」規模Sだったが、点検で欠落が全体に及ぶと
判明し、対応表による汎用機構の新設まで広げた）。

## 背景

ユーザー報告「天候系、災害系のレイヤは、表示するのに非常に時間がかかる」「特に災害系は
表示非表示の境界となる拡大率zを跨ぐ時に大量の情報取得が走る」の調査で、
`GET /api/jma-tile/{path}`（`api/routers/jma_tile.py`）が`Cache-Control`・`ETag`・
`Last-Modified`のいずれも返していないことが判明した。同じタイル配信でも
`api/routers/region.py`・`api/routers/accidents.py`は`Cache-Control: public, max-age=3600`
を付けている。

本番（Oracle VM、`nginx/1.30.4`）への実測レスポンス:

```
HTTP/2 200
server: nginx/1.30.4
content-type: image/png
content-length: 535
x-request-id: e75ea8882742
alt-svc: h3=":443"; ma=86400
```

キャッシュ関連ヘッダが1つも無いため、ブラウザはこの応答をキャッシュ不可として扱う。
JMAタイルのURLは`basetime`/`validtime`を含み**内容が確定して以後変化しない**にもかかわらず、
MapLibreがタイルを再要求するたび（ズームレベルの跨ぎ・パンで画面外へ出て戻る・
`setTiles`によるソース更新でMapLibre内部キャッシュが破棄される）に毎回ネットワーク往復が
発生していた。

実測レイテンシ（1枚あたり、535バイトのPNG）:

| 経路 | 初回 | 接続再利用時 |
|---|---|---|
| backend直接配信（`NEXT_PUBLIC_TILE_BASE_URL`） | 0.172秒 | 0.049秒 |
| Render frontend経由（`targetTimes.json`等の相対パス） | 0.404〜0.521秒 | — |

画面表示中の可視タイルは1レイヤーあたり約40枚（1600×1000px・256pxタイル）、災害チップの
7ソース＋降水・風で**約280リクエスト**が同時に飛ぶ。

## 対応方針

タイル本体・`targetTimes*.json`・404のそれぞれへ、内容の性質に応じた`Cache-Control`を
付ける。

| 対象 | ヘッダ | 理由 |
|---|---|---|
| タイル本体（PNG/PBF） | `public, max-age=1200, immutable` | URLに`basetime`/`validtime`を含むため内容は不変。`max-age`はRedis側TTL（`jma_tile_redis_cache.py: _TTL_SECONDS`=20分）と揃える |
| `targetTimes*.json` | `public, max-age=60` | プロセス内`TTLCache`のTTL（2分）より短くし、新しいフレームの発見が最大1分遅れる程度に抑える |
| 404（`TileNotFound`） | `public, max-age=600` | `basetime`が確定した過去の一時点に対する結果のため再問い合わせしても変わらない（恒久404、[T605](T605.md)と同じ判断） |

`immutable`はURLが変わらない限り再検証を行わせないディレクティブで、リロード時の
条件付きリクエストも抑止する。

スコープはJMAタイルに限らず、**キャッシュヘッダを持たない全エンドポイント**へ広げる
（点検結果は下表）。加えて、各ルーターが応答へ個別に`Cache-Control`を書くと方針が
散らばって一覧できなくなるため、パスとポリシーの対応表を1箇所へ集約する汎用機構
（`api/cache_policy.py`）として実装する。

## 実装メモ

`api/cache_policy.py`（新規）が唯一の情報源:

- `CachePolicy`（`max_age_seconds`・`immutable`・`handler_managed`）と、意味を持つ名前の
  ポリシー定数（`PERMANENT`・`IMMUTABLE_TILE`・`BATCH_TILE`・`BASEMAP`・`CATALOG`・`SHORT`・
  `VOLATILE`・`LIVE`・`NO_STORE`）。時間の調整はこの定義1箇所で行う。
- `_ROUTE_POLICIES`（パス前方一致→ポリシー）と`policy_for_path`（最長一致のため表への
  追記順に依存しない）。
- `CachePolicyMiddleware`（`main.py`へ登録）。2xxにのみ付与し、ハンドラが自分で設定した
  `Cache-Control`には触らない。

ルーター側の個別実装は撤去した（`region.py`・`accidents.py`の`max-age=3600`直書き、
`weather.py`へ一度入れた`_WIND_GRID_CACHE_CONTROL`）。例外は`/api/jma-tile/`のみで、
1つのパスで性質の異なる3種類（タイル本体・時刻一覧・恒久404）を返すため対応表では
`HANDLER_MANAGED`とし、どのポリシーを使うかを`jma_tile.py`が選ぶ（選択肢自体は
`cache_policy.py`が持つ）。`jma_tile_client.py`の`_TARGET_TIMES_PATTERN`判定は
`is_target_times_path`として公開し、クライアントとルーターで同じ判定を共有する。

### 適用結果（全36ルート）

| 区分 | ポリシー | 対象 |
|---|---|---|
| 静的タイル | `PERMANENT`（1日, immutable） | 色別標高図 |
| 気象タイル | `IMMUTABLE_TILE`（20分, immutable） | JMAタイル本体 |
| バッチ更新タイル | `BATCH_TILE`（1時間） | 路面・事故・POI |
| 基礎地図 | `BASEMAP`（10分） | OpenFreeMap中継 |
| カタログ | `CATALOG`（1時間） | 材料カタログ・材料値一覧 |
| 短命 | `SHORT`（5分） | 風グリッド・材料タイル・`/api/weather` |
| 警戒情報 | `VOLATILE`（2分） | 警報・WBGT・洪水予報・アメダス |
| 即時反映 | `LIVE`（1分） | 軸カタログ（軸スタジオの公開操作が即座に効く必要がある） |
| 禁止 | `NO_STORE` | ルート生成・進捗・管理API・`/health`・デバッグ |

基礎地図を10分にした理由は、`POST /api/basemap/refresh`（「変わらないデータを更新」
ボタン）がサーバー側のファイルキャッシュしか消せず利用者のブラウザ保持分へ手が届かない
ため——この`max-age`がそのままボタンの効果が現れるまでの最大の遅れになる。URLへ版数を
付けて即時破棄する案も検討したが、押す頻度の低さに対して仕組みが重いと判断した。

## 検証結果

`pytest tests/test_cache_policy.py tests/test_jma_tile_routes.py tests/test_weather_route.py
tests/test_region_routes.py` 75件パス。`tests/test_cache_policy.py`は全`APIRoute`と対応表を
突き合わせ、**表に無いルート（ポリシーの決め忘れ）**と**どの実ルートにも一致しないエントリ
（リファクタで残った死んだエントリ）**の両方を機械的に検出する（後者は実際に
`/api/axis-definitions`という死んだエントリを1件検出した）。

本番反映後の実測（`curl -D -`、Oracle VM上のnginx）:

| エンドポイント | 実測した`Cache-Control` |
|---|---|
| JMAタイル本体 | `public, max-age=1200, immutable` |
| JMA時刻一覧 | `public, max-age=60` |
| 基礎地図スタイル | `public, max-age=600` |
| 軸カタログ | `public, max-age=60` |
| 材料カタログ | `public, max-age=3600` |
| 警報 | `public, max-age=120` |
| `/health` | `no-store` |

404応答（色別標高図の整備区域外）にヘッダが付かないことも確認した（2xxのみへ付与する
ミドルウェアの仕様どおり。JMAタイルの恒久404はハンドラ側が明示するため付く）。
