# T632. JMAタイルプロキシのレスポンスへHTTPキャッシュヘッダを付与する

規模S。

## 背景

ユーザー報告「天候系、災害系のレイヤは、表示するのに非常に時間がかかる」「特に災害系は
表示非表示の境界となる拡大率zを跨ぐ時に大量の情報取得が走る」の調査で、
`GET /api/jma-tile/{path}`（`api/routers/jma_tile.py`）が`Cache-Control`・`ETag`・
`Last-Modified`のいずれも返していないことが判明した。同じタイル配信でも
`api/routers/region.py`・`api/routers/accidents.py`は`Cache-Control: public, max-age=3600`
を付けている。

本番（Oracle VM、`nginx/1.30.4`）への実測レスポンス:

```
HTTP/2 200
server: nginx/1.30.4
content-type: image/png
content-length: 535
x-request-id: e75ea8882742
alt-svc: h3=":443"; ma=86400
```

キャッシュ関連ヘッダが1つも無いため、ブラウザはこの応答をキャッシュ不可として扱う。
JMAタイルのURLは`basetime`/`validtime`を含み**内容が確定して以後変化しない**にもかかわらず、
MapLibreがタイルを再要求するたび（ズームレベルの跨ぎ・パンで画面外へ出て戻る・
`setTiles`によるソース更新でMapLibre内部キャッシュが破棄される）に毎回ネットワーク往復が
発生していた。

実測レイテンシ（1枚あたり、535バイトのPNG）:

| 経路 | 初回 | 接続再利用時 |
|---|---|---|
| backend直接配信（`NEXT_PUBLIC_TILE_BASE_URL`） | 0.172秒 | 0.049秒 |
| Render frontend経由（`targetTimes.json`等の相対パス） | 0.404〜0.521秒 | — |

画面表示中の可視タイルは1レイヤーあたり約40枚（1600×1000px・256pxタイル）、災害チップの
7ソース＋降水・風で**約280リクエスト**が同時に飛ぶ。

## 対応方針

タイル本体・`targetTimes*.json`・404のそれぞれへ、内容の性質に応じた`Cache-Control`を
付ける。

| 対象 | ヘッダ | 理由 |
|---|---|---|
| タイル本体（PNG/PBF） | `public, max-age=1200, immutable` | URLに`basetime`/`validtime`を含むため内容は不変。`max-age`はRedis側TTL（`jma_tile_redis_cache.py: _TTL_SECONDS`=20分）と揃える |
| `targetTimes*.json` | `public, max-age=60` | プロセス内`TTLCache`のTTL（2分）より短くし、新しいフレームの発見が最大1分遅れる程度に抑える |
| 404（`TileNotFound`） | `public, max-age=600` | `basetime`が確定した過去の一時点に対する結果のため再問い合わせしても変わらない（恒久404、[T605](T605.md)と同じ判断） |

`immutable`はURLが変わらない限り再検証を行わせないディレクティブで、リロード時の
条件付きリクエストも抑止する。
