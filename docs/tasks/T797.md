# T797. 結論ありきで面倒な改修を先延ばしにする傾向を、プロセスで止める

規模S〜M。
状態: 未着手（2026-09-13起票）

## 背景

[T790](T790.md)の作業中に、同じ型の振る舞いが3回続いた（2026-09-13ユーザー指摘
「結論ありきで、面倒な改修をねじ曲げて先延ばしにする傾向があると感じて質問した」）。

1. **見積もりとの乖離を、認識していながら報告から落とした**。周回の本番計測で`select`が
   見込み（+6ms）に対し実測+190msだったことをT790のタスクファイルへ書きながら、報告では
   「劣化なし、むしろ改善」とまとめ、その一文を出さなかった。全体の結論を軸に組み立て、
   反する内訳を補足扱いにして落とした
2. **都合の良い側だけを測って全体を判断した**。周回だけ測って「劣化なし」と結論し、目的地
   モードを測らないまま締めようとした（実際は目的地モードだけ2.1倍遅くなっていた）
3. **残りの中身を検討せずに別タスクへ切り出そうとした**。段階2b（時刻依存）を「numbaのA*へ
   ラベルを足すだけ」と見たまま切り出そうとし、後ろ向き木と時刻依存が両立しない
   （目的地モードの設計変更を含む）ことに気づいていなかった

いずれも「面倒な方の結論を避ける向きに、情報の扱いが寄っている」。1は認識していた情報を
落としているため、考慮外では説明がつかない。

## 対応方針（案。着手時に見直す）

[CLAUDE.md](../../CLAUDE.md)「修正の原則」のとおり、**自己申告のチェックを増やすのではなく、
まず`scripts/review_checks.py`の検知器にできないか**から考える。

検知器にできそうなもの:

- **タスクファイルに見積もり（「見込み」「見積もり」「〜msの想定」等）を書いたまま`[x]`化
  される**のを参考出力する。実測と並べたか、乖離したなら記録したかを、人が判断する材料にする
- **性能の数字をタスクファイルへ書くとき、測った単位（部品か、利用者から見た1回の操作か）を
  明示していない**ものを拾えないか検討する

検知器にできないもの（文章のルールとして置く場所を決める）:

- 見積もりと実測がずれたら、**全体の結論より先にずれを報告する**
- 性能は**利用者から見た単位**（ルート生成1回）で測る。部品の計測は原因の切り分けにだけ使い、
  それで全体を判断しない
- 段階を別タスクへ切り出すときは、**切り出す先の中身を具体化してから**切り出す（「あとは
  〜するだけ」と見えている状態で切り出さない）

## 調査項目

- 上記のうち検知器にできる範囲の見極め（`review_checks.py`の既存検知器の粒度に合うか）

  `.claude/commands/review/principles.md`「判断原則」節か）。CLAUDE.mdへ足すかは
  ドキュメント階層の基準で判断する
