# T875. T865の本番バックフィルを実施し、残りを起票し直す

規模S。
状態: 未着手（2026-09-15起票。統合レビュー第9回のP1）

## 背景

[T865](T865.md)（一方通行レイヤーから上下線の分かれた道の片側を外す）は`[x]`だが、
**本番DBの`way_divided_carriageway`は空のままで、利用者が指摘した症状はそのまま残って
いる**。残タスクも起票されていない。

- `docs/tasks/T865.md:37`が自ら「本番の既存データはバックフィルが要る」と書いているが、
  検証節の実測はすべて開発DB（86,642way、3.6秒）で、本番実行の記録は無い
- MVT側は`COALESCE(wdc.divided, false)`で安全側に倒れるため、テーブルが空の本番では
  **従来どおり全部塗られる**
- タイル世代だけが`25-d271340a28ec → 25-c0385c82cf5b`へ動いているのでキャッシュは
  作り直され、見た目は変わらない
- `- [ ]`行が無いため`/task:next`にも周期レビューにも上がらない

比較対象として、同じ依存を持つ[T654](T654.md)・[T764](T764.md)は`- [ ]`＋残りの明記を
保っている。T865だけが同じ扱いを受けていない。

## 判定条件1（`carriageway`タグ）は次回のPBF再取込まで死んでいる

T865は`carriageway`を`ALLOWED_WAY_TAGS`へ追加し、判定条件1を稼働中のものとして
記述しているが、取込時フィルタ（`osm_adapter.py:91-94`の`_filter_allowed_tags`）である
以上、**この変更より前に取り込まれたDBには当該タグが1件も存在しない**。
T865の「残る限界」節にこの制約は書かれていない。

## 対応方針

1. 本番で`python -m app.batch.precompute_way_divided_carriageway`を実行し、
   一方通行レイヤーに残る延長を実測してこのエントリへ書く
2. 条件2の前置フィルタ（`road_graph_repository.py:1099-1108`）は、条件3が明示的に
   避けた「wayの全体bboxで広げる」形になっている。**この本番実行の機会に所要時間を
   実測する**——開発DBの3.6秒からの単純外挿より悪化する可能性がある（長大な
   trunk/primaryが本番に多いため）。問題が無ければ「wayが短い層にしか効かないので許容」
   という根拠をコメントへ残す
3. 条件1については[T654](T654.md)と同じ形で「トリガー: 次回のPBF再取込」の行を別途立てる
   （現状は条件1が構造的に死んでいることがどこにも書かれていない）
4. T865の「残る限界」節へ上記を追記する

## 完了条件

本番実行後にレイヤーを実機で確認し、指摘の対象だった幹線が一方通行として塗られなく
なっていることを見てから完了扱いにする（開発DBの実測で代替しない）。
