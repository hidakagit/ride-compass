# T515. test_wind_way_service.pyの時刻依存フレーク（JST23時台に毎回失敗）を修正

## 背景

ユーザー報告（2026-08-31、T510のJMAタイルプリウォーム対応作業中に気づいた）:
`pytest -m "not postgis"`実行時に`tests/test_wind_way_service.py::
test_at_none_defaults_to_now_without_raising`が失敗する（単体実行でも再現するとの報告）。
失敗時のログに`WARNING ridecompass.wind_way:wind_way_service.py:143 指定の評価時刻が
配信の実況グリッド範囲外`が出ており、`assert set(result.keys()) == {1}`が
`assert set() == {1}`になっていた。

直近コミット`d94fbd6`（Open-Meteo複数地点応答の位置対応をzipから座標ベースへ変更）が
`weather_client.py`を触っていたため疑われたが、このテストは`WindWayService`を
`FakeWeatherService`（`weather_client.py`を一切呼ばない完全フェイク）越しにテストして
おり無関係と判明。

## 原因

`weather_client.py`側にもproduction (`wind_way_service.py`) 側にもバグはなく、
**テストのフィクスチャ構築ロジックのみ**の問題だった。

修正前のテストは「今日1日分（JST 0〜23時、24件）」の疑似`times`配列を用意し、
`datetime.now(JST)`が必ずその範囲内に収まる前提で書かれていた。しかし
`wind_way_service.py: _nearest_time_index`の範囲外判定は

```python
if target_naive < min(parsed) or target_naive > max(parsed):
    return None
```

という厳密な大小比較で、`times`配列の最後の要素は「23:00ちょうど」という時刻文字列
（時間帯を代表する1点であり23:59:59までの区間ではない）。そのため実行時刻がJSTの
23時台（例: 23:45）だと`23:45 > 23:00`が成立してしまい、`_nearest_time_index`が
`None`を返して`get_way_values`が空dictを返す——`assert set(result.keys()) == {1}`が
必ず失敗する。実際に`23:45`をシミュレートして再現を確認済み
（`datetime(2026,8,31,23,45) > datetime.fromisoformat("2026-08-31T23:00")`は`True`）。

本番環境では`WeatherService.get_wind_grid`が実際にOpen-Meteoから約48時間先まで
（`forecast_days=2`、`wind_grid.py`の`WindGridPoint`docstring参照）取得するため、
「今日の残り時間 + 翌日全体」が常にカバーされておりこの問題は起きない。**テストの
フィクスチャだけが持つ、本番挙動を過度に単純化した近似だった**（本番コードのバグでは
ない）。

## 対応

`tests/test_wind_way_service.py::test_at_none_defaults_to_now_without_raising`の
`wide_times`構築を、「今日1日24時間」から「今日0時〜翌日23時の48時間」へ拡張した
（本番の約48時間先までという実際の応答形状に合わせた）。これにより実行時刻が何時で
あっても`datetime.now(JST)`は必ず`min(wide_times)`〜`max(wide_times)`の範囲内に
収まる。

## 検証結果

- `pytest tests/test_wind_way_service.py -q`: 11 passed（修正前後とも、現在時刻が
  JST 00時台のため修正前でも再現しなかった。`datetime(2026,8,31,23,45)`を使った
  手動シミュレーションで原因を確認）
- `pytest -m "not postgis" -q`: 1217 passed（backend全体、修正前後とも問題なし）

`backend/app/config.py`）には一切触れていない。
