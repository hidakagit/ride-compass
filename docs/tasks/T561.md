# T561: docs/modules記載粒度違反の再発22箇所の是正と、経緯記述の機械検知パターンの拡充

状態: 完了（2026-09-03起票・同日完了。統合レビュー第4回
[history/2026-09-03_all.md](../../.claude/commands/review/history/2026-09-03_all.md) Phase 5 C-2、P1）

## 背景

`docs/modules/README.md`「記載粒度」節が禁止する「改善計画Txxxで…に変更した」型の経緯記述が、
`docs/modules/backend/routing-engine.md`で16箇所・`evaluation-scoring.md`で6箇所、計22箇所
再発している（2026-08-31のT458/T459で全15ファイルを是正した後、T531/T536の反映時に再発）。
Evidence（対象コミット`89c94cd`時点の行番号）: `routing-engine.md:21-23,40,131,150,171,191,
208,215-216,221,336,341,346,351,355,361,363`、`evaluation-scoring.md:67-69,104,108,138,214-217`。

機械検知が効かなかった理由: pre-commitフック`scripts/pre-commit-docs-modules-history.sh`と
`scripts/review_checks.py`（T560）の禁止パターンは`改善計画T[0-9]+で`しか拾わないため、
22箇所のうち同パターンに一致するのは5箇所だけで、「T536で…」「（旧T529/T534方式ではなく）」
「…へ変更した」のような言い回しは素通りした。また当該コミットが本フックを通ったかも不明
（`.git/hooks/pre-commit`は8月24日の旧コピーのままで、経緯記述チェックを含まない可能性がある）。

## 対応方針

1. 22箇所を「今のコードがどう動くか」だけの記述へ書き換える。経緯が必要な箇所は
   `docs/tasks/Txxx.md`へのリンク1つに置き換える（転記・要約しない）。
2. 禁止パターンを拡充する: `\bT[0-9]{3,4}で`・`旧T[0-9]`・`方式ではなく`・`へ変更した`・
   `に変更した`・`を導入した`等を候補に、docs/modules全15ファイルで誤検知（現在の制約を
   述べる正当な文）が出ないことを確認したうえで採用する。
3. パターンの二重管理を解消する: `pre-commit-docs-modules-history.sh`の役割を
   `review_checks.py docs --staged`（追加行の記載粒度チェックを既に持つ）へ寄せ、シェル側の
   PATTERN定義を削除するか、シェル側をpythonスクリプト呼び出しの薄いラッパにする。
4. `.git/hooks/pre-commit`が`scripts/pre-commit.sh`の最新コピーになっているかをユーザーに確認し、
   古ければ更新を依頼する（フックの設置は手動運用）。

   動くか」だけの記述へ書き換えた。history/2026-09-03_all.mdのEvidence行番号は本タスクの
   編集で前後にずれている（削除ベースの書き換えで行数がわずかに減少）。
2. **禁止パターンの拡充**: `scripts/review_checks.py`の`NARRATIVE_PATTERN`へ
   `旧T[0-9]`・`T[0-9]{3,4}で`・`方式ではなく`・`へ変更した`・`に変更した`・`を導入した`を
   追加。docs/modules全15ファイル（README.md除く）へ適用し誤検知0件を確認。既存パターン

   誤検知ではなく、既存パターンの守備範囲が広すぎたことによる既存の誤検知）。
3. **パターンの二重管理の解消**: `pre-commit-docs-modules-history.sh`（シェル側に独自
   PATTERN定義を持つ）を削除し、`pre-commit.sh`から呼び出しを外した。経緯記述検知は
   既に`pre-commit-docs-consistency.sh`が`review_checks.py docs --staged`経由で行っており
   （`NARRATIVE_PATTERN`は同スクリプト内の1箇所が唯一の定義元）、シェル側の別定義は

   直接言及していなかったため、整合を取るための追加修正は不要だった。
   **トレードオフ**: `pre-commit-docs-consistency.sh`はpythonが見つからない環境では
   soft-fail（警告のみでコミットを通す）する。旧`pre-commit-docs-modules-history.sh`は
   grepのみでpython非依存・常にhard-failしていたため、python不在環境での経緯記述検知の
   堅牢性はわずかに下がる。開発環境は通常backend用にpythonを要するため許容と判断した。

   ユーザーの手元環境での設置状況・`scripts/pre-commit.sh`との同期は本タスクでは確認
   できないため、ユーザーに確認を依頼する。
