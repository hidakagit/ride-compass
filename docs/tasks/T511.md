# T511. 風・勾配のcos向き投影式（wind_penalty/effective_gradient）の共通化

状態: DEFER（トリガー未到達、2026-08-31起票。ユーザー判断「提案の改善はdefer扱いでよい」）

- 背景: `domain/wind.py: WindCalculator.wind_penalty`と`domain/gradient.py:
  GradientCalculator.effective_gradient`は、どちらも「`magnitude × cos(材料自身の向き −
  走行方位)`」という数式的に同型のcos向き投影ロジックを個別に実装している
  （ユーザー指摘2026-08-31「風も勾配も同じ考え方の計算」）。ただし調査の結果、
  データ取得経路（勾配はDB由来の静的値でmaterial_catalog.pyの材料として登録済み、
  風は毎回変わる外部気象データで材料カタログの仕組みに乗らない、
  evaluation.py:305「風はEdgeに永続保存しない（動的データでありRoad Attributeとして
  扱わない、仕様書20章）」）・動的補正の要否（実際のルート評価で勾配はcos補正を使わず
  `gradient_percent`をそのまま使う一方、風は評価軸配信・ルート評価どちらもcos補正が
  必須）という2点で本質的に異なることが判明しており、「同じ考え方の計算」に見えるのは
  cosの式部分だけである。
- 対応方針（トリガー成立時）: `domain/directional_projection.py`に共通関数
  `project_onto_bearing(magnitude, material_bearing_deg, travel_bearing_deg)`を新設し、
  `WindCalculator.wind_penalty`/`GradientCalculator.effective_gradient`はこれを呼ぶ薄い
  ラッパーにする（式の重複を1箇所へ集約、各関数の符号の意味を説明するdocstringは個別に
  残す）。`WindWayService`/`GradientWayService`自体は統合しない——生データの取得元
  （気象APIグリッド vs DBのroad_edges属性）・出力粒度（タイル1値 vs way単位）が
  本質的に異なるため、1つの汎用サービスへ無理に統合すると逆に複雑になる。
- トリガー: 3つ目の「向きに依存する動的材料」（風・勾配と同じcos投影パターンを必要と
  する新規材料）が追加される時点。2件だけでの一般化は設計を誤りやすいと判断
  （T480と同じ理由）。
