# T483. windPenalty.tsの物理式JS移植とwindAxisPenalties/gradientAxisValuesの軸別prop構造の要否検討

状態: 完了（2026-08-31）

- **調査・判断の要約**: 2症状のうち1つは実装、もう1つは意図的に維持する判断とした。
  1. `windAxisPenalties`/`gradientAxisValues`の軸別prop → **統合を実施**（下記「実施内容」）。
     `dedicatedWayValueBoundaries`（T473）が既に同じ問題（軸ごとの別名prop）を
     `ReadonlyMap<axisId, ...>`で解消済みで、直接の前例として使える形だった。
  2. `windPenalty.ts`の物理式JS移植 → **意図的な例外として維持、コード変更なし**。
     理由は3点: (a) 環境グループのgridFillはコンパススライダーのドラッグ操作のたびに
     多数の格子セルを再着色する必要があり、都度backendへ問い合わせるとドラッグ操作の
     応答性が失われる（フロント側で完結させる技術的必然性がある）。(b) 対象の計算式は
     `wind_speed_ms * cos(風向-走行方位)`という調整可能なパラメータを一切持たない
     固定の三角関数1行のみで、設計原則1が本来問題視する「調整可能な値」（しきい値・
     重み等）は`dedicatedWayValueBoundaries`側で既にbackend/軸スタジオ由来に統一済み
     ——生成物経由でパラメータを同期する（T483対応方針案の1つ）は、そもそも
     パラメータが存在しないため適用できない。(c) 二重実装間のドリフトは
     `windPenalty.test.ts`の既知入出力ペアによる回帰テストが既に検知する仕組みを持つ。

- 背景: `docs/design-principles.md`「関連する過去の逸脱」が指摘していた3症状
  （windPenalty.tsの物理式JS移植・`WIND_AXIS_THRESHOLDS`ハードコード・
  `windAxisPenalties`/`gradientAxisValues`の軸ごとの別名prop）のうち、`WIND_AXIS_THRESHOLDS`
  ハードコードはT473で解消した（[T473](T473.md)参照）。残る2症状はスコープが異なる
  （T473が統合したのは表示しきい値のみで、`windAxisPenalties`/`gradientAxisValues`は
  way_id単位の実データ本体であり、`hooks/useDynamicWayValues.ts`をmaterialIdごとに
  個別インスタンス化して取得している構造上、単純な汎用Map化が既存のfetchライフサイクル
  （デバウンス・古いリクエストの後勝ち防止等）と両立するか要検討）。未起票のまま残すと
  「保留の理由・影響範囲が記録されないまま宙に浮く」という本プロジェクトで過去に
  繰り返し発生したパターン（統合レビュー第3回`history/2026-08-31_all.md`のC-1参照）を
  再発させるため、まず起票のみ行う。
- 対応方針（要調査、着手前に検討が必要）:
  1. `windPenalty.ts: windPenalty()`（backend `WindCalculator.wind_penalty`のJS移植）を
     二重実装のまま維持するか、生成物（export_openapi.py経由の計算式パラメータ書き出し等）
     で同期を機械化するか、あるいはbackend計算へ一本化しfrontendは表示のみにするかを判断する。
  2. `windAxisPenalties`/`gradientAxisValues`（`MapViewProps`）を`dedicatedWayValueBoundaries`
     と同型の`ReadonlyMap<string, ReadonlyMap<number, number>>`（axisId→way_id→値）へ
     統合できるか、`useDynamicWayValues.ts`のフック設計（materialIdごとの個別
     インスタンス化、デバウンス・レース対策）を踏まえて検討する。
- 規模: 未見積もり（要調査、着手判断はユーザー承認後）→ 実施時点でS〜M相当と判明。

## 実施内容（2026-08-31完了）

`page.tsx`/`MapView.tsx`側の変更のみ（`useDynamicWayValues.ts`・`windPenalty.ts`自体は
無変更）。

- `MapViewProps`の`windAxisPenalties: ReadonlyMap<number, number>`・
  `gradientAxisValues: ReadonlyMap<number, number>`を、`dedicatedWayValueBoundaries`
  （T473）と同型の`dedicatedWayValues: ReadonlyMap<string, ReadonlyMap<number, number>>`
  （axisId→way_id→値）へ統合した。
- `page.tsx`: `windAxisData.values`/`gradientAxisData.values`（`useDynamicWayValues`の
  戻り値、materialIdごとに個別インスタンス化する既存フック設計はそのまま）を、
  MapViewへ渡す直前で`useMemo`により1つの`Map`へ組み立てるだけに留めた
  （フック自体の呼び出し方・デバウンス・レース対策ロジックは無変更）。
- `MapView.tsx`: 新設`DEDICATED_WAY_VALUE_FEATURE_STATE_KEYS: Record<string, string>`
  （`{wind: WIND_AXIS_FEATURE_STATE_KEY, gradient: GRADIENT_AXIS_FEATURE_STATE_KEY}`）を
  介して、以前は風・勾配それぞれ独立していた2つの`useEffect`（`applyAxisFeatureStateValues`
  呼び出し）を1つのループへ統合。`redrawAllLayers`内の2箇所の明示的再呼び出しも同じ
  ループへ統合した。3件目の`dedicated_way_value_layer`軸が増えても、この
  Recordへ1行足すだけでeffect自体の変更が不要になる。
- `docs/modules/frontend/map-axis-coloring.md`・`docs/design-principles.md`
  「関連する過去の逸脱」を実施結果に合わせて更新した。
- 検証: `npx tsc --noEmit`・変更ファイルの`eslint`・`npx vitest run src/components/Map/
  src/app/page.test.tsx`（既存テストとの非干渉確認）・`npx vitest run`
  （frontend全体、878件）いずれも成功。プロパティ形状の変更のみで実際の計算・表示
  ロジックには手を入れていないため、実機（Browserペイン）確認は行っていない
  （並行セッションとdevサーバーを共有する状態のため、今回は型検査＋既存/新規の
  自動テストでの検証に留めた）。
