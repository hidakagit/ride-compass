# T652. Redisを撤去し「プロセス内キャッシュ＋ディスク」の2層構成にする 規模M

状態: 未着手（2026-09-07起票）

## 背景

[T651](T651.md)の本番実測で、Redisがルート生成へ与える寄与が**0.2〜0.3秒（全体の2%）**と
判明した。判断基準（1秒未満なら撤去）を満たすため、撤去する。

撤去の根拠は[T651](T651.md)と[docs/caching.md](../caching.md)にある。要点は、backendが
**単一プロセス**で動いており「プロセス間共有」というRedis最大の利点が働いていないこと、
全データが**5〜6MB**でプロセス内に持てる規模であること、失っても正本（PostGIS・外部API）から
復元できることの3点。

## 対象

| 現在の実装 | 移行先 |
|---|---|
| `jma_tile_redis_cache.py`（JMAタイル本体、TTL20分、base64+JSON包装） | プロセス内`TTLCache`。**包装が不要になる**（[T636](T636.md)は本タスクで解消） |
| `jma_tile_index.py`（在否インデックス、`redis_json_cache`経由） | プロセス内`TTLCache` |
| `road_edge_geometry_cache.py`（DirectedEdge、TTL24時間、mget一括） | プロセス内`TTLCache`（件数上限の検討が要る。2,794キー規模） |
| `road_graph_tile_cache.py`（取得済みマーカー・split鮮度） | プロセス内`TTLCache`（正本はPostGIS） |
| `dynamic_way_value_cache.py`（way_id→値） | プロセス内`TTLCache` |
| `jma_amedas_service.py`（観測値Hash、TTL15分、1,286件） | プロセス内`TTLCache`（バッチと読み出しが同一プロセスのため素直に置き換わる） |
| `redis_client.py`（接続・サーキットブレーカー）・`redis_json_cache.py` | **削除** |
| `docker-compose.yml`のredisサービス・`REDIS_URL` | 削除 |
| VM上のRedis（systemd） | 停止・アンインストールは最後（切り戻しできる状態を保つ） |

## 進め方

1. モジュールを1つずつプロセス内へ移す。**1つ移すごとに本番へ出して様子を見る**
   （すべてfail-open設計で機能は止まらないが、メモリ増加とヒット率の変化を見る）
2. すべて移し終えたら`redis_client.py`・`redis_json_cache.py`・設定・compose定義を削除
3. VM上のRedisは最後に停止する（切り戻せる状態を保つ）

## 確認すること

- **プロセスのメモリ増加**: Redisは6.32MBだったが、Pythonオブジェクトとして持つと数倍に
  なりうる。コンテナ上限は`--memory=6g`。移行のたびに`/api/debug/stats`と`docker stats`で見る
- **件数上限の設定**: Redisは`maxmemory` 2GBが歯止めになっていた。プロセス内へ移すと
  歯止めが無くなるため、各キャッシュに`maxsize`を設ける（根拠をコメントへ書く。
  [docs/caching.md](../caching.md)「TTLの決め方」と同じ扱い）
- **デプロイ直後の体感**: ルート生成への影響は0.3秒と実測済み。JMAタイルはプリウォームが
  10分以内に再充填する。実機で確認する

## 前提が変わる条件

`uvicorn --workers`の複数化、または blue/green デプロイ（複数コンテナ同時稼働）へ進む場合、
プロセス間共有が必要になりRedisの価値が復活する。現状は`--network=host`で単一ポートを
占有するため blue/green ができない。**この前提を`docs/caching.md`へ記録したうえで撤去する。**
