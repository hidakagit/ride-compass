# T652. ルート生成からRedisを追い出す（2つのcache-asideを削除） 規模M

状態: 完了（2026-09-07）

## 背景

[T651](T651.md)の本番実測で、Redisがルート生成へ与える寄与が**0.2〜0.3秒（全体の2%）**と
判明した。当初はRedis自体の撤去を想定したが、**将来ワーカーを複数化する可能性がある**ため
Redisは残し、**用途ごとに置き場所を決め直す**方針へ改めた（ユーザー判断、2026-09-07）。

[docs/caching.md](../caching.md)「Redisへ置くもの・置かないもの」に基準を書いた。要点は
**外部への負荷を肩代わりしているものだけをRedisへ置く**こと。プロセス内キャッシュは
ワーカーごとに独立するため、外部フェッチを肩代わりするキャッシュをプロセス内に置くと、
上流へのリクエストがワーカー数に比例して増える。一方、正本が自前のPostGISにあるものは、
ミスしても自分のDBへ往復するだけで、その増加は自分で観測・制御できる。

## 実施内容: 2つのcache-asideを削除した

計測で「救う時間」が判明したため、プロセス内へ移すのではなく**削除**した。

| 削除したもの | 肩代わりしていたクエリ | 実測 |
|---|---|---|
| `road_graph_tile_cache.py`（取込完了マーカー、TTL24h） | `road_graph_tiles`（1,020行）の照会 | 1.1 ms |
| 同（split鮮度マーカー、TTL1h） | `is_split_up_to_date`の空間クエリ | 5.8 ms |
| `road_edge_geometry_cache.py`（edge_id→形状、TTL24h） | 2,800エッジの主キー読み出し | 75 ms（Redis経路22msを差し引くと正味約53ms） |

削除の理由は速度ではなく構造である。

- **保持していたのが危険側の判断**: split鮮度は「splitは最新」という判断を保持しており、
  外れると古い道路データのままルートを返す。しかも一方向に単調ではない（fresh→staleへ戻る）
- **別プロセスからのpush無効化が必要だった**: PBF取込バッチ・事前splitバッチがweb側の
  キャッシュを外から消していた。この無効化はfail-openのため、Redisが一瞬不調なら
  静かに失われ、最大1時間／24時間にわたり古い値が返る
- **版をキーへ入れる正攻法が成立しない**: 版を読むには同じテーブルを引く必要があり、
  キャッシュが節約するコストと同じ桁になる（[docs/caching.md](../caching.md)
  「版をキーに入れるなら、版の照会が十分に安いこと」）

### 併せて消えたもの

- `import_pbf.py`からの`mark_fetched`・`invalidate_split_fresh`呼び出し
- `save_graph`内の`invalidate_edges`（precise invalidation）
- `get_edges_with_geometry`の`use_cache`引数（バッチが迂回するための逃げ道が不要になった）
- 上記2モジュールのテスト2ファイルと、Redisを前提にした既存テスト7件

### 結果

**ルート生成の呼び出し経路からRedisという語が消えた**（router→route_generator→
road_graph_engine→graph_service→repository→各キャッシュ→天候のすべてを確認）。
残るキャッシュはプロセス内メモリとディスクのみ。

## Redisに残るもの

| 実装 | 理由 |
|---|---|
| `jma_tile_redis_cache.py`（JMAタイル本体） | 失うと気象庁の非公式配信へ取りに行く。ワーカー複数化時に共有が必要 |
| `jma_tile_index.py`（在否インデックス） | 同上。プリウォームが作る共有知識 |
| `jma_amedas_service.py`（観測値） | 失うと気象庁へ全国分を取りに行く |
| `dynamic_way_value_cache.py`（way_id→値） | 地図タイル配信用。ルート生成の経路には無い |

## ワーカー複数化との関係

移行後にワーカーを複数化しても、外部連携（JMA系）はRedisで共有されたままになる。一方で
**キャッシュ以外に手当てが要る**ことを`docs/caching.md`へ記録済み: APSchedulerのバッチが
ワーカーごとに起動して同じ仕事をN回すること、上流への秒間上限がプロセス内状態のため実効値が
N倍になること。複数化に着手する際は別途扱う。
