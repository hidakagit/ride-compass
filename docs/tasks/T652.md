# T652. ルート生成系のキャッシュをプロセス内へ移す（Redisは外部連携用に残す） 規模M

状態: 未着手（2026-09-07起票）

## 背景

[T651](T651.md)の本番実測で、Redisがルート生成へ与える寄与が**0.2〜0.3秒（全体の2%）**と
判明した。当初はRedis自体の撤去を想定したが、**将来ワーカーを複数化する可能性がある**ため
Redisは残し、**用途ごとに置き場所を決め直す**方針へ改めた（ユーザー判断、2026-09-07）。

[docs/caching.md](../caching.md)「Redisへ置くもの・置かないもの」に基準を書いた。要点は
**外部への負荷を肩代わりしているものだけをRedisへ置く**こと。プロセス内キャッシュは
ワーカーごとに独立するため、外部フェッチを肩代わりするキャッシュをプロセス内に置くと、
上流へのリクエストがワーカー数に比例して増える。一方、正本が自前のPostGISにあるものは、
ミスしても自分のDBへ往復するだけで、その増加は自分で観測・制御できる。

## 対象: プロセス内へ移す3つ

| 現在の実装 | 移行先 | 理由 |
|---|---|---|
| `road_edge_geometry_cache.py`（DirectedEdge、TTL24時間、mget一括、2,794キー規模） | プロセス内`TTLCache` | 正本はPostGIS。ミスしても`mget`2回ぶんの往復が増えるだけ（実測avg 38ms） |
| `road_graph_tile_cache.py`（取得済みマーカー・split鮮度） | プロセス内`TTLCache` | 同上 |
| `dynamic_way_value_cache.py`（way_id→値） | プロセス内`TTLCache` | 失っても自前で再計算するだけ |

## Redisへ残す（触らない）

| 実装 | 理由 |
|---|---|
| `jma_tile_redis_cache.py`（JMAタイル本体） | 失うと気象庁の非公式配信へ取りに行く。ワーカー複数化時に共有が必須 |
| `jma_tile_index.py`（在否インデックス） | 同上。プリウォームが作る共有知識 |
| `jma_amedas_service.py`（観測値、1,286件） | 失うと気象庁へ全国分を取りに行く |
| `redis_client.py`・`redis_json_cache.py` | 上記が使い続けるため残す |

`jma_tile_redis_cache`のbase64+JSON包装（[T636](T636.md)）は、Redisへ残す以上そのまま
課題として残る。

## 進め方

1. 3モジュールを1つずつプロセス内へ移す。**1つ移すごとに本番へ出して様子を見る**
   （すべてfail-open設計で機能は止まらないが、メモリ増加とヒット率の変化を見る）
2. 移行後、Redisに残るキーが`jma:*`だけになっていることを確認する

## 確認すること

- **プロセスのメモリ増加**: Redisは6.32MBだったが、Pythonオブジェクトとして持つと数倍に
  なりうる。コンテナ上限は`--memory=6g`。移行のたびに`/api/debug/stats`と`docker stats`で見る
- **件数上限の設定**: Redisは`maxmemory` 2GBが歯止めになっていた。プロセス内へ移すと
  歯止めが無くなるため、各キャッシュに`maxsize`を設ける（根拠をコメントへ書く。
  [docs/caching.md](../caching.md)「TTLの決め方」と同じ扱い）
- **デプロイ直後の体感**: ルート生成への影響は0.3秒と実測済み。JMAタイルはプリウォームが
  10分以内に再充填する。実機で確認する

## ワーカー複数化との関係

移行後にワーカーを複数化しても、外部連携（JMA系）はRedisで共有されたままになる。一方で
**キャッシュ以外に手当てが要る**ことを`docs/caching.md`へ記録済み: APSchedulerのバッチが
ワーカーごとに起動して同じ仕事をN回すること、上流への秒間上限がプロセス内状態のため実効値が
N倍になること。複数化に着手する際は別途扱う。
