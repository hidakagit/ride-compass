# T590: 風penaltyの二乗則化とレンズUI再編（分割元・設計メモ）

状態: 完了（2026-09-05。分割先T591〜T599完了、分割元の仕上げ[design-principles.md
昇格・architecture.md追従・機械的チェック]も完了。T600のみトリガー待ちで対象外）

## 背景

現行の風penalty（`backend/app/domain/wind.py: WindCalculator.wind_penalty`）は
`wind_speed_ms × cos(風向 − 走行方位)`で走行速度を一切考慮しない。線形合成では
「同じ向かい風でも速く走るほどきつい」を表現できず、空気抵抗（相対風速の2乗）ベースへ
変更する検討を依頼された。検討の過程で以下が判明し、計算式の変更だけでは閉じないと
分かったため、設計メモ（本ファイル）と分割先タスクへ分けた。

- 式の実体は3箇所（`wind.py`スカラー版・`evaluation.py: _evaluate_axes_bulk`内インライン・
  `evaluation.py: _evaluate_wind_penalty_array`）。`_LegCostComposer`は式を持たず配線のみ。
  地図配信の`services/wind_way_service.py`はスカラー版を呼ぶ第4の消費者で、走行速度の
  新たな配線先になる。
- 現行の評価は追い風を0へクランプしている（開発DBの風軸breakpointsは`[[0,0],[8,100]]`、
  `np.interp`が範囲外を端値へ倒す）。探索上、追い風と横風は無差別。
- 風軸の`display_thresholds_override`が、ルート前の専用way値レイヤー（材料スケールm/s、
  `page.tsx: dedicatedWayValueBoundaries`）とルート後のルート線色分け（難易度0〜100、
  `routeStyleModes.ts: routeColorableModeFromAxis`）の2系統で共用されている。本番の
  `[10,20,30,40,50]`は難易度スケールとしては妥当な値で、「異常値」に見えた真因はこの
  二重帰属である可能性が高い（[T587](T587.md)残課題の再解釈）。
- 色分けの入口が3箇所に分散している（ルート設定パネルの軸チップの色分けアイコン、
  ルート結果のチップ列、地図の見え方のレイヤー一覧の「風（評価軸）」「勾配（評価軸）」
  「ramp軸」）。意味も、複数ON/単一選択、全道路/ルート線、で食い違う。
- 比較パネルの「風スコア m/s」行は風軸の重みに関係なく常に出る固定行で、風の名前を知る
  レガシーフィールド（`wind_score`・`RouteSegmentDetail.wind_penalty`・`gradient_percent`・
  `road_surface_good`・`road_score`）が残っている。
- 軸スタジオの折れ点編集はほぼ全て手入力で、曲線エディタは目盛り・スナップが無い。
  二乗則材料は単位が直感的でないため、換算の補助が無いと編集できない。

## 決定事項（2026-09-05、ユーザー合意）

### 1. 数式（材料側、Python実装）

相対風速ベクトルの2次元版を採用する。走行速度v、風速w、風向と走行方位の差dとして:

```
x  = v + w·cos(d)                 # 正=向かい風的（既存の符号規約と同じ）
Vr = sqrt(x² + (w·sin(d))²)       # 相対風速の大きさ
ΔF = Vr·x − v²                    # 進行方向の抗力増分（k=½ρCdAは省く、無風基準）
material = ΔF / v_ref²            # v_ref = 20 km/h = 5.556 m/s（専用の明示定数）
```

- 横風0（sin=0）のときVr=|x|となり、1次元候補式`sign(x)·x² − v²`と厳密に一致する。
- 符号はxの符号で自然に決まる。横風主体のときの符号ルールは不要（純横風は相対風速が
  増える分だけ小さな正の値）。追い風がvを超える領域も連続。
- 無次元化の基準速度は`ASSUMED_SPEED_KMH`とは別の専用定数にする（既定速度を変えても
  材料スケールがずれないようにするため）。走行速度自身のv²で割る案は速度依存を打ち消す
  ため不可。平方根でm/sへ戻す案は既存`wind_penalty`と同単位で意味が変わり、
  設計原則5（同名・同単位で意味を変えない）に反するため不採用。

値域の試算（無次元、v_ref²=30.86）:

| 仮定速度 | 向かい風2m/s | 4m/s | 8m/s | 追い風4m/s | 純横風4m/s |
|---|---|---|---|---|---|
| 10km/h | 0.49 | 1.24 | 3.51 | -0.30 | 0.19 |
| 20km/h | 0.85 | 1.96 | 4.95 | -0.92 | 0.23 |
| 30km/h | 1.21 | 2.68 | 6.39 | -1.64 | 0.25 |
| 60km/h | 2.29 | 4.84 | 10.71 | -3.80 | 0.26 |

初期breakpointsの案は`[[0,0],[5,100]]`（20km/hで8m/sの向かい風が100、既存の端点と
整合）。追い風を横風より優遇したい場合は`[[-1.2,0],[0,15],[5,100]]`のように無風へ
小さな基準値を置く（`cost ≥ distance`の不変条件と両立させる唯一の手段。軸スタジオだけで
決められる別判断）。

### 2. 材料の扱い

- `wind_penalty`（m/s）は新材料へ置き換える。表示用に残す案は、風専用フィールドの温存に
  なるため撤回した。
- 物理量の表示は「重み>0の公開軸が参照する材料id→値」の汎用辞書へ汎用化する（T592）。
  風軸を使っていなければ風の行は出ず、使っていれば軸が参照する材料の値が出る。
- 材料の切替はT584と同じ2段階（第1デプロイで材料追加、その後axis_admin API経由で本番の
  軸の参照先を切替、スナップショット更新）。

### 3. 走行速度

リクエスト単位の`assumed_speed_kmh`1本を維持する。勾配で速度を変える案は、通過時刻推定
（直線距離÷一定速度）と噛み合わず、風軸が勾配材料へ暗黙依存して軸スタジオから制御不能に
なるため採らない。将来やるなら「推定速度」を独立した材料として起票する。

### 4. 表示スケール

専用way値レイヤー（ルート前）の配信値を、signed-absでない軸は難易度（軸スタジオの
breakpointsで評価済み0〜100）へ統一する（T593）。ルート前後で1つのスケール・1つの
override・単位なし凡例になり、探索が使う値と地図が一致する。勾配（signed-abs shape）は
符号付き材料のまま。分岐はshape属性で行い軸固有コードは増やさない。

### 5. UI設計の基準（置き場所を決める5つ）

1. 反映タイミングで分ける。生成ボタンで効くものはルート設定、即時に効くものは地図の
   見え方、結果は読むだけ。
2. 1つの状態は1つの場所でだけ操作する。レンズ・走行方位・出発時刻・想定速度はそれぞれ
   入口を1つにし、他の場所は表示かショートカットに留める。
3. 数値は3層で見せる。地図は色だけ、パネルは段階ラベルと0〜100、物理量は区間の詳細だけ。
4. 消さずに薄くする。評価に使っていない軸・値が無い区間は非表示にせず「未使用」
   「データなし」として残す。
5. 一覧は軸カタログから同じ順・同じ色・同じ名前で生成する。手で並べた一覧を持たない。
6. 主な利用場面はロードバイク走行中のスマホ操作。1画面の情報量を増やさない。新しい表示を
   足すときは「走行中に見るか」を問い、見ないものは研究モード限定か折りたたみの奥に置く
   （ユーザー指示2026-09-05。例: 区間詳細に物理量を出すかは要相談で、既定は出さない）。

適用結果:

- レンズ（何で塗るか）を地図の見え方の先頭に単一選択で置く。ルート前は全道路、ルート後は
  ルート線を同じ凡例で塗り、生成をまたいで保持する。地図上部中央の凡例（[T587](T587.md)
  時点で既に上部中央へ移設済み、ボトムシートに隠れない）は現在のレンズを示し、タップで
  地図の見え方を開くショートカット。他の2パネルから表示系を抜く（T595）。
- 「重み0の軸はルート後の色分け候補から消す」（2026-09-03の判断）は撤回。未使用の軸も
  「未使用」表示で選べる。
- 出発時刻・走行方位・想定速度は地図下辺の条件バー1本へ（T596）。即時反映（レンズはすぐ、
  探索は次の生成で）と割り切る。
- デスクトップのサイドバーをモバイルの下部タブと同じ「ルート設定 / ルート結果 /
  地図の見え方」の3区分へ揃える（T597）。
- 将来のルート保存・参照・GPX出力（ユーザー要望2026-09-05）の置き場: ルート結果ヘッダの
  操作群（現状「ルートをクリア」と説明アイコン）に「保存」「GPX出力」を並べ、保存済み
  ルートの参照は候補タブ列の先頭に固定タブ「保存済み」として置く。3区分は増やさない。
  T597で操作枠（ヘッダの横並び領域と先頭タブの余地）だけ確保し、機能自体は別途起票する。
- おすすめ度は撤去済みのため、ルート結果の先頭は総合難易度のみ。
- 複数の軸を同じ線に重ね塗りする機能はやめる（後から追加した方が上書きするだけで
  情報が無かった）。一次属性・気象レイヤーの複数ONは維持。

### 6. 軸スタジオ

計算式（二乗則）は材料側のPythonが持ち、軸スタジオのshape定義は変えない
（`breakpoint_linear`の区分線形が材料の非線形を吸収する）。編集の省力化として、材料
カタログ配信の参考点・範囲＋形からの折れ点自動生成・効き目プレビュー・エディタ操作改善を
T598で行う。実データ分布の重ね描きはT600（トリガー待ち）。
