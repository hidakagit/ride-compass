# T699. 蛇行軸の配線を最後まで通す（3箇所の欠けが互いの検知を打ち消している） 規模M

状態: 完了（2026-09-10起票、統合レビュー第6回 I-4／2026-09-10完了）

## 背景

[T691](T691.md)/[T692](T692.md)で追加した蛇行軸（`curvature`、`default_weight=0.1`、本番で公開済み）の
配線が**3箇所で同じ方向に欠けており、互いの検知を打ち消している**。どれか1つでも正しければ気づけた。

### 1. バッチが実行されない

`app/batch/refresh_derived.py:57-66`の`_STAGES`は④〜⑪の8段で、
**`precompute_edge_curvature`を含まない**。一方
`backend/migrations/0035_add_road_edges_curvature.sql:5`は
「適用後は app/batch/precompute_edge_curvature.py の実行が必須」と書く。
派生データ再構築の**単一エントリポイント**を名乗るスクリプトが、必須と宣言されたバッチを呼ばない。

### 2. 評価が読む場所が埋まらない

ルート評価が読むのは`road_edges.curvature_deg_per_km`
（`get_edge_materials_batch`→`EdgeMaterialBundle.curvature_deg_per_km`）。
1により`build_road_graph`がsplit時に埋める新規Edge以外はNULLのまま残り、
蛇行軸はそれらの区間で欠損扱いになり重み再正規化で薄まって**無警告のまま評価から抜ける**。

### 3. 診断が別のテーブルを見ている

`app/infrastructure/material_coverage.py:206-216`の`curvature_deg_per_km`は
`way_geometry`のみを`missing_condition`にしている。コメント自身が
「Edge単位（road_edges、**ルート評価が読む**）とWay単位の両方にある」と認めたうえでWay側を選んでいる。
→ `precompute_way_curvature`だけ流せば**カバレッジ画面は「欠損0%」と報告する**一方、評価側は算出不能。

### 4. キャッシュ経路でも落ちる

`app/domain/attributes.py:416-431`の`EdgeMaterialTable.get()`が`curvature_deg_per_km`を
`EdgeMaterialBundle`へ渡していない（同`:269`/`:313`/`:385`/`:478-479`は保持・使用している）。
`SearchMaterials.materials`のdocstring（`:514-515`）が明言する
「いずれの型も`.get(edge_id)`で同じ意味論のbundleを返す」契約が破れている。

## なぜ気づけなかったか

T691完了コミット（`509f0210`）は「本番でルートを生成し、全候補・全区間の
axis_difficulties/axis_raw_valuesへcurvatureが載ることを確認した」と記録しているが、
それは`build_road_graph`が新規に埋めたEdgeを含むタイルでの確認であり、
1〜3が揃うと**既存Edgeの多いタイルでは静かに欠損する**。

## 対応方針

1. `_STAGES`へ`precompute_edge_curvature`を追加する。あわせて
   **`_STAGES`と`app/batch/precompute_*.py`のファイル一覧を突き合わせるドリフト検知テスト**を置く
   （現`tests/test_refresh_derived.py`は8段を手書き列挙するだけで、次に増えるバッチでも同じ漏れが再発する）。
2. カバレッジを評価が実際に読む`road_edges.curvature_deg_per_km`側で数える
   （Way側も見たいなら2エントリにする）。
3. `EdgeMaterialTable.get()`へフィールドを渡す。`tests/test_attributes.py:270`の往復テストは
   全fixtureが`None`のためこの種の漏れを検出できない——**bundleの全フィールドが往復で
   保存されることを型から機械的に確認する**形にする。

## 派生（同じ機能の周辺）

- `road_graph_repository.py:894-912`/`:2481-2487`の`recompute_edge_curvature`だけが
  `LIMIT/OFFSET`ページングで、[T660](T660.md)が確立した`stream_id_chunks`
  （サーバーサイドカーソル）を使っていない。他5本のprecomputeは揃っている。
  コメントは「edge_idの範囲で分割して呼ぶ」と述べるが実装はOFFSET分割で、
  本番504万行・20万件刻みで累計約6,300万タプルを読み捨てる。
- `road_graph_repository.py:918-941`の`_RECOMPUTE_WAY_CURVATURE_SQL`は
  `w.geom IS NOT NULL`のためgeomがNULLのwayに行を作らず、
  `WayGeometryRow`のdocstring（`road_graph_models.py:301`）が主張する
  「行が無い＝未計算、列がNULL＝算出不能」の2状態契約が成立しない
  （[T688](T688.md)と同型の欠陥を新設テーブルが再導入している）。
- `infrastructure/graph_material_cache.py:40-48`が`refresh_derived.py`の実行対象として
  `precompute_edge_curvature.py`を列挙しているが実際には含まれない（1と同じ穴）。

## 実装メモ

対応方針1〜3に加え、「派生（同じ機能の周辺）」の3件もすべて同じコミットで閉じた
（同じ材料の配線が途中で切れている状態を部分的に直すと、どこまで通っているかが
再び分からなくなるため）。

1. **`_STAGES`へ⑫`precompute_edge_curvature`を登録**（`refresh_derived.py`）。
   番号は末尾へ足した——road_edges起点なので第2グループ（⑤〜⑦）に属するが、
   ⑤〜⑪のどれとも順序制約が無く④の後であればよいため、既存の番号を振り直さない。
   ドリフト検知は`tests/test_refresh_derived.py`の2本:
   - `test_every_precompute_batch_module_is_registered_as_a_stage`:
     `app/batch/precompute_*.py`のファイル一覧を正として`_STAGES`と突き合わせる。
   - `test_every_stage_names_an_existing_callable`: `_STAGES`は関数名を文字列で持つ
     （monkeypatchを効かせるため）ので、綴り誤りが実行時まで露見しない穴を塞ぐ。
2. **カバレッジを`road_edges`側で数える**（`material_coverage.py`）。
   `WayMaterialCoverageSpec`（`way_geometry`を見る）から
   `EdgeMaterialCoverageSpec(present_count_sql="SELECT count(*) FROM road_edges
   WHERE curvature_deg_per_km IS NOT NULL")`へ変更。他のedge材料と違い、値は派生
   テーブルではなく母集団`road_edges`自身の列にある。
3. **`EdgeMaterialTable.get()`へ`curvature_deg_per_km`を渡す**（`domain/attributes.py`）。
   往復テストの検出力は、`_full_bundle`へ値を入れたうえで
   `test_full_bundle_fixture_fills_every_bundle_field`（dataclassのフィールド一覧を
   走査し、既定値のまま残っているフィールドが無いことを確認する）で担保する。
   fixtureが既定値のままだと`from_bundles`と`get()`のどちらが落としても等しくなり、
   等値比較の往復テストが何も検出しない。
4. **`recompute_edge_curvature`をLIMIT/OFFSETから`stream_id_chunks`へ**
   （`road_graph_repository.py`・`precompute_edge_curvature.py`）。
   引数を`(limit, offset)`から`edge_ids: list[str]`へ変更し、他5本のprecomputeと
   同じ`count_targets`＋`stream_id_chunks`の骨格に揃えた。
5. **`_RECOMPUTE_WAY_CURVATURE_SQL`とバッチの対象抽出から`geom IS NOT NULL`を撤去**。
   `WayGeometryRow`が宣言する「行が無い＝未計算、列がNULL＝算出不能」の2状態を
   成立させる（`ST_Length(NULL)`はNULLを返し`CASE WHEN t.length_m > 0`が偽にも真にも
   ならないため、行だけ作られ値はNULLになる）。
6. `graph_material_cache.py:40-48`の列挙（`precompute_edge_curvature.py`を
   refresh_derivedの実行対象として挙げている）は、1の登録により記述どおりになった。

## 検証結果

各修正について、修正を一時的に戻すとガードが実際に落ちることを確認した:

| 修正 | 戻したときの結果 |
|---|---|
| `_STAGES`の⑫ | `test_every_precompute_batch_module_is_registered_as_a_stage` 失敗 |
| カバレッジのEdge側集計 | `test_edge_materials_are_counted_over_road_edges_...` が `assert 0 == 1` で失敗 |
| `get()`のcurvature | 往復系4本（`..._roundtrip_at_realistic_scale`等）が失敗 |

- ローカルPostgreSQL 16＋PostGIS 3.4で全テスト実行: `pytest -q -m "not postgis"` 1,758 passed、
  `pytest -q -m "postgis"` 283 passed、`ruff check app scripts benchmarks tests` クリーン。
- `export_openapi.py`→`npm run generate:api`後、`git diff --exit-code --
  frontend/src/types/generated/` がクリーン（APIスキーマへの影響なし）。

## 本番運用として残る作業

本番DBの既存`road_edges`は依然`curvature_deg_per_km`がNULLのままである
（本タスクはバッチを配線しただけで、実行はしていない）。本番へのバッチ適用と
`TILE_MATERIALS_CACHE_VERSION`の引き上げは[T717](T717.md)へ分離した。
