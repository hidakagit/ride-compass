# T580: 路面タイルをRenderフロントを経由せずbackendへ直接配信する（接続上限対策とセット）

状態: 着手（2026-09-04起票、同日方式決定）

## 背景

[T578](T578.md)の調査で、利用者が体感するタイルの遅さの主成分はRenderフロント（遠隔
リージョン）経由のプロキシ往復（1タイルあたり0.3〜0.5秒）と判明した。backend
（Oracle東京）へ直接取りに行けばキャッシュヒットは0.05〜0.08秒で返る。ただしAPI呼び出し
（`NEXT_PUBLIC_API_URL`、既に直接fetch）と同じオリジンにタイルを載せると、ブラウザの
オリジン単位の同時接続数上限（HTTP/1.1で6本）をタイルが埋めてAPIが詰まる問題
（docs/architecture.md「同時接続数上限との競合」）が再発する。対策の方式は起票時点で未決定
（HTTP/2化 or タイル専用ホスト名の分離）だったが、同日HTTP/3化で決定した（下記）。

## 対応方針（2026-09-04、ユーザー判断）

VM上のnginxをnginx.org公式パッケージ（1.30系stable、QUIC/HTTP/3同梱）へ差し替え、
HTTP/3＋HTTP/2（UDPが通らない環境向けの退避先）を有効にした上で、タイルをbackendへ
直接取りに行かせる。HTTP/2のみの案（モバイル回線でのTCP head-of-line blocking、
1接続への多重化が逆効果になりうる）・タイル専用ホスト名の分離案（HTTP/1.1のまま接続枠
だけ分ける）と比較し、QUICが上記のTCP起因の懸念を解消しつつ接続上限の問題も多重化で
解けるため採用した。残るデメリット（同一接続内の帯域共有・UDP 443の開放・OpenSSL 3.0
互換レイヤーのため0-RTTなし・パッケージの出所がnginx.orgになる・QUICのCPU負荷）は
許容範囲と判断。

進め方:

1. コード側（リポジトリ内で完結、先行）: フロントのタイルURLの向き先を環境変数
   `NEXT_PUBLIC_TILE_BASE_URL`で切り替え可能にする。未設定時は従来どおりフロント自身の
   オリジン（Next.jsのrewrites経由）で挙動を変えない。backend側はCORS（既に許可済み）・
   レート制限（直接アクセスでは実IPが見える）を確認する。
2. VM側（手作業、SSHコマンドを用意しユーザーが実行）: nginx.org 1.30へ差し替え→
   `listen 443 quic reuseport`＋`http2 on`＋`Alt-Svc`→UDP 443開放（OCIセキュリティ
   リスト＋iptables）→ブラウザDevToolsで`h3`を確認。手順は`docs/disaster-recovery.md`へ
   記録する。
3. 反映: Renderの環境変数`NEXT_PUBLIC_TILE_BASE_URL`をbackend直接へ設定。問題があれば
   環境変数を外すだけでRender経由へ戻せる。

## VM側の作業手順（2026-09-04作成、実行前の構成: nginx 1.24.0[Ubuntu]、arm64、noble、
## sites-enabledに default/openmeteo-proxy.conf/ridecompass-backend.conf、certbot管理のTLS）

前提の確認と設定のバックアップ:

```bash
sudo cp -a /etc/nginx /root/nginx-backup-$(date +%Y%m%d%H%M%S) && ls -d /root/nginx-backup-*
```

1. nginx.org公式リポジトリの追加（1.30系stable、QUIC/HTTP/3同梱）と差し替え。
   `apt-mark`/pinで公式版を優先し、Ubuntu版（`nginx`+`nginx-common`）を置き換える。
   公式パッケージは`/etc/nginx/conf.d/*.conf`のみをincludeし`sites-enabled`を読まない。
2. `conf.d`へ設定を移設。backend用server blockへ`listen 443 quic reuseport`・`http2 on`・
   `http3 on`・`Alt-Svc`ヘッダを追加（certbot管理の証明書パス・options-ssl-nginx.confは
   そのまま使う）。openmeteo-proxy.conf（8080）と、certbotがHTTP-01更新で使うport 80の
   server blockも移す。
3. UDP 443の開放: VM内iptables（`netfilter-persistent save`で永続化）と、OCIセキュリティ
   リスト（`ridecompass-vcn`、Ingress: 0.0.0.0/0 UDP 443）。
4. 確認: `nginx -V`に`--with-http_v3_module`があること、`nginx -t`→reload、
   `curl -I`で`alt-svc: h3=":443"`が付くこと、ChromeのDevTools（Networkの「Protocol」列）で
   2回目以降の読み込みが`h3`になること。

### 実行結果（2026-09-05、ユーザーがSSHで実行）

- `/etc/nginx`を`/root/nginx-backup-<timestamp>`へ退避後、nginx.orgリポジトリ（`deb ... noble nginx`、
  pin優先度900）を追加し`apt-get remove nginx nginx-common`→`/etc/nginx`を`/root/nginx-old-etc`へ
  退避→`apt-get install nginx`。conffileの質問（fastcgi_params等）はすべて`Y`（公式版を採用）。
  結果: nginx 1.30.4、`nginx -V`に`--with-http_v3_module`。
- `/etc/nginx/conf.d/ridecompass-backend.conf`（下記）と`openmeteo-proxy.conf`（従来と同内容）を作成。
  `nginx -t`成功→`systemctl enable --now nginx`→reload。`ss -lunp`でUDP 443のリスナーを確認。
- iptables: `-I INPUT -p udp -m udp --dport 443 -m state --state NEW -j ACCEPT`→
  `netfilter-persistent save`。OCIセキュリティリスト（Default Security List for
  ridecompass-vcn）へIngress UDP 443（0.0.0.0/0）をコンソールから追加（OCI CLIで追加済みを確認）。
- 確認: `curl -I`が`HTTP/2`＋`alt-svc: h3=":443"; ma=86400`、タイル応答にCORSヘッダとgzipが
  従来どおり付く。アプリ内ブラウザから`https://193-123-166-150.sslip.io/health`を開き
  `performance.getEntriesByType("navigation")[0].nextHopProtocol`が`h3`（2回目以降約25ms）。
  なおクロスオリジンのResource Timingは`Timing-Allow-Origin`ヘッダが無いと`nextHopProtocol`が
  空文字になるため、プロトコルの確認は同一オリジンのnavigationエントリで行う。

backend用server block（`/etc/nginx/conf.d/ridecompass-backend.conf`）:

```nginx
server {
    server_name 193-123-166-150.sslip.io;
    listen 443 quic reuseport;
    listen [::]:443 quic reuseport;
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    http3 on;
    ssl_certificate /etc/letsencrypt/live/193-123-166-150.sslip.io/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/193-123-166-150.sslip.io/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;
    add_header Alt-Svc 'h3=":443"; ma=86400' always;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
        proxy_connect_timeout 10s;
    }
}
server {
    listen 80;
    listen [::]:80;
    server_name 193-123-166-150.sslip.io;
    return 301 https://$host$request_uri;
}
```

戻す場合: `apt-get remove nginx`→pin/リポジトリ定義を削除→`/root/nginx-old-etc`を`/etc/nginx`へ戻し
Ubuntu版`nginx`を再インストール（TCP 443のみ、HTTP/1.1に戻る）。

### 副次的に見つかった構成の食い違い（本タスクの対象外、要別途判断）

- OCIセキュリティリストのIngressにTCP 22の`0.0.0.0/0`許可が、管理者IP限定の行とは別に残っている
  （設計上は管理者IPのみ）。
- VM内iptablesにTCP 5432の送信元無制限の許可行がある（OCI側で管理者IP＋Renderレンジに絞られて
  いるため実害は無い）。
