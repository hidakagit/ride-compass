# T935: 補給POIが、種別を絞らず間引きもせず全点描かれる

状態: 着手中（2026-09-18起票。絞り込みを実装、本番の取り直し待ち）

## 背景

利用者から「自販機とか大量に点プロットされるけど本当にこんなにあるのか」という疑いが出た。
考えられる筋は3つあり、どれが効いているかで対処の重さがまったく違う。

1. **拾う条件が緩い**（飲料以外の自販機まで「自販機」として出している）
2. **見せ方に間引きが無い**（実在する点をすべて同時に描いている）
3. **実際にその密度で存在する**

## コード側の現状（2026-09-18）

**1の仕組みは確かにある。** `domain/traffic.py: classify_supply_poi`は`amenity`の値を辞書で
引くだけで、`vending`（何を売る機械か）を見ていない。取込プロファイル側のマッチ条件も
`amenity`の1キーのみ。つまりたばこ・切符・パーキング券等も区別せず「自販機」として地図に
出ている。

さらに、`domain/osm_adapter.py: ALLOWED_NODE_TAGS`に`vending`が含まれないため、このタグは
**DBに保存すらされていない**。本番で確認したところ、`kind='vending_machine'`の17,530件
すべてで`tags`に`vending`が無かった。**今のDBからは飲料かどうかを後から判別できず、
絞り込むにはPBF再取込が要る**（`barrier`を足したときと同じ落とし穴。[T654](T654.md)）。

**2も成立している。** タイルSQL（`road_graph_repository.py: _POI_TILE_MVT_SQL`）には、
補給POIについては間引きが無い（停止要因のまとめは[T934](T934.md)で入れた）。フロント側も
`circle`レイヤーで半径固定・レイヤー個別のminzoom無しで、`symbol`と違い衝突判定が働かない
ため重なった点もすべて描かれる。補給の各種別は出し分けが無く常に同時に出る。

## 起票時に落ちていた項目

[T101（改善計画アーカイブ 2026-08-17）](../improvement-plan-archive/2026-08-17.md)の起票文には
「数が多い自販機はズーム制限を個別に検討」と書かれている。しかし同じファイルの実装結果には
**採用も見送りも記録が無く、実装もされていない**。判断されないまま消えた項目である。

なお鮮度（閉店・撤去へOSMが追従できていない件）については同じT101で明示的に判断済みで、
「5種すべて取込対象にしつつ表示側で鮮度の差を利用者へ伝える」としている。**本タスクは
鮮度の話ではなく、拾う条件と見せ方の話**なので、その判断を覆すものではない。

## 測った結果（関東PBF、2026-09-18）

`backend/scripts/measure_vending_types.py`を新設してPBFを1パス舐めた。

| | 件数 | 割合 |
|---|---|---|
| `amenity=vending_machine` | 17,349 | 100% |
| 補給に使える | 14,225 | 82.0% |
| 補給に使えない | 1,476 | 8.5% |
| 不明（`vending`タグ無し） | 1,648 | 9.5% |

値の内訳は`drinks`が13,657（78.7%）で圧倒的に多い。補給に使えない側の中身は
`parking_tickets` 522・`cigarettes` 389・`public_transport_tickets` 209が大きく、
明らかに口に入らないものだけを足し上げると1,333（7.7%）になる。

（この実行時の判定表には`beverages`が入っておらず、18件が「使えない」側へ数えられている。
以後の実行では補給側に入る。割合の訂正は0.1ポイント。PBFは2026-08-15取得のもので、
本番DBの17,530件との差はその後の編集分。）

### この数字が何を決めたか（判断を1度取り違えている）

**最初に「1は見送る」と判断したのは誤りだった。** 「減らせるのは8.5%だけで再取込が要る」
＝費用対効果が悪い、と読んだが、これは**問題を「点が多くて読みにくい」として測っていた**。

ユーザー指摘で重みが直った。**当てにした自販機で飲み物が買えない方が、読みにくいことより
重い。** 8.5%は「減らせる量」ではなく「**利用者への偽の約束の量**」で、走行中に水を求めて
寄った先がたばこの機械だったときの損失は、点が混んでいることの比ではない。減る割合の
小ささを根拠に見送ったのが、そもそも見当違いだった。

**方針: 口に入らないものを売る機械は取り込まない。** 飲食物と分かるものと、`vending`が無く
分からないものは**別の種別にして地図でも分ける**（ユーザー判断）。分からないものを
「買えない」側へ寄せないのは、日本では飲料の自販機にこのタグを付けない慣習があり、
`drinks`が78.7%を占める母集団でタグ無しの多くは飲料と考えるのが自然なため。

| 種別 | 件数 | 扱い |
|---|---|---|
| 飲食物と分かる（`vending_drinks`） | 14,225（82.0%） | 「飲料自販機」として出す |
| `vending`が無い（`vending_unknown`） | 1,648（9.5%） | 「自販機(中身不明)」として薄い色で出す |
| 口に入らない | 1,476（8.5%） | 取り込まない |

**3の見立ては改める。** 起票時は「17,530件は実数より桁違いに少ないので、実在の密度を
正しく写した結果ではない」と書いたが、これは筋が通っていない。実数より少ないことは
「地図の点が実在する自販機である」ことと矛盾しない。実際に測ると中身の8割は飲料自販機で、
**地図は嘘をついていない。点が多いのは、そこに本当に多いからである。**

したがって残るのは2だけで、しかもそれは「間違ったものを消す」話ではなく
**「正しいが多すぎて読めないものを、どう見せるか」**という表示設計の話になった。

## 済んだこと

- `measure_vending_types.py`を新設（PBF 1パスで`vending`の内訳を数える。純粋関数側は
  単体テスト済み）。
- `stopPoi`・`supplyPoi`が`tileMinZoom`を宣言しておらず、タイルが配信されないズームで
  ONにしても「ズームインすると表示されます」の案内が出なかったのを直した。同じPOIタイルを
  共有する他レイヤーは宣言済みで、ここだけ漏れていた。

## 実装（2026-09-19）

- `domain/traffic.py`: `classify_vending_machine`を新設し、`SupplyPoiKind`の`vending_machine`を
  `vending_drinks`／`vending_unknown`へ置き換えた。判定に使う値の集合`SUPPLY_VENDING_VALUES`は
  計測スクリプトと共有する（別々に持つと、計測が言う残存件数と実際に入る件数がずれる）。
- `domain/osm_adapter.py`: `ALLOWED_NODE_TAGS`へ`vending`を追加。DBへ残すことで、以後は
  分け方を変えてもPBFを読み直さずに済む。
- `batch/import_pbf.py`: `--pois-only`を追加。**wayに触れないため、POIの分類を変えただけで
  道路グラフの分割が全域で古くなるのを避けられる**。
- フロント: 凡例を「飲料自販機」（`#0891b2`）と「自販機(中身不明)」（`#7dd3fc`、薄い色で
  確からしさの差を示す）の2つへ。

### 残っていること

- 本番でPOIを取り直し（`--pois-only`）、旧`kind='vending_machine'`の行を消す。
- 表示の混み具合そのもの（自販機155点/z14タイル）は、上の絞り込みでは大きく変わらない。
  種別ごとのON/OFFは既にあるため、**追加の間引きは入れない**——利用者が実際に見るズームで
  間引くと本物の補給地点が消え、低ズームだけ間引いてもこの不満は解けない（下記）。

## 参考: 表示の混み具合について測ったこと

**間引きの方式を決める前に、次の事実を踏まえる必要がある。**

- 利用者が実際に見るズーム（z14〜15）で点が多い。本番のz14タイル1枚（約2.4km四方、都心）を
  デコードすると自販機155点・コンビニ38点で、同じタイルの信号76点の2倍ある。
- **したがって「低ズームでは出さない」形の間引きは、この不満を解かない。** z12〜13を
  間引いても、利用者が見ているズームは変わらないままである。
- z14以上を間引くと、補給に使える本物の点が消える。近くにある別々の自販機を1つへ畳む
  （[T934](T934.md)のクラスタ化）のも、別々の実体を1つに見せることになり嘘になる。
- 種別ごとの表示ON/OFFは**既にある**（凡例の内訳トグル）。自販機だけ消すことは今でもできる。

残る選択肢は「点の描き方を変えて重なりを読めるようにする」（ズームに応じた半径・不透明度、
`symbol`＋衝突判定への変更など）か、「何もしない（既存の種別トグルで足りるとする）」になる。
どちらも見た目の設計判断のため、利用者と詰めてから実装する。

## 検証

- **緩和は影響を測ってから入れる**。絞り込み・間引きを入れるときは、それによって地図から
  消える点の件数と全体に対する割合を実測し、このファイルへ書く。
- 「実装した」ではなく「効いている」を見る: 点が埋まっている実在の地点を1つ選び、変更前後の
  描画点数を実機で数える（[T934](T934.md)で使った、配信中のタイルをデコードして数える方法が
  そのまま使える）。
