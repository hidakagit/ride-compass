# T919. 密度材料（事故・交差点・POI・土地被覆）を区間単位で持つ

状態: 未着手
規模: M

## 背景

[T918](T918.md)で路面タイルの単位が区間（road_edges）になったが、**way単位で事前集計した
材料はway全体の平均のままである**。1本のwayに属する全区間へ同じ値が載る。

対象は`way_attribute_counts`由来の密度（`accident_per_km`・`intersection_per_km`・
`poi_*_per_km`。正規化に使う`length_m`は`ST_Length(w.geom)`＝way全体の長さ）と、
`way_landcover`由来のクラス別割合（`*_pct`）。

T918の時点では**表示は何も変わっていない**（way1本＝1フィーチャーだった頃と同じ値が、
区間ごとに複製されて出るだけ）。悪化ではないが、区間単位で持てば見えるようになるはずの
差が、way平均に均されたままになっている。

## 何が見えていないか

事故が1箇所へ固まっている長いwayは、事故の無い区間まで同じ密度で塗られる。交差点密度も
同様で、交差点が密な区間とそうでない区間が1本の道の中で区別できない。

## 対応方針（未確定）

`way_attribute_counts`と同じ集計をedge単位で持つ必要がある（`precompute_edge_attribute_counts.py`
が既にedge単位の集計を持つため、そちらへ寄せられるかを先に見る）。焼き込みSQLの
JOIN先をosm_way_idからedge_idへ替え、way単位のズーム（z13以下）では従来どおりway集計を
引く形になる見込み。

## 先に測ること

- way内で区間ごとの密度がどれだけばらつくか（均されて消えている差の大きさ）。
  ばらつきが小さければこのタスク自体が不要である
- edge単位の集計テーブルを持つことによるDB容量・バッチ所要時間の増分
