# T919. 土地被覆のクラス別割合を区間単位で持つ

状態: 計測待ち（計測スクリプトは実装済み、実データでの実行待ち）
規模: M

## 背景

[T918](T918.md)段階5で、事故・交差点・POIの密度は区間単位の真値
（`edge_attribute_counts`）から焼くようにした。**土地被覆（`*_pct`）だけが残っている**
——`way_landcover`しか無く、区間単位の集計そのものが存在しないため。

密度3種と違い、これは「あるのに使っていない」ではなく「まだ作っていない」である。
`precompute_way_landcover.py`に相当する区間単位のバッチ（`edge_landcover`）を新設しない
限り切り替えられない。

## 何が見えていないか

長いwayの片側だけが森を抜ける道は、森に入っていない区間まで同じ`trees_pct`で塗られる。
市街地と郊外をまたぐ道も同様に均される。

## 先に測ること

**way内で区間ごとの土地被覆がどれだけばらつくか。ばらつきが小さければこのタスクは不要。**

測らずに着手すると、rasterio経由の重いバッチ（`precompute_way_landcover.py`は
`run_chunked_precompute`で全way走査する）をもう1本増やし、DB容量とバッチ所要時間を
払ったうえで見た目が変わらない、という結果になりうる。

### この計測は実装とほぼ同じコストである

区間ごとの土地被覆を知るには区間ごとにラスタを読むしかなく、それが新バッチの本体そのもの
である。**測定と実装を2回に分けても、重い計算は2回払うことになる**ため、
`benchmarks/bench_t919_edge_landcover.py`は`precompute_way_landcover.py`の
`build_ring`・`count_pixels_in_ring`・`class_percentages`をそのまま呼び、行を書かずに
way内のばらつきだけを集計して捨てる形にした（別の数え方をすると、測った差が実装で
再現しない）。区間の単位はタイルと同じ鍵で逆方向を潰す——タイルが1フィーチャーとして出す
単位に合わせないと、測った差が地図の差と対応しない。

出すのは配線済みクラスごとの**way内レンジ**（そのwayの区間の最大値−最小値、ポイント）の
中央値・p90・p99・最大と、`NOTABLE_RANGE_POINTS`（20pt）以上のwayの割合。

### 判断の目安

- notable率が数%なら、区間単位で持ってもほとんどの道で同じ色になり、このタスクは不要。
- 無視できない割合なら、そのぶんが今は見えていない。

### 実行

```
$env:DATABASE_URL = "postgresql+asyncpg://ridecompass:ridecompass@localhost:5432/ridecompass"
.venv\Scripts\python.exe -m benchmarks.bench_t919_edge_landcover --raster data\lulc\54S_2024.tif
```

前提: 対象範囲が取込済みで、`presplit_road_graph.py`が`road_edges`を埋めていること。

### 効いていることの確認（計測器そのもの）

- way内レンジの定義は`tests/test_bench_t919_edge_landcover.py`が固定する
  （全区間同値ならレンジ0、配線クラスが増えたら対象に入る）。
- 区間の単位がタイルと一致することは実DBで確認した: 3ノードのwayを隣のwayと交差させると
  `road_edges`は両方向込み4本になり、計測SQLは2区間として返す。1区間のwayは対象外になる。

## 対応方針（未確定）

`precompute_way_landcover.py`と同じラスタ読み出しを`road_edges`に対して回し、
`edge_landcover`へ入れる。タイル側は密度3種と同じ`_density_column_sql`と同じ方針
（区間単位のフィーチャーは区間の行、それ以外はwayの行へ落とす）で引く。
