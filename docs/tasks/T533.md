# T533: 過去の経緯だけで保持している冗長な分割・マージ漏れの総点検

状態: 調査完了・一部対応済み（2026-09-02。Explore agentでbackend/frontendを横断監査）

## 背景

T522派生の調査で、`get_edge_materials_batch`（改善計画T248）が既に1回のJOINクエリで
全材料を1行取得しているにもかかわらず、Python側で意図的に4つの辞書
（surface_attributes/edge_attribute_counts/way_tags/elevation_attributes）へ
再分割したままだった（クエリ統合時に戻り値の形を直し忘れた技術的負債）ことが発覚した。
同種の「過去の経緯（旧実装・旧クエリ本数等）だけを理由に分割されたまま残っている構造」や、
逆に「本来は分けておくべきなのに安易にマージされている構造」が他にも無いか、
リポジトリ全体を横断的に点検する。

## 調査結果・対応（2026-09-02）

backend中心に5件発見（frontendのhooks/servicesは同種の明確な候補なし）。

**対応済み（2件、T536の作業領域と無関係なため今回実施）**:
1. `AttributeRepository.get_edge_attribute_counts`（`road_graph_repository.py`、
   ファサード委譲含む）— `get_edge_materials_batch`のJOIN統合後、本番コードから
   一切呼ばれなくなっていたデッドコード。削除した（`test_graph_service.py`の
   Fakeが持っていた対応する未使用カウンタも併せて削除）。
2. `jma_amedas_service.py: _nearest_station`— `(station_id, 名称, 緯度, 経度)`の
   4要素タプルを返していたが、唯一の呼び出し元は`station_id`以外を即座に破棄していた。
   `str | None`（station_idのみ）を返す形へ簡略化した。

**保留・[T543](T543.md)へ分割（3件、[T536](T536.md)が現在編集中の
`domain/evaluation.py`・`graph_service.py`に触れるため）**:
3. `compute_edge_costs_bulk`とその周辺（`evaluation_service.py`・
   `MaterialExtractionContext`）— `EdgeMaterialBundle`統合前の7個の個別辞書引数構成の
   まま。T529以降は本番経路で実質デッドコード（回帰オラクル用途のみ）と判明。
4. `graph_service.py: _build_search_materials_uncached`の二重取得 — 取得済みの
   `surface_attributes`を使わず、直後の`get_edge_materials_batch`結果のsurface部分を
   捨てて上書きしている（コード中のコメントで無駄を自認済み）。
5. `get_way_attribute_counts`の無名4要素タプル（`road_graph_repository.py`・
   `domain/evaluation.py: axis_inspector_breakdown`）— 名前付き型
   （`EdgeAttributeCounts`）が既にあるのに、こちらだけ位置アンパックのタプルのまま。
