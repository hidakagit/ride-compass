# T573: 本番DB再構築（disaster recovery）の包括的手順書整備・検証

状態: 完了（2026-09-04。既存本番VM上の使い捨てPostgreSQL+PostGISクラスタで
bootstrap_fresh_db.py→import_pbf.py→refresh_derived.py→ルート生成までを実地検証）

## 背景

T281段階2（`refresh_derived.py`）実装完了後、ユーザーから「本番DBをイチから再構築する
ような手順」の要否を問われた。現状、以下2系統の再構築フローがそれぞれ個別には存在するが、
1つの検証済み手順書としてまとまっていない。

1. **定常運用フロー**（OSM再取込時）: `import_pbf.py`（差分UPSERT）→
   `refresh_derived.py`（T281段階2、④〜⑨の派生データ再構築）。
2. **新規環境向けfresh bootstrap**: `create_tables()`→`apply_pending_migrations()`→
   `bootstrap_fresh_db.py`（`axis_definitions_snapshot.json`投入）。CLAUDE.md「軸定義
   （axis_definitionsテーブル）の新規追加・削除...」節に記載済みだが、稼働中DBへの適用は
   想定外（意図的に本番からは呼ばない設計）。

ユーザー承認: 使い捨て検証環境は新規Oracle Cloudインスタンスを追加作成せず、既存VM上に
別のPostgreSQL+PostGISコンテナ（本番DBコンテナとは別ポート・別ボリューム）を一時起動して
検証する。

## 対応方針（着手時に確定）

1. 既存VM上に検証用PostgreSQL+PostGISコンテナを一時起動。
2. まっさらな状態から: `create_tables()`→migration適用→`bootstrap_fresh_db.py`
   （axis_definitions投入）→PBF取込（`import_pbf.py`、検証は小規模bboxで行う）→
   事故データ・指定路線データ取込→`refresh_derived.py`（派生データ再構築）→
   タイル永続キャッシュ・スコア行列キャッシュの版数確認、の一連を実際に実行し詰まる箇所を
   洗い出す。
3. 検証結果を踏まえ、定常運用フロー・disaster recoveryフローの両方を1つの手順書
   （新規docs、または既存docsへの追記。着手時に置き場所を決定）としてまとめる。
4. 検証用コンテナ・ボリュームは検証後に削除し、本番環境への影響が無いことを確認する。

## 完了条件（着手時に精緻化）

- 使い捨て環境での一連の手順（fresh bootstrap→PBF取込→派生データ再構築）が実際に
  成功することを確認。
- 手順書がdocsとして存在し、CLAUDE.md等から参照される。
- 検証用リソース（コンテナ・ボリューム）が削除され、本番環境に影響が残っていないことを
  確認。

## 実装メモ（2026-09-04）

対応方針どおり既存VM上に別ポート（15432）の使い捨てPostgreSQL 18+PostGIS 3.6クラスタを
`pg_createcluster`で作成した。当初Dockerの`postgis/postgis`公式イメージを使う想定だったが、
このOracle VMがARM64（Ampere A1）でイメージがamd64専用（`exec format error`）だったため、
本番と同じaptパッケージによるネイティブクラスタ方式へ切り替えた（副産物として、ARM64環境
向けの制約として[docs/disaster-recovery.md](../disaster-recovery.md)へ記録）。

検証手順（`bootstrap_fresh_db.py`→`import_pbf.py --bbox`東京都心→`refresh_derived.py`→
backend起動→`POST /api/routes/generate`での実ルート生成確認）はすべて成功。詳細な数値・
未検証範囲は[docs/disaster-recovery.md](../disaster-recovery.md)「検証実績」節に記載。
検証用コンテナ・イメージ・クラスタ・cloneディレクトリは全て削除済み（`pg_lsclusters`で
`main`のみ残存を確認、ディスク使用量は検証前と同水準）。

手順書は新規`docs/disaster-recovery.md`として作成した（定常運用フロー・disaster recovery
フローの両方、[deployment-sync.md](../deployment-sync.md)から相互参照）。
