# T958: 評価が要求する形のまま読める区間テーブルを持つ

状態: 未着手（2026-09-19起票。採番時にT957が並行セッションと衝突し、T958へ振り直した。**トリガー: [T956](T956.md)完了後に冷パスを再測定し、残りがまだ問題になる場合**）

## 背景

探索が要求するのは常に「あるz12タイルの全区間の材料」という単一の形なのに、それを毎回
`road_edges`へ属性テーブル群をLEFT JOINし指定路線を相関EXISTSで判定して組み立てている。
本番実測で、同じ結果を1テーブルから走査すると2,052ms→800ms（[T955](T955.md)）。

書き込み側がバッチごとに分かれているのは正しい。用意していないのは**読み出しの形**である。

詳細はこのファイルへ追記する。

## これは効率化ではなく、仕組みを1つ増やす提案である

[T955](T955.md)の段階A（[T956](T956.md)）が既存の経路を効率化するのに対し、こちらは
**新しい派生テーブルを1つ増やす**。増えるのは実体だけでなく、「どのバッチが走ったら
これは古いか」の判定で、これは`docs/batch-pipeline-dependencies.md`が書いている
「派生データの取り残しで軸が黙って抜け落ちる」クラス（T74・T101・T242の本番障害）である。

稼ぎは1タイルあたり約800ms（SQL 2,052ms→800ms、本番実測）。段階Aが7,830ms→約3,100msを
稼ぐのに対する上乗せ分でしかない。**段階Aの後に実測してから判断する**（ユーザー判断）。
