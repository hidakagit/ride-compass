# T944. キャッシュと世代の後始末（T848・T929の射程の外に残ったもの） 規模M

状態: 完了（2026-09-19起票・2026-09-20完了、統合レビュー第11回のP2/P3）

## 背景

T848（世代の実行時配信）とT929（キャッシュ世代まわりの欠陥3件）の後に残った、
鍵・無効化の粒度・docstringの主張のずれ。**対象は[history/2026-09-19_all.md](../../.claude/commands/review/history/2026-09-19_all.md)「Findings（P2）」の
「キャッシュ・世代まわり」節（1〜8）と、「契約・docs乖離」の53・55・56**、および
P3のうち同節が指すもの（`tile_serving.py`の世代確認の置き場、`landcover_raster`の
「記憶しない」、抑制の初期値、`migrations/0013`のバックフィル値）。

とくに次の3つは**黙って壊れる**型で、他より優先する。

- `--pois-only`が鮮度台帳の高水位を進め、way由来の6テーブルが一斉に「古い」判定になる
  （2026-09-18に本番適用済み。誤警報が常態化すると本物の陳腐化を見落とす）
- `dynamic_way_value_cache`の鍵に世代が入らず、世代更新後に勾配レンズが最大24時間・
  バケットごとに出たり消えたりする
- 土地被覆ラスタが部分構成で開けたまま固定され、欠けたゾーンの透明タイルが正しい鍵で
  恒久的に残る

## 対応方針

`tile_cache.clear_all()`は**症状（イベントループが止まる）ではなく欠陥（無効化の粒度が粗い）**を
直す。`asyncio.to_thread`へ逃がすのは暫定で、それで閉じたことにしない。
`docs/caching.md`「全消しは運用操作としてのみ残す」という正本と実装のどちらを正にするかを
先に決める。

## 対応（2026-09-20）

### 1: 取込runが「何を書いたか」で高水位を分ける

`MAX(id) WHERE status='succeeded'`は、**way・nodeを1行も書かない`--pois-only`の成功runまで
高水位にしていた**。ただしレビューが挙げた6テーブルのうち`edge_attribute_counts`は区間ごとの
停止要因POI数を持つため、POIが入れ替われば**本当に古い**——一律に無視するのも誤りになる。

そこで`SourceRunSpec.wrote_columns`で「**その取込が何を書いたときにこのテーブルが古くなるか**」
を宣言させ、高水位のSQLをそこから組み立てる（`osm_import_runs`へ`poi_count`列を足した。
migration 0045）。件数列がNULLのrunは「不明」として**書いたものとして数える**——列を足す前の
行が過去の全量取込であることを踏まえた安全側の倒し方で、これにより既存行の埋め戻しが要らない。

高水位の持ち場も`run_table`をキーにした共有辞書から**テーブル×情報源**へ移した。同じ
`osm_import_runs`でもテーブルごとに答えが変わるため、共有辞書のままだと先に計算した方が
使い回される（この形の欠陥をそのまま残すところだった）。

### 2: 無効化の粒度を直す（全消しをやめる）

**欠陥は「公開GETで同期`rmtree`する」ことではなく、サーバー側の鍵に世代が入っていないこと。**
路面・POI・事故タイルのディスクキャッシュのパスは形の署名だけを持ち、SQLが同じままバッチが
中身を作り直すと鍵が変わらない。それを`tile_cache.clear_all()`で帳消しにしていた。

ブラウザのURLへ入るのと**同じ文字列**（`<DBの世代>-<形の署名>`、`served_tile_version`）を
サーバー側の鍵にも使う形へ変え、世代が変われば別の鍵になるようにした。結果として自動経路
からの全消しは不要になり、`clear_all`の呼び出しは管理API（`POST /api/basemap/refresh`）
1箇所だけになった——`docs/caching.md`「全消しは運用操作としてのみ残す」と実装が一致する。
引かれなくなった古い鍵は`prune_to_size_limit`が古い順に回収する。

### 3: 動的way値キャッシュの鍵へ世代を入れる

鍵は`feature_key`（＝`road_edges`の中身そのもの）と一致して初めて意味を持つのに、形の署名
だけで作っていた。バッチが作り直すと同じSQLでも鍵の値が変わるため、世代をまたいだエントリが
どの地物にも一致しないまま生き残り、TTL（勾配は24時間）まで色が静かに消える。

世代は**呼び出し側が必須キーワードで渡す**（`revision`）。infrastructureから
`services/derived_data_revision_service.py`を読むと依存が逆向きになるため受け取るだけにし、
省略できない形にして渡し忘れをその場の失敗にした。

### 4: 鍵は「設定された構成」ではなく「実際に開けている構成」から作る

docstringは「**開いているラスタの構成**も鍵に入れる」と述べるのに、実装は
`settings.lulc_raster_paths_list`（設定された構成）の指紋だった。デプロイはラスタの取得と
コンテナ入れ替えを別のステップで行うため、**起動時に1枚だけ置かれていない**ことが実際に
ありうる（モジュール自身のコメントがその想定を書いている）。そのとき欠けたゾーンの透明な絵が
「完全な構成」の鍵で恒久的に残る。`landcover_raster.opened_raster_paths()`を足して鍵をそちら
から作る。

### 5: 今の区間の切り方に無い行を回収する

`edge_landcover`の鍵は（way＋両端ノード）で`edge_id`ではないため、兄弟の
`edge_attribute_counts`のようなFK `ON DELETE CASCADE`を張れない。再splitで切り方が変わると
古い行が取り残され、**切り方が元へ戻った瞬間に古いラスタ・古いアルゴリズム版の値が生きた値
として復活する**（増分実行は「値を持つ行がある」ので再計算対象から外す）。拾い直せる合図が
他に無いため、バッチが計算の前に毎回アンチジョインで掃除する（`LandcoverPlan.prepare`）。

### 6〜8・55・56: 主張と実装のずれ

- `prune_to_size_limit`はLRUではなくFIFO（`get`はmtimeを更新しない）。「現に読まれている
  タイルは書き直されて新しくなる」は成立しない。何順で消えるかを事実へ書き換えた。
- `regionApi.ts`の「世代を手で上げる」手順が、直後の「実行時にbackendから受け取る」と正面から
  矛盾していた。手で上げる手順を撤去し、**意味自体を変える非互換変更のときだけ**デプロイ順序に
  注意が要る、という残るべき内容だけにした。
- `export_openapi.py`が「タイルの世代はここへ書かない」と書いて13行下で`landcover.tile_version`
  を書いていた。例外である理由（DBを読まず、コードとクラス定義だけから決まる）を書いた。
- `graph_material_cache.clear()`の「本番コードパスからは呼ばない」は成り立っていない
  （世代変化時に`clear`として渡される）。
