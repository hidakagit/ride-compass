# T482. GitHub Actions CIの`e2e`ジョブが直近複数コミット連続で失敗している原因を調査する

状態: 起票

- 背景: T462（openrouteserviceエンジン撤去）関連のpushを`gh`CLI未導入の環境から
  GitHub REST APIで確認したところ、`e2e`ジョブ（Playwright、`npm run test:e2e`）が
  直近5コミット連続（`b77dbff9`・`da61193a`・`5a75dcb0`・`fc5e1209`・`7672fbe3`）で
  失敗していることが判明した。対象コミットはT460・T471・T472・T462関連のpushで、
  互いに無関係な変更内容にもかかわらず同じジョブが連続して赤くなっている。
  `backend`/`frontend`の各CIジョブと`Deploy Backend to Oracle VM`ワークフローは
  同じコミット群ですべて成功しており、本番デプロイ自体はブロックされていない
  （`deploy-backend.yml`は`e2e`ジョブの結果に依存せず独立して走る構成のため）。
- 未確認事項: 失敗した`npm run test:e2e`ステップの実際のログ内容
  （`https://api.github.com/repos/hidakagit/ride-compass/actions/jobs/<job_id>/logs`
  はリポジトリ管理者権限が必要で、認証無しのcurlアクセスでは`403 Must have admin
  rights to Repository`が返り取得できなかった）。フレーキー（タイムアウト・環境依存）
  なのか、実際の回帰（UIの挙動変化・selector変更漏れ等）なのか未判定。
- 対応方針: `gh`CLIまたはリポジトリ管理者権限を持つ環境から
  `gh run view --log-failed`等でログを取得し、原因を特定する。フレーキーなら
  再実行で復旧するか・タイムアウト値等の調整を検討する。実際の回帰なら、
  直近5コミットのうちどの変更が原因かを`git bisect`的に絞り込み、修正するか
  該当e2eテストを見直す。
- Confidence: Low（ログ未確認のため原因不明。調査タスクとして起票）。
- 規模S〜M（調査してみないと実際の規模は不明）。

## 追記（2026-08-31、ユーザーが実際のCIログを貼付、調査続行）

ユーザーから`7672fbe3`実行時の`npm run test:e2e`実ログを共有してもらい、以下が判明した:

- 2テスト中「ルート生成→候補一覧の表示」は**成功**、「地図レイヤーのON/OFF切替」のみ失敗。
  失敗箇所は`page.getByRole("button", { name: "観測", exact: true }).click()`
  （`e2e/smoke.spec.ts:33`）が30秒タイムアウト（リトライ1回も同様に失敗）。
- ログには`[WebServer] Failed to proxy http://localhost:8000/api/jma-tile/bosai/jmatile/data/risk/targetTimes.json`
  というECONNREFUSEDが大量に出ている。`frontend/e2e/fixtures.ts: installApiMocks`は
  `/api/jma-tile/**`・`/api/axis-catalog`のどちらもモックしておらず、ci.ymlのコメントが
  約束する「バックエンド・外部APIに依存しない」という設計と食い違っている
  （**確認済みの改善点、規模S**: `installApiMocks`へこの2エンドポイントのモックを追加する
  べき）。
- ただし、上記ノイズが「観測」ボタン未表示の**直接原因である可能性は低い**と判断した:
  「観測」ラベルは`useAxisCatalog`フック（`frontend/src/hooks/useAxisCatalog.ts`）が
  `useState(FALLBACK_CATALOG)`で**同期的に**静的フォールバック値を初期状態に持つため、
  `GET /api/axis-catalog`の成否を待たずに描画されるはず（コード確認済み、
  `frontend/src/types/generated/axis-catalog.json`の`category`フィールド由来）。また、
  「ルート生成→候補一覧の表示」テストも同じ`page.goto("/")`でMapView・jma-tile関連の
  同じネットワークノイズを受けるはずだが、こちらは成功しているため、ノイズ自体が
  ページ全体をブロックしているわけではなさそうだと考えられる。
- ローカルでの再現を試みたが、`playwright.config.ts`の`webServer`（`npm run build &&
  npm run start:standalone`、timeout 180秒）がbuild段階で180秒以内に完了せず
  `Error: Timed out waiting 180000ms from config.webServer`で終了した。これはCIとは
  別の、このdev機固有のビルド遅延（[[frontend-dev-server-map-load-hang]]メモリに記録済みの
  既知の傾向と類似）と考えられ、CI側の実際の失敗（webServer自体は起動しテストが走った後の
  特定ボタンのタイムアウト）とは異なる症状のため、有効な再現にならなかった。
- **未解明**: 「観測」ボタン自体がなぜCI環境でのみ30秒以内に描画されない/クリックできないか
  の直接原因。候補: (a) MapOverlayControls側でmap本体の`styledata`等のイベント待ちに
  なっており、jma-tile等の失敗した非同期処理が別の形でこのイベント発火を遅延させている、
  (b) T166/T406/T418等の直近のUI再編でこの折りたたみ見出しの表示条件・ラベルテキストが
  変わり、smoke.spec.tsが追従していない（テスト側の陳腐化）、(c) CI環境（GitHub Actions
  ubuntu-latest）特有の描画パフォーマンス起因のタイムアウト。
- 次の一手: (1) 上記の`installApiMocks`拡張は原因究明とは独立に実施する価値がある
  （ci.ymlの設計意図に合わせるだけでも正当化できる）。(2) 本当の原因特定には
  `actions/upload-artifact`でCIが保存している`playwright-report`
  （`frontend/playwright-report/`、失敗時のみ7日間保持）内のtrace.zip・スクリーンショットを
  `gh`CLI等で取得して確認するのが最も確実。(3) MapOverlayControls.tsxの「観測」グループ
  見出し（flat header）の実際のレンダリング条件を精読し、mapインスタンスの初期化完了に
  依存する経路が無いか確認する。
