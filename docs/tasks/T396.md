# T396. 軸スタジオの評価軸合成ロジックを4テンプレートから2プリミティブ+合成へ再設計 規模M

状態: backend・データ移行・OpenAPI契約・フロント互換修正まで完了（2026-08-29）。
UIの3カード化（表側の再設計）は別スコープとして未着手。

## 背景

軸スタジオの設計精査セッション（ユーザーとの対話、2026-08-29）で、外部から持ち込まれた
2件の設計案（DAGベースの「3ノード型」構想、動的属性拡張案）を実装コードと照合したところ、
大部分は現状と乖離していたが、1点だけ実質的な改善余地が見つかった: 現行4テンプレート
（`breakpoint_linear`/`recipe_then_breakpoint_linear`/`categorical`/`flag_sum`）は
実質2つの独立した原型に還元できる。

- **連続演算**: 材料（または他軸のスコア）を重み付き結合し、区分線形カーブでスコア化する。
- **離散演算**: 単一の離散値をテーブル引きでスコア化する。

「合成」（他軸のスコアを次の軸の入力として使う階層構造、改善計画T292）は独立した
プリミティブではなく、連続演算の結合ステップの性質——`terms`の各materialが材料id・
他軸のaxis_idのどちらも区別なく指せることから生じる。

## 対応方針・実装内容

### backend（domain層）

- `domain/axis_definitions.py`: `FlagSumShape`を撤去。`BreakpointLinearShape.kind`から
  `recipe_then_breakpoint_linear`別名を撤去（`Literal["breakpoint_linear"]`のみ）。
  `AxisShape = BreakpointLinearShape | CategoricalShape`（2型）。`AxisDefinition.materials`
  プロパティ・`evaluate_axis_scalar`/`evaluate_axis_array`のFlagSumShape分岐を撤去。
- `domain/axis_templates.py`: `evaluate_flag_sum`（旧flag_sum専用実装）・
  `evaluate_recipe_then_breakpoint_linear`（`evaluate_breakpoint_linear`のエイリアス）を
  撤去。目論見書の「テンプレート4種の線引き」という前提自体を今回見直したため、
  この2つを「意図的なKEEP」として残す理由も無くなった。
- `domain/axis_display.py`（地図ramp表示の自動導出）: 旧`FlagSumShape`という**型**で
  分岐していた閾値計算（達成しうる合計値の部分和・隣接中間点）を、
  「`BreakpointLinearShape`で全termがboolean材料か」という**構造**判定へ書き換えた。
  型を消すだけでは night軸の地図表示が自動導出できなくなる（`BreakpointLinearShape`側の
  既存ロジックは「単一材料・weight=1.0」限定のx値流用のみで、複数boolean termの部分和
  計算には対応していなかったため）——この構造判定の追加が本タスクの実装コストの主要部分。
  materialが12件超のboolean termsは組合せ爆発（2^N）を避けるため自動導出対象外にする
  安全弁を追加（旧`FlagSumShape.flags`のPydantic側`max_length=12`が撤去に伴い消えたため、
  同じ安全弁をここへ移設）。
- `api/routers/axis_admin.py`: `_check_materials_are_known`のFlagSumShape分岐を撤去
  （`BreakpointLinearShape`はnumeric/boolean材料、`CategoricalShape`はboolean/categorical
  材料、という2分岐に単純化）。

### データ移行

- `backend/fixtures/axis_definitions_snapshot.json`: night軸（唯一の`flag_sum`利用軸）の
  `shape`を新形状（`breakpoint_linear`、terms=[no_lit×50, has_tunnel×50]、
  breakpoints=[[0,0],[100,100]]）へ書き換え。
- **dev DB実データ**: night軸の`shape_params`カラムを新形状へ移行済み（ユーザー承認を
  得た上で実施）。通常のaxis_admin API経由（`AxisRegistryAdminService`）では、更新前に
  まず`get()`が旧`flag_sum`のJSONをPydanticでパースしようとして失敗する（型を撤去した
  ことで読めなくなったため、鶏と卵の状態）ため、この1回に限り`shape_params`カラムを
  直接UPDATEする一時スクリプトで実施し、実行後に削除した（他フィールドは無変更、
  `is_published`も触っていない）。移行後、通常のrepository経由での読み込みが正常に
  戻ったことを確認済み。
- **本番DB**: 未着手。本タスクでは触っていない。本番デプロイ時にdevと同じ移行
  （`shape_params`のみの直接UPDATE、または不可なら同等のワンショットスクリプト）が
  必要——デプロイ前に対応すること（デプロイパイプラインがmigration適用は自動化済みだが、
  この種の非DDL・行データ限定の移行は自動化対象外）。

### 契約同期（CLAUDE.md「コミット時の同期ルール」）

- `backend/scripts/export_openapi.py` → `frontend`側 `npm run generate:api`を実行し、
  `frontend/src/types/generated/`（`api.d.ts`・`openapi.json`・`axis-catalog.json`）を
  再生成・確認済み（`FlagSumShape`型・`kind`の`recipe_then_breakpoint_linear`選択肢が
  除去されたことを確認）。

### フロントエンド互換修正（`AxisComposer.tsx`ほか）

UIの4枚のカード（「数値の大きさに応じて」/「はい/いいえ、または種類ごとに」/
「複数の要素の有無を数えて」/「他の軸を重みで足し合わせて」）自体は変更していない
——表側の入り口の数と裏のprimitive数を一致させる必要は無いという判断（3カード化は
別スコープ、下記「残作業」参照）。

- `buildShape()`: 保存する`shape.kind`を常に`"breakpoint_linear"`または`"categorical"`へ
  正規化。旧flag_sumカードの入力（`flags`+`cap`）は`terms`（`weight`=旧`points`）＋
  `breakpoints=[[0,0],[cap,cap]]`（恒等クランプ）へ変換する（`cap`未入力時は全フラグの
  points合計を既定のクランプ上限にする）。
- `draftFromExisting()`: 保存済み`kind`だけでは元のカード種別を判別できなくなったため、
  `terms`の構造から推定し直す——全termが他軸参照（`materialOptions`に見つからない）なら
  「他の軸を組み合わせる」カード、全termがboolean材料かつbreakpointsが恒等クランプの形
  （`[[0,0],[N,N]]`）なら「複数の要素の有無を数える」カード、それ以外は通常の
  「数値の大きさに応じて」カードとして初期表示する（`domain/axis_display.py`の構造判定と
  同じ考え方）。
- `types/route.ts`: `FlagSumShape`型を撤去、`AxisShape`を2型のunionへ。
- `AxisStudio.tsx`: `materialIdsOf()`のFlagSumShape分岐を撤去。
- テスト（`AxisComposer.test.tsx`）: `flagSumShape()`ヘルパーを新形状ベースへ更新、
  `recipe_then_breakpoint_linear`を直接kindとして使っていた箇所を`breakpoint_linear`へ
  更新（編集読込テストは材料IDを実材料から軸参照風の非材料IDへ変更し、構造判定が
  正しく機能することを確認する内容に変更）。

## 残作業・未決定事項

- **UIの3カード化**: バックエンドの2プリミティブ+合成という整理に合わせ、表側も
  「なめらか評価」「ぴったり評価」「かけあわせ評価」の3カードへ再設計する方向性は
  セッション内で合意済み（ウィジェット選択: 係数はスライダー、そのまま/絶対値は
  ラジオボタン、折れ点はドラッグ式曲線エディタ、かけあわせは折れ点編集UIを出さず
  純粋な重み付き結合のみに絞る）。今回はスコープに含めず、既存4カードUIの互換性維持に
  留めた。着手する場合は本タスクとは別にタスクエントリを起票すること。
- **本番DBのnight軸移行**: 上記の通り未実施。デプロイ前に対応が必要。
- **連続→離散の橋渡し（しきい値/バケット化）**: 検討したが保留。具体的な需要が無い
  ため、必要になった時点で再検討する。
- **材料の排他帰属制約の緩和**: 検討したが維持。DB制約ではなくアプリ層検証のみのため
  後から緩和しても低コストと確認済み。
- **公開軸の重複度審査（Overlap Index）機構**: 新設しない。既存の排他帰属制約で足りる。
- **事故密度材料抽出の重複**（`_extract_accident_count_per_km_year`と
  `count_per_km_extractor`の統合余地）: 本タスクとは別件として認識したが未着手。

## 設計精査の記録

セッション内で外部から持ち込まれた2件の設計案（DAGベースの3ノード型構想、動的属性
拡張案）を却下した理由の詳細（`axis_dependencies`専用テーブルの不採用、材料排他制約の
維持理由、ベクトル演算[風・西日等]を独立primitiveにしない理由の`wind_penalty`実例による
反証など）は、セッション内で作成したArtifact「軸スタジオ設計仕様」に記録している
（Claude Code上の私有Artifactのため本リポジトリには実体が無い。要点は本ファイルの
上記「対応方針」に反映済み）。
