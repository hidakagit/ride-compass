# T650. コピペ検出で挙がった重複を個別に潰す

規模S〜M。2026-09-07、独立して直せる分（CSS・バッチ骨格）を実施。テスト骨格は[T644](T644.md)の実装共通化と連動するため未着手。

## 背景

[T648](T648.md)でコピペ検出（jscpd）をレビュー基盤へ組み込んだ結果、**ファイルをまたぐ
完全一致クローンが48件・713行**判明した（テスト・スクリプトを含む全ソースが対象、同一
ファイル内の重複は除外）。検出の仕組みは入ったが、**既に存在する重複はそのまま**である
（T648の目的は「新しい写経が増えたときに気づけること」であり、既存件数をゼロにすることでは
なかった）。

**過半はテスト側にある**。実装で共通化すればテストの重複も連動して減る関係のため、
実装側（[T644](T644.md)のRedis cache-aside共通化）と切り離して着手すると二度手間になりうる。

## 対応方針（案）

CSS 3件とバッチ`run()`骨格は性質が違うため、着手するなら分けて進める。

- **管理画面CSS**: 共通のパネル外枠クラスを1箇所へ置く。ただし`components/ui/`へ置くか
  各パネルのCSS Modulesのまま共有するかは、[frontend/page-composition.md](../modules/frontend/page-composition.md)の
  「汎用UI部品はここへ集約する」方針と突き合わせて決める。
- **バッチ`run()`骨格**: `precompute_*.py`4本が同じ引数・同じ手順（DB接続→dry_run分岐→
  集計→書き戻し→件数返却）を持つ。共通の骨格関数へ寄せられるか、バッチごとの差異が
  大きいかを確認してから判断する。

## 保留した場合の影響

機能上の実害は無い（いずれも動作しているコード）。ただし`review_checks.py duplication`の
前回値が48件のまま据え置かれるため、**「増えたら気づく」という監視の基準線が高いところに
固定される**。基準線を下げておくほど、新しい写経が相対的に目立ちやすくなる。

## 実施結果（2026-09-07、CSS・バッチ骨格）

**48件・713行 → 43件・618行**（5件・95行を削減）。

### 管理画面CSS（36行＋23行）

`BackendLogsPanel`・`DerivedDataFreshnessPanel`・`MaterialCoveragePanel`の3ファイルが
`.panel`/`.heading`/`.hint`/`.error`/`.controls`/`.summary`を**完全に同一の定義**で
持っていた。`components/ui/adminPanel.module.css`へ集約し、各パネルからは`composes`で
参照する（クラス名は呼び出し側のまま保つため、コンポーネント側の変更は不要）。
パネル固有の見た目（表・トグル・列幅）は各CSS Modulesに残す。359行→327行。

### バッチのエンジン管理（14行＋11行×3）

`precompute_*.py`5本と`presplit_road_graph.py`の**6ファイル**が、

```python
engine = create_async_engine(database_url or settings.database_url)
session_factory = async_sessionmaker(engine, expire_on_commit=False)
try:
    ...
finally:
    await engine.dispose()
```

という同じ前後を持っていた。`_common.py`（既に「複数バッチが共通で必要とする処理を
ここへ集約する」場所として存在）へ`batch_session_factory`（`asynccontextmanager`）を
追加し、`async with batch_session_factory(database_url) as session_factory:`へ寄せた。

`try`/`finally`が消えてネストが1段浅くなり、**途中`return`でも確実にdisposeされる**
（元の形も`finally`で保証していたが、`return 0`が複数あるバッチでは追いにくかった）。
