# T929: キャッシュ世代まわりの欠陥3件（繰り返し全消去・未実装の宣言・掃除の無い置き場）

状態: 完了（2026-09-19。2026-09-18起票）

## 1. 世代が読めないと、全タイルキャッシュを繰り返し消す

`cache_generation.py: sync_with_revision`は`revision is None`のとき「常に捨てる・記録し
直さない」設計で、次回も同じ判定になる。[T848](T848.md)がその先へ`tile_cache.clear_all()`
（基礎地図・DEM込み）を繋ぎ、その欠陥修正がさらに発火点を軸カタログの取得（＝ページを
開くたび、TTL 300秒）へ広げた。`derived_data_meta`の行が無い環境では、5分ごとに全タイルが
消え続ける。本番は行があり（`revision=12`を確認）現時点では発火していないが、消える範囲と
頻度の両方が広がっている。

## 2. `UNKNOWN_REVISION`の「ディスクへ残さない」が実装されていない

`cache_identity.py`の`UNKNOWN_REVISION`は「この値のタイルをディスクへ残さない」と宣言して
いるが、参照しているのは`tile_version()`自身だけで、ディスクパスは形の署名しか持たない。
世代不明のまま焼いたタイルが、正しいものと区別できずに残る。

## 3. `tile_cache`に容量上限も掃除も無い

`tile_cache.py`は`get`/`set`/`clear_all`だけで、退避もpruneも持たない。形の署名が変わる
デプロイのたびに旧世代がディスクへ残り続ける。起動時のprune（`main.py`）が見るのは
`tile_persistent_cache`の一部の名前空間だけで、`tile_cache`は対象外。
docs/caching.md「ディスクへ世代番号を使うなら、旧世代を削除する導線をセットで用意する」に
反している。

## 対応（2026-09-19）

### 1. 読めなかったことを記録し、繰り返しの全消去を止めた

`cache_generation.sync_with_revision`は、`revision`がNoneのときも**一度は捨てる**（安全側は
変えない）が、「読めなかった」ことを記録するようにした。状態が変わらない限り2度目は捨てない。
読めない状態から復帰したら、記録が食い違うので1度だけ捨てて記録し直す。

### 2. 世代が分からないあいだ、焼いたタイルをディスクへ残さない

`serve_cached_tile`へ`persist`を足し、路面・POI・事故の3系統は
`derived_data_revision_service.current_revision()`がNoneのあいだ書かないようにした。
`UNKNOWN_REVISION`が宣言していた性質が、これで実際の挙動になった。

**応答は変わらない**——キャッシュしないだけで利用者には同じ絵が出る。世代は軸カタログの取得
（ページを開くたび）で読まれるため、実運用でこの状態が続くのはDBが読めないときだけである。

### 3. 置き場に容量上限を付けた（ただし現状は発火しない）

`tile_cache.prune_to_size_limit`を足し、起動時の掃除（`main.py`）へ繋いだ。この置き場は
パスをハッシュ化してフラットに保つため世代単位では消せず、古い順に落とす形になる。

**効果は測って正直に書く。** docs/caching.mdの本番実測は`tile_cache`が11MB・土地被覆タイルが
上限45MBで、上限512MBに対して1桁の余裕がある。**通常の運用では何も消えない**——伸び続けた
ときの頭打ちとして置いたもので、今ある問題を解いたわけではない。起票時に「デプロイのたびに
旧世代が残り続ける」と書いたのは事実だが、**残る量は実測で数十MB規模**であり、そこは
起票時に確かめていなかった。
