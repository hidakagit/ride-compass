# T635. 平常時は災害系タイルを取得しない（危険度サマリの配信）

規模M。起票のみ・実装未着手。

## 背景

キキクル・洪水は`page.tsx: FIXED_LAYER_VISIBILITY_DEFAULTS`で既定ONのため、
すべての利用者が常時タイルを取得している。しかし危険度がどこにも無い平常時、
配信されるタイルは実質的に空である（実測: 土砂キキクルz11は関東の5地点すべてで
同一の334バイト空PNG、洪水のベクタタイルは0バイト）。

`basetime`は10分ごとに更新されURLが変わるため、[T632](T632.md)のブラウザキャッシュでも
[T633](T633.md)の枚数削減でも、この「10分ごとに空タイルを数百枚取り直す」構造そのものは
残る。

## 対応方針（案）

`jma_tile_prewarm_service.py`は既に運用範囲（`WIND_GRID_BBOX`）の全タイルを10分ごとに
取得している。その過程で「危険度を持つタイルが1枚でもあるか」を要素ごとに判定し、
軽量なJSONとして配信する。frontendはそれを見て、危険度ゼロの要素についてはソースを
空にする（タイルリクエスト自体を発生させない）。

判定方法の候補:

- **PNGデコードによる危険度色の検出**: 確実だが、Pillow等のデコードコストがかかる
  （256×256を約900枚、10分間隔なら許容範囲と見込まれる）。ラスタ3種に適用できる。
- **空タイルのバイト列との一致判定**: 最も安価。ただしz10には「危険度ゼロでも地点ごとに
  内容が異なるタイル」（陸域マスク等と推定、実測で335〜535バイトの複数パターン）が
  存在するため、単純なハッシュ一致では平常時を平常時と判定できない。要調査。
- **洪水（ベクタ）**: 0バイト判定で足りる可能性が高い。

「注意（黄）」レベルをどう扱うか（表示するのか、警報級のみ表示するのか）は表示方針の
判断を伴うため、実装前にユーザーと決める。

## 保留した場合の影響

年間の大半を占める平常時に、情報量ゼロのタイルを10分ごとに数百枚取得し続ける。
[T632](T632.md)・[T633](T633.md)を入れても残る唯一の構造的な無駄で、削減の余地としては
最も大きい。
