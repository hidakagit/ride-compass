# T635. タイル在否インデックスを全タイル系エンドポイント共通の仕組みとして設ける

規模L。起票のみ・実装未着手。

## 背景

JMA動的タイル（キキクル4種・降水・雷・竜巻・線状降水帯）は**疎**である——平常時は
ほぼ全面が空で、実際に描くものがあるのは一部に限られる。にもかかわらずクライアントは
中身があるかどうかを知らないまま画面内の全タイルを要求し、平常時は画面あたり
約40枚×4要素＝160リクエストがすべて空タイルの取得に費やされる。

**この機構が効くのは「疎」かつ「再取得が頻繁に起きる」レイヤーに限られる。**

| 系統 | URLの変化 | [T632](T632.md)のキャッシュ | 在否インデックスの追加効果 |
|---|---|---|---|
| JMA動的タイル | `basetime`で10分ごとに変わる | 効かない（毎回別URL） | **大きい** |
| 路面・事故・POI | 不変 | `max-age=3600`で効く | 小さい |
| 風グリッド | タイルではない・全地点に値がある | — | なし |

静的タイルはT632のブラウザキャッシュで再取得そのものが起きないため、在否を先に
問い合わせても「1リクエスト増やして、キャッシュから返るはずの40枚を省く」取引になり
割に合わない。風グリッドはそもそもタイルではなく、全格子点に値があるため在否の概念が無い。

**機構自体は汎用に作る**（レイヤーごとの分岐を書かない）が、**実際に乗せる価値があるのは
JMA動的タイル系**である。静的タイルは、将来キャッシュが効かない事情が生じたときに同じ
機構へ乗せられる状態にしておけばよい。

## 対応方針

**「まず在否を1回問い合わせ、中身のあるタイルだけを取りに行く」**という2段構えを、
タイル系エンドポイント共通の機構として設ける。[T632](T632.md)の`cache_policy.py`と同じく、
レイヤーごとの分岐を書かずに1つの表とミドルウェア相当で捌く形にする。

```
クライアント: GET /api/tile-index/{layer}?z=..&bbox=..   ← 送るのはzとbboxの4数値だけ
サーバー    : その範囲で中身のあるタイル座標を返す
クライアント: MapLibreのaddProtocolでタイル要求を横取りし、
              インデックスに無い座標 → 透明タイルを即座に返す（ネットワークに出ない）
              インデックスにある座標 → 実際に取得
```

**クライアントは座標リストを送らない**（URLが長くなる方向にはしない）。送るのは`z`と
bboxのみで、サーバーが座標を返す向きにする。

### 応答サイズ

画面に見えるタイルはズームに依らず約40枚のため、bboxを画面範囲に絞れば**返す座標は
最大40件・数百バイト**に収まる。運用範囲全体（`WIND_GRID_BBOX`）を一度に返す設計に
した場合でも、ビットマップ形式なら z10=10B・z12=128B・z14=1,979B・z16=31KB であり、
実用ズーム帯では十分小さい。座標リストとビットマップは、応答が疎か密かで選べばよい。

### レイヤーごとの在否の求め方

在否を答える関数だけをレイヤーごとに登録し、配信経路・クライアント側の横取りは共通にする。

**初期実装の対象はJMA動的タイル系のみ**とする。

| レイヤー | 在否の求め方 | 初期実装 |
|---|---|---|
| JMA動的タイル系 | `jma_tile_prewarm_service.py`が既に運用範囲の全タイルを10分ごとに取得しているため、その過程で判定して記録する。**空タイルは全要素・全地点で同一の334バイト**（md5 `df93104160`）と実測済みのため、画像デコード不要でバイト列の一致判定で足りる（洪水はベクタで0バイト判定） | **対象** |
| 路面 | `road_graph_tiles`のカバレッジ（既存。`region_service.py`がカバレッジ外をNoneで返している判定をそのまま使う） | 見送り（キャッシュが効くため） |
| 事故・POI | 対象テーブルの分布をPostGISで問い合わせる | 見送り（同上） |

なお路面・事故・POIが実際にどの程度疎かは未計測（本番で近傍走査を試みたが、連続
リクエストがレート制限に当たり測定できていない。同一座標でも単発では32,800B・連続走査では
0バイトが返る）。ただし上記のとおり疎密以前にキャッシュが効くため、結論は変わらない。

## 詰めるべき点

- **運用範囲外の扱い**: JMA系はプリウォーム範囲（`WIND_GRID_BBOX`）の外にインデックスを
  持たない。範囲外はスキップせず従来どおり取得する（安全側に倒す）。
- **インデックスと`basetime`の整合**: JMA系のインデックスは特定の`basetime`に対する
  ものなので、取得後に`basetime`が変わったら作り直す。インデックス自身の`Cache-Control`は
  [T632](T632.md)の対応表へ1行足して管理する。
- **`addProtocol`の導入範囲**: MapLibreのタイル取得を横取りする仕組みで、既存のタイル系
  レイヤー全体に影響する。段階導入するか一度に切り替えるかを決める。
- **在否インデックス自体の取得コスト**: レイヤー×ズームごとに1リクエスト増える。40枚を
  省くために1枚増やす取引なので通常は得だが、密なレイヤー（インデックスがほぼ全面true）
  では無駄になる。「疎であること」が前提条件であることを明示する。

## 期待効果

平常時のキキクルで画面あたり約160リクエストがゼロになる。年間の大半が平常時のため、
削減余地としては[T632](T632.md)〜[T633](T633.md)の後に残る最大のもの。危険度が出ている
ときも、実際に中身のあるタイルだけを取るため無駄が出ない。

## 経緯

当初は「キキクルの要素ごとに危険度の有無をboolで配信し、ゼロの要素はソースを空にする」
という案で起票していたが、ユーザーの指摘により**タイル単位の在否インデックス**かつ
**全タイル系エンドポイント共通の機構**へ設計を変更した（2026-09-07）。要素単位では、
関東のどこか1箇所に危険度があるだけで画面内の全タイルを取りに行くことになり、実害のある
日ほど効かなくなる。

起票時に「要調査」としていた判定方法は空タイルのバイト列一致で足りると判明し、
「実装前にユーザーと決める」としていた注意（黄）レベルの扱いは[T642](T642.md)の判断
（既定は出す側へ倒す＝中身があれば取得する）で決着済みのため、いずれも論点から外れた。
