# T842. コードの書式を機械に決めさせる（prettierの導入、段階適用）

規模M。
状態: 着手（2026-09-14、ユーザー指示「そういう議論をするなら入れたら？」から）

## 背景

frontendに**フォーマッタが無い**（prettierはdevDependencyにも設定ファイルにも無く、eslintも
行幅・改行のルールを持たない）。そのため書式は各自の手癖で決まり、既存コードの中でも揃って
いない。

[T840](T840.md)の作業中、書式を整えるつもりで`npx prettier`を一時インストールして使い、既定の
`printWidth 80`で既存と違う書式を持ち込んだ（不自然に折り返された箇所は手で戻した）。
**手で揃える議論をするより、機械に決めさせる方が筋が通る**というユーザー判断。

## 実測（2026-09-14）

- frontendの`.ts`/`.tsx`は317ファイル・48,308行。80文字超が7.3%、120文字超が**0.5%**、
  140文字超が0.1%。大半は120文字以内に収まっている。
- `printWidth: 120`で`--list-different`を取ると、**317ファイル中157ファイル**（約半分）が
  変更対象になる。

## 方針: 設定だけ入れて段階適用（ユーザー選択）

**既存157ファイルを一括整形しない。** このリポジトリは並行セッションが同じファイルを次々に
変更しており（T840の作業中だけでT837・T838・T841がpushされた）、一括適用はコンフリクトを
多発させる。本質的な変更が書式差分に埋もれてレビューもしづらくなる。

- `prettier`をdevDependencyへ追加し、`printWidth: 120`の設定を置く。
- pre-commitで**ステージしたファイルだけ**を整形する（`scripts/pre-commit-prettier.sh`を
  追加し、`pre-commit.sh`から呼ぶ）。既存の`pre-commit-ruff.sh`と同じ骨格——対象を
  ステージ済みへ絞り、prettierが見つからない環境では警告のみでコミットを止めない。
- 一括適用は、並行作業が落ち着いたタイミングで別途判断する（本タスクではやらない）。

backend側の`ruff format`も同じ議論になるが、まずfrontendだけで運用を見る。
