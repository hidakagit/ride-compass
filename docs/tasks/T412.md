# T412. JMA動的タイル系レイヤーのバックエンド経由化（プロキシ+キャッシュ） 規模M

状態: 完了（2026-08-30）

- 背景: T410（キキクル+線状降水帯予測マップ）の実機フィードバック検討中、ユーザーから
  「キキクルのような防災級の情報はユーザー操作を待たず常時ONにすべきでは」という指摘。
  常時ONにする前提として「JMAデータの取得はどこ経由か」を確認したところ、降水ナウキャスト
  （T171）・降水短時間予報（T407）・雷/竜巻ナウキャスト（T204）・キキクル/線状降水帯予測
  マップ（T410）は**いずれもフロントエンド（各ユーザーのブラウザ）がJMAの非公式内部API
  （`https://www.jma.go.jp/bosai/jmatile/...`）へ直接fetchしている**（バックエンド・
  Redis等のキャッシュを一切経由しない）ことが判明。常時ONにすると利用者数に比例して
  JMAの非公式エンドポイントへのポーリング負荷が線形に増えるため、常時ON化の前提として
  バックエンド経由への切り替えが必要という認識が一致。
- ユーザー方針（2026-08-30）: 「動的なデータはなるべくバックエンド経由に切り替える方向で
  検討して」（今回のJMAタイル系に限らず、既存の方針として繰り返し表明されている）。
- 既存の類似実装: [backend/app/infrastructure/basemap_client.py](../../backend/app/infrastructure/basemap_client.py)（Step10）が
  OpenFreeMapタイルを`path`ベースで透過プロキシしつつファイルシステムキャッシュ
  （`tile_cache.py`）する既存パターンを持つ。JMAラスタタイル（basetime/validtime/z/x/y
  で内容が確定する不変コンテンツ）は同じ「一度取得したら永続キャッシュ可能」という
  性質を共有するため、このパターンを流用できる見込み。一方targetTimes.json（数分〜
  数十分単位で更新）は`jma_warning_client.py`のTTLCache方式（短TTL）が近い。
  対象タイルURL・要素コードの一覧はdynamicWeather.ts「動的気象レイヤー」節参照
  （precipitationNowcast.ts/thunderNowcast.ts/riskMap.tsの3ファイルが該当）。

## 実装メモ

- **バックエンド**: [backend/app/infrastructure/jma_tile_client.py](../../backend/app/infrastructure/jma_tile_client.py)（新規）が
  `basemap_client.py`と同じ「pathを丸ごとプロキシ」方式を持つが、キャッシュ戦略を2つに
  分ける必要があった。①ラスタタイル本体（`basetime/validtime/z/x/y`が確定した時点で内容が
  不変、OpenFreeMapタイルと同じ性質）は`tile_cache.py`（永続ファイルキャッシュ）へそのまま
  乗せる。②`targetTimes*.json`（数分〜数十分単位で更新される時刻一覧）は`tile_cache.py`へ
  乗せると更新後も古い内容を無期限に返し続けてしまうため、`jma_warning_client.py`と同じ
  `cachetools.TTLCache`（プロセス内、TTL=2分）を別途用意し、パスの末尾が
  `targetTimes*.json`かどうかで振り分ける。ルーター
  ([backend/app/api/routers/jma_tile.py](../../backend/app/api/routers/jma_tile.py)、
  `GET /api/jma-tile/{path:path}`)・DI([dependencies.py](../../backend/app/api/dependencies.py):
  `get_jma_tile_client`)・レート制限設定(`config.py`: `jma_tile_rate_limit_per_minute=300`、
  basemapと同水準)も`basemap.py`の構成をそのまま踏襲した。
- **フロントエンド**: JMAタイル系の共通ベースURLを
  [jmaNowcastFrames.ts](../../frontend/src/components/Map/jmaNowcastFrames.ts)の
  `JMA_TILE_BASE_URL = "/api/jma-tile/bosai"`へ集約し、`precipitationNowcast.ts`・
  `thunderNowcast.ts`・`riskMap.ts`・`MapView.tsx`（プレースホルダURL）の計7箇所の
  `https://www.jma.go.jp/bosai/...`直書きをこの定数経由の相対パスへ置き換えた。
  `next.config.ts`のrewrites（`basemap`/`road-surface-tiles`等と同じ理由、別オリジンの
  タイル大量リクエストとAPI呼び出しの接続数競合を避ける）に`/api/jma-tile/:path*`を追加し、
  ブラウザからは常にフロントエンドと同一オリジンに見えるようにした。
- **横展開の検討**: ユーザーから「JMA以外の外部データも同じ問題があれば横展開してほしい」
  との指示を受け全文検索したところ、該当は国土地理院の色別標高図タイル
  （`cyberjapandata.gsi.go.jp`、[MapView.tsx](../../frontend/src/components/Map/MapView.tsx)）
  のみだった。ただしこちらは既存コードに「ブラウザからの直接埋め込み利用を前提に国が
  公開している正式なAPIのため意図的にプロキシしない」という判断が明記されており
  （JMAの「非公式の内部API」とは性質が異なる）、負荷分散の観点では対象外と判断した。
  一方ユーザーからの指摘で、レスポンス速度の観点（同一タイルの再取得をキャッシュで
  高速化できる）と、色別標高図が時刻に依存しない静的データである点（`targetTimes.json`の
  ような短TTLが不要で`tile_cache.py`の永続キャッシュがそのまま使える）は考慮不足だったと
  訂正した。この対応は本タスクのスコープ外とし、別の軽量タスクとして起票する方針で
  ユーザーと合意した（Open-Meteo・基礎地図・路面/事故/POIタイルは既にバックエンド経由の
  ため対象外）。
- **検証**: バックエンドテスト新規2ファイル（`test_jma_tile_client.py`8件・
  `test_jma_tile_routes.py`3件、キャッシュ戦略の分岐・レート制限・502エラーを検証）、
  フロントエンドの既存テスト（precipitationNowcast/thunderNowcast/riskMap各.test.ts）を
  新URLへ追従。バックエンド全体（`pytest -m "not postgis"`、1452件）・フロントエンド全体
  （vitest、781件）とも成功。実機（Browserペイン、backend/frontend双方を再起動して確認）で
  `targetTimes.json`・ラスタタイルPNGとも`/api/jma-tile/...`（同一オリジン）経由で200を
  確認し、`/api/debug/stats`で`weather:jma-tile`のcache_hit_rateが実際に0より大きい
  （初回ロード時点で18呼び出し中8件ヒット）ことも確認した。OpenAPI生成物
  （`export_openapi.py`→`npm run generate:api`）も新規ルーター追加に伴い再生成しコミットに
  含めた。
