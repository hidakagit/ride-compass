# T388. job_registryのマルチワーカー対応〔P3〕規模S — トリガー: backendの複数ワーカー/複数プロセス構成の採用時（現状は単一プロセスデプロイのため未到達）

状態: 未完了

- 背景: T386のレビュー指摘（/code-review高effort実施2026-08-28、CONFIRMED）。
  `backend/app/infrastructure/job_registry.py`（改善計画T265、ルート生成のバックグラウンド
  ジョブ化用）はプロセス内メモリのみの汎用非同期ジョブレジストリで、単一プロセスデプロイを
  前提にしている。同様の前提を置く`axis_registry_service.py`は[T288](T288.md)として
  「複数ワーカー化のタスクを起こす際は本タスクを完了条件に含めること」という正式な
  トリガー付きタスクを持つが、`job_registry.py`にはコード内コメントのみで対応するタスク
  番号での起票が無かった。現状は両者とも単一プロセスデプロイのため実害は無い。
- 影響範囲（保留した場合）: 単一プロセスデプロイを続ける限り実害なし。複数ワーカー化を
  「別の理由」（性能等）で行う際に本タスクを見落とすと、あるプロセスが受理したジョブの状態
  （queued/running/done/failed）が別プロセス（ポーリング先）から見えず、フロントが
  `GET /api/routes/generate/{job_id}`で永久に404を受け続ける不整合が黙って起きる——
  複数ワーカー化のタスクを起こす際は[T288](T288.md)と併せて本タスクも完了条件に含めること。
- 完了条件: 着手時に確定（ジョブ状態を外部ストアへ移すか、複数プロセスでのジョブ可視性を
  担保する代替設計のいずれかで、複数プロセスでのポーリング一貫性テストを含む。[T387](T387.md)で
  導入予定のRedisと統合できる可能性がある）。
