# T725. 路面タイルへ道路名（name/ref）を焼き込む 規模S

状態: 完了（2026-09-12。起票は2026-09-11、[T724](T724.md)のドキュメント棚卸しで、
どのタスクにも紐づかず`static-road-attributes-plan.md`の中だけで管理されていたことが判明した）

## 背景

`_ROAD_SURFACE_TILE_MVT_SQL`へ`name`/`ref`プロパティを追加し、路面クリックの
ポップアップに道路名を表示する。静的道路属性P1の残タスクとして2026-08-17に整理され、
**「`improvement-plan.md`側では二重管理を避けるためT番号を振らず本ファイルのみで管理する」**
と明記されていた。

その運用は、計画文書が読まれ続ける前提でのみ成り立つ。実際には
`static-road-attributes-plan.md`は自身が「P0完了・P1完了」と宣言した完了済み計画として
参照されなくなり、**この1件だけが誰にも拾われない状態で1か月近く残っていた**
（`/task:next`は`improvement-plan.md`の`- [ ]`行しか見ない）。

## 対応方針

`_ROAD_SURFACE_TILE_MVT_SQL`へ`name`/`ref`を足し、`ROAD_SURFACE_TILE_VERSION`を上げる
（CLAUDE.md「コミット時の同期ルール」。生成物`region-tile-config.json`も同一コミットで）。
frontend側は`buildRoadSurfacePopupHtml`へ行を追加する。

**OSMタグ由来の値をポップアップへ出すため、[T703](T703.md)段階1（自前エスケープ）と
同じ扱いが要る**——`name`/`ref`は第三者が編集できるデータで、対訳表を持たない生値。
T703段階1より後に着手するか、同じエスケープを同時に入れること。

## 優先度

据え置き扱いだった理由（2026-08-15時点）は「ルート評価・表示の正確性を大きく損なう
不具合ではなく、あると良い種類の改善」。この判断自体は変わっていない。

## 実装（2026-09-12）

| 層 | 変更 |
|---|---|
| backend | `_ROAD_SURFACE_TILE_MVT_SQL`へ`NULLIF(btrim(w.tags->>'name'), '')`・同`'ref'`を追加。`name`/`ref`は既に`ALLOWED_WAY_TAGS`にあり、`osm_raw_ways.tags`へ取込済みのため**PBF再取込は不要** |
| frontend | `buildRoadSurfacePopupHtml`の先頭行へ道路名を出す。`name`と`ref`は独立したタグで片方だけ持つwayが多いため、両方あるときだけ「名前[番号]」へ畳む |

正規化（小文字化）はかけない——材料ではなく利用者へそのまま見せる固有名詞のため。
前後空白を落とし、空になればキーごと省く（名前を持たないwayが大多数で、密度の`NULLIF`と
同じ流儀。欠損とタグ値`""`を区別する意味も無い）。

`name`/`ref`は**第三者が編集できる生値で対訳表を持たない**ため、[T703](T703.md)段階1の
`escapeHtml`を通す（`labelOrEscapedRaw`は対訳表がある値向けで、ここでは使わない）。

## 起票時の対応方針のうち、古くなっていた点

> `ROAD_SURFACE_TILE_VERSION`を上げる

**不要になっていた。** [T747](T747.md)でタイル世代は焼き込みSQLの署名から導出する形に
なっており、プロパティを足した時点で`24-a126de5b444a`→`24-bb4ca819b676`へ自動で変わる
（手で上げるのはSQLが読むテーブルの中身を作り直したときだけ）。生成物
`region-tile-config.json`の再生成は引き続き同一コミットで行う。

**これ自体が[T722](T722.md)の実例**——タスクファイルに書かれた方針だけを見て着手すると、
その後に変わった仕組みに気づかない。T722で入れた「着手前に対象領域の正本
（`docs/modules/backend/static-road-attributes.md`）を読む」に従ったことで気づいた。

## 測っていないこと

**タイルサイズへの影響**は測っていない。この環境にOSM実データが無く、実タイルを生成
できないため。名前を持つwayだけにプロパティが載る（日本の住宅道路の大半は`name`を
持たない）ので影響は限定的と見込むが、実測ではない。dev DBで
`GET /api/region/road-surface-tile/...`の応答サイズを新旧世代で比べれば確認できる。

プロパティの**追加**のみでデプロイ順序の制約は無い（削除を伴う変更はfrontendのデプロイを
先に、という制約は当てはまらない。旧フロントは未知のプロパティを無視し、新フロントは
旧世代タイルに対して道路名の行を出さないだけ）。
