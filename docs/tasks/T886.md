# T886. 周囲の土地被覆が、どこにも表示されない

規模M。
状態: 完了（2026-09-16起票・同日完了。段階1・段階2ともmasterへ反映。[T885](T885.md)の判断材料として、ユーザー要望
「土地状況見える化するところからかな。。地図パネルにできない？」から）

## 背景

`way_landcover`（[T624](T624.md)）は道路周囲100mリングの土地被覆を8クラス分持つが、
**利用者がその内訳を見る手段が無い**。

- 地図レンズ: タイルへ焼いているのは`trees_pct`・`built_pct`の2列だけで、レンズに出るのは
  その合成（開放度軸）。「この道は何で覆われているか」は読み取れない。
- 区間インスペクタ: `_WAY_LANDCOVER_BY_OSM_WAY_ID_SQL`が**8列すべてをDBから読んでいる**のに、
  `axis_inspector_breakdown`が評価パイプラインへ配線済みの2値（trees/built）しか先へ
  渡さないため、画面には出ない。

[T885](T885.md)で「樹木と建物を分けるか」を判断するにも、まず何がどこにあるかが見えないと
決められない。

## 段階1: 区間インスペクタへ内訳を出す

データは既に取得済みで、配線が切れているだけ。`AxisInspectorResult`へ
`LandcoverPercentages`（既存モデル、8クラス＋`valid_pixels`）を足し、
`RoadInspectorPopup`へ節を1つ増やす。

表示は畳む。走行中のスマホが主用途で情報量を増やさない方針のため、既存の「その他のタグ」と
同じ`<details>`にし、閉じている間は主なクラスだけを見せる。

### 実施（2026-09-16）

`AxisInspectorResult`へ`landcover`（既存の`LandcoverPercentages`、8クラス＋
`valid_pixels`）を足し、`RoadInspectorPopup`へ`RoadLandcoverRows`を1つ増やした。

表示は「その他のタグ」と同じ`<details>`。閉じている間は最も多いクラスだけを
（例: 「周囲の土地被覆: 建物 50%」）、開くと割合の大きい順に並べる。0.5%未満の
クラスは行を作らない——8クラスは合計100%になるため、出さなくても読み手は補える。

効いていることの確認: `RoadLandcoverRows`の呼び出しを外すとテストが落ちる。

## 段階2: 地図（未着手）

**当初「主なクラスをタイルへ焼く」と書いたが、撤回する。** 土地被覆は8クラスの割合で、
樹木20%・建物50%・農地30%のような混合が普通にある。`argmax`で1色へ潰すと「建物」になり、
半分が建物でないことが消える。34/33/33のような道ではわずかな差で色が飛ぶ。
**この演算をこのデータに使ってはいけない。**

そもそもこの混合は集約の副産物である。元のラスタは10m画素の分類済みデータで、
1画素に1クラスしか入っていない。半径100mリングの数百画素をヒストグラムにして1本の道へ
畳んだ結果として混合が生まれている。

したがって段階2は**元のラスタをそのまま面で配信する**（2026-09-16ユーザー判断
「源泉の10m間隔のラスタをそのまま色塗って地図パネルには出したい」）。1画素1色になり、
混合をどう塗るかという問題自体が消える。本番VMの`/home/ubuntu/54S_2024.tif`（69MB）が
そのまま素材になる。配信方式は未調査（GDAL未導入、静的タイルへ焼くか都度生成か）。

道路の線を塗るレンズは、軸の形が決まった後の確認手段として別に考える。

### 実施（2026-09-16）

**配信方式は「都度生成＋キャッシュ」**（GSI色別標高図・路面タイルと同じ形）。
`GET /api/region/landcover-tiles/{z}/{x}/{y}.png`が、要求されたタイルの範囲だけをGeoTIFFから
読み、Web Mercatorへ再投影してPNGで返す。焼いた成果物の置き場・配布経路を持たずに済み、
使われた範囲だけがコストになる。事前に全タイルを焼く案は、成果物をVMへ届ける経路が別途
必要になるため採らなかった。

**再投影は最近傍**。画素値はクラス番号で、平均・線形補間は存在しないクラス（農地5と建物7の
平均で6）を作る。

**下限ズームの根拠は当初の見込みと違った。** 「低ズームほど読む量が増える」を理由にz10を
下限にしていたが、配布元のGeoTIFFは縮小画像を同梱しており、間引いて読めば低ズームでも安い
（東京付近の1タイルでz6=97ms・z10=30ms・z14=14ms、開発機実測）。コストは下限を決める
理由にならないと分かったため、下限はz6（ラスタが覆うUTMゾーンより広い表示では読み取れない）
へ改めた。

**配色は配布元の公式パレットを使わなかった。** 公式では建物が鮮やかな赤で、このアプリは赤を
「難易度が高い」の意味で既に使っている。市街地は本番の道路周囲の平均で8割を超えるため、
地図がほぼ全面その色で覆われ、他の赤の意味が薄れる。建物を無彩色にし、他は自然な色相
（水=青・樹木=緑）を保ったまま彩度を落とした。面レイヤー共通の不透明度も0.4→0.32へ下げた
（地図背景が読めることを優先。値はレイヤーごとに持たない）。

**ラスタの取得を自動化した。** 起票時は「VMへ手で置く」前提で書いていたが、配布元は認証不要の
公開バケットで、手作業である必要が無い。`scripts/fetch_lulc_raster.py`が設定されたパスに
無いラスタだけを取得し、デプロイがコンテナ入れ替えの前に呼ぶ。ラスタはキャッシュとは別の
ディレクトリへ置き、コンテナへは読み取り専用でマウントする。

効いていることの確認: 実ラスタ（`54S_2024.tif`）を入れた開発機で、東京湾周辺のタイルが
水面・市街地・農地・樹木に塗り分かれること、ブラウザでチップをONにすると地図へ重なり凡例が
8クラスを出すことを確認した。ラスタ未設定のときは空タイルではなく503を返す（黙って何も
出ない状態にしない）。

実装中に見つけた構造の摩擦（静的レイヤーの追加が1箇所で済まない）は[T888](T888.md)へ
分離した。

### 本番デプロイが1回失敗した（libexpat1、同日修正）

`rasterio`を本番webイメージへ入れたことで、`import rasterio`が
`ImportError: libexpat.so.1: cannot open shared object file`で失敗しデプロイが止まった。
python公式slimイメージに`libexpat1`が無いという既知の制約で、
[disaster-recovery.md](../disaster-recovery.md)に`osmium`の同じ症状として記録済みだった
ものを、webイメージ側へ適用し忘れた。`Dockerfile`で`libexpat1`を入れて解決。

**このとき本番は落ちていない**——ラスタ取得ステップが旧コンテナのstopより前にあり、
`set -e`でそこで止まったため。ただし止まる位置がもう少し後ろだったら、起動不能の
コンテナへ入れ替わって本番全体が停止していた（`app.main`はregion router経由で
`rasterio`を読む）。

再発防止はデプロイ側の1段として入れた: ビルド直後・旧コンテナのstop前に、作った
イメージで`python -c "import app.main"`を実行する。共有ライブラリの不足のように
「テストでもビルドでも出ず、コンテナ入れ替えの瞬間に起動不能として現れる」壊れ方を、
本番を止めずに落とせる。効いていることの確認: `rasterio`をimportできない状態を作って
`import app.main`が実際にImportErrorで落ちることを確かめた。

## 保留することで何が起きうるか

[T885](T885.md)の選択肢A〜Dを、分布の数字だけで決めることになる。「並木道44,120本」が
実際にどこのどんな道なのかを見ずに軸の形を変えると、較正のときに同じ議論をやり直す。
