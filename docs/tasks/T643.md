# T643. 地域タイルの取得失敗が「200＋空タイル」で返り、1時間キャッシュされる

規模S〜M。起票のみ・実装未着手。

## 事象

`services/tile_serving.py: serve_cached_tile`（路面・POI・事故タイルが共有する骨格）は、
`fetch_tile`が`None`を返したとき**HTTP 200＋空タイル**を返す。

```python
tile_bytes = await fetch_tile(fields)
if tile_bytes is None:
    fields["source"] = "uncovered_empty"
    return empty_tile
```

`None`になる理由は複数あるのに、応答はどれも同じである。

| `None`になる理由 | 性質 |
|---|---|
| 取込範囲外（カバレッジ外） | **恒久的**。次に取込を広げるまで変わらない |
| repository未接続（`road_graph_use_repository`無効） | 設定由来。起動中は変わらない |
| DB障害・接続プールの逼迫・混雑によるタイムアウト | **一時的**。すぐ回復しうる |

そのうえで応答は2xxのため、[T632](T632.md)の`cache_policy.py`が`BATCH_TILE`
（`public, max-age=3600`）を付ける。結果として、**一時的な失敗で返った空タイルが利用者の
ブラウザに1時間キャッシュされ、その間その区画の道路が表示されないまま**になる。

サーバー側のファイルキャッシュには書かないため（`serve_cached_tile`は`None`のとき
`tile_cache.set`を呼ばない）、サーバーは次のリクエストで正しく生成する。**取り残されるのは
ブラウザ側だけ**という点が見つけにくい。

## 実測（2026-09-07）

本番で路面タイル`z14/14551/6447`を取得したところ、

- 単発で5回連続 → いずれも`200 / 32,800B`（`cache-control: public, max-age=3600`付き）
- 近傍3×5を1.2秒間隔で走査 → **同じ座標を含む15枚すべてが`200 / 0B`**

レート制限（`road_tile_rate_limit_per_minute`=120）には達しておらず、429でもない。
**再現条件は未特定**（サーバー側ファイルキャッシュの状態、`_region_tile_semaphore`
[`road_tile_max_concurrent`]の待ち、`road_graph_tiles`のカバレッジ判定のいずれかが
絡むと見られる）。

## 対応方針（案）

「取得不可」と「そこにデータが無い」を応答で区別する。[T632](T632.md)で
`jma_tile.py`の502にCache-Controlを付けない判断をしたのと同じ考え方を、地域タイルにも
適用する。

- **恒久的にデータが無い**（カバレッジ外）: 200＋空タイル＋長いキャッシュのままでよい。
- **一時的な失敗**（DB障害・タイムアウト等）: 空タイルを返すとしても`Cache-Control`を
  付けない（または503を返す）。`serve_cached_tile`の`fetch_tile`が理由を区別して返す形へ
  変える必要がある（現状は`bytes | None`しか返せない）。

MapLibreは失敗タイルを自動再試行しないため、503にする場合は「タイルが永久の空白になる」
既知の性質（`next.config.ts`の`proxyTimeout`のコメント参照）とのトレードオフを確認する。

## 保留した場合の影響

一時的な障害・混雑のたびに、その時点の利用者のブラウザへ空タイルが1時間刷り込まれる。
サーバー側は正常に戻っているため**ログにも異常として残らず**、利用者からは「道路が
表示されない」という再現性の低い不具合に見える。

## 経緯

[T635](T635.md)の検討で静的タイルの疎密を実測しようとした際に発見した。T632以前も
`region.py`・`accidents.py`が同じ`Cache-Control`を直書きしていたため、T632による
劣化ではなく既存の問題である（T632はヘッダの置き場所を移しただけ）。ただしT632で
「エラー応答をキャッシュさせない」方針を定めた以上、その方針から漏れている箇所として
扱う。
