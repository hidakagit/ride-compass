# T933: 平面のST_Azimuthを方位として使っている箇所が残っている

状態: 完了（2026-09-19。2026-09-18起票）

## 背景

[T931](T931.md)で、`ST_Azimuth(geometry, geometry)`が**経度緯度を平面として扱った角度**を
返すことが分かった（緯度35度で真の方位と約6度ずれ、`domain/geo.py: bearing_between`・
`road_edges.bearing_deg`と定義が合わない）。T931では`::geography`キャストで直した。

`road_graph_repository.py`の`_WAY_TRAVEL_BEARING_SQL`に、キャストの無い同じ形が残っている。

```
degrees(ST_Azimuth(ST_StartPoint({alias}.geom), ST_EndPoint({alias}.geom)))
```

これは上下線が分かれた道の判定（`_ANTIPARALLEL_SQL`、`:bearing_tolerance_deg`との比較）で
使われる。許容角と数度の系統誤差が同じ桁のため、東西方向の道ほど判定が歪む可能性がある。
migration 0013のコメントが「ST_Azimuthとbearing_betweenは同じ定義」と書いているのも、
この形では正しくない。

## 起票時の見立ての誤り（先に書く）

**「数度の系統誤差が許容角に乗る」という見立ては正しくない。** `_ANTIPARALLEL_SQL`は
2本のwayの方位を**同じ式で**求めて差を取るため、平面近似の歪みは差の中で大きく打ち消し合う。

平面方位 θp と測地線方位 θg は `tan θp = tan θg / cos φ` の関係にあり、
`f(θ+180) = f(θ)+180` を満たす。したがって対向に近い2本の「180度からのずれ」は、
**6度ずれるのではなく `f'(θ)` 倍に伸縮する**。緯度35.7度で `f'` は `cos φ = 0.812`
（東西の道）から `1/cos φ = 1.231`（南北の道）の範囲を動く。許容角45度に対しては、
真のずれが36.6〜55.4度の帯にいる対だけが判定を取り違える。

「東西方向の道ほど歪む」も正確ではない。東西では差が縮んで**通しすぎ**、南北では
差が広がって**落としすぎ**になり、歪みの大きさ自体は両端で同じである。

## 実測（本番DB、2026-09-19）

### 1. 上下線分離の判定が変わるway

判定SQLの`divided`をキャスト有無の両方で計算して突き合わせた（母集団は
`direction <> 'both'`のway全件、所要51.6秒）。

| | 件数 |
|---|---|
| 母集団 | 71,210 |
| 現行（平面）で分離と判定 | 37,609 |
| 修正後（測地線）で分離と判定 | 37,593 |
| **判定が変わる** | **120（0.169%）** |
| うち 分離でなかったものが分離になる | 52 |
| うち 分離だったものが分離でなくなる | 68 |

上の解析どおり、影響は許容角の境目にいる対に限られる。**0.169%は小さいが、方向は
一様ではない**（東西と南北で逆向きに間違える）ため、値を正しくする意味はある。

### 2. `road_edges.bearing_deg`に平面近似は残っていない

migration 0013のバックフィルは平面近似で書いており、[T405](T405.md)が
「既存の`road_edges.bearing_deg`自体を訂正する対応は本タスクのスコープ外（影響範囲の精査が
別途必要）」として先送りしていた。**この積み残しは、測って解消した。**

| | 値 |
|---|---|
| 対象（始点≠終点の区間） | 5,062,593 |
| 測地線方位との平均誤差 | 0.074度 |
| 同 最大誤差 | 0.13度 |
| 1度を超える行 | **0件** |
| 平面方位との平均誤差 | 3.540度 |

現在の値は測地線方位と一致していて、平面方位とは3.5度離れている。0013のバックフィル分は
その後の再構築（Python側`bearing_between`）で全て置き換わっている。**T405の先送りは、
別タスクを起こす必要なく閉じてよい。**

## 対応

- `_WAY_TRAVEL_BEARING_SQL`を`::geography`付きにした。
- `WAY_DIVIDED_CARRIAGEWAY_ALGORITHM_VERSION`を`v1`→`v2`へ上げた。鮮度台帳が既存行を
  古い版として検知し、管理画面の再実行対象に現れる。
- migration 0013のコメントを訂正した（「bearing_betweenと同じ定義」は平面のままでは
  成り立たない）。**バックフィルのSQL自体は書き換えない**——適用済みの履歴であり、
  まっさらなDBではこの時点で`road_edges`が空なので実行されても何も書かない。

`divided`は路面タイルの`oneway`プロパティに効く（`w.direction != 'both' AND NOT
COALESCE(wdc.divided, false)`）。タイルの署名はSQLが変わらないので動かないが、バッチが
`derived_data_meta.revision`を進めるためタイル世代は入れ替わる。

## 検証

- PostGIS統合テストを1件追加（`test_travel_bearing_is_geodesic_not_planar`）。東西の道と、
  測地線方位で48度ずれた相方（同じref・40m以内）を置く。測地線なら許容角45度の外なので
  「対向ではない」が正しい。
- **効いていることの確認**: キャストを外すと平面では42度に見えてこのテストが落ちる
  （`assert True is False`）。戻すと通る。
- **本番で効いていることの確認**: `precompute_way_divided_carriageway`を本番へ実行した
  （1,333,039件・50.0秒）。`divided=true`が37,609→**37,593**となり、事前に測った
  測地線側の予測値と一致した。全行が`algorithm_version='v2'`になり、
  `derived_data_meta.revision`は13へ進んでタイル世代が入れ替わった。
