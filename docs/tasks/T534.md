# T534: 軸別スコアの事前計算キャッシュ(compute_edge_cost内部の速度改善)

## 背景

T522派生の調査(T522.md参照)で、`compute_edge_cost`の内部処理(タグパース・区分線形補間・
`AXIS_DEFINITIONS`の軸評価ループ)が探索ホットパスの支配的コストと判明した。風以外の
軸別スコアはEdgeの材料(`EdgeMaterialBundle`)のみから一意に決まり、リクエスト間で
不変であるにもかかわらず、現状は温キャッシュ時でも毎リクエスト再計算されている。
これをタイル単位でEdgeMaterialBundleと同じタイミングで事前計算・キャッシュし、
風に依存する軸(現状"wind"のみ)だけをリクエスト時に追加評価する設計へ変更する。

軸スタジオでの軸定義編集(`AxisRegistryAdminService`)は`refresh_axis_definitions`を
同期的に呼ぶ一点に集約されており、本番は`uvicorn --workers`未指定の単一プロセスの
ため、スコアキャッシュのクリアもこの一点にフックすれば編集直後のリクエストから
即座に新定義が反映される(ユーザーとの設計議論で確認済み)。

## 実装(2026-09-01完了)

「実装可能性の分析（設計）」→「実装」の順で進めた。

**設計**:
- `domain/attributes.py: EdgeMaterialBundle`（T533）とは別に、`domain/evaluation.py:
  compute_edge_static_axis_data`（風を除いた材料からEdge単位で決まる軸別スコアを
  `evaluate_axes_scalar`経由で計算する新関数）を追加した。
- どの軸が風（`wind_penalty`材料）へ依存するかは`domain/axis_definitions.py:
  REQUEST_DYNAMIC_MATERIAL_IDS`（現状`{"wind_penalty"}`のみ）を起点に
  `dynamic_axis_topological_order`が固定点反復で機械的に導出する（軸id・材料idの
  ハードコードを軸ごとに増やさない汎用設計。軸スタジオが将来風へ依存する新しい軸を
  作っても自動的に追従する）。実データ（本番相当14軸）では`["wind"]`のみと確認済み
  （`tests/test_axis_hierarchy.py:
  test_dynamic_axis_topological_order_matches_realistic_axis_definitions`）。
- `compute_edge_axis_scores_from_static_data`が、キャッシュ済みの静的軸別スコアへ
  風を組み込み、`dynamic_axis_topological_order`が返す軸だけをその場で再評価する。
- キャッシュ本体は`infrastructure/axis_score_cache.py`（Edge ID単位のフラットな
  遅延LRU、上限100万件）。`graph_material_cache`（材料そのもの）とは意図的に別に持ち、
  `axis_registry_service.py: refresh_axis_definitions`が`AXIS_DEFINITIONS.update()`と
  同じ同期ブロック内でこちらだけをクリアする（材料キャッシュは温存し、軸編集直後の
  リクエストがDBへ再問い合わせせずに済む）。
- `road_graph_engine.py`の`cost_fn`（`_build_edge_cost_fn`）が消費側。訪問Edgeごとに
  `axis_score_cache.get`→ミスなら計算・`set`→`compute_edge_cost_from_static_data`。

**検討して見送った追加最適化**: 静的軸のスコアもキャッシュ構築時点で公開軸だけへ
事前フィルタし、動的軸の評価自体を`evaluate_axes_scalar(skip_axis_ids=...)`で
スキップする、より踏み込んだ設計も試作したが、実データベンチマークで温キャッシュの
改善（1.53→1.66倍）に対し初回訪問（冷キャッシュ）が悪化した（0.82→0.77倍、
`dynamic_axis_topological_order`の呼び出しが2回に増える等の追加コストが温キャッシュ
での節約を上回った）ため差し戻し、単純な設計を採用した（`domain/evaluation.py:
compute_edge_static_axis_data`のdocstring参照）。

**テスト**: `compute_edge_cost_from_static_data`/`compute_edge_axis_scores_from_static_data`
が非キャッシュ版とビット単位で一致することを、風あり/なし・材料あり/なし・
Hard Constraint除外・カスタム重み等の組み合わせで回帰確認（`tests/test_evaluation.py`）。
`axis_score_cache`はプロセス内グローバル状態のため、`tests/conftest.py`へ全テスト共通の
autouseクリアフィクスチャを追加（同じedge_idを異なる材料で使い回す複数テストが汚染し
合わないようにするため。実際に`test_prepare_applies_precomputed_gradient_to_search_cost`
で汚染が顕在化し、テスト内でも明示的なclear()が必要だった）。
`refresh_axis_definitions`がキャッシュをクリアすることも`test_axis_registry_service.py`で
確認済み。バックエンド全体1476件（postgis含む）green。

**実測（渋谷相当bbox、24.7万Edge、ローカルdev DB、同一プロセス内での比較）**:
```
旧方式（常にフル計算）        1回目=3200ms  2回目=3215ms
新方式（T534キャッシュ）      1回目(冷)=3991ms  2回目(温)=2088ms
温キャッシュでの速度比: 1.54倍
冷キャッシュでの速度比: 0.80倍（初回訪問は約2割遅くなる）
```
初回訪問（キャッシュミス）はキャッシュへの書き込みコスト分だけ旧方式よりわずかに遅く
なるが、同じEdgeへの2回目以降のアクセスは1.54倍速い。1リクエスト内で同じEdgeを
複数回訪れるケース（8方位の探索が起点付近で重なる等）・同一エリアへの繰り返し
リクエストの両方で恩恵がある設計。本番サンプリングでの効果測定は次のステップ。
