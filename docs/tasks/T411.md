# T411. 動的＋向きあり要素の「way_id→値」配信を汎用化する検討（風・勾配の2例が揃ってから）

状態: **[T423](T423.md)へ統合（2026-08-30ユーザー判断）**——トリガー（2例目=勾配の実装
着手）が実際に成立したため、T423（勾配実装）の一部として同時に実施する。本タスク単独では
これ以上動かさない。詳細な対応方針はT423.md参照。

- **2026-08-30追記（T414起票時の訂正で判明した区別）**: 本タスクが「2例揃うまで待つ」と
  しているのは**バックエンドの配信コード**（Redis way_id→値キャッシュ層等）をいつ共有するか
  という実装判断であり、**動的材料の状態別表現契約**（ルート確定の有無でパラメータの出所と
  塗る対象が変わる、という状態機械そのもの）とは別の話。契約自体は材料の実装例を待たず
  最初から材料非依存で設計すべきもので、[T400.md](T400.md)「2.」節（2026-08-30訂正版）・
  [T414](T414.md)で確立済み。本タスクのスコープはあくまで「コードをどこまで共有するか」に
  限定されることを明記しておく（T405実装時にこの区別が曖昧だったという指摘を受けた）。

- 発端: T405（風の評価軸表示、Redis経由の`way_id→wind_penalty値`配信＋
  `GET /api/region/dynamic-way-values/wind/{z}/{x}/{y}`＋MapLibre `setFeatureState`連携）の
  実装中に、ユーザーから「この仕組みは他の動的＋向きあり要素（例: 勾配）を追加する際、
  一から作り直さずに済むよう汎用的にできないか」という懸念が出た。
- T405の実装（`wind_way_service.py`・`wind_way_penalty_cache.py`という専用モジュール、
  エンドポイントパスに`wind`を直書き）は**風専用**であり、現時点では汎用化していない
  （ユーザー了承のうえ、あえて汎用化せず先に完成させる判断とした。1例だけから汎用設計を
  推測すると外れるリスクがあるため、2例目が揃ってから共通部分を抽出する方が確実という
  判断）。
- **2例目の候補は既に判明している**: T400.md「7. kind=noneが残る範囲」節に「勾配
  （gradient）がkind=noneから外れるために必要なのは、標高データの永続化ではなく、
  風と同型のRedis配信層（`way_id`をキーにした動的値配信）の実装だけ」と明記済み。
  つまり次に同じパターンが必要になるのは高い確度で勾配。
- 想定作業: 勾配版の実装に着手する際、T405（風）の実装（`wind_way_service.py`・
  `wind_way_penalty_cache.py`・`region.py`の`/dynamic-way-values/wind/{z}/{x}/{y}`
  エンドポイント・フロント側の`setFeatureState`連携コード）を先に読み直し、両者を
  見比べたうえで、以下のような汎用化を検討する:
  - エンドポイントを`/api/region/dynamic-way-values/{material_id}/{z}/{x}/{y}`のような
    材料id駆動の1本化にできないか
  - Redisキャッシュ層（`way_id→値`のTTLキャッシュ）を、計算式（風なら`wind_penalty`、
    勾配なら別の式）だけを差し替え可能な共通モジュールへ抽出できないか
  - フロントの`setFeatureState`連携ロジックを、材料ごとに複製せず共通化できないか
- トリガー: 勾配（または他の動的＋向きあり材料）を評価軸グループの軸として地図表示する
  実装に着手する判断をした時点。それまでは風専用の実装のまま運用する。
