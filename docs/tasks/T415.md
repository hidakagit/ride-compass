# T415. pytest-xdist並列実行時のDB競合フレークを調査する（T248で発見・未着手のまま放置）

状態: 未着手（起票のみ）

- 背景: [T248](T248.md)（road_graphのGiST/asyncpg改善）の検証中（2026-08-24）、
  pytest-xdist（`-n auto`）実行時にのみ、本タスクの変更とは無関係に発生する既存のDB競合
  フレークを発見した——`test_get_nearest_stop_poi_counts_...`・
  `test_recompute_way_attribute_counts_...`の2件が`IntegrityError`で失敗する。T248は
  「変更前のコードへ`git stash`で一時的に戻し、同一条件で同じ2件が再現することを確認済み」
  （＝T248由来のリグレッションではなく既存の潜在バグ）とした上で、「CI・並列実行時の
  安定性リスクとして記録のみ残す。追加調査は本タスクのスコープ外」と明記していたが、
  以降のどのタスクにも引き継がれずタスク番号を振られないまま埋もれていた
  （2026-08-30、CLAUDE.md「分割元タスク完了前のフラグ回収」ルール新設に伴う既存docs監査で
  発覚）。
- 影響: `-n auto`並列実行時にランダムにこの2テストが落ちる可能性が残ったまま。CIが
  pytest-xdistで並列化されている（`docs/testing.md`参照）ため、無関係な変更のPRでも
  フレークによりCIが赤くなるリスクがある。原因（複数ワーカーが同じDB行へ同時に書き込む
  競合か、テスト間のデータ後始末順序依存か等）は未特定。
- 対応方針（未検討、着手時に決定）: まず両テストの内容（`test_get_nearest_stop_poi_counts_...`
  はstop POI集計、`test_recompute_way_attribute_counts_...`はway属性再集計）とテストDB上の
  書き込み先を確認し、複数ワーカー間で同じ行/テーブルへ競合书き込みが起きていないか
  切り分ける。`pytest.mark.xdist_group`（同じDBリソースを使うテストを同一ワーカーへ強制する
  既存の仕組み、`docs/testing.md`参照）で解消できる可能性がある。
