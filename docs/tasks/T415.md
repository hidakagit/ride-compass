# T415. pytest-xdist並列実行時のDB競合フレークを調査する（T248で発見・未着手のまま放置）

状態: 調査完了・未再現のまま記録（規模Sの調査タスクとして完了、追加のコード変更なし）

- 背景: [T248](T248.md)（road_graphのGiST/asyncpg改善）の検証中（2026-08-24）、
  pytest-xdist（`-n auto`）実行時にのみ、本タスクの変更とは無関係に発生する既存のDB競合
  フレークを発見した——`test_get_nearest_stop_poi_counts_...`・
  `test_recompute_way_attribute_counts_...`の2件が`IntegrityError`で失敗する。T248は
  「変更前のコードへ`git stash`で一時的に戻し、同一条件で同じ2件が再現することを確認済み」
  （＝T248由来のリグレッションではなく既存の潜在バグ）とした上で、「CI・並列実行時の
  安定性リスクとして記録のみ残す。追加調査は本タスクのスコープ外」と明記していたが、
  以降のどのタスクにも引き継がれずタスク番号を振られないまま埋もれていた
  （2026-08-30、CLAUDE.md「分割元タスク完了前のフラグ回収」ルール新設に伴う既存docs監査で
  発覚）。
- 影響: `-n auto`並列実行時にランダムにこの2テストが落ちる可能性が残ったまま。CIが
  pytest-xdistで並列化されている（`docs/testing.md`参照）ため、無関係な変更のPRでも
  フレークによりCIが赤くなるリスクがある。原因（複数ワーカーが同じDB行へ同時に書き込む
  競合か、テスト間のデータ後始末順序依存か等）は未特定。
- 対応方針（未検討、着手時に決定）: まず両テストの内容（`test_get_nearest_stop_poi_counts_...`
  はstop POI集計、`test_recompute_way_attribute_counts_...`はway属性再集計）とテストDB上の
  書き込み先を確認し、複数ワーカー間で同じ行/テーブルへ競合书き込みが起きていないか
  切り分ける。`pytest.mark.xdist_group`（同じDBリソースを使うテストを同一ワーカーへ強制する
  既存の仕組み、`docs/testing.md`参照）で解消できる可能性がある。

## 調査結果（2026-08-30実施）

### 前提の誤りを発見: `xdist_group="postgis"`はT248発見時点で既に導入済みだった

起票時の「対応方針」は`xdist_group="postgis"`未適用を前提にしていたが、実際には
**T248がこのフレークを発見した時点（2026-08-24）で、`xdist_group="postgis"`は既に
1日前のT235（2026-08-23、改善計画T233フォローアップ）で全PostGIS統合テストファイルへ
適用済みだった**（`git log -p`で確認）。対象2テストが属する`test_road_graph_repository.py`
含め、DB接続する12ファイル全てに`pytestmark = [pytest.mark.asyncio(loop_scope="module"),
pytest.mark.xdist_group(name="postgis")]`が付いており、T248はこれが有効な状態のまま
フレークを踏んでいる。つまり「`xdist_group`未適用が原因」という仮説はそもそも成立せず、
本タスクの出発点だった対応方針は前提から見直す必要があった。

### テスト構造の確認

- 対象2テストはどちらも`backend/tests/test_road_graph_repository.py`内（
  `test_get_nearest_stop_poi_counts_excludes_supply_poi_kinds`・
  `test_get_nearest_stop_poi_counts_counts_pois_near_each_point`・
  `test_recompute_way_attribute_counts_computes_per_way_facts`）。
- `conftest.py`の`road_graph_session`フィクスチャは**関数スコープ**（`road_graph_engine`は
  モジュールスコープ）で、各テスト終了後に`Base.metadata.sorted_tables`を逆順で全削除する
  後始末を行う。両テストを含む多数のテストが`osm_node_id=900`のようなハードコードIDを
  使い回しているが、これはこの後始末が確実に効くという前提に依存した設計であり、
  単一プロセス・単一ワーカー内で厳密に逐次実行される限り安全に成立する。
- `recompute_way_attribute_counts`が書くSQL（`_RECOMPUTE_WAY_ATTRIBUTE_COUNTS_SQL`）は
  `ON CONFLICT (osm_way_id) DO UPDATE`のUPSERTで、同一キーへの並行INSERTに対して
  PostgreSQL側で安全に処理される設計。`get_nearest_stop_poi_counts`自体は読み取り専用
  （SELECT）で、IntegrityErrorが起きうるとすれば`_insert_poi`ヘルパーによる
  テストセットアップ側のINSERT（`osm_raw_pois.osm_node_id`重複）のみ。

### 再現試行（ローカルPostgreSQL `ridecompass_test`、実DB接続で実施）

`docs/testing.md`のPostGISテストDB前提どおり、`backend/.venv`から`TEST_DATABASE_URL`
既定値（`postgresql+asyncpg://ridecompass:ridecompass@localhost:5432/ridecompass_test`）へ
実接続できることを確認した上で、以下4回すべて実行した（Windows実行時、execnetの
ゲートウェイ起動がOneDrive配下の非ASCIIパスでUnicodeEncodeErrorを起こすため、
`PYTHONUTF8=1 PYTHONIOENCODING=utf-8`を付与して回避——本調査中に踏んだ環境固有の
問題で、コード側のバグではない）。

1. `test_road_graph_repository.py`＋`test_match_designations.py`を`-n 4 --dist loadgroup`
   で実行: 112件全green（245秒）。
2. 同条件で再実行: 112件全green（404秒、後述の並行セッション干渉で所要時間が増加）。
3. CIと同一コマンド`pytest -q -n auto --dist loadgroup`でbackend全体を実行:
   1094 passed, 362 skipped, 0 failed（195秒）。
4. 同条件で再実行: 1094 passed, 362 skipped, 0 failed（178秒）。

**4回とも対象2テストを含め一度も失敗せず、フレークを再現できなかった。**

### 環境要因の実地確認（CIリスクとは切り分けて記録）

調査中、`ps aux`で本セッションのworktreeとは別の並行Claude Codeセッション
（`.claude/worktrees/agent-acc8d629b031306c9`）が、同じ`backend/venv`のPythonプロセスで
稼働中であることを実際に確認した。`TEST_DATABASE_URL`は全worktreeで同じ既定値
（`localhost:5432/ridecompass_test`）を指すため、**ローカル環境では複数の並行セッションが
物理的に同一のテスト用PostgreSQLへ同時アクセスしうる**。`xdist_group`は同一pytest呼び出し
内のワーカー間競合しか防がず、別プロセス（別セッションの`pytest`実行）からの干渉は
防げない。既存メモリ「Parallel Worktree Resource Contention」（worktreeはコード分離のみで
テストDB自体は共有される、2026-08-16実測）と整合する具体例と言える。

一方、CI（`.github/workflows/ci.yml`）はジョブごとに専用のPostgresサービスコンテナ
（GitHub Actions services、ジョブ終了時に破棄）を使うため、**この経路の干渉はCI上では
原理的に発生しない**。したがって「ローカルでの再現しづらさ」と「CIでのフレーク発生
リスク」は別軸の問題であり、今回ローカルで再現できなかったことをもってCI側のリスクが
否定されるわけではない。

### 結論・今後の扱い

- 原因は特定できなかった。当初仮説（`xdist_group`未適用）は前提が誤りだったため却下。
  4回の再現試行はいずれも全green（対象2テストを含む）。
- 有力な仮説として、ローカル環境固有の「複数worktree/セッションによる同一テストDBへの
  並行アクセス」を記録として残す。ただしCIには影響しない構造（ジョブ専有コンテナ）の
  ため、CI赤化リスクとしての優先度は現時点で確認できていない。
- 保留した場合の影響範囲: 本調査で原因を確定・修正できなかったため、`-n auto`並列実行時に
  この2テストがまれに`IntegrityError`で落ちるリスクは理論上残ったままである。ただし
  CI環境（ジョブ専有Postgresコンテナ）では今回特定した環境要因（worktree間のDB共有）が
  作用しないため、CI側での再現性・発生頻度は本調査だけでは未確認。次にCIでこの2テストの
  失敗が実際に観測された場合は、CIのジョブログ（失敗時のスタックトレース・同時実行され
  ていた他ジョブの有無）を最初の切り分け材料にするとよい。
- 追加のコード変更は行わなかった（規模Sの調査タスクとして、原因未特定のまま状況を記録
  する形で完了とする）。
