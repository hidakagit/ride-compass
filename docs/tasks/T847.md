# T847. 材料キャッシュの世代を、コード定数ではなくDBを正にする

規模M。
状態: 未着手（2026-09-14起票。ユーザー方針「なるべくシンプルな運用にしたい。変わる値はdbが正」）

## 背景

派生データを作り直したあと、人間が`cache_identity.py`の`MATERIAL_REVISION`を書き換えて
pushしないと、ディスクへキャッシュ済みだったタイルは古い材料のまま復元され続ける。上げ忘れ
ても全体が壊れるわけではなく、**未訪問のタイルだけが新しい値になる**ため、「一部のエリアだけ
直っている」形で気づきにくい（定数自身のコメントが同じことを警告している）。

管理画面の「データ保守」タブが出す1コマンド（[T844](T844.md)）を打っても作業は終わらず、
この書き換えとpushが残る——**コマンドをコピーできる形にしても、導線としては途切れている**。

同じ問題を軸定義は既に解いている。`axis_registry_meta.revision`（軸の追加・更新・削除の
たびにDB側で増える単調カウンタ）をDBに持ち、`tile_score_matrix_cache.py:
sync_disk_cache_with_axis_revision`がディスクへ最後に書いた時点の記録と突き合わせて、
違えばディスクを消す。軸はGUIで編集してもデプロイが要らない。材料世代だけがコード定数のまま
取り残されている。

## 方針（ユーザー決定、2026-09-14）

**変わる値はDBを正にする。** `MATERIAL_REVISION`は撤去する。

分けて扱う成分が2つある。

- **形の署名**（`EdgeMaterialTable`の列構成）はコード側に残す。デプロイでしか変わらず、
  既に`cache_identity`が自動導出している。
- **データの世代**（派生データを作り直したか）をDBへ移す。これがいま手で書き換えている側。

キャッシュ鍵はこの2つの合成にする（軸定義の`sync_*`が「不一致なら消す」形を採っているのに
対し、こちらは鍵そのものを変える形でよいか——どちらの形に寄せるかは実装時に決める）。

### 読み直すきっかけ

バッチはVM上の別コンテナで走るだけでbackendは再起動しない。いまは「pushする→デプロイ→
再起動」が結果的にきっかけを兼ねているため、DBへ移してpushを不要にすると、**今度は誰も
再起動しないので世代の変化に気づかない**という裏返しの問題になる。

推奨は**プロセス内にTTL付きで持って、期限が切れたら読み直す**（遅延・pull）。専用の
バックグラウンドジョブも、バッチからbackendへの呼び出しも足さない。起動時ジョブを増やすのは
一過性の障害を起こした経緯があるため避ける（[weather-api-cold-start-failure]の症状と同型）。
古いままになりうる窓はTTL分だけ残るが、現状の「誰かが思い出すまで」という無制限の窓より短い。
TTLは「バッチ完了からどれだけ遅れて反映されてよいか」から導く（docs/caching.mdの「判断を
キャッシュしてよい条件」に沿う）。

採らなかった案: ①バッチ完了時に管理APIを叩く（バッチがbackendのURLと認証を知る必要があり、
呼び出しが失敗すると静かに元の問題へ戻る）。②専用の定期ジョブ（上記のとおり起動時ジョブを
増やしたくない）。

## 未決（実装時に決める）

- **DBのどこに持つか**: 新しい1行のカウンタを置くか、鮮度台帳が既に読んでいる系譜
  （`source_*_run_id`・`computed_at`・`algorithm_version`）から導出するか。後者は新しい
  書き込み経路が要らない代わりに、合成する材料が増える。
- **誰が上げるか**: precompute系バッチは共通ドライバ（`_common.py`）を通るものと自前ループの
  ものがあるため、1箇所で確実に上がる置き場所を決める必要がある。
- 旧世代のディスク実体を消す導線（`prune_stale_generations`）が、世代が変わる新しい
  タイミングでも確実に走ること。
