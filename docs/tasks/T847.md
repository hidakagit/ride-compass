# T847. 材料キャッシュの世代を、コード定数ではなくDBを正にする

規模M。
状態: 完了（2026-09-14。ユーザー方針「なるべくシンプルな運用にしたい。変わる値はdbが正」）

## 背景

派生データを作り直したあと、人間が`cache_identity.py`の`MATERIAL_REVISION`を書き換えて
pushしないと、ディスクへキャッシュ済みだったタイルは古い材料のまま復元され続ける。上げ忘れ
ても全体が壊れるわけではなく、**未訪問のタイルだけが新しい値になる**ため、「一部のエリアだけ
直っている」形で気づきにくい（定数自身のコメントが同じことを警告していた）。

管理画面の「データ保守」タブが出す1コマンド（[T844](T844.md)）を打っても作業は終わらず、
この書き換えとpushが残る——**コマンドをコピーできる形にしても、導線としては途切れている**。

同じ問題を軸定義は既に解いている。`axis_registry_meta.revision`（軸の追加・更新・削除の
たびにDB側で増える単調カウンタ）をDBに持ち、`tile_score_matrix_cache.py:
sync_disk_cache_with_axis_revision`がディスクへ最後に書いた時点の記録と突き合わせて、
違えばディスクを消す。軸はGUIで編集してもデプロイが要らない。材料世代だけがコード定数のまま
取り残されていた。

## 方針（ユーザー決定、2026-09-14）

**変わる値はDBを正にする。** `MATERIAL_REVISION`は撤去した。

分けて扱う成分が2つある。

- **形の署名**（`EdgeMaterialTable`の列構成）はコード側に残す。デプロイでしか変わらず、
  既に`cache_identity`が自動導出している。
- **データの世代**（派生データを作り直したか）をDBへ移す。これが手で書き換えていた側。

鍵そのものを変える方式は採らず、軸定義と同じ「マーカーと突き合わせて不一致なら消す」形に
した。鍵を実行時に変えるとディスク上へ旧世代の実体が積み上がり、掃除の導線を別に用意する
必要が出る。消す方式なら世代が変わった瞬間に実体も消える。

### 読み直すきっかけ

バッチはVM上の別コンテナで走るだけでbackendは再起動しない。従来は「pushする→デプロイ→
再起動」がきっかけを兼ねていたため、DBへ移してpushを不要にすると、今度は誰も再起動しないので
世代の変化に気づかなくなる。

**プロセス内にTTL付きで持って、期限が切れたら読み直す**（遅延・pull。ユーザー決定、
2026-09-14）。専用のバックグラウンドジョブも、バッチからbackendへの呼び出しも足さない。
起動時ジョブを増やすのは一過性の起動失敗を招くため避ける。古いままになりうる窓はTTL分だけ
残るが、従来の「誰かが思い出すまで」という無制限の窓より短い。

採らなかった案: ①バッチ完了時に管理APIを叩く（反映は即時だが、バッチがbackendのURLと認証を
知る必要があり、呼び出しが失敗すると静かに元の問題へ戻る）。②専用の定期ジョブ（上記のとおり
起動時ジョブを増やしたくない）。③リクエストのたびにDBを見る（遅れは無いが、ルート生成の熱い
経路で毎回小さな問い合わせが増える）。

### 系譜からの導出を採らなかった理由

鮮度台帳が既に読んでいる系譜（`source_*_import_run_id`・`algorithm_version`）から導出すれば
新しい書き込み経路が要らないが、**同じ取込run・同じ版数のままバッチをもう一度回した場合に
系譜が変わらない**。バッチ側のバグ修正後の再実行・`refresh_derived.py`の再実行がまさにこの
形で、いちばん直したい場面を取りこぼす。「中身を書き直した」という事実を表せるのは書いた側が
進めるカウンタだけである。

`computed_at`の最大値から導く案も、500万行規模のテーブルに対する`max()`をTTLごとに走らせる
ことになり、索引が無ければ毎回の全走査になる。

### 誰が上げるか

バッチの**入口**（`main`）を`_common.py: with_derived_data_revision_bump`で包み、終了コード0
かつdry-runでない場合に進める。どのバッチが材料に効くかを個別に判断しない——効かないバッチで
余分に進めてもキャッシュが1度作り直されるだけだが、効くバッチで進め忘れると静かに古い値が
残る。`run_simple_batch_cli`経由のバッチは自動的にこの経路を通る。

新しいバッチが素の`asyncio.run(run(...))`で書かれると同じ穴が開くため、入口の形を
`tests/test_batch_common.py: test_every_batch_entry_point_bumps_the_derived_data_revision`
が固定する。

## 実装メモ

- migration `0039_add_derived_data_meta.sql`と`infrastructure/derived_data_meta.py`
  （`axis_registry_meta`と同じ1行テーブルの形）。
- `graph_material_cache.TILE_MATERIALS_CACHE_VERSION`は`shape_digest(EdgeMaterialTable)`
  （形だけ）になり、`sync_disk_cache_with_derived_data_revision`を追加した。
- `services/derived_data_revision_service.py`がTTLの門番。材料を捨てたときは
  `tile_score_matrix_cache`も捨てる（スコア行列は材料からの派生物）。
- 呼び出し点は`GraphService.get_search_materials_for_bbox`の先頭。起動時の専用ジョブは
  足していない——TTLの初期値が0のため、プロセス起動後の最初の1回は必ずDBを読む。
- 世代の更新に失敗してもバッチの終了コードは変えない。データは既に書けており、キャッシュの
  追随は次のTTLでも回復するため、そこで失敗扱いにする方が害が大きい。

## 残る手作業

`ROAD_SURFACE_REVISION`・`POI_REVISION`・`ACCIDENT_REVISION`（タイルへ焼き込む側）は手で
上げる運用のまま。これらの世代は生成物`region-tile-config.json`を通じてフロントへ配られる
ため、実行時に変えるとフロントが知る世代とずれる。同じ性質の問題が残っているが、解くには
配信側の世代をどう配るかから決める必要があり、本タスクの範囲外とした。
