# T532: 探索中の風評価を時変化（時刻依存の到達時刻ベース再評価）に対応する

状態: 未着手（2026-09-01起票。ユーザー提案。前提としていたT529は本方式では実装されず
2026-09-05に完了[別方式のT536で目的達成]、T530は完了。ただし下記「前提の再検討」参照
——T536はT529とは逆方向のアーキテクチャ[探索前に一括ベクトル計算、Pythonコールバック

- 背景: 現行の探索（`road_graph_engine.py`）は「風は出発時点の起点付近の風を
  ルート全体に一様適用する（探索中は到達時刻が未確定のため、区間ごとの推定
  到達時刻の風は使わない）」という簡略化を採用している（`_build_search_graph`
  docstring明記）。ロードバイクは自動車と異なり時速20〜30km程度で、100kmの
  ルートには4〜5時間かかりうるため、出発時点の風のまま終盤の区間まで評価すると、
  実際の走行時には風向きが変わっている可能性が高い。
- ユーザー提案（2026-09-01）: 時変グラフ（Time-Dependent Graph）の導入。
  ノードに到達した時点の`g_score`（スタートからの累計コスト・実時間）から
  「今何時頃にここに到達するか」を概算し、その到達予想時刻の風データ（1時間
  予報のグリッドデータ等）をオンデマンドで参照してコストを決定する。これにより
  「午後から向かい風になるから午前中のうちにこっちのルートで帰ってこよう」
  という走行方位・時間帯を跨いだ高度なルーティングが可能になる。
- 前提の再検討（2026-09-05、`/task:next`実行時にT529の状態を見直した際に発覚）:
  起票時点では[T529](T529.md)（探索コストのlazy評価化、rustworkx+A*、`edge_cost_fn`が
  Edgeごとに都度呼ばれる設計）を基盤として想定していた——到達時刻を都度見て風データを
  オンデマンドで引き直す処理は、Edgeごとに呼ばれるコールバックがあって初めて自然に
  差し込める。しかしT529は本実装に着手される前に[T536](T536.md)へ置き換わり、
  T536は**逆方向**のアーキテクチャ（探索前にbbox全体のコスト配列を1回だけ構築し、
  A*はその配列への素の`list.__getitem__`のみを行う。「探索中にPythonの関数フレームを
  一切作らない」ことが高速化の核心）を採用して完了・本番反映済みである
  （[T530](T530.md)は完了）。
  つまり本タスクが前提としていた「Edgeごとに都度呼ばれるコールバック」という差し込み
  ポイント自体がもう無い。時変コストを導入するには、T536の「探索前に1回だけ配列を
  構築する」設計と両立する形（例: 到達時刻の粗いバケツ[15分刻み等]ごとに複数のコスト
  配列を事前構築しA*側で切り替える、等）を新たに設計する必要があり、旧`edge_cost_fn`
  ベースの想定はそのままでは使えない。着手判断の前に、この設計課題を検討し直すこと。
- 検討が必要な点（未着手のため未確定）:
  1. 到達予想時刻の算出方法（`g_score`＝累計コスト[m]から実時間へ逆算する
     仮定巡航速度、`domain/wind.py: ASSUMED_SPEED_KMH`が既存の類似定数として
     ある）。
  2. 風データの時間解像度（1時間予報グリッド等）と、探索中にオンデマンドで
     引く際のキャッシュ設計（同一時刻帯・同一グリッドセルへの再問い合わせを
     避ける）。
  3. A*のヒューリスティック（`_build_estimate_cost_fn`、直線距離ベース）との
     整合性——時変コストを導入してもadmissibility（`docs/decisions/

## 技術的結論（2026-09-05、`/task:next`実行時の状態見直しを受けた深掘り）

**現状（本タスク未着手時点）の挙動**: 風評価は起点1点・呼び出し時点の現在時刻のスナップ
ショット（`WeatherService.get_conditions`、`RoadGraphEngine.prepare`が1リクエストにつき
1回だけ取得、`road_graph_engine.py:406`）を、bbox内の全Edgeへ一様に適用している
（`domain/evaluation.py: _evaluate_wind_penalty_array`は`weather.wind_speed_ms`・
`weather.wind_direction_deg`という単一のスカラー値と各Edge自身の`bearing_deg`配列から
`wind_speed_ms * cos(wind_direction_deg - bearing_deg)`をベクトル計算するのみで、
Edgeの位置や到達予想時刻は一切参照しない）。したがって**「今は追い風の区間でも、
実際にそこへ到達する数時間後には向かい風に変わっている」というケースを現状は
評価できていない**——本タスクが解決しようとしている問題そのものが、まだ手つかずで
残っている。

**時間依存化が技術的に困難な理由**: 探索本体（`domain/routing.py:
shortest_path_node_ids_lazy`）はrustworkx（Rust実装）の`rx.astar_shortest_path`を
直接呼んでおり、`edge_cost_fn`のシグネチャは`Callable[[int], float]`——Edge indexのみを
受け取り、探索中の経路状態（現在の累計コスト・到達予想時刻）を一切受け取れない。
T536は「探索前にコスト配列を1回だけ構築し、A*は`cost_list.__getitem__`のような
素のlistアクセスだけを行う」ことで高速化しており（Pythonの関数フレームを探索中に
作らない）、この契約を保ったままEdgeごとに動的な時刻依存コストを注入する余地が無い。

**現実的な実装方針**: 時刻依存最短路問題の標準的な解法である**時間展開グラフ
（time-expanded graph）**——ノードを「(地点, 時刻バケット)」のペアへ複製し、
時刻バケットごとに別々のコスト配列（T536と同じ「探索前に1回だけ構築する配列」を
バケット数ぶん用意する）を割り当てる方式——であれば、T536の「precompute→配列参照
のみ」という設計思想と両立できる。ヒューリスティック（直線距離）は時刻に依存しない
ため、A*のadmissibility（`docs/decisions/t12-routing-scale.md`原則1）もそのまま
保たれる。ただしグラフサイズが時刻バケット数倍に膨らむ（例: 5時間のルートを
30分刻みにすると10倍）ため、既に数十万Edge規模のbboxグラフに対する影響（メモリ・
prepare時間）は着手前に試算が必要。

**結論**: 「検討が必要な点1〜5を詰めれば着手できる」規模ではなく、時間展開グラフという
新しいアルゴリズム基盤を1つ導入する規模Lの設計タスクである。着手する場合は、まず
グラフサイズ膨張の試算（本番相当bboxでの時刻バケット数と規模の関係）から始めること。
