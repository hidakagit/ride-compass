# T532: 探索中の風評価を時変化（時刻依存の到達時刻ベース再評価）に対応する

状態: 未着手（2026-09-01起票。ユーザー提案、T529/T530完了後の着手を想定）

- 背景: 現行の探索（`road_graph_engine.py`）は「風は出発時点の起点付近の風を
  ルート全体に一様適用する（探索中は到達時刻が未確定のため、区間ごとの推定
  到達時刻の風は使わない）」という簡略化を採用している（`_build_search_graph`
  docstring明記）。ロードバイクは自動車と異なり時速20〜30km程度で、100kmの
  ルートには4〜5時間かかりうるため、出発時点の風のまま終盤の区間まで評価すると、
  実際の走行時には風向きが変わっている可能性が高い。
- ユーザー提案（2026-09-01）: 時変グラフ（Time-Dependent Graph）の導入。
  ノードに到達した時点の`g_score`（スタートからの累計コスト・実時間）から
  「今何時頃にここに到達するか」を概算し、その到達予想時刻の風データ（1時間
  予報のグリッドデータ等）をオンデマンドで参照してコストを決定する。これにより
  「午後から向かい風になるから午前中のうちにこっちのルートで帰ってこよう」
  という走行方位・時間帯を跨いだ高度なルーティングが可能になる。
- 前提となる基盤: [T529](T529.md)（探索コストのlazy評価化、rustworkx+A*）・
  [T530](T530.md)（wind/nightを汎用的な動的コンテキストへ統合するリネーム・
  再設計）の両方が完了していること。特にT529のlazy評価（`edge_cost_fn`が
  Edgeごとに都度呼ばれる設計）が無いと、探索中に到達時刻を都度見て風データを
  引き直すという処理自体が高コストになる（T529の基盤があって初めて現実的な
  実装コストで成立する、という点はT531（フロンティア基準の周回ルート生成）と
  同じ構造）。
- 検討が必要な点（未着手のため未確定）:
  1. 到達予想時刻の算出方法（`g_score`＝累計コスト[m]から実時間へ逆算する
     仮定巡航速度、`domain/wind.py: ASSUMED_SPEED_KMH`が既存の類似定数として
     ある）。
  2. 風データの時間解像度（1時間予報グリッド等）と、探索中にオンデマンドで
     引く際のキャッシュ設計（同一時刻帯・同一グリッドセルへの再問い合わせを
     避ける）。
  3. A*のヒューリスティック（`_build_estimate_cost_fn`、直線距離ベース）との
     整合性——時変コストを導入してもadmissibility（`docs/decisions/
     t12-routing-scale.md`原則1「cost ≥ distance_m」の不変条件）を壊さない設計に
     すること。
  4. 8方位×最大3レグの現行探索構造・`cost_cache`（1リクエスト内でのEdgeコスト
     再利用）との関係——到達時刻依存になるとコストが「いつ通ったか」で変わるため、
     単純なEdge単位のキャッシュキーでは足りなくなる可能性がある。
  5. 気象予報APIの呼び出し回数増加への対策（現状は起点付近の風を1回だけ取得。
     時変化すると探索中に複数の時刻・複数のグリッドセルへ問い合わせが必要になる
     見込み）。
- 完了条件: 未確定（設計判断1〜5を先に固めてから着手する）。T529/T530完了後に
  着手判断を行う。
