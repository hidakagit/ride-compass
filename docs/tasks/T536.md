# T536: 探索コストを「タイル単位の静的スコア行列＋リクエスト時ベクトル計算」へ変え、A*からPythonコールバックを外す

状態: 実装完了・本番未検証（2026-09-02起票、[T522](T522.md)「評価ロジック全体の再点検」で判明。
本番VM試作でA* 24本 8.3〜17.7秒→0.37秒を確認済み。2026-09-02、対応方針1〜5を実装し
ローカル/dev DB環境での回帰テスト・速度サニティチェックまで完了。同日、本番Oracle VMの
使い捨てコンテナ（東京駅30km・split済み条件）での実測でbbox内に空タイル（Edge0件）が
混在するケースの不具合が発覚し修正済み（詳細は本ファイル末尾「本番実測で判明した不具合の
修正」節）。pushはユーザー確認後に別途実施するため、本番の同一条件での`trace_ms`実測は
このタスクのスコープ外として残る）。

- 背景: T529（lazy A*）・T534（軸スコアの辞書キャッシュ）後も、探索中のEdge1本あたりの
  コスト計算が本番VMで約50〜60µsかかり、A* 24本で温8.3秒・冷17.7秒を占める。
  内訳の43%は`dynamic_axis_topological_order`のキャッシュキー計算（`AxisDefinition.
  materials`をEdgeごとに全軸ぶん再構築）、残りも風軸の再評価・合成・
  `EdgeCostResult.model_construct`といったEdgeごとのPython処理。T529が「一括評価は
  18秒で遅い」と判断した根拠はPythonの逐次抽出フェーズであり、抽出をタイル単位で1回だけ
  行えば一括評価自体は0.1秒台で済む（T522.md実測）。
- 対応方針:
  1. タイル読込時（`GraphService._get_or_build_tile_materials`）に、`evaluate_axis_array`
     （`compute_edge_costs_bulk`の計算フェーズをそのまま流用）で「Edge×公開軸」の
     静的スコア行列（風など`REQUEST_DYNAMIC_MATERIAL_IDS`に依存する軸の列はNaN）と、
     `distance_m`・`bearing_deg`・0次フィルタ判定用の配列（highway種別・`bicycle=no`・
     勾配）をタイル単位でキャッシュする（`graph_material_cache`と同じ寿命・無効化、
     軸定義変更時は`axis_score_cache`と同様に`refresh_axis_definitions`でクリア）。
     `axis_score_cache`（Edgeごとの辞書、約1.3KB/Edge）はこの行列（8軸×8B/Edge）へ
     置き換えて廃止する。
  2. リクエスト時は、風の列（`wind_penalty`をbearing配列からベクトル計算し
     `evaluate_axis_array`で風軸を評価）と重みベクトルから、`compute_edge_costs_bulk`と
     同じ式（Neumaier加算・`round1_array`）でコスト配列を作り、0次フィルタ除外Edgeは
     `inf`にする。`RoutePreference.with_time_scope`（夜間）も重みベクトル側で吸収する。
  3. `LazyRoadGraph`のEdge payloadを整数Edge索引にし、`shortest_path_node_ids_lazy`へ
     `edge_cost_fn=cost_list.__getitem__`を渡す。A*の推定関数もレグごとに全Nodeの
     直線距離をnumpyで1回計算し`est_list.__getitem__`を渡す（Pythonのフレームを
     探索中に一切作らない）。同一Node間の並行Edgeは「cost最小を採用」（T363の元の
     意味論）へ戻せる（コストが事前に分かるため）。
  4. `_RoadGraphContext.cost_cache`は不要になる。`_build_segment_details`（区間表示）は
     同じコスト配列・スコア行列から`axis_difficulties`を引けるため、探索と表示の
     二重計算（T522.md「評価ロジック入口〜出口の再点検」1項）も同時に解消できる。
  5. 8方位の`trace_loop`は`to_thread`並列をやめ直列（1スレッド）で回す（GIL競合で
     並列の方が約2秒遅い実測）。rustworkx内部で完結する探索になれば、必要に応じて
     `to_thread`1本で全方位をまとめて逃がす。
- 本タスク着手までの暫定改善（本タスクを実装すれば不要になるため、着手時期が近ければ
  やらない）: `dynamic_axis_topological_order`と公開軸リストを`_build_edge_cost_fn`で
  1回だけ求めてEdgeごとに再計算しない（Edge1本あたり43%削減）、`_build_estimate_cost_fn`
  のPydantic`Coordinates`生成を素のhaversineへ（A* 24本 8.3→7.0秒）、`cost_fn`の
  `EdgeCostResult.model_construct`をfloat返却へ（約10%）、`build_lazy_road_graph`を
  `add_edges_from`一括投入＋ソート撤廃へ（957→565ms）、`axis_score_cache`の上限を
  メモリ試算（1.27GB）に合わせて下げる。
- 関連: [T529](T529.md)（lazy A*、本タスクで一括評価へ戻すが、遅かった原因である逐次
  抽出は復活させない）、[T534](T534.md)（辞書キャッシュを行列へ置き換え）、
  [T531](T531.md)（フロンティア方式は「lazy評価が前提」としているが、コスト配列は
  任意の探索から参照できるため前提は本方式でも満たされる）、[T537](T537.md)
  （グラフ・索引のキャッシュ。本タスクと独立に着手可能）。
- 完了条件:
  - 新方式の候補ルート（Edge列・distance_km・segmentsのdifficulty）が現行
    `compute_edge_cost`経路とビット単位で一致する回帰テスト（`compute_edge_costs_bulk`が
    スカラー版のオラクルで検証済みなのと同じ形）がpass
  - 本番の同一条件（東京駅30km、T522.md記載）で`trace_ms`が1秒未満、プロセスの

## 実装（2026-09-02、対応方針1〜5）

対応方針1〜5をそのまま実装した。要点:

1. **静的スコア行列**: `domain/evaluation.py`の`compute_edge_costs_bulk`を、抽出＋計算
   フェーズ（`_evaluate_axes_bulk`、新設）と重み付き合成フェーズ（
   `compose_costs_from_axis_matrix`、新設）へ分割し、`build_static_edge_score_matrix`
   （新設）が`_evaluate_axes_bulk`を`wind=None`で呼んで`StaticEdgeScoreMatrix`
   （Edge×公開軸の静的スコア行列＋distance_m/bearing_deg/0次フィルタ判定用の生配列
   `is_motorway`/`is_trunk`/`no_bicycle`/`gradient_percent`）を構築する。動的軸
   （風）の列はwind_penaltyがNaN配列になることで自然にNaNへ伝播し、軸ごとの特別扱いは
   不要（`evaluate_axis_array`の既存のNaN伝播をそのまま利用）。`GraphService.
   _get_or_build_tile_materials`と対になる`_get_or_build_tile_score_matrix`が
   タイル単位で`infrastructure/tile_score_matrix_cache.py`（旧`axis_score_cache.py`の
   後継、削除済み）へキャッシュする。複数タイルの結合は`combine_static_edge_score_matrices`
   （新設、後勝ちセマンティクス、numpy fancy indexingのみでPythonループを持ち込まない）。
2. **リクエスト時ベクトル計算**: `RoadGraphEngine._build_search_graph`が、
   `StaticEdgeScoreMatrix`へ動的軸（風）と重みベクトルを適用してbbox全体ぶんの
   コスト配列を1回だけ合成する（`evaluate_dynamic_axis_arrays`→
   `compose_costs_from_axis_matrix`→`compute_hard_filter_excluded`の順）。
   丸め・Neumaier加算は既存の`round1_array`/`_neumaier_accumulate`をそのまま共有
   （新規実装しない）ため、スカラー版とのビット単位一致が自動的に保たれる。
3. **A*からPythonコールバックを排除**: `domain/routing.py: LazyRoadGraph`の
   Node/Edge payloadを整数index（`add_nodes_from(range(n))`・edge payload=行列の
   添字）にし、`shortest_path_node_ids_lazy`のcost_fn/estimate_cost_fnの契約を
   edge_id/node_id文字列から整数indexへ変更した。呼び出し側（`road_graph_engine.py`）は
   `context.cost_list.__getitem__`（bbox全体ぶん合成済みのPython list）を
   そのまま`edge_cost_fn`として渡す。estimate_cost_fn（A*ヒューリスティック）は
   レグごとに`domain/geo.py: haversine_distance_km_array`（新設、numpyベクトル版
   haversine）で全Node分の直線距離を1回だけ計算し、`list.__getitem__`を渡す。
   並行Edge（同一Node間の複数Edge）はコストが判明済みのため`build_lazy_road_graph`が
   「cost最小を採用」する（改善計画T363の元の意味論、`edge_cost_by_id`引数）。
4. **探索と表示の二重計算解消**: `_RoadGraphContext.cost_cache`を撤去し、代わりに
   `full_edge_row`（edge_id→bbox全体の行index）・`difficulty_array`・`axis_arrays`を
   持たせた。`_build_segment_details`はこれらの配列からaxis_difficulties/difficultyを
   直接読み、`compute_edge_axis_scores`/`compute_cost_from_axis_scores`の再計算を
   行わない（重み[night時間帯スコープ含む]も探索コスト算出時点で折り込み済みのため、
   `_build_segment_details`側でのpreference再構築も不要になった）。
5. **8方位の直列実行**: `trace_loop`内の`_trace_segments`を`asyncio.to_thread`で
   包まず直接呼ぶよう変更した。`RouteGenerator.generate_loops`は変更していない
   （`asyncio.gather`のまま）——各`trace_loop`コルーチンが`await`を挟まず同期的に
   探索を完了させるため、gatherの協調的スケジューリングにより結果として直列実行になる
   （`await`のある`get_edges_with_geometry`まで到達して初めて次の方位へ制御が移る）。

**設計判断（分岐点）**:

- **動的軸のディスパッチは軸id単位ではなく材料id単位で登録した**
  （`domain/evaluation.py: DYNAMIC_MATERIAL_EVALUATORS`）。当初のコーディネーター指示は
  「axis_id→evaluatorの辞書（例: `DYNAMIC_AXIS_EVALUATORS`）」だったが、
  `REQUEST_DYNAMIC_MATERIAL_IDS`自体が既に材料id集合として宣言されており
  （`domain/axis_definitions.py`）、`dynamic_axis_topological_order`・
  `evaluate_axis_array`という既存の汎用トポロジカル合成が「動的材料さえ埋まれば
  どんな軸（軸スタジオが`wind_penalty`を直接参照して作ったカスタム軸を含む）でも
  正しく合成する」設計のため、材料id単位の登録だけで軸全体をカバーできる。軸id単位の
  登録だと、そのようなカスタム軸ごとに個別のevaluator追加が必要になり汎用性が後退する
  （＝カスタム軸が動的材料を参照してもこの機構に自動的に乗らない）ため、材料id単位を
  採用した。呼び出し側（`evaluate_dynamic_axis_arrays`）のループには軸名・材料名の
  ハードコードは一切現れず、「風」という具体的な名前が登場するのは
  `DYNAMIC_MATERIAL_EVALUATORS`辞書の1エントリのみ（コーディネーター指示の主旨
  「呼び出し側に軸名の分岐を持たせない」は満たしている）。
- **T534の`compute_edge_static_axis_data`/`compute_edge_axis_scores_from_static_data`/
  `compute_edge_cost_from_static_data`は削除した**（`infrastructure/axis_score_cache.py`
  ごと撤去）。本タスクでEdge単位のキャッシュ機構自体を置き換えるため、これらの関数は
  production上のどこからも呼ばれなくなり、docstringが参照する`axis_score_cache.py`も
  存在しなくなるため、残すとdocs/コードの整合性が崩れる（CLAUDE.md「ドキュメント↔実装の
  乖離」チェック）。対応するテスト（`tests/test_evaluation.py`の
  `test_static_data_path_matches_original_*`群）も削除し、代わりに
  `tests/test_road_graph_engine.py::test_build_segment_details_axis_difficulties_match_scalar_oracle`
  で「新方式の区間表示がスカラーオラクルとビット単位一致する」ことを確認する回帰テストを
  新設した（完了条件の「新方式がcompute_edge_cost経路とビット単位で一致する」を
  区間表示レイヤーでも担保する）。

**回帰テスト**: `tests/test_evaluation_bulk.py`（`compute_edge_costs_bulk`のリファクタ前後
一致、16件）・`tests/test_routing.py`（`LazyRoadGraph`の整数index契約、並行Edgeのcost最小

**ローカル/dev DB速度サニティチェック**（2026-09-02、dev機実DB、東京駅相当の起点・
distance_km=10、`benchmarks/bench_t536_route_generation.py`新設）: 対象グラフ
edges=129,504・nodes=52,698（本番30kmより小規模だが同種の稠密都心データ）。`git stash`で
本タスクの変更を一時的に外し旧実装（T529 lazy評価＋T534辞書キャッシュ）で計測した
`trace_ms`は温キャッシュで6,859ms／7,500ms（8方位×3レグ=24回のA*探索）。`git stash pop`で
本タスクの実装へ戻して同条件を計測すると`trace_ms`は329ms／375ms——**約18〜20倍の
高速化**をローカルで確認した（本番VM試作の8.3〜17.7秒→0.37秒[約22〜48倍]と方向性が
一致。絶対値は開発機と本番VMのスペック差・グラフ規模差のため単純比較不可）。
`prepare_ms`全体（materials取得・グラフ構築・索引構築含む）も温キャッシュで703ms
（旧実装も温キャッシュ時は同程度、materials取得自体はT536のスコープ外のため差は
出ない——旧実装のmaterials_ms=62msに対し新実装は4,250ms/3,875msとやや増えているのは
タイル読込時に静的スコア行列を構築するコスト`build_static_edge_score_matrix`の分。
これは「探索のたびに繰り返す」コストではなく「タイル単位で1回だけ」のコストのため、
2回目以降のリクエストでは`tile_score_matrix_cache`がヒットしてこの増分自体も消える
はずだが、本ベンチマークは`GraphService`インスタンスをリクエストごとに作り直しており
プロセス内キャッシュは3回とも共有されている前提——実際に2回目・3回目でmaterials_msが
横ばいなのはタイルキャッシュがヒットしているためで、想定どおりの挙動）。

**pushしていない**: このAgentの作業はworktree内でのローカルコミットまで。本番backendは

## 本番実測で判明した不具合の修正（2026-09-02、実装後の使い捨てコンテナ検証で発覚）

本番Oracle VMの使い捨てコンテナで東京駅30km・split済み条件を実測したところ、
`combine_static_edge_score_matrices`（`domain/evaluation.py`）が以下の例外でルート生成を
落としていた:

```
ValueError: all the input array dimensions except for the concatenation axis must match
exactly, but along dimension 1, the array at index 0 has size 8 and the array at index 15
has size 0
```

**原因**: bbox内16タイルのうち1枚がEdge0件（道路データが疎らな空タイル、都心部でも
実際に混在しうる）だった。`_evaluate_axes_bulk`のn==0（Edge0件）早期returnが
`axis_arrays={}`（列数0）を返しており、`build_static_edge_score_matrix`が構築する
`axis_scores`の形状が空タイルだけ`(0, 0)`になっていた。他タイル（形状`(N, 8)`、8=公開
軸数）と`combine_static_edge_score_matrices`が`np.concatenate(axis=0)`で連結する際、
axis=1（列数）が一致せず例外になっていた。ローカルの単体テスト・回帰テストは「bbox内の
全タイルにEdgeがある」ケースしか対象にしておらず、このシナリオ（空タイル混在）は
未カバーだった。

**修正**: `_evaluate_axes_bulk`のn==0早期returnで、`axis_arrays`を空dict`{}`ではなく
「公開軸それぞれに対応する長さ0のnumpy配列」の辞書にした（`topological_axis_order
(AXIS_DEFINITIONS)`を`is_published`でフィルタした順——非空グラフの計算フェーズと
同じ順序を使うことで、`combine_static_edge_score_matrices`が`matrices[0].axis_ids`を
全体のaxis_idsとして採用する際に列の並びが全タイルで一致するようにした）。これにより
空タイルの`axis_scores`も`(0, 8)`となり、他タイルと矛盾なく連結できる。

**回帰テスト**（新設）:
- `tests/test_evaluation.py`: `build_static_edge_score_matrix`が空グラフでも非空グラフと
  同じ`axis_ids`を返すこと、`combine_static_edge_score_matrices`が空タイルと非空タイルの
  混在（登場順どちらも）・全タイル空、の3パターンで例外なく正しい形状・値を返すことを
  直接確認する3件。
- `tests/test_graph_service.py`:
  `test_get_search_materials_for_bbox_handles_empty_tile_mixed_with_nonempty_tile`——
  `GraphService.get_search_materials_for_bbox`をエンドツーエンドで、bbox内の1タイルが
  完全に空（Wayが1件も無い）という本番と同じ条件で呼び、例外なく正しい結果を返すことを
  確認する。

`pytest backend/tests -q`（postgis含む全件、新設4件含む）は2026-09-02の最終実行で
1474件全件green。同日の別実行で`test_health.py::test_db_status_returns_table_row_counts_
and_import_run_status_for_empty_test_db`が1件だけ落ちたことがあったが、直後の再実行では
再現しなかった——ridecompass_test DBのmigration適用状態に依存する既知の環境要因

本修正のコードとは無関係と判断した。
