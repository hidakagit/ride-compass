# T918. 路面タイルの単位を、区間が読めるズームでは区間（edge）にする

状態: 着手中（段階1完了）
規模: L

## 背景

[T917](T917.md)の計測で、gzip後の費用と区間単位の情報量が、ズームで逆向きに効くことが
分かった。境界をz14に置く（z14以上=区間、z13以下=way）。

同じ「区間ごとの値」をルート前はway近似・確定後は区間実値で作り分けている状態を畳む。

## 段階

- [x] 1. タイルの単位をズームで切り替える（`feature_key`追加・世代は焼き込みSQLから自動で上がる）
- [ ] 2. 値の配信を`feature_key`鍵へ（低ズームはそのwayの最急へ差し替え）
- [ ] 3. フロントの`promoteId`切り替え
- [ ] 4. way単位で意味を持つ材料の扱いを決める

**段階1だけでは地図の見た目は変わらない**。フロントはまだ`osm_way_id`を`promoteId`に
しており、`feature_key`は焼かれるだけである。段階1を先に本番へ入れて実機で確かめられる。

## 段階1で見つけたこと（実DBを立てて初めて分かった）

この作業のためにローカルへPostgreSQL+PostGISを立てた。**実バグを2つ捕まえた**——
どちらも実DBが無ければpushまで気づけなかった。

**① z14以上のタイルテストが、1件も出ない状態になっていた。** 既存のタイルテストは生のwayしか
作っておらず、z14の単位が`road_edges`へ変わった瞬間に空タイルを見ていた。テスト側で
edgeも作る（`_save_ways_and_edges`）形へ直した。

**② 重複排除の鍵にwayが無く、別々の道が1本へ潰れていた。** 両端ノードの組だけを鍵にすると、
同じノード対を共有する別のway（並走する自転車道等）まで1本になる。鍵を
`(osm_way_id, LEAST(from,to), GREATEST(from,to))`へ直した。`bench_t917_edge_tile.py`も
同じ鍵へ揃えたため、**T917で測った重複排除後のフィーチャー数はわずかに少なく出ている**
（実データでの差は未計測）。

### 効いていることの確認

- 単位の境界を無効化（`EDGE_UNIT_MIN_ZOOM=99`）すると新規2件とも落ちる
- 重複排除の鍵からwayを外すと1件落ちる
- 戻すと12件（既存10＋新規2）とも通る
- `pytest -m postgis`＝279件passed／6件failed。**6件はすべて`test_precompute_way_landcover.py`で
  変更前から同じように落ちる**（この環境のrasterioのバージョンがピンと合わない）
- `pytest -m "not postgis"`＝2,038件passed／5件failed（同じく変更前から）
- `ruff check app scripts benchmarks tests`＝All checks passed
- 生成物: `export_openapi.py`→`npm run generate:api`を正規の手順で実行。差分は
  `region-tile-config.json`のタイル世代のみ（焼き込みSQLから自動で導出される）。
  `openapi.json`の`ValidationError`に出た`input`/`ctx`はこの環境のpydanticのバージョン
  由来のため戻した

## 段階2へ持ち越す制約

**値の配信側が別の代表を選ぶと、鍵が噛み合わず色が付かない。** 重複排除で残るのは
edge_id昇順の先頭（`way-N-segM-bwd`が`-fwd`より先に来る）で、タイルと配信で同じ
`DISTINCT ON`を使う必要がある。

## 未解決（段階2の前に測る）

**edgeを1本も持たないwayは、ズームを上げたときだけ地図から消える。** 座標が判明している
ノードが2点未満のway等（`domain/graph.py: build_road_graph`）。実データでの件数が分かるまで
対処の要否を決められない。0件に近ければ何もしなくてよく、無視できない数なら段階1の時点で
フォールバックを足す。
