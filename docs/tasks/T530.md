# T530: wind/nightを汎用的な動的コンテキストへ統合するリネーム・再設計

状態: 未着手（2026-09-01起票。T529実装中にユーザー指摘、意図的にT529とは分離）

- 背景: T529（`docs/tasks/T529.md`、ルート生成のlazy評価化）の実装中、
  `_SearchGraph`/`_RoadGraphContext`の`wind: WeatherConditions | None`フィールドについて
  ユーザーから指摘があった——この名前・型は「風」に固有だが、実態は「出発時刻に応じて
  リクエストごとに変わる動的要素」の一例に過ぎない。`night_active: bool`
  （市民薄明判定、`docs/decisions/t12-routing-scale.md`原則2「windをこの形に分解できる
  ことが本原則の要点である」参照）も同種の時刻依存の動的要素だが、現状は`wind`とは
  別の独立したフィールドとして扱われている。
- ユーザーの要望: `wind`という具体的な名前ではなく、「動的なもの」を表す汎用的な
  名前・構造へ整理する。
- **T529とは意図的に分離**（両者とも合意済み）: T529はコアなルーティングエンジンの
  差し替えという既に大規模な変更であり、無関係なリネーム・構造変更を混ぜると、
  テスト失敗時に「ロジック変更のせいか、リネームのせいか」の切り分けが難しくなる。
  「night_activeも同じ汎用概念に統合するか」は独立した設計判断であり、腰を据えて
  別途検討する方が良い設計になる。二度手間（T529で書いたwind参照箇所を後で
  もう一度触ること）は機械的な置換で小さいと判断した。
- 対応が必要な箇所（grep推奨、以下はT529実装時点で把握済みの主要箇所）:
  - `backend/app/services/road_graph_engine.py`: `_SearchGraph`/`_RoadGraphContext`の
    `wind`フィールド、`_build_search_graph`でのwind取得・cost_fnクロージャでの捕捉
    （T529で追加）、`_build_segment_details`・`_aggregate_wind_score`での参照
  - `backend/app/domain/evaluation.py`: `compute_wind_penalty(edge, wind)`とその
    呼び出し元シグネチャ
  - `backend/app/services/weather_service.py`: `WeatherConditions`型・`get_conditions`
  - 関連テスト（`test_road_graph_engine.py`等で`wind=...`を渡している箇所）
- 設計判断が必要な点（未着手のため未確定）:
  1. 単純な変数名リネーム（`wind`→`dynamic_conditions`等）に留めるか、`night_active`も
     同じ概念（「時刻依存の動的要素」）へ統合する構造変更まで行うか
  2. 統合する場合、`WeatherConditions`型自体も汎用化する必要があるか、それとも
     「動的要素の集合」を表す新しい上位の型/dataclassでラップするに留めるか
  3. `docs/decisions/t12-routing-scale.md`原則2の記述（wind/nightの分解方式）との
     整合性を保つこと
- 完了条件: 未確定（設計判断1〜3を先に固めてから着手する）。既存の全テストgreenは
  当然の前提。
