# T530: wind/nightを汎用的な動的コンテキストへ統合するリネーム・再設計

状態: フィールド名リネームのみ完了（2026-09-02。構造面はT536で別途解消済みと判明、
詳細は下記「再検証・対応」参照）

- 背景: T529（`docs/tasks/T529.md`、ルート生成のlazy評価化）の実装中、
  `_SearchGraph`/`_RoadGraphContext`の`wind: WeatherConditions | None`フィールドについて
  ユーザーから指摘があった——この名前・型は「風」に固有だが、実態は「出発時刻に応じて
  リクエストごとに変わる動的要素」の一例に過ぎない。`night_active: bool`
  （市民薄明判定、`docs/decisions/t12-routing-scale.md`原則2「windをこの形に分解できる
  ことが本原則の要点である」参照）も同種の時刻依存の動的要素だが、現状は`wind`とは
  別の独立したフィールドとして扱われている。
- ユーザーの要望: `wind`という具体的な名前ではなく、「動的なもの」を表す汎用的な
  名前・構造へ整理する。
- **T529とは意図的に分離**（両者とも合意済み）: T529はコアなルーティングエンジンの
  差し替えという既に大規模な変更であり、無関係なリネーム・構造変更を混ぜると、
  テスト失敗時に「ロジック変更のせいか、リネームのせいか」の切り分けが難しくなる。
  「night_activeも同じ汎用概念に統合するか」は独立した設計判断であり、腰を据えて
  別途検討する方が良い設計になる。二度手間（T529で書いたwind参照箇所を後で
  もう一度触ること）は機械的な置換で小さいと判断した。
- 対応が必要な箇所（grep推奨、以下はT529実装時点で把握済みの主要箇所）:
  - `backend/app/services/road_graph_engine.py`: `_SearchGraph`/`_RoadGraphContext`の
    `wind`フィールド、`_build_search_graph`でのwind取得・cost_fnクロージャでの捕捉
    （T529で追加）、`_build_segment_details`・`_aggregate_wind_score`での参照
  - `backend/app/domain/evaluation.py`: `compute_wind_penalty(edge, wind)`とその
    呼び出し元シグネチャ
  - `backend/app/services/weather_service.py`: `WeatherConditions`型・`get_conditions`
  - 関連テスト（`test_road_graph_engine.py`等で`wind=...`を渡している箇所）
- 設計判断が必要な点（未着手のため未確定）:
  1. 単純な変数名リネーム（`wind`→`dynamic_conditions`等）に留めるか、`night_active`も
     同じ概念（「時刻依存の動的要素」）へ統合する構造変更まで行うか
  2. 統合する場合、`WeatherConditions`型自体も汎用化する必要があるか、それとも
     「動的要素の集合」を表す新しい上位の型/dataclassでラップするに留めるか
  3. `docs/decisions/t12-routing-scale.md`原則2の記述（wind/nightの分解方式）との
     整合性を保つこと
- 完了条件: 未確定（設計判断1〜3を先に固めてから着手する）。既存の全テストgreenは
  当然の前提。

## 再検証・対応（2026-09-02、T536完了後）

T536（`docs/tasks/T536.md`、探索コストのタイル単位静的スコア行列化）が、本タスクが
懸念していた「軸名をハードコードした分岐」を副産物として解消済みと判明した:
`domain/evaluation.py: DYNAMIC_MATERIAL_EVALUATORS`（材料id→評価関数の登録制ディスパッチ、
現状`wind_penalty`のみ登録）により、動的軸を追加する際に呼び出し側のロジックへ分岐を
足さず1エントリ追加するだけで対応できる構造になっている。夜間（night）側も元々
`AxisDefinition.time_scope`という別の汎用的な宣言フィールド（`time_scoped_weights`）で
処理されており、設計判断1（wind/nightを同じ構造へ統合するか）は「性質の異なる2つの
仕組み（Edge単位の動的スコア計算 vs. 重みの時間帯ゲーティング）を無理に1つへ統合する
必要はない」と決着した。設計判断2・3もこれに伴い不要になった。

残っていたのは`_RoadGraphContext.wind`/`_SearchGraph.wind`/`DynamicAxisRequestContext.wind`
（いずれも型`WeatherConditions | None`）というフィールド名だけで、動的材料が
`wind_penalty`の1件しかない現状でこれを一般名へリネームする実利は無い
（このプロジェクトの「3件目が出るまで汎用化を待つ」方針、T479/T480/T511と同じ判断軸）
と整理したが、**ユーザー判断によりフィールド名のリネームのみ実施した**（`weather`へ
統一。型`WeatherConditions`自体は温度・降水等も含む正しい名前のため据え置き）。

**リネーム対象**（`backend/`配下、grep で`wind=`/`.wind`が0件になることを確認済み）:
- `domain/evaluation.py`: `compute_edge_axis_scores`・`compute_edge_cost`・
  `_evaluate_axes_bulk`・`compute_edge_costs_bulk`の`wind`パラメータ、
  `DynamicAxisRequestContext.wind`フィールド
- `services/road_graph_engine.py`: `_RoadGraphContext.wind`・`_SearchGraph.wind`
- `services/evaluation_service.py`: `EvaluationService.evaluate_graph`の`wind`パラメータ
- 上記に対応するテスト（`test_evaluation.py`・`test_evaluation_bulk.py`・
  `test_road_graph_engine.py`）・ベンチマーク（`benchmarks/bench_route_trace.py`）の
  呼び出し箇所

**リネームしなかったもの（意図的、wind固有の実装のため）**: `compute_wind_penalty(edge, wind)`・
`_aggregate_wind_score(edges, wind)`・`_evaluate_wind_penalty_array`——いずれも関数の目的自体が
風向風速の計算に限定されており、汎用コンテキストを運ぶ器ではない。軸id・材料id
（`"wind"`・`"wind_penalty"`）もそのまま。
