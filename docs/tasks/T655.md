# T655. 停止密度を作り直す（種別別カウント・way上カウント・信号のクラスタ化） 規模M〜L

状態: 未着手

## 背景

評価軸`stop_density`が機能していない。本番の軸インスペクタで東京都心のwayを無作為抽出した
ところ、静かな`unclassified`から`secondary`（外堀通り）まで**全件が難易度100.0**だった。
本番タイル6枚（総延長555km）を距離で重み付けした合成値`stop + 0.3×intersection`の分布は
p50=15.4・p90=53.0で、軸の飽和点4.0を**延長の92.3%が超えている**。

この状態では「ストップアンドゴーが少ないルート」を作れない。候補道路がほぼ全部同点のため、
軸の重みをいくら上げてもルートは変わらない。

## 原因は3つあり、すべて集計層にある

### 1. 停止要因の種別を捨てている

集計SQL（`_STOP_POI_COUNTS_SQL`）が`STOP_POI_KINDS`で一括COUNTしており、軸からは合計しか
見えない。実測した内訳（本番POIタイル、3,413件）:

| 種別 | 停止要因内の割合 |
|---|---|
| 横断歩道（`crossing`） | **59.6%** |
| 一時停止（`stop`） | 19.5% |
| 信号（`traffic_signals`） | 18.5% |
| 踏切（`level_crossing`） | 2.4% |

**6割が横断歩道**で、自転車が道なりに走るとき進行方向の横断歩道はほぼ停止要因にならない。

ただし**横断歩道を丸ごと落としてはいけない**。開発DBの48,975件のうち
`crossing=traffic_signals`（信号付き横断歩道）が12,124件（24.8%）あり、独立した信号ノード
（`highway=traffic_signals`）13,095件と合わせると、**実質的な信号の48%が「横断歩道」として
登録されている**。押しボタン式・歩車分離がここに入る。落とすのではなく、信号かどうかで拾う。

### 2. 自分の道の上に無い地点まで数えている

`ST_DWithin(..., 15m)`の近接カウントのため、交差する別の道に付いている信号・並行する歩道の
横断歩道まで拾う。開発DBの同一3,000wayで比較すると:

| 数え方 | 件数 |
|---|---|
| 現行（線から15m以内） | 14,661 |
| そのwayの構成ノードのみ | **5,755** |

**現行は実際の2.5倍を数えており、61%は自分が走る道の上に無い。**
`osm_raw_ways.node_ids`と`osm_raw_pois.osm_node_id`の配列包含判定で正確に数えられる。
`road_edges.osm_way_id`は319,530件中319,530件（100%）埋まっているため、区間単位でも
「そのwayのノード かつ その区間の線上」で絞れる。

### 3. 1つの信号交差点を複数ノードとして数えている

日本のOSMは信号交差点を、流入路ごとの`highway=traffic_signals`と横断歩道位置の
`highway=crossing`+`crossing=traffic_signals`という複数ノードで描く。開発DBで40m以内を
1つの交差点としてまとめると:

| | 件数 |
|---|---|
| 信号ノード総数 | 25,229 |
| まとめた交差点の数 | 8,353 |
| **1交差点あたりのノード数** | **3.02** |

**信号ノードを数えると停止回数の約3倍になる。**

#### 決定: 案Aを採用する（2026-09-08）

| 案 | 内容 | 判断 |
|---|---|---|
| **A** | 集計時に40m程度でまとめてから数える（`ST_ClusterDBSCAN`） | **採用**。正確で、SQLのひと手間は1回きり |
| B | 交差点ノード（次数3以上）へ紐付けて数える | 不採用。交差点の外にある単独信号を落とす |
| C | 何もしない | 不採用。倍率が一律なら順位は保たれるが、大きい交差点ほどノードが多く幹線が過大評価される。「幹線は待ちが長い」という現実と偶然そろうだけで、偶然に依存する |

## 対応方針

### 段階1: 材料へ値を渡す「基本型」を用意する（振る舞いは変えない）

先にここを直さないと、種別を増やすたびに配線が増え続ける。現に[T624](T624.md)で土地被覆を
入れたとき、材料2つのために`MaterialExtractionContext`へ2フィールド足し、**15箇所**を配線
している（`EdgeMaterialBundle`のフィールド・`compute_edge_costs_bulk`の引数・None正規化・
Context組み立て・別関数の引数と受け渡し・bundleからdictへの詰め替え・legacy分岐）。
土地被覆は8クラス中2つしか配線しておらず、残り6つで45箇所になる。

正しい形は同じContextの中に既にある。`way_tags`は名前と値のペアをまとめた1フィールドで、
`surface`も`lit`も`maxspeed`も`bridge`も、`raw_way_tag_extractor`/`tag_equals_extractor`
経由でここから生えており、**材料が何個増えてもフィールドは増えない**。同じ形を数値の束にも
用意する。

```python
EdgeKeyedMetrics = Mapping[str, Mapping[str, float]]   # edge_id -> {key: value}

@dataclass(frozen=True)
class MaterialExtractionContext:
    edge: EdgeLike
    edge_id: str
    distance_km: float
    way_tags: dict[str, str] | None              # 文字列の束（既存）
    metrics: Mapping[str, EdgeKeyedMetrics]      # 数値の束（新設） group -> edge_id -> {key: value}
    elevation_attributes: dict[str, ElevationAttribute]
    surface_attributes: dict[str, str | None]
    designated_edge_ids: set[str]
```

抽出は既存のファクトリ群へ`keyed_value_extractor(group, key)`・
`keyed_density_extractor(group, key)`を足すだけ。

**フィールドを足してよいかの判定基準**（これが歯止め）:
> その材料の兄弟がこれから増えるなら、フィールドではなく`metrics`のgroupにする。

| 現在のフィールド | 材料が増えると | 判定 |
|---|---|---|
| `way_tags` / `elevation_attributes` / `surface_attributes` / `designated_edge_ids` | 増えない | 残す |
| `stop_counts` / `intersection_counts` / `accident_counts` | 増える | `metrics["counts"]`へ |
| `landcover_trees_percent` / `landcover_built_percent` | 増える（残り6クラス） | `metrics["landcover"]`へ |

`MaterialDType`（numeric/boolean/categorical）は**変えない**。JSONBから生える材料はすべて
`numeric`で、新しい値の型は要らない。保存形式（JSONB1列／実カラム8本）が違っても、Context
へ載る時点で同じ型へそろえる。

### 段階2: POIの種別別カウントを`metrics["poi"]`として持つ

`edge_attribute_counts`・`way_attribute_counts`へJSONB1列（`poi_counts`）を足す。
`stop_count`は当面残して並走させ、切り替えを段階的にする。

```
現行:  stop_count = 11
案  :  poi_counts = {"traffic_signals": 5, "crossing_signals": 5, "crossing": 1}
```

**集計キーは5つ**（層2の原則「迷ったら分けない」。分ける基準は「軸スタジオで違う重みを
付けたいか」だけ）:

| キー | 開発DBの件数 | 分ける理由 |
|---|---|---|
| `traffic_signals` | 13,095 | 止まる |
| `crossing_signals` | 12,124 | 止まる。信号の48%がここ |
| `crossing` | 36,851 | 止まらない（重み0にしたい） |
| `stop` | 18,600 | 一瞬止まる |
| `level_crossing` | 1,251 | 待たされる |

分けないもの: `crossing`の`uncontrolled`/`marked`/`unmarked`細分（全部「信号が無い」で
同じ重み）、`give_way`（開発DBで5件、`stop`へ統合）、踏切の遮断機有無（データが0件）。
細かくしすぎると軸スタジオの選択肢が人間の判断能力を超え、情報を増やしたつもりで意思決定を
壊す（[T624](T624.md)の土地被覆が8クラスで止めているのと同じ理由）。

**分類は集計層で行う**（取込時ではなく）。`osm_raw_pois.tags`に生タグが全件残っているため、
`crossing=traffic_signals`の判定は集計SQLの`CASE`一行で書ける。取込時に分類するとルール変更の
たびにPBF再取込（数時間）が必要になるが、集計層ならバッチ再実行（数分）で済む。

材料はキー一覧からループで生成し、N個手書きしない。`POI_COUNT_KINDS`を単一ソースにして、
DBに現れたキーがこの一覧に全部あることをテストで照合する（`STOP_POI_KINDS`について
「Literal値と乖離しないようテストで照合する」という同じ前例が`domain/traffic.py`にある）。

地図タイルはJSONBを持てないため、タイル側だけは種別ごとに列を展開する。ここも同じ一覧から
生成する。

### 段階3: 数え方を直す（実施済み）

`poi_counts`だけを新しい数え方へ切り替えた（`stop_count`は従来のまま残すため、
段階4で軸を組み替えるまで利用者から見た振る舞いは変わらない）。

1. 近接15m → **そのwayの構成ノード**（`osm_node_id = ANY(node_ids)`）。Edge単位は
   さらに「この区間の線上にある」（`ST_DWithin`、許容`POI_ON_EDGE_TOLERANCE_M`=1m）で絞る
2. **区間の始点にあるノードを数えない**（`(始点, 終点]`）。止まるのは区間を走り終える
   ところなので到着側が持つ。有向Edgeのため逆向きでも同じ規則が成り立つ。Way単位は
   方向を持たないため`node_ids`の先頭を除く
3. **同じキーの点を40m（`POI_CLUSTER_EPS_M`）でまとめてから数える**（`ST_ClusterDBSCAN`、
   案A）

#### 集計キーを5→4へ整理した

クラスタ化は同じキーの中でしか効かないため、`traffic_signals`と`crossing_signals`を
分けたままだと1つの信号交差点が両方へ計上されて二重になる。**信号に別々の重みを付ける
理由が無い**（層2の原則「軸スタジオで違う重みを付けたいものだけ分ける」）ことと合わせ、
`signal`へまとめた。

| キー | 中身 |
|---|---|
| `signal` | `highway=traffic_signals` ＋ `crossing=traffic_signals` |
| `crossing` | 信号を伴わない横断歩道 |
| `stop` | 一時停止・徐行 |
| `level_crossing` | 踏切 |

#### 効果の実測（開発DB、3,000 Edge・191.9km）

| | 総数 |
|---|---|
| 旧`stop_count`（15m近接・全kind） | 3,714 |
| 新`poi_counts`の合計 | **968**（26%） |

内訳: `crossing` 459 / `signal` 252 / `stop` 247 / `level_crossing` 10。
信号相当は988→252（**約1/3.9**）で、クラスタ化・way上絞り込み・始点除外の複合効果。

飽和の解消:

| 指標 | 中央値 | p75 | p90 | 4回/km以上が占める延長 |
|---|---|---|---|---|
| 旧`stop_count` | 0.0 | 31.5 | 95.9 | **41.2%** |
| 新「実質の停止」（信号＋一時停止＋踏切） | 0.0 | 0.0 | 13.9 | **17.0%** |
| 新「信号のみ」 | 0.0 | 0.0 | 0.0 | **8.7%** |

所要時間は3,000 Edgeで444ms（旧160ms）。本番319,530 Edgeでも1分弱の見込みで、
バッチとして許容できる。

### 段階4: 軸を組み直す（軸スタジオのGUIのみ）

公開済み軸は不変のため、unpublish→複製→材料と重みを変更→公開。元の軸を消すまでは材料が
衝突する点に注意（`check_material_exclusivity`）。

```
停止密度 = 信号×1.0 + 信号付き横断歩道×1.0 + 踏切×1.5 + 一時停止×0.3 + 横断歩道×0.0
```

折れ点は段階3の完了後に測り直してから引く。段階3の前の分布に合わせて引いても、直した瞬間に
引き直しになる。

### 交差点密度の扱い（段階4で判断する）

`intersection_count_per_km`は`road_nodes.degree >= 3`を30m以内で数えたもので、信号の有無とは
無関係にグラフの形だけから出ている。T字路でも曲がれば止まり、十字路でも直進なら止まらない
ため、「停止」の代理としては弱い。測っているのは「注意・減速の頻度」であり、現在は重み0.3で
薄めることでその曖昧さを表現している。

選択肢は「停止密度から外して別の関心事にする」「次数4以上へ絞る（開発DBで交差点ノード
105,979件中、次数4以上は32,446件＝31%に減る）」の2つ。段階1〜3で停止側が正確になってから
判断する。

## 完了条件

- `MaterialExtractionContext`のフィールドが13→8になり、材料を1つ増やす編集箇所が
  カタログの1行だけになること
- 停止要因が種別別に保持され、軸スタジオで種別ごとの重みを設定できること
- 「横断歩道の重みを0にする」がコード変更なしに実現できること
- 停止密度の難易度が全wayで100に張り付いていないこと（本番の軸インスペクタで確認）
