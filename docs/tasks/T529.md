# T529: ルート生成の探索コスト計算をlazy評価化（rustworkx+A\*）してprepare_msを根本的に短縮

状態: 完了（2026-09-01起票。PoCでrustworkxのlazy A\*が有効と確認したが、本実装
着手前に[T536](T536.md)（タイル単位の静的スコア行列＋リクエスト時ベクトル計算）が
同じ問題[prepare_ms内の`cost_ms`]を別方式で解消し2026-09-02に完了・本番反映済みと
なったため、本方式での実装は不要と判断し2026-09-05に完了扱いへ確定した。詳細は
末尾「完了判定」参照）

- 背景: T522（`docs/tasks/T522.md`）の調査で、本番実測（王子駅・30km周回）の
  `prepare_ms`のうち`cost_ms`（`EvaluationService.evaluate_graph`＝
  `compute_edge_costs_bulk`）が18,105ms（Edge 558,426件）と、`asyncio.to_thread`化
  （T522で対応済み）では解決できない支配的なCPUコストであることが判明した。原因は
  bbox全体（探索が実際に必要とする範囲よりはるかに広い場合が多い）のEdgeコストを
  探索前に一括計算している設計自体にある。T523（`docs/tasks/T523.md`、フロント
  ポーリングのタイムアウト）とも直結しており、backend側のprepare()が遅いことが
  フロントの6分ポーリング上限（`MAX_POLL_DURATION_MS`）への接近・超過を引き起こしている。
- 検討した代替案（詳細はT522.md・`docs/decisions/valhalla-adoption-evaluation.md`参照）:
  - Valhalla等既存エンジンへの全面移行 → 不採用（軸スタジオの自由度を再現できない）
  - 抽出フェーズのベクトル化のみ（bbox全体を評価する設計は変えない対症療法） →
    フォールバック案として保持
  - **rustworkx（Rust実装、Qiskit/IBMメンテ）のlazy A\*/Dijkstra** → 本命として採用
- PoC結果（2026-09-01、王子実測相当の合成グリッドグラフ nodes=139,876 edges=558,008）:
  - A\*（直線距離ヒューリスティック）: edge_cost_fn呼び出し15,543件（**全体の2.79%**）
  - Dijkstra+goal（ヒューリスティック無し）: 86,685件（15.53%）
  - 実際の`compute_edge_cost`（スカラー版、21材料評価）は1回あたり約20〜44
    マイクロ秒（実測）。A\*なら1レグあたり約314〜681ms（現状のbbox全体一括評価
    13,854〜18,105msの20〜40分の1）と推定
  - 判定基準（探索が触るEdgeが全体の20%未満なら本実装へ進む）を大きく上回って達成
- 対応方針（詳細は実装中に更新）:
  1. `domain/routing.py`のscipy依存部分（`SparseRoadGraph`/`build_sparse_graph`/
     `shortest_path_node_ids_sparse`）をrustworkxベースの新実装へ置き換える
  2. `edge_cost_fn`は既存のスカラー版`compute_edge_cost`（`domain/evaluation.py`）を
     ラップする。bulk版`compute_edge_costs_bulk`のベクトル化（フォールバック案）とは
     別経路のため、本タスクでは対象外
  3. `RoadGraphEngine._build_search_graph`の「探索前にevaluate_graphを一括呼び出し」を
     廃止し、`trace_loop`が直接rustworkxのA\*を呼ぶ形へ再設計
  4. 1リクエスト最大24回（8方位×3レグ）の探索間でEdgeコストをキャッシュし、
     重複計算を避ける（PoCでは未検証、実装時に追加する最適化）
  5. 8方位×最大3レグが同じグラフ（PyDiGraph）を共有する現行設計は維持
- 完了条件:
  - 新旧エンジンが同一リクエストで同じ候補ルート（同じEdge列・同じcost）を返すことを
    検証する新規回帰テストがpass
  - 既存の`test_evaluation_bulk.py`・`test_road_graph_engine.py`・`test_route_generator.py`
    等が無修正でpass（scalar版cost関数自体は変更しないため）
  - 本番の未splitエリアへの実リクエストで、既にデプロイ済みのステージ別ログ
    （`road_graph_engine.py`のT522ログ、`materials_ms`/`cost_ms`/`sparse_ms`/`index_ms`）
    で`cost_ms`相当の短縮を数値で確認
  - `pytest backend -q -m "not postgis"`全体green
- 残作業・フォローアップ候補:
  - PoCは合成グリッドグラフのため、実データ（不均一な道路密度・一方通行・幹線道路の
    ショートカット構造）での再検証が必要
  - T523（フロントポーリングタイムアウト）は本タスク完了後に効果を再確認し、
    それでも残る場合は別途対応（`MAX_POLL_DURATION_MS`引き上げ・打ち切り後の結果
    再取得手段等）を検討する
  - フォールバック案（抽出フェーズのベクトル化）は本タスクが不成立と判明した場合のみ着手

## 完了判定（2026-09-05、`/task:next`実行時の状態見直しで発覚）

実装コミットは起票時のスタブと診断ログ追加のみで、rustworkx本実装（対応方針1〜5）には
着手していなかった。一方[T536](T536.md)（2026-09-02着手・完了、`docs/tasks/T536.md`
「関連」節に「T529（lazy A\*、本タスクで一括評価へ戻すが、遅かった原因である逐次抽出は
復活させない）」と明記）が、本タスクが解決対象としていた`prepare_ms`内の`cost_ms`
（Edgeごとの逐次コスト計算）を「タイル単位で静的スコア行列を1回だけ構築し、リクエスト時は
ベクトル演算で合成する」という別方式で解消し、本番実測（東京駅30km）で`trace_ms=809ms`
（旧実装比10〜20倍高速化）を達成・本番反映済みである。

本タスクの完了条件（`cost_ms`相当の短縮を数値で確認）は、本タスク自身の方式ではなく
T536によって既に満たされているため、rustworkxへの置き換えを追加で実装する意味は無い。
状態を「完了」（T536経由での達成）へ更新し、[T523](T523.md)・[T532](T532.md)の着手前提
（「T529完了後」）も「T536完了済み」を根拠に読み替える（`improvement-plan.md`側の
該当行も合わせて更新した）。
