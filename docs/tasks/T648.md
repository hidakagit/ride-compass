# T648. 同種の処理が各所へ写経されるのを機械的に検出する

規模M。2026-09-07完了（段階1・2。段階3は[T650](T650.md)へ分離）。

## 背景

2026-09-07の一連の作業で、「**1つの決まりごとが複数箇所へ写経され、どこかで判断がずれる**」
という同型の問題を1セッションのうちに4回踏んだ。

| タスク | 写経されていたもの | 実害 |
|---|---|---|
| [T632](T632.md) | 応答の`Cache-Control`の判断 | 34エンドポイント中31本で欠落 |
| [T633](T633.md) | `maxzoom`の導出（`zoomUse`と`maxNativeZoom`の突き合わせ） | **7要素中6要素が実データの無いズームを指し、地図から色が消えていた** |
| [T634](T634.md) | JMAプロキシのURL組み立て（オリジン＋パス構造） | 時刻一覧6本で配信オリジンの付け忘れ |
| [T644](T644.md) | Redis cache-asideの骨格 | 5モジュールで重複（実害は未顕在） |

いずれも「気づいた人が直す」形で見つかっており、**機械的に検出する手段が無い**。
`scripts/review_checks.py`のサブコマンドは`docs`・`size`・`metrics`・`trigger`のみで、
重複・写経を見る観点は持っていない。

## 重要な限界: 上記4件のうち3件はjscpdでは捕まらない

| 発見 | jscpdで検出されるか | 理由 |
|---|---|---|
| [T632](T632.md) | ❌ | 各所1〜2行で形も違う |
| [T633](T633.md) | ❌ | **ただの数値リテラル**（`maxzoom: 11`） |
| [T634](T634.md) | ❌ | テンプレート文字列で中身が違う |
| [T644](T644.md) | ⭕（部分的） | 骨格がまとまった行数で一致する |

**「同じ決まりごとが各所で少しずつ違う形に書かれている」型は、コピペ検出では原理的に
見つからない**。今日の4件はすべてこの型だった。コピペ検出は必要だが十分ではない。

## 対応方針

段階を分ける。

### 段階1: コピペ検出をレビュー基盤へ組み込む

`scripts/review_checks.py`へ`duplication`サブコマンドを追加し、`/review:complexity`から
呼べるようにする。jscpdはnpx経由で実行し、未導入環境ではスキップする
（`pre-commit-api-contract`が`backend/.venv`未検出時にスキップするのと同じ扱い）。

閾値を決めて「前回からの増加」を見る形にする——既存25件をゼロにすることが目的ではなく、
**新しい写経が増えたときに気づける**ことが目的。

### 段階2: リテラル重複の検出（本命）

今日の4件の型を捕まえる。「**設定値・規則が、それを使う場所に直接書かれている**」ことを
検出する:

- 同一の数値・文字列リテラルが複数ファイルに散っている（`maxzoom: 11`・TTL秒数・URL断片）
- 同じ関数呼び出しの並びがN箇所に現れる（Redis骨格・`log_external_call`の定型）

誤検出が多くなりやすいため、**違反として落とすのではなく参考件数として出す**
（`review_checks.py docs`のソースコード経緯コメントが、フルスキャンでは参考件数のみを
出しているのと同じ扱い）。

### 段階3: 検出済みの重複を潰す

[T650](T650.md)へ分離した（管理画面CSS 3件・バッチ`run()`骨格）。本タスクの目的は
「検出できる状態にすること」で、既存24件をゼロにすることではない。

## 実装メモ

### 段階1（完了）

`scripts/review_checks.py`へ`duplication`サブコマンドを追加した。

- jscpdは`npx`経由で呼ぶが、**Windowsの`npx`はバッチファイル（`npx.cmd`）で
  `shell=False`のsubprocessからは起動できない**（WinError 193）。npm同梱の
  `npx-cli.js`を`node`で直接実行してOS差を吸収する。node/npmが無ければスキップする。
- 前回値は`.claude/commands/review/history/duplication.json`。`--update`で更新し、
  増加時のみ「判定: 増加」を出す。**件数をゼロにすることは目的ではなく、増えたときに
  気づけることが目的**。
- 出力の末尾に**この検出の限界**（完全一致しか捕まらない）を常に印字する。これを根拠に
  「写経は無い」と結論されるのを防ぐため。
- `.claude/commands/review/complexity.md`へ「写経の監視」節を追加し、周期レビューの
  手順へ組み込んだ。捕まらない3つの型（設定値の直書き・組み立て規則の手書き・定型処理の
  順序）を明記し、人手で見る観点として残した。
- jscpdの一時出力（`.jscpd-report/`）は`.gitignore`へ追加。

**対象範囲**: `backend/app`・`backend/tests`・`backend/scripts`・`frontend/src`・`scripts`。
当初は実装（`backend/app`・`frontend/src`）だけを見ていたが、それでは**同じ骨格がテスト側へ
写されたぶんを見落とす**。実際、全ソースへ広げると151件（テスト側が124件）検出され、上位は
外部APIクライアント・Redisキャッシュのテスト骨格だった——[T644](T644.md)が実装側で指摘した
重複が、テストにも同じ形で存在している。

**同一ファイル内の重複は数えない**。写経とは「同じ理由で変わるものが分かれて書かれている」
ことであり、1ファイル内に似たテストケース（`ComparisonPanel.test.tsx`140行等）やアイコン
定義（`icons.tsx`586行）が並ぶのはそれに当たらない——むしろ1件ずつ独立して読める方がよい。
この除外により151件中103件が落ち、**残る48件はすべてファイルをまたぐ本物の写経**になる。

### 段階2（完了・参考ツールとして残す）

`scripts/literal_scan.py`を追加した。**`review_checks.py`のサブコマンドへは入れていない**
——出力の大半がドメイン語彙（材料id等）とフレームワークの定型で、**ノイズと本物を機械的に
分けられなかった**ため。合否を判定せず、`/review:complexity`で人が材料として眺める用途に
限る位置づけとし、その旨をスクリプトのdocstringとcomplexity.mdの両方へ明記した。

精度を上げ切る案（キーの組み合わせで判定する等）も検討したが、**得られるのは結局
「人が見る材料」で変わらない**ため採らなかった。

## 検証結果

`scripts/review_checks.py duplication`が動作し、クローン24件・838行・1.93%を検出。
`--update`で`history/duplication.json`へ記録し、次回以降は増加時のみ判定行が出る。
既存の`docs`・`size`・`metrics`・`trigger`サブコマンドに影響が無いことも確認した。

段階2の試作で得られた実際の発見:

- `result`/`miss`/`cache`/`error_type`が**13〜16ファイル**に散在。`log_external_call`へ
  渡す`fields`の定型で、[T644](T644.md)が「5モジュール」と見ていたRedis骨格の重複は
  実際にはより広い範囲に及ぶ。手作業では気づけなかった範囲。
- 一方で`maxzoom: 11`のような単独の数値リテラル（[T633](T633.md)の型）は拾えない。
  閾値を下げるとノイズが支配的になるため。
