# T440. ルート結果・ルート設定パネルの色分けを軸スタジオへ完全同期する 規模L

状態: Part A〜C完了、Part D着手中（2026-08-30）

- 背景: T433・T434（+フォローアップ）でも「ルート結果の色分けが固定要素」という指摘への
  対応が最小パッチにとどまり、都度「軸スタジオと同期していない」と再指摘を受ける手戻りが
  続いた。設計をやり直し、ルート結果・ルート設定パネル両方の色分けを軸スタジオのデータ
  （`shape`・`supports_route_coloring`・`display_thresholds_override`・新設
  `dedicated_way_value_layer`）で完全に駆動する形にする。詳細な設計は承認済みPlan
  （このセッションのPlan Mode出力）を参照し、実装完了後にここへ転記する。

## 実装メモ（Part A〜C）

- **Part A**（フロントのみ、[a6d91ba]）: `page.tsx`に`generatedRoutePreference`state
  （`conditions.route_preference`から生成成功時に複製）を追加し、
  `filteredRouteStyleModes`の判定を`generatedRoutePreference ?? routePreference`へ
  差し替えた。バックエンドは既に`conditions.route_preference`を返していたため
  バックエンド変更は不要だった。
- **Part B/C**（backend+frontend一体、routeStyleModes.tsの全面書き直し）:
  - `domain/registry_defaults.py`は軸のフィールド値を持たない（`AXIS_DEFINITIONS`は
    DBが唯一の正本、`export_openapi.py`もビルド時に実DBへ接続する）と判明したため、
    当初計画していたコード変更は行わず、開発DBへ`axis_admin` API経由
    （unpublish→PUT→republish）で`gradient`・`surface_q`の`supports_route_coloring`を
    trueへ、`gradient`の`display_thresholds_override`を`[-2,2,6,10]`へ設定した。
  - `backend/app/api/routers/axis_catalog.py: AxisCatalogEntry`へ`shape`・
    `display_thresholds_override`を追加（ユーザー指摘「axis-catalogは、軸スタジオで
    決められること全部返すほうがいい」を受け、個別フィールドの都度追加ではなく
    まとめて返す方針）。`export_openapi.py`のビルド時静的生成物にも同様に追加。
    OpenAPI/axis-catalog.json再生成済み。
  - `frontend/src/components/Map/axisLayers.ts: CatalogAxis`へ`shape`・
    `display_thresholds_override`を追加。
  - `frontend/src/components/Map/routeStyleModes.ts`を全面書き直し:
    - `STATIC_MODES`配列・`STATIC_MODE_AXIS_IDS`レジストリを削除し、`DIFFICULTY_MODE`
      （対応する軸を持たない唯一の固定モード）だけを残した。
    - `isSignedAbsShape(shape)`: `shape.kind==="breakpoint_linear" &&
      shape.preprocess==="abs" && shape.terms.length===1`という軸データの属性で、
      「符号付き値を直接読むべきか」を判定する（`axis.axis_id==="gradient"`という
      文字列比較を全廃）。真ならshape.terms[0].material（gradientの場合
      "gradient_percent"）をRouteSegmentDetailのプロパティ名として直接読む。
    - `buildRangeSteppedMode`: 境界値配列（軸スタジオの`display_thresholds_override`、
      未設定時は経路ごとの既定値）の**長さがそのまま段階数を決める**汎用関数。
      ラベルは境界値の実際の数字から機械的に生成する（「易しい/普通/難しい」
      「下り/上り」のような固定語彙は使わない）。
    - `interpolateColors(colorLow, colorHigh, count)`: 2色の間をHSL色空間で
      count色に均等補間する（新設）。固定の色配列を持たないため、軸スタジオで
      しきい値の個数を変えても色が自動的に追従する。
    - `road`という名前のモードは無くなり、`surface_q`が他の動的モードと同じ
      `${axis.label}の影響`という汎用ラベル（実際のラベルは「舗装質」なので
      「舗装質の影響」）で現れる。
  - `frontend/src/components/Map/gradientAxisLayer.ts:
    buildGradientColorExpression`・`gradientAxisColorExpression`、
    `gradientGridFill.ts: gradientFillColorExpression`へ`boundaries`パラメータを追加
    （省略時`GRADIENT_BOUNDARIES`、`interpolateColors`で色を生成）——固定4色配列を撤去。
    **既知の未了項目**: 実際にMapView.tsx側の呼び出し箇所（`gradientAxisColorExpression()`
    等、2箇所）へ軸スタジオ由来の値を渡す配線は、Part D（MapView.tsxの
    ensureWindAxisLayer/ensureGradientAxisLayer統合と同じファイルを触るため）まで
    まとめて行う。現時点ではデフォルト値（GRADIENT_BOUNDARIES）にフォールバックする
    ため、表示は壊れない。
  - 検証: `tsc --noEmit`・`eslint`・対象vitest（routeStyleModes 16件・
    gradientAxisLayer 5件・useAxisCatalog・page・RouteSettingsPanel・MapView系、
    計70件超）・backend pytest（axis関連266件）すべて通過。
  - 実データでの確認: `GET /api/axis-catalog`で`gradient`/`wind`/`surface_q`いずれも
    `supports_route_coloring: true`、`gradient`の`display_thresholds_override`が
    `[-2,2,6,10]`になっていることを確認済み。
