# T576: precompute_elevation_attributesの高速化（地理的順序＋タイル単位バッチ化）

## 背景

[T575](T575.md)（`_tile_grid_cache`のLRU上限化）実施後、Fableモデルへ本番規模での
さらなる高速化を検討依頼したところ、以下が判明した:

- `_fetch_all_edge_ids`のEdge取得順が地理的にバラバラ（実質`edge_id`文字列順＝OSM
  way id順）なため、T575のLRU上限（500）と組み合わせると、1チャンクあたり本番規模で
  約70〜100枚のタイルをディスクから再パースする見込みで、**T575時点の見積もり
  （約2.5時間）より遅くなりうる**（現状のまま=3.7〜5.5時間の見込み）。
- Edgeを地理的順序（`ORDER BY geom`）へ変更すると、1チャンクが触る一意タイル数が
  大幅に減り（dev実測で65.2枚→4.7枚）、再パースがほぼ解消する（→2.2〜2.5時間）。
- 点単位のasyncioタスク生成・`log_external_call`のオーバーヘッドが、キャッシュヒット
  経路のコストの9割を占める（dev実測、12,000点で0.41秒のうち0.34秒相当）。タイル単位の
  バッチAPIへ書き換えるとこの経路が約10分の1になる。
- 同一タイルへの重複リクエスト（`Semaphore(5)`分の先頭点が同じタイルを重複取得）が
  発生しうる。

Fableの提案A（地理的順序＋anti-join）・B（同一タイルのsingle-flight）・
C（タイル単位バッチAPI＋同期補間）を組み合わせると、本番規模で約30〜45分まで
短縮できる見込み（すべてdev実測からの外挿、確定値ではない）。

## 対応方針

A・B・Cをまとめて実装する。いずれも「どのEdgeを計算するか」「計算結果の値」を
変えない（冪等性・再実行安全性に影響しない）。
