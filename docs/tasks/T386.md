# T386. T265（ルート生成の非同期ジョブ化）コードレビュー指摘対応 規模M

状態: 未完了

- 発端: T265完了直後（コミット`6b41e41`）に`/code-review`（高effort、8観点finder×1-vote verify）を
  実施した結果、9件がCONFIRMEDと判定された（2026-08-28）。うち1件（同時実行数ガードの
  レース条件）は、T265が明示的に維持するとコメントしていた「投稿時点で即429」という
  既定挙動が実質的に壊れているという、設計意図と実装が食い違う重大な指摘のため、
  他の指摘とまとめて本タスクへ起票する。

## 指摘一覧（優先度順）

1. **同時実行数ガードのTOCTOUレース**（`backend/app/api/routers/routes.py:253`／`299`）:
   `_generate_semaphore.locked()`の同期チェックと、実際の`async with _generate_semaphore:`
   による取得が別々の実行タイミング（POSTハンドラ内 vs `BackgroundTasks`経由でレスポンス
   送出後に実行される`_run_generate_job`内）に分離された。旧実装は「locked()確認→即座に
   同一コルーチン内でacquire」でawaitを挟まなかったため隙間はほぼ無かったが、新実装は
   HTTPレスポンス送出という実I/Oを挟むため隙間が大きく開く。複数リクエストがほぼ同時に
   届くと、`generate_max_concurrent`（既定2）を超える数のジョブが202で受理され、
   バックグラウンドで静かにセマフォ待ちの列ができる——「投稿時点で即429」という
   コメント上の既定挙動と矛盾する。`test_generate_routes_rejects_when_concurrency_limit_reached`
   はセマフォを直接acquireしてから単発POSTするだけで、このレース自体は検出できない
   （3エージェント独立確認・CONFIRMED）。

2. **ポーリング単発失敗が生成全体を即座に失敗させる**
   （`frontend/src/services/routeApi.ts:141`）: `pollGenerationJob`はリトライ機構が無い
   `fetchJson`をそのまま使う。1.5秒間隔・最大240回のポーリングのうち1回でも一時的な
   ネットワーク瞬断・5xxで失敗すると、`generateRoutes`全体が即座に例外を投げる。
   バックエンド側`_run_generate_job`は`_generate_semaphore`を握ったまま処理を継続し
   （ジョブをキャンセルする手段が無い）、ユーザーが再試行すると同時実行枠
   （既定2）の半分を孤立ジョブが無駄に占有し続ける。旧実装（単一の長時間fetch）と
   比べ独立試行回数が大幅に増えている（CONFIRMED）。

3. **バックグラウンドジョブの例外メッセージがクライアントへそのまま公開される**
   （`backend/app/api/routers/routes.py:343`）: 旧`generate_routes`は生成処理中の例外を
   一切catchしておらず、FastAPIのデフォルト500（詳細非公開）に委ねていた。T265で
   `except Exception as exc: ... job_registry.set_failed(job_id, str(exc))`が追加され、
   `str(exc)`がそのまま`GET .../generate/{job_id}`のレスポンス（HTTP 200、`error`
   フィールド）としてクライアントへ返るようになった。`ors_client.py`の`RoutingError`は
   外部API（openrouteservice）の生レスポンス本文を例外メッセージに含めており、内部詳細の
   公開範囲が意図せず拡大している（CONFIRMED）。

4. **open_route_generation_setupが使わない側のエンジン用DBセッションも無条件に開く**
   （`backend/app/api/dependencies.py:246`）: `_assemble_route_generation_setup`自体は
   `settings.routing_engine`で分岐し使わないサービスがあるが、`open_route_generation_setup`
   は`AsyncExitStack`で3つのDB接続系依存を無条件に開く。旧実装がこれを無条件にしていた
   理由（FastAPI DIの制約）はこの関数がDependsに縛られない普通の関数になった時点で
   もう当てはまらない。`get_surface_match_repository`は路面/事故タイル配信と共有する
   プール（`config.py`が過去の実障害として記録している、逼迫気味の共有プール）から
   接続を取得するため、road_graphエンジン構成でも生成ジョブの全期間（コールド時最大
   175秒超）未使用の接続を1つ保持し続けることになる（CONFIRMED）。

5. **job_registryの単一プロセス前提が、複数ワーカー化時に静かに壊れるリスクとして
   未起票**（`backend/app/infrastructure/job_registry.py`）: 同様の前提を置く
   `axis_registry_service.py`は`docs/tasks/T288.md`として「複数ワーカー化のタスクを
   起こす際は本タスクを完了条件に含めること」という正式なトリガー付きタスクを持つが、
   `job_registry.py`にはコード内コメントのみで対応するタスク番号での起票が無い。現状は
   両者とも単一プロセスデプロイのため実害は無いが、将来複数ワーカー化する際に見落とされる
   リスクがある（CONFIRMED）。

6. **ウォームパスでも必ず最低1.5秒待たされる**（`frontend/src/services/routeApi.ts:141`）:
   `await sleep(POLL_INTERVAL_MS)`がループの最初、初回の`pollGenerationJob`より前に
   配置されているため、サーバー側の生成が数百ms〜1秒程度で終わる典型的なウォームパス
   （curl実機確認でsubmitは4.6ms）でも、クライアントは必ず1.5秒待ってから初回の状態
   確認を送る。旧実装（同期POST）は生成完了と同時に結果が返っていた。docs/tasks/T265.md
   にこのトレードオフの記載は無く、意図的な判断ではなく見落としと判断される
   （CONFIRMED）。

7. **404エラーメッセージがTTL経過のみを示唆し、サーバー再起動によるジョブ消失と
   区別できない**（`backend/app/api/routers/routes.py:280`）: `job_registry`は
   プロセス内メモリのみのため、バックエンド再起動・デプロイでも全ジョブが消失するが、
   404メッセージは「完了から時間が経過して破棄された可能性があります」というTTL経過を
   前提にした文言のまま返る。生成中（running）に再起動が挟まった場合も同じメッセージに
   なり、原因の切り分けを誤らせる。生成所要時間（最大316秒実測）とデプロイ頻度を
   踏まえると実害の発生頻度は低い（CONFIRMED、優先度低）。

8. **onProgressへ渡すelapsedMsが常に古い値**（`frontend/src/services/routeApi.ts:136`）:
   `elapsedMs`はポーリングループ先頭（`sleep`・GETの前）で計算され、`onProgress`へは
   その古い値のまま渡る。「生成中...(N秒経過)」表示が実際の経過時間よりPOLL_INTERVAL_MS
   （1.5秒）+GET応答時間ぶん常に少なく表示され続ける。累積ドリフトはせず、実害は
   コスメティックな軽微レベル（CONFIRMED、優先度低）。

9. **job_registry.pyのTTLスイープ参照コメントが不正確**
   （`backend/app/infrastructure/job_registry.py:23`）: 「`debug_control.py`の
   リングバッファと同じ『呼ばれたついでに掃除』方式」という参照コメントがあるが、
   `debug_control.py`のリングバッファは`deque(maxlen=...)`による件数ベースの暗黙FIFO
   破棄であり、TTL・時刻判定のロジックを持たない。実際に構造が近いのは
   `rate_limiter.py`の`dict + time.monotonic() + 呼び出し時_sweep`パターン。実害は
   無いがコメント修正漏れ（CONFIRMED、優先度最低）。
