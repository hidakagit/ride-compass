# T391. generate_loopsの8方位並列trace_loopが共有するGraphServiceのAsyncSessionを保護 規模S（完了）

状態: 完了

- 背景: T390（road_graph評価ホットパスのRedis cache-aside化）の調査中に副産物として
  ユーザーが発見した疑いを調査した（2026-08-29）。`RouteGenerator.generate_loops`
  （[route_generator.py:131-137](../backend/app/services/route_generator.py)）は8方位分の
  `RoadGraphEngine.trace_loop`を`asyncio.gather`で並列実行する。`trace_loop`
  （[road_graph_engine.py:415](../backend/app/services/road_graph_engine.py)）は経路確定後に
  `self._graph_service.get_edges_with_geometry(edge_ids)`を呼びDBへ問い合わせるが、
  `graph_service`は1リクエストにつき1インスタンス（`api/dependencies.py: get_graph_service`が
  1つのAsyncSessionで生成）であり、8方位すべてが同一セッションを共有する。
  同種のパターン（`RoadGraphEngine.evaluate_loops`が候補ごとに`asyncio.gather`で
  `ElevationAttributeService`を並列呼び出し）は、実PostGIS E2Eで
  `IllegalStateChangeError`のクラッシュが過去に確認され（
  [docs/decisions/road-graph-migration.md:276](../docs/decisions/road-graph-migration.md)）、
  `asyncio.Lock`による直列化で修正済みだった。`GraphService`には同種のロックが
  一切無く（`grep -n "Lock" app/services/graph_service.py`でヒット0件）、
  かつ`FakeGraphService`（`tests/test_road_graph_engine.py`）はインメモリ辞書のFakeで
  実AsyncSessionの同時アクセス制約を再現しないため、既存テストはこの経路を
  検証していなかった。
- 調査結果（実測で確認）:
  1. ローカルPostGIS（`postgresql+asyncpg://ridecompass:ridecompass@localhost:5432/ridecompass`）に
     対し、同一`AsyncSession`へ`asyncio.gather`で8並列に`session.execute()`を投げる
     最小再現スクリプトで検証した。**セッションがまだ一度もクエリを実行していない
     「コールド」な状態だと、最初の1件だけ成功し残り7件が
     `sqlalchemy.exc.InvalidRequestError: This session is provisioning a new connection;
     concurrent operations are not permitted`（＝IllegalStateChangeError）で確実にクラッシュする**
     ことを直接確認した（`ElevationAttributeService`が過去にクラッシュしたのはこの経路——
     専用の別セッションで、`evaluate_loops`のgatherが同セッションへの初回アクセスだったため）。
  2. 一方、**gather開始前に同一セッションで最低1回クエリが完了済み（「ウォーム」な状態）だと、
     以降の同時`execute()`はクラッシュせず、SQLAlchemyのAsyncSession内部が透過的に
     直列化（後続コールは先行コールの完了を待ってから実行）することも直接確認した**
     （8並列で`pg_sleep(0.3)`を投げても、313ms間隔でmonotonicに完了、クラッシュ無し）。
  3. `GraphService`のセッションは、`RoadGraphEngine.prepare`
     （`generate_loops`内でgather開始前に`await`済み、[route_generator.py:121](../backend/app/services/route_generator.py)）が
     `get_search_materials_for_bbox`経由で必ず先に複数クエリを実行するため、
     trace_loopのgatherが始まる時点で常にウォーム状態。**そのため現状のコードパスでは
     このクラッシュは再現しない**——上記2.の「ウォーム」ケースに該当する。
  4. 本番ログでの実害確認は不可だった。本番backend（Oracle Cloud VM、
     `docker logs`）は調査当日（2026-08-29）午前にT387関連の作業で再デプロイされており
     （`RestartCount=0`、Created 09:26 UTC、直前コンテナは既に削除済み）、
     ログ保持がdocker json-file（max-size 10m×5）のみのため過去のログ自体が残っていない。
     `IllegalStateChangeError`/`another operation is in progress`の検索は再デプロイ後の
     ログでは0件だったが、その間`generate engine=`のログ自体が1件も無く
     （＝ルート生成リクエストが来ていない）、実害の有無を判定できる材料ではない。
- 判断: 現状のコードパスでは実害（クラッシュ）は発生しない（3.の理由）。ただし
  「gather開始前に必ず1回以上クエリが完了している」という暗黙の前提は、コード上どこにも
  文書化・保証されておらず、`prepare`側の実装が変わる（例: 材料取得の一部をキャッシュ
  経由に変えてDB往復が0回になる等）と、`ElevationAttributeService`と全く同じ
  クラッシュが再発しうる潜在的なフラジリティと判断した。実害が無い＝対応不要、とはせず、
  ElevationAttributeServiceと同じ確立済みパターン（低コスト・実績あり）で予防的に
  修正することとした。
- 対応内容: `GraphService.__init__`に`asyncio.Lock`を追加し、`get_edges_with_geometry`
  （8方位gatherから同時に呼ばれる唯一のメソッド。他メソッドは常にgather開始前の
  prepare段階で逐次呼ばれるため対象外）だけをロックで直列化した
  （[graph_service.py](../backend/app/services/graph_service.py)）。
  回帰テスト: [tests/test_graph_service.py](../backend/tests/test_graph_service.py)に
  `ReentrancyDetectingRepository`（`test_elevation_attribute_service.py`の同名フェイクと
  同じ考え方、get_edges_with_geometry呼び出し中に別コルーチンが割り込んだら検出する）と
  `test_get_edges_with_geometry_serializes_concurrent_calls`を追加。ロックを外すと
  このテストが確実に失敗する（`concurrent_access_detected=True`）ことを実装時に確認済み。
- 優先度: P2（実害未確認・現状クラッシュしないが、暗黙の前提に依存した潜在的フラジリティ。
  安価な予防的修正のため今回のうちに解消）。
- 未実施（次のトリガーで対応）: 本番Oracle VMへの反映（デプロイ）はユーザー承認後に
  別途実施する。現状クラッシュしない潜在的フラジリティの予防修正であり、緊急デプロイの
  必要性は無いと判断した。
