# T619. レンズで風を選ぶと全灰色になるバグを修正 規模S

状態: 完了（2026-09-06）

## 背景

ユーザー報告「レンズで風を選ぶと全灰色」。

当初はOpen-Meteo取得失敗（`WeatherClient.get_forecast_many`の障害）を疑ったが、
ユーザーから提供されたログ（`風の評価軸配信の時刻が風グリッド範囲外`が連発）と
`/api/debug/stats`の`weather:open-meteo`カテゴリ（1回トライ・失敗0）を突き合わせた結果、
Open-Meteo自体は成功しており原因は別にあると判明した。

## 原因

`backend/app/services/wind_way_service.py: _nearest_time_index`が、tz-awareな`target`の
tzinfoを`.replace(tzinfo=None)`で単純に剥がすだけで、JSTへ変換していなかった。

- フロント（`regionApi.ts: fetchDynamicWayValues`）は`Date.toISOString()`でtz-aware
  （UTC）な時刻を送る。
- Open-Meteoの風グリッドhourly配列は`timezone=Asia/Tokyo`指定のためJST基準の壁時計時刻
  （tzなし文字列）。
- `_nearest_time_index`はtzinfoを剥がすだけでJST変換をしないため、UTC時刻の数値がそのまま
  JST時刻として比較され、実質9時間ズレる。
- JST深夜〜早朝（0時台〜8時台）にアクセスすると、ズレた時刻が風グリッド取得日の前日扱いに
  なり配列の範囲外（`target_naive < min(parsed)`）と判定され`None`が返る（`get_way_values`
  が空dictへ倒すため地図が全灰色になる）。

同じ関数シグネチャの形（tz-aware/naiveどちらも受けて`.replace(tzinfo=None)`で比較）を
リポジトリ全体でgrepしたところ、`api/routers/routes.py: _resolve_start_time`・
`road_graph_engine.py`（`now.astimezone(JST).replace(tzinfo=None)`）・
`domain/twilight.py`は既に正しくJST変換してから剥がしており、`wind_way_service.py`だけが
変換を欠いていた。`wbgt_service.py`にも同型の未変換箇所があるが、`now`引数はrouterから
常に省略（`None`→`datetime.now(JST)`）で呼ばれておりテスト注入専用のため、現状は
到達不能（生きたバグではない）。

## 対応内容

`_nearest_time_index`に、tz-awareな`target`をJSTへ変換してから`tzinfo`を剥がす処理を追加。

```python
if target.tzinfo is not None:
    target = target.astimezone(JST)
target_naive = target.replace(tzinfo=None)
```

## テスト

`test_wind_way_service.py`へ`test_utc_aware_at_is_converted_to_jst_before_range_check`を
追加。JST今日00:30をフロントと同じ経路（tz-aware UTC）で表現した`at`を渡し、正しく風データが
返ることを検証する（修正前のコードでは本テストが「時刻が風グリッド範囲外」で失敗することを
確認済み）。
