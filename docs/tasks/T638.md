# T638. 開発機でPostgreSQL同梱のPROJとrasterioのPROJが衝突しテストが失敗する

規模S。

状態: 完了（2026-09-08）

## 背景

開発機で`pytest -q -m "not postgis"`を実行すると、`tests/test_precompute_way_landcover.py`の
2件（`test_count_pixels_in_ring_detects_mixed_classes`・
`test_count_pixels_in_ring_returns_none_when_outside_raster`）が失敗する。

```
rasterio.errors.CRSError: The EPSG code is unknown.
PROJ: proj_create_from_database: C:\Program Files\PostgreSQL\18\share\contrib\postgis-3.6\proj\proj.db
contains DATABASE.LAYOUT.VERSION.MINOR = 2 whereas a number >= 6 is expected.
It comes from another PROJ installation.
```

rasterioが自前のPROJではなく、PATH上で先に見つかるPostgreSQL 18同梱（PostGIS 3.6）の
`proj.db`を掴んでいる。そちらはレイアウト版が古くrasterioの要求（>= 6）を満たさないため、
EPSG解決が失敗する。

**影響範囲は開発機のローカル実行のみ**。CIはLinuxコンテナでPostgreSQLとPythonの依存が
同居しないため再現せず、本番も影響を受けない（`precompute_way_landcover.py`は
[T624](T624.md)の開放度軸バッチで、`a322f55`でrasterio/pyprojのimportを遅延化済み）。

## 対応方針（案）

- `PROJ_DATA`（PROJ 9系。旧称`PROJ_LIB`）でrasterio同梱の`proj.db`を明示し、PostgreSQL側を
  見に行かせない。`conftest.py`でテスト実行時のみ設定するか、開発手順書へ記載するかを選ぶ。
- テスト側で設定する場合、実行環境ごとにrasterioの`proj.db`パスが違う点をどう吸収するかを
  決める必要がある（`rasterio.env.default_options()`や`pyproj.datadir.get_data_dir()`から
  引く等）。

## 保留した場合の影響

開発機でバックエンド全体テストを流すたびに2件が赤いまま残る。**本物の失敗とノイズの
区別がつかなくなり、他の回帰を見落とす**のが実害。テスト自体の内容には問題がないため、
skipマーカーで隠すのではなく環境側を直すべき。

## 実施内容（2026-09-08）

対応方針の1つ目（`PROJ_DATA`でrasterio同梱の`proj.db`を明示する）を採った。実行機ごとに
パスが違う点は`importlib.util.find_spec("rasterio")`から引くことで吸収する。

`app/infrastructure/proj_data.py: pin_bundled_proj_data()`を追加し、次の2経路が
rasterioをimport・使用する前に呼ぶ。

| 呼び出し元 | 効く範囲 |
|---|---|
| `tests/conftest.py`（他のimportより前） | `pytest`実行全体 |
| `precompute_way_landcover.py`の遅延import2箇所 | バッチの手動実行 |

**テストだけを直すと不十分だった**。この開発機は`PROJ_LIB`が
`C:\Program Files\PostgreSQL\18\share\contrib\postgis-3.6\proj`を指したままで、
バッチを直接起動すると`_RasterSource`（`rasterio.open`→`dataset.crs`）が同じ`CRSError`で
落ちる。実際に再現させた上で両方を通した。

同梱データが無いビルド（システムのGDAL/PROJへリンクした構成）では何もしないため、
本番の構成には影響しない。

## 検証

- `tests/test_proj_data.py`を追加（固定先に`proj.db`が実在すること・別インストールを
  指す設定があっても上書きすること・固定後にEPSGが解決できること）。
- バッチ経路は、`PROJ_LIB`がPostgreSQLを指したままのプロセスで`_RasterSource`を作り、
  CRS読み取りと座標変換が通ることを確認した。
- backend全体 1619 passed（従来失敗していた`test_precompute_way_landcover.py`の2件を含む）。
