# ルート評価モデル研究インターフェース 全体レビュー（2026-08-15・第3回）

静的道路属性の拡充フェーズを前に、本アプリを「最終ユーザー向けUI」ではなく
**「評価軸・重み・条件・組み合わせを人間が効率よく探索・研究するための実験環境」**として
評価したレビューの記録。**本書はレビュー・分析・改善計画のみでコード変更は含まない。**

前提資料: [design-review-2026-08-15.md](design-review-2026-08-15.md)（第1回・全体設計）/
[complexity-review-2026-08-15.md](complexity-review-2026-08-15.md)（第2回・複雑度平衡）/
[static-road-attributes-plan.md](static-road-attributes-plan.md)（静的属性計画・承認待ち）/
[improvement-plan.md](improvement-plan.md)（T1〜T22）。
本レビューは第1・2回の指摘と重複しないよう「研究ループの回転効率」の観点に限定し、

## 1. Executive Summary

**判定: 一部改善が必要。**

裏側のアーキテクチャは研究環境としてすでに優秀である。
「道路属性 → セグメント評価 → ルート評価」の3層は実装上も明確に分離されており
（`*_attributes` → `domain/difficulty.py`/`compute_edge_cost` → `RouteScorer`）、
正準語彙の一元化・生成物照合テスト・レイヤーカタログ・軸機構など、
属性を増やしても壊れにくい仕組みが第1・2回レビューで整備済みである。

一方、**研究ループの「入口」と「出口」がUI・APIに存在しない**。

- **入口（条件設定）**: 評価の重みはサーバー側YAML 2ファイル
  （`scoring.yaml`・`route_preference.yaml`）にのみ存在し、
  `/api/routes/generate` のリクエスト（[routes.py:46](../backend/app/api/routers/routes.py#L46)）は
  座標・距離・許容差しか受け付けない。現在の実験手段は
  「エディタでYAMLを編集 → ブラウザで再生成」であり、UIから実験条件を変える手段が無い。
- **出口（比較・内訳）**: 生成結果は `page.tsx` の `setRoutes` で**前回結果を上書き**するため、
  Experiment A と Experiment B のルートを並べて比較する手段が無い。また `total_score` は
  合成後の1値のみ返され、成分スコア（距離・標高・風・路面の正規化値×重み）は
  `RouteScorer.score` 内で計算後に捨てられている。

さらに研究計画上の重要な制約が2つある（§2・§8で詳述）:

1. **既定エンジン（openrouteservice）では、重みはルート形状を一切変えない。**
   8方位の候補形状はORSが決め、重みは同じ8本の並べ替えにしか効かない。
   「評価軸を変えるとルートがどう変わるか」という研究の本丸は road_graph エンジンでしか成立しない。
2. **`total_score` は候補集合内のmin-max相対評価**であり、リクエスト（＝実験）間で比較できない。
   実験間比較の物差しとして使えるのは生値（獲得標高・wind_score・舗装率）と
   絶対基準の `segments[].difficulty` だけである。

要するに現状は「**研究の土台（データモデル・評価パイプライン）は A ランク、
研究の操作環境（条件変更・比較・内訳）は未着工**」という状態である。
静的属性P0（表示レイヤー先行）とは独立に、小さいAPI変更2つ
（重みのリクエスト上書き＋スコア内訳の返却）から着手することを推奨する（§10・§15）。

## 2. Research Loop Evaluation

理想ループ「仮説→条件設定→生成→結果確認→比較→仮説修正→再実験」を段階別に評価する。

### 2-1. 仮説 → 条件設定

- **現状**: 重みは `backend/app/scoring.yaml`（ルート単位・4指標）と
  `backend/app/route_preference.yaml`（Edge単位・3指標）をエディタで直接編集する。
  DI（`get_route_scorer`/`get_route_preference`、[dependencies.py:69-74](../backend/app/api/dependencies.py#L69-L74)）が
  **リクエスト毎にYAMLを再読込するため、サーバー再起動は不要**。編集→保存→再生成で反映される。
- **問題**: ①UIから変更できない（ブラウザ⇄エディタの往復が毎実験発生）
  ②どの実験がどの重みだったかの記録が残らない（YAMLは上書きなので履歴はgit頼み）
  ③ハード制約（`DISALLOWED_HIGHWAY_TYPES`）はコード定数で、変更にはコード編集が必要。
- **改善案**: `RouteGenerateRequest` にオプショナルな重み上書き
  （省略時はYAML既定値）を追加する（§10-1）。
- **優先度: 最高**（ループ1周あたりの操作量を最も減らす）。

### 2-2. 条件設定 → ルート生成

- **現状**: ボタン1クリック。所要時間はORSエンジンで数秒〜10秒程度、
  road_graphエンジンはコールド40〜70秒・PostGIS WARMで8〜11秒。
  レート制限（10/分）・同時実行2は研究用途でも現実的な範囲。
- **問題**: **重み変更の実験はroad_graphエンジンでのみ形状に反映される**のに、
  既定はORS。しかもroad_graphのWARM 8〜11秒は「1時間に何十回も回す」研究には重い
  （主成分は`surface_attributes`ロード。T9で削減予定）。
- **改善案**: 研究時は `.env` で road_graph を明示する運用の明文化（§10-9）。
  T9（surface導出化）・T12（グラフキャッシュ設計）が研究回転数に直結することを
  トリガー判断に織り込む。
- **優先度: 中**（運用の明確化は即可能。性能改善は既存タスクのトリガー通り）。

### 2-3. ルート生成 → 結果確認

- **現状**: `RouteList` が候補ごとに total_score・距離・獲得標高・風・舗装率を1行表示。
  地図は全候補＋選択候補の色分け（風・勾配の2モード）。ポップアップで区間値確認可。
- **問題**: ①total_scoreの内訳が見えない（§5）
  ②ルート色分けモードが風・勾配のみで、**segmentsに既に入っている
  `road_difficulty`・総合 `difficulty` の色分けモードが無い**
  （データは返却済みなのに表示手段が無い。旧モード切替廃止時に風だけ残した経緯）
  ③どのエンジン・どの重みで生成されたかが画面に出ない（engineはデバッグログのみ）。
- **改善案**: `routeStyleModes.ts` へ「路面」「総合難易度」モードを追加（データ追加不要、§10-5）。
  レスポンスに使用条件のエコーを追加（§10-6）。
- **優先度: 高**（変更規模が小さく効果が大きい）。

### 2-4. 結果確認 → 比較

- **現状**: **1回の生成内**の8候補の比較は一覧＋地図で可能（これは維持すべき強み）。
  **実験間**（重み違い・エンジン違い）の比較は不可能。`setRoutes` が上書きし、
  前の実験のルートは消える。
- **問題**: 研究の中心操作「Experiment A/B の地図上での形状比較」が
  スクリーンショットを撮る以外に手段が無い。
- **改善案**: フロントに実験スロット（直近N回の生成結果を条件付きで保持し、
  地図に色違いで重ね描き＋メトリクス表で並置）を追加（§10-3）。
- **優先度: 高**（研究ループの出口。§10-1・2の後に実施）。

### 2-5. 比較 → 仮説修正 → 再実験

- **現状**: 仮説修正の材料（なぜこのルートが選ばれたか）が内訳非表示のため弱い。
  再実験はYAML再編集に戻る。
- **問題**: 「traffic_stressを50→20にしたら何が変わったか」を数値で確認できず、
  地図の見た目の記憶に頼ることになる。
- **改善案**: 内訳返却（§10-2）＋スロット比較（§10-3）で閉じる。
- **優先度: 高**。

**ループ全体の評価**: 現状の1周は「エディタでYAML編集 → 保存 → ブラウザへ移動 →
生成クリック → （前回結果は消えるので）記憶とスクリーンショットで比較」。
開発者1人なら回せなくはないが、比較の信頼性が人間の記憶に依存しており、
属性が10個に増えた時点で破綻する。§10の上位3項で「UIだけで1周・結果は並置」へ変わる。

## 3. Evaluation Axis Flexibility

「道路属性 → セグメント評価 → ルート評価」の3層構造は実装から明確に読み取れる。

```
[属性]   osm_raw_ways(highway/surface/oneway) → ElevationAttribute / SurfaceAttribute
[セグメント評価] domain/difficulty.py: gradient/wind/road_difficulty（0-100絶対基準）
          → compute_edge_cost（route_preference.yaml重み・距離乗算ペナルティ）
[ルート評価]  RouteScorer（scoring.yaml重み・候補集合内min-max相対）→ total_score
```

| 操作 | 容易さ | 実態 |
|---|---|---|
| 道路属性の追加 | ○（計画済） | static-road-attributes-plan §6 の手順どおり。ゲートT16-T20完了済 |
| 評価軸の追加 | △ | 変換関数＋重みフィールド＋YAML＋両エンジン＋モデル＋表示。§8 Case C参照 |
| 評価軸のON/OFF | △ | 専用機構は無いが**重み0で実質OFF**（`composite_difficulty`/`RouteScorer`とも重み0の項は寄与0）。ただしYAML編集が必要 |
| 重み変更 | ○（開発者のみ） | YAML1行。再起動不要。UIからは不可 |
| 重みの正規化 | ○ | 両層とも有効な項の重み和で除算するため、合計1.0でなくても壊れない（`scoring.yaml`のコメント「合計1.0で管理」は運用上の規約に過ぎない） |
| 条件（距離等）変更 | ○ | UIから可能 |
| ハード制約の追加 | △ | `is_edge_allowed` 1箇所だが、コード編集＋**road_graphエンジン限定**（§6） |
| 複数軸の組み合わせ | △ | 加重平均合成は自由だが、非線形な組み合わせ（例: 「未舗装×下り」だけ重罰）は `compute_edge_cost` の書き換えになる（設計上は想定内: docstringに「この関数だけ差し替えれば済む」と明記） |
| 評価モデル自体の切替 | △ | `load_route_preference(path)` は複数プロファイルYAMLを想定した設計だが、切替の配線（設定・API）は未実装 |

**核心の指摘**: 軸の柔軟性を制約しているのは評価ロジックではなく、
**「重みという実験変数がリクエストに乗らない」**ことと
**「軸のメタデータ（名前・説明・重みキー・表示文言）が1箇所に無い」**ことである。
現在、1つの軸は `RoutePreference` フィールド・YAMLキー・`RouteScorer` の component 辞書・
`RouteList` のハードコード文言（「距離の合わせ込み・獲得標高・向かい風・舗装率」）・
`routeStyleModes` に分散しており、軸追加のたびに全部へ手作業で追従することになる。
フロントのレイヤー機構（`mapLayers.ts`/`roadFilterAxes.ts`）が達成した
「カタログ1箇所＋汎用ループ」の型を、評価軸にも適用する余地がある（§10-8。ただし
静的属性P1で軸が実際に増えるタイミングまで待つのが適切）。

## 4. Route Comparison

- **同一実験内（8候補）**: ○。一覧のメトリクス比較＋地図の全候補表示＋選択ハイライト＋
  区間ポップアップ。研究用途として既に機能している。
- **実験間（重み・エンジン・距離違い）**: ×。結果の保持機構が無い。
  地図上の形状比較（最重要要件）は不可能。
- **メトリクスの比較可能性**: 距離・獲得標高・wind_score（m/s）・舗装率（%）は物理量なので
  実験間比較可能。**total_scoreは実験間比較不可**（相対正規化）。この区別は
  `RouteList` の注記に書かれているが、比較UIが無いため誤用の機会も今は無い——
  比較機能を作る際に「並べてよい数値」と「並べてはいけない数値」の区別を
  UI側で強制する必要がある（§10-3の設計条件）。
- **信号数・平均交通ストレス等**: 属性未取込のため存在しない（計画P1で
  `RouteCandidate` へのルート単位集約値追加が既に予定されている。本レビューの
  比較UIはその受け皿になる）。

## 5. Explainability

**現状は「半分ブラックボックス」。**

- 返却されるもの: total_score（合成後1値）、生値4つ、区間ごとの
  `*_difficulty`（軸別・0-100絶対基準）と合成 `difficulty`。
- 返却されないもの: **total_scoreの成分分解**。`RouteScorer.score` は
  `component_scores`（軸別の正規化スコア）を計算しているのに、合成後に捨てている
  （[route_scorer.py:33-63](../backend/app/services/route_scorer.py#L33-L63)）。
  「Route A 87点 = 距離28 + 標高12 + 風30 + 路面17」という分解は、
  **新しい計算を一切追加せず**、計算済みの値を `RouteCandidate` に持たせるだけで返せる。
- 区間レベルの説明可能性は良い: `RouteSegmentDetail` が生値（gradient_percent・
  wind_penalty・road_surface_good）と難易度の両方を持ち、「閾値ロジックをフロントに
  複製しない」設計も正しい。Edge Cost（road_graph探索が実際に使ったコスト）は
  レスポンスに出ないが、これは仕様上恒久保存しない設計（`EdgeCostResult`）であり、
  区間難易度で代替できるため現段階では許容範囲。

**改善案**: 成分スコアの返却（§10-2）を最優先。将来的には「候補Aが候補Bに勝った軸・
負けた軸」の差分表示（フロント計算で可能になる）。

## 6. 重み・ソフトペナルティ・ハード制約・優先条件の区別

構造としては既に区別されている:

- **重み（ソフト）**: `RoutePreference` → difficulty → 距離乗算ペナルティ（1.0〜2.0倍）
- **ハード制約**: `is_edge_allowed`（motorway/trunk系除外）— コストではなく探索から除外
- **優先条件（ボーナス）**: 未実装（計画のサイクリングロード・ボーナス評価がP2）

区別の設計は健全で、現段階でこれ以上の仕組み（制約DSL等）は**作るべきでない**。
ただし2点を記録しておく:

1. **ハード制約はroad_graphエンジンにしか効かない。** ORSエンジンの通行可否は
   ORSの`cycling-road`プロファイル任せで、`DISALLOWED_HIGHWAY_TYPES` を変えても
   既定エンジンの挙動は変わらない。「勾配8%以上を原則避ける」のような
   **属性ベースの新ハード制約の実験も、road_graph限定**になる（§8 Case E）。
2. 距離乗算ペナルティの上限が2.0倍のため、「ほぼ絶対に避けたい（が通行は可能）」を
   表現する強ペナルティ帯が無い。将来「ソフト制約の強さ」を実験したくなった場合は
   `compute_edge_cost` の係数レンジ自体が実験変数になる（設計上1関数の差し替えで済む）。

## 7. 評価軸の段階的追加（路面だけ → +交通ストレス → …）

重み0がOFFとして機能するため、**YAML編集ベースでは今日でも可能**
（例: wind=0, elevation=0 にすれば「路面だけ」）。しかし:

- UIが無いため「段階的に足しながら形状変化を見る」一連の実験が全てエディタ往復になる
- 実験間比較が無いため「軸を足した結果ルートがどう変わったか」を並べて見られない
- min-max相対のtotal_scoreは軸構成を変えると意味が変わるため、
  軸構成違いの実験間でtotal_scoreを比べることに意味が無い（生値で比べるしかない）

§10-1〜3が入れば、この実験パターンは「スライダーを0にする→生成→スロット比較」になる。

## 8. Architecture / Change Cost（Case A〜F シミュレーション）

前提: ゲートT16-T20完了済み・静的属性計画承認後の状態を基準にする。
「2エンジン税」はADR（decisions/pre-static-attributes-gate.md）で
「新指標はORS側では最初からNone」と決定済みのため、以下ではORS側実装を数えない。

### Case A: 新しい道路属性を1つ追加（表示レイヤーまで）

計画書§6の手順どおり。**backend 5〜6箇所＋PBF再取込、frontend 1箇所**。

| 層 | 変更対象 |
|---|---|
| 取込 | `import_profile.yaml`（keep_tags）・取込バッチ（tags列）・`osm_adapter.py` |
| DB | migration 1本（T17機構）＋再取込実行 |
| 派生 | `domain/traffic.py` 等の純関数（属性による） |
| 表示 | MVT SQL（`RoadSurfaceTileQuery`）＋タイル世代更新（ドリフト検知テスト有） |
| UI | `roadFilterAxes.ts` へ軸1定義（凡例・絞り込み・チップは汎用機構が処理） |
| テスト | 純関数単体＋正準語彙照合の追従 |

評価: **健全**。第2回レビューI-2の診断どおり増幅要因は除去済みで、
これ以上の汎用化（タグのJSONB直接表示等）は不採用の判断も正しい。

### Case B: 既存評価軸の重み計算を変更

- 重みの**値**の変更: YAML 1行・0ファイル・再起動不要。**最小**。
- 重み→難易度の**変換**の変更（例: 勾配ブレークポイント）: `domain/difficulty.py` 1ファイル＋テスト。
  ただし両エンジンの表示・評価に同時に波及する（共有しているので望ましい波及）。

### Case C: 新しい評価軸を追加（ルート評価まで組み込み）

**約8〜10ファイル**。現状の最重コース。

1. `domain/difficulty.py`: 変換関数（例: `traffic_difficulty`）
2. `domain/evaluation.py`: `RoutePreference` フィールド＋ `compute_edge_cost` の項
3. `route_preference.yaml` / `scoring.yaml`: 重みキー
4. `route_scorer.py`: component追加
5. `domain/route.py`: `RouteCandidate`/`RouteSegmentDetail` フィールド（→OpenAPI型生成で
   フロント型は自動追従。T4の成果が効く）
6. `road_graph_engine.py`: 属性供給とsegments組み立て
7. （ORS側: None返却の明示のみ）
8. `RouteList.tsx`: 表示1行＋scoreHint文言
9. `routeStyleModes.ts`: 色分けモード（表示したい場合）
10. テスト: 1〜6の各層

評価: 層をまたぐが**各層1箇所ずつ**であり、経路は素直。問題はコード構造より
「追加した軸で実験する手段が無い」こと（本レビューの主題）。
なお5→8の間で `RouteList` のscoreHint文言・表示行だけが手動追従であり、
軸が増えるほどここが第3の「手動同期ペア」になる（§10-8）。

### Case D: 評価軸2つを組み合わせた新指標

- 線形結合なら: 重み設定だけで表現でき、新指標を作る必要自体が無い。
- 非線形（例: 未舗装×急勾配の相乗ペナルティ）なら: `domain/difficulty.py` に
  合成関数1つ＋ `compute_edge_cost` の1行。**2ファイル**。UI・API・DB変更不要
  （合成後のdifficultyに溶け込む）。内訳を表示したい場合のみCase Cに準ずる。

### Case E: 新しいハード制約を追加

- highwayベース: `DISALLOWED_HIGHWAY_TYPES` へ1値＋テスト。**1ファイル**。
- 属性ベース（bicycle=no・勾配8%以上等）: `is_edge_allowed` の拡張＋属性の供給配線。
  2〜3ファイル。ただし**いずれもroad_graphエンジン限定**（§6）。
- 将来「制約のON/OFF自体を実験する」なら、制約もRoutePreference相当の設定に
  乗せる必要がある（現時点では不要。実験ニーズが出てから）。

### Case F: ルート評価ロジックを変更

- Edge単位（合成方式・ペナルティカーブ）: `compute_edge_cost` 1関数（設計意図どおり）。
- ルート単位（正規化方式・ソート基準）: `RouteScorer`＋`domain/scoring.py`。
- **1〜2ファイル＋テスト。** 隔離は良好。

**総括**: 変更コストは全ケースで「各層1箇所」の原則が守られており、
過剰な汎用化も無い。研究効率のボトルネックはコード構造ではなく操作環境である。

## 9. Complexity Balance

- **過剰な抽象化**: 見当たらない（第2回レビューの結論を再確認。エンジンポート・
  リポジトリファサードとも実需に裏付けあり）。
- **不足している抽象化**: 「評価軸のカタログ」（§3末尾）。ただし導入は
  軸が実際に3→6以上へ増える静的属性P1のタイミングでよい。**今作るのは早すぎる**。
- **データ変換の多重化**: 評価値の2系統（ORS数値ID/OSMタグ・標高2経路・風2意味論）は
  既知のI-1で、ADRで封じ込め済み。新規の指摘なし。
- **UIと評価ロジックの結合**: 無い。むしろ**UIに評価ロジックへの接点が無さすぎる**のが
  本レビューの主指摘（結合の欠如という逆側の問題）。
- **重複ロジック**: `composite_difficulty` と `RouteScorer` の「None除外＋重み再正規化」は
  同じ考え方の2実装だが、対象（Edge絶対/候補相対）が異なり意図的。許容。
- **将来のためだけの過剰設計**: `load_route_preference(path)` のプロファイル差し替え口は
  未使用だが1引数であり無害。むしろ§14の受け皿として活きる。

## 10. Top 10 Improvements（研究効率への効果順）

### 1. 評価重みのリクエスト上書き（最優先）
- **問題**: 実験変数（重み）がAPIに乗らず、実験=サーバー側ファイル編集。
- **推奨**: `RouteGenerateRequest` に `scoring_weights` / `route_preference`（省略可、
  省略時YAML既定値）を追加。`get_route_generator` 系DIへ受け渡し。
  バリデーション（非負・上限）のみ付ける。既存クライアント無変更で後方互換。
- **期待効果**: ループ1周からエディタ往復が消える。§10-4のUIの前提。
- **変更規模**: S〜M（routers/routes.py・dependencies.py・2エンジン配線・テスト）。

### 2. total_score成分の返却
- **問題**: 計算済みの成分スコアを捨てており、スコアがブラックボックス。
- **推奨**: `RouteCandidate` に `score_breakdown`（軸別の正規化スコアと重み、または
  寄与点）を追加。`RouteScorer` の `component_scores` を保持するだけ。OpenAPI型生成で
  フロント型は自動追従。
- **期待効果**: 「なぜ87点か」が即答可能に。仮説修正の材料が数値になる。
- **変更規模**: S。

### 3. フロントの実験スロット（結果の保持と並置比較）
- **問題**: 生成のたびに前回結果が消え、実験間比較が記憶頼み。
- **推奨**: 直近の生成結果を条件（重み・エンジン・距離・時刻）付きで2〜3スロット保持し、
  ①メトリクス表で並置（**生値と絶対基準difficultyのみ**。total_scoreは
  スロット間比較に出さない——相対評価の誤用防止をUIで強制する）
  ②地図にスロット別の色で重ね描き（形状比較が本命）。
  保存はメモリ内でよい（リロードで消えてよい。永続化はDEFER）。
- **期待効果**: 「比較→仮説修正」が初めて成立する。
- **変更規模**: M（page.tsx状態設計＋MapView候補ソースの拡張＋一覧UI）。

### 4. 重み調整UI（研究用パネル）
- **問題**: §10-1のAPIができてもUIが無ければブラウザ内で完結しない。
- **推奨**: デバッグモード（既存の `DebugPanel` トグル）配下に評価重みパネルを追加。
  scoring 4値＋preference 3値の数値入力/スライダー＋「既定値に戻す」。
  一般ユーザーUIと混ざらない場所に置く（§14の分離方針どおり）。
- **期待効果**: 仮説→実験の操作量が最小化。
- **変更規模**: M。

### 5. ルート色分けモードの拡充（路面・総合難易度）
- **問題**: segmentsに返却済みの `road_difficulty`・`difficulty` に表示手段が無い。
- **推奨**: `routeStyleModes.ts` へ2モード追加（データ・API変更ゼロ、既存の
  `buildSteppedMode` で完結）。
- **期待効果**: 「路面重視にしたら実際に舗装区間が増えたか」を地図で直接確認できる。
- **変更規模**: S。

### 6. 使用条件のレスポンスエコー
- **問題**: どの重み・エンジンで生成された結果か、レスポンス自体から再現できない。
- **推奨**: `RouteGenerateResponse` に適用重み・パラメータ・生成時刻を含める
  （`engine` フィールドの拡張と同じ流儀）。フロントのスロット保持（§10-3）が
  そのまま実験記録になり、JSONコピーで再現条件の保存にもなる。
- **期待効果**: 再現性の最低ラインを機構なしで確保。
- **変更規模**: S。

### 7. 実験間比較の「物差し」整備
- **問題**: total_scoreが実験間比較不可のため、比較の共通尺度が生値しかない。
- **推奨**: ルート単位の**絶対基準集約値**（segmentsの軸別difficultyの距離加重平均）を
  `RouteCandidate` に追加する。既存データの集約のみで新規取得なし。
  静的属性P1の「ルート単位集約値（trafficStressScore等）」と同じ形にして先行例を作る。
- **期待効果**: 「候補内の順位付け（相対）」と「実験間の良し悪し（絶対）」の
  2つの尺度が明示的に分かれる。
- **変更規模**: S〜M。

### 8. 評価軸メタデータの散在の解消（軸カタログ）
- **問題**: 軸の定義がYAMLキー・モデル・スコアラー・表示文言に分散（§3）。
  RouteListのscoreHint文言は軸を増やすと必ずズレる第3の手動同期ペア。
- **推奨**: 静的属性P1（評価組み込み）と同時に、軸のid/表示名/重みキー/説明を
  1カタログ化し、内訳表示・hint文言・重みUIをそこから列挙生成する
  （`mapLayers.ts` と同じ型）。**それまでは着手しない**。
- **変更規模**: M（実施タイミング条件付き）。

### 9. 研究フェーズのエンジン運用方針の明文化
- **問題**: 「重み実験はroad_graph、既定はORS」という使い分けがdocsに明示されていない。
  新指標はORS側Noneの決定により、静的属性の評価実験は全てroad_graph前提になる。
- **推奨**: architecture.md（または研究手順メモ）に「評価モデル研究時の構成」を1節追加。
  T9/T12（road_graph高速化）の優先度判断を「研究回転数」の観点で再評価する。
- **変更規模**: S（docsのみ）。

### 10. Human-in-the-loop記録（軽量メモ）
- **問題**: 「このルートは実走的に良い/悪い」という人間の判断を残す場所が無い。
- **推奨**: 当面は§10-3のスロット＋§10-6のJSONコピーで代替し、**専用機構はDEFER**。
  実験数が増えて記憶で回らなくなった時点で、スロットへの一言メモ（localStorage）程度から。
- **変更規模**: S（ただし今はやらない）。

## 11. KEEP（変更しない方がよいもの）

- **3層評価構造**（属性→セグメント難易度→ルートスコア）と
  `scoring.yaml`（相対）/`route_preference.yaml`（絶対）の役割分離。
  研究UIはこの構造を**表示する**だけでよく、構造自体の変更は不要。
- **絶対基準のdifficulty（0-100）**: 実験間比較の物差しとして研究フェーズの主役になる。
  基準値（ブレークポイント）を`domain/difficulty.py` 1箇所に持つ形も維持。
- **重みのYAML既定値**: リクエスト上書きを足しても、YAMLは「既定プロファイル」として残す
  （git履歴が実験の粗いログにもなる）。
- **レイヤーカタログ＋軸機構＋正準語彙の生成物照合**: 属性が増える研究フェーズの
  インフラそのもの。新属性は必ずこの型に乗せる。
- **1生成内の8候補比較UI**（一覧＋地図＋選択ハイライト＋ポップアップ）と
  「下書き→適用」方式の絞り込み編集。
- **エンジン切替＋`engine`フィールド**: 研究（road_graph）と安定運用（ORS）の
  両立手段として研究フェーズでこそ価値が上がる。
- **`compute_edge_cost` の「1関数差し替えで評価方式を変えられる」設計**と、
  Edge Costを恒久保存しない方針。
- **デバッグ基盤**（request-id貫通・DebugConsole・/api/debug/stats・ステージ別サマリログ）:
  実験の遅い/失敗の切り分けにそのまま効く。

- **総合難易度スコアの本格チューニング（0-100統一等）**: 計画P2どおり。

- **Human-in-the-loop専用機構**（§10-10）。

## 14. Future Product Interface

研究→製品の落とし込みは、既存の設計がすでに受け皿を持っている:

```
Research UI（重みを直接操作・スロット比較）
  ↓ 良い重みセットが見つかる
名前付きプロファイルYAML（route_preference_comfort.yaml 等。
  load_route_preference(path) の差し替え口が既にある）
  ↓
一般ユーザーUI: プリセット選択（快適重視/信号少なめ/坂を楽しむ…）
  ＋ 距離・時間 ＋ せいぜい1〜2本の抽象スライダー（楽さ⇄挑戦）
  ↓ プリセットがリクエストの重み上書き（§10-1と同じAPI）に変換される
一般ユーザー向けルート提案（内訳・重みは見せず、
  「舗装率98%・信号少なめ・獲得標高320m」のような特徴ラベルへ要約）
```

つまり§10-1のAPIは研究用の使い捨てではなく、将来のプリセット機構の配線を先に作る
ことに相当する。逆に、研究用の詳細表示（内訳・スロット・重みパネル）は
デバッグモード配下に置き続けることで、製品UIと自然に分離できる。
現在のUIは研究情報と一般向け情報の混在がほぼ無く（唯一、RouteListの相対評価注記が
一般向けとしては専門的すぎる程度）、この分離方針を守れば将来の整理コストは小さい。

## 15. Recommended Roadmap

### Phase 1: 実験ループの開通（backend中心・小さく速く）— **実施済み（2026-08-15、improvement-plan.md T23）**

- **対象**: §10-3（実験スロット＋地図重ね描き＋比較表）・§10-4（重みパネル）・

- **リスク**: 中。page.tsx の状態設計（スロット×候補×レイヤー）が複雑化しうるため、

### Phase 3: 新属性の評価組み込みと軸スケール対応
- **対象**: 静的属性P1（評価組み込み・ルート集約値）と同時に §10-8（軸カタログ化）。

  「新属性を1つ足して比較する」という本来の研究シナリオがフルで回る。
- **期待効果**: 冒頭の最終判断基準シナリオ（属性追加→評価組込→重み設定→生成→比較→
  内訳確認→修正→再実験）が全段UIで完結。
- **リスク**: 中。2エンジン税の再発だけ警戒（新軸はADRどおりORS側None。
  road_graph研究常用が進んだ時点でT21の要否を再判断）。
