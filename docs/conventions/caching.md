# キャッシュ方針

サーバーの中で、一度得た値をどこに・どれだけ持つかの決め方。ブラウザへ返す`Cache-Control`は
`backend/app/api/cache_policy.py`の対応表が正本。キャッシュを足すとき、TTL・保持方式を変えるときに読む。

## 大原則

1. **正本を持たないものだけをキャッシュする。** 失っても呼び出し元が取り直す・求め直せば正しい答えに戻れるものに限り、
   キャッシュを唯一の持ち主にしない。
2. **fail-open。** キャッシュ層の障害（Redisに届かない・壊れたエントリ・ディスクのエラー）は「未キャッシュ」へ倒し、
   通常の取得経路へ進ませる。
3. **fail-openでも、失敗は必ず記録する。** 失敗は`log_external_call`のfields（`result="error"`・`error_type`）へ載せ、
   Redisならサーキットブレーカー（`record_redis_failure`）へも記録する。記録が無いと、障害が「少し遅いだけ」に見えて誰も気づけない。
4. **キャッシュで隠すのは遅さだけで、正しさを隠さない。** 古い値でも返す（stale fallback）なら、どれだけ古いものまで許すかを定数で明示する。

## 入力（取得）と保持（キャッシュ）の対応

取得層と保持層は対で決め、どちらも既存の共通骨格を使う。自前で書くのは「Redisへ持つときは`redis_json_cache`を使う」の例外に当たるときだけ。

| 取得するもの | 入力（取得層） | 保持（キャッシュ層） |
|---|---|---|
| 更新頻度の低い外部JSON/CSV（警報・WBGT・洪水・地域マスタ） | `simple_api_client.py: cached_fetch` | プロセス内`cachetools.TTLCache`（クライアントのモジュールが作り、呼び出し側（`api/dependencies.py`）が持って`cached_fetch`へ渡す） |
| アメダスの観測 | `simple_api_client.py: cached_fetch` | `jma_amedas_store.py`（Redis。定期の取得が書き、読む側はRedisから読む） |
| 気象庁の動的タイル（ナウキャスト・キキクル等） | `jma_tile_client.py: JmaTileClient.fetch`（上流への秒間上限つき） | `jma_tile_redis_cache.py`（Redis） |
| 気象庁MSMの予報 | `msm_client.py: refresh`（ETag条件付きGETでファイル同期） | ローカルファイル（`backend/data/msm/`） |
| 色別標高図・基礎地図 | 各クライアント（`gsi_tile_client`・`basemap_client`） | `tile_cache.py`（ディスク、生バイト列） |
| PostGIS由来の重い中間結果 | リポジトリ層 | 用途で選ぶ（次節） |

新しい外部連携は、上表のどれと同じ性質かを先に考え、同じならその行の組み合わせを使う。

## 保持層の選び方

保持層は次の2つの軸だけで決める。値の形式（バイト列かオブジェクトか）は層を増やす理由にしない。

| | 実体がRAMに載る | 実体がディスクに載る |
|---|---|---|
| **プロセス内**（そのプロセスだけ） | `cachetools`（`TTLCache`／`LRUCache`） | — |
| **プロセスをまたぐ** | **Redis**（既定） | ディスク（`tile_cache`・`tile_persistent_cache`） |

「再起動しても残るか」は軸にしない。RedisもRDBスナップショット（本番は`save 3600 1 / 300 100 / 60 10000`、`appendonly no`）で
再起動をまたいで戻り、ディスクもホスト側のディレクトリをマウントしている限り残る。

| | Redis | ディスク |
|---|---|---|
| 実体の置き場所 | **常にRAM**（11GBのVMをPostgreSQLと共有） | ディスク。RAMにはOSのページキャッシュとして要る分だけ載る |
| 上限 | `maxmemory` 2GB | 無し（自分で持つ） |
| 退避 | `maxmemory-policy volatile-lru`＝**TTLのあるキーだけ**自動退避。TTLなしのキーで上限に達すると書き込みがエラーになる | 無し（自分で消す） |
| 使用量の見方 | `INFO memory` | `du` |

### 速度は判断材料にならない

速さを理由にRedisを選ばない。大きな値の読み出しは時間の大半がデシリアライズ（unpickle）で、繰り返し読まれるものは
OSのページキャッシュに載るため、ディスクはRedisより遅くない。速くしたいなら、保持層ではなくシリアライズ形式を変える。

**判断の順序**:

1. プロセス内で足りるなら、それが最も安い
2. プロセスをまたぐ必要があり、**値が小さくTTLを付けられる**ならRedis
3. **数百MB規模、またはTTLを付けられない**ならディスク。掃除は自分で持つ（「ディスクを選ぶときの責任」）

### プロセス内キャッシュは`cachetools`に統一する

追い出し（`OrderedDict`＋`move_to_end`＋`popitem`）を自前で書かない。TTLが要るなら`TTLCache`、件数上限だけなら`LRUCache`。
件数上限の根拠（メモリ量の実測等）はコメントへ書く。ライブラリで表せない要件があっても、追い出しは`LRUCache`・`TTLCache`へ委ね、
`cachetools`を内側に包む薄い包みだけを書く。

上限で追い出すこと自体は`cachetools`の振る舞いなので、テストで確かめるのは使う側の入口から見える振る舞いだけ
（[testing.md](testing.md)「確かめる高さ」）。

**L1（プロセス内）＋L2（Redis）の2段構成は既定にしない。** 1段で足りないことを実測で示せたときだけ足す。

### ディスクを選ぶときの責任

ディスクが向くのは、大きくて、TTLで自然に消したくないもの。これをRedisに置くと、RAMを占有したまま`volatile-lru`の退避対象にも
ならず、`maxmemory`に達したとき書き込みが落ちる。ディスクを選んだら、次を用意する。

1. **容量の上限と退避**: `diskcache`の`size_limit`と退避の順（`eviction_policy`）で持ち、自前で書かない。退避の順は読み方で選ぶ——
   `least-recently-used`は読むたびに書き込みが走るため、地図の読み込みで大量に読まれる`tile_cache`は書いた順（`least-recently-stored`）にする
2. **世代交代で要らなくなった実体を消す手段**と、それを**どこで呼ぶか**（上限に達するまで居座るため、上限とは別に要る。「無効化」）
3. 使用量が想定内かを確かめる方法

鍵・読み書きの骨格・掃除は`infrastructure/`のモジュールが持ち（例: 地域タイルは`region_tile_cache.py`）、`services/`とは値で
やり取りする。上の層が`tile_cache.py`・`tile_persistent_cache.py`を直にimportすると`lint-imports`が落ちる
（[directory-layout.md](../architecture/directory-layout.md)「backend」）。

今のディスクの置き場:

| 用途 | 置き場所の判断 | 掃除 |
|---|---|---|
| `tile_cache`（基礎地図・DEM・色別標高図の生バイト） | 外部由来で不変・TTL不要 | 容量上限（`tile_cache_size_limit_mb`）を超えると`diskcache`が書いた時刻の古い順に退避する。鍵に世代を持たないので、伸び続けたときの頭打ちとして持つ |
| `tile_cache`のうち土地被覆タイル（PNG） | 同上。ラスタ構成ごとに鍵が割れる | 起動直後と24時間ごとに、今開けているラスタ構成でない世代を消す。容量上限の対象でもある |
| `tile_cache`のうち地域のMVTタイル（路面・点。鍵`region/<系統>/v<世代>/…`） | PostGISから焼き直す費用を払わずに配る。世代の中では不変 | 起動直後と24時間ごとに、配っていない世代を消す。容量上限の対象でもある |
| `msm`（予報の`.om`ファイル） | 大きくTTLに馴染まない | 同期のたびに予報窓の外を消す |
| `tile_persistent_cache`（way_id別の動的値のpickle） | 求め直す費用を払わずにプロセスをまたぐ | 容量上限＋`expire`による失効 |
| `road_network`（取込範囲全体の道路網の配列、世代ごとの置き場。GB規模） | 作るのに数分かかり、プロセスをまたいで全員が読む。メモリマップで開くため、使う列だけがRAMに載る | 作ったときに同じ形の古い世代を消し、起動後に形の違う置き場を消す |

これらをRedisへ移さない（数百MB規模をRAMへ移し、同居するPostgreSQLのページキャッシュを圧迫する）。

## Redisへ置くもの・置かないもの

基準は、外部への負荷を肩代わりしているかどうか。

- **Redisへ置く**: 失うと自分で制御できない相手（気象庁等の外部サービス）へ取りに行くもの。プロセスの数だけ外部への問い合わせが増えないよう共有する
- **プロセス内で持つ**: 失っても自前の正本（PostGIS）から戻せるもの。ミスのコストは自分のDBへの往復で、自分で観測・制御できる

| データ | 失うと誰に取りに行くか | 置き場所 |
|---|---|---|
| JMAタイル本体（`jma:tile`） | **気象庁**（非公式配信・秒間上限を自主設定） | Redis |
| 在否インデックス（`jma:tile-index`） | 同上（プリウォームが作る共有知識） | Redis |
| アメダス観測値（`jma:amedas`） | **気象庁**（10分ごとに全国分を1リクエスト） | Redis |
| アメダスの1時間雨量の履歴（`jma:amedas:rain-history`、正時ごと×観測所） | **気象庁**（失うと過去の正時の地図JSONを全本取り直す） | Redis（読む側は求めた材料の値をプロセス内に5分持つ） |
| 取込範囲全体の道路網の配列（`road_network_store`） | 自前のPostGIS | ディスク（メモリマップで読む） |
| way_id別の動的値（勾配） | 自前で求め直す | ディスク |

ルート生成系はRedisへ置かない（寄与はルート生成1回の2%ほど）。

### キャッシュしないという選択

キャッシュが節約する時間を測ってから置き場所を決め、節約が小さければキャッシュ自体をやめる。例: 風の材料は節約が1タイル数msで
エントリが190KBになるためキャッシュせず、勾配は約0.8秒を節約するためディスクへ持つ
（[dynamic-way-values.md](../modules/backend/dynamic-way-values.md)）。

地点の検索（住所の辞書）もサーバーでは持たない。引くのは手元のファイルで1件数ms〜200ms前後、同じ入力が続くのはほぼ同じ利用者の
打ち直しなので、ブラウザが持つ（`api/cache_policy.py`）。

### ワーカー複数化に備えて注意すること

backendは1プロセスでしか正しく動かず、ワーカーを増やすと起動を止める（`infrastructure/single_process.py: require_single_worker`。
[cross-cutting-infrastructure.md](../modules/backend/cross-cutting-infrastructure.md)「1プロセスの境界」）。複数化するときは、
キャッシュのほかに次の2つを別に扱う。キャッシュをRedisへ寄せてもこの2つは解けない。

- APSchedulerのバッチ（アメダス更新10分・JMAタイルのプリウォーム10分・MSM同期30分）は`main.py`のlifespanで登録されるため、
  ワーカーごとに同じ仕事をする。1プロセスへ寄せる仕組み（専用ワーカー・Redisロック等）が要る
- 上流への秒間上限（`jma_tile_upstream_max_requests_per_second`）はプロセス内の状態のため、実効値がワーカー数倍になる。
  同じ理由で、外部の取得を肩代わりするキャッシュをプロセス内に置くと、上流への要求がワーカー数に比例して増える

## Redisへ持つときは`redis_json_cache`を使う

Redisが使えるかの確認・クライアントの取得・`log_external_call`での計測・失敗を未キャッシュへ倒す・成否をサーキットブレーカーへ
記録する、の定型は`redis_json_cache.py: get_json`/`redis_json_cache.py: set_json`が持つ。値がバイナリなら
`redis_json_cache.py: get_bytes`/`redis_json_cache.py: set_bytes`を使う（base64でJSONへ包むと、ヒットのたびにデコードと約1.33倍の容量を払う）。
キーごとの項目をまとめて書くなら、Hashの`redis_json_cache.py: get_hash`/`redis_json_cache.py: set_hashes`（pipelineで1往復）を使う。
呼び出し元が持つのは、キー設計・TTL・値の意味づけだけにする。

呼び出し元は`infrastructure/`のモジュールにする。鍵・保存する形・TTL・保存した形の検査はそのモジュールが持ち、`services/`とは
値でやり取りする（例: `infrastructure/jma_amedas_store.py`）。上の層がRedisの接続を直にimportすると`lint-imports`が落ちる
（[directory-layout.md](../architecture/directory-layout.md)「backend」）。`services/`がプロセス内（`cachetools`）に持つ、
自分で求めた値のキャッシュはこの規則の外にある。

```python
from app.infrastructure.redis_json_cache import get_json, set_json

value = await get_json(key, category="cache:xxx")            # ミスはNone・障害はUNAVAILABLE
await set_json(key, payload, ttl_seconds=TTL, category="cache:xxx")
```

**自前で骨格を書いてよい例外**（当たるなら、その理由をモジュールのdocstringへ書く）:

- 骨格に無い一括読み書きが要る（`mget`で1リクエストに数百キーを引く等）
- キーの生存期間を個別に操作する（TTLの付与以外のRedis機能を使う）

例外でも、大原則2（fail-open）と3（失敗の記録）は満たす。

## TTLの決め方

TTLの数字には、何に合わせた値かをコメントへ書く。決め方は次のどれかに揃える。

| 類型 | 決め方 | 今の例 |
|---|---|---|
| 上流の更新間隔に合わせる | 上流の更新周期 ＋ 取り込みの余裕 | アメダス観測15分（バッチ10分＋余裕） |
| 内容が変わらない期間に合わせる | 内容が確定して以後変わらないなら、その識別子が有効な間 | JMAタイル本体20分（`basetime`が変わればキーも変わる） |
| ほぼ不変なマスタ | 1日 | 地域マスタ・WBGT地点マスタ・観測所一覧（いずれも24時間）・地点の検索をブラウザが持つ時間（`api/cache_policy.py: MASTER_LOOKUP`） |
| 共有率で決める | 短すぎるとヒットせず、長すぎると鮮度を失う中間 | `targetTimes`2分 |
| 再計算コストで決める | 失っても求め直すだけなら長め | 道ごとの勾配の値（24時間） |

どれにも当たらないなら、その値にした理由を1行で書けるかを先に確かめる。書けないなら、まだ決め方が定まっていない。

## 判断をキャッシュしてよい条件

データ（正本の行の写し）ではなく判断（真偽値・鮮度）をキャッシュするときは、次の3つを**すべて**満たす。1つでも欠けるならキャッシュしない。

1. **入力がすべてキーに入っている**（純関数のメモ化になっている）。キーに無い入力があると、その入力の書き手全員が無効化に加わらなければならない
2. **判断が一方向に単調で、保持するのが安全側**。「一度真なら覆らない」判断の真だけを保持するなら、外れても害がない。
   危険側（「最新である」等）を保持すると、外れたときに古いデータを黙って返す
3. **TTLが「誤ってよい窓」から導かれている**。その時間だけ誤った判断を返しても許容できると説明できる

別プロセス（バッチ等）から無効化を送りつける形にしない。fail-openと組むと伝え漏れに誰も気づかないため、1〜3を満たすか、キャッシュしない。

### 版をキーに入れるなら、版の照会が十分に安いこと

1を満たす標準の手段は、入力の版（世代番号・更新時刻）をキーへ含めること。版の照会は、キャッシュが節約する時間の1/10以下を目安にする。
同じ桁なら、最初からそのテーブルを引く。

## 「取っても得るものが無い」ことの覚え方

疎なデータ（気象庁の動的タイル・整備区域外のDEM等）では、空振りを覚えること自体がキャッシュの目的になる。覚える対象と減らせる通信は
次の3つで違う。新しく疎なデータを扱うときは、どれが要るかを先に決める（3つとも要るとは限らない）。

| 種類 | 覚えるもの | 減る通信 |
|---|---|---|
| 恒久404 | 上流に存在しないパス | サーバー → 上流 |
| 空の実体 | 200で返るが中身が空（透明タイル等） | クライアント → サーバー |
| 在否インデックス | 「その範囲のどこが空か」の一覧 | クライアントの要求自体を起こさない |

## 無効化（キャッシュを捨てる）

**既定は世代番号。** キー自体に世代を埋め、変わった瞬間から新旧を別物にする。

**世代は手で書かず、`app/infrastructure/cache_identity.py`で組み立てる。** 鍵は手で書くリビジョンと形の署名の合成で、形——MVTへ焼き込む
SQL、そこへあらかじめ束ねた値（分類タグ集合等）、pickleするdataclassの列構成——は機械的に署名する。署名に入らないものを増やさない
（`str()`に現れない材料（バインドパラメータの値等）は、焼き込む値だけが変わって鍵が動かない）。手で上げるのは、形は変わらず意味が
変わったときだけ（同じSQL・同じ列のまま、読み先のテーブルの中身をバッチで作り直したとき）。

**デプロイを伴わずに起きる変化は、DBを正にする。** バッチはコードを書き換えないので、手で書くリビジョンでは表せない。書いた側が単調カウンタを
進め、読み手はディスクへ最後に書いた時点の記録と突き合わせて、違えば捨てる（派生データは`derived_data_meta.revision`、生データは成功した
取込の数`source_models.py: succeeded_run_count`）。

- 鍵に入れる世代は、キャッシュする値が読む表のすべてを覆う。配信するタイルは派生の表と生データの両方を読むため、両方の世代を持つ
- 生データの世代はどのソースの取込でも進め、系統ごとに読むソースを宣言して絞らない（宣言は値を作るSQLの写しになり、SQLが新しいソースを
  読み始めても気づけない）。取込は稀で、過剰な無効化はディスクのタイルを焼き直すだけで済む
- 読み手は、再起動を待たずに気づけるようTTL付きで読み直す（`services/derived_data_revision_service.py`、配信するタイルの世代）。
  読み直しは、そのキャッシュを実際に読む経路の入口へ置く（別のメソッドへ置くと、キャッシュから直接戻せる定常状態では通らない）
- 世代を置き場の名前に入れる形（道路網の配列、`road_network_store.py`）なら、読み手は読むたびに一番新しい世代の置き場を選ぶだけで、
  突き合わせは要らない

**値を作る関数のソースまではハッシュしない。** 改名やコメントの直しでも全キャッシュが捨てられ、毎デプロイで冷えたパスを踏む。
過剰な無効化のコストが実害を上回る場合は手動に留める（[design-principles.md](../architecture/design-principles.md)構造仕様12の例外）。

**派生物の世代は元データの世代に従属させる。** 派生物の鍵には元データの世代も署名の材料として含め、元データの世代を上げれば派生物も
機械的に捨てられるようにする。独立した2つの文字列にしない。

**世代番号は、古い実体が消えることを意味しない。** TTLのある層（Redis・TTLCache）は古い世代が自然に失効するが、ディスクは残る。
ディスクに世代番号を使うなら、世代を上げたときに古い世代を消す手段を用意し、どこで呼ぶかまで決める。今の掃除の導線は次のとおりで、
新しくディスクに世代番号を使うキャッシュにも同じ導線を用意する。

- 道路網の配列の置き場: 作ったときに同じ形の古い世代を消し（`road_network_store.prune`）、起動後に形の違う置き場を消す
  （`prune_other_shapes`、`main.py`の起動時ジョブ。入れ替わるまで旧コンテナが読んでいるため、起動後にだけ消す）
- 地域タイル（路面・点・土地被覆）: 起動直後と24時間ごとに、今配っている世代の鍵でないものを消す
  （`region_tile_cache.py: prune_other_generations`、`main.py`の定期ジョブ。世代は派生の作り直し・取込でも再起動なしに変わる）。
  世代を読めていない系統（DBの世代が読めない・土地被覆のラスタが1枚も開けない）は消さず、系統の表に無い系統の鍵は消す。
  入れ替わりの間に旧コンテナの読むタイルを消しても、そのタイルが冷えるだけで配信は壊れない

**世代が変わった直後の地図のタイルは、事前に焼かない。** 配信するタイルの鍵は世代から組む（`services/tile_version_service.py: tile_version`）
ので、世代が変わるとディスクのタイルは全部冷え、各タイルは最初に要求されたときに焼かれる。目に見えて待つのは道の密な所を広く見たとき
（z12、1枚数秒）のその区画を最初に開いた1人だけで、世代は派生の作り直し・取込・タイルのSQLを変えたデプロイのあとにしか変わらず、
焼いておくには変わるたびに万の桁のタイルを焼いてサーバーを重くするため。世代が定期に変わるようになった・冷えたタイルの待ちが伸びたときは、
焼くかを決め直す。

**全消し（`tile_cache.clear_all()`）は例外。** 他のレイヤーのキャッシュまで巻き添えにするため、運用操作としてだけ残す。
新しいキャッシュへ全消しの手段を足さない。

**元データの世代には、どの元データを開いていたかも含む。** 土地被覆タイルは`LULC_RASTER_PATHS`（環境変数）で開くGeoTIFFが決まり、
1枚足せば継ぎ目のタイルの絵が変わるため、ラスタ構成の指紋（`infrastructure/cache_identity.py: raster_set_fingerprint`）をディスクの鍵へ
入れる。この指紋はURLへは入れない——URLの世代は生成物（`region-tile-config.json`）でフロントへ渡り、生成はビルド機で行うため、
環境ごとの値を入れられない。そのぶんブラウザ側は`immutable`を付けず再検証させる（`api/cache_policy.py`）。

焼き込み値（MVTのCASE式・材料タグ・domain純関数）を変えても、MVTの世代は手で上げない——`infrastructure/cache_identity.py: tile_version`が
DBの世代と焼き込みの形の署名から決める。同じコミットで揃えるのは生成物（[deployment-sync.md](deployment-sync.md)「コミットと同時に揃えるもの」）。
手で上げる世代定数は、署名に表れない土地被覆の画素の変化を表す`LANDCOVER_REVISION`だけ。

## 直接使ってよい場所

`get_redis_client_or_none`・`record_redis_failure`・`record_redis_success`・`redis_available`を直接呼んでよいファイルは
`backend/tests/structure/test_redis_skeleton.py: ALLOWED`が持つ（骨格そのもの・その接続本体と、単一キーのJSON読み書きでは表せないもの）。
ここに無いファイルで使うとテストが落ちる。寄せられない事情があるなら、理由とともに`ALLOWED`へ足す。寄せ終わったのに`ALLOWED`へ
残っていても落ちる。
