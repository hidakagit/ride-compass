# ドキュメント記載方針

`docs/`配下・`.claude/`配下・README・モジュールdocstringに共通する、**何を書き何を書かないか**の
方針。コードコメントについては[comments.md](comments.md)が別に定める。

## 判定基準: その文書だけを読んで、正しさを検証できるか

**書いてよいのは、その文書（またはそのdocstring）を読むだけで正しいか誤りか判定できる記述。**
判定に他所を見に行く必要がある記述は、他所が変わると黙って嘘になる。

この基準を外れる書き方は次の形で現れる。用語の定義は下の用語集にある。

| 型 | 書いてしまう例 | 代わりに書く |
|---|---|---|
| **数え上げ** | 「car_stressが5つの内部軸を参照する」「段は④〜⑫」 | 「内部軸を組み合わせて算出する」「段は`derive_cli.py: STAGES`が持ち、足せば順序が決まる」 |
| **代弁** | 「フロントはこれを基準に超過分を出す」「配線するのは1行足すだけで済む」 | 自分の側の契約だけを書く（「この値は基準として配る」） |
| **撤去済みの名指し** | 廃止した軸・存在しない引数・削除した方針を現行として説明 | 名前を出さず挙動を書く。他のファイルの定義を名指すなら「パス: 名前」で書き、機械に照合させる（下記「他のファイルの名前は「パス: 名前」で指す」） |
| **写し** | コードにある式・閾値・手順をそのまま書き写す（「`[max(0,(目標−許容)/2.0), (目標+許容)/2.3]`に入るNode」「重複率0.6を超えたら飛ばす」） | その式が**何を達成しようとしているか**を書く（「往路の実距離が目標の半分付近に入るNode」「重複しすぎる候補を飛ばす。しきい値は同ファイルの定数が持つ」） |

相手の挙動に依存する説明が要るなら、相手の実装を要約せず、依存していること自体を書く
（「この値の解釈は受け取る側が決める」）。

**写しと、許容される定数の書き方の線引きは「機械が照合できるか」**。`NAME`（600）のように
定数名と値を並べる形は照合の対象になる（下記「DBの行データ・コードの定数を名指しするとき」）。
式・条件・手順の写しは照合できないので書かない。

### 適用範囲の目安

- `docs/modules/*.md`とdocstring——**読者は次にそのコードを触る人**。実装を読めば分かることは
  書かず、実装を読んでも分からないこと（中身は下の「挙動を書く。要素を数え上げない」の「代わりに書くもの」の3つ目）だけを書く。
- `docs/architecture/`——**読者は仕様を理解したい人**。関数・ファイル名は、コードから導けない
  構造の約束を書くのに要る範囲で名指してよい。実装の手順・中身の説明は`docs/modules/`へ置く。

## 挙動を書く。要素を数え上げない

**ドキュメントが示すべきは「何がどう振る舞うか」「なぜそうなっているか」。**
コードから数えられるものを散文へ写さない（増減しても文書側は何も壊れず、実装より先に古くなる）。

書かないもの:

- **個数**（「4本のバッチが参照する」「現行8軸」「5値の分類」「六つの材料」）
- **全件の一覧**（ファイル一覧・エンドポイント一覧・state一覧・定数一覧・軸id一覧）
- **組み合わせの網羅**（「①〜⑦の要素それぞれについて…」）

代わりに書くもの:

- その要素**群が何をするか**（「派生データを作るバッチは、対象件数を数えてからチャンク単位で
  更新し、進捗を1行INFOで出す」）
- **増えたときに何が起きるか**（「派生の段を1つ足しても`derive_cli.py: STAGES`へ登録すれば順序は決まる」）
- **実装を読んだだけでは分からないこと**（暗黙の前提・モジュール間の隠れた依存・契約・外部システムの実際の挙動・実測値）

## 代表例は許容する。ただし「例」と分かる書き方にする

挙動を分かりやすくするために代表的な要素を挙げるのは**よい**。全件のつもりで読まれる
書き方をしないこと。

- よい: 「`common.py`が共通ヘルパ（`batch_session_factory`等）を提供し、
  派生バッチはこれに乗る」
- よい: 「タイル世代の定数（`LANDCOVER_REVISION`など）」
- 避ける: 「`common.py`は`asyncpg_dsn`・`fetch_verified`を提供する。4バッチが参照する」
- 避ける: 「対象は`gradient`・`surface_q`・`stop_density`・`car_stress`・`accident`・`night`の6軸」

判断の目安は**「要素が1つ増えたときにこの文は嘘になるか」**。嘘になるなら数え上げている。

## 全件が必要なときは、生成物かコードを指す

一覧そのものが必要な場面（デバッグ・棚卸し）では、文書へ写さず、
**生成物**（`region-tile-config.json`・`material-catalog.json`等）か、
**それを定義しているコード**（`MATERIAL_CATALOG`・`derive_cli.py: STAGES`）を指す。

## 派生の表のNULLの意味は、正本の1か所にだけ書く

派生の表の列がNULLのとき何を表すかは、[静的道路属性](../modules/backend/static-road-attributes.md)「値が無ければNULL」
だけが書く。読み手の側の文書・docstring・コメントは「値が無い」とだけ書くか、その節を名指す（言い換えると、正本が変わったときに
読み手の側だけが古い意味を言い続ける）。作り直しの段の中（作業用のスキーマ）のNULLは、まだ値を出していない状態を表してよい
（入れ替えの前の状態で、読み手には届かない）。

外部キー・NOT NULLが保証する行の有無は、「ふつうは起きない」のような確率の言い方で書かず、保証している制約を書く。

## 例外: 責務の逆引きに使う対象ファイル表

**一覧そのものが目的を持つ場合のみ、全件の表を持ってよい。** これに当たるのは
`docs/modules/*.md`の**対象ファイル表**（新しいファイルの責務の逆引き）、`docs/architecture/data-sources.md`の
**外部データソースの表**（提供元の公式ページにしか無い利用条件）、`docs/architecture/tech-stack.md`「秘密の値とトークン」の表
（GitHub等の設定の画面にしか無い、どのトークンがどこへ届くか）だけで、どれもコード側に等価な表現が無い。

完全性を機械で検査する仕組みは無く、周期レビューで人が見る。**表へ足すのが既定**で、
本文だけで済ませるのは表の粒度に合わないとき（本文で責務を説明してあれば逆引きは成立する）。

同じ一覧を検査の無い場所へ二重に持たない。

## DBの行データ・コードの定数を名指しするときは、照合できる形で書く

**デプロイを伴わずに変わるもの**を名指しすると、変わったときに説明だけが黙って嘘になる。軸idの正本は本番DBにあり
リポジトリは写しを持たないので、機械では検査せず、周期レビューで人が見る。

- **axis_id**: 軸は軸スタジオのGUIから追加・削除でき、作り直した軸は生成された別idを持つ。
  本番DBの軸定義に無いidを現行として名指しすると違反。
- **数値の定数**: 「`NAME`（600）」のように名前の直後へ値を書いたら、実装の値と合わなければ違反（秒↔分のような単位の読み替えは許す）。

どちらも、名前を出さずに挙動だけ書けば対象外になる。名前と値を並べて書くのは、照合できる形にするためである。

## 他のファイルの名前は「パス: 名前」で指す

文書・コメントが他のファイルの定義（関数・クラス・定数・フィールド等）を名指すときは、
`domain/material_catalog.py: MaterialSpec.value_labels`のように**「パス: 名前」の形**で書く。
この形の名指しは`backend/tests/structure/test_named_references.py`が全件を今のリポジトリと
突き合わせ、名前が消えた・動いたら、その変更のCIで落ちる。手元では`git add`前の新しいファイルも
実在に数える（`.gitignore`で無視されたものは数えない）。形を外れた名指し（「`page.tsx`の
`handleX`」等）は機械が見ず、周期レビューの「名指しの実在」でしか拾われない。

- **パスは、リポジトリのファイルへ末尾一致で1本に決まる長さ**で書く（`page.tsx`は画面と
  管理画面の2本に当たるので`app/page.tsx`）。同じ名前のファイルが後から増えると、その変更で
  「曖昧」として落ちる。`*`を含むパスは、当たったファイルのどれかに名前があればよい。
- **名前は、そのファイルのコードに現れる綴りそのもの**（`Class.attr`のようにドットでつないでよい）。
  コメント・docstringにだけ残った名前は、無いものに数える。
- 読む側はMarkdownの全文と、ソースのコメント・docstring。文字列リテラルはデータなので読まない。
  `docs/records/`は維持しない階層なので読まない。
- backendのコメントがfrontendの実装を名指さないことは[comments.md](comments.md)「他所を写さない・代弁しない（docstringも同じ）」。
- **「パス:」の直後に英字で始まる説明を書かない**（「パス: int32へ詰める」は`int32`という名前の名指しとして読まれる）。
  説明は日本語で始めるか、コロンを使わない。

ファイルのパスとAPIのパスも、同じ検査が同じ読む側（上の3つ目）で実在を見る。

- **ファイルのパス**は、テストのファイル名（`test_*.py`・`*.test.ts(x)`）と、リポジトリの最上位のディレクトリから
  書いたパス（`backend/`・`docs/`等で始まるもの）だけを読み、末尾一致でどれかのファイルに当たれば実在に数える。
  `.gitignore`が無視するパスは、開発機にだけ置くファイル（`.env`等）の置き場の宣言として実在に数える。
  ほかの拡張子つきの綴り（外部の配信のファイル名・ライブラリの名前）は読まない（最上位から書いていない、
  テストでないファイルの名指しは周期レビューが見る）。
- **APIのパス**（`/api/…`）は、backendのOpenAPIの生成物とNextのroute handlerに照らし、APIのパスそのものか、
  その先頭の区切り（`/api/admin`）か、`{…}`の位置に値を埋めたもの（`/api/jma-tile/a/b.png`）なら実在に数える。
- **例の名前は`<…>`の形で書く**（`backend/tests/<テストのファイル>`・`/api/admin/<X>`）。実在しうる仮の綴り
  （`test_`で始まる仮の名前等）で書くと、無いファイルの名指しとして落ちる。`<…>`・`{…}`を含む綴りは、ファイルのパスとしては読まず、
  APIのパスではその位置に何かが入るものとして読む。

## 数え上げの判断は、書いた本人がその場で行う

「N個」「N種」のような数え上げを機械で検出する仕組みは無い（数の大半は正当な記述で、パターンでは区別できない）。
「要素が1つ増えたときに嘘になる文」かどうかは、書いた本人が判断する。

## 用語集

判定基準を読む前提。同じ語を違う意味で使わない。

| 語 | 定義 | 定義から外れる例 |
|---|---|---|
| **現状** | いまのコードがどう振る舞うか。読んだ人がコードを触るために要る情報 | 「以前は〜だった」「Txxxで変えた」（これは経緯） |
| **経緯** | なぜ今の形になったかの履歴。置き場所はタスクの issue だけ | 「このロックは並列に呼ばれるため必要」（これは今も成り立つ制約で、現状） |
| **数え上げ** | 要素が1つ増減したときに嘘になる記述。個数・全件の一覧・網羅 | 「〜等」「例:」と分かる形の代表例（これは許容） |
| **代弁** | 他のファイル・レイヤー・外部システムの挙動を、自分の文書の中で要約した記述 | 自分が満たす契約の宣言（「この値は正規化済みで配る」） |
| **記述と実装の不一致** | 文書・docstring・コメントが述べる内容が、現在のコードと合わない状態。機能の欠陥とは別に数える | 機能の欠陥（契約の取りこぼし・構造仕様違反など） |
| **写し** | コードにある式・閾値・手順を、照合できない形でそのまま書き写した記述 | 定数名と値を並べた記述（機械が照合するため許容） |
| **自己検証可能** | その文書だけを読んで、正しいか誤りかを判定できる状態 | 判定に他ファイルを開く必要がある記述 |

## 付録

作業の前には読まない。方針の背景。

### なぜこの方針か

文書の陳腐化は、周期レビューの指摘の最大の種類である。件数はレビューのたびに数え直し
（性質の語は`.claude/commands/review.md`「指摘の書き方」）、ここへ数字を写さない。
古くなるのは写しの側で、写しは更新し続ける対象ではなく削る対象である。コードから導けない事実を書いた記述は古くならない。
検査の母集団についての同じ原則は[design-principles.md](../architecture/design-principles.md)構造仕様12にある。
