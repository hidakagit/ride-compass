# ユーザーへの確認依頼

ユーザーへ確認・判断を求めるときの取り決め。テストの欠陥の要確認（`testing.md`）、並行実行の
判断待ち（`orchestration.md`）、タスクの保留など、**どこから出る問いもこの形で出す**。

## 聞くかどうかを決める

- **外から見える振る舞いが変わる** → 聞く
- **変わらない** → 聞かない。**報告して直す**（実装のdocstringやdocsが既に意図を書いているなら、
  それに合わせるだけ。決定はもう済んでいる）

**中途半端に聞いてから勝手に進めない。** 構造と判定したなら最初から聞かない。聞いたなら
答えを待つ。

## 書く順

読み手が「で、何を選ぶのか」へ辿り着くまでの距離が短くなる順で書く。

1. **利用者への約束を1文で。** 何を守るための話かを最初に置く。
2. **問題が顕在化する場面を1つ。** 抽象論にしない。利用者が何をして、何が表示され、実際は
   何が違うか。**起きない場面も1行添える**——書かないと、読み手が自分で境界を探しに行く。
3. **選択肢と、各選択肢で利用者に何が起きるか。**

docstringの引用・実装の経緯・自分がどう判断したかは、**聞かれてから出す**。

## 背景を知らない人が、その1問だけで判断できるように書く

読み手はタスクの経緯を知らない。「番号で言われても背景を知らないから判断できない」。1問には
次を必ず入れる:

- 何の画面・機能の話か（利用者から見える言葉で）
- いまどうなっているか
- なぜ決める必要があるか
- 各選択肢で利用者に何が起きるか

**設問の中に中身を書く。**「この食い違いはどこがズレているか」では、読み手が前の段落へ戻る
ことになる。設問だけを読んで答えられる状態にする。

**画面の見た目・情報量に関わる判断は、変更前と変更後の実画面かモックを添える。** 文章だけでは
「出したらどうなるか」が判断できない。

## 製品の言葉で書く

- 関数名・引数名・「配列」「列」といった**実装の語を使わない**。
- **固有名詞を使わない**（「環八」ではなく「片側2車線の幹線道路」——どこに住む読み手にも同じ絵が
  浮かぶ語を選ぶ）。
- **タスク番号・内部の識別子に頼らない。** 番号は参照として末尾に添えるだけにする。画面に出ない
  内部の話なら、そう明記する。

## 選択肢

- **自分の領分を選択肢に入れない**（例外の出し方・書き方・どう直すか）。
- **選択肢の文面と、実際に当てる作業を一致させる。** 書く前に、その作業が何を変えるかを確かめる。
- 推奨を先頭に置き、理由を添える。

## 届け方

- **選択式の質問（`AskUserQuestion`）で出す。** 1回に4問まで、各2〜4択。推奨を先頭にして、
  ラベルに「（推奨）」を付ける。会話に書くだけにしない。
- **並行実行中の判断待ちは、ためておき、ユーザーが「判断待ちはある？」と聞いたときにまとめて
  出す**（`/asks`。仕掛中のタスク全体は`/dashboard`）。こちらから催促・通知しない。**推奨案を自動で採用しない。**
- **判断待ちは他の作業を止めない。** 判断が要るタスクの、その項目だけを保留し、残りを進める。

## 実測

この形は8往復かけて直された結果である。外したのは順に——選択肢の文面と実際の作業が違う
（「型で通らなくする」と書いたが型注釈は既に済んでおり何も変わらなかった）／「消す」を2つ並べる
（違いは例外の出し方で、自分が決めることだった）／誰が決めるべきかを示さずに聞く／軸を示した
直後に承認を取らず進める／3者の主張を自分の要約で書く／設問を抽象語で書く／「データ」「待ち」が
何を指すか曖昧／実装の語で書く／固有名詞を使う。

並行実行の第1回（[T1049](../records/tasks/T1049.md)）では、判断待ちをタスク番号と短い問いだけで
出し、「番号で言われても背景知らないから判断できない」「出したらどうなるか実画面あるいはモックで
示して」と差し戻された。

## 仕掛中のダッシュボード

タスクにまつわる情報は、次の3か所に役割を分けて置く。同じ事実を2か所で持たない。

| 置き場 | 役割 | 持つもの |
|---|---|---|
| 台帳（`docs/improvement-plan.md`） | 全未完了タスクの正本一覧 | タスクがあること・題名・規模・トリガー・範囲の移り先。判断待ち・決定・進み具合は書かない |
| 記録（`docs/records/tasks/Txxx.md`） | 全タスクの記録の正本（書いた時点で正しければよく、後から直さない） | 背景・方針・問い・ユーザーの答え・確認の結果・検証。タスクのコミットと一緒に入る |
| 仕掛中のダッシュボード（非公開のArtifact） | 仕掛中のタスクを1か所で見る画面 | 下のとおり。正本ではない |

**仕掛中のタスク**は、次のどれかに当たるもの: 担当・ユーザーのセッションが進めている／ユーザーへの問い・操作のお願い・
改善案が出ていて、答えがまだ記録に入っていない。

**ダッシュボード**: https://claude.ai/artifact/E8G458My7xPA8RpbkU3RWF のデータベース（collection `pending`）。手元のセッション・
担当（サブエージェント）・クラウドのセッションのどこからでも`ArtifactData`で読み書きできる（2026-09-24に3つとも実測）。
ページを開けば、ユーザーも画面で見られる。

- **1件＝仕掛中のタスクへの1つの問い・お願い・改善案・答え**。doc_idは`<タスク番号>-<短い名前>`。項目は`task`（タスク番号。
  台帳に行があること）・`kind`（`保留`＝決めてほしい問い／`操作`＝実行してほしい操作／`改善案`＝入れてよいか決めてほしい改善／
  `決定`＝問いを経ずに出た指示）・`text`（その1件だけで分かる本文。問いはこの文書の書き方、操作はそのまま実行できる手順）・
  `answer`（ユーザーの答え。出るまで空）・`source`（書いたセッション・担当）。日時は手で入れず、表の`updatedAt`を使う。
  題名・規模は書かない（台帳から引く）。
- **問いは、記録とダッシュボードの両方に置かない**: 仕掛中のタスクへの問いはダッシュボードに置き、答えが出たら、そのタスクの
  コミットで問いと答えをまとめて記録へ書き、ダッシュボードから消す。記録にある問いは、答えを記録へ書き足して閉じる。
- **ダッシュボードにしか無い事実は、記録へ移すまでの問い・答えだけ**。誰が何を進めているか（状態の表`board.json`）・題名（台帳）は
  写さない。
- **見るコマンドは2本**（並行実行に限らず使う）:
  - `/dashboard`: 仕掛中のタスクを全部、タスクごとに出す——誰が進めているか・どこまで進んだか（状態の表から導く）、
    実行してほしい操作（そのまま実行できる手順で）、入れてよいか決めてほしい改善案（何が起きたか・何を変えるか・入れたら
    何が変わるか）、答えは出たがまだ記録に入っていないもの、最後にページのURL。操作の報告と改善案の承認は、この一覧を見て
    返してもらう（チャットで返すか、ページの「済」「承認」「見送り」のボタンで`answer`に書く）。
  - `/asks`: 仕掛中のタスクのうち、決めてほしい問い（kind `保留`と、記録にある答えの無い保留）だけを選択式の質問で聞き、
    答えをダッシュボードの`answer`へ書く。
  どちらも、台帳に行の無いタスクの件、タスクが既に閉じているのに残っている件を「移し忘れ」として出す。
- **バックアップ**: 1日1回、全件を`.git/orchestration/pending-backup/<日付>.json`へ書き出す（コミットしない。作業フォルダごと
  OneDriveに同期される）。直近14日分を残す。件数が急に0件になったら確認待ちの一覧で知らせる。
- **弱い点**: Artifactのデータベースは公式の公開文書に記載が無い機能。使えなくなったら、最新のバックアップを材料に記録へ移す。
