# ユーザーへの確認依頼

ユーザーへ確認・判断を求めるときの取り決め。テストの欠陥の要確認（`testing.md`）、並行実行の
判断待ち（`orchestration.md`）、タスクの保留など、**どこから出る問いもこの形で出す**。

## 聞くかどうかを決める

- **外から見える振る舞いが変わる** → 聞く
- **変わらない** → 聞かない。**報告して直す**（実装のdocstringやdocsが既に意図を書いているなら、
  それに合わせるだけ。決定はもう済んでいる）

**中途半端に聞いてから勝手に進めない。** 構造と判定したなら最初から聞かない。聞いたなら
答えを待つ。

## 書く順

読み手が「で、何を選ぶのか」へ辿り着くまでの距離が短くなる順で書く。

1. **利用者への約束を1文で。** 何を守るための話かを最初に置く。
2. **問題が顕在化する場面を1つ。** 抽象論にしない。利用者が何をして、何が表示され、実際は
   何が違うか。**起きない場面も1行添える**——書かないと、読み手が自分で境界を探しに行く。
3. **選択肢と、各選択肢で利用者に何が起きるか。**

docstringの引用・実装の経緯・自分がどう判断したかは、**聞かれてから出す**。

## 背景を知らない人が、その1問だけで判断できるように書く

読み手はタスクの経緯を知らない。「番号で言われても背景を知らないから判断できない」。1問には
次を必ず入れる:

- 何の画面・機能の話か（利用者から見える言葉で）
- いまどうなっているか
- なぜ決める必要があるか
- 各選択肢で利用者に何が起きるか

**設問の中に中身を書く。**「この食い違いはどこがズレているか」では、読み手が前の段落へ戻る
ことになる。設問だけを読んで答えられる状態にする。

**画面の見た目・情報量に関わる判断は、変更前と変更後の実画面かモックを添える。** 文章だけでは
「出したらどうなるか」が判断できない。

## 製品の言葉で書く

- 関数名・引数名・「配列」「列」といった**実装の語を使わない**。
- **固有名詞を使わない**（「環八」ではなく「片側2車線の幹線道路」——どこに住む読み手にも同じ絵が
  浮かぶ語を選ぶ）。
- **タスク番号・内部の識別子に頼らない。** 番号は参照として末尾に添えるだけにする。画面に出ない
  内部の話なら、そう明記する。

## 選択肢

- **自分の領分を選択肢に入れない**（例外の出し方・書き方・どう直すか）。
- **選択肢の文面と、実際に当てる作業を一致させる。** 書く前に、その作業が何を変えるかを確かめる。
- 推奨を先頭に置き、理由を添える。

## 届け方

- **選択式の質問（`AskUserQuestion`）で出す。** 1回に4問まで、各2〜4択。推奨を先頭にして、
  ラベルに「（推奨）」を付ける。会話に書くだけにしない。
- **並行実行中の判断待ちは、ためておき、ユーザーが「判断待ちはある？」と聞いたときにまとめて
  出す**（`/orchestrate:asks`）。こちらから催促・通知しない。**推奨案を自動で採用しない。**
- **判断待ちは他の作業を止めない。** 判断が要るタスクの、その項目だけを保留し、残りを進める。

## 実測

この形は8往復かけて直された結果である。外したのは順に——選択肢の文面と実際の作業が違う
（「型で通らなくする」と書いたが型注釈は既に済んでおり何も変わらなかった）／「消す」を2つ並べる
（違いは例外の出し方で、自分が決めることだった）／誰が決めるべきかを示さずに聞く／軸を示した
直後に承認を取らず進める／3者の主張を自分の要約で書く／設問を抽象語で書く／「データ」「待ち」が
何を指すか曖昧／実装の語で書く／固有名詞を使う。

並行実行の第1回（[T1049](../records/tasks/T1049.md)）では、判断待ちをタスク番号と短い問いだけで
出し、「番号で言われても背景知らないから判断できない」「出したらどうなるか実画面あるいはモックで
示して」と差し戻された。
