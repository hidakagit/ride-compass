# ユーザーへの確認依頼

ユーザーへ確認・判断を求めるときの取り決め。テストの欠陥の要確認（`testing.md`）、並行実行の
判断待ち（`orchestration.md`）、タスクの保留など、**どこから出る問いもこの形で出す**。

## 聞くかどうかを決める

- **外から見える振る舞いが変わる** → 聞く
- **変わらない** → 聞かない。**報告して直す**（実装のdocstringやdocsが既に意図を書いているなら、
  それに合わせるだけ。決定はもう済んでいる）

**中途半端に聞いてから勝手に進めない。** 構造と判定したなら最初から聞かない。聞いたなら
答えを待つ。

## 書く順

読み手が「で、何を選ぶのか」へ辿り着くまでの距離が短くなる順で書く。

1. **利用者への約束を1文で。** 何を守るための話かを最初に置く。
2. **問題が顕在化する場面を1つ。** 抽象論にしない。利用者が何をして、何が表示され、実際は
   何が違うか。**起きない場面も1行添える**——書かないと、読み手が自分で境界を探しに行く。
3. **選択肢と、各選択肢で利用者に何が起きるか。**

docstringの引用・実装の経緯・自分がどう判断したかは、**聞かれてから出す**。

## 背景を知らない人が、その1問だけで判断できるように書く

読み手はタスクの経緯を知らない。「番号で言われても背景を知らないから判断できない」。1問には
次を必ず入れる:

- 何の画面・機能の話か（利用者から見える言葉で）
- いまどうなっているか
- なぜ決める必要があるか
- 各選択肢で利用者に何が起きるか

**設問の中に中身を書く。**「この食い違いはどこがズレているか」では、読み手が前の段落へ戻る
ことになる。設問だけを読んで答えられる状態にする。

**画面の見た目・情報量に関わる判断は、変更前と変更後の実画面かモックを添える。** 文章だけでは
「出したらどうなるか」が判断できない。

## 製品の言葉で書く

- 関数名・引数名・「配列」「列」といった**実装の語を使わない**。
- **固有名詞を使わない**（「環八」ではなく「片側2車線の幹線道路」——どこに住む読み手にも同じ絵が
  浮かぶ語を選ぶ）。
- **タスク番号・内部の識別子に頼らない。** 番号は参照として末尾に添えるだけにする。画面に出ない
  内部の話なら、そう明記する。

## 選択肢

- **自分の領分を選択肢に入れない**（例外の出し方・書き方・どう直すか）。
- **選択肢の文面と、実際に当てる作業を一致させる。** 書く前に、その作業が何を変えるかを確かめる。
- 推奨を先頭に置き、理由を添える。

## 届け方

- **問いは仕掛中のダッシュボードにkind `保留`で置き、ユーザーはページのボタンで答える**（置き場と1件の形は下の
  「仕掛中のダッシュボード」節）。置く側が最初から、`text`を1行の題名（問いそのもの）、`options`を選択肢（各2〜4択、
  推奨は`recommend`）、`detail`を上の書き方の本文にして書く。会話に書くだけにしない。
- チャットでその場で聞くときは選択式の質問（`AskUserQuestion`。1回に4問まで、各2〜4択、推奨を先頭にしてラベルに
  「（推奨）」）で出してよいが、同じ問いを先にダッシュボードへ置き、答えはその件の`answer`へ書く——置き場とページの
  ボタンが正である。
- 置かれた問いがその1件だけで判断できない形なら、答えを求めずに、書いた側（担当がいなければ司令塔）へ書き直させる。
- こちらから催促・通知しない（答えを待つ問いはページの「あなたへ」に出る）。**推奨案を自動で採用しない。**
- **判断待ちは他の作業を止めない。** 判断が要るタスクの、その項目だけを保留し、残りを進める。

## 実測

この形は8往復かけて直された結果である。外したのは順に——選択肢の文面と実際の作業が違う
（「型で通らなくする」と書いたが型注釈は既に済んでおり何も変わらなかった）／「消す」を2つ並べる
（違いは例外の出し方で、自分が決めることだった）／誰が決めるべきかを示さずに聞く／軸を示した
直後に承認を取らず進める／3者の主張を自分の要約で書く／設問を抽象語で書く／「データ」「待ち」が
何を指すか曖昧／実装の語で書く／固有名詞を使う。

並行実行の第1回（[T1049](../records/tasks/T1049.md)）では、判断待ちをタスク番号と短い問いだけで
出し、「番号で言われても背景知らないから判断できない」「出したらどうなるか実画面あるいはモックで
示して」と差し戻された。

## 仕掛中のダッシュボード

タスクにまつわる情報は、次の3か所に役割を分けて置く。同じ事実を2か所で持たない。

| 置き場 | 役割 | 持つもの |
|---|---|---|
| 台帳（`docs/improvement-plan.md`） | 承認されたタスクの未完了の正本一覧 | タスクがあること・題名・規模・トリガー・範囲の移り先。判断待ち・決定・進み具合は書かない |
| 記録（`docs/records/tasks/Txxx.md`） | 全タスクの記録の正本。維持しない（書いた時点で正しければよく、後から直さず書き足すだけ） | 背景・方針・問い・ユーザーの答え・確認の結果・検証。タスクのコミットと一緒に入る |
| 仕掛中のダッシュボード（非公開のArtifact） | 仕掛中のタスクのうち人が関わるもの（問い・操作・改善案・起票案・前提の一覧・答え）の置き場 | 下のとおり。正本ではない |

進め方の状態——誰が何を進めているか・担当の状態・`heavy`の枠・スロットの印——は、手元の`.git/orchestration/`にある状態の表
（`board.json`）とロックの記録が正本で、ダッシュボードには写さない（写すと重複になる）。

**仕掛中のタスク**は、次のどれかに当たるもの: 担当・ユーザーのセッションが進めている／ユーザーへの問い・操作のお願い・
改善案が出ていて、答えがまだ記録に入っていない（コミットの前に答えが出たタスクも、答えが記録に入るまでは仕掛中）。

**ダッシュボード**: https://claude.ai/artifact/E8G458My7xPA8RpbkU3RWF のデータベース（collection `pending`）。手元のセッション・
担当（サブエージェント）・クラウドのセッションのどこからでも`ArtifactData`で読み書きできる（2026-09-24に3つとも実測）。
**人の手を待つものの置き場はここだけ**で、記録には置かない（道具も記録から拾わない）。ページは2つのタブで出す:
「あなたへ」（反映待ち・送った取り込み待ち・答えを待っているもの）と「すべて」（仕掛中のタスクごとの全件）。誰が進めているか等は
出ない（状態の表が持つ。手元で`python scripts/orchestrate.py status`）。ページはclaude.aiのサイドバーにピン留めしてあり、
Claude Codeでは`/artifacts`からも開ける。

- **1件＝仕掛中のタスクの件名（下記）、そのタスクへの1つの問い・お願い・改善案・答え、または1つの起票案**。doc_idは`<タスク番号>-<短い名前>`
  （起票案は番号がまだ無いので`起票案-<短い名前>`）。項目は`task`（タスク番号。台帳に行があること。起票案は空）・
  `kind`（`保留`＝決めてほしい問い／`操作`＝実行してほしい操作／`改善案`＝入れてよいか決めてほしい改善／
  `起票案`＝入れてよいか決めてほしい新しいタスク／`決定`＝問いを経ずに出た、タスクの中身への指示。ほかに下の`件名`・`前提`）・
  `text`（**1行目が題名**。問いなら問いそのもの、操作なら何をするか。置く側は1行の題名だけにし、細部は`detail`へ）・
  `options`（問いの選択肢。1つ1行の文字列の並び。推奨があれば`recommend`にその番号（1始まり））・`detail`（題名と選択肢の外の
  本文。問いはこの文書の書き方で背景・各選択肢で何が起きるかを、操作はそのまま実行できる手順を、起票案は題名・規模・背景・
  なぜ既存のタスクに入らないかを書く。text・options・detailを合わせて、その1件だけで分かること）・
  `answer`（ユーザーの答え。出るまで空。ページのボタンで問いに答えると`(n) <選択肢>（日付）`の形で入る）・
  `comments`（ユーザーのコメント。下記）・`answered_at`・`sent_at`・`taken_at`・`taken_note`（下の「反映の流れ」）・`source`（書いたセッション・
  担当）。日時は手で入れず、表の`updatedAt`を使う（`sent_at`・`taken_at`は書いた側がその時刻を入れる）。
  台帳にあるタスクの題名・規模は書かない（台帳から引く）。
- **ページでの見え方**: 各件は題名（`text`の1行目）を太字の1行で出す。答えを待っている問いは、選択肢を畳まずに題名の下へ
  出す（答えのボタンは番号だけなので、選択肢の文を見ながら押せるように）。本文（`text`の2行目以降と`detail`。改行はそのまま）
  と書き手は、題名を押すと開く。答え済みの件は選択肢も畳む。
- **コメント**: 前提以外のどの件にも「コメントを書く」があり、送るとその件の`comments`に`{text, at}`（`at`はISOの時刻）が
  1件足される。件を書いた側が読んで件を直し、直したら`comments`を外す（`ArtifactData`の`update`で
  `{"comments": {"__delete__": true}}`）。
- **反映の流れ**: 答え（またはコメント）を付けた件は、まず「あなたへ」の**反映待ち**に残る（答えを付けた時刻は
  ページが`answered_at`に書く。答え・コメントの新しい方が`sent_at`より新しければ反映待ち——一度送った件に、あとから答えても
  反映待ちに戻る）。ユーザーが「Claude に反映を頼む」を
  押すと、反映待ちの件だけを Claude へ送り、ページがそれぞれに`sent_at`（送った時刻）を書く——**送った・取り込み待ち**になる。
  起こされたセッションは、`sent_at`があって`taken_at`がそれより前（または無い）件**だけ**を読んで扱い、扱ったら`taken_at`
  （扱った時刻）と`taken_note`（どう扱ったか1行。例: 「担当 W-fix へ伝えた」「振り出し待ちに積んだ」）を書く——**取り込み済み**に
  なり「あなたへ」から消える。答えを読み直して二重に扱わないための印で、件を持つセッション（司令塔・T1001 のセッション等）が
  自分の件に書く。答えを取り消すと`sent_at`も外れる。
- **件名**: 仕掛中のタスク1つにつき1件、kind `件名`を持つ。形はコミットの件名と同じ`T1234: <何が変わるか（利用者・運用から
  見た結果）>`。ダッシュボードのページは、タスクごとにこの件名を見出しにし、その下に問い・操作・改善案を並べる。
  そのタスクをコミットするときは、この件名をそのままコミットの件名にする。件名は途中で変わってよい（範囲が変わったら
  書き直し、コミットの時点の件名とそろえる。改善案・起票案も、承認の前後で題名が変わってよい）。コミットしたら件名の1件も
  問い・答えと一緒にダッシュボードから消え、以後はコミットの件名として履歴に残る。**台帳の題名（タスクの名前。起票のときに
  決まり、変えない）とは別物**である。起票案の1行は台帳に入る予定の題名。
- **手動タスクの前提の一覧もここで持つ**（ユーザーが手動で進めるタスクの前に済ませるタスク。前提に入れる基準は
  [orchestration.md](orchestration.md)「ユーザーが手動で進めているタスク」節）。足す・外すはダッシュボードで行い、
  記録を書き換えるコミットにしない。1件の形: 前提1つにつき1件、kind `前提`・`task`は手動タスク・`text`は前提のタスク番号で
  始め、そのあとに短い名前を書く（例: `T1068 ピンチでページ全体が拡大する`）。前提に入れた理由は`detail`へ。
  doc_idは`<手動タスク>-prereq-<前提のタスク>`。`answer`は使わない。前提のタスクを取り込んだら、その件を消す。
- **問いは、記録とダッシュボードの両方に置かない**: 仕掛中のタスクへの問いはダッシュボードに置き、答えが出たら、そのタスクの
  コミットで問いと答えをまとめて記録へ書き、ダッシュボードから消す。
- **着手するときは、記録とダッシュボードの件を合わせて読む**: 記録（`Txxx.md`）を土台にし、そのタスクのダッシュボードの答え・
  決定を上に足す。食い違ったら日付の新しい方を黙って採らず、問いとしてダッシュボードに置く。台帳の行は題名と規模だけで、
  中身を持たない。
- **閉じたタスクに残った問いに答えが出たら**: 答えで作業が生まれるなら、そのタスクを開け直して（仕掛中にして）作業の
  コミットで記録へ移す。作業が生まれない（見送り等）なら、下の「記録だけを変えるコミットの例外」の`記録: 答え …`で移す。
- **ダッシュボードにしか無い事実は、コミット前の件名と、記録へ移すまでの問い・答えと、承認前の起票案と、手動タスクの前提だけ**。
  誰が何を進めているか・担当の状態・`heavy`の枠・スロットの印・進め方の指示（待つ・続ける・順番。状態の表とロックの記録が持ち、
  記録にもコミットにもしない）・台帳にあるタスクの題名（台帳）は写さない。
- **見るのも答えるのもページ**: 問いには選択肢の番号のボタン、操作の報告と改善案・起票案の承認には「済」「承認」「見送り」の
  ボタンがある。チャットで返してもらった答えは、聞いた側がその件の`answer`へ書く。
- **バックアップ**: 1日1回、全件を`.git/orchestration/pending-backup/<日付>.json`へ書き出す（コミットしない。作業フォルダごと
  OneDriveに同期される）。直近14日分を残す。件数が急に0件になったとき、閉じたタスクに答え・件名・前提が残って
  いるとき（記録への移し忘れ・消し忘れ）、記録の無いタスクの件があるときは知らせる。書き出しは
  `python scripts/orchestrate.py pending-backup --pending <dir>`（残す日数と知らせもここ）、起動はClaudeデスクトップの
  ローカルの予約タスク（ファイルを書くので、手元の機械で動くものに限る。アプリが開いていて機械が起きている間だけ動き、
  寝ていた日は起きたときに1回だけ追いつく）。知らせは`pending-backup`が出し、終了コード1で予約タスクの結果に残る。
- **弱い点**: Artifactのデータベースは公式の公開文書に記載が無い機能。使えなくなったら、最新のバックアップを材料に記録へ移す。

### 起票は承認制

台帳に載るのは、ユーザーが承認したタスクだけである。振り出し・着手の対象にできるのも台帳にあるタスクだけ。

1. **新しいタスクが要ると分かったら**（担当の報告・監査・`/review`・ユーザーとのやり取り・作業中の気づき）、まず既存の
   タスクに属するかを見る。**属するなら、そのタスクへの追記で済ませ、起票案にしない**——いま進めているタスクのコミットが
   あればそれに含める。無ければ（`/review`・会話から出たもの）そのタスクの件としてダッシュボードにkind `改善案`で置き、
   承認されたらそのタスクを仕掛中にして、次のコミットで記録へ移す。
2. 属さなければ、kind `起票案`としてダッシュボードに置く（題名・規模とその根拠の1行（CLAUDE.md「規模の札」）・背景・
   なぜ既存のタスクに入らないか）。
   **番号はまだ振らない**（`scripts/new_task.py`を実行しない）。
3. ユーザーがページのボタンかチャットで承認したら、その時点で`scripts/new_task.py`で番号を振り、台帳の行と記録の
   雛形を作る。承認された分を`--`で区切って1回で渡すと、道具が下の`台帳: 起票 …`の1コミットにしてmasterへ入れる。
   入れたらダッシュボードから消す。
4. 見送りは、ダッシュボードから消すだけ（番号も記録も作らない）。

レビューの指摘（`/review`・`/code-review`）も同じ振り分けで置く: 既存のタスクに属するならその改善案、属さなければ
起票案。`/code-review`はこのプロジェクトの決まりを知らず一覧を出すだけなので、回したセッションが一覧を読んで置く。
見送る指摘は、理由を添えてチャットで伝える（`/review`の見送りは周期レビューのタグの注釈に残る）。

### 記録だけを変えるコミットの例外

記録（`docs/records/`）だけを変えるコミットは作らない（CLAUDE.md「1タスク=1コミット」）。例外は次の2つだけで、どちらも
決まった件名の1コミットにする。

- **`台帳: 起票 T1090・T1091`**: 起票の承認の1回のやり取りで承認された分に番号を振り、台帳の行と記録の雛形を入れる
  （上の「起票は承認制」の3。`scripts/new_task.py`が作る）。
- **`記録: 答え T1082・T1083`**: 実装のコミットが入ったあとに出た答え・確認の結果のうち、作業が生まれないもの（見送り・
  ユーザーの操作や目視の確認が済んだこと等）をまとめて記録へ移す。閉じたタスクに残った問いへの答えも、実装済みで確認だけが
  残っていたタスクを閉じるときも同じ（答えで作業が生まれるなら、そのタスクを開け直して作業のコミットで移す）。
