# 修正の原則

CLAUDE.md「修正の原則」から参照される詳細版。指摘・不具合を直すときは、症状ではなく欠陥を直す。
直した結果が次の指摘になるのは、次のどれかを飛ばしたときである。

## 直し方

- **範囲は性質から導く**: 直す対象を「症状が出た場所」で決めず、「その欠陥を成立させている
  性質」で決め、その性質に当てはまる箇所を機械的に列挙してから直す
  （導出の考え方は[design-principles.md](../architecture/design-principles.md)構造仕様12と同じ）。
- **機械の出力をそのまま処置へ繋げない**: grep・AST・参照カウントが出した一覧は
  **候補**であって判定ではない。処置（削除・改名・撤去）へ移す前に、**その機械が見て
  いないもの**を1つずつ確かめる。とくに「参照0だから消してよい」は成り立たない——
  フレームワークが規約として読む口（`app/**/route.ts`の`GET`/`POST`、`layout.tsx`の
  `metadata`/`viewport`）、文字列やパスで解決される参照、走査範囲の外にあるもの
  （`frontend/e2e/`等）は、どれも参照0に見える。**名前の除外リストで逃げない**——
  除外リストは誤検知を認めた印であり、代わりに「規約として読まれる場所にあるか」という
  位置で判定する（実例は[T1001](../records/tasks/T1001.md)）。
- **検証は別の入力で行う**: 修正を書く根拠にした入力で測り直しても証拠にならない。とくに
  **検査の側を緩めて「検知0件になった」ことは、その検査が直った証拠にならない**——緩める前に
  検知できていた既知の1件が今も検知されることを、別途示す。
- **緩和は影響を測ってから入れる**: 除外・許可リスト・判定条件のゆるめを足すときは、それが
  検査対象から外す件数と母集団に対する割合を実測し、タスクの issue へ書く。測らずに入れた
  緩和は、直した件数より多くを静かに見逃す。
- **「実装した」ではなく「効いている」を確認して完了にする**: 新設した検知器・ガード・
  表示は、わざと壊した入力を1件通して落ちる/出ることを見てから完了扱いにする。
  **手順・規約を新設したときも同じで、それに従って作った成果物を1件読んでから確定する**
  ——規約は検知器より波及が大きく、守られるほど同じ歪みが量産される。
- **見積もりとずれたら、全体の結論より先にずれを報告する**: 実測が見積もりと違ったら、
  それを結論の補足へ回さない。反する内訳を落として全体を「改善」とまとめると、次に同じ
  場所を測るまで誰も気づけない。
- **性能は利用者から見た単位で測る**: 部品の計測（関数1本・木1本）は原因の切り分けにだけ
  使い、それで全体を判断しない。利用者が通る経路が複数あるなら、都合の良い側だけを測って
  結論にしない。

## 消す・残す

- **置き換えではなく削除を既定にする**: XをYへ置き換えるなら、「Xをただ消せない理由」を
  先に言えること。言えないなら消す。
- **変更のたびに「これで何が死んだか」を測り、同じコミットで消す**: 参照が0になった
  フィールド・関数・分岐・テストは、その変更が作った残骸である。次のタスクへ回さない。
- **いま消したものを見張るテスト・アサーションを足さない**: 消えたことは検査ではなく、
  変更そのものが示す。守りを足すのは、消していないものに対してだけ。
- **本番から外れたものを「残す」判断を自分でしない**: 1本化・置き換えの改修で、
  置き換えられた側（旧実装・フォールバック・既定値）を残す理由として「回帰テストの
  オラクルにする」「既存を壊さないため」「後で消す」を挙げない。**残したいと思ったら、
  残す理由と、いつ通るのかを添えてユーザーへ問う**——判断はユーザーのもので、
  こちらで決めてコメントに書いて流さない。残したものは本番から到達しないぶん誰も直さず、
  そのテストまで一緒に保守対象として残り続ける（実例は[T956](../records/tasks/T956.md)）。
  **置き換えた側が本番から呼ばれなくなったら、そのテストも同時に消す**——デッドコードの
  テストは保守対象ではない。

## 書かないテスト

- **宣言をそのまま書き写すテストを作らない**: レジストリ・カタログ・定数に
  ベタで書いてある値を、テストでもう一度書いて突き合わせるのは、同じ literal を2箇所へ
  置いているだけで何も守らない（「この材料は登録されていない」「この材料の値式はNone」
  「生成された集合 == 同じ内包表記」など）。宣言に対して書いてよいのは、**導出した母集団
  すべてに対する不変条件**だけ（「全材料が空でない説明文を持つ」のように、要素が1つ増えた
  ときに発火するもの）。手で名指しした数件に対する検査は母集団が導出されていないため
  書かない（設計原則 構造仕様12）。
- **「等価であること」だけを確かめるテストを残さない**: 新旧2実装の出力一致を見る
  テストは、どちらが正しいかを誰も保証していない。残すのは**入力に対するあるべき値**を
  書いた期待値テストで、それを**生きている1本の実装へ当てる**。移行が終わったら等価
  テストは消す（実装ごと消えるので、等価テストだけが残ることはない）。

## 報告と段取り

- **完了報告には実装の増減を添える**（聞かれてから出さない）。文書・テストと分けて数える
  （`python scripts/review_checks.py change` の出力を写す。手で数えない）。
- **新しい種類の成果物は、置き場と命名を先に決める**: 既存の慣習が無い所へ1本目を置くとき、
  書き始める前に決めて合意する。後から移せるが、決めずに進めると次に足す人も散らかす。
  分ける軸は「何を守るか」ではなく**それが何を読むか・何に属するか**
  （例: テストは [testing.md](testing.md)「ソースを読む検査は、専用ディレクトリへ置く」）。
- **段階を別タスクへ切り出すときは、切り出す先の中身を具体化してから切り出す**: 「あとは
  〜するだけ」と見えている状態で切り出さない。見えていないぶんは、切り出した瞬間に
  検討されないまま確定する。

## 検知器を足す条件は厳しい

検知器（`scripts/review_checks.py docs`）はプロジェクト全体への一律チェックとして自動実行され、
**実行タイミングも走査範囲もこちらで選べない**（CI）。したがって足してよいのは、
**どの文脈でも絶対に正しいと保証できるものだけ**である。次のどれかに当たるものは足さない:

- **許可リストが要る**——許可リストは誤検知を認めた印。「この綴りは外部の語彙だから除外」が
  必要なら、その検査は事実を見ていない
- **実装そのものを検査対象にする**（コードの書き方・import規則・型・レイヤーの不変条件）
  ——実装側の道具（lint・型検査・テスト）が持つ。検知器が実装の姿を知ろうとすると写し
  （スナップショット・定数表）を抱え、実装が変わった瞬間に黙って死ぬ
- **保存した過去の値と比べる**——それは検査ではなく報告

**基準を満たさないものを足した代償は大きい。** 撤去には文書・台帳・手順書の広範な
作り直しが伴う（実例は[T986](../records/tasks/T986.md)）。**思いつきは issue に起こして人が採否を決める**ことにし、検知器にはしない。
自己申告のチェックを文章のルールとして足すこともしない。その場合も
**実行したコマンドと観測値をコミットメッセージへ書く**（「確認した」とだけ書かない）。
上の3項目は、検知器の候補を実測したうえで届かないと判定して置いたもの
（数字と判定は[T798](../records/tasks/T798.md)）。

## 人が見るしかないもの

文書の整合は`scripts/review_checks.py docs`がCIで常に全件を見るが、次の3つは検査器にできず人が見る。
どれも実行したgrepと観測値をコミットメッセージへ残す。

1. **共有フィールド・パターン・形（データや文書の書式・契約）を変更/廃止したとき**: 変更前のフィールド・パターンを
   リポジトリ全体でgrepし、①取り残された消費者がいないか、②**残る消費者が変更後の契約と
   両立するか**——従来その契約が無いことを前提に外側から別の値を与えていた箇所は、
   直した側が正しく動くぶんだけその指定が静かに巻き戻る——の両方を確認する。③**前の形の実物が残るなら、
   読む側に前の形を残さず、実物を今の形へ一度で直す**（読み方が2つ並ぶと経路が2つになる。設計原則 構造仕様8）。
   正本の規則は1つで紛れが無いもの（許す行を列挙し、それ以外は形に合わないとする）にし、直す対象はその規則から機械的に
   導く（新しい規則で読めない実物＝対象。別の見分け方を持たない）。直し方は推測で書かない——その形を作った・受け付けた側の
   コードの規則をそのまま使い、対象の全件を前の読み方と直した結果に通して一致を確かめ、直した結果が新しい規則で読めることも
   確かめる。直した後に前の形が新しく作られないことも確かめる。直す道具は、流した
   後に消すタスクを紐づける。
2. **タスクを閉じる（completed で閉じる）とき、issue に未実施の段階・派生が残っていないか**: 「見送り」
   （今後もやらない確定判断）以外が残るなら、**元タスクを閉じずに**段階（sub-issue）にするか、保留へ動かして
   残りと再開の条件を書く。別の issue へ切り出すのは、残りが元タスクと別の時機で進むと分かっているときだけにする。
   **範囲外で見つけたものも同じときに見る**。1件ずつ、行き先（既存の issue へのリンク・新しく起こした issue）か
   直さない理由を添えてから閉じる。
3. **関数・ファイル・設定項目を撤去・改名するとき、それを前提にしたものが取り残されないか**:
   探す範囲を自分で決めない。`python scripts/review_checks.py leftovers`（置き場を読むので`GH_TOKEN`に
   `FLOW_BOT_TOKEN`の値）が、master との差分から消した・名前を変えた名前と、それがまだ当たる所（記録を除く
   リポジトリ全体・置き場のラベルの説明・開いた issue の本文とコメント）・消したコメント行・置き場に無いラベルを
   候補として出す。候補の1件ずつに、次の処置か「別の意味なので残す」を Pull Request の本文に書く。
   - **そこにしか無い判断**: 撤去した差分の
     コメント行（`leftovers`の「消したコメント行」）を
     [comments.md](comments.md)の判定木へ1件ずつ通す。**コードの撤去と同じ操作で
     まとめて落とさない**——参照が0かはコードの判定で、文には効かない。
     横断的な判断が他に無ければ`docs/modules/*.md`へ昇格してから消す。
   - **開いているタスク**: 撤去・改名した名前が当たった開いている issue（`leftovers`の「名前が当たった所」）へ、
     前提が変わったことをコメントで書く。
   - **生き残った型と設定**: 値を作る経路を減らしたら、残った型の既定値・任意型（`| None`）・
     設定項目を組み立て箇所と読み手に突き合わせ、もう来ない値・読み手のいない項目を同じコミットで消す。
