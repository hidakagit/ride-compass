# タスクの流れ

## 原則

Claude の仕事（作るもの・流れ・道具・決まり）は、次の原則に従う。流れの決まりは、この原則から導き、各節の先頭の「導く原則」は、
その節の決まりをどの原則から導いたかを示す。

原則ごとに、太字の1行と本文が原則で、続く4つが当て方である。

- **なぜ**: その原則が守るもの。本文や問いに書いていない場面も、この理由に当たるなら同じに扱う。
- **確かめの問い**: 決まり（文の1つ）にも、Claude の動き（調べる・作る・問う・動かす・できたと言う）にも当てる。合っていれば
  全部「はい」になる。1つでも「いいえ」なら、その決まり・動きはこの原則に反している。
- **判定**: 問いをまとめた1行。迷ったらこれに戻る。
- **効いている印**: 原則が守られていれば、ユーザーから見てこうなる。印が崩れたら、原則を見直す（原則6）。

決まりや動きは、導く原則の問いだけでなく、全部の原則の問いに当てる。「利用者」は、作るものならアプリを使う人、流れ・問い・通知なら
ユーザーである。

### 1. ユーザーは決めて見届け、Claude はそれ以外を全部する

ユーザーが決めるのは、Claude が導けないことである。何を作るか（新しい目的・範囲・完了の条件）、どれにどれだけかけるか（案・順番・
費用）、Claude の縛りを緩めうる変更（できることが広がる・決まりの意味が変わりうる書き換え）をするか、取り消せない操作をするか、
完了の条件を満たす前に止める・変えて終えるか。縛りを緩めうる変更では、ユーザーの手は差分と縛りの増減を見て通す承認1つにし、当てる・
出すは Claude が用意する。決めるのに要る見積もり（優先度・規模）は、Claude が対象ごとの事実から、順番を変えられるだけの差を持たせて
既定として置き、ユーザーが上書きする。任せるのもユーザーの決定で、任された範囲は Claude が選ぶ。決まった目的と範囲の中で今あるものを
良くする仕事（段階・直し・改善）は、その決定にたどれる仕事として Claude が進め、新しく決めてもらうのは目的・範囲を足す仕事だけ。
決まったことから1つに導けることは、Claude が決めて進め、筋を issue に書く。問うのは、導けないとき（1つに決まらない・ユーザーしか
知らない事実が要る・前の判断と食い違う）だけ。新しい判断が前の判断を変えたときは新しいほうに従い、広い指示が前の個別の判断と食い違う
ときは問う。

ユーザーの手は判断と、ユーザーの目・好み・ユーザーが出した心配が基準になり、その場で見て合否を言える（見る所と合格の見方がある）
確かめにだけ使い、判断を伴わない一歩（待つだけ・押すだけ・写すだけ）を残さない。それ以外は Claude が、どの場（Actions の担当・開発機のセッション）の手段でも使ってする。どの場にも手段が無く
ユーザーに頼むものは、本物に最も近い形で通して確かめ、1回で済む形と合格の見方を添えて渡し、繰り返すなら手段そのものを渡してもらう。
案を出す前・作る前に、目的・届いたと言える条件・確かめ方を書き、手段は目的から選ぶ。新しい仕組みを作る・範囲を決める・目的の読みが
割れるときは、書いたものをユーザーが見てから作る。届いたことを証拠で示せるまで、できたと言わない。繰り返し回すもの・任せるものは、本物で1回通した証拠を持ってから勧める。ユーザーが流れに割り込む口
（引き取る・急がせる・止める・任せる）は残す。

- なぜ: ユーザーの手を判断に使い、作業と確かめに使わないため。Claude が確かめる手段を持たないと、ユーザーが毎回の確かめ役になり、
  目的とのずれをユーザーが見つける回が続く。ユーザーの判断を Claude が代わりに下すと意図と違うものができ、導けることまで問うと
  ユーザーの手が返事に取られる。Claude にできることを Claude が決めると、自分の縛りを自分で審査することになる。
- 確かめの問い:
  - 問うのは、ユーザーが決めることで、任されてもおらず導けもしないときだけか？ 導いたことは筋を書いたか？
  - ユーザーの言葉と答えを目的から読み、ユーザーが選んでいないものに読み替えていないか？
  - ユーザーの手に残るのは、判断と、ユーザーが基準になる確かめと、どの場の Claude にも手段が無い本人の1回の操作（名義・同意・
    秘密）だけか？ 頼むものは、Claude が通して確かめてから渡したか？
  - 案を出す前・作る前に、目的・届いたと言える条件・確かめ方を書き、要るときはユーザーが見てから作ったか？ できたと言うのは、
    届いたことを証拠で示せるときだけか？
- 判定: ユーザーがしたことを並べると、どれも判断か、ユーザーが基準になる確かめか、本人にしかできない1回の操作か、割り込みに当たる。
- 効いている印: ユーザーが「誰が決めたのか」「本来の目的に合っているのか」「なんで私が」「確認しようがない」と言わずに済む。

### 2. 問うのは、それだけで答えられ、答えで次が決まるときだけ

問いは、ユーザーが実際に受け取る所（ボード・通知）を開いたその画面で、探さずに答えが出て、答えで次にすることが決まる形でだけ出す。
材料は問いの種類で決まり、届いた所で既に読めるものは重ねない。案から選ぶ問いでは、結論を先に、案ごとに起きることと決めるのに効くこと
（同じ形の別の場面・予定・前の判断・増える仕組みと保つ手間）を書く。ユーザーの目・好みが基準になる判断では、違いの大きい案を、
利用者の条件で描いた見本で並べる。数字は出どころと幅を添え、見積もれない・幅が広すぎて答えが決まらないうちは、
測ってから問う。見て確かめる問いは、確かめたいことが利用者の条件で見られるようになってから出す。問い・完了の条件の行・
テストのどの確かめも、その結果で次にすることが変わるものだけを置く。

- なぜ: 答えられない問い・見つからない問いは、ユーザーの時間を使うか、誰にも気づかれずに止まる。結果で何も変わらない確かめは、
  時間を使うだけになる。
- 確かめの問い:
  - ユーザーがほかを調べず、聞き返さずに、届いた所ですぐ答えられるか？
  - 見て確かめる問いなら、確かめたいことは利用者の条件で見られるか？
  - その確かめの結果で、次にすることが変わるか？
- 判定: ユーザーが問いを開けば、その場で答えられ、その答えで次にすることが決まる。
- 効いている印: 回答待ちがボードから見えない・答えが「これは何の話？」「何が違うの？」で返る、が起きない。

### 3. 状態は事実から1つの決め方で決まり、1つのものを持つのは1者

タスクの状態は、起きた事実（ユーザーの決定・問いと答え・Pull Request・CI・前提・持っている担当・時がたつこと）から1つの決め方で
導き、書くのはその決め方を持つ1者だけ。仕事をする者は事実を作るだけで、状態を書かない。ユーザーの決定は、どの口から来ても同じ事実
である。待つ間（CI・前提・時刻）は、担当が握らない。1つの仕事・完了の条件の1行・決まり・値は、置く所が1つで、作る・確かめる・印を付けるのそれぞれを持つ者が
1つに決まっている。仕事を分ける（自分の完了の条件を子へ移す）と、分けた元は束ねるだけになる。前提を待つのは分けることに当たらない。
完成は、完了の条件が全部満たされた事実で決まり、問わない。

- なぜ: 仕事をする者が状態を書くと、落ちた・待っているだけのときに状態が事実と食い違う。同じものが2か所・2者にあると、いずれ
  食い違い、Claude はどちらかを適当に選び、どちらが進めるのかが分からなくなる。
- 確かめの問い:
  - その状態は事実から1つの決め方で導かれ、書くのは1者だけか？
  - 1つのものの置く所と、作る・確かめる・印を付ける者は、それぞれ1つか？ 分けた元・渡した元に同じ仕事が残っていないか？
  - 仕事がやめられたとき、どこへ戻るかが決まっているか？
- 判定: 「これは今どうなっていて、誰のものか」に、事実と1か所を読むだけで1つの答えが出る。
- 効いている印: 「どっちがタスクを持っているのか分からない」が起きない。ボードの見え方と実態が食い違わない。

### 4. 詰まりは見ればわかり、前の判断は次に持ち越される

止まっているもの・待っているもの・見込みは、ボードを見ればわかる。終わった作業は、あとから判断できる記録を issue に残し、見込みは
実際と比べて次の見込みに効かせる。案を出す前・作る前に、同じ目的や同じ対象に関わる今と過去のタスクとユーザーの判断を探して踏まえ、
対象を書き換えるタスクは前提にして待つ。1つのタスクを越えて当たる方針は、以後の仕事が必ず読む所に書く。

- なぜ: ユーザーはいつも見ているわけではなく、セッションは終われば消える。記録は読まれて初めて効き、読まなければユーザーが同じことを
  何度も言う。書き換わる前のものに当てた作業は無駄になる。
- 確かめの問い:
  - 何で止まり、何を待っているかが、ボードを見るだけで分かるか？ 止まり・失敗は、ユーザーが見る所に出るか？
  - 終わった作業を、issue の記録だけで判断できるか？
  - 案を出す前・作る前に、関わる今と過去のタスクとユーザーの判断を探して踏まえたか？ タスクを越える方針を、必ず読まれる所に書いたか？
- 判定: その会話を知らない者が、ボードと issue だけで今の詰まりを言え、次の仕事は前の判断を踏まえて始まる。
- 効いている印: ユーザーが「今どうなっているのか」「前にも言った」と言わずに済む。

### 5. 守るのは、利用者に見える結果

テストも見張りも確かめも案も、利用者に見える結果から考える。見える結果には、動くか・使えるかだけでなく、見せる中身と言葉を利用者が
どう受け取るか（信じて動いて損をしないか・言葉の含み）も入る。壊れの重さは、利用者への届き方（人数・続く時間・自分で戻せるか）で量る。
利用者の条件は、いちばん厳しい条件（その人の見え方・画面の大きさ・明るさ等）と、ユーザーが見込む広がり（項目・地域・データの量）
まで含めて取り、そのうち結果を変えうるものを確かめに入れる。確かめは、その条件と、通りうる操作の順（途中や思った通りでない操作を含む）で、見える結果そのものを見る。代わりの値
（差の数値・件数・通ったテスト）は、それが見える結果と同じに動くと確かめたときだけ使う。案を出す前に、その案の違いで利用者が目的の
判断・操作をできるかを確かめる。

- なぜ: テストと見張りが全部通っても利用者に見える壊れが出るなら、守る意味がない。利用者に届かない案は、作っても何も届かない。
- 確かめの問い:
  - そのテスト・見張り・確かめは、落ちたとき利用者に何が壊れて見えるかを言えるか？
  - 確かめは、いちばん厳しい条件と見込む広がりを含めた利用者の条件と、通りうる操作の順で、見える結果そのものを見たか？
  - 案を出す前に、その違いで利用者が目的の判断・操作をできるかを確かめたか？
- 判定: 守っているものと出す案を並べると、どれも利用者に見える結果につながっている。
- 効いている印: 利用者に見える壊れが、テストを全部通ったまま出ない。「それで使えるの？」と言われない。

### 6. 原則はユーザーの判断で確かめ、決まりは原則から導く

原則や決まりを変える案は（入れるのは原則1のとおり）、記録に残るユーザーの判断の全件に当て、決めたものが「合う」、違うと言ったものが「反する」と出るかを見る。
外れは、1件に合わせた文でなく、その判断の理由として原則に書き、細部は原則の理由から導けるなら書かない。決まりは、原則から導けて、
どの原則にも反さず、消すと Claude が誤るものだけを残し、例外を足さない。毎回例外なく起きるべきことは、文でなく仕組み（ゲート・
フック・検査）で守る。変更の区切りは、途中のどの形でも原則が成り立ち（2つの決め方・2者が並ばない）、破れが見えないものを失わない（全部を移してから、
一覧を見せて刈る）ように決める。

- なぜ: 原則は Claude が書いたもので、正しさの基準はユーザーの判断にしかない。1件に合わせた文は増えるほど、長く・食い違い・落とされる。
  決まりの文は Claude にとって守らせる設定ではなく読む文脈である。
- 確かめの問い:
  - 原則や決まりを変えたら、ユーザーの判断の全件に当て、外れを理由として原則に書いたか？
  - その決まりに導く原則が言え、全部の原則の問いに「はい」で答えられ、消すと Claude が誤るものか？ 原則から導ける細部を書いていないか？
  - 毎回起きるべきことは、仕組みで守っているか？
- 判定: どの原則もユーザーの判断で外れず、どの決まりも導く原則が言え、消すと誤るものだけが残っている。
- 効いている印: ユーザーが同じ種類の指摘を2回しない。

### 7. 既存の形と、世の中のやり方に合わせる

作るもの・流れ・道具・決まりは、まずこのプロジェクトの既存の形（構成・作法・ユーザーが示した方針）に、次に世の中で一般に行われている
やり方（公式の案内・広く使われている例・標準の手段・法令や規約・一般の作法）に合わせ、どちらも案を出す前に調べる。理由なく一般から
外れた既存の形は、合わせる先にせず直す。外れるときだけ、理由を書く。

- なぜ: このプロジェクトは特殊なことをしていない。既存の形とずれたものは余計な違いを残し、一般のやり方を外れて自前で作ると、多くの人が
  踏んで直した穴を踏み直す。
- 確かめの問い:
  - 案を出す前に、既存の形と一般のやり方を調べたか？
  - 既存の形にそろえ、外れるものには理由を書いたか？
- 判定: どの作るもの・決まり・道具も、既存の形と一般のやり方に合っているか、外れる理由が書いてある。
- 効いている印: ユーザーが「他と合わせて」「世の中ではどうしているのか」と言わずに済む。

### 8. 同じ形のもの全部を、いちばん小さい形で直す

直す・作るときは、見つかった1件ではなく同じ形のもの全部（母集団。あとから来る同じ形のものも含む）に効く1つの形で、症状を隠さず
原因を直す。調べる・直す・確かめる手間と、足すもの・回すもの（仕組み・依存・経路・表示・確かめ）は、守るものの重さ（原則5）と
残る疑いに見合う最小にする。原因を直さずに回避で止めるのは費用の決定なので、手間と重さと回避を並べて問う（原則1）。意味を失った
もの・使われなくなったもの（経路・値・タスク・条件の行・ブランチ）は、置き換えた作業の中で、置き換えた先を書いて消す・閉じる。
案には今の形を活かす小さい案を必ず並べ、収まらないときは器を変える前に中身を小さくする案を出し、器を変える案には、小さい案で届かない
理由を書く。

- なぜ: 1件ずつの直しは、同じ形の別の場面でまた壊れ、場面ごとの処理が積み上がる。足したもの・残したものは、作る手間より保つ手間が
  かかり、余計な表示は利用者の目的の操作を押しのける。
- 確かめの問い:
  - 母集団を書き、その全部に効く形で、原因を直したか？
  - 足すもの・回すものは目的に見合う最小で、意味を失ったものを残していないか？
  - 案に、今の形を活かす小さい案を並べたか？
- 判定: 直したものと出した案を並べると、母集団ごとに1つの形で、目的に要る以上のものが無い。
- 効いている印: ユーザーが「全体最適で」「根本対応は」「シンプルにならない？」「つけ焼き刃」と言わずに済む。

## 流れのあらまし

導く原則: 3。

タスクは GitHub の issue である。1つの Pull Request に収まらないタスクは段階に分け、段階も同じ形の issue（親の sub-issue）に
する（.claude/skills/file-issue/SKILL.md「段階に分ける」）。ステータスは段階も含めてどの issue も持ち、Project の欄「Status」に置く。
ステータスの移り変わりは**遷移の表**（`tools/flow-gate/flow.config.json: transitions`）だけが決め、ゲート（`tools/flow-gate/`）が
誰の・どの経路の変更（ボードの移動・回答フォーム・Pull Request・Claude の道具・閉じる操作）でも同じように表で照らす。表に無い
変化はゲートが前へ戻して理由をコメントする。誰の番かはステータスだけで決まり、ユーザーの判断は回答フォームかチャット（.claude/skills/ask/SKILL.md「答え」）で答えるか、表にある
遷移ならボードで動かして行う。仕組みが守るのは遷移までで、それぞれの状態で何をするかは、この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）の手順が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリと Project（`flow.config.json: repository`・`project`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない。Project の「状況の更新」に見回りが書く全体の様子（「様子を見る」） |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事を表で照らしてステータスを書き、担当者をステータスの番に揃える。表に無い変化を戻す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメントを書く・実施の順番・検証中の確かめとマージ・Project の欄の規模と優先度 |
| ユーザー（hidakagit） | 判断を回答フォームで答える（開発機の対話のセッションではチャットで。.claude/skills/ask/SKILL.md「答え」）。本番での最後の確かめ。表にある遷移ならボードでステータスを動かす（表に無い移動はゲートが戻す）。ラベル（`急ぎ` 等）を付け外しする |

- Claude が置き場へ書く名義とトークンは「担当」の「名義」が持つ（開発機の対話のセッションも同じ）。
- ゲートは自分の書き込み（送り主 `flow.config.json: gate`）を無視する。組み込みの自動化「Auto-add to project」
  （段階は「Auto-add sub-issues to project」）が issue を Project に入れると、ゲートが入口（下）を処理する。

## ステータスと割り当て

導く原則: 1・2・3・4。

ステータスの名前・並び・表は設定ファイルが正本で、ここに写さない。読み方だけを書く。

- **誰の番か**（`owner`）: ステータスだけで決まる。回答待ち・保留はユーザーの番、未着手・進行中・検証中は Claude の番。
  担当者の欄は、ゲートがステータスから書く表示と通知のためのもので、手で変えてもゲートがステータスの番へ戻す。
- **入口**: Project に入ったとき、起こした人と種類で決まる（入った時点のステータス＝ボードで選んだ列は見ない）。起こしたことが
  判断なので未着手で入る（ユーザーが起こしたもの・段階・Claude が起こした改善（種類が `todoTypes`））。Claude が起こした
  それ以外（要望＝利用者に見える新しいもので、何を作るかは原則1のユーザーの判断。種類なしも）は保留で入り、起こした者が同じ回に、
  `field.js` で欄を入れたあと（Project に入って保留になってから）問いを書いて `ask.js` で回答待ちへ動かす。ゲートは入口で
  問いを置かない（原則2）。段階は優先度の欄が空なら親の優先度を継ぐ。ほかの欄は書かない。
- **本文の先頭**: 回答待ちの間だけ、ゲートが回答フォームへのボタンを1つ置く（ゲートの印 `<!-- flow-gate -->` の間）。
  それ以外のときは何も置かない。保留から出すのはボードの移動（未着手・完了の列。回答待ちの列へは、答えていない問いがあるときだけ入れる（無ければゲートが戻す。
  下の「問い」））か、`Close as not planned`（見送り）。
- **問い**: 回答待ちへは、答えていない問い（最新の「## 問い」のあとに「## 回答」が無い。読むのは回答フォームと同じ件数の
  コメント）が形（.claude/skills/ask/SKILL.md「問い」）に合うときだけ入る。どの経路（道具・ボードの移動）でも同じ照らしで、
  合わなければゲートが前へ戻して理由をコメントする。ゲートは問いを書かない。
- **遷移**（`transitions`）: FROM のステータスごとに、行ける TO の並びを持つ（先頭が既定）。誰が・どの経路で動かしても、ゲートは
  同じ照らし（`tools/flow-gate/src/rules.js: judge`）で、FROM → TO が表にあれば通し、無ければ戻す。起こした者・出来事の種類は
  見ない。前提（blocked by）の開いた未着手を振り出さないのは見回り（.claude/skills/file-issue/SKILL.md「前後関係と組」）。
- **完了**: 閉じた理由（completed＝完成／not planned＝見送り）で分ける。表のほかにゲートが持つルールは、上の「問い」とこれだけで、完成で完了へ
  入るときは、どの経路でも、残り（下）があれば通さない。見送りは残りを問わない。完了からは戻せない（続きは新しい issue）。
- **残り**（`tools/flow-gate/src/rules.js: remaining`）: 本文の完了の条件のうちチェックの無いもの。ゲートはラベルを見ない。ユーザーに
  確かめてもらうことも、完了の条件の1行（`- [ ] ユーザーが確かめる: …`）として書く。

## Claude がステータスを動かす

導く原則: 3。

問いを置いて回答待ちにするのは `ask.js`（.claude/skills/ask/SKILL.md「問い」）、ほかは次の道具で動かす。行けるかはゲートと同じ照らしで決まり、理由を渡すと
理由をコメントに書いてから動かす。

    node tools/flow-gate/bin/move.js <issue の番号> <行き先のステータス> [理由]

流れの道具（`tools/flow-gate/bin/`）は、どの作業ツリーで打っても master の版で書く。打った作業ツリーの `tools/flow-gate` が
`origin/master` と違えば、道具が master の版を一時の場所へ取り出して打ち直し、そのことを1行出す（`tools/flow-gate/bin/cli.js`）。
試し（`--dry-run`）は書かないので作業ツリーの版で動き、道具を変える作業ブランチでは、変えた道具を試しの形で流して確かめる
（.claude/skills/task-work/SKILL.md「書き込みのある道具を流す」）。

- 未着手 → 進行中: 担当のワークフローが、最初の段（引き受ける）で動かす（「担当」）。開発機の対話のセッションは、タスクを持ってから
  理由を付けて動かす（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。
- 進行中 → 未着手・保留（理由を書く）: 作る担当が、タスクを進行中のまま終えたとき。どちらへ動かすかは終わり方で決まる。担当のワークフローの後始末が動かす（「担当」）。

**1つのタスクを触るのは1者だけ**。決まりは1つで、タスクを持つ印（置き場の git の参照 `flow.config.json: coordinator.holdRef` の下の
issue の番号。`tools/flow-gate/src/hold.js`）が持つ。印は番号ごとに1つで、参照を作れた者だけが持ち、もうあれば作るのを断られる（git の
押し込みは、受ける側が参照の今の値を押し込む側の見た前の値と照らしてから書く。git の文書 `gitprotocol-pack` の receive-pack）。
持てたかは読み直して自分の印があることで決め、持てなければ自分の印を消して触らない。担当は引き受けで取って後始末の最後に手放し、
開発機の対話のセッションは `hold.js` で取って手放す。見回りは、印のある番号と終わっていない実行（待っているものを含む）のある番号へは
振り出さず、実行が終わったのに残った担当の印を消す。同じタスクの担当の実行は、担当のワークフローのグループ（`.github/workflows/claude-task.yml`
の `concurrency`）でも1本ずつ動き、あとから来たものは取り消されずに順に待つ（`queue: max`）。
開発機の対話のセッションの持ち方は.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」。

仕組みは Claude の移動を表のほかに絞らない。手順として、検証中へ入る・検証中から出るのは Pull Request の出来事に任せ（ゲートが
出来事を受け損ねたときだけ、Claude が出来事の行き先へ動かす。.claude/skills/task-work/SKILL.md「Pull Request のあと」）、ユーザーの
番（回答待ち・保留）のタスクは Claude が動かさない。

## 担当（Claude が自分の番を進める）

導く原則: 1・3・4・5。

役割は次のとおりに分ける。どの役も、ほかの役の持ち物を持たない。作る担当・確かめる担当の手順は .claude/skills/task-work/SKILL.md にある。

| 役 | 持つもの・すること |
|---|---|
| GitHub（issue・Project・ゲート） | タスクの状態（ステータス）。遷移はゲートが表で守る |
| 振り出しの見回り（`.github/workflows/claude-dispatch.yml` が決まった間隔ごとに `tools/flow-gate/bin/dispatch.js` を1周打つ） | 自分のワークフローが有効か・止める時刻を見て、種類ごとの枠（`flow.config.json: coordinator.slots`）まで担当のワークフローを起こし、全体の様子を Project の状況の更新に書く |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 1件を引き受け、準備をして担当を起こし、終わったら後始末をする |
| 作る担当・確かめる担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（PR・問い・issue へのコメント）。次の担当を起こすことには触れない |

**キュー**（仕事の並び）は GitHub のステータスから毎回導くもので、どこにも別に持たない。作る担当が PR を出すとゲートが検証中にし、
それが確かめる依頼として載る。

- **枠**: 作る担当と確かめる担当で、別々の上限（`coordinator.slots`）を持つ。貸し借りしない。
- **振り出す条件と順**（`tools/flow-gate/src/dispatch.js: ready`。待つ理由の見分けは `tools/flow-gate/src/rules.js: waitsFor`）: どちらも、
  持つ印とラベル「開発機が要る」のあるタスクと、動いている担当の番号は除く。確かめるは、残りの検証中のタスク全部（前提・着手可能日時を問わない）。
  作るは、残りの未着手のうち、前提が全部閉じていて（段階に分けた親も、段階に blocked by されてここで待つ）、
  着手可能日時（.claude/skills/file-issue/SKILL.md「ラベルと種類と欄」）が今（日本時間）以前のもの。並びはラベル「急ぎ」
  （ユーザーの依頼）→ Project の優先度の欄の選択肢の順（空は `flow.config.json: project.unsetPriority` の位置）→ 番号の小さい順。
- **見回り**: GitHub Actions のランナーで常駐し、`coordinator.watchEveryMinutes` ごとに master の今の道具を取り出し直して1周打つ
  （道具や設定の変更は、master に入れば次の周から効く）。答え・前提が閉じた・ラベルを外した・止める時刻が過ぎた、のどれも、次の周で
  拾われる。実行の持ち時間（`coordinator.watchForMinutes`。GitHub のジョブの上限6時間より短い）が過ぎたら、次の実行を
  `workflow_dispatch` で起こしてから終える。1周の失敗では止まらず、最後に通った周（無ければ実行の始まり）から
  `coordinator.watchFailMinutes` のあいだ1周も通らなかったときだけ失敗で終わって次を起こさない（GitHub の失敗の知らせが届く）。
  途切れたら、手で `gh workflow run claude-dispatch.yml -R hidakagit/ride-compass`（Actions の画面の Run workflow でもよい）で起こし直す。
  定期の起動（`schedule`）は使わない。
  `node tools/flow-gate/bin/dispatch.js --dry-run` で、何を起こすか・状況の更新に何を書くかを見られる。
- **担当のワークフローの1回**:
  1. 引き受ける（`tools/flow-gate/bin/claim.js`）: 先に持つ印を取り、取れたらタスクを読み直して、振り出しと同じ待つ理由が無く、作るなら
     未着手 → 進行中へ動かせたときだけ、確かめるなら検証中のときだけ進み、issue に着手（担当の種類・実行へのリンク）を書く。進まなければ
     印を手放して何もせず終わる。待っていた実行は前の実行が終わってからここで照らされる（「1つのタスクを触るのは1者だけ」）。
  2. 準備（`.github/workflows/claude-task.yml` の段）。
  3. 担当を起こす。持ち時間はジョブの `timeout-minutes` で、超えると Actions がジョブを止める。担当の実行は、担当が手番を終えた
     最初の発言で終わる。裏で動かす道具（Bash の `run_in_background`・Monitor・ScheduleWakeup・
     cron の道具・Workflow）は担当のワークフローが外してある（`claude_args` の `--disallowedTools` と環境変数
     `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）。担当が待つときは、終わるまで前に出したまま待つ。起こす指示（`claude-task.yml` の
     `prompt`）は、役・作業ツリー・issue の番号と読む節だけを渡し、決まりも環境の説明も写さない（出どころは
     .claude/skills/dev-session/SKILL.md「開発機の対話のセッション」の「決まりの出どころ」）。
  4. 後始末（担当が落ちても止められても走る）: 作る担当の GitHub に無い変更（未コミットの変更・push していないコミット）は
     `wip/tasks-<番号>-<時刻>` の枝へ残す（作業ブランチは書き換えない）。そのあと `tools/flow-gate/bin/after.js` が、連携の書き出す
     実行のファイルで終わり方を見分ける（`tools/flow-gate/src/after.js: settle`）。作る担当のタスクが進行中のまま終わったら、理由を書いて動かす:
     - 未着手へ戻す: ジョブが Cancel されずに担当の仕事の外の失敗（Claude の利用の上限・認証・サーバーの一時の失敗・担当が起きる前の
       落ち）で止まった・作業ブランチの開いた Pull Request がある（ゲートが開いた出来事を受け損ねた）・振り出しを待つ理由（開いた前提・
       ラベル「開発機が要る」・今より先か形の合わない着手可能日時。見回りと同じ見分け）がある。
     - 保留にする: それ以外（PR も問いも出さずに終わった・持ち時間を超えた・Cancel された）。Cancel されたジョブは、担当が起きる前でも、
       担当の発言に利用の上限・認証の `error` があっても保留にする。落ちたとみなし、保留から出すのはユーザー。
       作業ブランチに push 済みの分から続けられる。

     Cancel されずに Claude の利用の上限・認証（担当の発言の `error`）で止まったなら、
     どちらの担当でも振り出しを `coordinator.pauseMinutes` の間止める（コードのリポジトリの変数
     `coordinator.pauseVariable` に止める時刻を置き、振り出しがそれを読む）。段階に分けて終えたときは、`stage.js` が親を未着手へ
     戻しているので動かさない（.claude/skills/file-issue/SKILL.md「段階に分ける」）。確かめる担当のタスクは動かさない（検証中はキューに残り、次に起こし直される）。
     続けて、どちらの担当でも手番の記録（実行のファイル）を gzip して置き場のリリースへ置く（`tools/flow-gate/src/after.js: keepLog`。
     リリースは日（UTC）ごとに1つ。リンクは終わりのコメントの「後始末がしたこと」に出る）。続けて、どちらの担当でも issue に
     終わりのコメントを書く（`tools/flow-gate/src/after.js: endReport`）。読み手は後から確かめるユーザーと後の担当（作る・確かめる・
     開発機の対話のセッション）。書くのは、担当の最後の発言（担当が書く要約。.claude/skills/task-work/SKILL.md「作る担当・確かめる
     担当の終え方」）・後始末がしたこと・判定に断られた操作（あるときだけ）・実行へのリンクだけで、issue と実行のページで読めるもの
     （ステータス・ジョブの結果・時間・手数）は写さない。PR も報告も出さずに終わった担当の理由は、この最後の発言で読む。
     最後に、1 で取った持つ印を手放す（後始末が落ちて印が残ったら、実行が終わったあとに見回りが消す）。
- **名義**: 置き場へは hidakagit-bot（secret `FLOW_BOT_TOKEN`）、コードのリポジトリへは hidakagit（secret `CODE_TOKEN`。
  `GITHUB_TOKEN` で打ったマージは master の CI とデプロイを起こさないため）、Claude は契約のトークン（secret `CLAUDE_CODE_OAUTH_TOKEN`）。
  どのトークンがどこへ届くかは docs/architecture/tech-stack.md「秘密の値とトークン」が持つ。Claude は置き場へ hidakagit-bot の
  トークンでだけ書き、hidakagit のトークンで書かない（開発機の対話のセッションでは、同じ値をユーザー環境変数 `FLOW_BOT_TOKEN` に持つ）。
  `CODE_TOKEN` はコードのリポジトリにだけ届き、置き場に届かない。担当のワークフローは gh の既定（`GH_TOKEN`）に `CODE_TOKEN` を
  置くので、gh で置き場を打つときは、読むときも `GH_TOKEN=$FLOW_BOT_TOKEN` を付ける（担当は付け忘れると断られる。開発機の対話の
  セッションは gh の既定が hidakagit で、付け忘れると hidakagit の名義で書かれうるので、必ず付ける）。名義の誤りを止めるのはこのトークンの範囲だけ（gh はトークンをホストごとにしか選べず、権限の拒否の
  規則は先頭の変数の代入を越えて当たるので、付けた打ち方と付け忘れた打ち方を見分けられない）。
- **止める**: Actions の画面で Claude Dispatch を無効にする（Disable workflow）。動いている見回りは次の1回で無効と読み、状況の更新に
  止めていると書いて、振り出さずに終える（次の見回りも起こさない）。戻すときは Enable workflow のあと Run workflow。
  利用の上限で後始末が止めた時刻（変数 `coordinator.pauseVariable`）を早く解くなら、コードのリポジトリの Settings → Secrets and
  variables → Actions → Variables で消す。動いている担当は止まらないので、止めるなら Actions の画面でその実行を Cancel する
  （後始末の段は走る）。1つのタスクだけを止めるなら、ボードで保留へ動かす。
- **開発機が要る**: 開発機にしか無いもの（本番への調べ `run_probe.py` の SSH の鍵・開発 DB の実データ）が要るタスクと、担当が
  しない操作（「自動で進めないもの」「担当が書けないファイル」）が要るタスクは、Actions では進めない。担当は、それが要ると分かった
  ところで作業を止め（途中の変更は作業ブランチへ push してから）、issue にラベル「開発機が要る」（`coordinator.devLabel`）を付け、
  何がなぜ要るかをコメントに書いて終える。振り出しはこのラベルの付いたタスクを飛ばし、開発機の対話のセッションが扱う
  （.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。ユーザーが付けてもよく、Actions の担当の進め方が合わないと判断したタスクを開発機の対話の
  セッションへ引き取る口になる。

**担当の権限**: 担当は自動モードで動き、操作の可否は判定役が1回ずつ決める。判定役には `tools/flow-gate/settings.json` の
`autoMode` で、担当の置かれた環境（2つのリポジトリがユーザーのもの・担当は使い捨てのランナーの無人の作業役 等）と日常の操作
（作業ブランチへの push と Pull Request を出す・タスクの issue を読む・コメントする・閉じる・`tools/flow-gate/bin` の道具を打つ 等）を
教える。決して打たせない操作（master への push・強制の push・GitHub の API での書き込み・ワークフローを止める・止めたのを戻す等）は、
同じファイルの `permissions.deny` で断る（拒否は判定役より先に効く）。ユーザーの答えが要る変更（規模の閾値の数を変える
`scripts/size_thresholds.json` の編集）は `permissions.ask` に置く（どのモードでも自動では通らず、開発機ではユーザーに確かめ、
担当には確かめる人がいないので通らない。Python 等のスクリプトの中の書き込みには当たらない）。拒否の規則はコマンドの文に当てるので、流れの道具が中で打つもの
（`hold.js` が置き場へ打つ git の押し込み等）には当たらず、読むだけでも
`-X`・`-f` 等の付いた `gh api`（`-X GET` に `-f` で欄を渡す一覧・`gh api graphql`）は断られる。つないだコマンドは全文にも当たるので
（`git push … ; gh pr create --base master …` は `Bash(git push *master*)` に当たる）、規則の頭の道具（`git push`・`gh api`）はつながずに1つで打つ。読むときは欄を URL に書き
（`gh api 'repos/<所有者>/<リポジトリ>/actions/workflows/<ファイル>/runs?created=<範囲>'`）、`gh run list`・`gh issue view --json`（`blockedBy` 等）で済むものはそれを使う。自動モードそのものも同じファイルの `permissions.defaultMode` で
決める。各一覧は既定の規則（`$defaults`）を必ず残す。担当は連携の `settings` で
このファイルを読む。開発機の対話のセッションも同じ決まりで動く: セッションの始まりのフック（`.claude/settings.json` の
`SessionStart`）で `tools/flow-gate/bin/settings.js` が、master の版のこのファイルの `permissions` と `autoMode` をユーザー設定
（`~/.claude/settings.json`）へ写す（判定役はリポジトリの `.claude/settings.json` の `autoMode` を読まず、`defaultMode` の `auto` も
リポジトリの設定からは効かない。`permissions` は丸ごと置き換えるので、開発機にだけある許可は残らない）。決まりを変えるのは
このファイルだけで、master に入った次のセッションから両方に効く（作業ブランチで直しても、作業中の自分の権限は変わらない）。
判定役が自分を動かす設定の書き換えとして編集を断ったら、「担当が書けないファイル」のとおりにする。日常の操作が断られたら、
回り込まず（別の道具・別の名義で打たない）、流れの摩擦として記録する（.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」。直すのは `autoMode` の説明）。断られた操作は、後始末の終わりのコメントの
「判定に断られた操作」に、道具と打とうとしたものが出る。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（本番の接続情報も持たない）。
要るときは、書く中身（打つスクリプト・対象・前後に読んで比べるもの）を作業ブランチか issue のコメントに置き、「開発機が要る」の
とおり返す。開発機の対話のセッションが.claude/skills/dev-session/SKILL.md「本番へ書く」のとおり進める（Claude が打てない操作を原則1のとおり
ユーザーに頼むのも、開発機の対話のセッションのチャットで渡す）。ユーザーに打たせる問いにしない。
マージの前に済ませる本番への書き込み（コードが新しく読む表を作る等。.claude/rules/deployment-sync.md「コミットと同時に揃えるもの」）が
要る変更は、作る担当が Pull Request を出す前に返す（出すとゲートが検証中へ動かし、確かめる担当がマージする）。作ったコードは作業ブランチへ
push し、書く中身はそのコードから出す。書き込みが済んでラベルが外れると、次の作る担当が作業ブランチから続けて Pull Request を出す。
Claude が持たない権限の操作（クラウドの画面・外部サービスの登録・GitHub のリポジトリの設定やトークン）だけは、`ask.js` で問う。
問いの文の頭に「PC での操作:」と書き、判断材料に手順と確かめ方を書く。
済んだら次のステータスを未着手に、できなければ補足に理由を、と判断材料に書く。未着手で答えが来たら、Claude が確かめ方のとおりに
確かめ、完了の条件にチェックを付ける。

**担当が書けないファイル**: Claude Code の自動モードの判定は、CLAUDE.md・`.claude/` の設定・権限（`tools/flow-gate/settings.json`）・
流れの手順（flow.md 等）の編集を、自分を動かす設定の書き換えとして断ることがある（1か所目が通っても、続く編集が通る根拠にしない。
判定役への説明が日常の作業と教えていても、回によって断られる）。断られたら回り込まず（別の道具・写しの差し替え・別の名義で書かない）、
パッチにもせず、「開発機が要る」のとおり返す。書けた分は作業ブランチへ push し（push も断られたら、後始末が `wip/` の枝へ残す）、
何をどこまで書いたかをコメントに書く。開発機の対話のセッションが続きを書く。

## 様子を見る

導く原則: 4。

- **動いている担当**: コードのリポジトリの Actions の画面（Claude Task の実行。名前は「#<番号> <種類>」）。振り出しが何を起こしたかは
  Claude Dispatch の実行の記録に出る。
- **全体の様子**（`tools/flow-gate/src/dispatch.js: summary`）: 見回りが Project の「状況の更新」（Status updates）に、種類ごとの動いている
  担当（実行へのリンク）・振り出しを待つ仕事の数と、気づくべきもの4つ（下の「気づける範囲」で守る症状）を書く。どれかがあれば At risk、無ければ On track。中身が変わった
  ときだけ書き、状態が同じなら最新の更新を書き換え、変わったら新しく足す（履歴には状態の移り変わりだけが残る）。最新の1件の状態が
  Project の見出しと Projects の一覧に出る。
  - **想定を超えたタスク**: 作業の状態（進行中・検証中）にいて規模の欄を持つタスクで、作業時間が同じ規模の想定を超えたもの
    （`tools/flow-gate/src/dispatch.js: workload`）。作業時間は、issue に残る Claude（hidakagit-bot）とゲートのコメントと閉じだけから
    読んだ、作業の状態にいた区間の和。入りは担当の着手・進行中か検証中にする理由・ゲートが進行中か検証中へ戻したコメント。出は問い・
    ほかのステータスにする理由・ゲートがほかへ戻したコメント・ゲートの Pull Request のコメント・閉じる（形は `tools/flow-gate/src/rules.js: notes`
    が作り、同じ所の `worksAfter` が読む）。記録を残さない移動（ユーザーのボードの移動・理由を付けない `move.js`）は読まないので、
    記録なしに作業の状態へ入った時間は数えず、記録なしに作業の状態から外へ出た時間は、次の出の記録か閉じるまで作業時間に入る。
    `flow.config.json: coordinator.recordsSince` より前の着手から始まる区間は数えない。想定は、同じ規模で完成で閉じた直近 `coordinator.recent` 件の
    うち作業時間を持つものの p90 で、毎周計算し直す。下の「進行中なのに動いている担当が無いタスク」にも当たるタスクは、その行に添えて1行で出す。
  - **進行中なのに動いている担当が無いタスク**: 進行中のタスクのうち、番号の終わっていない担当の実行（開発機の対話のセッションが
    持つ実行も）が無いもの（担当のジョブが後始末を走らせずに止まった等）。
  - **振り出せる仕事があるのに空いた枠**: その理由（見回りのワークフローが無効・止める時刻）。
  - **落ちた実行**: 開いたタスクの一番新しい担当の実行が失敗で終わっているもの（次の実行が走れば消える）。
- **気づける範囲**: Claude の番のタスクが長く止まる・仕事があるのに担当が動かない・動かしているものが失敗する、のどれかが起きたら、
  ユーザーは上の状況の更新（At risk）か、後始末の保留への移動（担当者がユーザーになる）か、GitHub の Actions の失敗の知らせで気づける。
  原因ごとに見張りを足さず、この症状で拾えるものだけを守る。
  - **見回りが失敗し続ける**: 状況の更新には出ない。`coordinator.watchFailMinutes` のあいだ
    1周も通らなければ見回りの実行が失敗で終わり、失敗の知らせで気づける（上の「担当」の「見回り」）。
  - この症状で拾えない詰まりに当たったら、例外として書き並べず流れの摩擦として記録する（.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」）。
- 異常の処置は issue に書く（保留の理由など）。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（またはPR）。ただし**段階に分けたタスクは段階ごとに1コミット**にする（段階ごとに Pull Request を出す。
.claude/skills/file-issue/SKILL.md「段階に分ける」）。**コミット履歴は、ある時点へ戻すときに
どのコミットまで戻せばよいかを件名と本文だけで特定できる状態に保つ**。問い・決定・確認の結果はそのタスクの issue に書き、git には写さない。
master のコミットは Pull Request の題名と本文から作られる。題名が件名で `tasks#1234: <何が変わったか（1行。利用者・運用から見た結果）>`、
本文の形は `.github/pull_request_template.md` だけが持ち、Pull Request の CI（Claude Gate の flow-gate）が照らす。

件名は必ず `tasks#<issue の番号>:` から始める（段階なら段階の sub-issue の番号、複数なら`tasks#12・tasks#13:`）。
属するタスクの無い変更は作らない（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。

## ゲートを変える・公開する

導く原則: 3・5。

表・枠は `flow.config.json`、問いの形は `question_template.md` を直す。公開は、master に入ると `claude-gate.yml` の `deploy-gate` が、
ゲートを変えたかによらず master の先頭の版を `wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で行う（コードのリポジトリの秘密の値 `CLOUDFLARE_API_TOKEN`・
`CLOUDFLARE_ACCOUNT_ID` を使う）。ゲートは出来事が届いた issue だけを今の規則の姿（担当者・本文の先頭のボタン）へ
書き直すので、規則を変えた直後、出来事の無い issue は次の出来事まで前の姿のまま残る。
手で公開するときは `tools/flow-gate` で同じコマンドを打つ。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`。構文と import の解決（無いファイル・無い名前）は、`tools/flow-gate` で
`npm ci` のあと `npm run lint` が動かさずに見る（ESLint と eslint-plugin-import の `errors` の組。`tools/flow-gate/eslint.config.js`）。
道具（`bin/`）の静的な誤りはテストでは落ちず、lint だけが落とす。CI（`claude-gate.yml` の `flow-gate`）も同じ2つを流す。
