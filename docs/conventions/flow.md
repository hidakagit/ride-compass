# 段の流れ

リポジトリを変える作業の単位は**段**（例 `T1253-A`）である。段は下の状態①〜⑥を通り、master へ入るのも
段ごと。タスク（`T1253`）は段の id の頭で、状態も入れ物も持たない。状態を書き換える口は
`scripts/flow.py` だけで、遷移の表に無い遷移は断る。

## 置き場

| 置き場 | 持つもの | 消えたら |
|---|---|---|
| 非公開のリポジトリの Issues と、その持ち主の Project | 仕掛の段（①〜⑤）。段1つが issue 1つで、問い・答え・申し送り・遷移の理由はその issue のコメント。⑥ は閉じた issue | 仮置き場。記録と git は残る |
| `docs/records/tasks/T1253.md`（タスクごとに1本） | 段ごとの背景・方針・検証。段のコミットで `## T1253-A` の節を足すだけで、前の節は直さない。状態の行は持たない | ― |
| git（master） | 完成した段のコミット | ― |

置き場の名前と回答ページの URL はコードに書かず、git の設定で持つ（`git config flow.repo <持ち主>/<リポジトリ>`・
`git config flow.project <Project の番号>`・`git config flow.answer <回答ページの URL>`）。Project の欄は
`python scripts/flow.py setup <持ち主>/<リポジトリ>` が出す gh のコマンドで作る。欄の名前と選択肢の正本は
`scripts/flow.py: FIELDS`。

番号を振るのはリポジトリを変える作業だけ。本番の操作・問い合わせには振らない。ユーザーが master へ直接入れる
改修は置き場を通さず番号も無く、識別子はコミットのハッシュ、記録はコミットメッセージ。担当の作業はすべて置き場を通す。

## 見張り

集計のコードは持たず、GitHub の標準の機能で見る（Issues・Projects・非公開のリポジトリは Free のプランに含まれる）。
ビューは Project の画面で作って保存する（日付の欄は `@today` と比べて絞れる）:

- ボード: 列＝「状態」、絞り込み `is:open`
- 私の番: `is:open 次に動かす人:ユーザー`
- 期限切れ: `is:open 状態:"② 保留" 見直す日:<@today`
- 止まっている担当: `is:open 状態:"④ 進行中" updated:<@today`。`updated` は issue の作成・編集・コメント等で
  進み、日の単位でしか絞れない。時間の単位で止まったことは、担当の終わりの知らせ（Claude Code の Agent の完了）で気づく。
- **ユーザーへの知らせ**: ユーザーへの問いのコメントだけを道具用の別アカウントが書き、本文でユーザーを名指しする
  （名指しは GitHub の通知になる）。別アカウントは置き場のリポジトリにだけ招き、そのトークン（classic）は環境変数
  `FLOW_ASK_TOKEN` に置く。道具のそれ以外の操作は gh のアカウント（ユーザー）のまま。
- 定期の見回りのコードは持たない。`python scripts/flow.py take` は、司令塔が担当の報告を受けるたびと、ユーザーに
  声をかけられたときに流す。

## 状態

| 状態 | 決める事実 | 次に動かす人 |
|---|---|---|
| ① 提案 | 承認されていない（番号なし） | ユーザー |
| ② 保留 | 前提が欠けている。止めている人・欠けているもの・見直す日・延ばした回数を必ず持つ | 止めている人 |
| ③ 未着手 | 前提を満たし、手が付いていない | 司令塔 |
| ④ 進行中 | 担当が作業している | 担当 |
| ⑤ 検証中 | 作業ブランチの上で CI・完了の条件・本番と画面の確かめをしている | 司令塔 |
| ⑥ 完了 | master に入った、または見送った（閉じた issue）。終点で戻らない。続きは新しい提案 | なし |

「次に動かす人」は Project の欄で、道具が遷移のたびに書く。② ではこの欄が止めている人を表す。
② へ入るときに欄「戻り先」を書く（①・④ から入ったら ③、⑤ から入ったら ⑤）。欠けていたものが満たされたら戻り先へ移す。
② の見直す日は1回だけ延ばせる。2回目は見送るかをユーザーに問う。

## 遷移

厳密に制御するのは入口（承認された ① に番号を振る）・出口（`land`）・この表の3つだけ。

| 遷移 | 誰が | 条件 |
|---|---|---|
| ① → ③ | 入口 | 「承認」の回答があり、前提が欠けていない |
| ① → ② | 入口 | 「承認」の回答があり、本文の「前提:」の段がまだ⑥でない |
| ② → 戻り先 | 止めている人（前提の段が⑥になったら出口） | 欠けていたものが満たされた（ユーザーの問いは回答、前提の段は⑥）。行き先は ② へ入ったときの戻り先（①・④ からは ③、⑤ からは ⑤） |
| ② → ② | 止めている人 | 見直す日を延ばす。1回だけ |
| ③ → ④ | 司令塔 | 空いたスロットがある |
| ④ → ⑤ | 担当 | 作業ブランチの master より先のコミットがあり、件名がすべて段で始まる |
| ④ → ② | 担当 | 止めている人・欠けているもの・見直す日 |
| ⑤ → ④ | 司令塔 | 差し戻しの理由 |
| ⑤ → ② | 司令塔 | ユーザーの操作・目視が要る |
| ⑤ → ⑥ | 出口 | ④→⑤の条件に加え、コミットの本文に検証の結果があり、CI が緑で、master から早送りできる |
| ①〜⑤ → ⑥ | ユーザー（見送り） | 「見送り」の回答 |

この表は `scripts/flow.py: TRANSITIONS` と同じ行を持つ（テストが突き合わせる）。

    python scripts/flow.py propose "<題名>" [--task T1253] [--body "<本文>"]   # ① を置く（段を足すなら --task）
    python scripts/flow.py take                                              # ユーザーの回答を取り込む
    python scripts/flow.py move <段> <②|③|④|⑤> [--reason …] [--by … --missing … --review YYYY-MM-DD --choice …]
    python scripts/flow.py land <段>
    python scripts/flow.py ci <40桁のsha>                                      # CI を待って結論を出す

- **入口**（`take` が「承認」の回答のある ① に対して行う）: 新しいタスクの番号は、記録のファイル名と置き場の
  全部の issue の題名にある最大の番号＋1で、段は A。段を足す提案（`--task`）は、そのタスクの issue の題名と master の
  コミットの件名にある最後の文字の次。振った id は issue の題名の頭と欄「段」に書き、以後変えない（issue を別の
  リポジトリへ移すと issue の番号は振り直されるので、issue の番号からは導かない）。提案の本文に `前提: T1253-A` の
  行があり、その段がまだ⑥でなければ ② にし（止めている人は司令塔、見直す日は30日後）、その段が⑥になったとき
  出口が ③ へ動かす。入口は issue の本文に「見送り」の回答ページへのリンクを置く。
- **出口**: 作業ブランチ `orch/<段>` の先端を、CI の緑と「検証:」の行を確かめてから `git push origin <sha>:master`
  で入れる（書き換えない。早送りでなければ git が断る）。master が先へ進んでいたら差し戻して、担当が rebase し直す。
  master へのコミットはこの道でしか生まれない。

## ユーザーが答える形

ユーザーが答える入口は回答ページ1つ（`tools/answer-form/worker.js`。Cloudflare Workers で動き、Cloudflare Access で
ユーザーだけが開ける）。ページは選択肢（1つだけ選べる）・補足（任意）・送信を出し、置き場の issue へ
「回答: <記号>（<選択肢>）」と補足のコメントを書く。書くのはユーザーの細かい権限のトークン（Worker の秘密の値。
置き場のリポジトリの Issues: write だけ）で、置き場のリポジトリ以外へは書かない。

- **承認・見送り**: ① を置くと、道具が「承認／見送り」を選ぶ問いを書く。入口を通った段の本文には「見送り」だけの
  リンクがあり、ユーザーは ③〜⑤ のどこでも見送れる。
- **問い**: ユーザーに止めてもらう ② は、`move … ② --by ユーザー --missing "<1問で判断できる問い>" --choice "<選択肢>" …`
  で置く。道具が問いと回答ページへのリンクを書く（上の「ユーザーへの知らせ」）。
- **取り込み**: `take` は開いている issue のコメントのうち「回答:」で始まるものだけを答えとして読む。「見送り」の答えは
  どの段でも ⑥ へ閉じる。それ以外は最後の問いより後の最後の答えを読み、① の「承認」は入口へ、ユーザーが止める
  ② の答えは戻り先へ動かす。
- 「状態」の欄は手で動かさない（Projects には遷移を断る仕組みが無く、止められない）。

## コミット

- 1段1コミット。件名は `T1253-A: <利用者・運用から見た結果>`。本文は `背景:`・`課題:`・`成果:`・`検証:`
  （実行したコマンドと観測値）・`増減:`（実装・テスト・文書を分けて）・`残り:` の行を持つ。
- 記録は同じコミットで `docs/records/tasks/T1253.md` に `## T1253-A` の節を足す。新しいタスクの最初の段は
  記録のファイルを作り、issue の本文を背景として写す。記録だけを変えるコミットは作らない。
- 段の中で出た問い・答え・申し送りは issue のコメントにあり、その段か次の段のコミットで記録へ写す。

## 担当への約束

- 作業ブランチは `orch/<段>`。origin/master の上に積み、push は作業ブランチへだけ（master へは出口が入れる）。
- 着手の前に、依頼の進め方が実行できて決まりに反しないかを確かめる。合わなければ選択肢を付けた問いで ② へ止める。
  答えに依らない残りは終えてよい。
- 終えたら `python scripts/flow.py ci <sha>` で CI を待ち、緑なら `move <段> ⑤`。報告には CI の実行の URL を添える。
- `git reset --hard`・`git stash` は使わない（作業ツリーの間で共有される）。
- frontend の検査の前に、依存が無い・古ければ `frontend` で `npm ci` を流す（スロットは node_modules を残す）。

## 司令塔がすること

- 担当の報告を受けるたびと、ユーザーに声をかけられたときに `take` を流す。③ → ④: `move <段> ④` の後、担当を
  `isolation: "worktree"` で起動する。
- ⑤: CI の結論、完了の条件（記録の段の節とコミットの本文）、本番と画面の確かめ（要るとき）を見て、
  `land`・差し戻し（`move <段> ④ --reason …`）・ユーザーの操作待ち（`move <段> ② --by ユーザー … --choice …`）のどれかにする。

## 作業ツリーのスロット

担当の作業ツリーは `.claude/worktrees/slot-<N>` を使い回す（node_modules・.venv を毎回入れ直さないため）。
貸した印は git のロック（`git worktree lock` の理由が `slot ` で始まる）だけで、ロックは作成が原子的なので同時に
取りに来た2本のうち片方だけが取れる。WorktreeCreate フック（`hook-create`）はロックの無いスロットを
origin/master に戻して貸し、未コミットの変更かどのリモートからも届かないコミットがあるスロットは貸さない。
印は ④ から出る `move`（担当がスロットの中で打つ）と WorktreeRemove フックが外す。失う作業があれば外さない。
担当が落ちて印が残ったら、中身を確かめてから `git worktree unlock <パス>` で外す。
テストDBは作業ツリーごとに分かれている（`backend/tests/conftest.py: default_test_database_name`）ので、
スロットどうしで取り合わない。同時に走る担当の数はスロットの数で決まる。
