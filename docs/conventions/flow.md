# タスクの流れ

タスクは置き場（ridecompass/ride-compass-tasks）の issue で、ステータスは Project の欄「Status」が持つ。この文書は流れの決まりだけを書く。
PR の作り方と確かめ方は [pull-requests.md](pull-requests.md)、ゲート・見回り・担当のワークフロー・道具の仕組みは
[task-flow.md](../architecture/task-flow.md)。

## 原則

流れの決まりは、次の6つから導く。原則に合わない場面が出たら、決まりに例外を足さず、原則を見直す。

1. **ユーザーの手は、判断と最後の確かめだけ**: ユーザーに求めるのは、何を作るか・どちらの案にするかの判断と、本番での最後の確かめだけ。操作（PC での作業・パッチ当て・本番への書き込み）は求めない。
2. **回答待ちは、答えられる状態のときだけ**: 問い・答える中身（本番に出ていること）・回答フォームがそろってから、回答待ちにする。
3. **状態は1か所・動かす道は1つ**: タスクの状態の正本は1つで、同じ状態を複数の経路で書かない。
4. **詰まりは見ればわかる**: どのタスクが止まっていて、何を（誰を）待っているかが、聞かなくても一目でわかる。
5. **守るのは、利用者に見える結果**: テストも見張りも、利用者に見える壊れを先に守る。部品の内側の細部は後。
6. **例外は原則を直して扱う**: 原則に合わない場面が出たら、手順書に例外を足さず、原則を見直す。原則から導けない決まりは書かない。

## 役

| 役 | すること |
|---|---|
| ユーザー（hidakagit） | 判断を答える（回答フォームか、開発機の対話のセッションのチャット）。本番での最後の確かめ。ボードの移動・ラベル |
| ゲート | 出来事を遷移の表（`tools/flow-gate/flow.config.json: transitions`）で照らしてステータスと担当者を書き、表に無い変化を戻す。回答フォーム |
| 担当（GitHub Actions の Claude） | 見回りに振り出され、作る担当は作って PR を出し、確かめる担当は確かめてマージする |
| 開発機の対話のセッション（Claude） | 担当が進められないタスクを引き取る。本番へ書く |

Claude は置き場へ hidakagit-bot の名義（`GH_TOKEN=$FLOW_BOT_TOKEN`）でだけ書く。記録（問い・答え・決定・確かめた結果）は issue にだけ置く。

## ステータス

- **誰の番か**: 回答待ち・保留はユーザー、未着手・進行中・検証中は Claude。担当者の欄はゲートがステータスから書く。
- **入口**: ユーザーが書いた issue と段階は未着手。Claude が書いた issue は回答待ちで、ゲートが採否の問いを置く。
- **回答待ち**: 答えていない問いと、本文の先頭の「回答する」のボタンがいつもある（無ければゲートが置く）。ボードで回答待ちへ動かせば、どの状態のタスクにも回答フォームで指示を返せる。
- **完了**: 完成（completed）は、完了の条件にチェックの無い行（残り）があれば通らない。見送り（not planned）は残りを問わない。完了からは戻さず、続きは新しい issue にする。
- **動かす**: Claude は `move.js <番号> <行き先> <理由>`（[task-flow.md](../architecture/task-flow.md)「道具」）で動かす。検証中への出入りは Pull Request の出来事に任せ、ユーザーの番のタスクは動かさない。
- **1つのタスクを触るのは1者だけ**: 担当の実行と開発機の対話のセッションの「持つ」は、番号ごとに1本ずつ動く。

## 振り出しと担当

- 見回りが、未着手のうち前提（blocked by）が全部閉じ、ラベル「開発機が要る」が無く、着手可能日が今日以前のものを作る担当へ、検証中を確かめる担当へ振り出す。並びは「急ぎ」→ 優先度 → 番号の小さい順。
- 作る担当は、次のどれかで終える: PR を出す（検証中へ）・問う（回答待ちへ）・段階に分ける・「開発機が要る」で返す・残りを済ませて閉じる・着手可能日を入れて待つ。手順は [pull-requests.md](pull-requests.md)「作る」。
- 確かめる担当は、満たしていればマージし、満たしていなければ理由を書いて PR を閉じる（未着手へ戻る）。手順は [pull-requests.md](pull-requests.md)「確かめる」。
- どちらも、範囲の外の気づきは、同じ直す場所の開いた issue へ寄せる・起票する・直さない理由を書く、のどれかをしてから終える。手番の最後の発言は、その回にやったことの要約にし、作ったもの（PR・コミット・問い・issue）を番号で名指す。

## 開発機が要る

担当が進められないタスクは、ラベル「開発機が要る」を付けて返す。当たるのは次のもの。

- 本番の読み書き・開発機の開発 DB の実データが要る
- 自動モードの判定が、CLAUDE.md・`.claude/`・`tools/flow-gate/settings.json`・流れの文書の編集を断った

担当は書けた分を作業ブランチへ push し、何がなぜ要るかをコメントに書いて終える。見回りはこのラベルのタスクを飛ばし、
開発機の対話のセッションが引き取る。ユーザーが付けてもよく、担当の進め方が合わないタスクを開発機のセッションへ引き取る口になる。

## 開発機の対話のセッション

担当と同じ決まり（CLAUDE.md・この文書・[pull-requests.md](pull-requests.md)・`tools/flow-gate/settings.json`）で進める。違うのは次だけ。

- **持つ**: タスクを触る前に `hold.js <番号>` で持ち、`move.js <番号> 進行中 <理由>` で動かす。触り終えたら `hold.js <番号> --release <実行の id>` で手放す。進行中のまま手放すなら、先に未着手へ戻す。PR を出したあと確かめる担当に任せるなら手放す。
- **答え**: ユーザーがチャットで決めたことを、ユーザーの言葉を引いて issue に記録する（下の「答え」）。
- **本番へ書く**: 対象・中身・差（前 → 後）をチャットで見せ、ユーザーがその操作を書くよう言ったときだけ、Claude が打つ。打ったあと前後を読んで確かめ、ユーザーの言葉と結果を issue に記録する。打つスクリプトは `C:\Users\h7g4b\ride-compass-ops\`（コミットしない）に置く。
- **裏の作業役に任せる**: [pull-requests.md](pull-requests.md) のとおり進めるよう渡し、`hold.js`・`move.js`・`ask.js` は打たせない。

## 問い

- ユーザーに求めるのは判断と最後の確かめだけ。聞くのは、外から見える振る舞いが変わるときだけにし、変わらないなら直して報告する。
- 操作は頼まない。Claude が持たない権限の操作（クラウドの画面・外部サービスの登録・GitHub の設定やトークン）だけは、問いの文の頭に「PC での操作:」を付けて頼み、判断材料に手順と確かめ方を書く。
- 本番の実物で確かめてほしい問いは、その版が本番に出てから置く（出たかの見方は [pull-requests.md](pull-requests.md)「本番に出たか」）。判断材料に、ユーザーが見る版を書く。
- 作る前に、答えの無い判断が残っていれば、問いに要る分だけを調べて、作らずに問う。

問いはファイルに書き、`node tools/flow-gate/bin/ask.js <番号> <ファイル>` で置く（回答待ちへ動く）。形は `tools/flow-gate/src/rules.js: parseQuestion` が正本で、
`<details>` より前に置けるのは次の行だけ。

    ## 問い
    <問いの文（1行）>

    ### 案
    - <案の中身>

    <details><summary>判断材料</summary>

    （この問い1つだけで判断できるように書く）
    </details>

- **案**: どちらにするかを決めてほしいときだけ書く。次のステータスは書かない（回答フォームが出す）。
- **判断材料**: 利用者への約束を1文 → 問題が起きる場面と起きない場面 → 案ごとに利用者に起きること → 推奨と理由。何の画面・機能の話か・今どうなっているかを入れ、製品の言葉で書く（関数名・タスク番号に頼らない）。
- **画像**: 画面に関わる判断は前後の画像を添える。`gh issue comment <番号> --attach '<画像>#<見出し>'` で issue へ1枚ずつ載せ、出た `https://github.com/user-attachments/assets/…` を判断材料の `![<見出し>](<URL>)` で指す。
- 開発機の対話のセッションでユーザーがチャットにいるときは、チャットで聞く。問いを残して終えるときは、回答フォームの直リンク（`flow.config.json: urls.form` の `/answer?issue=<番号>`）をチャットに添える。

## 答え

Claude は、issue のコメントに残った答えだけで判断する。答えは、ユーザーがその項目に答えたものだけで、方針の答えから導いた細部
（数字・期限・例外）は答えではないので聞く。回答フォームは次の形で書き、チャットで決まったことは Claude が同じ形で書く。

    ## 回答
    **<問いの文>**

    回答: <選んだ案>（案があったときだけ）
    次のステータス: <名前>
    - [x] <確かめた完了の条件>（完成を選んだときだけ）
    ラベル: +<付けたもの> −<外したもの>（変えたときだけ）
    補足: <書いたときだけ>

## 保留

- 保留は、人の判断か、日付で見に行けない外の出来事を待つもの。日付で再開するものは、未着手＋着手可能日で待つ。
- Claude が保留にするときは、何が止まるか・続けたら何が起きるか・再開の条件を書く。
- 保留から出すのはユーザー（ボードの移動・回答フォーム）。

## 段階と前提

- 1つの PR に収まらないタスクは、`node tools/flow-gate/bin/stage.js <親> <題名> <本文のファイル> [前の段階...]` で段階に分ける。親は段階が全部閉じるまで待ち、閉じたら残りの完了の条件を確かめて閉じる。
- タスクどうしの関係は blocked by だけで持つ（`gh issue edit <後> -R ridecompass/ride-compass-tasks --add-blocked-by <先>`）。張るのは、後が先の中身に依る（先の結果しだいで後が要らなくなる・作り直しになる）ときだけで、張った理由を後の issue に1行書く。同じファイルの別の所に触るだけなら張らず、後からマージする側が合わせる。
- 同じ範囲に触り、別々に進めると作り直しや確かめが2回になるタスクは、1つの PR に収まるなら1つの issue にまとめる。
- ほかのタスクへの申し送りは、その issue へコメントで書く（本文は書き換えない）。
- **探す**: 起票・着手・段階に分けるときに、直す場所（ファイル・関数・設定の項目・文書の節）の名前で開いた issue を探す
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue list -R ridecompass/ride-compass-tasks --state open --limit 1000 --search '"<語>" in:title,body'`）。探した語を報告に書く。

## 起票

- 作業中に当たった流れ・道具・検査の改善点は、終える前に起票する。今の差分で直せるなら直す。観測の無い思いつきは起こさない。
- 直す場所で書き、同じ直す場所の開いた issue があれば、起こさずにそこへコメントで足す。
- `GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --type <種類> --title <題名> --body-file <ファイル>` で起こし、`field.js <番号> 優先度 <高|中|低>` を入れる。入口で採否の問いが付く。

## issue の形

題名は、何をするか（何が困るか）を30字前後で書く。本文は次の節をこの順に並べ、1 以外は `<details><summary>節</summary>` で畳む
（`<summary>` の行のあとに空行を1つ入れる）。

| 順 | 節 | 書くもの |
|---|---|---|
| 1 | 要約（畳まない） | 何が起きていて、何をするか（1〜2文） |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | 誰がどの場面で何に困るかの事実。不具合なら再現の手順と、期待する動き・実際の動き。保留中は再開の条件 |
| 3 | やること（調査は: 調べ方） | 案と手段を番号付きで |
| 4 | 決めること | 決まっていないことを1行ずつ（無ければ省く。答えが出たら消して 6 へ） |
| 5 | 完了の条件 | 外から確かめられるチェック（`- [ ]`）。ユーザーの確かめは `- [ ] ユーザーが確かめる: …`。マージのあとにしかできない作業は別の issue にして blocked by でつなぐ |
| 6 | 経緯 | 決まったこと・変わったことを日付つきで1行ずつ（無ければ省く） |
| 7 | 優先度の根拠 | 値と根拠1行 |

issue だけ読めば、誰がやっても同じ対象を同じ基準で扱えるように書く（対象の数え方・完了の判定・何をどう測るか）。

## ラベルと欄

- 種類は Issue types（不具合・要望・保守・調査）で1つ。
- 優先度（高・中・低）と着手可能日は Project の欄で、`field.js` で読み書きする。高は利用者に届いている不具合・データの誤り・止まっている流れ、低は調べ・整理・見た目の小さな直し、それ以外は中。誰も決めていない優先度は空のまま。
- 着手可能日は、その日（日本時間）より前に振り出さない日。
- ラベルは「急ぎ」（ユーザーの依頼。振り出しの先頭）と「開発機が要る」。ステータスはラベルに写さない。

## コミット

1タスク（段階なら1段階）＝1コミット。master に入るコミットは PR の題名と本文から作られる。書式:

    tasks#<番号>: <何が変わったか（1行。利用者・運用から見た結果）>

    背景: <なぜ必要だったか>
    課題: <何を直す・作るか。約束の差分（足した・消した・変えた約束を1行ずつ）>
    成果: <何が変わったか>
    検証: <実行したコマンドと観測値>
    増減: <python scripts/review_checks.py change の出力の行>
    残り: <このタスクに残るもの。無ければ「なし」>
