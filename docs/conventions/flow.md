# タスクの流れ

タスクは GitHub の issue、段階は sub-issue である。ステータスはタスクだけが持ち、Project の欄「Status」に置く。
ステータスの移り変わりと割り当ては**遷移の表**（`tools/flow-gate/flow.config.json: transitions`）だけが決め、
ゲート（`tools/flow-gate/`）が GitHub の出来事を受けて表で照らす。表に無い変化は、誰が起こしてもゲートが前へ戻して
理由をコメントする。人（hidakagit）の判断は、回答フォームで明確な選択肢を選んで行う。

## 置き場と役割

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリと Project（`flow.config.json: repository`・`project`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 表で次のステータスと割り当てを決めて書く。表に無い変化を戻す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメントを書く・実施の順番・検証中の確かめ・Project の欄の規模・ラベル（操作） |
| hidakagit | 回答フォームで答える。GitHub の画面で何を動かしてもよい（表に無ければゲートが戻す） |

- Claude は GitHub の置き場へ、hidakagit-bot のトークン（ユーザー環境変数 `FLOW_BOT_TOKEN`）でだけ書く。hidakagit の
  トークンで書かない——hidakagit に通知が届かず、ゲートが hidakagit の操作と見分けられなくなる。
  gh で書くときは `GH_TOKEN` に `FLOW_BOT_TOKEN` の値を渡す。
- ゲートは自分の書き込み（送り主 `flow.config.json: gate`）を無視する。組み込みの自動化「Auto-add to project」が
  issue を Project に入れると、ゲートが入口（下）を処理する。

## ステータスと割り当て

ステータスの名前・意味の並びと表は設定ファイルが正本で、ここに写さない。読み方だけを書く。

- **入口**（`entry`）: issue を書いた人で決まる。hidakagit が書いた issue は未着手で hidakagit-bot に、それ以外
  （Claude が書いた提案）は採否待ちで hidakagit に割り当てる。採否の問い（`adoption`）は決まった中身なので本文に書かず、
  回答フォームが設定から出す（採否待ちで本文の先頭に Claude の問いがあれば、そちらが今の問い）。段階は入口にしない。
- **遷移**（`transitions`）: `from` から `to` へ動けて、`assign` がそのときの割り当ての既定（`null` は今のまま）。
  `when: blockersCompleted` の行は、前提（blocked by）が全部 completed で閉じているときだけ通る。
- **割り当て**: 回答フォームを通らない変化は表の既定、回答フォームを通る変化はフォームで選んだ「次に動くのは」。
  検証中だけは、ラベル `ユーザー確認`（`verify.label`）があればユーザー（`ask.answerer`）にする。このラベルは回答フォームの
  ラベルの欄で付ける（hidakagit が書いた issue のように問いを通らないものは、GitHub で手で付ける）。
  開いているタスクには常に hidakagit か hidakagit-bot の1人が割り当たる。**hidakagit-bot に割り当たったものが Claude の番**。
- **完了**: 閉じた理由（completed＝完成／not planned＝見送り）で分ける。Claude は master へ入れたら issue を
  completed で閉じる。開いた段階が残っていれば、ゲートが最初の段階だけを閉じてタスクを `nextStage` へ戻す。
  ボードで完了へ動かしたもの・回答フォームで完了を選んだものは、見送りで閉じる。完了からは戻せない（続きは新しい issue）。

## Claude がステータスを動かす

    node tools/flow-gate/bin/move.js <issue の番号> <ステータス>

表で通らない変化は書く前に断る。回答待ちへ動かすときは、今の問い（「問い」の節）が形に合わなければ断る。
問うときは move.js ではなく `ask.js`（「問い」の節）を使う。
Claude の番を振り出す順に並べて出すのは `node tools/flow-gate/bin/queue.js`（`--json` で機械向け）。

## 司令塔と担当（Claude が自分の番を進める）

Claude の番（hidakagit-bot に割り当て）は、司令塔が担当へ振り出して進める。司令塔は起動のたびに空いた作業ツリーを埋めて
終わり、自分では作業せず、状態は issue とゲートだけが持つ（司令塔は自分の表を持たない）。

- **起動**: この PC の予定のタスク（Desktop の Routines の `ridecompass-coordinator`）が司令塔のセッションを起こす。
  アプリが開いていて PC が起きている間だけ動く。前の回のセッションが動いている間は次の回を飛ばすが、背景の担当を待って
  いる間はセッションが動いていない扱いになり、次の回が起きる。そのため司令塔は担当を待たずに終わり、終わったあとに届いた
  担当の報告では何も動かさない（二つの司令塔が同じ作業ツリーへ振り出さないため）。空いた作業ツリーは次の起動が埋める。
- **作業ツリー**: 本体の `.claude/worktrees/` に、司令塔用の `coord` と担当用の `w1`〜`w4` を置いたままにして使い回す
  （frontend の依存の入れ直しを毎回しないため。`node_modules` の共有は CLAUDE.md で禁止）。どれをどの issue が
  使っているかは `node tools/flow-gate/bin/slots.js` が、作業ツリーのブランチ・issue のステータス・ステータスが変わってからの
  時間・Project の規模の欄からその場で組み立てて出す（表は持たない）。担当を一度に動かすのは最大4人。
- **重い処理は機械全体で1本ずつ**: 依存の入れ直し・型検査・テスト・ビルド・e2e は `python scripts/heavy.py -- <コマンド>`
  で包む（同時に走ると CPU とディスクを取り合って1本ごとの所要が何倍にも伸びる）。

**司令塔の1回**
1. `coord` を `git fetch origin master` のあと `git checkout --detach origin/master` にし、そこでこの節を読み直す。
2. `node tools/flow-gate/bin/queue.js --json` で Claude の番を読む（並びは Claude に戻った採否待ち・回答待ち → 検証中 → 未着手、
   中はラベル「急ぎ」（ユーザーの依頼。優先度の欄より上。`project.urgentLabel`）→ Project の優先度の欄の選択肢の順 → 番号の若い順）。
3. `slots.js` で空いている作業ツリーを見て、その数まで上から振り出す。
   採否待ち・回答待ち（Claude に戻った問い）は、ステータスを動かさずに作る担当へ渡す（担当は答えや補足を読み、提案か問いを
   直して hidakagit に割り当て直すか、表のとおり動かす）。検証中は確かめる担当へ、未着手（前提待ちでないもの）は
   `node tools/flow-gate/bin/move.js <番号> 進行中` のあと作る担当へ渡す。担当は背景の Agent で起動し、作業ツリーの
   パスと issue の番号を渡す（司令塔が渡す固定の作業ツリーを使うので、`isolation` は付けない）。
4. 振り出したら、担当の報告を待たずに終わる。
5. `slots.js` で、ステータスが変わってから4時間を超えて進行中・検証中のままの作業ツリーは、担当が落ちた（PC の再起動等）と
   みなし、その issue にコメントで書いて `move.js` で 保留 にする（作業ツリーの変更は消さない。hidakagit が棚卸しで決める）。

**作る担当**・**確かめる担当**のどちらも、作業は渡された作業ツリーの中だけで行う（ほかの作業ツリーや本体では、ファイルの
編集も git の操作もしない。ほかの作業ツリーは別の担当が使っていて、変更を残すとその作業に混ざる）。

**作る担当**
1. 渡された作業ツリーで、未コミットの変更が無いことを確かめてから `git fetch origin master` と
   `git checkout -B orch/tasks-<番号> origin/master`。変更が残っていれば、何もせず司令塔へ報告する。
2. `frontend/package-lock.json` が前の回と違えば、`frontend` で `python ../scripts/heavy.py -- npm ci`。backend は
   作業ツリーに `.venv` を持たず、本体の `backend/.venv` の Python を使う（依存は共有してよい）。
3. issue の本文とコメント（やり直しなら、前の Pull Request のコメントも）を読み、CLAUDE.md と規約のとおりに作る。
   hidakagit の判断が要るところは「問い」の形で書いて `ask.js` で問い、そこで終える（答えは次の起動で拾われる）。
4. `tasks#<番号>:` の件名でコミットし、`orch/tasks-<番号>` へ push して CI を待つ（競合で作り直すときは master の上へ
   rebase して push し直す。作業ブランチは書き換えてよい）。
5. CI が通ったら、コードのリポジトリに Pull Request を出す（`gh pr create --base master --head orch/tasks-<番号>`。
   コードのリポジトリは hidakagit のものなので、`GH_TOKEN` に hidakagit のトークン（ユーザー環境変数 `GH_TOKEN`）を渡す）。
   件名はコミットと同じ、本文は次の順に書く:
   - 置き場の issue へのリンク（`https://github.com/ridecompass/ride-compass-tasks/issues/<番号>`）と、何が変わったかの1〜3行
   - 修正前後のキャプチャ（`--attach <前の画像>` と `--attach <後の画像>`。画面・幅など、何を撮ったかを添える）
   - 画面に出ない変更は、確かめ方と根拠（実行したコマンドと出た値・読んだ公式の文書）
   - `backend/scripts/lost_constraints.py`（master との合流点からの、ORM の宣言から消えた制約）が出した「消えた」の
     1件ずつに、処置（移した先・意図して外した理由）。書き直しで落ちた制約は差分に1行も出ないため
   前の Pull Request が開いたまま残っていれば、新しく出さずに push し、撮り直したキャプチャを `gh pr comment --attach` で足す。
6. issue の本文を直し（経緯・完了の条件のチェック）、Pull Request へのリンクをコメントに書いて、`move.js <番号> 検証中` にして
   報告する。確かめる番は、ラベル `ユーザー確認`（`flow.config.json: verify`）があればユーザー、無ければ Claude
   （確かめる担当）になる（ゲートが割り当てる）。

**Pull Request のあと**（ゲートが、コードのリポジトリの Webhook から届く Pull Request と CI の出来事で動かす）
- マージされずに閉じた → 未着手（閉じたときのコメントを作る担当が読んでやり直す）。master と競合して Merge が押せない
  ときも、確かめる人が「競合」と書いて閉じる（競合を知らせる出来事は GitHub に無い）
- マージされた → マージのあとの master の CI を待ち、通れば完了で閉じ、落ちれば落ちた実行を書いて未着手
- Claude も司令塔も、これらを自分で動かさない（`move.js` を使わない）。
- GitHub は届かなかった出来事を送り直さない。マージや CI のあとも検証中のまま止まったものは、コードのリポジトリの Settings →
  Webhooks → Recent Deliveries から Redeliver する（3日分まで）。

**確かめる担当**（ラベル `ユーザー確認` の無い検証中。作った担当とは別）
1. Pull Request（本文のキャプチャ・差分）・作業ブランチの CI・issue の完了の条件・変更が届く範囲（要るなら画面）を
   確かめる。作る担当の報告を読み写さず、自分で見る（画面なら自分で撮る）。Pull Request が無ければ（手順が変わる前に
   検証中になったもの）、作る担当の5のとおりに出してから確かめる。`lost_constraints.py` も自分で回し、「消えた」の
   1件ずつに本文の処置があるかを見る（処置の無いものが1件でもあれば満たしていない）。
2. 確かめた結果を、満たしていてもいなくても issue にコメントで書く（見出し「確かめた結果」）。完了の条件の1件ごとに、
   何をどう見て（実行したコマンド・開いた画面）何が出たかを書き、撮った画面は Pull Request へ `gh pr comment --attach` で貼る。
   ここに書いたことだけが、確かめた証拠として残る。
3. ユーザーが見るべきだと判断したら（利用者から見える振る舞い・モジュールの設計が変わる等）、issue にラベル `ユーザー確認` を
   付け、理由を書いて hidakagit に割り当て直して終える（本文の先頭に Pull Request を開くボタンが出る）。
4. 満たしていなければ、足りないことを書いて Pull Request を閉じる（`gh pr close <番号> --comment <理由>`）。ゲートが未着手へ戻す。
5. 満たしていれば Pull Request をマージする（`gh pr merge <番号> -R hidakagit/ride-compass --rebase`。Claude Code の許可の
   規則 `gh pr merge *` に合う形なので、この書き方のまま打つ。ほかの書き方や API の呼び出しは許可の判定で止まる）。
   master の CI は待たない（ゲートが閉じる）。
   競合でマージできなければ、「競合」と書いて閉じる（4 と同じ）。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当が自分でしない。
`操作` のラベルを付け、hidakagit に頼む問い（手順と、確かめ方）を `ask.js` で問う。

## 問い

hidakagit に求めることは、採否・判断・操作のお願い・確認のどれも、次の形でファイルに書き、道具で問う（hidakagit-bot の名義）。

    node tools/flow-gate/bin/ask.js <issue の番号> <問いのファイル>

道具は形を照らしてから、問いを本文の先頭（ゲートの印の間）に画面に出ない形（HTML のコメント）で書き、回答待ちへ動かす
（もう回答待ち・採否待ちなら hidakagit に割り当て直す）。hidakagit の番の間は、ゲートがその下へ「回答する」のボタンの
画像（リンク付き。スマホのアプリでも押せる）と、ステータス・問いの文の1行を置く（コメントは古い順にしか並ばず、一番下は
見落とすため。GitHub の画面そのものにはボタンを足せない）。選択肢と判断材料は回答フォームで読む。

    ## 問い
    <問いの文（1行）>

    ### 選択肢
    - <文> → <次のステータス> / <次に動く者>
    - <文> → <次のステータス>
    - <文>

    <details><summary>判断材料</summary>
    （この問い1つだけで判断できるように書く）
    </details>

- 今の問いは、本文の先頭にある1つだけ。問い直すと置き換わり、答えるとゲートが本文から消す。`-->` は書けない
  （問いを隠す HTML のコメントが途中で閉じる。道具が断る）。
- 答えを待っているのは、採否待ち・回答待ちで hidakagit に割り当たっている間。答えるとステータスか割り当てが必ず変わる
  （今のままになる答えは Claude の番になる）ので、答えたあとに回答フォームは開かない。
- 選択肢は2つ以上で、判断そのものだけを書く。`→` の後ろは要るときだけ書く: 次のステータス（設定の名前）・次に動く者
  （`people` の `shown`。Claude か hidakagit）。ラベルは選択肢に書かない（回答フォームのラベルの欄で付ける）。
  書かなければ、次に動く者は表の既定。ステータスは、回答待ちの問いなら未着手へ進み（`flow.config.json: afterAnswer`。
  答えたのに回答待ちに残さない）、それ以外は今のまま。今のままになる答えのあとに動けるのは Claude だけなので、
  回答フォームは次に動く者を選ばせない。
- 回答フォームは「その他（コメント）」を足し（`formOptions`）、表で行けない選択肢は出さない。
  選択肢とは別に、置き場のリポジトリに GitHub で定義されているラベルを全部、今の付き方のまま並べ、
  付け外しをそのまま効かせる（答えのコメントに「ラベル: +… −…」を残す）。札を足すときは GitHub でラベルを作るだけでよい。
  「その他」も行き先を書いていない選択肢と同じで、回答待ちは未着手へ進み（Claude が補足を読んで次を決める）、採否待ちは
  採否が決まらないまま Claude の番になる（Claude が補足を読んで提案を直し、`ask.js` で採否を問い直す）。
- 答える時点で答えられることだけを聞く。
- **聞くかどうか**: 外から見える振る舞いが変わるときだけ聞く。変わらないなら聞かずに報告して直す。聞いたら答えを待つ。
- **書く順**（判断材料の中）: 利用者への約束を1文 → 問題が起きる場面を1つと、起きない場面を1行 → 選択肢ごとに
  利用者に何が起きるか。背景を知らない人がこの問い1つだけで判断できるように、何の画面・機能の話か・いまどうなって
  いるか・なぜ決める必要があるかを入れる。画面の見た目・情報量に関わる判断は、変更前と変更後の画面かモックを添える。
- **製品の言葉で書く**: 実装の語（関数名・引数名）・固有名詞・タスク番号に頼らない。
- **選択肢**: 自分の領分（どう直すか・書き方）を選択肢に入れない。選択肢の文と実際に当てる作業を一致させる。
  推奨は判断材料の最後に理由と一緒に書く。回答フォームで完了を選ぶと見送りで閉じるので、完成を問いで決めない。
- 形が崩れた問いのまま回答待ちになると、ゲートがそう書いて hidakagit-bot に割り当てる。書き直してから
  hidakagit を割り当て直す。

## 答え

回答フォームが hidakagit の名義で次のコメントを書く。問いは答えると本文から消えるので、問いの文・全部の選択肢・判断材料も
ここに残す（このコメント1つで、何を問われて何を選んだかが読める）。Claude はこれだけを読み、チャットでの答えを判断に
使わない。補足は決定を変えない。

    ## 回答
    **<問いの文>**

    ○ <選ばなかった選択肢>
    ● **<選んだ選択肢>**

    次のステータス: <名前>
    次に動くのは: <Claude／hidakagit>
    ラベル: +<付けたもの> −<外したもの>（変えたときだけ）
    補足: <書いたときだけ>

    <details><summary>判断材料</summary>（問いにあったときだけ）</details>

## issue の形

**題名**は、何をするか（または何が困るか）だけを30字前後で書く。数値・経緯・やり方・括弧書きの補足は本文へ。

**本文**は次の節をこの順に並べ、1 以外は `<details><summary>節の名前</summary>` で畳む。節ごとに「答える問い」が1つだけあり、
それに当たらないものはその節に書かない。

| 順 | 節 | 答える問い | 書くもの | 書かないもの |
|---|---|---|---|---|
| 1 | 要約（畳まない） | 開いて2行で何が分かるか | 何が起きていて、何をするか（1〜2文） | 経緯・数値の詳細 |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | なぜやるのか | 事実（誰がどの場面で何に困るか。不具合なら再現の手順と、期待する動き・実際の動き）。保留中は最後に「再開の条件」 | 案・やり方 |
| 3 | やること（調査は: 調べ方） | どうやるのか | 案と手段。番号付き。段階があれば段階ごと | なぜやるかの事実 |
| 4 | 決めること | まだ決まっていないことは何か | 決まっていないことを1行ずつ（問うのは1度に1つ。問うているものは本文の先頭にある） | 決まったこと（→ 6）。無ければ節ごと省く |
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる形のチェック（`- [ ]`） | 手段 |
| 6 | 経緯 | いつ何が決まり、何が変わったか | 日付つきで1行ずつ、新しいものを上に。無ければ省く | 問いと答えの全文（答えのコメントにある） |
| 7 | 規模の根拠 | 規模の札の根拠 | 札と根拠1行 | ― |

- 節の中では、並べるものは箇条書きにし、長い段落を作らない。複数の案や観点を比べるときは表にする。
- `<details>` の中は、`<summary>` の行のあとに空行を1つ入れてから書く（入れないと Markdown が効かない）。
- 問いに答えが出たら、Claude は 4 からその行を消し、6 へ1行足す（本文だけ読めば今の状態が分かるように）。
- hidakagit が GitHub の画面で種類のテンプレート（置き場の `.github/ISSUE_TEMPLATE/`）から作った issue は、節が
  見出し（`###`）で並ぶ。Claude は着手するときに、この形（畳む節）へ整える。

## ラベルと種類と欄

- 種類は Issue types（不具合・要望・保守・調査）で、1つのタスクにちょうど1つ。
- 1つのタスクに1つの値を持つもの（Status・優先度・規模）は、Project の単一選択の欄に置く。スマホの GitHub アプリでも
  issue の ⓘ →「プロジェクト」に出る（組織の issue fields は出ないので使わない）。優先度は仕事としての重さの見積もりで、
  入口でゲートが既定の値（`flow.config.json: project.defaults`）を入れ、Claude が起票するときは CLAUDE.md「優先度の見積もり」で
  入れる（ユーザーが直してもよい）。司令塔はその選択肢の順に並べる。規模は Claude が `field.js` で入れる。
  欄は機械が決めるものなので、回答フォームには出さない（ユーザーが直すときはボードで）。選択肢を足せば並べ順はそのまま効く。
- ステータスは Project の Status だけが持ち、ラベルに写さない。動かすのはボード・回答フォーム・move.js・ask.js。
- ラベルは自由に付ける札（例: 急ぎ・操作・ユーザー確認）。「急ぎ」はユーザーの「急いで」の依頼で、司令塔は優先度の欄より先に並べる。回答フォームは、置き場に定義されたラベルを
  名前を持たずに全部出す。規模の決め方は CLAUDE.md「規模の札」。前提は blocked by で付ける。
- 状態を動かしただけのコメントは書かない。本文と判断材料の詳細は `<details>` に入れる。

## コミット

件名は `tasks#<issue の番号>: <issue の題名>`。本文の行（背景・課題・成果・検証・増減・残り）は CLAUDE.md
「コミット時の同期ルール」のとおり。

## ゲートを変える・公開する

表・入口・問いの形の選択肢は `flow.config.json` を直す。公開は `tools/flow-gate` で `wrangler deploy`（Webhook）と
`wrangler deploy --env form`（回答フォーム）。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`（CI の `flow-gate` も同じ）。
