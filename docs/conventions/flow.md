# タスクの流れ

## 原則

流れ（タスクの進め方・ゲート・担当・道具・この手順書と流れのスキル）の決まりは、[CLAUDE.md](../../CLAUDE.md)「原則」から導く。各節の先頭の「導く原則」は、その節の決まりをどの原則から導いたかを、原則の番号で示す。

## 流れのあらまし

導く原則: 3。

タスクは GitHub の issue である。1つの Pull Request に収まらないタスクは段階に分け、段階も同じ形の issue（親の sub-issue）に
する（.claude/skills/file-issue/SKILL.md「段階に分ける」）。ステータスは段階も含めてどの issue も持ち、Project の欄「Status」に置く。
**ステータスはゲート（`tools/flow-gate/`）が事実から決める**。事実は、issue（開き閉じ・本文の完了の条件・問いと答え・前提・
着手可能日時）と、作業ブランチの Pull Request（下書きか・CI・差し戻し）と、担当の実行の有無で、決め方は1つ
（`tools/flow-gate/src/decide.js: decide`）。同じ事実からは何度決めても同じになり、ゲートは今の値と違う所だけを書く。Claude は
ステータスを書かない。ユーザーがボードで書くのは保留へ入れる・出すだけで、ほかの移動はゲートが事実から決め直す。
仕組みが守るのはステータスまでで、それぞれの状態で何をするかは、この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）の手順が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリ（`flow.config.json: tasks`）と2つのボード（`flow.config.json: boards`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない。Actions のボードは担当が進めるタスク、対話作業のボードは issue の種類「対話作業」（`flow.config.json: dialogType`）の、開発機の対話のセッションだけが進めるタスク |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事を受けて事実を読み、ステータス・担当者・本文の先頭のボタン・ボード・種類・優先度を決めて書く。担当を振り出す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメントを書く・段階と前提を張る・検証待ちの確かめとマージ・Project の欄の規模と優先度と着手可能日時 |
| ユーザー（hidakagit） | 判断を回答フォームで答える（開発機の対話のセッションではチャットで。.claude/skills/ask/SKILL.md「答え」）。本番での最後の確かめ。保留へ入れる・出す。ラベル（`急ぎ` 等）を付け外しする |

- Claude が置き場へ書く名義とトークンは「担当」の「名義」が持つ（開発機の対話のセッションも同じ）。
- ゲートは自分の書き込み（送り主 `flow.config.json: gateBot`）を無視する。issue をボードへ入れるのもゲートで、種類が対話作業なら
  対話作業のボードへ、ほかは Actions のボードへ入れる。種類は作るときに決まり、対話作業の境目をまたいで変えるとゲートが戻す。

## ステータスと割り当て

導く原則: 1・2・3・4。

ステータスの名前と並びはボードの選択肢が、決め方は `tools/flow-gate/src/decide.js: decide` が正本で、ここには読み方だけを書く。

- **誰の番か**: 回答待ち・保留はユーザーの番で、ゲートが担当者の欄にユーザーを入れる。ほかは Claude の番。
- **入口**: ボードに入ったとき、Claude が起こした要望（段階でないもの。何を作るかは原則1のユーザーの判断）は回答待ちにし、ゲートが
  採否を問う。ほかは未着手で入る。段階は優先度の欄が空なら親の優先度を継ぐ。
- **持たれている間**: 担当の実行（始まる前の順番待ちを含む）がある間は、作るなら進行中、確かめるなら検証中で、決め直さない。
  ユーザーが保留へ置いたら、ゲートがその実行を取り消す。
- **保留**: ユーザーが置いた保留（ボードの移動・問いへの答え）は、ユーザーが出すまで保つ。
- **問い**: 最新の「## 問い」のコメントが形（.claude/skills/ask/SKILL.md「問い」）に合い、答えが無ければ回答待ち。形に合わない
  問いは問いとして読まない。答えが来たら、見送りは閉じ、保留は保留にし、確かめは項目ごとに読み（よくない項目は「直す: …」の行を
  完了の条件に足して未着手、全部よければ確かめの行にチェックを付ける）、ほかは下の手放したあとの決め方へ進む。
- **手放したあと**: 作業ブランチの Pull Request が下書きなら、CI が終わるまで CI待ち、通れば検証待ち（ゲートがレビュー可能にする）、
  落ちたか変異テストに新しい生き残りが出たら未着手。確かめる担当が下書きへ戻したら未着手。レビュー可能なものは検証待ち。
  Pull Request が無ければ、残りが無いなら完成で閉じ、残りが全部ユーザーの確かめの行なら回答待ちにしてゲートが確かめを問う。
  担当が問いも Pull Request も出さず、残りも済ませずに手放したら（マージ済みの Pull Request が無いとき）、回答待ちにしてゲートが
  何が起きたかを問う（イレギュラー）。それ以外は未着手。
- **完了**: 閉じた理由（completed＝完成／not planned＝見送り）で分ける。完成で閉じても残り（下）があれば、ゲートが開き直す。
  見送りは残りを問わない。続きは新しい issue にする。
- **残り**（`tools/flow-gate/src/questions.js: remaining`）: 本文の完了の条件のうちチェックの無いもの。ゲートはラベルを見ない。ユーザーに
  確かめてもらうことも、完了の条件の1行（`- [ ] ユーザーが確かめる: …`）として書く。
- **本文の先頭**: 回答待ちの間だけ、ゲートが回答フォームへのボタンを1つ置く（ゲートの印 `<!-- flow-gate -->` の間）。
  それ以外のときは何も置かない。

**1つのタスクを触るのは1者だけ**。担当は振り出しでだけ起き、同じ issue の実行は担当のワークフローのグループ
（`.github/workflows/claude-task.yml` の `concurrency`）で1本ずつ動き、あとから来たものは取り消されずに順に待つ（`queue: max`）。
実行のあるタスクは振り出さない。開発機の対話のセッションは、対話作業の段階を前提に張って持つ
（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。

## 担当（Claude が自分の番を進める）

導く原則: 1・3・4・5。

役割は次のとおりに分ける。どの役も、ほかの役の持ち物を持たない。作る担当・確かめる担当の手順は .claude/skills/task-work/SKILL.md にある。

| 役 | 持つもの・すること |
|---|---|
| GitHub（issue・Project・ゲート） | タスクの状態（ステータス）。ゲートが事実から決め、担当を振り出し、定時に突き合わせる |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 準備をして担当を起こし、終わったら後始末をする |
| 作る担当・確かめる担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（PR・問い・issue へのコメント）。次の担当を起こすことには触れない |

**キュー**（仕事の並び）は GitHub のステータスから毎回導くもので、どこにも別に持たない。

- **枠**: 作る担当と確かめる担当で、別々の上限（`flow.config.json: slots`）を持つ。貸し借りしない。使っている数は動いている実行の数。
- **振り出す条件と順**（`tools/flow-gate/src/decide.js: dispatchable`・`tools/flow-gate/src/dispatch.js: dispatch`）: 作るは未着手、
  確かめるは検証待ちのタスク。前提が開いている・着手可能日時（.claude/skills/file-issue/SKILL.md「ラベルと種類と欄」）が今（日本時間）より先・
  対話作業・実行がある、のどれかに当たるものは除く。並びはラベル「急ぎ」（ユーザーの依頼）→ 優先度の欄の選択肢の順
  （空は `flow.config.json: unsetPriority` の位置）→ 番号の小さい順。振り出すのは、担当の実行が終わったとき・タスクが振り出せる
  ステータスになったとき・突き合わせのとき。
- **突き合わせ**（`tools/flow-gate/src/dispatch.js: mismatched`）: ゲートが定時（`tools/flow-gate/wrangler.toml` の `triggers`）に、作業のステータスなのに実行が無い・実行があるのに作業の
  ステータスでない・CI待ちのタスクを決め直し、空いた枠へ振り出す。ゲートが出来事を取りこぼしたときの守り。
- **担当のワークフローの1回**:
  1. 振り出し: ゲートが担当のワークフローを `workflow_dispatch` で起こす。実行の名前「#<番号> <種類>」から、ゲートがどのタスクの
     どの担当かを読む。
  2. 準備（`.github/workflows/claude-task.yml` の段）。
  3. 担当を起こす。持ち時間はジョブの `timeout-minutes` で、超えると Actions がジョブを止める。担当の実行は、担当が手番を終えた
     最初の発言で終わる。裏で動かす道具（Bash の `run_in_background`・Monitor・ScheduleWakeup・
     cron の道具・Workflow）は担当のワークフローが外してある（`claude_args` の `--disallowedTools` と環境変数
     `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）。担当が待つときは、終わるまで前に出したまま待つ。起こす指示（`claude-task.yml` の
     `prompt`）は、役・作業ツリー・issue の番号と読む節だけを渡し、決まりも環境の説明も写さない（出どころは
     .claude/skills/dev-session/SKILL.md「開発機の対話のセッション」の「決まりの出どころ」）。
  4. 後始末（担当が落ちても止められても走る。ステータスは書かない。実行の終わりの出来事で、ゲートが決める）: 作る担当の GitHub に
     無い変更（未コミットの変更・push していないコミット）は `wip/tasks-<番号>-<時刻>` の枝へ残す（作業ブランチは書き換えない）。
     そのあと、手番の記録（実行のファイル）を gzip して置き場のリリースへ置き（リリースは日（UTC）ごとに1つ）、issue に
     終わりのコメントを書く（`.github/claude-task/after.js`）。担当が Claude の利用の上限・認証（担当の発言の `error`）で止まったなら、
     最後の段（`flow.config.json: quotaStep`）を落とす。ゲートは、最後に終わった担当の実行でこの段が落ちていれば、その終わりから
     `flow.config.json: pauseMinutes` の間振り出さない。読み手は後から確かめるユーザーと後の担当（作る・確かめる・
     開発機の対話のセッション）。書くのは、担当の最後の発言（担当が書く要約。.claude/skills/task-work/SKILL.md「作る担当・確かめる
     担当の終え方」）・後始末がしたこと・判定に断られた操作（あるときだけ）・実行へのリンクだけで、issue と実行のページで読めるもの
     （ステータス・ジョブの結果・時間・手数）は写さない。PR も報告も出さずに終わった担当の理由は、この最後の発言で読む。
- **名義**: 置き場へは hidakagit-bot（secret `FLOW_BOT_TOKEN`）、コードのリポジトリへは hidakagit（secret `CODE_TOKEN`。
  `GITHUB_TOKEN` で打ったマージは master の CI とデプロイを起こさないため）、Claude は契約のトークン（secret `CLAUDE_CODE_OAUTH_TOKEN`）。
  どのトークンがどこへ届くかは docs/architecture/tech-stack.md「秘密の値とトークン」が持つ。Claude は置き場へ hidakagit-bot の
  トークンでだけ書き、hidakagit のトークンで書かない（開発機の対話のセッションでは、同じ値をユーザー環境変数 `FLOW_BOT_TOKEN` に持つ）。
  `CODE_TOKEN` はコードのリポジトリにだけ届き、置き場に届かない。担当のワークフローは gh の既定（`GH_TOKEN`）に `CODE_TOKEN` を
  置くので、gh で置き場を打つときは、読むときも `GH_TOKEN=$FLOW_BOT_TOKEN` を付ける（担当は付け忘れると断られる。開発機の対話の
  セッションは gh の既定が hidakagit で、付け忘れると hidakagit の名義で書かれうるので、必ず付ける）。名義の誤りを止めるのはこのトークンの範囲だけ（gh はトークンをホストごとにしか選べず、権限の拒否の
  規則は先頭の変数の代入を越えて当たるので、付けた打ち方と付け忘れた打ち方を見分けられない）。
- **止める**: Claude Task を無効にする。ゲートは担当のワークフローが無効なら振り出さない。ユーザーがチャットで頼めば、開発機の対話のセッションが
  `gh workflow disable "Claude Task" -R ridecompass/ride-compass` で打つ（ユーザーが Actions の画面の Disable workflow で打ってもよい）。
  戻すときは `gh workflow enable "Claude Task" -R ridecompass/ride-compass`（画面なら Enable workflow）で、次の突き合わせから振り出す。
  担当は止める・戻すを打てない（下の「担当の権限」の拒否の一覧）。
  利用の上限で止まった振り出しを早く戻すなら、担当を1件手で起こす（`gh workflow run claude-task.yml`。終われば、それが最後の実行になる）。動いている担当は止まらないので、止めるなら Actions の画面でその実行を Cancel する
  （後始末の段は走る）。1つのタスクだけを止めるなら、ボードで保留へ動かす（ゲートがその実行を取り消す）。
- **開発機でしかできない作業**: 開発機にしか無いもの（本番への調べ `run_probe.py` の SSH の鍵・開発 DB の実データ）が要る作業と、担当が
  しない操作（「自動で進めないもの」「担当が書けないファイル」）は、Actions では進めない。担当は、それが要ると分かったところで作業を止め
  （途中の変更は作業ブランチへ push してから）、何がなぜ要るかを本文に書いた対話作業の段階を起こして元のタスクの前提に張り
  （.claude/skills/file-issue/SKILL.md「段階に分ける」）、終える。開発機の対話のセッションが段階を進めて閉じると、元のタスクがまた振り出される
  （.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。ユーザーが同じように段階を起こしてもよく、Actions の担当の進め方が
  合わないと判断したタスクを開発機の対話のセッションへ引き取る口になる。

**担当の権限**: 担当は自動モードで動き、操作の可否は判定役が1回ずつ決める。判定役には `.github/claude-task/settings.json` の
`autoMode` で、担当の置かれた環境（2つのリポジトリがユーザーのもの・担当は使い捨てのランナーの無人の作業役 等）と日常の操作
（作業ブランチへの push と Pull Request を出す・タスクの issue を読む・コメントする・閉じる・段階を起こす・Project の欄を書く 等）を
教える。決して打たせない操作（master への push・強制の push・GitHub の API での書き込み・ワークフローを止める・止めたのを戻す等）は、
同じファイルの `permissions.deny` で断る（拒否は判定役より先に効く）。ユーザーの答えが要る変更（規模の閾値の数を変える
`scripts/size_thresholds.json` の編集）は `permissions.ask` に置く（どのモードでも自動では通らず、
担当には確かめる人がいないので通らない。Python 等のスクリプトの中の書き込みには当たらない）。拒否の規則はコマンドの文に当て、読むだけでも
`-X`・`-f` 等の付いた `gh api`（`-X GET` に `-f` で欄を渡す一覧・`gh api graphql`）は断られる。つないだコマンドは全文にも当たるので
（`git push … ; gh pr create --base master …` は `Bash(git push *master*)` に当たる）、規則の頭の道具（`git push`・`gh api`）はつながずに1つで打つ。読むときは欄を URL に書き
（`gh api 'repos/<所有者>/<リポジトリ>/actions/workflows/<ファイル>/runs?created=<範囲>'`）、`gh run list`・`gh issue view --json`（`blockedBy` 等）で済むものはそれを使う。自動モードそのものも同じファイルの `permissions.defaultMode` で
決める。各一覧は既定の規則（`$defaults`）を必ず残す。担当は連携の `settings` で
このファイルを読む（連携は中身をランナーのユーザー設定へ書く）。このファイルは担当だけのもので、master に入った次の担当の実行から効く
（作業ブランチで直しても、作業中の自分の権限は変わらない）。開発機の対話のセッションはこのファイルを読まない: 判定役への説明と
自動モードは使う人が決めるもので、Claude Code はリポジトリの設定から読まない（公式の文書「Configure auto mode」）。開発機の
対話のセッションの権限は、使う人であるユーザー自身の設定（`~/.claude/settings.json`）が持ち、リポジトリからは書かない（変えるときは、
Claude が案を見せ、ユーザーが名指して入れる）。担当にも開発機にも効かせたい守りは、Claude の設定ではなく、Claude が変えられない
GitHub の側（ルールセット・トークンの権限）に置く。
判定役が自分を動かす設定の書き換えとして編集を断ったら、「担当が書けないファイル」のとおりにする。日常の操作が断られたら、
回り込まず（別の道具・別の名義で打たない）、流れの摩擦として記録する（.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」。直すのは `autoMode` の説明）。断られた操作は、後始末の終わりのコメントの
「判定に断られた操作」に、道具と打とうとしたものが出る。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（本番の接続情報も持たない）。
要るときは、書く中身（打つスクリプト・対象・前後に読んで比べるもの）を作業ブランチか issue のコメントに置き、「開発機でしかできない作業」の
とおり返す。開発機の対話のセッションが.claude/skills/dev-session/SKILL.md「本番へ書く」のとおり進める（Claude が打てない操作を原則1のとおり
ユーザーに頼むのも、開発機の対話のセッションのチャットで渡す）。ユーザーに打たせる問いにしない。
マージの前に済ませる本番への書き込み（コードが新しく読む表を作る等。.claude/rules/deployment-sync.md「コミットと同時に揃えるもの」）が
要る変更は、作る担当が Pull Request を出す前に返す（出すとゲートが検証待ちにし、確かめる担当がマージする）。作ったコードは作業ブランチへ
push し、書く中身はそのコードから出す。書き込みが済んで段階が閉じると、次の作る担当が作業ブランチから続けて Pull Request を出す。
Claude が持たない権限の操作（クラウドの画面・外部サービスの登録・GitHub のリポジトリの設定やトークン）だけは、問う（.claude/skills/ask/SKILL.md「問い」）。
問いの文の頭に「PC での操作:」と書き、判断材料に手順と確かめ方を書く。
済んだら「済んだ」、できなければ補足に理由を、と案に書く。済んだと答えが来たら、Claude が確かめ方のとおりに
確かめ、完了の条件にチェックを付ける。

**担当が書けないファイル**: Claude Code の自動モードの判定は、CLAUDE.md・`.claude/` の設定・権限（`.github/claude-task/settings.json`）・
流れの手順（flow.md 等）の編集を、自分を動かす設定の書き換えとして断ることがある（1か所目が通っても、続く編集が通る根拠にしない。
判定役への説明が日常の作業と教えていても、回によって断られる）。断られたら回り込まず（別の道具・写しの差し替え・別の名義で書かない）、
パッチにもせず、「開発機でしかできない作業」のとおり返す。書けた分は作業ブランチへ push し（push も断られたら、後始末が `wip/` の枝へ残す）、
何をどこまで書いたかをコメントに書く。開発機の対話のセッションが続きを書く。

## 様子を見る

導く原則: 4。

- **動いている担当**: コードのリポジトリの Actions の画面（Claude Task の実行。名前は「#<番号> <種類>」）。
- **全体の様子**: ボードそのもの。ステータスは事実から決まるので、ボードの列が実態になる。
- **気づける範囲**: 担当が何も出さずに手放したらゲートが何が起きたかを問い（回答待ちで、担当者がユーザーになる）、ゲートが出来事を
  取りこぼしたら突き合わせが決め直し、ワークフローが落ちたら GitHub の Actions の失敗の知らせが届く。原因ごとに見張りを足さず、
  この症状で拾えるものだけを守る。拾えない詰まりに当たったら、例外として書き並べず流れの摩擦として記録する
  （.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」）。
- 異常の処置は issue に書く（保留の理由など）。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（またはPR）。ただし**段階に分けたタスクは段階ごとに1コミット**にする（段階ごとに Pull Request を出す。
.claude/skills/file-issue/SKILL.md「段階に分ける」）。**コミット履歴は、ある時点へ戻すときに
どのコミットまで戻せばよいかを件名と本文だけで特定できる状態に保つ**。問い・決定・確認の結果はそのタスクの issue に書き、git には写さない。
master のコミットは Pull Request の題名と本文から作られる。題名が件名で `tasks#1234: <何が変わったか（1行。利用者・運用から見た結果）>`、
本文の形は `.github/pull_request_template.md` だけが持ち、Pull Request の CI（Claude Gate の flow-gate）が照らす。

件名は必ず `tasks#<issue の番号>:` から始める（段階なら段階の sub-issue の番号、複数なら`tasks#12・tasks#13:`）。
属するタスクの無い変更は作らない（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。

## ゲートを変える・公開する

導く原則: 3・5。

ボード・欄・枠の設定は `flow.config.json`、決め方は `src/decide.js`、問いの形は `question_template.md` を直す。公開は、master に入ると `claude-gate.yml` の `deploy-gate` が、
ゲートを変えたかによらず master の先頭の版を `wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で行う（コードのリポジトリの秘密の値 `CLOUDFLARE_API_TOKEN`・
`CLOUDFLARE_ACCOUNT_ID` を使う）。ゲートは出来事が届いた issue だけを今の決め方の姿へ
書き直すので、決め方を変えた直後、出来事の無い issue は次の出来事まで前の姿のまま残る。
手で公開するときは `tools/flow-gate` で同じコマンドを打つ。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`。構文と import の解決（無いファイル・無い名前）は、`tools/flow-gate` で
`npm ci` のあと `npm run lint` が動かさずに見る（ESLint と eslint-plugin-import の `errors` の組。`tools/flow-gate/eslint.config.js`）。
CI（`claude-gate.yml` の `flow-gate`）も同じ2つを流す。
