# 段の流れ

リポジトリを変える作業の単位は**段**（例 `T1253-A`）である。段は下の状態①〜⑥を通り、master へ入るのも
段ごと。タスク（`T1253`）は段の id の頭で、状態も入れ物も持たない。状態の移り変わりは**遷移の表1枚**だけが
決め、どの入口から来ても同じ表で判定する。表に無い遷移・必要な入力が欠けた遷移は断る。特例は作らない。

## 置き場と部品

| 置き場・部品 | 持つもの・すること | やらないこと |
|---|---|---|
| 非公開のリポジトリの Issues と、その持ち主の Project | 仕掛の段（①〜⑤）。段1つが issue 1つで、問い・答え・遷移の記録はその issue のコメント。⑥ は閉じた issue | ― |
| `scripts/flow.py`（道具） | 状態・遷移・答えの取り込み・棚卸・出口（検証が通れば master へ） | 作業ツリー・スロットの管理 |
| 回答ページ（`tools/answer-form/worker.js`。Cloudflare Workers、Access の内側） | ユーザーが問いに答える1枚の汎用の画面 | 状態の判定（道具が行う） |
| `scripts/worktree_slots.py`（WorktreeCreate・WorktreeRemove フック） | スロットの貸し借り | カードの状態 |
| `docs/records/tasks/T1253.md`（タスクごとに1本） | 段ごとの背景・方針・検証。段のコミットで `## T1253-A` の節を足すだけで、前の節は直さない | 状態の行 |
| git（master） | 完成した段のコミット | ― |

置き場の名前と回答ページの URL はコードに書かず、git の設定で持つ（`flow.repo`＝`<持ち主>/<リポジトリ>`・
`flow.project`＝Project の番号・`flow.answer`＝回答ページの URL）。

**書くアカウント**: 道具はユーザーのトークン（`GH_TOKEN` か `gh auth token`）で読み書きし、ユーザーを名指す
書き込み（問い・棚卸の issue）だけを道具用のアカウント Hidgit のトークン（環境変数 `FLOW_ASK_TOKEN`）で書く。
GitHub の名指しの通知は、本人以外が書いたときにだけ届くため。Hidgit は置き場のリポジトリにだけ招き、gh・git へは
ログインさせない。回答ページは、置き場のリポジトリの Issues の読み書きだけを持つユーザーの細かい権限のトークンで書く
（答えはユーザーの名前で付く）。

**問い合わせ枠**: GitHub の GraphQL の枠は1時間 5,000点。道具は Project の全件を100件ごとに1回の問い合わせで読み、
1回の遷移の書き込みを1回の問い合わせにまとめる。実測の点数は T1196 の記録にある。

## 状態

| 状態 | 決める事実 | 次に動かす役割 |
|---|---|---|
| ① 提案 | 承認されていない（番号なし） | ユーザー |
| ② 保留 | 前提が欠けている | 欄「止めている人」（司令塔・ユーザー・担当） |
| ③ 未着手 | 前提を満たし、手が付いていない | 司令塔 |
| ④ 進行中 | 担当が作業している | 担当 |
| ⑤ 検証中 | 作業ブランチの上で CI・完了の条件・本番と画面の確かめをしている | 司令塔 |
| ⑥ 完了 | issue を閉じた。欄「終わり方」＝完成（master に入った）／中止 | なし（終点。続きは新しい提案） |

### 欄（Project）

| 欄 | 中身 |
|---|---|
| 状態 | ①〜⑤。ボードの列。ユーザーが動かせる |
| 確定状態 | 道具だけが書く最後の状態（①〜⑥）。ビューに出さない。「状態」と食い違えばボードで動かされたと分かる |
| 段 | `T1234-A`。承認のときに道具が振り、以後変えない（issue の題名の頭にも書く） |
| 止めている人・欠けているもの・戻り先 | ② のとき。戻り先は ③ か ⑤（④・③ から入れば ③、⑤ から入れば ⑤） |
| 見る時機 | ①・② のとき: すぐ／次の棚卸 |
| 最初に止まった日・持ち越した回数 | ② のとき。表示のためだけで、回数で自動的に何かを起こさない |
| 終わり方 | ⑥: 完成／中止。中止は GitHub の Close as not planned でも入る |

### 欄の初期設定

Project を作ったら1回だけ流す（`N` は Project の番号、`<持ち主>` はユーザー）。新しい Project に最初からある
「Status」の欄は使わない（ビューで隠す）。ビューは gh で作れないので画面で作る（下の「ビュー」）。

    gh project field-create N --owner <持ち主> --name "状態" --data-type SINGLE_SELECT --single-select-options "① 提案,② 保留,③ 未着手,④ 進行中,⑤ 検証中"
    gh project field-create N --owner <持ち主> --name "確定状態" --data-type SINGLE_SELECT --single-select-options "① 提案,② 保留,③ 未着手,④ 進行中,⑤ 検証中,⑥ 完了"
    gh project field-create N --owner <持ち主> --name "段" --data-type TEXT
    gh project field-create N --owner <持ち主> --name "止めている人" --data-type SINGLE_SELECT --single-select-options "司令塔,ユーザー,担当"
    gh project field-create N --owner <持ち主> --name "欠けているもの" --data-type TEXT
    gh project field-create N --owner <持ち主> --name "戻り先" --data-type SINGLE_SELECT --single-select-options "③ 未着手,⑤ 検証中"
    gh project field-create N --owner <持ち主> --name "見る時機" --data-type SINGLE_SELECT --single-select-options "すぐ,次の棚卸"
    gh project field-create N --owner <持ち主> --name "最初に止まった日" --data-type DATE
    gh project field-create N --owner <持ち主> --name "持ち越した回数" --data-type NUMBER
    gh project field-create N --owner <持ち主> --name "終わり方" --data-type SINGLE_SELECT --single-select-options "完成,中止"
    gh label create "棚卸" -R <持ち主>/<リポジトリ> --description "棚卸の issue（flow.py inventory が付ける）"
    git config flow.repo <持ち主>/<リポジトリ>
    git config flow.project N
    git config flow.answer <回答ページの URL>

道具は欄とラベルを名前で引き、無い欄・無い選択肢・無いラベルへ書こうとすると書く前に断る。ラベルの名前の正本は
`scripts/flow.py: INVENTORY_LABEL`。

### ② の止めている人の決め方

止めている理由（`hold` の引数）が止めている人・欠けているもの・動かし方を決める。正本は `scripts/flow.py: HOLD_REASONS`
で、表は下の `table` のコマンドで読む。

## 遷移の表（唯一の規則）

表は写さない。正本は `scripts/flow.py: ROWS`（transitions の状態機械へそのまま渡す）と、入力の意味の
`scripts/flow.py: INPUTS` だけで、人が読むときは次のコマンドで Markdown の表として出す（GitHub へは触らない）。

    python scripts/flow.py table

各行は「遷移・どこから・どこへ・役割・必要な入力・行き先の条件・道具がすること」を持つ。役割の「止めている人」は
欄「止めている人」が指す役割のこと。行を足す・変えるときは `ROWS` だけを直す（テストは行ごとに並ぶので、足した行を
通す場面を書くまで落ちる）。

⑤ → ②（ユーザーの確認）の答えは、「OK」が ② → 戻り先（⑤）、「NG」が ② → ③。

**範囲外の行き先**: 段のコミットが持つ記録の、見出しに「範囲外」を含む節の箇条（`- `）はすべて `行き先: <段・起票案・
直さない（理由）>` を含む。記録を持たない段は当てはまらない。

### 状態を変える入口（判定はすべて遷移の表）

1. **道具のコマンド**（司令塔・担当が打つ。`--as` で役割を名乗る）
2. **回答ページが書く答えのコメント**（ユーザー）
3. **ボードでカードを動かす・閉じる**（ユーザー）。`take` のたびに全件の「状態」と「確定状態」（と閉じ方）を
   1回の問い合わせで読み、食い違う件をユーザーの遷移として判定する。通ればそのまま記録し、通らなければ「状態」を
   確定状態へ書き戻し（閉じられたなら開け直し、開けられたなら閉じ直し）、断った理由をコメントに書く。ボードでの
   再開は、止めている人がユーザーの ② だけで通る（動かしたこと自体を答えとして読む）。中止の理由は、道具の最後の
   記録より後にユーザーが書いたコメント。

    python scripts/flow.py propose "<題>" --file <判断材料.md> [--task T1253] [--after T1253-A]
    python scripts/flow.py take                                     # 回答ページの答えとボードの操作を取り込む
    python scripts/flow.py do <段> <遷移> --as <司令塔|担当> [--text <理由>] [--slot N]
    python scripts/flow.py hold <段> <前提|時機|判断|担当> <欠けているもの> --as <司令塔|担当> [--kind 保留の問い|確認 --file … --choice …]
    python scripts/flow.py ask <段|#番号> <起票|保留の問い|確認> "<問いの題>" --file <判断材料.md> [--choice …]
    python scripts/flow.py land <段>                                # 出口
    python scripts/flow.py inventory [--close <棚卸の issue の番号>]

- **入口（承認）**: 新しいタスクの番号は、origin/master の記録のファイル名と振った段にある最大の番号＋1で、段は A。
  段を足す提案（`--task`）は、そのタスクの振った段と master の件名にある最後の文字の次。題名の頭と欄「段」に書き、
  issue の本文に中止の回答ページへのリンクを置く（③〜⑤ の段はそこから中止する）。`take` は司令塔だけが流す
  （採番は読んでから書くので、2か所で同時に流すと同じ番号を振りうる）。
- **出口**: 作業ブランチ `orch/<段>` の先端を、上の条件を確かめてから `git push origin <sha>:master` で入れる
  （書き換えない。早送りでなければ git が断る）。master が先へ進んでいたら差し戻し、担当が rebase し直す。
  master へのコミットはこの道でしか生まれない。
- 「確定状態」は道具だけが書く。手で書き換えると、その後のボードの判定が狂う。

## 問いと答え

問いのコメントは道具が書く（`propose` は起票の問い、`hold … 判断` は保留の問いか確認、`ask` は書き直し）。
コメントは、判断材料（`--file` の「## 見出し」の節）と、機械で読む部分（`<!-- flow` で始まる囲みの中の種類と
選べる操作）を持つ。**判断材料の見出しが欠けた問いは、書く時点で断る。**

### 問いの種類の表

種類ごとに、要る判断材料の見出しと、回答ページで選べる操作（と必須の入力）が決まっている。正本は
`scripts/flow.py: KINDS` で、表は `python scripts/flow.py table` で読む。中止の種類は問いのコメントではなく、
承認のときに issue の本文へ置く中止の口（③〜⑤ の段で使う）。

### 答えの書式（1つ）

回答ページは issue のコメントに次の行だけを書く。道具はこの行だけで判定し、選択肢の文言では判定しない。

    種別: 保留の問い
    問い: #123-c5851484033
    選んだもの: 1
    本文: （理由・記述・質問・補足）

「問い」は `#<issue の番号>-c<問いのコメントの番号>`（中止は `#<番号>-本文`）。今の最後の問いと違えば、古い問い・
別の問いへの取り違えとして断る。道具が読むのは、道具の最後の記録より後の答えの最後の1件で、取り込むと道具が
記録を書くので同じ答えを二度読まない。

## 回答ページ

問いのリンク（`/answer?issue=<番号>`、中止は `&from=body`）を開くと、上に判断材料、下にその問いで選べる操作だけを
並べる。「確認へ」でサーバーが確認画面を返し、「送信」で上の書式のコメントを書く（ブラウザ側の JavaScript は
使わない）。必須の入力の欠け・問いに無い操作は、サーバーが入力画面へ戻す。公開（`wrangler deploy`）はユーザーが行う。
書き先のリポジトリは `tools/answer-form/wrangler.toml: TASKS_REPO`、トークンは `wrangler secret put GITHUB_TOKEN`。

## ビュー

| ビュー | 中身 |
|---|---|
| 状態のボード | 列＝欄「状態」（① 提案〜⑤ 検証中）。② の列は欄「止めている人」で横に区切る。絞り込み `is:open` |
| ① 提案・② 保留（ユーザー） | ① と、② のうち止めている人＝ユーザー。どちらも `見る時機:すぐ` |

棚卸で見直す件は ② の列の中（見る時機＝次の棚卸）。中止した件は、閉じた issue を `終わり方:中止` で絞り込んで見る。

## 棚卸（周期レビューと同じ間隔）

`inventory` は ① ② の全件を1回の問い合わせで読み、件ごとに前提の段の状態・前回の棚卸以降のコメントの数・
最初に止まった日・持ち越した回数を出す。前提の段が完成した ② はその場で戻り先へ動かす。止めている人が
司令塔・担当の件は、司令塔が判断して一覧にする。ユーザーが決める件（① と、止めている人がユーザーの ②）は
棚卸の issue（ラベル「棚卸」を付ける。Project には入れない）を1つ作り、ユーザーを1回だけ名指す。ユーザーはボードで
操作する（続ける＝何もしない、再開＝戻り先の列へ、中止＝Close as not planned で理由はコメント、判断できない＝コメント）。
`inventory --close <番号>` は、載せた件のうちまだ ② のものの持ち越した回数を1つ増やして棚卸の issue を閉じる
（ラベルの無い issue は断る）。ラベルの付いた閉じた issue のうち最新の閉じた日が、次の棚卸の「前回」になる。

## コミット

- 1段1コミット。件名は `T1253-A: <利用者・運用から見た結果>`。本文は `背景:`・`課題:`・`成果:`・`検証:`
  （実行したコマンドと観測値）・`増減:`（実装・テスト・文書を分けて）・`残り:` の行を持つ。
- 記録は同じコミットで `docs/records/tasks/T1253.md` に `## T1253-A` の節を足す。新しいタスクの最初の段は
  記録のファイルを作り、起票の問いの判断材料を背景として写す。範囲外で見つけたものは、その節に行き先を付けて書く。
- 段の中で出た問い・答えは issue のコメントにあり、その段のコミットで記録へ写す。

## 担当への約束

- 作業ブランチは `orch/<段>`。origin/master の上に積み、push は作業ブランチへだけ（master へは出口が入れる）。
- 着手の前に、依頼の進め方が実行できて決まりに反しないかを確かめる。合わなければ `hold <段> 判断 …` で問う。
  答えに依らない残りは終えてよい。
- 終えたら CI を待ち（`gh run list --commit <sha>`・`gh run watch <id> --exit-status`）、緑なら `do <段> 検証へ --as 担当`。
  報告には CI の実行の URL を添える。
- `git reset --hard`・`git stash` は使わない（作業ツリーの間で共有される）。

## 司令塔がすること

- 担当の報告を受けるたびと、ユーザーに声をかけられたときに `take` を流す。③ → ④: `do <段> 着手 --as 司令塔 --slot N`
  の後、担当を `isolation: "worktree"` で起動する。
- ⑤: CI の結論、完了の条件（記録の段の節とコミットの本文）、本番と画面の確かめ（要るとき）を見て、`land`・
  差し戻し（`do <段> 差し戻し --as 司令塔 --text …`）・確認（`hold <段> 判断 … --kind 確認`）のどれかにする。
- 止めている人が司令塔になった件（どれでもない・判断できない）は、読んで答え、`ask` で問いをユーザーへ戻すか、
  `do <段> 再開 --as 司令塔` で戻り先へ動かす。

## 作業ツリーのスロット

担当の作業ツリーは `.claude/worktrees/slot-<N>` を使い回す（node_modules・.venv を毎回入れ直さないため）。
貸した印は git のロック（`git worktree lock` の理由が `slot ` で始まる）だけ。WorktreeCreate フックはロックの無い
スロットを origin/master に戻して貸し、未コミットの変更かどのリモートからも届かないコミットがあるスロットは貸さない。
WorktreeRemove フックは、失う作業が無ければ印を外す。担当が落ちて印が残ったら、中身を確かめてから
`git worktree unlock <パス>` で外す。テストDBは作業ツリーごとに分かれている
（`backend/tests/conftest.py: default_test_database_name`）ので、スロットどうしで取り合わない。
