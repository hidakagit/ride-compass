# タスクの流れ

タスクは GitHub の issue である。1つの Pull Request に収まらないタスクは段階に分け、段階も同じ形の issue（親の sub-issue）に
する（下の「段階に分ける」）。ステータスは段階も含めてどの issue も持ち、Project の欄「Status」に置く。
ステータスの移り変わりは**遷移の表**（`tools/flow-gate/flow.config.json: transitions`）だけが決め、ゲート（`tools/flow-gate/`）が
GitHub の出来事（回答・Pull Request・Claude の道具の書き込みなど）を受けて表で照らす。表に無い変化はゲートが前へ戻して理由を
コメントする。誰の番かはステータスだけで決まり、ユーザーの判断は回答フォームで選択肢を選んで行う。仕組みが守るのは遷移までで、
それぞれの状態で何をするかは、この文書の手順が決める。

## 置き場と役割

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリと Project（`flow.config.json: repository`・`project`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない。Project の「状況の更新」にゲートの失敗（「様子を見る」） |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事を表で照らしてステータスを書き、担当者をステータスの番に揃える。表に無い変化を戻す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメントを書く・実施の順番・検証中の確かめとマージ・Project の欄の規模と優先度 |
| ユーザー（hidakagit） | 回答フォームで答える。ラベル（`急ぎ`・`ユーザー確認` 等）を付け外しする。ボードでステータスを動かしても、ゲートが戻す |

- Claude は GitHub の置き場へ、hidakagit-bot のトークン（ユーザー環境変数 `FLOW_BOT_TOKEN`）でだけ書く。hidakagit の
  トークンで書かない——hidakagit に通知が届かず、ゲートが hidakagit の操作と見分けられなくなる。
  gh で書くときは `GH_TOKEN` に `FLOW_BOT_TOKEN` の値を渡す。
- ゲートは自分の書き込み（送り主 `flow.config.json: gate`）を無視する。組み込みの自動化「Auto-add to project」
  （段階は「Auto-add sub-issues to project」）が issue を Project に入れると、ゲートが入口（下）を処理する。

## ステータスと割り当て

ステータスの名前・並び・表は設定ファイルが正本で、ここに写さない。読み方だけを書く。

- **誰の番か**（`owner`）: ステータスだけで決まる。回答待ち・保留はユーザーの番、未着手・進行中・検証中は Claude の番。
  担当者の欄は、ゲートがステータスから書く表示と通知のためのもので、手で変えてもゲートがステータスの番へ戻す。
- **入口**（`entry`）: Project に入ったとき、書いた人で決まる（入った時点のステータス＝ボードで選んだ列は見ない）。
  ユーザーが書いた issue と段階（親のある issue）は未着手。Claude が書いた issue は回答待ちで、ゲートが採否の問い
  （`entry` の `question`）を本文の先頭に置く（`ask.js` の問いと同じ置き場）。
- **遷移**（`transitions`）: 行ごとに、出来事（`on`）・その前の状態（`from`）・行き先（`to`）を持つ。`by: claude` の行は Claude の
  道具がステータスを書き換えて起こす出来事で、それ以外の者（ボードの手での移動）の書き換えはゲートが戻す。
  `when: blockersClosed` の行は、前提（blocked by）が全部閉じているときだけ通る（見送りで閉じた前提も待たない。作る担当が
  読んで、進める前に問う）。
- **完了**: 閉じた理由（completed＝完成／not planned＝見送り）で分ける。完成になる道は、Pull Request のマージ（残りが無いとき）・
  回答フォームの「完成」・Claude が残りを済ませて completed で閉じたとき（ゲートが残りの無いことを照らす）。
  子（段階）が全部閉じると、子が完成でも見送りでも、ゲートが親を completed で閉じる。完了からは戻せない（続きは新しい issue）。
- **残り**（`tools/flow-gate/src/rules.js: remaining`）: 本文の完了の条件のうちチェックの無いものと、ラベル `ユーザー確認`
  （`confirmLabel`）。残りがあるうちは完成で閉じない。

## Claude がステータスを動かす

Claude が起こす出来事は、表の `by: claude` の行だけ。問いは `ask.js`（「問い」）、ほかは次の道具で起こす。

    node tools/flow-gate/bin/move.js <issue の番号> <出来事>（理由が要る出来事なら続けて <理由>）

- 振り出し（未着手 → 進行中）: 担当のワークフローが、最初の段（引き受ける）で起こす（「担当」）。
- 落ちた（進行中 → 保留）: 担当が落ちたとき。理由が必須で、道具が理由をコメントに書いてから動かす。
- 戻す（進行中 → 未着手）: 作る担当が、担当の仕事の外の失敗（Claude の利用の上限・認証・サーバーの失敗）で止まったとき。担当のワークフローの後始末が起こす（「担当」）。理由が必須。

検証中へ入る・検証中から出るのは Pull Request の出来事だけで、Claude は動かさない。回答待ち・保留から出るのはユーザーの答えだけ。
振り出す順に並べて出すのは `node tools/flow-gate/bin/queue.js`（`--json` で機械向け）。

## 担当（Claude が自分の番を進める）

役割は次のとおりに分ける。どの役も、ほかの役の持ち物を持たない。

| 役 | 持つもの・すること |
|---|---|
| GitHub（issue・Project・ゲート） | タスクの状態（ステータス）。遷移はゲートが表で守る |
| 振り出し（`.github/workflows/claude-dispatch.yml` が `tools/flow-gate/bin/dispatch.js` を起こす） | 止めの印を見て、動いている担当の数が上限（`flow.config.json: coordinator.parallel`）になるまで、キューの上から担当のワークフローを起こす |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 1件を引き受け、準備をして担当を起こし、終わったら後始末をする |
| 作る担当・確かめる担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（PR・問い・issue へのコメント）。次の担当を起こすことには触れない |

**キュー**（仕事の並び）は GitHub のステータスから毎回導くもので、どこにも別に持たない（`queue.js`。並びはステータスの順
`coordinator.order`（検証中 → 未着手）、中はラベル「急ぎ」（ユーザーの依頼。優先度の欄より上。`project.urgentLabel`）→ Project の
優先度の欄の選択肢の順 → 番号の若い順）。作る担当が PR を出すとゲートが検証中にし、それが確かめる依頼としてキューに載る。

- **起きる時機**: 振り出しは、担当のワークフローが終わったとき・定期（15分ごと。取りこぼしを拾う）・手で
  （`gh workflow run claude-dispatch.yml -R hidakagit/ride-compass`）起きる。どれも GitHub Actions のランナーで動き、開発機は要らない。
  振り出しは、動いている担当（担当のワークフローの終わっていない実行）の番号・前提が開いたままの未着手・子の段階が開いている親（親の仕事は子で進み、子が全部閉じるとゲートが閉じる）・ラベル「開発機が要る」の
  付いたものを飛ばす。`node tools/flow-gate/bin/dispatch.js --dry-run` で、何を起こすかを見られる。
- **担当のワークフローの1回**:
  1. 引き受ける: 作るなら `move.js <番号> 振り出し`（未着手 → 進行中）が通ったときだけ、確かめるなら検証中のときだけ進む。
     同じ issue のジョブは1本ずつ動き、重ねて起こされた2本目はここで何もせず終わる。
  2. 準備: `ci.yml` の backend と同じ PostgreSQL + PostGIS、backend と frontend の依存を入れ、許可の行（`.claude/settings.json` の
     `permissions`）を担当へ渡す。
  3. 担当を起こす。持ち時間はジョブの `timeout-minutes` で、超えると Actions がジョブを止める。
  4. 後始末（担当が落ちても止められても走る）: 作る担当の GitHub に無い変更（未コミットの変更・push していないコミット）は
     `wip/tasks-<番号>-<時刻>` の枝へ残す（作業ブランチは書き換えない）。そのあと `tools/flow-gate/bin/after.js` が、連携の書き出す
     実行のファイルで終わり方を見分ける。Claude の利用の上限・認証・サーバーの失敗（担当の発言の `error`）か、担当が動けなかった
     ときは、担当の仕事の外の失敗なので、作る担当のタスクを `戻す` で未着手へ戻す。利用の上限・認証なら、続けて起こしても同じく
     止まるので、振り出しを `coordinator.pauseMinutes` の間止める（コードのリポジトリの変数 `coordinator.pauseVariable` に止める時刻を
     置き、振り出しがそれを読む）。それ以外で作る担当のタスクが進行中のまま（PR も問いも出さずに終わった・持ち時間を超えた・
     Cancel された）なら、落ちたとみなして `落ちた` で保留にする（ユーザーが回答フォームで決める。作業ブランチに push 済みの分から
     続けられる）。確かめる担当のタスクは動かさない（検証中はキューに残り、次に起こし直される）。
- **名義**: 置き場へは hidakagit-bot（secret `FLOW_BOT_TOKEN`）、コードのリポジトリへは hidakagit（secret `CODE_TOKEN`。
  `GITHUB_TOKEN` で打ったマージは master の CI とデプロイを起こさないため）、Claude は契約のトークン（secret `CLAUDE_CODE_OAUTH_TOKEN`）。
- **記録**: Actions の実行の記録に、「#<番号> <種類>」の名前で並ぶ。コードのリポジトリは公開なので、記録は誰でも読める。
  担当の出力の全文と報告は記録に出さない（出るのは指示文と、手数・費用の目安）。
- **止める**: 置き場の開いた issue のどれかにラベル「停止」（`coordinator.stopLabel`）を付けると、振り出さない
  （スマホからでも付けられる。外すと次の振り出しから戻る）。利用の上限で後始末が止めた時刻（変数 `coordinator.pauseVariable`）を早く
  解くなら、コードのリポジトリの Settings → Secrets and variables → Actions → Variables で消す。動いている担当は止まらないので、止めるなら Actions の画面で
  その実行を Cancel する（後始末の段は走る）。振り出しそのものを止めるなら、Actions の画面で Claude Dispatch を無効にする
  （Disable workflow）。
- **開発機が要る**: 開発機にしか無いもの（本番への調べ `run_probe.py` の SSH の鍵・開発 DB の実データ）が要るタスクは、Actions では
  進めない。担当は、それが要ると分かったところで作業を止め（途中の変更は作業ブランチへ push してから）、issue にラベル
  「開発機が要る」（`coordinator.devLabel`）を付け、何がなぜ要るかをコメントに書いて終える。ユーザーが最初から付けてもよい。
  振り出しはこのラベルの付いたタスクを飛ばし、ユーザーが開発機の対話のセッションで扱う。

**作る担当**・**確かめる担当**のどちらも、作業は担当のワークフローが取り出した作業ツリーの中だけで行う。どの終わり方でも
（PR を出した・問うた・段階に分けた・完成で閉じた・確かめてマージした／閉じた・開発機が要ると返した）、手順の中で当たった改善点を
「改善を起票する」のとおり起票し、push と issue への報告をして終える。次の担当を起こすのは振り出しなので、担当は触れない。

**作る担当**
1. `git fetch origin`。作業ブランチ `orch/tasks-<番号>` が GitHub にあれば（Pull Request が閉じられて戻った・答えをもらって
   戻ったタスク）、`git checkout -B orch/tasks-<番号> origin/orch/tasks-<番号>` のあと
   `git rebase origin/master` で前の作業を master の上へ載せ直す（競合したら「競合を解く」のとおりに直して続け、直せなければ
   issue にコメントで書いて終える）。無ければ `git checkout -B orch/tasks-<番号> origin/master`。前の担当の残り
   （`wip/tasks-<番号>-*` の枝。担当のワークフローの後始末の4）があれば読んで要るものを取り込み、取り込んだら枝を消す
   （`git push origin --delete wip/tasks-<番号>-<時刻>`）。
2. backend と frontend の依存とテスト用の DB は、担当のワークフローが入れてある（backend は `python`、frontend は `frontend/node_modules`）。
3. issue の本文とコメント（答えのコメント・やり直しなら前の Pull Request のコメントも）を読み、CLAUDE.md と規約のとおりに作る。
   - ユーザーの判断が要るところは「問い」の形で書いて `ask.js` で問い、そこで終える（答えは次の起動で拾われる）。
     作る前に、答えの無い判断（方針・見た目の案・本番への書き込み等）が残っていないかを見て、残っていれば問いに要る分だけを
     調べて（画面を撮る・件数を数える等）作らずに問う。作り込んだあとに問うと、答えしだいで作ったものが無駄になる。
     答えが「その他」なら、補足を読んで問いか提案を直して問い直す。前提（blocked by）が見送りで閉じていたら、進める前に問う。
   - 1つの Pull Request に収まらないと分かったら、「段階に分ける」のとおりに分けて終える（段階は次の起動から1件ずつ振り出される）。
   - マージ済みの Pull Request があって戻ってきたタスク（マージのあとの残り）は、残りを済ませて完了の条件にチェックを付ける。
     ラベル `ユーザー確認` が残っていれば、確かめてほしいことを問う（完成・進める等は回答フォームが一律に出す）。残りが無くなれば
     `gh issue close <番号> --reason completed` で閉じる（ゲートが、残りが無いことを照らしてから完了にする）。
   - コードを変えないタスク（調査・見積もり・計測）は、結果を本文に書いて自分の分の完了の条件にチェックを付け、結果を確かめてほしいと
     問う（Pull Request が無いので、完了はユーザーの答えで決まる）。
4. `tasks#<番号>:` の件名でコミットし、`git push origin orch/tasks-<番号>` で push する（載せ直した・前のコミットへまとめたなど、
   作業ブランチを書き換えたときは `git push --force-with-lease origin orch/tasks-<番号>`）。CI は、push したコミットの実行の id を
   `gh run list -R hidakagit/ride-compass --commit <コミット> --workflow ci.yml --json databaseId` で引き（出ていなければ少しおいて
   引き直す）、`gh run watch <id> -R hidakagit/ride-compass --exit-status` で終わるまで待つ。
5. CI が通ったら、コードのリポジトリに Pull Request を出す（`gh pr create --base master --head orch/tasks-<番号>`。
   コードのリポジトリは hidakagit のものなので、`GH_TOKEN` に hidakagit のトークン（ユーザー環境変数 `GH_TOKEN`）を渡す）。
   件名はコミットと同じ、本文は次の順に書く:
   - 置き場の issue へのリンク（`https://github.com/ridecompass/ride-compass-tasks/issues/<番号>`）と、何が変わったかの1〜3行
   - 修正前後のキャプチャ（`--attach <前の画像>` と `--attach <後の画像>`。画面・幅など、何を撮ったかを添える）
   - 画面に出ない変更は、確かめ方と根拠（実行したコマンドと出た値・読んだ公式の文書）
   - `backend/scripts/lost_constraints.py`（master との合流点からの、ORM の宣言から消えた制約）が出した「消えた」の
     1件ずつに、処置（移した先・意図して外した理由）。書き直しで落ちた制約は差分に1行も出ないため
   - 派生の値か軸の難易度を変える変更なら、列・軸ごとの分布の前後（下の「分布の前後」）
   前の Pull Request が開いたまま残っていれば、新しく出さずに push し、撮り直したキャプチャを `gh pr comment --attach` で足す。
6. issue の本文を直し（経緯・完了の条件のチェック。マージのあとでないとできない条件だけをチェックの無いまま残す）、
   Pull Request へのリンクをコメントに書いて報告する。Pull Request を出すと、ゲートが検証中へ動かし、確かめる担当に渡る。

**分布の前後**（派生の表の値か評価軸の難易度を変える変更。差分が `backend/app/batch/` の派生の段か、
`backend/app/domain/` の材料の値式・軸の評価に触れるもの）
落ちた絞り込み・二重に数えた値は、エラーにもテストの失敗にもならず、値の偏りとしてだけ現れる。作る担当は変える列・軸を
変更の前と後で測り、Pull Request の本文に1件1行で「前 → 後」と、変わった理由を書く。前は編集する前（作業ツリーが master の版の
うち）に測る。測るには開発 DB と本番への調べが要り、担当のワークフローでは測れないので、対象と分かったら「担当」の
「開発機が要る」のとおりにする（確かめる担当が本番で測り直すときも同じ）。どちらの道具もプローブの後ろの引数をそのまま受け取るので、本番へは `run_probe.py` の後ろに並べて打つ。
- 派生の値: 開発DBで、変える段から `python -m app.batch.derive_cli --from <段>` を流し、`backend/scripts/derived_distribution.py --column <表.列>` で
  測る（前）。変えたあとに同じ段を流して測る（後）。前も流し直すのは、開発DBは別の担当が別の版で作り直していることがあるため。
  本番の今の値も `run_probe.py scripts/derived_distribution.py --column <表.列>` で測って添える（開発DBは範囲が狭いので、
  前が本番と大きく違えば開発DBの側を疑う）。本番の派生を作り直すのは本番DBへ書くことなので、担当はしない。
- 軸の難易度: 本番を `run_probe.py scripts/measure_axis_saturation.py --axis <軸> --bbox <範囲>` で前と後に測る（読み取りだけ。
  軸の定義の正本は本番DBにある。抽選は回ごとに標本が変わるので、範囲を決めて同じ標本にする）。

**Pull Request のあと**（ゲートが、コードのリポジトリの Webhook から届く Pull Request の出来事で動かす）
- コードのリポジトリは、master に入れる前に必須チェック（`ci.yml` の `ci-ok` と Docs Consistency 等）が Pull Request で通ることを
  求める（ルールセット。管理者にも効く）。最新の master の取り込みは求めない（求めると、1件入るたびにほかの Pull Request が
  全部載せ直しと CI の待ちになり、並べて進めた分が1本ずつに潰れる）。それぞれ通った Pull Request の組み合わせで壊れたものは
  master の CI が捕まえ、通るまで本番へは出ない（`ci.yml` の `deploy-backend`）。マージは hidakagit のトークンで打つので、
  落ちた知らせは GitHub の通知（Actions の失敗）で hidakagit に届き、直すのは普通のタスクにする。
- 開いた（開き直された） → 進行中なら検証中。ほかの状態なら何もしない
- マージされずに閉じた → 未着手（閉じたときのコメントを作る担当が読んでやり直す）。master と競合して Merge が押せない
  ときも、確かめる人が「競合」と書いて閉じる（競合を知らせる出来事は GitHub に無い）
- マージされた → 残り（チェックの無い完了の条件・ラベル `ユーザー確認`）が無ければ完了（completed）、あれば残りを書いて未着手
  （作る担当が残りを済ませ、ユーザーの確認が残っていれば問う）
- GitHub は届かなかった出来事を送り直さない。Pull Request が閉じたのに検証中のまま止まったものは、コードのリポジトリの Settings →
  Webhooks → Recent Deliveries から Redeliver する（3日分まで）。

**確かめる担当**（検証中。作った担当とは別）
1. 作業ブランチを取る（`git fetch origin` と
   `git checkout -B orch/tasks-<番号> origin/orch/tasks-<番号>`）。Pull Request（本文のキャプチャ・差分）・作業ブランチの CI・issue の完了の条件・変更が届く範囲（要るなら画面）を
   確かめる。作る担当の報告を読み写さず、自分で見る（画面なら自分で撮る）。Pull Request が無ければ（手順が変わる前に
   検証中になったもの）、作る担当の5のとおりに出してから確かめる。`lost_constraints.py` も自分で回し、「消えた」の
   1件ずつに本文の処置があるかを見る（処置の無いものが1件でもあれば満たしていない）。「分布の前後」の対象なら、
   列・軸ごとの前後の行が本文にあるかを見て、本番で測れる側（派生は本番の今、軸は後）を自分で測り直す。
   **設計書の条件を1つ当てる**: 作り直しで落ちた条件（絞り込み・不変条件・制約）は、差分にも作る担当の報告にも1行も出ないので、
   報告の主張ではなく設計書を基準にする。差分が変えた関数・SQL・材料のファイルを `docs/modules/*.md` の対象ファイル表で引き
   （表に無い `scripts/`・`tools/flow-gate/` 等は docs/modules/README.md「このディレクトリが扱わない領域」の正本。依存・デプロイ・
   実行環境に触れるなら docs/architecture/ の該当箇所も）、そこに書かれた条件のうち差分が触れたものを1つ選ぶ（ファイルを消して
   書き直した差分なら、書き直した側から）。その条件が実装で成り立つかを、コードを読み、条件を入力にしたテストか開発DBの
   問い合わせで値を見て、自分で確かめる。成り立たなければ（設計書の直し忘れでも）満たしていない。文書だけの変更には当てない。
   確かめる担当は設計の良し悪しを判じない（別の設計が良いと思えば起票する）が、設計書との照合はする。
2. 確かめた結果を、満たしていてもいなくても issue にコメントで書く（見出し「確かめた結果」）。完了の条件の1件ごとに、
   何をどう見て（実行したコマンド・開いた画面）何が出たかを書き、撮った画面は Pull Request へ `gh pr comment --attach` で貼る。
   設計書の条件は、選んだ条件（文書と節）・確かめた方法・出た値を書く。ここに書いたことだけが、確かめた証拠として残る。
3. ユーザーが見るべきだと判断したら（利用者から見える振る舞い・モジュールの設計が変わる等）、issue にラベル `ユーザー確認` を
   付け、理由を書く。マージは確認を待たない（マージのあとに残りとして未着手へ戻り、作る担当が問う）。「分布の前後」の対象は
   いつもそうし、理由に前後の行を写す（値の偏りが意図どおりかは、完了の条件にもテストにも出ない）。
4. 満たしていなければ、足りないことを書いて Pull Request を閉じる（`gh pr close <番号> --comment <理由>`）。ゲートが未着手へ戻す。
5. 満たしていれば Pull Request をマージする（`gh pr merge <番号> -R hidakagit/ride-compass --rebase`）。CI は 1 で通ったのを
   見ているので、待たずに打つ。master の CI も待たない（ゲートが閉じる）。
6. master と競合してマージできなければ、`git rebase origin/master` で載せ直し、「競合を解く」のとおりに解く。どの競合も
   片側を採るだけで解けたら、`git push --force-with-lease origin orch/tasks-<番号>` で push し、
   `gh pr checks <番号> -R hidakagit/ride-compass --watch --required` で必須のチェックを待ってから、5 のとおりマージする
   （片側を採るだけなら、確かめた中身と master のどちらかがそのまま残るので、確かめ直さない）。新しい行を書かないと解けない
   競合が1つでもあれば、`git rebase --abort` で戻し、どのファイルのどこが重なったかを書いて「競合」として閉じる（4 と同じ。
   作る担当が載せ直して出し直す）。

**競合を解く**（作る担当の 1・確かめる担当の 6）: 競合したファイルを開き、`<<<<<<<`・`=======`・`>>>>>>>` の印と採らない側の行を
編集で消してから `git add <ファイル>` と `git rebase --continue`。`git checkout --ours`・`--theirs` は使わない（許可の判定で止まる）。

**許可の一覧に合わせて打つ**: 担当は無人で動き、許可の一覧（`.claude/settings.json` の `permissions.allow`）に合わない操作は、
自動モードの判定役が1回ずつ可否を決める（同じ操作が通る回と断られる回に分かれる）。そのため、この節の手順の push・枝の削除・
マージ・CI の待ちは、一覧の行に合う形でここに書いてある。書いてある形のまま、1回に1つずつ（`&&`・`;`・`|` でつながずに）打つ。
手順に新しい操作を足すときは、一覧の行も同じコミットで足す。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当が自分でしない。
ユーザーに頼む問いを `ask.js` で問う。問いの文の頭に「PC での操作:」と書き（スマホで本文の先頭の1行を見て、PC が要ると
分かるように）、判断材料に手順と確かめ方を書く。済んだら「進める」、できなければ「その他」に理由を、と判断材料に書く。
「進める」の答えが来たら、Claude が確かめ方のとおりに確かめ、完了の条件にチェックを付ける。

## 改善を起票する

担当は、手順を進める中で流れそのもの（この文書の手順・`tools/flow-gate` の道具・担当のワークフロー・検査）の改善点に当たったら、
終える前にタスクとして起票する。控えや報告に書くだけにしない——担当の出力はログに残るだけで誰も読まないので、issue に
しないものは次の回に届かない。

- **起こすもの**: この回に実際に起きたことだけ。例: 手順どおりに打った道具が断った・失敗した、手順に無い場面や手順どうしが
  食い違う場面で自分で決めた、同じ長いコマンドを手で組み立て直した、待ち（鍵・CI・重い処理の順番）が作業より長かった。
  観測の無い思いつきは起こさない。
- **今の差分で直せるものは直す**: 今のタスクの範囲で片付く直しは、起票せずに今の差分へ入れる（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。
- **重ねない**: 先に開いた issue を探す（`gh issue list -R ridecompass/ride-compass-tasks --state open --search "<語>"`。
  日本語の検索は緩く当たるので題名を読んで判じる）。同じものがあれば、起きたこと（日時・作業中の issue の番号・打ったコマンドと
  出た値）をその issue へコメントで足すだけにする。重なった回数は、ユーザーが採否を決める材料になる。
- **書き方**: 「issue の形」のとおりに本文をファイルへ書き、hidakagit-bot の名義で起こす
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --type 保守 --title <題名> --body-file <ファイル>`。
  道具の失敗なら種類は不具合）。背景の節に、どの issue の作業中に・何を打って・何が出たか（観測値）を書く。規模と優先度は
  `field.js` で入れる（CLAUDE.md「規模の札」「優先度の見積もり」）。
- ゲートが入口で採否の問いを置いて回答待ちにするので、やるかはユーザーが決める。担当は、起こした・コメントを足した issue の
  番号を自分のタスクの issue への報告に書き添える。

## 様子を見る

- **動いている担当**: コードのリポジトリの Actions の画面（Claude Task の実行。名前は「#<番号> <種類>」）。GitHub のスマホアプリの
  Actions からも見られる。振り出しが何を起こしたかは Claude Dispatch の実行の記録に出る。
- **ゲートの失敗**（`tools/flow-gate/src/status.js: reportFailure`）: Webhook の出来事の処理で例外が出たら、Project の「状況の更新」
  （Status updates）に At risk で書く。最新の更新もゲートの失敗なら、新しく足さずにその本文へ1行足す（鍵が切れたときなど、出来事ごとに
  履歴が増えないため）。最新の1件の状態が Project の見出しと Projects の一覧に出る（公式の文書「Sharing project updates」）。
- 異常の処置は issue に書く（保留の理由など）。

## 問い

ユーザーに求めることは、採否・判断・操作のお願い・確認のどれも、次の形でファイルに書き、道具で問う（hidakagit-bot の名義）。

    node tools/flow-gate/bin/ask.js <issue の番号> <問いのファイル>

道具は形を照らしてから、問いを本文の先頭（ゲートの印の間）に画面に出ない形（HTML のコメント）で書き、回答待ちへ動かす。
ユーザーの番の間は、ゲートがその下へ「回答する」のボタンの画像（リンク付き。スマホのアプリでも押せる）と、ステータス・問いの文の
1行を置く（コメントは古い順にしか並ばず、一番下は見落とすため。GitHub の画面そのものにはボタンを足せない）。案と判断材料は
回答フォームで読む。

    ## 問い
    <問いの文（1行）>

    ### 案
    - <案の中身>
    - <案の中身>

    <details><summary>判断材料</summary>
    （この問い1つだけで判断できるように書く）
    </details>

- **形の決まり**（`tools/flow-gate/src/rules.js: parseQuestion` が正本）: 最初の `<details>` から後ろは判断材料で、中身は自由に書ける
  （解釈しない）。それより前に置けるのは、1行目の「## 問い」・問いの文（1行）・「### 案」とその下の「- 」で始まる行（1行に1案、
  書いたとおりの文）・空行だけで、ほかの行が1行でもあれば形に合わない（`ask.js` が断り、ゲートは回答待ちにしない）。
- **選択肢は問いに書かない**。回答フォームが、今のステータスから「回答」で行ける先を `flow.config.json: answers` から一律に出す
  （例: 進める・止める・完成・見送り・その他）。問いが持つ個別の部分は、問いの文・案・判断材料だけ。
- **案**: 「A と B のどちらにするか」を決めてほしいときだけ書き、要らなければ節ごと省く。回答フォームは「進める」を案の数だけ
  「「<案>」で進める」に分け、選んだ案が答えに残る。行き先は案によらず同じ。
- 判断に付く意思（`ユーザー確認`・`急ぎ` など）は選択肢と掛け合わせず、回答フォームのラベルの欄で付け外しする（置き場の
  リポジトリに定義されたラベルを全部、今の付き方のまま並べ、答えのコメントに「ラベル: +… −…」を残す）。
- 「止める」「その他」は補足が必須。「止める」は保留になり、「その他」は未着手に戻って Claude が補足を読んで問い直す。
- 保留には問いが無くてもよい。回答フォームは決まった問い（`flow.config.json: questions`）で開く。
- 今の問いは、本文の先頭にある1つだけ。問い直すと置き換わり、答えるとゲートが本文から消す。`-->` は書けない
  （問いを隠す HTML のコメントが途中で閉じる。道具が断る）。
- 答える時点で答えられることだけを聞く。
- **聞くかどうか**: 外から見える振る舞いが変わるときだけ聞く。変わらないなら聞かずに報告して直す。聞いたら答えを待つ。
- **書く順**（判断材料の中）: 利用者への約束を1文 → 問題が起きる場面を1つと、起きない場面を1行 → 案ごとに
  利用者に何が起きるか。背景を知らない人がこの問い1つだけで判断できるように、何の画面・機能の話か・いまどうなって
  いるか・なぜ決める必要があるかを入れる。画面の見た目・情報量に関わる判断は、変更前と変更後の画面かモックを添える。
  推奨は判断材料の最後に理由と一緒に書く。
- **製品の言葉で書く**: 実装の語（関数名・引数名）・固有名詞・タスク番号に頼らない。
- **案**: 自分の領分（どう直すか・書き方）を案に入れない。案の文と実際に当てる作業を一致させる。

## 答え

回答フォームがユーザーの名義で次のコメントを書く。問いは答えると本文から消えるので、問いの文・全部の選択肢・判断材料も
ここに残す（このコメント1つで、何を問われて何を選んだかが読める）。Claude はこれだけを読み、チャットでの答えを判断に
使わない。補足は決定を変えない。

    ## 回答
    **<問いの文>**

    ○ <選ばなかった選択肢>
    ● **<選んだ選択肢>**

    次のステータス: <名前>
    ラベル: +<付けたもの> −<外したもの>（変えたときだけ）
    補足: <書いたときだけ>

    <details><summary>判断材料</summary>（問いにあったときだけ）</details>

## 段階に分ける

1つの Pull Request に収まらないタスクは、段階ごとに親と同じ形（「issue の形」）の issue を作り、普通のタスクとして進める。

    node tools/flow-gate/bin/stage.js <親の番号> <題名> <本文のファイル> [前の段階の番号...]

- 道具は段階を親を付けたまま作り（作ってから親を付けると、Project に入った時点で段階と分からず採否の問いが付く）、
  前の段階を blocked by にする（前の段階が完了で閉じるまで進行中にできない）。Project へは「Auto-add sub-issues to project」が
  入れ、ゲートが入口で未着手・Claude にする。規模と優先度は `field.js` で入れる。
- 親の本文の「やること」に段階の番号を並べる。親は進行中のまま置く（進行中はキューに入らないので、振り出されない）。
- 段階は1件ずつ、自分の作業ブランチ（`orch/tasks-<段階の番号>`）と Pull Request で進む。子が全部閉じると、ゲートが親を閉じる。

## 保留と棚卸

保留は「止めて、あとで決める」置き場で、ユーザーの番。ユーザーが回答フォームで1件ずつ決める（AI は決めない）。

- **保留に入る道**（どれも理由がコメントに残る）: 回答フォームの「止める」（補足が答えのコメントに残る）・
  `move.js <番号> 落ちた <理由>`（担当のワークフローの後始末が、PR も問いも出さずに終わった作る担当を止める）。
- **棚卸**（回答フォーム）: 進める → 未着手（Claude の番）・見送り → 完了（見送りで閉じる）・完成 → 完了（completed）。

## issue の形

**題名**は、何をするか（または何が困るか）だけを30字前後で書く。数値・経緯・やり方・括弧書きの補足は本文へ。

**本文**は次の節をこの順に並べ、1 以外は `<details><summary>節の名前</summary>` で畳む。節ごとに「答える問い」が1つだけあり、
それに当たらないものはその節に書かない。

| 順 | 節 | 答える問い | 書くもの | 書かないもの |
|---|---|---|---|---|
| 1 | 要約（畳まない） | 開いて2行で何が分かるか | 何が起きていて、何をするか（1〜2文） | 経緯・数値の詳細 |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | なぜやるのか | 事実（誰がどの場面で何に困るか。不具合なら再現の手順と、期待する動き・実際の動き）。保留中は最後に「再開の条件」 | 案・やり方 |
| 3 | やること（調査は: 調べ方） | どうやるのか | 案と手段。番号付き。段階があれば段階ごと | なぜやるかの事実 |
| 4 | 決めること | まだ決まっていないことは何か | 決まっていないことを1行ずつ（問うのは1度に1つ。問うているものは本文の先頭にある） | 決まったこと（→ 6）。無ければ節ごと省く |
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる形のチェック（`- [ ]`。本文のチェックはここにだけ使う。チェックの無いものが残るとゲートは閉じない）。マージの時点で確かめられることだけを書く（ユーザーの確認はラベル `ユーザー確認`） | 手段。マージのあとにしかできない作業（本番での操作・公開・長い観測）は、自動にするか別の issue にして blocked by でつなぐ |
| 6 | 経緯 | いつ何が決まり、何が変わったか | 日付つきで1行ずつ、新しいものを上に。無ければ省く | 問いと答えの全文（答えのコメントにある） |
| 7 | 規模の根拠 | 規模の札の根拠 | 札と根拠1行 | ― |

- 節の中では、並べるものは箇条書きにし、長い段落を作らない。複数の案や観点を比べるときは表にする。
- `<details>` の中は、`<summary>` の行のあとに空行を1つ入れてから書く（入れないと Markdown が効かない）。
- 問いに答えが出たら、Claude は 4 からその行を消し、6 へ1行足す（本文だけ読めば今の状態が分かるように）。
- hidakagit が GitHub の画面で種類のテンプレート（置き場の `.github/ISSUE_TEMPLATE/`）から作った issue は、節が
  見出し（`###`）で並ぶ。Claude は着手するときに、この形（畳む節）へ整える。

## ラベルと種類と欄

- 種類は Issue types（不具合・要望・保守・調査）で、1つのタスクにちょうど1つ。
- 1つのタスクに1つの値を持つもの（Status・優先度・規模）は、Project の単一選択の欄に置く。スマホの GitHub アプリでも
  issue の ⓘ →「プロジェクト」に出る（組織の issue fields は出ないので使わない）。優先度は仕事としての重さの見積もりで、
  入口でゲートが既定の値（`flow.config.json: project.defaults`）を入れ、Claude が起票するときは CLAUDE.md「優先度の見積もり」で
  入れる（ユーザーが直してもよい）。振り出しはその選択肢の順に並べる。規模は Claude が `field.js` で入れる。
  欄は機械が決めるものなので、回答フォームには出さない（ユーザーが直すときはボードで）。選択肢を足せば並べ順はそのまま効く。
- ステータスは Project の Status だけが持ち、ラベルに写さない。動かすのは回答フォーム・Pull Request の出来事・Claude の道具（`move.js`・`ask.js`）・閉じる操作で、ボードで動かすとゲートが戻す。
- ラベルはユーザーが付ける札（例: 急ぎ・ユーザー確認）。状態・操作待ちのように、ステータスと問いで表せるものはラベルにしない。「急ぎ」はユーザーの「急いで」の依頼で、振り出しは優先度の欄より先に並べる。「開発機が要る」は担当かユーザーが付け、振り出しはそのタスクを飛ばす（「担当」）。「ユーザー確認」は「完成にする前に自分で確かめたい」の意思表示で、残りに数えられる。回答フォームは、置き場に定義されたラベルを
  名前を持たずに全部出す。規模の決め方は CLAUDE.md「規模の札」。前提は blocked by で付ける。
- 状態を動かしただけのコメントは書かない。本文と判断材料の詳細は `<details>` に入れる。

## コミット

件名は `tasks#<issue の番号>: <何が変わったか（利用者・運用から見た結果の1行）>`。本文の行（背景・課題・成果・検証・増減・残り）は CLAUDE.md
「コミット時の同期ルール」のとおり。

## ゲートを変える・公開する

表・入口・回答フォームの選択肢・決まった問いは `flow.config.json` を直す。公開は、master に入ると CI（`ci.yml` の `deploy-gate`）が
`wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で行う（コードのリポジトリの秘密の値 `CLOUDFLARE_API_TOKEN`・
`CLOUDFLARE_ACCOUNT_ID` を使う）。公開の直後に、`tools/flow-gate/bin/refresh.js` が開いた issue を全部、今の規則が書くはずの姿
（担当者・本文の先頭のボタンと問い）へ揃える（ゲートは出来事が届いた issue しか書き直さないため。揃っていれば何も書かない）。
手で公開するときは `tools/flow-gate` で同じコマンドを打ち、続けて `refresh.js` を流す（`--dry-run` で揃える件数を先に見られる）。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`（CI の `flow-gate` も同じ）。
