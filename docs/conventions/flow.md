# タスクの流れ

タスクは GitHub の issue である。1つの Pull Request に収まらないタスクは段階に分け、段階も同じ形の issue（親の sub-issue）に
する（下の「段階に分ける」）。ステータスは段階も含めてどの issue も持ち、Project の欄「Status」に置く。
ステータスの移り変わりと割り当ては**遷移の表**（`tools/flow-gate/flow.config.json: transitions`）だけが決め、
ゲート（`tools/flow-gate/`）が GitHub の出来事を受けて表で照らす。表に無い変化は、誰が起こしてもゲートが前へ戻して
理由をコメントする。人（hidakagit）の判断は、回答フォームで明確な選択肢を選んで行う。

## 置き場と役割

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリと Project（`flow.config.json: repository`・`project`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 表で次のステータスと割り当てを決めて書く。表に無い変化を戻す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメントを書く・実施の順番・検証中の確かめ・Project の欄の規模と優先度 |
| hidakagit | 回答フォームで答える。GitHub の画面で何を動かしてもよい（表に無ければゲートが戻す） |

- Claude は GitHub の置き場へ、hidakagit-bot のトークン（ユーザー環境変数 `FLOW_BOT_TOKEN`）でだけ書く。hidakagit の
  トークンで書かない——hidakagit に通知が届かず、ゲートが hidakagit の操作と見分けられなくなる。
  gh で書くときは `GH_TOKEN` に `FLOW_BOT_TOKEN` の値を渡す。
- ゲートは自分の書き込み（送り主 `flow.config.json: gate`）を無視する。組み込みの自動化「Auto-add to project」
  （段階は「Auto-add sub-issues to project」）が issue を Project に入れると、ゲートが入口（下）を処理する。

## ステータスと割り当て

ステータスの名前・意味の並びと表は設定ファイルが正本で、ここに写さない。読み方だけを書く。

- **入口**（`entry`）: issue を書いた人で決まる。hidakagit が書いた issue は未着手で hidakagit-bot に、それ以外
  （Claude が書いた提案）は回答待ちで hidakagit に割り当て、ゲートが設定の採否の問い（`adoption`。やる → 未着手／
  やらない → 完了＝見送り）を本文の先頭に置く（`ask.js` の問いと同じ置き場）。段階（親のある issue）は、
  書いた人によらず未着手で hidakagit-bot に割り当てる（採否は親で済んでいる）。
- **遷移**（`transitions`）: `from` から `to` へ動けて、`assign` がそのときの割り当ての既定（`null` は今のまま）。
  `when: blockersCompleted` の行は、前提（blocked by）が全部 completed で閉じているときだけ通る。
- **割り当て**: 回答フォームを通らない変化は表の既定、回答フォームを通る変化はフォームで選んだ「次に動くのは」。
  検証中だけは、ラベル `ユーザー確認`（`verify.label`）があればユーザー（`ask.answerer`）にする。このラベルは回答フォームの
  ラベルの欄で付ける（hidakagit が書いた issue のように問いを通らないものは、GitHub で手で付ける）。
  開いているタスクには常に hidakagit か hidakagit-bot の1人が割り当たる。**hidakagit-bot に割り当たったものが Claude の番**。
- **完了**: 閉じた理由（completed＝完成／not planned＝見送り）で分ける。マージのあとの master の CI が通り、完了の条件が
  全部チェックされていると、ゲートが completed で閉じる（「Pull Request のあと」）。ボードで完了へ動かしたもの・回答フォームで完了を選んだものは、見送りで閉じる。
  子（段階）が全部閉じると、子が完成でも見送りでも、ゲートが親を completed で閉じる。完了からは戻せない（続きは新しい issue）。

## Claude がステータスを動かす

    node tools/flow-gate/bin/move.js <issue の番号> <ステータス>（保留なら続けて <理由>）

表で通らない変化は書く前に断る。回答待ちへは動かさない（問いと一緒に `ask.js` で動かす。「問い」の節）。保留へは理由が
必須で、道具が「保留にする理由: …」のコメントを書いてから動かす（「保留と棚卸」の節）。
Claude の番を振り出す順に並べて出すのは `node tools/flow-gate/bin/queue.js`（`--json` で機械向け）。

## 司令塔と担当（Claude が自分の番を進める）

Claude の番（hidakagit-bot に割り当て）は**キュー**で、担当が動く作業ツリーは**スロット**である。司令塔は起動のたびに、
空いたスロットの数までキューの上から担当へ渡して終わる。それ以外はしない（自分では作業せず、表も持たない。状態は issue と
ゲートとスロットの枝だけが持つ）。作る担当が PR を出すとゲートが検証中にし、それが確かめる依頼としてキューに載る。

- **起動**: この PC の予定のタスク（Desktop の Routines の `ridecompass-coordinator`）が司令塔のセッションを起こす。
  アプリが開いていて PC が起きている間だけ動く。前の回のセッションが動いている間は次の回を飛ばすが、背景の担当を待って
  いる間はセッションが動いていない扱いになり、次の回が起きる。そのため司令塔は担当を待たずに終わり、終わったあとに届いた
  担当の報告では何も動かさない（二つの司令塔が同じ作業ツリーへ振り出さないため）。空いた作業ツリーは次の起動が埋める。
- **スロット**: 本体の `.claude/worktrees/` に、司令塔用の `coord` と担当用（`flow.config.json: coordinator.worktrees`。例: `w1`〜`w4`）を置いたままにして使い回す
  （frontend の依存の入れ直しを毎回しないため。`node_modules` の共有は CLAUDE.md で禁止）。担当は始めるときに自分の枝
  （作る担当は `orch/tasks-<番号>`、確かめる担当は `verify/tasks-<番号>`（`coordinator.verifyPrefix`））をまっさらに取り、
  終わるときに push してから枝を手放す（`git checkout --detach`）。スロットには何も残さず、担当から担当へ渡すのは GitHub の
  作業ブランチと issue だけ。`node tools/flow-gate/bin/slots.js` が、枝を持つスロット＝使用中（その番号の担当が動いている）、
  持たないスロット＝空き、と枝を取ってからの時間を出す。担当を一度に動かすのは、スロットの数まで。
- **重い処理は機械全体で1本ずつ**: 依存の入れ直し・型検査・テスト・ビルド・e2e は `python scripts/heavy.py -- <コマンド>`
  で包む（同時に走ると CPU とディスクを取り合って1本ごとの所要が何倍にも伸びる）。

**司令塔の1回**
1. `coord` を `git fetch origin master` のあと `git checkout --detach origin/master` にし、そこでこの節を読み直す。
2. `node tools/flow-gate/bin/queue.js --json` で Claude の番を読む（並びはステータスの順 `coordinator.order`（Claude に戻った回答待ち → 検証中 → 未着手）、
   中はラベル「急ぎ」（ユーザーの依頼。優先度の欄より上。`project.urgentLabel`）→ Project の優先度の欄の選択肢の順 → 番号の若い順）。
3. `slots.js` で空いているスロットを見て、その数までキューの上から渡す。**使用中のスロットが持つ番号の項目は、担当が
   動いている最中なので飛ばす**。未着手（前提待ちでないもの）は `node tools/flow-gate/bin/move.js <番号> 進行中` のあと
   作る担当へ、検証中は確かめる担当へ、回答待ち（「その他」などで Claude に戻った問い）は作る担当へ（補足を読んで問いか
   提案を直し、`ask.js` で問い直すだけ。ステータスは動かさない）渡す。担当は背景の Agent で起動し、スロットのパスと
   issue の番号を渡す（司令塔が渡す固定のスロットを使うので、`isolation` は付けない）。
4. 渡したら、担当の報告を待たずに終わる。
5. `slots.js` で、枝を取ってから4時間を超えて使用中のスロットは、担当が落ちた（PC の再起動等）とみなす。
   - 作る担当（`orch/tasks-<番号>`）: 進行中はキューに入らず誰も拾わないので、`move.js <番号> 保留 <理由>` で保留にする
     （hidakagit が棚卸で決める。作業ブランチに push 済みの分から続けられる）。未コミットの変更が無ければ枝を手放させる
     （`git -C <スロット> checkout --detach`）。変更があれば消さずにスロットごと残し、理由に書く。
   - 確かめる担当（`verify/tasks-<番号>`）: 枝を手放させるだけ（検証中はキューに残っているので、次に渡し直される）。
   進行中にするのは司令塔だけ（空いたスロットへ作る担当を渡すとき）なので、進行中の数はスロットの数を超えない。

**作る担当**・**確かめる担当**のどちらも、作業は渡されたスロットの中だけで行う（ほかのスロットや本体では、ファイルの
編集も git の操作もしない。ほかのスロットは別の担当が使っていて、変更を残すとその作業に混ざる）。どの終わり方でも
（PR を出した・問うた・段階に分けた・確かめてマージした／閉じた）、push してから `git checkout --detach` で枝を手放して終える。

**作る担当**
1. 渡されたスロットで、未コミットの変更が無いことを確かめてから `git fetch origin master`。変更が残っていれば、何もせず
   司令塔へ報告する。作業ブランチ `orch/tasks-<番号>` が GitHub にあれば（Pull Request が閉じられて戻った・答えをもらって
   戻ったタスク）、`git fetch origin orch/tasks-<番号>` と `git checkout -B orch/tasks-<番号> origin/orch/tasks-<番号>` のあと
   `git rebase origin/master` で前の作業を master の上へ載せ直す（競合したら直して続け、直せなければ司令塔へ報告）。
   無ければ `git checkout -B orch/tasks-<番号> origin/master`。
2. `frontend/package-lock.json` が前の回と違えば、`frontend` で `python ../scripts/heavy.py -- npm ci`。backend は
   作業ツリーに `.venv` を持たず、本体の `backend/.venv` の Python を使う（依存は共有してよい）。
3. issue の本文とコメント（やり直しなら、前の Pull Request のコメントも）を読み、CLAUDE.md と規約のとおりに作る。
   hidakagit の判断が要るところは「問い」の形で書いて `ask.js` で問い、そこで終える（答えは次の起動で拾われる）。
   1つの Pull Request に収まらないと分かったら、「段階に分ける」のとおりに分けて終える（段階は次の起動から1件ずつ振り出される）。
4. `tasks#<番号>:` の件名でコミットし、`orch/tasks-<番号>` へ push して CI を待つ（競合で作り直すときは master の上へ
   rebase して push し直す。作業ブランチは書き換えてよい）。
5. CI が通ったら、コードのリポジトリに Pull Request を出す（`gh pr create --base master --head orch/tasks-<番号>`。
   コードのリポジトリは hidakagit のものなので、`GH_TOKEN` に hidakagit のトークン（ユーザー環境変数 `GH_TOKEN`）を渡す）。
   件名はコミットと同じ、本文は次の順に書く:
   - 置き場の issue へのリンク（`https://github.com/ridecompass/ride-compass-tasks/issues/<番号>`）と、何が変わったかの1〜3行
   - 修正前後のキャプチャ（`--attach <前の画像>` と `--attach <後の画像>`。画面・幅など、何を撮ったかを添える）
   - 画面に出ない変更は、確かめ方と根拠（実行したコマンドと出た値・読んだ公式の文書）
   - `backend/scripts/lost_constraints.py`（master との合流点からの、ORM の宣言から消えた制約）が出した「消えた」の
     1件ずつに、処置（移した先・意図して外した理由）。書き直しで落ちた制約は差分に1行も出ないため
   - 派生の値か軸の難易度を変える変更なら、列・軸ごとの分布の前後（下の「分布の前後」）
   前の Pull Request が開いたまま残っていれば、新しく出さずに push し、撮り直したキャプチャを `gh pr comment --attach` で足す。
6. issue の本文を直し（経緯・完了の条件のチェック。マージのあとでないとできない条件だけをチェックの無いまま残す）、
   Pull Request へのリンクをコメントに書いて報告する。Pull Request を出すと、ゲートが検証中へ動かす（`move.js` は使わない）。
   確かめる番は、ラベル `ユーザー確認`（`flow.config.json: verify`）があればユーザー、無ければ Claude（確かめる担当）になる
   （ゲートが割り当てる）。

**分布の前後**（派生の表の値か評価軸の難易度を変える変更。差分が `backend/app/batch/` の派生の段か、
`backend/app/domain/` の材料の値式・軸の評価に触れるもの）
落ちた絞り込み・二重に数えた値は、エラーにもテストの失敗にもならず、値の偏りとしてだけ現れる。作る担当は変える列・軸を
変更の前と後で測り、Pull Request の本文に1件1行で「前 → 後」と、変わった理由を書く。前は編集する前（スロットが master の版の
うち）に測る。どちらの道具もプローブの後ろの引数をそのまま受け取るので、本番へは `run_probe.py` の後ろに並べて打つ。
- 派生の値: 開発DBで、変える段から `python -m app.batch.derive_cli --from <段>` を流し、`backend/scripts/derived_distribution.py --column <表.列>` で
  測る（前）。変えたあとに同じ段を流して測る（後）。前も流し直すのは、開発DBは別の担当が別の版で作り直していることがあるため。
  本番の今の値も `run_probe.py scripts/derived_distribution.py --column <表.列>` で測って添える（開発DBは範囲が狭いので、
  前が本番と大きく違えば開発DBの側を疑う）。本番の派生を作り直すのは本番DBへ書くことなので、担当はしない。
- 軸の難易度: 本番を `run_probe.py scripts/measure_axis_saturation.py --axis <軸> --bbox <範囲>` で前と後に測る（読み取りだけ。
  軸の定義の正本は本番DBにある。抽選は回ごとに標本が変わるので、範囲を決めて同じ標本にする）。

**Pull Request のあと**（ゲートが、コードのリポジトリの Webhook から届く Pull Request と CI の出来事で動かす）
- 開いた（開き直された） → 進行中（`verify.from`）なら検証中。もう検証中なら何もしない
- マージされずに閉じた → 未着手（閉じたときのコメントを作る担当が読んでやり直す）。master と競合して Merge が押せない
  ときも、確かめる人が「競合」と書いて閉じる（競合を知らせる出来事は GitHub に無い）
- マージされた → マージのあとの master の CI を待ち、通れば完了で閉じ、落ちれば落ちた実行を書いて未着手。通っても、本文の
  完了の条件にチェックの無いもの（`- [ ]`）が残っていれば閉じず、残りを書いて未着手（Claude）へ戻す。Claude は残りを済ませ
  （hidakagit の操作なら `ask.js` で頼む）、チェックを付けてから `gh issue close <番号> --reason completed` で閉じる
- 上のどれにも当たらないとき（開いたのに issue が進行中でも検証中でもない・閉じたのに検証中でない。検証中を通らずに
  マージした・閉じた issue の古い Pull Request など）は、ステータスは動かさず（確かめる段を飛ばさないため）、理由をコメントに
  書いて、開いていれば hidakagit に割り当てる。次は hidakagit が決める
- Claude も司令塔も、これらを自分で動かさない（`move.js` を使わない）。
- GitHub は届かなかった出来事を送り直さない。マージや CI のあとも検証中のまま止まったものは、コードのリポジトリの Settings →
  Webhooks → Recent Deliveries から Redeliver する（3日分まで）。

**確かめる担当**（ラベル `ユーザー確認` の無い検証中。作った担当とは別）
1. 渡されたスロットで、未コミットの変更が無いことを確かめてから、作業ブランチを確かめる枝として取る（`git fetch origin orch/tasks-<番号>` と
   `git checkout -B verify/tasks-<番号> origin/orch/tasks-<番号>`）。Pull Request（本文のキャプチャ・差分）・作業ブランチの CI・issue の完了の条件・変更が届く範囲（要るなら画面）を
   確かめる。作る担当の報告を読み写さず、自分で見る（画面なら自分で撮る）。Pull Request が無ければ（手順が変わる前に
   検証中になったもの）、作る担当の5のとおりに出してから確かめる。`lost_constraints.py` も自分で回し、「消えた」の
   1件ずつに本文の処置があるかを見る（処置の無いものが1件でもあれば満たしていない）。「分布の前後」の対象なら、
   列・軸ごとの前後の行が本文にあるかを見て、本番で測れる側（派生は本番の今、軸は後）を自分で測り直す。
2. 確かめた結果を、満たしていてもいなくても issue にコメントで書く（見出し「確かめた結果」）。完了の条件の1件ごとに、
   何をどう見て（実行したコマンド・開いた画面）何が出たかを書き、撮った画面は Pull Request へ `gh pr comment --attach` で貼る。
   ここに書いたことだけが、確かめた証拠として残る。
3. ユーザーが見るべきだと判断したら（利用者から見える振る舞い・モジュールの設計が変わる等）、issue にラベル `ユーザー確認` を
   付け、理由を書いて hidakagit に割り当て直して終える（本文の先頭に Pull Request を開くボタンが出る）。「分布の前後」の対象は
   いつもそうし、理由に前後の行を写す（値の偏りが意図どおりかは、完了の条件にもテストにも出ない）。
4. 満たしていなければ、足りないことを書いて Pull Request を閉じる（`gh pr close <番号> --comment <理由>`）。ゲートが未着手へ戻す。
5. 満たしていれば Pull Request をマージする（`gh pr merge <番号> -R hidakagit/ride-compass --rebase`。Claude Code の許可の
   規則 `gh pr merge *` に合う形なので、この書き方のまま打つ。ほかの書き方や API の呼び出しは許可の判定で止まる）。
   master の CI は待たない（ゲートが閉じる）。
   競合でマージできなければ、「競合」と書いて閉じる（4 と同じ）。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当が自分でしない。
hidakagit に頼む問いを `ask.js` で問う。問いの文の頭に「PC での操作:」と書き（スマホで本文の先頭の1行を見て、PC が要ると
分かるように）、判断材料に手順と確かめ方を書く。選択肢は「済んだ」とその他（できない理由）。済んだと答えが来たら、
Claude が確かめ方のとおりに確かめ、完了の条件にチェックを付ける。

## 問い

hidakagit に求めることは、採否・判断・操作のお願い・確認のどれも、次の形でファイルに書き、道具で問う（hidakagit-bot の名義）。

    node tools/flow-gate/bin/ask.js <issue の番号> <問いのファイル>

道具は形を照らしてから、問いを本文の先頭（ゲートの印の間）に画面に出ない形（HTML のコメント）で書き、回答待ちへ動かす
（もう回答待ちなら hidakagit に割り当て直す）。hidakagit の番の間は、ゲートがその下へ「回答する」のボタンの
画像（リンク付き。スマホのアプリでも押せる）と、ステータス・問いの文の1行を置く（コメントは古い順にしか並ばず、一番下は
見落とすため。GitHub の画面そのものにはボタンを足せない）。選択肢と判断材料は回答フォームで読む。

    ## 問い
    <問いの文（1行）>

    ### 選択肢
    - <文> → <次のステータス> / <次に動く者>
    - <文> → <次のステータス>
    - <文>

    <details><summary>判断材料</summary>
    （この問い1つだけで判断できるように書く）
    </details>

- 今の問いは、本文の先頭にある1つだけ。問い直すと置き換わり、答えるとゲートが本文から消す。`-->` は書けない
  （問いを隠す HTML のコメントが途中で閉じる。道具が断る）。
- 答えを待っているのは、回答待ちで hidakagit に割り当たっている間。答えるとステータスか割り当てが必ず変わる
  （今のままになる答えは Claude の番になる）ので、答えたあとに回答フォームは開かない。
- **ステータスは、選んだ選択肢に書いた行き先だけで決まる**（AI が状態を判断しない）。選択肢は2つ以上で、判断そのもの
  だけを書く。`→` の後ろは要るときだけ書く: 次のステータス（設定の名前）・次に動く者（`people` の `shown`。Claude か
  hidakagit）。ラベルは選択肢に書かない（回答フォームのラベルの欄で付ける）。行き先を書いていない選択肢は状態を決めず、
  回答待ちのまま Claude の番になる（回答フォームは次に動く者を選ばせない）。次に動く者を書かなければ、表の既定。
  見送り（完了）を選べるようにするかは、問いを書く人が選択肢で決める（採否の問いには「やらない → 完了」がある）。
- 回答フォームは、どの問いにも次の2つを足し（`formOptions`）、表で行けない選択肢は出さない。
  - 「その他（コメント）」: 状態を決めない。回答待ちのまま Claude の番になり、Claude は補足を読んで問いか提案を直し、
    `ask.js` で問い直す（ステータスは動かさない）。
  - 「止める（保留）」: 補足（理由）が必須。保留になり hidakagit の担当になる（「保留と棚卸」）。
  選択肢とは別に、置き場のリポジトリに GitHub で定義されているラベルを全部、今の付き方のまま並べ、
  付け外しをそのまま効かせる（答えのコメントに「ラベル: +… −…」を残す）。札を足すときは GitHub でラベルを作るだけでよい。
- 答える時点で答えられることだけを聞く。
- **聞くかどうか**: 外から見える振る舞いが変わるときだけ聞く。変わらないなら聞かずに報告して直す。聞いたら答えを待つ。
- **書く順**（判断材料の中）: 利用者への約束を1文 → 問題が起きる場面を1つと、起きない場面を1行 → 選択肢ごとに
  利用者に何が起きるか。背景を知らない人がこの問い1つだけで判断できるように、何の画面・機能の話か・いまどうなって
  いるか・なぜ決める必要があるかを入れる。画面の見た目・情報量に関わる判断は、変更前と変更後の画面かモックを添える。
- **製品の言葉で書く**: 実装の語（関数名・引数名）・固有名詞・タスク番号に頼らない。
- **選択肢**: 自分の領分（どう直すか・書き方）を選択肢に入れない。選択肢の文と実際に当てる作業を一致させる。
  推奨は判断材料の最後に理由と一緒に書く。回答フォームで完了を選ぶと見送りで閉じるので、完成を問いで決めない。
- 形が崩れた問いのまま回答待ちになると、ゲートがそう書いて hidakagit-bot に割り当てる。書き直してから
  hidakagit を割り当て直す。

## 答え

回答フォームが hidakagit の名義で次のコメントを書く。問いは答えると本文から消えるので、問いの文・全部の選択肢・判断材料も
ここに残す（このコメント1つで、何を問われて何を選んだかが読める）。Claude はこれだけを読み、チャットでの答えを判断に
使わない。補足は決定を変えない。

    ## 回答
    **<問いの文>**

    ○ <選ばなかった選択肢>
    ● **<選んだ選択肢>**

    次のステータス: <名前>
    次に動くのは: <Claude／hidakagit>
    ラベル: +<付けたもの> −<外したもの>（変えたときだけ）
    補足: <書いたときだけ>

    <details><summary>判断材料</summary>（問いにあったときだけ）</details>

## 段階に分ける

1つの Pull Request に収まらないタスクは、段階ごとに親と同じ形（「issue の形」）の issue を作り、普通のタスクとして進める。

    node tools/flow-gate/bin/stage.js <親の番号> <題名> <本文のファイル> [前の段階の番号...]

- 道具は段階を親を付けたまま作り（作ってから親を付けると、Project に入った時点で段階と分からず採否の問いが付く）、
  前の段階を blocked by にする（前の段階が完了で閉じるまで進行中にできない）。Project へは「Auto-add sub-issues to project」が
  入れ、ゲートが入口で未着手・Claude にする。規模と優先度は `field.js` で入れる。
- 親の本文の「やること」に段階の番号を並べ、親を `move.js <親の番号> 保留 "段階（#…）の完了を待つ"` で保留にする。
- 段階は1件ずつ、自分の作業ブランチ（`orch/tasks-<段階の番号>`）と Pull Request で進む。子が全部閉じると、ゲートが親を閉じる。

## 保留と棚卸

保留は「止めて、あとで決める」置き場で、担当はいつも hidakagit。hidakagit が棚卸で1件ずつ決める（AI は決めない）。

- **保留に入る道**（どれも理由がコメントに残る）: 回答フォームの「止める」（補足が答えのコメントに残る）・
  `move.js <番号> 保留 <理由>`（Claude。司令塔が落ちた担当を止める・段階を待つ親など）・ボードで直接（hidakagit。
  理由は必要なら hidakagit がコメントに書く。ゲートは何もしない）。
- **棚卸**（hidakagit がボードで動かす）: やる → 未着手（Claude の番）・やめる → 完了（見送りで閉じる）・
  Pull Request まで済んでいる → 検証中。保留から回答待ちへは表に道が無い（ボードで動かすとゲートが戻す。問いが要るなら
  未着手に戻せば Claude が問う）。

## issue の形

**題名**は、何をするか（または何が困るか）だけを30字前後で書く。数値・経緯・やり方・括弧書きの補足は本文へ。

**本文**は次の節をこの順に並べ、1 以外は `<details><summary>節の名前</summary>` で畳む。節ごとに「答える問い」が1つだけあり、
それに当たらないものはその節に書かない。

| 順 | 節 | 答える問い | 書くもの | 書かないもの |
|---|---|---|---|---|
| 1 | 要約（畳まない） | 開いて2行で何が分かるか | 何が起きていて、何をするか（1〜2文） | 経緯・数値の詳細 |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | なぜやるのか | 事実（誰がどの場面で何に困るか。不具合なら再現の手順と、期待する動き・実際の動き）。保留中は最後に「再開の条件」 | 案・やり方 |
| 3 | やること（調査は: 調べ方） | どうやるのか | 案と手段。番号付き。段階があれば段階ごと | なぜやるかの事実 |
| 4 | 決めること | まだ決まっていないことは何か | 決まっていないことを1行ずつ（問うのは1度に1つ。問うているものは本文の先頭にある） | 決まったこと（→ 6）。無ければ節ごと省く |
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる形のチェック（`- [ ]`。本文のチェックはここにだけ使う。チェックの無いものが残るとゲートは閉じない） | 手段 |
| 6 | 経緯 | いつ何が決まり、何が変わったか | 日付つきで1行ずつ、新しいものを上に。無ければ省く | 問いと答えの全文（答えのコメントにある） |
| 7 | 規模の根拠 | 規模の札の根拠 | 札と根拠1行 | ― |

- 節の中では、並べるものは箇条書きにし、長い段落を作らない。複数の案や観点を比べるときは表にする。
- `<details>` の中は、`<summary>` の行のあとに空行を1つ入れてから書く（入れないと Markdown が効かない）。
- 問いに答えが出たら、Claude は 4 からその行を消し、6 へ1行足す（本文だけ読めば今の状態が分かるように）。
- hidakagit が GitHub の画面で種類のテンプレート（置き場の `.github/ISSUE_TEMPLATE/`）から作った issue は、節が
  見出し（`###`）で並ぶ。Claude は着手するときに、この形（畳む節）へ整える。

## ラベルと種類と欄

- 種類は Issue types（不具合・要望・保守・調査）で、1つのタスクにちょうど1つ。
- 1つのタスクに1つの値を持つもの（Status・優先度・規模）は、Project の単一選択の欄に置く。スマホの GitHub アプリでも
  issue の ⓘ →「プロジェクト」に出る（組織の issue fields は出ないので使わない）。優先度は仕事としての重さの見積もりで、
  入口でゲートが既定の値（`flow.config.json: project.defaults`）を入れ、Claude が起票するときは CLAUDE.md「優先度の見積もり」で
  入れる（ユーザーが直してもよい）。司令塔はその選択肢の順に並べる。規模は Claude が `field.js` で入れる。
  欄は機械が決めるものなので、回答フォームには出さない（ユーザーが直すときはボードで）。選択肢を足せば並べ順はそのまま効く。
- ステータスは Project の Status だけが持ち、ラベルに写さない。動かすのはボード・回答フォーム・move.js・ask.js。
- ラベルはユーザーが付ける札（例: 急ぎ・ユーザー確認）。状態・操作待ちのように、ステータスと問いで表せるものはラベルにしない。「急ぎ」はユーザーの「急いで」の依頼で、司令塔は優先度の欄より先に並べる。回答フォームは、置き場に定義されたラベルを
  名前を持たずに全部出す。規模の決め方は CLAUDE.md「規模の札」。前提は blocked by で付ける。
- 状態を動かしただけのコメントは書かない。本文と判断材料の詳細は `<details>` に入れる。

## コミット

件名は `tasks#<issue の番号>: <issue の題名>`。本文の行（背景・課題・成果・検証・増減・残り）は CLAUDE.md
「コミット時の同期ルール」のとおり。

## ゲートを変える・公開する

表・入口・問いの形の選択肢は `flow.config.json` を直す。公開は `tools/flow-gate` で `wrangler deploy`（Webhook）と
`wrangler deploy --env form`（回答フォーム）。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`（CI の `flow-gate` も同じ）。
