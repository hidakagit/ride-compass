# タスクの流れ

## 原則

流れ（タスクの進め方・ゲート・担当・道具・この手順書と流れのスキル）の決まりは、次の6つから導く。各節の先頭の「導く原則」は、
その節の決まりをどの原則から導いたかを示す。

1. **ユーザーの手は、判断と最後の確かめだけ**: ユーザーに求めるのは、何を作るか・どちらの案にするかの判断と、本番での最後の確かめだけ。操作（PC での作業・パッチ当て・本番への書き込み）は求めない。ただし Claude が打てない操作（本番のデータを完全に消す・外部の画面でのアカウント作成等）だけは、打つものを用意して頼む。
2. **回答待ちは、答えられる状態のときだけ**: 問い・答える中身（本番に出ていること）・回答フォームがそろってから、回答待ちにする。
3. **状態は1か所・動かす道は1つ**: タスクの状態の正本は1つで、同じ状態を複数の経路で書かない。
4. **詰まりは見ればわかり、あとから判断できる**: どのタスクが止まっていて、何を（誰を）待っているかが、聞かなくても一目でわかる。終わった作業は、あとから判断できる記録（担当の実行の全文・修正前後のキャプチャ・測り直した値）を残す。
5. **守るのは、利用者に見える結果**: テストも見張りも、利用者に見える壊れを先に守る。部品の内側の細部は後。
6. **例外は原則を直して扱う**: 原則に合わない場面が出たら、手順書や流れのスキルに例外を足さず、原則を見直す。原則から導けない決まりは書かない。

## 流れのあらまし

導く原則: 3。

タスクは GitHub の issue である。1つの Pull Request に収まらないタスクは段階に分け、段階も同じ形の issue（親の sub-issue）に
する（.claude/skills/file-issue/SKILL.md「段階に分ける」）。issue は種類で2つの世界に分かれる: 種類「対話作業」（`flow.config.json: dialog`）は
開発機の対話のセッションだけが触る対話作業の世界で、対話作業のボードに載る。それ以外は Actions の世界で、Actions のボード（`flow.config.json: project`）に
載り、ステータスを Project の欄「Status」に持つ。2つの世界は、同じ置き場の中の前提（blocked by）と段階でだけつながる。

Actions の世界のステータスは、**ゲート**（`tools/flow-gate/`）だけが書く。担当（作る・確かめる）は持つ・手放すだけをし、ステータスを
書かない。ゲートは出来事（担当の実行の始まりと終わり・CI の終わり・問い・答え・PR・ユーザーのボードの移動・閉じる）を受けるたびに、
そのときの事実（動いている担当・答えの無い問い・作業ブランチの PR と CI・完了の条件・前提・着手可能日時）を読み、表（下の「ステータスと割り当て」）で
ステータスを決めて書く。ユーザーの決定で受けるのは保留と完了だけで、ほかのボードの移動は表で決め直す。それぞれの状態で何をするかは、
この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）の手順が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリと2つのボード（`flow.config.json: repository`・`project`・`dialog`） | タスクの issue・段階・問いと答え・記録。記録は issue にだけ持ち、git に写さない |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | issue を種類でボードへ入れる・事実からステータスを決めて書く・担当者と本文の先頭のボタンを揃える・ゲートが出す問い・PR をレビュー可能にする・保留にしたタスクの担当の実行を取り消す・種類の変更を見張る。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・担当の問いとコメントを書く・検証待ちの確かめとマージ・Project の欄の規模と優先度 |
| ユーザー（hidakagit） | 問いに回答フォームで答える（開発機の対話のセッションではチャットで。.claude/skills/ask/SKILL.md「答え」）。本番での最後の確かめ。ボードで保留へ入れる・出す・完了にする。ラベル（`急ぎ` 等）を付け外しする |

- Claude が置き場へ書く名義とトークンは「担当」の「名義」が持つ（開発機の対話のセッションも同じ）。
- ゲートは自分の書き込み（送り主 `flow.config.json: gate`）を無視する。issue をボードへ入れるのはゲートで（issue が作られた出来事を受ける）、
  組み込みの自動追加（Auto-add to project）は使わない（自動追加の条件は issue の種類で分けられない。公式の文書「Adding items automatically」）。
- 種類は作るときに決め、あとから変えられない: 種類の変更が対話作業の境目（どちらのボードに載っているか）をまたぐと、ゲートが元の種類へ
  戻して1行書く。GitHub の標準には issue ごとに種類を固定する設定が無い（公式の文書「Managing issue types in an organization」）。
  境目をまたがない変更（不具合から保守へ等）は通す。

## ステータスと割り当て

導く原則: 1・2・3・4。

ステータスの名前は設定ファイル（`flow.config.json: status`）が正本で、表の決め方は `tools/flow-gate/src/rules.js: decide` が持つ。ここには読み方を書く。

- **持ったとき**（担当の実行が起きた時点。同じ組の前の実行を待つ順番待ちを含む）: 作る担当なら進行中、確かめる担当なら検証中。
  持たれている間は、ほかのどの出来事でも動かない。
- **決め直すとき**（手放し＝担当の実行の終わり・CI の終わり・問い・答え・PR の出来事・ユーザーの移動・閉じる・見回りの頼み）: 上から最初に当たるもの。

  | 事実 | ステータス |
  |---|---|
  | 答えの無い問いがある（最新の「## 問い…」の後に「## 回答」が無い） | 回答待ち |
  | 作業ブランチ（`orch/tasks-<番号>`）の開いた下書きの PR がある | 先頭のコミットの CI が終わっていなければ CI待ち、落ちていれば未着手、通ったあとに下書きへ戻されていれば（差し戻し）未着手、それ以外はゲートが PR をレビュー可能にして検証待ち |
  | 下書きでない開いた PR がある | 検証待ち |
  | 完了の条件のチェックがあって、`- [ ]` が残っていない | 完了（完成で閉じる） |
  | 残りの条件が全部「ユーザーが確かめる」（`flow.config.json: userCheck`）の行 | ゲートが確かめの問いを出して回答待ち |
  | 開いた前提（blocked by）か、未来の（か形の合わない）着手可能日時がある | 未着手（その間は振り出されない） |
  | 担当が手放し、どれにも当たらず、マージした PR も無い（落ちた・取り消された・役目を果たさずに終わった） | ゲートがイレギュラーの問いを出して回答待ち |
  | それ以外（マージのあとの残り・答えで続けた等） | 未着手 |

- **CI**: 作業ブランチの PR の必須のチェック（master のルールセット）と、走っていれば変異テスト（`flow.config.json: code.mutation`）が全部
  終わったら CI が終わったとみる。成功・飛ばし以外で終わったものがあれば落ちた。変異テストの生き残りの注記は、前のコミットの回にも同じ
  注記があったもの（作る担当が一度見たもの）を除いて、落ちたものと同じに扱う。CI の各ワークフローの実行の終わりを受けるたびに決め直す。
- **保留と完了**: ユーザーがボードで保留へ入れると保留になり、担当が持っていればその実行を取り消す。保留はユーザーが出すまで
  動かず、出したら表で決め直す（ユーザーが選んだ列は見ない）。完了へは、完成（ボードの完了の列・Close as completed）なら完了の条件が全部
  チェック済みのときだけ入り、残りがあれば残りをコメントして表で決め直す。見送り（Close as not planned）はいつでも完了。完了からは戻せない（続きは新しい issue）。
  それ以外のボードの移動は、表で決め直す。
- **入口**: ゲートがボードへ入れた時点で表で決める（入った時点のボードの列は見ない）。ユーザーの起票・段階・Claude が起こした改善（種類が
  `todoTypes`）は、起こしたことが判断なので表のとおり（ふつうは未着手）。Claude が起こしたそれ以外（要望＝利用者に見える新しいもので、
  何を作るかは原則1のユーザーの判断。種類なしも）は、ゲートが採否の問いを出して回答待ちにする。段階は優先度の欄が空なら親の優先度を継ぐ。ほかの欄は書かない。
- **問いの種類**: 採否（入口でゲートが出す）・判断（担当が `ask.js` で出す）・確かめ（ゲートが出す）・イレギュラー（ゲートが出す）。問いの頭に種類を
  書く（「## 問い（確かめ）」）。回答フォームは種類ごとに要るものだけを出し、次のステータスは見せない（.claude/skills/ask/SKILL.md「問い」）。
- **答え**: ゲートが答えのコメントの決定を受ける。見送りは閉じ、保留は保留、続けるは表で決め直す。確かめで「よい」の項目は完了の条件に
  チェックを付け、「よくない」の項目は何がおかしいかを `- [ ] 直す: …` の行として完了の条件に足す（未着手になり、作る担当が直す）。
- **本文の先頭**: 答えの無い問いがある間だけ、ゲートの印 `<!-- flow-gate -->` の間に回答フォームへのボタンを1つ置く。問いを出す者
  （`ask.js`・ゲート）は、ボタンを書いてから問いのコメントを書く（問いの通知から開いた時点でボタンがある）。
- **担当者**: 回答待ちと保留のときだけユーザー（ユーザーの番になった通知）で、ほかは空。手で変えてもゲートが戻す。
- **残り**（`tools/flow-gate/src/rules.js: remaining`）: 本文の完了の条件のうちチェックの無いもの。ゲートはラベルを見ない。ユーザーに
  確かめてもらうことも、完了の条件の1行（`- [ ] ユーザーが確かめる: …`）として書く。

**1つのタスクを触るのは1者だけ**。Actions の世界のタスクを触る担当は1人で、同じタスクの担当の実行は担当のワークフローの組
（`.github/workflows/claude-task.yml` の `concurrency` の `claude-task-<番号>`）で1本ずつ動き、あとから来たものは取り消されずに順に待つ
（`queue: max`）。見回りは、担当の実行が終わっていないタスクへは振り出さない。開発機の対話のセッションが触るのは対話作業の世界の
issue で、Actions の世界のタスクには書かない（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」。例外はユーザーの介入）。

## 担当（Claude が自分の番を進める）

導く原則: 1・3・4・5。

役割は次のとおりに分ける。どの役も、ほかの役の持ち物を持たない。作る担当・確かめる担当の手順は .claude/skills/task-work/SKILL.md にある。

| 役 | 持つもの・すること |
|---|---|
| GitHub（issue・Project・ゲート） | タスクの状態（ステータス）。ゲートが事実から決めて書く |
| 振り出しの見回り（`.github/workflows/claude-dispatch.yml` が決まった間隔ごとに `tools/flow-gate/bin/dispatch.js` を1周打つ） | 振り出す（作る担当を未着手から、確かめる担当を検証待ちから、種類ごとの枠 `flow.config.json: coordinator.slots` まで）と、ボードと担当の実行の突き合わせ |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 準備をして担当を起こし、終わったら後始末をする |
| 作る担当・確かめる担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（PR・問い・issue へのコメント）。ステータスにも、次の担当を起こすことにも触れない |

**キュー**（仕事の並び）は GitHub のステータスから毎回導くもので、どこにも別に持たない。作る担当が下書きの PR を残して手放すと CI待ちになり、
CI が通るとゲートが PR をレビュー可能にして検証待ちにし、それが確かめる依頼として載る。

- **枠**: 作る担当と確かめる担当で、別々の上限（`coordinator.slots`）を持つ。貸し借りしない。作る担当の枠の使用数は進行中の数、確かめる担当の
  枠の使用数は検証中の数と一致する。CI待ちは担当がいないので、どちらの枠も使わない（CI 自身がランナーを使う）。
- **振り出す条件と順**（`tools/flow-gate/src/dispatch.js: ready`）: どちらも動いている担当の番号は除く。確かめるは検証待ちのタスク全部（前提・着手可能日時を問わない）。
  作るは未着手のうち、前提が全部閉じていて（段階に分けた親も、段階に blocked by されてここで待つ）、
  着手可能日時（.claude/skills/file-issue/SKILL.md「ラベルと種類と欄」）が今（日本時間）以前のもの。並びはラベル「急ぎ」
  （ユーザーの依頼）→ Project の優先度の欄の選択肢の順（空は `flow.config.json: project.unsetPriority` の位置）→ 番号の小さい順。
- **突き合わせ**（`tools/flow-gate/src/dispatch.js: mismatches`）: 毎周、担当が持つのにその種類のステータスでない・進行中か検証中なのに担当がいない・
  CI待ちなのに作業ブランチの CI が動いていないタスクを見つけ、ゲートに決め直しを頼む（置き場への `repository_dispatch` の `recheck`）。
  ゲートが出来事を取りこぼしたときの守りで、見回りはステータスを書かない。
- **見回り**: GitHub Actions のランナーで常駐し、`coordinator.watchEveryMinutes` ごとに master の今の道具を取り出し直して1周打つ
  （道具や設定の変更は、master に入れば次の周から効く）。前提が閉じた・止める時刻が過ぎた、のどれも、次の周で
  拾われる。実行の持ち時間（`coordinator.watchForMinutes`。GitHub のジョブの上限6時間より短い）が過ぎたら、次の実行を
  `workflow_dispatch` で起こしてから終える。1周の失敗では止まらず、最後に通った周（無ければ実行の始まり）から
  `coordinator.watchFailMinutes` のあいだ1周も通らなかったときだけ失敗で終わって次を起こさない（GitHub の失敗の知らせが届く）。
  途切れたら、手で `gh workflow run claude-dispatch.yml -R hidakagit/ride-compass`（Actions の画面の Run workflow でもよい）で起こし直す。
  定期の起動（`schedule`）は使わない。`node tools/flow-gate/bin/dispatch.js --dry-run` で、何を起こすか・何の決め直しを頼むかを見られる。
- **担当のワークフローの1回**:
  1. 起きる: 実行が起きた（順番待ちを含む）出来事をゲートが受け、持ったとして進行中か検証中にする。
  2. 準備（`.github/workflows/claude-task.yml` の段）。
  3. 担当を起こす。持ち時間はジョブの `timeout-minutes` で、超えると Actions がジョブを止める。担当の実行は、担当が手番を終えた
     最初の発言で終わる。裏で動かす道具（Bash の `run_in_background`・Monitor・ScheduleWakeup・
     cron の道具・Workflow）は担当のワークフローが外してある（`claude_args` の `--disallowedTools` と環境変数
     `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）。担当が待つときは、終わるまで前に出したまま待つ。起こす指示（`claude-task.yml` の
     `prompt`）は、役・作業ツリー・issue の番号と読む節だけを渡し、決まりも環境の説明も写さない（出どころは
     .claude/skills/dev-session/SKILL.md「開発機の対話のセッション」の「決まりの出どころ」）。作る担当は PR を下書きで出して作業ブランチへ
     push したら手放し、CI を待たない（ランナーを返す）。確かめる担当は CI が通ってから振り出されるので、CI を待たない。
  4. 後始末（担当が落ちても止められても走る）: 作る担当の GitHub に無い変更（未コミットの変更・push していないコミット）は
     `wip/tasks-<番号>-<時刻>` の枝へ残す（作業ブランチは書き換えない）。そのあと `tools/flow-gate/bin/after.js` が、Cancel されずに
     Claude の利用の上限・認証（担当の発言の `error`）で止まったなら、振り出しを `coordinator.pauseMinutes` の間止める（コードのリポジトリの変数
     `coordinator.pauseVariable` に止める時刻を置き、振り出しがそれを読む。`tools/flow-gate/src/after.js: pauseOf`）。
     続けて手番の記録（実行のファイル）を gzip して置き場のリリースへ置き（`tools/flow-gate/src/after.js: keepLog`。
     リリースは日（UTC）ごとに1つ。リンクは終わりのコメントの「後始末がしたこと」に出る）、issue に終わりのコメントを書く
     （`tools/flow-gate/src/after.js: endReport`）。読み手は後から確かめるユーザーと後の担当。書くのは、担当の最後の発言（担当が書く要約。
     .claude/skills/task-work/SKILL.md「作る担当・確かめる担当の終え方」）・後始末がしたこと・判定に断られた操作（あるときだけ）・実行へのリンクだけで、
     issue と実行のページで読めるもの（ステータス・ジョブの結果・時間・手数）は写さない。後始末はステータスを書かない。
  5. 終わる: 実行が終わった出来事をゲートが受け、手放したとして表で決める。
- **名義**: 置き場へは hidakagit-bot（secret `FLOW_BOT_TOKEN`）、コードのリポジトリへは hidakagit（secret `CODE_TOKEN`。
  `GITHUB_TOKEN` で打ったマージは master の CI とデプロイを起こさないため）、Claude は契約のトークン（secret `CLAUDE_CODE_OAUTH_TOKEN`）。
  どのトークンがどこへ届くかは docs/architecture/tech-stack.md「秘密の値とトークン」が持つ。Claude は置き場へ hidakagit-bot の
  トークンでだけ書き、hidakagit のトークンで書かない（開発機の対話のセッションでは、同じ値をユーザー環境変数 `FLOW_BOT_TOKEN` に持つ）。
  `CODE_TOKEN` はコードのリポジトリにだけ届き、置き場に届かない。担当のワークフローは gh の既定（`GH_TOKEN`）に `CODE_TOKEN` を
  置くので、gh で置き場を打つときは、読むときも `GH_TOKEN=$FLOW_BOT_TOKEN` を付ける（担当は付け忘れると断られる。開発機の対話の
  セッションは gh の既定が hidakagit で、付け忘れると hidakagit の名義で書かれうるので、必ず付ける）。名義の誤りを止めるのはこのトークンの範囲だけ（gh はトークンをホストごとにしか選べず、権限の拒否の
  規則は先頭の変数の代入を越えて当たるので、付けた打ち方と付け忘れた打ち方を見分けられない）。
- **止める**: Actions の画面で Claude Dispatch を無効にする（Disable workflow）。動いている見回りは次の1回で無効と読み、
  振り出さずに終える（次の見回りも起こさない）。戻すときは Enable workflow のあと Run workflow。
  利用の上限で後始末が止めた時刻（変数 `coordinator.pauseVariable`）を早く解くなら、コードのリポジトリの Settings → Secrets and
  variables → Actions → Variables で消す。1つのタスクだけを止めるなら、ボードで保留へ動かす（担当が動いていれば、ゲートがその実行を取り消す）。
- **開発機が要る作業**: 開発機にしか無いもの（本番への調べ `run_probe.py` の SSH の鍵・開発 DB の実データ）が要る作業と、担当が
  しない操作（「自動で進めないもの」「担当が書けないファイル」）が要る作業は、Actions では進めない。担当は、それが要ると分かった
  ところで、途中の変更を作業ブランチへ push し、対話作業の段階（`stage.js --dialog`。.claude/skills/file-issue/SKILL.md「段階に分ける」）を起こして
  何がなぜ要るかを書いて手放す。段階は元のタスクの前提になるので、元のタスクは段階が閉じるまで未着手で待つ。開発機の対話のセッションが
  段階を済ませて閉じると、元のタスクが振り出される。

**担当の権限**: 担当は自動モードで動き、操作の可否は判定役が1回ずつ決める。判定役には `tools/flow-gate/settings.json` の
`autoMode` で、担当の置かれた環境（2つのリポジトリがユーザーのもの・担当は使い捨てのランナーの無人の作業役 等）と日常の操作
（作業ブランチへの push と Pull Request を出す・タスクの issue を読む・コメントする・閉じる・`tools/flow-gate/bin` の道具を打つ 等）を
教える。決して打たせない操作（master への push・強制の push・GitHub の API での書き込み・ワークフローを止める・止めたのを戻す等）は、
同じファイルの `permissions.deny` で断る（拒否は判定役より先に効く）。ユーザーの答えが要る変更（規模の閾値の数を変える
`scripts/size_thresholds.json` の編集）は `permissions.ask` に置く（どのモードでも自動では通らず、開発機ではユーザーに確かめ、
担当には確かめる人がいないので通らない。Python 等のスクリプトの中の書き込みには当たらない）。拒否の規則はコマンドの文に当てるので、流れの道具が中で打つもの
（`dispatch.js` が置き場へ送る決め直しの頼み等）には当たらず、読むだけでも
`-X`・`-f` 等の付いた `gh api`（`-X GET` に `-f` で欄を渡す一覧・`gh api graphql`）は断られる。つないだコマンドは全文にも当たるので
（`git push … ; gh pr create --base master …` は `Bash(git push *master*)` に当たる）、規則の頭の道具（`git push`・`gh api`）はつながずに1つで打つ。読むときは欄を URL に書き
（`gh api 'repos/<所有者>/<リポジトリ>/actions/workflows/<ファイル>/runs?created=<範囲>'`）、`gh run list`・`gh issue view --json`（`blockedBy` 等）で済むものはそれを使う。自動モードそのものも同じファイルの `permissions.defaultMode` で
決める。各一覧は既定の規則（`$defaults`）を必ず残す。担当は連携の `settings` で
このファイルを読む。開発機の対話のセッションも同じ決まりで動く: セッションの始まりのフック（`.claude/settings.json` の
`SessionStart`）で `tools/flow-gate/bin/settings.js` が、master の版のこのファイルの `permissions` と `autoMode` をユーザー設定
（`~/.claude/settings.json`）へ写す（判定役はリポジトリの `.claude/settings.json` の `autoMode` を読まず、`defaultMode` の `auto` も
リポジトリの設定からは効かない。`permissions` は丸ごと置き換えるので、開発機にだけある許可は残らない）。決まりを変えるのは
このファイルだけで、master に入った次のセッションから両方に効く（作業ブランチで直しても、作業中の自分の権限は変わらない）。
判定役が自分を動かす設定の書き換えとして編集を断ったら、「担当が書けないファイル」のとおりにする。日常の操作が断られたら、
回り込まず（別の道具・別の名義で打たない）、流れの摩擦として記録する（.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」。直すのは `autoMode` の説明）。断られた操作は、後始末の終わりのコメントの
「判定に断られた操作」に、道具と打とうとしたものが出る。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（本番の接続情報も持たない）。
要るときは、書く中身（打つスクリプト・対象・前後に読んで比べるもの）を作業ブランチか段階の本文に置き、「開発機が要る作業」の
とおり対話作業の段階にして手放す。開発機の対話のセッションが.claude/skills/dev-session/SKILL.md「本番へ書く」のとおり進める（Claude が打てない操作を原則1のとおり
ユーザーに頼むのも、開発機の対話のセッションのチャットで渡す）。ユーザーに打たせる問いにしない。
マージの前に済ませる本番への書き込み（コードが新しく読む表を作る等。.claude/rules/deployment-sync.md「コミットと同時に揃えるもの」）が
要る変更は、作る担当が PR をレビュー可能にされる前に返す: 作ったコードは作業ブランチへ push し、書く中身はそのコードから出して、
対話作業の段階にする（下書きの PR は残してよい。前提が開いている間は振り出されない）。段階が閉じると、次の作る担当が作業ブランチから続ける。
Claude が持たない権限の操作（クラウドの画面・外部サービスの登録・GitHub のリポジトリの設定やトークン）も、同じく対話作業の段階にする。

**担当が書けないファイル**: Claude Code の自動モードの判定は、CLAUDE.md・`.claude/` の設定・権限（`tools/flow-gate/settings.json`）・
流れの手順（flow.md 等）の編集を、自分を動かす設定の書き換えとして断ることがある（1か所目が通っても、続く編集が通る根拠にしない。
判定役への説明が日常の作業と教えていても、回によって断られる）。断られたら回り込まず（別の道具・写しの差し替え・別の名義で書かない）、
パッチにもせず、「開発機が要る作業」のとおり対話作業の段階にする。書けた分は作業ブランチへ push し（push も断られたら、後始末が `wip/` の枝へ残す）、
何をどこまで書いたかを段階の本文に書く。開発機の対話のセッションが続きを書く。

## 様子を見る

導く原則: 4。

- **ボード**: ステータスは事実から決まるので、ボードの列がそのまま今の様子である。進行中と検証中の数は、動いている担当の数と一致する。
  ユーザーの番は回答待ちと保留だけ（担当者がユーザーになり、通知が届く）。
- **動いている担当**: コードのリポジトリの Actions の画面（Claude Task の実行。名前は「#<番号> <種類>」）。振り出しと決め直しの頼みは
  Claude Dispatch の実行の記録に出る。
- **気づける範囲**: 担当が役目を果たさずに終わったら、ゲートがイレギュラーの問いで回答待ちにする（ユーザーに通知が届く）。ゲートが出来事を
  取りこぼしたら、見回りの突き合わせが次の周で決め直させる。見回りが `coordinator.watchFailMinutes` のあいだ1周も通らなければ見回りの実行が
  失敗で終わり、GitHub の失敗の知らせで気づける（上の「担当」の「見回り」）。原因ごとに見張りを足さず、この症状で拾えるものだけを守る。
  この症状で拾えない詰まりに当たったら、例外として書き並べず流れの摩擦として記録する（.claude/skills/file-issue/SKILL.md「流れの摩擦を記録する」）。
- 異常の処置は issue に書く（保留の理由など）。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（またはPR）。ただし**段階に分けたタスクは段階ごとに1コミット**にする（段階ごとに Pull Request を出す。
.claude/skills/file-issue/SKILL.md「段階に分ける」）。**コミット履歴は、ある時点へ戻すときに
どのコミットまで戻せばよいかを件名と本文だけで特定できる状態に保つ**。問い・決定・確認の結果はそのタスクの issue に書き、git には写さない。
master のコミットは Pull Request の題名と本文から作られる。題名が件名で `tasks#1234: <何が変わったか（1行。利用者・運用から見た結果）>`、
本文の形は `.github/pull_request_template.md` だけが持ち、Pull Request の CI（Claude Gate の flow-gate）が照らす。

件名は必ず `tasks#<issue の番号>:` から始める（段階なら段階の sub-issue の番号、複数なら`tasks#12・tasks#13:`）。
属するタスクの無い変更は作らない（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。

## ゲートを変える・公開する

導く原則: 3・5。

ステータスの名前・枠は `flow.config.json`、表は `tools/flow-gate/src/rules.js: decide`、問いの形は `question_template.md` を直す。公開は、master に入ると `claude-gate.yml` の `deploy-gate` が、
ゲートを変えたかによらず master の先頭の版を `wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で行う（コードのリポジトリの秘密の値 `CLOUDFLARE_API_TOKEN`・
`CLOUDFLARE_ACCOUNT_ID` を使う）。ゲートは出来事が届いた issue だけを今の規則の姿（ステータス・担当者・本文の先頭のボタン）へ
書き直すので、規則を変えた直後、出来事の無い issue は次の出来事（か見回りの突き合わせ）まで前の姿のまま残る。全部をすぐ決め直させる
ときは `node tools/flow-gate/bin/migrate.js`（ステータスをゲートが決める形へ移したときの1回だけの道具。札「開発機が要る」を対話作業の段階へ移し、
開いたタスクを全部ゲートに決め直させる。`--dry-run` で何をするかを見られる）。
ゲートの App は、置き場（issues・issue_comment・projects_v2_item・repository_dispatch）とコードのリポジトリ（pull_request・workflow_run）の出来事を受け、
コードのリポジトリでは実行の一覧と取り消し・PR とチェックとルールセットの読み・PR をレビュー可能にする書き込みをする（権限の名前は GitHub の App の設定の画面のもの）。
手で公開するときは `tools/flow-gate` で同じコマンドを打つ。秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭にある。
テストは `node --test tools/flow-gate/test/*.test.js`。構文と import の解決（無いファイル・無い名前）は、`tools/flow-gate` で
`npm ci` のあと `npm run lint` が動かさずに見る（ESLint と eslint-plugin-import の `errors` の組。`tools/flow-gate/eslint.config.js`）。
道具（`bin/`）の静的な誤りはテストでは落ちず、lint だけが落とす。CI（`claude-gate.yml` の `flow-gate`）も同じ2つを流す。
