# 並行実行（司令塔）の規約

複数のタスクを、複数のエージェントへ振り分けて同時に進めるときの取り決め。親セッション
（司令塔）が何を決め、エージェントが何を守り、1回回すたびに何を測って本規約を直すかを
ここに集約する。**1タスクを1セッションで進めるときには適用しない**（CLAUDE.mdだけで足りる）。

本規約は実測で直していく前提で書かれている。直し方は末尾の「改善の回し方」節。

## 司令塔の役割

司令塔は**振り分け・監査・ユーザー判断の集約**を持ち、実装はしない。例外は、会話の文脈
そのものが材料になる作業（その回の振り返りの実測値を書き戻す等）だけ。

- 振り分けと監査を同じ人が持つのは、エージェントの完了報告を**主張として受け取り、
  事実で確かめる**役が要るからである。報告は作業者の自己申告であり、誤りを含む
  （実例は「完了時の監査」節）。
- ユーザーへの質問は、エージェントから上がった保留をまとめて1回で出す。エージェントに
  直接ユーザーへ聞かせない——並行する複数の問いが、互いの前提を知らないまま届くため。

## 振り出す前

### 対象の導出

`docs/improvement-plan.md`の未完了行のうち、トリガーの無いものと発火済みのものが候補。
次に当たるものは振り出さず、一覧にしてユーザーへ示す:

- **別セッション・ユーザー自身が進めているもの**。`git worktree list`・リモートの作業
  ブランチ・`ListAgents`（他のローカルセッション）で確かめる。作業ツリーが在るだけでは
  進行中と言えない（HEADと未コミット変更の更新時刻を見る）。ユーザーが「別途やる」と
  言ったものと、それに充てられた派生タスクも含む。
- **画面の設計をユーザーと詰めてから作るもの**（新機能のUI・利用者に見える情報量を
  増やすもの）。設計原則（`docs/architecture/design-principles.md`）のUI原則は、
  実装前にユーザーと合意することを前提にしている。
- **ユーザーの判断・外部アカウントの操作が要るもの**（残すか消すかを決めるタスク・
  クラウドの後始末等）。
- **判断の重い総点検**（規模Lで、対象の母集団を決めること自体が作業の中心のもの）。

### ユーザーが手動で進めているタスク

ユーザーが別セッションで手動で進めるタスクの番号を伝えてきたら、それを「手動中」として
扱い、**影響のあるタスクを振り出しの候補から外す**。

1. 手動中のタスクの`Txxx.md`から、触る範囲（ファイル・モジュール・文書）と、段階・派生
   として充てられたタスクを取る。
2. 影響のあるタスクを機械的に列挙する: 手動中のタスクを本文・トリガーで参照している
   タスク、充てられた派生タスク、同じファイル・モジュールを触るタスク。
3. **既に稼働中のエージェントの担当と重なるもの**は、重なりの中身をユーザーへ示し、
   止めるか続けるかを確かめる（続けると、後からpushする側——多くは手動のセッション——が
   rebaseの衝突を払う）。
4. 手動中の番号と除外したタスクは、その回の記録（`Txxx.md`）に書く。会話だけに置くと、
   司令塔のセッションが切れたときに失われる。
5. 手動中のタスクが終わったと伝えられたら、除外を解いて候補へ戻す。

ユーザーが**これから**手動で始める大きなタスクについては、始める前に済ませておくべき
タスク（前提）を司令塔が洗い出して先に消化し、済んだら開始してよいことを知らせる。
手動のセッションが後から衝突を払うより、先に片付けておく方が全体の手戻りが少ない。

- **前提に入れるもの**: そのタスクが組み替える範囲（ファイル・モジュール）を触り、かつ
  そのタスクに吸収されないもの——利用者に届いている誤りの修正・安全網（そのタスクの前に
  あるべきテスト）・前段の後始末など。**入れないもの**: そのタスクの段階として充てられて
  いるもの（そのタスクがやる）と、ユーザー判断待ちで止まっているもの（判断が出るまで
  前提にすると永久に開始できない——一覧に「判断待ち」として別に示す）。
- 前提の一覧・根拠・残りを、その回の記録へ書く。完了の監査のたびに残りを更新する。
- **残りが0になったら、会話とプッシュ通知の両方で「開始してよい」と知らせる**。
  ユーザーはその場にいないことがある。

### キューの組み方

- **テーマ単位のキューにし、同じファイルを触るタスクは同じエージェントへ直列に積む**。
  並行する2本が同じファイルを触ると、後からpushする側がrebaseの衝突解消を払う。
  触るファイルはタスクエントリの背景・方針から見積もる（外れても致命的ではないが、
  大きな書き換え同士を並べない）。
- キューの中は**1タスク=1コミットで止まらず進む**。1タスクが保留で止まっても次へ進む。
- 振り出すエージェント同士に、互いが何を触っているかを指示文で伝える（衝突したときに
  相手の変更を尊重して統合する判断材料になる）。

### ローカルかリモートか

**本番（VMへのSSH・本番DB）・この開発機そのもの・手元のテストDBが要るものだけローカル**で
動かし、ほかはリモート（`isolation: "remote"`）で動かす。

- リモートはエージェントごとに別の機械で、依存の導入・型検査・テストを取り合わない。
  Linuxなので開発機固有の遅さ（MSYSのプロセス起動・ウイルス対策の走査）を受けない。
- リモートからは本番へ触れない。本番での計測・データ移行が要る段は、リモートでコードを
  終えてローカルへ引き継ぐ（エージェントに「ユーザー確認事項（ローカル実行が必要）」として
  報告させる）。
- リモートは開発機のロック（下記）を共有しない。リモート同士・リモートとローカルの
  pushは、rebaseのやり直しで吸収する。

### 起動のしかた

- ローカルは`isolation: "worktree"`。**作業ツリーを同時に作ると、検証が時間切れになって
  起動が失敗する**——1本ずつ起動する。失敗して残った作業ツリーは中身を確かめてから
  片付ける（自動で作られた`.claude/settings.local.json`以外の変更が無いこと）。
- 指示文には、担当キュー・各タスクの注意点・並行する他エージェントの担当範囲を書き、
  共通ルールは本規約の「エージェント共通ルール」節を**読ませる**（貼り付けない）。
  リモートもリポジトリを読めるので同じでよい。

## エージェント共通ルール

司令塔から振り出されたエージェントは、着手前にこの節と`CLAUDE.md`の全文を読み、厳守する。

### 前提

- 各タスクの正本は`docs/records/tasks/Txxx.md`。完了条件を満たしたかで完了を判断する
  （「実装した」ではなく「効いている」）。
- 対象モジュールの`docs/modules/*.md`を手を入れる前に精読し、乖離は同じコミットで直す。
- ユーザーへ見せる文言・コミットメッセージ・最終報告はすべて日本語。
- 作業するのは自分に割り当てられた作業ツリーの中だけ。本体のチェックアウトと、他の
  セッション・エージェントの作業ツリーは触らない。自分が変更したのではない差分を
  見つけても戻さない。
- 最初に`git config core.hooksPath .githooks`が効いているかを確かめる（リモートでは
  設定されていないことがある。`--no-verify`は禁止）。
- `git add -A`・`git add .`は禁止。明示パスでステージし、コミット前に
  `git diff --cached --stat`を見る。
- 使い捨てのファイル（調査スクリプト・スクリーンショット・一時spec）はリポジトリに
  置かない（`frontend/e2e/`へ置いたspecはCIが拾う）。

### 重い処理は1本ずつ（ローカルのみ）

同じ開発機の上で複数のエージェントが走るため、重い処理は`scripts/lockrun.py`を通す:

```
python scripts/lockrun.py <ロック名> -- '<bashコマンド文字列>'
```

| ロック名 | 通すもの |
|---|---|
| `npm-ci` | `cd frontend && npm ci`（作業ツリーには`node_modules`が無い。ジャンクションで共有しない） |
| `frontend-heavy` | `tsc --noEmit`・`next typegen`・`vitest run <ファイル>`・`playwright test` |
| `backend-db` | backendの`pytest`（共有の`ridecompass_test`を掴むため） |
| `git-push` | fetch→rebase→pushの一続き（下記） |

backendのPythonは作業ツリーに`.venv`が無いため、本体のチェックアウトの
`backend/.venv`を使う。

### 本番

- 本番DBの読み取りの計測（`backend/scripts/run_probe.py`経由）は確認なしでよい。
- 本番への書き込み・削除・バッチ実行・常設設定の変更はしない。コード側を終え、必要な
  操作を最終報告の「ユーザー確認事項」に書く。
- `backend/**`をpushすると本番へ自動デプロイされる。既存DB行を新コードが読めなくなる
  変更は、本番データ移行が先（CLAUDE.md「コミット時の同期ルール」）——その場合は
  pushせずに報告する。

### 判断に迷ったら

ユーザーにしか決められない判断（本番から外れたものを残すか・利用者に見える情報量を
増やすか・要件の推定が要るもの）は、その項目だけ保留してタスクエントリに「保留: 何が・
なぜ・選択肢」を書き、残りを進める。保留があるタスクは`状態: 未完了`のまま台帳の行も
残す。新しいタスクは`scripts/new_task.py`で起票する。範囲外で見つけたものは、直さずに
最終報告へ書く（司令塔が担当のエージェントへ回す）。

### 完了とpush

- 完了の作法: `Txxx.md`の`状態:`を`完了`にして実施内容・検証結果を書き、
  `docs/improvement-plan.md`からその行を消す。本文に未実施の段階・派生が残るなら別Txxxへ起票。
- コミットメッセージには、実行したコマンドと観測値、実装の増減（実装・テスト・文書を
  分けて行数）を書く。
- pushは、ローカルでは`git-push`ロックの中でfetch→rebase→pushを一続きに行う:

  ```
  python scripts/lockrun.py git-push -- 'git fetch origin master && git rebase origin/master && git log --oneline origin/master..HEAD && git push origin "$(git rev-parse HEAD)":refs/heads/master'
  ```

  pre-pushフックの実行中に他者のpushが割り込むと、rebaseのやり直しが連鎖するため。
  rebaseが衝突して失敗したら（ロックは解放される）、解消→`git rebase --continue`→
  影響範囲の静的検査→同じコマンドを再実行する。リモートではロック無しで同じ手順を行い、
  拒否されたら最初からやり直す。
- `docs/improvement-plan.md`は各エージェントが隣接する行を消すため衝突しやすい。
  **両方の削除を残す**（相手が消した行を戻さない）。

### 最終報告

キューを終えたら、タスクごとに: 状態（完了／一部保留／未着手）とコミットsha、何を直したか、
検証に使ったコマンドと結果、実装の増減、新規起票、ユーザー確認事項、見積もりとのずれ。

## 稼働中

- 完了はエージェントの通知で知る。ポーリングしない。
- エージェントが範囲外で見つけたものは、担当のエージェントへ`SendMessage`で回す
  （担当がいなければ起票）。
- 規約・手順を途中で変えたら、稼働中の全エージェントへ伝える。本規約の該当節を直し、
  指示文には「該当節を読み直せ」と書く。
- CIが赤くなったら、原因のコミットを**ログで**特定してから扱う。エージェントの
  「別のコミットのせい」は主張であり、直後のコミットで緑に戻るなら並列実行の不安定な
  テストを疑う（不安定なテストも、赤を本物と見分けられなくするので起票する）。

## 完了時の監査

通知が来たら、次のタスクを振り出すより先に監査する。

- 報告されたコミットが`origin/master`に入っているか（`git merge-base --is-ancestor`）。
- `Txxx.md`の`状態:`と台帳の行が一致しているか（完了なら行が無い、保留があるなら残る）。
- コミットメッセージに、実行したコマンドと観測値・わざと壊した入力での確認・緩和の
  影響の実測があるか。
- 報告の中の**事実の主張を1つずつ確かめる**。実例: 「本体のチェックアウトが別ブランチに
  いる」（実際はmasterのまま）、「このコミットがCIを赤くした」（実際は不安定なテスト）
  ——どちらも結論の一部は正しく、根拠の側が誤っていた。
- 保留になった判断は、まとめてユーザーへ出す。答えが出たら、そのタスクを担当した
  エージェントへ`SendMessage`で返す（会話の文脈を持っているので、新しく起動するより速い）。

## 環境

- **開発機が飽和しているときは計測しない**。性能の比較は、条件をそろえて交互に複数回
  取った中央値か、本番で取る。
- **遅いときは環境を先に疑う**。プロセス1つの起動に秒単位かかるなら、コードではなく
  ウイルス対策の走査・CPUの飽和を測る（`Get-Counter`でプロセス別のCPU使用率）。
  実例: 第三者製のウイルス対策が並行実行中にCPUの2〜4割を使い、`git status`が5倍遅く
  なっていた（[T1049](../records/tasks/T1049.md)）。
- `core.hooksPath`は相対パス（`.githooks`）にする。絶対パスだと全作業ツリーが本体の
  チェックアウトにあるフックを走らせ、作業ツリーで直したフックが効かない。

## 改善の回し方

本規約は、1回の並行実行（司令塔が振り出してから全エージェントが終わるまで）ごとに実測で
直す。**実測の裏付けが無い変更は入れない**（CLAUDE.md「修正の原則」と同じ基準）。

### 回ごとに残す記録

1回ごとに`scripts/new_task.py`で記録用のタスクを起こし（または既存の改善タスクへ追記し）、
次を書く。数字は取り方も一緒に書く。

| 測るもの | 取り方 | 何を見るためか |
|---|---|---|
| 振り出したタスク・完了・保留の数 | 台帳と各エージェントの最終報告 | 振り出しの精度（保留が多いなら「振り出さない」基準が緩い） |
| ロックごとの待ち時間・保持時間・失敗回数 | `python scripts/lockrun.py --report --since <開始時刻>` | どの資源が詰まったか（待ちが大きいロックは分割・リモート化の候補） |
| `git-push`ロックの失敗回数 | 同上の「失敗」列 | rebaseの衝突・フックの拒否の頻度（キューの組み方の良し悪し） |
| 監査で見つかった誤った主張 | 監査のたびに司令塔が控える | 監査の項目に何を足すか |
| ユーザー判断の待ち時間 | 保留が上がってから答えが返るまで | 保留の出し方（まとめ方・粒度） |
| CIの赤とその原因 | CIの履歴とログ | 不安定なテスト・並行pushによる破損の有無 |

### 直し方

1. 回の終わりに振り返り（`/task:retro`）を行い、本規約への変更案を出す。
2. 変更案ごとに、上の記録のどの数字が根拠かを書く。根拠が無いものは次の回で測る項目に
   回し、本規約へは入れない。
3. 当てたら、次の回で同じ数字が動いたかを見る。動かなければ変更を取り消すか、別の
   原因を探す。
