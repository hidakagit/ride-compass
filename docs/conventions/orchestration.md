# 並行実行（司令塔）の規約

複数のタスクを、複数のエージェントへ振り分けて同時に進めるときの取り決め。親セッション
（司令塔）が何を決め、エージェントが何を守り、1回回すたびに何を測って本規約を直すかを
ここに集約する。**1タスクを1セッションで進めるときには適用しない**（CLAUDE.mdだけで足りる）。

本規約は実測で直していく前提で書かれている。直し方は末尾の「改善の回し方」節。

## 司令塔の役割

司令塔の成果物は**管理されている状態**であって、振り出した本数ではない。管理されている
状態とは、いつ誰に聞かれても、全エージェントについて「何をしていて・いつ始めて・見込みに
対してどこにいて・異常があるか」を事実で答えられ、異常には手を打っている状態をいう。
そのために司令塔は**計画（上限と門）→ 実行（振り出し）→ 確認（時間で回す）→ 是正**を
回す。振り出しだけを繰り返すのは司令塔ではない。逆に、**振り出せるのに振り出さないのも管理の失敗である**——
定期確認のたびに、門が開いていて枠が空いていれば次に何を振り出すかを決め、振り出せないものはその理由を判断待ち
（ダッシュボード）か振り出し待ちの前提に置く。ユーザーの問いに答えている間も、この確認は止めない
（`check`は、稼働0本で母集団に担当も判断待ちも無い残りがある・司令塔の作業待ちがあるときに要対応を出す）。

司令塔は**振り分け・監査・ユーザー判断の集約**を持ち、実装はしない。例外は、会話の文脈
そのものが材料になる作業（その回の振り返りの実測値を書き戻す等）だけ。**実行中に来た
新しい依頼も、司令塔が自分で片付けずに状態の表のキューへ積み、上限の範囲で振り出す**——
司令塔が実装に回っている間、全体を見ている者がいなくなる。

- 振り分けと監査を同じ人が持つのは、エージェントの完了報告を**主張として受け取り、
  事実で確かめる**役が要るからである。報告は作業者の自己申告であり、誤りを含む。
- ユーザーへの質問は、エージェントから上がった保留をまとめて1回で出す。エージェントに
  直接ユーザーへ聞かせない——並行する複数の問いが、互いの前提を知らないまま届くため
  （下の「ユーザーの判断待ち」節）。

**実装はしないが、手が空いている間に、振り出しを止めないための準備を先回りして行う**（読み取りと
ダッシュボード・状態の表への書き込みだけ。順位は下の表の7）:

1. **判断の先回り**: 振り出し待ちのタスクのうち、ユーザーの判断が要ると今分かるもの（表示の案・残すか消すか等）は、
   担当が着手してそこへ辿り着くのを待たずにダッシュボードへ置く。答えを待つ時間を、前のタスクの作業と重ねる。
2. **前提と重なりの下調べ**: 振り出し待ちのタスクの記録を読み、記録を書いた後にmasterへ入った変更で崩れた前提
   （済んだはずの作業・触るファイル）と、他の担当と重なるファイルを確かめる。崩れていれば、振り出し待ちの前提
   （`after`）と優先度を組み直すか、問いとしてダッシュボードへ置く。
3. **依頼文の準備**: 回の中で分かった詰まりどころ（担当が繰り返し払った摩擦）を、依頼文の定型（「起動のしかた」の
   よく抜ける規則）かそのタスクの注意点へ書き足しておく。

手続きのうち機械で判定できるもの（門・状態・定期確認・監査の機械的な項目・状態の表の更新）は
`scripts/orchestrate.py`（中身は`scripts/orchestration/`）が持つ。司令塔は手で表を書かず、
判定を自分の注意に頼らない。

## 司令塔の作業の優先順位

司令塔には複数の種類の仕事が同時に来る。次の順位で処理する。

| 順位 | 仕事 | 理由 |
|---|---|---|
| 1 | 被害が進行中のもの（機械の飽和・エージェントの暴走・masterのCIの赤・本番デプロイの失敗・破壊的操作の途中） | 待つほど被害が広がる。止める手段（下の「止める手段の段階」）を先に使う |
| 2 | ユーザーからの問い合わせ・指示 | 判断者を待たせない。深く答えられなくても、まず1〜2行で受領と「いつ・どの順で答えるか」を返す |
| 3 | 監査結果のイレギュラー（誤った主張・止めの項目・衝突） | 門を塞いでいる。仕組みの穴の兆候でもある |
| 4 | 至急の調査 | 1〜3のための調査なら、その順位を引き継ぐ |
| 5 | 通常の監査依頼 | 他を塞いでいるもの（手動タスクの前提・利用者に届いている欠陥・セキュリティ）を先に、残りは受領順 |
| 6 | 定期確認 | 作業の区切りで行う |
| 7 | 手が空いた間の準備（判断の先回り・前提と重なりの下調べ・依頼文の準備。「司令塔の役割」節） | 次の振り出しで担当が待つ時間・読み違える前提を先に消す |
| 8 | 規約の改善・記録・振り返り | |

- 割り込みは安全な区切りでだけ受ける。push・rebaseの途中で中断しない。
- 同時に来たら、処理する順番をまずユーザーへ1行で示す。
- 中断した作業は**司令塔のキュー**へ積み、会話の流れに埋もれさせない:
  `python scripts/orchestrate.py board todo push "<何を・どこまで>" --priority <順位>`。
  次に取るのは`board todo pop`（順位の小さい順、同じなら積んだ順）、一覧は`board todo list`。
  順番と関係なく済んだものは`board todo done <listの番号>`で外す（残すと、済んだ作業が作業待ちに数え続けられる）。

## 振り出す前

### 対象の導出

`docs/improvement-plan.md`の未完了行のうち、トリガーの無いものと発火済みのものが候補。
次に当たるものは振り出さず、一覧にしてユーザーへ示す:

- **別セッション・ユーザー自身が進めているもの**。`git worktree list`・リモートの作業
  ブランチ・`ListAgents`（他のローカルセッション）で確かめる。作業ツリーが在るだけでは
  進行中と言えない（HEADと未コミット変更の更新時刻を見る）。ユーザーが「別途やる」と
  言ったものと、それに充てられた派生タスクも含む。
- **画面の設計をユーザーと詰めてから作るもの**（新機能のUI・利用者に見える情報量を
  増やすもの）。設計原則（`docs/architecture/design-principles.md`）のUI原則は、
  実装前にユーザーと合意することを前提にしている。
- **ユーザーの判断・外部アカウントの操作が要るもの**（残すか消すかを決めるタスク・
  クラウドの後始末等）。
- **判断の重い総点検**（規模Lで、対象の母集団を決めること自体が作業の中心のもの）。

### 手元かクラウドか

担当は手元（開発機、Windows）のほか、クラウドのセッション（Claude Code on the web、Linux）でも
動かせる。クラウドでは開始時のフックが依存を繋ぎ、DB（本番と同じ版のPostGIS）とRedisを起動する
ので、`-m postgis`を含むテストを手元と同じように回せる（DBは裏で起動するので、使う前に
`bash scripts/remote_dev/wait_db.sh`で待つ。アプリの起動はしない。用意の仕組みは
[setup.md](../architecture/setup.md)「クラウドのセッション」）。

- **クラウドへ出すもの**: Docker・Linuxが要る作業（本番と同じイメージでの観測・composeの確認等）と、
  手元の機械を`heavy`の枠で待たせたくない作業。クラウドのセッションは機械を共有しないので枠を取らない。
- **手元に残すもの**: 本番への接続が要る作業（`run_probe.py`等。接続情報の`backend/.env.oracle.local`とSSHの鍵はリポジトリに入れないため、クラウドには無い）、
  Windowsでしか起きない事象の確認、状態の表・スロットを使う作業（`.git/orchestration/`は手元にしか無い）。
- クラウドの担当も作業ブランチ`orch/<名前>`へpushし、監査は手元の司令塔が行う（「完了とpush」節）。

**クラウドへの振り出し方**: この環境では`Agent`の`isolation: "remote"`は効かず、手元のスロットで起動する
（2026-09-25に観測）。クラウドの担当は、司令塔が**1回だけ動く予約タスク**（`RemoteTrigger`の`create`）で起動する。
予約タスクが使えないときだけ、依頼文を仕掛中のダッシュボードにkind `操作`で置き（`text`は「クラウドのセッションを開いて
この依頼文を貼る」、`detail`に全文）、ユーザーに貼ってもらう。

1. 依頼文を「起動のしかた」の定型で書く（担当の名前・作業ブランチ`orch/<名前>`・よく抜ける規則を含む）。**依頼文の冒頭に
   push先を明示する**: 「pushは`git push origin +<sha>:refs/heads/orch/<名前>`だけ。クラウドの環境が指定する`claude/…`の枝へは
   pushしない（CIが走らず、監査できない）」。クラウドのセッションは環境の指示に従い`claude/<名前>`の枝へpushしがちで、
   よく抜ける規則の1行だけでは上書きされない。予約で起動した担当のそばには誰もいないので、最終報告まで自力で進める前提で書く
   （確認事項はダッシュボードへ置いて残りを進める）。
2. `RemoteTrigger`の`create`で起動する: `run_once_at`に数分後の時刻を入れて1回だけ動かし、環境はこのリポジトリの環境
   （RideCompass環境）、依頼文は`events`のメッセージに入れる。予約は1回動くと止まるが、一覧
   （https://claude.ai/code/routines）には残る。消すのはユーザーで、司令塔は消さない。
3. `board add <名前> current_task=<Txxx> where=クラウド`で表へ記録する（`id`は無い）。手元で起動に失敗してから
   クラウドへ移したときは`board set <名前> where=クラウド`——着手時刻がその時点へ置き直る（手元で失敗した起動の
   時刻から数えると、見込み超過を誤って出す）。起動したセッションの名前が分かったら（`ListAgents`に出る名前）、
   `board set <名前> session=<セッション名>`で書く——答えを届ける宛先になる（5.）。
4. クラウドの担当は開発機の作業ツリーも機械も使わないので、`gate`の稼働の本数（上限）にも作業ツリーの検査にも
   数えない（`status`は「稼働（クラウド）」として別に出す）。見込み超過は手元の担当と同じく数える。**最終報告は
   予約の実行ログで読む**（`RemoteTrigger`の`list_runs`で実行を出し、`get_run_log`で本文を読む）。途中の様子は
   作業ブランチへのpushとCIで知る。2026-09-26のT1113（担当D-pid）では、起動17:37 UTC→`orch/D-pid`へpush 17:43→
   CI緑を確かめて最終報告17:45まで、担当が自力で進めた。
5. **答えは司令塔が届ける**。クラウドのセッションはダッシュボードに問いを置けるが、答えを自分では取りに来ない。
   `pending-inbox`が持ち主をクラウドの担当と出した件は、司令塔が`SendMessage`（宛先は表の`session`）で答えの文を
   そのまま送り、`taken_at`・`taken_note`を書く。届くのは片方向で、読んだかの返事は来ない——読んだことは、その担当の
   次のpushか報告で確かめる。
6. **差し戻しは、予約で起動した担当へは送れない**。予約タスクで起動したクラウドのセッションは`SendMessage`の宛先の
   一覧に出ない（2026-09-26、M-close3への差し戻しで観測）。差し戻すときは、同じ作業ブランチ`orch/<名前>`へ直しを積ませる
   担当を新しく起こす: 手元の担当（`<名前>b`等。スロットで起動し、`git fetch origin orch/<名前>`の先端から始めて同じ枝へpushする）か、
   同じ枝を指定した新しい予約。依頼文には差し戻しの指摘と、元の担当のshaを書く。表には直しを積む担当を`board add`し、
   監査はその担当の報告のshaで行う。元の担当は差し戻しを受け取れず報告し直さないので、`強制停止`にする（`停止済み`のままだと
   監査待ちに数え続けられる）。

### ユーザーが手動で進めているタスク

ユーザーが別セッションで手動で進めるタスクの番号を伝えてきたら、それを「手動中」として
扱い、**影響のあるタスクを振り出しの候補から外す**。

1. 手動中のタスクの`Txxx.md`から、触る範囲（ファイル・モジュール・文書）と、段階・派生
   として充てられたタスクを取る。
2. 影響のあるタスクを機械的に列挙する: 手動中のタスクを本文・トリガーで参照している
   タスク、充てられた派生タスク、同じファイル・モジュールを触るタスク。
3. **既に稼働中のエージェントの担当と重なるもの**は、重なりの中身をユーザーへ示し、
   止めるか続けるかを確かめる（続けると、後からpushする側——多くは手動のセッション——が
   rebaseの衝突を払う）。
4. 手動中の番号は状態の表（`manual`）に置く。会話だけに置くと、司令塔のセッションが切れたときに
   失われる。除外したタスクは手動中の番号から2.で読むたびに導く（進め方なので記録にもコミットにもしない。
   「回の始まりと終わり」節）。
5. 手動中のタスクが終わったと伝えられたら、除外を解いて候補へ戻す。

ユーザーが**これから**手動で始める大きなタスクについては、始める前に済ませておくべき
タスク（前提）を司令塔が洗い出して先に消化し、済んだら開始してよいことを知らせる。
手動のセッションが後から衝突を払うより、先に片付けておく方が全体の手戻りが少ない。

- **前提に入れるもの**: そのタスクが組み替える範囲（ファイル・モジュール）を触り、かつ
  そのタスクに吸収されないもの——利用者に届いている誤りの修正・安全網（そのタスクの前に
  あるべきテスト）・前段の後始末など。**入れないもの**: そのタスクの段階として充てられて
  いるもの（そのタスクがやる）と、ユーザー判断待ちで止まっているもの（判断が出るまで
  前提にすると永久に開始できない——一覧に「判断待ち」として別に示す）。
- **前提の一覧は仕掛中のダッシュボードで持つ**（手動タスクごと。足す・外すはダッシュボードで行い、
  記録を書き換えるコミットにしない。[asking-user.md](asking-user.md)「仕掛中のダッシュボード」節）。
  状態の表には、どのタスクが手動中か（`manual`のタスク番号。`board run manual+=<Txxx>`）だけを持つ。
  `check`・`status`が、手動タスクごとに前提の状態（完了／稼働中／判断待ち——前提に答えの出ていない
  保留がある／振り出し待ち／停止中／未着手。台帳・各タスクの記録・ダッシュボード・状態の表から導く）と残りの
  件数を出し、残り0なら`check`が要対応として「開始してよい」を出す。ダッシュボードは最新のバックアップ
  （「仕掛中のダッシュボード」節の`pending-backup`）から読むので、前提を足した・外した直後に見るときは
  `pending-backup`で書き出し直す。前提を先に消化させるなら`/orchestrate:priority <前提のTxxx>... 高`。
- **残りが0になったら、会話とプッシュ通知の両方で「開始してよい」と知らせる**。
  ユーザーはその場にいないことがある。

### タスクの分割

タスクを適切な大きさに分けてから割り振るのも司令塔の仕事である。

1. **振り出す前に分ける。** 1担当に渡すのは、見込みが規模M以内で、同じ性質の作業
   だけにする。分ける軸:
   - 性質——管理に必須の作業か、依頼による機能か
   - 触るファイルの重なり
   - 判断待ちになりうる部分（分けておけば、残りを進められる）
   - 本番の操作を含むか（ローカルでしかできない部分を分ける）
   - **担当に実行できない段を含むか**——本番への書き込み（VMのパッケージ・設定・DBの行）、
     取り消せない削除、Claude Codeの設定の書き換え、外部サービスの画面での設定。その段は振り出す
     前に分け、仕掛中のダッシュボードにkind `操作`として置いてユーザーに頼む（「ユーザーへのお願いは
     ダッシュボードに置く」節）。担当にはその前後（読み取りの確認・そのまま貼れる手順の用意・事後の確認）だけを渡す
     ——担当は途中で権限に止められる。
2. **振り出した後に来た依頼は、担当に継ぎ足さない。** 既存のタスクに属さなければ起票案として
   ダッシュボードに置き、承認されて番号が振られたらキューに積む（[asking-user.md](asking-user.md)「起票は承認制」）。
   継ぎ足すと見込みも完了条件も崩れる。
3. **見込みを超えそうなら、終わった段だけ監査に出させ、残りを別タスクに分ける。**

### 依頼は1件ずつ、依存は表で

- **1回の依頼で渡すのはタスク1件（段階を切るなら1段階）だけ。** 担当はそれを終えたら報告して
  止まる。振り出した時刻がそのタスクの着手、完了の通知がその終わりになり、見込み超過も監査も
  タスク単位で自然に回る。複数件をキューで渡すと、担当が次へ進むため通知は最後にしか来ず、
  経過も予算もどのタスクのものか分からなくなる。
- **作業ツリーは固定数のスロットを使い回し、担当（エージェントの会話）はタスクごとに新しくする。**
  作業ツリーを新しく作ると`npm ci`と`core.hooksPath`の書き換えを払うので、作らずに渡し直す
  （「作業ツリーのスロット」節）。一方、担当の会話は長くなるほど読み違いと遅さの元になる。
  この2つを同じものとして扱わない。同じ担当を再開してよいのは**同じタスクの差し戻し**だけで、
  次のタスクは新しい担当へ渡す。並行する2本に同じファイルを触らせない——後からpushする側が
  rebaseの衝突解消を払う。触るファイルはタスクエントリの背景・方針から見積もる。
- **タスク間の依存（順序）は振り出し待ちの表に持つ**。会話や担当の頭の中に置かない——要約・
  停止で失われる。依存は担当ではなくタスクの性質なので、振り出し待ちの各行に前提と担当を書く:
  `board dispatch push <Txxx> after=<前提のTxxx> agent=<再開する担当> --priority 高|中|低`
  （前提が複数なら`after='["T1","T2"]'`）。行に持つのはタスク番号・前提・担当・優先度・積んだ時刻
  だけで、題名と規模と完了したかは写さない。`board dispatch list`は各行に台帳の題名と、前提が済んだか（前提の
  `Txxx.md`がorigin/masterで`状態: 完了`か）を出し、`board dispatch pop`は前提が済んだ行だけを
  優先度の順に取り出す。行のタスク自体が既に完了している行（別の経路で片付いたもの）は、同じく記録の`状態:`から
  導いて取り出さず、`check`の「振り出し待ち」にも数えない（行は消さない。開け直せば、また取り出せる）。閉じたタスクの
  後始末（取り込み後に見つかった衝突の解消等）を振り出すときは、行に後始末の印を付けて積む
  （`board dispatch push <Txxx> cleanup=true`）——印の行は記録が完了でも取り出す。優先度は
  `/orchestrate:priority <Txxx>... 高|中|低`で変える。
- **振り出す予定のものは、決めたその場で振り出し待ちへ積む。これが残りの作業の唯一の正本。**
  回の途中で承認されて起票したタスク、止めた担当の続き、分けた段階の残り、判断が出て進められるように
  なったものが対象。会話・状態の表の自由記述（「再開順」のようなメモ）・担当の頭の中に
  置かない——拾うトリガー（「見送った振り出しを拾うトリガー」節）はキューしか見ないので、
  キューに無いものは枠が空いても振り出されない。判断待ちで止まって
  いるものは積まず、判断が出た時点で積む。
- 振り出すエージェント同士に、互いが何を触っているかを指示文で伝える（衝突したときに
  相手の変更を尊重して統合する判断材料になる）。

### 上限と門

- **同時に動かす本数の上限は、`/orchestrate`の起動時に引数で受け取る**（例:
  `/orchestrate --concurrent 3`）。省略時は**3本**。状態の表の`limits.concurrent`へ書く
  （`board run limits.concurrent=3`）。根拠: 重い処理は機械全体で1本ずつしか走らない
  （「重い処理は機械全体で1本ずつ」節）ため、それを超えるエージェントは列に並ぶだけで、
  7〜8本でCPUが常時100%・ロック待ち最大16〜19分になった（実測は[T1049](../records/tasks/T1049.md)）。
  上限は、`heavy`の枠が空いている時間がまだあるうちだけ意味を持つ——枠の待ちが続いているなら、
  上限未満でも本数を足さない。
- **振り出す前に毎回`python scripts/orchestrate.py gate`を通す。NGなら振り出さない。**
  門は次を見て、理由付きでOK/NGを返す:
  - 稼働中が上限未満か。稼働中は、状態の表で`稼働`・`停止指示`のものに、**手元の作業ツリーで
    未コミットの変更が最近更新されたもの**を足して数える（表に無いもの・停止済みのはずの
    ものも含む。サブエージェントは指定に関係なく手元で動くため）
  - 監査待ちが無いか（監査を先にする）
  - 見込み超過が無いか（是正を先にする。問い合わせて進みを確かめ、是正済みの印を付けた担当は数えない——「異常の是正」節）
  - 停止ファイルが無いか
  - 直近のロック待ちが大きくないか（`lockrun/log.jsonl`）・CPUが飽和していないか
  - 回が振り出してよい状態か: 母集団が表にあり（回が始まっている）、終わりの条件1に当たっていないか
    （「回の始まりと終わり」節）。閉じた理由には回の名前・目的・母集団がすべて済んだことを出す。
    `board dispatch pop`も同じ条件で取り出さず、母集団の外のタスクも取り出さない
- **門を開けるのは確認の結果であって、依頼の勢いではない**。「どんどん進めて」と言われても、
  門が閉じていれば振り出さず、閉じている理由（`gate`の出力）を返す。

### 状態の表

`<gitの共通ディレクトリ>/orchestration/board.json`（全作業ツリーから読める・リポジトリには
入らない）を、エージェントの状態の**唯一の正本**にする。回の名前・目的・母集団（タスク番号と派生元）・打ち切りの引き継ぎ・
上限・確認間隔・手動中のタスク、エージェントごとの名前・居場所（`where`。クラウドなら`クラウド`、書かなければ手元）・
クラウドの担当のセッション名（`session`。答えを`SendMessage`で届ける宛先）・
状態（司令塔の指示: 稼働・停止指示・停止済み・強制停止）・現在のタスクとその着手時刻・監査の記録、司令塔のキュー・振り出し待ちのキューを持つ。持ってよいキーと
状態の語彙の正本は`scripts/orchestration/core.py`（`ALLOWED_KEYS`）。依頼で足す
機能は別のモジュールから同じ表を読み書きする。

**表に持つのは、表にしか無い事実だけ。** 管理の仕組みは、同じ事実を二か所に持った瞬間に
破綻する——片方だけが直され、もう片方が古いまま正しそうに残る。他に正本があるもの（タスクの
題名・規模は台帳、手動タスクの前提の関係とユーザーへの問い・答えは仕掛中のダッシュボード（答えが記録へ
移ったあとは記録）、masterに入ったかはgit、担当が動いているかは作業ツリーの動き）は写さず、読むときに
正本から導く。規則の文（規約の写し）と出来事の記録（回の記録`Txxx.md`の持ち物）も表に置かない。
表にしか無いのは、振り出し（誰に・何を・いつ・どこで）・見込み超過を問い合わせて確かめた時刻（是正済みの印）・
振り出し待ちの並び（前提・担当・優先度・後始末の印）・
司令塔の作業待ち・監査の記録（報告のshaと結果）・回の設定（目的と母集団・打ち切りの引き継ぎを含む）だけである。
導く側の実装は`scripts/orchestration/core.py`の冒頭が正本:
予算は担当の現在のタスクの台帳の規模札と所要の実績から、監査待ちは担当の状態（`停止済み`で現在のタスクが
残っている）から、未pushは監査の記録とgitから、
前回のpushの時刻はorigin/masterの先端から。所要の実績は担当が完了のコミットで`Txxx.md`へ残す
（「完了とpush」節）。

**手で書かず、`scripts/orchestrate.py board`で更新する**（書き込みは一時ファイルからの置き換えで
原子的）。振り出し・停止・報告の受領・監査・定期確認のたびに更新する。会話にだけ状態を
置くと、司令塔のセッションが切れたとき・会話が要約されたときに失われる。**持ってよいキーの外は書けず**、
表を書き込むときに外のキー（手で書かれたもの・持たなくなったもの）を外して出す——写しを再び作らせない。

| 場面 | コマンド |
|---|---|
| 振り出した | `board add <名前> current_task=T1234 id=<エージェントのid>`（着手時刻が入る。予算は台帳の規模札と所要の実績から導く）。クラウドの担当は`id`の代わりに`where=クラウド`と、開いたセッションの`session=<セッション名>`（「手元かクラウドか」節） |
| 停止・再開 | `board set <名前> state=停止指示`（`稼働`・`強制停止`も同じ）。同じタスクの再開（差し戻しを含む）は`state=稼働`で、着手時刻は変わらない。監査せずに止めたままにする担当は`強制停止`にする（`停止済み`は監査待ちを表す） |
| 見込み超過の担当に問い合わせて、進んでいると確かめた | `board set <名前> overrun_ack=now`（是正済みの印。「異常の是正」節） |
| 報告を受けた | `board set <名前> state=停止済み reported_sha=<sha>`（監査待ちは、`停止済み`で現在のタスクが残っていることから導く） |
| 監査の結果 | `board set <名前> audit_done=now audit_result=通す`（通すと監査の記録に現在のタスクが残り、現在のタスクが表から外れ、スロットの印が外れる。下の「監査の記録」） |
| 回の値 | `board run limits.concurrent=3`・`board run check_interval_min=20`・`board run manual+=T1001`（書けるのはこの3つ。`k+=v`で配列へ追加） |
| 回の目的と母集団 | `board run start <名前>`・`board run goal <文>`・`board run add <Txxx>... from=<派生元>`・`board run remove <Txxx>`・`board run handover <文>`（打ち切りの引き継ぎ）・`board run list`（各タスクの状態は記録と台帳から導く。下の「回の始まりと終わり」） |

`/orchestrate:status`（`python scripts/orchestrate.py status [名前またはTxxx]`）は、この表と
リポジトリの事実（作業ツリーの先頭・最新コミット・未コミット件数、担当タスクのorigin/master上の
`状態:`と台帳の行）を突き合わせ、食い違いに印を付けて出す（表は稼働なのに作業ツリーが無い・
表は停止済みなのに作業ツリーが動いている・完了なのに台帳に行がある等）。

### 起動のしかた

- `isolation: "worktree"`。作業ツリーは新しく作られず、空いているスロットが渡る（次の節）。
  **1本ずつ起動する**——渡すたびにfetchと枝の作り直し（温めていないスロットで`package-lock.json`が
  変わっていれば`npm ci`）が走る。空きが無いと起動そのものが失敗する（上限を仕組みで守っている。`slot list`で
  印の残りを確かめる）。
- 指示文には、担当するタスク1件・その注意点・並行する他エージェントの担当範囲を書き、
  共通ルールは本規約の「エージェント共通ルール」節を**読ませる**（貼り付けない）。
- **実装かテストに手が入るタスク（目安は規模M以上）は、振り出すときに`/code-review`を回すかをダッシュボードで聞く**
  （そのタスクの件、kind `保留`。選択肢は「回さない（既定）」「回す（medium）」「回す（high）」）。担当は答えを待たずに
  着手する。**答えが無いまま監査に来たら回さない**（既定。取り込みを止めない）。`ultra`は課金の確認が要り
  ユーザーが起動するものなので、ここには入れない。
- **指示文には、次の「よく抜ける規則」を毎回そのまま添える**（規約全体を読ませても、長い節の中の
  1行は抜ける）。抜けた規則が見つかるたびに見直し、10行以内に保つ:

  ```
  - masterへはpushしない。作業ブランチ orch/<名前> へpushし、報告にCIのrunのURLと結論を添える。CI待ち・落ちたジョブのログは python scripts/orchestration/github.py wait|log <40桁のsha>
  - docs・*.mdだけの変更ではci.ymlは走らない（Docs Consistencyだけ）。来ないCIを待たない
  - 報告の前に python scripts/orchestrate.py audit <名前> <sha> --base <rebase先> を通す（枠で包まない）
  - 重い段（npm ci・tsc・vitest・pytest・build・playwright・ディレクトリ単位のeslint）だけを lockrun に入れる。上限10分。数分かかる本物の処理は最終確認の1回まで
  - git reset --hard・git stash（共有）は使わない。退避は一時的なWIPコミット、戻しは reset --keep
  - 規模の予算を超えそうなら、その時点で途中の状態を報告する（母集団を数えて件数が見えた時点も）
  - 完了のコミットで Txxx.md に所要の1行を残す。最終報告に「摩擦」の欄を書く

  - 複数の段・変数・ループを含む処理はscratchpadのPythonファイルに書いて実行する（隔離の検査に拒否されにくい）。scratchpadは並行する担当と共有なので、名前の頭に担当名を付ける（例: R-ledger_wait_ci.py）
  - 着手時に記録とダッシュボードの件（答え・決定）を読み、記録の前提（済んだはずの作業・触る範囲）を今のコード（origin/master）で確かめる。食い違えば問いとして置く。確認事項もダッシュボードへ（asking-user.md「仕掛中のダッシュボード」節）。問いを置くとき sent_at は書かない
  ```

### 作業ツリーのスロット

担当の作業ツリーは`<本体>/.claude/worktrees/slot-<N>`に**回の上限（`limits.concurrent`）と
同じ数だけ**置き、消さずに次の担当へ渡し直す。上限を超える作業はできない。道具は
`python scripts/orchestrate.py slot ...`で、渡し方・止まる条件・依存の入れ直しの正本は
`scripts/orchestration/slots.py`の冒頭。

- **渡すのはClaude CodeのWorktreeCreateフック**（本体の`.claude/settings.json`に登録）。
  `isolation: "worktree"`で起動すると、フックが空いているスロットを最新のorigin/masterから
  作り直して渡し、渡した印（`git worktree lock`の理由`slot agent-<id> <時刻>`）を付ける。
  前の担当の未コミットの変更・pushしていないコミットが残っていれば、そのスロットは渡さない
  （黙って消さない）。空きが無ければ起動が失敗する。
- **取り込み済みの元のコミットは、pushしていない成果に数えない。** 取り込みは担当のコミットを畳み直した
  別のコミットとしてmasterへ入れ、回の終わりに作業ブランチを消すので、担当の元のコミットはどのリモートの枝からも
  届かなくなる。監査で通した報告のshaから届き、そのタスクがmasterへ入ったもの（監査の記録と、そのタスクの番号から
  始まる件名のコミットが監査の後にmasterへ入ったかから導く。`board unpushed`の判定と同じ）は取り込み済みとして
  渡し直す。報告のshaより後に積んだコミット・監査で通していないコミット・まだmasterへ入っていないタスクの
  コミットは、今までどおり止める。
- **印を外すのは、監査で担当を通したとき**（`board set <名前> audit_done=now audit_result=通す`。
  作業ツリーにしか無い成果が残っていれば外さずに理由を出す）。担当の終了では外れない——
  Claude Codeは、フックが返した作業ツリーに中身があれば担当の終了時にWorktreeRemoveフックを
  呼ばずに残す（[T1066](../records/tasks/T1066.md)）。差し戻しの間は同じ担当が同じスロットで
  再開するので、印を残しておく。
- **通さずに止めた担当（強制停止・打ち切り）の印は、中身を確かめてから`slot release <N>`で外す。**
  `status`・`check`は、止まって監査も待っていない担当がスロットの印を持ったままなら指摘する
  （印が残ると、同時に動かせる本数が1つ減る）。フックは全セッションに効くので、司令塔の外で
  `isolation: "worktree"`で起動した担当（`/review`の分担等）も同じスロットを使う。監査を
  通らないので、起動した側が担当の終了後に外す。
- **空いているスロットは、渡す前に温めておく。** 定期確認（`check`）は、印の無いスロットの依存
  （前回`npm ci`した`package-lock.json`）がorigin/masterと違えば、`slot warm`を裏で起こして
  「スロットの温め: …」の1行を出す（確認そのものは待たない。出力は`<gitの共通ディレクトリ>/orchestration/warm.log`）。
  `slot warm`はそのスロットに`slot warm-<pid>`の印を付けて最新のorigin/masterへ作り直し、`heavy`の枠で
  `npm ci`してから印を外す。担当に渡しているスロットと、渡し直しを止める条件に当たるスロットには触らない。
  渡す側は、温めている途中のスロットしか空いていなければ温め終わるのを待つ。どのスロットが温まっているかは
  `slot list`の「依存」が出す。masterの`package-lock.json`を変えるタスクを取り込んだら、次の確認
  （確認間隔以内）で温まる——すぐ振り出すなら、先に`slot warm`を裏で起こしておく。
- 担当とスロットの対応は印から導く（`status`の「作業ツリー」）。状態の表には写さない。
- 担当はスロットを消さない・`git worktree unlock`しない。作業ツリーの中にリンク
  （ジャンクション）を置かない——置くとそのスロットは渡し直せなくなる。

## エージェント共通ルール

司令塔から振り出されたエージェントは、着手前にこの節と`CLAUDE.md`の全文を読み、厳守する。

### 前提

- 各タスクの正本は`docs/records/tasks/Txxx.md`。完了条件を満たしたかで完了を判断する
  （「実装した」ではなく「効いている」）。
- 対象モジュールの`docs/modules/*.md`を手を入れる前に精読し、乖離は同じコミットで直す。
- ユーザーへ見せる文言・コミットメッセージ・最終報告はすべて日本語。
- 作業するのは自分に割り当てられた作業ツリーの中だけ。本体のチェックアウトと、他の
  セッション・エージェントの作業ツリーは触らない。自分が変更したのではない差分を
  見つけても戻さない。
- `core.hooksPath`は全作業ツリーで共有される設定なので、自分で書き換えない（相対の
  `.githooks`であることは司令塔の定期確認が見る）。`--no-verify`は禁止。
- `git add -A`・`git add .`は禁止。明示パスでステージし、コミット前に
  `git diff --cached --stat`を見る。
- 使い捨てのファイル（調査スクリプト・スクリーンショット・一時spec）はリポジトリに
  置かない（`frontend/e2e/`へ置いたspecはCIが拾う）。

### コマンドの書き方（隔離の検査に拒否されにくく）

担当のコマンドは、作業ツリーの外へ出ないかを見る検査（隔離の検査）を通ってから走る。検査は1行に複数の段を
つないだコマンドの中身を読み切れないと拒否し、書き直すたびに数分を失う（担当6人が2〜5分ずつ失った。[T1162](../records/tasks/T1162.md)）。
拒否された形と、代わりの書き方:

| 拒否された形 | 代わりの書き方 |
|---|---|
| `cd <作業ツリー> && git ...` | `git -C <作業ツリー> ...`（1段で済む） |
| `git push origin $(git rev-parse HEAD):...`のようなコマンド置換 | 先に`git rev-parse HEAD`だけを走らせ、出た値を次のコマンドへそのまま書く |
| ヒアドキュメントでファイルを書き、同じ行で`git add` | Writeの道具でファイルを書き、`git add <パス>`を別に走らせる |
| 変数・ループ・複数の段をまとめた処理 | scratchpadのPythonファイル（`<担当名>_<用途>.py`）に書いて`python <そのファイル>`で走らせる |

CIを待つ・ジョブのログを取るような決まった処理は、自前で組み立てずに用意された道具を使う（「完了とpush」節）。

### 重い処理は機械全体で1本ずつ

**枠が守るもの**: エージェントが何本動いていても、CPUとディスクは開発機1台ぶんしか無い。
重い処理が同時に走ると同じCPUを取り合い、1本ごとの所要が何倍にも伸びる（単独27秒の`tsc`を
含む一式が、`npm ci`・backendテストと重なって18分かかった。実測は[T1049](../records/tasks/T1049.md)）。
そこで重い処理は、機械全体で共有する1つの枠（ロック名`heavy`）を通して1本ずつ走らせる。
枠は順番を決める道具ではなく、CPUとディスクを守るためのものである。テストDBの取り合いは
作業ツリーごとのDB（[T964](../records/tasks/T964.md)）で別に解けている。
枠を2つにしない根拠は実測にある: 2本を同時に走らせると機械全体の所要は直列より1〜3割縮むが、
軽いほうの1本が単独の2.4倍まで伸びる（`tsc --noEmit`と`vitest run`。実測は[T1057](../records/tasks/T1057.md)）。
枠が守るのは1本ごとの所要なので、1つのままにしている。

```
python scripts/lockrun.py -- '<bashコマンド文字列>'
```

**何を枠の下に置くか——処理の段1つで決め、包みでは決めない**:

- **対象**: 単独で走らせても、複数のコアかディスクを数十秒以上使い切る段。依存の導入
  （`npm ci`）・ビルド（`next build`・`next typegen`）・型検査（`tsc --noEmit`・`mypy`）・テストの実行
  （`vitest run`・`pytest`・`playwright test`）・ディレクトリ単位のlint（`eslint`）等。
- **対象外**: 数秒で終わる段と、ネットワーク待ちが主の段。`git`の操作（`fetch`・`rebase`・
  `push`そのもの）・`ruff`・変更ファイルだけの`prettier`・`review_checks.py docs`・
  `orchestrate.py audit`の機械項目・APIへの問い合わせ等。
- **重い段と軽い段が混ざった一続きを、丸ごと枠で包まない**。包むと、ネットワークを待つ間も
  軽い段の間も枠を持ち続ける。重い段だけが枠を取る。`git push`は枠で包まない（pre-push
  フックは検査をしない）。自作のスクリプトで複数の段をまとめて
  流すときも、段ごとに`lockrun`を呼ぶ。
- 1回の呼び出しには1段階だけ入れる（①静的検査、②変更が届くテスト、③E2E のどれか）。
  前の段階が落ちても後ろの段階の時間を払わないため、また段階の間で枠を放して他の処理を
  間に入れるため。
- **ロックを通さずに重い段を走らせない**（1本でも外で走ると、枠の中の処理が遅くなる）。
  司令塔の定期確認（`orchestrate.py check`）は、上の「対象」の項目に**コード書式で挙げた段**を
  プロセス一覧のコマンドラインから探し、枠の保持者の子孫でないものを「枠の外の重い処理」として出す。
  段の一覧はこの項目から読む（別の一覧を持たない）ので、対象を足すときはコード書式で書く。
  Git for Windowsのbashがforkした子は親を辿れなくなるため、枠が持たれている間は、系列がMSYSの
  シェルで途切れた段を出さない。枠の外で走らせた段は、段の語を持つ包み（`bash -c '…'`）の側で出る。
- 枠を持った処理の中から同じ枠を取りに来た呼び出し（例: 枠の中で走らせたスクリプトが、
  さらに`lockrun`を呼ぶ）は、`lockrun`が待たずにそのまま走らせる（環境変数`LOCKRUN_HELD`）。

**1回の保持の上限は10分**（`LOCKRUN_MAX_HOLD_SECONDS`、既定600）。超えると`lockrun`が処理を
子プロセスごと打ち切り（終了コード124）、枠を放す。根拠は、対象の段を単独で走らせたときの
最長が`npm ci`の166〜526秒だったこと。上限に掛かるのは、段を束ねた包みか、下の「独占」に
当たる作業である。上限を青天井にすると、1本が枠を持つ間、後ろに並んだ全員（数秒で終わる
ものも含む）が同じだけ待つ。

**機械を独占しないと成り立たない作業は、枠ではなく「独占の時間帯」で扱う**。所要時間の
計測（`npm ci`の方式比較・性能の新旧比較等）は、他の処理が同時に走ると値が意味を持たない
うえ、1回で数十分かかりうる。司令塔は、稼働中の担当が他に無いときにだけ振り出し、その間は
他を振り出さない。担当は計測を上限内の単位に分け、単位ごとに`lockrun`を呼ぶ。

枠を待つ時間は、機械を取り合うかわりに列に並んだ時間である。待ちが長いことは、エージェントの
本数が機械の能力を超えている——または上の定義に反した包みが枠を持っている——という司令塔への
合図になる（「上限と門」節。`python scripts/lockrun.py --report`で保持の長いものを見る）。

backendのPythonは作業ツリーに`.venv`が無いため、本体のチェックアウトの
`backend/.venv`を使う。

### 重い処理を減らす

枠で並べても、需要そのものが多ければ列が伸びるだけである。**同じ答えを2回買わない**:

- **検査は変更が届く範囲を1回だけ回す**（CLAUDE.md「テスト方針」）。落ちたら一式を
  流し直さず、落ちたものの原因を取り、直した範囲だけを確かめる。書式の指摘（prettier・
  ruff format）は、書式ツールで直した差分が空白だけであることを見れば済み、テストを回し直す
  理由にならない。
- **`next build`と`playwright test`は、変更がその経路に届くと示せるときか、タスクが画面の
  確認を求めるときだけ回す**。コンポーネントの単体で確かめられることは`vitest`で確かめる。
  画面の確認は`frontend/e2e/fixtures.ts`のモックで撮る。**例外は`frontend/e2e-live/`**: 地図の描き方・
  タイルへ焼く値・軸カタログ・気象・ルート生成の応答に触る担当は、作業ブランチを出す前に1回回す
  （条件・前提・手順は[testing.md](testing.md)パターン4「走らせ方」）。
- **検知器・ガードが効くことは、テストの中で壊して確かめる。数分かかる本物の処理は最終確認の1回まで。**
  画面の検知器は、playwrightの`page.addStyleTag`やvitestの入力の差し替えで壊した状態をテストの中で作る——ソースを
  書き換えて本番ビルドし直さない。道具（`scripts/`）の仕組みは、一時的なgitリポジトリと入力の差し替えで確かめる
  （`backend/tests/test_orchestration_slots.py`）。本番ビルド・本物の`npm ci`は、仕組みの確認に繰り返し使わない
  （1回約5分のビルドを数回回して規模Sの予算の2.5倍かかった例、本物の`npm ci`の出力の文字コードの食い違いで10分
  空待ちした例がある。[T1162](../records/tasks/T1162.md)）。書き方は[testing.md](testing.md)「わざと壊すのは、テストの中で」。
- **`npm ci`は、スロットの`frontend/package-lock.json`が前回の`npm ci`から変わったときだけ**走り、
  多くは渡す前に定期確認が裏で起こす温めの中で済む（「作業ツリーのスロット」節。どちらも`heavy`の枠で
  走る）。渡すその場で走るのは、温める前に振り出したときだけ。担当は自分で`npm ci`しない。
- **フルスイートは回さない**（CIの持ち物。CLAUDE.md「テスト方針」）。
- **確かめる検査は、作業ブランチへpushしてCIに回す**（「完了とpush」節）。手元で回すのは
  静的検査（`ruff`・`mypy`・`review_checks.py docs`・prettier・`tsc --noEmit`）と、書きながら挙動を
  確かめる最小のテスト（変更が届くファイルだけ）までにする。CIのランナーは実行ごとに別の
  機械なので、何本同時に回しても開発機の`heavy`の枠を取り合わない。

### 本番

- 本番DBの読み取りの計測（`backend/scripts/run_probe.py`経由）は確認なしでよい。
- 本番への書き込み・削除・バッチ実行・常設設定の変更はしない。コード側を終え、必要な
  操作を最終報告の「ユーザー確認事項」に書く。
- `backend/**`の変更はmasterへ入ってCIが通ると本番へ自動デプロイされる。既存DB行を新コードが読めなくなる
  変更は、本番データ移行が先（CLAUDE.md「コミット時の同期ルール」）——その場合は
  pushせずに報告する。

### 判断に迷ったら

ユーザーにしか決められない判断（本番から外れたものを残すか・利用者に見える情報量を
増やすか・要件の推定が要るもの）は、その項目だけ保留して仕掛中のダッシュボードにkind `保留`
（何が・なぜ・選択肢。書き方は[asking-user.md](asking-user.md)）として置き、残りを進める。保留があるタスクは
`状態: 未完了`のまま台帳の行も残す。新しいタスクが要ると分かったら、既存のタスクに属さないことを確かめてから
起票案としてダッシュボードに置く（番号は振らない。`scripts/new_task.py`は実行しない。
[asking-user.md](asking-user.md)「起票は承認制」）。範囲外で見つけたものは、直さずに
最終報告へ書く（司令塔が担当のエージェントへ回す）。

### 完了とpush

- 完了の作法: `Txxx.md`の`状態:`を`完了`にして実施内容・検証結果を書く。**台帳
  （`docs/improvement-plan.md`）の行には触らない**——台帳は全担当が1行ずつ触る共有のファイルで、
  隣り合った行を別々のブランチで変えると取り込みで衝突する。閉じたタスクを開け直すときも`状態:`を
  `未完了`へ戻すだけにし、**台帳の行は司令塔が取り込みで消す・戻す**（`ledger sync`。「監査の結果」）。
  作業ブランチの`review_checks.py docs`は状態と台帳の行の食い違いを参考として出すだけで違反にしない
  （masterでは違反）。本文に未実施の段階・派生が残るなら、閉じずに
  `状態: 未完了`のまま残す（CLAUDE.md「検査器にできず、人が見るしかないのは…」の2.）。別の担当・別の時機で
  進むと分かっているものだけ、起票案としてダッシュボードに置く。
- **所要を1行残す**（完了のコミットで、`Txxx.md`の末尾へ。段階を切ったなら段階ごと）:
  `所要（並行実行）: 依頼 2026-09-23 14:22 → 完了 15:05（43分）、うち枠待ち6分・CI待ち4分、規模札S、実績 +120/−40 → S`
  依頼は司令塔の依頼を受けた時刻、完了は完了のコミットの時刻（どちらも日本時間）。枠待ちは自分の作業ツリーで`python scripts/lockrun.py
  --report --since <依頼の時刻> --mine`の待ち合計（スロットは担当を替えて使い回すので`--since`と合わせる）、CI待ちは完了のコミットより前にpushして
  待った分（pushからCIの結論まで）を足す。分からなければ「不明」と書く。実績は実装＋テストの変更行（生成物を除く）と、
  それで付け直した札（CLAUDE.md「規模の札」）。
  **これが所要の実績の唯一の置き場**——状態の表には実時間・予算・差を写さない（「状態の表」節）。
  並行実行の予算は、この行を集めて規模札ごとに読むときに計算する（保存しない。「管理のループ」節）。
  機械が読むのは「完了 …（N分」の分・`枠待ちN分`・`CI待ちN分`・`規模札X`で、「不明」の待ちがある行は
  実時間の側にだけ数える。段階を切ったタスクの段階の行は規模札を書かない。
  予算を超えたら、同じ行の後ろに理由を1つ書く（`超過: 見立てより中身が大きい／環境の待ち／進め方`）。
  `/orchestrate:status`が規模札ごとの理由の件数を出す——「見立てより中身が大きい」が続く規模札は、
  起票の規模の見立て方を見直す材料としてユーザーへ示す。
- コミットメッセージはCLAUDE.md「1タスク=1コミット」の書式で書く（検証に実行したコマンドと観測値、
  増減に実装・テスト・文書を分けた行数）。
- **masterへはpushしない。** masterへ出すのは監査を通したあとの司令塔である——backendは
  masterのCIが通ると本番へ自動デプロイされるため、監査を後にすると、監査前のものが本番に出る。
- **作業ブランチ`orch/<名前>`へpushしてCIに回す。** `ci.yml`・`docs-consistency.yml`は
  `orch/**`へのpushでも走る（本番へのデプロイは走らない）。pre-pushフックは検査をしない
  （検査の置き場はtesting.md「検査の置き場」）。CIはLinuxで動き、開発機（Windows）で通ったことはLinuxで通る証拠にならない
  （OSで結果が変わるテストの例は[testing.md](testing.md)パターン10）——**masterへ入れてよいかの
  最終的な判定は、作業ブランチのCIの結論である**。1タスク（段階を切るなら1段階）を終えるごとに:
  1. 手元で最新のorigin/masterへrebaseする（`git fetch origin master && git rebase origin/master`）。
  2. 先端のコミットを明示してpushする: `git push origin +<sha>:refs/heads/orch/<名前>`
     （rebaseで履歴が変わるので強制で上書きする。このブランチは担当1人だけが使う）。
     docs・`*.md`だけの変更では`ci.yml`は走らず、`docs-consistency.yml`だけが走る。
  3. CIの結論を待つ。実行全体で2〜3分かかる。結論は下の監査コマンドの「CI」の項が出す
     （`https://api.github.com/repos/hidakagit/ride-compass/actions/runs?head_sha=<sha>`を読む）。
     GitHubへの問い合わせは`scripts/orchestration/github.py`の1か所にまとめてあり、
     `git credential fill`でトークンが取れれば認証付き（上限は1時間5,000回。実測は
     [T1071](../records/tasks/T1071.md)）、取れなければ認証なし（接続元のIPごとに1時間60回で、
     開発機の全エージェント・masterへのpushの警告が同じ枠を使う）で読む。自分で問い合わせを
     組み立てず、この関数か監査コマンドを使う。今の枠は`python scripts/orchestration/github.py`
     で見られる。待つのは`python scripts/orchestration/github.py wait <40桁のsha>`（全ワークフローが終わるまで
     90秒おきに読み直し、結論とrunのURLを出す。全部成功なら終了コード0）。Actionsの実行は完全なshaでしか引けない
     ので、短いshaは断る。自前で待つときも数秒おきに問い合わせない。
  4. 赤なら、ジョブのログで原因を取って直し（CLAUDE.md「テスト方針」のテストが落ちたときの
     直し方）、同じブランチへ積んで1.からやり直す。緑になるまで「監査待ち」にしない。ログは
     `python scripts/orchestration/github.py log <40桁のsha>`（落ちたジョブごとのログの末尾）で取る——ログは署名付きの
     別のURLへの転送で返り、転送先へ認証の見出しを渡すと401になるので、自前で取りに行かない。
  5. 司令塔へ「監査待ち」と報告する（**コミットsha**・CIの**runのURLと結論**・検証のコマンドと
     観測値を添える）。
  **報告の前に、監査の機械項目を自分で1回通す**:
  `python scripts/orchestrate.py audit <名前> <sha> --base <rebase先>`（数秒で終わる軽い段なので枠を取らない）
  で、CIの結論が緑で機械で見る項目の指摘が0件であることを確かめる。書式（prettier）・lint・
  型・テスト・docs検査・API契約はCIのジョブが見る。
  監査を待たずに次のタスクへ進んでよい（次のコミットは同じブランチに積む）。
- 司令塔から「差し戻し」が来たら、指摘を直して同じブランチへ積み、pushしてCIに回し、
  新しいshaで報告し直す。
- `docs/improvement-plan.md`がrebaseで衝突したら**両方の変更を残す**（司令塔が消した行を戻さない）。

### 最終報告

渡されたタスク1件を終えたら、次へ進まずに報告して止まる: 状態（完了／一部保留）とコミットsha、CIのrunのURLと
結論、何を直したか、検証に使ったコマンドと結果、実装の増減、ダッシュボードに置いた起票案・ユーザー確認事項、見積もりとのずれ、
**摩擦**（待った・やり直した・道具や規約が邪魔した事象と、失った時間。無ければ「なし」）。

## 管理のループ（時間で回す）

**確認を、エージェントからの完了通知だけに頼らない。** 通知は終わったときにしか来ない
ので、止まっている・遅れているエージェントは何も知らせてこない——**何も起きていないことは、
時間で見に行かないと検知できない**。

- **定期確認の本体は`python scripts/orchestrate.py check`**。異常だけを出し（無ければ1行）、
  終了コードで異常の有無を返す。`--record`で表の最終確認時刻を更新する。見るもの（どれも
  軽いコマンドで取れるものだけ。飽和した機械に重い確認を足さない）:
  - 見込み超過。**担当の現在のタスク（`current_task`）ごとに、その着手時刻（`task_first_started`。
    再開しても上書きしない）から通算で数え、そのタスクの台帳の規模札（幅があれば大きい側）の
    予算と比べる**。報告を受けて監査待ちの間は数えない。**予算は、タスク記録の所要の行
    （「完了とpush」節）を規模札ごとに集めた80パーセンタイル**で、読むたびに計算する。作業
    そのものの時間（実時間から枠待ち・CI待ちを引いたもの）が5件以上あればそれを、無ければ実時間を
    使う——作業そのものの時間は機械の飽和中の待ちを含まないので、飽和中の1件が予算を押し上げない。
    どちらも5件に満たない規模札は、実績のある隣の規模札に規模札の定義の比（S:M:L=1:4:8）を掛けて
    補い、隣も無ければ定義の値（S=60・M=240・L=480分）を使う。規模札の定義は人が作業する前提の
    見立てで、並行実行ではMの実績が30〜105分だった（定義の240分では、止まったタスクの検知に
    4時間かかる。[T1067](../records/tasks/T1067.md)）。checkは毎回、規模札ごとの予算と件数を1行出す。是正済みの印が
    効いている担当（「異常の是正」節）は異常に数えず、「是正済み」と添えて別の行に出す。現在のタスクと
    着手時刻は、振り出しで入り、監査を通したときに外れる——再開のたびに起点を置き直すと、通算で規模を
    超えたタスクを検知できない
  - 一定時間（既定30分）コミットが無いまま未コミット変更が積み上がっている
  - 表は稼働なのに作業ツリーが無い／表は停止済みなのに作業ツリーが動いている／止まった担当が
    スロットの印を持ったまま／上限超過
  - 監査待ちの放置（報告のコミットから30分）・報告のshaの記録漏れ
  - 監査済み・未pushのコミットがpushの時期に来た（未pushはgitから、前回のpushの時刻は
    origin/masterの先端から導く）
  - 共有設定（`core.hooksPath`が相対の`.githooks`のままか——全作業ツリーで共有される。
    Claude Codeは作業ツリーを作るたびにこれを本体の絶対パスへ書き換える
    （[anthropics/claude-code#66993](https://github.com/anthropics/claude-code/issues/66993)）。`board add`・`board set ... state=稼働`が
    記録のたびに相対へ戻すので、振り出しを表へ記録すれば直る）
  - 停止ファイル・直近のロック待ち・CPUの飽和・枠の外で走る重い段（「重い処理は機械全体で1本ずつ」。
    候補であって判定ではない——Bashツールの包みのように、コマンドラインに段の語を含むだけのものも拾う）
  - 共有資源への波及: 稼働中・監査待ちの担当の作業ブランチ（`orch/<名前>`）の直近の成功したCIで、
    ジョブの所要がmasterの基準より伸びたもの（監査の項目10と同じ比較。GitHubへの問い合わせは実行の一覧と、
    まだ読んでいない実行のジョブだけ（完了した実行のジョブはキャッシュする）。取得できなければ異常にしない）
  - **振り出し待ちがあり、門が開いている**（下の「見送った振り出しを拾うトリガー」）
  - **稼働0本（手元もクラウドも）で、振り出し待ちは無いが進められるものがある**: 門が開いていて母集団の残りに
    担当・手動・判断待ち（最新の`pending-backup`の答えの出ていない問い）・母集団の中の前提待ちのどれでもないものがある、
    または司令塔の作業待ちがある（「司令塔の役割」）
  - **ダッシュボードの取り込み待ち**: 最新の`pending-backup`で、ページの「取り込み待ち」タブと同じ定義の件（答えかコメントが
    付いていて、`taken_at`が無いか、それより前の件。[asking-user.md](asking-user.md)「仕掛中のダッシュボード」）を、今の持ち主ごとに
    出す（`pending-inbox`と同じ並び）。書き出しが確認間隔の2倍より古い・無いときは
    「ダッシュボードの書き出しがN分前」を出す。ダッシュボードは`ArtifactData`でしか読めず道具からは読めないので、**司令塔は
    定期確認の結果を受けるたびに、`ArtifactData`の`list`（collection `pending`、`out_dir`付き）で書き出して
    `pending-backup --pending <out_dir>`し直す**——`pending-backup`も取り込み待ちの件を知らせるので、書き出した時点で拾える。
    答えはページの「Claude に反映を頼む」が押されなくても付くので、送られるのを待たない
- **確認は時間で自動的に回る。** `.claude/settings.json`のPostToolUseフック
  （`scripts/orchestration/hook.sh`）が、司令塔のセッションが道具を使うたびに、前回の確認から
  確認間隔（表の`check_interval_min`、既定20分）を過ぎていれば`check`を走らせ、結果を文脈へ
  返す。`CronCreate`の定期実行は待機中にしか発火せず、司令塔が忙しいほど確認が抜けたため、
  道具の使用に結びつけた。**司令塔は起動時に`python scripts/orchestrate.py board claim`を
  1回実行する**——`board claim`は頼み（`claim_pending`）を置いて終わり、直後のフックがそのセッションを司令塔として記録し
  （`<gitの共通ディレクトリ>/orchestration/coordinator_session`）、文脈へ「記録した」と知らせる。以後そのセッションでだけ
  確認が走る（他のセッションでは何もしない）。記録するのは、道具に渡したコマンド（`tool_input.command`）が`board claim`の
  呼び出しだけで、コマンドはフックの入力をJSONとして読むpythonの側が見る（引用符を含む1行のコマンドでもよい）。
  **「記録した」が出なければ登録されていない**: PostToolUseは成功した道具の呼び出しの後にだけ走る（[公式](https://code.claude.com/docs/en/hooks)）
  ので、`board claim`を含むコマンドが0以外で終わると直後のフックが走らない。そのときは頼みが残り、次の道具の呼び出しの
  フックが「記録されていない」と知らせて頼みを消す——`board claim`を単独のコマンドで実行し直す。司令塔が起動した担当
  （サブエージェント）の呼び出しは司令塔と同じ`session_id`を持つので、フックの入力の`agent_id`（サブエージェントの呼び出しに
  だけ付く。同じ公式の共通の入力の項）で見分けて何もしない（担当の中の`board claim`は記録されない）。
  フックは全セッションの全ての道具の呼び出しで走るため、確認するか（司令塔のセッションか・次の確認の時刻
  `next_check`を過ぎたか）は`hook.sh`がプロセスを起こさずに判定し、確認しないときはそのまま抜ける。フックは`/bin/sh -c`で
  動き、`/bin/sh`は開発機ではbash、クラウドではdashなので、`hook.sh`はPOSIXのshの組み込みだけで書く。今の時刻を
  持つ変数`EPOCHSECONDS`はbash 5.0からで、dashと開発機のGit Bash（4.4）には無いため、司令塔のセッションの時刻の比較で
  `date`を1本起こす（司令塔の道具の呼び出しごとに1本。他のセッションでは起こさない）。フックは`$CLAUDE_PROJECT_DIR`（セッションを始めた本体のチェックアウト。
  作業ツリーへ入っても動かない）から読まれ、本体はmasterが進んでも早送りしない限り古いままなので、
  確認そのものは**origin/masterの版の道具**で走る（`scripts/orchestration/launch.py`がgitの中から
  `<gitの共通ディレクトリ>/orchestration/tools/<sha>/`へ書き出して動かす。本体は書き換えない）。
  入口の`hook.sh`だけは本体から読まれるので、origin/masterの版と違えば確認の結果に
  「フックの入口が古い」と出る——出たら本体のチェックアウトを早送りする。
  待機中は`CronCreate`の定期実行（振り出しと同時に設定する）が確認を回す。
- 異常があれば下の是正の段階へ進む。

### 見送った振り出しを拾うトリガー

門がNGで振り出しを見送るとき、「落ち着いたら」と会話に書いて終えない——それを誰がいつ
見直すかが決まっていない。**見送ったものは必ず振り出し待ちのキューへ積む**
（`board dispatch push <Txxx> agent=<名前> --priority 高|中|低`）。拾うのは次の2つで、どちらも
人の注意に頼らない:

1. **出来事**: エージェントの完了・報告の通知を受けたとき（稼働が1本減る＝門が開きうる）。
   監査を済ませたら`gate`を回し、開いていれば`board dispatch pop`で取り出して振り出す。
2. **時間**: 定期確認（`check`）が、振り出し待ちがあって門が開いていれば
   「要対応: 振り出し待ちN件があり、門が開いている」を出す。CPUの飽和のように通知を伴わずに
   解けるNGは、こちらでしか拾えない。

### 異常の是正

進捗が無い（見込み時間を超えた、または一定時間コミットが無いのに未コミットの変更が
積み上がっている）エージェントには、次の順で手を打つ。**コミットがあることを進捗とみなさない**
——コミットが続いていても、通算が規模の予算を超えていれば是正の対象である。

1. **問い合わせる**（`SendMessage`）: いま何に時間を取られているか・詰まっている点・
   あとどれだけか。進んでいると確かめたら、是正済みの印を付ける（`board set <名前> overrun_ack=now`）。
   印の付いた担当の見込み超過では門を閉じない（`check`は「是正済み」として別の行に出し続ける）——確かめた担当1本の
   ために、空いた枠を遊ばせない。確かめたのはその時点の進みだけなので、印は付けてから同じタスクの予算の分数が
   経つと効かなくなる（そのとき超過が続いていれば、もう一度問い合わせて付け直す）。タスクが替わるか監査を通すと外れる。
2. **途中の成果をコミットさせる**: 作業ツリーにだけある変更は、停止・事故で失われる。
   段階を切れるなら段階として報告させる。
3. **分割する**: 見積もりと実態が大きくずれていれば、残りを起票案としてダッシュボードに置かせて、
   終わっている段だけ閉じる。
4. **一時停止する**: 資源の逼迫が原因なら、上限を下げて止める（下の「止める手段の段階」）。

- 完了はエージェントの通知で知る。完了の確認のためにポーリングしない（上の定期確認は
  「何も起きていない」ことを見るためのもので、完了の検知には使わない）。

### 止める手段の段階

止める手段は、**止めたい原因（司令塔の注意・機械の応答・エージェントの協力）に頼らない**
ものを段階で持つ。前の段が効かなければ次へ進む。段1は、司令塔のセッションが生きていて、機械が応答し、
エージェントが指示を読めるときにだけ効く。

| 段 | 手段 | 頼るもの |
|---|---|---|
| 1 | 停止の指示（`SendMessage`: 実行中のコマンドが終わったら、途中の成果をWIPコミットしてpushせずに報告して終える） | エージェントの協力。長いコマンドの途中では読まれない |
| 2 | 強制停止（`TaskStop`）。作業ツリーの変更はディスクに残る | 司令塔のセッション |
| 3 | **停止ファイル**: `<gitの共通ディレクトリ>/orchestration/STOP`を置く。置かれている間、`scripts/lockrun.py`は重い処理とpushを始めず、pre-pushフックはpushを拒否し、`orchestrate.py gate`はNGを返し、`check`は異常として出す | ファイル1つ。司令塔が不在でも、ユーザーがエクスプローラーで空ファイルを作るだけで効く |
| 4 | ユーザーの操作: アプリで各セッションを止める。それでも止まらなければOSでプロセスを止める（下記） | ユーザー |
| 5 | 被害の回復: masterへ出た誤りはrevertをpushする（backendは自動デプロイされるので、revertも自動で本番へ出る）。デプロイ自体を止めるならGitHubの画面でCIのワークフロー（`ci.yml`。デプロイはそこから呼ばれる）を無効にする。本番DBは取り直せない管理データのバックアップ（[T972](../records/tasks/T972.md)）から戻す | 手順とバックアップ |

段3は、エージェントが指示に従わなくても、**masterと本番へ何も出ていかなくする**ことが目的で、
作業そのものを止めるものではない（重い処理を新しく始めないので、負荷は下がっていく）。
解除はファイルを消すだけ。

段4でOSのプロセスを止めるとき（PowerShell。作業ツリーの下で動いているものだけを対象にし、
本体のチェックアウトや他のアプリを巻き込まない）:

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*\.claude\worktrees\slot-*' -or $_.CommandLine -like '*\.claude\worktrees\agent-*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

止めたあとの作業ツリーは消さない（未コミットの変更が残っている）。中身を確かめてから、
再開するか片付けるかを決める。
- エージェントが範囲外で見つけたものは、担当のエージェントへ`SendMessage`で回す
  （担当がいなければ起票案にする）。
- 規約・手順を途中で変えたら、稼働中の全エージェントへ伝える。本規約の該当節を直し、
  指示文には「該当節を読み直せ」と書く。
- CIが赤くなったら、原因のコミットを**ログで**特定してから扱う。エージェントの
  「別のコミットのせい」は主張であり、直後のコミットで緑に戻るなら並列実行の不安定な
  テストを疑う（不安定なテストも、赤を本物と見分けられなくするので起票案にする）。

## 完了時の監査（masterへの門）

「監査待ち」の報告が来たら、次のタスクを振り出すより先に監査する。**監査がmasterへの門**で、
通したものだけを司令塔がmasterへ進める。

- **`python scripts/orchestrate.py audit <名前> <sha>`を先に回す。** 範囲は
  `git merge-base origin/master <sha>`（合流点）から`<sha>`まで——`origin/master..<sha>`で
  取ると、土台が古いコミットではmaster側の変更の逆向きが混ざる。前回通したコミットがまだmasterへ届いていなければ、その先だけを見る。
  機械で判定できる項目（1.範囲・2.記録の整合・4.検証の証拠の有無・7.同期ルール・10.共有資源への波及）と、
  **報告のshaに対するCIの結論**（ワークフローごとの最新の実行。失敗・結論待ち・実行が無い・
  取得できないはどれも指摘になる）を出す。静的検査（ruff・prettier・tsc・docs検査・OpenAPI生成物の
  ずれ）は監査で走らせない——同じものを作業ブランチのCIが走らせ、その結論を「CI」の項が読む。
  - 3.完了条件・5.主張の抜き取り検証・6.本番への影響・8・9は「未判定」として並ぶ。
    **司令塔の監査の本体はここ**である。
- 通さなければ、何が足りないかを添えてエージェントへ差し戻す。

### 監査の目的と範囲

監査は**「このコミットをmasterへ進めてよいか」を決める門**である。確かめるのは、
報告どおりのものが・報告どおりの証拠つきで・安全にmasterへ入る形になっているか。

**監査がやらないこと**: 設計のやり直し・コードの書き方の好みの指摘（`/code-review`の持ち物）、
フルスイートの実行（CIの持ち物）。監査で気づいた範囲外の改善点は、差し戻しの理由にせず
起票案にする。

**`/code-review`を回すと答えが出ているタスク**（「起動のしかた」の問い）は、監査で司令塔がその担当のブランチに対して
回す（`/code-review <深さ> <合流点>...orch/<名前>`。モデルから起動でき、裏のサブエージェントで走る）。そのタスクの中で
直せる指摘は担当へ返して直してから取り込み、タスクの外の指摘は改善案か起票案としてダッシュボードに置く
（[asking-user.md](asking-user.md)「起票は承認制」）。所要は記録へ書く。

### 監査の項目と合格の基準

1件の監査で、次をすべて見る。**止め（ブロック）**の項目が1つでも満たされなければ差し戻す。

| 項目 | 合格の基準 | 区分 |
|---|---|---|
| 1. 範囲 | 合流点から報告のshaまでの差分のファイルが、そのタスクの範囲に収まる。無関係なファイル・使い捨てのspec/スクリプト・生成物の取り残しが無い | 止め |
| 2. 記録の整合 | 担当が書いた記録は自分のタスクの`Txxx.md`だけ。`状態:`と台帳の行が一致する（未完了なら行が残る。完了の行・開け直したタスクの行は取り込みで司令塔が直すので、食い違っていてよい）。未完了なら、残っている問い（何が・なぜ・選択肢）がダッシュボードにkind `保留`として置かれている。本文に残った未実施の段階・派生は、元のタスクが閉じずに残っているか、起票案としてダッシュボードにある | 止め |
| 3. 完了条件 | `Txxx.md`の完了条件の各項目に、満たしたことを示す記述（何で確かめたか）がある。満たせない項目は保留としてダッシュボードに置かれている | 止め |
| 4. 検証の証拠 | コミットメッセージに、実行したコマンドと観測値がある。検知器・ガード・テストを足したなら、わざと壊した入力で落ちることの確認がある。緩和を入れたなら、外した件数と割合がある | 止め |
| 5. 主張の抜き取り検証 | 報告の中の事実の主張のうち、**結論が最も強く依存しているもの**を少なくとも1つ、司令塔が自分で確かめる（コード・公式資料・DB・CIのログ）。誤っていれば、その主張に依存する結論も疑う | 止め |
| 6. 本番への影響 | `backend/**`を含むなら、既存のDB行を新コードが読めるか・マイグレーションが要るか・本番での操作が要るかが書かれていて、要る操作は実施されずに「ユーザー確認事項」になっている。秘匿情報を含まない | 止め |
| 7. 同期ルール | CLAUDE.md「コミット時の同期ルール」の対象（API・Pydantic・レジストリ・domain定数・焼き込み値）を変えたなら、生成物が同じコミットで再生成されている。対象モジュールの`docs/modules/*.md`が実装に追従している | 止め |
| 10. 共有資源への波及 | 作業ブランチのCIで、いずれかのジョブの所要が、masterの直近5回の成功した実行の同じジョブの**最大値より60秒以上長い**なら、司令塔は通さず**ユーザー確認**に上げる（通す・縮めてから通す・CIの持ち場を変える、をユーザーが決める）。60秒は、masterのジョブごとの揺れ（2026-09-23時点で最大と最小の差が20秒以内）の3倍。masterでだけ走る段（今は無い）を足す・伸ばす変更は作業ブランチのCIに出ないので、担当に手元で前後の所要を測らせ、伸びていれば同じくユーザー確認。比較は`audit`の「10.」が出す（基準は報告のshaの祖先にあたるmasterの成功した実行。60秒・5回の値は`scripts/orchestration/ci_duration.py`が持つ）。masterと作業ブランチで走る段が違うジョブ（masterでだけ走る段を持つe2e等）は「比べられない」と出る——その段の伸びは上の手元の測定で判断する | ユーザー確認 |
| CI | 報告のshaに対する`ci.yml`（docs・`*.md`だけの変更なら対象外）と`docs-consistency.yml`の最新の実行が成功している | 止め |
| 8. 報告の正確さ | 報告の数字・sha・ブランチ名が事実と合う。誤りは止めにはしないが、記録に残す（「回ごとに残す記録」の「監査で見つかった誤った主張」） | 記録 |
| 9. 見積もりとのずれ | 規模・所要が見立てと大きくずれていれば、その理由が書かれている | 記録 |

### 監査の結果

- **通す**: `board set <名前> reported_sha=<sha> audit_base=<合流点> audit_done=now audit_result=通す`
  （`audit`の出力の最後の行）。監査の記録が1件残り、担当の現在のタスクが表から外れる。
  masterに入るまでそのコミットは**監査済み・未push**として`board unpushed`に出る（監査の記録と
  gitから導く。監査で通したタスク（その時点の現在のタスク）の番号から始まる件名のコミットが、監査の後にmasterへ
  入っていれば入ったとみなす——取り込みで衝突を解き・後始末を畳み・件名を直しても判定が変わらない）。すぐにはpushしない——masterへのpushのたびにCIとbackendのデプロイ（本番の再起動）が
  走るため、溜めて1回で出す。pushの時期は
  次のどれかで、`check`が「要対応」として知らせる:
  - 溜まったものが複数そろった
  - 前回のmasterへのpushから60分
  - セキュリティか利用者に届いている欠陥の修正（`urgent=true`を添えて通す）は即時

  取り込みは`board unpushed`が1行ずつ出す手順で、司令塔の作業ツリーで行う（枠で包まない）: origin/masterから
  枝を作り、担当の範囲ごとにcherry-pickし、`python scripts/orchestrate.py ledger sync`で台帳の行を記録の状態へ
  合わせ（完了の行を消し、開け直したタスクの行を戻す。作業ツリーのファイルを直すだけでコミットしない）、それを
  **取り込んだそのタスクのコミットへ畳む**（範囲が1コミットなら`git commit --amend`、複数なら`git reset --soft`で
  1コミットにまとめる。masterには1タスク1コミットで入る。件名と本文はCLAUDE.md「1タスク=1コミット」の書式）。
  衝突したら自分で解かず、担当へ差し戻す。**pushは取り込みが最後まで通ったのを確かめてから、別のコマンドで打つ**
  ——同じ行に続けると、止まった取り込みの手前までがmasterへ出る。push後に表を書き換える手順は無い（入ったかは
  gitから導く）。
  **組み合わせた木を初めて検査するのはpush後のmasterのCI**で、赤ならbackendのデプロイは
  起動しない。定期確認でその結論を見て、赤ければ原因をログで特定する。
  回の終わりに、全コミットがmasterへ届いたエージェントの作業ブランチを消す
  （`git push origin --delete orch/<名前>`）。
- **差し戻す**: 満たしていない項目と、何があれば通すかを具体的に書いて、担当のエージェントへ
  返す。司令塔が自分で直さない（直すと、監査した者と書いた者が同じになる）。
- **保留する**: ユーザーの判断がmasterへ入れる前に要るもの（本番のデータを読めなくする変更等・
  項目10に当たる変更）は、判断が出るまで進めない。

### 監査の記録

報告のsha（`reported_sha`）・監査の終了（`audit_done`）・結果（`audit_result`）を`board set`で書く。
`audit_done`を書くたびに、その時点の値と現在のタスク（`task`）が`audit_log`へ1件残る。監査の
待ち時間（報告のコミットから結果まで）は「回ごとに残す記録」の測るものに入れる——門を置いた以上、
監査の遅れはそのまま全体の処理量の低下になる。止めた項目・見つけた誤りは差し戻しの文と回のまとめに書き、
表には持たない。

## ユーザーの判断待ち

確認依頼の形式（背景を知らない人がその1問だけで判断できる書き方・ダッシュボードでの届け方）は
[asking-user.md](asking-user.md)が正本。ここには並行実行での扱いだけを書く。

- **判断の問いは、答えが記録に入るまで仕掛中のダッシュボード（kind `保留`）に置き、答えが出たら、
  そのタスクのコミットで問いと答えをまとめて記録（`Txxx.md`）へ書く**（「判断に迷ったら」節、
  [asking-user.md](asking-user.md)「仕掛中のダッシュボード」節）。状態の表には写さない。
- ユーザーはダッシュボードのページで問いに答える。こちらから催促・通知しない。推奨案を自動で採用しない。
  判断待ちのタスクだけ保留し、他の作業は止めない。
- 記録へは問いと答えを並べて書く（形は決めない。道具は記録から問いを拾わず、判断待ちかはダッシュボードだけで決まる）。
- **ダッシュボードの件の持ち主はタスク番号で決まり、件を置いたセッションでは決まらない**（[asking-user.md](asking-user.md)
  「反映の流れ」）。ページに起こされたのがどのセッションでも、送った・取り込み待ちの件は
  `python scripts/orchestrate.py pending-inbox --pending <書き出し>`でタスクごとの今の持ち主（担当・手動のセッション・
  司令塔）を出して回す。持ち主のいないタスクの件と起票案は、今の司令塔が引き取る。定期確認では`check`が
  最新の`pending-backup`から同じ並びを要対応として出す（書き出しより後の答えは見えないので、定期確認と「反映を頼む」の
  たびに書き出し直す。「管理のループ」節）。
  持ち主がクラウドの担当なら、`pending-inbox`が出す宛先へ`SendMessage`で届ける（「手元かクラウドか」節の5.）。
- 答えが出たら、ダッシュボードの`answer`へ書き、そのタスクのコミットで問いと答えを記録へ書く作業を担当のエージェントへ
  `SendMessage`で返す（会話の文脈を持っているので、新しく起動するより速い）。担当がいなければ
  司令塔のキューへ積む。記録へ書かれるまで、その件はダッシュボードに残る。閉じたタスクの問いの答えの移し方は
  [asking-user.md](asking-user.md)「記録だけを変えるコミットの例外」節。

## ユーザーへのお願いはダッシュボードに置く（問い・操作・改善案・起票案）

ユーザーへのお願い——判断を仰ぐ問い・ユーザーにしかできない操作（本番VMでのコマンド、取り消せない削除、Claude Codeの
設定の書き換え、外部サービスの画面での設定等）・改善を標準にしてよいかの承認——は、**頼んだその場で仕掛中のダッシュボードに
置く**。会話にだけ置かない（会話はログに流れ、ユーザーが全部を読み返さないと拾えない）。
置き場・1件の書き方・答えの記録への移し方・見方（ページ）は
[asking-user.md](asking-user.md)「仕掛中のダッシュボード」節が正本。答えは、そのタスクのコミットで記録（`Txxx.md`）へ移す
（記録だけのコミットは作らない。CLAUDE.md「1タスク=1コミット」）。

- **チャットでユーザーに判断を聞くときも、ダッシュボードの件から問いを作る**。そこに無いものは、先にダッシュボードへ置いて
  から聞く——チャットの一覧を記憶から作ると、出どころの違い（担当の報告から出た論点等）で漏れる。
- **担当は、ユーザー確認事項を報告に書くだけでなく、ダッシュボードに置く**（担当もArtifactDataで書ける）。
- **新しいタスクの起票案も同じ置き場に置く**。承認されたら司令塔が番号を振る（[asking-user.md](asking-user.md)
  「起票は承認制」）。担当は番号を振らない。
- **摩擦を必ず集める**: 担当の最終報告に「摩擦」の欄を置く（「最終報告」節）。司令塔は監査のたびに、その欄と自分の観測した
  摩擦を、直す（直したら、直した変更のコミットの本文に書く）か、改善案としてダッシュボードに置くかのどちらかにする。
  **控えは作らない**——摩擦・改善の材料を司令塔のキュー（`board todo`）や会話に「回の改善の材料」として溜めると、
  ユーザーから見えず、回の終わりまで判断されない。定期確認のたびに、それまでに観測した摩擦を改善案（`task`は
  その回の改善タスク。起きたこと・直す案・入れないと何が続くかを書く）としてダッシュボードへ置く。

## 環境

- **開発機が飽和しているときは計測しない**。性能の比較は、条件をそろえて交互に複数回
  取った中央値か、本番で取る。
- **遅いときは環境を先に疑う**。プロセス1つの起動に秒単位かかるなら、コードではなく
  ウイルス対策の走査・CPUの飽和を測る（`Get-Counter`でプロセス別のCPU使用率）。第三者製のウイルス対策が
  並行実行中にCPUの2〜4割を使い、`git status`が5倍遅くなった実測がある（[T1049](../records/tasks/T1049.md)）。
- `core.hooksPath`は相対パス（`.githooks`）にする。絶対パスだと全作業ツリーが本体の
  チェックアウトにあるフックを走らせ、作業ツリーで直したフックが効かない。

## 回の始まりと終わり

1回の並行実行（回）は、**目的で終わり、打ち切りの条件で切る**。時間や件数では終わらない。

- **始め**: 回の目的と、その目的のために片付けるタスク（母集団）を、ユーザーとのやり取りで決め、**状態の表に
  置く**（`board run start <名前>`・`board run goal <文>`・`board run add <Txxx>... from=<派生元>`）。
  **母集団には、それを進める途中で派生した課題も含める**——母集団のタスクの報告・監査・ユーザーの指摘から
  起票案として出し、承認されて番号が振られたもので、`from=`に派生元を持たせる。母集団の外のタスクは振り出さず、次の回の候補として振り出しの
  列に残す（`check`は母集団の外の振り出し待ちを拾わず、`board dispatch pop`は取り出さない）。
  **母集団が表に無い間は、`gate`が閉じ`board dispatch pop`も取り出さない**——母集団の外は振り出さない
  ので、母集団が無ければ振り出せるタスクが無い。目的と母集団を置くのが回の最初の操作になる。
  始めにダッシュボードを書き出して`pending-inbox`を回し、取り込み待ちの件（送った・答えが出た）を全件拾う（前の司令塔が
  区切った後に送られた件は、ほかに拾う者がいない）。
- **司令塔を区切るときは、ページからの受け取りも止める**（ダッシュボードのArtifactのコメント・反映の受け取りの
  watchを外す）。残すと、区切った古いセッションが送られた件を受け取り続け、次の司令塔へ届かない。
- **目的と母集団は「今どう動いているか」という状態であって、記録ではない**。母集団の各タスクが完了・
  トリガー待ち・残りのどれかは表に写さず、記録の`状態:`と台帳の行から読むたびに導く（`board run list`・
  `status`・`check`が出す）。
- **進め方の指示（待つ・続ける・順番を変える・母集団へ足す）は、記録にもコミットにもしない**。表で表す:
  待つは振り出し待ちの前提（`after`）、順番は優先度、足す・外すは`board run add`・`remove`、目的の
  言い直しは`board run goal`。記録へ書くと、指示のたびにコミットとCIが走り、記録が会話の写しで膨らみ、
  決定（タスクの中身への判断。記録の「ユーザー決定」）と見分けが付かなくなる。
- **回の記録（「回ごとに残す記録」）に書くのは、終わりのまとめ1回だけ**（下の「終わった状態」）。
  途中の経過は書かない。まとめも記録だけのコミットにせず、回の終わりに入れる変更のコミットに含める。
  規約・道具の変更が1つも無い回は、まとめを残さない（所要は各タスクのコミットにあり、摩擦は改善案としてダッシュボードに
  置かれ、変更が無いならすべて見送ったということ）。
- **終わりの条件**（どれか1つ）:
  1. 母集団がすべて、masterに入ったか、ユーザーの判断で先送り（見送り・トリガー待ち）になった。
     機械が導く: 台帳の着手の条件（`— トリガー:`）が母集団のタスクを名指ししているもの（例: 「T1078の
     完了」）は、先送りではなく回の中の順番なので残りに数える。母集団の外のタスクを名指す条件（例:
     「T204だけでは見通しが不足するという利用実績」）は、完了を待つのか利用実績を待つのかを文から
     決められないので先送りのまま数える——そのタスクを回で待つなら、母集団へ足す。`check`は当たったら出す。
  2. **打ち切り**: 司令塔のセッションが長くなりすぎた——セッションのトークン（文脈）の使用が85%を超えた。
     司令塔は自分の使用率を直接は読めないので、ユーザーが画面の表示で超えたと伝えたとき、または会話の
     自動要約（compact）が起きたときに超えたとみなす。
  3. **打ち切り**: 差し戻し・事故が重なった、またはユーザーから管理の異常を指摘され、ユーザーが回を切ると決めた。
- **終わりに入ったら、新しいタスクは振り出さない**。動いている担当は仕上げさせて監査する（同じタスクの
  差し戻しはしてよい）。終わりの条件1に当たっている間は`gate`が閉じ、`board dispatch pop`も取り出さない
  （司令塔が`check`を読み落としても振り出さない）。2・3は機械が判定できないので、司令塔が止める。
- **終わった状態**: 稼働中の担当が0本・監査済みでmasterに入っていないコミットが0件・印の残ったスロットが0個・
  仕掛中のダッシュボードの確認待ちをユーザーへ伝えた・回の記録へまとめを1回書いた（規約・道具の変更が無い回は書かない。目的と
  母集団は`board run list`の出力を写し、摩擦とそこから出た改善・所要の実績を添える）・次の回の目的の案を
  出した。
- **打ち切りで終わったときは、次の司令塔が最初に読む引き継ぎを状態の表に書く**（`board run handover <文>`。
  回に1つで、書き直すと置き換わる）。まとめには書かない——規約・道具の変更が無い回はまとめを残さないので、
  そこに置くと引き継ぎごと消える。母集団の残りは引き継ぎの文に写さない（表の母集団と記録・台帳から導ける）。
  次の回は新しい司令塔のセッションで`board run start`から始める。`start`は前の回の引き継ぎを、前の回の
  名前・目的・母集団と一緒に新しい回へ移し（引き継ぎの無い回からは何も移さない）、`board run list`・
  `status`・`check`が前の回の引き継ぎと、前の回の母集団の残り（記録と台帳から導く）を出す。次の司令塔は
  それを読んでから目的と母集団を決める。移した引き継ぎはその回の間残り、次の`start`で、その回に書いた
  引き継ぎ（あれば）に置き換わる。

## 改善の回し方

本規約は、1回の並行実行（司令塔が振り出してから全エージェントが終わるまで）ごとに実測で
直す。**実測の裏付けが無い変更は入れない**（CLAUDE.md「修正の原則」と同じ基準）。

### 回ごとに残す記録

回を始めるときに、その回の改善（規約・道具の直し）と記録を持つタスクを起票案として出し、承認を受けてから番号を振る
（[asking-user.md](asking-user.md)「起票は承認制」）。そのタスクは回の終わりに閉じる。**前の回の改善タスクへ積み足さない**
——回ごとの改善を1つのタスクへ積み足すと、完了条件を満たしても閉じる時機が来ず、終わりの無いタスクになる
（[T1049](../records/tasks/T1049.md)）。書くのは回の終わりの1回で、その回の改善（規約・道具の変更）のコミットに含める（記録だけの
コミットにしない）。規約・道具の変更が1つも無い回は残さない（所要は各タスクのコミットにあり、摩擦は改善案として
ダッシュボードに置かれ、変更が無いならすべて見送ったということ）。次を書く。数字は取り方も一緒に書く。

| 測るもの | 取り方 | 何を見るためか |
|---|---|---|
| 振り出したタスク・完了・保留の数 | 台帳と各エージェントの最終報告 | 振り出しの精度（保留が多いなら「振り出さない」基準が緩い） |
| ロックごとの待ち時間・保持時間・失敗回数 | `python scripts/lockrun.py --report --since <開始時刻>` | どの資源が詰まったか（待ちが大きいロックは分割・クラウドセッションへの切り出しの候補） |
| 監査で見つかった誤った主張 | 監査のたびに司令塔が控える | 監査の項目に何を足すか |
| 監査の待ち時間 | 報告のコミットの時刻と、監査の記録の`audit_done`の差 | 監査が門として全体を詰まらせていないか |
| ユーザー判断の待ち時間 | 保留が上がってから答えが返るまで | 保留の出し方（まとめ方・粒度） |
| CIの赤とその原因 | CIの履歴とログ | 不安定なテスト・並行pushによる破損の有無 |

### 直し方

1. 回の終わりに振り返り（`/task:retro`）を行い、本規約への変更案を出す。
2. 変更案ごとに、上の記録のどの数字が根拠かを書く。根拠が無いものは次の回で測る項目に
   回し、本規約へは入れない。
3. 当てたら、次の回で同じ数字が動いたかを見る。動かなければ変更を取り消すか、別の
   原因を探す。
