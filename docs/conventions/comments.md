# コードコメントの方針

コードコメント（docstringを含む）を書く・見直す・撤去するときに読む。

## ルール

**書いてよいコメント**: 今のコードを安全に変えるのに要る、非自明な制約・理由を**現在形の一文**で書いたもの（例:「このロックはXがYから並列に
呼ばれるため要る」「下限を0ではなくSTEPにするのは、0だとチェックOFF相当に化けて区間数が変わるため」）。実装を読めば分かることは書かない。

**書いてはいけないコメント**: 経緯——いつ・誰の指摘で・どのタスクで・以前は〜だった・実機や実測で〜だったため、という時系列の記述。経緯の置き場は
タスクの issue（[documentation.md](documentation.md)の用語集「経緯」）で、コードに書くと`docs/modules/*.md`との二重管理になり、タスク番号の指す先は
コードが変わっても追従しない。

## 判定基準（新しくコメントを書く/既存コメントを見直す/コードを撤去するとき）

**撤去のときは、コードと文を別の工程で判定する。** コードは参照が0かで決まるが、文は今も成り立つか・他に記録があるかでしか決まらない。
関数・ファイルを丸ごと消すときも、消す対象の文は下の判定木へ1件ずつ通してから消す。

**既定は削除。** 経緯の言い回し（「以前は」「タスク番号で」「ユーザー要望…」「実機で…」等）を含むコメントは、次の**両方**を満たすと確かめられたときだけ、
経緯の言い回しを落として残す。推測では残さない。

1. **そのコメントを消したら、今後の安全な変更が妨げられる非自明な制約・理由か？**（実装を読めば分かることは、理由があっても書かない）
   - No → 削除。経緯を残したいなら該当タスクの issue へ（既にそこにある背景と重ならないかを先に見る）。
   - Yes → 2へ。
2. **その制約・理由は、コード内コメント以外の場所にまだ無いか？**（`docs/modules/*.md`に同じ内容がある・型・assert・テストで既に強制されている、
   のどれにも当たらないか）。`docs/records/`は数えない——維持されない記録で、そこにしか無いなら、まだ書かれていないのと同じに扱う。
   - 当たる → 削除（対象のモジュールは`docs/modules/README.md`の索引で引ける）。
   - 当たらず、モジュール横断で再利用される知識 → `docs/modules/*.md`へ現在の事実として書いてから削除。
   - 当たらず、この1箇所だけの局所的な制約 → 経緯の言い回しだけ落として、現在形の一文で残す。

2では、コメントを型・assert・テストへ置き換えられないか（実行して壊れる形にできないか）も見る。できるなら、そちらを優先する。

## 残すと決めたものの行き先

判定木で「残す」になったら、中身の性質で置き場を決める。

| 中身の性質 | 行き先 | なぜそこか |
|---|---|---|
| **(e) 要件として採るかの判断が要るもの** | **タスクとして提案する**（置き場に issue を起こすと採否の問いが付く。既存のタスクに属するならその issue へ書く。[flow.md](flow.md)） | 仕様を採るかはコメントで決めない。先にここを分け、残りの4つは採ると決まっているものに使う |
| **(a) 罠（その機構が消えても再発する落とし穴）** | **コードのコメント** | 踏む場所はコード。**迷ったら残す側へ倒す**。その罠を置けるコードが1行も残っていないなら設計書へ |
| **(b) 根拠・実測値（なぜこの値なのか）** | **設計書** | 次にその値を動かす人が辿り着ける階層。コメントへ実測値を書くのは経緯に当たる |
| **(c) 現行の記述から落ちた含み** | **コードのコメント（残す）** | 否定形の知見（「◯◯では解決しない」）・弊害の形・条件・「安全側ではない」等の自己申告。コードはそれ自身の意図を全部は語らない |
| **(d) 一般則・規約になりうるもの** | **設計書**（`docs/conventions/*.md`・`docs/modules/*.md`） | 横断して効く取り決めは、コードに置くとそこにしか効かない |

(b)(d)を設計書へ置いたら、コードには残さない。値の近くに何か要るなら、どの文書のどの節を読むかを名指した1行だけにする（節の名前の無いポインタは
下の「中身の無いポインタ」に当たる）。

## 他所を写さない・代弁しない（docstringも同じ）

判定基準は[documentation.md](documentation.md)と同じ——**そのコメントを読むだけで正しいか誤りか判定できるか**。判定に他のファイルを開く必要がある
コメントは、他所が変わった瞬間に嘘になり、コンパイルもテストも通り続ける。

数え上げ・代弁・撤去済みの名指し・写しは、[documentation.md](documentation.md)「判定基準: その文書だけを読んで、正しさを検証できるか」の表の型が
そのまま当たる。コメントとdocstringには、ほかに次の型が出る。

| 型 | 例 | 代わりに書く |
|---|---|---|
| **存在しないものの説明** | 「タイルへ焼く3系統は手で書く定数を持たない」——そのファイルに無いものについて、なぜ無いかを書く | 書かない。読み手はファイル内を探して見つからず、どこかにあると思って探し続ける |
| **中身の無いポインタ** | 「詳細は`◯◯.py`のdocstring参照」「上のモジュールdocstring『△△』節を参照」 | 要る事実をその場に1行で書くか、消す |
| **定数の値の復唱** | `# TTL 900秒` の隣に `_TTL_SECONDS = 15 * 60` | 値ではなく、その値でなければならない理由を書く |
| **外部の数値の書き写し** | backend側が「frontendの`MAX_POLL_DURATION_MS=360秒`より十分長い」 | 数値を写さず、制約（「ポーリングの最大待機以上であること」）だけ書く |
| **責務の自己申告** | 「ここは組み立てだけを持つ」「DBに依存しない」 | 書かない。ファイルを開けば分かり、責務が増えても誰も直さない |
| **「次の1回」しか想定しない指示文** | 「3つ目の軸を追加する際は、このdictへ1エントリ足すだけでよい」 | 個数を言わずに足し方だけ書く |

**backendのコメントはfrontendの実装（ファイル・関数・state）を名指さない。** 書くのは境界の契約——APIのフィールド名・生成物の名前・受け取る側に
任せること——だけにする。同じファイルの外の定義を名指すときは「パス: 名前」の形で書く（[documentation.md](documentation.md)
「他のファイルの名前は「パス: 名前」で指す」）。

**「〜と同じ」と書きたくなったら、コメントではなく実装を1本へ寄せる。** 「`npa_honhyo.py`と同じ導き方」「`create()`と同じ」は、実体が2つあることを示す。

**同じ説明を1ファイル内で二重に書かない。** モジュールdocstring・定数コメント・関数docstringに同じ制約が載っていたら、1箇所へ寄せる。

**インフラ・スキーマの移行のタスクでは、移行前を前提にした説明を同じコミットで消す。** 個々のシンボルは実在するので死んだ参照として見つからず、
前提（接続方式・テーブル名・配置先）だけが消えている。

自分のモジュールの中で閉じた説明——引数の意味・不変条件・並行性の前提——は書いてよい。

## テストのdocstringも対象（判定基準）

この方針はテストコードにも当てる。判定基準2は、実装のコメント・docstringとテストのdocstringの間でも成り立つ——実装が既に言っていることをテストへ
写すと、実装を直した日にテスト側だけが古くなる。

**判定は1問**——その文は、対象の実装を読んでも書かれていないことか。「対象の実装」は、そのテストがimportしているapp配下のモジュール全部。

答えがYesのものは次の3つのどれかに落ちる。落ちないなら、Yesの判定を疑う。

| 型 | 中身 | 例 |
|---|---|---|
| **落ちたとき、利用者の側で何が起きるか** | 実装は「何をするか」しか語らない。表示・経路・所要時間がどう壊れるかは実装に無い | 「0点で塗ると、最良の色になってしまう」「解除済みの河川が出続ける」「無風の地点に矢印が出る」 |
| **このファイルが見ない範囲と、どのファイルが持つか** | テストの分担はテスト側にしか無い | 「取得・キャッシュは`test_wbgt_service.py`、地点の解決は`test_geo.py`（最寄りの点）が持つ」 |
| **テストの手法そのもの** | その確かめ方を選んだ理由。実装は知らない | 「刻みが0.1mなので、0.1m単位へ丸めてから比べる（二進小数の端数を持ち込まない）」「実装の規則をここで書き写して突き合わせない（恒真になる）」 |

**モジュールdocstringの宣言部分は重なってよい。** 「対象は何か」と「ここでは見ないもの・どのファイルが持つか」は宣言として要る（[testing.md](testing.md)）。
重なってよいのはこの2つだけで、本文は対象外。

書いてはいけない形:

- **実装のコメントの裏返し**——実装が「XはYのため」と書いているのを、テストが「YでないとXが壊れる」と書く
- **アサーションの言い換え**——`assert x is None`の上に「Noneを返す」
- **典拠の再掲**——外部仕様・公開値の出どころは実装が持つ。テストは突き合わせる値だけを持つ

**文面の類似は、読む順序にしか使えない。** docstringと実装の散文の重なりの大きい順に読むのはよいが、しきい値で捨てる判断はしない（類似度の分布に
切れ目が無く、どのしきい値も恣意的になる）。1文ずつ判定する。

## 実例（`RouteSettingsPanel.tsx`のコメントより）

- **① 設計書と重複 → 削除**: 軸をカテゴリで分けて表示しない理由を経緯で語るコメントは、`docs/modules/frontend/route-settings-and-results.md`が現在形で
  持っているので消す。手がかりが要るなら、その文書を名指す1行にする。
- **② 非自明な理由 → そのまま残す**: 経緯を書かないことは、理由を書かないことではない。

  ```ts
  // 下限は0ではなくWEIGHT_STEPにする——0まで下げるとその軸がチェックOFF相当（weight>0判定）に
  // 化け、ドラッグ中に帯の区間数が変わってしまうため、ドラッグでは「チェックを外す」操作を
  // 兼ねさせない（0まで下げたい場合は詳細ポップオーバーかチェックボックス自体を使う）。
  ```

- **③ 日記的記述 → 技術的判断だけ残す**: いつ・どう頼まれたかを消し、今の振る舞いだけを書く。

  ```ts
  // 境界を1つ動かすと、その両隣の2軸間でだけ重みが移動する（他の軸・合計自体は変わらない）。
  ```

## 適用範囲・実行タイミング

- 新しく書く・変えるコメントは、すぐにこの方針に従う。
- 既存コードに残る経緯コメントは一括では消さず、モジュール単位のタスクで消す（着手するモジュールごとに issue を起こす）。
- 判定基準2の設計書との重複は機械では見分けられないため、対象ファイルが属するモジュールの`docs/modules/*.md`を先に読んでから読み比べる
  （[docs/modules/README.md](../modules/README.md)「着手の前に読む」）。

## 守り方

この方針を語彙で機械的に強制する仕組みは持たない。禁止語でコメント行を走査する検知器は、言い換えを取りこぼし、正当な記述を誤検知するため、
検知器の要件（どの文脈でも正しいと保証できる事実だけを見る。`scripts/review_checks.py`冒頭）を満たさない。

守るのは書く人と、周期レビュー（`/review`）の「整合性」の観点。例外は他のファイル・APIの名指しで、「パス: 名前」の形の名前と、テストのファイル名・
最上位のディレクトリから書いたパス・APIのパスが実在するかを`backend/tests/structure/test_named_references.py`が見る（読む範囲は
[documentation.md](documentation.md)「他のファイルの名前は「パス: 名前」で指す」）。
