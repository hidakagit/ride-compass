# テスト方針

この文書は、**書く前の判定**（単体で確かめるか・そのテストは要るか・起こし直しの手順・消すべき型）と、**書き方**
（実行時間・置き場・パターン）を持つ。検査とテストを手元・CI・開発機でどう回すかは[testing-operations.md](testing-operations.md)が持つ。

**新しいテストは、下のパターンに従い、実行時間の増加を最小限に抑える。**

## 基本原則

1. **ループで実I/O（HTTPリクエスト・新規DB接続）を繰り返さない。** 上限回数の検証は、境界の直前までを実I/O無しで埋め、
   境界の1〜2回だけ実際に実行する。
2. **新規リソース（DB接続・テスト環境）の構築は、テストスイート全体で使い回せないか検討する。** テスト関数ごとに作る
   コストは、テストの数に比例して積み重なる。
3. **速度の最適化は、テストが確かめる内容を変えない範囲で行う。** 境界の実地の検証は残し、その手前の準備だけを削る。
4. **結果はpassedの件数だけを見ない。警告も結果の一部として扱う。**

## 確かめる高さ

**振る舞いは、モジュールの公開の入口で確かめる。** 途中の手順（内部の関数の呼ばれ方・中間の値・呼ぶ順番）を
確かめるテストは実装の構造の写しで、作り替えのたびに落ちる。

- **内部名（`_`で始まる名前）へ直接入らない。** 計算を直接確かめたい・入口から条件を作りにくいなら、その計算を公開名に
  してから（`_`を外す、または公開の小さな部品へ切り出す）その入口で確かめる。内部名へ入る・途中を差し替える、で済ませない。
- **テストを読み手に数えて公開してよいのは、次の3つだけ。** モジュールの外に本番の読み手が無くても、この3つはテストが
  読むことを公開の理由にしてよい（周期レビューの「参照0の公開シンボル」も同じに数える）。
  - (a) 入力を値で受けて判断を持つ計算（関数・クラス。モジュールの状態を読み書きしない）
  - (b) テストが本物の値から境界の入力を組み立てる定数（`count = ID_CHUNK_SIZE + 1` 等）
  - (c) テストが差し替えるプロセス境界の置き場（ディスクのパス・OSのファイル。`infrastructure/road_network_store.py: ROOT`・
    `infrastructure/container_memory.py: CGROUP_MEMORY_MAX`等）。置き場を引数や設定から受ける形にはしない（本番がいつも
    同じ置き場を渡すだけの、テストのための口になる）。3つ以上のテストが同じ置き場を差し替えるなら、差し替えは共有の
    fixture（`backend/tests/conftest.py: road_network_root`等）が持つ
- **可変の状態（キャッシュ・接続・スケジューラ・時刻や世代の記録・集計）は、テストのために公開しない。**
  テストが空にしたい・差し替えたい状態は、上から順に直す。
  1. 大域に持たない——持ち主のオブジェクトへ寄せ、依存として注入する（例: GSI の整備区域外の記憶は DI の
     工場が持つ。`api/dependencies.py: get_gsi_tile_client`）
  2. 本番の寿命の口（閉じる・作り直す等、本番が呼ぶもの）を使う。無ければ本番が要る口として作り、足場もそれを使う
  3. どちらもできないものだけ、理由を定義の隣に書いた例外にする
- **差し替えてよいのはプロセス境界**（網・ディスク・時計・外部サービス）、契約の狭い層の境目（依存として注入される
  Service等。自分のDB（Repository）は除く。例外は「フェイクの数は、実装の外向き参照の写し」の「自分のDB（Repository）は
  差し替えない」）、本番の正本を持つ宣言のデータ（「テストは、テストだけで成立させる」）**だけ**。
  自分のdomainの関数（走行モデル・格子の生成等）と自分の定数は**差し替えずに本物を通す**
  （関数・クラスは`backend/tests/structure/test_domain_not_replaced.py`が落とす）。上限値のような定数を差し替えて
  境界を作らず、本物の定数から入力を組み立てる。
- **差し替えた相手への呼び出しを確かめてよいのは、状態を変える呼び出し（送る・書く）だけ。** 読むだけの相手は応答を
  差し替えるだけにし、呼ばれたか・何回・どの引数で、を確かめない。外部サービスへの問い合わせのうち、回数そのものが
  相手との約束（回数制限・利用の上限・課金）に効くものは、送る側に数える。確かめる引数も、そのテストの関心事に絞る。
- **呼ばれたかを記録するために自分の関数を包まない**（本物へ委ねる記録用の包みも含む）。「作る前に断る」のような順序の
  約束が入口の結果に現れないなら、テストでは確かめず、理由を実装の隣のコメントが持つ。入口の結果に現れる形
  （断ったときに外部サービスへ問い合わせない等）があるなら、そちらで確かめる。

### frontend

同じ原則を、画面の語へ置き直したもの。

**入口**は、対象の種類で決まる。内部のstate・フックの呼ばれ方・子へ渡した関数の同一性は見ない。

| 対象 | 入力 | 確かめる出力 |
|---|---|---|
| 部品（`*.tsx`） | props・利用者の操作（`userEvent`） | 描いたもの（role・名前・表示文言・`aria-*`の状態）と、呼ばれたコールバックの引数 |
| フック（`use*.ts`） | 引数（`renderHook`の`rerender`で変える）・戻り値の関数を呼ぶこと | 戻り値と、backendへ送ったもの（状態を変える要求だけ。読むだけの要求は応答を与えるだけで、送ったかを見ない） |
| ページ（`app/**/page.tsx`） | 部品と同じ | 部品と同じ。ある機能の変化が別の機能の振る舞いを変える受け渡しを見る（[page-composition.md](../modules/frontend/page-composition.md)） |
| 純関数（`lib/`等） | 引数 | 戻り値 |

**画面の操作は、利用者の1つの流れを1本のテストにしてよい**（開く→選ぶ→送る、のような流れ。途中で何度確かめてもよい）。
流れを段ごとに別のテストへ割らない。backendは1つのテストで1つの振る舞いを確かめる。

**差し替えてよいのは次の境界だけ。** 自前のフック・`lib/`の関数・定数は、表の境界（環境変数の読み取り口・ファイルを
落とす関数等）を除いて、差し替えずに本物を通す。

| 境界 | 差し替え方 |
|---|---|
| backendとの通信 | 網の層で差し替える（msw）。backendを呼ぶ口のモジュール（`services/*Api.ts`・`features/**/*Api.ts`）も、通信を包む自前のフック（`hooks/useAxisCatalog.ts: useAxisCatalog`等）も差し替えず、本物を通す（口が応答をどう読むかを使う側のテストに残すため）。取得のキャッシュは`vitest.setup.ts`がテストごとに空にする。応答は`frontend/src/testing/backendServer.ts`の手引きで経路ごとに与え、応答を与えていない要求はテストを落とす。口それぞれは、網の層で確かめる自分のテストを持つ |
| 時計 | `vi.useFakeTimers()`で進める。待ち時間の定数や、待つフック（`hooks/useDebouncedValue.ts: useDebouncedValue`）を差し替えない |
| 環境変数 | 値を**使う側**は、読み取り口のモジュール（`lib/tileBaseUrl.ts: tileBaseUrl`・`lib/adminBasicAuth.ts: adminBasicAuthCredentials`等）を`vi.mock`して値を固定する。`process.env`はテストファイルをまたいで共有されるので、使う側のテストで立てない。立ててよいのは読み取り口そのもののテストだけ（パターン7） |
| テスト環境に無いブラウザの機能 | WebGL（`maplibre-gl`）・レイアウトの実寸（`embla-carousel-*`）等。`maplibre-gl`は`frontend/src/testing/maplibre.ts`の代役へ差し替え、地図の部品は本物を描く（代役は受けたものを記録するだけで、出来事と押した所の地物はテストが起こす）。テスト環境が持つもの（`localStorage`・`navigator`の値等）は、それを読むフックを差し替えず、環境に値を置く。`localStorage`が投げる場面は`window`のゲッター（`vi.spyOn(window, "localStorage", "get")`）を差し替えて作る（happy-domの`localStorage`の`getItem`/`setItem`へ張ったスパイは`vi.restoreAllMocks()`で戻らない） |
| ファイルを落とす | GPXの書き出し等、ブラウザにファイルを保存させる関数 |
| 子の部品 | 下の条件を満たすときだけ |

**子の部品は、既定では本物を描く。** 差し替えてよいのは、子の中身がテスト環境に無い境界（上の表の「テスト環境に無い
ブラウザの機能」）を要し、それを境界の側で差し替えられないときだけ。差し替えたら、親のテストで見るのは受け渡し（親の
状態がどの値として子へ渡るか、子から上がった操作で親の何が変わるか）だけで、差し替えた子の表示は確かめない（子のテストが持つ）。

代役は受け取ったpropsを記録し、`children`を描くだけにする。子の振る舞いを真似ない。差し替えたものと、それで見えなく
なるものは、ファイル冒頭の「ここで見ないもの」に書く。

## 単体で確かめるかを、コードの種類で先に決める

**1本ずつ3問へ通す前に、対象のコードがどの種類かで、単体で確かめるかを決める。** 軸は2つで、計算・業務の判断を持つか
（込み入っているか、外れると利用者への約束が崩れるか）と、つなぐ相手が多いか（呼ぶ他のモジュール・外部の数）である。

| 種類 | 例 | 確かめ方 |
|---|---|---|
| 判断を持ち、相手が少ない | domainの計算・分類・検証 | 単体で確かめる。下の3問と起こし直しは主にここへ当てる |
| 判断が無く、相手も少ない | 受け取った値を詰め替えて渡すだけの関数 | 確かめない。使う側のテストが通す（3問の1問目の「1行の委譲」） |
| 判断が無く、相手が多い（つなぎ役） | 相手を順に呼ぶだけのServiceやフック・子を並べるだけの部品・ルーター | 単体では書かない。上の入口（APIの経路・ページ）のテストで受け渡しを少し通す（3問の3問目の「別の高さで同じ判断を見ている」） |
| 判断を持ち、相手も多い | 判断と結線が1つの関数・部品に混ざったもの | テストの前に実装を分け、判断を相手の少ない部品へ出す（[書きたくなったテストが、実装の歪みを教える](#書きたくなったテストが実装の歪みを教える)） |

つなぎ役を単体で確かめると、相手を全部差し替えることになり、テストは呼ぶ順番と引数の写しになる。

## そのテストは要るか（3問を順に）

**新しく書くとき・既存を見直すときは、この3問を使う。** 先に出た問いで決まったらそこで終わりで、「念のため残す」は
しない。起こし直しで**旧版にしか無い**ものが出たときは、先に[マージの4分類](#既存テストを直さず実装から起こし直す)を
通してからここへ来る。

1. **構造が守っているか。守っているなら書かない。**
   - **既に守られている → 消す。** 恒真式・1行の委譲（受け取った props・属性・参照をそのまま中へ渡す、呼び出し側の
     ハンドラを同じ名前の受け口へそのまま渡す（`onFocus`を中の`onFocus`へ）、値に単位を付けてstyleへ渡す
     （`` `${height}px` ``））・宣言の書き写し・型が保証していること（Pydanticの`Field`制約・`Literal`）・フレームワークの
     設定や結線・宣言から作った足場へ同じ宣言を当てる形・テストの足場に対する不変条件（見分け方は「消すべきテストの型」）。
     自前の要素にハンドラを結ぶ形（✕を押すと`onClose`）は委譲ではない——どの操作でどの知らせを上げるかは部品の判断なので、
     知らせ1つにつき1本残す。
   - **守れるが守っていない → 実装を直してから消す。** 型で通らなくする（`Field(min_length=1)`・`allow_inf_nan=False`）、
     片方をもう片方から導く、並びそのもので順序を表す（直し方は
     [書きたくなったテストが、実装の歪みを教える](#書きたくなったテストが実装の歪みを教える)の表）。
   - **守れない → 2問目へ。** ただし**構造で表せない理由を1行で言えること**。言えないならまだ「守れる」側である
     （例: 停止要因の種別と較正値の対応は、`tuning.py`が`traffic.py`をimportすると循環するため構造で保証できない）。

   **「構造が守っている」と判断したら、消してからカバレッジで確かめる。** 未到達の行が出たら、守っていたのは構造ではなく
   **コード**である（検証関数の早期return・既定値を組み立てる分岐）。
2. **外部影響があるか。判定は「落ちるとき、何が壊れるか言えるか」。** その答えはモジュールの外——利用者の画面・
   他モジュール・配信される値・保存されるデータ——についてでなければならない（「この定数がこの値であること」には答えが無く、
   「この境界を1つずらすと、まだ明るい時間帯に街灯の軸が効き始める」には答えがある）。
   - **言えない → 消す。**
   - 答えを実装のコメントが既に持っているなら、テストのdocstringへ書き写さない（判定基準は[comments.md](comments.md)
     「テストのdocstringも対象（判定基準）」）。
3. **他に同じことを見ているものがあるか。**
   - **別のモジュールの責務 → 移す。** その影響の持ち主が別のモジュールなら、判定はそちらにある（テスト対象がファイル名の
     指すモジュールでないなら、それだけで移す理由になる）。移した先で同じことを見ているなら、移さず消す。
   - **同じファイルの別のテストが同じ実装要素を見ている → 狭い方を消す。** 広い入力で見ているテストがあるなら、その
     部分集合は足していない（`a→b`の順序は`a→b→c`の連鎖が見ている。委譲しているだけの関数の欠損検査は、委譲先の検査が
     見ている）。広い方が別の操作で狭い方を含むこともある（どのテストもメニューを押して開いてから確かめるなら、
     「押すまでメニューを出さない」は別に書かない）。
   - **別の高さで同じ判断を見ている → 低い方に残す。** APIの経路のテストとdomainのテストが同じ判断の入力違いを並べて
     いるなら、判断はdomainのテストに残し、経路のテストは受け渡し（判断の結果が応答のどこへ出るか）だけを見る。ただし
     **経路ごとに受け渡しを1本は残す**（設定・結線の壊れは低い層のテストでは拾えない）。E2Eとvitestの分担はパターン4の
     「何を対象にするか」が持つ。
   - **どれも無い → 残す。** 他のテストと似ていても残す。

**残すと決めたものも、同じ判断の入力違いは1つのテストの表の行にする。** 検証が断る形の1つずつ・分類の1つずつ・境界の
両側を、別のテストにしない。表の行は判断の違う入力だけを置き（境界は両側の2つ）、同じ側の値を足さない。

- **両側は、書かれた比べ方の両側である。** `!== 0`なら「0」と「0でない」の2行。負の値の行は、本番で負が来て、扱いが
  違うときだけ足す。
- **既定を持つ読み出しも、書かれた比べ方である。** `.get(k)`・`?.`は「キーが無い」と「ある」、`??`は「null・undefined」と
  「それ以外」、`or`は偽と真を両側に持つ。1つの行が、通る比べ方の片側をいくつも兼ねてよい。`entry.get("status") == X`なら、
  「キーが無い」の行は`.get`の無い側と`==`の偽の側を兼ね、「値がnull」の行は`.get`のある側・`==`の偽の側なので、`X`でない
  値の行が別にあれば同じ側である。既定を持たない読み出し（`entry["k"]`・`obj.k`）は比べ方ではない。
- **最小・最大で寄せる所には、境界ちょうどの行を書かない。** `<=`と`<`の違いが結果に出ない。
- **同じ判断の関数を何か所で呼ぶときは、判断の両側は関数のテストに置く。** 呼ぶ所ごとには、寄せていることを示す1行だけにする。

**消す・まとめる前に、消すテストが落ちる実装の壊れ方を1つ書き、残す側がそれで落ちるかを見る。** どの経路で消す・まとめる
テストにも当てる（1問目の既に守られている・2問目の言えない・3問目の移した先が見ている・狭い方を消す・低い方に残す・表の行へ
まとめる）。行と分岐のカバレッジは、残す側が同じ行を通るだけで結果を見ていなくても変わらないので、代わりにならない。
下の2・3は手で組み立てず、`scripts/break_tests.py`で流す（壊れ方の一覧を1件ずつ実装へ当てて残す側のテストのファイルだけを
回し、落ちたテストの名前を出して戻す。frontend も backend も同じ一覧で、`--ref`で前の版のテストも並べて回す。一覧の形と
使い方は道具の先頭）。

1. 消す・まとめるテスト1本ごとに、それが落ちる実装の壊れ方を1つ書く（比べ方を1つ変える・境界を1つずらす・値を定数へ変える）。
   - 書けないなら、そのテストは何も見ていない（1問目の恒真式）ので、確かめずに消す。
   - 宣言の書き写しは、宣言の値を変えることを壊れ方に数えないので、書けないものとして確かめずに消す。並び・値が利用者に
     見える振る舞いを決める宣言は書き写しではない（「消すべきテストの型」）ので、並びを入れ替える・値を変える壊れ方を当てる。
   - 約束ごと消したテスト——見ていた約束が Pull Request の課題の「消した約束」か「変えた約束」の前の側に当たり、見ていた
     実装を同じ差分で消したもの——も、書けないものとして確かめずに消す。実装が後の版に残る（約束だけを変えた）テストは
     これに当たらず、残った実装に壊れ方を書く。
   - 同じ側の行——通る書かれた比べ方のどれでも、残す側の入力と同じ側にある行（「同じ側の値を足さない」で消す・まとめる行と、
     3問目の「狭い方を消す」で消す行のうち入力が広い方と同じ側にあるもの）——には、書かれた比べ方の片側をまるごと変える
     壊れ方だけを当てる: 向きを反対にする・境界を1つずらす・比べ方を外して常に片側の結果にする・値を残す行の答えと違う
     定数へ変える。同じ側の中で答えを分ける壊れ方——別の比べ方へ置き換える（`in`を`==`へ・`Number.isFinite`を
     `Number.isNaN`へ）・書かれていない比べ方を足す（`if a:`を`if a and not b:`へ）・書かれた値の並びから1つ外す
     （`IN (…)`の値）・書かれていない既定値を足す（`?? 0`）・定数を残す行の答えに合わせる——は当てない（表は書かれた
     比べ方を両側で留めるもので、別の比べ方を全部は留めない）。
2. 実装のその行を一時に変え、残す側（まとめた先の表・含むとした広い方・移した先・低い方）のテストのファイルだけを回して、
   次のどれかになることを見る。
   - (a) 残す側が落ちる。
   - (b) その壊れ方は作れない: 型・制約・宣言の検査（tsc・mypy・DB の制約・構造のテスト）が止める。止める検査を壊した版で
     回し、落ちることを見る（テストのファイルなら残す側に並べる。tsc・mypy は壊した版で打ち、3 と同じく戻す）。
     宣言を壊して `tests/conftest.py` の import で止まった件は、`break_tests.py` が「テストの前に止まった（(b)）」と止まり方の
     1行で出すので、その行を 4 の出力として書く。型の計算を自前で書いたもの（パスの文字列から引数の型を導く等）は、
     その計算を崩しても tsc が通るので (b) に数えない。
   - (c) 前の版の消すテストも、その壊れ方で落ちない（`--ref`で並べて回す）: 消すテストは何も見ていなかった。

   どれにもならなければ、残す側が見ていないので、残す側を直す（表の補助が見る値を足す・行を足す）か、消さずに残す。
3. 変えた行を編集で戻し、`git diff --exit-code -- <実装のファイル>` で戻ったことを見てから次へ進む。
4. Pull Request の本文の検証に、消した・まとめたテスト1本につき1行の表で、壊れ方と結果（(a) 落ちたテストの名前・(b) 止めた
   検査とその出力・(c) 前の版でも落ちなかったこと・壊れ方が書けない理由（恒真式・宣言の書き写し・約束ごと消した））を書く。
   - 約束ごと消した行は、当たる課題の約束の行と、消した実装を書き、変えた約束なら新しい約束を見るテストの名前も書く。消した
     実装は、名前を持つもの（関数・定数・印）を丸ごと消したならその名前を書く。持ち主（関数・部品・ハンドラ）が残り、その中の
     一部（呼び出し・分岐・行）だけを消したなら、持ち主（ファイルと、名前か画面の位置）と、消した一部が使っていた名前を書く
     （例: `UsageGuide.tsx` の ✕ のボタンの `onClick` から消した `onEndRef.current()` の呼び出し）。
   - 1本は、前の版にあって後の版に無いテスト（関数・`it`）と、表から消した行で、表の行を持つテストを丸ごと消したときは中の
     表の行ごとに1本と数える（テストの実行が数える本数と同じ）。行の数はその数と同じにする。
   - 同じ側の行は、どの書かれた比べ方（実装のファイルとその比べ方）の同じ側かも書く。

**消す・まとめる・題名を変えるテストを名指す設計書の行は、同じ差分で直す。** `scripts/review_checks.py docs`はリンクが
解決するかしか見ないので、手を入れたテストのファイル名を `docs/` で grep し（例: `grep -rn 'legends.test' docs/modules`）、
そのテストが確かめる・固定すると書いた行があれば、保証の今の置き場（残す側のテストとその題名・型・源泉の宣言）に合わせて書き直す。

**「対象へ届いているか」は測れる。** `pytest --cov=app --cov-context=test`でテスト単位の文脈を取り、対象モジュールの行を
1つも実行していないテストを機械的に出す（静的な名前解析は`self._helper`のような属性アクセスを数えられない）。ただし
**定数・型宣言を見るテストは対象の行を実行しない**——SQL文字列の定数・規則表・Pydanticの`Field`制約・`Protocol`の宣言は
import時に評価されるため、この信号だけでは判定できない。出たものを3問へ通す。

**本番のデータそのものに対する不変条件**（「全材料が説明文を持つ」「参考点の値が有限」）も1問目を通る——型で通らなく
すれば検査は要らない。型でも導出でも保証できないものだけが、そのデータを宣言しているモジュールのテストへ残る（その場合は
差し替えない節を分け、ファイル冒頭の宣言にそう書く）。

## 既存テストを直さず、実装から起こし直す

**作り替え・構造の変更で落ちたときは、落ちた箇所を直して済ませない。** 1ファイルずつ、**毎回一から書く**（ファイルごと
置き換える。部分編集しない）。振る舞いを変えたときは、その振る舞いを見ている該当のテストを直す（どちらに当たるかは
「テストが落ちたときの直し方」の②で決める）。既存のテストを1本ずつ[3問](#そのテストは要るか3問を順に)へ通して消す・
表の行へまとめる見直しは、起こし直しではなく部分の直しとして行ってよい。足す・書き換えるなら、起こし直しの側で行う。

**始める前に、そのファイルが単体で確かめる種類かを決める**（[単体で確かめるかを、コードの種類で先に決める](#単体で確かめるかをコードの種類で先に決める)）。
つなぎ役なら起こし直さない——そのテストのファイルを消し、受け渡しは上の入口のテストへ寄せる（上の入口のテストが既に
通しているなら足さない）。判断と結線が混ざったものなら、先に実装を分ける（テストの起こし直しとは別の作業）。

1. **既存テストを開かずに**、**公開の入口から見える振る舞い**を箇条書きで列挙する（どの入力の組で何が返り、何が外へ出るか。
   エラー経路・表示文言・disabled条件を落とさない）。
   - **期待値の出どころは仕様**（`docs/modules/*.md`・APIの契約・画面の約束）で、先にそこから列挙する。仕様が書いていない
     振る舞いは、実装から入口の言葉へ言い直して列挙する。**仕様と実装が食い違ったら、期待値を実装へ合わせず問いに回す**
     （「要確認の出し方」）。
   - **列挙の単位は分岐ではなく振る舞いである。** 実装は、振る舞いの見落としを探す手がかりとして読む: `if`の両側、同じ判断を
     2度実装している経路（スカラーと配列・PythonとSQL）、モジュールが持つデータの不変条件、比較（`<`・`>=`）の境界ちょうどの値、
     画面部品が子の部品へ何を渡すか。`if`にも分岐カバレッジにも現れない判断——`and`/`or`の各項・numpyのベクトル化された条件
     （`np.where`・`np.clip`等）・SQL文字列の中の条件・`dict.get`の既定値・剰余や`min`/`max`での寄せ・`Field(ge=…)`の宣言した
     範囲・ルーターの宣言（認証・`response_model`）等——も、入口からどう見えるかへ言い直して列挙する。入口から見えないものは
     列挙しない。
   - **列挙は見落としを探すためのもので、列挙したものを全部書くのではない。**
2. 列挙した振る舞いを1つずつ[3問](#そのテストは要るか3問を順に)へ通し、残ったものだけを**新しいファイルとして**書き起こす
   （同じ判断の入力違いは表の行にまとめる）。**他のモジュールの実装を読まないと分からないことは書かない。**
3. **カバレッジで見落としを探す**（1ファイル分を書き終えてから当てる。書きながら測らない）。対象モジュールへ分岐カバレッジを
   当て、届いていない行・分岐を出す。
   - **母集団は「同名のテストファイル」ではない。** 先に `grep -rln --include='*.py' '<モジュール名>' tests` で、対象を読む
     テストのファイルを出す。起こし直す前の値も同じ母集団で、旧版を**実行して**取る（中身を読むのは手順4からで、手順1〜3では
     開かない）。backendは`backend/scripts/audit_test_rewrite.py`（「書き終えたら、テストが触る外のシンボルを数える」）、
     frontendは`frontend/scripts/audit-test-rewrite.mjs <実装>`で測り、手で組み立てない（前の値は`--ref origin/master`）。
   - **grepの母集団は間接的な消費者を落とす。** 1行だけ孤立して見えたら、`--cov-context=test`でどのテストが通しているかを
     引いてから「無検査」と判断する。
   - **下がってよい。下がった箇所ごとに、なぜ見なくてよいかを1行書く**（入口から見えない・到達できない・構造が守っている等）。
     **書けなければ見落としとして扱い、列挙をやり直す。**
   - **分岐カバレッジは「どこを見ていないか」の検出器であって、母集団ではない。** 未到達を埋める前に3問を通す
     （`if cached is not None`の両側のように、1問目が「既に守られている→消す」と判定するものが多い）。**埋めなかった未到達は、
     なぜ埋めないかを1行ずつ残す。**
   - **埋める前に、その入力が本番で作れるかを確かめる**（パターン8）。**対象ファイルが作る値**（`_bin_count`が
     `[1, MAX_TIME_BINS]`しか返さない等）は実装を読んで必ず確かめ、**境界の向こうから来る値**（他モジュールの戻り値・DBの行）は、
     確かめるなら向こうの契約を1関数だけ読み、何を何のために読んだかを残す。
   - **作れない組を使っていたら、テストを消すのではなく作れる組へ置き換える。** 作れない組でしか通らない分岐は実装の
     到達不可コードなので、入力を直したうえで撤去する。
4. 既存テストのテスト名を並べ、新旧を突き合わせる。**旧版を開いてよい目的は「今のソースからは導けない過去の事情」だけ**
   である——回帰（過去のバグを刺したもの）と、実データ由来の事情。**構造を写すために開かない。**

   **旧版を物差しにしない。**
   - 2つのファイルを diff しない
   - 「新版は◯◯を落とした」と言わない（導出がそう決めた）
   - 旧版にあったからという理由で足さない
   - 一致率で新版の出来を語らない
   - 「今あるものから無駄を省く」形にしない
5. 両方向を判定する。
   - **新版にしか無い**: 実装の判断が無検査だった。手順2で3問を通してあるので、そのまま残す。
   - **旧版にしか無い**: 下の4分類を通す。
6. **埋め残しを作らない。** 旧版にあって新版に無いものは必ずどれかへ振り分ける。

**起こし直しの成果は、判定の件数で報告する。** 4分類それぞれの件数を書き、とくに**「列挙漏れ」の件数**（自分の導出の不足）と、
**「責務外」「重複」で消した件数**（削減の実測値）を出す。あわせてテスト本数・行数・行カバレッジ・分岐カバレッジ・seams 数
を**前後の値つき**で書く。行数は手順3の母集団のテストのファイルの
`git diff --numstat`の増減で、起こし直しの物差しはこれ1つにする（変更全体の増減は[fixing.md](fixing.md)「報告と段取り」の
`review_checks.py change`が出す別の数）。

**起こし直したあとのテストの行数は、前の行数を超えない。** 手順3の母集団のテストのファイルについて、起こし直しのコミットの
`git diff --numstat`の足した行から消した行を引いた値が0以下であることを、完了の条件にする。超えたら、増えた分のテストごとに
守るもの（落ちたら何が壊れるか）を1行ずつ書き、確かめる担当がそれで判断する。行数を減らすために、補助の関数・ループ・共有の
準備へ畳まない——減らすのは本数と確かめる対象で、読みやすさのための少しの重複は残してよい。

**マージで「足す」ことになったら、それは起こし直しが不完全だった印である。** 旧版にしか無いものは、次のどれかでしかない。

| 判定 | 見分け方 | すること |
|---|---|---|
| **重複** | 同じ実装要素を、別の入力・別の言い方で見ているだけ（分岐の同じ側・同じ早期return） | 足さない。「対比のため」「代表を変えて」は重複の言い換えである |
| **責務外** | 実在のid・実データ・他モジュールの宣言に依っている | 足さない。持ち主のファイルへ移すか、消す |
| **列挙漏れ** | 実装の別要素なのに新版に無い（`if`の反対側・2つ目の経路・型でも導出でも保証できないデータそのものの不変条件） | **列挙をやり直す**。1件を足して済ませない——同じ数え方をした他の要素も漏れている。データの不変条件は、テストを足す前に型で通らなくできないかを見る |
| **上のどれとも言い切れない** | 同じ要素の別の入力に見えるが、重複と断じる根拠が無い（過去のバグを刺した回帰がここへ来る） | 「そのテストは要るか」の3問を通す |

**旧版にしか無いものを「残す」と決めたら、なぜ自分の導出から漏れたのかを、次に導出する人が読む場所へ1行足す。** 実装から
導けるはずだったなら実装のdocstringへ、仕様に書かれていなかったなら`docs/modules/*.md`へ書く。

**回帰と重複を一律のルールで分けようとしない。** 両者は同じ見た目（同じ実装要素を、別の入力で見ている）で、違いは実装に
無い事実だけなので、印を付ける取り決めは作らず、表の「言い切れない」として3問へ送る。回帰はそこの3問目で残る。

**3問を当ててよいのは、起こし直し版に元からある検査と、表で「言い切れない」へ落ちたものだけである。** **起こし直した版に
無い要素は、旧版から戻さない**——`git log -S`で初出を引き、自分の起こし直しのコミットなら自分の誤削除なので戻してよく、
それ以前なら列挙漏れとして**列挙をやり直し、実装から自分で導く**。

**「残す」「移す」と決めた場でテストを書き換えない。** 移すなら移すだけ、残すならそのまま残す。書き直したくなったら、
起こし直しの側（列挙）でやる。

判定と理由はタスクの issue へ書く（Pull Request の本文の検証にも、消した・まとめたテストごとの判定を書く）。**3問のどこで
決まったかまで書く。**

**旧版の構造をそのまま引き受けない。** 「旧版の形のほうが強い」と思ったときは、その強さが何に由来するかを言う。実在のid・
実データに由来するなら、それは強さではなく責務外である。

**テストが落ちたら、まず自分の前提を疑う。** 実装の欠陥だと決める前に、書いた性質が本当に成り立つかを確かめる（平面の直感で
書いた性質は球面で成り立たない: 大円の逆方位は±180度にならない、タイルの範囲は隣と辺を共有するので自分の範囲を渡しても
1枚には戻らない）。

## テストの足場で、本来のNGを覆わない

**テストは要るものを自分で宣言し、無ければ落ちる。** 足場（共通のフィクスチャ・セットアップ・共通のフェイク）が既定を配ったり
失敗を吸ったりすると、落ちるべきテストが緑になる。

| 形 | 何が覆われるか | 代わりに |
|---|---|---|
| 既定を自動で入れる足場（autouseのフィクスチャ・vitestの`setupFiles`） | 足場の中身に依っているテストが、依っていると言わないまま通る | 要るテストが引数（`usefixtures`）で取る |
| 例外を握りつぶす`try`/`catch` | 解釈できない応答・走査できない要素が検査の対象から黙って抜ける | 失敗してよい操作だけを囲み、それ以外の失敗は失敗として記録する |
| 環境が無いときのスキップ（`pytest.skip`・`skipif`・`test.skip`） | DBに繋がらないとファイルのテストが1件も走らないまま緑になる | 落とす。外すかどうかは実行する側がマーカーで選ぶ（`-m "not postgis"`） |
| 落ちたテストを再試行する設定（Playwright の `retries`） | 再試行で通ったテストは flaky と出るだけで、実行は既定で成功で終わる（公式の文書 TestConfig の `failOnFlakyTests`） | 再試行しない（`retries: 0`）。不安定に落ちたら、落ちた原因を直す |
| 警告を無視する設定 | 同じ種類の別の警告まで消える | 「警告は既定でエラー」の条件を満たすものだけ |
| 呼び出しの内容を見ずに値を返すフェイク（`lambda *a: 値`・任意の属性を受ける器） | 本物に合わない引数・必須項目の欠けた組み立てを通す | `tests/bound_fake.py: bound(本物, フェイク)`で本物の署名に当てる。組み立てて返す型は本物を使う |

**autouseで配ってよいのは、何も与えないものだけ**（何を「何も与えない」とするかと判定は
`backend/tests/structure/test_autouse_fixtures_give_nothing.py`が持つ）。

**片付けは、本番のコードが既に持つ操作だけで書く**（持ち主のオブジェクトをテストごとに作り直して注入する・本番の寿命の口
（閉じる・作り直す）を呼ぶ等）。片付けのためにappへ口（テスト専用の初期化関数・引数）を足さず、可変の状態を公開名にもしない
（設計原則 構造仕様15）。本番の操作だけで片付けられない大域状態は、その状態を大域に持っている実装を直す（直す順は
[確かめる高さ](#確かめる高さ)の可変の状態の箇条）。既存の口の撤去は、それぞれのモジュールを触るときに行う。

**宣言させる範囲は、外して落ちたテストだけではない。** 外しても通るが、主張がその前提に立つテストも宣言する（「誤った認証情報を
拒む」は認証情報が未設定でも拒まれて通り、「公開軸だけを返す」は軸が空なら空どうしを比べて通る）。

**覆いを外して落ちたら、どちらの欠陥かを分ける。** 前提を宣言していなかっただけならテストに宣言させる。本物の型が拒む入力を
足場が通していた等、**実装の判断が問われるもの**は直さずに要確認として出す（「要確認の出し方」）。

**覆いではないもの**: 並行実行のための隔離（作業ツリーごとのDB・一時ディレクトリ）、時刻の固定、テスト環境が作れない本番の
規則を本番と同じに置くもの（`vitest.setup.ts`の`pointer-events-auto`の規則。Tailwindが本番で作る規則を置くだけで、前提を
足さない）、呼ばれないことを確かめるフェイク・例外を投げるだけのフェイク、`await`されないPromiseの未処理扱いを避ける`catch`
（後で同じPromiseを検査する）、E2Eの共通応答のうち画面まで進める導線（パターン4「共通フィクスチャに置くもの」）。

## 黙って縮退する分岐は、取り除いて実験する

**「この分岐は要るか」をコードを読んで決めない。** 母集団を機械で導き、1件ずつ取り除いてテストを流す。

母集団（AST）: **例外を送出せずに縮退した結果を返す分岐**——空を返す`return`・`.get(`・`x or y`・`except: pass`。変異は縮退の
道を外す（`x or y`→`x`、`d.get(k)`→`d[k]`、`except: pass`→`except: raise`、空の`return`→`raise`）。

- **落ちる** → その縮退はテストが見ている。仕分け終わり
- **通る** → 誰も見ていない。**要確認**へ送る

**コメントの語（「通常は到達しない」「念のため」「防御的」）でgrepしない。** 自己申告している分岐しか拾えない。

**「テストが見ていない」は「消すべき」を意味しない。** 実験が出すのは未検査の一覧までで、消すか要件かの判定には別の事実が要る。
**要確認を群にまとめるときは、その縮退が起きる実データ上の条件を1つ挙げてからまとめる**——挙げられないものは別の群にする
（例: 一方通行で逆方向Edgeが無いのは正常な事実で、欠陥と同じ群に入れない）。

### 要確認の出し方

**欠陥と判定する前に、対比先が本当に何を言っているかを読む。**「兄弟の扱いと違う」「docstring・設計書と実装が食い違う」
「引数が結果に効かない」は、対比先（宣言の隣のコメント・docstringが対で読めと指す関数）が現状を選んだ理由をその場に
書いていることがある。

問いの形と届け方は[flow.md](flow.md)「問い」が正本。テストの欠陥の要確認で判断材料に足すのは次の2つだけ。

- **設計書・コード・テストが、それぞれ何を主張しているか。** 利用者への約束と場面の次に、3行の表で、**同じ粒度・実装の語を
  使わずに**書く（「コードはこう実装されている」ではなく「コードはこう主張している」）。食い違いが1対2なのか2対1なのかが
  見えるようにする。
- **選択肢は2つ。消すか、残すか。** 添えるのは**消したとき外で何が起きるか**と**その道を通る呼び出し元の件数**だけ。

## 消すべきテストの型

| 型 | 見分け方 | なぜ有害か |
|---|---|---|
| **正しく直すと落ちるテスト** | 実行せずに、SQL文字列やパスへ特定の名前が含まれることをアサートする | 壊れたコードで通り、直したコードで落ちる |
| **空振りの検知器** | 「Xが作る形を検証する」と書きながらXを呼ばず、期待値を手で書いている | 検知したいドリフトを検知できない |
| **宣言の書き写し** | 定数・モデルの既定値・レジストリの中身をテスト側へ再掲して突き合わせる。ただし宣言の並び・値が利用者に見える振る舞い（地図に描く順・既定で選ばれる項目）を決めているなら、書き写しではなく振る舞いの確かめである | 同じリテラルを2箇所へ置いているだけ |
| **恒真式** | `set(versions) == set(TILE_SHAPES)`（同じ内包表記の結果を同じ定数と比べる） | どんな実装でも通る |
| **効いていない除外リスト** | ガードに付けた除外の一覧 | 効いているか誰も測らないので、存在しないファイル名や、先行条件で既に弾かれるものが残る |
| **消したものを見張るアサーション** | `assert not cleared`のように、呼ばれないことを確かめる | 消えたことは検査ではなく、変更そのものが示す |
| **等価テスト** | 新旧2実装の出力一致 | どちらが正しいかを誰も保証していない |
| **カバレッジの水増し** | 「落ちるとき何が壊れるか」に答えられない。`MIN <= MAX`・`isinstance(x, int)`・定数への等値 | 実装の判断を1つも通らない |
| **実装の規則の再実装** | 実装が「名称に『特別警報』を含むか」で決めているのを、テストも同じ規則で期待値を作る | どんな実装でも通る |
| **型が保証していることの検査** | 戻り値が3値の`Literal`なのに「3値のいずれかへ落ちる」を確かめる | 型検査が既に保証している |
| **本番に生えたテスト専用の口の検査** | テスト専用の初期化関数（`reset_*_for_testing()`の類）が状態を空にすることを確かめる | 本番から到達しないものを守っている |
| **宣言から作った足場へ宣言を当てる** | 宣言された全クラスについて`em.lc_{key}`が読めることを、`lc_{key}`という列を自分で用意して確かめる。宣言された語彙の全件が`= ANY(:語彙)`で真になることを確かめる | 期待値も足場も同じ宣言から出ているため恒真になる。**振る舞いがidごとに違わないなら、性質ごとに1件で足りる**。「宣言した列・値が実在するか」は別の問いで、実テーブル・実カタログへ通して確かめる |
| **テストのフィクスチャに対する不変条件** | `AXIS_DEFINITIONS`の全軸が排他チェックを通ることを確かめる（テスト中の中身は注入したフィクスチャで、本番の軸はDBにある） | 守っているのはテストの足場である。**その宣言がテスト中に差し替わるなら、全件の不変条件は書けない**。足場そのものを対象と名乗る足場のテスト（パターン5）はこれに当たらない |

## 残すべきテストの型（起こし直しで取り込む）

これは**旧版から取り込むかどうか**の判定で、「そのテストは要るか」の3問とは別の問いである。3問を通った検査のうち、**仕様と
実装を読んで復元できないもの**だけが取り込む対象になる。

| 型 | 見分け方 | 例 |
|---|---|---|
| **外部の権威との突き合わせ** | 期待値の出どころが公開値・配布物・実測で、コードのどこにも無い | 市民薄明の終了時刻をNOAA準拠の公開値と±3分で比べる。事故統計の本票CSVの実データ1行目で度分秒の切り出しを確かめる。巡航20km/hから逆算した出力が実際の自転車の範囲（約55W）に入る |
| **過去のバグを刺した回帰** | 「この入力で落ちた」という事実 | 由来はタスクの issue が持つ（テストのdocstringへ経緯は書かない）。消すかどうかは3問で決める |

**仕様と実装から復元できるものは取り込まない。**

**「意図的に外した値」は残す理由にならない。** 除外を値で名指しして「入っていない」と確かめるのは宣言の書き写しの否定形で、
除外の根拠（実測）をテストは持っていない。除外の理由は設計書（`docs/modules/*.md`）が持ち（実測値は[comments.md](comments.md)
「残すと決めたものの行き先」の (b) で設計書へ置く。宣言の隣に要るなら、その節を名指す1行だけ）、テストは書かない。

## 性質で確かめる（hypothesis）

**任意の入力で成り立つ性質が実装か公開の仕様から言える計算は、例を並べる代わりに性質で書く**（backendはhypothesisの`@given`）。
向くのは幾何・座標変換・補間のような、連続した入力の範囲を持つ純関数である。期待値に別の道で求めた答え（最寄りを全点と
比べた答え・逆変換・同じ道の逆向きの行）を使えるときに強い。

**性質で書いたら、その性質が覆う例は書かない。** 性質の主張が成り立つが乱数がまず引かない入力——境界ちょうどの値（`<=`と`<`の
違い）・過去のバグを刺した入力——は、例のテストにせず、性質のテストに`@example`で付ける。例のテストで残すのは、性質の主張では
答えが決まらないもの——呼び名の対応のような離散の約束・外部の権威との突き合わせ——だけである。

- **性質は外への影響で選ぶ**（「そのテストは要るか」の2問目）。「落ちたら何が壊れるか」を言えない性質（値域が0〜360度に
  収まる等。使う側が360で畳んで読むなら何も壊れない）は書かない。
- **入力の範囲は本番の範囲で作る**（パターン8）。全世界の乱数では起きにくい場面（地点が格子より細かく散らばって最寄りが
  入れ替わる等）は、その場面を作る範囲を別に与える。
- **期待値を実装と同じ規則で作らない**（「消すべきテストの型」の実装の規則の再実装）。比べる相手は、より遅いが素直な計算か、
  公開の仕様である。
- **見つかった入力は、実装の欠陥か自分の前提の誤りかを分けてから直す**（「テストが落ちたら、まず自分の前提を疑う」）。前提の
  誤りで、実装に書かれていない事実（計算の分解能等）だったなら、実装のdocstringへ足してからテストの許容を直す。
- 例の数は既定（100）のまま回す。例ごとの壁時計の締め切りは`tests/conftest.py`が外している。
- **CIは見つけた失敗の例を残さない。** hypothesisは環境変数`CI`があると`ci`の設定（乱数を固定し、例の保存先を持たない）を
  既定で効かせ、`tests/conftest.py`の設定はそれを引き継ぐ。手元では作業ツリーの`.hypothesis/`に残り、次の実行が先に試す。
  CIで落ちた例は、出力の`@reproduce_failure`をテストへ一時的に付けて手元で再現し、残すなら`@example`にする。

## テストは、テストだけで成立させる

本番の正本（材料カタログ・軸定義）や生成物を読むテストは、そちらが変わると意味が変わる。**性質だけを表す架空の名前**
（`num_a`・`bool_a`・`cat_a`・`axis_a`）を使い、モジュール大域の辞書ごと差し替える。「この材料が実在すること」がテストの
関心なのかを毎回問う——たいていは「数値の材料が1つあること」で足りる。

**ファイルの冒頭で責務を宣言する。** モジュールdocstringに「対象は何か」と**「ここでは見ないもの・どのファイルが持つか」**を
書く。書けないなら責務が定まっていない。

```python
"""`domain/axis_definitions.py`——軸の宣言と、その評価。

ここで見ないもの:
- 軸が軸を読むときの並べ替え・軸の集合の評価 → `test_axis_hierarchy.py`
- 地図表示（ramp）の導出 → `test_axis_display.py`

**材料カタログの中身には踏み込まない。** どの材料がどの一次属性に属するかはカタログ側の
話なので、差し替えて与える。
"""
```

**大きな足場が要るのは設計の症状**である。テストごとに同じ偽の世界を建て直しているなら、実装が大域から読んでいることを疑う
（直す順は「確かめる高さ」の可変の状態の箇条）。

## 書き終えたら、テストが触る外のシンボルを数える

テストが対象モジュール経由で触るシンボル（`engine.X`の`X`）を集め、**対象ファイルの定義**か**他モジュールからのimport**かに
分ける。import側は1件ずつ「差し替えのseamか、責務外か」を言う。

**テストファイルから直接importしてよい`app.*`は、対象モジュールと、対象の公開シグネチャが要求する型だけ。** 他モジュールの
**関数・サービス・例外・定数**は触らない（テストがそのモジュールの振る舞いへ結びつく）。例外は、本番の状態を本番の口で作るもの
（回数制限の上限まで埋める`infrastructure/rate_limiter.py: check_rate_limit`。パターン1）で、経路のテストが境界の直前までを
実I/O無しで埋めるために、その口だけを読む。入力を組み立てるのに要る値は、対象が受け取る形の値として書くか、対象の名前空間から
読む。差し替えが要るのは[確かめる高さ](#確かめる高さ)が許すものだけで、そのときは対象の名前空間で差し替える。

**対象が引数に取る型の中身の型（ノード・辺等）は、偽の型を作らず実物で作る。** 作るコストの無い型（frozen dataclass等）の偽物は、
実物が変われば黙ってずれる（設計原則 構造仕様16「境界は、破られたときに落ちる形で表現する」）。

**「実装へ入らないテスト」の検出に静的解析を使わない**（`setattr(engine, ...)`の形・ヘルパ経由を数え落とす）。
`--cov-context=test`で、対象モジュールの行を1行も実行しないテストを引く。

**この数え上げは手で組み立てない。** `backend/scripts/audit_test_rewrite.py`が、実装の変更・`app.*`直接import・`<対象>.X`の内訳・
seams 数・実装へ1行も入らないテスト・そのテストだけが通す行が0行のテスト・行/分岐カバレッジ・テストファイルごとの項目・`test_`の
関数・行（空行とコメントを除く）の数・テストからしか使われない公開の名前の候補を出す（テストは起こし直しの手順3の母集団を並べて
渡す。出すものの詳細と数え方の穴は道具の先頭と出力）。**自分で書いたものにも当てる。**

- `njit`を通る対象は`--no-jit`を付ける。
- `postgis`の印のテストは、テスト用DBのサーバーへ繋がるときだけ含めて測る。繋がらなければ外し、外したことと理由を出力の先頭に出す。
- 起こし直す前の値は`--ref origin/master`を付けて同じ実行で取る。母集団は前と後を合わせて渡す（改名は前の名と後の名を両方渡す）。
  前の版のテスト名は出さない。
- 出力は候補であって判定ではない: 属性を変数で指す差し替えは内訳に入らず行番号と候補の名前だけが出る。宣言のデータだけを読む
  テストは「実装へ入らない」に出る。

## 書きたくなったテストが、実装の歪みを教える

**「この検査を書かないと守れない」と思ったら、まず実装が構造で保証できないかを問う。** できるなら実装を直し、検査は消す。

| 書きたくなった検査 | 何が歪んでいるか | 直し方 |
|---|---|---|
| 2つの独立した宣言の関係（「Aの全要素がBにある」） | 片方がもう片方から導かれていない | **導く** |
| 戻り値だけでは2つの意味を区別できない（0が「宣言が0」か「未知」か分からない） | 既定値へ倒す設計が、正常と異常を同じ値にしている | 宣言の側を見る検査でしのがず、**呼び出し側が区別できる形**にできないかを問う |
| どんな入力でも通らない分岐がある | 起こり得ない状態への防御が残っている | **消す** |
| 常に空のフィールドを「空であること」で確かめたくなる | 公開契約に、配信されない値が乗っている | フィールドごと外す |
| 条件を作るのに他モジュールの実装へ寄りかかる（実在の材料を選んでrampにする等） | そのモジュールが他の判断へ強く結びついている | **差し替えて与える**。差し替えられないなら、依存の向きを疑う |
| 同じ偽の世界をテストごとに建て直す | 実装が大域から読んでいる | 大域に持たず、持ち主のオブジェクトへ寄せて注入する（直す順は「確かめる高さ」の可変の状態の箇条） |

**カバレッジは目標にしない。** 使うのは2つの場面だけ——書く**前**に穴を見つけるときと、起こし直しの**前後**で下がった箇所を出し、
1箇所ずつ理由を書くとき（下げないことを条件にしない。起こし直しの手順3）。**100%にならない行が残ったら、まずそれが到達できる
状態かを問う**——到達できないなら、埋めるのではなく消す。

## フェイクの数は、実装の外向き参照の写し

**「フェイク」と呼んでいるものは3種類ある。混ぜて数えない。**

| 種別 | 判断 |
|---|---|
| **プロセス境界**（網・ディスク・時計・Redis・ログ） | **必ず差し替える** |
| **層の境目**（Service・Repository・Engine・Client） | 外部（Client・他のシステム）は差し替えてよい。**自分のDB（Repository）は差し替えない**（下の段落）。Service・Engineは**契約が狭いときだけ**（差し替え先が5メソッド10引数なら、それは層ではなく癒着） |
| **自分が持つデータ型・その他** | **差し替えない。実物を作る** |

**自分のDB（Repository）は差し替えない。** DBはこのアプリだけが読み書きし、SQLと表の形は実装の一部なので、SQLは実DBで確かめる
（パターン2）。Repositoryを差し替えてよいのは、その上の層に固有の判断があり、それを確かめるときだけで、そのときもRepositoryへの
呼び出しは確かめない（読むだけの相手。「確かめる高さ」の差し替えの箇条）。

**実物は組み立ての関数で作り、組み立ての関数は、そのテストが関心を持つ値だけを引数に取って他を妥当な既定値で埋める。** ただし
**判定に効く値は必ず引数で渡す**（既定値に隠すと、何が結果を決めたかが見えない。「テストの足場で、本来のNGを覆わない」の
「宣言させる範囲」）。

プロセス境界の代役は境界の種類ぶんしか増えないので共有する。増え続けるのは自分が持つデータ型の代役で、これは実物で作る。

**差し替えが増えたらテストを疑う前に実装を数える。** フェイクは、対象モジュールが外へ持つ参照（実装がimportする`app.*`
モジュール）を映したものである。

- **2つ目以降のフェイクを書きたくなったら、対象の外向き参照を数える。** 4本以上なら、テストの書き方ではなく**そのモジュールが
  何を読んでいるか**を先に問う
- **起こし直しの報告に seams 数（`monkeypatch.setattr`の第2引数の文字列のユニーク数）を入れる**（本数・行数・カバレッジと並べて）。
  増えていたら、増えたのはテストではなく結合である
- **共有フェイクへ出すのは3箇所目から**（CLAUDE.md「同じ操作を3回やったら仕組み化を検討する」）。3箇所に増えたら、寄せる前に、
  その外部が本当に3つのモジュールから読まれるべきかを1度問う。共有の足場があるのに写した定義・差し替え・組み立ては、構造テスト
  （`backend/tests/structure/test_scaffold_copies.py`・`frontend/src/structure/scaffoldCopies.test.ts`）が落とす

**この歯止めを検知器にしない**（実装を検査対象にする検知器になる。[fixing.md](fixing.md)「検知器を足す条件は厳しい」）。数えるのは
起こし直しの報告のときで、判断は人が行う。

**起こし直しのあとで共有フェイクを見直すときは、その共有物が無ければ書かれなかったテストが混ざっていないかも見る。**

## テストと実装のずれを疑う印

- **ファイル名が指すモジュールを検証していない。**
- **テストにだけ残った語彙。** 実装から消えた機構の名前がフィクスチャ名・テスト名に残る。実装側と突き合わせれば機械的に出せる。
- **テストのために本番コードへ生えた宣言。** 消費者が`backend/tests/`だけの公開名のうち、「確かめる高さ」の (a)〜(c) に当たらない
  もの。

## 警告は既定でエラー

警告は1つでも出たらテストを落とす（出ているだけの警告は誰も読まない）。

| | 落とす仕組み | 直せない警告を許す場所 |
|---|---|---|
| backend | `backend/pytest.ini`の`filterwarnings`が`error`から始まる | 同じ`filterwarnings`へ`ignore:<メッセージの先頭>:<警告の種類>`の1行 |
| frontend | `frontend/vitest.setup.ts`が`console.warn`・`console.error`（Reactの警告もここへ届く）を受け、出したテストを落とす（vitestには出力の警告で落とす設定が無い。`onConsoleLog`は出力を隠すかを決めるだけ） | `vitest.setup.ts: ALLOWED_WARNINGS`へ文の正規表現の1件 |

直せない／直すべきでない警告（依存ライブラリが自分の内部で出すもの等）だけを、**1件ずつ文で名指して、理由と外せる条件を添えて
許す**。依存を上げて不要になったら消す。

- 絞り込みはメッセージまで書く。`ignore::DeprecationWarning`や「`console.error`を全部」のように種類だけで黙らせない
- テストの中で警告を出すこと自体を確かめるテスト（ログの口のテスト等）は、`vi.spyOn(console, ...)`に`mockImplementation`を
  付けて出力を止め、中身を確かめる（`vitest.setup.ts`はスパイを見分けないので、止めずに張っただけのスパイではそのテストが落ちる）
- 依存ライブラリを上げただけでCIが赤くなりうる。それを知るためにエラーにしている
- vitestはAIの作業役の下（環境変数で見分ける）では既定のレポーターを`minimal`にし、通ったテストの出力を出さない。警告はテストの
  失敗の文に載るので、それで読む（出力を全部見たいときは`--reporter=default --silent=false`）

## テストが落ちたときの直し方（①〜⑥）

落ちた状態から緑へ戻すまでの手順。全体を流し直しながら1件ずつ直さない。

1. **失敗した対象を最小コストで洗い出す。** 直前の実行ログが手元にあるなら**それを読む**。列挙のためにテストを流し直さない。
   **失敗した操作を、出力をもう一度見るためだけに再実行しない。** 出力が読めない（文字化け・打ち切り・スクロールで流れた）なら、
   **判定している側を直接見る**——フックならそのスクリプトを読む、CIなら失敗したジョブのログを取る、検査なら検査単体を対象を
   絞って走らせる。
2. **落とした変更がどれかを決める。** 変更は、作り替え（利用者から見た振る舞いを変えない）・新しい機能・バグ直し・振る舞いの
   変更のどれかである。**既存のテストを直してよいのは、振る舞いを変えたときだけ**（誤った振る舞いを固定していたテストが落ちた
   バグ直しも、ここに数える）。作り替えで落ちたテストは実装の構造に結びついていた印なので、直さずに、入口の高さへ書き直す側
   （「既存テストを直さず、実装から起こし直す」）へ回す。新しい機能で既存のテストが落ちたら、既存の振る舞いを変えていないかを
   問い、変えていたなら振る舞いの変更に数える。**小さな実装の変更でテストに大きな変更が要ったら、テストが多すぎるか、実装に
   結びつきすぎている印である。**
3. **失敗の原因を洗い出す。** テスト名や件数ではなく、`AssertionError`の中身・例外の種類・実際に渡された値まで取る（①の出力は
   「何が落ちたか」しか言わない）。**落ちたテストを、何に敏感だったかで分ける**: 口（呼び方・引数の形）の変更、準備や確かめに
   使った他の振る舞いの変更、共有のデータ（足場・フィクスチャの中身）の変更、時計や外部の変化。落ちたテストに共通するものを見て、
   1本ずつ直さず、その結びつきを1回で断つ（組み立ての関数へ寄せる・前提を引数で宣言させる・時計を固定する等）。
4. **同根のものだけをまとめて直す。** 束ねられないのは③が足りていない合図で、③へ戻る。
5. **④で触った範囲だけを検証する。** テストと**静的検査の両方**をその範囲へ当てる。
6. ④⑤を繰り返す。全部解けたらpushし、全体はCIで見る（[testing-operations.md](testing-operations.md)「手元の検査の回し方」）。

**手を動かす前に現物を読む。** 書いた当時の文字列で照合しない（整形が入っていると置換が黙って空振りする）。複数ファイルを直す
ときは、1ファイルの失敗が残りを巻き添えにしない形（ファイルごとに独立）で当て、**どれが変わってどれが変わらなかったかを出力に
残す**。

### 収束しなかったら、理由を書く

2周しても同じ失敗が残るなら、原因は手順ではなく③にある。**何を見落としたかをタスクの issue へ書いてから**3周目に入る。

## 挙動を変えるなら、テストを先に書く

**挙動を変えるタスクは、テストを先に追加/更新してから実装する。** 実装のあとに書くと、書いたコードが通ることだけを確かめる
テストになりやすい。

## わざと壊すのは、テストの中で

検知器・ガード・テストが効いていることは、わざと壊した入力で落ちることを見て確かめる（[fixing.md](fixing.md)「直し方」）。
**壊すのはテストの中の入力で、ソースやビルドを書き換えない。** 例外は、消す・まとめるテストの壊れ方で残す側が落ちるかを見るとき
（「そのテストは要るか（3問を順に）」）で、確かめる相手がテストなので実装の1行を一時に変える。戻し方もそちらが持つ。

- **画面の検知器**は、壊れた状態をテストの中で作る: playwrightなら`page.addStyleTag`で崩れたスタイルを足す・モックの応答を
  差し替える、vitestなら渡す入力（props・フェイクの応答）を差し替える。
- **道具（`scripts/`）の仕組み**は、一時的なgitリポジトリと入力の差し替え（網・時計・書き出したファイル）で、入口から確かめる。
- **数分かかる本物の処理**（本番ビルド・本物の`npm ci`・E2Eの一式）は、最終確認の1回までにする。

## ソースを読む検査は、専用ディレクトリへ置く

置き場を決める軸は、**そのテストが何を読むか**である。

- **リポジトリのソースをデータとして読む**（ASTやテキストとして走査し、コードは動かさない）——素の`BaseModel`を使っていないか、
  設定の項目に読み手がいるか、未定義のCSSトークンを参照していないか等。これを下の専用ディレクトリへ置く
- **コードを動かして確かめる**——横断的な不変条件を守るものでも、対象を実際に動かすなら普通のテストであり、**対象の隣へ置く**
  （例: スタイル作り直しの前後でレイヤー状態が戻るかは、MapViewを動かして見るので`features/map/MapView/`側に置く）

前者のうち、CIが既に流している静的な検査（backendの`ruff.toml`・`.importlinter`・`mypy.ini`、frontendのESLint・knip）の設定で
表せて、許可リストが要らないものは、テストにせずその設定へ置く（例: web層が`app.batch`をモジュール直下でimportしない →
`backend/ruff.toml`の`TID253`）。テストにするのは、自前でソースを読む（ASTの走査・一覧からの母集団）ことが要るものと、許可リストが
要るもの（ruffの`per-file-ignores`と`# noqa`は、古くなっても落ちない）だけである。`scripts/review_checks.py`の検知器へは置かない
（[fixing.md](fixing.md)「検知器を足す条件は厳しい」）。

| 対象 | 置き場 |
|---|---|
| backend | `backend/tests/structure/` |
| frontend | `frontend/src/structure/` |

**普通のテストと混ぜない**（何が機械的に守られているかを1か所で見られるようにする）。

書き方は他のテストと同じで、**母集団をソースから導く**（ファイルを手で名指ししない）。許可リストが要るなら、**その列挙が古く
なったときにテスト自身が落ちる**ようにする（載っているのに実態が無い側も違反にする。`test_redis_skeleton.py`参照）。

## パターン1: レート制限テスト → rate_limiterを直接埋める

```python
from app.infrastructure import rate_limiter

def test_xxx_is_rate_limited_per_client():
    ...
    for _ in range(settings.xxx_rate_limit_per_minute - 1):
        rate_limiter.check_rate_limit("xxx:testclient", settings.xxx_rate_limit_per_minute)
    assert client.get(...).status_code == 200  # 境界の1回だけ実HTTP
    response = client.get(...)
    assert response.status_code == 429
```

`TestClient`の接続元`client_id`は常に`"testclient"`（`app/api/rate_limit.py: client_id`）。キーは`f"{prefix}:{client_id(request)}"`で、
prefixは各routerが`enforce_rate_limit`へ渡すものに合わせる。

**テストは回数0から始まる。** 回数制限が読む時計は`conftest.py`が止めた時計へ替えてあり、autouseの`monotonic_clock`がテストごとに
1窓より長く進めて前のテストの回数を窓の外へ出す。回数の記録（`rate_limiter`の内部）は消し込まない・差し替えない。窓の境界を
確かめるテストは`monotonic_clock`を引数に取って進める（`test_rate_limiter.py`）。

例: test_region_routes.py, test_weather_route.py, test_basemap_routes.py, test_routes_generate.py

## パターン2: PostGIS統合テスト（road_graph_session）→ ファイル単位でエンジン・イベントループを共有

`conftest.py: road_graph_session`/`conftest.py: road_graph_repository`はテストファイル（モジュール）単位で1本のDB接続・イベントループを
使い回す（新規DB接続の確立に1〜2秒かかるため）。

新しいテストファイルでこれらのフィクスチャを使う場合:

1. ファイル冒頭に `pytestmark = pytest.mark.asyncio(loop_scope="module")` を付ける（同期テストが同じファイルに混在していても影響しない）。
2. ファイル内で自前のasync fixtureを定義してroad_graph_session/road_graph_repositoryに依存させる場合は、その自前fixtureにも明示的に
   `loop_scope="module"`を付ける（`@pytest_asyncio.fixture(loop_scope="module")`）。省略すると`pytest.ini`の
   `asyncio_default_fixture_loop_scope`（関数ごとのループ）で動き、`RuntimeError: ... attached to a different loop`で落ちる。
3. 素の`@pytest.fixture`でasync fixtureを書かない。`@pytest_asyncio.fixture`を明示的に使う（前者は`loop_scope`を受け取れない）。
4. ファイル単位で共有するのは接続とスキーマまでにする。**テストが書き換える行（生データ・派生の表）は、関数スコープのfixtureで
   各テストの前に作り直す。** 共有した行を書き換えて後片付けで戻す形にしない（実行順は毎回混ぜている。
   [testing-operations.md](testing-operations.md)「実行順をばらす」）。

例: test_material_values.py（road_graph_sessionを直接使う）, test_derive_topology.py（自前のmodule fixtureを重ねる）

**xdist_group="postgis"（必須）**: CIは`-n auto --dist loadgroup`でDB以外のテストを並列化している。road_graph_session系フィクスチャを
使うテスト（ファイルまたは個別テスト関数）には必ず`pytest.mark.xdist_group(name="postgis")`と`pytest.mark.postgis`の両方を付け、
`pytestmark`は
`pytestmark = [pytest.mark.asyncio(loop_scope="module"), pytest.mark.xdist_group(name="postgis"), pytest.mark.postgis]`
の形にする。xdist_groupが無いと、同じテストDBへ複数workerが同時接続し、他ファイルのTRUNCATEでテストデータが消える。`postgis`の印
（`pytest.ini`の`markers`に登録済み）は、DBの無い環境でDBを使うテストを外す唯一の仕組みである（`road_graph_engine`はDBに繋がらないと
スキップせずに落とす）。

## パターン3: フロントエンドのテスト環境 → DOM不要ならnode環境

DOM（render/renderHook/window/document等）を使わない純ロジックのテストファイルは、ファイル先頭へ`// @vitest-environment node`
docblockを付けてnode環境で動かす（DOM環境の構築コストはテストファイルごとにかかる）。設定の`environmentMatchGlobs`はVitest 4に
無いので使わない。既定のDOM環境はhappy-domで、個別ファイルで`// @vitest-environment jsdom`を付ければjsdomで動く。

新規テストファイルがservices/lib配下やMap内の式・フィルタ関数のようにDOMに触れない場合、このdocblockの追加を検討する（省略しても
happy-domのままで壊れない）。判断は、そのテストファイルが`render`/`renderHook`/`screen`/`document`/`window`のいずれかを使っているかで
行い、**importしている実装側の関数が内部で`document.createElement`等を呼んでいないかも確かめる**（例: 地図の記号の絵（`sdfIcon.ts`）が
`document.createElement("canvas")`を使う）。

## パターン4: フロントエンドのE2E（Playwright）→ 実機でしか出ないものだけを見る

### 何を対象にするか

E2Eは、**実ブラウザ・本番ビルドでしか出ず、かつ機械で判定できるもの**を確かめる場である。単体テスト（vitest・happy-dom）は実寸を
返さず、CSSのカスケードを解かず、地図は代役（Worker・描画・スタイル検証を持たない）なので、次の3つの観点はE2Eでしか見られない。

| 観点 | 例 | 何で判定するか |
|---|---|---|
| 1. 収まる・押せる | ヘッダーが幅からはみ出す、凡例の行がセルからはみ出す、下部のバーの下に潜り込んで押せない | `scrollWidth`/`clientWidth`・`boundingBox()`の実寸 |
| 2. ブラウザ・ランタイムの実挙動 | ブラウザ既定の動作（暗黙のフォーム送信・タッチ操作の割り当て）、実イベントが地図を通って届くか、MapLibreのWorker・描画・スタイル検証・`idle` | 実イベントを起こした結果・画素・コンソール |
| 3. カスケードの勝ち負け | `@layer`の外に置いたリセットがTailwindのユーティリティを潰す、モジュールCSSの詳細度が部品の既定サイズを踏む | `getComputedStyle`の計算後の値 |

**対象にしないもの**:

- **読みやすさ・色**（配色が凡例と合っているか、縁取りが見えるか）。人が見る
  （[frontend-design-system.md](../modules/frontend/frontend-design-system.md)「実機確認の方法」）。
- **DOMの状態・ロジックだけの主張**（押すと何が出るか・候補が何件並ぶか・`aria-pressed`が反転するか）。vitestで確かめる。

**合否の基準が、決まった規則として既にあるものだけを置く**（ページが横にスクロールしない・地図の外でピンチしてもページが拡大しない、
のように機械がそのまま判定できるもの）。どの状態・見え方が正しいかを実機の画面を見て判断する必要があるものは、「人が見る」に入る。

各テストは、冒頭のコメントで**どの観点を見ているか**を言えること。言えないテストは置かない。ブラウザはChromiumだけにする。

### 共通フィクスチャに置くもの

`e2e/fixtures.ts`に置いてよいのは、**目的の画面まで進める導線**だけ——アプリが起動するためのAPIモックの既定応答と、
`openMobileApp`・`openMobileSheet`・`generateRoutes`・`seedStoredState`のような段取りのヘルパー。

**判定対象になる値は、各テストが自分で用意する**（幅を測るための長いラベル・段階の細かい軸・描けたかを見る塗り色等）。共通側の
応答を上書きするには、テストの中で同じURLへ`page.route`を後から登録する（Playwrightは後から登録したルートを先に当てる）。

### 走査する画面の状態は、画面から辿る

観点1〜3は、要素を性質で集めるだけでなく、**当てる画面の状態も手で選ばない**。`e2e/all-states.spec.ts`が、`e2e/states.ts`の辿る画面の
状態へ`e2e/scans.ts`の走査を当てる。

**土台**は幅 × 段階で、ここだけは人が決めた前提である:

- 幅: 幅の分岐はCSSの`--breakpoint-mobile`だけなので、その両側に1つずつ置く（両側にあることは実行時に検算する）。
- 段階: ルートの生成前・生成後・区間を乗り換えた後。生成後にしか現れない部品へ届くには生成を1回押す。乗り換えた後へ届くには、
  目的地へ向かう2候補を生成し、合成を始めて地図の乗り換え先を1つ押す（段取りと、途中の1区間だけ別の道を通る2候補の応答は
  `e2e/states.ts: splice`）。
- 軸カタログ: 本番と同じく重みのある軸を複数持つ（`e2e/states.ts: installScanMocks`）。重みのある軸が2つ以上のときだけ出る部品
  （重みの境目）は、既定のモックの1軸では出ない。
- モード（デバッグモード等）は切り替えない。

**土台の上は画面から辿る**。画面がARIAで開閉を宣言している部品——`aria-expanded`を持つ部品（折りたたみ・ポップオーバー・チップの
グループ・モバイルの下部タブ等）と`role="tab"`——のうち、**最前面で押せるもの**（中心点のヒットテストが部品自身か子孫を返す）だけを
押し、押せる限り奥まで辿る。押せないものは押さない（違反にもしない）。どの状態へも1回だけ入る: 幅 × 段階ごとに1枚のページで辿り、
開いたものは閉じて元へ戻す（同じタブ列のタブは戻らずに次へ渡り、最後に元のタブへ戻す）。各段階のページは開き直したもので、前の
段階と同じ段取り（生成・乗り換え）を踏んでから辿る。祖先の状態にあった部品は押さない。

**同じ部品**は、要素から祖先までの**タグと（並べ替えた）クラスの並び**で見分ける（並びが同じなら同じCSSの規則が当たる。開くたびに
作り直される部品も同じ部品として扱える）。

**閉じたら元に戻る**ことは、それ自体を違反として見る。押す前と閉じたあとの**指紋**（開閉の値を部品の見分けごとに集めたものと、
ページの倍率）が一致しなければ落とす。同じタブ列のタブは見分けが同じになるので、指紋ではタブ列の中の位置を添える。localStorageは
指紋に入れない（辿る間にページを読み直さないので、保存値は開閉の値で読める）。

押したあとは、画面が**落ち着く**まで待ってから次を見る（何を見て落ち着いたとするかは`e2e/states.ts: settle`）。**Playwrightの
`networkidle`では済ませない**: 公式が試験での使用を勧めておらず、読み込み状態の待ちなので押した後に呼んでもすぐ返りうる
（`waitForLoadState`の型定義の説明。版は`frontend/package.json`の`@playwright/test`）うえ、アニメーションや描き直しを待たない。

**検査は、判定が読むものから2種類に分けて当てる回数を変える**:

| 種類 | 判定が読むもの | 当て方 | 例 |
|---|---|---|---|
| 配置の検査 | 要素の座標・寸法、ページの幅 | 状態ごと | ページが横にスクロールしない、操作できる部品（ブラウザが計算したロールがWAI-ARIAのwidgetに当たるもの）が画面の横幅からはみ出さない（横スクロールする容器——縦にスクロールする容器も含む——の中の部品は、最も近いその容器が画面の横幅に収まるかを見る）、操作できる部品の押す点（中心点）がスクロールしない祖先（`overflow`が`hidden`・`clip`）に切り取られていない（その軸でスクロールする祖先より外側は見ない）、操作できる部品の箱が24px四方以上（WCAG 2.2 達成基準 2.5.8。例外はブラウザが入力欄の内側に描く部品だけ）、省略記号で切られた文字が無い（計算後の`text-overflow`が`ellipsis`で、中身が箱より広い要素）、中身が箱から横にはみ出して親の縁の外へ漏れていない（自分と親の計算後の`overflow-x`がどちらも`visible`で、中身が箱より広い要素のうちいちばん内側。親が切る・スクロールするなら見ない） |
| 部品の検査 | 要素と祖先の計算後のスタイル | 段階ごとに各部品1回 | 余白ユーティリティがリセットに潰されない、地図の外で始めたピンチがページを拡大しない（タッチを持つ文脈＝モバイル幅だけ） |

**新しいシート・パネルは、開閉する部品に`aria-expanded`（または`role="tab"`）を付ければ走査の母集団に入る。** 窓（`Dialog/Dialog.tsx`）を
開くボタンも、`aria-haspopup="dialog"`と開いている間`true`の`aria-expanded`を付けて入れる（Radixの`Dialog.Trigger`が付けるのと同じ宣言）。
付けなければ走査に入らない。

### 書き方

1. **「見たい画面まで進める段取り」は`e2e/fixtures.ts`のヘルパーを使い、テストごとに書き直さない。** モバイルはデスクトップと導線が
   別（下部タブバーとボトムシート）である。`openMobileApp`（モック登録・390x812・goto）→`openMobileSheet`（タブを押して開く。
   ハイドレーション前のクリックは効かないため開くまで再試行する）→`generateRoutes`（距離指定→生成→完了待ち）の順に呼ぶ。保存される
   画面状態（レイヤーのON/OFF等）はクリックで作らず`seedStoredState`でlocalStorageへ与える。
2. **レイアウトの溢れは座標・幅を実測して押さえる。** 画面外へ出た要素もアクセシビリティツリーには残るため、role・名前で見つかる
   ことは「押せる」ことを意味しない。`scrollWidth`/`clientWidth`の比較と`boundingBox()`で確かめる（`e2e/mobile.spec.ts`のヘッダー検査）。
3. **ロケータを当て推量で書かない。** 落ちたテストは`test-results/<テスト名>/error-context.md`へその時点の画面構造（role・アクセシブル名）を
   吐くので、実際の名前はそこで確かめる。
4. **地図が描けたかは画素で見る**（地図が何も描かれなくてもcanvasとDOMの状態は変わらない）。描けたことを見るのは
   `e2e/map-runtime.spec.ts`の1本だけに置き（GeoJSONの面を専用色で塗り、canvasの写しにその色の画素が出るかを数える）、他のテストへ
   同じ確認を足さない。
5. **タッチ操作は`Input.dispatchTouchEvent`（CDP）で指ごとに送る。** `isMobile`・`hasTouch`を付けた文脈で、2本指の開始・移動・終了を
   送ると、ブラウザは`touch-action`に従ってページの拡大まで行う（`visualViewport.scale`で読める）。`Input.synthesizePinchGesture`は
   `touch-action`に関わらずページを拡大しないので、既定動作の確認に使わない。
6. **足したテストは、わざと壊した入力で落ちることを見てから完了にする**（[fixing.md](fixing.md)「直し方」）。

## パターン5: 外部クライアントのフェイクは共有モジュールから取る

`backend/tests/`直下の、`test_`で始まらないモジュール（`conftest.py`を除く）が、複数のテストで同じ形になるフェイク・足場を持つ。
何を持ち、どの場面で使うかは各モジュールの先頭のdocstringが書く（例: `fake_tile_cache.py`はディスクキャッシュを、
`fake_external_log.py`は`log_external_call`の記録を差し替える）。新しいフェイクを書く前に、この直下を一覧してdocstringを読む。
**新しいテストで同じものを書き写さず、ここからimportする。** 複数のテストで要る足場を新しく置くときも、この直下に置き、用途を
先頭のdocstringに書く。

**共有の足場とフェイク（この直下と、frontendの`frontend/src/testing/`）は、それ自身のテストを持つかを3問で決める。**

- 本物の口を真似て、ずれうる振る舞いを自分で持つフェイクは持つ。同じ公開の口に対するテストを本物とフェイクの両方へ流してずれを
  止める（本物の側はHTTPならrespx、DBなら実DBで流し、テスト環境で作れない`maplibre-gl`は実ブラウザ（パターン4のE2E）で流す。
  例: `frontend/src/testing/mapTrace/recordingMap.contract.ts`）。
- 組み立ての足場は、崩れても頼るテストが緑のまま通る約束だけを確かめる。
- 値を並べるだけ・1行の委譲の足場は持たない（1問目）。約束が崩れると頼るテストが赤になる足場も持たない（3問目）。

これはテストの足場を対象にするテストで、「消すべきテストの型」の「本番に生えたテスト専用の口の検査」とは別物である。

**網・時計・Redisの代役は自前で書かず、定番の道具を使う**（どれも`requirements-dev.txt`）。

| 境界 | 道具 | 使い方 |
|---|---|---|
| HTTP（クライアントを受け取る実装） | respx | 経路（`respx.Router`）で応答を決め、`tests/fake_http.py: client_for`で本物の`httpx.AsyncClient`にして渡す。どのURLへも同じ応答で足りるなら`answering`。要求は`router.calls`で見る（見てよいのは状態を変える要求だけ） |
| HTTP（実装が自分で`httpx.stream`等を呼ぶ） | respx | pytestのフィクスチャ`respx_mock`。実装の中で作られる`httpx.Client`は証明書の読み込みに開発機で1つ0.5秒かかるので、1テストで何度も作らせない |
| 時計 | freezegun | フィクスチャ`clock`（`tests/conftest.py`）。`tick`・`move_to`で進める |
| Redis | fakeredis | フィクスチャ`fake_redis`（`tests/conftest.py`）。接続の失敗は`redis_server.connected = False` |

例外は窓・TTLを数える単調時計（`tests/conftest.py: MonotonicClock`。回数制限・外部I/Oの警告の抑制・データの世代の読み直しが読む）で、
セッションを通して1本の時計を進め続けるため、これらのモジュールが読む時計だけを差し替えている。

`admin_credentials`は、認証情報が設定されている前提に立つテストが引数で取る。ファイル内の全テストが管理画面APIを叩く場合も
autouseで配らない（「テストの足場で、本来のNGを覆わない」の「宣言させる範囲」）。

フィクスチャ同士に順序が要るなら、**先に動くべきものを引数に取って依存で書く**。同じスコープのautouseフィクスチャは、ファイル内の
宣言順ではなく**名前の辞書順**でセットアップされる。確かめるには`pytest <対象> --setup-plan`でセットアップ順を出す。

frontendは`frontend/src/testing/`配下が同じ役割を持ち、用途は各ファイルの先頭のコメントが書く（例: `routeFixtures.ts: makeRouteCandidate()`は、
`e2e/fixtures.ts`も含めてルート候補を組み立てるすべての場所が使う）。

## パターン6: 絞り込んだ母集団をループするテストは、空でないことを確かめる

実データ・生成物・定数表から条件で絞った一覧をループして要素ごとに検査する形は、**母集団が0件になると何も確かめないまま緑になる**。

```python
picked = [m for m, s in SPECS.items() if isinstance(s, WayMaterialCoverageSpec)]
assert picked, "way材料のカバレッジ仕様が1件も無い"   # これが無いと下のループは空振りしうる
row = await fetch_values(conn, edge_id)                # 組み立てたSQLを実行した結果
for material_id in picked:
    assert row[material_id] is not None
```

```ts
const expressionColors = COLOR_EXPRESSION.filter((i) => typeof i === "string" && i.startsWith("#"));
expect(expressionColors.length).toBeGreaterThan(0);
for (const color of expressionColors) { expect(legendColors.has(color)).toBe(true); }
```

空でないことの主張は**同じテストの中**に置く（別のテストにある主張は、このテストが空振りしないことの根拠にならない）。

**要素ごとの検査は、ループより`parametrize`で書く**（落ちた要素がテストの名前に出て、1つの失敗で残りの要素が止まらない）。ループで
書くのは、上の例のように1回の実I/Oの結果を要素ごとに見るときである（基本原則1）。宣言から導いた母集団を`parametrize`へ渡し、それが
空になったら集める時点で落ちる（`backend/pytest.ini`の`empty_parameter_set_mark`）。

絞り込みの書き方は問わない。ループの中の条件で要素を選ぶ形（`if`の片側にだけアサーションを置く・`continue`で飛ばす）と、空なら真に
なる量化（`assert all(...)`・`assert not any(...)`・`expect(xs.every(...)).toBe(true)`）も同じで、どれも、絞り込んだ一覧を名前へ束ね、
空でないことを主張してから検査する。

`backend/tests/structure/test_vacuous_loops.py`（Python、AST）と`frontend/src/structure/vacuousLoops.test.ts`（TypeScriptの構文木）が、
この性質の混入を止める。どちらも要素ごとの検査（本体にアサーションがあるループ・上の量化）について、①反復対象がその場で絞り込み
（`if`付きの内包表記・`filter`）を経ている、②ループ本体の条件を通らないとアサーションへ届かない、③反復対象の名前が絞り込みで
束ねられていて同じテストに空でないことの主張が無い、のどれかに当たるものを落とす。**読めるのは上の例の形の主張だけ**で、別の形
（`assert set(picked) == {...}`等）で確かめていても違反として出る——そのときは上の形の主張を1行足す。反復対象が関数の引数
（parametrize等）のループは見ない。

## パターン7: 環境変数に依存する挙動のテスト → 判断を純関数へ出し、テストは環境変数に触らない

frontendのvitestは`pool: "vmThreads"`で走るため、**`process.env`はテストファイルをまたいで共有される**。実装が環境変数を呼び出しの
たびに読む設計（SSRでの参照を避けるため）なので、あるファイルが立てた環境変数が並行実行中の別ファイルの期待値を変える。`afterEach`で
戻しても足りず、`process.env`ごと差し替える（`process.env = { ...ORIGINAL }`）と`vi.stubEnv`の復元も壊れる。

**判断を、環境変数を引数で受ける純関数へ出す**。環境変数を読むのは分岐を持たない薄い関数だけにし、テストはその純関数を呼ぶ
（`lib/tileBaseUrl.ts: resolveTileBaseUrl`）。純関数の`export`は「確かめる高さ」の (a) に当たる。

```ts
export function tileBaseUrl(): string {
  return resolveTileBaseUrl(process.env.NEXT_PUBLIC_TILE_BASE_URL, origin());
}
export function resolveTileBaseUrl(configured: string | undefined, origin: string | null): string { ... }
```

その値を**使う側**のテスト（URLの組み立て等）は、読み取り口のモジュールをモックして固定する。

```ts
vi.mock("@/lib/tileBaseUrl", () => ({ tileBaseUrl: () => "" }));
```

**漏れたかどうかは`vitest.setup.ts`が実行時に見る**——テストファイルの終わりに`process.env`が開始時と違えば落ちる（`vi.stubEnv`のように
復元されるものは通る）。`process.env`ごとの差し替えは束縛を固定して止めてある。自分のテスト対象だけが読む環境変数
（`app/api/version/route.ts: RENDER_GIT_COMMIT`・`lib/adminBasicAuth.ts`の資格情報等）は、他へ波及しないため対象外で、`vi.stubEnv`で立てて
公開の入口を呼ぶ（使う側のテストは読み取り口のモジュールをモックして、その値を読まない）。

## パターン8: テストが用意する状態は、本番で起こりうるものに限る

DBの制約・取込の順序から**作れない状態**をテストで作らない（その状態向けの分岐が実装に残り続ける）。

- **派生行を作るテストは、親を先に入れる**。区間（`road_edges`）は生の道（`source_features`の`osm_way`）とノード（`node_materials`、端点は
  FK）の派生。本番と同じ順（生データを入れてから派生バッチを流す）で作り、派生の表へ行を直接書き込まない（`test_derive_topology.py:
  topology_conn`が、生の道を取り込んでから`derive_topology.derive`を呼ぶ形）。
- **生データも取込の入口から入れる**。`source_features`・`source_runs`へ直接書かない。`tests/source_ingest.py: ingest_records`が
  アダプタだけを差し替えて`ingest_source`を通す。行を変えたいときは、変えた後の全行で取り込み直す（本番の取り直しと同じく、そのソースの
  行が入れ替わって新しいrunになる）。
- **値式が必ず値を返すものを「欠損」にしない**。真偽の材料は`COALESCE(条件, false)`で閉じるため、「材料が1つも無い区間」は作れない。
  軸が算出できない状況を確かめたいなら、軸の集合を差し替えて表現する（土台は`tests/axis_system_fixture.py`）。
- 制約を足した結果としてテストが大量に落ちたら、**テストの前提が本番と食い違っていた証拠**として読む。

## パターン9: 期待値の出どころを選ぶ（書き写さない・素のテキストを引く・軸を取り違えない）

**同じ計算を2つの言語で持つなら、期待値を手で書き写さない。** 片方（正本側）の実行結果をフィクスチャとして書き出し、もう片方を
それに突き合わせる。backendと画面の間の置き場と作り方は「パターン11」。

**素のテキストノードは、要素として引けない。** 凡例ラベルのように`<span>`と`<span>`の間へ直に書かれたテキストは、`getByText`の
完全一致ではなく正規表現で当てる。

**座標のように「どの軸をどこへ渡すか」を間違えうる値は、入れ替えると別物になる実例で見る。** XYZタイル座標は`x`と`y`を取り違えても
値としては通るので、既知の1点（例: 東京都心のz/x/y）を通して**入れ替えたら落ちる**形にする。

## パターン10: 期待値が実行環境（OS）で変わる入力を使わない

開発機はWindows、CI・本番はLinuxで動く。**OSによって解釈が変わる入力をテストに使わない。** 典型はパスで、`r"C:\venv\Scripts\uvicorn.exe"`は
Linuxの`Path`では`\`が区切りにならない。パスは実行中の環境の区切りで組む:

```python
str(Path("venv") / "Scripts" / "uvicorn.exe")
```

確かめたいのが「拡張子つきでも読める」なら、その性質だけを入力に持たせ、OS固有の書き方を持ち込まない。実装に両方の区切りを読む
分岐を足してテストへ合わせることもしない。機械では確かめておらず、最終的には作業ブランチの Pull Request のCI（Linux）が判定する。

## パターン11: backendと画面が同じ計算を持つ → backendが「入力→答え」の表を出す

方位の呼び名の丸め・2点間の距離のように、同じ計算をbackend（Python）と画面（TypeScript）の両方が持つところは、backendが出す表を
画面のテストが通して一致を確かめる（パターン9の「書き写さない」の形）。

- **入力はbackendに置き、答えはbackendの関数が出す**。入力の並びと、それを関数へ通して表にする関数を
  `backend/scripts/cross_language_expectations.py`に置き、同じファイルの`EXPECTATIONS`へ「組の名前 → 表を作る関数」を1行足す。
  `backend/scripts/export_openapi.py`が組ごとに`frontend/src/types/generated/<組>-expectations.json`へ書き出す（組の名前は何の計算か。
  例: `geo`）。表は組の中で計算ごとにキーを分けた行の並びにする。
- **入力は答えが分かれるところを選ぶ**: 区分の境界ちょうどとその少し手前・負の値・一周を超える値・0・日付変更線のような折り返し。
  区分の数などbackendの宣言から決まるものは、入力もそこから導く。
- **生成物は機械によらずバイト単位で同じにする**（ドリフト検査が`git diff`で見るため）。浮動小数の答えは、CPUで最下位の桁が
  変わりうるなら、意味のある桁へ丸めて出す。
- **画面のテストは表の全行を画面の関数へ当てる**。表の置き場は対象の関数の隣のテスト（例: `lib/cardinalLabel.test.ts`）で、全行を
  回す前に表が空でないことを確かめる（パターン6）。浮動小数の許す差は表に持たせず、テストの側で決める。
- **backendの関数は、表とは別に手で書いたあるべき値のpytestで確かめる**（表の答えはbackendが出すので、表を通しても何も確かめない）。
- 表とbackendの実装はドリフト検査が結ぶ——backendの答えが変わると生成物が変わってCIの`api-contract`が落ち、生成し直すと画面の
  テストが落ちる。表と画面の両方で同じ事実を確かめる手書きのテストは、表へ寄せて消す。
- **式の定数（丸めの桁・ズームの列・入力の下限等）は、表で確かめずに生成物から読む**。backendの定数を生成物（`export_openapi.py`）へ
  出し、画面の式はそれを読む（例: タイルから組む点数の丸めは`mapDisplay.valueScale.difficultyDecimals`）。読む形なら食い違いが起きない
  ので、一致を確かめるテストは書かない。backendに源泉の無い画面だけの値は、画面の中の1つの定数に置いて使う所がそれを読む。
