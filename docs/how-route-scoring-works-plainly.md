# 道の走りやすさをどう決めているか（やさしい説明）

このアプリ（RideCompass）は、地図上の道の「走りやすさ」を機械的に判断して、良いルートを
選ぶ仕組みを持っている。ここでは、その仕組みを専門用語を使わずに説明する。
（技術的な正式版は`RideCompass 目論見書`Artifact、詳細な設計判断は
[material-normalization-for-axis-composition.md](decisions/material-normalization-for-axis-composition.md)
を参照）

## 4段階の流れ

道の走りやすさを決めるまでには、4つの段階がある。

```
①観測データ  →  ②材料を揃える  →  ③点数に変換する  →  ④全部混ぜて最終点数
（生の事実）     （正規化）        （評価軸）           （合成）
```

### ①観測データ（生の事実）

地図データ（OpenStreetMap）や、事故の統計、天気予報などから、道の特徴をそのまま集める。
「この道の速度制限は60km/h」「この道にトンネルがある」「この交差点には信号がある」
といった、加工していない事実の集まり。ここでは何が良い・悪いという判断は一切しない。

### ②材料を揃える（正規化）

集めた事実を、後で計算しやすいように「同じ形」に整える。バラバラな情報を、
できるだけ「あるか・ないか」(はい/いいえ)や、数字のような単純な形に変換する作業。

たとえば「この道にトンネルがある」は、そのまま「はい」か「いいえ」の1つの材料になる。
「速度制限は60km/h」は、そのまま数字の材料になる。

道の特徴の中には、複数の事実を組み合わせないと意味が分からないものもある
（例:「自転車専用道なのか、車道に自転車マークがあるだけなのか」は、複数の地図タグを
見比べないと判断できない）。こうした場合も、できるだけ「Aという印があるか」「Bという
印があるか」のような、単純な「あるか・ないか」の材料に分解しておく。

### ③点数に変換する（評価軸）

材料を使って、「勾配のきつさ」「車の多さ・怖さ」「事故の多さ」といった、1つのテーマ
ごとの点数（0〜100点）を計算する。この「材料から点数への変換ルール」こそが、
このアプリの本当の価値であり、開発者が実測データを見ながら育てていく部分。

計算のやり方は、主に次の2つ:

- **足し算方式**: 「トンネルがある: -50点」「街灯がない: -50点」のように、当てはまる
  材料の点数を全部足し算する。
- **グラフ方式**: 材料の数字(勾配など)を、折れ線グラフに当てはめて点数を読み取る。
  数字が大きいほど点数が下がる、というような関係を表現できる。

複数の材料を組み合わせて1つの点数を出す場合も、基本は「それぞれの材料に重み(点数)を
割り振って、当てはまったものを全部足し算する」というシンプルな計算だけで済ませる。
「もしAならこれで決まり、Aでなければ次にBを見て…」というような複雑な優先順位の
ルールをできるだけ避け、単純な足し算に寄せることで、新しい材料が増えても計算方法自体は
複雑にならないようにしている。

### ④全部混ぜて最終点数（合成）

「勾配」「車の多さ」「事故の多さ」など、複数のテーマの点数を、ユーザーが決めた
重要度（重み）で混ぜ合わせて、1つのルートの最終的な「走りやすさ」を決める。
この重みだけが、ユーザーごとに自由に変えられる部分——「坂は平気だけど車は怖い」
という人は、車の多さの重みを大きくすればよい。

## 地図の色分けと、点数の計算は別物

地図上で道を色分けして見せる機能（例: 自転車専用道は緑、車道は灰色）と、上で説明した
「点数の計算」は、実は別の目的で作られている。

- **点数の計算**は、②で作った「あるか・ないか」の単純な材料を、③で足し算するだけで
  求まる。
- **地図の色分け**は、人間が地図をパッと見て理解できるように、「分離された自転車道」
  「自転車レーン」「車道」というような、分かりやすい名前の分類に整理し直したもの。

この2つは目的が違うので、別々の仕組みとして持っておいてよい。点数の計算方法を
シンプルにしても、地図の色分けの分かりやすさが損なわれることはない。

## なぜこの分け方が大事か

このアプリの成長は「新しい種類の観測データをどんどん取り込んで、より正確な走りやすさの
判断を作れるかどうか」にかかっている。もし新しいデータを取り込むたびに、複雑な判断
ロジックをプログラムのコードとして書き足していく必要があるなら、データが増えるほど
コードが際限なく複雑になっていってしまう。

材料をできるだけシンプルな形（あるか・ないか、単純な数字）に揃えておけば、新しい
評価テーマ（点数のつけ方）を作るときは、既存の材料を選んで足し算の重みを決めるだけで
済むようになる。プログラムのコードを新しく書く必要が減り、開発者(将来的には研究者)が
「材料をどう組み合わせるか」というアイデアの検証に集中できるようになる。
