# 軸定義のメンテナンス経路の分担（軸スタジオ / スクリプト）

軸定義（`axis_definitions`の行データ）を変える手段を、軸スタジオのGUIとスクリプトへ
どう分けるかの決定。正本がDBであること自体は変えない（[T361](../tasks/T361.md)）。

ステータス: 決定（2026-09-17、ユーザー判断）

## 背景

軸スタジオには繰り返し手が入っているが、同じ不満が戻ってくる——2026-09-08「軸スタジオ
使いにくいね・・・直接DBにInsertした方が楽かなって思うくらい」（[T686](../tasks/T686.md)で
分布プレビューを追加）、2026-09-17「数値をポチポチ手打ちするなら、apiで裏更新するのと
同じ」。改善のたびに**入力欄の作り込み**を足してきたが、利用者がやりたいのは入力ではなく
**較正**（実データを見て根拠のある値を決めること）なので、入力欄をいくら磨いても効かない。

一方でAPIを直接叩く運用には、GUIとは無関係な弱点が1つある。**開発DB・本番DB・
スナップショットの同期が人の記憶頼みになる**ことで、[deployment-sync.md](../deployment-sync.md)が
記録している反映漏れの実績はすべてこれである。

**履歴（誰がいつ何を変えたか・ロールバック）はこの分担の目的ではない。** 軸の値は唯一の正解が
無い継続的チューニングの対象で、監査証跡・ロールバックは過剰品質だと既に判断している
（[T361](../tasks/T361.md)の背景に残るT221・T353の判断）。実際に起きた事故も履歴があって
防げるものではない。将来ロールバックが要るとなれば、1世代しか持てないファイルではなく
DB側に世代を持つのが筋になる。

## 決定: 「値を探すあいだ」と「決めた値を配るとき」で切る

| | 軸スタジオ（GUI） | スクリプト |
|---|---|---|
| 担当する状態 | 値がまだ決まっていない（探索・試行） | 値が決まっている（反映・配布） |
| 主な操作 | 現状を読む、実データの分布で効き方を確かめる、試しに変えて結果を見る、公開/非公開を切り替える | 決まった内容を開発DB・本番DBへ同じように適用し、スナップショットを揃える |
| 対象の環境 | 開発DBのみ（試行のため） | 開発DB・本番DBの両方を同じ内容へ揃える |

境界の一文: **読むこと・試すことはGUI、決めたものを配ることはスクリプト。**

### 軸スタジオがやること

- 公開軸の一覧・各軸の形・重み・公開状態・材料の欠損割合を読む。
- **実データの分布で効き方を確かめる**（`DistributionPreview`、[T686](../tasks/T686.md)）。
  値を決める前に「この折れ点だと延長の94.6%が満点」と分かること自体がGUIの存在理由。
- 段階分け（`display_thresholds_override`）を変えたときに、**段階の並びと地図の色が
  その場で見える**こと。
- 公開/非公開の切り替えと、壊す操作の拒否理由の提示。

### 軸スタジオがやらないこと

- **値の入力体験をこれ以上作り込まない**。数値を並べて打つ作業は、エディタとスクリプトの
  方が速く・記録も残る。入力欄は「試すために少し動かす」ために必要な最小限で止める。
- 本番への反映を単独で完結させること（GUIでの変更は開発DBのみに効く前提で扱う）。

### スクリプトがやること

- リポジトリ上の軸定義ファイル（fresh bootstrap用に既にある
  `backend/fixtures/axis_definitions_snapshot.json`。**履歴のためではなく、置き場を増やさない
  ため**にこれを入力にする）と、対象環境の現在値との**差分を先に見せる**。
- axis_admin APIを通して適用する（APIを迂回してDBへ直接書かない。検証と認可境界を
  素通りさせないため）。
- 開発DB・本番DBの両方へ同じ内容を適用し、スナップショットを再ダンプするところまでを
  1つの手順に収める。

## 影響

- `docs/deployment-sync.md`の「axis_admin API経由のDB変更は開発DB・本番DB両方への反映を
  完了条件にする」は、このスクリプトが担保する形になる。
- 「GUIが唯一の入口」という運用はやめる。ただし**APIを迂回したDBへの直接書き込みは
  引き続き行わない**——分担の対象は入口であって、検証・認可境界ではない。
