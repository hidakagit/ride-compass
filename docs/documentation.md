# ドキュメント記載方針

`docs/`配下・`.claude/`配下・README・モジュールdocstringに共通する、**何を書き何を書かないか**の
方針。コードコメントについては[comments.md](comments.md)が別に定める。

## 判定基準: その文書だけを読んで、正しさを検証できるか

**書いてよいのは、その文書（またはそのdocstring）を読むだけで正しいか誤りか判定できる記述。**
判定に他所を見に行く必要がある記述は、他所が変わった瞬間に嘘になり、文書側は何も壊れない
ため誰も気づかない。

この基準を外れる書き方は次の形で現れる。用語の定義は末尾の用語集にある。

| 型 | 書いてしまう例 | 代わりに書く |
|---|---|---|
| **数え上げ** | 「car_stressが5つの内部軸を参照する」「段は④〜⑫」 | 「内部軸を組み合わせて算出する」「段は`_STAGES`が持ち、足せば順序が決まる」 |
| **代弁** | 「フロントはこれを基準に超過分を出す」「配線するのは1行足すだけで済む」 | 自分の側の契約だけを書く（「この値は基準として配る」） |
| **撤去済みの名指し** | 廃止した軸・存在しない引数・削除した方針を現行として説明 | 名前を出さず挙動を書く。当時の記録として残すなら廃止の断りを添える |
| **写し** | コードにある式・閾値・手順をそのまま書き写す（「`[max(0,(目標−許容)/2.0), (目標+許容)/2.3]`に入るNode」「重複率0.6を超えたら飛ばす」） | その式が**何を達成しようとしているか**を書く（「往路の実距離が目標の半分付近に入るNode」「重複しすぎる候補を飛ばす。しきい値は同ファイルの定数が持つ」） |

**代弁**がとくに壊れやすい。相手の実装を要約した文は、相手が変わっても自分のテストは
通り続ける。相手の挙動に依存する説明が要るなら、依存していること自体を書く
（「この値の解釈は受け取る側が決める」）。

**写しと、許容される定数の書き方の線引きは「機械が照合できるか」**。`NAME`（600）のように
定数名と値を並べる形は検査対象で、ずれれば違反として出る（下記「DBの行データ・コードの
定数を名指しするとき」）。式・条件・手順の写しは照合できないため書かない——古くなっても
誰も気づかず、しかも読んだ人はそれを仕様だと信じる。

### 適用範囲の目安

- `docs/modules/*.md`とdocstring——**読者は次にそのコードを触る人**。実装を読めば分かることは
  書かず、実装を読んでも分からないこと（暗黙の前提・隠れた依存・外部システムの実際の挙動・
  実測値）だけを書く。
- `docs/architecture.md`・`docs/design-principles.md`——**読者は仕様を理解したい人**。
  個々の関数・引数・ファイル名の水準へ降りない。

## 挙動を書く。要素を数え上げない

**ドキュメントが示すべきは「何がどう振る舞うか」「なぜそうなっているか」。**
コードから数えられるものを散文へ写さない。

書かないもの:

- **個数**（「4本のバッチが参照する」「現行8軸」「5値の分類」「六つの材料」）
- **全件の一覧**（ファイル一覧・エンドポイント一覧・state一覧・定数一覧・軸id一覧）
- **組み合わせの網羅**（「①〜⑦の要素それぞれについて…」）

これらは**必ず実装より先に古くなる**。書いた時点では正しく、増減があっても文書側は
何も壊れないため、誰も気づかない。実際、統合レビューで繰り返し検出されている
（第6回で個数表現の陳腐化12件、第7回でも`_common.py`の「4バッチが参照」が実際は12本、
`page-composition.md`のstate一覧が3件不足）。

代わりに書くもの:

- その要素**群が何をするか**（「派生データを作るバッチは、対象件数を数えてからチャンク単位で
  更新し、進捗を1行INFOで出す」）
- **増えたときに何が起きるか**（「バッチを1本足しても`_STAGES`へ登録すれば順序は自動で決まる」）
- **実装を読んだだけでは分からないこと**（暗黙の前提・隠れた依存・外部システムの実際の挙動・実測値）

## 代表例は許容する。ただし「例」と分かる書き方にする

挙動を分かりやすくするために代表的な要素を挙げるのは**よい**。全件のつもりで読まれる
書き方をしないこと。

- よい: 「`_common.py`が共通ドライバ（`run_chunked_precompute`等）を提供し、
  precompute系バッチはこれに乗る」
- よい: 「タイル世代の定数（`ROAD_SURFACE_TILE_VERSION`など）」
- 避ける: 「`_common.py`は`asyncpg_dsn`・`download_to_path`を提供する。4バッチが参照する」
- 避ける: 「対象は`gradient`・`surface_q`・`stop_density`・`car_stress`・`accident`・`night`の6軸」

判断の目安は**「要素が1つ増えたときにこの文は嘘になるか」**。嘘になるなら数え上げている。

## 全件が必要なときは、生成物かコードを指す

一覧そのものが必要な場面（デバッグ・棚卸し）はある。そのときは文書へ写さず、
**生成物**（`axis-catalog.json`・`region-tile-config.json`・`material-catalog.json`）か、
**それを定義しているコード**（`MATERIAL_CATALOG`・`_STAGES`）を指す。

## 例外: 機械が完全性を保証している表

**一覧が機械的に「漏れていないこと」を検査されている場合のみ、全件の表を持ってよい。**
この場合、要素が増えたときに文書側が壊れる（CIが落ちる）ため、静かに古くならない。

現在この例外に当たるのは`docs/modules/*.md`の**対象ファイル表**だけ。この表の目的は
「この新規ファイルの責務はどのモジュールが持つか」の逆引きで、コード側に等価な表現が無い。

**検査しているのは「表に載っていること」ではなく「そのモジュール文書のどこかに名前が
出ること」である**（`scripts/review_checks.py: find_undocumented_files`）。表のセルは
`| app | page.tsx・layout.tsx |`のように**列で階層を表す**書き方をしており、
パスで照合すると表に載っているファイルまで「載っていない」と判定してしまうため。
本文で責務を説明してあれば逆引きは成立するので、この弱い形で足りると判断している
（実測: 本文に名前があり表のセルには無い実装ファイルが9件あり、いずれも責務は本文で
説明されていた）。**表へ足すのが既定**で、本文だけで済ませるのは表の粒度に合わないとき。

**逆に、同じ一覧を検査の無い場所へ二重に持たない。** `docs/architecture.md`の
ファイル樹形図は`docs/modules/*.md`の対象ファイル表と重複しており、検査が無い側だけが
古くなっている。

## DBの行データ・コードの定数を名指しするときは、機械検査に載せる

文書・コメントが名指しする対象のうち、**デプロイを伴わずに変わるもの**は、変わった瞬間に
どこも壊れず説明だけが嘘になる。`scripts/review_checks.py`がこの2種を突き合わせる
（強制する経路は同ファイルの`DETECTOR_ENFORCEMENT`が持つ）。

- **axis_id**: 軸は軸スタジオのGUIから追加・削除でき、作り直した軸は生成された別idを持つ。
  `backend/fixtures/axis_definitions_snapshot.json`に無いidを現行として名指しすると違反。
  当時の記録として残すなら、同じ段落に廃止・撤去の断りを書く。
- **数値の定数**: 「`NAME`（600）」のように名前の直後へ値を書くと、定数を変えたときに
  文書側は何も壊れない。実装の値と合わなければ違反（秒↔分のような単位の読み替えは許す）。

どちらも、名前を出さずに挙動だけ書けば対象外になる——**名前と値を並べて書くのは、
照合できる形にするためでもある**。

## 数え上げ自体は、書いた行を目に入れるだけ（参考表示）

「N個」「N種」のような数え上げは、追加行に対してだけ`count_narrative`が参考として並べる
（ブロックはしない）。数の大半は正当な記述で、パターンだけでは区別がつかないため——
実測した内訳は[T824](tasks/T824.md)にある。出た行が「要素が1つ増えたときに嘘になる文」
かどうかは、書いた本人がその場で判断する。

## なぜこの方針か

ドキュメントの陳腐化は、統合レビューで一貫して最大の指摘カテゴリである。件数は
`python scripts/review_checks.py categories`が出す（分類語は
`.claude/commands/review/principles.md`の個票の`category`の節）。**ここへ数字を書き写さない**
——写した側だけが古くなる。なお2026-09-19より前の回は個票の分類語が自由記述で、同じ基準では
数え直せない（当時の手集計では「およそ3割」だった）。固定語彙での最初の実測は40%である。
同じ期間、`docs/modules`は全コミットの2割で更新されている。**書く量に見合った戻りが
得られていない**のがこの方針の出発点である。

一方で「コードから導けない事実」を書いた記述は古くならない（`maplibre-gl`のバージョン
固定の制約は1か月後の再検証でも正しかった）。

**古くなるのは写しの側**で、写しは更新し続ける対象ではなく削る対象
（[T707](tasks/T707.md)・[T723](tasks/T723.md)・[T724](tasks/T724.md)）。
検査の母集団についての同じ原則は
[design-principles.md](design-principles.md)構造仕様12にある。

## 用語集

判定基準を読む前提。**同じ語を違う意味で使うと、基準がそのまま曲解される。**

| 語 | 定義 | 定義から外れる例 |
|---|---|---|
| **現状** | いまのコードがどう振る舞うか。読んだ人がコードを触るために要る情報 | 「以前は〜だった」「Txxxで変えた」（これは経緯） |
| **経緯** | なぜ今の形になったかの履歴。置き場所は`docs/tasks/Txxx.md`のみ | 「このロックは並列に呼ばれるため必要」（これは今も成り立つ制約で、現状） |
| **数え上げ** | 要素が1つ増減したときに嘘になる記述。個数・全件の一覧・網羅 | 「〜等」「例:」と分かる形の代表例（これは許容） |
| **代弁** | 他のファイル・レイヤー・外部システムの挙動を、自分の文書の中で要約した記述 | 自分が満たす契約の宣言（「この値は正規化済みで配る」） |
| **記述と実装の不一致** | 文書・docstring・コメントが述べる内容が、現在のコードと合わない状態。機能の欠陥とは別に数える | 機能の欠陥（契約の取りこぼし・構造仕様違反など） |
| **写し** | コードにある式・閾値・手順を、照合できない形でそのまま書き写した記述 | 定数名と値を並べた記述（機械が照合するため許容） |
| **自己検証可能** | その文書だけを読んで、正しいか誤りかを判定できる状態 | 判定に他ファイルを開く必要がある記述 |
