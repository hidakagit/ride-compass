# コードコメントの方針

CLAUDE.md「コメント方針（必読）」から参照される詳細版。判定に迷ったときはここへ戻る。

## 背景

2026-09-03、ユーザー指摘「全般的にソースコードに大量の過去経緯のコメントが残っていて
読みにくい」を受けて`改善計画T[0-9]+`等のマーカーで機械的に調査したところ、backend/frontend
合わせて次の規模の経緯コメントが見つかった（[T566](tasks/T566.md)調査、重複ヒットあり）。

| パターン | 件数 | ファイル数 |
|---|---|---|
| `改善計画T[0-9]+` | 2,844件 | 373 |
| `以前は` | 289件 | 129 |
| `実機フィードバック/検証/確認/指摘` | 212件 | 80 |
| `ユーザー要望/指摘/判断/報告` | 185件 | 74 |

`docs/modules/README.md`は2026-08-31、設計書（`docs/modules/*.md`）に対して同種の経緯記述を
禁止するルールを既に明文化していたが、対象がドキュメントのみでソースコードのコメント自体は
対象外だった。実際に`RouteSettingsPanel.tsx`等を調べると、`docs/modules/*.md`側に既に現在形で
書かれている内容とほぼ同じ経緯コメントがコード側に残っており、二重管理（かつコード側の
「改善計画Txxx」参照はリファクタで陳腐化しうる）になっていた。本ドキュメントは
`docs/modules/README.md`の原則をソースコードのコメントへ拡張したものである。

## ルール

**書いてよいコメント**: 今のコードを安全に変更するために必要な、非自明な制約・理由を
**現在形の一文**で書いたもの（例:「このロックはXがYから並列に呼ばれるため必要」「下限を
0ではなくSTEPにするのは、0だとチェックOFF相当に化けて区間数が変わってしまうため」）。
実装を読めば分かることは書かない。

**書いてはいけないコメント**: 経緯——「いつ・誰の指摘で・改善計画Txxxで・以前は〜だった・
実機/実測で〜だったため」という時系列の記述。これは`docs/tasks/Txxx.md`（起票済みタスクの
背景）またはgit blame/コミットメッセージ/PRの役割であり、ソースコードのコメントに書くと
①`docs/modules/*.md`に同じ内容がある場合は二重管理になる、②参照先のTxxxがリファクタで
実態と食い違っても追従されず陳腐化する、という2つの理由でコストだけが残る。

## 判定基準（新しくコメントを書く/既存コメントを見直すとき）

**既定は削除**。経緯の言い回し（「以前は」「改善計画Txxxで」「ユーザー要望…」「実機で…」等、
`scripts/review_checks.py`の`NARRATIVE_PATTERN`が機械検出する言い回し）に一致したコメントは、
以下の**両方**を満たすと確認できた場合に限り、経緯の言い回しだけを落として残してよい。
どちらか一方でも満たさなければ削除する——「たぶん理由がありそう」という推測では残さない。

1. **そのコメントを消したら、今後の安全な変更が妨げられる非自明な制約・理由か？**
   （実装を読むだけでは分からないことか。実装を読めば分かることは、理由があっても書かない）
   - No → 削除（日記的記述。経緯自体を残したいなら該当タスクの`docs/tasks/Txxx.md`へ——
     新規に書き足すのではなく、既にそこにある背景と重複していないか先に確認する）。
   - Yes → 2へ。
2. **その制約・理由は、コード内コメント以外の場所にまだ存在しないか？**
   （`docs/modules/*.md`に同じ内容がある、型・assert・テストで既に強制されている、
   のいずれにも該当しないか）
   - 該当する（docs/modulesに既にある、または強制されている） → 削除する
     （`docs/modules/README.md`索引で対象モジュールを確認できる）。
   - 該当しない、かつモジュール横断で再利用される知識なら → `docs/modules/*.md`側へ
     「現在の事実」として昇格してから削除する。
   - 該当しない、かつこの1箇所だけの局所的な制約なら → 経緯の言い回しだけ落として
     現在形の一文で残す（実例②参照）。

コメントを型・assert・テストへ置き換えられないか（実行して壊れる形にできないか）も
2の判断時に検討する。コメントは読まれなくても放置され続けるが、テストや型は変更時に
実際に落ちるため、可能な場合は自己強制できる形の方が経緯コメントより優先度が高い。

## 実例（`RouteSettingsPanel.tsx`、2026-09-03調査時点のコメントより）

**① 設計書と重複 → 削除**

```ts
// Before（コード）
// 改善計画T306: 以前は軸を観測/推定/動的の3カテゴリへ見出し付きで分けて表示していた
// （T267の意図的な設計判断）。しかし改善計画T305で軸スタジオのGUIが常にcategory="推定"
// 固定で軸を作るようになった結果、「観測/動的グループに入るのはコード内蔵の既定軸だけ」
// というハードコードされた非対称性が生まれた。この非対称性を無くすため、ルート設定画面の
// 表示からカテゴリによるグルーピングを撤去し...
```

`docs/modules/frontend/route-settings-and-results.md`に既に「カテゴリ（観測/推定/動的）に
よるグルーピング表示は行わない。軸スタジオは常にcategory="推定"固定で軸を作るため、
フラットな1本のリストで表示する。」と現在形で書かれている。コード側は削除してよい
（どうしても手がかりを残したいなら`// 表示順序: docs/modules/frontend/
route-settings-and-results.md参照`程度の1行に圧縮する）。

**② 非自明な理由 → 経緯の言い回しだけ落として残す**

```ts
// Before
// 下限は0ではなくWEIGHT_STEPにする——0まで下げるとその軸がチェックOFF相当（weight>0判定）に
// 化け、ドラッグ中に帯の区間数が変わってしまうため、ドラッグでは「チェックを外す」操作を
// 兼ねさせない（0まで下げたい場合は詳細ポップオーバーかチェックボックス自体を使う）。

// After（変更なし——既に現在形の理由説明であり経緯の言い回しを含まないため）
```

このコメントはそのままでよい実例。「経緯を書かない」は「理由を書かない」ことではない。

**③ 日記的記述のみ → 削除**

```ts
// Before
// ユーザー要望（2026-08-31、「複数要素を足し合わせて1にするのを直感的に省スペース設定
// できるUIはないか」）: 既存の重み配分バー（帯グラフ、以前は表示専用）を、隣り合う2要素の
// 境界をドラッグして配分し直せるようにする...（AskUserQuestionでユーザーが選択）。

// After（「なぜドラッグ方式か」という技術的判断だけ残し、いつ・どう頼まれたかは削除）
// 境界を1つ動かすと、その両隣の2軸間でだけ重みが移動する（他の軸・合計自体は変わらない）。
```

## 適用範囲・実行タイミング

- **新規に書く/変更するコメントは、このルール確定と同時に即座に従う**（既存コードの
  一掃を待たない）。
- **既存コードに残る経緯コメントの一掃**は規模が大きい（2026-09-03時点で2,844件超・
  373ファイル）ため、一括では行わず[T567](tasks/T567.md)としてモジュール単位（過去の
  ゼロベース網羅レビュー[T425](tasks/T425.md)/[T426](tasks/T426.md)と同じ分割方針）で
  計画的に実施する。
- 判定基準2前半（設計書との重複確認）を機械的に行うのは難しい（文面が完全一致するとは
  限らない）ため、実施時は必ず対象ファイルが属するモジュールの`docs/modules/*.md`を
  先に読んでから人が読み比べる。CLAUDE.mdの既存ルール（「既存モジュールへの修正・追加に
  着手する際は、対象となるdocs/modules/*.mdを必ず先に精読」）と同じ運用。

## 機械的な強制（[T570](tasks/T570.md)）

自己申告・レビューでの見直しだけでは新規の経緯コメントの混入を防ぎきれないため、
`scripts/review_checks.py docs`の`NARRATIVE_PATTERN`（docs/modules向けの禁止パターンと
同一定義）をbackend/app・frontend/srcのコメント行にも適用し、以下の2箇所で機械的に
ブロックする。既存分（T567完了まで残る大量の残存分）は対象にせず、**新規に追加された
行のみ**を対象にする（フルスキャンでは参考件数として表示するのみで違反扱いにしない）。

- **ローカルのpre-commitフック**（`scripts/pre-commit.sh`→`pre-commit-docs-consistency.sh`
  →`review_checks.py docs --staged`）。`.git/hooks/pre-commit`はgit管理外のため、
  `.claude/settings.json`のSessionStartフックがセッション開始のたびに自動インストールする
  （手動インストールを前提にしない）。
- **CI**（`.github/workflows/docs-consistency.yml`、`review_checks.py docs --since <直前SHA>`）。
  ローカルフックは新しいセッション・コンテナで欠落しうる（インストール漏れ・意図的なスキップ等）
  ため、常に走る安全網として独立に持つ。ci.yml本体はdocs/\*\*・\*\*/*.mdの変更でCIを
  スキップする設計（無償枠対策）のため、docsのみの変更でも走るよう別ワークフローにしてある。
